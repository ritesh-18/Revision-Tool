## 13.1 Concept Explanation

An inference system is the software that runs a trained model and serves predictions to clients. For LLMs, this is not "load model, call forward, return output" — that approach hits a wall above a single user. Production inference systems handle batching, KV cache management, parallelism, scheduling, and streaming, often producing 10–100× more throughput than naive serving.

This chapter goes deep on the systems that make modern LLM inference economically viable: vLLM, TGI, Triton, TensorRT-LLM, llama.cpp, SGLang, Ollama. Understanding them lets you choose, deploy, and operate inference clusters with confidence.

## 13.2 The Inference Workload Has Two Phases

LLM inference has fundamentally different characteristics in two phases:

**Prefill phase.** Processing the prompt (input tokens). All tokens are known up front, so they can be processed in parallel. Compute-bound. GPU FLOPs are the bottleneck.

**Decode phase.** Generating output tokens one at a time. Each token requires reading all model weights to produce the next prediction. Memory-bandwidth-bound. HBM throughput is the bottleneck.

A system optimized for one phase is suboptimal for the other. Modern inference servers schedule prefill and decode together so the GPU is always busy doing whatever it can do best.

## 13.2a The Two Phases in Numbers 🔧

The two-phase split above explains almost every number you will see on an inference dashboard. This section works through the arithmetic and the metrics that follow from it.

### Why decode is memory-bound: a back-of-envelope 🔧

**Problem.** A 70B model on two H100s produces only about 20 to 40 tokens per second for a single user, though the GPUs can do roughly a petaFLOP each.

**Why it happens.** At batch size 1, each decode step must read every weight from HBM once to produce one token per sequence. A matrix-vector product does about 2 FLOPs per weight read. The GPU can do several hundred FLOPs in the time it takes to read one byte, so it sits idle waiting for memory. Prefill processes thousands of tokens per weight read, which is why it keeps the compute units busy.

**Mechanism.** Compare the time to read the weights with the time to do the math. Whichever is larger sets the speed.

```python
# Rough roofline for one decode step. Ignores KV-cache reads and overheads.
params = 70e9
bytes_per_param = 2          # FP16/BF16
hbm_bw = 3.35e12 * 2         # bytes/s, two H100 SXM with tensor parallelism
flops_peak = 989e12 * 2      # dense BF16 FLOP/s, two GPUs

def step_time(batch: int) -> tuple[float, float]:
    t_mem = params * bytes_per_param / hbm_bw        # weights read once per step
    t_compute = 2 * params * batch / flops_peak      # 2 FLOPs per param per token
    return t_mem, t_compute

for b in (1, 16, 64, 256):
    t_mem, t_comp = step_time(b)
    t = max(t_mem, t_comp)
    print(f"batch {b:>3}: {1/t:6.1f} steps/s, {b/t:8.0f} tok/s total, "
          f"{'memory' if t_mem > t_comp else 'compute'}-bound")
# batch   1:   47.9 steps/s,       48 tok/s total, memory-bound
# batch  16:   47.9 steps/s,      766 tok/s total, memory-bound
# batch  64:   47.9 steps/s,     3064 tok/s total, memory-bound
# batch 256:   47.9 steps/s,    12262 tok/s total, memory-bound
# Same step time, 256x the tokens: batching is nearly free until batch ~ 300,
# where compute time catches up with weight-read time.
```

**Edge cases.** The ceiling here is optimistic: real kernels reach maybe 60 to 80 percent of peak bandwidth, and every step also reads the KV cache, which grows with context length and batch size. At long contexts, KV reads, not weight reads, dominate decode time. That is why KV-cache size (section 13.12a) and quantization (section 13.25a) matter so much.

### TTFT, TPOT, ITL and end-to-end latency 🔧

**Problem.** "The model is slow" can mean the first word takes too long or the words come out too slowly. They have different causes and different fixes.

**Mechanism.** Use four standard metrics:

| Metric | Definition | Driven by |
|---|---|---|
| TTFT (time to first token) | Request sent to first token received | Queueing plus prefill of the prompt |
| ITL (inter-token latency) | Gap between two consecutive tokens | Decode step time, batch size, prefill interference |
| TPOT (time per output token) | Average of ITL over one request, excluding the first token | Same as ITL |
| E2E latency | Request sent to last token | `TTFT + TPOT * (output_tokens - 1)` |

TTFT is what users notice in chat and voice. TPOT matters once the output is longer than people can read (about 5 to 10 tokens per second is reading speed). For long outputs, E2E is dominated by TPOT.

**Implementation.** Measure from the client side, against any OpenAI-compatible server (vLLM, SGLang, TGI), by timing streamed chunks.

```python
import time

from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://vllm:8000/v1", api_key="unused")


async def measure(prompt: str) -> dict[str, float]:
    t0 = time.perf_counter()
    first = last = 0.0
    gaps: list[float] = []
    output_tokens = 0

    stream = await client.chat.completions.create(
        model="meta-llama/Llama-3.1-8B-Instruct",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=256,
        stream=True,
        stream_options={"include_usage": True},
    )

    async for chunk in stream:
        now = time.perf_counter()
        if chunk.choices and chunk.choices[0].delta.content:
            if not first:
                first = now
            else:
                gaps.append(now - last)
            last = now
        if chunk.usage:
            output_tokens = chunk.usage.completion_tokens

    gaps.sort()
    to_ms = 1000
    return {
        "ttft_ms": (first - t0) * to_ms,
        "tpot_ms": (last - first) / (output_tokens - 1) * to_ms if output_tokens > 1 else 0.0,
        "itl_p99_ms": gaps[int(len(gaps) * 0.99)] * to_ms if gaps else 0.0,
        "e2e_ms": (last - t0) * to_ms,
    }
```

**Edge cases.** A streamed chunk can hold more than one token (servers batch small deltas, and speculative decoding emits several at once), so compute TPOT from the usage token count, not the chunk count. Report percentiles, not means: one long prefill can stall all decodes for hundreds of milliseconds and only shows up in p99 ITL.

### Measuring under load: goodput 🔧

**Problem.** A benchmark at one request at a time shows great latency. In production, latency falls apart at 30 requests per second.

**Why it happens.** Latency depends on load. Batching trades per-request latency for throughput, so a single-user number says nothing about the operating point.

**Mechanism.** Sweep the request rate and record TTFT and TPOT percentiles at each step. Define **goodput** as the highest request rate at which your SLO still holds (for example, p95 TTFT under 500 ms and p95 TPOT under 50 ms). That is the number to size clusters with. vLLM ships a load generator for this:

```bash
vllm bench serve \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random --random-input-len 1500 --random-output-len 250 \
  --request-rate 20 --num-prompts 1000
# Repeat for several --request-rate values and plot p95 TTFT and TPOT against rate.
```

**Edge cases.** Use input and output lengths drawn from your real traffic, because random-length synthetic loads can be off by 2 times in either direction. Disable or account for prefix caching in benchmarks, since repeated synthetic prompts can hit the cache and look unrealistically fast.

## 13.3 vLLM — The Modern Standard

vLLM, from UC Berkeley, is the most widely adopted open-source LLM inference server. Its key innovation is **PagedAttention**: managing KV cache as virtual memory pages rather than contiguous blocks. This eliminates fragmentation, allows much higher batch sizes, and dramatically improves throughput.

Other features:
- Continuous batching (also called in-flight batching).
- Tensor parallelism for multi-GPU inference.
- Speculative decoding.
- Prefix caching for repeated prompts.
- Compatibility with Hugging Face model formats.
- Production-grade OpenAI-compatible API.

vLLM is the default starting point for self-hosted open-source models in production today.

**🔧 Serving a model with vLLM.** The features above map onto a handful of flags. Each one is a decision about how GPU memory and the per-step token budget are split.

```bash
# --tensor-parallel-size     shard weights across 4 GPUs (section 13.13)
# --max-model-len            longest prompt plus output you accept
# --gpu-memory-utilization   share of GPU memory vLLM may use. The rest is headroom
# --max-num-seqs             cap on concurrent sequences in a batch
# --max-num-batched-tokens   per-step token budget (section 13.11a)
# --kv-cache-dtype fp8       halve KV memory (section 13.25a)
# --enable-prefix-caching    reuse KV for shared prefixes (section 13.12a)
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 128 \
  --max-num-batched-tokens 8192 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching
```

After loading the weights, vLLM gives the rest of the allowed memory to the KV cache and logs how many tokens fit, as a line similar to "GPU KV cache size: N tokens". That number, divided by your typical context length, is your real concurrency ceiling. For offline batch jobs, skip the server and use the Python engine directly:

```python
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct", gpu_memory_utilization=0.9)
params = SamplingParams(temperature=0.2, max_tokens=256)
prompts = [f"Summarize ticket {i}: ..." for i in range(10_000)]
for out in llm.generate(prompts, params):  # vLLM batches and schedules internally
    print(out.outputs[0].text[:80])
```

## 13.4 TGI — Hugging Face Text Generation Inference

TGI is Hugging Face's inference server. Strengths: tight integration with Hugging Face Hub, broad model support, production-grade with built-in tracing and metrics. Slightly behind vLLM on raw throughput in many benchmarks but easier integration in HF-centric ecosystems.

TGI supports streaming, tensor parallelism, quantization, watermarking, and a clean Rust core. A solid choice when your organization is already on the Hugging Face ecosystem.

## 13.5 TensorRT-LLM — NVIDIA's High-Performance Path

TensorRT-LLM is NVIDIA's library for compiling LLMs into highly optimized TensorRT engines. The result is the fastest inference on NVIDIA hardware, period. Cost: build complexity, version sensitivity, and lock-in to NVIDIA's stack.

When to use: production inference on NVIDIA hardware where every millisecond and every dollar matters, and the engineering team can absorb the build complexity. Often used inside Triton Inference Server.

## 13.6 Triton Inference Server

Triton is NVIDIA's general-purpose inference server. It serves any model in any framework (PyTorch, TensorFlow, ONNX, TensorRT-LLM, vLLM as a backend) behind a unified API. Strong scheduling, dynamic batching, model ensembles, multi-GPU.

Triton is the right answer when you serve many different models, or when you want enterprise-grade orchestration plus deep NVIDIA optimization. It is more complex than vLLM but more general.

## 13.7 llama.cpp

llama.cpp is the open-source C++ project that runs LLMs efficiently on CPUs and consumer GPUs with aggressive quantization. It is what makes running 70B models on a MacBook possible.

Strengths: minimal dependencies, runs anywhere, GGUF quantization formats, broad hardware support (CUDA, Metal, ROCm, Vulkan, CPU).

Limits: not designed for high-throughput multi-user serving. Use for local development, on-device inference, or low-traffic deployments.

## 13.8 SGLang

SGLang is a newer inference engine focused on structured generation, complex prompting patterns, and high throughput. Strong at workloads with branching, JSON-constrained outputs, and prefix sharing across many requests. Used by teams running heavily structured agent workloads.

## 13.8a Structured-Output Engines ➕

SGLang's strength with JSON-constrained output comes from a component every modern server now has: a grammar engine inside the decoding loop. This section covers how it works on the serving side. For the prompt and schema side, see [Prompt Engineering](/docs/genai-handbook/12-prompt-engineering) section 12.6a.

### Grammar-constrained decoding inside the server ➕

**Problem.** A self-hosted model must return JSON matching a schema, every time, for an agent that parses it.

**Why it happens.** Sampling can pick any token in the vocabulary (often more than 100,000 entries). Without a constraint, a small chance of a stray token per step adds up over hundreds of steps.

**Mechanism.** The engine compiles the schema (or a regex, or a context-free grammar) into an automaton. At each decode step it computes a bitmask over the vocabulary of the tokens allowed in the current automaton state, applies it to the logits, and then samples. The hard part is speed. A naive check of every vocabulary token against the grammar at every step would cost more than the forward pass itself. XGrammar (Dong et al., 2024) splits tokens into those whose validity can be decided ahead of time and a small set that needs checking at runtime, precomputes the first group, and overlaps the mask computation with the GPU forward pass. That brings the overhead close to zero for typical JSON schemas. vLLM supports XGrammar and guidance (llguidance) backends, and by default (`auto`) picks one per request.

### Using it from vLLM ➕

**Mechanism.** vLLM's OpenAI-compatible server accepts the standard `response_format` with a JSON schema. Other constraint types (choice lists, regex, grammar) go in a `structured_outputs` field. The older `guided_json` style parameters are deprecated.

```python
from openai import OpenAI
from pydantic import BaseModel

class Ticket(BaseModel):
    category: str
    severity: int
    summary: str

client = OpenAI(base_url="http://vllm:8000/v1", api_key="unused")

# JSON Schema, via the standard OpenAI field
r = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "Classify: checkout page crashes on submit"}],
    response_format={
        "type": "json_schema",
        "json_schema": {"name": "ticket", "schema": Ticket.model_json_schema()},
    },
    max_tokens=300,
)
ticket = Ticket.model_validate_json(r.choices[0].message.content)

# A closed set of answers, via vLLM's own field
r2 = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "Is this review positive or negative? 'Arrived broken.'"}],
    extra_body={"structured_outputs": {"choice": ["positive", "negative"]}},
)
```

### Performance and failure modes ➕

**Problem.** After turning on structured outputs, p99 latency spikes for some requests, and some outputs come back cut off.

**Why it happens and what to do.**
- **Grammar compilation.** A new schema has to be compiled before the first token. Large or deeply nested schemas can take noticeable time. Engines cache compiled grammars, so reuse a fixed set of schemas instead of building a new one per request.
- **Truncation.** The mask guarantees that each prefix is valid, not that the output finishes. If `max_tokens` runs out inside a string, the JSON is incomplete. Check `finish_reason` (it is `length` in that case) before parsing.
- **Degenerate loops.** If the schema allows unlimited whitespace or open-ended strings, a model can keep emitting spaces or repeating text inside a field until `max_tokens`. Engines can be set to disallow free whitespace. Set `maxLength` on strings where your engine supports it.
- **Unsupported features.** Each backend supports a different subset of JSON Schema. Unsupported keywords can cause the request to fail or a fallback to another backend. Test your actual schemas against your vLLM version.
- **Quality.** A constraint that forces a format the model rarely saw in training (for example an unusual field order) can lower accuracy even though the output parses. Evaluate quality with and without the constraint.

## 13.11 Continuous Batching

Naïve batching gathers a fixed number of requests, processes them together, returns all results. This wastes capacity when individual requests finish at different times.

Continuous batching (in-flight batching) constantly admits new requests and evicts completed ones at every step. The result: GPU stays full, latency stays low, throughput climbs. Every modern inference server does this.

## 13.11a Chunked Prefill and Prefill/Decode Disaggregation ➕

Continuous batching mixes requests that are in different phases into one step. That creates a new problem, interference between prefill and decode, and the two main fixes are covered here.

### Prefill-decode interference ➕

**Problem.** Fifty users are streaming answers smoothly. A new request arrives with a 30,000-token prompt, and every stream freezes for close to a second.

**Why it happens.** In one batched step, the GPU runs the new prompt's prefill together with everyone's decode. The step lasts as long as its slowest part. Prefilling 30,000 tokens is a large compute job, so every decoding user waits for it, and their inter-token latency jumps.

**Mechanism.** Two fixes. Chunked prefill splits long prompts into pieces so no single step gets too big. Disaggregation runs prefill and decode on different GPUs so they cannot interfere at all.

### Chunked prefill ➕

**Mechanism.** Each scheduler step has a token budget (`max_num_batched_tokens` in vLLM). Decoding sequences are scheduled first (one token each), and the rest of the budget goes to prefill, taking at most one chunk of each waiting prompt. A 30,000-token prompt is then prefilled over several steps, while decodes keep moving. Sarathi-Serve (Agrawal et al., 2024) introduced this approach, and vLLM V1 enables it by default.

```python
from collections import deque
from dataclasses import dataclass

@dataclass
class Req:
    rid: str
    prompt_left: int        # prompt tokens not yet prefilled
    decoding: bool = False

def schedule_step(running: list[Req], waiting: deque[Req], budget: int = 2048) -> list[tuple[str, int]]:
    """Return (request id, tokens this step). Decode first, then prefill chunks."""
    plan = []
    for r in running:                       # 1 token per decoding sequence
        if r.decoding and budget > 0:
            plan.append((r.rid, 1)); budget -= 1
    for r in list(running) + list(waiting): # spend what is left on prefill chunks
        if budget == 0:
            break
        if not r.decoding and r.prompt_left > 0:
            chunk = min(r.prompt_left, budget)
            plan.append((r.rid, chunk)); budget -= chunk
            r.prompt_left -= chunk
            if r.prompt_left == 0:
                r.decoding = True           # first token is produced at the end of this step
            if r in waiting:
                waiting.remove(r); running.append(r)
    return plan
```

**Trade-off.** The budget sets the balance. A small budget (about 2,048) keeps ITL smooth but makes long prompts take more steps, so their TTFT rises. A large budget (8,192 or more) improves TTFT and overall throughput but lets prefill chunks slow decodes more. The vLLM docs give exactly this advice. Tune it against your SLO with the goodput sweep from section 13.2a.

**Edge cases.** Chunking adds a small cost, because each chunk re-reads the KV cache of the chunks before it. Very small budgets waste GPU time. Also, a prompt prefilled over many steps holds its KV blocks for the whole time, which lowers how many other requests fit.

### Disaggregated prefill and decode ➕

**Problem.** Even with chunking, a cluster cannot meet a strict TTFT target and a strict ITL target at once for a mixed workload.

**Why it happens.** The two phases want different things. Prefill wants compute and large batches of tokens. Decode wants memory bandwidth, large KV capacity and small steps. One GPU pool tuned for both is a compromise.

**Mechanism.** Run separate prefill workers and decode workers. A prefill worker computes the prompt's KV cache, sends it over a fast interconnect (NVLink, InfiniBand or RDMA) to a decode worker, and the decode worker streams the tokens. Each pool is sized and parallelized for its own phase. DistServe (Zhong et al., 2024) and Splitwise (Patel et al., 2024) showed large gains in goodput under tight SLOs. vLLM has disaggregated prefill support through KV-transfer connectors, and orchestration layers such as NVIDIA Dynamo and llm-d build on this idea. Check the current status in your version's docs, because these components move quickly.

**When it is worth it.** Disaggregation pays off at scale with long prompts and strict latency targets (RAG with large contexts, agents with long tool histories). For a single node or modest traffic, the cost of moving KV caches and running two pools usually outweighs the benefit. Chunked prefill on a unified pool is the right default.

## 13.12 KV Cache Management

The KV cache (Chapter 4) holds per-user state. Managing it well is the difference between 10 and 100 concurrent users on the same GPU.

PagedAttention (vLLM) treats KV cache as fixed-size blocks managed like virtual memory pages. Requests share the page table. Fragmentation drops, packing improves, throughput rises.

Prefix caching detects when multiple requests share a common prefix (the system prompt, a shared retrieval context) and reuses the KV computation for that prefix. Throughput gain depends on prefix overlap; for chatbots with stable system prompts, the gain is large.

## 13.12a KV-Cache Sizing and PagedAttention in Depth 🔧

The paragraphs above say what PagedAttention and prefix caching do. This section adds the numbers behind KV-cache memory and the mechanisms inside both features.

### KV-cache sizing maths 🔧

**Problem.** You need to know how many concurrent users at a given context length fit on your GPUs before you buy them, not after.

**Why it happens.** For every token in every active sequence, every layer stores one key vector and one value vector for each KV head. That memory grows linearly with both context length and concurrency, and at long contexts it is larger than the weights.

**Mechanism.** The formula, in bytes per token:

```text
kv_bytes_per_token = 2 (K and V) x num_layers x num_kv_heads x head_dim x bytes_per_element
total_kv_bytes     = kv_bytes_per_token x context_tokens x concurrent_sequences
```

```python
def kv_bytes_per_token(layers: int, kv_heads: int, head_dim: int, bytes_per_el: float) -> float:
    return 2 * layers * kv_heads * head_dim * bytes_per_el

GiB = 1024**3

# Llama 3.1 70B: 80 layers, 64 query heads but only 8 KV heads (GQA), head_dim 128
per_tok = kv_bytes_per_token(80, 8, 128, 2)          # FP16 KV
print(per_tok / 1024, "KiB per token")                 # 320.0 KiB
per_seq = per_tok * 8192                               # 8K context
print(per_seq / GiB, "GiB per 8K sequence")            # 2.5 GiB
print(per_seq * 64 / GiB, "GiB for 64 users at 8K")    # 160 GiB

weights = 70e9 * 2 / GiB                               # FP16 weights, about 130 GiB
print("total, before activations and overhead:", round(weights + per_seq * 64 / GiB), "GiB")  # about 290 GiB
```

This answers hands-on exercise 1 for a Llama-3.1-70B-shaped model: about 130 GiB of weights plus 160 GiB of KV cache, so roughly 290 GiB before activation memory and runtime overhead. Four 80 GB GPUs (about 298 GiB in total) is too tight in practice. Eight 80 GB GPUs, or four 141 GB GPUs, fit with headroom.

**Edge cases.** Sequences rarely all sit at full context at once, so real concurrency is usually higher than this worst-case figure. That is exactly what PagedAttention exploits. Plan for the worst case anyway if your workload has long-context bursts, or set admission control that queues requests instead of preempting.

### How GQA and a smaller KV dtype shrink the cache 🔧

**Problem.** The same calculation for an older model design gives an impossible number.

**Why it happens.** Multi-head attention (MHA) keeps one KV head per query head. Grouped-query attention (GQA, Ainslie et al., 2023) shares each KV head across a group of query heads. Multi-query attention (MQA) shares a single KV head across all of them.

**Mechanism.** The KV head count appears directly in the formula, and so does the bytes per element:

```python
for name, kv_heads, dtype_bytes in [("MHA, FP16", 64, 2), ("GQA-8, FP16", 8, 2), ("GQA-8, FP8 KV", 8, 1)]:
    gib = kv_bytes_per_token(80, kv_heads, 128, dtype_bytes) * 8192 * 64 / GiB
    print(f"{name:14s} {gib:7.0f} GiB for 64 users at 8K")
# MHA, FP16         1280 GiB
# GQA-8, FP16        160 GiB
# GQA-8, FP8 KV       80 GiB
```

GQA is chosen when the model is trained, so you get it by picking a model that uses it (most current open models do). FP8 KV cache is a serving choice (`--kv-cache-dtype fp8` in vLLM) that halves KV memory again. Its quality cost is usually small, but check it on long-context tasks (section 13.25a). Some models use other designs, such as DeepSeek's multi-head latent attention, which compresses K and V into a smaller latent vector. Check `config.json` (`num_key_value_heads`, `head_dim`) for the model you actually serve.

### Inside PagedAttention: block tables and sharing 🔧

**Problem.** Before PagedAttention, servers reserved one contiguous KV region per request, sized for the maximum possible length. Most of it was never used.

**Why it happens.** The output length is unknown when a request starts. Reserving for the maximum wastes memory on short answers (internal fragmentation), and variable-sized contiguous regions leave unusable gaps between them (external fragmentation). The vLLM paper (Kwon et al., 2023) measured that earlier systems used only 20 to 40 percent of KV memory for actual token state.

**Mechanism.** KV memory is cut into fixed-size blocks (16 tokens per block by default in vLLM). Each sequence has a block table, like an OS page table, that maps its logical token positions to physical blocks anywhere in GPU memory. A new block is allocated only when the last one fills, so waste is limited to the unfilled part of one block per sequence (under 4 percent in the paper). The attention kernel follows the block table when it reads K and V.

```python
BLOCK = 16

class BlockManager:
    def __init__(self, num_blocks: int):
        self.free = list(range(num_blocks))
        self.ref = [0] * num_blocks                 # reference counts allow sharing
        self.tables: dict[str, list[int]] = {}

    def append_token(self, seq: str, pos: int) -> None:
        table = self.tables.setdefault(seq, [])
        if pos % BLOCK == 0:                        # previous block full: allocate one more
            if not self.free:
                raise MemoryError("preempt a sequence")   # the scheduler must free space first
            b = self.free.pop()
            self.ref[b] = 1
            table.append(b)

    def fork(self, parent: str, child: str) -> None:
        """Parallel sampling or beam search: share all blocks, copy on write later."""
        self.tables[child] = list(self.tables[parent])
        for b in self.tables[child]:
            self.ref[b] += 1

    def release(self, seq: str) -> None:
        for b in self.tables.pop(seq, []):
            self.ref[b] -= 1
            if self.ref[b] == 0:
                self.free.append(b)
```

**Edge cases.** When blocks run out, the scheduler must preempt a running sequence. vLLM V1 defaults to recomputing the preempted sequence's KV later rather than swapping it to CPU memory. Frequent preemption shows up as latency spikes and wasted compute, which is the signal that `max_num_seqs` or the memory share is set too high for your traffic.

### Prefix caching: hashing, eviction and tenant isolation 🔧

**Problem.** Ten thousand requests share a 3,000-token system prompt. Without reuse, the server prefills the same 3,000 tokens ten thousand times.

**Mechanism.** vLLM identifies each full KV block by a hash of the parent block's hash, the token IDs in the block, and extra keys (LoRA adapter, multimodal inputs, an optional cache salt). Because each hash includes its parent's, a block hash stands for the whole prefix up to that block. A new request walks its prompt block by block, and every block whose hash is already in the cache is reused instead of computed. Unused cached blocks stay in memory until space is needed, and are evicted least recently used first.

```python
import hashlib

def block_hashes(token_ids: list[int], block: int = 16, salt: str = "") -> list[str]:
    hashes, parent = [], salt                       # the salt separates tenants
    for i in range(0, len(token_ids) - len(token_ids) % block, block):   # full blocks only
        h = hashlib.sha256(f"{parent}|{token_ids[i:i + block]}".encode()).hexdigest()
        hashes.append(h)
        parent = h
    return hashes
```

**Failure modes.**
- **Layout decides the hit rate.** A single differing token early in the prompt (a timestamp, a user name) changes that block's hash and every hash after it. The prompt-layout rules in [Prompt Engineering](/docs/genai-handbook/12-prompt-engineering) section 12.19a apply to self-hosted servers exactly as to hosted APIs.
- **Cross-tenant timing leaks.** A cache hit makes TTFT measurably faster. In a shared multi-tenant server, an attacker could in principle probe whether another tenant recently sent a given prefix. vLLM accepts a per-request `cache_salt` so that different tenants never share cache entries. Use it, or separate tenants by deployment, when prompts are sensitive (see section 13.22).
- **Partial blocks are not cached.** Only full blocks are hashed, so the last partial block of a prefix is always recomputed. That is a small cost but explains why hit counts are slightly lower than you might expect.

## 13.13 Tensor Parallelism

Tensor parallelism splits each weight matrix across multiple GPUs. The matrix multiplications are split too; partial results are exchanged via NCCL all-reduce. This lets a model that does not fit in one GPU's memory be served across two or four GPUs.

Cost: inter-GPU communication during every forward pass. NVLink between GPUs makes this fast; PCIe makes it slow. The hardware matters.

Tensor parallelism is most useful for very large models (70B and up). Below that, it often hurts throughput because communication overhead dominates.

## 13.14 Pipeline Parallelism

Pipeline parallelism splits the model by layer across GPUs — GPU 0 holds layers 1-20, GPU 1 holds 21-40, etc. Each batch is split into "micro-batches" that flow through the pipeline so GPUs are not all waiting for one.

Pipeline parallelism scales further than tensor parallelism but is harder to make latency-friendly. Common at extreme scale (huge models across many nodes) and rare at single-node scale.

## 13.15 Speculative Decoding

A small "draft" model proposes several tokens, the large "target" model verifies them in parallel. When the draft agrees with the target (most of the time on easy tokens), generation speeds up by 2–5× with no quality loss.

Implementation matters: the draft model must share tokenizer with the target. Recent work uses the target model itself in a self-speculative configuration, eliminating the need for a separate draft.

## 13.15a Speculative Decoding: Verification, Speed-up and Configuration 🔧

The section above gives the idea. This section shows why verification keeps the output unchanged, how to estimate the speed-up, and when speculation backfires.

### How verification keeps the output distribution 🔧

**Problem.** If a small model writes the draft, why doesn't the output get worse?

**Why it works.** Checking k drafted tokens with the large model takes one forward pass, which costs about the same as generating one token, because decode is memory-bound (section 13.2a): reading the weights once can serve several positions. The question is only which drafted tokens to keep.

**Mechanism.** For each drafted token x, with draft probability `q(x)` and target probability `p(x)`, accept it with probability `min(1, p(x) / q(x))`. At the first rejection, sample a replacement from the normalized leftover distribution `max(0, p - q)` and discard the rest of the draft. Leviathan et al. (2023) and Chen et al. (2023) proved that this rule gives exactly the target model's distribution. With greedy decoding it reduces to "keep drafted tokens while they match the target's top choice".

```python
import numpy as np

def verify(draft_tokens, q_probs, p_probs, rng=np.random.default_rng()):
    """draft_tokens: k ints. q_probs: k x V draft distributions.
    p_probs: (k + 1) x V target distributions from ONE target forward pass."""
    out = []
    for i, x in enumerate(draft_tokens):
        if rng.random() < min(1.0, p_probs[i][x] / q_probs[i][x]):
            out.append(x)                                   # accepted
            continue
        residual = np.maximum(p_probs[i] - q_probs[i], 0)   # rejected: resample from the leftover
        out.append(rng.choice(len(residual), p=residual / residual.sum()))
        return out
    out.append(rng.choice(p_probs.shape[1], p=p_probs[-1])) # all accepted: one bonus token
    return out
```

### Expected speed-up 🔧

**Problem.** Deciding how many tokens to draft (k), and whether a given draft model is worth running at all.

**Mechanism.** If each drafted token is accepted with probability `a` (independently, as a simplification), one verification step produces on average `(1 - a^(k+1)) / (1 - a)` tokens. The cost of the step is one target pass plus k draft passes.

```python
def expected_tokens(a: float, k: int) -> float:
    return (1 - a ** (k + 1)) / (1 - a)

def speedup(a: float, k: int, draft_cost: float) -> float:
    """draft_cost: time of one draft step relative to one target step (for example 0.05)."""
    return expected_tokens(a, k) / (1 + k * draft_cost)

for a in (0.6, 0.8, 0.9):
    best = max(range(1, 9), key=lambda k: speedup(a, k, 0.05))
    print(f"a={a}: best k={best}, speed-up ~ {speedup(a, best, 0.05):.2f}x")
# a=0.6: best k=4, speed-up ~ 1.92x
# a=0.8: best k=8, speed-up ~ 3.09x
# a=0.9: best k=8, speed-up ~ 4.38x   (k capped at 8 in this search)
# Real gains are lower: verification is not free and acceptance is not independent.
```

The acceptance rate is the variable that matters. It is high for predictable text (code, structured output, quoting retrieved context) and low for creative writing at high temperature.

### Configuring it in vLLM 🔧

**Mechanism.** vLLM takes one `--speculative-config` JSON. Methods include a separate draft model, n-gram prompt lookup (no extra model: it copies spans from the prompt, good for RAG and code editing), EAGLE-style heads trained on the target's hidden states, and multi-token prediction heads for models trained with them.

```bash
# Draft model (must share the tokenizer with the target)
vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4 \
  --speculative-config '{"method": "draft_model", "model": "meta-llama/Llama-3.2-1B-Instruct", "num_speculative_tokens": 5}'

# N-gram lookup: no draft model, cheap, helps when output repeats the input
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 4, "prompt_lookup_min": 2, "prompt_lookup_max": 5}'
```

### When speculation hurts 🔧

**Problem.** After turning on speculative decoding, throughput at peak traffic goes down.

**Why it happens.** Speculation spends extra compute (draft passes, verifying tokens that are then rejected) to save memory-bandwidth time. At low load the GPU has spare compute, so the trade is good. At high load, large batches have already made decode compute-bound, so the wasted work directly displaces useful work. The vLLM docs describe speculative decoding as a tool for lowering inter-token latency at medium to low QPS.

**What to do.** Turn it on for latency-sensitive, low-to-medium-load deployments (interactive chat, voice). Benchmark at your peak request rate before enabling it on a throughput-oriented cluster. Track the acceptance rate the server reports. If it falls (for example after a prompt change or a model update), the speed-up disappears while the overhead stays. Some engines can also reduce or turn off speculation automatically as the batch grows.

## 13.16 Throughput vs Latency Tradeoff

Bigger batches = higher throughput but higher per-request latency. The optimal point depends on the workload.

- **Latency-sensitive chat.** Small batches, prioritize time-to-first-token, possibly use speculative decoding.
- **Throughput-oriented batch processing.** Large batches, accept higher per-request latency.
- **Mixed workload.** Continuous batching with priority queues. Latency-critical requests jump the queue.

## 13.16a Latency Budgets for Real-Time Voice ➕

Real-time voice agents are the most latency-sensitive end of the list above. The LLM is only one of several stages that all have to fit inside a conversational pause.

### The budget ➕

**Problem.** A voice agent answers correctly, but callers talk over it or hang up because it feels slow.

**Why it happens.** In human conversation the typical gap between turns is around 200 ms, measured across many languages (Stivers et al., 2009). Pauses much over a second feel awkward. A cascaded voice pipeline puts several stages in that gap, and each one adds latency.

**Mechanism.** Write down a budget per stage and measure against it. The figures below are a rough illustration of a well-tuned cascaded pipeline, not vendor guarantees:

| Stage | What it waits for | Rough target |
|---|---|---|
| Endpointing (VAD and turn detection) | Enough silence to decide the user has finished | 200 to 500 ms |
| STT final transcript | Streaming recognizer finalizing the last words | 100 to 300 ms |
| LLM time to first token | Queueing plus prefill | 150 to 400 ms |
| Collect first phrase | Enough tokens to speak a natural chunk | 100 to 200 ms |
| TTS time to first audio | Synthesis of the first chunk | 100 to 250 ms |
| Network and audio buffering | Transport both ways, jitter buffer | 50 to 150 ms |

Added up, this lands between about 0.7 and 1.8 seconds from the end of speech to the first audio, which is why every stage must stream and overlap with the next.

### Overlapping stages with streaming ➕

**Problem.** Waiting for the full LLM answer before starting TTS adds the whole generation time (often 2 to 5 seconds) to the response delay.

**Mechanism.** Stream LLM tokens, cut them into speakable chunks at sentence or clause boundaries, and send each chunk to TTS as soon as it is ready. The first chunk should be short so audio starts early. Later chunks can be longer for more natural prosody.

```python
import asyncio
import re
from typing import Protocol

from anthropic import AsyncAnthropic
from anthropic.types import MessageParam

client = AsyncAnthropic()

# First chunk: flush at a comma or sentence end. Later: only at sentence ends.
FIRST_CHUNK = re.compile(r"^(.{12,}?[,.!?])\s")
LATER_CHUNK = re.compile(r"^(.{40,}?[.!?])\s")


class TTS(Protocol):
    async def say(self, text: str) -> None: ...


async def speak_reply(history: list[MessageParam], tts: TTS) -> None:
    """Run as one asyncio task per turn; cancelling that task (barge-in)
    closes the LLM stream and cancels every pending TTS call."""
    buf = ""
    first = True
    async with asyncio.TaskGroup() as tg:  # a real TTS client plays these in order
        async with client.messages.stream(
            model="claude-haiku-5-5",  # small, fast model for the voice turn
            max_tokens=400,
            thinking={"type": "disabled"},  # no thinking pause before the first token
            system="You are a phone agent. Answer in short spoken sentences. No lists or markdown.",
            messages=history,
        ) as stream:
            async for text in stream.text_stream:
                buf += text
                pattern = FIRST_CHUNK if first else LATER_CHUNK
                while m := pattern.match(buf):
                    tg.create_task(tts.say(m[1]))
                    buf = buf[m.end():]
                    first = False
        if buf.strip():
            tg.create_task(tts.say(buf.strip()))
```

**Edge cases.** Abbreviations and decimals ("Dr.", "3.5") create false sentence ends, so use a small sentence splitter or a minimum chunk length as above. Many TTS services accept a streaming text input over a WebSocket and handle chunking themselves, which is simpler when available. Text for speech should avoid markdown, lists and long numbers, so say so in the system prompt.

### Endpointing and barge-in ➕

**Problem.** If the agent waits too long, it feels slow. If it jumps in too early, it cuts users off mid-sentence. When the user interrupts, the agent keeps talking.

**Why it happens.** Silence-based voice activity detection (VAD) cannot tell a thinking pause from the end of a turn. Any fixed silence threshold trades responsiveness against interruptions. On the output side, audio already queued in TTS keeps playing unless something stops it.

**Mechanism.** Combine VAD with a turn-detection model that also looks at the transcript (an unfinished phrase such as "my account number is" means the user is not done), and start the LLM speculatively on the partial transcript, discarding the result if the user keeps talking. For barge-in, run each agent turn as one asyncio task; calling `task.cancel()` the moment the caller starts speaking cancels the LLM stream, stops TTS synthesis and flushes the playback buffer.

```python
import asyncio
from typing import Any

from anthropic.types import MessageParam

_turn: asyncio.Task[None] | None = None


def on_user_speech_start() -> None:
    global _turn
    if _turn is not None:
        _turn.cancel()  # cancels the LLM request, pending TTS calls and playback
    _turn = None


async def on_user_turn_end(history: list[MessageParam], tts: Any) -> None:
    global _turn
    _turn = asyncio.create_task(speak_reply(history, tts))
    try:
        await _turn
    except asyncio.CancelledError:
        # A barge-in cancelled the turn task, which is expected. If this
        # coroutine itself is being cancelled, let the cancellation propagate.
        current = asyncio.current_task()
        if current is not None and current.cancelling():
            raise
    # Any other exception from speak_reply propagates: those are real errors.
```

**Failure modes.** After a barge-in, the history should record only what was actually spoken, not the full generated reply. Otherwise the model believes the user heard things they never heard. Echo from the agent's own audio can trigger false barge-ins, so use echo cancellation on the client.

### Serving choices for voice ➕

**Problem.** The LLM stage alone uses up the whole budget.

**Mechanism.** In a voice pipeline, TTFT is everything and long-output throughput hardly matters, so tune the serving stack for TTFT:
- Use the smallest model that passes your evals for the voice turn, and hand off hard requests to a larger model with a spoken filler ("Let me check that").
- Keep the system prompt and tool definitions stable so prefix caching (section 13.12a, hosted prompt caching in [Prompt Engineering](/docs/genai-handbook/12-prompt-engineering)) removes most of the prefill.
- Self-hosted: keep batches small, consider speculative decoding (section 13.15a), and give voice traffic its own priority class or pool so batch jobs cannot inflate its TTFT.
- Put the LLM, STT and TTS in the same region as the telephony or WebRTC edge. A cross-continent hop costs 100 ms or more each way.
- Speech-to-speech models (audio in, audio out) remove the STT and TTS hops altogether, at the cost of less control over the text and the tools. Evaluate both architectures against your latency and quality needs.

## 13.17 GPU Scheduling

Within a single GPU, the scheduler decides which requests to admit, which to preempt, which to evict from KV cache when memory is tight.

Modern schedulers consider:
- Available KV cache memory.
- Request priority (free tier vs paid tier).
- Estimated remaining tokens per request.
- Fairness across users.
- Deadline awareness (streaming chat needs first token fast; offline batch can wait).

vLLM and TensorRT-LLM both have sophisticated schedulers with knobs to tune.

## 13.21 Scaling Challenges

- **Cold starts.** Loading a 70B model into GPU memory takes minutes. Keep warm replicas.
- **Memory fragmentation.** Long-running servers fragment KV cache; periodic restarts can help.
- **Tail latency.** A few requests with very long inputs stall others. Use admission control and per-request token budgets.
- **Multi-region.** Replicating GPU clusters across regions is expensive; route latency-sensitive traffic by region.

## 13.22 Security Concerns

- Inference servers should not be exposed directly to the internet. Place behind a gateway with auth and rate limiting.
- Validate input lengths to prevent prompt-flood DoS.
- Separate tenants either by separate clusters or by careful KV cache isolation.

## 13.23 Deployment Guide

Containerize the inference server (vLLM publishes images). Deploy on Kubernetes with the NVIDIA device plugin and GPU operator. Use autoscalers that consider GPU utilization, queue depth, and per-request token budgets, not just CPU. Chapter 15 details deployment.

## 13.25a Quantization Formats and Their Quality Trade-offs 🔧

"Quantize (AWQ, GPTQ, FP8)" above is one of the biggest cost levers in self-hosting. The formats behave very differently, so this section explains what each one changes and how to check what it costs in quality.

### Why quantization speeds up decode 🔧

**Problem.** A team quantizes to save memory, then is surprised that latency also improves, but only for some workloads.

**Why it happens.** Decode is memory-bound (section 13.2a). Halving the bytes per weight halves the bytes read per step, so small-batch decode gets close to 2 times faster with 8-bit weights and close to 4 times with 4-bit weights, minus dequantization overhead. Prefill and large-batch decode are compute-bound, so weight-only quantization helps them much less. They only speed up when the matrix multiplications themselves run in lower precision (FP8 or INT8 tensor cores).

```python
GiB = 1024**3
for name, bits in [("BF16", 16), ("FP8 / INT8", 8), ("INT4 (AWQ / GPTQ)", 4.25)]:  # 4.25: group scales add ~0.25 bit
    gib = 70e9 * bits / 8 / GiB
    print(f"{name:18s} {gib:6.0f} GiB weights for a 70B model")
# BF16                  130 GiB  -> needs 2+ 80 GB GPUs
# FP8 / INT8             65 GiB  -> fits one 80 GB GPU, little room for KV cache
# INT4 (AWQ / GPTQ)      35 GiB  -> one 80 GB GPU with ~40 GiB left for KV cache
```

### Weight-only INT4: AWQ and GPTQ 🔧

**Problem.** Rounding every weight to 4 bits naively (16 levels) damages the model badly.

**Why it happens.** A few weights and channels matter much more than the rest, because they multiply large activations. Rounding errors on those dominate the output error.

**Mechanism.** Both methods use a small calibration set and quantize in groups (commonly 128 weights per group, each group with its own scale):
- **GPTQ** (Frantar et al., 2022) quantizes a layer's weights one at a time and uses second-order (Hessian) information to adjust the remaining weights so they compensate for each rounding error.
- **AWQ** (Lin et al., 2023) finds the input channels with large activations and scales them up before quantizing (folding the inverse scale elsewhere), so their weights lose less precision. It needs no backpropagation and is less prone to overfitting the calibration set.

At inference the weights stay 4-bit in memory and are expanded to 16-bit inside fused kernels (such as Marlin in vLLM) just before the multiplication. vLLM detects the format from the checkpoint:

```bash
# Pre-quantized AWQ or GPTQ checkpoints are detected from their config
vllm serve hugging-quants/Meta-Llama-3.1-70B-Instruct-AWQ-INT4 --max-model-len 16384
```

**Edge cases.** The calibration data matters: a model calibrated on generic web text can lose more on your domain (code, another language). Quantize with a calibration set that resembles your traffic, or test community checkpoints on your evals before trusting them.

### FP8 weights and activations 🔧

**Problem.** INT4 saves memory but does not speed up prefill or high-throughput batches.

**Mechanism.** FP8 (usually the E4M3 format: 4 exponent bits, 3 mantissa bits) quantizes both weights and activations, and the matrix multiplications run natively on FP8 tensor cores (Hopper, Ada and Blackwell GPUs). Memory halves and compute-bound phases speed up as well. With per-channel or per-tensor scales, quality is usually very close to BF16 for large models. vLLM can quantize a BF16 checkpoint to FP8 dynamically at load time, or load a pre-calibrated FP8 checkpoint, which is generally more accurate:

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct --quantization fp8   # dynamic, no calibration step
```

**Edge cases.** On GPUs without FP8 tensor cores (A100, A10G), FP8 checkpoints fall back to weight-only kernels and lose the compute speed-up. Newer 4-bit floating-point formats (MXFP4, NVFP4) run natively on Blackwell-class GPUs, and some open models now ship in them. Check hardware support before choosing a format.

### KV-cache quantization 🔧

**Problem.** At long contexts the KV cache, not the weights, fills the GPU (section 13.12a).

**Mechanism.** Store K and V in FP8 (`--kv-cache-dtype fp8`). That halves KV memory and KV read bandwidth, roughly doubling the number of tokens that fit. It is independent of weight quantization, so the two can be combined.

**Edge cases.** KV quantization errors build up over long sequences and show most on long-context retrieval tasks ("find the clause on page 41"). Use calibrated scales where your engine supports them, and test long-context evals specifically.

### Measuring the quality cost 🔧

**Problem.** A quantized model scores within 0.5 points on a public benchmark, then breaks JSON outputs and multi-step math in production.

**Why it happens.** Averages over broad benchmarks hide where the damage is. Quantization error tends to hurt the hard tails first: long reasoning chains, long contexts, rare languages and strict formats.

**Mechanism.** Run your own eval set on both the full-precision and the quantized model, with identical prompts and sampling, and compare per slice, using the paired methods from [Prompt Engineering](/docs/genai-handbook/12-prompt-engineering) section 12.14a.

```python
def compare(full: dict[str, bool], quant: dict[str, bool], slices: dict[str, str]):
    """full/quant: case id -> pass. slices: case id -> slice name."""
    report = {}
    for sl in set(slices.values()):
        ids = [i for i, s in slices.items() if s == sl]
        f = sum(full[i] for i in ids) / len(ids)
        q = sum(quant[i] for i in ids) / len(ids)
        report[sl] = (round(f, 3), round(q, 3), round(q - f, 3))
    return dict(sorted(report.items(), key=lambda kv: kv[1][2]))  # worst drops first

# Gate: no slice may drop more than your tolerance (for example 2 points), JSON validity must not drop at all.
```

For the GPU side of these formats (tensor-core support, memory hierarchy), see [GPU Systems](/docs/genai-handbook/14-gpu-systems). For training-time choices such as quantization-aware fine-tuning, see [Fine-tuning and Training](/docs/genai-handbook/23-finetuning-training).

- Why is decode memory-bandwidth-bound while prefill is compute-bound?
- Design an inference cluster for 10,000 QPS chat traffic.
- How would you reduce TTFT by 30%?
- ➕ What is the difference between TTFT, TPOT and ITL? **TTFT is queueing plus prefill until the first token. TPOT is the average gap per output token. ITL is each individual gap, and its p99 exposes prefill interference.**
- ➕ How much KV cache does Llama 3.1 70B need per token in FP16? **2 x 80 layers x 8 KV heads x 128 dims x 2 bytes = 320 KiB per token, so 2.5 GiB for one 8K sequence.**

- ➕ What does chunked prefill trade off? **Smaller per-step token budgets smooth ITL for decoding users, but long prompts take more steps, so their TTFT rises.**
- ➕ AWQ versus FP8: when would you pick each? **INT4 AWQ to fit a big model on fewer GPUs and speed up small-batch decode. FP8 for near-lossless quality and faster compute-bound phases on GPUs with FP8 tensor cores.**
- ➕ Where does the latency go in a cascaded voice agent? **Endpointing, STT finalization, LLM TTFT, first-phrase collection, TTS first audio and the network. Every stage must stream and overlap to stay near one second.**

3. Sketch the autoscaling policy for a vLLM cluster facing bursty chat traffic.

## 13.28 Common Mistakes

- Naïve batching at fixed sizes.
- Ignoring prefix caching for stable system prompts.
- Single-replica clusters with no warm capacity.
- Autoscaling on CPU instead of GPU and queue depth.
- Treating prefill and decode latency as the same metric.

## 13.29 Enterprise Best Practices

Standardize on an inference server per model family. Build an internal "LLM gateway" that abstracts which backend serves which request. Run quarterly performance reviews to evaluate new versions of vLLM/TGI/TensorRT. Maintain per-model latency and throughput SLAs. Plan for new hardware generations as part of cost forecasting.
