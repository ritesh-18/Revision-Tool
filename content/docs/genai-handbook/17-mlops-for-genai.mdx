## 17.1 Concept Explanation

MLOps is the discipline of operating machine learning systems reliably. For GenAI, "the model" is often a managed API or a frozen open-source artifact — but everything around it (prompts, retrieval indices, embeddings, fine-tunes, evaluations, deployments) still benefits from MLOps practice. The center of gravity shifts from "training to production" toward "prompt and pipeline to production."

Done well, MLOps lets a small team operate dozens of AI features safely. Done poorly, teams burn weeks debugging silent regressions and waiting on artifact handoffs.

## 17.2 The MLOps Layers

Every layer has tools. The good news: you do not need all of them on day one. The bad news: skipping the foundational layers (versioning, evaluation, monitoring) costs more than building them later.

## 17.3 ML Pipelines

A pipeline is a directed graph of steps that transform data and produce artifacts. For GenAI, common pipelines include:

- **Ingestion.** Pull source documents, parse, chunk, enrich, embed, index.
- **Fine-tuning.** Collect data, prepare, train, evaluate, register, deploy.
- **Evaluation.** Run a suite of prompts and inputs against a model version, score, report.
- **Drift detection.** Sample production data, compare distributions to baseline, alert.
- **Re-embedding.** When the embedding model changes, re-embed the corpus incrementally.

Pipelines are scheduled (nightly evals), event-driven (new document arrives, embed it), or manual (one-time backfill).

## 17.4 Experiment Tracking

Experiment tracking records every training, evaluation, or major prompt-change run with its inputs, outputs, metrics, and artifacts. Without tracking, you cannot reproduce yesterday's improvements; with it, you can.

For GenAI, an "experiment" might be: prompt version + model + retrieval config + eval set + scores. Each run is captured so you can compare prompt v3 against v2 a month later.

Tools: MLflow, Weights & Biases, Comet, Neptune.ai, ClearML. Many AI-specific tools (LangSmith, Phoenix, Braintrust, Langfuse) overlap with this space for prompt and LLM workflows.

## 17.5 MLflow

MLflow is the most widely adopted open-source experiment tracking system. It logs runs, parameters, metrics, and artifacts; provides a UI for comparison; and includes a model registry for versioned artifacts.

Strengths: open source, framework-agnostic, broad adoption. Weaknesses: prompt/LLM-specific features less mature than dedicated tools.

## 17.6 Kubeflow

Kubeflow is Kubernetes-native ML platform. It bundles experiment tracking (Pipelines), model serving (KServe), notebooks (Notebooks), and hyperparameter tuning (Katib). Heavy but powerful; common in large enterprises.

For GenAI, Kubeflow Pipelines is sometimes used for fine-tuning and bulk inference jobs. KServe serves traditional ML models; for LLMs, vLLM or TGI are typically preferred.

## 17.7 Airflow

Apache Airflow is the dominant workflow orchestrator in data engineering. Pipelines are DAGs of tasks written in Python. Great for batch workloads — nightly evals, ingestion, embedding refresh.

Strengths: mature, broad community, massive ecosystem of operators. Weaknesses: scheduler is a bottleneck at very high scale, real-time workflows are awkward.

## 17.8 Prefect

Prefect is a newer workflow orchestrator with a cleaner Python API and better support for dynamic, parametrized flows. Strong for GenAI pipelines that branch based on data (e.g., re-embed only changed documents).

## 17.9 Dagster

Dagster is another modern orchestrator with strong asset-based mental model — pipelines are functions that produce data assets, with dependencies inferred from the graph. Great for data + ML teams who want lineage and observability built in.

## 17.10 Comparison of Orchestrators

| Tool | Best for | Weakness |
|---|---|---|
| Airflow | Mature batch ETL, broad ecosystem | Real-time, dynamic flows |
| Prefect | Modern Python flows, dynamic | Smaller ecosystem |
| Dagster | Asset-based ML/data | Steeper learning curve |
| Kubeflow Pipelines | Kubernetes-native ML | Operational complexity |
| Temporal | Durable workflows, agents | Less data-centric |

Pick one and stick to it. Mixing orchestrators across teams becomes its own problem.

## 17.11 Feature Stores

Feature stores manage features for ML models — point-in-time correct training data and low-latency online lookups. Tools: Feast, Tecton, Hopsworks, AWS SageMaker Feature Store.

For GenAI, "features" are less central, but feature-store-like concepts apply to:
- **User profiles** for personalization.
- **Cached embeddings** for low-latency retrieval.
- **Recent activity** to ground agent context.

You may not need a full feature store. You will likely build a "context store" — a system to fetch the right context per user per request.

## 17.12 Model Registry

A model registry is the canonical store for model artifacts: weights, configs, metadata, evaluation scores, ownership, lineage.

For GenAI:
- **Fine-tuned model artifacts** live in the registry.
- **Prompt versions** can live alongside or in a separate prompt registry.
- **LoRA adapters** are small artifacts with their own versioning.

MLflow Model Registry, SageMaker Model Registry, Vertex AI Model Registry, and Weights & Biases all play in this space.

## 17.13 Model Versioning

A model version is a triple of (architecture, weights, config). For GenAI, "the model" also implicitly includes the tokenizer.

Versioning practices:
- Every artifact has an immutable version ID.
- Promotions through environments (dev → staging → prod) record the version and the approver.
- Production references a version, not a tag like "latest."
- Rollback is a config change to a prior version, not a redeploy of code.

### Versioning a model you do not host 🔧

When the model is a managed API, the "never reference latest" rule above needs one more step, because providers expose both moving aliases and fixed snapshots.

**Problem.** A provider alias (a model name without a date or version suffix) can be repointed to a newer snapshot. Your code and prompts did not change, yet behaviour did: answers get longer, JSON formatting drifts, refusals move. Nothing in your deploy history explains the regression.

**Why it happens.** An alias is a pointer owned by the provider. Your "version" is only as immutable as the thing it names. Snapshots are also retired on a published schedule, so even a pinned snapshot has an end date you must plan for.

**Mechanism.** Treat the provider's snapshot ID as one field of your own immutable model-config record, together with the decoding parameters that change behaviour. Production references your record ID, never the raw provider string.

```python title="model_configs.py"
# One immutable record per behaviour-relevant change.
from dataclasses import dataclass
from datetime import date
from typing import Final, Literal


@dataclass(frozen=True)
class ModelConfig:
    provider: Literal["anthropic", "openai", "bedrock"]
    model: str
    temperature: float
    max_output_tokens: int
    retires_on: date


MODEL_CONFIGS: Final[dict[str, ModelConfig]] = {
    "support-answer@7": ModelConfig(
        provider="anthropic",
        model="provider-snapshot-id-2026-05-01",  # a dated snapshot, never an alias
        temperature=0.2,
        max_output_tokens=800,
        retires_on=date(2027, 3, 1),  # copied from the provider's deprecation page
    ),
}

type ModelConfigId = Literal["support-answer@7"]
```

**Edge cases.**
- Some providers only offer aliases for some models. Record the observed `response.model` value returned by the API on every call (see the `gen_ai.response.model` span attribute in [19.7](/docs/genai-handbook/19-monitoring-observability#197-opentelemetry)) so you can still detect a silent swap.
- Add a CI check that fails when any `retires_on` date is less than 60 days away. Retirement migrations need a full eval cycle, not a same-day patch.

## 17.14 Prompt Versioning and Registries

Prompts are first-class artifacts in GenAI MLOps. A prompt registry stores prompt versions, their evaluation scores, owners, intended models, and deployment targets.

Tools: LangSmith, Langfuse, PromptLayer, Braintrust, plus custom solutions built on Git. Many teams start with prompts in code (versioned via Git) and graduate to a dedicated registry when the prompt count grows.

### A prompt registry in practice 🔧

The registry idea above becomes concrete once you decide what a "prompt version" contains and how production resolves one.

#### What a version must contain

**Problem.** Teams version the template text and forget everything else that changes the output. Rolling back "the prompt" then does not restore the old behaviour.

**Why it happens.** The output is a function of template, variables schema, target model config, and output schema together. Change any one and you have a different artifact.

**Mechanism.** A version is an immutable row keyed by a content hash, and environments point at versions through movable aliases (`production`, `staging`). Promotion moves the alias. Rollback moves it back.

```sql
CREATE TABLE prompt_version (
  name           text        NOT NULL,
  version        int         NOT NULL,
  template       text        NOT NULL,
  model_config   text        NOT NULL,  -- e.g. 'support-answer@7'
  output_schema  jsonb,
  content_sha256 text        NOT NULL,
  eval_run_id    text,                  -- the eval that justified promotion
  created_by     text        NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (name, version),
  UNIQUE (name, content_sha256)          -- same content cannot get two versions
);

CREATE TABLE prompt_alias (
  name        text NOT NULL,
  alias       text NOT NULL,             -- 'production', 'staging'
  version     int  NOT NULL,
  moved_by    text NOT NULL,
  moved_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (name, alias),
  FOREIGN KEY (name, version) REFERENCES prompt_version (name, version)
);
```

#### Resolving a prompt at request time

**Problem.** If every request reads the alias from the database, the registry becomes a hot dependency. If you cache forever, a rollback does not take effect.

**Mechanism.** Cache the alias lookup with a short TTL, resolve it once per request, and carry the resolved version through the whole request (including retries and agent steps) so one conversation turn never mixes two versions. Record the version on the trace.

```python
import time
from collections.abc import Awaitable, Callable
from dataclasses import dataclass

from opentelemetry import trace


@dataclass(frozen=True)
class PromptVersion:
    name: str
    version: int
    template: str
    model_config: str


TTL_SECONDS = 30.0  # rollback takes effect within 30 s
_cache: dict[str, tuple[PromptVersion, float]] = {}


async def resolve_prompt(
    name: str,
    alias: str,
    load: Callable[[str, str], Awaitable[PromptVersion]],
) -> PromptVersion:
    key = f"{name}@{alias}"
    hit = _cache.get(key)
    if hit and hit[1] > time.monotonic():
        return hit[0]
    value = await load(name, alias)  # SELECT ... JOIN prompt_alias
    _cache[key] = (value, time.monotonic() + TTL_SECONDS)
    trace.get_current_span().set_attributes({
        "gen_ai.prompt.name": value.name,
        "gen_ai.prompt.version": str(value.version),
    })
    return value
```

If you use MLflow, its prompt registry (in recent releases, under the `mlflow.genai` namespace) offers the same model: `mlflow.genai.register_prompt(...)` creates a version, `mlflow.genai.set_prompt_alias(name, alias, version)` moves an alias, and `mlflow.genai.load_prompt("prompts:/summarization-prompt@production")` resolves it.

#### Edge cases
- **Registry outage.** Keep a last-known-good copy of every production alias in the service (baked in at build time or in a local file) and fall back to it. A prompt registry should never be able to take down the product.
- **Long-running agent tasks.** A task that runs for an hour should keep the version it started with. Store the resolved version on the job record, not just in memory.
- **Variables drift.** A new version that needs a new variable breaks old callers. Validate variables against a schema at render time and fail loudly in staging.

## 17.15 Eval as CI

The single highest-leverage MLOps practice in GenAI: every PR that touches a prompt, retrieval config, or model version runs the evaluation harness automatically. PRs that regress scores fail to merge unless explicitly approved with the regression noted.

Without this, prompt and model changes degrade silently. With it, regressions are caught at PR time.

### Building the eval gate 🔧

The practice above is simple to state, but a gate that blocks merges has to cope with noisy, non-deterministic scores, so it needs a few design decisions.

#### Triggering on the right changes

**Problem.** Running a paid eval suite on every PR wastes money. Running it on none lets regressions through.

**Mechanism.** Trigger the gate only when behaviour-relevant files change: prompt templates, model configs, retrieval settings, tool definitions, the eval set itself.

```yaml
# .github/workflows/eval-gate.yml
name: eval-gate
on:
  pull_request:
    paths:
      - 'prompts/**'
      - 'src/llm/model_configs.py'
      - 'src/rag/retrieval_config.py'
      - 'src/agents/tools/**'
      - 'evals/**'
jobs:
  eval:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run python -m evals.gate --suite evals/golden/support.jsonl --baseline evals/baselines/support.json
        env:
          LLM_API_KEY: ${{ secrets.EVAL_LLM_API_KEY }} # a separate, budget-capped key
```

#### Comparing against a baseline without being fooled by noise

**Problem.** LLM outputs vary between runs, so a two-point drop on 200 cases can be noise. A naive "score must not drop" rule produces flaky failures, and people learn to override it.

**Why it happens.** Each case's score is a random variable (sampling temperature, judge variance). The mean over a few hundred cases still has a spread of a few points.

**Mechanism.** Score candidate and baseline on the same cases and look at the per-case difference (a paired comparison, which cancels case difficulty). Bootstrap a confidence interval on the mean difference. Fail when the regression is both statistically clear and larger than an agreed tolerance. Separately, hard-fail on any case tagged `critical` (safety, compliance, known past incidents).

```python title="evals/gate.py"
# Core logic; loading files and calling the model omitted.
import random
from dataclasses import dataclass, field
from statistics import fmean


@dataclass
class CaseResult:
    id: str
    score: float  # in [0, 1]
    tags: list[str] = field(default_factory=list)


def bootstrap_mean_diff_ci(diffs: list[float], iters: int = 2000) -> tuple[float, float]:
    n = len(diffs)
    means = sorted(fmean(random.choices(diffs, k=n)) for _ in range(iters))
    return means[int(iters * 0.025)], means[int(iters * 0.975)]


def decide(candidate: list[CaseResult], baseline: dict[str, float], tolerance: float = 0.02) -> dict:
    critical_failures = [c for c in candidate if "critical" in c.tags and c.score < 1]
    diffs = [c.score - baseline[c.id] for c in candidate if c.id in baseline]
    mean = fmean(diffs)
    lo, hi = bootstrap_mean_diff_ci(diffs)
    significant_regression = hi < 0 and mean < -tolerance
    return {
        "pass": not critical_failures and not significant_regression,
        "mean": mean,
        "ci": (lo, hi),
        "critical_failures": [c.id for c in critical_failures],
    }
```

#### Edge cases and failure modes
- **Stale baseline.** Regenerate the baseline from `main` after each merge (a nightly job is enough). Comparing to a months-old baseline hides gradual drift.
- **Provider drift during the run.** If the baseline was scored last week, a provider change shows up as a "regression" in your PR. Re-score the baseline in the same job when budget allows.
- **Overrides.** Allow a labelled override (for example a `eval-regression-accepted` PR label) that requires a written reason. Log it. A gate without an escape hatch gets disabled.
- **Cost.** Use a small, stratified PR suite (100 to 300 cases) and the full suite nightly, as 17.23 suggests. Put the API key behind a hard spend limit.

## 17.15a Golden Datasets and Their Maintenance ➕

Eval-as-CI is only as good as the dataset it runs on, and the chapter mentions "golden eval sets" (17.27) without saying how to build or keep one, so this section covers that.

### Composition: what goes in ➕

**Problem.** Teams write 50 cases by hand from what they imagine users ask. Scores look great and production still fails.

**Why it happens.** Hand-written cases cluster around the happy path the author already had in mind. Real traffic has a long tail of intents, phrasings, languages and broken inputs.

**Mechanism.** Build the set from stratified samples of real traffic (after redaction, see [18.15c](/docs/genai-handbook/18-data-engineering#1815c-pii-detection-and-redaction-before-embedding-)), then add targeted cases: known past failures, adversarial inputs, and "should refuse" or "should say I don't know" cases. Tag every case with its stratum so you can read scores per slice.

```json
{"id":"sup-0412","input":"How do I move my invoices to another workspace?","expected_facts":["Settings > Billing > Transfer","owner role required"],"must_not":["delete the workspace"],"tags":["billing","how-to","from-prod-2026-08"],"source":"prod-sample"}
{"id":"sup-0977","input":"What is our refund policy for the Enterprise plan in Brazil?","expected_behavior":"answer_not_in_corpus","tags":["refusal","i18n"],"source":"incident-2026-07-14"}
```

### Expected outputs that age well ➕

**Problem.** Exact reference answers break as soon as the wording style changes, so every prompt edit "fails" the suite.

**Mechanism.** Store what must be true instead of the full answer: required facts, forbidden claims, required citations, expected tool calls, or an expected behaviour class (answer, refuse, ask a clarifying question). Score with deterministic checks where you can and a calibrated judge (see [19.19](/docs/genai-handbook/19-monitoring-observability#1919-llm-as-judge-evaluation)) for the rest.

### Maintenance loop ➕

**Problem.** A golden set frozen at launch slowly stops representing traffic, and the team optimises for an outdated product.

**Mechanism.**
- Every production incident or confirmed bad answer becomes a new case before the fix merges (the regression-test habit from ordinary software).
- Each quarter, compare the tag distribution of the set with a fresh traffic sample and fill gaps.
- When the corpus changes, re-verify facts in affected cases. A case whose correct answer changed is worse than no case.
- Version the set (`support-golden@v14`) and store the set version with every eval run, so scores from different set versions are never compared directly.

### Overfitting and contamination ➕

**Problem.** After months of prompt tuning against the same 300 cases, the prompt is fitted to those cases and generalises worse.

**Mechanism.** Keep a held-out split that engineers do not look at while iterating, and run it only at release time. If the scores on the dev split and the held-out split diverge, you are overfitting. If you fine-tune, make sure no golden case (or a near-duplicate, see [18.15b](/docs/genai-handbook/18-data-engineering#1815b-near-duplicate-detection-with-minhash-)) leaks into training data.

### Edge cases ➕
- **PII.** Production-derived cases are user data (17.22). Redact before storing, restrict access, and honour deletion requests for cases traced to a user.
- **Label disagreement.** When two reviewers disagree on the expected behaviour, the case is ambiguous. Fix the case or drop it. Ambiguous cases add noise to every gate decision.

## 17.16 Continuous Evaluation

Beyond CI evals, production should run continuous evaluations:
- Sample real production traffic.
- Score with LLM-as-judge or heuristics.
- Track scores by prompt version, model version, retrieval config.
- Alert on score drops.

This catches degradations from data drift, prompt drift, model provider changes, and tool changes.

**🔧 Implementation.** A sampling worker for this (arq, with the sampling rate set per feature and the judge kept off the request path) is shown in [19.15](/docs/genai-handbook/19-monitoring-observability#1915-what-to-monitor--quality--evals), and calibrating the judge against human labels in [19.19](/docs/genai-handbook/19-monitoring-observability#1919-llm-as-judge-evaluation).

## 17.16a Online Experiments: A/B Tests and Interleaving ➕

Continuous evaluation tells you whether quality held, but deciding whether a new prompt or model is better for users needs a controlled experiment on live traffic, which the chapter does not cover.

### Why offline evals are not enough ➕

**Problem.** A candidate wins the offline suite and loses in production: users regenerate more, or tasks take more turns.

**Why it happens.** Offline scores measure what your rubric rewards. Users reward things the rubric misses (length, tone, latency, formatting in their client). Only randomized exposure separates the effect of the change from everything else that moved that week.

### Assignment and the randomization unit ➕

**Problem.** Randomizing per request means one user sees both variants within a conversation, which confuses them and contaminates conversation-level metrics.

**Mechanism.** Randomize per user (or per tenant for B2B, where users in a tenant talk to each other). Use a deterministic hash so assignment is stable without storing it, and salt it per experiment so experiments are independent.

```python
import hashlib
from typing import Literal


def assign_variant(
    experiment_id: str, unit_id: str, treatment_share: float = 0.5
) -> Literal["treatment", "control"]:
    h = hashlib.sha256(f"{experiment_id}:{unit_id}".encode()).digest()
    bucket = int.from_bytes(h[:4], "big") / 0xFFFFFFFF  # uniform in [0, 1]
    return "treatment" if bucket < treatment_share else "control"

# Log the exposure at the moment the variant actually affects the response,
# not at login, so the analysis only counts users who were exposed.
```

### Metrics, guardrails and sample size ➕

**Problem.** "Thumbs-up rate" is sparse (most users never click), so tests on it take months or are underpowered.

**Mechanism.** Pick one primary metric that is frequent and tied to value (task success, regeneration rate, accepted suggestion rate), plus guardrails that must not regress (p95 latency, cost per request, safety flag rate). Estimate sample size before launch. For a rate metric, a common rule of thumb for 5 percent significance and 80 percent power is about `16 * p * (1 - p) / delta^2` units per arm. With a 30 percent regeneration rate and a target detectable change of 2 points, that is about 16 × 0.21 / 0.0004 = 8,400 users per arm.

### Interleaving for ranking and retrieval changes ➕

**Problem.** Retrieval and reranking changes have small effects that an A/B test needs huge traffic to detect.

**Mechanism.** Interleaving shows each user one merged result list built from both rankers and credits the ranker whose items get clicked or cited. Each user acts as their own control, so it typically needs far less traffic than A/B testing for the same decision. Team-draft interleaving is the standard variant.

```python
import random
from typing import Literal, Protocol


class Ranked(Protocol):
    id: str


def team_draft[T: Ranked](a: list[T], b: list[T], k: int) -> list[tuple[T, Literal["A", "B"]]]:
    """Team-draft interleaving: rankers take turns picking their best remaining item."""
    out: list[tuple[T, Literal["A", "B"]]] = []
    used: set[str] = set()
    ia = ib = count_a = count_b = 0
    while len(out) < k:
        while ia < len(a) and a[ia].id in used:  # skip items the other team took
            ia += 1
        while ib < len(b) and b[ib].id in used:
            ib += 1
        a_left, b_left = ia < len(a), ib < len(b)
        if not a_left and not b_left:
            break
        pick_a = not b_left or (
            a_left and (count_a < count_b or (count_a == count_b and random.random() < 0.5))
        )
        if pick_a:
            item = a[ia]
            ia += 1
            count_a += 1
        else:
            item = b[ib]
            ib += 1
            count_b += 1
        out.append((item, "A" if pick_a else "B"))
        used.add(item.id)
    return out  # credit clicks or citations to the item's team, then compare per query
```

For RAG, the "click" can be which chunks the generator actually cited. Note that interleaving tells you which ranker is preferred, not how much end-to-end answer quality changed. Confirm large changes with an A/B test.

### Failure modes ➕
- **Sample ratio mismatch.** If you planned 50/50 and observe 52/48 on large numbers, assignment or logging is broken (for example, one variant times out and its exposures are lost). Run a chi-square test on exposure counts before reading any result.
- **Novelty effects.** Users try a new behaviour more at first. Run for at least one full weekly cycle.
- **Shared caches.** A semantic cache shared across variants serves control answers to treatment users. Include the variant in the cache key.
- **Peeking.** Checking significance every day and stopping at the first green result inflates false positives. Fix the duration up front, or use a sequential testing method built for repeated looks.

## 17.17 Data Drift Detection

Data drift is when production input distributions diverge from training or evaluation distributions. For LLMs, drift manifests as:
- New user intents not represented in evals.
- New languages or styles.
- New document types in retrieval corpora.
- New tool inputs an agent has not seen.

Detect drift by comparing distributions (embeddings, length, language, intent classification) across time windows. Tools: Evidently, Arize, Fiddler, WhyLabs.

## 17.18 Feedback Loops

User signals are the most valuable training data you have.

- **Thumbs up/down** ratings.
- **Edit traces** (the user accepted an answer but edited a part).
- **Regenerations** (the user disliked the first response).
- **Session length and return rate.**
- **Explicit feedback comments.**

Feed these back into:
- Evaluation set updates.
- Fine-tuning datasets (RLHF, DPO).
- Prompt iteration priorities.
- Retrieval improvements (queries that produced poor answers).

### Capturing feedback so it is usable 🔧

The list above names the signals, but they only become training or eval data if each one can be joined back to exactly what the system did.

#### Join keys

**Problem.** A thumbs-down arrives with a message ID and nothing else. Nobody can tell which prompt version, model, retrieved chunks or tool calls produced the answer, so the signal cannot be acted on.

**Mechanism.** At generation time, store a record keyed by the trace ID with the resolved prompt version, model config, retrieved chunk IDs and tool calls. Feedback events carry the same trace ID.

```sql
CREATE TABLE llm_feedback (
  id          bigserial PRIMARY KEY,
  trace_id    text        NOT NULL,      -- joins to the generation record and the trace
  tenant_id   text        NOT NULL,
  kind        text        NOT NULL CHECK (kind IN ('thumb','edit','regenerate','comment','copy')),
  value       smallint,                  -- +1 / -1 for thumbs
  edited_text text,                      -- for edit traces, redacted
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON llm_feedback (trace_id);
```

```python
# FastAPI route: the client sends back the trace ID it received with the answer.
from typing import Annotated, Literal

from arq.connections import ArqRedis
from fastapi import APIRouter, Depends
from pydantic import BaseModel
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession

router = APIRouter()


class FeedbackIn(BaseModel):
    trace_id: str
    kind: Literal["thumb", "edit", "regenerate", "comment", "copy"]
    value: Literal[1, -1] | None = None
    edited_text: str | None = None


@router.post("/feedback", status_code=204)
async def feedback(
    dto: FeedbackIn,
    user: Annotated[User, Depends(current_user)],
    db: Annotated[AsyncSession, Depends(get_session)],
    queue: Annotated[ArqRedis, Depends(get_arq)],
) -> None:
    await db.execute(
        text(
            "INSERT INTO llm_feedback (trace_id, tenant_id, kind, value, edited_text) "
            "VALUES (:trace_id, :tenant_id, :kind, :value, :edited_text)"
        ),
        {
            "trace_id": dto.trace_id,
            "tenant_id": user.tenant_id,
            "kind": dto.kind,
            "value": dto.value,
            "edited_text": redact(dto.edited_text),
        },
    )
    await db.commit()
    if dto.kind == "thumb" and dto.value == -1:
        await queue.enqueue_job("triage", trace_id=dto.trace_id)  # arq worker
```

#### Turning signals into eval cases

**Mechanism.** A triage queue shows reviewers the full trace for negative signals. Confirmed failures become golden cases (17.15a), and the reviewer writes the expected behaviour. Edits are especially valuable: the user's edited version is close to a preference pair (rejected = original, chosen = edited) for DPO-style fine-tuning (see [Chapter 23](/docs/genai-handbook/23-finetuning-training)).

#### Biases to correct for
- **Selection bias.** Users who click feedback buttons are not representative (usually a small minority of sessions). Do not read the thumbs-up ratio as a quality score without also sampling unrated traffic.
- **Implicit signals are ambiguous.** A regenerate can mean "wrong" or "show me another option". A copy can mean "useful" or "I'll fix it elsewhere". Treat implicit signals as triage priority, not as labels.
- **Feedback loops on your own outputs.** If you fine-tune on accepted outputs only, the model learns to please the users who accept, and its errors can compound. Keep human review in the loop for training data.

## 17.21 Scaling Challenges

- Eval cost grows with eval set size and frequency. Budget it.
- Embedding refresh at large scale takes days; plan incremental.
- Model artifact storage grows; tier old artifacts.
- Pipeline orchestrator load grows; shard or scale up the orchestrator.

## 17.22 Security Concerns

- Eval sets contain real user queries — treat them as PII.
- Model artifacts in registries should be access-controlled.
- Prompts can contain secrets if poorly written.
- Pipeline credentials should use workload identity, not stored keys.

## 17.23 Cost Optimization

- Run heavy evals nightly, lightweight evals per-PR.
- Sample production traffic for continuous evaluation rather than scoring everything.
- Use cheaper judge models for first-pass eval; escalate to frontier models only on contested results.

## 17.24 Interview Questions

- What does MLOps look like when the model is an API?
- How do you version a prompt?
- Walk through a fine-tuning pipeline from data to production.
- How do you detect drift in an LLM application?
- Compare Airflow, Prefect, and Dagster.
- ➕ Your eval gate fails a PR by 1.5 points on 200 cases. Is that a regression? **Not necessarily. Compare per-case scores against the baseline (paired), put a confidence interval on the mean difference, and fail only if the regression is significant and above the agreed tolerance. Critical-tagged cases hard-fail regardless.**
- ➕ How do you keep a golden dataset from going stale? **Add every confirmed production failure as a case, compare its tag distribution with fresh traffic each quarter, re-verify facts when the corpus changes, and version the set so scores are only compared within one version.**
- ➕ Why randomize an A/B test per user rather than per request? **Per-request assignment lets one conversation mix variants, which confuses users and contaminates conversation-level metrics. Hash a stable user or tenant ID with an experiment salt.**
- ➕ When would you use interleaving instead of A/B testing? **For ranking and retrieval changes, where each user can compare both rankers in one merged list. It needs much less traffic to find the preferred ranker, but does not measure the size of the end-to-end effect.**
- ➕ What does a prompt version have to include? **Template, variables schema, model config (including the pinned provider snapshot) and output schema. Anything less and a rollback does not restore behaviour.**

## 17.26 Common Mistakes

- No eval set; flying blind.
- Manual rollouts of prompt or model changes.
- Skipping experiment tracking; cannot reproduce prior wins.
- Versioning code but not prompts.
- Ignoring drift until users complain.

## 17.27 Enterprise Best Practices

Eval-as-CI from day one. Standardize on one orchestrator and one experiment tracker. Maintain golden eval sets per product area. Make prompt and model versions immutable. Tie every production version to a documented owner. Quarterly drift reviews per critical feature.
