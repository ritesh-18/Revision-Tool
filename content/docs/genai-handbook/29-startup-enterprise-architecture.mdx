## 29.1 Concept Explanation

Architecture choices for a 10-person startup differ from a 10,000-person enterprise. The same engineer in different contexts should make different decisions. This chapter contrasts the two ends of the spectrum and the path between them.

The principle: match architecture to your true constraints. A startup's true constraint is time-to-market; an enterprise's is risk and integration. Optimizing the wrong constraint is the most common architecture mistake at every scale.

## 29.2 The Startup MVP Architecture

Stage: 1-5 engineers. Goal: ship something users will actually use. Budget: tight.

<Mermaid chart={`flowchart TD
  B["Browser<br/>(Next.js on Vercel)"] --> BE["Backend<br/>(FastAPI or Next.js API routes)"]
  BE --> MS
  subgraph MS["Managed services"]
    M1["OpenAI / Anthropic / Bedrock"]
    M2["Pinecone or pgvector on managed Postgres"]
    M3["Supabase or Neon for relational"]
    M4["Upstash or managed Redis"]
    M5["Sentry for errors, PostHog for analytics"]
  end
  MS --> CF["Cloudflare for DNS, CDN, WAF"]`} />

Principles:
- Managed everything. Your time is more expensive than the cloud bill.
- Single region. Latency tradeoffs can wait.
- One model provider. Failover can wait.
- No Kubernetes. Vercel, Render, Fly.io, Railway are enough.
- Simple observability. Sentry + provider dashboards.
- Ship in weeks, not months.

What you skip without guilt: Kubernetes, service mesh, multi-cloud, fine-tuning, self-hosted inference, complex MLOps.

## 29.3 Startup at 10k Users

Stage: 5-15 engineers. Goal: reliability and unit economics.

Changes from MVP:
- Add a real LLM gateway (Portkey, LiteLLM, or homegrown) for routing and observability.
- Add semantic and prefix caching.
- Move from notebooks to a proper eval harness.
- Add real observability (LangSmith or Langfuse + Grafana).
- Begin model routing — cheap model for easy queries.
- Start cost dashboards.
- First retrospective on architecture.

What you still skip: self-hosted inference (still cheaper to buy than build at this scale), full enterprise compliance posture, multi-region.

## 29.4 Startup at 100k Users

Stage: 15-50 engineers. Goal: scale to a million.

Changes:
- Kubernetes (managed) becomes worth it.
- Self-host the highest-volume models (often a quantized small open model).
- Multi-region deployments for global users.
- SOC 2 compliance work begins.
- Dedicated platform team forms.
- Multi-provider for resilience.
- Cost optimization becomes a discipline.

## 29.4a Build vs Buy: A Decision Framework With Numbers ➕

Sections 29.2 to 29.4 say when teams *usually* move from managed to self-hosted. This section gives you a way to make that call for any component (inference, vector DB, gateway, observability, the voice stack) from your own numbers instead of from the stage you are at.

### Problem

"Build vs buy" arguments tend to compare a vendor invoice with a GPU or VM bill, and leave out the engineers needed to run the self-hosted option. That is the most common reason self-hosting projects disappoint.

### Why: the true cost of building

The total cost of ownership (TCO) of building includes:
- **Upfront engineering**: the weeks to build, harden and document it.
- **Ongoing operations**: on-call, upgrades, security patches and capacity planning, as a fraction of an engineer.
- **Infrastructure**: GPUs, VMs, storage, egress.
- **Opportunity cost**: what those engineers would otherwise ship. It is hard to price, so treat it as a tie-breaker.

The cost of buying is the vendor bill plus integration work plus the exit cost if you ever leave (see 29.14a).

### Mechanism: a break-even calculation

```ts
type Option = {
  name: string;
  upfrontEngWeeks: number;   // one-time build effort
  opsFte: number;            // ongoing engineer fraction, e.g. 0.25
  infraPerMonth: number;     // USD
  vendorPerMonth: number;    // USD, usage-based bill
};

const LOADED_FTE_PER_MONTH = 6_000; // assumption: salary + overhead, in USD. Use your own.

function tco(o: Option, months: number): number {
  const upfront = (o.upfrontEngWeeks / 4.33) * LOADED_FTE_PER_MONTH;
  const monthly = o.opsFte * LOADED_FTE_PER_MONTH + o.infraPerMonth + o.vendorPerMonth;
  return upfront + monthly * months;
}

// Example: serving a small open model ourselves vs paying an API for it.
// All prices are placeholders. Plug in current quotes.
const tokensPerMonth = 3e9;          // 3B tokens
const apiPricePerM = 0.6;            // USD per 1M tokens, blended input/output
const gpuHourly = 2.0;               // USD per GPU-hour, one mid-range GPU

const buy: Option = { name: "API", upfrontEngWeeks: 1, opsFte: 0.05, infraPerMonth: 0,
  vendorPerMonth: (tokensPerMonth / 1e6) * apiPricePerM };                     // 1,800
const build: Option = { name: "self-host vLLM", upfrontEngWeeks: 6, opsFte: 0.25,
  infraPerMonth: gpuHourly * 730 * 2, vendorPerMonth: 0 };                      // 2 GPUs for HA = 2,920

for (const o of [buy, build]) console.log(o.name, Math.round(tco(o, 12)));
// API            ~ 26,600 over 12 months
// self-host vLLM ~ 61,400 over 12 months

// Break-even volume, ignoring upfront: price * V = infra + ops
const breakEvenTokens = ((build.infraPerMonth + (build.opsFte - buy.opsFte) * LOADED_FTE_PER_MONTH) / apiPricePerM) * 1e6;
console.log((breakEvenTokens / 1e9).toFixed(1), "B tokens/month"); // about 6.9B
```

**Reading the result.** At 3 billion tokens a month, buying wins clearly. Self-hosting only breaks even on running costs at about 7 billion tokens a month, and it takes longer still to recover the 6 weeks of upfront work. 3 billion tokens a month is only about 1,150 tokens per second on average, and a small model on vLLM with continuous batching can usually serve more than that on one GPU. So the two GPUs have spare capacity, and the self-hosted cost per token falls as volume grows until you need more hardware. Check that with a load test before relying on it. That is why Chapter 25 ([cost optimization](/docs/genai-handbook/25-cost-optimization)) frames self-hosting around sustained volume and utilisation.

### Implementation: the non-cost questions

Run these after the numbers. Any single "yes" can override the cost result.

| Question | Points towards |
|---|---|
| Is this component our differentiation? | Build |
| Must data stay in our VPC or a specific region, and no vendor offers that? | Build, or a vendor's private deployment |
| Do we need it within weeks? | Buy |
| Do we have engineers who have run this before? | Build becomes realistic |
| Is the vendor market immature or consolidating? | Buy with a thin abstraction, so you can switch |
| Would leaving the vendor take months of migration? | Buy only behind an abstraction (29.14a) |

### Edge cases

- **Utilisation.** Self-hosted GPUs cost the same idle as busy. Bursty traffic with low average utilisation can make "build" several times more expensive than the calculation suggests.
- **Quality is not equal.** The comparison assumes the self-hosted model is good enough. Run your eval suite on it before doing the cost maths.
- **Hybrid is common.** Self-host the one high-volume, simple task (classification, embeddings) and buy everything else.
- **Revisit it.** API prices for a given capability have tended to fall quickly, so rerun the calculation every quarter or two.

## 29.4b From MVP to Scale-Up: The Architecture and Its Seams 🔧

Sections 29.2 to 29.4 list what changes at each stage. This section draws the 100k-user architecture and names the cheap seams to put into the MVP so that the move does not need a rewrite.

<Mermaid chart={`flowchart TD
  U["Web and mobile clients"] --> CDN["Cloudflare<br/>(CDN, WAF, rate limits)"]
  CDN --> API["API services on managed Kubernetes<br/>(multi-region)"]
  API --> Q["Queue<br/>(ingestion, long agent runs)"]
  Q --> W["Workers<br/>(chunk, embed, evals)"]
  API --> GW["LLM gateway<br/>(routing, caching, quotas, tracing)"]
  GW --> SH["Self-hosted vLLM<br/>(hottest small model)"]
  GW --> P1["Provider A"]
  GW --> P2["Provider B (failover)"]
  API --> PG["Managed Postgres<br/>(app data, pgvector or a dedicated vector DB)"]
  API --> R["Managed Redis<br/>(sessions, semantic cache)"]
  W --> PG
  GW --> OBS["Observability<br/>(Langfuse or LangSmith, Grafana)"]
  API --> OBS`} />

| Seam to add in the MVP | Cost now | What it saves later |
|---|---|---|
| All LLM calls go through one internal interface | An hour | Gateway, routing and failover become a config change (29.14a) |
| Prompts in versioned files, not inline strings | An hour | Prompt registry and A/B tests |
| Store conversation state in your own Postgres, not vendor-hosted threads | None | Changing provider without losing history |
| Log tokens, latency and model per call | A few hours | Cost dashboards and routing decisions backed by data |
| Long jobs (ingestion, agent runs) behind a queue interface | A day | Moving to workers or a workflow engine without touching the API |
| Store the embedding model name and version with every vector | Minutes | Re-indexing safely when you change embedding models |

**Edge case.** Seams are not layers. One TypeScript interface with a single implementation is a seam. A plugin framework with three abstraction layers is the over-engineering that 29.15 warns against.

## 29.7 The Path From Startup to Enterprise

Recognizable inflection points:

- **First non-engineer user.** Documentation must improve.
- **First multi-tenant customer.** Isolation becomes serious.
- **First compliance audit.** Logging and governance solidify.
- **First on-call rotation.** Operational maturity required.
- **First platform team.** Federated AI patterns emerge.
- **First international launch.** Multi-region and data residency.
- **First fine-tune in production.** MLOps grows up.

Each inflection invalidates some MVP-era choices. Plan for them, don't fight them.

## 29.8 FAANG-Level AI Architecture

At hyperscaler scale, AI infrastructure is its own product line. Distinctive patterns:

- Custom hardware accelerators (TPUs, Inferentia, Trainium).
- Internal model training at frontier scale.
- Massive RAG corpora with custom retrieval infrastructure.
- Bespoke serving frameworks (often building on or alongside open-source).
- Dedicated platform teams numbering in hundreds.
- Multi-region deployments with sub-second failover.
- Compliance posture for every major regulatory regime.
- Internal evaluation infrastructure at scale.

Most engineers will not work at this scale. The patterns at this scale inform standards everyone else inherits.

## 29.9 The Cost-Efficient Startup AI Stack

For a startup wanting maximum capability on minimum budget:

- Cloudflare for DNS, CDN, WAF — generous free tier.
- Vercel or Cloudflare Pages for frontend.
- Supabase or Neon for relational data.
- Upstash for Redis and queues.
- pgvector or Pinecone serverless for vectors.
- OpenAI/Anthropic via direct API, with model routing.
- Sentry for errors.
- PostHog for product analytics.
- GitHub Actions for CI.

Total fixed cost under $200/month. Variable cost dominated by LLM tokens. Scales to first thousand users without changes.

## 29.10 The Mid-Stage AI Stack

For a company at hundreds of thousands of users:

- AWS or GCP as primary cloud.
- Managed Kubernetes (EKS or GKE).
- Qdrant or Pinecone for vectors.
- Managed Postgres and Redis.
- LiteLLM or Portkey as LLM gateway.
- LangSmith or Langfuse for AI observability.
- Grafana + Prometheus + Loki for infra observability.
- ArgoCD for GitOps.
- Self-hosted vLLM for the hottest model.
- OpenAI/Anthropic for the rest.

Monthly cost in the tens of thousands. Reliability matters; ops discipline emerges.

## 29.11 The Enterprise AI Stack

At enterprise scale:

- Multi-region Kubernetes with service mesh.
- Hybrid managed + self-hosted models.
- Multi-cloud with primary and secondary.
- Internal AI platform team.
- Vault for secrets.
- SIEM for audit logs.
- Full OpenTelemetry coverage.
- Comprehensive eval and red-team harnesses.
- Compliance automation.

Monthly cost in the millions. Headcount in dozens or hundreds focused on platform.

## 29.12 Team Structure

Startup: full-stack engineers everywhere.

Growth: specialists emerge — frontend, backend, infra, ML.

Mid-stage: platform team forms. Product teams consume platform.

Enterprise: many platform teams (infra, MLOps, AI services, security, observability). Central architecture function. Multiple AI CoEs.

## 29.12a Team Topology for AI Features 🔧

The stages above describe *who* exists. This section covers *how the teams interact*, because most AI delivery problems are ownership problems: nobody owns the evals, or the platform team is a ticket queue.

### Problem

AI features cut across product, data, infrastructure and compliance. Without clear ownership you get one of two failures. Either every product team builds its own gateway, prompt store and eval scripts (duplication), or a central "AI team" builds every feature and becomes the bottleneck.

### Mechanism: four team types

The *Team Topologies* model (Skelton and Pais) defines four team types. They map well onto AI work:

| Team type | AI version | Owns |
|---|---|---|
| Stream-aligned | Product teams with AI engineers inside them | The feature, its prompts, its eval set, its quality metrics |
| Platform | AI platform team | Gateway, embedding service, vector DB, eval runner, cost accounting, offered self-service |
| Enabling | AI centre of excellence or guild | Coaching, patterns, reviews. Temporary help, not ownership |
| Complicated subsystem | Inference or fine-tuning specialists | Self-hosted serving, custom models, GPU fleet |

<Mermaid chart={`flowchart LR
  subgraph ST["Stream-aligned product teams"]
    A["Support assistant team"]
    B["Search team"]
    C["Voice agent team"]
  end
  PL["AI platform team<br/>(gateway, evals, vector DB, cost)"] -->|"self-service APIs"| ST
  EN["Enabling team<br/>(AI CoE)"] -.->|"coaching, reviews"| ST
  CS["Inference and fine-tuning specialists"] -->|"model endpoints"| PL`} />

### How it applies at each stage

- **Startup (under 15 engineers).** One team does all of it. The only rule that matters is that the people who ship a prompt change also own its eval.
- **Growth (15 to 50).** Form a platform team when two or more product teams have built the same thing, such as two separate LLM wrappers. Not before.
- **Enterprise.** Run the platform as a product: documentation, SLOs, a self-service portal and internal customers. An enabling team helps product teams adopt it and then steps back.

### The key rule: evals belong to the feature team

The platform team owns the eval *runner* and the dashboards. The product team owns the eval *dataset* and the thresholds, because only they know what correct output looks like for their users. When a central team owns quality for features it does not understand, evals become a box-ticking exercise.

### Common mistakes

- **A central AI team that builds every feature.** It feels fast for the first two features and then becomes a queue.
- **A platform built before demand.** See 29.15.
- **AI engineers kept out of product teams.** Prompt and retrieval changes are product changes, and they need someone in the team who understands them.
- **An enabling team that never leaves.** If the CoE still writes the prompts a year later, it has become a hidden feature team.

## 29.13 Operational Maturity

Startup: founder is on-call. Incidents are messy and personal.

Growth: rotation forms; postmortems start.

Mid-stage: SLOs documented. Runbooks built. Fire drills quarterly.

Enterprise: 24/7 follow-the-sun on-call. SREs dedicated. Reliability is a measured discipline.

## 29.14 Tradeoffs

| Approach | Win | Cost |
|---|---|---|
| Managed everything (startup) | Velocity | Future ceiling |
| Self-hosted everything | Control | Engineering time |
| Centralized platform | Consistency | Coordination overhead |
| Federated teams | Velocity | Inconsistency |
| Multi-cloud | Resilience | Complexity |
| Single cloud | Simplicity | Lock-in |

## 29.14a Vendor Lock-In Mitigation: The Model Gateway Abstraction ➕

The table above lists lock-in as the cost of a single cloud. For AI systems the stronger lock-in is usually to a *model provider*, and it builds up quietly in places other than the API call.

### Problem: where lock-in hides

1. **API shape.** Message formats, tool-calling schemas, structured output and streaming events differ between providers.
2. **Prompts tuned to one model.** A prompt optimised for one model family often loses quality on another, even when the API is identical.
3. **Vendor-hosted state.** Hosted threads, assistants, files and vector stores keep your data in a format only that vendor reads.
4. **Embeddings.** Vectors from one embedding model are meaningless to another, so switching means re-embedding the whole corpus.
5. **Cloud-native glue.** Provider-specific guardrails, eval tools and fine-tuned weights you cannot export.

### Why it matters

Prices, quality rankings and rate limits change often. If you cannot switch, you cannot take advantage of a cheaper or better model, and an outage at your provider is an outage for you. Section 30.14 makes the same point about the open vs closed trajectory.

### Mechanism: one interface, thin adapters, evals as the switch gate

```ts
// llm/types.ts — the only LLM types application code may import
export type Msg = { role: "user" | "assistant"; content: string };
export type ChatRequest = { system?: string; messages: Msg[]; maxTokens: number; model: string };
export type ChatResult = { text: string; inputTokens: number; outputTokens: number; provider: string };
export interface LlmProvider { name: string; chat(req: ChatRequest, signal?: AbortSignal): Promise<ChatResult> }
```

```ts
// llm/providers.ts — adapters hide each vendor's shape
import OpenAI from "openai";
import Anthropic from "@anthropic-ai/sdk";
import type { LlmProvider } from "./types";

const openai = new OpenAI();
const anthropic = new Anthropic();

export const openaiProvider: LlmProvider = {
  name: "openai",
  async chat(req, signal) {
    const messages = [
      ...(req.system ? [{ role: "system" as const, content: req.system }] : []),
      ...req.messages,
    ];
    const r = await openai.chat.completions.create(
      { model: req.model, max_tokens: req.maxTokens, messages }, { signal });
    return { text: r.choices[0].message.content ?? "", inputTokens: r.usage?.prompt_tokens ?? 0,
             outputTokens: r.usage?.completion_tokens ?? 0, provider: "openai" };
  },
};

export const anthropicProvider: LlmProvider = {
  name: "anthropic",
  async chat(req, signal) {
    const r = await anthropic.messages.create(
      { model: req.model, max_tokens: req.maxTokens, system: req.system, messages: req.messages }, { signal });
    const text = r.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("");
    return { text, inputTokens: r.usage.input_tokens, outputTokens: r.usage.output_tokens, provider: "anthropic" };
  },
};
```

```ts
// llm/gateway.ts — routing and failover live here, driven by config
import type { ChatRequest, ChatResult, LlmProvider } from "./types";

type Route = { provider: LlmProvider; model: string; timeoutMs: number };

export async function chatWithFailover(routes: Route[], req: Omit<ChatRequest, "model">): Promise<ChatResult> {
  let lastErr: unknown;
  for (const route of routes) {
    const ac = new AbortController();
    const timer = setTimeout(() => ac.abort(), route.timeoutMs);
    try {
      return await route.provider.chat({ ...req, model: route.model }, ac.signal);
    } catch (err) {
      lastErr = err; // log provider, model and error class, then try the next route
    } finally {
      clearTimeout(timer);
    }
  }
  throw lastErr;
}
```

Routes come from config, for example "summarise: primary model A on provider X, fallback model B on provider Y". Application code calls `chatWithFailover(routes.summarise, req)` and never imports a vendor SDK. Hosted gateways such as LiteLLM or Portkey do the same job as a service. The design principle is identical: your code depends on your interface, not on theirs.

### Implementation: the rest of the mitigation

- **Keep state in your own database.** Store conversations, files and vectors yourself, and use vendors for stateless inference.
- **Version prompts per model.** Keep `summarise.modelA.v3` and `summarise.modelB.v1` side by side. One prompt rarely works best everywhere.
- **Make the eval suite the switch gate.** A provider change is a config change plus an eval run (see the harness in [Chapter 28](/docs/genai-handbook/28-portfolio-projects)). If quality, latency and cost hold, ship it.
- **Plan embedding migrations.** Store the embedding model and version with each vector. To switch, dual-write to a new index, backfill in the background, compare retrieval recall on your eval set, then cut over.
- **Negotiate exit terms.** For enterprise contracts, confirm data export formats and deletion guarantees before signing.

### Edge cases

- **The lowest common denominator.** A strict common interface can hide useful features such as prompt caching, reasoning controls or citations. Allow typed, optional provider-specific options rather than banning them, and keep a list of where you depend on them.
- **Tool calling and structured output.** These differ the most between vendors. Define tool schemas once (for example in Zod or JSON Schema) and convert them in each adapter. Validate the model's output yourself rather than trusting either vendor's strict mode.
- **Failover changes behaviour.** A fallback model may answer differently, so a failover is not invisible. Tag responses with the provider so that evals and support can tell what happened.
- **Retries on non-idempotent tool calls.** If a call fails after a tool has already run, failing over can repeat the action. Make tools idempotent with request IDs.

## 29.15 Common Mistakes

- Premature Kubernetes adoption.
- Over-engineering for scale you do not have.
- Skipping observability "until later."
- Building a platform before customer demand justifies it.
- Treating enterprise patterns as universal.

- What is the right MVP stack for a GenAI startup?

**➕ More questions with short answers**

- **"Your API bill is $3k a month. The CTO wants to self-host to save money. What do you say?"** **Do the TCO maths including engineer time (29.4a). At that bill the operations staff alone usually cost more than the API. Cut the bill first with routing, caching and shorter prompts.**
- **"How do you avoid lock-in without building a huge abstraction?"** **One internal LLM interface with thin adapters, state kept in your own database, prompts versioned per model, and an eval suite that decides whether a switch is safe (29.14a).**
- **"Who should own the eval dataset for an AI feature?"** **The product team that ships the feature. The platform team owns the runner and dashboards (29.12a).**
- **"What would you put into an MVP so it can scale later?"** **Cheap seams: one LLM interface, versioned prompts, your own conversation store, per-call token and latency logs, and the embedding model version stored with each vector (29.4b).**
- **"When does a startup need a platform team?"** **When at least two product teams have built the same AI infrastructure and the duplication is slowing them down. Not earlier.**

## 29.19 Enterprise Best Practices

Match architecture to stage. Plan for next inflection, not current one. Document decisions so future engineers understand why. Invest in the platform team only when product teams' duplicated work justifies it. Treat reliability and cost as engineering disciplines, not afterthoughts.
