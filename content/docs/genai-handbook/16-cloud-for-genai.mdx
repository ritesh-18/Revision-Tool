## 16.1 Concept Explanation

Cloud platforms host the vast majority of GenAI infrastructure. The choice of cloud determines GPU availability, managed AI services, networking, identity, and cost. This chapter walks the major providers, the GPU-specialist secondaries, and the GenAI-specific services each offers.

There is no universally best cloud. There are tradeoffs in price, capacity, ecosystem maturity, and where your organization already lives. Picking is a strategic decision shaped as much by hiring and procurement as by technical fit.

## 16.2 AWS for GenAI

AWS is the most widely adopted cloud for GenAI workloads. Key services:

- **EC2 GPU instances.** P5 (H100), P4d (A100), G5 (A10G), G6 (L4/L40S), Inf2/Trn1 (Inferentia/Trainium).
- **SageMaker.** End-to-end ML platform: training, inference endpoints, JumpStart for pretrained models, Pipelines for orchestration.
- **Bedrock.** Managed access to multiple foundation models (Anthropic, Meta, Mistral, Cohere, Amazon Titan) with one API.
- **Lambda.** Serverless functions, useful for thin LLM proxies, glue logic.
- **OpenSearch.** Managed search with vector capabilities.
- **EKS.** Managed Kubernetes for self-hosted inference.
- **S3.** Object storage for model weights, training data, RAG corpora.
- **CloudFront, API Gateway.** Edge and API.

Strengths: largest service catalog, deepest enterprise integrations, broadest region coverage. Weaknesses: GPU capacity is tight, pricing can be opaque, egress fees punish multi-cloud architectures.

**🔧 The AWS GPU instance families as of 2026.** The family list above is slightly out of date: G6 carries the L4, and the L40S lives in a separate G6e family. A current map:

| Family | Accelerator | Typical GenAI use |
|---|---|---|
| P6-B200, P6-B300 | 8 × NVIDIA Blackwell (B200) or Blackwell Ultra (B300) | Frontier training, largest-model serving |
| P6e-GB200 | Grace Blackwell, up to 72 GPUs per UltraServer | Very large training and serving at rack scale |
| P5 | up to 8 × H100 | Training, 70B+ serving with NVLink |
| P5e, P5en | up to 8 × H200 (141 GB each) | 70B+ serving with larger KV pools |
| P4d | up to 8 × A100 | Older training and serving fleets |
| G6e | up to 8 × L40S (48 GB) | 7B-34B serving, embeddings, rerankers |
| G6 | up to 8 × L4 (24 GB) | Small models, embeddings, cost-sensitive serving |
| G5 | up to 8 × A10G (24 GB) | Small models on older generation |
| Inf2, Trn2 | Inferentia2, Trainium2 chips | Cost-optimised inference and training via the Neuron SDK |

The GPUs inside one family come on several instance sizes. A `g6e.xlarge` has one L40S, while a `g6e.48xlarge` has eight, so choose the size by the GPU count that your tensor-parallel layout needs ([GPU Systems, 14.6.1](/docs/genai-handbook/14-gpu-systems)).

## 16.3 Azure for GenAI

Azure has the tightest integration with OpenAI (Microsoft's exclusive cloud partner for OpenAI's hosted models). Key services:

- **Azure OpenAI Service.** Hosted OpenAI models with Azure's compliance posture, regional deployments, and private networking.
- **Azure ML.** End-to-end ML platform.
- **AI Foundry / AI Studio.** Higher-level model and agent development environment.
- **Azure Kubernetes Service (AKS).** Managed Kubernetes.
- **Cognitive Search.** Search service with vector capabilities.
- **NDv5 / ND H100 v5 / ND H200 v5.** GPU VM families.
- **Functions.** Serverless.

Strengths: OpenAI integration, strong enterprise sales motion, Microsoft 365 and Active Directory integration. Weaknesses: smaller GPU footprint than AWS in some regions, capacity constraints, complex pricing.

## 16.4 Google Cloud (GCP) for GenAI

GCP's distinctive offering is TPUs alongside GPUs. Key services:

- **Vertex AI.** Unified ML platform with model garden, training, online and batch inference.
- **Gemini API.** Google's frontier models, hosted on Vertex.
- **TPU v5e / v5p.** Tensor Processing Units for training and inference.
- **GPU VMs.** A3 / G2 / A2 families.
- **GKE.** Managed Kubernetes, widely considered the most polished of the big three.
- **Vector Search.** Managed vector database.
- **BigQuery.** Analytical database with embedded vector search and ML integration.

Strengths: best Kubernetes, TPU alternative to GPU monoculture, strong networking, integrated data + AI stack. Weaknesses: smaller GPU pool than AWS, less enterprise sales heritage.

## 16.5 Oracle Cloud (OCI)

Oracle has emerged as an aggressive GenAI player. Key advantages:

- **GPU pricing** often lower than hyperscalers.
- **Free egress** in many cases — significant for AI workloads with heavy data movement.
- **OCI Generative AI Service.** Managed model access.
- **Strong RDMA networking** for training clusters.
- **Reserved GPU capacity** that is sometimes more available than AWS/Azure.

Many AI labs and startups run training on OCI for cost reasons. Production inference often stays on AWS/Azure/GCP for ecosystem fit.

## 16.6 GPU-Specialist Clouds

A new class of GPU-specialist providers has emerged. They are not hyperscalers — fewer services, fewer regions — but compete aggressively on GPU price and availability.

- **RunPod** — on-demand and spot GPUs, simple ergonomics, popular with indie developers.
- **Lambda Labs** — AI-focused, simple billing, often-available GPUs.
- **CoreWeave** — large-scale GPU specialist with enterprise contracts.
- **Crusoe** — GPU clouds powered by stranded energy, competitive pricing.
- **FluidStack** — aggregated GPU capacity from multiple sources.
- **Together AI, Fireworks, Replicate** — model-serving platforms that abstract the cloud entirely.
- **Modal** — serverless GPU platform with fast cold starts.

For self-hosted inference, secondary GPU clouds can save 30-60% versus hyperscalers. Cost: less enterprise tooling, capacity volatility, fewer integrated services.

## 16.8 GPU Services and Instance Selection

A right-sizing framework:

- **Small models (1-13B).** Single A10G, L40S, or RTX 4090 (consumer/dev).
- **Medium models (30B).** Single A100 80GB or H100, or 2x A10G with tensor parallelism.
- **Large models (70B).** H100 single GPU at INT4, or 2-4 GPUs at FP16, or 8x A100.
- **Frontier models (400B+).** Multi-node H100/H200 clusters with NVLink and InfiniBand.

Match GPU to traffic profile, not just to model size. A small model serving 10k QPS may need many A10G replicas; a large model serving 100 QPS may need one H100.

**🔧 Checking the framework with the memory equation.** The table is a starting point. Before you commit to an instance type, run the serving memory calculation from [GPU Systems, 14.4.1](/docs/genai-handbook/14-gpu-systems), with your real context length and concurrency. The KV cache often decides the GPU count, not the weights. For example, a 70B model at INT4 fits on one H100 by weights (about 35-40 GB), but with long contexts and dozens of concurrent users the remaining 35-40 GB of KV pool may hold only a handful of conversations.

### 16.8.1 Provisioning GPU node groups as code, and the quota trap 🔧

Choosing an instance type is half the job. Getting the cloud to give you that instance type is the other half, and it starts with quotas.

#### The problem

A Terraform apply for a new GPU node group succeeds, but no nodes ever appear, and the autoscaling group logs show `VcpuLimitExceeded` or "insufficient capacity". GPU instances are gated twice: by your account's **service quota** and by the provider's actual **capacity** in that zone.

#### Why it happens: quotas are counted in vCPUs

On AWS, On-Demand and Spot quotas for accelerated instances are set per instance-family group and counted in **vCPUs**, not in instances or GPUs. A `p5.48xlarge` has 192 vCPUs, so the quota "Running On-Demand P instances" must be at least 192 to run a single one, and 384 to run two. New accounts often start at 0 for P and G families. Spot has its own separate quotas. Request increases well before launch, because large increases are reviewed by hand.

#### Implementation: an EKS GPU node group in Terraform

```hcl
resource "aws_eks_node_group" "gpu_l40s" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "gpu-l40s"
  node_role_arn   = aws_iam_role.eks_node.arn
  subnet_ids      = var.private_subnet_ids

  ami_type       = "AL2023_x86_64_NVIDIA"   # EKS-optimised AMI with NVIDIA driver and container toolkit
  instance_types = ["g6e.2xlarge"]
  capacity_type  = "ON_DEMAND"
  disk_size      = 200                      # room for the multi-GB vLLM image and cached weights

  scaling_config {
    min_size     = 1
    desired_size = 2
    max_size     = 8
  }

  labels = {
    "workload" = "llm-inference"
  }

  taint {
    key    = "nvidia.com/gpu"
    value  = "true"
    effect = "NO_SCHEDULE"
  }

  lifecycle {
    ignore_changes = [scaling_config[0].desired_size]   # let the autoscaler own the count
  }
}
```

The AL2023 NVIDIA AMI provides the driver and container runtime, but you still need the NVIDIA device plugin (or the GPU Operator with its driver component turned off) so Kubernetes can see the GPUs. Bottlerocket's NVIDIA variants include the device plugin. If you use Karpenter instead of managed node groups, the same choices move into the NodePool and EC2NodeClass ([AI Deployment, 15.6.1](/docs/genai-handbook/15-ai-deployment)).

#### Edge cases and failure modes

- **Capacity, not quota.** A quota increase does not guarantee capacity. A single-type, single-zone node group for H100s can stay empty for days. Allow several subnets (zones) and, where the model allows it, several instance types, or reserve capacity (16.16b).
- **Spot quotas are separate.** A Spot NodePool can fail while On-Demand works, because the Spot vCPU quota for that family is still at its default.
- **Driver drift.** Upgrading the AMI upgrades the driver. Pin AMI release versions for GPU node groups and test new ones against your inference image's CUDA version ([AI Deployment, 15.2.1](/docs/genai-handbook/15-ai-deployment)).

## 16.9 Managed AI Services

Why use managed services like Bedrock, Vertex, or Azure OpenAI?

- **No infrastructure to manage.** No GPU pools, no scaling, no incident response on inference itself.
- **Compliance posture.** SOC2, HIPAA, FedRAMP often easier through managed services.
- **Multiple models, one API.** Bedrock and Vertex offer a unified surface across providers.
- **Regional availability.** Use providers' regional deployments to meet data residency.
- **Volume discounts.** Negotiated rates at scale.

Why not?

- **Cost at scale.** Self-hosted often wins beyond a threshold.
- **Latency.** Network hops add tens to hundreds of ms.
- **Fine-tuning constraints.** Limited compared to self-hosted.
- **Vendor lock-in.** API differences are real, even with "compatible" shims.

The hybrid pattern: managed for hardest queries, self-hosted for high-volume cheap queries.

## 16.9a Managed inference vs self-hosting: the break-even maths ➕

The "cost at scale" point above deserves numbers, because the crossover is often much further away than teams expect. [Cost Optimization, 25.12](/docs/genai-handbook/25-cost-optimization) gives rule-of-thumb volumes. This section derives the crossover from your own inputs.

### The problem

Teams compare an API's price per million tokens with "GPU price divided by a benchmark throughput", decide self-hosting is 5× cheaper, and then find the real bill is higher than the API's. The comparison left out utilisation, the minimum fleet and the people needed to run it.

### First principles: marginal cost and fixed cost

Self-hosted cost has two parts:

```text
marginal cost per 1M tokens = (GPU $/hour × GPUs per replica) / (tokens/s per replica × 3600 × utilisation) × 1e6
monthly cost                = max(min replicas, replicas needed for volume) × replica $/month + ops $/month
```

Two consequences follow:

1. **If the marginal cost is above the API price, self-hosting never wins on cost**, at any volume. Utilisation matters a lot here: a GPU that is 30% busy costs twice as much per token as one that is 60% busy.
2. **If the marginal cost is below the API price**, break-even volume is roughly `fixed monthly costs / (API price − marginal cost)`, where the fixed costs are the minimum fleet plus the people.

### Worked example

All inputs are assumptions for illustration, so replace them with your own measured throughput and current prices.

**Case A: small open model that is also sold cheaply as an API.** 8B model on one L40S-class GPU at $2.00/hour, 2,500 tokens/s per replica at 60% utilisation. Marginal cost: `2.00 / (2500 × 3600 × 0.6) × 1e6 ≈ $0.37` per million tokens. If an API sells the same model at $0.30 per million, self-hosting does not win at any volume. Cheap hosted versions of popular open models usually run on large, well-utilised fleets, and that is hard to beat.

**Case B: replacing a premium API with a self-hosted 70B model.** Assume evals show a self-hosted 70B is good enough to replace an API priced at $3.00 per million tokens for this workload. 4 × H100 per replica at $4.00 per GPU-hour, 8,000 tokens/s per replica, 60% utilisation, two replicas minimum, $15,000/month of engineering and on-call time:

| Tokens per month | API cost | Self-hosted cost | Replicas |
|---|---|---|---|
| 5 B | $15,000 | $38,360 | 2 |
| 10 B | $30,000 | $38,360 | 2 |
| 20 B | $60,000 | $38,360 | 2 |
| 40 B | $120,000 | $61,720 | 4 |
| 80 B | $240,000 | $96,760 | 7 |

Break-even is around 13 billion tokens a month (about 430 million a day). Below that, the minimum fleet and the people cost more than the API.

### Implementation

```python
# breakeven.py: compare managed API cost with a self-hosted fleet
import math

HOURS_PER_MONTH = 730

def self_hosted_monthly(tokens: float, tok_s_per_replica: float, gpus_per_replica: int,
                        gpu_hour_usd: float, utilisation: float = 0.6,
                        min_replicas: int = 2, ops_usd: float = 0.0) -> tuple[float, int]:
    capacity = tok_s_per_replica * 3600 * HOURS_PER_MONTH * utilisation
    replicas = max(min_replicas, math.ceil(tokens / capacity))
    gpu_cost = replicas * gpus_per_replica * gpu_hour_usd * HOURS_PER_MONTH
    return gpu_cost + ops_usd, replicas

def api_monthly(tokens: float, usd_per_million: float) -> float:
    return tokens / 1e6 * usd_per_million

for tokens in (5e9, 10e9, 20e9, 40e9, 80e9):
    hosted, n = self_hosted_monthly(tokens, 8000, 4, 4.0, ops_usd=15_000)
    print(f"{tokens / 1e9:>4.0f}B tokens: API ${api_monthly(tokens, 3.0):>9,.0f}"
          f"  self-hosted ${hosted:>9,.0f} ({n} replicas)")
```

### Edge cases and failure modes

- **Input and output tokens are priced and processed differently.** APIs usually charge several times more for output tokens, and GPUs process prompt tokens much faster than generated ones. Do the comparison separately for input and output, using your real ratio.
- **Throughput has to be measured on your traffic.** Benchmarks with short prompts and large batches overstate tokens per second. Measure at your latency SLO with your prompt-length distribution.
- **Peaks set fleet size, averages set the bill.** If peak traffic is 4× the average, a fleet sized for the peak runs at a quarter of its utilisation on average, and the marginal cost goes up 4×.
- **Prompt caching and batch discounts.** Managed APIs offer cached-input and batch pricing that can halve the effective price. Compare against the price you would actually pay.
- **Non-cost reasons dominate.** Data control, fine-tuned models that no API serves, or latency can justify self-hosting below break-even. Make that a deliberate decision, not an accident of the spreadsheet.

## 16.10 Networking Inside the Cloud

- **VPC (Virtual Private Cloud).** Logical network isolation.
- **Subnets.** Public (internet-facing) and private (internal).
- **NAT gateways.** Egress for private subnets. Expensive at high volume.
- **VPC Peering, Transit Gateway, Cloud Interconnect.** Connect VPCs and on-prem.
- **PrivateLink, Private Service Connect, Azure Private Link.** Access cloud services privately.
- **Direct Connect / ExpressRoute / Cloud Interconnect.** Dedicated lines from on-prem to cloud.

For AI specifically, PrivateLink-to-managed-LLM-services keeps traffic off the public internet — required for many compliance regimes.

**🔧 PrivateLink to Bedrock in Terraform.** An interface endpoint puts an elastic network interface for the Bedrock runtime API inside your private subnets. With private DNS enabled, the normal regional hostname resolves to the private IPs, so the SDK needs no change:

```hcl
resource "aws_vpc_endpoint" "bedrock_runtime" {
  vpc_id              = var.vpc_id
  service_name        = "com.amazonaws.${var.region}.bedrock-runtime"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = var.private_subnet_ids
  security_group_ids  = [aws_security_group.bedrock_endpoint.id]
  private_dns_enabled = true
}
```

Edge cases: the endpoint's security group must allow HTTPS (443) from your pods' security group or subnet CIDRs. Interface endpoints are billed per hour per zone plus per GB processed. And the endpoint covers only the runtime API: management calls such as listing models use the separate `bedrock` service endpoint.

## 16.11 IAM (Identity and Access Management)

Each cloud has its own IAM model with similar concepts:

- **Users / Service Accounts.** Identities.
- **Roles.** Sets of permissions.
- **Policies.** Permission documents attached to identities.
- **Workload Identity / IRSA.** Bind Kubernetes service accounts to cloud roles, eliminating long-lived credentials in pods.

For AI: scope permissions tightly. Models should access only what they need. Use temporary credentials. Audit logging on every model and tool action.

### 16.11.1 Least-privilege model access from a Python service on EKS 🔧

"Scope permissions tightly" has a concrete shape for model APIs: which models a service may invoke, from which pod, with credentials that expire.

#### The problem

The common shortcut is an IAM policy with `bedrock:*` on `*`, attached to the node role. Every pod on every node can then call every model, including expensive ones, in any region, and the audit trail shows only "the node" as the caller.

#### Mechanism

- **Pod-level identity.** EKS Pod Identity (or the older IRSA) binds a Kubernetes service account to an IAM role. The SDK in the pod gets short-lived credentials for that role automatically, so there are no keys in environment variables.
- **Resource-scoped actions.** Bedrock's runtime permissions are `bedrock:InvokeModel` (also used by the Converse API) and `bedrock:InvokeModelWithResponseStream` (used by ConverseStream). Both can be limited to specific foundation-model and inference-profile ARNs.

#### Implementation: policy, binding and the call

```hcl
data "aws_iam_policy_document" "chat_service_bedrock" {
  statement {
    actions = ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"]
    resources = [
      "arn:aws:bedrock:eu-central-1:${data.aws_caller_identity.me.account_id}:inference-profile/${var.eu_profile_id}",
      "arn:aws:bedrock:eu-*::foundation-model/${var.model_id}",   # regions the EU profile may route to
    ]
  }
}

resource "aws_iam_role_policy" "chat_service_bedrock" {
  role   = aws_iam_role.chat_service.id
  policy = data.aws_iam_policy_document.chat_service_bedrock.json
}

resource "aws_eks_pod_identity_association" "chat_service" {
  cluster_name    = aws_eks_cluster.main.name
  namespace       = "app"
  service_account = "chat-service"
  role_arn        = aws_iam_role.chat_service.arn
}
```

The role's trust policy must allow the `pods.eks.amazonaws.com` service principal, and the cluster needs the EKS Pod Identity Agent add-on. In the FastAPI service, boto3's default credential chain picks up the pod's role:

```python
import os

import boto3

bedrock = boto3.client("bedrock-runtime", region_name="eu-central-1")  # no keys: Pod Identity supplies them


def summarise(ticket: str) -> str:
    out = bedrock.converse(
        modelId=os.environ["BEDROCK_PROFILE_ID"],  # a geographic (EU) inference profile, see 16.16a
        messages=[{"role": "user", "content": [{"text": f"Summarise this support ticket:\n\n{ticket}"}]}],
        inferenceConfig={"maxTokens": 400},
    )
    content = out["output"]["message"]["content"]
    return content[0].get("text", "") if content else ""
```

#### Edge cases and failure modes

- **Cross-region profiles need every destination.** When you invoke a cross-region inference profile, IAM checks the foundation-model ARN in the region that serves the request, so the policy must cover all regions in the profile (hence the `eu-*` wildcard above). A policy listing only the source region fails intermittently, whenever traffic is routed elsewhere.
- **Service control policies.** An organisation-level SCP that denies regions outside an allow-list will block cross-region routing unless it allows the profile's destination regions (16.16a).
- **Node role fallback.** If the Pod Identity association is missing, the SDK quietly falls back to the node's instance role. Remove model permissions from node roles so a misconfiguration fails loudly.

## 16.12 Storage

- **Object storage** (S3, GCS, Azure Blob, OCI Object Storage). Model weights, training data, RAG corpora.
- **Block storage** (EBS, GCE PD, Azure Disk). Pod-attached volumes for stateful workloads.
- **File storage** (EFS, Filestore, Azure Files). Shared filesystems.
- **Specialized** (FSx for Lustre on AWS, Hyperdisk on GCP) — high-throughput shared storage for training data.

For inference, object storage holds model weights; a fast local NVMe cache speeds loading on cold start.

**🔧 Moving model weights out of S3 without a surprise bill.** Model weights are some of the largest objects a GenAI system moves, and the network path to S3 matters both for cold-start time ([AI Deployment, 15.8a](/docs/genai-handbook/15-ai-deployment)) and for cost.

*The cost trap.* Pods in private subnets reach S3 through a NAT gateway unless you add a gateway endpoint, and NAT gateways charge per GB processed (about $0.045/GB in us-east-1 as of 2026). Pulling a 141 GB 70B checkpoint costs about `141 × 0.045 ≈ $6.35` per pod start. At 50 scale-ups a day that is over $300 a day for traffic that could be free. An S3 **gateway** endpoint has no hourly or per-GB charge and routes S3 traffic through your route tables:

```hcl
resource "aws_vpc_endpoint" "s3" {
  vpc_id            = var.vpc_id
  service_name      = "com.amazonaws.${var.region}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = var.private_route_table_ids
}
```

*The throughput limit.* S3 supports at least 5,500 GET requests per second per partitioned prefix, and each connection is limited to a fraction of the node's bandwidth. Fast loading therefore comes from many parallel ranged GETs (s5cmd, the Run:ai streamer, or Mountpoint for S3 with parallel reads), not from a single `aws s3 cp` stream. Keep the bucket in the same region as the GPUs: cross-region reads are both slower and billed as inter-region transfer.

*Edge case.* Gateway endpoints only work for S3 (and DynamoDB) in the same region. Hugging Face Hub downloads still go through NAT, which is one more reason to mirror approved models into your own bucket.

## 16.13 Security

Cloud security baseline for AI:

- Encryption at rest (cloud-managed or customer-managed keys).
- Encryption in transit (TLS everywhere).
- Secrets in cloud Secret Manager, not env vars or images.

- Network policies and zero trust internal communication.
- Tenant isolation for multi-tenant AI products.

## 16.15 Cost Optimization

The biggest cloud-cost levers for AI:

- **Reserved instances / committed use** for steady state (1-year typically saves 30-50%, 3-year more).
- **Spot / preemptible** for batch and stateless workloads (50-90% savings).
- **Right-sizing** — many teams over-provision GPUs.
- **Egress** — keep traffic in-region; use private connections for cross-region.
- **Storage tiering** — move cold data to cheaper tiers.
- **Multi-cloud arbitrage** — run batch workloads where GPU price is lowest.
- **Idle GPU detection** — track utilization; shut down idle replicas.

Budget alarms per service. Review the top 10 cost drivers monthly. Set anomaly detection on cost — sudden 5x spike usually means a leak.

## 16.16 Multi-Region Strategy

Reasons to deploy multi-region: latency for global users, regulatory residency, disaster recovery, GPU capacity arbitrage.

Patterns:
- **Per-region inference clusters** with regional model deployments.
- **Geo-DNS routing** to the nearest region.
- **Failover regions** with smaller standby capacity.
- **Per-region data isolation** for residency compliance.

Watch cross-region egress costs and replication lag for RAG indices.

## 16.16a Data residency for GenAI workloads ➕

"Per-region data isolation" sounds simple until you list every place a prompt goes. This section covers where GenAI data actually flows and how to pin each flow to a jurisdiction.

### The problem

A team deploys its app in Frankfurt for an EU customer and assumes the data stays in the EU. Then an audit finds prompts processed in US regions by a managed model's global routing, traces with full prompts in a US observability SaaS, and embeddings of customer documents replicated to a DR region in another jurisdiction.

### Why it happens: GenAI multiplies the copies of user data

A single chat request can create copies of user data in:

1. **The inference location**: where the model actually runs, which managed services may choose dynamically.
2. **Provider-side storage**: abuse-monitoring logs, prompt caches, batch job files and fine-tuning data held by the model provider.
3. **Your own stores**: conversation history, RAG documents, embeddings (derived from personal data, so usually still personal data), and vector-index replicas.
4. **Telemetry**: LLM tracing tools record full prompts and completions by default.

Each is a separate residency decision.

### Mechanism: how the big three handle the inference location

- **AWS Bedrock** offers **geographic** cross-region inference profiles (US, EU, APAC and others), which route requests only to regions inside that geography, and **global** profiles, which may route to any supported commercial region in exchange for more capacity and about 10% lower prices. CloudTrail logs every request in the source region, and the `additionalEventData.inferenceRegion` field records where it was processed.
- **Azure OpenAI / Foundry Models** deployment types set the processing scope. **Global** types may process in any Azure region. **Data Zone** types process only within the US, the EU (following the EU Data Boundary) or APAC. **Standard** and **Regional Provisioned** types process within the chosen Azure geography. In all cases data at rest stays in the resource's geography.
- **Google Vertex AI** offers regional endpoints as well as a global endpoint. Choosing the global endpoint for capacity gives up the regional processing guarantee.

  R{"Residency requirement?"} -- none --> G["Global routing<br/>Bedrock global profile, Azure Global"]
  R -- "within a geography (e.g. EU)" --> Z["Geography routing<br/>Bedrock EU profile, Azure Data Zone EU"]

### Implementation: enforce it, don't just document it

**1. Route each tenant to a compliant model endpoint in code.** In the Python gateway:

```python
import os
from dataclasses import dataclass
from typing import Literal

from pydantic import BaseModel

type Residency = Literal["EU", "US", "ANY"]


@dataclass(frozen=True)
class ModelTarget:
    region: str
    model_id: str


MODEL_BY_RESIDENCY: dict[Residency, ModelTarget] = {
    "EU":  ModelTarget(region="eu-central-1", model_id=os.environ["BEDROCK_EU_PROFILE"]),
    "US":  ModelTarget(region="us-east-1",    model_id=os.environ["BEDROCK_US_PROFILE"]),
    "ANY": ModelTarget(region="us-east-1",    model_id=os.environ["BEDROCK_GLOBAL_PROFILE"]),
}


class Tenant(BaseModel):
    id: str
    residency: Residency | None = None


def model_for(tenant: Tenant) -> ModelTarget:
    # Fail closed: a tenant with no residency setting gets the strictest option, not the cheapest.
    return MODEL_BY_RESIDENCY[tenant.residency or "EU"]
```

**2. Block other regions at the organisation level.** An AWS SCP that denies actions outside the allowed regions stops a misconfigured service from calling a US endpoint. Cross-region inference interacts with SCPs: for a geographic profile the SCP must allow every destination region in that profile, and global profiles need `aws:RequestedRegion` of `unspecified` allowed, so an EU-only SCP blocks global profiles by design.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOutsideEU",
    "Effect": "Deny",
    "NotAction": ["iam:*", "organizations:*", "sts:*", "support:*", "cloudfront:*", "route53:*"],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": { "aws:RequestedRegion": ["eu-central-1", "eu-west-1", "eu-west-3", "eu-north-1"] }
    }
  }]
}
```

Make sure the allowed list covers every region your EU inference profile can route to. The exact set is in the Bedrock docs for each profile and changes over time.

**3. Pin the rest of the data path.** Run tracing (Langfuse, Phoenix) self-hosted in-region or on a vendor's EU instance, keep vector indices and their backups in-region, and redact or hash prompts before they reach any global logging pipeline ([Security for GenAI](/docs/genai-handbook/20-security-for-genai)).

### Edge cases and failure modes

- **Profiles change.** Providers add regions to geographic profiles and data zones over time (Microsoft states it can add regions to a data zone without notice). Re-check the region lists periodically, and keep your SCP and IAM policies in step.
- **Disaster recovery breaks residency.** A DR region in another jurisdiction makes a failover a compliance incident. Pick the DR region inside the same boundary, even if GPUs there are scarcer.
- **New models launch globally first.** Azure releases new models as Global deployments first, then Data Zone, then regional. A residency-bound tenant may wait months for a model, which the product roadmap has to plan for.
- **Embeddings are not anonymous.** Text can be partially reconstructed from embeddings, so treat vector stores with the same residency rules as the source documents.

## 16.16b Cross-region GPU capacity: quotas, reservations and fallbacks ➕

Multi-region strategy usually starts from latency and compliance. For GPUs there is a third driver: some regions simply do not have the capacity you need when you need it.

### The problem

A launch is planned for Monday. On Friday the team discovers that H100 capacity in its primary region is exhausted for on-demand use, the spot market is dry, and the quota increase is still pending. Self-hosted inference does not scale like a web tier, because the hardware itself is rationed.

### Why it happens

High-end GPUs are supply-constrained, and capacity is allocated per zone and per instance type. On-demand means "if available", not "guaranteed". Spot is surplus capacity that disappears first under pressure. Quotas (16.8.1) are a separate gate on top of physical capacity.

### Mechanism: the capacity instruments

| Instrument | What it guarantees | Fits |
|---|---|---|
| On-demand | Nothing, best effort | Small or flexible fleets |
| Spot | Nothing, can be reclaimed | Batch, burst above a floor |
| On-Demand Capacity Reservation (AWS) | Capacity in a zone while you pay for it, no term | A guaranteed floor for serving |
| EC2 Capacity Blocks for ML (AWS) | Fixed GPU capacity for a set window, booked ahead | Launches, evals, fine-tuning runs |
| Savings Plans or committed use | A discount, not capacity | Steady state you already obtain |
| GCP Dynamic Workload Scheduler | Flex-start: queued until capacity appears. Calendar mode: fixed future blocks | Training, batch, planned events |

As of 2026, AWS Capacity Blocks can be booked up to 8 weeks ahead, for 1 to 14 days or in 7-day multiples up to 182 days, on P5, P5e, P5en, P6 and Trainium instances in selected regions. GCP's calendar mode books 7- or 14-day blocks up to 8 weeks ahead. Note that discounts such as Savings Plans lower the price but do not reserve hardware.

### Implementation: query and reserve capacity

```bash
# Find Capacity Block offerings for 2 x p5.48xlarge for 7 days, starting within the next 3 weeks
aws ec2 describe-capacity-block-offerings \
  --instance-type p5.48xlarge --instance-count 2 \
  --capacity-duration-hours 168 \
  --start-date-range 2026-10-05T00:00:00Z --end-date-range 2026-10-26T00:00:00Z

# Purchase one of the returned offerings
aws ec2 purchase-capacity-block --capacity-block-offering-id cbr-0123456789abcdef0 \
  --instance-platform Linux/UNIX
```

Then design the serving fleet so it can use whatever exists:

- **A reserved floor** in the primary region (capacity reservation) sized for baseline traffic.
- **Flexible burst**: a NodePool that allows several GPU families and both capacity types (see [AI Deployment, 15.8b](/docs/genai-handbook/15-ai-deployment)), with each model's config valid on every allowed GPU.
- **Regional fallback** in the gateway: when the primary pool is saturated or failing, route to a secondary region's pool, or to a managed API for the same model class ([Backend for GenAI](/docs/genai-handbook/06-backend-for-genai)), within the tenant's residency boundary (16.16a).

### Edge cases and failure modes

- **Reservations are per zone.** A capacity reservation in one availability zone does nothing for pods scheduled in another. Pin the GPU node group to the reserved zone.
- **Capacity Blocks end hard.** Instances in a Capacity Block are terminated when the block ends. Checkpoint training and drain serving before the end time.
- **Fallback regions add latency and egress.** Sending traffic cross-region adds network round trips (often tens of milliseconds, more across continents) and inter-region transfer charges, so RAG context fetched in one region and sent to another region's model costs twice.
- **Heterogeneous fallbacks change behaviour.** Falling back from an H100 pool running a 70B model to a smaller model on L40S keeps the service up but changes answer quality. Make it an explicit degraded mode with its own metrics.

## 16.17 Hybrid and Multi-Cloud Patterns

- **Burst to cloud.** On-prem baseline plus cloud burst capacity.
- **Cloud primary, on-prem disaster recovery.** Reverse of burst.
- **Multi-cloud active-active.** Geo-routed traffic across multiple clouds.
- **Cloud-of-clouds.** Aggregator services (model serving platforms) abstract clouds entirely.

Most teams start single-cloud and expand only when motivated by clear capacity, cost, or regulatory pressure.

## 16.20 Interview Questions

- Compare Bedrock, Vertex, and Azure OpenAI.
- When would you choose a specialist GPU cloud over a hyperscaler?
- Design a multi-region failover for a global chat product.
- Walk through cost optimization for a $1M/year GPU bill.
- Where does PrivateLink fit in a compliance-bound architecture?
- ➕ When does self-hosting never beat a managed API, whatever the volume? **When your marginal cost per token, `GPU $/hour ÷ (tokens/s × 3600 × utilisation)`, is above the API price. Above that line, more volume only adds loss.**
- ➕ Your EU customer requires EU-only processing. What do you check besides the app's region? **The model's routing scope (Bedrock geographic vs global profile, Azure Data Zone vs Global), provider-side retention, tracing and logging destinations, vector-index replicas and the DR region.**
- ➕ A new GPU node group stays empty after Terraform succeeds. Why? **Usually the vCPU-based service quota for that instance family (P or G) or a lack of capacity in the chosen zones. Check the autoscaling group's activity for `VcpuLimitExceeded` or insufficient-capacity errors.**
- ➕ What is the difference between a Savings Plan and a Capacity Block? **A Savings Plan is a billing discount and reserves no hardware. A Capacity Block reserves specific GPU instances for a fixed future window.**
- ➕ Why add an S3 gateway endpoint to a GPU cluster? **Without one, model-weight downloads from private subnets go through the NAT gateway and are billed per GB. The gateway endpoint is free and keeps the traffic on the AWS network.**

## 16.22 Common Mistakes

- Forgetting egress fees in multi-cloud designs.
- Pinning to one provider's proprietary APIs (lock-in).
- Over-provisioning GPUs.
- Skipping reserved capacity for steady state.
- Letting credentials live in env vars when workload identity is available.

## 16.23 Enterprise Best Practices

Standardize on one primary cloud; use specialists tactically. Terraform everything; manual cloud changes drift fast. Tag every resource with owner, project, environment. Centralize log and metric aggregation across clouds. Negotiate annual commitments tied to projected usage. Review cost monthly and capacity quarterly.
