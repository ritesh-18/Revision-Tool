## 3.1 Concept Explanation

Deep learning is the practice of building functions out of stacked layers of simple, differentiable operations whose parameters are learned from data. The "deep" refers to the number of layers stacked. The reason depth matters: each layer transforms its input into a slightly more abstract representation, and stacked layers compose those abstractions into something powerful enough to recognize a face, translate a sentence, or generate a paragraph.

A GenAI engineer does not train foundation models from scratch — that is a multi-million-dollar exercise. But you will fine-tune, you will quantize, you will run inference at scale, and you will debug models that misbehave. All of those require the mental model in this chapter.

## 3.2 Neural Networks — The Building Block

A neural network is a function. It takes an input vector, multiplies it by a learned weight matrix, adds a learned bias vector, and passes the result through a nonlinear activation function. That is one "layer." Stacking layers produces deeper functions. Stacking the right kinds of layers in the right pattern produces transformers, convolutional networks, diffusion models, and everything else.

Without nonlinear activation, stacking layers is mathematically equivalent to a single layer — you just get a bigger linear function. Nonlinearity is what gives depth its power. The activation function bends the flat line into a curve, and stacking many bent curves can approximate any function. This is the universal approximation theorem in plain English.

## 3.3 Forward Propagation

Forward propagation is the act of running the network from input to output. Input vector enters layer 1, gets transformed, exits as a new vector, enters layer 2, and so on until the final layer produces the output. In an LLM, this output is the logits vector — one number per token in the vocabulary. Forward propagation at inference time is what your production system spends 99% of its compute on.

There is no learning in forward propagation. The weights are fixed; the computation is deterministic given the input and the sampling seed. Forward pass per token is what dictates inference latency.

## 3.4 Backpropagation — How Learning Happens

Backpropagation computes the gradient of the loss with respect to every parameter in the network. It does this by applying the chain rule of calculus, working backward from the output layer to the input layer. Each layer receives the gradient flowing in from above, uses it to compute the gradient with respect to its own parameters, and passes the resulting gradient downward.

This is *exclusive to training*. Production inference does not do backpropagation. But knowing it exists explains why training is roughly 3× the memory of inference: you must store intermediate activations from the forward pass so backprop can use them. This is also why "gradient checkpointing" is a common training trick — recompute some activations rather than store them, trading compute for memory.

## 3.4a Backpropagation in 40 Lines 🔧

The description above becomes concrete once you build a tiny automatic-differentiation engine, the same idea PyTorch's autograd implements at scale, and check it against PyTorch.

### The computational graph and local derivatives

**Problem.** A network is a composition of thousands of operations, and you need the derivative of one scalar loss with respect to every input of every operation.

**Why it works.** Each operation only needs to know its *local* derivative: how its output changes when each of its inputs changes. For `c = a × b`, `dc/da = b` and `dc/db = a`. The chain rule says the derivative of the loss with respect to `a` is `dL/dc × dc/da`. So if every node records its inputs and local derivatives during the forward pass, one backward sweep can multiply them together.

**Implementation.**

```python
import math

class Value:
    """A scalar that remembers how it was computed."""
    def __init__(self, data, parents=(), local_grads=()):
        self.data, self.grad = data, 0.0
        self._parents, self._local = parents, local_grads   # d(self)/d(parent)

    @staticmethod
    def wrap(x):
        return x if isinstance(x, Value) else Value(x)

    def __add__(self, other):
        other = Value.wrap(other)
        return Value(self.data + other.data, (self, other), (1.0, 1.0))

    def __mul__(self, other):
        other = Value.wrap(other)
        return Value(self.data * other.data, (self, other), (other.data, self.data))

    def __pow__(self, n):
        return Value(self.data ** n, (self,), (n * self.data ** (n - 1),))

    def __sub__(self, other):
        return self + Value.wrap(other) * -1.0

    __radd__, __rmul__ = __add__, __mul__

    def tanh(self):
        t = math.tanh(self.data)
        return Value(t, (self,), (1 - t * t,))

    def backward(self):
        order, seen = [], set()
        def visit(v):                      # topological order: inputs before outputs
            if id(v) not in seen:
                seen.add(id(v))
                for p in v._parents:
                    visit(p)
                order.append(v)
        visit(self)
        self.grad = 1.0                    # dL/dL
        for v in reversed(order):          # outputs before inputs
            for parent, local in zip(v._parents, v._local):
                parent.grad += local * v.grad   # chain rule; += handles reuse

# One neuron: pred = tanh(w1*x1 + w2*x2 + b), loss = (pred - 1)^2
w1, w2, b = Value(0.5), Value(-0.3), Value(0.1)
pred = (w1 * 2.0 + w2 * -1.0 + b).tanh()
loss = (pred - 1.0) ** 2
loss.backward()
print(w1.grad, w2.grad, b.grad)
```

### Checking against PyTorch

```python
import torch

x = torch.tensor([2.0, -1.0])
w = torch.tensor([0.5, -0.3], requires_grad=True)
b = torch.tensor(0.1, requires_grad=True)
loss = (torch.tanh((w * x).sum() + b) - 1) ** 2
loss.backward()
print(w.grad, b.grad)   # same numbers as the scalar engine
```

### Why gradients accumulate with +=

**Problem.** A value used in two places (a weight shared across positions, a residual branch) receives gradient from both uses.

**Mechanism.** The multivariable chain rule *sums* contributions from every path. That is why the engine uses `+=`, and why PyTorch also accumulates into `.grad` until you call `optimizer.zero_grad()`. Forgetting to zero gradients between steps adds old gradients to new ones, a classic training bug. The same behavior is used on purpose for *gradient accumulation*: run several small batches, call `backward()` on each, then step once to simulate a bigger batch.

### What the backward pass needs to keep, and why that costs memory

**Mechanism.** Look at the local derivatives above: the one for `__mul__` needs the *other input's value*, and the one for `tanh` needs the output `t`. Every operation keeps something from the forward pass alive until backward runs. In a real network those are whole activation tensors per layer, which is the activation memory the handbook mentions. Gradient checkpointing drops them and recomputes the forward pass for a segment during backward.

### Failure mode: vanishing gradients and how residuals fix them

**Problem.** In deep stacks the gradient reaching the first layers can shrink toward zero, so those layers stop learning.

**Why it happens.** Backprop multiplies one local derivative per layer. The sigmoid's derivative is at most 0.25, so 30 sigmoid layers can scale the gradient by up to `0.25 ** 30`, about `1e-18`. A residual connection `h + f(h)` has local derivative `1 + f'(h)`, so the identity path carries the gradient through unchanged.

```python
import torch

torch.manual_seed(0)
def grad_at_input(residual: bool, depth: int = 30) -> float:
    x = torch.randn(256, 64, requires_grad=True)
    h = x
    for _ in range(depth):
        W = torch.randn(64, 64) / 8.0          # 1/sqrt(64) scaling
        out = torch.sigmoid(h @ W)
        h = h + out if residual else out
    h.sum().backward()
    return x.grad.abs().mean().item()

print("plain   ", grad_at_input(False))   # vanishingly small
print("residual", grad_at_input(True))    # many orders of magnitude larger
```

**Edge case.** The recursive `visit` in the toy engine hits Python's recursion limit on graphs a few thousand nodes deep. Real frameworks walk the graph iteratively and operate on tensors, not scalars, but the algorithm is the same.

## 3.5 Loss Functions

The loss function is a scalar that measures how wrong the model is. Training minimizes this scalar. The choice of loss depends on the task.

**Cross-entropy loss** dominates language modeling. For each predicted token, it asks: how surprised was the model by the correct next token? If the model assigned 90% probability to the correct token, the loss is small. If it assigned 0.01%, the loss is huge.

**Mean squared error** dominates regression. **Triplet/contrastive losses** dominate embedding training. **KL divergence** dominates distillation, where a small model is trained to match the output distribution of a large one.

You do not implement these. But you should recognize them in papers and config files, because they tell you what behavior the model is being shaped toward.

## 3.5a Cross-Entropy, Perplexity and KL, Worked Through 🔧

The handbook says you will not implement these losses, but you will read them in training logs and eval reports, so this section works through the numbers and the PyTorch calls that produce them.

### Cross-entropy as surprise

**Problem.** A training log says "loss 2.1". You need to know what that means.

**Mechanism.** For one position, cross-entropy is `−log(p_correct)`, the negative log of the probability the model gave the true next token, in nats (natural log). The reported loss is the mean over all predicted positions.

```python
import numpy as np

p_correct = np.array([0.9, 0.5, 0.01])
print(-np.log(p_correct))   # [0.105 0.693 4.605]: confident-right is cheap, confident-wrong is costly
```

### Perplexity

**Mechanism.** Perplexity is `exp(mean cross-entropy)`. A loss of 2.1 nats is a perplexity of about 8.2: on average the model is as uncertain as if it were choosing uniformly among about 8 tokens. Lower is better, and 1 would be perfect prediction.

**Implementation.** Measuring a text's perplexity under a small open model with Hugging Face Transformers:

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("gpt2")
model = AutoModelForCausalLM.from_pretrained("gpt2").eval()

enc = tok("The capital of France is Paris.", return_tensors="pt")
with torch.no_grad():
    out = model(**enc, labels=enc["input_ids"])   # the model shifts labels internally
print(f"loss={out.loss.item():.3f}  perplexity={torch.exp(out.loss).item():.1f}")
```

### The causal LM loss by hand: shifting and masking

**Problem.** Writing the loss yourself (custom training, eval scripts) goes wrong in two predictable ways: off-by-one targets and counting padding.

**Mechanism.** The logit at position `t` predicts token `t + 1`, so logits and labels must be shifted against each other. Positions that are padding (or the prompt, when you only want to train on answers) get label `−100`, which `F.cross_entropy` skips by default.

```python
import torch.nn.functional as F

def causal_lm_loss(logits, input_ids, loss_mask):
    """logits [B, T, V]; input_ids [B, T]; loss_mask [B, T] is 1 where we score a token."""
    labels = input_ids.masked_fill(loss_mask == 0, -100)
    shift_logits = logits[:, :-1, :].reshape(-1, logits.size(-1))   # predictions for 1..T-1
    shift_labels = labels[:, 1:].reshape(-1)                         # the tokens they predict
    return F.cross_entropy(shift_logits, shift_labels, ignore_index=-100)
```

### KL divergence for distillation

**Mechanism.** Distillation trains a student to match the teacher's whole distribution, not just its top token. KL divergence measures the gap between the two distributions. Dividing both sets of logits by a temperature `T` above 1 softens them, which exposes how the teacher ranks the wrong answers. Multiplying by `T²` keeps gradient size comparable across temperatures (Hinton et al., 2015).

```python
def distill_loss(student_logits, teacher_logits, T=2.0):
    """Both [N, V]; flatten [B, T, V] to [B*T, V] first so 'batchmean' averages per token."""
    s = F.log_softmax(student_logits / T, dim=-1)
    t = F.log_softmax(teacher_logits / T, dim=-1)
    return F.kl_div(s, t, log_target=True, reduction="batchmean") * T * T
```

### Failure modes

- **Perplexity across tokenizers is not comparable.** A model with a bigger vocabulary predicts fewer, longer tokens, which changes per-token loss. To compare models with different tokenizers, normalize by text length, for example bits per byte: `total_loss_nats / ln(2) / number_of_utf8_bytes`.
- **Padding counted as tokens.** Forgetting `ignore_index` lets easy padding predictions drag the loss down and makes runs look better than they are.
- **Chat models on raw text.** A post-trained assistant can have higher perplexity on plain web text than its base model while being far more useful. Perplexity measures fit to a distribution, not helpfulness.
- **`F.kl_div` argument order.** The first argument must be the student's *log*-probabilities. Passing probabilities, or swapping student and teacher, still runs but optimizes the wrong thing.

## 3.6 Optimizers

The optimizer is the algorithm that converts gradients into parameter updates. The naïve version is SGD: subtract a small multiple of the gradient. Modern optimizers are far more sophisticated.

**Adam** and **AdamW** track two running averages per parameter — the mean and variance of recent gradients — and use these to adapt the per-parameter step size. This converges much faster than SGD on transformer architectures.

**Adafactor** approximates Adam with less memory, useful at scale.

**Lion** is a newer optimizer that uses only one momentum value and produces competitive results with lower memory.

Production implication: Adam doubles your optimizer state memory (two moments per parameter). For a 7B model in mixed precision, that is roughly 14 GB of weights, 14 GB of gradients, 28 GB of optimizer state, plus activations — easily 80 GB for training versus 14 GB for inference. This is why training requires bigger GPUs than inference.

## 3.6a AdamW, Warmup and Clipping in Code 🔧

To see where the "two moments per parameter" above come from and how they are used, here is the AdamW update written out, followed by the training-loop settings almost every LLM recipe uses.

### The AdamW update

**Problem.** Gradients for different parameters differ in scale by orders of magnitude, so one global learning rate is too big for some and too small for others.

**Mechanism.** Adam keeps a running mean of each parameter's gradient (`m`, the momentum) and of its squared gradient (`v`). The step is `m / sqrt(v)`: parameters with consistently large gradients get proportionally smaller steps. Both averages start at zero, so early estimates are biased toward zero and are corrected by dividing by `1 − β^t`. AdamW applies weight decay directly to the weights instead of mixing it into the gradient (Loshchilov and Hutter, 2019), which keeps decay independent of the adaptive scaling.

```python
import torch

@torch.no_grad()
def adamw_step(p, g, m, v, t, lr, b1=0.9, b2=0.95, eps=1e-8, wd=0.1):
    m.mul_(b1).add_(g, alpha=1 - b1)           # running mean of gradients
    v.mul_(b2).addcmul_(g, g, value=1 - b2)    # running mean of squared gradients
    m_hat = m / (1 - b1 ** t)                  # bias correction, t starts at 1
    v_hat = v / (1 - b2 ** t)
    p.mul_(1 - lr * wd)                        # decoupled weight decay
    p.add_(-lr * m_hat / (v_hat.sqrt() + eps))
```

**Memory consequence.** `m` and `v` are two extra full-size tensors. In standard mixed-precision training they are kept in FP32 together with an FP32 master copy of the weights, so the ZeRO paper counts 16 bytes per parameter: 2 (BF16 weights) + 2 (BF16 gradients) + 12 (FP32 master weights, `m`, `v`). For 7B parameters that is about 112 GB before activations, more than the 80 GB estimate above. Recipes that keep optimizer state in BF16 or use 8-bit optimizers get closer to that lower figure. Sharding this state is covered in [Fine-tuning and Training](/docs/genai-handbook/23-finetuning-training).

### Warmup, cosine decay and gradient clipping

**Problem.** Training with a constant learning rate often diverges in the first few hundred steps, or plateaus later.

**Why it happens.** At the start, `v` is estimated from very few gradients and can be tiny, which makes `m / sqrt(v)` steps huge. Warmup ramps the learning rate up from near zero while the estimates settle. Later, a decaying rate lets the model settle into a minimum instead of bouncing around it. Gradient clipping caps the total gradient norm so that one bad batch cannot throw the weights far away.

```python
import math
import torch

def lr_at(step, max_lr=3e-4, warmup=500, total=20_000, min_lr=3e-5):
    if step < warmup:
        return max_lr * (step + 1) / warmup
    progress = (step - warmup) / max(1, total - warmup)
    return min_lr + 0.5 * (max_lr - min_lr) * (1 + math.cos(math.pi * progress))

# No weight decay on norms and biases (1-D tensors): decaying them only hurts
decay = [p for p in model.parameters() if p.ndim >= 2]
no_decay = [p for p in model.parameters() if p.ndim < 2]
opt = torch.optim.AdamW(
    [{"params": decay, "weight_decay": 0.1}, {"params": no_decay, "weight_decay": 0.0}],
    lr=3e-4, betas=(0.9, 0.95),
)

for step, batch in enumerate(loader):
    for group in opt.param_groups:
        group["lr"] = lr_at(step)
    loss = model(**batch).loss
    loss.backward()
    grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    opt.step()
    opt.zero_grad(set_to_none=True)
```

### Failure modes

- **Loss spikes.** A sudden jump usually follows a large `grad_norm`. Log the norm every step: a rising trend warns you before the loss diverges, and the usual fixes are a lower peak learning rate or longer warmup.
- **Fine-tuning with pre-training learning rates.** Fine-tuning a pre-trained model typically uses a learning rate one or two orders of magnitude lower than pre-training. Too high a rate erases what the model knew.
- **Resuming without optimizer state.** Restarting from a checkpoint that saved weights but not `m` and `v` resets the moments, which behaves like a fresh warmup-free start and can spike the loss. Save and restore the optimizer and the step counter.

## 3.7 Activation Functions

The nonlinearity injected between layers. The historical sequence:

- **Sigmoid** squashes any input to (0, 1). Used in older networks; suffers from vanishing gradients at the extremes.
- **Tanh** squashes to (−1, 1). Similar issues to sigmoid.
- **ReLU** outputs max(0, x). Solves vanishing gradients but introduces "dead neurons" (outputs stuck at 0).
- **GELU** is a smoother approximation of ReLU, standard in transformers.
- **SwiGLU** is a gated variant used in many modern LLMs (Llama, PaLM). It splits the layer into two halves, multiplies them, and provides better gradient flow.

You will not pick the activation function in production — the model architecture has already picked. But knowing which activation a model uses is part of understanding why it has the inference characteristics it does.

## 3.8 CNN — Convolutional Networks

CNNs dominated vision before transformers and are still the most efficient architecture for many image tasks. The core idea is *weight sharing*: instead of learning a separate weight for every pixel position, the network learns small filters that slide over the image. This drastically reduces parameter count and exploits the fact that visual features (edges, textures) look the same regardless of where they appear in the image.

For GenAI engineers, CNNs are relevant in two places: image embedding models (CLIP-style encoders), and the earliest stages of multimodal models that ingest images before passing tokens to a transformer.

## 3.9 RNN and LSTM — Predecessors of the Transformer

RNNs process sequences one element at a time, maintaining a hidden state that carries information across time. LSTMs and GRUs are gated variants that mitigate the vanishing gradient problem.

These were the dominant sequence architecture until 2017. They are nearly extinct in new LLM work because they cannot be parallelized over time during training. They survive in two niches: extremely small on-device sequence models, and recent "linear attention" or "state-space" models (like Mamba) that revive RNN-like recurrence with modern tricks to scale better than transformers on very long sequences.

## 3.10 Transformers — The Architecture That Won

A transformer block is, conceptually, two halves stacked many times:

1. **Self-attention.** Each token looks at all other tokens via Q-K-V projections and attention weights.
2. **Feed-forward network.** Each token is independently transformed through a much larger hidden layer (typically 4× the embedding dimension) and projected back.

Layer normalization and residual connections wrap each half. Residual connections allow gradients to flow easily through deep stacks; without them, training a 80-layer model would be nearly impossible.

## 3.10a Where the Norm Goes: Pre-Norm and RMSNorm ➕

The diagram above shows the original transformer's layout, with the norm applied *after* each residual addition; almost every modern LLM moves the norm and changes its type, and the reasons explain a lot about training stability.

### Post-norm versus pre-norm

**Problem.** Deep post-norm transformers are hard to train: they need careful learning-rate warmup and still diverge at depth.

**Why it happens.** In post-norm, `x = Norm(x + F(x))`, every layer's output passes through a normalization, so the residual stream is re-scaled at every layer and the gradient has to pass through every norm on its way down. Xiong et al. (2020) showed that this makes gradients near the output large at initialization, which is why warmup is essential. In pre-norm, `x = x + F(Norm(x))`, the residual stream is never normalized: there is a clean identity path from the last layer to the first, exactly the residual effect demonstrated in 3.4a.

**Mechanism.** Pre-norm adds one final norm after the last block, before the output projection, because the residual stream itself is never normalized. GPT-2 and later GPT models, Llama, Mistral and Qwen all use pre-norm with a final norm (you will see it as "Final layer norm" in the pipeline in [LLM Internals](/docs/genai-handbook/04-llm-internals)).

**Edge case.** Pre-norm's residual stream can grow in magnitude with depth, and some recent models add extra norms (for example on queries and keys) to keep attention logits in range. When you read a model's config, the norm placement is one of the details that must match exactly for converted weights to work.

### LayerNorm versus RMSNorm

**Problem.** LayerNorm subtracts the mean and divides by the standard deviation of each token's vector, then applies a learned scale and shift. That is two reductions per token per norm, and norms run several times per layer.

**Mechanism.** RMSNorm (Zhang and Sennrich, 2019) drops the mean subtraction and the shift: it divides by the root mean square and applies a learned scale. The paper found re-centering contributes little, and RMSNorm is cheaper. Llama, Mistral and Qwen use it.

```python
import torch
import torch.nn as nn

class RMSNorm(nn.Module):
    def __init__(self, dim: int, eps: float = 1e-6):
        super().__init__()
        self.eps = eps
        self.weight = nn.Parameter(torch.ones(dim))

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        x32 = x.float()                                   # compute the statistic in FP32
        rms_inv = torch.rsqrt(x32.pow(2).mean(dim=-1, keepdim=True) + self.eps)
        return (x32 * rms_inv).to(x.dtype) * self.weight
```

**Failure modes.** Computing the mean of squares in BF16 loses precision, which is why implementations upcast as above. `eps` differs between models (`1e-5` and `1e-6` are both common); using the wrong value when porting weights causes small but real output drift.

## 3.10b A Complete Pre-Norm Decoder Block 🔧

With the norm settled, the whole block from the diagram fits in about 30 lines of PyTorch, which is the best way to check that you can label every tensor shape (exercise 1 in 3.17).

### SwiGLU and its odd hidden size

**Mechanism.** SwiGLU (Shazeer, 2020) computes `down(silu(gate(x)) × up(x))`: one projection decides how much of the other passes through. It has three weight matrices instead of the classic FFN's two. To keep the parameter count of a `4 × d` classic FFN (`8d²`), the hidden size becomes `8d / 3`, rounded to a hardware-friendly multiple. Model designers then often scale it further: Llama 3 8B has a hidden size of 4,096 and an FFN size of 14,336 (3.5 times), so FFN sizes in configs rarely look like round multiples of the hidden size.

### The block

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class SwiGLU(nn.Module):
    def __init__(self, dim: int, hidden: int):
        super().__init__()
        self.gate = nn.Linear(dim, hidden, bias=False)
        self.up = nn.Linear(dim, hidden, bias=False)
        self.down = nn.Linear(hidden, dim, bias=False)

    def forward(self, x):
        return self.down(F.silu(self.gate(x)) * self.up(x))

class DecoderBlock(nn.Module):
    def __init__(self, dim=512, n_heads=8, ffn_hidden=1376):    # 8/3 * 512 rounded to 32
        super().__init__()
        self.n_heads = n_heads
        self.attn_norm, self.ffn_norm = RMSNorm(dim), RMSNorm(dim)  # RMSNorm from 3.10a
        self.qkv = nn.Linear(dim, 3 * dim, bias=False)
        self.out = nn.Linear(dim, dim, bias=False)
        self.ffn = SwiGLU(dim, ffn_hidden)

    def forward(self, x):                                       # x: [B, T, D]
        B, T, D = x.shape
        q, k, v = self.qkv(self.attn_norm(x)).split(D, dim=-1)  # each [B, T, D]
        q, k, v = (t.view(B, T, self.n_heads, D // self.n_heads).transpose(1, 2)
                   for t in (q, k, v))                          # each [B, H, T, d]
        a = F.scaled_dot_product_attention(q, k, v, is_causal=True)  # [B, H, T, d]
        x = x + self.out(a.transpose(1, 2).reshape(B, T, D))    # residual 1
        return x + self.ffn(self.ffn_norm(x))                   # residual 2

block = DecoderBlock()
y = block(torch.randn(2, 10, 512))
print(y.shape)                                        # torch.Size([2, 10, 512])
print(sum(p.numel() for p in block.parameters()))    # 3,163,136
```

The parameter count checks the maths: attention `4 × 512²` = 1,048,576, SwiGLU `3 × 512 × 1376` = 2,113,536, two norms 1,024.

### What a real model adds

- **Positional information.** Real blocks rotate `q` and `k` with RoPE before attention (section 4.6a in [LLM Internals](/docs/genai-handbook/04-llm-internals)). Without it this block cannot tell token order.
- **Grouped-query attention.** Modern models use fewer key/value heads than query heads to shrink the KV cache (section 4.4a there).
- **KV cache plumbing.** At inference, `k` and `v` from previous steps are concatenated instead of recomputed.

**Failure mode.** Weight-loading bugs between this kind of code and a checkpoint (fused versus separate `q`, `k`, `v` matrices, different head ordering) usually produce fluent-looking garbage rather than an error. Always compare logits against the reference implementation on a fixed input before trusting a port.

## 3.11 GPU Acceleration

Deep learning runs on GPUs because the computation is overwhelmingly matrix multiplication, and GPUs are matrix-multiplication machines. A modern training-grade GPU performs thousands of multiplications per clock cycle across thousands of cores. CPUs perform a handful per core across dozens of cores. The throughput gap is one to two orders of magnitude.

The catch: GPU compute is wasted unless the GPU's memory bandwidth keeps up. Modern GPUs use HBM (high-bandwidth memory) precisely because feeding the compute cores is the constraint. Chapter 14 covers the hardware in depth.

## 3.12 CUDA — The Lingua Franca of AI Hardware

CUDA is NVIDIA's parallel computing platform. Every major deep learning framework — PyTorch, JAX, TensorFlow — compiles to CUDA kernels for execution on NVIDIA GPUs. AMD has ROCm as a competing stack; Intel has oneAPI. Apple has Metal Performance Shaders. NVIDIA's lead in software ecosystem is as important as its lead in hardware.

You will rarely write CUDA. You will frequently debug installations involving CUDA, cuDNN (NVIDIA's deep learning primitives), NCCL (multi-GPU communication), and the driver version mismatches that produce mysterious crashes. Knowing this stack exists demystifies the error messages.

## 3.13 Mixed Precision Training

Modern training uses a mix of floating-point precisions: 16-bit (FP16 or BF16) for most operations to halve memory and double throughput, and 32-bit for accumulators and weight updates to preserve numerical stability.

BF16 (brain float 16) is the standard for LLM training because it has the same exponent range as FP32 — it loses precision but not magnitude. FP16 has narrower range and can underflow during loss computation, requiring "loss scaling" tricks.

For inference, even more aggressive precisions are used: FP8 (newest hardware only), INT8, and INT4 via quantization. This trades model quality for memory and speed, and is the foundation of running large models on consumer hardware.

## 3.13a Number Formats and Mixed Precision in Code 🔧

The BF16-versus-FP16 distinction above comes down to how each format splits its bits, and seeing the bits explains both the overflow risk and the loss-scaling trick.

### How the bits are split

| Format | Sign / exponent / mantissa bits | Largest value | Typical use |
| --- | --- | --- | --- |
| FP32 | 1 / 8 / 23 | about 3.4e38 | master weights, optimizer state, reductions |
| BF16 | 1 / 8 / 7 | about 3.4e38 | training and inference activations and weights |
| FP16 | 1 / 5 / 10 | 65,504 | inference, older training with loss scaling |
| FP8 E4M3 | 1 / 4 / 3 | 448 | forward pass on newer GPUs |
| FP8 E5M2 | 1 / 5 / 2 | 57,344 | gradients on newer GPUs |

**Mechanism.** Exponent bits set the *range*, mantissa bits set the *precision*. BF16 keeps FP32's 8 exponent bits, so anything FP32 can hold, BF16 can hold (roughly). It pays with only 7 mantissa bits, about 2 to 3 significant decimal digits. FP16 has more precision but overflows at 65,504.

```python
import torch

print(torch.finfo(torch.float16).max, torch.finfo(torch.bfloat16).max)  # 65504.0, ~3.39e38
big = torch.tensor(70_000.0)
print(big.to(torch.float16), big.to(torch.bfloat16))   # inf, 70144. (range vs precision)
print(torch.tensor(1 + 1 / 512, dtype=torch.bfloat16)) # 1.: the small increment is lost
```

### Autocast for BF16

**Mechanism.** `torch.autocast` runs matrix multiplications in the low-precision type and keeps precision-sensitive operations such as softmax, norms and loss in FP32. Weights stay FP32 in the optimizer, so small updates are not rounded away (the `1 + 1/512` problem above).

```python
model = model.cuda()
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)

for batch in loader:
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        loss = model(**batch).loss
    loss.backward()                 # gradients land in FP32 .grad of FP32 weights
    opt.step()
    opt.zero_grad(set_to_none=True)
```

### Loss scaling for FP16

**Problem.** With FP16, small gradients fall below the smallest representable number and become zero.

**Mechanism.** Multiply the loss by a large factor before backward so gradients are shifted into FP16's range, then divide them back before the optimizer step. `GradScaler` picks the factor dynamically: when it sees `inf` or `nan` gradients, it skips that step and lowers the factor.

```python
scaler = torch.amp.GradScaler("cuda")
for batch in loader:
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = model(**batch).loss
    scaler.scale(loss).backward()
    scaler.unscale_(opt)                                   # real gradient values again
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(opt)                                       # skipped if gradients overflowed
    scaler.update()
    opt.zero_grad(set_to_none=True)
```

### Failure modes

- **BF16 weights without an FP32 master copy.** Updates smaller than about 1/256 of a weight's value round to nothing, and training silently stalls. Pure-BF16 recipes need special handling (for example stochastic rounding or Kahan summation).
- **Clipping before unscaling.** With FP16, clipping scaled gradients clips at the wrong threshold. Call `scaler.unscale_` first, as above.
- **FP16 inference overflow.** Some models trained in BF16 produce activations above 65,504, so running them in FP16 yields `inf` and garbage text. Prefer BF16 when the GPU supports it.
- **FP8 needs per-tensor scaling.** With only 448 as the E4M3 maximum, FP8 training and inference keep scale factors per tensor or per block. Hardware details are in [GPU Systems](/docs/genai-handbook/14-gpu-systems).

## 3.14 Real-World Use Cases of These Fundamentals

Every production LLM system you will touch is the product of these primitives composed at scale. Embedding models are transformer encoders trained with contrastive loss. Chat models are decoder-only transformers post-trained with RLHF. Vision-language models stack image encoders onto LLMs. Diffusion image models are U-Nets — a CNN variant — trained to remove noise step by step. None of this is exotic once you see the parts.

## 3.15 Common Mistakes

- Confusing "training" and "inference" when discussing memory requirements.
- Believing that more parameters always means better — a well-trained 7B can outperform a poorly trained 70B.
- Treating quantization as free — there is always some quality loss, even if small.
- Assuming PyTorch and TensorFlow models can be swapped interchangeably; weights, layer naming, and conventions differ.
- Ignoring the dataloader as a performance bottleneck. GPUs sit idle waiting for data more often than people admit.

**➕ More questions:**

- *Why does PyTorch accumulate gradients instead of overwriting them?* — **The chain rule sums contributions from every path a value takes. Accumulation is also used on purpose to simulate larger batches, which is why you must zero gradients between optimizer steps.**
- *A model reports a loss of 2.0 nats per token. What is its perplexity?* — **`exp(2.0)`, about 7.4. Only compare perplexities between models that use the same tokenizer.**
- *Why do modern LLMs use pre-norm?* — **The residual stream keeps an un-normalized identity path from output to input, so gradients flow cleanly and deep models train stably with less sensitivity to warmup.**
- *Why is the SwiGLU hidden size about 8/3 of the model dimension?* — **SwiGLU has three matrices instead of two, so shrinking the hidden size to `8d/3` keeps the parameter count of a classic `4d` FFN.**
- *Why does BF16 rarely need loss scaling but FP16 does?* — **BF16 has FP32's exponent range, so small gradients do not underflow. FP16's 5-bit exponent does underflow, so the loss is scaled up before backward.**
- *How many bytes per parameter does mixed-precision Adam training need?* — **About 16: BF16 weights and gradients (4) plus FP32 master weights and two moments (12), before activations.**

## 3.18 Enterprise Best Practices

Pin framework, CUDA, driver, and cuDNN versions together — version drift is the single biggest source of phantom production failures. Profile data loaders before profiling models; idle GPUs cost more than slow models. Standardize on BF16 for training and reserve FP16 for inference where appropriate. Build internal benchmarks that exercise the full inference path, not just the model forward pass.
