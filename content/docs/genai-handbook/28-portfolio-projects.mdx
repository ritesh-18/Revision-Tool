## 28.1 Concept Explanation

Portfolio projects are how you prove you can do the work. A polished resume gets you a screening call; a portfolio gets you a job offer. For GenAI engineers, the bar has risen — interviewers expect to see real deployments, real observability, real cost analysis, not just a notebook with a chat demo.

This chapter walks through six portfolio projects, each progressively more ambitious. For each, the architecture, deployment, observability, scaling, CI/CD, and infra are sketched. Build at least one to depth; build all six over time.

## 28.2 Why Portfolio Projects Matter

- They demonstrate end-to-end thinking that interviews cannot fully test.
- They prove you have shipped, not just studied.
- They give you stories — "in my agent project, I encountered X and solved it with Y."
- They establish reputation. Public projects with users compound over time.

The depth-vs-breadth choice: one polished project is better than four half-finished ones. Pick one and ship it well.

## 28.3 Project 1 — AI Chat App

**Goal.** Production-quality chat application backed by an open or closed LLM, deployed to a cloud, instrumented with observability.

**Architecture.**

- FastAPI backend with SSE streaming, JWT auth, rate limiting.
- Redis for sessions and rate limits.
- Postgres for conversation history.
- LLM gateway calling OpenAI/Anthropic with provider failover.

**Deployment.** Containerized; deployed to a managed cloud (Vercel + Render, or full Kubernetes if you want extra credit).

**Observability.** OpenTelemetry across frontend and backend. Grafana dashboard with TTFT, error rate, token usage, cost.

**Scaling.** Demonstrate handling 100 concurrent users. Add autoscaling rules and document the choice.

**CI/CD.** GitHub Actions: build, test, deploy on main.

**Infra.** Terraform for cloud resources.

**What to demonstrate.** Streaming, cancellation, retries, observability, cost dashboard. Not just "it works" but "I know why each piece is there."

## 28.4a Project Skeleton With an Eval Harness 🔧

Project 2 asks for "an eval harness with at least 50 questions" and "eval gates" in CI. This section gives you a skeleton that does both, so the eval becomes the backbone of the project rather than something added at the end.

### Repository layout

| Path | Contents |
|---|---|
| `app/ingest/` | Loaders, structure-aware chunker, embedding job |
| `app/rag/answer.py` | One async function: question in, answer with citations and timings out |
| `app/api/` | FastAPI router with SSE streaming |
| `evals/golden.jsonl` | Test cases, one JSON object per line |
| `evals/run.py` | The harness below |
| `evals/thresholds.json` | Minimum scores that CI enforces |
| `evals/reports/` | One JSON report per run, committed for history |
| `docs/architecture.md` | Diagram, decisions and their alternatives |

**Why this split matters.** The harness calls the same `answer()` function the API uses. If the eval goes through a separate code path, it measures something you do not ship.

### The test case format

```json
{"id":"q017","question":"What is the refund window for annual plans?","expectedSourceIds":["billing-faq#refunds"],"referenceAnswer":"30 days from purchase.","tags":["billing","single-hop"]}
{"id":"q042","question":"Does the API support SOAP?","expectedSourceIds":[],"referenceAnswer":"NOT_IN_CORPUS","tags":["unanswerable"]}
```

Include unanswerable questions on purpose (about 10% of the set). A RAG system that confidently answers questions its corpus cannot support is the most common failure, and only these cases catch it.

### The harness

```python
# evals/run.py  — run with: uv run python -m evals.run
import asyncio
import json
import math
import sys
import time
from collections.abc import Awaitable, Callable, Sequence
from pathlib import Path
from statistics import fmean

from openai import AsyncOpenAI
from pydantic import BaseModel, ConfigDict
from pydantic.alias_generators import to_camel

from app.rag.answer import RagResult, answer  # the same function the API calls


class Case(BaseModel):
    # golden.jsonl uses camelCase keys; map them onto snake_case fields
    model_config = ConfigDict(alias_generator=to_camel)

    id: str
    question: str
    expected_source_ids: list[str]
    reference_answer: str
    tags: list[str]


# RagResult (defined next to answer()) has: text, retrieved_ids, cited_ids, contexts, latency_ms, cost_usd

judge = AsyncOpenAI()
cases = [Case.model_validate_json(line) for line in Path("evals/golden.jsonl").read_text("utf-8").splitlines() if line]
thresholds: dict[str, float] = json.loads(Path("evals/thresholds.json").read_text("utf-8"))


def recall_at_k(exp: list[str], got: list[str], k: int) -> float | None:
    return None if not exp else sum(i in got[:k] for i in exp) / len(exp)


def citation_precision(exp: list[str], cited: list[str]) -> float | None:
    return None if not cited else sum(i in exp for i in cited) / len(cited)


def percentile(xs: Sequence[float], p: float) -> float:
    s = sorted(xs)
    return s[max(0, math.ceil(p / 100 * len(s)) - 1)]


def mean(xs: Sequence[float | None]) -> float:
    values = [x for x in xs if x is not None]
    return fmean(values) if values else 0.0


async def faithfulness(c: Case, r: RagResult) -> float:
    context = "\n---\n".join(r.contexts)
    res = await judge.chat.completions.create(
        model="gpt-4o-mini",
        temperature=0,
        response_format={"type": "json_object"},
        messages=[{
            "role": "user",
            "content": (
                "Score 1-5 how well every claim in ANSWER is supported by CONTEXT. "
                "If the reference says NOT_IN_CORPUS, score 5 only if the answer declines. "
                'Reply as JSON: {"score": n, "reason": "..."}\n\n'
                f"QUESTION: {c.question}\nREFERENCE: {c.reference_answer}\nCONTEXT:\n{context}\nANSWER: {r.text}"
            ),
        }],
    )
    return float(json.loads(res.choices[0].message.content or "{}").get("score", 0))


async def map_pool[T, R](items: Sequence[T], n: int, fn: Callable[[T], Awaitable[R]]) -> list[R]:
    """Like asyncio.gather, but with at most n calls in flight."""
    sem = asyncio.Semaphore(n)

    async def run(item: T) -> R:
        async with sem:
            return await fn(item)

    return await asyncio.gather(*(run(i) for i in items))  # results keep input order


async def score(c: Case) -> dict:
    r = await answer(c.question)
    return {
        "id": c.id, "tags": c.tags,
        "recall_at_5": recall_at_k(c.expected_source_ids, r.retrieved_ids, 5),
        "citation_precision": citation_precision(c.expected_source_ids, r.cited_ids),
        "faithfulness": await faithfulness(c, r),
        "latency_ms": r.latency_ms, "cost_usd": r.cost_usd,
    }


async def main() -> int:
    rows = await map_pool(cases, 4, score)

    summary: dict[str, float] = {
        "n": len(rows),
        "recall_at_5": mean([r["recall_at_5"] for r in rows]),
        "citation_precision": mean([r["citation_precision"] for r in rows]),
        "faithfulness": mean([r["faithfulness"] for r in rows]),
        "p50_latency_ms": percentile([r["latency_ms"] for r in rows], 50),
        "p95_latency_ms": percentile([r["latency_ms"] for r in rows], 95),
        "cost_per_1k_queries_usd": mean([r["cost_usd"] for r in rows]) * 1000,
    }

    reports = Path("evals/reports")
    reports.mkdir(parents=True, exist_ok=True)
    (reports / f"{int(time.time() * 1000)}.json").write_text(json.dumps({"summary": summary, "rows": rows}, indent=2))
    for k, v in summary.items():
        print(f"{k:<26}{v:>12.3f}")

    # thresholds.json holds minimums for quality metrics, e.g. recall_at_5, faithfulness
    failures = [k for k, minimum in thresholds.items() if summary[k] < minimum]
    if failures:
        print("Eval gate failed:", ", ".join(failures), file=sys.stderr)
        return 1
    return 0


if __name__ == "__main__":
    sys.exit(asyncio.run(main()))
```

The CI gate is then one step in GitHub Actions:

```yaml
- name: RAG eval gate
  run: uv run python -m evals.run
  env:
    OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

### Edge cases and honest caveats

- **Judge cost and flakiness.** Every CI run pays for N judge calls, and the same output can score 4 one run and 5 the next. Use a cheap judge model, temperature 0, and gate on the mean over the whole set, not on individual cases. For prompt changes, run the full set. For unrelated code changes, run a 20-case smoke subset.
- **Recall is undefined for unanswerable cases.** That is why `recall_at_k` returns `None` and `mean` skips `None` values. Track a separate "declined correctly" rate for those cases.
- **Overfitting to the golden set.** If you tune prompts until the 50 cases pass, the score stops meaning anything. Keep a held-out set of 20 cases that you only run before a release.
- **Report slices, not just averages.** Break results down by `tags`. "Multi-hop recall 0.55" is a far more useful finding than an overall 0.82.
- **Thresholds that drift.** Starting thresholds should sit a few points below the current baseline. Raise them when you improve, so a regression is caught relative to where you are now.

Chapter 17 ([MLOps for GenAI](/docs/genai-handbook/17-mlops-for-genai)) covers eval pipelines at organisation scale. This harness is the portfolio-sized version.

## 28.6a Latency Breakdown for a Real-Time Voice Agent 🔧

Project 4 says "latency budgets dominate" and asks for end-to-end latency from user speech to assistant audio. This section shows where that time goes and how to measure it per stage with LiveKit Agents. A per-stage breakdown is the most convincing artefact a voice project can show.

### Problem: why one latency number is not enough

**Why.** People in conversation typically leave a gap of only about 200 ms between turns, a pattern found across many languages (Stivers et al., 2009). A voice agent will not match that, but every extra few hundred milliseconds makes it feel slower. "Our latency is 1.4 s" tells a reviewer nothing about which stage to fix. "End-of-utterance 500 ms, TTFT 550 ms, TTS first byte 200 ms, transport about 150 ms" tells them exactly where to look.

### Mechanism: the stages of one turn

<Mermaid chart={`sequenceDiagram
  participant U as User (browser or phone)
  participant L as LiveKit room (WebRTC)
  participant A as Agent worker
  participant S as Streaming STT
  participant M as LLM
  participant T as Streaming TTS
  U->>L: speech audio frames (uplink about 50 to 100 ms)
  L->>A: audio frames
  A->>S: stream audio
  S-->>A: interim then final transcript
  Note over A: VAD silence plus turn detector decide the turn ended<br/>(end-of-utterance delay, about 300 to 700 ms)
  A->>M: transcript plus chat context
  M-->>A: first token (TTFT, about 300 to 800 ms)
  A->>T: first sentence of the reply
  T-->>A: first audio chunk (TTFB, about 100 to 300 ms)
  A->>L: audio frames
  L->>U: playback starts (downlink about 50 to 100 ms)`} />

The ranges are typical planning figures for a cascaded STT, LLM and TTS pipeline, not guarantees. Measure your own. The perceived delay is roughly end-of-utterance delay plus LLM TTFT plus TTS TTFB, plus network transport each way.

### Implementation: collect per-turn metrics

LiveKit Agents emits a `metrics_collected` event with typed metrics: `EOUMetrics` (`end_of_utterance_delay`, `transcription_delay`), `LLMMetrics` (`ttft`, `tokens_per_second`) and `TTSMetrics` (`ttfb`). Group them by `speech_id` to get one row per agent turn.

```python
from collections import defaultdict
from livekit.agents import AgentSession, MetricsCollectedEvent, metrics

turns: dict[str, dict[str, float]] = defaultdict(dict)

def attach_latency_tracking(session: AgentSession) -> None:
    @session.on("metrics_collected")
    def _on_metrics(ev: MetricsCollectedEvent) -> None:
        m = ev.metrics
        metrics.log_metrics(m)
        sid = getattr(m, "speech_id", None)
        if sid is None:
            return
        if isinstance(m, metrics.EOUMetrics):
            turns[sid]["eou"] = m.end_of_utterance_delay
            turns[sid]["stt"] = m.transcription_delay
        elif isinstance(m, metrics.LLMMetrics):
            turns[sid]["ttft"] = m.ttft
        elif isinstance(m, metrics.TTSMetrics):
            turns[sid]["tts_ttfb"] = m.ttfb

        t = turns[sid]
        if {"eou", "ttft", "tts_ttfb"} <= t.keys():
            total = t["eou"] + t["ttft"] + t["tts_ttfb"]
            # Ship this to Prometheus, Langfuse or your own table, then plot p50 and p95 per stage.
            print(f"turn={sid} eou={t['eou']:.2f}s ttft={t['ttft']:.2f}s "
                  f"tts={t['tts_ttfb']:.2f}s total={total:.2f}s")
            turns.pop(sid)
```

Call `attach_latency_tracking(session)` in your entrypoint before `session.start(...)`. The Node SDK exposes the same metrics with millisecond fields (`endOfUtteranceDelayMs`, `ttftMs`, `ttfbMs`).

### What to put in the README

| Stage | p50 | p95 | What you changed |
|---|---|---|---|
| End of utterance | your number | your number | Turn detector model, endpointing delay |
| LLM TTFT | your number | your number | Shorter prompt, faster model, same region |
| TTS first byte | your number | your number | Streaming TTS, sentence-level chunking |
| Total (server side) | your number | your number | |

### Levers, in the order they usually pay off

1. **End-of-utterance tuning.** Silence-only VAD forces a choice between cutting people off (short timeout) and feeling slow (long timeout). A semantic turn detector, such as LiveKit's open-weights model, uses the transcript to tell "my number is nine eight..." apart from a finished sentence, so you can keep the timeout short without more interruptions.
2. **Colocation.** Put the agent worker in the same region as the STT, LLM and TTS endpoints. Cross-region round trips get added to every stage.
3. **Prompt size.** TTFT grows with input length. Trim the system prompt, cap chat history, and keep static instructions as a cacheable prefix.
4. **Start TTS on the first sentence.** Do not wait for the full LLM reply.
5. **Speech-to-speech models.** A single realtime model removes the STT and TTS hops, at the cost of less control over each stage (see [Chapter 30](/docs/genai-handbook/30-future-of-genai)).

### Edge cases

- **Interruptions skew the averages.** When the user barges in, the turn is cancelled and may never record TTS metrics. Count cancelled turns separately, and track the false-interruption rate as its own metric.
- **The first turn is slower.** Cold connections and model warm-up inflate turn 1. Report it separately or exclude it.
- **Server metrics leave out the client.** WebRTC jitter buffers and device audio add delay that the agent never sees. For a full end-to-end figure, record a few calls and measure from the end of user speech to the start of agent audio in the recording.

## 28.9a Making the Evidence Credible 🔧

The checklist above says what to include. This section covers how to present each item so a reviewer believes it. Reviewers skim, and one vague number makes them doubt the rest.

### Eval results that hold up

**What reviewers check.** The dataset size, where the cases came from, the metric definitions and a baseline. "95% accuracy" with none of these is ignored, or worse, it reads as a red flag.

**How to present it.** One small table with a baseline row and one row per change, followed by a single sentence on method: "62 questions (40 from real usage logs, 22 hand-written edge cases, 6 unanswerable). Faithfulness judged by an LLM rubric validated against 30 hand labels with 87% agreement." Link to `evals/golden.jsonl` so the cases can be inspected.

**Mistake.** Reporting only the final configuration. The improvement from a baseline is the story.

### Latency and cost numbers

**What reviewers check.** Percentiles, not averages, and the conditions of the measurement.

**How to present it.** "p50 TTFT 420 ms, p95 1.1 s, measured over 500 requests with k6 at 20 concurrent users, server in ap-south-1, model X." Cost as cost per 1,000 queries or per conversation, calculated from logged token usage rather than estimated. Include one sentence on what dominates the cost and what you would change at 100 times the volume.

**Mistake.** Mean latency from three manual tries on localhost.

### A live demo that survives being clicked

**Why it matters.** Many reviewers will click the demo before they read any code. A dead link costs more than having no link at all.

**How to do it.** Put it behind a spending cap: a per-IP rate limit, a daily token budget enforced in code, and a hard monthly limit set in the provider's dashboard. Show a friendly "demo budget used up for today, here's the video" page instead of an error. Seed the demo with three example prompts that show the best paths, and keep a 2-minute video as a fallback.

**Edge case.** A public LLM endpoint attracts abuse within days. Never ship the demo without the token budget.

### A README with architecture

**How to structure it.** In this order: a one-line summary, the demo link and video, an architecture diagram (Mermaid renders on GitHub), the results table, decisions and tradeoffs, how to run it, limitations, and next steps. Reviewers read the top screen and decide whether to continue, so put the numbers there.

**Mistake.** Starting with installation steps. Nobody installs a project before they know why it is interesting.

## 28.10 Build Approach

A schedule that works:

- **Week 1.** Scope, requirements, architecture sketch. Set up the repo, CI, basic skeleton.
- **Week 2-3.** Core functionality. Make the happy path work end to end.
- **Week 4.** Observability, eval, error handling, edge cases.
- **Week 5.** Polish, write the README, record a demo.
- **Week 6.** Publish. Write a blog post. Share for feedback.

Six weeks per project; one project per quarter if working part-time on top of a job.

## 28.11a Writing the Project Up: Blog Posts and LinkedIn 🔧

The list above names where to publish. What gets read and remembered depends on how the write-up is built, and the shape differs by channel.

### The blog post: one problem, told as an investigation

**What works.** A post about one hard problem gets read. A post covering everything you built does not. "How I cut my voice agent's response delay from 1.6 s to 0.9 s" beats "Building a voice AI assistant with LiveKit".

**Structure.**
1. **The hook (2 to 3 sentences).** The symptom and the number: "Users said the agent felt rude. It interrupted 1 in 6 turns."
2. **Context.** The architecture in one diagram, and only the parts relevant to the problem.
3. **The investigation.** What you measured, what you first suspected, what the data showed. Include the wrong turns, because they are what makes the post credible.
4. **The fix.** Code snippets of 10 to 30 lines, not whole files.
5. **Results.** A before and after table with the method.
6. **What I would do differently.** One or two honest points.

**Length.** 1,200 to 2,000 words is enough. Publish on your own domain or a dev blog platform, and cross-post if you like, using a canonical link back to the original.

### The LinkedIn post: one result and one visual

**What works.** Short text, a specific number, and a demo video or a screenshot of a diagram. The aim is for someone to click through to the repo or the post.

```text
My voice agent kept interrupting people mid-sentence.

Silence-based endpointing treated every pause as "done talking",
e.g. while someone read out a phone number.

What fixed it:
-> logged per-stage latency for every turn (end-of-utterance, LLM TTFT, TTS)
-> added a semantic turn detector on top of VAD
-> moved static instructions into a cached prompt prefix

Result on 40 recorded test calls: false interruptions 17% -> 5%,
median response delay 1.6 s -> 0.9 s.

Write-up with code: <link>
Repo: <link>
```

The numbers above are placeholders. Use your measured ones.

### Common mistakes

- **Announcement posts without substance.** "Excited to share my new project!" with no problem and no number.
- **Hype vocabulary.** "Revolutionary", "game-changing". Engineers stop reading.
- **Claiming more than you measured.** Interviewers read these posts and ask about them.
- **Posting once.** A short series (the problem, the fix, the eval) gets more reach and gives you more to talk about in interviews.

## 28.11b Open-Source Contribution Strategy ➕

Publishing your own projects shows you can build. Contributing to projects others depend on shows you can read unfamiliar code, work with maintainers and meet a review bar you do not control. The chapter does not cover this, and it carries a lot of weight with AI startups that build on open-source stacks.

### What interviewers probe

Whether the contribution was meaningful (a bug fix or feature that was merged) or cosmetic, whether you understood the codebase around your change, and how you handled review feedback.

### Why it matters

A merged pull request into a project such as LiveKit Agents, LangGraph, vLLM or Langfuse is reviewed evidence from strangers that your code meets their bar. It also shows that you understand the tools on a job description at the level of their internals.

### How to do it well: the contribution ladder

1. **Pick projects you already use at work or in your portfolio.** You have real context and real bugs to report. For this reader, that might be LiveKit Agents (Python), LangGraph, a FastAPI integration or an STT/TTS plugin.
2. **Start with a precise issue.** A minimal reproduction, versions, and expected vs actual behaviour. Maintainers remember good bug reports.
3. **Docs and examples next.** Fix a wrong snippet you hit, or add a missing example, such as a Python version of an example that only exists for another language. These merge quickly and teach you the review process.
4. **Then tests and bug fixes.** Look for "good first issue" or "help wanted" labels, comment that you are working on one before you start, and keep the pull request small.
5. **Finally a feature or plugin.** Discuss the design in an issue first. Large, unannounced pull requests are often closed unread.

**How to talk about it.** "I found that the Python agents SDK dropped metrics for interrupted turns, wrote a reproduction, fixed it in a 40-line PR and added a test. The maintainer asked me to change the event ordering, which taught me how their pipeline schedules TTS." That is a deep-dive story by itself. (This is an illustrative example, not a real PR.)

### Common mistakes

- **Typo pull requests made only to be listed as a contributor.** Reviewers can see the diff size.
- **Abandoning a pull request after review comments.** It reads worse than never opening one.
- **Spreading thin.** Five pull requests to one project build a relationship and real knowledge. Five pull requests to five projects build neither.
- **Ignoring the contribution guide.** Commit conventions, a CLA and test requirements are part of the bar.

## 28.12 Avoiding Portfolio Anti-Patterns

- **Pure notebook demos** with no deployment.
- **No observability** or eval — "it works, trust me."
- **Copies of existing tutorials** without distinctive contribution.
- **Over-engineering** for a portfolio scale (you do not need Istio).
- **Half-finished projects** abandoned mid-way.

## 28.13 Tradeoffs

| Choice | Win | Cost |
|---|---|---|
| Deep on one project | Memorable, demonstrates rigor | Less breadth |
| Many small projects | More keywords | Each is shallow |
| Bleeding-edge tech | Distinctive | Possibly unreliable |
| Boring choices | Reliable, employable | Less differentiating |

## 28.14 Interview Use of Portfolio

Bring the portfolio into interviews. "When discussing system design, I encountered this exact problem in my X project — here's how I solved it." Specific, credible, prepared.

## 28.15 Common Mistakes

- Building yet another generic chatbot. Differentiate.
- Skipping deployment.
- Skipping observability.
- No documentation; reviewers can't tell what you built.
- Hidden in a private repo.

## 28.16 Enterprise Best Practices

(For hiring managers reviewing portfolios.) Look for: end-to-end ownership, evidence of measurement, willingness to address failure modes, documentation quality. A polished portfolio is a strong signal of how the candidate will work on the job.
