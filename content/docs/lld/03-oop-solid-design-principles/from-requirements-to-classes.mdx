title: "3.11 From requirements to classes"
---

In an LLD round you get a paragraph of requirements. Turning that into classes is a repeatable process.

## 3.11.1 The process

1. **Clarify** scope: ask 3–5 questions (users, core flows, limits, what's out of scope).
2. **Nouns → candidate classes/fields.** Underline every noun. Some become classes, some become fields, some are just synonyms or out of scope.
3. **Verbs → methods.** Each verb becomes a method on the class that owns the data it needs (put behaviour where the data is).
4. **Relationships.** For each pair of classes: is-a, owns, has-shared, uses?
5. **Find the axis of change** and put an interface there (OCP).
6. **Sketch** a class diagram, then code the main flow first.

## 3.11.2 Worked example: a brokerage watchlist

> *"A user can create up to 5 watchlists. Each watchlist has a name and holds up to 20 instruments. An instrument has a symbol, an exchange (NSE/BSE) and a last traded price. Users can add or remove instruments and rename watchlists. The same instrument can be in multiple watchlists. Users can sort a watchlist by symbol or by percentage change. When a price updates, every watchlist containing that instrument should show the new price."*

**Noun analysis**

| Noun | Decision | Reason |
|---|---|---|
| user | `User` class | owns watchlists, enforces the "max 5" rule |
| watchlist | `Watchlist` class | has behaviour (add, remove, rename, sort) |
| name | field on `Watchlist` | a simple value |
| instrument | `Instrument` class | shared across watchlists, has price state |
| symbol, exchange | fields on `Instrument` | values; exchange is a union type |
| last traded price, % change | fields on `Instrument` | updated by price feed |
| price update | `PriceFeed` | the source of change, updates instruments |
| sort order | `SortStrategy` interface | the obvious axis of variation |

**Verb analysis**

| Verb | Method | Owner |
|---|---|---|
| create watchlist | `createWatchlist(name)` | `User` |
| add / remove instrument | `add(i)`, `remove(symbol)` | `Watchlist` |
| rename | `rename(name)` | `Watchlist` |
| sort | `view(strategy)` | `Watchlist` |
| price updates | `publish(symbol, price)` → `instrument.updatePrice(p)` | `PriceFeed`, `Instrument` |

**Relationships**

- `User *-- Watchlist` (composition: watchlists die with the user)
- `Watchlist o-- Instrument` (aggregation: instruments are shared)
- `PriceFeed --> Instrument` (association via a registry)
- `BySymbol ..|> SortStrategy`, `ByChange ..|> SortStrategy` (realization)

Because instruments are *shared objects*, "every watchlist shows the new price" comes for free. No observer wiring is needed for this scope. That's a nice YAGNI point to make out loud.

```ts
type Exchange = 'NSE' | 'BSE';

class Instrument {
  #ltp: number;
  constructor(readonly symbol: string, readonly exchange: Exchange, readonly prevClose: number) {
    this.#ltp = prevClose;
  }
  get ltp(): number {
    return this.#ltp;
  }
  changePct(): number {
    return ((this.#ltp - this.prevClose) / this.prevClose) * 100;
  }
  updatePrice(price: number): void {
    if (price <= 0) throw new RangeError(`Bad price for ${this.symbol}`);
    this.#ltp = price;
  }
}

interface SortStrategy {
  readonly label: string;
  compare(a: Instrument, b: Instrument): number;
}
const BySymbol: SortStrategy = { label: 'symbol', compare: (a, b) => a.symbol.localeCompare(b.symbol) };
const ByChangeDesc: SortStrategy = { label: 'change', compare: (a, b) => b.changePct() - a.changePct() };

class Watchlist {
  static readonly MAX_ITEMS = 20;
  readonly #items = new Map<string, Instrument>();
  constructor(private name: string) {}

  add(instrument: Instrument): void {
    if (this.#items.has(instrument.symbol)) return;
    if (this.#items.size >= Watchlist.MAX_ITEMS) throw new Error(`${this.name} is full`);
    this.#items.set(instrument.symbol, instrument);
  }
  remove(symbol: string): void {
    this.#items.delete(symbol);
  }
  rename(name: string): void {
    if (!name.trim()) throw new Error('Name required');
    this.name = name.trim();
  }
  view(strategy: SortStrategy): string {
    const rows = [...this.#items.values()]
      .sort(strategy.compare)
      .map((i) => `${i.symbol} ${i.ltp} (${i.changePct().toFixed(2)}%)`);
    return `${this.name} by ${strategy.label}: ${rows.join(', ')}`;
  }
}

class User {
  static readonly MAX_WATCHLISTS = 5;
  readonly #watchlists: Watchlist[] = [];
  constructor(readonly id: string) {}
  createWatchlist(name: string): Watchlist {
    if (this.#watchlists.length >= User.MAX_WATCHLISTS) throw new Error('Watchlist limit reached');
    const wl = new Watchlist(name);
    this.#watchlists.push(wl);
    return wl;
  }
}

class PriceFeed {
  readonly #registry = new Map<string, Instrument>();
  register(i: Instrument): Instrument {
    this.#registry.set(i.symbol, i);
    return i;
  }
  publish(symbol: string, price: number): void {
    this.#registry.get(symbol)?.updatePrice(price);
  }
}

// --- wiring & demo ---
const feed = new PriceFeed();
const infy = feed.register(new Instrument('INFY', 'NSE', 1500));
const tcs = feed.register(new Instrument('TCS', 'NSE', 4000));
const hdfc = feed.register(new Instrument('HDFCBANK', 'NSE', 1600));

const user = new User('U-1');
const it = user.createWatchlist('IT');
const core = user.createWatchlist('Core');
it.add(tcs);
it.add(infy);
core.add(infy);
core.add(hdfc);

feed.publish('INFY', 1545);
feed.publish('TCS', 3960);
feed.publish('HDFCBANK', 1640);

console.log(it.view(BySymbol));
console.log(it.view(ByChangeDesc));
core.rename('  Core Holdings ');
console.log(core.view(ByChangeDesc));

for (let i = 0; i < 3; i++) user.createWatchlist(`W${i}`);
try {
  user.createWatchlist('One too many');
} catch (err) {
  if (err instanceof Error) console.log(err.message);
}
```

**How to present this.** "I pulled nouns into classes and fields, verbs into methods on the class that owns the data, and I made sorting a strategy because it's the obvious thing to extend. Instruments are shared by reference, so a price update shows everywhere without extra wiring. If prices came over a socket to many clients, I'd add an observer on `Instrument`, but it isn't needed at this scope."

## 3.11.3 Common mistakes in this step

- Making every noun a class (`Name`, `Price` classes with no behaviour). Primitive obsession has an opposite, and this is it.
- Putting all verbs on a `WatchlistManager`, which becomes a god class while `Watchlist` is left as a bag of data (an *anemic domain model*).
- Missing the limits (5 watchlists, 20 items). Interviewers deliberately plant rules like these to see whether you enforce invariants.
