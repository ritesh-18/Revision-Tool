---
title: "3.6 Cohesion and coupling"
---

These two words sum up most of the principles above.

- **Cohesion**: how closely the things *inside* a module belong together. Aim **high**.
- **Coupling**: how much a module depends on the *internals* of others. Aim **low**.

| | Low coupling | High coupling |
|---|---|---|
| **High cohesion** | ✅ The goal: focused classes talking via small interfaces | Focused classes, but they reach into each other's fields |
| **Low cohesion** | Grab-bag `Utils` classes; loose but meaningless | ❌ The big ball of mud |

**Types of coupling, from worst to best** (worth naming in interviews):

1. **Content coupling**: one class modifies another's private data.
2. **Common/global coupling**: both read and write a shared mutable global (`globalConfig.feeRate = ...`).
3. **Control coupling**: passing a flag that tells the callee *what to do* (`export(data, true, false)`).
4. **Stamp coupling**: passing a whole object when only one field is used.
5. **Data coupling**: passing just the primitive data needed. Best.

**Low-cohesion example and fix**

```ts
// ❌ Low cohesion: unrelated jobs in one "service"
class TradeUtils {
  formatInr(n: number) {}
  isMarketOpen(date: Date) {}
  hashPassword(p: string) {}
  calculateStt(turnover: number) {}
}
```

Split by concept: `CurrencyFormatter`, `MarketCalendar`, `PasswordHasher`, `ChargesCalculator`. Each now has one reason to change, and a module that only needs market hours no longer depends on the crypto code.

**Quick heuristics**

- If most methods use most fields, cohesion is high. If methods split into groups that each use a separate set of fields, that's two classes hiding in one.
- If changing class A's private field forces a change in class B, coupling is too high.
- Depend on interfaces, pass the minimum data, and avoid shared mutable state.
