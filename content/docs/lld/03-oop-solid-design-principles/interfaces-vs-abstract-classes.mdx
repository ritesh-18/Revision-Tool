---
title: "3.7 Interfaces vs abstract classes"
---

TypeScript gives you both. Here is how to choose.

| Question | `interface` | `abstract class` |
|---|---|---|
| Exists at runtime? | No (erased) | Yes (can use `instanceof`) |
| Can hold implementation? | No | Yes: shared methods and fields |
| Constructor / shared state? | No | Yes |
| Multiple per class? | Many (`implements A, B`) | Only one (`extends`) |
| Works with plain objects? | Yes (structural) | No, needs `extends` or careful shaping |
| Protected members? | No | Yes |
| Best for | Contracts, ports, DI tokens, capabilities | Template method, shared skeleton logic |

**Decision guide**

1. Is it a contract between modules (repository, notifier, payment gateway)? → **interface**.
2. Do several implementations share real code *and* a fixed algorithm? → **abstract class** (usually implementing an interface too).
3. Does a class need several capabilities? → **multiple interfaces**.
4. Do you need `instanceof` at runtime? → abstract class, or a discriminant field on an interface.
5. Unsure? → start with an interface. Adding an abstract base later is easy.

A common production shape is both: an interface for callers, and an abstract class for implementers who want the boilerplate.

```ts
interface ReportExporter {
  export(title: string, rows: string[][]): string;
}

abstract class BaseExporter implements ReportExporter {
  // Fixed skeleton (template method)
  export(title: string, rows: string[][]): string {
    const body = rows.map((r) => this.row(r)).join(this.separator());
    return `${this.header(title)}${this.separator()}${body}`;
  }
  protected abstract header(title: string): string;
  protected abstract row(cells: string[]): string;
  protected separator(): string {
    return '\n';
  }
}

class CsvExporter extends BaseExporter {
  protected override header(title: string): string {
    return `# ${title}`;
  }
  protected override row(cells: string[]): string {
    return cells.join(',');
  }
}

class MarkdownExporter extends BaseExporter {
  protected override header(title: string): string {
    return `**${title}**`;
  }
  protected override row(cells: string[]): string {
    return `| ${cells.join(' | ')} |`;
  }
}

// A one-off exporter doesn't need the base class at all
const jsonExporter: ReportExporter = {
  export: (title, rows) => JSON.stringify({ title, rows }),
};

const rows = [
  ['INFY', '10'],
  ['TCS', '2'],
];
const exporters: ReportExporter[] = [new CsvExporter(), new MarkdownExporter(), jsonExporter];
for (const e of exporters) console.log(e.export('Holdings', rows));
console.log(`csv is BaseExporter: ${exporters[0] instanceof BaseExporter}`);
```

```text
# Holdings
INFY,10
TCS,2
**Holdings**
| INFY | 10 |
| TCS | 2 |
{"title":"Holdings","rows":[["INFY","10"],["TCS","2"]]}
csv is BaseExporter: true
```

**NestJS note.** Interfaces vanish at runtime, so Nest can't inject by interface type. You either inject with a token (`@Inject(PAYMENT_GATEWAY)`) or use an abstract class as the token. That's a runtime concern, not a design reason to prefer abstract classes.
