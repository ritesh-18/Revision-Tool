---
title: "3.4 Composition over inheritance"
---

**Intuition.** Inheritance says "I *am* one of those". Composition says "I *have* one of those and delegate to it". Composition lets you mix behaviours at runtime and avoids class explosions.

## 3.4.1 The problem: two dimensions of variation

Notifications vary by **channel** (SMS, email) *and* by **policy** (retry, rate-limit, quiet hours). With inheritance you end up with this:

```ts
// ❌ Class explosion: channels × policies
class SmsNotifier { send() {} }
class RetryingSmsNotifier extends SmsNotifier {}
class RateLimitedSmsNotifier extends SmsNotifier {}
class RetryingRateLimitedSmsNotifier extends RetryingSmsNotifier {} // copy rate-limit logic here?
class EmailNotifier { send() {} }
class RetryingEmailNotifier extends EmailNotifier {}                // retry logic duplicated
// ...and one more class for every new policy × channel pair
```

## 3.4.2 The refactor: wrap behaviours around a channel

<Mermaid chart={`classDiagram
  class Channel {
    <<interface>>
    +send(to, msg) Promise~void~
  }
  Channel <|.. SmsChannel
  Channel <|.. EmailChannel
  Channel <|.. WithRetry
  Channel <|.. WithRateLimit
  WithRetry o-- Channel : wraps
  WithRateLimit o-- Channel : wraps`} />

```ts
interface Channel {
  readonly label: string;
  send(to: string, msg: string): Promise<void>;
}

class FlakySmsChannel implements Channel {
  readonly label = 'sms';
  #attempts = 0;
  async send(to: string, msg: string): Promise<void> {
    this.#attempts++;
    if (this.#attempts < 3) throw new Error(`SMS gateway timeout (attempt ${this.#attempts})`);
    console.log(`sms -> ${to}: ${msg}`);
  }
}

class EmailChannel implements Channel {
  readonly label = 'email';
  async send(to: string, msg: string): Promise<void> {
    console.log(`email -> ${to}: ${msg}`);
  }
}

class WithRetry implements Channel {
  constructor(private readonly inner: Channel, private readonly maxAttempts: number) {}
  get label(): string {
    return `retry(${this.inner.label})`;
  }
  async send(to: string, msg: string): Promise<void> {
    for (let i = 1; ; i++) {
      try {
        return await this.inner.send(to, msg);
      } catch (err) {
        const reason = err instanceof Error ? err.message : String(err);
        console.log(`  ${this.label} failed: ${reason}`);
        if (i >= this.maxAttempts) throw err;
      }
    }
  }
}

class WithRateLimit implements Channel {
  readonly #sentTo = new Map<string, number>();
  constructor(private readonly inner: Channel, private readonly perRecipient: number) {}
  get label(): string {
    return `limit(${this.inner.label})`;
  }
  async send(to: string, msg: string): Promise<void> {
    const count = this.#sentTo.get(to) ?? 0;
    if (count >= this.perRecipient) {
      console.log(`  ${this.label} dropped message to ${to}`);
      return;
    }
    this.#sentTo.set(to, count + 1);
    await this.inner.send(to, msg);
  }
}

// Mix and match at runtime, no new subclasses
const sms: Channel = new WithRateLimit(new WithRetry(new FlakySmsChannel(), 3), 1);
const email: Channel = new WithRateLimit(new EmailChannel(), 2);

console.log(sms.label);
await sms.send('+91-98xxxx', 'OTP 4821');
await sms.send('+91-98xxxx', 'OTP 9911');
await email.send('a@b.in', 'Contract note ready');
```

```text
limit(retry(sms))
  retry(sms) failed: SMS gateway timeout (attempt 1)
  retry(sms) failed: SMS gateway timeout (attempt 2)
sms -> +91-98xxxx: OTP 4821
  limit(retry(sms)) dropped message to +91-98xxxx
email -> a@b.in: Contract note ready
```

Two channels plus two policies = four small classes, and any combination works. With inheritance you'd need a class per combination. (This wrapping shape is the **Decorator** pattern.)

## 3.4.3 When inheritance is still fine

- A genuine is-a with a stable base: `abstract class Vehicle` → `Car`, `Bike` in a parking-lot design.
- Framework requirements: `class InsufficientMarginError extends Error`, NestJS exception filters.
- Template method with one or two hook points.

> **Interview line:** "I default to composition: small interfaces, behaviours injected or wrapped. I use inheritance only for a true, stable is-a with a shallow hierarchy, because deep hierarchies make every base-class change risky."
