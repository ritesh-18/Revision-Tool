## Chapter recap

- **Encapsulation** protects invariants (use `#private` and intent-revealing methods); **abstraction** hides the how behind a small contract; **inheritance** fits only a stable, shallow is-a; **polymorphism** replaces type switches when the set of variants is open.
- **SRP**: one reason to change. **OCP**: add variants by adding classes. **LSP**: subtypes must not surprise callers. **ISP**: small role interfaces. **DIP**: business code owns the interfaces, and details plug in.
- **DRY** is about knowledge, not identical-looking lines. **KISS** means few moving parts. **YAGNI** means make only the *known* axis of change pluggable, especially under machine-coding time pressure.
- Prefer **composition** (wrapping and delegating) to avoid class explosions across several dimensions.
- **Law of Demeter**: tell, don't ask, and avoid dot-chains through other objects' internals.
- Aim for **high cohesion, low coupling**, and know the coupling types from content (worst) to data (best).
- **Interfaces** for contracts and capabilities; **abstract classes** for shared skeletons. Often you'll use both.
- Relationships: dependency `..>`, association `-->`, aggregation `o--`, composition `*--`, realization `..|>`, inheritance `<|--`. Ask "do parts outlive the whole?" to separate aggregation from composition.
- Use **noun/verb analysis** to go from requirements to classes, and put behaviour where the data lives.
- Know the smells: god class, feature envy, primitive obsession, shotgun surgery, long parameter lists and boolean flags, plus their refactors.

## Interview questions on this chapter

**1. What's the difference between encapsulation and abstraction?**

<details>
<summary>Answer</summary>

Encapsulation is about *protection*: bundling data with the methods that keep it valid and hiding the state so nobody can break the invariants (a wallet balance that can't go negative). Abstraction is about *simplification*: exposing a meaningful contract and hiding implementation details (a `QuoteSource` whose callers don't know about caching). They work together: abstraction decides what the outside sees, and encapsulation enforces that nothing else gets in.

</details>

**2. Explain SRP. Isn't "a class should do one thing" enough?**

<details>
<summary>Answer</summary>

"Do one thing" is too vague, since any class can be described as doing one thing at some level. The sharper definition is *one reason to change*: one source of requirements. An invoice class that queries the DB, computes GST, builds HTML and sends email changes for the DBA, finance, design and infra teams. I'd split it into repository, tax calculator, formatter and sender, with a thin service that coordinates them.

</details>

**3. How would you add a new payment method without modifying existing code?**

<details>
<summary>Answer</summary>

Define a `PaymentMethod` (or `PaymentGateway`) interface with `pay`, and keep a registry keyed by method code. Checkout looks up the strategy and calls it. A new method (say, a BNPL provider) is a new class plus a single registration line at the composition root. That's OCP via the Strategy pattern. I'd make only the payment axis pluggable, not everything.

</details>

**4. Give a real example of an LSP violation and how you'd fix it.**

<details>
<summary>Answer</summary>

A `GiftCardPayment extends PaymentMethod` whose `refund()` throws "non-refundable". Any code that handles `PaymentMethod` and calls `refund` during cancellation will crash for gift cards, even though it type-checks. The fix is to model capabilities honestly: split `Payable` and `Refundable` interfaces, implement `Refundable` only where it's real, and let cancellation check the capability (or route to a store-credit flow). Other signs: empty overrides, or `instanceof` checks before calling parent methods.

</details>

**5. What's the relationship between ISP and LSP?**

<details>
<summary>Answer</summary>

A fat interface often *forces* LSP violations: an implementer that can't support some method ends up throwing or doing nothing. ISP fixes the cause by splitting the interface into roles (`TableExporter`, `ChartExporter`, `PasswordProtectable`), so each class implements only what it truly supports, and misuse becomes a compile-time error instead of a runtime surprise.

</details>

**6. DIP vs dependency injection vs IoC container: what's the difference?**

<details>
<summary>Answer</summary>

DIP is a *principle*: high-level modules and low-level modules both depend on abstractions, and the high-level side owns the abstraction. Dependency injection is a *technique*: pass dependencies in (usually through the constructor) instead of creating them inside. An IoC container (NestJS's DI system) is a *tool* that automates the wiring. You can follow DIP with manual DI and no container at all, and you can use a container while still violating DIP if your services inject concrete vendor classes.

</details>

**7. When would you choose an abstract class over an interface in TypeScript?**

<details>
<summary>Answer</summary>

When implementations share real code and a fixed algorithm (template method), need shared state or a constructor, need `protected` hooks, or I need a runtime type (`instanceof`, or a DI token in Nest). For pure contracts between modules, capabilities, or anything plain objects should satisfy, I use interfaces, since a class can implement many of them and they cost nothing at runtime. A common setup is both: an interface for callers and an abstract base for implementers.

</details>

**8. Aggregation vs composition: how do you decide?**

<details>
<summary>Answer</summary>

Ask whether the part makes sense and can be shared without the whole. A watchlist *aggregates* instruments: INFY exists independently and sits in many watchlists (`Watchlist o-- Instrument`). A bracket order is *composed of* its legs: they're created by the order, never shared, and meaningless without it (`BracketOrder *-- OrderLeg`). In code, composition usually means the whole constructs the parts internally; aggregation means it receives existing objects.

</details>

**9. Why "composition over inheritance"? Show where inheritance breaks down.**

<details>
<summary>Answer</summary>

Inheritance fixes behaviour at compile time along a single axis. When there are two axes (notification channel × retry/rate-limit policies), you get one subclass per combination and duplicated policy code. With composition, each policy wraps any `Channel` (`new WithRateLimit(new WithRetry(sms, 3), 1)`), giving N + M small classes that combine freely at runtime. It also avoids the fragile base class problem. I still use inheritance for a stable, shallow is-a such as a custom `Error` or a template-method base.

</details>

**10. What is the Law of Demeter, and when is a chain of calls acceptable?**

<details>
<summary>Answer</summary>

A method should only talk to its own fields, its parameters, objects it creates and itself, not reach through `client.getAccount().getWallet().getBalance()`. The fix is "tell, don't ask": `client.reserveMargin(amount)`. Chains are fine for fluent APIs that return the same kind of object (query builders, array `filter().map()`) and for navigating plain data/DTOs. The rule targets coupling to other objects' internal structure.

</details>

**11. Explain cohesion and coupling with an example from your work.**

<details>
<summary>Answer</summary>

Cohesion is how well a module's contents belong together; coupling is how much it depends on other modules' internals. A `TradeUtils` with currency formatting, market hours, password hashing and STT calculation has low cohesion, and anything importing it for one function is coupled to all of it. Splitting it into `CurrencyFormatter`, `MarketCalendar`, `PasswordHasher` and `ChargesCalculator` raises cohesion and cuts coupling. I also mention coupling types: passing boolean control flags is control coupling, and passing only the data needed is data coupling, which is the best kind.

</details>

**12. How do you avoid over-engineering in a 90-minute machine-coding round?**

<details>
<summary>Answer</summary>

Get the core flow running end to end with clean, in-memory classes first. Add interfaces only where the prompt hints at variation (pricing, payment modes, notification channels), usually one interface with two implementations. Skip generic plugin systems, DI containers, persistence layers and concurrency unless asked. Then *talk through* extensions ("swapping in Redis only changes the repository") so you get design credit without spending the time. That's YAGNI and KISS, with OCP applied only on the known axis.

</details>

**13. What's primitive obsession, and how does TypeScript help fix it?**

<details>
<summary>Answer</summary>

Using raw `string`/`number` for domain concepts: account IDs, PANs, rupees vs paise. It leads to swapped arguments and unit bugs that compile fine. TypeScript offers branded types (`type AccountId = string & { __brand: 'AccountId' }`) created through a validating factory, and value-object classes like `Money` with a private constructor and paise-based arithmetic. Validation happens once at the boundary, and the compiler blocks mix-ups afterwards.

</details>

**14. How do you go from a requirements paragraph to a class diagram?**

<details>
<summary>Answer</summary>

Clarify scope first. Then do noun analysis (nouns become candidate classes or fields, dropping synonyms and out-of-scope items) and verb analysis (verbs become methods on the class that owns the needed data). Next, decide relationships (is-a, owns, shares, uses) and multiplicities, and spot the axis of change to put behind an interface. Sketch 5–8 core classes, then code the main use case first. I also look for planted constraints like "max 5 watchlists" and enforce them as invariants.

</details>

**15. What's the difference between a god class and shotgun surgery?**

<details>
<summary>Answer</summary>

They're opposites. A god class concentrates too many responsibilities in one place, so unrelated changes collide in one file; the fix is extracting classes. Shotgun surgery scatters one responsibility across many places, so a single change (adding an order type) needs edits in many files; the fix is consolidating that knowledge into one strategy, spec or registry. Both mean responsibilities aren't aligned with reasons to change.

</details>

## Practice exercises

1. **SRP refactor.** Write (unchecked) a `ContractNoteService.generate(tradeId)` that fetches trades, computes brokerage/STT/GST/stamp duty, renders text and "emails" it. Then refactor it into focused classes with a coordinating service, and make it runnable with in-memory fakes.
2. **OCP fee engine.** Build a `ChargesEngine` for equity delivery vs intraday vs F&O, where each charge (brokerage, STT, exchange fee, GST, stamp duty) is a `Charge` implementation. Add a new "SEBI turnover fee" without editing the engine.
3. **LSP hunt.** Design `Watchlist` and a `PredefinedWatchlist` (like "NIFTY 50", which users can't edit). Show why `PredefinedWatchlist extends Watchlist` breaks LSP, then fix it with separate `ReadableWatchlist`/`EditableWatchlist` interfaces.
4. **ISP + DIP.** Model a `KycVerifier` flow that needs PAN verification, Aadhaar OTP and bank penny-drop. Different vendors support different subsets. Design role interfaces, write two fake vendors, and inject them into a `KycService`.
5. **Composition.** Extend the notifier example with a `WithQuietHours` wrapper (drop non-critical messages between 22:00 and 07:00, with the hour passed in, not read from the clock) and a `WithTemplate` wrapper. Show three different stacks.
6. **Relationships.** Draw a Mermaid class diagram for a parking lot (`ParkingLot`, `Floor`, `Spot`, `Vehicle`, `Ticket`, `PaymentStrategy`) using every relationship type at least once, and justify each arrow in one sentence.
7. **Sequence diagram.** Draw the "cancel order" flow: controller → service → exchange → wallet unblock → notifier, including an `alt` branch for "order already executed".
8. **Noun/verb analysis.** Take this prompt: *"A library has books and members. A member can borrow up to 3 books for 14 days. Late returns incur a fine of ₹5 per day. Members can reserve a book that is currently borrowed; when it's returned, the first reservation gets notified."* Produce the noun and verb tables, a class diagram and a runnable implementation (pass dates in as day numbers).
9. **Smell spotting.** Write a deliberately smelly 60-line `PortfolioManager` containing at least four smells from section 3.12. Swap with a friend (or revisit after a day), list the smells and refactor.
10. **Interview drill.** For each SOLID principle, record yourself giving a 30-second explanation using a *different* domain than this chapter (food delivery, ride hailing, OTT subscriptions). Aim for definition, example and benefit, in that order.
