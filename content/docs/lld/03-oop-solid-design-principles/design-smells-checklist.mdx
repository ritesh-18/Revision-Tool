title: "3.12 Design smells checklist"
---

A *smell* isn't a bug. It's a hint that change will hurt. Here are the six you'll be asked about most, each with a refactor.

## 3.12.1 God class

**Symptom.** One class knows and does everything: `TradingManager` with 60 methods and 25 fields.
**Why it hurts.** Every change risks everything; merge conflicts; impossible to test.
**Refactor.** Extract classes by responsibility (SRP), keep a thin facade if callers need one entry point.

```ts
// ❌
class TradingManager {
  placeOrder() {} cancelOrder() {} calculateBrokerage() {} calculateStt() {}
  sendSms() {} sendEmail() {} generateContractNote() {} exportPnlCsv() {}
  loginUser() {} resetPassword() {} fetchQuotes() {} /* ...50 more */
}
// ✅ OrderService, ChargesCalculator, NotificationService,
//    ContractNoteGenerator, ReportExporter, AuthService, QuoteService
```

## 3.12.2 Feature envy

**Symptom.** A method uses another object's data more than its own.
**Refactor.** Move the method to the class that owns the data.

```ts
// ❌ ReportService is "envious" of Position's fields
class ReportService {
  unrealisedPnl(p: Position) {
    return (p.ltp - p.avgPrice) * p.qty * (p.side === 'SHORT' ? -1 : 1);
  }
}
```

```ts
class Position {
  constructor(
    readonly symbol: string,
    private readonly side: 'LONG' | 'SHORT',
    private readonly qty: number,
    private readonly avgPrice: number,
    private ltp: number,
  ) {}
  mark(price: number): void {
    this.ltp = price;
  }
  // ✅ behaviour lives next to the data it needs
  unrealisedPnl(): number {
    const direction = this.side === 'LONG' ? 1 : -1;
    return (this.ltp - this.avgPrice) * this.qty * direction;
  }
}

class ReportService {
  line(p: Position): string {
    return `${p.symbol}: ${p.unrealisedPnl()}`;
  }
}

const long = new Position('INFY', 'LONG', 10, 1500, 1500);
const short = new Position('NIFTYFUT', 'SHORT', 50, 22000, 22000);
long.mark(1530);
short.mark(21950);
const report = new ReportService();
console.log(report.line(long));
console.log(report.line(short));
```

```text
INFY: 300
NIFTYFUT: 2500
```

## 3.12.3 Primitive obsession

**Symptom.** Domain concepts passed around as raw `string`/`number`: a `string` that is sometimes a PAN, sometimes a client ID; a `number` that is sometimes rupees, sometimes paise.
**Refactor.** Introduce value objects or branded types that validate once.

```ts
// ❌ Which string is which? Is amount in rupees or paise?
function transfer(from: string, to: string, amount: number, currency: string) {}
transfer('INR', 'ACC-1', 500, 'ACC-2'); // compiles. Oops.
```

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };
type AccountId = Brand<string, 'AccountId'>;

function accountId(raw: string): AccountId {
  if (!/^ACC-\d+$/.test(raw)) throw new Error(`Invalid account id: ${raw}`);
  return raw as AccountId;
}

class Money {
  private constructor(readonly paise: number) {}
  static rupees(r: number): Money {
    if (!Number.isFinite(r) || r < 0) throw new RangeError(`Invalid amount: ${r}`);
    return new Money(Math.round(r * 100));
  }
  plus(other: Money): Money {
    return new Money(this.paise + other.paise);
  }
  toString(): string {
    return `₹${(this.paise / 100).toFixed(2)}`;
  }
}

function transfer(from: AccountId, to: AccountId, amount: Money): string {
  return `${amount.toString()} ${from} -> ${to}`;
}

const a = accountId('ACC-1');
const b = accountId('ACC-2');
console.log(transfer(a, b, Money.rupees(499.99).plus(Money.rupees(0.01))));
// transfer('ACC-1', b, Money.rupees(1));  // compile error: string is not AccountId
try {
  accountId('INR');
} catch (err) {
  if (err instanceof Error) console.log(err.message);
}
```

```text
₹500.00 ACC-1 -> ACC-2
Invalid account id: INR
```

## 3.12.4 Shotgun surgery

**Symptom.** One logical change requires small edits in many files. Adding a new order type means touching the validator, the pricer, the UI mapper, the report and the DB enum.
**Why.** One concept's knowledge is scattered (the opposite of a god class).
**Refactor.** Pull the scattered knowledge into one place: a strategy per order type, or a single config/registry that the other modules read.

```ts
// ✅ Everything about an order type lives in one definition
interface OrderTypeSpec {
  readonly code: string;
  readonly needsPrice: boolean;
  readonly needsTrigger: boolean;
  label(): string;
}

const ORDER_TYPES: Record<string, OrderTypeSpec> = {
  MARKET: { code: 'MARKET', needsPrice: false, needsTrigger: false, label: () => 'Market' },
  LIMIT: { code: 'LIMIT', needsPrice: true, needsTrigger: false, label: () => 'Limit' },
  SL: { code: 'SL', needsPrice: true, needsTrigger: true, label: () => 'Stop-loss limit' },
};

// Validator, UI and reports all read the same spec
function validate(type: string, price?: number, trigger?: number): string {
  const spec = ORDER_TYPES[type];
  if (!spec) return `unknown type ${type}`;
  if (spec.needsPrice && price === undefined) return `${spec.label()} needs a price`;
  if (spec.needsTrigger && trigger === undefined) return `${spec.label()} needs a trigger`;
  return 'ok';
}

console.log(validate('MARKET'));
console.log(validate('LIMIT'));
console.log(validate('SL', 100));
// Adding "SL-M" is one new entry in ORDER_TYPES
ORDER_TYPES['SL-M'] = { code: 'SL-M', needsPrice: false, needsTrigger: true, label: () => 'Stop-loss market' };
console.log(validate('SL-M', undefined, 95));
```

```text
ok
Limit needs a price
Stop-loss limit needs a trigger
ok
```

## 3.12.5 Long parameter list

**Symptom.** `placeOrder(clientId, symbol, exchange, side, qty, price, trigger, product, validity, disclosedQty, tag)`: easy to swap two arguments of the same type.
**Refactor.** Introduce a parameter object (a typed command), optionally with a builder for complex ones.

```ts
// ❌ Did I pass price before trigger? qty before disclosedQty?
placeOrder('C1', 'INFY', 'NSE', 'BUY', 10, 1500, 1495, 'CNC', 'DAY', 0, 'swing');
```

```ts
type PlaceOrderCommand = {
  clientId: string;
  symbol: string;
  side: 'BUY' | 'SELL';
  qty: number;
  product: 'CNC' | 'MIS';
  price?: number;
  trigger?: number;
  validity?: 'DAY' | 'IOC';
};

function placeOrder(cmd: PlaceOrderCommand): string {
  const { validity = 'DAY' } = cmd;
  const px = cmd.price === undefined ? 'MKT' : `@${cmd.price}`;
  return `${cmd.clientId} ${cmd.side} ${cmd.qty} ${cmd.symbol} ${px} ${cmd.product}/${validity}`;
}

console.log(placeOrder({ clientId: 'C1', symbol: 'INFY', side: 'BUY', qty: 10, product: 'CNC', price: 1500 }));
console.log(placeOrder({ clientId: 'C2', symbol: 'SBIN', side: 'SELL', qty: 25, product: 'MIS', validity: 'IOC' }));
```

```text
C1 BUY 10 INFY @1500 CNC/DAY
C2 SELL 25 SBIN MKT MIS/IOC
```

## 3.12.6 Boolean flag arguments

**Symptom.** `generateReport(data, true, false)`. The call site is unreadable, and the function secretly does two or more different things (control coupling).
**Refactor.** Split into separate, well-named functions, or replace the flags with a union/strategy.

```ts
// ❌ What do true/false mean here?
exportTrades(trades, true, false);
function exportTrades(t: Trade[], asPdf: boolean, includeCharges: boolean) {
  if (asPdf) { /* ... */ } else { /* ... */ }
  if (includeCharges) { /* ... */ }
}
```

```ts
type Trade = { symbol: string; qty: number; charges: number };
type Format = 'csv' | 'text';

function formatTrade(t: Trade, format: Format, withCharges: boolean): string {
  const cols = withCharges ? [t.symbol, t.qty, t.charges] : [t.symbol, t.qty];
  switch (format) {
    case 'csv':
      return cols.join(',');
    case 'text':
      return cols.join(' ');
  }
}

// Intent-revealing entry points instead of exportTrades(trades, true, false)
const exportForClient = (ts: Trade[]) => ts.map((t) => formatTrade(t, 'text', false)).join('; ');
const exportForAccounts = (ts: Trade[]) => ts.map((t) => formatTrade(t, 'csv', true)).join('; ');

const trades: Trade[] = [
  { symbol: 'INFY', qty: 10, charges: 18.5 },
  { symbol: 'TCS', qty: 2, charges: 9.2 },
];
console.log(exportForClient(trades));
console.log(exportForAccounts(trades));
```

```text
INFY 10; TCS 2
INFY,10,18.5; TCS,2,9.2
```

The internal helper still takes an options argument, but it's a named union type, and callers use functions whose names say what they do.

## 3.12.7 Quick reference

| Smell | Tell-tale sign | Refactor |
|---|---|---|
| God class | 500+ lines, vague name | Extract class, facade |
| Feature envy | `other.x`, `other.y`, `other.z` in one method | Move method |
| Primitive obsession | `string` everywhere, unit bugs | Value object, branded type |
| Shotgun surgery | One change → many files | Consolidate into strategy/registry |
| Long parameter list | 4+ positional params | Parameter object, builder |
| Boolean flags | `fn(x, true, false)` | Split functions, union/strategy |
| Switch on type (bonus) | Same `switch` in many places | Polymorphism (OCP) |
| Refused bequest (bonus) | Subclass throws "not supported" | Split interfaces (LSP/ISP) |
