## 3.3.1 DRY: Don't Repeat Yourself

**Real meaning.** Every piece of *knowledge* should have one authoritative home. It's about knowledge, not about lines that happen to look alike.

Good DRY: the brokerage-fee formula lives in one function used by the order screen, the contract note and the P&L report. If SEBI changes a rate, you edit one line.

Bad DRY (the *wrong abstraction*): two functions look similar today, so you merge them with a flag. Next month they diverge and the shared function sprouts `if (isForReport)` branches.

```ts
// One home for the fee rule
const BROKERAGE = { pct: 0.0003, cap: 20 } as const;
const brokerage = (turnover: number) => Math.min(BROKERAGE.cap, turnover * BROKERAGE.pct);

// Different features reuse the knowledge, not copy it
const orderPreview = (qty: number, price: number) => `est. brokerage ₹${brokerage(qty * price).toFixed(2)}`;
const contractNoteLine = (id: string, turnover: number) => `${id}: brokerage ${brokerage(turnover).toFixed(2)}`;

console.log(orderPreview(10, 1500));
console.log(contractNoteLine('T-44', 250_000));
```

```text
est. brokerage ₹4.50
T-44: brokerage 20.00
```

**Guideline:** duplicate once, abstract on the third occurrence (the "rule of three"), and only if the copies change for the *same* reason.

## 3.3.2 KISS: Keep It Simple

Pick the simplest design that meets today's requirements clearly. Simple is not the same as easy or short; it means few moving parts and obvious flow.

```ts
// ❌ "Clever" one-liner nobody can review
const status = o => ((o.f / o.q) | 0) ? 'FILLED' : o.f ? 'PARTIAL' : o.c ? 'CANCELLED' : 'OPEN';
```

```ts
type OrderState = { qty: number; filled: number; cancelled: boolean };

function orderStatus(o: OrderState): string {
  if (o.filled >= o.qty) return 'FILLED';
  if (o.cancelled) return o.filled > 0 ? 'PARTIALLY_FILLED_CANCELLED' : 'CANCELLED';
  if (o.filled > 0) return 'PARTIALLY_FILLED';
  return 'OPEN';
}

console.log(
  [
    { qty: 10, filled: 10, cancelled: false },
    { qty: 10, filled: 4, cancelled: false },
    { qty: 10, filled: 4, cancelled: true },
    { qty: 10, filled: 0, cancelled: false },
  ]
    .map(orderStatus)
    .join(', '),
);
```

```text
FILLED, PARTIALLY_FILLED, PARTIALLY_FILLED_CANCELLED, OPEN
```

The readable version also exposed a case the one-liner got wrong (partially filled, then cancelled).

## 3.3.3 YAGNI: You Aren't Gonna Need It

Don't build for requirements you *imagine*. Build clean seams where change is *likely*, and stop there.

**Over-engineering traps in machine-coding rounds** (90–120 minutes, working code expected):

- Adding a generic plugin system, event bus and DI container for a parking lot with three vehicle types.
- Writing an `AbstractFactoryProvider` for one factory.
- Supporting multiple databases, currencies and locales when the prompt says "in-memory is fine".
- Building persistence, auth and a REST layer before the core flow (`park → pay → exit`) runs end to end.
- Adding threads, locks and distributed IDs "for scale" when nothing asked for concurrency.
- Spending 30 minutes on a perfect class diagram and leaving 20 for code.

**What to do instead:**

1. Get the core use-case working with clean classes.
2. Put interfaces only where the prompt hints at variation ("pricing may change", "support more payment modes later").
3. *Say* the extension out loud: "If we needed Redis, only the repository implementation would change." That earns the design credit without the time cost.

**KISS vs OCP tension.** Interviewers like extensibility, and YAGNI says don't overbuild. The balance: make the *known* axis of change pluggable (one interface, two implementations), keep everything else concrete.
