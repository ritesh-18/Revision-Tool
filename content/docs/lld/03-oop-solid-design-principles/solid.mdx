title: "3.2 SOLID"
---

SOLID is five principles for keeping classes easy to change. You won't be asked to recite them. You'll be asked to *apply* them while designing, and to justify a split. For each one we'll use the same pattern: definition, broken design, refactor, how to spot it, how to explain it.

## 3.2.1 S: Single Responsibility Principle (SRP)

**Plain English.** A class should have one *reason to change*, meaning one group of people or one kind of requirement that can force an edit.

"Does one thing" is a weak reading. The useful question is: *who will ask me to change this class?* If the answer is "the finance team for tax rules, the design team for email layout, and the DBA for the schema", you have three responsibilities.

❌ **Violation: an order-invoice class that does everything**

```ts
// ❌ One class, four reasons to change
class InvoiceService {
  generate(orderId: string) {
    const row = db.query(`SELECT * FROM orders WHERE id='${orderId}'`); // persistence
    const gst = row.amount * 0.18;                                       // tax rules
    const html = `<h1>Invoice</h1><p>${row.amount + gst}</p>`;           // presentation
    smtp.send(row.email, 'Your invoice', html);                          // delivery
  }
}
```

✅ **Refactor: one job per class, a thin coordinator on top**

```ts
type OrderRecord = { id: string; email: string; amount: number };
type Invoice = { orderId: string; subtotal: number; gst: number; total: number };

class OrderRepository {
  readonly #rows = new Map<string, OrderRecord>([
    ['ORD-7', { id: 'ORD-7', email: 'ritesh@example.com', amount: 1000 }],
  ]);
  find(id: string): OrderRecord {
    const row = this.#rows.get(id);
    if (!row) throw new Error(`Order ${id} not found`);
    return row;
  }
}

class GstCalculator {
  constructor(private readonly rate = 0.18) {}
  build(order: OrderRecord): Invoice {
    const gst = Math.round(order.amount * this.rate * 100) / 100;
    return { orderId: order.id, subtotal: order.amount, gst, total: order.amount + gst };
  }
}

class InvoiceFormatter {
  toText(inv: Invoice): string {
    return `Invoice ${inv.orderId}: ${inv.subtotal} + GST ${inv.gst} = ${inv.total}`;
  }
}

class EmailSender {
  send(to: string, body: string): void {
    console.log(`email -> ${to}: ${body}`);
  }
}

class InvoiceService {
  constructor(
    private readonly repo: OrderRepository,
    private readonly tax: GstCalculator,
    private readonly fmt: InvoiceFormatter,
    private readonly mail: EmailSender,
  ) {}

  sendInvoice(orderId: string): void {
    const order = this.repo.find(orderId);
    const text = this.fmt.toText(this.tax.build(order));
    this.mail.send(order.email, text);
  }
}

const svc = new InvoiceService(new OrderRepository(), new GstCalculator(), new InvoiceFormatter(), new EmailSender());
svc.sendInvoice('ORD-7');
try {
  svc.sendInvoice('ORD-9');
} catch (err) {
  if (err instanceof Error) console.log(err.message);
}
```

```text
email -> ritesh@example.com: Invoice ORD-7: 1000 + GST 180 = 1180
Order ORD-9 not found
```

**How to spot violations**

- The class name has "And", "Manager", "Helper" or "Util" in it, or you can't name it without a vague word.
- Imports (or constructor dependencies) span unrelated areas: DB, HTTP, templating, crypto.
- Unit tests need a huge setup just to check one tax rule.
- Git history shows unrelated tickets all touching the same file.

**Pitfall.** Don't split until each class has one method and three lines. SRP is about *reasons to change*, not line counts. `GstCalculator` can own several tax-related methods.

**Interview line.** "SRP means one reason to change. I separated persistence, tax rules, formatting and delivery because different people change them for different reasons. `InvoiceService` just orchestrates, so a GST change never risks breaking email."

## 3.2.2 O: Open/Closed Principle (OCP)

**Plain English.** You should be able to add new behaviour by *adding* code, not by *editing* code that already works.

"Closed" doesn't mean frozen forever. It means the stable core doesn't need an edit for every new variant.

❌ **Violation: a pricing function that grows a branch per promotion**

```ts
// ❌ Every new offer means editing (and re-testing) this function
function finalPrice(cart: Cart, promo: string): number {
  if (promo === 'FLAT100') return cart.total - 100;
  else if (promo === 'TEN_PCT') return cart.total * 0.9;
  else if (promo === 'BOGO') { /* ... */ }
  else if (promo === 'DIWALI') { /* added last week, broke BOGO */ }
  return cart.total;
}
```

✅ **Refactor: a rule interface plus a registry**

```ts
type CartLine = { sku: string; unitPrice: number; qty: number };
type Cart = { lines: CartLine[] };

const subtotal = (c: Cart) => c.lines.reduce((s, l) => s + l.unitPrice * l.qty, 0);

interface PricingRule {
  readonly code: string;
  discount(cart: Cart): number;
}

class FlatOff implements PricingRule {
  constructor(readonly code: string, private readonly amount: number, private readonly minOrder: number) {}
  discount(cart: Cart): number {
    return subtotal(cart) >= this.minOrder ? this.amount : 0;
  }
}

class PercentOff implements PricingRule {
  constructor(readonly code: string, private readonly pct: number, private readonly cap: number) {}
  discount(cart: Cart): number {
    return Math.min(this.cap, (subtotal(cart) * this.pct) / 100);
  }
}

class PricingEngine {
  readonly #rules = new Map<string, PricingRule>();

  register(rule: PricingRule): this {
    this.#rules.set(rule.code, rule);
    return this;
  }

  price(cart: Cart, code?: string): number {
    const base = subtotal(cart);
    if (!code) return base;
    const rule = this.#rules.get(code);
    if (!rule) throw new Error(`Unknown promo ${code}`);
    return Math.max(0, base - rule.discount(cart));
  }
}

const engine = new PricingEngine()
  .register(new FlatOff('FLAT100', 100, 500))
  .register(new PercentOff('TEN_PCT', 10, 150));

const cart: Cart = { lines: [{ sku: 'BOOK', unitPrice: 400, qty: 2 }, { sku: 'PEN', unitPrice: 50, qty: 4 }] };
console.log(engine.price(cart));
console.log(engine.price(cart, 'FLAT100'));
console.log(engine.price(cart, 'TEN_PCT'));
```

Now marketing wants "buy 2 get 1 free" on a SKU. We *add* a class and register it. `PricingEngine` stays exactly as it was:

```ts
class BuyXGetY implements PricingRule {
  readonly code = 'B2G1';
  constructor(private readonly sku: string) {}
  discount(cart: Cart): number {
    const line = cart.lines.find((l) => l.sku === this.sku);
    return line ? Math.floor(line.qty / 3) * line.unitPrice : 0;
  }
}

engine.register(new BuyXGetY('PEN'));
console.log(engine.price(cart, 'B2G1'));
try {
  engine.price(cart, 'NOPE');
} catch (err) {
  if (err instanceof Error) console.log(err.message);
}
```

```text
1000
900
900
950
Unknown promo NOPE
```

**How to spot violations**

- A `switch`/`if` chain on a type string that appears in several places.
- Every feature ticket of the same kind ("add a new payment method") touches the same core file.
- Enum additions break unrelated tests.

**Pitfall.** Don't pre-build extension points for variation that isn't coming. OCP is worth it along the axis you *know* changes: promos, payment methods, notification channels, fee components.

**Interview line.** "I identified the axis that changes (promotion types) and put it behind a `PricingRule` interface. New promos are new classes registered at startup, so the engine is closed for modification but open for extension. It's basically the Strategy pattern."

## 3.2.3 L: Liskov Substitution Principle (LSP)

**Plain English.** If code works with a parent type, it must keep working when you hand it any subtype, with no surprises. A subtype may *accept more* and *promise more*, but never *demand more* or *deliver less*.

Concretely, a subtype must not:

- throw for inputs the parent accepts (stronger preconditions),
- return something weaker than the parent promised (weaker postconditions),
- break invariants the parent maintains.

❌ **Violation: a payment method that can't actually refund**

```ts
// ❌ Callers of PaymentMethod assume refund() works
abstract class PaymentMethod {
  abstract pay(amount: number): string;
  abstract refund(txnId: string, amount: number): void;
}

class GiftCardPayment extends PaymentMethod {
  pay(amount: number) { return 'GC-1'; }
  refund(): void {
    throw new Error('Gift cards are non-refundable'); // surprise!
  }
}

function cancelOrder(pm: PaymentMethod, txn: string, amt: number) {
  pm.refund(txn, amt); // blows up for gift cards in production
}
```

The type system happily accepts this, which is why LSP bugs are sneaky. The *contract* was broken, not the signature.

✅ **Refactor: model the capability honestly**

```ts
interface Payable {
  readonly name: string;
  pay(amount: number): string;
}

interface Refundable {
  refund(txnId: string, amount: number): string;
}

class UpiPayment implements Payable, Refundable {
  readonly name = 'UPI';
  pay(amount: number): string {
    return `UPI-TXN-${amount}`;
  }
  refund(txnId: string, amount: number): string {
    return `refunded ${amount} to ${txnId}`;
  }
}

class GiftCardPayment implements Payable {
  readonly name = 'GiftCard';
  pay(amount: number): string {
    return `GC-TXN-${amount}`;
  }
}

function isRefundable(p: Payable): p is Payable & Refundable {
  return typeof (p as Partial<Refundable>).refund === 'function';
}

function cancelOrder(p: Payable, txnId: string, amount: number): string {
  if (isRefundable(p)) return p.refund(txnId, amount);
  return `${p.name}: issue store credit of ${amount}`;
}

for (const p of [new UpiPayment(), new GiftCardPayment()]) {
  const txn = p.pay(499);
  console.log(cancelOrder(p, txn, 499));
}
```

```text
refunded 499 to UPI-TXN-499
GiftCard: issue store credit of 499
```

The famous textbook example is `Square extends Rectangle`: setting a square's width silently changes its height, which breaks any caller that sets width and height independently. The broker version: a `ReadOnlyWatchlist extends Watchlist` whose `add()` throws. Same bug, different clothes.

**How to spot violations**

- Overrides that throw `NotImplemented`/`NotSupported`, or that are empty no-ops.
- Callers doing `if (x instanceof SpecialChild)` before calling a parent method.
- Subclass tests that need to skip parent tests.

**Interview line.** "LSP says any subtype must be usable wherever the base type is expected without surprising the caller. If a subclass has to throw 'not supported', the hierarchy is wrong. I'd split the capability into its own interface, like `Refundable`, so the type tells the truth."

## 3.2.4 I: Interface Segregation Principle (ISP)

**Plain English.** Don't force a class to implement methods it doesn't need. Prefer several small, role-based interfaces over one big one.

ISP and LSP often show up together: a fat interface *causes* the "throw not supported" LSP bug.

❌ **Violation: a do-everything exporter contract**

```ts
// ❌ CSV can't do charts or password protection, but must pretend to
interface ReportExporter {
  exportTable(rows: Row[]): string;
  exportChart(series: number[]): string;
  protectWithPassword(pwd: string): void;
  emailTo(address: string): void;
}

class CsvExporter implements ReportExporter {
  exportTable(rows: Row[]) { /* real */ }
  exportChart() { throw new Error('CSV has no charts'); }
  protectWithPassword() { /* silently ignored!? */ }
  emailTo() { throw new Error('not my job'); }
}
```

✅ **Refactor: small role interfaces, each class picks what it can honour**

```ts
type Row = Record<string, string | number>;

interface TableExporter {
  exportTable(rows: Row[]): string;
}
interface ChartExporter {
  exportChart(title: string, series: number[]): string;
}
interface PasswordProtectable {
  protect(password: string): void;
}

class CsvExporter implements TableExporter {
  exportTable(rows: Row[]): string {
    if (rows.length === 0) return '';
    const headers = Object.keys(rows[0]!);
    const lines = rows.map((r) => headers.map((h) => String(r[h])).join(','));
    return [headers.join(','), ...lines].join('\n');
  }
}

class PdfExporter implements TableExporter, ChartExporter, PasswordProtectable {
  #locked = false;
  exportTable(rows: Row[]): string {
    return `[PDF table, ${rows.length} rows${this.#locked ? ', locked' : ''}]`;
  }
  exportChart(title: string, series: number[]): string {
    return `[PDF chart "${title}" max=${Math.max(...series)}]`;
  }
  protect(_password: string): void {
    this.#locked = true;
  }
}

// Each client asks only for the role it uses
function dailyPnlReport(exp: TableExporter, rows: Row[]): string {
  return exp.exportTable(rows);
}
function monthlyDeck(exp: TableExporter & ChartExporter, rows: Row[], series: number[]): string {
  return `${exp.exportTable(rows)} + ${exp.exportChart('Equity curve', series)}`;
}

const rows: Row[] = [
  { symbol: 'INFY', pnl: 1200 },
  { symbol: 'TCS', pnl: -300 },
];
console.log(dailyPnlReport(new CsvExporter(), rows));
const pdf = new PdfExporter();
pdf.protect('pan-based-secret');
console.log(monthlyDeck(pdf, rows, [100, 450, 320]));
```

```text
symbol,pnl
INFY,1200
TCS,-300
[PDF table, 2 rows, locked] + [PDF chart "Equity curve" max=450]
```

Passing `new CsvExporter()` to `monthlyDeck` is now a *compile-time* error, which is much better than a runtime throw.

**How to spot violations**

- Implementations full of empty methods or `throw new Error('not supported')`.
- An interface with 10+ methods used by clients that each call only 2 of them.
- Test mocks that stub out a pile of methods the test never touches.

**Interview line.** "ISP says clients shouldn't depend on methods they don't use. I split the exporter into table, chart and password roles. CSV implements one, PDF implements all three, and each report function asks for exactly the roles it needs, so mistakes show up at compile time."

## 3.2.5 D: Dependency Inversion Principle (DIP)

**Plain English.** High-level business logic shouldn't depend on low-level details like a specific SMS vendor or database. Both should depend on an abstraction, and the *business side* owns that abstraction.

The "inversion" is about who owns the interface. Without DIP, `OrderService` imports `TwilioClient`. With DIP, `OrderService` declares `interface Notifier` and the Twilio adapter implements it. The dependency arrow now points *toward* the business code.

DIP (a principle) is different from **dependency injection** (a technique: passing dependencies in through the constructor) and from an **IoC container** (a tool, like NestJS's). DI is the usual way to *achieve* DIP.

❌ **Violation: business logic welded to vendors**

```ts
// ❌ Can't test without real SMS; switching vendor means editing OrderService
import { TwilioClient } from 'twilio';
import { PgPool } from './db';

class OrderService {
  private sms = new TwilioClient(process.env.SID!, process.env.TOKEN!);
  private db = new PgPool();
  async place(o: Order) {
    await this.db.query('INSERT ...');
    await this.sms.messages.create({ to: o.phone, body: 'Order placed' });
  }
}
```

✅ **Refactor: the service declares what it needs, adapters plug in**

```ts
type Order = { id: string; clientId: string; symbol: string; qty: number };

// Abstractions owned by the business layer
interface OrderStore {
  save(order: Order): Promise<void>;
}
interface Notifier {
  notify(clientId: string, message: string): Promise<void>;
}

class OrderService {
  constructor(private readonly store: OrderStore, private readonly notifier: Notifier) {}

  async place(order: Order): Promise<void> {
    if (order.qty <= 0) throw new Error('Quantity must be positive');
    await this.store.save(order);
    await this.notifier.notify(order.clientId, `Order ${order.id}: BUY ${order.qty} ${order.symbol} placed`);
  }
}

// Low-level details implement the abstractions
class InMemoryOrderStore implements OrderStore {
  readonly saved: Order[] = [];
  async save(order: Order): Promise<void> {
    this.saved.push(order);
  }
}

class SmsNotifier implements Notifier {
  async notify(clientId: string, message: string): Promise<void> {
    console.log(`[SMS to ${clientId}] ${message}`);
  }
}

class PushNotifier implements Notifier {
  async notify(clientId: string, message: string): Promise<void> {
    console.log(`[PUSH to ${clientId}] ${message}`);
  }
}

class FanOutNotifier implements Notifier {
  constructor(private readonly channels: Notifier[]) {}
  async notify(clientId: string, message: string): Promise<void> {
    await Promise.all(this.channels.map((c) => c.notify(clientId, message)));
  }
}

// Composition root: the only place that knows concrete classes
const store = new InMemoryOrderStore();
const service = new OrderService(store, new FanOutNotifier([new SmsNotifier(), new PushNotifier()]));
await service.place({ id: 'O1', clientId: 'C-9', symbol: 'HDFCBANK', qty: 5 });

// A test double is trivial to write
class SpyNotifier implements Notifier {
  readonly messages: string[] = [];
  async notify(_c: string, m: string): Promise<void> {
    this.messages.push(m);
  }
}
const spy = new SpyNotifier();
const testService = new OrderService(new InMemoryOrderStore(), spy);
await testService.place({ id: 'T1', clientId: 'C-1', symbol: 'ITC', qty: 1 });
console.log(`spy captured: ${spy.messages.length}, stored: ${store.saved.length}`);
try {
  await testService.place({ id: 'T2', clientId: 'C-1', symbol: 'ITC', qty: 0 });
} catch (err) {
  if (err instanceof Error) console.log(err.message);
}
```

```text
[SMS to C-9] Order O1: BUY 5 HDFCBANK placed
[PUSH to C-9] Order O1: BUY 5 HDFCBANK placed
spy captured: 1, stored: 1
Quantity must be positive
```

In NestJS you'd register `{ provide: NOTIFIER, useClass: SmsNotifier }` and inject by token. The idea is the same; the container just does the wiring.

**How to spot violations**

- `new SomeConcreteService()` inside business classes.
- Business modules importing vendor SDKs, ORMs or `fetch` directly.
- Tests that need network access or heavy module mocking.

**Interview line.** "DIP means the order service depends on a `Notifier` interface it owns, not on the SMS vendor. I inject implementations at a composition root. That lets me swap vendors, fan out to multiple channels and test with a spy, all without touching business logic."

## 3.2.6 SOLID at a glance

| Principle | One-line test | Typical fix | Related pattern |
|---|---|---|---|
| SRP | "Who would ask me to change this?" has one answer | Split by reason to change | Facade as the coordinator |
| OCP | New variant = new file, not edited `switch` | Interface + registry | Strategy, Decorator |
| LSP | Every subtype passes the parent's tests | Split capabilities; avoid "not supported" | — |
| ISP | No empty/throwing implementations | Role interfaces | Adapter |
| DIP | Business code has no `new Vendor()` | Constructor injection of interfaces | Dependency injection |
