## 8.7.1 The last 15–30 minutes

A good review has a shape. Aim for this within the first five minutes of it:

1. **One-sentence summary.** "An in-memory library system: catalogue, members, loans with tier policies, holds with a FIFO queue, fines via Strategy, search via Specification, and notifications via an event bus."
2. **Demo.** Run it. Narrate two or three scenes, not all of them.
3. **Architecture tour.** Folder by folder, one sentence each.
4. **The core flow.** Open the main service method and read it aloud.
5. **Trade-offs and known gaps.** Say them before you're asked.

Then let the interviewer drive. Common questions and good answer shapes:

| Question | Answer shape |
|---|---|
| "Why this pattern here?" | The axis of change it absorbs + what the alternative would look like |
| "Why not just an `if`?" | "With two cases an `if` is fine; the prompt said rules will vary by tier, so a strategy keeps checkout closed for modification." Agreeing that simpler can be fine scores points. |
| "What's the complexity of X?" | Big-O of the current code + the index you'd add |
| "How would you test this?" | Unit tests for strategies and models; service tests with fake clock; one end-to-end driver |
| "What would break at scale?" | Scans, in-memory state, single process, locks that don't span instances |
| "What would you do with more time?" | Your parked list, in priority order |

## 8.7.2 Answering "how would you extend…?"

Use a four-part answer and keep it under a minute:

1. **Restate** the new requirement in your own words.
2. **Locate** the change: which class or interface absorbs it.
3. **List** the edits: new classes, changed signatures, wiring.
4. **Check** side effects: data migration, tests to add, concurrency impact.

If an extension would need edits in many places, don't hide it. Say "this one cuts across checkout and return because fines currently only see days overdue; I'd change the strategy to receive the loan." Explaining where your design bends is a senior-engineer signal.

## 8.7.3 Discussing concurrency: TypeScript vs Java

Most interviewers in Indian product companies are Java engineers, and many rubrics (PhonePe's ConcurrentHashMap feedback, for example) assume Java primitives. You'll be writing TypeScript, so be ready to translate.

| Concern | Java | TypeScript / Node |
|---|---|---|
| Execution model | Many threads share memory | One thread runs your JS; concurrency comes from interleaving at `await` points |
| When races happen | Between any two bytecode instructions | Only across `await` (or callbacks); synchronous blocks are atomic with respect to other JS |
| Mutual exclusion | `synchronized`, `ReentrantLock`, `StampedLock` | Async mutex / per-key promise chain (as in 8.4.13); or avoid `await` inside the critical section |
| Thread-safe map | `ConcurrentHashMap`, `computeIfAbsent` | A plain `Map` is safe from JS interleaving; the danger is check-`await`-act, not the map itself |
| Atomic counters | `AtomicInteger`, `LongAdder` | Plain numbers in-process; `Atomics` on a `SharedArrayBuffer` with worker threads |
| True parallelism | Thread pools, `ExecutorService` | `worker_threads` (separate isolates, message passing), or several processes |
| Across instances | Same problem as Node: needs DB/Redis locks | Conditional updates, optimistic versions, `SELECT … FOR UPDATE`, Redis locks, idempotency keys |
| Bounded work queue | `BlockingQueue`, `Semaphore` | Promise-based semaphore / `p-limit`-style limiter |

What to say, in order:

1. "Node runs my code on one thread, so a synchronous method like `checkout` can't be interrupted by another request."
2. "The race appears at `await` points: if I read stock, await something, then write, another request can run in between. That's the classic check-then-act bug."
3. "In-process, I guard it with a per-key async mutex, or restructure so the check and write happen with no `await` between them."
4. "Across instances, which is the real deployment, in-memory locks don't help, so I rely on the database: conditional updates or version checks, with retries. For money, like a trading wallet at Angel One or Groww, I'd add idempotency keys so a retried request doesn't double-debit."
5. "If the interviewer wants the Java version: `ConcurrentHashMap` for the repositories and a `ReentrantLock` per ISBN from a striped lock map, or `synchronized` on the copy."

This answer shows you understand *both* models. That's worth more than pretending TypeScript has `synchronized`.
