title: "8.6 Common mistakes and how to recover"
---

## 8.6.1 The mistakes

1. **Over-engineering.** Abstract factories, generic plugin loaders, a custom DI container. Each costs ten minutes and earns nothing unless the prompt calls for it. *Fix:* only add a pattern when you can name the change it absorbs.
2. **God class.** A single `LibraryManager` with thirty methods. *Fix:* one service per use-case cluster; models guard their own invariants.
3. **No demo.** The most common reason for rejection in machine coding. *Fix:* write the driver line for each flow *as soon as* the flow exists.
4. **No validation.** Negative quantities, unknown IDs, double returns. *Fix:* the "validations" step has its own time slot; don't let it get eaten.
5. **Hard-coded values.** `14`, `10`, `'PREMIUM'` sprinkled everywhere. *Fix:* a config or policy table and enums.
6. **Using `new Date()` and `Math.random()` inside logic.** Makes tests impossible. *Fix:* inject `Clock` and `IdGenerator`.
7. **Ignoring concurrency.** *Fix:* even if you don't implement a lock, point at the critical section and say what you'd do.
8. **Talking too little.** The interviewer can't score reasoning they can't hear. *Fix:* announce each step and each checkpoint.
9. **Not handling edge cases.** Last copy, exactly-on-due-date return, hold by someone who already has the book. *Fix:* keep a running "edge cases" list in a comment, and tick items off.
10. **Anaemic everything.** Models are bags of public fields, and every rule lives in services, so any code can put a copy in an illegal state. *Fix:* private state plus transition methods on the model.
11. **Returning `null`/`false` for failures.** The caller forgets to check. *Fix:* throw typed errors for rule violations; reserve `undefined` for "not found" lookups.
12. **Printing inside the domain.** `console.log` in services couples logic to the console. *Fix:* return values; print in the driver (observers that simulate email are the exception, and you should say so).
13. **Setting up tooling late.** Discovering at minute 80 that `ts-node` isn't installed. *Fix:* run "hello world" in minute 1.

## 8.6.2 Recovery tactics

**When you're stuck on the design (minute 15 with no clear entities):**
- Go back to the verbs. Write the three most important use cases as method signatures; the entities fall out of their parameters.
- Ask the interviewer a narrowing question: "Should I treat X as a separate entity or a field of Y?" This is allowed, and it's scored as collaboration.
- Pick the simplest model that works and say "I'll refine this if needed."

**When a bug eats your time:**
- Timebox it to 5 minutes. Add a `console.log` of the exact state, not guesses.
- If it's still broken, comment the scenario out of the demo, write `// TODO: known bug — X` and move on. Mention it in the review. A known, explained bug beats a missing feature set.

**When you're running out of time:**
- At the 75% mark, list what's left and cut aggressively. Tell the interviewer: "I'll finish checkout and return and skip holds. Here's how holds would plug in."
- Stub the remaining plug-in points with an interface and one trivial implementation, so the design is visible even if the behaviour is minimal.
- Never spend the last ten minutes on a new feature. Spend them on the demo.

**When the interviewer changes requirements mid-way:**
- This is often deliberate: they're testing extensibility. Restate the change, say which file it touches, and do it. If it touches many files, say so honestly and explain which abstraction would have prevented it.

**When you realise the design is wrong:**
- Under 40% of the time used: refactor now.
- Over 40%: keep going, and describe the better design in the review. Interviewers respect "here's what I'd change" far more than a half-finished rewrite.
