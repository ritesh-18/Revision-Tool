## Chapter recap

- There are two formats. **Whiteboard LLD** (45–60 min) scores modelling and reasoning; **machine coding** (90–150 min) scores working, modular, validated code plus a review. Find out which one you face.
- Follow the same arc every time: clarify → scope → entities → relationships → diagram → APIs → patterns → skeleton → core flows → validation → concurrency → demo → tests → extensions. Have something running by 60% of the time, and stop adding features at 80%.
- Use a fixed project layout (enums, models, repositories, services, strategies, specifications, observers, exceptions, app, main) and a starter kit with an injected `Clock`, an `IdGenerator`, a typed error hierarchy and a generic in-memory repository.
- In the library example, the key modelling moves were: splitting `Book` from `BookCopy`, keeping tier rules in a policy table, fines as a Strategy (with a grace-period decorator), search as composable Specifications, notifications through an event bus, and models that guard their own state transitions.
- Interviewers consistently score working code, clarification, modularity, extensibility, validation, concurrency awareness, tests, communication and speed. Score yourself after every practice session.
- The usual failures are process failures: over-engineering, god classes, no demo, no validation, hard-coded values, silence. Recover by cutting scope out loud and protecting the demo.
- In the review, run the demo first, walk the layers, read the core method, and name trade-offs before you're asked. Answer extension questions with restate → locate → list → check.
- In TypeScript, races happen at `await` points, not between arbitrary instructions. Guard in-process with per-key async mutexes, and across instances with database conditional updates, optimistic versioning and idempotency.

## Interview questions on this chapter

**1. How do you spend the first ten minutes of a 90-minute machine-coding round?**

<details>
<summary>Answer</summary>

Clarify and scope. I ask 5–8 targeted questions (actors, core use cases, entity lifecycle, limits, money and time rules, duplicates and ordering, whether concurrency and tests matter). Then I write a visible list of requirements, out-of-scope items and assumptions, and read it back. I also check that my TypeScript setup runs. Those ten minutes prevent the most expensive mistake: building the wrong thing.

</details>

**2. What is the difference between a whiteboard LLD round and a machine-coding round, and how does your approach change?**

<details>
<summary>Answer</summary>

A whiteboard round (45–60 min, typical at Amazon) scores modelling: entities, relationships, diagrams, patterns and trade-offs, with maybe one class coded. A machine-coding round (90–150 min, typical at Flipkart, PhonePe, Razorpay, Meesho) needs a running in-memory app, a demo and a code review. In the whiteboard round I spend longer on diagrams and "what if" discussion. In machine coding I keep the diagram rough, get a skeleton in fast, and make one flow work end to end as early as possible.

</details>

**3. Why inject a clock and an ID generator instead of calling `new Date()` and generating random IDs?**

<details>
<summary>Answer</summary>

Determinism and testability. With a `FakeClock`, the demo and tests can jump forward 17 days to check fines without sleeping, and results are identical on every run. With a sequential ID generator, output such as `LN-1` is predictable, so assertions and demos are stable. It's also dependency inversion: services depend on a `Clock` interface, and production wiring passes a system clock.

</details>

**4. In the library design, why separate `Book` from `BookCopy`?**

<details>
<summary>Answer</summary>

They have different identities and lifecycles. `Book` is title-level metadata that you search and place holds against. `BookCopy` is a physical item with a status (available, on loan, on hold) that loans point to. Merging them forces a `quantity` counter that can't tell you which copy is overdue or which one is held for whom. The same type-vs-instance split shows up in many problems: show vs seat, product vs inventory unit, vehicle type vs parking spot.

</details>

**5. When would you use the State pattern for `BookCopy` instead of a guarded enum?**

<details>
<summary>Answer</summary>

When states gain their own behaviour, not just allowed transitions. With three states and four transitions, a private status plus a `transition(allowedFrom, to)` guard is clearer and quicker to write. If copies gained states like `IN_TRANSIT`, `UNDER_REPAIR` and `LOST`, each with different rules for checkout, return and fines, I'd move to State classes so each state's behaviour lives in one place.

</details>

**6. JavaScript is single-threaded. Can two members still borrow the last copy?**

<details>
<summary>Answer</summary>

Yes, if there's an `await` between checking availability and marking the copy on loan. Other requests run at every `await`, so both can see "1 available" before either writes. A purely synchronous check-and-set is safe inside one process. Fixes: keep the critical section free of `await`, use a per-key async mutex, or, since production runs several instances, enforce it in the database with a conditional update (`WHERE status = 'AVAILABLE'`), a version column with retries, or `SELECT … FOR UPDATE`.

</details>

**7. How do you decide whether a design pattern belongs in your solution?**

<details>
<summary>Answer</summary>

I name the axis of change it absorbs. Fine rules that vary by tier justify Strategy; "notify when…" justifies Observer; arbitrary filter combinations justify Specification. If I can't name a likely change, I use plain code. I'm also happy to say "with two cases an `if` would do, but the prompt says these rules will grow." Two or three well-justified patterns score better than many decorative ones.

</details>

**8. Your code has a bug and 12 minutes remain. What do you do?**

<details>
<summary>Answer</summary>

Timebox debugging to about five minutes and log the actual state rather than guessing. If it's still broken, comment the failing scenario out of the driver, leave a `TODO` explaining the known bug, and make sure the rest of the demo runs cleanly. In the review I mention the bug and my hypothesis. A working demo with one explained gap beats a broken demo.

</details>

**9. How would you add a Student tier with different limits and fines?**

<details>
<summary>Answer</summary>

Add `Student` to the `MemberTier` enum. Because policies are typed as `Record<MemberTier, MembershipPolicy>`, the compiler flags the missing row, and I add one with its limits and a fine strategy (a new `UncappedPerDayFine` if needed). `LoanService` doesn't change, because it only reads `policies[member.tier]`. That's the Open/Closed Principle in practice.

</details>

**10. What makes a machine-coding submission a "no hire" even if it runs?**

<details>
<summary>Answer</summary>

A god class with all the logic, rules implemented as scattered `if`s with magic numbers, no validation or typed errors (happy path only), failures signalled by `console.log` or `null`, time read directly from `new Date()` so fines can't be demonstrated, no tests, and a candidate who can't explain how to add a new rule without editing many places. Silence during the round and no clarifying questions make it worse.

</details>

**11. How do you structure the final code walkthrough?**

<details>
<summary>Answer</summary>

One-sentence summary, run the demo, a folder-by-folder tour of the layers, then read the core service method aloud, then state trade-offs and known gaps myself: O(n) scans, in-memory state, single-process locks, parked features. After that I let the interviewer drive and answer extension questions with restate → locate → list edits → check side effects.

</details>

**12. How would you explain your concurrency approach to an interviewer who thinks in Java?**

<details>
<summary>Answer</summary>

Map the concepts. Java threads can interleave anywhere, so you use `synchronized`, `ReentrantLock` and `ConcurrentHashMap`. Node runs JS on one thread, so interleaving happens only at `await` points; a synchronous method is effectively atomic in-process. My equivalent of a per-ISBN `ReentrantLock` is a per-key async mutex. For parallel CPU work I'd use worker threads with `SharedArrayBuffer` and `Atomics`. Across instances both languages need the same thing: database conditional updates, optimistic versioning or distributed locks, plus idempotency keys for money movements.

</details>

## Practice exercises

1. **Timed rerun.** Close this chapter and rebuild the library system from scratch in 90 minutes with a timer. Score yourself with the rubric in 8.5. Repeat a week later and compare.
2. **Hold expiry.** Add a READY-hold expiry of 3 days: a `HoldExpiryJob.run()` that uses the injected clock, expires stale holds, and passes the copy to the next in line (or back to AVAILABLE). Add PASS/FAIL tests for both paths.
3. **Renewals.** Add `LoanService.renew(loanId)` with a maximum of 2 renewals, refused if anyone is waiting for the title or if the loan is already overdue. Decide which checks belong in `Loan` and which in the service.
4. **Async repositories.** Convert the repositories and services to `async` (simulate I/O with `setTimeout`). Show the last-copy race appearing, then fix it with the `KeyedMutex`, and write a test that fires 10 concurrent checkouts for 3 copies.
5. **Command parser.** Some Flipkart-style prompts want input like `BORROW MEM-1 978-0132350884`. Write a `CommandParser` that maps lines to service calls using a `Map<string, CommandHandler>` (Command pattern), and prints errors without crashing.
6. **Whiteboard drill.** In 45 minutes, with no code, produce the clarifying questions, entity table, Mermaid class diagram and one sequence diagram for a **stock watchlist with price alerts** (Angel One style). Record yourself explaining it.
7. **Machine-coding drill, trading flavour.** In 120 minutes build an in-memory **order book** for one symbol: limit buy/sell orders, price-time priority matching, partial fills, cancel, and a trade log, with an injected clock and a PASS/FAIL test harness. Then answer: "What happens if two orders arrive at the same time?"
8. **Rubric swap.** Take a solution you wrote a month ago (or a friend's). Score it on all 12 rubric rows, list the three biggest problems, and refactor only those within 30 minutes.
9. **Extension speed-round.** For each row in the follow-ups table in 8.4.13, write the one-paragraph answer from memory, then implement the SMS notifier and the availability specification.
10. **Explain it to Java.** Write a half-page note translating your `KeyedMutex` and optimistic `compareAndSet` into Java (`ConcurrentHashMap<String, ReentrantLock>`, `AtomicInteger`/version column). Practise saying it aloud in under two minutes.
