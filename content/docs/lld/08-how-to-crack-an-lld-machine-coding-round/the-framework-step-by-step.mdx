## 8.2.1 Time budgets

| Step | Whiteboard (60 min) | Machine coding (120 min: 90 coding + 30 review) |
|---|---|---|
| 1. Clarify requirements | 0–7 | 0–8 |
| 2. Scope and assumptions | 7–10 | 8–10 |
| 3. Entities (noun/verb) | 10–15 | 10–14 |
| 4. Relationships + 5. class diagram | 15–25 | 14–20 (rough, on paper) |
| 6. Interfaces / APIs | 25–30 | 20–22 |
| 7. Patterns | 30–33 (named while drawing) | 22–24 |
| 8. Code skeleton | — | 24–32 |
| 9. Core flows | 33–42 (sequence diagram, 1 class in code) | 32–65 |
| 10. Validations and errors | 42–45 | 65–75 |
| 11. Concurrency | 45–50 | 75–78 (guard the critical section, or at least talk it through) |
| 12. Demo / driver | — | 78–85 |
| 13. Tests | — | 85–90 |
| 14. Extensions discussion | 50–60 | 90–120 (review + follow-ups) |

Two rules sit above the table:

1. **Something must run by the 60% mark.** In a 90-minute coding window, you want one end-to-end flow running by minute 55. After that you add features, not structure.
2. **Protect the demo.** At 80% of the time, stop adding features. Wire the driver, fix what's broken, and make the output readable.

## 8.2.2 Step 1: clarify requirements

The prompt is vague on purpose; Salesforce and Razorpay write-ups say so explicitly. Asking good questions *is* part of the score. Use this checklist and pick the questions that matter for the problem:

**Functional scope**
- Who are the actors (user, admin, system job)? What can each do?
- What are the 3–5 core use cases? Which are must-have and which are nice-to-have?
- What's the lifecycle of the main entity (created → active → closed)? Can it be cancelled or reversed?
- Are there limits (max items per user, max bookings, quotas)?
- Are there money calculations? Currency, rounding, caps?

**Rules and edge cases**
- What happens when a resource is unavailable? Fail, queue or waitlist?
- Duplicates: can the same user do X twice?
- Time: due dates, expiry, time zones? (Answer: inject a clock.)
- Ordering: FIFO? Priority? Tie-breaking?

**Non-functional (lightweight)**
- Single process, in-memory storage? (Almost always yes.)
- Concurrency: can two requests race on the same resource?
- Interface: CLI/driver, or method calls? Must I parse commands from input?
- Should I write tests? Which language and runtime?

**Evaluation hints**
- "Which parts do you care most about?" Interviewers often answer honestly, and it tells you where to spend time.

Don't ask twenty questions in a row. Ask 5–8, write the answers down as bullet points, and read them back.

## 8.2.3 Step 2: define scope and assumptions

Turn the answers into a short written list the interviewer can see:

```text
IN SCOPE:  add books/copies, register members, search, borrow, return, fines, holds
OUT:       payments gateway, auth, UI, persistence, multi-branch
ASSUME:    single library, in-memory, amounts in whole rupees, dates via injected clock
```

This list protects you later. When the interviewer says "what about multiple branches?", you can say "I parked that as out of scope. Here's how I'd add it", instead of looking like you forgot.

## 8.2.4 Step 3: identify entities (noun/verb analysis)

Underline nouns (candidate classes or fields) and verbs (candidate methods) in the requirements. Throw out synonyms and anything out of scope. For each surviving noun, ask: *does it have identity and a lifecycle?* If yes, it's an entity. If it's just a value (money, a date range), make it a value object or a field.

## 8.2.5 Steps 4–5: relationships and class diagram

For each pair of entities, decide: is-a (inheritance, rare), has-a with ownership (composition), has-a without ownership (association by ID), or uses (dependency). In machine coding, **reference other entities by ID**, not by object pointer, just as a database would. It keeps repositories simple and avoids circular object graphs.

Keep the diagram to 8–12 boxes. Show enums, the key interfaces (strategies, observers) and multiplicities.

## 8.2.6 Step 6: interfaces / APIs

Write the public method signatures of your services *before* implementing them. This is your contract with the interviewer:

```ts
// plain sketch — signatures only
catalog.addBook(input): Book
catalog.search(spec): Book[]
loans.checkout(memberId, isbn): Loan
loans.returnCopy(copyId): ReturnReceipt
holds.placeHold(memberId, isbn): Hold
```

## 8.2.7 Step 7: choose patterns, only where they earn their place

A pattern earns its place when it sits on an **axis of change** the interviewer has hinted at, or will very likely ask about:

| Signal in the prompt | Pattern |
|---|---|
| "different pricing / fine / split / assignment rules" | Strategy |
| "notify users when…" | Observer (event bus) |
| "search/filter by any combination of fields" | Specification / composable predicates |
| "entity moves through states with rules" | State (or a guarded status enum for simple cases) |
| "undo", "queue of operations", "audit" | Command |
| "create different kinds of X" | Factory |
| "add behaviour without touching the class" | Decorator |

If you can't name the axis of change, don't add the pattern. A `SingletonFactoryManager` for one class is a red flag, not a bonus.

## 8.2.8 Step 8: code skeleton

Create folders and empty files, enums, model classes with constructors, repository classes and service classes with method stubs that throw `not implemented`. Five to eight minutes, maximum. Section 8.3 gives you a skeleton to type from memory.

## 8.2.9 Step 9: implement core flows

Pick the **single most important flow** (borrow a book, book a seat, place an order) and make it work end to end, including the driver line that calls it. Then add the next flow. Running code at every step means you're never more than a few minutes from a demo.

## 8.2.10 Step 10: validations and errors

Validate at the service boundary: required fields, positive numbers, entity exists, state transition allowed, business limits. Throw **typed custom errors** with clear messages. Never `return null` to mean "failed", and never `console.log` an error and carry on.

## 8.2.11 Step 11: concurrency

In Java you'd reach for `synchronized`, `ReentrantLock` or `ConcurrentHashMap`. In TypeScript the story is different (section 8.7.3), but you still need to *identify the critical sections* (last copy, last seat, wallet balance) and either guard them or explain how you would.

## 8.2.12 Steps 12–13: demo and tests

The driver tells a story: set-up, happy path, each rule being enforced, an error or two, and an edge case. Tests can be a tiny hand-rolled harness printing PASS/FAIL. You don't need Jest to show you think about testing.

## 8.2.13 Step 14: extensions discussion

Keep two or three extensions ready and explain *which file changes* for each. If the answer is "one new class and one line of wiring", your design is doing its job.
