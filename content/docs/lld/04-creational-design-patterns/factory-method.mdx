title: "4.3 Factory Method"
---

## Intent

Declare a method that returns a product in a base class, and let subclasses decide which concrete product to create. The base class holds the *workflow*; subclasses fill in the *creation step*.

## Problem

Every payment flow does the same thing: validate the amount, create a gateway client, charge, record the result. Only the gateway differs (Razorpay-like for UPI, Stripe-like for international cards). You want the workflow written once, and the "which client?" decision pushed to the specific processor, without an `if (type === ...)` inside the workflow.

## TypeScript implementation

```ts
interface Gateway {
  readonly name: string;
  charge(amountPaise: number): string;
}

class UpiGateway implements Gateway {
  readonly name = 'UPI';
  charge(amountPaise: number): string {
    return `upi_txn_${amountPaise}`;
  }
}

class CardGateway implements Gateway {
  readonly name = 'CARD';
  constructor(private readonly feePercent: number) {}
  charge(amountPaise: number): string {
    const fee = Math.round((amountPaise * this.feePercent) / 100);
    return `card_txn_${amountPaise + fee}`;
  }
}

abstract class PaymentProcessor {
  // The template workflow: identical for all processors.
  pay(amountRupees: number): string {
    if (amountRupees <= 0) throw new Error('Amount must be positive');
    this.validate(amountRupees);
    const gateway = this.createGateway(); // <- the factory method
    const txnId = gateway.charge(Math.round(amountRupees * 100));
    return `[${gateway.name}] paid Rs.${amountRupees} -> ${txnId}`;
  }

  protected abstract createGateway(): Gateway;

  // Hook with a default; subclasses may override.
  protected validate(_amountRupees: number): void {}
}

class UpiProcessor extends PaymentProcessor {
  protected override createGateway(): Gateway {
    return new UpiGateway();
  }
  protected override validate(amountRupees: number): void {
    if (amountRupees > 100_000) throw new Error('UPI limit is Rs.1,00,000 per transaction');
  }
}

class CardProcessor extends PaymentProcessor {
  protected override createGateway(): Gateway {
    return new CardGateway(2); // 2% fee
  }
}

const processors: PaymentProcessor[] = [new UpiProcessor(), new CardProcessor()];
for (const p of processors) {
  console.log(p.pay(250));
}
try {
  new UpiProcessor().pay(150_000);
} catch (err) {
  console.log(`rejected: ${(err as Error).message}`);
}
```

```text
[UPI] paid Rs.250 -> upi_txn_25000
[CARD] paid Rs.250 -> card_txn_25500
rejected: UPI limit is Rs.1,00,000 per transaction
```

Notice that `pay()` never names a concrete gateway. Adding a `NetBankingProcessor` means one new subclass, zero edits to existing code.

**The TypeScript-flavoured version.** In TS you often don't need a subclass just to override one method; pass the factory in as a function. Same idea, less inheritance:

```ts
interface Gateway {
  charge(amountPaise: number): string;
}

class PaymentProcessor {
  constructor(private readonly createGateway: () => Gateway) {}

  pay(amountRupees: number): string {
    return this.createGateway().charge(amountRupees * 100);
  }
}

const upi = new PaymentProcessor(() => ({ charge: (p) => `upi_${p}` }));
export const receipt: string = upi.pay(10);
```

## When to use / when NOT to use

- **Use** when a base class owns an algorithm and one step is "make the right object", and subclasses already exist for other reasons (framework hooks, per-exchange handlers).
- **Don't use** just to create one object; a Simple Factory or an injected function is lighter. Don't build deep inheritance trees only to vary creation.

## Pitfalls

- **Subclass explosion**: one subclass per product. If products multiply, switch to a registry or injected factory function.
- Calling the factory method from the **constructor** of the base class: the subclass's fields are not initialised yet (with `useDefineForClassFields`), so you get `undefined` surprises.
- Forgetting `override` (with `noImplicitOverride` the compiler catches it; turn that flag on).

## Related patterns

- **Simple Factory** decides with a switch in one place; Factory Method decides with polymorphism in subclasses.
- **Template Method** (Chapter 6): Factory Method is usually one step *inside* a template method, exactly like `pay()` above.
- **Abstract Factory** is often implemented as a set of factory methods.

## Where it shows up in LLD interview problems

- Payment system: processor subclasses create their gateway client.
- Document/report exporter: `ReportExporter.export()` calls `createWriter()` (PDF/CSV/Excel).
- Logistics / ride-sharing: `DeliveryService.createVehicle()`.
- Game design (Snake and Ladder, Chess): `Game.createBoard()` overridden by variants.

Interview line: *"The workflow lives in the base class; the one thing that varies, which object to create, is a protected factory method that subclasses override."*

## Quick check

1. In one sentence, how is Factory Method different from Simple Factory?
2. Why is calling `this.createGateway()` inside the base constructor risky?

<details>
<summary>Answers</summary>

1. Simple Factory picks the class with a conditional in one place; Factory Method lets each subclass pick by overriding a method that the base class's workflow calls.
2. The base constructor runs before the subclass's field initialisers, so the overridden method may read fields that are still `undefined`.

</details>
