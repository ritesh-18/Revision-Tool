## Chapter recap

- Creational patterns separate **deciding what to create** from **using it**, so callers depend on interfaces, not constructors.
- **Singleton**: one instance per process. In TS prefer a module-level instance or a DI singleton-scoped provider; cache the *promise* for async init; remember "per process" is not "per cluster".
- **Simple Factory** centralises a switch; use a union type plus `never` for exhaustiveness, or a registry for extensibility.
- **Factory Method** puts a creation step inside a base-class workflow and lets subclasses override it. In TS, an injected factory function is often enough.
- **Abstract Factory** creates families of related objects that must match; new families are cheap, new product types are expensive.
- **Builder** tames many optional, interdependent fields. Fluent builders validate at runtime; step builders enforce order at compile time.
- **Prototype** copies configured objects. Write explicit `clone()` for classes; `structuredClone` loses prototypes and rejects functions.
- **Object Pool** lends expensive, limited resources: lazy creation, FIFO waiters, timeouts, reset on release, `use()` with `finally`.

## Interview questions on this chapter

**Q1. What is the Singleton pattern and why do many engineers call it an anti-pattern?**

<details>
<summary>Answer</summary>

It restricts a class to one instance and provides global access to it. The criticism is about the global access: dependencies become hidden (`X.getInstance()` inside methods), tests share state and become order-dependent, and it is hard to substitute fakes. The single-instance *lifetime* is fine; the fix is to keep that lifetime but deliver the instance through DI (NestJS providers are singleton-scoped by default).

</details>

**Q2. How do you make a singleton safe in Node.js, given it is single-threaded?**

<details>
<summary>Answer</summary>

Synchronous creation is already safe. The danger is async initialisation: two callers can both pass the "not created yet" check before the first `await` completes. Store the initialisation **promise** synchronously (`this.pending ??= this.connect()`) and return it to everyone. Also handle failure: if the promise rejects, clear it so a later call can retry.

</details>

**Q3. Explain the difference between Simple Factory, Factory Method and Abstract Factory.**

<details>
<summary>Answer</summary>

- Simple Factory: one function or class with a conditional that returns one of several implementations of an interface.
- Factory Method: a base class workflow calls an overridable `createX()` method; subclasses decide the concrete product (inheritance-based).
- Abstract Factory: an object with several `createX()` methods that produce a *family* of related products; you inject a different factory to switch the whole family (composition-based).

</details>

**Q4. In a Parking Lot design, where would you use creational patterns?**

<details>
<summary>Answer</summary>

`ParkingLot` as a single instance (injected, singleton-scoped); a `VehicleFactory` or `SpotFactory` keyed by vehicle/spot type; possibly a builder to configure the lot (floors, spot counts per type, pricing strategy); and the set of free spots behaves like a pool (acquire on entry, release on exit), often implemented with a min-heap or a queue per spot type.

</details>

**Q5. When would you choose a Builder over a constructor with an options object?**

<details>
<summary>Answer</summary>

An options object with defaults is idiomatic TS and enough for simple cases. Choose a builder when there are cross-field rules (LIMIT needs price, SL trigger vs price), when construction happens in steps across different code paths, when you want a frozen/immutable result validated once in `build()`, when readable test-data setup matters, or when you want compile-time step ordering (step builder).

</details>

**Q6. What is a step (type-state) builder and how does TypeScript help implement it?**

<details>
<summary>Answer</summary>

A builder where each method returns a different interface that exposes only the next legal steps, e.g. `SymbolStep -> SideStep -> TypeStep -> OptionalStep(build)`. TypeScript's structural typing lets a single class implement all step interfaces while the static entry point returns only the first interface, so calling `build()` too early is a compile error.

</details>

**Q7. What are the limitations of `structuredClone` for implementing Prototype?**

<details>
<summary>Answer</summary>

It deep-copies plain data well (including `Date`, `Map`, `Set`, typed arrays, circular refs), but it drops class prototypes (the result is a plain object, so methods disappear while TypeScript still believes the type is the class), throws `DataCloneError` on functions, and can't clone DOM nodes or things like sockets. For domain classes, write an explicit `clone()`.

</details>

**Q8. Design a connection pool. What are the key decisions?**

<details>
<summary>Answer</summary>

Max size (and optional min/warm size); lazy vs eager creation; a waiting queue (FIFO for fairness) with acquire timeout; release that resets state and hands the connection directly to the next waiter; protection against double release and leaks (a `use(fn)` helper with `finally`, leak detection by checkout duration); health checks/eviction of broken or idle connections; reserving the slot before async creation to avoid exceeding max; and metrics (in use, idle, waiting, wait time).

</details>

**Q9. Is Object Pool useful for ordinary objects in JavaScript?**

<details>
<summary>Answer</summary>

Rarely. V8's generational GC makes short-lived allocations cheap, so pooling small objects mostly adds complexity and state-leak bugs. Pool things that are expensive or limited outside the JS heap: connections, threads, browser pages, big buffers. Game loops and hot paths with measured GC pauses are the exception.

</details>

**Q10. Abstract Factory makes adding which kind of change easy, and which kind hard?**

<details>
<summary>Answer</summary>

Adding a new family (a new exchange, a new theme) is easy: one new factory plus its products, no existing code changes. Adding a new product type to every family is hard: the factory interface and every concrete factory must change. Choose it when families change more often than product types.

</details>

**Q11. How does NestJS's DI container relate to these patterns?**

<details>
<summary>Answer</summary>

The container is a factory (it constructs providers and resolves dependencies), and it manages lifetimes: default providers are singletons, `Scope.REQUEST` creates one per request, `Scope.TRANSIENT` creates one per injection. `useFactory` providers are literally factory functions, and `forRoot()/forRootAsync()` dynamic modules act like builders for module configuration.

</details>

## Practice exercises

1. **Async config singleton with retry.** Extend `DbClient` so that if `connect()` rejects, the cached promise is cleared and the next `get()` retries. Write a demo where the first attempt fails and the second succeeds, and print the number of attempts.
2. **Notification factory to registry.** Convert `NotifierFactory` into a registry that keeps type safety: the key type should be derived from the registered map (`keyof typeof registry`), so `create('fax')` fails to compile.
3. **Pizza step builder.** Build `PizzaBuilder.create().size('M').base('thin').addTopping('olive').addTopping('paneer').build()` where `size` and `base` are mandatory and in that order, toppings are optional (max 5), and `build()` computes the price.
4. **Abstract factory for payment regions.** Create `IndiaPaymentFactory` and `USPaymentFactory`, each producing a `TaxCalculator` (GST 18% vs state sales tax), a `CurrencyFormatter` (₹ with lakh grouping vs $) and a `Gateway`. Write a `Checkout` class that uses only the abstract factory.
5. **Basket order prototype.** Model a basket of orders that can be cloned for "repeat yesterday's basket". Each cloned order must get a new client order ID while keeping everything else. Add a test that the clone's legs are not shared with the original.
6. **Pool with health checks.** Add `validate(conn)` to the pool: on acquire, if a connection is stale (say, `id % 3 === 0` for the demo), discard it and create a new one without exceeding `max`. Add `drain()` that rejects all waiters and closes idle connections for graceful shutdown.
