## Intent

Provide one interface for creating a **family of related objects** that must be used together, without naming their concrete classes.

## Problem

Your broker supports NSE and BSE. Each exchange needs its own *set* of collaborators: a symbol formatter (`NSE:INFY-EQ` vs `BSE:500209`), a fee calculator (different transaction charges), and an order validator (different tick sizes and circuit rules). Mixing an NSE formatter with a BSE fee calculator produces a wrong contract note, a compliance issue. You want to guarantee that the whole family comes from the same exchange.

## TypeScript implementation

```ts
interface OrderRequest {
  symbol: string;
  scripCode: number;
  qty: number;
  price: number;
}

interface SymbolFormatter {
  format(o: OrderRequest): string;
}
interface FeeCalculator {
  fees(turnover: number): number;
}
interface OrderValidator {
  validate(o: OrderRequest): string | null; // null = ok
}

interface ExchangeFactory {
  readonly exchange: string;
  createFormatter(): SymbolFormatter;
  createFeeCalculator(): FeeCalculator;
  createValidator(): OrderValidator;
}

// ----- NSE family -----
class NseFormatter implements SymbolFormatter {
  format(o: OrderRequest): string {
    return `NSE:${o.symbol}-EQ`;
  }
}
class NseFees implements FeeCalculator {
  fees(turnover: number): number {
    return +(turnover * 0.0000297).toFixed(2);
  }
}
class NseValidator implements OrderValidator {
  validate(o: OrderRequest): string | null {
    // price must be a multiple of 0.05 (tick size); compare in paise to avoid float issues
    return Math.round(o.price * 100) % 5 === 0 ? null : 'NSE tick size is 0.05';
  }
}
class NseFactory implements ExchangeFactory {
  readonly exchange = 'NSE';
  createFormatter(): SymbolFormatter {
    return new NseFormatter();
  }
  createFeeCalculator(): FeeCalculator {
    return new NseFees();
  }
  createValidator(): OrderValidator {
    return new NseValidator();
  }
}

// ----- BSE family -----
class BseFormatter implements SymbolFormatter {
  format(o: OrderRequest): string {
    return `BSE:${o.scripCode}`;
  }
}
class BseFees implements FeeCalculator {
  fees(turnover: number): number {
    return +(turnover * 0.0000375).toFixed(2);
  }
}
class BseValidator implements OrderValidator {
  validate(o: OrderRequest): string | null {
    return o.qty <= 10_000 ? null : 'BSE max qty per order is 10000';
  }
}
class BseFactory implements ExchangeFactory {
  readonly exchange = 'BSE';
  createFormatter(): SymbolFormatter {
    return new BseFormatter();
  }
  createFeeCalculator(): FeeCalculator {
    return new BseFees();
  }
  createValidator(): OrderValidator {
    return new BseValidator();
  }
}

// ----- Client: only knows the abstract factory -----
class OrderRouter {
  private readonly formatter: SymbolFormatter;
  private readonly feeCalc: FeeCalculator;
  private readonly validator: OrderValidator;

  constructor(private readonly factory: ExchangeFactory) {
    this.formatter = factory.createFormatter();
    this.feeCalc = factory.createFeeCalculator();
    this.validator = factory.createValidator();
  }

  route(o: OrderRequest): string {
    const error = this.validator.validate(o);
    if (error) return `${this.factory.exchange} REJECTED: ${error}`;
    const fees = this.feeCalc.fees(o.qty * o.price);
    return `${this.factory.exchange} SENT ${this.formatter.format(o)} x${o.qty} @${o.price} fees=${fees}`;
  }
}

const factories: Record<string, ExchangeFactory> = { NSE: new NseFactory(), BSE: new BseFactory() };
const order: OrderRequest = { symbol: 'INFY', scripCode: 500209, qty: 100, price: 1500.05 };

for (const ex of ['NSE', 'BSE']) {
  console.log(new OrderRouter(factories[ex]).route(order));
}
console.log(new OrderRouter(factories.NSE).route({ ...order, price: 1500.03 }));
console.log(new OrderRouter(factories.BSE).route({ ...order, qty: 20_000 }));
```

```text
NSE SENT NSE:INFY-EQ x100 @1500.05 fees=4.46
BSE SENT BSE:500209 x100 @1500.05 fees=5.63
NSE REJECTED: NSE tick size is 0.05
BSE REJECTED: BSE max qty per order is 10000
```

`OrderRouter` cannot accidentally mix families: it only ever talks to one `ExchangeFactory`.

## When to use / when NOT to use

- **Use** when you have *several product types* that vary *together* along one axis (exchange, cloud provider, UI theme, database dialect, country/region) and consistency across the family matters.
- **Don't use** when you only have one product type (use Factory Method or Simple Factory), or when families are unlikely to grow beyond one.

## Pitfalls

- **Adding a new product type is expensive**: a new `createMarginCalculator()` must be added to the interface and *every* concrete factory. Adding a new *family* (MCX) is cheap. Know which axis changes more often.
- **Interface bloat**: a factory with 12 `create*` methods usually hides two separate families.
- Over-engineering for a family of one.

## Related patterns

- **Factory Method** creates one product via subclassing; Abstract Factory groups several factory methods behind one object and is passed around by composition.
- **Builder** constructs one complex object step by step; Abstract Factory returns several simple objects immediately.
- **Bridge** (Chapter 5): an abstract factory is a common way to pick the right implementation side of a bridge.
- Concrete factories are frequently **Singletons**.

## Where it shows up in LLD interview problems

- Trading platform: exchange-specific components (NSE/BSE/MCX).
- Cross-platform UI kit: `LightThemeFactory` / `DarkThemeFactory` producing Button + Input + Modal.
- Cloud-agnostic storage: `AwsFactory` / `GcpFactory` producing BlobStore + Queue + SecretStore.
- Payment system with country-specific tax + currency + gateway.

Interview line: *"These three components vary together by exchange and must never be mixed, so I hide them behind one factory per exchange and inject that factory."*

## Quick check

1. Your product manager asks for MCX support. How much code changes? What if they instead ask for a new `MarginCalculator` for all exchanges?
2. Abstract Factory vs Builder in one line?

<details>
<summary>Answers</summary>

1. MCX: one new factory class plus its three products; nothing existing changes. New product type: the interface and every existing factory change. Abstract Factory makes new families cheap and new product types expensive.
2. Abstract Factory returns a family of related objects in one go; Builder assembles one complex object step by step.
