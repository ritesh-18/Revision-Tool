title: "4.2 Simple Factory"

## Intent

Put the `if/switch` that decides *which concrete class to instantiate* in one function or class, so callers ask for "an SMS notifier" without knowing about `SmsNotifier`.

(Strictly speaking this is an idiom, not one of the original 23 Gang of Four patterns, but interviewers call it "factory pattern" all the time.)

## Problem

Your notification service sends OTPs, trade confirmations and margin calls over email, SMS, push and WhatsApp. Without a factory, every caller has its own switch:

```ts
// ❌ This switch is copy-pasted into 6 files. Adding WhatsApp = editing all 6.
let sender;
if (user.pref === 'sms') sender = new SmsNotifier(twilioKey);
else if (user.pref === 'email') sender = new EmailNotifier(sesClient);
```

## TypeScript implementation

The switch version, with a compile-time exhaustiveness check so adding a channel to the union forces you to handle it:

```ts
type Channel = 'email' | 'sms' | 'push';

interface Notifier {
  readonly channel: Channel;
  send(to: string, message: string): string;
}

class EmailNotifier implements Notifier {
  readonly channel = 'email' as const;
  send(to: string, message: string): string {
    return `EMAIL to ${to}: ${message}`;
  }
}

class SmsNotifier implements Notifier {
  readonly channel = 'sms' as const;
  send(to: string, message: string): string {
    return `SMS to ${to}: ${message.slice(0, 20)}`; // SMS has a length limit
  }
}

class PushNotifier implements Notifier {
  readonly channel = 'push' as const;
  send(to: string, message: string): string {
    return `PUSH to device(${to}): ${message}`;
  }
}

class NotifierFactory {
  static create(channel: Channel): Notifier {
    switch (channel) {
      case 'email':
        return new EmailNotifier();
      case 'sms':
        return new SmsNotifier();
      case 'push':
        return new PushNotifier();
      default: {
        const unreachable: never = channel; // compile error if a case is missing
        throw new Error(`Unknown channel: ${String(unreachable)}`);
      }
    }
  }
}

// The caller only knows the interface and the factory.
function notifyTradeExecuted(channel: Channel, to: string): void {
  const notifier = NotifierFactory.create(channel);
  console.log(notifier.send(to, 'Your BUY order for 10 INFY is executed'));
}

notifyTradeExecuted('email', 'ritesh@example.com');
notifyTradeExecuted('sms', '+91-98xxxxxx01');
notifyTradeExecuted('push', 'dev-42');
```

```text
EMAIL to ritesh@example.com: Your BUY order for 10 INFY is executed
SMS to +91-98xxxxxx01: Your BUY order for 1
PUSH to device(dev-42): Your BUY order for 10 INFY is executed
```

**Registry variant** (closer to Open/Closed): new types register themselves, the factory never changes. Useful when the key comes from runtime data such as a DB row or a config file.

```ts
interface Vehicle {
  describe(): string;
}

type VehicleCtor = (plate: string) => Vehicle;

class VehicleFactory {
  private static readonly registry = new Map<string, VehicleCtor>();

  static register(kind: string, ctor: VehicleCtor): void {
    VehicleFactory.registry.set(kind, ctor);
  }

  static create(kind: string, plate: string): Vehicle {
    const ctor = VehicleFactory.registry.get(kind);
    if (!ctor) throw new Error(`No vehicle registered for "${kind}"`);
    return ctor(plate);
  }
}

VehicleFactory.register('bike', (plate) => ({ describe: () => `Bike ${plate} needs a SMALL spot` }));
VehicleFactory.register('car', (plate) => ({ describe: () => `Car ${plate} needs a MEDIUM spot` }));
// A new type is one line, no edits to the factory:
VehicleFactory.register('truck', (plate) => ({ describe: () => `Truck ${plate} needs a LARGE spot` }));

for (const [kind, plate] of [['car', 'MH12AB1234'], ['truck', 'KA01XY9999'], ['bus', 'DL3C0001']]) {
  try {
    console.log(VehicleFactory.create(kind, plate).describe());
  } catch (err) {
    console.log(`error: ${(err as Error).message}`);
  }
}
```

```text
Car MH12AB1234 needs a MEDIUM spot
Truck KA01XY9999 needs a LARGE spot
error: No vehicle registered for "bus"
```

Trade-off: the switch version is type-safe (the `never` check), the registry version is extensible but only checked at runtime.

## When to use / when NOT to use

- **Use** when creation logic is duplicated in several places, or when the concrete type is chosen from runtime data (user preference, config, request body).
- **Don't use** when there is only one implementation and no sign of a second; `new Thing()` is fine. Don't wrap a factory around a DI container that already resolves the right class.

## Pitfalls

- The factory becomes a **god switch** that imports every concrete class in the system. Split by domain.
- Returning concrete types (`create(): SmsNotifier`) defeats the purpose; return the interface.
- Stringly-typed keys (`create('sms ')`) fail at runtime. Prefer a union type.

## Related patterns

- **Factory Method** moves the decision into *subclasses* rather than a switch.
- **Abstract Factory** creates a *family* of related objects, not one.
- **Strategy** (Chapter 6) often gets its strategy object from a simple factory.

## Where it shows up in LLD interview problems

- Parking Lot: `VehicleFactory` / `ParkingSpotFactory` by type.
- Notification system: `NotifierFactory` by channel.
- Payment system: `PaymentMethodFactory` for UPI / card / net-banking.
- Trading: `OrderFactory.create('MARKET' | 'LIMIT' | 'SL')`.

Interview line: *"Creation of the concrete type is centralised here; callers depend only on the interface, and the union type plus `never` check means the compiler tells me if I forget a new type."*

## Quick check

1. What does the `const unreachable: never = channel` line buy you?
2. When would you prefer the registry variant over the switch?

<details>
<summary>Answers</summary>

1. Exhaustiveness checking. If someone adds `'whatsapp'` to `Channel` and forgets a `case`, `channel` is no longer `never` in the default branch and compilation fails.
2. When types are added by plugins or other modules, or chosen from runtime data you can't enumerate at compile time, and you want the factory to stay closed for modification.

</details>
