## Intent

Split a class that varies along two independent dimensions into two hierarchies (an **abstraction** and an **implementation**) connected by composition, so each can grow without multiplying classes.

## Problem

Your broker sends alerts. There are alert *kinds* (price alert, margin call, order update) and delivery *channels* (email, SMS, push, WhatsApp). With inheritance only you'd write `PriceAlertEmail`, `PriceAlertSms`, `MarginCallEmail`, ... 3 kinds × 4 channels = 12 classes, and each new channel adds 3 more. The two dimensions are independent: *what the alert says* and *how it is delivered*. Bridge keeps them in separate hierarchies: 3 + 4 = 7 classes.

## TypeScript implementation

```ts
interface Message {
  title: string;
  body: string;
  urgent: boolean;
}

// ----- Implementation side: HOW to deliver -----
interface MessageChannel {
  deliver(userId: string, msg: Message): string;
}

class EmailChannel implements MessageChannel {
  deliver(userId: string, msg: Message): string {
    return `email(${userId}) subject="${msg.title}" body="${msg.body}"`;
  }
}

class SmsChannel implements MessageChannel {
  deliver(userId: string, msg: Message): string {
    const text = `${msg.title}: ${msg.body}`;
    return `sms(${userId}) "${text.length > 40 ? `${text.slice(0, 37)}...` : text}"`;
  }
}

class PushChannel implements MessageChannel {
  deliver(userId: string, msg: Message): string {
    return `push(${userId}) [${msg.urgent ? 'HIGH' : 'normal'}] ${msg.title}`;
  }
}

// ----- Abstraction side: WHAT to say -----
abstract class Alert {
  constructor(protected readonly channel: MessageChannel) {}

  notify(userId: string): string {
    return this.channel.deliver(userId, this.compose());
  }

  protected abstract compose(): Message;
}

class PriceAlert extends Alert {
  constructor(
    channel: MessageChannel,
    private readonly symbol: string,
    private readonly price: number,
  ) {
    super(channel);
  }

  protected override compose(): Message {
    return { title: `${this.symbol} crossed ${this.price}`, body: 'Your price alert was triggered', urgent: false };
  }
}

class MarginCallAlert extends Alert {
  constructor(
    channel: MessageChannel,
    private readonly shortfall: number,
  ) {
    super(channel);
  }

  protected override compose(): Message {
    return {
      title: 'Margin shortfall',
      body: `Add Rs.${this.shortfall} before 3:00 PM to avoid square-off`,
      urgent: true,
    };
  }
}

const email = new EmailChannel();
const sms = new SmsChannel();
const push = new PushChannel();

console.log(new PriceAlert(email, 'INFY', 1500).notify('u1'));
console.log(new PriceAlert(push, 'INFY', 1500).notify('u1'));
console.log(new MarginCallAlert(sms, 12500).notify('u2'));
console.log(new MarginCallAlert(push, 12500).notify('u2'));
// Channel can even be chosen at runtime from user preferences:
const prefs: Record<string, MessageChannel> = { email, sms, push };
console.log(new MarginCallAlert(prefs['email'], 800).notify('u3'));
```

```text
email(u1) subject="INFY crossed 1500" body="Your price alert was triggered"
push(u1) [normal] INFY crossed 1500
sms(u2) "Margin shortfall: Add Rs.12500 before..."
push(u2) [HIGH] Margin shortfall
email(u3) subject="Margin shortfall" body="Add Rs.800 before 3:00 PM to avoid square-off"
```

Adding WhatsApp: one class implementing `MessageChannel`. Adding an "order executed" alert: one subclass of `Alert`. Neither touches the other side.

## When to use / when NOT to use

- **Use** when you see a class hierarchy growing as a *product* of two dimensions (shape × renderer, alert × channel, report × export format, payment method × gateway), or when you want to switch the implementation at runtime.
- **Don't use** when there is only one dimension of variation. A plain Strategy or interface is enough.

## Pitfalls

- Choosing the wrong split: the implementor interface must be **primitive and stable** (`deliver`), with the high-level logic on the abstraction side. If every new alert kind forces a new method on `MessageChannel`, the bridge is leaking.
- Over-design: in TypeScript many "bridges" collapse into "a class that takes an interface in its constructor". That is fine; the pattern is the *two independent hierarchies* idea, not the ceremony.

## Related patterns

- **Strategy** has the same shape (composition + interface). The difference is intent: Strategy swaps an *algorithm*; Bridge separates a whole *abstraction hierarchy* from an *implementation hierarchy*, both of which grow.
- **Adapter** makes mismatched things work after they exist; Bridge is planned up front.
- **Abstract Factory** can create and configure the right implementor for a bridge.

## Where it shows up in LLD interview problems

- Notification system: notification type × channel.
- Drawing/whiteboard app: shape × rendering engine (Canvas/SVG).
- Remote control × device (TV, AC) in classic OOD rounds.
- Report generation: report type × output format.

Interview line: *"Alert kind and delivery channel vary independently, so instead of a class per combination I'll compose them: `Alert` holds a `MessageChannel`. That's a bridge, M + N classes instead of M × N."*

## Quick check

1. With 5 alert kinds and 4 channels, how many classes do inheritance-only and Bridge need?
2. Bridge and Strategy have the same UML shape. What distinguishes them?

<details>
<summary>Answers</summary>

1. Inheritance-only: 5 × 4 = 20 concrete classes. Bridge: 5 + 4 = 9 (plus the two base types).
2. Intent and scope. Strategy swaps one algorithm inside a context. Bridge splits two whole hierarchies that both evolve independently, with the abstraction delegating its low-level work to the implementor.

</details>
