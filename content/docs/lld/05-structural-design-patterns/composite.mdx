## Intent

Compose objects into tree structures and let clients treat individual objects (leaves) and groups (composites) through the same interface.

## Problem

An investor's wealth dashboard shows: a *family account* containing *Ritesh's portfolio* and *Spouse's portfolio*; Ritesh's portfolio contains stocks, a mutual fund and a *"Long term" basket* that itself contains stocks. The UI needs `value()` and `dayChange()` at every level. Without Composite, the code is full of `if (node is Stock) ... else if (node is Portfolio) loop ...`, repeated for every operation. With Composite, you call `node.value()` and each node knows how to answer.

The same shape appears in file systems (file vs folder size), org charts (employee vs team cost), menus, and UI component trees.

## TypeScript implementation

```ts
type PriceMap = ReadonlyMap<string, number>;

interface Holding {
  readonly name: string;
  value(prices: PriceMap): number;
  count(): number; // number of leaf positions
  render(prices: PriceMap, indent?: string): string[];
}

const inr = (n: number) => `Rs.${n.toLocaleString('en-IN', { maximumFractionDigits: 2 })}`;

// ----- Leaves -----
class Stock implements Holding {
  constructor(
    readonly symbol: string,
    readonly qty: number,
  ) {}

  get name(): string {
    return this.symbol;
  }

  value(prices: PriceMap): number {
    const ltp = prices.get(this.symbol);
    if (ltp === undefined) throw new Error(`no price for ${this.symbol}`);
    return ltp * this.qty;
  }

  count(): number {
    return 1;
  }

  render(prices: PriceMap, indent = ''): string[] {
    return [`${indent}- ${this.symbol} x${this.qty} = ${inr(this.value(prices))}`];
  }
}

class MutualFund implements Holding {
  constructor(
    readonly name: string,
    readonly units: number,
    readonly nav: number,
  ) {}

  value(): number {
    return this.units * this.nav;
  }

  count(): number {
    return 1;
  }

  render(_prices: PriceMap, indent = ''): string[] {
    return [`${indent}- ${this.name} ${this.units}u = ${inr(this.value())}`];
  }
}

// ----- Composite -----
class Portfolio implements Holding {
  private readonly children: Holding[] = [];

  constructor(readonly name: string) {}

  add(...holdings: Holding[]): this {
    for (const h of holdings) {
      if (h === this) throw new Error('a portfolio cannot contain itself');
      this.children.push(h);
    }
    return this;
  }

  remove(name: string): void {
    const i = this.children.findIndex((c) => c.name === name);
    if (i >= 0) this.children.splice(i, 1);
  }

  value(prices: PriceMap): number {
    return this.children.reduce((sum, c) => sum + c.value(prices), 0); // recursion, no type checks
  }

  count(): number {
    return this.children.reduce((sum, c) => sum + c.count(), 0);
  }

  render(prices: PriceMap, indent = ''): string[] {
    const n = this.count();
    const header = `${indent}+ ${this.name} (${n} position${n === 1 ? '' : 's'}) = ${inr(this.value(prices))}`;
    return [header, ...this.children.flatMap((c) => c.render(prices, `${indent}  `))];
  }
}

const prices: PriceMap = new Map([
  ['INFY', 1500],
  ['TCS', 4100],
  ['HDFCBANK', 1650.5],
  ['ITC', 430],
]);

const longTerm = new Portfolio('Long term').add(new Stock('HDFCBANK', 20), new Stock('ITC', 100));
const ritesh = new Portfolio('Ritesh').add(
  new Stock('INFY', 10),
  new MutualFund('Nifty 50 Index Fund', 250.5, 180),
  longTerm,
);
const spouse = new Portfolio('Spouse').add(new Stock('TCS', 5));
const family = new Portfolio('Family').add(ritesh, spouse);

console.log(family.render(prices).join('\n'));

// The client treats a leaf and a whole tree the same way:
const items: Holding[] = [new Stock('INFY', 1), longTerm, family];
console.log(items.map((h) => `${h.name}: ${inr(h.value(prices))}`).join(' | '));

longTerm.remove('ITC');
console.log(`after selling ITC, family = ${inr(family.value(prices))}`);

try {
  family.add(new Stock('ZOMATO', 10));
  family.value(prices);
} catch (err) {
  console.log(`error: ${(err as Error).message}`);
}
```

Note that `Portfolio.value()` never asks "what type is this child?". Every node answers for itself; recursion does the rest.

**Design choice: where do `add`/`remove` live?** We put them only on `Portfolio` (the *safe* design): you can't call `add()` on a stock, and the compiler enforces it. The alternative (*transparent* design) puts `add/remove` on the common interface so clients never need to know if a node is a group, at the cost of leaves throwing "not supported" at runtime. In TypeScript, prefer the safe version and use a type guard (`h instanceof Portfolio`) in the rare place that builds the tree.

## When to use / when NOT to use

- **Use** whenever data is naturally a part-whole tree and you apply the same operations at every level: file systems, org charts, menus, bill of materials, nested comments, portfolio/basket hierarchies, UI trees, expression trees.
- **Don't use** when the structure is flat, or when leaves and groups share almost no operations (forcing a common interface then produces meaningless methods).

## Pitfalls

- **Cycles**: adding a parent into its own subtree causes infinite recursion. Guard against it (we only guard the trivial self case; a full check walks ancestors).
- **Performance**: recomputing `value()` over a deep tree on every tick is expensive. Cache aggregates and invalidate on change (or use Observer to push updates upward).
- **Shared children**: the same node in two parents is double-counted. Decide whether the structure is a tree (single parent) or a DAG.
- **Deep recursion** on very deep trees can blow the stack; use an explicit stack for traversal.

## Related patterns

- **Decorator** also wraps objects of the same interface, but it has exactly *one* child and adds behaviour; Composite has *many* children and aggregates results.
- **Iterator** and **Visitor** (Chapter 6) are the usual tools for walking and operating on composite trees.
- **Builder** is handy for constructing complex trees.
- **Flyweight** can share leaf data (e.g. instrument metadata) across many tree nodes.

## Where it shows up in LLD interview problems

- Design a file system (`File` and `Directory` both have `size()`, `ls`, `find`).
- Org chart / employee hierarchy (salary roll-up).
- Restaurant menu with sub-menus; e-commerce category tree.
- Splitwise-style groups inside groups; portfolio of instruments and baskets.

Interview line: *"Files and directories share `size()` and `name`, so both implement `FileSystemNode`; a directory holds children and sums their sizes recursively. The client never checks types."*

## Quick check

1. What's the trade-off between putting `add()` on the component interface vs only on the composite?
2. Why is Composite a natural fit for `du -sh` style disk usage?

<details>
<summary>Answers</summary>

1. On the interface ("transparent"): uniform treatment everywhere, but leaves must throw at runtime. Only on the composite ("safe"): the compiler prevents `file.add()`, but tree-building code must know which nodes are groups.
2. A directory's size is the sum of its children's sizes, and a child can itself be a directory; a recursive `size()` on a common interface computes it without any type checks.

</details>
