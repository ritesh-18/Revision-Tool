---
title: "5.8 Comparing the structural patterns"
---

| Pattern | Intent in one line | Interface to client | Wraps | Who composes it | LLD example |
| --- | --- | --- | --- | --- | --- |
| Adapter | Make an incompatible object fit your interface | **Different** from the adaptee's (yours) | 1 adaptee | Wiring code, per vendor | Payment gateways, market-data vendors |
| Bridge | Split two independent dimensions | Abstraction's own interface | 1 implementor (by design) | Designed up front | Alert kind × channel, shape × renderer |
| Composite | Treat one and many the same | **Same** for leaf and group | Many children | Tree-building code | File system, portfolio, org chart |
| Decorator | Add behaviour without subclassing | **Same** as the wrapped object | 1 component, stackable | Client/wiring, any order | Logging/caching/retry, pizza add-ons |
| Facade | Simplify a complex subsystem | **New, simpler** interface | Many subsystem objects | Module author | Order placement, booking |
| Flyweight | Share immutable common state | Flyweight + extrinsic params | Nothing (it is shared) | Flyweight factory | Instrument metadata, chess pieces |
| Proxy | Control access to an object | **Same** as the subject | 1 subject, often manages it | Usually the proxy/infrastructure | Caching, auth, lazy load, JS `Proxy` |

**The wrapper cheat-sheet:** *Adapter converts, Decorator decorates, Proxy protects (and postpones), Facade fronts, Composite collects.*
