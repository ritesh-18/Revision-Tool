How to use this bank: read the question, answer it **out loud** in under a minute, then open the answer and compare. The model answers are longer than what you would say. They are written so you understand the idea, not so you recite them. A good spoken answer has three parts: a definition, a concrete example from a problem you have built, and one trade-off.

## OOP (10)

**Q1. Explain the four pillars of OOP using one example.**

<details>
<summary>Answer</summary>

Use a payment system as the running example.

- **Encapsulation.** A `Wallet` keeps its balance private and exposes only `credit()` and `debit()`. `debit()` enforces the invariant that the balance never goes negative. Nobody outside can write `wallet.balance = -5`.
- **Abstraction.** Callers depend on a `PaymentMethod` interface with `pay(amount)`. They do not know whether UPI, a card or a wallet sits behind it.
- **Inheritance.** `CreditCard` and `DebitCard` can extend an abstract `Card` that shares expiry and CVV validation.
- **Polymorphism.** `checkout(method: PaymentMethod)` calls `method.pay()`, and the right implementation runs at runtime.

The interview-grade point: encapsulation protects **invariants**, not just fields. Abstraction and polymorphism are what make the Strategy pattern possible. Inheritance is the pillar to use most sparingly.

</details>

**Q2. What is the difference between abstraction and encapsulation? They sound the same.**

<details>
<summary>Answer</summary>

They work at different levels.

- **Abstraction** is about *what* you expose: pick the few operations that matter and hide the rest. It is a design decision about the interface, for example `RateLimiter.isAllowed(key)`.
- **Encapsulation** is about *how* you protect state: keep data and the rules that guard it in one place, and stop outside code from bypassing those rules. It is an implementation decision, for example the token count is `private` and changes only inside `isAllowed`.

You can have one without the other. A class with all-public fields but a nice method name has abstraction and no encapsulation. A good class has both.

</details>

**Q3. Composition vs inheritance: when do you pick each?**

<details>
<summary>Answer</summary>

Use **inheritance** only for a true, stable "is-a" relationship where the subclass can be used anywhere the parent is expected (Liskov). `Bishop extends Piece` is a reasonable example.

Use **composition** ("has-a") by default, especially when behaviour varies independently or changes at runtime. A `Vehicle` that *has* a `PricingStrategy` can switch pricing without new subclasses. With inheritance you would end up with `WeekendCarPricing`, `WeekendBikePricing`, `SurgeCarPricing`… — one class per combination.

Reasons to prefer composition:

1. Behaviour can be swapped at runtime.
2. It avoids the fragile-base-class problem, where a change in the parent silently breaks children.
3. Each part can be tested in isolation.
4. TypeScript has single class inheritance, but a class can hold any number of collaborators.

Rule of thumb: inherit to share **identity**, compose to share **behaviour**.

</details>

**Q4. What is polymorphism in TypeScript, given that types are erased at runtime?**

<details>
<summary>Answer</summary>

There are three kinds, and TypeScript supports all of them:

1. **Subtype (runtime) polymorphism.** Method dispatch through the prototype chain. `shape.area()` calls whichever class's `area` the object was built from. Type erasure does not matter here because the dispatch is done by JavaScript.
2. **Parametric polymorphism.** Generics, such as `Repository<T>`. This exists only at compile time.
3. **Ad-hoc polymorphism.** Function overloads and union narrowing. At runtime there is one implementation that checks its arguments.

The catch with erasure: you cannot write `if (x instanceof PaymentMethod)` when `PaymentMethod` is an interface. Use a class, a discriminant field (`kind: 'upi'`), or a user-defined type guard instead.

</details>

**Q5. Abstract class or interface: how do you choose?**

<details>
<summary>Answer</summary>

- **Interface**: a pure contract with no state or code. A class can implement many of them. It has zero runtime cost because it is erased. Use it for roles such as `Notifier`, `Clock` or `Repository<T>`.
- **Abstract class**: a partial implementation. It can hold shared fields, constructor logic and template methods, and leave hooks `abstract`. It exists at runtime, so `instanceof` works. A class can extend only one.

Pick an abstract class when subclasses genuinely share code and state, such as a `Piece` with `color` and a `position` plus an abstract `canMove()`. Otherwise pick an interface. A common combination is an interface for callers, plus an optional abstract base class that implementers can extend to save boilerplate.

```ts
interface Notifier { send(to: string, msg: string): string }

abstract class BaseNotifier implements Notifier {
  send(to: string, msg: string): string {
    if (!to) throw new Error('recipient required');
    return this.deliver(to, msg.trim());
  }
  protected abstract deliver(to: string, msg: string): string;
}

class SmsNotifier extends BaseNotifier {
  protected override deliver(to: string, msg: string): string {
    return `SMS to ${to}: ${msg}`;
  }
}

const n: Notifier = new SmsNotifier();
n.send('98xxxx', ' hi ');
```

</details>

**Q6. What are association, aggregation and composition? Give examples from a parking lot.**

<details>
<summary>Answer</summary>

All three are "uses" or "has" relationships. They differ in ownership and lifetime.

- **Association**: objects know each other but neither owns the other. A `Ticket` references a `Vehicle`, and the vehicle exists independently of the ticket.
- **Aggregation** (weak has-a): a whole groups parts, but the parts can outlive it. A `ParkingLot` has `Attendant`s, and attendants still exist if the lot closes.
- **Composition** (strong has-a): the part's lifetime is bound to the whole. A `ParkingFloor` owns its `ParkingSpot`s. Delete the floor and its spots go with it.

In code the difference is usually who **creates** the part: the whole creates composed parts inside its constructor, while aggregated parts are passed in. On a UML diagram, composition is a filled diamond and aggregation a hollow one (see §16.7).

</details>

**Q7. Why is a "god class" bad, and how do you spot one in a machine-coding round?**

<details>
<summary>Answer</summary>

A god class knows and does too much. Typical examples are a `ParkingLotManager` that parses input, allocates spots, computes fees, prints tickets and stores data. It breaks SRP, is hard to test, and every new feature touches it, so merge conflicts and regressions pile up.

Warning signs:

- it runs to hundreds of lines;
- it has many unrelated private fields;
- its method names cover several domains (`calculateFee`, `printReceipt`, `findSpot`);
- most other classes are plain data holders with no behaviour (an anemic model).

Fix it by pulling out cohesive collaborators: a `SpotAllocator` (Strategy), a `FeeCalculator` (Strategy), a `TicketRepository`, and a thin `ParkingService` that coordinates them.

</details>

**Q8. What does "program to an interface, not an implementation" mean in practice?**

<details>
<summary>Answer</summary>

Your variables, parameters and constructor dependencies should be typed with the **role** (`PaymentGateway`), not the concrete class (`RazorpayGateway`). Only the composition root, meaning `main()` or your DI setup, names concrete classes.

The benefits: you can swap implementations, for example a fake gateway in tests or a fallback gateway in production, without touching business logic. That is DIP applied at the level of a single variable.

In TypeScript this is cheap. Interfaces are erased, and structural typing means a test double only needs the right shape. It does not have to `implements` anything.

</details>

**Q9. What is the difference between deep and shallow copy, and why does it matter in LLD? (Reported at Microsoft [snippet].)**

<details>
<summary>Answer</summary>

A **shallow copy** duplicates the top-level object, but nested objects are still shared. `{ ...order }` copies `order` but shares `order.items`. A **deep copy** duplicates the whole graph (`structuredClone(order)`).

Why it matters:

- **Leaking internal state.** If `getItems()` returns the internal array, a caller can `push` into it and bypass your validation. Return a copy or a `ReadonlyArray`.
- **Prototype pattern and snapshots.** Memento or undo snapshots must be deep enough that later edits do not change the saved history.
- **Concurrency.** Shared mutable nested objects are where races hide.

Trade-off: deep copies cost time and memory. Often the better option is **immutable data**, which can be shared safely without copying.

```ts
type Order = { id: string; items: string[] };
const original: Order = { id: 'o1', items: ['pen'] };

const shallow = { ...original };
shallow.items.push('book');
console.log(`after shallow edit: ${original.items.join(',')}`);

const deep = structuredClone(original);
deep.items.push('lamp');
console.log(`after deep edit: ${original.items.join(',')}`);
```

```text
after shallow edit: pen,book
after deep edit: pen,book
```

</details>

**Q10. What is immutability, and where would you use it in an LLD answer?**

<details>
<summary>Answer</summary>

An immutable object cannot change after it is created. A "change" produces a new object instead.

Good places to use it:

- **Value objects**: `Money`, `Price`, `DateRange`, `Position`. Two `Money(100, 'INR')` values are interchangeable.
- **Events and ledger entries**: `Trade`, `LedgerEntry`, `OrderPlaced`. History must never be rewritten.
- **Configuration and snapshots**: shared across components with no defensive copies.

In TypeScript, use `readonly` fields, `ReadonlyArray<T>` / `readonly T[]`, `Readonly<T>`, and `Object.freeze` when you also need a runtime guarantee. `readonly` is compile-time only and shallow.

Benefits: the object is always valid after construction, it is safe to share between async tasks, and it is easy to reason about and test. Cost: more allocations. Keep entities with an identity and a lifecycle (such as `Order`) mutable behind methods, and make values immutable.

</details>

## SOLID & principles (10)

**Q11. Explain SRP with a counter-example.**

<details>
<summary>Answer</summary>

**Single Responsibility Principle**: a module should have one reason to change, meaning one stakeholder or one axis of change.

Counter-example: an `Invoice` class that computes totals, formats a PDF and saves itself to the DB. Finance changes the tax rules, design changes the PDF layout, and the platform team changes the database. That is three reasons to change, so three teams end up editing one file.

Fix: `Invoice` (data + total calculation), `InvoiceRenderer`, and `InvoiceRepository`.

SRP does **not** mean "one method per class". A class with ten methods about the same concern is fine.

</details>

**Q12. How do you demonstrate OCP in a 90-minute machine-coding round?**

<details>
<summary>Answer</summary>

**Open/Closed Principle**: add behaviour by adding code, not by editing working code.

In a round, show it in three steps:

1. Put the variation behind an interface, for example `SplitStrategy`.
2. Register implementations in a map or factory, for example `{ EQUAL: new EqualSplit(), ... }`.
3. During the walkthrough, add a new variant live. "To add SHARES splits, I write one class and register it. Nothing else changes."

The telltale OCP violation is a `switch (type)` that is copied into several places. One `switch` inside a factory is fine: it is the single place that knows every concrete type.

```ts
interface SplitStrategy { split(total: number, n: number): number[] }

class EqualSplit implements SplitStrategy {
  split(total: number, n: number): number[] {
    const base = Math.floor(total / n);
    const rem = total - base * n;
    return Array.from({ length: n }, (_, i) => base + (i < rem ? 1 : 0));
  }
}

const registry = new Map<string, SplitStrategy>([['EQUAL', new EqualSplit()]]);

// Extension: a new class plus one registration line. No edits above.
class FirstPaysAll implements SplitStrategy {
  split(total: number, n: number): number[] {
    return Array.from({ length: n }, (_, i) => (i === 0 ? total : 0));
  }
}
registry.set('FIRST_PAYS', new FirstPaysAll());

for (const key of ['EQUAL', 'FIRST_PAYS']) {
  console.log(`${key}: ${registry.get(key)!.split(1000, 3).join(' ')}`);
}
```

```text
EQUAL: 334 333 333
FIRST_PAYS: 1000 0 0
```

Notice that the amounts are in paise (integers). The remainder is handed out one paisa at a time, so the parts always add up to the total.

</details>

**Q13. Give a Liskov Substitution violation that looks innocent.**

<details>
<summary>Answer</summary>

The classic is `Square extends Rectangle`: setting the width of a square also changes its height, which breaks callers that expect them to be independent.

A domain example: `ReadOnlyAccount extends Account` overrides `withdraw()` to throw. Any code written against `Account` that calls `withdraw()` now fails unexpectedly. The subclass has **strengthened a precondition**.

LSP rules of thumb:

- subclasses may not demand more (preconditions) or promise less (postconditions);
- they must keep the parent's invariants;
- they must not throw new kinds of errors for inherited operations.

Fix: split the capabilities, for example `interface Withdrawable`, and have only the accounts that support withdrawal implement it. That is ISP helping LSP.

</details>

**Q14. What is the Interface Segregation Principle? Show a fix.**

<details>
<summary>Answer</summary>

**ISP**: clients should not be forced to depend on methods they do not use. A fat `Printer` interface with `print`, `scan` and `fax` forces a simple printer to stub out `scan` and `fax`.

In LLD rounds this shows up as a `Vehicle` interface with `fly()`, or a `User` with admin methods. Split by role:

```ts
interface Bookable { book(slotId: string, userId: string): void }
interface Cancellable { cancel(bookingId: string): void }
interface Reportable { report(): string[] }

class GymClass implements Bookable, Cancellable {
  book(slotId: string, userId: string): void { void slotId; void userId; }
  cancel(bookingId: string): void { void bookingId; }
}

class AdminDashboard implements Reportable {
  report(): string[] { return []; }
}
```

Smaller interfaces also make test doubles tiny.

</details>

**Q15. What is the Dependency Inversion Principle, and how is it different from dependency injection?**

<details>
<summary>Answer</summary>

- **DIP** is a *principle*: high-level policy (for example `BookingService`) should depend on abstractions (`SeatRepository`, `PaymentGateway`), and the low-level details implement those abstractions. The abstraction belongs to the high-level module.
- **Dependency injection** is a *technique*: an object receives its dependencies from outside (usually through the constructor) instead of creating them with `new`.

DI is the usual way to achieve DIP, but they are not the same thing. You can inject a concrete class, which is DI without DIP. You can also depend on an interface but look it up from a global registry, which is DIP without clean DI. NestJS gives you a DI container. In a machine-coding round, plain constructor injection wired up in `main()` is enough.

</details>

**Q16. DRY, KISS, YAGNI: when do they conflict?**

<details>
<summary>Answer</summary>

- **DRY** (Don't Repeat Yourself) is about not duplicating *knowledge*: one source of truth for a rule.
- **KISS** (Keep It Simple): prefer the simplest design that works.
- **YAGNI** (You Aren't Gonna Need It): don't build for speculative requirements.

They conflict when DRY tempts you to build a clever generic abstraction for two pieces of code that only *look* alike. That abstraction breaks KISS and YAGNI, and it couples two things that will change for different reasons.

A useful heuristic is the "rule of three": wait for the third occurrence before extracting. In interviews, YAGNI has a twist: interviewers *will* ask for extensions. So put a seam (an interface) where the obvious follow-ups will land (new vehicle type, new split type), but don't implement them until asked.

</details>

**Q17. What is the Law of Demeter?**

<details>
<summary>Answer</summary>

"Talk only to your immediate friends." A method should call methods on itself, its fields, its parameters, and objects it creates. It should not reach through chains like `order.getCustomer().getWallet().debit(x)`.

Why it matters: chains couple you to the internal structure of objects several hops away. Fix it with a **tell, don't ask** method: `order.chargeCustomer(x)` or `customer.pay(x)`.

Fluent builders (`builder.withA().withB()`) do not violate it, because each call returns the same object you are already talking to.

</details>

**Q18. What do "high cohesion, low coupling" mean? How do you measure them informally?**

<details>
<summary>Answer</summary>

- **Cohesion**: how closely the members of a module belong together. High cohesion means every method uses most of the fields and serves one purpose.
- **Coupling**: how much a module depends on others' internals. Low coupling means it depends on a few narrow interfaces.

Informal checks:

- Can you describe the class in one sentence without "and"? (cohesion)
- How many imports and constructor parameters does it have? (coupling)
- Changing class A forces edits in how many other classes? (coupling)
- Can you unit-test it with two or fewer fakes? (both)

</details>

**Q19. Your interviewer says, "This is over-engineered." How do you respond?**

<details>
<summary>Answer</summary>

Don't get defensive. Look at the seams you added and ask, for each one, which likely change it enables.

- If you can name a concrete, likely change ("pricing rules change every quarter"), explain it in one sentence and keep the seam.
- If you can't, offer to collapse it: "Fair point, a single class is enough until we need a second strategy. I'll inline it."

Signs of over-engineering in a 90-minute round: interfaces with one implementation and no likely second one, abstract factories for three objects, generic event buses when one callback would do, and layers that only pass calls through. Interviewers reward *proportionate* design.

</details>

**Q20. What is the difference between a domain entity, a value object and a DTO?**

<details>
<summary>Answer</summary>

- **Entity**: has an identity that stays the same while its state changes (`Order#o-17`, `User#u-1`). Two entities are equal if their IDs are equal. It is usually mutable through methods that protect invariants.
- **Value object**: defined entirely by its values (`Money(500, 'INR')`, `Seat('A', 7)`). It is immutable and compared by value.
- **DTO** (Data Transfer Object): a dumb data shape for moving data across a boundary (API request or response, message payload). It has no behaviour and is often validated on entry.

In TypeScript, DTOs are usually `type`s or interfaces, value objects are small classes with `readonly` fields and an `equals()` method, and entities are classes with private state. Keeping them apart stops HTTP-shaped data from leaking into domain logic.

</details>

## Design patterns (15)

**Q21. Strategy vs State: they look identical in code. What is the difference?**

<details>
<summary>Answer</summary>

Both delegate to an object behind an interface. The difference is **who changes the delegate, and why**.

- **Strategy**: the *client* chooses an algorithm, and the strategies do not know about each other. Examples: `PricingStrategy`, `SplitStrategy`.
- **State**: the *context's own state* changes, often triggered by the state objects themselves (`this.machine.setState(new HasCoinState())`). Each state knows which transitions are legal. Examples: vending machine, ATM session, elevator.

Quick test: if the same object moves through the implementations over its lifetime according to rules, it is State. If an implementation is picked once by configuration, it is Strategy.

</details>

**Q22. Which pattern would you use for different pricing rules in a parking lot (hourly, flat weekend, EV discount)?**

<details>
<summary>Answer</summary>

**Strategy** for each pricing rule, behind `PricingStrategy.price(ticket, exitTime)`. If the rules stack (EV discount *on top of* weekend pricing), wrap them with **Decorator**: `new EvDiscount(new WeekendPricing(base))`. Choose the strategy with a small **Factory** keyed by lot configuration or vehicle type.

```ts
interface Pricing { price(hours: number): number }

class Hourly implements Pricing {
  constructor(private readonly ratePaise: number) {}
  price(hours: number): number { return Math.ceil(hours) * this.ratePaise; }
}

class PercentOff implements Pricing {
  constructor(private readonly inner: Pricing, private readonly pct: number) {}
  price(hours: number): number {
    const base = this.inner.price(hours);
    return base - Math.floor((base * this.pct) / 100);
  }
}

const car: Pricing = new Hourly(4000);
const evCar: Pricing = new PercentOff(car, 20);
console.log(`car 2.5h = ${car.price(2.5)} paise`);
console.log(`ev car 2.5h = ${evCar.price(2.5)} paise`);
```

```text
car 2.5h = 12000 paise
ev car 2.5h = 9600 paise
```

</details>

**Q23. Which pattern would you use to notify users when a stock hits their price alert?**

<details>
<summary>Answer</summary>

**Observer (pub-sub)** on price ticks: a `PriceFeed` publishes `(symbol, price)`, and an `AlertService` subscribes per symbol. Inside `AlertService`, don't scan every alert on each tick. Keep two sorted structures per symbol: "above" alerts sorted by trigger price ascending and "below" alerts sorted descending. Then each tick only pops the alerts that have crossed.

Delivering the notification is a **Strategy** per channel (push, SMS, email). A trailing stop-loss adds **State** or a small per-order updater whose trigger price moves with the market.

Mention the edge cases: ticks arriving out of order (use sequence numbers), and firing each alert exactly once (mark it triggered atomically before sending).

</details>

**Q24. Which pattern would you use to support undo/redo in a text editor?**

<details>
<summary>Answer</summary>

**Command**: each edit is an object with `execute()` and `undo()`. Keep two stacks, `undoStack` and `redoStack`. A new command clears the redo stack.

When computing an inverse is hard (for example "apply formatting to a large selection"), store a **Memento** (a snapshot of the affected state) inside the command instead.

For memory, you can cap the stack size or merge consecutive typing commands into one.

```ts
interface Command { execute(): void; undo(): void }

class Doc { text = ''; }

class Insert implements Command {
  constructor(private readonly doc: Doc, private readonly s: string) {}
  execute(): void { this.doc.text += this.s; }
  undo(): void { this.doc.text = this.doc.text.slice(0, -this.s.length); }
}

class History {
  private undos: Command[] = [];
  private redos: Command[] = [];
  run(c: Command): void { c.execute(); this.undos.push(c); this.redos = []; }
  undo(): void { const c = this.undos.pop(); if (c) { c.undo(); this.redos.push(c); } }
  redo(): void { const c = this.redos.pop(); if (c) { c.execute(); this.undos.push(c); } }
}

const doc = new Doc();
const h = new History();
h.run(new Insert(doc, 'Hello'));
h.run(new Insert(doc, ' world'));
h.undo();
console.log(`after undo: "${doc.text}"`);
h.redo();
console.log(`after redo: "${doc.text}"`);
```

```text
after undo: "Hello"
after redo: "Hello world"
```

</details>

**Q25. Which pattern would you use for a file system with files and folders, where you need total size?**

<details>
<summary>Answer</summary>

**Composite**: `FileNode` is the common interface with `size()` and `name`. `File` is a leaf. `Folder` holds children and sums their sizes recursively.

Search features ("find all `.log` files larger than 1 MB") fit a **Specification** / filter chain that is combined with AND and OR. Different reports over the tree (size, count, permissions audit) can use **Visitor**. If you only have one or two reports, a recursive method is simpler.

</details>

**Q26. Which pattern would you use for ATM cash dispensing with ₹2000/₹500/₹100 notes?**

<details>
<summary>Answer</summary>

**Chain of Responsibility**: each handler dispenses as many notes of its denomination as it can, then passes the remainder to the next handler.

Two cautions:

1. **Check before you commit.** Greedy dispensing can fail halfway (you need ₹600 and have no ₹100 notes left). So compute the whole plan first, check that it covers the amount exactly, and only then deduct the notes. That is the "atomic" part interviewers ask about.
2. Greedy works for canonical denomination systems like INR. For arbitrary denominations, mention that you would need a DP-style search.

The ATM session itself (idle → card inserted → authenticated → transaction) is **State**.

</details>

**Q27. When is Singleton acceptable, and what are its problems?**

<details>
<summary>Answer</summary>

It is acceptable for things that are truly single *per process*, where tests can still replace them: a logger, a config snapshot, a metrics registry.

Problems:

- hidden global state;
- tests leak state into each other;
- dependencies are hidden (nobody sees them in constructors);
- in multi-threaded languages, lazy initialisation needs double-checked locking (Java) or `sync.Once` (Go).

In Node, an ES module is evaluated once, so `export const logger = new Logger()` is already a process-wide singleton. The better approach is to *create* one instance in `main()` and *inject* it. You get the "one instance" guarantee without the global lookup.

</details>

**Q28. Factory Method vs Abstract Factory vs Builder: when do you use each?**

<details>
<summary>Answer</summary>

- **Simple factory / Factory Method**: create *one* product whose concrete type depends on input, e.g. `VehicleFactory.create('CAR')` or `NotifierFactory.for(channel)`.
- **Abstract Factory**: create *families* of related products that must match, e.g. `UiKit.dark()` returns a matching button, input and modal, or a payment provider factory returns a matching client, webhook verifier and refund API.
- **Builder**: create *one complex* object step by step, with many optional parts and validation at the end, e.g. `OrderBuilder` for a limit order with a stop price, validity and tags; an `HttpRequest` builder.

A quick way to decide: a big `switch` on type → factory; a parameter list longer than 4 → builder; "these objects must be consistent with each other" → abstract factory.

</details>

**Q29. Which pattern would you use to integrate three payment gateways with different SDKs?**

<details>
<summary>Answer</summary>

- **Adapter**: wrap each SDK behind your own `PaymentGateway` interface (`charge`, `refund`, `status`), converting its request and response shapes into your domain types.
- **Strategy / router**: choose the gateway per transaction (by method, cost or success rate).
- **Chain of Responsibility** or a fallback loop: if gateway A fails with a *retryable* error, try B.
- **Circuit breaker** (a Proxy-like wrapper, §7.10) around each gateway: stop calling a gateway that is failing.
- **Idempotency key** passed to every call, so a retry never charges twice.

This combination is what "multi-gateway payment with fallback" (Walmart 2026) is really asking for.

</details>

**Q30. Decorator vs Proxy: what is the difference?**

<details>
<summary>Answer</summary>

Both wrap an object that has the same interface.

- **Decorator** *adds behaviour* the client asked for, and decorators are often stacked: `new Compress(new Encrypt(new FileSink()))`, or logging and metrics around a repository.
- **Proxy** *controls access* to the real object, and the client usually doesn't know it's there: lazy loading, caching, access control, remote proxies, rate limiting, circuit breaking.

The code can look the same. The difference is intent. When asked, name the intent.

</details>

**Q31. Which pattern would you use for a rule-based coupon engine (min cart value, category, first order, user tier)?**

<details>
<summary>Answer</summary>

- **Specification / Composite predicates**: each rule is an object with `isSatisfiedBy(ctx)`, and `And`, `Or` and `Not` combine rules into trees. New rule → new class (OCP).
- **Strategy**: the discount *calculation* (flat, percent with cap, buy-X-get-Y).
- **Chain of Responsibility / pipeline**: when rules must run in order and can short-circuit with a reason ("coupon expired").
- **Factory / Interpreter**: when rules come from JSON config, parse them into the predicate tree.

Tie-breaking ("best coupon for this cart") is a simple max over the eligible coupons.

</details>

**Q32. Mediator vs Observer?**

<details>
<summary>Answer</summary>

- **Observer**: one-to-many broadcast. The subject doesn't know who is listening, and listeners don't coordinate with each other.
- **Mediator**: many-to-many coordination through a central object that contains the *interaction logic*. The colleagues talk only to the mediator.

Examples: a chat room (users send to the room, and the room decides who receives), an air-traffic control tower, the elevator controller that coordinates cars and floor buttons.

The risk with Mediator: it can grow into a god class. Keep the policy decisions in Strategies it calls.

</details>

**Q33. Template Method vs Strategy?**

<details>
<summary>Answer</summary>

Both let you vary part of an algorithm.

- **Template Method** uses *inheritance*. The base class fixes the skeleton (`validate → reserve → charge → confirm`) and subclasses override hooks. The variation is chosen at compile time, and the skeleton is enforced.
- **Strategy** uses *composition*. The whole algorithm (or one step of it) is a pluggable object, can change at runtime, and can be tested in isolation.

Prefer Strategy by default. Template Method works well when the order of steps is a rule that subclasses must not break, for example report generators or game turn loops.

</details>

**Q34. Which pattern would you use to add caching, logging and retry to a repository without changing it?**

<details>
<summary>Answer</summary>

Stack **Decorators** (or Proxies) that implement the same `Repository<T>` interface:

```ts
interface Repo<T> { get(id: string): Promise<T | undefined> }

class CachingRepo<T> implements Repo<T> {
  private cache = new Map<string, T>();
  constructor(private readonly inner: Repo<T>) {}
  async get(id: string): Promise<T | undefined> {
    const hit = this.cache.get(id);
    if (hit !== undefined) return hit;
    const v = await this.inner.get(id);
    if (v !== undefined) this.cache.set(id, v);
    return v;
  }
}

class LoggingRepo<T> implements Repo<T> {
  constructor(private readonly inner: Repo<T>, private readonly log: (m: string) => void) {}
  async get(id: string): Promise<T | undefined> {
    this.log(`get ${id}`);
    return this.inner.get(id);
  }
}
```

The order matters: `Logging(Caching(db))` logs every call, while `Caching(Logging(db))` logs only cache misses. Say this out loud, because it shows you understand the pattern.

</details>

**Q35. How do you pick patterns without "pattern-stuffing"?**

<details>
<summary>Answer</summary>

Start from the **axis of change** in the requirements, not from a list of patterns:

- "different ways to do X" → Strategy
- "object behaves differently depending on its status" → State
- "when X happens, others react" → Observer
- "create one of many types" → Factory
- "build something with many options" → Builder
- "tree of parts and wholes" → Composite
- "incompatible third-party API" → Adapter
- "undo, queue or log actions" → Command
- "pass a request along until someone handles it" → Chain of Responsibility

If no requirement names a variation, don't add a pattern. In the walkthrough, justify each pattern with the requirement it serves: "I used Strategy for splits because the spec lists three types and hints at more." Research-backed guides agree that Strategy, State, Observer and Factory cover most LLD rounds.

</details>

## UML & modelling (5)

**Q36. Walk me through turning requirements into classes.**

<details>
<summary>Answer</summary>

1. **Nouns → candidate entities.** Underline the nouns: user, show, seat, booking, payment.
2. **Remove duplicates and plain attributes.** "Seat number" is an attribute, not a class.
3. **Verbs → methods and services.** "book seats" goes on a `BookingService`, not on `Seat`.
4. **Find the variation points** (Strategy, State) and **the events** (Observer).
5. **Decide ownership and relationships**: composition, aggregation, association; cardinalities.
6. **Define the invariants** each entity protects ("a seat can't be booked twice for a show").
7. **Sketch the key sequence** for the main use case to check that the responsibilities make sense.

Then write the interfaces first, then the models, then the services, then `main()`, as covered in Chapter 8.

</details>

**Q37. What goes on a class diagram, and how much detail should you draw in an interview?**

<details>
<summary>Answer</summary>

Draw classes (name, key fields, key methods), interfaces, relationships (inheritance, realisation, composition, aggregation, association, dependency) and multiplicities (`1`, `0..*`).

In an interview, draw **only the core 6–12 classes**. Show the relationships that matter and the interfaces where Strategies plug in. Skip getters, setters and private helpers. Five minutes is plenty. The diagram exists to agree on the design, not to document it.

- **State diagram**: when *one object's lifecycle* is the heart of the problem: order (PLACED → CONFIRMED → OUT_FOR_DELIVERY → DELIVERED / CANCELLED), elevator, ATM session, seat.

**Q39. How do you model many-to-many relationships, such as users and groups?**

<details>
<summary>Answer</summary>

Introduce an explicit **association entity** when the relationship has its own data: `Membership { userId, groupId, role, joinedAt }`. Store indexes both ways (`membershipsByUser`, `membershipsByGroup`) so both lookups are O(1) plus the size of the result.

This also makes constraints like "max 5 groups per admin" or "max 10 memberships per user" (Groww group-chat [snippet]) easy to enforce in one place. Avoid storing object arrays on both sides that must be kept in sync by hand. That is where bugs creep in.

**Q40. How do you decide where a method lives, e.g. `calculateFine()` on `Book`, `Member`, `Loan` or a service?**

<details>
<summary>Answer</summary>

Apply **Information Expert** (GRASP): put the behaviour with the object that holds the data it needs. The fine depends on the due date and return date, which belong to the `Loan`, and on a fine policy.

So write `loan.fine(policy, returnedOn)`, or a `FinePolicy.compute(loan, returnedOn)` Strategy. Use a service only when the operation coordinates several aggregates (for example, returning a book updates the loan, the book copy and the waitlist).

Anti-pattern: every method on a `LibraryService` while `Book`, `Member` and `Loan` are plain data holders (an anemic domain model).

</details>

## Concurrency & consistency in LLD (10)

**Q41. Node is single-threaded. Why do we still have race conditions?**

<details>
<summary>Answer</summary>

JavaScript runs one piece of code at a time, but **async operations interleave at every `await`**. If you check something, `await` (a DB call, a payment, even `await Promise.resolve()`), and then act, another request can run in between and invalidate your check. This is the classic check-then-act or read-modify-write race.

Synchronous code between two `await`s is atomic with respect to other JS code in the same process, and that is your main tool. It is not atomic across processes or servers, so production systems still need DB transactions, conditional updates or distributed locks.

```ts
let balance = 100;

async function withdraw(who: string, amount: number): Promise<void> {
  if (balance >= amount) {
    await Promise.resolve(); // simulated I/O, e.g. a fraud check
    balance -= amount;
    console.log(`${who} withdrew ${amount}, balance ${balance}`);
  } else {
    console.log(`${who} rejected`);
  }
}

await Promise.all([withdraw('A', 80), withdraw('B', 80)]);
console.log(`final balance ${balance}`);
```

```text
A withdrew 80, balance 20
B withdrew 80, balance -60
final balance -60
```

Both requests passed the check before either one deducted. The fix is in Q42.

</details>

**Q42. How do you implement a mutex in TypeScript?**

<details>
<summary>Answer</summary>

Chain promises: each `acquire()` waits for the previous holder's release. Always release in `finally`.

```ts
class Mutex {
  private tail: Promise<void> = Promise.resolve();
  async runExclusive<T>(fn: () => Promise<T>): Promise<T> {
    let release!: () => void;
    const next = new Promise<void>(r => (release = r));
    const prev = this.tail;
    this.tail = prev.then(() => next);
    await prev;
    try {
      return await fn();
    } finally {
      release();
    }
  }
}

let balance = 100;
const lock = new Mutex();

async function withdraw(who: string, amount: number): Promise<void> {
  await lock.runExclusive(async () => {
    if (balance < amount) {
      console.log(`${who} rejected`);
      return;
    }
    await Promise.resolve();
    balance -= amount;
    console.log(`${who} withdrew ${amount}, balance ${balance}`);
  });
}

await Promise.all([withdraw('A', 80), withdraw('B', 80)]);
console.log(`final balance ${balance}`);
```

```text
A withdrew 80, balance 20
B rejected
final balance 20
```

For per-account locking, keep a `Map<key, Mutex>` (a keyed mutex) so unrelated accounts don't block each other. Chapter §7.8 builds the full toolkit.

</details>

**Q43. Global lock vs per-key lock vs lock striping?**

<details>
<summary>Answer</summary>

- **Global lock**: one lock for everything. Simple and correct, but it serialises all users, so throughput collapses under load.
- **Per-key lock**: one lock per resource (user, seat, symbol). Maximum parallelism, but the lock map grows without limit unless you delete idle entries, and operations touching two keys need a fixed **lock order** to avoid deadlock (e.g. always lock the smaller account ID first).
- **Lock striping**: `N` locks, and a key uses `locks[hash(key) % N]`. Memory is bounded and parallelism is good. Two keys can occasionally share a stripe, which is fine. Java's older `ConcurrentHashMap` used segment striping.

For a rate limiter serving thousands of users, per-key or striped locks are the expected answer. In Node, if the check-and-update for a key contains no `await`, you need no lock at all.

</details>

**Q44. Optimistic vs pessimistic locking: when do you use each? (Walmart asks this.)**

<details>
<summary>Answer</summary>

- **Pessimistic**: lock first, then read and modify (`SELECT … FOR UPDATE`, a mutex, a seat hold). Use it when conflicts are **likely** or retries are expensive: hot seats at a show opening, inventory for a flash sale.
- **Optimistic**: read with a `version`, then write with `UPDATE … WHERE id = ? AND version = ?`. If zero rows were updated, someone else won: reload and retry, or fail. Use it when conflicts are **rare** and reads dominate: profile edits, most cart updates.

Trade-offs: pessimistic locking can deadlock and reduces throughput. Optimistic locking wastes work under contention and needs a retry limit.

```ts
class VersionConflict extends Error { override name = 'VersionConflict'; }

type Row = { qty: number; version: number };
const store = new Map<string, Row>([['sku1', { qty: 5, version: 1 }]]);

function compareAndSet(id: string, expectedVersion: number, qty: number): void {
  const row = store.get(id)!;
  if (row.version !== expectedVersion) throw new VersionConflict(`expected v${expectedVersion}, found v${row.version}`);
  store.set(id, { qty, version: row.version + 1 });
}

const a = { ...store.get('sku1')! };
const b = { ...store.get('sku1')! };
compareAndSet('sku1', a.version, a.qty - 2);
console.log(`A saved, stock ${store.get('sku1')!.qty}`);
try {
  compareAndSet('sku1', b.version, b.qty - 1);
} catch (e) {
  if (e instanceof VersionConflict) {
    console.log(`B conflict: ${e.message}`);
    const fresh = store.get('sku1')!;
    compareAndSet('sku1', fresh.version, fresh.qty - 1);
    console.log(`B retried, stock ${store.get('sku1')!.qty}`);
  }
}
```

```text
A saved, stock 3
B conflict: expected v1, found v2
B retried, stock 2
```

</details>

**Q45. What is idempotency, and how do you implement it for a payment API?**

<details>
<summary>Answer</summary>

An operation is idempotent if doing it several times has the same effect as doing it once. Networks retry, users double-click, and webhooks are delivered at least once, so any operation that moves money must be idempotent.

Implementation:

1. The client sends an `Idempotency-Key` (a UUID per logical operation).
2. The server stores `key → {status, requestHash, response}`.
3. On a repeat, if the request is complete, return the stored response. If it is still in progress, return 409 or make the caller wait. If the same key comes with a different payload, reject it.
4. Store the key **atomically** with the side effect (same DB transaction, or a unique constraint), and give keys a TTL.

In TypeScript, store the *in-flight promise*, so concurrent duplicates share one execution:

```ts
class IdempotencyStore<T> {
  private results = new Map<string, Promise<T>>();
  run(key: string, op: () => Promise<T>): Promise<T> {
    const existing = this.results.get(key);
    if (existing) return existing;
    const p = op();
    this.results.set(key, p);
    p.catch(() => this.results.delete(key)); // failures may be retried
    return p;
  }
}

let charges = 0;
const store = new IdempotencyStore<string>();
const charge = async (): Promise<string> => {
  charges++;
  await Promise.resolve();
  return `txn-${charges}`;
};

const [r1, r2] = await Promise.all([store.run('key-42', charge), store.run('key-42', charge)]);
const r3 = await store.run('key-42', charge);
console.log(`${r1} ${r2} ${r3}; charged ${charges} time(s)`);
```

```text
txn-1 txn-1 txn-1; charged 1 time(s)
```

</details>

**Q46. How do you prevent double booking of a seat across multiple servers?**

<details>
<summary>Answer</summary>

In-process locks don't help once there are several servers. Options, from simplest:

1. **DB unique constraint** on `(show_id, seat_id)` in a bookings or holds table. The second insert fails. Simple and robust.
2. **Conditional update**: `UPDATE seats SET state='HELD', held_by=?, hold_expires=? WHERE show_id=? AND seat_id=? AND (state='AVAILABLE' OR hold_expires < now())`. Check that the affected row count is 1.
3. **Pessimistic row lock** (`SELECT … FOR UPDATE`) inside a transaction for multi-seat holds. Lock the seats in sorted order to avoid deadlocks.
4. **Distributed lock with TTL** (e.g. Redis `SET key val NX PX 300000`) for the hold phase, plus a fencing token or a DB check at confirmation.

Flow: hold with expiry → pay → confirm only if the hold is still yours → release on failure or timeout. Payment callbacks must be idempotent (Q45).

</details>

**Q47. How would Java and Go solve the same concurrency problems you solve in TypeScript?**

<details>
<summary>Answer</summary>

| Need | TypeScript / Node | Java | Go |
|---|---|---|---|
| Mutual exclusion | Promise-chain mutex; no `await` inside the critical section | `synchronized`, `ReentrantLock` | `sync.Mutex` |
| Read-heavy lock | Usually unnecessary | `ReentrantReadWriteLock`, `StampedLock` | `sync.RWMutex` |
| Thread-safe map | A plain `Map` (single thread) | `ConcurrentHashMap` (`compute`, `merge`) | `sync.Map` or a map + mutex |
| Atomic counter | A plain number | `AtomicInteger`, `LongAdder` | `sync/atomic` |
| Limit concurrency | Semaphore / p-limit style pool | `Semaphore`, `ThreadPoolExecutor` | Buffered channel as a semaphore, worker goroutines |
| Producer–consumer | Async queue + awaiting consumers | `BlockingQueue` | Channels |
| One-time init | Module scope / a memoised promise | Double-checked locking, holder idiom | `sync.Once` |
| Scheduled tasks | `setTimeout`/`setInterval` + a heap | `ScheduledExecutorService` | `time.Ticker`, `time.AfterFunc` |
| CPU parallelism | `worker_threads` | Threads / `ForkJoinPool` | Goroutines |

The interview line: "In Node, my critical sections are the synchronous code between awaits. Where I must await inside one, I use an async mutex keyed by resource. In Java I would use a `ConcurrentHashMap.compute` or a per-key `ReentrantLock`, in Go a mutex or a channel."

</details>

**Q48. What is a deadlock, and how do you avoid one in LLD code?**

<details>
<summary>Answer</summary>

A deadlock happens when two or more tasks each hold a lock the other needs, and none can proceed. It requires four conditions together (Coffman): mutual exclusion, hold-and-wait, no preemption, and circular wait.

Avoidance in practice:

- **Global lock ordering**: always acquire locks in a fixed order (sorted account IDs for transfers, sorted seat IDs for multi-seat holds). This breaks circular wait.
- **Timeouts** on lock acquisition (`tryLock(timeout)`), then back off and retry.
- **Smaller critical sections**, and never call external services while holding a lock.
- **One lock per operation** where possible, or a single coarser lock for rare multi-key operations.

Async mutexes in Node can deadlock too: `a` awaits lock X then Y while `b` awaits Y then X. The same rules apply.

</details>

**Q49. How do you design a thread-safe (or concurrency-safe) LRU cache?**

<details>
<summary>Answer</summary>

The structure is a hash map plus a doubly linked list. Both `get` and `put` **mutate** the list (a `get` moves the node to the front), so a plain read-write lock doesn't help: every operation is a write.

Options:

1. **One lock around each operation.** Simple and correct. Contention is the cost.
2. **Sharding**: N independent LRU caches, key → shard by hash. Each shard has its own lock. Eviction becomes approximate (per shard), which is usually acceptable.
3. **Lazy recency updates**: record accesses in a buffer and apply them in batches (the approach used by Caffeine in Java).

In Node, `get` and `put` are synchronous, so they are already atomic and need no lock. Locking matters only if a loader `await`s on a miss. Then use **single-flight**: store the in-flight promise per key so concurrent misses trigger one load (the cache-stampede fix).

</details>

**Q50. At-most-once, at-least-once, exactly-once: what does your pub-sub guarantee?**

<details>
<summary>Answer</summary>

- **At-most-once**: commit the offset before processing. A crash loses messages. It is fast.
- **At-least-once**: process, then commit the offset. A crash causes redelivery, so consumers must be **idempotent** (dedup by message ID). This is the usual default.
- **Exactly-once** end to end is practically *effectively-once*: at-least-once delivery plus idempotent or transactional processing (commit the offset and the side effect together, or dedup on write).

In an LLD answer, say which one you chose, where the offset lives (per consumer group, per partition), how you retry (backoff, max attempts) and where poison messages go (a dead-letter queue). Ordering is guaranteed only within a partition, so choose a partition key such as `orderId` to keep related events in order.

</details>

## TypeScript-specific design (5)

**Q51. How do you get compile-time exhaustiveness for state machines in TypeScript?**

<details>
<summary>Answer</summary>

Model the states as a **discriminated union** (or a string-literal union) and `switch` on the discriminant with a `never` check in the `default` branch. Adding a new state then produces compile errors at every `switch` that hasn't handled it.

```ts
type OrderState =
  | { kind: 'PLACED' }
  | { kind: 'SHIPPED'; trackingId: string }
  | { kind: 'CANCELLED'; reason: string };

function assertNever(x: never): never {
  throw new Error(`Unhandled: ${JSON.stringify(x)}`);
}

function describe(s: OrderState): string {
  switch (s.kind) {
    case 'PLACED': return 'placed';
    case 'SHIPPED': return `shipped ${s.trackingId}`;
    case 'CANCELLED': return `cancelled: ${s.reason}`;
    default: return assertNever(s);
  }
}
```

For the *transitions*, keep a table such as `const allowed: Record<Kind, Kind[]>` and validate every move against it.

</details>

**Q52. How would you stop someone from passing a `userId` where an `orderId` is expected?**

<details>
<summary>Answer</summary>

TypeScript is structurally typed, so two `string` aliases are interchangeable. Use **branded types**:

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };
type UserId = Brand<string, 'UserId'>;
type OrderId = Brand<string, 'OrderId'>;

const asUserId = (s: string): UserId => s as UserId;
const asOrderId = (s: string): OrderId => s as OrderId;

function cancelOrder(id: OrderId): string { return `cancel ${id}`; }

cancelOrder(asOrderId('o-1'));
// @ts-expect-error a UserId is not an OrderId
cancelOrder(asUserId('u-1'));
```

Create brands only at the boundaries (parsing and validation). The brand costs nothing at runtime. Use the same trick for `Paise` vs `Rupees`.

</details>

**Q53. Enums or string-literal unions for domain constants?**

<details>
<summary>Answer</summary>

- **String-literal unions** (`type Side = 'BUY' | 'SELL'`): no runtime code, great narrowing, work nicely with JSON, and support exhaustive checks. Pair them with `as const` arrays when you need to iterate: `const SIDES = ['BUY', 'SELL'] as const; type Side = typeof SIDES[number];`
- **String enums** (`enum Side { Buy = 'BUY' }`): a runtime object you can iterate, and familiar to Java developers. They are nominal-ish: you can't pass the raw string `'BUY'` without a cast. Plain numeric enums have reverse-mapping surprises and accept any number, so avoid them.

Both are defensible in an interview. What matters is being consistent and avoiding numeric enums. Note that `const enum` and enums are not supported by some "strip-only" TypeScript runtimes, which is one more reason many codebases prefer unions.

</details>

**Q54. How do you handle errors in TypeScript LLD code: exceptions or Result types?**

<details>
<summary>Answer</summary>

- **Exceptions** (custom classes such as `class SeatUnavailableError extends DomainError`) for broken invariants and failures the caller cannot handle locally. Set `name`, keep a machine-readable `code`, and catch them at the boundary (controller or CLI).
- **Result types** (`{ ok: true, value } | { ok: false, error }`) for *expected* outcomes that the caller must handle: validation failures, "insufficient balance", "no driver available". The type system forces the caller to deal with them.

In a machine-coding round, a small hierarchy of domain errors plus `instanceof` checks in `main()` is the quickest clean approach. Don't throw plain strings, and never swallow errors silently.

In TypeScript, `catch (e)` gives `unknown` under strict settings, so narrow it before reading `.message`.

</details>

**Q55. How do you make a TypeScript class truly encapsulated? `private` vs `#private`, `readonly` vs `Object.freeze`.**

<details>
<summary>Answer</summary>

- `private` is a **compile-time** check only. At runtime, `(obj as any).balance` still works and the field appears in `JSON.stringify`.
- `#balance` is a **runtime-enforced** ECMAScript private field. It is inaccessible outside the class body and is not serialised.
- `readonly` is compile-time and **shallow**: a `readonly items: string[]` field can still be `push`ed. Use `readonly string[]` / `ReadonlyArray` for the contents too.
- `Object.freeze` is a runtime, shallow freeze.

In an interview, either `private` or `#` is fine. Mention the difference once, and above all return copies or readonly views of internal collections.

</details>

## Extensibility, testing & API design (6)

**Q56. How do you make your machine-coding solution testable?**

<details>
<summary>Answer</summary>

- **Constructor-inject** every collaborator: repositories, strategies, a `Clock`, an `IdGenerator`, notifiers.
- **Inject time and randomness.** `Date.now()` and `Math.random()` inside business logic make tests flaky. Pass a `Clock` you can move forward, and a seeded or sequential ID generator (§7.6).
- **Keep I/O at the edges.** Services return values and throw domain errors; only `main()` prints.
- **Use in-memory repositories** behind interfaces, which the problem asks for anyway.
- **Write tests as scenarios**: "two users hold the same seat → the second gets `SeatUnavailable`".

Even without a test framework, a `main()` that runs asserted scenarios counts as tests for Atlassian- and CRED-style rounds.

</details>

**Q57. What tests would you write for a rate limiter?**

<details>
<summary>Answer</summary>

Use a fake clock and cover these cases:

1. Allows up to N requests in a window, rejects request N+1.
2. Allows again once the window rolls over. Check the exact boundary: `t = windowStart + size` belongs to the new window.
3. Keys are independent (user A's traffic doesn't affect user B).
4. Sliding window: no burst of 2N across a boundary.
5. Token bucket: refill rate, capacity cap, fractional refills.
6. Config per resource: different strategies for different resources.
7. Concurrency: N parallel calls for the same key → exactly `limit` allowed.
8. Invalid config (limit ≤ 0) → error at construction.

</details>

**Q58. How do you design the public API of an in-memory library (e.g. a cache or rate limiter) so it can evolve?**

<details>
<summary>Answer</summary>

- **Small surface**: `get`, `set`, `delete`, `stats`. Hide internals.
- **Options objects** instead of positional parameters (`new Cache({ capacity, ttlMs, policy })`), so adding an option doesn't break callers.
- **Interfaces for extension points** (`EvictionPolicy`, `Clock`, `Serializer`) plus sensible defaults.
- **Explicit error semantics**: return `undefined` for a miss, throw on misuse.
- **Generics** for type safety (`Cache<K, V>`).
- **Events or hooks** (`onEvict`) instead of subclassing.
- **Versioning**: deprecate before you remove, and never change the meaning of an existing option.

</details>

**Q59. How would you structure the code of a 90-minute machine-coding solution?**

<details>
<summary>Answer</summary>

```text
src/
  models/        entities and value objects (Show, Seat, Booking, Money)
  enums/         or union types (SeatState, PaymentStatus)
  strategies/    PricingStrategy, SeatAllocation...
  repositories/  interfaces + InMemory implementations
  services/      BookingService, PaymentService (orchestration)
  errors/        DomainError subclasses
  main.ts        wiring + demo scenarios (the "driver")
```

Keep the dependency direction one-way: `main → services → (repositories, strategies) → models`. Models import nothing from services. In a single-file online editor, keep the same ordering and section comments. This is the "MVC-style layering" that Groww and Flipkart write-ups mention.

</details>

**Q60. How do you add a REST API on top of your in-memory design later?**

<details>
<summary>Answer</summary>

If the services already hold all the business logic, a controller layer is thin. For example, in NestJS:

1. Controllers parse and validate DTOs (class-validator or zod), call the service, and map domain errors to HTTP codes (`SeatUnavailableError` → 409, `NotFound` → 404, validation → 400).
2. Replace in-memory repositories with DB-backed ones that implement the same interfaces. The services don't change, which is the DIP payoff.
3. Add idempotency keys to POSTs that create money movement or bookings.
4. Use cursor pagination for list endpoints, and version the API (`/v1`).

If your services print to the console or read input themselves, this step is painful. That is why I/O stays at the edges.

</details>

**Q61. What makes code "extensible" in the interviewer's eyes? Give a checklist.**

<details>
<summary>Answer</summary>

- A new *type* (vehicle, split, channel, order type) = one new class + one registration line.
- A new *rule* (pricing, fine, ranking) = a new Strategy, chosen by configuration.
- A new *reaction* to an event (notify, audit, analytics) = a new subscriber.
- Changing *storage* = a new repository implementation.
- Nothing is hard-coded that the spec called "configurable" (board size, limits, rates).
- No `if (type === ...)` chains spread across services.
- Names that match the domain, so a newcomer can find where to change things.

Test this by **demonstrating an extension live** during the walkthrough. It is the most persuasive two minutes of the round.

</details>

**Q62. The interviewer asks, "How would you scale this?" in an LLD round. What do they want?**

<details>
<summary>Answer</summary>

They want you to connect your LLD to HLD concerns *without* rewriting it:

- **State** moves from in-memory maps to a DB or cache; repositories make that a swap.
- **Concurrency** moves from in-process locks to DB constraints, conditional updates, or distributed locks with TTLs.
- **Events** move from an in-process bus to Kafka / SQS, with at-least-once delivery and idempotent consumers.
- **Partitioning**: shard by a natural key (userId, symbol, showId). The order matching engine stays single-threaded *per symbol*.
- **Read paths**: caches, precomputed leaderboards (e.g. Redis sorted sets), pagination.

Keep this to 2–3 minutes, unless it's a combined LLD+HLD round (as reported at Upstox and Paytm), where it may be the main event.

</details>
