## Pattern picker: situation → pattern

| When the requirement says… | Reach for | Seen in |
|---|---|---|
| "different ways to calculate / allocate / split / rank" | **Strategy** | Parking pricing, Splitwise, rate limiter, doctor ranking, cab matching |
| "behaves differently depending on its status"; legal transitions | **State** | Vending machine, ATM, elevator, order, seat, traffic light |
| "when X happens, notify / update others" | **Observer / pub-sub** | Notifications, price alerts, news feed, inventory sync |
| "create the right kind of object from input" | **Factory** (simple / method) | Vehicles, notifiers, split types, data sources |
| "families of matching objects" | **Abstract Factory** | UI themes, payment-provider kits |
| "object with many optional parts, validated at the end" | **Builder** | Orders, HTTP requests, search queries |
| "exactly one per process" (use sparingly) | **Singleton** / one instance injected | Logger, config, registry |
| "copy a pre-configured object" | **Prototype** | Game boards, templates, document snapshots |
| "tree of parts and wholes, treat uniformly" | **Composite** | File system, org chart, menu with add-ons, ACL folders |
| "add behaviour around an object, stackable" | **Decorator** | Pricing add-ons, logging/caching repositories, stream wrappers |
| "control access: lazy, cache, auth, limit" | **Proxy** | Rate-limited client, circuit breaker, lazy image |
| "incompatible third-party interface" | **Adapter** | Payment gateways, banks, file converters |
| "simple front door to a complex subsystem" | **Facade** | `BookingFacade`, SDK entry points |
| "two dimensions vary independently" | **Bridge** | Notification type × channel, shape × renderer |
| "many tiny shared objects" | **Flyweight** | Chess piece types, text glyphs, seat templates |
| "undo / redo / queue / log actions" | **Command** | Text editor, TODO (PhonePe feedback), admin actions |
| "restore an earlier snapshot" | **Memento** | Editor, game save, transaction rollback |
| "pass along until someone handles it" | **Chain of Responsibility** | Logger levels, ATM notes, middleware, discount pipeline |
| "fixed skeleton, variable steps" | **Template Method** | Game turn loop, report export, payment flow |
| "central coordinator for many peers" | **Mediator** | Chat room, elevator controller, auction house |
| "walk a collection without exposing it" | **Iterator** | Playlist, paginated results, tree traversal |
| "new operations over a stable object structure" | **Visitor** | File-system reports, AST evaluation |
| "no-op default instead of null checks" | **Null Object** | `NoDiscount`, `SilentLogger` |
| "filter by combinable criteria" | **Specification** | Search, coupon rules, file find |
| "swap storage" | **Repository** | Every machine-coding round |
| "limit concurrent work / retries / failures" | **Semaphore, Retry+backoff, Circuit breaker** | Job scheduler, payouts, gateways |

## SOLID one-liners

| Principle | One-liner | Smell when violated | Fix |
|---|---|---|---|
| **S**RP | One reason to change. | A class name with "Manager" and 20 methods across domains | Extract cohesive collaborators |
| **O**CP | Extend by adding code, not by editing it. | `switch(type)` copied across files | Strategy / polymorphism + registry |
| **L**SP | Subtypes must honour the parent's promises. | An override that throws "not supported" | Split interfaces; prefer composition |
| **I**SP | No client should depend on methods it doesn't use. | Empty stub methods in implementations | Role interfaces |
| **D**IP | Policy depends on abstractions; details implement them. | `new MySqlRepo()` inside a service | Constructor injection of interfaces |

Companion principles: **DRY** (one source of truth for each rule), **KISS**, **YAGNI** (seams yes, speculative features no), **composition over inheritance**, **Law of Demeter** (no `a.b().c().d()`), **tell, don't ask**, **high cohesion / low coupling**.

| Arrow | Mermaid | Meaning | Code hint |
|---|---|---|---|
| Inheritance | `A <\|-- B` | B is an A | `class B extends A` |
| Realisation | `I <\|.. C` | C implements I | `class C implements I` |
| Composition | `W *-- P` | W owns P; P dies with W | W creates P in its constructor |
| Aggregation | `W o-- P` | W groups P; P lives on | P passed into W |
| Association | `A --> B` | A holds a reference to B | a field of type B |
| Dependency | `A ..> B` | A uses B temporarily | a parameter or local variable of type B |

Multiplicity labels go in quotes: `ParkingLot "1" *-- "many" ParkingFloor`.

## Concurrency toolkit in TypeScript

| Problem | Tool | One-line rule |
|---|---|---|
| Check-then-act across `await` | Keep it synchronous, or use a **Mutex** | No `await` between the check and the write |
| Unrelated keys block each other | **Keyed mutex** / lock striping | Lock the resource, not the world |
| Too many concurrent calls | **Semaphore** / pool | Bound concurrency per dependency |
| Duplicate requests / retries | **Idempotency key** + stored promise | Same key → same result |
| Lost updates | **Optimistic locking** (version CAS) | Update only if the version matches; retry a bounded number of times |
| Hot contended resource | **Pessimistic hold with TTL** | Hold → pay → confirm; expire holds automatically |
| Cache stampede | **Single-flight** | One in-flight load per key |
| Ordered processing per entity | **Per-key serial queue** | Partition by key |
| Flaky dependency | **Timeout + retry with jitter + circuit breaker** | Retry only idempotent operations |
| Multi-lock operations | **Lock ordering** | Always lock in sorted key order |
| Across servers | **DB constraints / conditional updates / distributed lock + fencing** | In-process locks don't cross processes |

A compact keyed mutex and semaphore you can type from memory:

```ts
class KeyedMutex {
  private tails = new Map<string, Promise<void>>();
  async run<T>(key: string, fn: () => Promise<T>): Promise<T> {
    const prev = this.tails.get(key) ?? Promise.resolve();
    let release!: () => void;
    const mine = new Promise<void>(r => (release = r));
    const tail = prev.then(() => mine);
    this.tails.set(key, tail);
    await prev;
    try {
      return await fn();
    } finally {
      release();
      if (this.tails.get(key) === tail) this.tails.delete(key);
    }
  }
}

class Semaphore {
  private waiters: Array<() => void> = [];
  constructor(private permits: number) {}
  async acquire(): Promise<void> {
    if (this.permits > 0) { this.permits--; return; }
    await new Promise<void>(r => this.waiters.push(r));
  }
  release(): void {
    const next = this.waiters.shift();
    if (next) next(); else this.permits++;
  }
}

const log: string[] = [];
const locks = new KeyedMutex();
const step = (key: string, label: string) =>
  locks.run(key, async () => {
    log.push(`${label} start`);
    await Promise.resolve();
    log.push(`${label} end`);
  });

await Promise.all([step('seat-1', 'A'), step('seat-1', 'B'), step('seat-2', 'C')]);
console.log(log.join(' | '));

const sem = new Semaphore(2);
let active = 0;
let peak = 0;
const job = async (): Promise<void> => {
  await sem.acquire();
  active++;
  peak = Math.max(peak, active);
  await new Promise(r => setTimeout(r, 5));
  active--;
  sem.release();
};
await Promise.all([job(), job(), job(), job(), job()]);
console.log(`peak concurrency ${peak}`);
```

```text
A start | C start | A end | C end | B start | B end
peak concurrency 2
```

`A` and `B` share `seat-1`, so `B` waits for `A`. `C` uses a different key and runs alongside `A`.

## Machine-coding checklist

**Before coding (first 10–15%)**

- [ ] Restate the problem; list the functional requirements in priority order (P0/P1/P2).
- [ ] Ask about scale, concurrency, persistence (in-memory?), input format (CLI? method calls?), and what "done" means.
- [ ] Agree on the out-of-scope items out loud.
- [ ] List the entities, their relationships, the variation points (Strategy/State) and the events (Observer).
- [ ] Sketch the classes and the main sequence in 5 minutes.

**While coding**

- [ ] Models → repositories (interface + in-memory) → strategies → services → `main` demo.
- [ ] Constructor injection; no `new` for collaborators inside services.
- [ ] Inject `Clock` and `IdGenerator`; integer paise for money.
- [ ] Validate inputs; custom domain errors; no silent failures.
- [ ] Enums / unions for states; a transition table for state machines.
- [ ] Get the P0 flow running end to end *early*, then add features.
- [ ] Commit to names from the domain; no `data`, `info`, `manager2`.
- [ ] Talk while you code: say what you're doing and why.

**Before the walkthrough**

- [ ] The demo covers the happy path + 2–3 edge cases + one error case.
- [ ] Concurrency: identify the shared state and say how it's protected.
- [ ] Prepare the "add a new X" story (one class + one registration).
- [ ] Remove dead code and debug prints; make sure it runs from a clean start.
- [ ] Know your complexity for the hot operations.

**Walkthrough script**

1. The requirements you covered, and what you skipped deliberately.
2. The class diagram / module layout (1 minute).
3. The core flow through the code (2 minutes).
4. Patterns and why (1 minute).
5. Demo run.
6. Extensions, concurrency, and scaling.

## Time-boxing plans

| Phase | 60-min round (Atlassian-style) | 90-min round (Flipkart / PhonePe / Groww) | 120–150-min round (Meesho / CRED / Groww SDE-3) |
|---|---|---|---|
| Clarify requirements | 5 min | 10 min | 15 min |
| Design (entities, interfaces, sketch) | 5 min | 10 min | 15 min |
| Core models + repositories | 10 min | 15 min | 20 min |
| Services + P0 flow running | 15 min | 25 min | 30 min |
| P1 features + validation | 5 min | 15 min | 25 min |
| Tests / demo scenarios | 10 min (tests are graded) | 5 min | 15 min (run the provided tests early and often) |
| Buffer, cleanup, walkthrough prep | 10 min | 10 min | 10–30 min |

Rules: if P0 is not running by the halfway mark, **cut scope**, not quality. A clean, running subset beats a complete but buggy system (Blind advice; Flipkart pass-with-incomplete-code anecdote).

## Vocabulary to use when presenting

- "The **axis of change** here is the pricing rule, so I put it behind a Strategy."
- "This class owns the **invariant** that a seat can't be double-booked."
- "The service is an **orchestrator**; the domain logic lives in the entities and strategies."
- "Repositories are the **seam** for persistence; swapping to Postgres doesn't touch the services."
- "This is the **composition root**: the only place that names concrete classes."
- "The critical section is **synchronous**, so it's atomic on the event loop; across instances I'd use a conditional update."
- "Holds have a **TTL**, so abandoned checkouts release their seats automatically."
- "The payment call is **idempotent** via an idempotency key, so client retries are safe."
- "Delivery is **at-least-once**, so consumers dedup by event ID."
- "I've kept this **open for extension**: a new split type is one class and one registry line. Let me show you."
- "I chose a **heap** over sorting because top-K is read on every tick: O(log n) updates versus O(n log n) sorts."
- "That's a **trade-off**: per-key locks give throughput at the cost of lock-map memory, so I evict idle keys."
- "I've **descoped** X to keep the core flow correct; here's where it would plug in."
