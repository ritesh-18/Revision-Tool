## Chapter recap

Six problems, one chapter, fifteen steps each. The pattern that appears in every single one is *inject what changes*: a clock for time, an ID generator for identity, a dice for randomness, a strategy for the part that will vary, a repository for storage. That discipline is what makes code testable, and testable code is what interviewers in machine-coding rounds are checking for when they ask "how would you test this?".

The design choices worth remembering:

- **Strategy** earns its place when more than one algorithm for the same operation is in scope — now or in a foreseeable follow-up. Parking lot spot selection and pricing are good examples because Microsoft and Goldman Sachs both asked for several of them. A single hardcoded algorithm is not a smell; it just means you don't need the pattern yet.
- **State** earns its place when the same method means different things in different states. The vending machine's `insert` is an error in `Idle` but a payment in `ProductSelected`. A `switch(state)` in every method is the tell that you need the pattern. Game status in Tic-Tac-Toe, by contrast, only gates whether moves are allowed — a single guard does that, and State would over-engineer it.
- **Command** earns its place when you need undo, audit trails, or queued execution. PhonePe asked for it by name. For any problem with mutable state and a "what if the user changes their mind?" requirement, reach for Command before a direct mutation.
- **Chain of Responsibility** earns its place when a sequence of independent steps can be reordered, inserted, or removed without changing the surrounding code. The logging pipeline is the canonical case. A vending machine that simply needs "do A, then B, then C" doesn't need it.
- **Observer** earns its place when several unrelated consumers need to react to the same event. The Snake & Ladder narrator and the stats collector are both observers. If there's only one consumer and it won't change, a direct method call is clearer.
- **Specification** earns its place when filter criteria are composable, user-configurable, or testable in isolation. A task manager with several filter options is the right scope. A single `isActive()` check on a user object doesn't need a spec class.

Concurrency appears in every problem at SDE-2 level, even in "basic" ones. The five recurring answers are:
1. **Check-then-act across an `await`?** Reserve synchronously first, confirm or roll back after.
2. **Multi-instance?** Move the claim into the database as an atomic conditional update.
3. **Async callbacks on a cancelled session?** Give every session an ID and check it before acting.
4. **Lost update?** Optimistic locking with a version counter; fail with a conflict, not a silent overwrite.
5. **Overlapping async operations on the same resource?** Single-flight or per-key mutex.

## Practice exercises

1. **Parking Lot:** add a `WaitingList` so that when a vehicle is rejected for a full lot, it is queued and notified (via Observer) when a compatible spot is freed.
2. **Tic-Tac-Toe:** extend the bot from section 9.2 to use minimax for 3×3. Memoize the game states. Measure how many unique states there are.
3. **Snake & Ladder:** add a `FreezeEffect` that skips the next player's turn (from the special-cells extension), then write a `ScriptedDice`-based test that proves a frozen player does skip exactly one turn.
4. **Vending Machine:** replace the greedy `makeChange` with the DP version. Write tests that show a case the greedy fails and the DP solves.
5. **Logging Framework:** add a `SamplingHandler` that passes only 1 in N records to the rest of the chain, where N is configurable per module, and verify it with the in-memory sink.
6. **TODO Manager:** add a `SetPriorityCommand` (LOW / MEDIUM / HIGH), a `PrioritySpec`, and a `MacroCommand`-based "bulk deprioritise all DONE tasks".
7. **Cross-problem:** pick any two problems from this chapter and combine them. For example: a parking lot that logs every `park` and `unpark` event to your logging framework, with the events queryable by time range and vehicle type.
