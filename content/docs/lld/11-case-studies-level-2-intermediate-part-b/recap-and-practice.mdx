## Chapter recap

Six problems, one through-line: **patterns are tools, not decoration**.

- **Notification System**: Observer decouples producers from channels; Strategy + Adapter hides vendor quirks; retry and dedup are policy objects, not hardcoded loops.
- **Food Ordering**: The order state machine enforces legal transitions; Strategy gives you free substitution of pricing and partner-assignment rules; Observer keeps the restaurant dashboard updated without coupling the order service to it.
- **Cab Booking**: The same Strategy + State Machine recipe, with the additional twist that fare is locked at request time so a surge change mid-trip doesn't surprise the rider. Concurrency is the exam question — the driver-assignment guard runs before any `await`.
- **Chess**: Polymorphism means `Game` never asks "what kind of piece is this?". Sliding logic is written once. Check detection works by simulation and revert.
- **Custom HashMap**: Separate chaining, load-factor resize, and `[Symbol.iterator]` are all O(1) amortised. Lock striping scales the concurrent variant without a global bottleneck.
- **Payment Gateway**: All money in integer paise. Idempotency and per-key locking prevent double-execution and double-spend. The double-entry ledger is an always-consistent audit trail.

**Three cross-cutting rules** that earned marks in every problem above:

1. **Inject the clock and ID generator.** Hardcoded `Date.now()` and `Math.random()` make demos non-deterministic and tests slow.
2. **Record failure, don't throw it.** One broken channel (or one failed transaction) must not abort the whole operation.
3. **Name your error.** `InsufficientFundsError`, `PermanentSendError`, `InvalidMoveError` tell a grader you understand the domain.

## Practice exercises

1. **Notification**: Extend the notification system to support **quiet hours** (no non-OTP SMS between 10 pm and 7 am IST). Add a `DeliveryRule` chain-of-responsibility that runs before the sender.

2. **Food Ordering**: Add a `SCHEDULED` order type where the customer picks a delivery slot. The order stays `PLACED` until 30 minutes before the slot, then auto-transitions to `ACCEPTED` if the restaurant is open.

3. **Cab Booking**: Implement the ride-sharing variant (Flipkart): a `RideOffer` has `availableSeats`; a `RideSelectionStrategy` picks the most-vacant ride within 2 km. Booking decrements seats atomically.

4. **Chess**: Add castling. Track `hasMoved` per piece. Validate the three conditions (unmoved king and rook, clear path, king not in check on any square it crosses). Undo must revert both pieces.

5. **Custom HashMap**: Implement `LinkedHashMap<K, V>` that iterates in insertion order. Add a doubly-linked list that threads through all entries; `set` appends; `delete` unlinks.

6. **Payment Gateway**: Add **partial refund** support. `refund(txId, amountPaise, idempotencyKey)` where `amountPaise <= original.amountPaise`. Track cumulative refunded amount; block over-refund.

7. **Cross-problem**: The notification system and the payment gateway both use a `KeyedMutex`. Extract it to a shared module and verify the same implementation works correctly in both contexts.
