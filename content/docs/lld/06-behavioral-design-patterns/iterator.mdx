## Intent

Give sequential access to the elements of a collection **without exposing how it is stored**. The collection might be an array, a tree, a price ladder computed on the fly, or a paginated API.

## Problem

- The UI needs to walk a **price ladder** (100.00, 100.05, 100.10, ...) without building a huge array.
- A reconciliation job must process **all trades** from an API that returns 100 at a time with a cursor, and callers shouldn't have to write pagination loops.
- You want `for...of`, the spread operator, and destructuring to work on your own classes.

In JavaScript, Iterator is built into the language: anything with a `[Symbol.iterator]()` method is **iterable**, and **generators** (`function*`) are the easiest way to write iterators.

## TypeScript implementation

**1. A hand-written iterator** so you can see the protocol: `next()` returns `{ value, done }`.

```ts
class PriceLadder implements Iterable<number> {
  constructor(private readonly from: number, private readonly to: number, private readonly tick: number) {}

  [Symbol.iterator](): Iterator<number> {
    // Work in paise (integers) to avoid floating-point drift.
    let current = Math.round(this.from * 100);
    const end = Math.round(this.to * 100);
    const step = Math.round(this.tick * 100);
    return {
      next: (): IteratorResult<number> => {
        if (current > end) return { done: true, value: undefined };
        const value = current / 100;
        current += step;
        return { done: false, value };
      },
    };
  }
}

const ladder = new PriceLadder(100, 101, 0.25);
console.log(`ladder: ${[...ladder].join(', ')}`);

// Each for...of gets a fresh iterator, so the ladder can be walked many times.
let count = 0;
for (const p of ladder) if (p > 100.3) count++;
console.log(`levels above 100.3: ${count}`);
```

**2. Generators** make iterators much shorter. They are also **lazy**: values are produced only when someone asks for them, which makes infinite sequences safe.

```ts
function* orderIds(prefix: string): Generator<string> {
  let n = 1;
  while (true) yield `${prefix}-${n++}`; // infinite but lazy
}

function* take<T>(source: Iterable<T>, n: number): Generator<T> {
  if (n <= 0) return;
  for (const item of source) {
    yield item;
    if (--n === 0) return;
  }
}

function* filter<T>(source: Iterable<T>, pred: (x: T) => boolean): Generator<T> {
  for (const item of source) if (pred(item)) yield item;
}

console.log(`ids: ${[...take(orderIds('ORD'), 3)].join(', ')}`);

// A tree walked depth-first with yield* (delegation to a nested generator).
interface Category {
  name: string;
  children: Category[];
}

function* walk(node: Category, depth = 0): Generator<string> {
  yield `${'  '.repeat(depth)}${node.name}`;
  for (const child of node.children) yield* walk(child, depth + 1);
}

const segments: Category = {
  name: 'Markets',
  children: [
    { name: 'Equity', children: [{ name: 'NSE', children: [] }, { name: 'BSE', children: [] }] },
    { name: 'Derivatives', children: [{ name: 'F&O', children: [] }] },
  ],
};
for (const line of walk(segments)) console.log(line);

const bigTrades = filter([120, 5000, 75, 9800], (v) => v >= 1000);
console.log(`big trades: ${[...bigTrades].join(', ')}`);
```

```text
ladder: 100, 100.25, 100.5, 100.75, 101
levels above 100.3: 3
ids: ORD-1, ORD-2, ORD-3
Markets
  Equity
    NSE
    BSE
  Derivatives
    F&O
big trades: 5000, 9800
```

**3. Async iterator over a paginated API.** This is the most useful form in backend work. Callers write a simple `for await` and never see cursors.

```ts
interface Page<T> {
  items: T[];
  nextCursor: string | null;
}

const ALL_TRADES = Array.from({ length: 7 }, (_, i) => `T${i + 1}`);
let apiCalls = 0;

// Fake HTTP API: returns `limit` items starting at the cursor.
async function fetchTrades(cursor: string | null, limit: number): Promise<Page<string>> {
  apiCalls++;
  await new Promise<void>((resolve) => setTimeout(resolve, 5));
  const start = cursor ? Number(cursor) : 0;
  const end = start + limit;
  return { items: ALL_TRADES.slice(start, end), nextCursor: end < ALL_TRADES.length ? String(end) : null };
}

async function* paginate<T>(fetchPage: (cursor: string | null) => Promise<Page<T>>): AsyncGenerator<T> {
  let cursor: string | null = null;
  do {
    const page: Page<T> = await fetchPage(cursor);
    console.log(`  fetched page: ${page.items.length} item(s)`);
    yield* page.items;
    cursor = page.nextCursor;
  } while (cursor !== null);
}

// Early exit: `break` stops the generator, so no extra pages are fetched.
const firstTwo: string[] = [];
for await (const t of paginate((c) => fetchTrades(c, 3))) {
  firstTwo.push(t);
  if (firstTwo.length === 2) break;
}
console.log(`first two: ${firstTwo.join(', ')} (api calls: ${apiCalls})`);

apiCalls = 0;
const all: string[] = [];
for await (const t of paginate((c) => fetchTrades(c, 3))) all.push(t);
console.log(`all: ${all.join(', ')} (api calls: ${apiCalls})`);
```

```text
  fetched page: 3 item(s)
first two: T1, T2 (api calls: 1)
  fetched page: 3 item(s)
  fetched page: 3 item(s)
  fetched page: 1 item(s)
all: T1, T2, T3, T4, T5, T6, T7 (api calls: 3)
```

## When to use / when NOT to use

**Use it when**
- A collection's internal structure (tree, graph, ring buffer, remote pages) should be hidden from callers.
- The data is large, infinite, or remote and you want **lazy** evaluation.
- You want your domain classes to work with `for...of`, spread, and `Array.from`.

**Don't use it when**
- You already have an array and just need `map`/`filter`. Don't wrap it.
- Callers need random access or the length up front. An iterator only goes forward.

## Pitfalls

- **Iterator vs iterable.** A generator object is iterable only **once**. After it's exhausted, a second `for...of` yields nothing. Make your *class* iterable (return a fresh iterator each time), as `PriceLadder` does.
- **Mutating the collection while iterating** gives surprising results. Snapshot the collection or document the behavior.
- **Resource cleanup.** If an async generator holds a DB cursor, put cleanup in `try/finally`. It runs on `break` too.
- **Hidden N+1.** A lazy iterator that makes a network call per item can be very slow. Fetch in pages.

## Related patterns

- **Iterator + Composite:** walking a tree (`yield*` above).
- **Iterator vs Observer:** an iterator is *pull*-based (the consumer asks for the next item). An observable is *push*-based (the producer sends items). RxJS sits on the push side, and async iterators on the pull side.
- **Factory Method:** `[Symbol.iterator]()` is itself a factory method for iterators.

## Where it shows up in LLD interview problems

- **Paginated order history / trade book** APIs.
- **Custom collections:** LRU cache iteration, playlist shuffle iterator, file system tree.
- **Social feed:** infinite scroll with cursors.
- **Snake & ladder / board games:** iterating players in turn order (a circular iterator).

*How to say it:* "I'll expose trade history as an `AsyncIterable<Trade>`. Callers write `for await`, pagination stays inside the generator, and a `break` stops fetching."

## Quick check

1. What is the difference between an iterable and an iterator?
2. Why is `orderIds()` safe even though it contains `while (true)`?
3. What happens to pending pages when you `break` out of a `for await` over an async generator?

<details>
<summary>Answer</summary>

1. An iterable has `[Symbol.iterator]()`, which *creates* an iterator. An iterator has `next()` and holds the current position. A class that's iterable can be walked many times, while a single iterator is used up after one pass.
2. Generators are lazy. Each `yield` pauses the loop until the consumer asks for the next value, and `take` stops asking after 3.
3. The loop calls the generator's `return()`, which ends it (running any `finally` block). No further pages are fetched.

</details>
