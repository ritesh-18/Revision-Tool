## Intent

Turn a request into an **object**. Once the request is an object, you can store it, queue it, log it, retry it, and undo it.

## Problem

A trading terminal lets a user place, modify, and cancel orders, and it offers **undo/redo** while orders are still in the "draft basket". It also supports **AMO (After Market Orders)**: requests are collected at night and executed when the market opens. A "place basket" button must place 5 orders as one unit and undo them as one unit.

If the UI calls `orderBook.place()` directly, there is nothing to undo, nothing to queue, and nothing to replay. You need each action to be a thing you can hold on to.

The roles are:

- **Command:** the request object (`PlaceOrderCommand`).
- **Receiver:** the object that does the real work (`OrderBook`).
- **Invoker:** triggers commands and keeps the history (`CommandManager`, a queue, a button).
- **Client:** creates commands and wires them to receivers.

## TypeScript implementation

```ts
interface Order {
  id: string;
  symbol: string;
  qty: number;
  price: number;
}

// Receiver
class OrderBook {
  private orders = new Map<string, Order>();

  place(order: Order): void {
    if (this.orders.has(order.id)) throw new Error(`duplicate order ${order.id}`);
    this.orders.set(order.id, { ...order });
  }

  cancel(id: string): Order {
    const order = this.orders.get(id);
    if (!order) throw new Error(`order ${id} not found`);
    this.orders.delete(id);
    return order;
  }

  /** Returns the previous quantity so the caller can undo. */
  modifyQty(id: string, qty: number): number {
    const order = this.orders.get(id);
    if (!order) throw new Error(`order ${id} not found`);
    const prev = order.qty;
    order.qty = qty;
    return prev;
  }

  summary(): string {
    const list = [...this.orders.values()].sort((a, b) => a.id.localeCompare(b.id));
    return list.length ? list.map((o) => `${o.id} ${o.symbol} x${o.qty}@${o.price}`).join(', ') : '(empty)';
  }
}

interface Command {
  readonly label: string;
  execute(): void;
  undo(): void;
}

class PlaceOrderCommand implements Command {
  readonly label: string;
  constructor(private readonly book: OrderBook, private readonly order: Order) {
    this.label = `Place ${order.id}`;
  }
  execute(): void {
    this.book.place(this.order);
  }
  undo(): void {
    this.book.cancel(this.order.id);
  }
}

class ModifyQtyCommand implements Command {
  readonly label: string;
  private prevQty: number | undefined;
  constructor(private readonly book: OrderBook, private readonly id: string, private readonly qty: number) {
    this.label = `Modify ${id} -> ${qty}`;
  }
  execute(): void {
    this.prevQty = this.book.modifyQty(this.id, this.qty); // remember what we need to undo
  }
  undo(): void {
    if (this.prevQty === undefined) throw new Error('cannot undo a command that never ran');
    this.book.modifyQty(this.id, this.prevQty);
  }
}

class CancelOrderCommand implements Command {
  readonly label: string;
  private removed: Order | undefined;
  constructor(private readonly book: OrderBook, private readonly id: string) {
    this.label = `Cancel ${id}`;
  }
  execute(): void {
    this.removed = this.book.cancel(this.id);
  }
  undo(): void {
    if (!this.removed) throw new Error('cannot undo a command that never ran');
    this.book.place(this.removed);
  }
}

// Composite of commands: runs in order, undoes in reverse order.
class MacroCommand implements Command {
  constructor(readonly label: string, private readonly commands: Command[]) {}
  execute(): void {
    for (const c of this.commands) c.execute();
  }
  undo(): void {
    for (const c of [...this.commands].reverse()) c.undo();
  }
}

// Invoker with undo/redo history
class CommandManager {
  private undoStack: Command[] = [];
  private redoStack: Command[] = [];

  run(cmd: Command): void {
    cmd.execute();
    this.undoStack.push(cmd);
    this.redoStack.length = 0; // a new action invalidates the redo history
    console.log(`do   ${cmd.label}`);
  }

  undo(): void {
    const cmd = this.undoStack.pop();
    if (!cmd) return console.log('nothing to undo');
    cmd.undo();
    this.redoStack.push(cmd);
    console.log(`undo ${cmd.label}`);
  }

  redo(): void {
    const cmd = this.redoStack.pop();
    if (!cmd) return console.log('nothing to redo');
    cmd.execute();
    this.undoStack.push(cmd);
    console.log(`redo ${cmd.label}`);
  }
}

const book = new OrderBook();
const manager = new CommandManager();
const show = () => console.log(`     book: ${book.summary()}`);

manager.run(new PlaceOrderCommand(book, { id: 'O1', symbol: 'INFY', qty: 10, price: 1500 }));
show();
manager.run(new ModifyQtyCommand(book, 'O1', 25));
show();
manager.undo();
show();
manager.redo();
show();
manager.run(
  new MacroCommand('Basket[O2,O3]', [
    new PlaceOrderCommand(book, { id: 'O2', symbol: 'TCS', qty: 5, price: 3900 }),
    new PlaceOrderCommand(book, { id: 'O3', symbol: 'HDFCBANK', qty: 20, price: 1650 }),
  ]),
);
show();
manager.undo();
show();
manager.run(new CancelOrderCommand(book, 'O1'));
show();
manager.redo();
manager.undo();
show();
```

Because commands are objects, **queueing** comes for free. Here is an AMO queue that holds requests overnight and runs them when the market opens:

```ts
class CommandQueue {
  private pending: Command[] = [];

  enqueue(cmd: Command): void {
    this.pending.push(cmd);
    console.log(`queued: ${cmd.label}`);
  }

  flush(): void {
    console.log(`market open -> flushing ${this.pending.length}`);
    let cmd: Command | undefined;
    while ((cmd = this.pending.shift())) {
      try {
        cmd.execute();
        console.log(`executed: ${cmd.label}`);
      } catch (err) {
        console.log(`failed: ${cmd.label} (${(err as Error).message})`);
      }
    }
  }
}

const amoBook = new OrderBook();
const amo = new CommandQueue();
amo.enqueue(new PlaceOrderCommand(amoBook, { id: 'A1', symbol: 'SBIN', qty: 100, price: 820 }));
amo.enqueue(new PlaceOrderCommand(amoBook, { id: 'A2', symbol: 'ITC', qty: 50, price: 465 }));
amo.enqueue(new CancelOrderCommand(amoBook, 'A9'));
amo.flush();
console.log(`amo book: ${amoBook.summary()}`);
```

Note that `nothing to redo` after the cancel is correct: running a new command clears the redo stack. Every editor behaves this way.

## When to use / when NOT to use

**Use it when**
- You need **undo/redo**, **queues**, **scheduling**, **retries**, **audit logs**, or **macros**.
- The thing that *triggers* an action (a button, a keyboard shortcut, a cron job) should be decoupled from the thing that *performs* it.

**Don't use it when**
- An action is fire-and-forget with none of the needs above. Wrapping `save()` in `SaveCommand` for no reason is ceremony.

## Pitfalls

- **Undo that isn't really undo.** Real-world actions (an order sent to the exchange, an SMS delivered) can't be reversed. Undo then means a *compensating* action ("cancel order"), and that can fail. Only offer undo where it is honest.
- **Missing state for undo.** Capture what you need (`prevQty`) *during* `execute()`, not in the constructor. The state may change between creating the command and running it.
- **Forgetting to clear redo** after a new command leads to confusing history.
- **Macro partial failure.** If the 2nd of 5 commands fails, undo the ones that already ran. Real systems need an explicit rollback policy for this (compare with the Saga pattern).
- **Unbounded history.** Cap the undo stack size.

## Related patterns

- **Command vs Strategy.** A strategy is *an algorithm you plug in* and is usually called many times. A command is *one specific request* with its arguments bound, and it can be stored and undone.
- **Command + Memento.** When computing an inverse operation is hard, the command stores a memento (snapshot) and restores it on undo.
- **MacroCommand** is the **Composite** pattern applied to commands.
- **Command vs Chain of Responsibility.** Command packages a request. The chain decides *who* handles it. They combine well: a queued command passes through a validation chain.
- Redux actions, CQRS commands, and job-queue payloads (BullMQ) are the "serializable command" cousins.

## Where it shows up in LLD interview problems

- **Text editor / Google Docs:** undo/redo.
- **Trading app:** order placement, AMO queue, basket orders.
- **Smart home / remote control:** buttons mapped to commands, "party mode" macro.
- **Job scheduler / task queue.**
- **Restaurant ordering:** a waiter (invoker) passes order tickets (commands) to the kitchen (receiver).

*How to say it:* "Every user action becomes a `Command` with `execute` and `undo`. The `CommandManager` keeps two stacks. A new command clears redo. Basket orders are a `MacroCommand` that undoes in reverse order."

## Quick check

1. Why does `ModifyQtyCommand` record `prevQty` in `execute()` and not in the constructor?
2. Why must a macro undo its children in reverse order?
3. What does "undo" mean for an order that is already at the exchange?

<details>
<summary>Answer</summary>

1. The quantity may change between creating the command and running it, for example because of other commands or a redo. Undo must restore the value that existed right before *this* execution.
2. Later commands may depend on the effects of earlier ones, so effects must be unwound last-in, first-out.
3. It becomes a compensating action (a cancel or modify request), which can itself fail. Undo is not a guaranteed rollback.

</details>
