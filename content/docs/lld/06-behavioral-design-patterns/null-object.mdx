---
title: "6.11 Null Object"
---

## Intent

Replace "no object" (`null`/`undefined`) with an object that implements the expected interface and **does nothing** (or returns a neutral value). Callers no longer need `if (x != null)` checks everywhere.

## Problem

Some users have registered a phone number for SMS alerts and some haven't. Some orders have a promo code and most don't. The code ends up full of checks like these:

```ts
// ❌ null checks spread everywhere
if (user.notifier) user.notifier.notify(msg);
const discount = promo ? promo.apply(amount) : amount;
if (logger) logger.debug('...');
```

Miss one check and production crashes with `Cannot read properties of undefined`.

## TypeScript implementation

```ts
interface Notifier {
  notify(message: string): void;
}

class SmsNotifier implements Notifier {
  constructor(private readonly phone: string) {}
  notify(message: string): void {
    console.log(`  SMS to ${this.phone}: ${message}`);
  }
}

// Null Object: same interface, deliberately does nothing.
const NULL_NOTIFIER: Notifier = Object.freeze({ notify: () => {} });

interface Promo {
  readonly code: string;
  apply(amount: number): number;
}

const NO_PROMO: Promo = Object.freeze({ code: 'NONE', apply: (amount: number) => amount });

const promos = new Map<string, Promo>([['FLAT50', { code: 'FLAT50', apply: (a: number) => Math.max(0, a - 50) }]]);

interface User {
  name: string;
  phone?: string;
}

// The null check happens exactly once, at the boundary.
const notifierFor = (u: User): Notifier => (u.phone ? new SmsNotifier(u.phone) : NULL_NOTIFIER);
const promoFor = (code?: string): Promo => (code ? promos.get(code) : undefined) ?? NO_PROMO;

function placeOrder(user: User, amount: number, promoCode?: string): void {
  const promo = promoFor(promoCode);
  const payable = promo.apply(amount); // no null checks here...
  console.log(`order for ${user.name}: ${amount} -> ${payable} (promo ${promo.code})`);
  notifierFor(user).notify(`order placed, pay ${payable}`); // ...or here
}

placeOrder({ name: 'ritesh', phone: '98XXXXXX01' }, 500, 'FLAT50');
placeOrder({ name: 'guest' }, 500);
placeOrder({ name: 'asha', phone: '98XXXXXX02' }, 500, 'BOGUS');
```

```text
order for ritesh: 500 -> 450 (promo FLAT50)
  SMS to 98XXXXXX01: order placed, pay 450
order for guest: 500 -> 500 (promo NONE)
order for asha: 500 -> 500 (promo NONE)
  SMS to 98XXXXXX02: order placed, pay 500
```

## When to use / when NOT to use

**Use it when**
- "Absent" has a sensible **neutral behavior**: no notification, zero discount, a no-op logger, a guest user with no permissions.
- The same null check is repeated in many places.

**Don't use it when**
- Absence is an **error** the caller must handle (a missing account, a missing price). Hiding it makes bugs silent. Use `undefined` plus a type check, or throw.
- The caller needs to know that nothing happened (for example, to show "SMS not configured"). Then expose `isNull` or use an explicit union.

## Pitfalls

- **Silently swallowing problems.** A null logger in production means no logs when you need them.
- **Null objects with state** should be immutable singletons (`Object.freeze`).
- **TypeScript already helps.** With `strictNullChecks`, `?.` and `??`, many null checks are cheap. Use Null Object where it simplifies *behavior*, not just syntax.

## Related patterns

- A **Strategy** or **State** can have a null implementation (`ZeroBrokerage` from 6.1 is effectively a null strategy).
- Null objects are usually **Singletons**.
- **Special Case** (Fowler) is the generalization: `UnknownCustomer`, `MissingPrice`, with specific behavior.

## Where it shows up in LLD interview problems

- **Logger** with a `NoOpLogger` in tests.
- **Parking lot:** `NoDiscount` pricing, or an `EmptySpot` sentinel.
- **Notification service:** users who opted out.
- **Game development:** a `NullPlayer` or `NoWeapon`.

*How to say it:* "Users without a phone get a `NullNotifier`. The decision is made once in a factory, and the order flow calls `notify()` without null checks."

## Quick check

1. When is a Null Object a bad idea?
2. Where should the "real or null?" decision be made?

<details>
<summary>Answer</summary>

1. When absence is an error or the caller must react to it. A silent no-op hides bugs.
2. Once, at the boundary: a factory, the DI configuration, or a lookup function with a `?? NULL_X` fallback.

</details>
