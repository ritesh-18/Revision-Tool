## Chapter recap

- Behavioral patterns are about **responsibility and communication**: who decides, who acts, who gets told.
- **Strategy** swaps algorithms. **State** swaps behavior as the lifecycle moves. They share a structure but have different intent.
- **Observer** fans out events. Return unsubscribe functions, iterate over a copy, and isolate listener errors.
- **Command** turns actions into objects, which makes undo/redo, queues, macros, and audit logs possible. Capture undo data during `execute()`.
- **Chain of Responsibility** builds pipelines of checks. Express/Koa/NestJS middleware is the everyday form.
- **Template Method** fixes a skeleton with inheritance. Prefer passing step functions when variations multiply.
- **Iterator** is built into JS: `Symbol.iterator`, generators, and async generators for pagination.
- **Mediator** centralizes many-to-many rules. Watch for god objects.
- **Memento** snapshots state opaquely. `WeakMap` + `structuredClone` is a clean TypeScript approach.
- **Visitor** adds operations across stable types through double dispatch. In TypeScript, a discriminated union with `assertNever` is often the better tool.
- **Null Object** removes repeated null checks when "absent" has a neutral behavior. Never use it to hide errors.
- **Interpreter** turns a tiny grammar into an evaluable tree. Parse once and never use `eval`.

## Interview questions on this chapter

**1. Strategy and State have almost the same class diagram. How do you explain the difference?**

<details>
<summary>Answer</summary>

The difference is **who changes the delegate and why**. With Strategy, the client selects an algorithm (often once, from config), and the strategies are independent of each other. With State, the delegate represents the object's current lifecycle position, and the state objects themselves trigger transitions to other states when events happen. A good one-liner: "Strategy is *how* to do something, State is *what I'm allowed to do now*."

</details>

**2. Design price alerts for a trading app. Which pattern and what are the key details?**

<details>
<summary>Answer</summary>

Use **Observer** inside the service: a market-data feed emits typed `tick` events, and `PriceAlert` objects subscribe and filter by symbol and condition. Key details:

- `on()` returns an unsubscribe function, and one-shot alerts unsubscribe after firing.
- Iterate over a copy of the listeners and wrap each one in try/catch.
- For millions of alerts, don't loop over every alert per tick. Index alerts by symbol, and keep sorted thresholds per symbol (for example, a heap for "above" and one for "below").
- Delivery (push/SMS) goes to a queue (**Pub/Sub**) so slow channels don't block the feed.

</details>

**3. How would you implement undo/redo in a text editor? Command or Memento?**

<details>
<summary>Answer</summary>

Both are valid. **Command** stores operations with their inverses (`InsertText` ↔ `DeleteText`). It is memory-efficient and works well for granular edits. **Memento** stores snapshots. It is simpler when inverses are hard (complex formatting) and the state is small. A common hybrid is commands that capture a memento before executing. The mechanics are the same either way: an undo stack and a redo stack, a new action clears redo, history size is capped, and consecutive keystrokes can be merged into one command.

</details>

**4. What is double dispatch, and why does Visitor need it?**

<details>
<summary>Answer</summary>

Single dispatch picks a method based on one runtime type (the receiver). Visitor needs the operation to depend on **both** the visitor and the element's concrete type. `element.accept(visitor)` dispatches on the element, and inside, `visitor.visitEquity(this)` dispatches on the visitor while passing the statically known concrete type. TypeScript's method overloading is compile-time only, so this trick (or a discriminated union) is needed.

</details>

**5. When would you choose a discriminated union over the Visitor pattern in TypeScript?**

<details>
<summary>Answer</summary>

When the elements are **plain data** (DTOs, JSON, DB rows) rather than rich classes. A `kind` tag plus an exhaustive `switch` with `assertNever` gives compile-time errors for unhandled kinds, keeps operations outside the data, and needs no `accept` boilerplate. Choose classic Visitor when elements are classes with encapsulated state, or when you're walking a heterogeneous object tree that is already class-based.

</details>

**6. Design the pre-trade validation for an order. How do you keep it extensible?**

<details>
<summary>Answer</summary>

Use a **Chain of Responsibility** of validators: KYC → market hours → instrument tradable → margin → risk limits. Each validator either returns a rejection (with the validator name and a reason) or passes the request on. The chain is assembled in one place (or per segment: equity vs F&O). Cheap, local checks go before expensive ones such as a margin service call. New regulations mean a new validator class, and each validator is unit-tested alone. Log which validator rejected the order for support and audit.

</details>

**7. How is Observer different from Pub/Sub, and when would you move from one to the other?**

<details>
<summary>Answer</summary>

In Observer, subscribers register directly with the subject, in-process and usually synchronously. In Pub/Sub, a broker/topic sits between publishers and subscribers, so neither knows the other, and delivery is usually async, durable, and cross-service (Kafka, Redis Streams, SNS/SQS). Move to Pub/Sub when consumers live in other services, need retries and durability, or when a slow consumer must not block the producer.

</details>

**8. Model an order's lifecycle. How do you prevent illegal transitions, and how do you persist it?**

<details>
<summary>Answer</summary>

Use **State**: a base state whose actions throw by default, plus concrete states that override only the legal actions. Alternatively, use a typed transition table. Persist the **status string** (not the object) and rebuild the state object with a factory on load. Protect against concurrent events (two fills at once) with optimistic locking (a version column) or by processing events for an order sequentially (a partitioned queue keyed by order ID). Record every transition in an audit table.

</details>

**9. What problems does Mediator solve, and how do you stop it from becoming a god object?**

<details>
<summary>Answer</summary>

It removes N×N references between peers and centralizes interaction rules (chat room, auction, ATC). To keep it manageable, split it by responsibility (a bid validator, a notifier, a settlement service), let the mediator delegate to strategies for its rules, and communicate outward through events instead of calling everything directly.

</details>

**10. How do you write a custom iterable in TypeScript, and what's the gotcha with generators?**

<details>
<summary>Answer</summary>

Implement `[Symbol.iterator](): Iterator<T>`, most easily as `*[Symbol.iterator]() { ... yield ... }`. The gotcha is that a **generator object** is a one-shot iterator. After it's consumed, iterating again yields nothing. If callers need to iterate more than once, make the class iterable (each call creates a new generator) rather than passing the generator object around.

</details>

**11. How would you expose a paginated external API so callers don't deal with cursors?**

<details>
<summary>Answer</summary>

Wrap it in an **async generator**: loop, fetch a page with the current cursor, `yield*` its items, and stop when `nextCursor` is null. Callers use `for await (const trade of allTrades())`. `break` stops fetching automatically (put cleanup in `finally`). Add backoff and retries inside the generator, and optionally a page-size parameter.

</details>

**12. Template Method vs Strategy: which would you use for a report generator with multiple output formats and data sources?**

<details>
<summary>Answer</summary>

Formats and sources vary **independently** (PDF/CSV/Excel × DB/API/file). With Template Method you'd need a subclass for each combination. Use **Strategy** (composition) instead: `ReportGenerator` takes a `DataSource` and a `Formatter`. A thin template method can still fix the order `fetch → compute → format → deliver`, with each step delegating to an injected strategy.

</details>

**13. When is Null Object a bad idea?**

<details>
<summary>Answer</summary>

When absence is a real problem that should be handled or surfaced: a missing account, a missing price, a failed configuration. A silent no-op turns a bug into missing behavior that nobody notices. It's also a bad fit when callers need to know that nothing happened. Then use an explicit `undefined` with TypeScript narrowing, or a `Result` type.

</details>

**14. How would you let users define alert conditions like `price > 100 AND volume > 1000` safely?**

<details>
<summary>Answer</summary>

Use **Interpreter**: tokenize, parse with a small recursive-descent parser (encoding `AND` precedence over `OR`) into an expression tree (`Compare`, `And`, `Or`), validate field names against a whitelist, limit length and depth, store the tree (or the source), and call `evaluate(tick)` on updates. Never use `eval`/`new Function`. For larger rule sets, use a standard format such as JSON Logic or CEL, and index rules by field and symbol.

</details>

## Practice exercises

1. **Parking fee strategies.** Implement `FeeStrategy` with `HourlyFee` (₹20/hour, first 30 minutes free), `FlatDailyFee`, and `WeekendFee`. Add a registry keyed by `VehicleType × DayType`. Bonus: combine strategies with a Decorator (`EvChargingSurcharge`).
2. **Stop-loss engine.** Build on the `TypedEmitter`: a `StopLossOrder` subscribes to ticks, triggers a market sell when price ≤ trigger, and unsubscribes. Add a `marketStatus` event so triggers are ignored while the market is closed.
3. **Basket orders with partial failure.** Extend `MacroCommand` so that if the 3rd of 5 orders fails, the first two are undone and the error is reported. Write a demo that proves the rollback.
4. **Elevator states.** Model `Idle`, `MovingUp`, `MovingDown`, `DoorsOpen`, and `Maintenance` as state classes. Requests are queued, and "open door" is ignored while moving. Then rewrite the transitions as a typed table and compare the two versions.
5. **ATM dispenser chain.** Build a Chain of Responsibility for ₹2000/₹500/₹200/₹100 notes with limited stock per handler. Reject amounts that can't be dispensed *before* dispensing anything.
6. **Middleware with error handling.** Extend `compose` with (a) a guard that throws if `next()` is called twice and (b) an error-handling middleware at the top that turns thrown errors into `status = 500`.
7. **Statement importer.** Use Template Method to import bank statements from CSV and fixed-width text. Then refactor it to pass `parse`/`transform` as functions and write down which version you prefer and why.
8. **Order history iterator.** Write `async function* orderHistory(userId)` over a fake paginated API that fails on page 2 the first time it is requested (keep it deterministic). Add retry with backoff inside the generator.
9. **Group chat mediator.** Implement a `ChatRoom` with join/leave, direct messages, mute, and an admin who can kick users. Users must never hold references to each other.
10. **Drawing app undo.** Use Memento for a canvas with shapes (nested arrays). Prove that a shallow copy breaks undo, then fix it with `structuredClone`. Cap history at 20 entries.
11. **Margin visitor.** Add a `MarginVisitor` (equity 100%, futures 12% of contract value, option buy = premium) to the Visitor example, then do the same with the discriminated-union version. Add a new `Bond` instrument to both and note where the compiler complains.
12. **Rule engine upgrade.** Extend the interpreter with `NOT`, field-to-field comparisons (`price > vwap`), and error messages that include the token position.
