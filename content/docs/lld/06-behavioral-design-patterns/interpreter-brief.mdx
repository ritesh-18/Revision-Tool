## Intent

Define a small **language** (grammar), represent sentences in that language as a tree of objects, and evaluate the tree. Each grammar rule becomes a class.

## Problem

Users want custom alerts written as rules, for example `price > 100 AND volume > 1000 OR price < 50`. Hard-coding each combination is impossible. You need to **parse** the rule once, store it, and **evaluate** it on every tick.

## Structure

        -left Expr

    }
    class Parser {

    }
    Expr <|.. Compare
    Expr <|.. And
    Expr <|.. Or
    And o-- Expr
    Or o-- Expr
    Parser ..> Expr : builds`} />

`Compare` is a **terminal** expression (a leaf). `And` and `Or` are **non-terminal** expressions, built as a Composite.

## TypeScript implementation

Grammar (`AND` binds tighter than `OR`):

```text
or      := and ( "OR" and )*
and     := primary ( "AND" primary )*
primary := "(" or ")" | FIELD OP NUMBER
```

```ts
type Ctx = Partial<Record<string, number>>;

interface Expr {
  evaluate(ctx: Ctx): boolean;
  toString(): string;
}

const OPS = ['>=', '<=', '==', '!=', '>', '<'] as const;
type Op = (typeof OPS)[number];
const isOp = (s: string): s is Op => (OPS as readonly string[]).includes(s);

class Compare implements Expr {
  constructor(private readonly field: string, private readonly op: Op, private readonly value: number) {}
  evaluate(ctx: Ctx): boolean {
    const v = ctx[this.field];
    if (v === undefined) throw new Error(`unknown field ${this.field}`);
    switch (this.op) {
      case '>': return v > this.value;
      case '<': return v < this.value;
      case '>=': return v >= this.value;
      case '<=': return v <= this.value;
      case '==': return v === this.value;
      case '!=': return v !== this.value;
    }
  }
  toString(): string {
    return `${this.field} ${this.op} ${this.value}`;
  }
}

class And implements Expr {
  constructor(private readonly left: Expr, private readonly right: Expr) {}
  evaluate(ctx: Ctx): boolean {
    return this.left.evaluate(ctx) && this.right.evaluate(ctx);
  }
  toString(): string {
    return `(${this.left} AND ${this.right})`;
  }
}

class Or implements Expr {
  constructor(private readonly left: Expr, private readonly right: Expr) {}
  evaluate(ctx: Ctx): boolean {
    return this.left.evaluate(ctx) || this.right.evaluate(ctx);
  }
  toString(): string {
    return `(${this.left} OR ${this.right})`;
  }
}

// A tiny recursive-descent parser that turns text into the Expr tree.
class Parser {
  private pos = 0;
  private constructor(private readonly tokens: string[]) {}

  static parse(src: string): Expr {
    const tokens = [...(src.match(/>=|<=|==|!=|[<>()]|[A-Za-z_]+|\d+(?:\.\d+)?/g) ?? [])];
    const p = new Parser(tokens);
    const expr = p.parseOr();
    if (p.pos < tokens.length) throw new Error(`unexpected token ${tokens[p.pos]}`);
    return expr;
  }

  private peek(): string | undefined {
    return this.tokens[this.pos];
  }

  private take(): string {
    const t: string | undefined = this.tokens[this.pos++];
    if (t === undefined) throw new Error('unexpected end of input');
    return t;
  }

  private parseOr(): Expr {
    let left = this.parseAnd();
    while (this.peek() === 'OR') {
      this.pos++;
      left = new Or(left, this.parseAnd());
    }
    return left;
  }

  private parseAnd(): Expr {
    let left = this.parsePrimary();
    while (this.peek() === 'AND') {
      this.pos++;
      left = new And(left, this.parsePrimary());
    }
    return left;
  }

  private parsePrimary(): Expr {
    if (this.peek() === '(') {
      this.pos++;
      const inner = this.parseOr();
      if (this.take() !== ')') throw new Error('expected )');
      return inner;
    }
    const field = this.take();
    if (!/^[A-Za-z_]+$/.test(field)) throw new Error(`expected field but got ${field}`);
    const op = this.take();
    if (!isOp(op)) throw new Error(`expected operator but got ${op}`);
    const value = Number(this.take());
    if (Number.isNaN(value)) throw new Error('expected number');
    return new Compare(field, op, value);
  }
}

const rule = Parser.parse('price > 100 AND volume > 1000 OR price < 50');
console.log(`parsed: ${rule}`);

const ticks: Ctx[] = [
  { price: 120, volume: 1500 },
  { price: 120, volume: 500 },
  { price: 40, volume: 10 },
];
for (const t of ticks) console.log(`price=${t.price} volume=${t.volume} -> ${rule.evaluate(t)}`);

const grouped = Parser.parse('price > 100 AND (volume > 1000 OR oi >= 5000)');
console.log(`parsed: ${grouped} -> ${grouped.evaluate({ price: 150, volume: 10, oi: 7000 })}`);

for (const bad of ['price >', 'price ~ 5', 'price > 1 volume']) {
  try {
    Parser.parse(bad);
  } catch (err) {
    console.log(`"${bad}": ${(err as Error).message}`);
  }
}
try {
  rule.evaluate({ volume: 5 });
} catch (err) {
  console.log(`evaluate: ${(err as Error).message}`);
}
```

```text
parsed: ((price > 100 AND volume > 1000) OR price < 50)
price=120 volume=1500 -> true
price=120 volume=500 -> false
price=40 volume=10 -> true
parsed: (price > 100 AND (volume > 1000 OR oi >= 5000)) -> true
"price >": unexpected end of input
"price ~ 5": expected operator but got 5
"price > 1 volume": unexpected token volume
evaluate: unknown field price
```

Note the second error: the tokenizer drops the unknown `~` character, so the parser sees `5` where it expected an operator. A production tokenizer should report unknown characters instead of skipping them.

## When to use / when NOT to use

**Use it when**
- You have a **small, stable grammar** that business users or config files need: alert rules, feature-flag conditions, pricing rules, search filters.

**Don't use it when**
- The grammar is large or evolving. Use a parser generator (PEG.js / Peggy, Chevrotain) or an existing format (JSON Logic, CEL).
- You're tempted to use `eval` / `new Function`. **Never** evaluate user-supplied strings as code.

## Pitfalls

- **Precedence bugs:** `AND` must bind tighter than `OR`. Encode that in the grammar, as above.
- **Performance:** parse once and evaluate many times. Don't re-parse on every tick.
- **Security / abuse:** limit expression length and depth.
- **Error messages matter.** Users write these rules, so report positions and expected tokens.

## Related patterns

- **Composite:** the expression tree *is* a composite.
- **Visitor:** add operations (pretty-print, optimize, convert to SQL) without touching node classes.
- **Iterator:** walk the tokens.
- **Strategy:** each operator is a tiny strategy.

## Where it shows up in LLD interview problems

- **Stock alert rules**, **rule engines** (discount eligibility, fraud rules).
- **Calculator / expression evaluator** (a classic machine-coding round).
- **Search query filters** (`status:open AND amount>1000`).
- **Feature flags** with targeting conditions.

*How to say it:* "Alert conditions are a tiny grammar. I parse them once into an expression tree of `Compare`, `And`, and `Or` nodes and call `evaluate(tick)` on each price update. No `eval`, and the tree can be stored as JSON."

## Quick check

1. Which classes are terminal and which are non-terminal expressions here?
2. Why must you never implement this with `eval`?

<details>
<summary>Answer</summary>

1. `Compare` is terminal (a leaf). `And` and `Or` are non-terminal: they contain child expressions.
2. `eval` runs arbitrary code from the user's string, which is a remote-code-execution vulnerability. It is also hard to validate and gives poor error messages.

</details>
