## Intent

Add new operations to a family of classes **without modifying those classes**, by moving each operation into a separate "visitor" object. It uses **double dispatch**: the element tells the visitor its concrete type.

## Problem

Your portfolio holds different instruments: **equity**, **futures**, and **options**. You keep adding operations over them: STT (securities transaction tax), brokerage, margin requirement, a human-readable description, a CSV export... Putting `calculateStt()`, `calculateBrokerage()`, `toCsv()` and so on into every instrument class bloats the domain classes and mixes tax logic with instrument logic. Each new report means touching every class.

The instrument *types* are stable (they don't change often), while the *operations* keep growing. That is exactly the situation Visitor is built for.

## TypeScript implementation (classic, with generic return type)

> The rates below are **simplified and illustrative only**, not current regulatory values.

```ts
interface InstrumentVisitor<R> {
  visitEquity(e: Equity): R;
  visitFuture(f: Future): R;
  visitOption(o: OptionContract): R;
}

interface Instrument {
  accept<R>(visitor: InstrumentVisitor<R>): R;
}

class Equity implements Instrument {
  constructor(readonly symbol: string, readonly qty: number, readonly price: number) {}
  accept<R>(v: InstrumentVisitor<R>): R {
    return v.visitEquity(this); // double dispatch: "I am an Equity"
  }
}

class Future implements Instrument {
  constructor(readonly symbol: string, readonly lots: number, readonly lotSize: number, readonly price: number) {}
  accept<R>(v: InstrumentVisitor<R>): R {
    return v.visitFuture(this);
  }
}

class OptionContract implements Instrument {
  constructor(
    readonly symbol: string,
    readonly strike: number,
    readonly type: 'CE' | 'PE',
    readonly lots: number,
    readonly lotSize: number,
    readonly premium: number,
  ) {}
  accept<R>(v: InstrumentVisitor<R>): R {
    return v.visitOption(this);
  }
}

// Operation 1: tax
class SttVisitor implements InstrumentVisitor<number> {
  visitEquity(e: Equity): number {
    return e.qty * e.price * 0.001;
  }
  visitFuture(f: Future): number {
    return f.lots * f.lotSize * f.price * 0.0002;
  }
  visitOption(o: OptionContract): number {
    return o.lots * o.lotSize * o.premium * 0.001;
  }
}

// Operation 2: brokerage
class BrokerageVisitor implements InstrumentVisitor<number> {
  visitEquity(): number {
    return 0; // free delivery
  }
  visitFuture(): number {
    return 20;
  }
  visitOption(): number {
    return 20;
  }
}

// Operation 3: a different return type, no changes to the instruments
class DescribeVisitor implements InstrumentVisitor<string> {
  visitEquity(e: Equity): string {
    return `EQ  ${e.symbol} x${e.qty}`;
  }
  visitFuture(f: Future): string {
    return `FUT ${f.symbol} ${f.lots}x${f.lotSize}`;
  }
  visitOption(o: OptionContract): string {
    return `OPT ${o.symbol} ${o.strike}${o.type} ${o.lots}x${o.lotSize}`;
  }
}

const portfolio: Instrument[] = [
  new Equity('INFY', 10, 1500),
  new Future('NIFTY', 2, 75, 24000),
  new OptionContract('NIFTY', 24500, 'CE', 2, 75, 120),
];

const stt = new SttVisitor();
const brokerage = new BrokerageVisitor();
const describe = new DescribeVisitor();

let totalStt = 0;
let totalBrokerage = 0;
for (const item of portfolio) {
  const t = item.accept(stt);
  const b = item.accept(brokerage);
  totalStt += t;
  totalBrokerage += b;
  console.log(`${item.accept(describe).padEnd(24)} | STT ${t.toFixed(2).padStart(7)} | brokerage ${b.toFixed(2)}`);
}
console.log(`TOTAL STT ${totalStt.toFixed(2)}, brokerage ${totalBrokerage.toFixed(2)}`);
```

```text
EQ  INFY x10             | STT   15.00 | brokerage 0.00
FUT NIFTY 2x75           | STT  720.00 | brokerage 20.00
OPT NIFTY 24500CE 2x75   | STT   18.00 | brokerage 20.00
TOTAL STT 753.00, brokerage 40.00
```

## The TypeScript alternative: discriminated union + exhaustive `switch`

In TypeScript, you often don't need Visitor at all. If instruments are **plain data** with a `kind` tag, a `switch` with an exhaustiveness check gives the same two guarantees: operations live outside the data, and adding a new kind causes a compile error everywhere it isn't handled.

```ts
type Instrument =
  | { kind: 'equity'; symbol: string; qty: number; price: number }
  | { kind: 'future'; symbol: string; lots: number; lotSize: number; price: number }
  | { kind: 'option'; symbol: string; strike: number; lots: number; lotSize: number; premium: number };

function assertNever(x: never): never {
  throw new Error(`unhandled instrument: ${JSON.stringify(x)}`);
}

function stt(i: Instrument): number {
  switch (i.kind) {
    case 'equity':
      return i.qty * i.price * 0.001;
    case 'future':
      return i.lots * i.lotSize * i.price * 0.0002;
    case 'option':
      return i.lots * i.lotSize * i.premium * 0.001;
    default:
      return assertNever(i); // compile error here if a new kind is added and not handled
  }
}

// A "visitor object" in functional style: a map of handlers, one per kind.
type Handlers<R> = { [K in Instrument['kind']]: (i: Extract<Instrument, { kind: K }>) => R };

function match<R>(i: Instrument, h: Handlers<R>): R {
  // TS can't correlate i.kind with the handler type by itself, so one small cast is needed.
  return (h[i.kind] as (x: Instrument) => R)(i);
}

const portfolio: Instrument[] = [
  { kind: 'equity', symbol: 'INFY', qty: 10, price: 1500 },
  { kind: 'future', symbol: 'NIFTY', lots: 2, lotSize: 75, price: 24000 },
  { kind: 'option', symbol: 'NIFTY', strike: 24500, lots: 2, lotSize: 75, premium: 120 },
];

const total = portfolio.reduce((sum, i) => sum + stt(i), 0);
console.log(`total STT (union): ${total.toFixed(2)}`);

const labels = portfolio.map((i) =>
  match(i, {
    equity: (e) => `${e.symbol} cash`,
    future: (f) => `${f.symbol} fut`,
    option: (o) => `${o.symbol} ${o.strike} opt`,
  }),
);
console.log(`labels: ${labels.join(' | ')}`);
```

```text
total STT (union): 753.00
labels: INFY cash | NIFTY fut | NIFTY 24500 opt
```

**When to prefer which in TS?**

| Situation | Prefer |
|---|---|
| Instruments are plain data (from JSON, DB rows, API DTOs) | Discriminated union + `switch` |
| Instruments are rich classes with behavior and private state | Classic Visitor |
| Walking a heterogeneous tree (AST, file system, UI tree) with many operations | Visitor (or union + recursive function) |
| New *kinds* are added often, operations are few | Neither. Use polymorphic methods on each class |

The union approach is more idiomatic in modern TypeScript and needs far less code. Knowing the classic Visitor still matters: interviewers ask about double dispatch, and compilers and linters (the TypeScript compiler API, Babel, ESLint rules) use visitors on ASTs.

## When to use / when NOT to use

**Use it when**
- The set of element types is **stable** but the set of operations **keeps growing**.
- Operations need type-specific logic and you want to keep that logic out of the domain classes.

**Don't use it when**
- New element types are added often. Every new type forces a change to *every* visitor.
- There are only one or two operations. Put them on the classes.

## Pitfalls

- **Breaking encapsulation.** Visitors need access to element data, so fields become public (`readonly` helps).
- **The expression problem.** Visitor makes new operations easy and new types hard. Know which way your domain grows.
- **Forgetting `accept` in a new class** gives a compile error only if the class implements `Instrument`. Always declare `implements`.
- **Over-engineering** in TS where a union would do.

## Related patterns

- **Visitor + Composite:** visiting every node of a tree (ASTs, org charts, file systems).
- **Visitor vs Strategy:** a strategy varies *one algorithm*. A visitor varies *an operation across many types*.
- **Visitor vs Iterator:** the iterator decides *how to walk*. The visitor decides *what to do at each node*. They're often used together.
- **Interpreter** trees are commonly evaluated or printed with visitors.

## Where it shows up in LLD interview problems

- **Tax / fee / margin calculation** across instrument or product types.
- **Shopping cart:** compute price, tax, and shipping for books, electronics, and groceries.
- **File system:** size calculator, search, and permission audit over files and folders.
- **Compilers / expression evaluators:** evaluate, pretty-print, and optimize an AST.
- **Insurance / HR systems:** payroll or bonus rules per employee type.

*How to say it:* "Instrument types are stable, while tax and fee reports keep growing, so I'll use Visitor: each instrument has `accept(visitor)`, and every report is a new visitor class. In TypeScript, if instruments are plain DTOs, I'd use a discriminated union with an exhaustive `switch`. It gives the same safety with less code."

## Quick check

1. What is double dispatch, and where does it happen in this code?
2. What change is cheap and what change is expensive with Visitor?
3. Why does `assertNever` give you a compile error when a new `kind` is added?

<details>
<summary>Answer</summary>

1. The operation that runs depends on *two* runtime types: the visitor and the element. The first dispatch is `item.accept(v)`, which picks the element's `accept`. The second is `v.visitEquity(this)`, which picks the visitor's method for that concrete type.
2. A new operation (a new visitor class) is cheap. A new element type is expensive, because every visitor interface and implementation must change.
3. In the `default` branch, TypeScript has narrowed `i` to the cases not yet handled. When every case is handled, that's `never`. A new unhandled kind makes `i` a real type, which can't be passed to a `never` parameter.

</details>
