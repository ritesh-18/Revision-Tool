title: "6.1 Strategy"

## Intent

Define a family of interchangeable algorithms, put each one behind a common interface, and let the caller pick one at runtime. The code that *uses* the algorithm never changes when you add a new one.

## Problem

Your brokerage app charges different fees for different plans:

- **Delivery** trades: zero brokerage.
- **Intraday**: 0.03% of turnover, capped at ₹20 per order.
- **F&O**: flat ₹20 per order.
- Marketing wants a "festive offer" plan next month, and nobody knows what the plan after that will be.

The naive version is a growing `if/else` (or `switch`) inside `OrderService.calculateCharges()`. Every new plan edits a class that is already tested and deployed, which breaks the Open/Closed Principle. The branches also can't be unit-tested in isolation.

The same shape shows up for **payment methods** (UPI / card / net-banking), **parking fee rules** (hourly / flat / weekend), **expense splitting** (equal / exact / percentage), and **ride pricing** (normal / surge).

The **context** (`OrderCharges`) holds a reference to a strategy and delegates the calculation to it. The **client** decides which strategy to plug in.

## TypeScript implementation

```ts
interface BrokerageStrategy {
  readonly name: string;
  calculate(turnover: number): number;
}

class FlatFeeBrokerage implements BrokerageStrategy {
  readonly name = 'flat';
  constructor(private readonly feePerOrder: number) {}
  calculate(): number {
    return this.feePerOrder;
  }
}

class PercentCappedBrokerage implements BrokerageStrategy {
  readonly name = 'percent-capped';
  constructor(private readonly rate: number, private readonly cap: number) {}
  calculate(turnover: number): number {
    return Math.min(turnover * this.rate, this.cap);
  }
}

class ZeroBrokerage implements BrokerageStrategy {
  readonly name = 'zero';
  calculate(): number {
    return 0;
  }
}

// The context: knows *that* a fee must be computed, not *how*.
class OrderCharges {
  constructor(private strategy: BrokerageStrategy) {}

  setStrategy(strategy: BrokerageStrategy): void {
    this.strategy = strategy;
  }

  quote(qty: number, price: number): string {
    const turnover = qty * price;
    const fee = this.strategy.calculate(turnover);
    return `${this.strategy.name.padEnd(15)} turnover=${turnover} fee=${fee.toFixed(2)}`;
  }
}

const charges = new OrderCharges(new FlatFeeBrokerage(20));
console.log(charges.quote(10, 2500));

charges.setStrategy(new PercentCappedBrokerage(0.0003, 20));
console.log(charges.quote(10, 2500));
console.log(charges.quote(80, 2500)); // 0.03% of 2,00,000 = 60, capped at 20

charges.setStrategy(new ZeroBrokerage());
console.log(charges.quote(10, 2500));
```

In real code you rarely call `setStrategy` by hand. A **registry** (a lookup map) picks the strategy from data, so no `if/else` is needed:

```ts
type Plan = 'DELIVERY' | 'INTRADAY' | 'FNO';

// Record<Plan, ...> forces you to handle every plan at compile time.
const planStrategies: Record<Plan, BrokerageStrategy> = {
  DELIVERY: new ZeroBrokerage(),
  INTRADAY: new PercentCappedBrokerage(0.0003, 20),
  FNO: new FlatFeeBrokerage(20),
};

for (const plan of ['DELIVERY', 'INTRADAY', 'FNO'] as const) {
  console.log(`${plan}: ${planStrategies[plan].calculate(40000).toFixed(2)}`);
}

// In TypeScript, a strategy with a single method is often just a function type.
type FeeFn = (turnover: number) => number;
const festiveOffer: FeeFn = (turnover) => Math.min(turnover * 0.0001, 10);
console.log(`festive: ${festiveOffer(40000).toFixed(2)}`);
```

```text
flat            turnover=25000 fee=20.00
percent-capped  turnover=25000 fee=7.50
percent-capped  turnover=200000 fee=20.00
zero            turnover=25000 fee=0.00
DELIVERY: 0.00
INTRADAY: 12.00
FNO: 20.00
festive: 4.00
```

> **Class or function?** Use a plain function type when the strategy is a single method with no configuration or state. Use an interface plus classes when the strategy has several methods (for example `calculate()` and `describe()`), needs constructor-injected dependencies, or must be registered with a DI container such as NestJS providers.

## When to use / when NOT to use

**Use it when**
- You have several ways to do the same job and the choice depends on config, user type, or runtime data.
- A `switch` on a "type" or "mode" keeps growing inside one method.
- You want to unit-test each algorithm on its own.

**Don't use it when**
- There are only two options and they will never change. A ternary is fine.
- The "algorithms" need very different inputs. Forcing them behind one interface leads to awkward optional parameters.

## Pitfalls

- **The client must still choose.** Strategy removes the `switch` from the context but not from the whole system. Put the choice in *one* place, such as a registry, a factory, or DI config.
- **Leaky interface.** If `calculate()` takes a parameter that only one strategy uses, the abstraction is wrong. Pass a context object instead, for example `{ turnover, segment, side }`.
- **Stateful strategies shared across requests.** If a strategy instance holds mutable state and is a singleton provider, concurrent requests will interfere with each other. Keep strategies stateless.

## Related patterns

- **Strategy vs State.** Both delegate to an object behind an interface. In Strategy, the **client** picks the object, and the strategies don't know about each other. In State, the **states switch themselves** as events happen.
- **Strategy vs Template Method.** Strategy uses *composition* and swaps the whole algorithm. Template Method uses *inheritance* and fixes the skeleton while subclasses fill in steps.
- **Strategy vs Command.** A strategy is *how* to do something. A command is *a request to do* something that you can store, queue, and undo.
- Strategies are often created by a **Factory** and can be shared as **Flyweights** when they are stateless.

## Where it shows up in LLD interview problems

- **Parking lot:** `FeeStrategy` (hourly, flat, weekend, EV surcharge).
- **Splitwise:** `SplitStrategy` (equal, exact, percentage).
- **Ride hailing:** `PricingStrategy` (base, surge) and `DriverMatchingStrategy` (nearest, highest rated).
- **Elevator:** `SchedulingStrategy` (FCFS, SCAN, LOOK).
- **Payment gateway / checkout:** `PaymentStrategy` (UPI, card, wallet).
- **Rate limiter:** token bucket vs sliding window.

*How to say it:* "Fee calculation varies by plan and will keep changing, so I'll put it behind a `FeeStrategy` interface and inject the right one from a registry keyed by plan. Adding a plan means adding a class. `OrderService` doesn't change."

## Quick check

1. What is the main difference between Strategy and State?
2. When is a plain function a better strategy than a class?
3. Where should the "which strategy?" decision live?

<details>
<summary>Answer</summary>

1. In Strategy the client chooses the algorithm and the strategies don't know about each other. In State the current state object decides the next state when events happen.
2. When the strategy is one stateless operation with no dependencies, for example `(turnover) => number`.
3. In exactly one place: a registry map, a factory, or DI configuration. It should not be scattered across the code that uses the strategy.

</details>
