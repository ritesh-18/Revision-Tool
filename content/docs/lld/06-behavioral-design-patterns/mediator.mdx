title: "6.8 Mediator"
---

## Intent

Make a set of objects communicate through **one central coordinator** instead of referencing each other directly. Many-to-many connections become many-to-one.

## Problem

In an online **auction** (think of a bond or collectible auction), every bidder needs to know when they've been outbid, bids must beat the current high by a minimum increment, and the auction closes with a winner. If each `Bidder` held references to all other bidders and checked rules itself, you would get N×N coupling, duplicated rules, and chaos when someone joins mid-auction.

The same problem shows up in **chat rooms** (users shouldn't hold references to each other), **air-traffic control** (planes talk to the tower, not to each other), and **UI forms** (a checkbox enabling a text field that updates a button).

## TypeScript implementation

```ts
interface AuctionMediator {
  join(bidder: Bidder): void;
  placeBid(bidder: Bidder, amount: number): void;
}

class Bidder {
  constructor(readonly name: string, private readonly house: AuctionMediator) {
    house.join(this);
  }
  bid(amount: number): void {
    this.house.placeBid(this, amount);
  }
  notify(message: string): void {
    console.log(`  [${this.name}] ${message}`);
  }
}

class AuctionHouse implements AuctionMediator {
  private bidders: Bidder[] = [];
  private highest: { bidder: Bidder; amount: number } | undefined;
  private closed = false;

  constructor(private readonly item: string, private readonly startPrice: number, private readonly minIncrement: number) {}

  join(bidder: Bidder): void {
    this.bidders.push(bidder);
  }

  placeBid(bidder: Bidder, amount: number): void {
    if (this.closed) return bidder.notify('auction is closed');
    const minimum = this.highest ? this.highest.amount + this.minIncrement : this.startPrice;
    if (amount < minimum) return bidder.notify(`bid ${amount} rejected, minimum is ${minimum}`);

    const previous = this.highest;
    this.highest = { bidder, amount };
    console.log(`${bidder.name} bids ${amount}`);

    // The mediator owns the "who needs to know what" rules.
    if (previous && previous.bidder !== bidder) previous.bidder.notify(`outbid by ${bidder.name} at ${amount}`);
    for (const b of this.bidders) {
      if (b !== bidder && b !== previous?.bidder) b.notify(`new high bid ${amount}`);
    }
  }

  close(): string {
    this.closed = true;
    return this.highest
      ? `SOLD: ${this.item} to ${this.highest.bidder.name} for ${this.highest.amount}`
      : `UNSOLD: ${this.item}`;
  }
}

const house = new AuctionHouse('Vintage Bond Certificate', 1000, 100);
const asha = new Bidder('asha', house);
const ravi = new Bidder('ravi', house);
const meera = new Bidder('meera', house);

asha.bid(1000);
ravi.bid(1050);
ravi.bid(1100);
meera.bid(1300);
console.log(house.close());
asha.bid(2000);
```

```text
asha bids 1000
  [ravi] new high bid 1000
  [meera] new high bid 1000
  [ravi] bid 1050 rejected, minimum is 1100
ravi bids 1100
  [asha] outbid by ravi at 1100
  [meera] new high bid 1100
meera bids 1300
  [ravi] outbid by meera at 1300
  [asha] new high bid 1300
SOLD: Vintage Bond Certificate to meera for 1300
  [asha] auction is closed
```

Bidders never reference each other. Adding a rule such as "anti-sniping: extend the auction by 2 minutes if someone bids in the last minute" touches only `AuctionHouse`.

## When to use / when NOT to use

**Use it when**
- Many objects interact in complex ways and the interaction *rules* keep changing.
- You want to reuse components (a `Bidder`, a form field) in different contexts without them knowing about their peers.

**Don't use it when**
- Communication is simple one-way broadcasting. Observer is enough.
- The mediator would just forward calls with no rules of its own.

## Pitfalls

- **God object.** The mediator can grow into a class that knows everything. Split it by concern (bidding rules, notifications, settlement), or have it publish events.
- **Single point of failure / bottleneck** in distributed versions (the "tower").
- **Circular constructor wiring.** Here `Bidder` joins in its constructor, which is convenient but hides a side effect. Explicit `house.join(bidder)` is more testable.

## Related patterns

- **Mediator vs Observer.** An observer subject doesn't care who listens. A mediator *knows its colleagues* and decides who gets what. Mediators are often *implemented* with observer-style notifications.
- **Mediator vs Facade.** A facade simplifies a subsystem for *outside* callers, and the subsystem doesn't know the facade exists. A mediator coordinates *peers*, and the peers know the mediator.
- **Mediator vs Pub/Sub broker.** A broker routes messages by topic with no business rules. A mediator contains domain rules.

## Where it shows up in LLD interview problems

- **Chat room / group chat / Slack channel.**
- **Auction system** (online bidding).
- **Air-traffic control / runway allocation.**
- **Ride matching:** a dispatcher mediates between riders and drivers.
- **Stock exchange matching engine:** buyers and sellers never talk directly. The exchange matches orders.

*How to say it:* "Bidders only know the `AuctionHouse`. It validates increments, tracks the high bid, and decides who gets an 'outbid' vs 'new high bid' message. That keeps rules in one place and bidders reusable."

## Quick check

1. How does Mediator reduce coupling compared with peers talking directly?
2. What is the main risk of this pattern?
3. Is a stock exchange closer to a Mediator or an Observer? Why?

<details>
<summary>Answer</summary>

1. Each colleague depends only on the mediator (N links) instead of on every other colleague (up to N×N links), and interaction rules live in one place.
2. The mediator becomes a god object that is hard to change and test.
3. A mediator. It applies rules (price-time priority matching) between buyers and sellers who never reference each other. It *also* publishes trades to observers, but its core role is coordination.
