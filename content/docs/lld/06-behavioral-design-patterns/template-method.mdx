title: "6.6 Template Method"
---

## Intent

Define the **skeleton of an algorithm** in a base class and let subclasses fill in specific steps without changing the overall order.

## Problem

Your back-office imports trade files from different sources: a CSV from one exchange, JSON from a partner API, and later fixed-width files. Every import follows the same steps: **parse → validate each row → transform → save → report errors**. Only *parse* (and sometimes *transform*) differs. Copy-pasting the pipeline per source means a bug fix to validation has to be applied three times.

The same shape appears in **report generation** (fetch data → compute → format as PDF/CSV → deliver).

The step types are:

- **Template method** (`run`): the fixed algorithm. Subclasses must not override it.
- **Abstract steps** (`parse`): subclasses *must* implement them.
- **Hooks** (`transform`, `afterImport`): have a default and *may* be overridden.

## TypeScript implementation

```ts
interface TradeRow {
  symbol: string;
  qty: number;
  price: number;
}

abstract class TradeImporter {
  constructor(protected readonly source: string) {}

  /** The template method. TypeScript has no `final`, so document it and never override it. */
  run(raw: string): string {
    console.log(`[${this.source}] start`);
    const valid: TradeRow[] = [];
    const errors: string[] = [];
    try {
      this.parse(raw).forEach((row, i) => {
        const err = this.validate(row);
        if (err) errors.push(`row ${i + 1}: ${err}`);
        else valid.push(this.transform(row));
      });
    } catch (err) {
      return `${this.source}: parse failed (${(err as Error).message})`;
    }
    this.save(valid);
    this.afterImport(valid.length, errors);
    return `${this.source}: imported ${valid.length}, rejected ${errors.length}`;
  }

  // Abstract step: every source must say how to parse.
  protected abstract parse(raw: string): TradeRow[];

  // Default steps (can be overridden, but usually shouldn't be).
  protected validate(row: TradeRow): string | null {
    if (!row.symbol) return 'symbol missing';
    if (!(row.qty > 0)) return 'qty must be positive';
    if (!(row.price > 0)) return 'price must be positive';
    return null;
  }

  protected save(rows: TradeRow[]): void {
    console.log(`  saved ${rows.map((r) => `${r.symbol}x${r.qty}`).join(', ') || 'nothing'}`);
  }

  // Hooks: no-op or simple defaults.
  protected transform(row: TradeRow): TradeRow {
    return row;
  }

  protected afterImport(_count: number, errors: string[]): void {
    for (const e of errors) console.log(`  ${e}`);
  }
}

class CsvImporter extends TradeImporter {
  constructor() {
    super('csv');
  }
  protected parse(raw: string): TradeRow[] {
    return raw
      .trim()
      .split('\n')
      .slice(1) // skip header
      .map((line) => {
        const [symbol = '', qty = '', price = ''] = line.split(',');
        return { symbol, qty: Number(qty), price: Number(price) };
      });
  }
}

class JsonImporter extends TradeImporter {
  constructor() {
    super('json');
  }
  protected parse(raw: string): TradeRow[] {
    const data: unknown = JSON.parse(raw);
    if (!Array.isArray(data)) throw new Error('expected an array');
    return data as TradeRow[];
  }
  // Partner sends lowercase symbols.
  protected override transform(row: TradeRow): TradeRow {
    return { ...row, symbol: row.symbol.toUpperCase() };
  }
}

const csv = 'symbol,qty,price\nINFY,10,1500\nTCS,0,3900\nSBIN,50,820';
const json = '[{"symbol":"hdfcbank","qty":5,"price":1650},{"symbol":"itc","qty":20,"price":-1}]';

for (const [importer, raw] of [
  [new CsvImporter(), csv],
  [new JsonImporter(), json],
  [new JsonImporter(), '{"oops":true}'],
] as const) {
  console.log(importer.run(raw));
}
```

> **The TypeScript/functional twist.** Inheritance isn't the only way. You can pass the variable steps in as functions: `runImport({ parse, transform })`. That is effectively "Template Method via Strategy", and it avoids deep class hierarchies. NestJS lifecycle hooks (`onModuleInit`) and React class component lifecycles are template-method hooks.

## When to use / when NOT to use

**Use it when**
- Several classes share the same algorithm and differ only in a few steps.
- You want to *enforce* the order of steps (validation always before save).

**Don't use it when**
- The variations are large or need to be combined (CSV parsing + partner transform + S3 save). Composition with strategies scales better than a subclass per combination.
- There is only one implementation.

## Pitfalls

- **Overriding the template method** by accident. TypeScript has no `final` keyword. Document it, and consider keeping the skeleton in a function that isn't meant to be overridden.
- **Too many hooks** make the flow hard to follow ("which of 9 hooks runs when?").
- **Fragile base class.** Changing the skeleton affects every subclass. Keep the base small and well tested.
- **Liskov violations.** A subclass that makes `validate` always return `null` quietly breaks guarantees.

## Related patterns

- **Template Method vs Strategy.** Inheritance and compile-time structure vs composition and runtime swapping. Prefer Strategy when you need to mix and match steps.
- **Factory Method** is often *one step* inside a template method (`createParser()`).
- **Template Method vs Hooks in frameworks.** Framework lifecycles are template methods where *you* supply the hooks.

## Where it shows up in LLD interview problems

- **Report generators** (daily P&L report in PDF/CSV/email).
- **Data import/ETL pipelines**, bank statement parsers.
- **Game engines:** `initialize → loop(update, render) → shutdown`.
- **Payment flows:** `validate → authorize → capture → notify` with gateway-specific steps.
- **Beverage machines:** the classic "boil → brew → pour → add condiments".

*How to say it:* "All importers share `parse → validate → transform → save → report`, so that sequence lives in an abstract `run()`. Each source only implements `parse`, and it can optionally override the `transform` hook."

## Quick check

1. What is the difference between an abstract step and a hook?
2. How do you prevent subclasses from overriding the template method in TypeScript?
3. When would you replace Template Method with Strategy?

<details>
<summary>Answer</summary>

1. An abstract step *must* be implemented by subclasses. A hook has a default (often a no-op) and *may* be overridden.
2. TypeScript has no `final`. You rely on convention and docs, or you move the skeleton into a standalone function or a separate class that takes the steps as dependencies, which is composition.
3. When steps need to vary independently and be combined at runtime, or when the subclass hierarchy starts to multiply.

</details>
