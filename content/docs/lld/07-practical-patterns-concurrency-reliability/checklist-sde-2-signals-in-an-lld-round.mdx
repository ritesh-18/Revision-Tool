---
title: "7.14 Checklist: SDE-2 signals in an LLD round"
---

Use this as a final pass before you say "done". Each item is something interviewers explicitly write down.

**Structure and design**

- [ ] Clarified requirements and **stated assumptions** (scale, single vs multi-instance, what's out of scope) before coding
- [ ] Entities, value objects and enums identified. Invariants live **inside** the model (no `order.status = 'FILLED'` from outside)
- [ ] Layers: models / repositories (interfaces) / services / strategies / driver. Services don't print
- [ ] Dependencies injected through constructors, and a single composition root
- [ ] Extension points use Strategy/State/Observer **where requirements vary**, not everywhere

**Correctness**

- [ ] Money in integer paise (`bigint` when needed), with rounding mode named
- [ ] Explicit state machines with guarded transitions (order, seat, payment, circuit)
- [ ] Typed errors: `Result` for business outcomes, an `AppError` hierarchy for infrastructure, `unknown` narrowed in `catch`
- [ ] Edge cases tested: zero/negative amounts, duplicates, boundaries (`>=` vs `>`), empty collections

**Concurrency and reliability**

- [ ] Can point to **every check-then-act** and explain why it's safe (synchronous section, mutex, version check, DB constraint)
- [ ] Per-key locking rather than a global lock, and a consistent lock order for multi-key operations
- [ ] Idempotency keys on anything that moves money or sends messages
- [ ] Retries only on retryable, idempotent calls, with backoff and jitter; a circuit breaker and timeouts around remote calls
- [ ] Holds and locks have TTLs, and you can explain fencing tokens
- [ ] Knows what changes with **N instances**: DB row locks, conditional updates, Redis with caveats, outbox

**Testability and operability**

- [ ] `Clock`, `IdGenerator`, `random` and `sleep` injected, so demos and tests are deterministic
- [ ] A driver or test that exercises the happy path **and** the failure paths
- [ ] Logging and metrics seams, with no PII in logs
- [ ] Can state the time/space complexity of the core operations (LRU O(1), heap O(log n), and so on)

**Communication**

- [ ] Narrated trade-offs ("optimistic because conflicts are rare; I'd switch to `FOR UPDATE` if…")
- [ ] Prioritized: working core first, then extensions, and said what you'd do with more time
