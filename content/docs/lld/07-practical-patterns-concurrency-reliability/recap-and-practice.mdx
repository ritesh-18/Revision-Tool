## Chapter recap

- **Layer** machine-coding solutions: models → repositories → strategies → services → driver, with dependencies pointing inward and one composition root.
- A **generic repository** hides storage, and **Specifications** turn filters into named, combinable business rules.
- **Constructor injection** of ports makes every I/O boundary a test seam. A DI container is optional.
- **Domain events** decouple side effects. The **outbox** makes events durable, with at-least-once delivery and idempotent consumers.
- Use **`Result`** for expected business failures and **exceptions** (a typed hierarchy) for unexpected ones.
- **Inject `Clock` and `IdGenerator`** (and `random` and `sleep`) so tests can control time.
- **Money** means integer paise, basis points, explicit rounding modes, and remainder-aware allocation.
- **JS concurrency**: synchronous code is atomic, and every `await` is a potential interleaving. The fixes are a synchronous check-and-reserve, an async mutex, a semaphore, keyed locks with ordered acquisition, optimistic versioning with retry, TTL holds with lazy expiry, and idempotency stores. Across instances, push atomicity to the DB, and use Redis locks only with fencing tokens.
- **Rate limiters**: fixed window (boundary spikes), sliding log (exact, memory-heavy), sliding counter (approximate, O(1)), token bucket (bursty but bounded), leaky bucket (smooth).
- **Retry** with capped exponential backoff and jitter, only for retryable and idempotent calls. The **circuit breaker** is CLOSED → OPEN → HALF_OPEN → CLOSED.
- **Caches**: LRU (Map order, or DLL + map), LFU (frequency buckets + `minFreq`), TTL with lazy expiry; cache-aside with delete-on-write and single-flight.
- **Job queues**: a delayed heap plus a ready heap, backoff retries, and a DLQ; at-least-once delivery means handlers must be idempotent.
- **Observability** is a set of ports plus decorators: structured logs, counters and histograms, and no PII.

## Interview questions on this chapter

1. **Node.js is single-threaded. Can it have race conditions?**

<details>
<summary>Answer</summary>

Yes. Synchronous code runs without interruption, but every `await` hands control back to the event loop, and other requests can then run and change shared state. A "read balance → await → write balance" sequence can interleave with another request doing the same thing, which causes lost updates or double spending. On top of that, production usually runs several Node processes, which share state only through the DB or Redis, so you get classic distributed races too. The fixes: keep check-and-act synchronous, use an async mutex or keyed lock in-process, and use conditional updates, row locks or version columns across processes.

</details>

2. **How would you implement an async mutex in TypeScript? What makes it correct?**

<details>
<summary>Answer</summary>

Use a `locked` flag and a FIFO array of waiter `resolve` functions. `acquire()` either takes the free lock synchronously or pushes a resolver and awaits it. Release **hands ownership directly** to the next waiter (the flag stays `true`), so there's no window for a newcomer to barge in, and it only clears the flag when nobody is waiting. Wrap it in `runExclusive(fn)` with `try/finally`, so exceptions always release the lock. Make release idempotent. Mention the limitations: it isn't re-entrant, it needs a timeout (`AbortSignal`) for production, and it only protects a single process.

</details>

3. **Optimistic vs pessimistic locking: when do you choose which?**

<details>
<summary>Answer</summary>

Optimistic locking (a version column plus `UPDATE … WHERE version = ?`, retrying on 0 rows) holds no locks while the request works. It's great when conflicts are rare and transactions are short or span user think-time (edit forms, profile updates). Pessimistic locking (`SELECT … FOR UPDATE`, or a TTL hold) makes contenders wait. It's better when conflicts are frequent (hot inventory, a popular seat, a single wallet under heavy traffic), because optimistic retries would pile up. With optimistic locking, always re-validate business rules after re-reading, and add backoff with jitter to the retries.

</details>

4. **Design seat holding for a ticketing system so abandoned checkouts free up seats automatically.**

<details>
<summary>Answer</summary>

Seats go AVAILABLE → HELD(holdId, userId, expiresAt) → BOOKED. The hold is atomic and all-or-nothing: either one synchronous section in memory, or one conditional `UPDATE` whose row count must equal the number of seats. Expiry is **lazy**: a HELD seat with `expiresAt <= now` counts as available on every read, so no per-seat timers are needed, and a background sweeper can clean up for reporting. `confirm(holdId)` checks that the hold is still valid and belongs to the caller. The hold id works as a fencing token, so an expired holder can't book a seat that someone else now holds. The clock is injected so the 5-minute boundary can be tested exactly.

</details>

5. **How do idempotency keys work, and what edge cases matter?**

<details>
<summary>Answer</summary>

The client generates a unique key per logical operation and resends it on retries. The server atomically claims the key (`SET NX`, or an `INSERT` into a table with a unique constraint), runs the operation, and stores the response keyed by it. Retries get the stored response back. Edge cases: **concurrent duplicates** (wait on the in-flight result or return 409); **same key with a different payload** (store a request fingerprint and reject with 422); **failure** (release the key if retryable, store the failure if final); **TTL** for cleanup; and **atomicity** between the side effect and the stored result (write both in the same DB transaction so a crash doesn't leave a charge with no record).

</details>

6. **Compare token bucket and sliding window log. Which would you use for an order-placement API?**

<details>
<summary>Answer</summary>

A token bucket stores two numbers per key (tokens and last refill time), allows bursts up to its capacity, and enforces a long-run average rate. A sliding window log stores every timestamp in the window, which makes it exact but O(limit) in memory. For order placement (for example, "10 orders per second per user"), a token bucket is the usual choice: cheap, tolerant of small bursts, and easy to implement atomically in Redis with a Lua script. For a low, strict limit such as "5 OTP attempts per 15 minutes", a sliding log is fine, and its exactness is worth the memory.

</details>

7. **Why does fixed-window rate limiting allow 2× the limit?**

<details>
<summary>Answer</summary>

The counter resets at window boundaries. A client can send the full limit in the last few milliseconds of one window and the full limit again in the first few milliseconds of the next, which is 2× the limit within a span much shorter than one window. Sliding window algorithms and token buckets don't have this boundary effect.

</details>

8. **Explain exponential backoff with jitter. Why jitter?**

<details>
<summary>Answer</summary>

The delay before retry n is `min(cap, base × 2^(n-1))`, so each retry waits roughly twice as long, which gives the dependency time to recover. Without jitter, every client that failed at the same moment retries at the same moments too, producing synchronized load spikes (a thundering herd). Full jitter picks a random delay in `[0, backoff]`, which spreads the retries out. Only retry retryable errors on idempotent operations, cap the attempts or the total time, honor `Retry-After`, and retry at only one layer to avoid multiplying calls.

</details>

9. **Walk through the circuit breaker's states and transitions.**

<details>
<summary>Answer</summary>

In CLOSED, calls pass through and failures are counted (consecutively, or as a rate in a rolling window). When the count crosses the threshold, the breaker goes OPEN: calls fail fast without touching the dependency until a cool-down has passed. The next call after the cool-down moves it to HALF_OPEN, where only a limited number of probe calls are allowed. If enough probes succeed, it goes back to CLOSED. If any probe fails, it goes back to OPEN and the timer restarts. Use an injected clock, emit a metric on each transition, and decide which errors count (5xx and timeouts do, caller 4xx don't).

</details>

10. **Implement LRU in O(1). How does it change in JavaScript?**

<details>
<summary>Answer</summary>

The classic approach is a hash map from key to node, plus a doubly linked list ordered by recency. `get` looks up the node and moves it to the head. `put` updates and moves an existing node, or, if the cache is full, removes the tail node (and its map entry) and inserts the new node at the head. Everything is O(1). In JS, a `Map` preserves insertion order, so deleting and re-inserting a key on access makes `map.keys().next()` the LRU key. That's still O(1), with much less code, but interviewers may ask for the explicit DLL version.

</details>

11. **How does an O(1) LFU cache work?**

<details>
<summary>Answer</summary>

Keep a key → \{value, freq\} map, a freq → ordered set of keys map (insertion order breaks ties by recency), and a `minFreq` variable. On access, move the key from bucket f to bucket f+1. If bucket f becomes empty and f was `minFreq`, increment `minFreq`. On insert when full, evict the oldest key in the `minFreq` bucket, then add the new key with freq 1 and set `minFreq = 1`. All operations are O(1). Mention aging/decay or W-TinyLFU to deal with stale hot keys.

</details>

12. **Cache-aside: on an update, should you set the cache or delete it? What's a cache stampede?**

<details>
<summary>Answer</summary>

Delete it. If you set it, a slow concurrent reader that loaded the old value from the DB can write that stale value to the cache *after* your update, and it stays there until the TTL expires. Deleting shrinks that window, and delayed double-delete or CDC-based invalidation shrinks it further. A stampede happens when a hot key expires and many requests miss at once and all hit the DB. Mitigations: single-flight (share one in-flight load per key), a short lock around the load, jittered TTLs, and refresh-ahead for hot keys.

</details>

13. **Why store money in paise, and how do you handle rounding and splitting?**

<details>
<summary>Answer</summary>

Binary floats can't represent most decimal fractions (`0.1 + 0.2 ≠ 0.3`), so repeated arithmetic drifts and reconciliation fails. Store integer paise (a `bigint` when values can exceed 2^53, or to be safe) and express rates in basis points. Every division takes an explicit rounding mode (half-up, half-even, or down) chosen by the business or the regulator, and rounding happens at defined points. For splits, compute floor shares and hand the leftover paise out one by one, so the parts always add up to the total. Never parse money with `parseFloat`, and serialize it as a string.

</details>

14. **Result types or exceptions: which do you use?**

<details>
<summary>Answer</summary>

Both, for different things. Expected business outcomes that callers branch on (insufficient funds, seat taken, below minimum) are modeled as a discriminated-union `Result`, so they show up in the signature, and an exhaustive `switch` with `never` makes the compiler catch unhandled cases. Unexpected or infrastructure failures (DB down, bugs, broken invariants) throw typed `AppError` subclasses carrying a code, an HTTP status and a `cause`, and a single boundary handler maps them to responses. In `catch`, the error is `unknown`, so narrow it with `instanceof`.

</details>

15. **What is the transactional outbox, and what delivery guarantee does it give?**

<details>
<summary>Answer</summary>

It solves the dual-write problem (the DB commit succeeds but the event publish fails, or the other way round). The event is inserted into an `outbox` table in the **same transaction** as the state change. A relay (a poller, or CDC such as Debezium) publishes unpublished rows in order and then marks them as sent. A crash between publishing and marking causes a re-publish, so the guarantee is **at-least-once**, and consumers must be idempotent, typically by recording processed event ids (an inbox table).

</details>

16. **You have 10 pods. How do you stop two of them from processing the same account at the same time?**

<details>
<summary>Answer</summary>

Prefer designs that don't need a lock: conditional updates (`WHERE balance >= ?`), version columns, unique constraints, or routing all work for an account to one Kafka partition (keyed by account id), which gives per-key ordering. If you need mutual exclusion, use DB row locks (`SELECT … FOR UPDATE`), Postgres advisory locks, or `SKIP LOCKED` for work queues. Redis `SET key token NX PX ttl`, with a compare-and-delete unlock, is fine for efficiency. For correctness, the TTL can expire during a GC pause, so add fencing tokens that the storage layer checks. Redlock has known caveats around clock drift and pauses, so for correctness-critical locks use the DB or a consensus store such as etcd/ZooKeeper.

</details>

17. **How would you answer "how would you do this in Java or Go?" for the wallet?**

<details>
<summary>Answer</summary>

In Java: `synchronized` methods or a `ReentrantLock` (with `tryLock` timeouts), `AtomicLong.updateAndGet` for lock-free CAS, `ConcurrentHashMap.compute` for per-key atomic updates, and `Semaphore` to cap concurrency. In Go: a `sync.Mutex` with `defer Unlock`, or the idiomatic approach where one goroutine owns the balance and receives requests over a channel; a buffered channel works as a semaphore, and `singleflight` prevents cache stampedes. Across processes, all of these languages still rely on the database or a distributed coordinator.

</details>

18. **How do you make time-based logic testable?**

<details>
<summary>Answer</summary>

Inject a `Clock` interface (`now()`) and, where waiting is involved, a `sleep` function. Production uses `Date.now()` and `setTimeout`. Tests use a `FakeClock` that is advanced by hand, and a fake `sleep` that records the delays and resolves immediately. Inject `random` too (for jitter) and an `IdGenerator`. Then expiry boundaries, backoff schedules, circuit breaker cool-downs and rate-limit windows can all be asserted exactly, in microseconds, with no flakiness.

</details>

## Practice exercises

1. **Stock-order machine coding (90 min).** Build `OrderService` with place/cancel/modify for LIMIT and MARKET orders, using the layered layout from 7.1, an `InMemoryRepository<Order>`, Specifications for "open orders by symbol", a `BrokerageStrategy`, injected `Clock` and `IdGenerator`, and domain events (`OrderPlaced`, `OrderCancelled`). Write a driver that shows both the happy path and the failure paths.
2. **Wallet under fire.** Implement `WalletService.transfer(from, to, amountPaise, idempotencyKey)` using `bigint` paise, a `KeyedMutex` with sorted lock order, and an idempotency store. Fire 100 concurrent random transfers, generated from a seeded PRNG that you inject, and assert that the total money is conserved and that replays return the same result.
3. **Optimistic vs pessimistic benchmark.** Using a fake store with an `await` per call, compare the conflict/retry count of the optimistic wallet against the mutex version as you vary concurrency from 2 to 50. Plot (or print) where optimistic stops paying off.
4. **Distributed-ready rate limiter.** Define a `RateLimitStore` port with an atomic `takeToken(key, capacity, refillPerSec, now)`. Implement it in memory, then write (as pseudo-code) the Redis Lua script version. Add `Retry-After` computation.
5. **Resilient client.** Compose `timeout → retry(backoff + jitter) → circuitBreaker → fallback(cached value)` as decorators around a `MarketDataClient` port. Write deterministic tests with a fake clock, fake sleep and fake random that cover: blip recovered, outage (breaker opens), and recovery (half-open → closed).
6. **LFU with aging.** Extend the O(1) LFU so that every `N` operations all frequencies are halved (rounded down, minimum 1). Keep `minFreq` correct and add a `describe()` test.
7. **Seat booking with waitlist.** Extend `SeatHoldService` so that when a hold expires or is released, the seats are offered to the first waiting user (an event on the bus), who gets a new 2-minute hold. Test it entirely with `FakeClock`.
8. **Job queue upgrades.** Add a concurrency limit (a semaphore), per-key ordering (jobs with the same `accountId` never run in parallel), priority aging, and a `replayDeadLetters()` method. Prove FIFO order within the same priority.
9. **Outbox relay.** Extend the outbox simulation with multiple relay instances that claim rows using a `claimedBy` + `claimedUntil` lease (like `SKIP LOCKED`), and show that a crashed relay's rows are picked up after the lease expires.
10. **Talk track.** Record yourself answering "Node is single-threaded, so why do you need locks?" and "What changes with 10 pods?" in under 2 minutes each, using the table in 7.8.9.
