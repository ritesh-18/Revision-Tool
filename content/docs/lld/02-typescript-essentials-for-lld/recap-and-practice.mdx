## Chapter recap

- Use **interfaces** for contracts classes implement and **type aliases** for unions and computed types; be consistent.
- TypeScript is **structural**. Use **branded types** to stop `UserId`/`OrderId` mix-ups at zero runtime cost.
- **Classes**: parameter properties for dependencies, getters for read-only access, static factories for named construction.
- `private` is compile-time only; `#private` is real runtime privacy and doesn't leak via `JSON.stringify`.
- `readonly`, `Readonly<T>`, `readonly T[]` and `as const` are **shallow, compile-time** guarantees.
- Default to **interfaces** for collaborators; add an **abstract class** when implementations share an algorithm (Template Method). Always use `override`.
- **Generics** (`Repository<T extends Entity>`, `EventBus<Events>`) give reusable, fully typed building blocks. Use them only when a type parameter links things.
- Prefer **string-literal unions** (with an `as const` source array) over enums.
- **Discriminated unions + `assertNever`** make state machines safe and extensible.
- **Type guards** (`typeof`, `instanceof`, `in`, predicates, assertion functions) narrow `unknown` input into domain types.
- **Utility types** (`Omit`, `Partial`, `Pick`, `Record`, `ReturnType`) keep DTOs in sync with entities.
- Use `Map`/`Set` for dynamic in-memory stores; `Record` for fixed lookup tables.
- Throw **custom error classes** with a `code` and set `name`; use `{ cause }` for wrapping.
- **`unknown` over `any`**, **`??` over `||`**, and `satisfies` for config tables.
- **Money = integer minor units** (`number` paise or `bigint`) inside an immutable `Money` value object.

## Interview questions on this chapter

**1. When would you use `type` instead of `interface`?**

<details>
<summary>Answer</summary>

Use `type` when you need something an interface can't express: unions (`"BUY" | "SELL"`), discriminated unions, tuples, function types, mapped or conditional types (`Partial<Order>`). Use `interface` for object contracts that classes implement or that you inject (`Notifier`, `OrderRepository`). Interfaces also support declaration merging, which is handy for extending library types but can surprise you in domain code. For plain object shapes the two are equivalent, so pick one convention and stick to it.

</details>

**2. What is structural typing, and how can it cause bugs? How do you prevent them?**

<details>
<summary>Answer</summary>

TypeScript decides compatibility by shape, not name. So `type UserId = string` and `type OrderId = string` are the same type, and swapping them in a call compiles. The fix is a **branded type**: `type OrderId = string & { readonly [brand]: "OrderId" }`, created only through a validating function like `toOrderId(raw)`. The brand is compile-time only, so there is no runtime cost, but passing a `UserId` where an `OrderId` is expected becomes an error.

</details>

**3. What's the difference between `private` and `#private`?**

<details>
<summary>Answer</summary>

`private` is checked only by the TypeScript compiler. After compilation it's a normal property, visible through bracket access, `Object.keys` and `JSON.stringify`. `#private` is an ECMAScript feature enforced by the JavaScript runtime. It cannot be accessed from outside the class at all and does not appear in serialization. `#field in obj` also works as a brand check. I use `private` by default (it plays well with parameter properties and DI) and `#` for secrets like tokens or PINs.

</details>

**4. Abstract class or interface for `PaymentMethod`? Justify.**

<details>
<summary>Answer</summary>

Start with an interface, `PaymentMethod { pay(amount): Result }`, because the checkout service should depend on an abstraction, and interfaces are easy to mock and let unrelated classes (a wallet, a third-party SDK adapter) implement them. If UPI, card and netbanking share a flow (validate → check limit → charge → compute fee), add `abstract class BasePaymentMethod implements PaymentMethod` with the shared template method and abstract `charge()`. That way you get code reuse without forcing every implementation into the hierarchy. Also, a class can implement many interfaces but extend only one class.

</details>

**5. Why use `override`, and what does `noImplicitOverride` do?**

<details>
<summary>Answer</summary>

`override` states that a method replaces a base-class method. With `noImplicitOverride`, the compiler requires it on every overriding member, and it errors if you write `override` on a method that doesn't exist in the base class. This catches two bugs: accidentally overriding a base method you didn't know about, and a typo or base-class rename that leaves your "override" as a new method that is never called.

</details>

**6. Enums or string-literal unions? What do you prefer and why?**

<details>
<summary>Answer</summary>

I prefer string-literal unions. They produce no runtime code, values are readable in JSON and logs, raw strings from requests are directly assignable after validation, and they narrow cleanly in a `switch`. If I need the list of values at runtime, I write `const STATUSES = [...] as const` and derive `type Status = typeof STATUSES[number]`. Numeric enums are the worst option because any number is assignable to them. String enums are fine if the codebase already uses them (for example, for Swagger in NestJS), and they are not supported by Node's type-stripping mode.

</details>

**7. How do you make sure every order status is handled everywhere?**

<details>
<summary>Answer</summary>

Model the status as a discriminated union (`{ kind: "OPEN"; ... } | { kind: "FILLED"; ... }`), handle it in a `switch` on `kind`, and in the `default` branch call `assertNever(s)`, where `assertNever(x: never): never` throws. If someone adds a new state to the union and forgets a case, the value in `default` isn't `never` any more, so the code fails to compile. This turns a runtime bug into a compile-time error.

</details>

**8. What's the difference between `unknown` and `any`?**

<details>
<summary>Answer</summary>

`any` turns off type checking: you can call any method on it, and it silently spreads into other types. `unknown` is the type-safe top type: you can hold it, but you must narrow it (with `typeof`, `instanceof`, `in`, or a custom guard) before using it. I type all external input (`JSON.parse`, request bodies, queue messages, `catch` variables) as `unknown` and validate it at the boundary.

</details>

**9. How would you store money in a trading or wallet system?**

<details>
<summary>Answer</summary>

Never as a floating-point rupee value, because `0.1 + 0.2 !== 0.3`. Store integer minor units (paise). In `number` that is safe up to `Number.MAX_SAFE_INTEGER` (about 9 × 10^15 paise); for large aggregates use `bigint`. Wrap it in an immutable `Money` value object carrying the currency, with `add`, `subtract`, `multiply`, explicit rounding (for example basis-point fees rounded half up) and `allocate` for splitting without losing paise. Serialize `bigint` as a string, since `JSON.stringify` throws on it.

</details>

**10. When would you use a `Map` over a plain object?**

<details>
<summary>Answer</summary>

For dynamic keyed stores such as orders by id or positions by user. `Map` accepts any key type, has O(1) `size`, keeps insertion order, is optimized for frequent adds and deletes, and `get` always returns `V | undefined`, so you're forced to handle missing keys. Plain objects (or `Record<K, V>`) are better for fixed lookup tables whose keys are a known union, and they serialize to JSON directly. Remember that `JSON.stringify(map)` gives `{}`, and object keys in a `Map` are compared by reference.

</details>

**11. What does `satisfies` do that a type annotation doesn't?**

<details>
<summary>Answer</summary>

An annotation (`const x: Record<Segment, FeeRule> = ...`) checks the value and then **widens** its type to the annotation, so you lose the specific literal types and keys. `satisfies` checks the value against the type but keeps the inferred type. For example, `FEES.COMMODITY.exchange` stays `"MCX"` instead of `"NSE" | "BSE" | "MCX"`, and `keyof typeof routes` stays a union of the actual keys instead of `string`. It's ideal for config tables and strategy registries.

</details>

**12. How do you write a custom error class properly in TypeScript?**

<details>
<summary>Answer</summary>

Extend `Error` (usually through a `DomainError` base), call `super(message, { cause })` when wrapping, set `this.name` (for example `new.target.name` in the base) so logs show the right name, and add typed fields such as `code`, `accountId` and `shortBy`. With an ES2015+ target, `instanceof` works for subclasses. Only when compiling down to ES5 do you need `Object.setPrototypeOf(this, new.target.prototype)`. A single mapper can then turn error classes into HTTP status codes.

</details>

**13. When are function overloads worth it?**

<details>
<summary>Answer</summary>

When the return type depends on the argument type in a way a union can't express, for example `find(id: string): Order | undefined` and `find(ids: string[]): Order[]`. The implementation signature is hidden from callers and must cover all overloads. If the return type is the same for all inputs, a union parameter is simpler. In LLD, two clearly named methods (`findById`, `findByIds`) are often the most readable choice.

</details>

**14. Is `readonly` enough to make an object immutable?**

<details>
<summary>Answer</summary>

No. `readonly`, `Readonly<T>` and `readonly T[]` are shallow and exist only at compile time. Nested objects can still be mutated, and a cast removes the protection. For stronger guarantees, return copies from getters, use value objects that create new instances on every change, and use `Object.freeze` (also shallow, but enforced at runtime) for config objects.

</details>

## Practice exercises

1. **Branded IDs.** Create `UserId`, `OrderId` and `InstrumentId` brands with validating constructors (`U-`, `O-`, `I-` prefixes). Write `placeOrder(user: UserId, instrument: InstrumentId, qty: number): OrderId` and confirm that swapping arguments fails to compile.
2. **Generic repository with indexes.** Extend `InMemoryRepository<T extends { id: string }>` with `addIndex<K extends keyof T>(key: K)` and `findBy<K extends keyof T>(key: K, value: T[K]): T[]` that uses a `Map<T[K], Set<string>>` under the hood. Keep indexes correct on `save` and `delete`.
3. **Order state machine.** Add an `EXPIRED` state (reached from `OPEN` or `PARTIALLY_FILLED` at market close) to the discriminated union from section 2.11. Notice where the compiler forces you to make changes, then implement them.
4. **Notification channels.** Define `interface Notifier { send(to: string, msg: string): Promise<void> }` and an abstract `BaseNotifier` that adds retry with a max attempt count (template method: `protected abstract deliver()`). Implement `SmsNotifier` and `EmailNotifier`, where `EmailNotifier` overrides a `format()` hook. Use `override` everywhere.
5. **Money.** Add `Money.compare(a, b): -1 | 0 | 1`, `Money.sum(list)`, and `allocateByRatio(ratios: number[])` (for example, splitting a brokerage 70/30 between broker and sub-broker) that never loses a paisa.
6. **Input validation.** Write `isModifyOrderDto(v: unknown): v is ModifyOrderDto`, where `ModifyOrderDto = Partial<Pick<Order, "qty" | "pricePaise">>` and at least one field must be present and a positive integer. Test it against five JSON strings.
7. **Error mapping.** Build `DomainError` subclasses for `InsufficientMarginError`, `MarketClosedError` and `InstrumentNotFoundError`, and a `Record<DomainErrorCode, number>` (checked with `satisfies`) mapping each code to an HTTP status. Make adding a new error class without a mapping a compile error.
8. **Spot the bugs.** Take this snippet and list every TypeScript smell from section 2.22, then rewrite it:

   ```ts
   // ❌ intentionally bad
   class Svc {
     orders: any = {};
     status = 0; // 0=open 1=filled
     place(o: any) { this.orders[o.id] = o; }
     fill(id) { this.orders[id].status = 1; this.orders[id].price = this.orders[id].price || 100.5; }
   }
   ```
