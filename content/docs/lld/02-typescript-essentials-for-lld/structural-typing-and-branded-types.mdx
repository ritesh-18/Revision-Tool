---
title: "2.3 Structural typing and branded types"
---

## Intuition

TypeScript is **structurally typed**: two types are compatible if their shapes match. Names do not matter. Java and C# are **nominally typed**: a `UserId` is never an `OrderId` unless you say so.

Structural typing is convenient, but it lets domain mix-ups through:

```ts
// ❌ compiles fine, bug in production
type UserId = string;
type OrderId = string;

function cancelOrder(orderId: OrderId, byUser: UserId) { /* ... */ }

const userId: UserId = "U-42";
const orderId: OrderId = "O-9001";
cancelOrder(userId, orderId); // arguments swapped — TypeScript doesn't care, both are string
```

Another structural gotcha: any object that has the right fields "is" the type, even if it came from somewhere else.

```ts
interface Money { amount: number; currency: string }
interface Distance { amount: number; currency: string } // same shape, unrelated meaning

function pay(m: Money): string {
  return `paid ${m.amount} ${m.currency}`;
}

const d: Distance = { amount: 5, currency: "km?" };
console.log(pay(d)); // compiles: shapes match

// Excess property check only applies to fresh object literals
const extra = { amount: 10, currency: "INR", note: "tip" };
console.log(pay(extra)); // OK: `extra` is not a fresh literal
// pay({ amount: 10, currency: "INR", note: "tip" }); // ❌ would error: 'note' does not exist in type 'Money'
```

```text
paid 5 km?
paid 10 INR
```

## The fix: branded (nominal) types

Add a fake, compile-time-only property ("brand") so that two strings with different meanings stop being interchangeable. You create branded values only through a small constructor function, which is also the perfect place for validation.

```ts
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };

type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;
type Paise = Brand<number, "Paise">;

function toUserId(raw: string): UserId {
  if (!raw.startsWith("U-")) throw new Error(`invalid user id: ${raw}`);
  return raw as UserId;
}
function toOrderId(raw: string): OrderId {
  if (!raw.startsWith("O-")) throw new Error(`invalid order id: ${raw}`);
  return raw as OrderId;
}
function toPaise(n: number): Paise {
  if (!Number.isSafeInteger(n) || n < 0) throw new Error(`invalid paise: ${n}`);
  return n as Paise;
}

function cancelOrder(orderId: OrderId, byUser: UserId): string {
  return `order ${orderId} cancelled by ${byUser}`;
}

const userId = toUserId("U-42");
const orderId = toOrderId("O-9001");

console.log(cancelOrder(orderId, userId));
// cancelOrder(userId, orderId); // ❌ error: 'UserId' is not assignable to 'OrderId'

// Branded values still behave like their base type at runtime
console.log(orderId.toUpperCase(), toPaise(2500) + 100);

try {
  toPaise(10.5);
} catch (err) {
  if (err instanceof Error) console.log(err.message);
}
```

```text
order O-9001 cancelled by U-42
O-9001 2600
invalid paise: 10.5
```

Notes:

- The brand exists **only in the type system**. At runtime `orderId` is a plain string, so there is zero cost.
- `declare const brand: unique symbol` makes the brand key impossible to create by accident.
- Note that `toPaise(2500) + 100` gives a plain `number`, not `Paise`. Arithmetic drops the brand, which is usually what you want: re-validate when you create a new domain value.

> **How to say it in an interview:** "TypeScript is structural, so two `string` aliases are interchangeable. For IDs and money I use branded types, so passing a `UserId` where an `OrderId` is expected becomes a compile error, with zero runtime cost."
