title: "2.2 Types vs interfaces"
---

## Intuition

Both `type` and `interface` can describe the shape of an object. They overlap about 90%. The difference is in the remaining 10%.

| Feature | `interface` | `type` alias |
|---|---|---|
| Object shapes | Yes | Yes |
| `extends` another shape | `extends` keyword | intersection `&` |
| A class can `implements` it | Yes | Yes (if it is an object type) |
| Unions (`A \| B`) | No | Yes |
| Primitives, tuples, mapped/conditional types | No | Yes |
| Declaration merging (same name declared twice gets merged) | Yes | No (duplicate name is an error) |
| Error messages | Usually shows the interface name | Sometimes expands the full shape |

## Rule of thumb

- Use **`interface`** for **contracts that classes implement** and for object shapes of entities: `PaymentMethod`, `Notifier`, `OrderRepository`.
- Use **`type`** for **unions, discriminated unions, tuples, function types and computed types**: `OrderStatus`, `OrderEvent`, `Handler<T>`, `Partial<Order>`.
- Be consistent. Interviewers care more about consistency than about which one you pick.

```ts
// Contract a class will implement → interface
interface Notifier {
  readonly channel: string;
  send(to: string, message: string): string;
}

// Union → must be a type
type Channel = "SMS" | "EMAIL" | "PUSH";

// Function type → type reads nicely
type Formatter = (name: string, amountPaise: number) => string;

// Extending: interface uses `extends`, type uses `&`
interface Entity { readonly id: string }
interface User extends Entity { name: string }

type Timestamped = { createdAt: number };
type AuditedUser = User & Timestamped;

const format: Formatter = (name, paise) => `Hi ${name}, ₹${(paise / 100).toFixed(2)} credited`;

class SmsNotifier implements Notifier {
  readonly channel: Channel = "SMS";
  send(to: string, message: string): string {
    return `[${this.channel}] to ${to}: ${message}`;
  }
}

const u: AuditedUser = { id: "U1", name: "Ritesh", createdAt: 0 };
console.log(new SmsNotifier().send(u.name, format(u.name, 150050)));
```

```text
[SMS] to Ritesh: Hi Ritesh, ₹1500.50 credited
```

## Declaration merging: a gotcha

```ts
// ❌ interfaces with the same name silently MERGE
interface Config { retries: number }
interface Config { timeoutMs: number }
// Config is now { retries: number; timeoutMs: number } — surprising in a big codebase

// ❌ with type aliases this is an error instead
type Settings = { retries: number };
type Settings = { timeoutMs: number }; // error: Duplicate identifier 'Settings'
```

Merging is useful for extending library types (for example adding `user` to Express's `Request`). In your own domain code it is rarely what you want.

> **How to say it in an interview:** "I use interfaces for contracts that classes implement, and type aliases for unions and computed types. Functionally they are close; the real differences are unions, which only `type` supports, and declaration merging, which only `interface` does."
