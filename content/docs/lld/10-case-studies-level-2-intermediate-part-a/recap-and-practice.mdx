## Chapter Recap

Six intermediate problems, one common theme: **put a seam in the right place and the follow-up is a 10-line addition**.

| Problem | The seam | The follow-up it absorbs |
|---------|----------|--------------------------|
| Splitwise | `SplitStrategy` + `SplitStrategyRegistry` | New split type (SHARES, etc.) |
| Rate Limiter | `RateLimiter` interface + `LimiterFactory` | New algorithm (Fixed Window, GCRA, …) |
| Cache | `EvictionPolicy` interface + injected policy | LFU → ARC, new eviction strategy |
| Elevator | `DispatchStrategy` interface | SCAN → LOOK → Nearest-Car |
| Meeting Room | `RoomSelectionStrategy` | Best-fit → greenest-floor, VIP priority |
| Snake | `FoodSource` + `GrowthPolicy` | Random food, grow-by-N-on-every-Kth |

The implementation rules are the same across all six:

1. **Money is integer paise; percentages are basis points.** No floats in a ledger.
2. **Inject time (`Clock`), randomness (`FoodSource`), and IDs (`IdGenerator`).** Everything deterministic.
3. **Validate before mutating.** A half-applied expense or a half-booked meeting is worse than a clean rejection.
4. **Name what you reject.** `ValidationError: Percentages add up to 90, expected 100` is ten times faster to debug than an uncaught NaN.
5. **Separate data from behaviour.** `Expense` stores what happened; `SplitStrategy` computes it. `Booking` stores the slot; `RoomCalendar` protects it.

## Practice Exercises

1. **Splitwise — SHARE split.** Add a `SHARES` type (e.g. Alice:2, Bob:1, Chetan:1 means 50%/25%/25%). Write `ShareSplitStrategy`, register it, add three test cases (exact divisible, indivisible with remainder, all shares zero except one).

2. **Rate Limiter — GCRA.** Implement Generic Cell Rate Algorithm as a new `RateLimiter`. It needs `emissionInterval = windowMs / limit` and a `tat` (theoretical arrival time) per key. No existing code should change. Verify it with a deterministic fake clock.

3. **Cache — LFU eviction.** The existing `LFUPolicy` removes the least-frequently-used item; ties broken by LRU. Draw the frequency-bucket linked list before writing a single line of code. Then benchmark `get` and `put` against `LRUPolicy` with 10 000 random operations — both should be O(1).

4. **Elevator — priority requests.** Add `priority: 'NORMAL' | 'EMERGENCY'` to `ElevatorRequest`. Emergency requests jump to the front of the queue. Change only `RequestQueue`; no other class should change.

5. **Meeting Room — "find the next free slot".** Given a list of attendees and a required duration, return the earliest `[start, end]` window where all attendees are free and a room of sufficient capacity is available. Use a merge-intervals approach on the union of all busy periods.

6. **Snake — wrap-around board.** Change `SnakeGame` so that moving off the right edge reappears on the left, and off the bottom reappears on the top. The change should touch only the `step` function (or the inBounds logic). All other code, including tests, should pass unchanged.
