title: "15. Frontend LLD in TypeScript"
---

The classic LLD problems (parking lot, elevator, splitwise) come from backend interviews. When the role is **frontend-heavy**, as it is at Angel One, Atlassian, Swiggy, Flipkart and Razorpay, the "low-level design" round looks different. You are rarely asked to model a hotel. More often you are asked to design **the engine behind a UI**: the event bus, the analytics client, the feature-flag service, the tree behind a file explorer, the store behind a dashboard.

This chapter works through nine of these engines. Each one is written as **framework-agnostic TypeScript**: plain classes with no DOM, which a React or Vue app would wrap in a thin hook. That split is the most important habit to show in the round, because it keeps the logic testable, lets you run it in a Node script (which is exactly what we do here), and keeps rendering as a separate concern.

**What you'll learn**

- How a frontend LLD round is scored compared with a backend one.
- API-first design: write the TypeScript interface before the class, and get the interviewer to agree on it.
- Modelling UI state explicitly (normalized trees, state machines, queues) instead of scattering booleans.
- Making time and I/O injectable (schedulers, transports, storage) so the code is deterministic and testable.
- Connecting any of these engines to React with `useSyncExternalStore`.

## How frontend LLD rounds differ

| Dimension | Backend LLD round | Frontend LLD round |
|---|---|---|
| Main artifact | Domain model (entities, services, repositories) | **Public API of a library or component**: what the caller types |
| State | Usually in a DB; in-memory maps for the round | Lives in the client: normalized, derived, subscribed to, sometimes persisted |
| Events | Domain events, queues | Listener lifecycles, unsubscribe handles, memory leaks, ordering |
| Concurrency | Threads, locks | **Async races**: stale responses, cancellation, debouncing, retries |
| Performance | Throughput, DB indexes | Re-render counts, memoized selectors, virtualization, bundle size |
| Testability | Mock repositories | Inject clocks, schedulers, storage, network; make every side effect a seam |
| Failure modes | Transactions, idempotency | Offline, flaky network, tab hidden or closed, a listener that throws |

Three rules cover most of the scoring:

1. **Start from the API.** Write `interface FeatureFlagClient { ... }` and a three-line usage example before you write any implementation. Interviewers at product companies care a lot about the developer experience of the thing you build.
2. **Keep time and I/O out of the core.** `Date.now()`, `setTimeout`, `fetch` and `localStorage` all go behind small interfaces. That one decision makes the code deterministic, lets it run on the server, and lets you test it without mocks.
3. **Everything that subscribes returns an unsubscribe function.** React's `useEffect` cleanup and `useSyncExternalStore` both depend on that contract.

## A shared toolkit you will see repeatedly

Every problem below is self-contained (each code ID compiles on its own), but the same small seams keep appearing:

```ts
// Illustrative: the three seams that make frontend engines testable.
interface Clock { now(): number }
interface Scheduler {
  setTimeout(fn: () => void, ms: number): number;
  clearTimeout(id: number): void;
}
type Unsubscribe = () => void;
```

A **fake scheduler** keeps a sorted list of pending callbacks and a virtual `now`. Calling `advance(ms)` runs everything that is due. Our demos use it instead of real timers, so they finish instantly and print the same output on every run.
