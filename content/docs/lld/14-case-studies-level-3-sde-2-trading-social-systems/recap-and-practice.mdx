## Chapter recap

| Section | Core problem | Data structures | Patterns |
|---------|-------------|-----------------|---------|
| 14.1 Order Matching Engine | Price-time priority matching | Max-heap (bids), min-heap (asks), FIFO queues at each price level | Observer (trades), Facade (Exchange), single-writer per symbol |
| 14.2 Brokerage Platform | Money-safe order placement with async exchange | State machine (order lifecycle), per-user promise queue | Chain of Responsibility (validation), Adapter (gateway), Observer (alerts), Strategy (alert conditions) |
| 14.3 Social Feed | Scalable personalised feed with celebrity accounts | Binary max-heap (k-way merge), hash sets (follower graph), bounded ring cache (fan-out) | Repository, Service layer, Strategy (ranker), Observer (feed updates) |

Three things a grader at a broker remembers:

1. **Money in integers.** Floats cannot represent ₹0.05 exactly. Store everything in paise, derive averages from totals, never store a computed average.
2. **Every reservation has an exit.** In 14.2 every path — reject, cancel, fill, timeout-then-not-found — explicitly releases or settles the blocked funds. Grep your code for every place you call `block()` and verify there is a matching `release()` or `settleBlocked()` on every exit path.
3. **Concurrency story.** Name the race, show it happening, fix it with one of: single-writer queue (14.1), per-key mutex (14.2), read-after-await (14.3). Say what the database equivalent is (`UPDATE ... WHERE available >= amt`, `SELECT ... FOR UPDATE`, `UNIQUE` constraint for idempotency).

## Practice exercises

**Exercise 1 (Angel One leaderboard).** Design a leaderboard that ranks all users by their total executed order value (buy + sell, in paise) for the current trading day. Support: `recordFill(userId, value)`, `topN(n)` (returns top N users with their rank and value), and `rank(userId)` (a specific user's current rank). Use a sorted structure that can update a user's score in O(log U) and answer `topN` in O(N). *Hint: a max-heap gives O(1) top-1, but arbitrary rank queries need a BST-style structure. A skip-list or a Fenwick tree over discretised scores both work. Discuss which you'd choose and why.*

**Exercise 2 (price alert at scale).** The current `AlertService` checks all alerts for a symbol on every tick in O(A) time. Redesign it so that "crosses above X" alerts for a symbol use a min-heap (sorted by threshold ascending): only alerts whose `threshold <= ltp` are dequeued in O(fired × log A) per tick. Mirror with a max-heap for "crosses below". Show that a quiet tick with no firings costs O(1) after the initial heap-peek check.

**Exercise 3 (GTT order).** A Good-Till-Triggered (GTT) order waits until the LTP satisfies a condition, then fires a limit or market order. Reuse `AlertCondition` (Strategy) for the trigger and `BrokerService.placeOrder` for the action. Add an `AlertAction` interface with two implementations: `NotifyAction` (the existing alert) and `PlaceOrderAction`. Show that the trigger is idempotent: using a deterministic `clientOrderId` derived from the GTT id means a double-trigger does not place a second order.

**Exercise 4 (FIFO cost basis for tax).** The weighted-average method in 14.2 is correct for margin calculations but not for capital-gains tax in India, which uses FIFO. Implement a `FifoCostBasis` class that maintains a queue of `{qty, pricePaise}` lots and computes the cost basis of a sell by draining the oldest lots first. Compare the realised P&L it produces against the weighted-average P&L for the same buy/sell sequence. *Example: buy 10 @ ₹100, buy 10 @ ₹120, sell 15. FIFO cost = 10 × ₹100 + 5 × ₹120 = ₹1,600; weighted-average cost = 15 × ₹110 = ₹1,650.*

**Exercise 5 (delete tweet with cache cleanup).** Extend the 14.3 social feed to support `deleteTweet(userId, tweetId)`. The deletion must (a) soft-delete in `TweetStore` so `byUser` filters it out, (b) scan the `FeedCache` of every warm follower and remove the entry, and (c) be idempotent (deleting an already-deleted tweet returns `false` gracefully, no error). Show that the pull feed returns correct results (deleted tweets never appear) while the hybrid feed's cache is repaired inline.
