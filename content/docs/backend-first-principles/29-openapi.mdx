## 1. The problem: three copies of the same knowledge 🎓

The lesson starts from the task-board project built in an earlier video. Its route table has about six routes. One handler, **move**, takes a JSON body with three fields (`taskId`, `to`, `actor`) and responds with different status codes depending on what happens downstream (service layer, repository, ...):
- **200** on success;
- **400 / 404** for validation or client errors (404 means the task doesn't exist);
- **500 / 502** when something goes wrong on the server side.

The React frontend **knows all of this**: the endpoint is `/api/move`, the body has those three fields, and 404 means "no such task". But where does that knowledge actually live? In **three places**:

1. the **backend handler**, the code that reads the body;
2. the **frontend's** `fetch` or axios call, the calling side;
3. a **document** an engineer wrote describing the API's requirements and behaviour.

<Mermaid chart={`flowchart TB
  K(("Knowledge about POST /api/move"))
  K --> H["Backend handler<br/>enforced: rejects bad bodies"]
  K --> F["Frontend fetch call<br/>enforced only at runtime"]
  K --> D["Wiki / markdown doc<br/>enforced by nothing"]
  H -.->|"rename to as column"| H2["updated"]
  F -.->|"updated, otherwise errors"| F2["updated"]
  D -.->|"nobody remembers"| D2["stale"]`} />

### How it goes wrong 🎓
1. A colleague renames the body field `to` to `column` because it reads better.
2. They update the **handler**. They update the **frontend**, because otherwise the backend's validation rejects the request.
3. The **document** enforces nothing, so they forget it.
4. Weeks later, a new engineer integrates the same endpoint on another page. They read the **document**, which claims to be the source of truth, rather than the handler, and send `to`.
5. **Validation error** from the backend.

**Root cause:** several copies of the truth with nothing keeping them in sync.

## 2. Why this only happens across the network 🎓

Inside one codebase this class of bug **can't survive compilation**. A Go function has a **signature** (argument types, return type). Change a struct field's name, or a type from string to integer, and **every call site fails to compile**. You find out during development, not in production.

Across an **HTTP boundary** there is **no signature**. The client builds a JSON string; the server parses it. A renamed field or changed type is only discovered **at runtime**, when a real request fails.

<Mermaid chart={`flowchart LR
  subgraph Local["Inside one codebase"]
    direction TB
    L1["moveTask(taskId, to, actor)"] --> L2["signature changes"] --> L3["compiler errors at every call site"]
  end
  subgraph Remote["Across the network"]
    direction TB
    R1["POST /api/move with JSON"] --> R2["field renamed on server"] --> R3["nothing fails until a real request: 400 in prod"]
  end`} />

**The idea of the whole lesson:** give remote calls a **signature** too. Freeze, in one central and **machine-readable** document:
- which routes exist;
- each endpoint's **query parameters**, **path parameters** and **request body fields**, down to each field's **data type**;
- every **response** an endpoint can return.

Because it's machine-readable (not a text or markdown doc), tools can **enforce** it on both sides of the network. That specification is **OpenAPI**.

## 3. What an OpenAPI description is 🎓

An **OpenAPI description is just a file**, in **JSON or YAML** (both are fully supported). It lists every endpoint, and for each one describes its **inputs, outputs and behaviour**.

### Origin story 🎓
- **2010:** a startup called **Wordnik**, about **six engineers**, had an API. Customers wanted **client SDKs** in Python, PHP, JavaScript and others, each with documentation.
- **Tony Tam**, who started the specification, summed up the motivation: *we code faster than we can document.*
- **The idea:** the server **describes itself in a JSON file**, and separate programs read that file for different purposes: one renders **friendly, interactive docs**; another **generates client libraries** in any language. The file describes behaviour, not implementation, so it doesn't care which language consumes it. The only requirement is the **promise that the file is true** about the backend.
- **Why a format and not prose:** JSON or YAML can be parsed, searched, transformed and formatted by any program. Plain text can't.

### What one file gives you 🎓

| Benefit | What it means | Mechanism |
|---|---|---|
| **Documentation** | read-only, or **interactive** (Swagger UI, Scalar, ...): fill in a sample body, add a token, send the request, see the response | a renderer reads the file |
| **Client libraries** | ready-made functions to call the API, in any language, with no hand-written request code | a generator reads the file |
| **Server boilerplate** | interfaces or stubs you'd otherwise type out and keep in sync by hand | a generator reads the file |
| **Validation** | incoming query, path, header and body are checked automatically against the spec | middleware reads the file at startup |

The lesson calls it the most useful, most productive thing you can add to a codebase, for backend, frontend and infrastructure alike.

### The spec's own definition, in three parts 🎓
1. **Language-agnostic:** it doesn't matter if the server is Go, Node, Python, Java or PHP. It documents behaviour, requirements and outputs, not implementation.
2. **For humans and computers:** the same file produces interactive docs for people **and** is parsed by programs to generate code and validations with no human involved.
3. **Without source code, documentation or traffic inspection:** you don't need to read the backend, trust a possibly stale doc, or open the browser's network tab to learn how the API behaves. The file is enough.

## 4. Four names that get confused 🎓

| Name | What it is |
|---|---|
| **OpenAPI Specification (OAS)** | the **rules**: which fields exist and what they mean |
| **OpenAPI Description (OAD)** | **your file**, which must obey every rule of the OAS; usually `openapi.json` or `openapi.yaml` |
| **OpenAPI Initiative (OAI)** | the **organisation** that publishes and evolves the spec; part of the **Linux Foundation** |
| **Swagger** | the **old name** of the spec; today the name of a **family of tools**, notably Swagger UI |

So "the Swagger file" means the OpenAPI description, while "Swagger UI" means the tool that renders it into an interactive page.

**JSON vs YAML:** interchangeable, same features; pick whichever your tools support (most support both). Most people write YAML because it allows **comments**. 🔧 Strictly, YAML 1.2 is (nearly) a superset of JSON, so a JSON file is also valid YAML.

### Timeline 🎓
<Mermaid chart={`timeline

  2011 : Swagger 1.0 open-sourced
  2014 : Swagger 2.0, adoption grows

The 2017 and 2021 entries are 🔧 additions. **Version advice (🎓):** at recording time the latest is **3.2.0**, but people still write **3.1**, because most tools (docs renderers, client generators, type generators) only support 3.1 so far.

🔧 Why 3.0 → 3.1 matters: 3.1 makes the Schema Object **full JSON Schema (draft 2020-12)**. One visible change: nullable is written `type: [string, "null"]` instead of 3.0's `nullable: true`. Check which version each tool in your pipeline supports before you upgrade.

## 5. The document's structure 🎓

### 5.1 The smallest valid file
```yaml title="openapi.yaml"
openapi: 3.1.1          # version of the SPECIFICATION this file follows
info:
  title: Task Board API
  version: 1.0.0        # version of YOUR API (your own versioning)
paths: {}               # no endpoints yet
```

- `openapi` matters because many tools in use still only run on particular versions.
- **Two different versions:** `openapi` (the spec version, e.g. 3.1.1) vs `info.version` (your backend's API version, the route-versioning idea from the routing lesson).

### 5.2 Root fields
| Field | Required? | Purpose |
|---|---|---|
| `openapi` | **yes** | spec version |
| `info` | **yes** | title, version (plus description, contact, license) |
| `paths` / `components` / `webhooks` | **at least one** | the endpoints, reusable pieces, outbound callbacks |
| `servers` | no | **where** the API lives |
| `security` | no | auth requirements applied to every endpoint |
| `tags` | no | group endpoints in the docs |

### 5.3 `servers`
A **list**, because the same API runs in several places: local, staging, production. The demo uses `http://localhost:8080`. Endpoints are then written **relative** to the base URL, so you never repeat the host per endpoint.

### 5.4 `paths` and path items
- A **map**: each key is an endpoint path and **must start with `/`**.
- Each value is a **path item**: everything you can do at that address, **one entry per HTTP method** (`get`, `post`, `put`, `patch`, `delete`, and sometimes `head`, `options`, ...). In the demo, `/api/board` has `get` and `/api/move` has `post`.
- **Dynamic segments** use curly braces. To fetch one task by ID (the standard HTTP way is a **path parameter**, not a query parameter), the path is written `/api/tasks/{taskId}`, because the ID is only known when the client calls.

### 5.5 Operations
Each method under a path is an **operation**, with:
- `summary` (one line) and `description` (longer; **Markdown** allowed, e.g. tables);
- `tags`, so renderers can group, say, all task endpoints together;
- `operationId`: a **unique** name across the whole file. **Write it like a function name** (`getBoard`, `moveTask`), because generators turn it into a real function the client calls. Get this right and the generated client reads naturally.
- `parameters`, `requestBody`, `responses`.

### 5.6 Parameters
Inputs come in two kinds: **parameters** and the **request body**.

A parameter has a `name`, an `in` (its location), a `required` flag and a `schema`:

| `in` | Example |
|---|---|
| `path` | the `taskId` in `/api/tasks/{taskId}` |
| `query` | the demo's polling endpoint takes `since` (integer): the last sequence number the client has seen |
| `header` | the events (SSE) endpoint: the same value arrives as the `Last-Event-ID` header, sent by the **browser itself** when it reconnects to the stream |
| `cookie` | a session cookie |

**Path parameters are always required.** An optional path segment would mean two different URLs, so the spec forces `required: true`.

### 5.7 Request body
Used by `post`, `put` and `patch`. Described by `content`: a **map from media type to body shape**. The media type is the `Content-Type` label:
- `application/json`, the usual for JSON APIs;
- `multipart/form-data` for file uploads;
- `application/x-www-form-urlencoded` for classic HTML forms (less common in the SPA era, still valid).

Each media type has a `schema`. In the demo, **move** accepts JSON with `taskId` and `to` **required** (omit them and the backend errors) and `actor` **optional**, defaulting to `"guest"` on the server. The file describes the backend's behaviour without anyone reading the backend code.

### 5.8 Responses
Keyed by **status code, in quotes** (`"200"`). 2xx success, 3xx redirects, 4xx client errors, 5xx server errors, as in the HTTP lesson. Each response needs a `description` and usually `content` (media type + schema), same shape as the request body.

The demo's **move** lists four:
| Code | Meaning | Body |
|---|---|---|
| `200` | moved | the **event** object |
| `400` | invalid input | error |
| `404` | no task with that ID | error |
| `502` | the move **succeeded**, but publishing it to the **message bus** failed | error |

### 5.9 Schema objects
The part clients use the most: the **shape and types** of every field.
- `type`: `string`, `number`, `integer`, `boolean`, `array`, `object` or `null`;
- **objects**: string keys whose values are any type, including nested objects;
- **strings**: `minLength`, `maxLength`, `pattern`; `enum` for a fixed set (e.g. a status of `active`, `inactive` or `deleted`);
- **numbers**: `minimum`, `maximum`;
- **arrays**: `items`, itself a schema.

By composing these you can describe any data structure. There's also a section for **authentication** (security schemes: what token the client sends and how).

### 🔧 The task board, as a complete description

```yaml title="openapi.yaml"
openapi: 3.1.1
info:
  title: Task Board API
  version: 1.0.0
  contact: { name: Platform team, email: platform@example.com }
servers:
  - url: http://localhost:8080
  - url: https://api.example.com
tags:
  - name: board
  - name: tasks
security:
  - bearerAuth: []
paths:
  /api/board:
    get:
      operationId: getBoard
      summary: Get the whole board
      description: Returns every column with its tasks, in display order.
      tags: [board]
      responses:
        "200":
          description: The board
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Board" }
              example: { columns: [{ id: todo, tasks: [{ id: t1, title: Write spec }] }] }
  /api/tasks/{taskId}:
    get:
      operationId: getTask
      summary: Get one task
      description: Fetch a single task by id.
      tags: [tasks]
      parameters:
        - name: taskId
          in: path
          required: true                     # mandatory for path parameters
          schema: { type: string }
      responses:
        "200": { description: The task, content: { application/json: { schema: { $ref: "#/components/schemas/Task" } } } }
        "404": { $ref: "#/components/responses/NotFound" }
  /api/move:
    post:
      operationId: moveTask
      summary: Move a task to another column
      description: Moves the task and publishes a TaskMoved event to the bus.
      tags: [tasks]
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [taskId, to]
              additionalProperties: false      # reject unknown fields such as a stale "column"
              properties:
                taskId: { type: string, minLength: 1 }
                to: { type: string, enum: [todo, doing, done] }
                actor: { type: string, default: guest }
      responses:
        "200": { description: Task moved, content: { application/json: { schema: { $ref: "#/components/schemas/Event" } } } }
        "400": { $ref: "#/components/responses/BadRequest" }
        "404": { $ref: "#/components/responses/NotFound" }
        "502": { description: "Moved, but the event could not be published", content: { application/json: { schema: { $ref: "#/components/schemas/Error" } } } }
  /api/poll:
    get:
      operationId: pollEvents
      summary: Poll for events
      description: Returns events with a sequence number greater than since.
      tags: [board]
      parameters:
        - { name: since, in: query, required: false, schema: { type: integer, minimum: 0 } }
      responses:
        "200": { description: New events, content: { application/json: { schema: { type: array, items: { $ref: "#/components/schemas/Event" } } } } }
  /api/events:
    get:
      operationId: streamEvents
      summary: Server-sent event stream
      description: SSE stream; on reconnect the browser sends Last-Event-ID.
      tags: [board]
      parameters:
        - { name: Last-Event-ID, in: header, required: false, schema: { type: string } }
      responses:
        "200": { description: Event stream, content: { text/event-stream: { schema: { type: string } } } }
components:
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }
  schemas:
    Task:
      type: object
      required: [id, title]
      properties: { id: { type: string }, title: { type: string, maxLength: 200 } }
    Board:
      type: object
      required: [columns]
      properties:
        columns:
          type: array
          items:
            type: object
            required: [id, tasks]
            properties: { id: { type: string }, tasks: { type: array, items: { $ref: "#/components/schemas/Task" } } }
    Event:
      type: object
      required: [seq, type, taskId, to, actor]
      properties:
        seq: { type: integer }
        type: { type: string, enum: [TaskMoved] }
        taskId: { type: string }
        to: { type: string }
        actor: { type: string }
    Error:
      type: object
      required: [code, message]
      properties: { code: { type: string }, message: { type: string } }
  responses:
    BadRequest: { description: Invalid input, content: { application/json: { schema: { $ref: "#/components/schemas/Error" } } } }
    NotFound: { description: Task not found, content: { application/json: { schema: { $ref: "#/components/schemas/Error" } } } }
```

Engineering notes: `components` plus `$ref` keeps one definition per shape, so `Event` can't drift between endpoints. `additionalProperties: false` makes the "renamed field" bug from section 1 fail loudly at validation instead of being silently ignored.

### 5.10 Designing reusable schemas ➕

The example above already uses `components` and `$ref`. Once a spec grows past a few endpoints, *how* you split and reuse schemas decides whether it stays readable and whether generated code is pleasant to use.

#### One schema for reading and writing: `readOnly` and `writeOnly` ➕
**Problem.** `Task` has an `id` and `createdAt` the server assigns. If the create endpoint reuses `Task` as its request body, the spec says clients must send `id`, and the generated client type forces them to invent one. If you make `id` optional instead, every response type now says `id` might be missing.

**Why it happens.** The same resource has different shapes in different directions: the server fills some fields, and some fields (a password) go in but never come out.

**Mechanism.** Either mark direction-specific fields, or split the schema.
- `readOnly: true` means the field is relevant only in responses and **should not** be sent in requests; `writeOnly: true` means the opposite. One schema, and tools that honour these flags (validators, some generators) treat each direction correctly.
- **Separate schemas** (`TaskCreate`, `Task`) are more explicit and are understood by every tool. Many teams prefer this for anything non-trivial.

```yaml
components:
  schemas:
    TaskCreate:
      type: object
      required: [title]
      additionalProperties: false
      properties:
        title: { type: string, maxLength: 200 }
        column: { type: string, enum: [todo, doing, done], default: todo }
    Task:
      allOf:
        - $ref: "#/components/schemas/TaskCreate"
        - type: object
          required: [id, createdAt]
          properties:
            id: { type: string, readOnly: true }
            createdAt: { type: string, format: date-time, readOnly: true }
```

**Edge cases.** Generator support for `readOnly` and `writeOnly` varies: some generate one type and ignore the flags. Check what your client generator actually emits before relying on them; that's a reason to prefer separate schemas.

#### The `allOf` plus `additionalProperties: false` trap ➕
**Problem.** The `Task` above composes `TaskCreate`, which has `additionalProperties: false`. Every `Task` response now **fails validation**, because `id` and `createdAt` are "additional" from `TaskCreate`'s point of view.

**Why it happens.** `allOf` validates the instance against **each** subschema independently. `additionalProperties` only knows about the `properties` declared **in its own subschema**; it cannot see the properties added by the sibling.

**Mechanism.** In OpenAPI 3.1 (JSON Schema 2020-12), use **`unevaluatedProperties: false` on the composed schema** instead. It considers every property evaluated by any subschema, so it rejects only fields that no part of the composition declared.

```yaml
TaskBase:                          # no additionalProperties here
  type: object
  properties: { title: { type: string } }
Task:
  allOf:
    - $ref: "#/components/schemas/TaskBase"
    - type: object
      properties: { id: { type: string } }
  unevaluatedProperties: false     # rejects anything that is neither title nor id
```

**Edge cases.** `unevaluatedProperties` is a 3.1 feature; tools still on 3.0 ignore it or reject the file. Check your validator and generators, as with every 3.1 feature (section 4).

#### Splitting a large spec into files ➕
**Problem.** A 6,000-line `openapi.yaml` causes merge conflicts on every PR and nobody can find anything.

**Mechanism.** `$ref` can point to other files (`$ref: "./schemas/task.yaml"`), so each resource lives in its own file. Many tools want a **single file**, so CI **bundles** the pieces into one artifact that everything downstream consumes.

```bash
npx @redocly/cli bundle openapi/root.yaml -o dist/openapi.yaml   # resolves external $refs into one file
npx @stoplight/spectral-cli lint dist/openapi.yaml
```

**Edge cases.** Relative `$ref` paths resolve against the **referencing file's** location, not the root; moving a file breaks its references. Lint the bundled output, since that's what clients and generators see.

### 5.11 Polymorphism: `oneOf`, `anyOf` and `discriminator` ➕

Real APIs return "one of several shapes": a payment method that is a card or a bank account, an event that is `TaskMoved` or `TaskDeleted`. JSON Schema has keywords for this, and they are a common source of spec bugs.

#### `oneOf` means exactly one ➕
**Problem.** A `PaymentMethod` is `oneOf: [Card, BankAccount]`, and both variants list only optional properties. A payload such as `{ "nickname": "work" }` validates against **both** schemas, so validation fails with "matches more than one", even though the payload looks fine.

**Why it happens.** `oneOf` requires the instance to match **exactly one** subschema. Without `additionalProperties: false` or a distinguishing required field, objects match many schemas at once, because JSON Schema objects accept extra and missing optional fields by default. `anyOf` means **at least one** and doesn't have this problem, but it also doesn't tell a reader which variant they have.

**Mechanism.** Make the variants **mutually exclusive** with a required constant field (a tag), then `oneOf` works and is cheap to check.

```yaml
components:
  schemas:
    Card:
      type: object
      required: [type, last4]
      properties:
        type: { const: card }
        last4: { type: string, pattern: "^[0-9]{4}$" }
    BankAccount:
      type: object
      required: [type, iban]
      properties:
        type: { const: bank_account }
        iban: { type: string }
    PaymentMethod:
      oneOf:
        - $ref: "#/components/schemas/Card"
        - $ref: "#/components/schemas/BankAccount"
      discriminator:
        propertyName: type
        mapping:
          card: "#/components/schemas/Card"
          bank_account: "#/components/schemas/BankAccount"
```

#### `discriminator` is a hint, not a rule ➕
**Problem.** A team adds `discriminator` and assumes it makes validation pick the right variant. A payload `{ "type": "card" }` (missing `last4`) is rejected, but the error lists failures from **every** variant (`last4` missing, `type` must be `bank_account`, `iban` missing), which confuses whoever reads it.

**Why it happens.** In OpenAPI, `discriminator` is an **annotation** that tells tools which property selects the variant. Validation still follows `oneOf`'s rules; the discriminator doesn't change the result. Its real value is for **code generators** (to emit a tagged union or a class hierarchy) and for clearer error messages in tools that use it.

**Mechanism.** Use both together: `const` tags on each variant make validation correct, and `discriminator` with an explicit `mapping` makes generated code correct. In TypeScript the result is a union you can narrow with a `switch` on `type`.

**Edge cases.**
- Generator support for `discriminator` and nested `oneOf` is the least consistent area of OpenAPI tooling; generate a client and read the output before you commit to a design.
- **Adding a variant is a breaking change for clients** that switch exhaustively on the tag (see section 8's versioning policy). Document that unknown variants may appear and must be ignored or handled generically.

### 5.12 Security schemes in depth ➕

The lesson mentions that the spec has an authentication section; the example declares one bearer scheme for everything. Real APIs mix public and protected endpoints, several credential types and scopes, and the spec only *documents* all of it unless you wire it to enforcement.

#### Scheme types and per-operation overrides ➕
**Problem.** The root-level `security: [bearerAuth: []]` applies to **every** operation, including a public health check and the login endpoint. The docs show a lock icon on login, and generated clients demand a token to log in.

**Mechanism.** Declare every scheme once in `components.securitySchemes`, set a default at the root, and **override per operation**. An empty array `security: []` marks an operation as public. A list means *any one of* these schemes works; several schemes inside one object mean *all of them together*.

```yaml
components:
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }
    apiKey:     { type: apiKey, in: header, name: X-API-Key }       # server-to-server integrations
    oauth:
      type: oauth2
      flows:
        authorizationCode:
          authorizationUrl: https://auth.example.com/authorize
          tokenUrl: https://auth.example.com/token
          scopes: { "tasks:read": Read tasks, "tasks:write": Create and move tasks }
security:
  - bearerAuth: []
paths:
  /api/login:
    post:
      operationId: login
      security: []                          # public
  /api/move:
    post:
      operationId: moveTask
      security:
        - oauth: ["tasks:write"]            # either an OAuth token with this scope
        - apiKey: []                        # or an API key
```

The available types in 3.1 are `apiKey`, `http` (bearer, basic), `oauth2`, `openIdConnect` and `mutualTLS`.

#### Documented is not enforced ➕
**Problem.** The spec says `/api/move` needs `tasks:write`. The handler only checks that *some* valid token is present. Docs and reality now disagree on the most important property of the endpoint.

**Why it happens.** Security schemes are descriptive metadata. Nothing in OpenAPI checks tokens; your auth middleware does, and it can drift from the spec like any other copy of the truth (section 1).

**Mechanism.** Drive enforcement from the spec. express-openapi-validator can call your handlers for each scheme an operation requires, passing the required scopes, so the spec becomes the single source for "who may call this".

```ts title="server.ts (security from the spec)"
app.use(OpenApiValidator.middleware({
  apiSpec: './openapi.yaml',
  validateRequests: true,
  validateSecurity: {
    handlers: {
      bearerAuth: async (req) => Boolean(await verifyJwt(req.headers.authorization)),
      oauth: async (req, scopes) => {
        const token = await verifyJwt(req.headers.authorization);
        return scopes.every(s => token.scope.split(' ').includes(s));    // scopes come from the spec
      },
      apiKey: async (req) => apiKeys.isValid(req.header('x-api-key')),
    },
  },
}));
```

**Edge cases.** Spec-driven checks cover **authentication and scopes**, not object-level authorisation ("may this user move *this* task?"), which still lives in the service layer (see [08-authentication-authorization](/docs/backend-first-principles/08-authentication-authorization)). Never put real credentials in `example` values; the spec is usually published.

## 6. Code-first vs design-first 🎓

If this file is the contract between server and client code, which comes first?

<Mermaid chart={`flowchart LR
  subgraph CF["Code-first"]
    direction TB
    C1["Write handlers + types"] --> C2["Annotations, comments or schemas in code"] --> C3["Generate openapi.json"] --> C4["Docs + clients"]
  end
  subgraph DF["Design-first (contract-first)"]
    direction TB
    D1["Write openapi.yaml"] --> D2["Review + lint"] --> D3["Backend implements<br/>generated interface"]
    D2 --> D4["Frontend builds on<br/>mock + generated client"]
  end`} />

- **Code-first:** write the handlers and services first; the OpenAPI file is **derived from the code** via annotations, comments above handlers, or the types themselves. The file is a **by-product**.
- **Design-first (contract-first):** write the description **before** the implementation. Then build the backend, and build client code, mocks and tests from the spec. **The contract is the source of truth.**

**History:** the Swagger team started code-first, because they already had a server and wanted the file derived from it. They later concluded contract-first makes more sense (the lesson points to a 2013 talk on this).

**The author's own practice:** existing codebases got OpenAPI added code-first (for interactive testing or client generation). Almost every **new** project has gone **contract-first**, because:
- once the contract is agreed, **frontend and backend start in parallel**; nobody waits for the backend to finish;
- in the **agentic era** it fits well: agree the contract with your AI agent, then run **two agents in parallel**, one on the server and one on the client, without blocking each other.

## 7. Code-first in practice 🎓

**The demo (the "Tasker" app from the Go series):**
1. **Zod schemas** define the shapes, in a structured, code-first way.
2. A **ts-rest contract** attaches those schemas to paths and methods.
3. A **generator** takes the contract and produces `openapi.json`.
4. The **Go server serves** that file for interactive docs.

Nobody writes `openapi.json` by hand. That's why the lesson doesn't go through every spec feature: with libraries like ts-rest you only need to think about **three things**: the **path**, the **inputs** (query, body, path params, headers) and the **responses** (schema and status code). And it's plain JavaScript (JSON Schema or zod, which is even shorter).

This differs from the "comments above the handler" style of code-first. The author prefers schemas in **code** over comments: code is easier to maintain and much harder to let drift. **FastAPI** (Python) is another example: the framework reads the handler code and type annotations, generates `openapi.json` and serves it, with no separate comments.

🔧 **The ts-rest version:**

```ts title="contract.ts"
import { initContract } from '@ts-rest/core';
import { z } from 'zod';

const c = initContract();

export const Event = z.object({ seq: z.number().int(), type: z.literal('TaskMoved'), taskId: z.string(), to: z.string(), actor: z.string() });
const ApiError = z.object({ code: z.string(), message: z.string() });

export const contract = c.router({
  moveTask: {                                   // key becomes the operationId
    method: 'POST',
    path: '/api/move',
    body: z.object({
      taskId: z.string().min(1),
      to: z.enum(['todo', 'doing', 'done']),
      actor: z.string().default('guest'),
    }).strict(),
    responses: { 200: Event, 400: ApiError, 404: ApiError, 502: ApiError },
    summary: 'Move a task to another column',
  },
});
```

```ts title="generate-openapi.ts"
import { generateOpenApi } from '@ts-rest/open-api';
import { writeFileSync } from 'node:fs';
import { contract } from './contract';

const doc = generateOpenApi(contract, { info: { title: 'Task Board API', version: '1.0.0' } });
writeFileSync('openapi.json', JSON.stringify(doc, null, 2));
```

🔧 **NestJS code-first** is the decorator flavour: `@nestjs/swagger` reads DTO classes and `@ApiProperty`, `@ApiResponse`, `@ApiOperation({ operationId })` decorators, and `SwaggerModule.createDocument(app, config)` builds the document at startup. The risk is the one the lesson names: decorators are metadata next to the code, and nothing stops a decorator from disagreeing with what the handler actually returns. Typed contracts like ts-rest close that gap because the handler's return type is checked against the declared responses.

## 8. The design-first pipeline 🎓

The task board from the real-time lesson has no OpenAPI description yet. It's small and new, a good case for going design-first and making it the team's habit. One file feeds every stage.

<Mermaid chart={`flowchart LR
  F[("openapi.yaml<br/>single source of truth")] --> L["Stage 1: Lint<br/>Spectral"]
  L --> M["Stage 2: Mock server<br/>Prism"]
  L --> CL["Stage 3: Client types + calls<br/>openapi-typescript + openapi-fetch"]
  L --> SV["Stage 4: Server interfaces<br/>oapi-codegen (Go)"]
  L --> DOC["Stage 5: Docs<br/>Swagger UI, Redoc, Scalar"]
  SV --> RS["Running server"]
  F --> CT["Contract tests<br/>Schemathesis"]
  CT -->|"generated valid + invalid requests"| RS
  RS -->|"responses checked against the spec"| CT`} />

### Stage 1: lint (Spectral) 🎓
Like ESLint for code. **Spectral** knows the OpenAPI rules and flags mistakes: missing descriptions, operations without `operationId`, responses without a schema. **What the demo shows:** the first run reports **three problems** (no `contact` in `info`, two operations with no description); after fixing them, it passes.

```yaml title=".spectral.yaml"
extends: ["spectral:oas"]
rules:
  operation-description: error      # promote from warning so CI fails
  info-contact: error
  operation-operationId: error
```

```bash
npx @stoplight/spectral-cli lint openapi.yaml
```

### Stage 2: mock server (Prism) 🎓
**Prism** reads the spec and runs a **fake server** that answers every documented endpoint with the **examples written in the file**, before any backend code exists. A separate frontend team can build against the mock while the backend team writes handlers. **The demo:** calling the board endpoint returns exactly the example from the file; the move operation accepts bodies matching the documented schema.

```bash
npx @stoplight/prism-cli mock openapi.yaml      # serves on http://127.0.0.1:4010
curl -X POST localhost:4010/api/move -H 'content-type: application/json' -d '{"taskId":"t1"}'
# missing required "to": Prism rejects it with a validation error, like the real server will
```

### Mocks a frontend team can actually build on ➕

A mock that only returns one happy-path example lets the frontend build the happy path. The error states, empty states and edge cases are where most UI work goes, and they need the mock's help too.

#### Named examples for every state the UI must handle ➕
**Problem.** The board screen has to render an empty board, a board with 500 tasks and a task with a 200-character title. The single `example` in the spec covers none of these, so the frontend team hard-codes fixtures that drift from the spec.

**Mechanism.** Use the `examples` map (plural) on a media type: several **named** examples, each a realistic state. Prism returns the first one by default and a specific one when the request sends `Prefer: example=<name>`.

```yaml
responses:
  "200":
    description: The board
    content:
      application/json:
        schema: { $ref: "#/components/schemas/Board" }
        examples:
          typical: { value: { columns: [{ id: todo, tasks: [{ id: t1, title: Write spec }] }] } }
          empty:   { value: { columns: [{ id: todo, tasks: [] }, { id: doing, tasks: [] }, { id: done, tasks: [] }] } }
```

```bash
curl localhost:4010/api/board -H 'Prefer: example=empty'
```

#### Forcing error responses and random data ➕
**Problem.** The frontend needs to see what the UI does on a 404 or a 502, but the mock always answers 200.

**Mechanism.** Prism picks the response by the `Prefer` header too: `Prefer: code=404` returns the documented 404 response, which is one more reason to document every status code with a schema and example (section 5.8). For robustness testing, **dynamic mode** (`prism mock -d`, or `Prefer: dynamic=true` per request) generates random data that matches the schema, which quickly finds UI code that assumes short strings or non-empty arrays.

```tsx title="board.test.tsx (frontend, against the mock)"
const notFound = await fetch('http://127.0.0.1:4010/api/tasks/t-missing', { headers: { Prefer: 'code=404' } });
expect(notFound.status).toBe(404);
render(<TaskPage response={notFound} />);   // the UI's "task no longer exists" state, built before the backend exists
```

#### Keeping examples honest ➕
**Problem.** Someone renames a field in the schema and forgets the examples. The mock now returns data the real API never will, and the frontend builds against it.

**Mechanism.** Lint examples against their schemas. Spectral's built-in OpenAPI ruleset includes rules that check that examples are valid for their schema (`oas3-valid-media-example`, `oas3-valid-schema-example`); keep them at `error` severity in CI.

```yaml title=".spectral.yaml (addition)"
rules:
  oas3-valid-media-example: error
  oas3-valid-schema-example: error
```

**Edge cases.** A mock validates requests against the spec but has no business logic: moving a task doesn't change what the board endpoint returns next. For stateful flows, frontend teams usually combine the mock with a small hand-written handler layer (for example MSW in the browser) that uses the generated types.

### Stage 3: the client (openapi-typescript + openapi-fetch) 🎓
**openapi-typescript** converts the spec into **TypeScript types** that know every path, field, type and condition; **openapi-fetch** makes the actual calls using those types. Misspell a field or pass the wrong type and the **compiler** catches it. That's the "signature across the network" from section 2.

```bash
npx openapi-typescript openapi.yaml -o src/api/schema.d.ts
```

```ts title="board-client.ts"
import createClient from 'openapi-fetch';
import type { paths } from './api/schema';

const api = createClient<paths>({ baseUrl: import.meta.env.VITE_API_URL });

const { data, error, response } = await api.POST('/api/move', {
  body: { taskId: 't1', to: 'done' },          // body: { taskId, column } would be a COMPILE error
});
if (error) {
  if (response.status === 404) showToast('That task no longer exists');
  else throw new Error(error.message);         // error is typed as the Error schema
} else {
  applyEvent(data);                            // data is typed as Event
}
```

The section 1 bug becomes a build failure: when the spec renames `to` to `column` and types are regenerated, every call still sending `to` stops compiling.

### Publishing SDKs and keeping them in sync ➕

Generating types inside the frontend repo works when one team owns both sides. When **other** teams or external customers consume the API, the generated client becomes a published package, and keeping it in sync becomes a release process.

#### Where generated code lives ➕
**Problem.** Three consumer services each run the generator themselves, with different generator versions and options. The "same" client has three different shapes, and a spec change breaks them at different times.

**Why it happens.** Generation is a build step with inputs (spec, generator version, config). If each consumer controls those inputs, each gets a different output.

**Mechanism.** Generate **once, centrally**, from the bundled spec, and publish the result as a versioned package (`@taskboard/api-client`). Consumers depend on a version, like any library. For polyglot consumers, **openapi-generator** produces clients for many languages from the same file; pin its version and keep its config in the repo.

```yaml title=".github/workflows/sdk.yml (excerpt)"
on: { push: { branches: [main], paths: ["openapi/**"] } }
jobs:
  publish-ts-sdk:
    steps:
      - run: npx @redocly/cli bundle openapi/root.yaml -o dist/openapi.yaml
      - run: npx openapi-typescript dist/openapi.yaml -o sdk/ts/src/schema.d.ts
      - run: npm version "$(yq '.info.version' dist/openapi.yaml)" --no-git-tag-version --prefix sdk/ts
      - run: npm publish --prefix sdk/ts
```

#### Versioning the SDK with the API ➕
**Problem.** The spec gained a required field, and the SDK was published as a patch release. Every consumer on a `^1.4.0` range upgraded automatically and broke.

**Mechanism.** Derive the SDK version from `info.version` and follow semantic versioning **for the API contract**: a breaking spec change (as detected by `oasdiff breaking` in the CI section below) must bump the major version; additive changes bump the minor. The CI step can enforce this by failing when the diff is breaking but the major version didn't change.

**Edge cases.** The SDK also has breaking changes that the spec doesn't show: a generator upgrade that renames functions, or a changed `operationId`. Treat `operationId` renames as breaking for SDK users even though the HTTP API is unchanged.

### Stage 4: the server (oapi-codegen for Go) 🎓
**oapi-codegen** turns the spec into **Go interfaces**; your handlers must **satisfy** them. That enforces the documented behaviour on the server. **The demo:** add a field to the file, regenerate, and the **build fails at the handler** because it no longer matches the contract.

```bash
go run github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen \
  -generate types,std-http-server -package api -o internal/api/api.gen.go openapi.yaml
```

🔧 **The same in Node:** type the handlers from the generated types, and validate at runtime from the same file, so both compile-time and runtime follow the contract.

```ts title="server.ts"
import express from 'express';
import * as OpenApiValidator from 'express-openapi-validator';
import type { operations } from './api/schema';

type MoveBody = operations['moveTask']['requestBody']['content']['application/json'];
type MoveOk = operations['moveTask']['responses']['200']['content']['application/json'];

const app = express();
app.use(express.json());
app.use(OpenApiValidator.middleware({
  apiSpec: './openapi.yaml',
  validateRequests: true,                       // 400 for bodies, params and headers that break the spec
  validateResponses: process.env.NODE_ENV !== 'production', // catch server drift in dev and CI
}));

app.post('/api/move', async (req, res) => {
  const body = req.body as MoveBody;            // already validated against the schema
  const event: MoveOk = await moveTask(body.taskId, body.to, body.actor ?? 'guest');
  res.json(event);
});
```

### Stage 5: docs (Swagger UI, Redoc, Scalar) 🎓
Render the **same file** three ways: **Swagger UI** (the classic interactive docs, with *Try it out*), **Redoc** (another layout), **Scalar** (interactive, with a modern, clean UI; the author's personal choice).

```ts
import swaggerUi from 'swagger-ui-express';
import YAML from 'yaml';
import { readFileSync } from 'node:fs';
const spec = YAML.parse(readFileSync('openapi.yaml', 'utf8'));
app.get('/openapi.json', (_req, res) => res.json(spec));
app.use('/docs', swaggerUi.serve, swaggerUi.setup(spec));
```

### Verifying the server really matches (Schemathesis) 🎓
Generated interfaces prove the handler **signatures** match; they don't prove the **behaviour** does (a handler can still return 500 for an input the spec allows, or a body missing a required field). **Schemathesis** reads the file, **generates requests** from the schemas, both **valid and invalid**, sends them to the **real server**, and checks every response against the contract. Mismatches are flagged. **The demo:** it generates requests for every schema and validates every response.

```bash
schemathesis run openapi.yaml --url http://localhost:8080
```

### The whole pipeline, one more time 🎓
Write the spec (by hand, or in code with ts-rest and generate it) → **lint** → **mock** → **generate client** → **generate server interfaces** → **test the server against the contract** → **render docs**. One file, a single source of truth, at every stage.

### 🔧 Wiring it into CI
The pipeline only protects you if it runs on every change:

```yaml title=".github/workflows/api-contract.yml (excerpt)"
- run: npx @stoplight/spectral-cli lint openapi.yaml
- run: npx openapi-typescript openapi.yaml -o src/api/schema.d.ts && git diff --exit-code src/api/schema.d.ts
- run: npx tsc --noEmit                                    # clients that drifted fail here
- run: oasdiff breaking origin-main-openapi.yaml openapi.yaml --fail-on ERR   # block breaking changes
- run: schemathesis run openapi.yaml --url http://localhost:8080
```

`oasdiff breaking` catches what the section 1 story really was: renaming a required field is a **breaking change** for existing clients. Additive changes (new optional field, new endpoint) are safe; renames, removals, new required inputs and narrowed types are not. For a public API, ship them as a new version or keep the old field during a deprecation window.

### Versioning and the breaking-change policy ➕

The CI step blocks breaking changes. A team also needs a written answer to the next questions: what counts as breaking for *our* clients, and how do we retire something when we must?

#### "Additive is safe" has exceptions ➕
**Problem.** A new value `archived` is added to the `to` enum in responses. No field was removed, the diff tool doesn't block it, and the mobile app crashes on its exhaustive `switch`.

**Why it happens.** Whether a change breaks a client depends on what the client **assumes**, not only on the schema. The usual exceptions to "additive is safe":
- **new enum values or `oneOf` variants in responses** break clients that handle every case and treat unknown values as errors;
- **new response fields** break clients that validate responses strictly (`additionalProperties: false` on the client side);
- **new optional request fields with server-side defaults** change behaviour for old clients that never send them.

**Mechanism.** State the policy in the spec's `info.description` and in client guidelines: clients must be **tolerant readers** (ignore unknown fields, map unknown enum values to an "other" case). Then test that your own generated clients actually behave that way, and configure the diff tool to treat response enum additions as at least a warning that needs review.

#### Deprecation as a lifecycle, not a deletion ➕
**Problem.** A field or endpoint must go. Removing it immediately breaks whoever still uses it; keeping it forever accumulates dead weight.

**Mechanism.** Run each removal through stages that are visible both in the spec and on the wire:

<Mermaid chart={`flowchart LR
  A["Mark deprecated: true<br/>in the spec"] --> B["Send Deprecation +<br/>Sunset headers"]
  B --> C["Measure usage<br/>per client"]
  C --> D["Contact remaining<br/>callers"]
  D --> E["After the sunset date:<br/>remove, return 410"]`} />

1. **In the spec**: `deprecated: true` on the operation, parameter or schema property. Docs renderers strike it through, and generated clients add `@deprecated` so editors warn the developer.
2. **On the wire**: the `Deprecation` header (RFC 9745, a structured date such as `Deprecation: @1767225599`) says it's deprecated, and the `Sunset` header (RFC 8594, an HTTP date) says when it will stop working. RFC 9745 requires the sunset to be no earlier than the deprecation date.
3. **Measure**: log or count calls to deprecated operations per client (API key, user agent), so you know who must migrate.
4. **Remove** only after the sunset date and once usage is near zero.

```ts title="deprecation.ts (Express)"
export function deprecated(opts: { since: Date; sunset: Date; link: string }) {
  return (req, res, next) => {
    res.setHeader('Deprecation', `@${Math.floor(opts.since.getTime() / 1000)}`);
    res.setHeader('Sunset', opts.sunset.toUTCString());
    res.setHeader('Link', `<${opts.link}>; rel="deprecation"`);
    deprecatedCalls.inc({ route: req.route?.path, client: req.header('x-client-id') ?? 'unknown' });
    next();
  };
}
app.get('/api/poll', deprecated({ since: new Date('2026-07-01'), sunset: new Date('2027-01-01'), link: 'https://docs.example.com/migrate-to-sse' }), pollHandler);
```

#### Where the version number goes ➕
**Problem.** A breaking change can't be avoided (a resource is redesigned). Old and new clients must both work for months.

**Mechanism.** Keep `info.version` as semantic versioning of the contract, and expose **major** versions to clients as separate surfaces: `/v1` and `/v2` paths are the most common (URL versioning and its alternatives are compared in [11-rest-api-design](/docs/backend-first-principles/11-rest-api-design)). Each major version gets **its own OpenAPI document**, so `oasdiff` compares v2 against v2, and v1's document is frozen apart from fixes.

**Edge cases.** Running two majors doubles the surface to test; share the service layer and keep version differences in thin controller and DTO mappings. Schema-based contract tests (Schemathesis) check the server against the spec; if you also need to know what **consumers** actually rely on, consumer-driven contract testing (Pact) records that from the client side, see [27-testing](/docs/backend-first-principles/27-testing).

## 9. Real-world use 🎓

- **Generate API clients** from the file.
- **Validate requests in API gateways** against the spec, before they reach your service.
- **Big platforms publish their OpenAPI files** so anyone can build on them. **GitHub's** is around **344,000 lines** and **Stripe's** around **171,000**, natural for platforms that size and age. This is what "OpenAPI is the standard" means: the industry agreed this is how backends are described.
- **AI agents:** when you give an agent a tool to call an API, an OpenAPI description tells it what endpoints exist and what they take and return.

### AsyncAPI: the same contract for events ➕

The task board doesn't only answer requests: **move** publishes a `TaskMoved` event to a message bus, and other services consume it. That event is an API too, with the same drift problem from section 1, and OpenAPI can't describe it.

#### Why OpenAPI stops at the request and response ➕
**Problem.** The billing service consumes `TaskMoved` from the bus. Someone renames `to` in the event payload, the HTTP spec and all its CI checks are green, and the billing consumer silently fails to parse every message.

**Why it happens.** OpenAPI's model is **request then response** over HTTP. A message bus has no request: a producer **sends** to a channel (topic, queue, subject) and any number of consumers **receive** from it, at some later time. Its `webhooks` field covers outgoing HTTP callbacks (see [30-webhooks](/docs/backend-first-principles/30-webhooks)), not Kafka topics, RabbitMQ queues or Redis streams.

**Mechanism.** **AsyncAPI** is a sibling specification for event-driven APIs, with a deliberately similar shape (`info`, `components`, JSON Schema payloads). In version 3.0, **channels** describe where messages flow and which messages they carry, and **operations** say whether this application `send`s or `receive`s on a channel.

```yaml title="asyncapi.yaml"
asyncapi: 3.0.0
info:
  title: Task Board events
  version: 1.0.0
channels:
  taskEvents:
    address: taskboard.task-events            # the topic or queue name on the broker
    messages:
      taskMoved:
        name: TaskMoved
        payload:
          $ref: "./openapi.yaml#/components/schemas/Event"   # one schema shared with the HTTP API
operations:
  publishTaskMoved:
    action: send                              # this service produces the event
    channel: { $ref: "#/channels/taskEvents" }
    messages:
      - $ref: "#/channels/taskEvents/messages/taskMoved"
```

#### Reusing one schema across both specs ➕
**Problem.** The `Event` shape is returned by `/api/poll` over HTTP and also published on the bus. Two copies would drift.

**Mechanism.** Reference the **same schema file** from both documents (as above), so the HTTP response and the bus message are guaranteed identical. The same tooling ideas then apply to events: lint the AsyncAPI file, generate typed producers and consumers, render docs, and run a breaking-change diff in CI.

**Edge cases.**
- An event's consumers are often unknown to the producer, and old messages may sit in a topic for days. Event schemas need **stricter** compatibility rules than HTTP: only additive changes, and consumers must tolerate unknown fields. A **schema registry** (with Kafka, for example) can reject incompatible schema versions at publish time.
- AsyncAPI tool support, like OpenAPI 3.1 support, lags the spec; check that your generators handle 3.0 before adopting it.

## 10. Recap 🎓

- Inside one codebase, the **compiler** enforces signatures. Across the **network boundary** there's no signature, so drift between handler, client and docs only shows up at runtime.
- **OpenAPI** fixes that: one machine-readable file describing every path, its inputs and outputs, field-level data types, and authentication.
- From that file you generate **client code, server interfaces, mocks, tests and docs**.
- **Names:** OAS = the rules, OAD = your file, OAI = the Linux Foundation organisation, Swagger = the old name and now a set of tools.
- **Structure:** `openapi` + `info` (+ at least one of `paths`, `components`, `webhooks`), `servers`, `security`, `tags`; operations with `operationId`, parameters (path, query, header, cookie), request bodies by media type, responses by quoted status code, schemas.
- **Code-first** derives the file from code; **design-first** writes the contract first so frontend and backend (or two agents) work in parallel. The author goes contract-first for new projects.
- **Design-first pipeline:** Spectral → Prism → openapi-typescript/openapi-fetch → oapi-codegen → Swagger UI/Redoc/Scalar, verified with Schemathesis.
- ➕ **Schema design:** separate create and read schemas (or `readOnly`/`writeOnly`), use `unevaluatedProperties: false` with `allOf` instead of `additionalProperties: false`, split large specs into files and bundle them in CI.
- ➕ **Polymorphism:** `oneOf` needs mutually exclusive variants (a `const` tag); `discriminator` helps generators but doesn't change validation.
- ➕ **Security schemes:** default at the root, override per operation (`security: []` for public), alternatives vs combinations, and enforce scopes from the spec so docs and auth can't drift.
- ➕ **Useful mocks:** named examples, `Prefer` headers for specific examples and error codes, dynamic mode, and linted examples.
- ➕ **SDKs:** generate once centrally, publish versioned packages, and tie the major version to breaking spec changes.
- ➕ **Versioning policy:** tolerant readers, care with enum and variant additions, deprecation through `deprecated: true` plus `Deprecation` and `Sunset` headers and usage tracking, one document per major version.
- ➕ **AsyncAPI** describes the event side (channels, send and receive operations) and can share schemas with the OpenAPI file.

## Interview questions

1. **Why do API contract bugs survive to production when function signature changes don't?** **The compiler checks call sites inside one codebase; across HTTP there's no signature, so mismatches only appear at runtime unless a shared machine-readable contract is enforced on both sides.**
2. **What's the difference between OAS, an OAD, the OAI and Swagger?** **OAS is the rules, an OAD is your file following them, the OAI is the Linux Foundation body maintaining the spec, Swagger is the old name and now a tool family (Swagger UI).**
3. **What are the minimum required fields of an OpenAPI 3.1 document?** **`openapi`, `info` (with `title` and `version`), and at least one of `paths`, `components` or `webhooks`.**
4. **What's the difference between `openapi` and `info.version`?** **The first is the spec version the file follows; the second is your API's own version.**
5. **Why should `operationId` look like a function name?** **Generators turn it into the client function name, and it must be unique across the file.**
6. **Why must path parameters be required?** **An optional path segment would describe two different URLs; the spec mandates `required: true`.**
7. **Code-first vs design-first, and when would you pick each?** **Code-first derives the spec from existing code (good for existing services). Design-first writes the contract first so frontend and backend work in parallel against mocks and generated code (good for new projects).**
8. **Generated server interfaces compile. How do you know the server behaves as the spec says?** **Contract testing: Schemathesis generates valid and invalid requests from the spec and checks real responses; plus response validation in dev and CI.**
9. **Which spec changes are breaking for clients?** **Removing or renaming fields or endpoints, adding required inputs, narrowing types or enums, changing response shapes. Adding optional fields or new endpoints is safe. Catch it in CI with a diff tool such as oasdiff.**
10. **Why do many teams still write 3.1 when 3.2 exists?** **Tool support: most docs renderers and generators only support 3.1 so far.**
11. ➕ **`Task` is `allOf` a base schema with `additionalProperties: false` plus an `id`. Why do valid responses fail validation, and what's the fix?** **Each `allOf` branch is validated alone, so the base rejects `id` as additional. Remove it from the base and put `unevaluatedProperties: false` on the composed schema (3.1).**
12. ➕ **Why can a valid-looking payload fail a `oneOf`, and does `discriminator` fix it?** **`oneOf` requires exactly one match, and loose variants overlap. Add a required `const` tag to make them exclusive. `discriminator` is a hint for tools; it doesn't change validation.**
13. ➕ **How do you mark one endpoint as public when the root requires a bearer token?** **Override with `security: []` on that operation.**
14. ➕ **The spec says an endpoint needs scope `tasks:write`. What guarantees the server checks it?** **Nothing in OpenAPI. Drive enforcement from the spec (for example express-openapi-validator security handlers) or test it, and keep object-level authorisation in the service layer.**
15. ➕ **How does a frontend team test error states against a Prism mock?** **Document each status with a schema and example, then send `Prefer: code=404` (or `example=name`, or use dynamic mode).**
16. ➕ **Adding an enum value to a response is "additive". Why can it still break clients?** **Clients that switch exhaustively or validate strictly reject unknown values. Require tolerant readers and review such changes.**
17. ➕ **How do you retire an endpoint safely?** **Mark it `deprecated: true`, send `Deprecation` and `Sunset` headers, measure usage per client, contact the remaining callers and remove it only after the sunset date.**
18. ➕ **Why doesn't OpenAPI describe your Kafka events, and what does?** **OpenAPI models HTTP request and response; events are sent to channels and received later by unknown consumers. AsyncAPI describes channels, messages and send or receive operations, and can reuse the same JSON Schemas.**
