## 1. The requirement every backend shares 🎓

### Problem
Imagine an HTTP server that can process **exactly one request at a time**. While it handles one user, a thousand other users either wait in line or get a "server busy" error. That cannot work for a real product.

### Why it matters to understand the mechanism
Every runtime (Node.js, Python, Go, Rust, Java) gives you some way to express "handle many things at once". They look different on the surface (`async`/`await`, threads, goroutines), but they rest on a small number of underlying mechanisms. Knowing them helps you:
- **debug** (why does one slow endpoint make every endpoint slow?),
- **structure** code (which calls can run side by side?),
- make **architecture** decisions (when to move work to a worker or a separate service).

## 2. What is the server doing while it waits? 🎓

### The scenario
A browser sends a request. Your server goes through routing, handler, service and repository layers, sends a **query to the database**, waits for the database to execute it, then sends the response back.

How long is that wait? The lesson's rough numbers for a simple query:

| Where the database is | Round trip for a simple query |
|---|---|
| Same machine (localhost) | about 1–2 ms |
| Different availability zone | about 20–30 ms |
| Different, far region | about 90–100 ms |

### The naive answer: nothing
If the server runs **synchronously** (line by line, no concurrency), then during those milliseconds the **CPU is idle**. It's just waiting for the database's network packets to arrive.

### Quantifying the waste
- A modern CPU executes roughly **3 billion instructions per second**, so about **3 million per millisecond**.
- Waiting **100 ms** idle means about **300 million instructions** that could have run, and **zero** did.

Now a realistic API call:

| Work | Count | Time |
|---|---|---|
| Network operations (3–5 DB queries, a Redis call, an email provider) | 5 | 5 × 50 ms = **250 ms waiting** |
| Actual CPU work (parsing, validation, building the response) | – | **about 10 ms** |

So the CPU and memory are idle roughly **95% of the request**. Across a typical backend, the lesson estimates **more than 70% of time is spent waiting on IO**.

### Vocabulary: IO
**IO (input/output)** is any operation where the CPU sends something out to a device or another system and waits for the answer: network calls (DB, cache, HTTP APIs), files, standard input/output (including logging to stdout), keyboard and display.

### The problem concurrency solves
**While one task waits on IO, use the CPU and memory for other tasks.** That's the whole point of concurrency.

## 3. Concurrency vs parallelism 🎓

### Parallelism
**Executing multiple instructions at the same instant.** One CPU core executes one instruction stream at a time, so parallelism **needs hardware support**: at least two cores for two simultaneous instructions.

### Concurrency
**Structuring a program so that many tasks can be started, paused and resumed**, so that they all make progress, even if only one runs at any instant. It works on **a single core**. It's about **structure**, not hardware.

> Parallelism is **doing** many things at once. Concurrency is **dealing with** many things at once.

### The lesson's timeline, one core
Requests A and B arrive together, and there is one core.

1. A gets the CPU first: validation, routing, JSON deserialization, about **5 ms**. B waits.
2. A sends a DB query and doesn't need the CPU, so the **scheduler** (OS or language runtime) gives the CPU to **B**.
3. B does about **15 ms** of CPU work (heavier validation, a long loop), then sends its own DB query.
4. A's DB response arrives at about **40 ms**, but A doesn't get the CPU the instant it arrives. Scheduling and priorities apply, and A resumes at about **50 ms**, filters the results and responds.
5. B's response arrives in the meantime, then B finishes.

Key observations:
- From the client's point of view, **both requests are in progress** the whole time.
- Zoom into any time slice and **only one is using the CPU**.
- **No CPU time was wasted** while either was waiting on IO.
- In reality the CPU is shared by far more than two requests: logging to stdout, telemetry calls, background jobs and so on. The CPU keeps jumping to whichever task is ready and away from any task that starts waiting on IO.

### Same requests with two cores (parallelism)
When B arrives and a second core is free, B starts **immediately**. Both are in progress *and* both run in the same time window.

## 4. IO bound vs CPU bound 🎓

| | IO bound | CPU bound |
|---|---|---|
| Time spent | Waiting for something external | Executing instructions |
| Examples | DB queries, HTTP calls, file reads, logging, cache | Validation, JSON parsing (light); image processing, video encoding, encryption, password hashing, ML (heavy) |
| What helps | **Concurrency**: overlap the waits | **Parallelism**: more cores finish sooner |
| More cores help? | Barely. The bottleneck is IO either way | Yes, roughly linearly for parallelizable work |

Points the lesson makes:
- **Most backend work is IO bound.** Light CPU work like validation or JSON parsing usually takes 1–2 ms because CPUs are fast, so you don't notice it.
- **Heavy CPU bound work** exists: image processing (lots of matrix math), cryptography (the lesson cites JWT verification in auth middleware), video encoding, ML.
- For IO bound work, **concurrency is mandatory**. Whether you have 1 core or 8, the bottleneck is IO.
- A real backend **needs both**: concurrency for DB connections, APIs, files, logging and background jobs; parallelism for the heavy computations.

🔧 **How to tell which one you have, in practice:** measure. If a request takes 300 ms but the process uses almost no CPU, it's IO bound, so look at queries, network round trips and pool waits. If the CPU sits near 100% per core and latency grows with load, it's CPU bound. In Python, `py-spy top --pid <pid>` or `py-spy record` (a sampling profiler that attaches to a running process) shows where CPU time goes, and the event-loop lag metric (section 7) tells you whether CPU work is starving IO.

## 5. How a computer does many things at once: two mechanisms 🎓

At bottom there are essentially **two** mechanisms:
1. **Threads**
2. **Event loops**

Every concurrency feature you meet is built on one of these, or a combination: **goroutines** in Go, **async/await** in Python (asyncio) and JavaScript, **virtual threads** in Java. They usually don't expose raw threads, but they're built on top of threads, an event loop, or both.

---

## 6. Mechanism 1: OS threads 🎓

### What a thread is
A **thread** is an independent stream of execution that the **operating system** manages. When one is created, the OS allocates:
- a **stack**: the chain of function calls (main → `get_users` → …) and their **local variables** (`a = 3` inside a function lives in that call's frame),
- an **instruction pointer**: where in the code this thread currently is, so it can **resume** at that exact spot after being switched out,
- plus internal bookkeeping (saved registers, state).

### The scheduler (OS controlled)
The **scheduler** decides which thread runs, stops, blocks and resumes. For classic threads, **the OS controls it**. That's the key difference from runtimes that add their own scheduler on top (Go, section 9).

- Each thread gets a **time slice** of CPU, typically measured in milliseconds.
- When the slice ends, the scheduler **saves the thread's state** (last instruction, registers) and switches to another thread.
- This is **preemptive scheduling**: threads are stopped before they finish, whether they like it or not.

📚 The lesson recommends **"Operating Systems: Three Easy Pieces"** if you want to go deep on schedulers.

### What happens on blocking IO
A **blocking operation** is one where the CPU can do nothing useful: network calls (the NIC, packets, TCP, HTTP), DB calls (network calls too, but a category of their own), logging and other device IO.

<Mermaid chart={`stateDiagram-v2
  [*] --> Runnable : created
  Runnable --> Running : scheduler picks it
  Running --> Runnable : time slice ends (preempted)
  Running --> Blocked : blocking read on a socket
  Blocked --> Runnable : IO completes (DB replied)
  Running --> [*] : finished`} />

1. The thread hits a blocking call, so it tells the OS it can't continue until the IO completes.
2. The OS marks it **blocked** and runs another thread.
3. When the IO completes, the thread becomes **runnable**. It doesn't get the CPU instantly; it waits until the scheduler picks it.

### Processes vs threads: who shares memory

<Mermaid chart={`flowchart LR
  subgraph P1["Process 1"]
    direction TB
    H1[("Heap + globals<br/>(shared)")]
    T1["Thread 1<br/>own stack + IP"] --- H1
    T2["Thread 2<br/>own stack + IP"] --- H1
  end
  subgraph P2["Process 2"]
    direction TB
    H2[("Heap + globals")]
    T3["Thread 1<br/>own stack + IP"] --- H2
  end
  P1 -. "isolated: cannot read each other's memory" .- P2`} />

- **Every running program is a process.** Two processes (even of the same program) are **isolated** and can't see each other's memory, for security and to prevent corruption.
- **Threads in the same process share memory**: the heap, globals, anything allocated dynamically. If thread 1 allocates an object (a struct in Go, a dict or class instance in Python), thread 2 can reach it through its **address**.
- Benefit: threads communicate by **reading and writing the same data structure**. No copying, no serialization, so it's fast.
- Danger: the same sharing is the root of race conditions (section 11).
- With **multiple cores**, threads of one process truly run **in parallel**: 2 cores → 2 threads at once, 4 cores → 4. This is what speeds up CPU bound work.

🔧 **Python's twist: the GIL.** `threading.Thread` creates a real OS thread, scheduled by the OS exactly as above. But the standard CPython build has a **global interpreter lock**: only one thread at a time may execute Python bytecode. A thread releases it when it blocks on IO (`socket.recv`, `time.sleep`, a DB driver waiting on the network), when C code such as `hashlib`, `zlib` or numpy releases it, and otherwise every 5 ms (`sys.getswitchinterval()`) so another thread gets a turn. So Python threads overlap **IO waits** well, but pure-Python **CPU work** doesn't run in parallel. The **free-threaded build** (PEP 703, officially supported since Python 3.14, installed as `python3.14t`) removes the GIL, and its threads run bytecode on several cores at once. `sys._is_gil_enabled()` tells you which one you're running. Section 8 measures the difference.

### The three overheads of threads

**1. Memory.**
- Each thread gets its own stack. On Linux the default stack reservation is about **8 MB**. Most of it is **virtual** (physical pages are only committed when touched), but each thread still costs real memory.
- The lesson's what-if: a framework that creates **one thread per request** (most don't) hits a traffic spike of **10,000 requests**. At about 500 KB–1 MB each, that's **around 8–9 GB** just for request threads, before the rest of the server's needs. The process or the server runs out of memory and crashes.

**2. Creation cost.**
- Creating a thread is a **system call**. The kernel sets up the stack, allocates its internal structures, initializes the instruction pointer and registers the thread with the scheduler.
- That takes from **a few microseconds to a few milliseconds**: negligible to a human, significant on a hot request path.

**3. Context switches**, the biggest latency cost. Every switch from one thread to another means:
1. save the current thread's CPU registers,
2. update the scheduler's bookkeeping,
3. pick the next thread,
4. restore that thread's registers and state.

This costs roughly **1–10 µs** on modern hardware, more when the data isn't in CPU cache. With 4 cores and 100 threads the scheduler is constantly juggling; with thousands of threads the switching adds up to many milliseconds of **pure maintenance work**. That's why **thread-per-request** has always struggled with very high concurrency.

🔧 **How production thread-based servers cope:** they use a **fixed thread pool** (for example a few hundred threads), not one thread per request. Requests queue when the pool is busy. This caps memory and switching, but now **the pool size caps concurrent IO waits**. With 200 threads all blocked on a slow DB, request 201 waits even though the CPU is idle.

## 7. Mechanism 2: the event loop 🎓

### The idea
Instead of many threads, there is usually **one thread**. Tasks never sit and wait on IO. Instead, they say: *"start this DB query, and when the result arrives, resume me. Until then, take the CPU back."*

1. The task starts the IO and **registers a callback** (or, with `async`/`await`, the rest of the function becomes the callback).
2. It **returns control to the event loop** immediately.
3. The event loop keeps track of all pending operations. Conceptually it's an **infinite loop**; on each iteration it:
   - asks the OS which IO operations have completed,
   - queues the callbacks for those (with priorities),
   - runs them, then loops again.

### Why the OS must help
A language can't build this alone. The OS provides a way to **watch thousands of sockets at once** and be told which are ready:
- **epoll** on Linux,
- **kqueue** on macOS/BSD,
- 🔧 **IOCP** (I/O Completion Ports) on Windows.

### Why it wins for IO bound work
- **No context switches** between request handlers: one thread.
- **No per-request stacks** of megabytes: a pending request is a small object (a suspended coroutine: its frame, saved position and local variables).
- So for IO bound workloads, **more threads don't help; they hurt**, because more threads mean more switching. That's why an event loop is **more efficient than threads for IO bound work**.

### The trade-off: never block the event loop
If any callback does CPU heavy work, for example **100 ms** of computation, **nothing else runs for 100 ms**: no other request, no timers, no IO callbacks. So in an event-loop runtime, **callbacks must be fast**.

The lesson's realism check: typical SaaS backends rarely have 100 ms CPU tasks. Those show up with **images, animations, video rendering and ML**. The latency of typical endpoints comes from IO.

### Callbacks, futures and async/await are tools for this model
asyncio's callbacks (`loop.call_soon`, `Future.add_done_callback`), futures and `async`/`await` exist to **make yielding explicit**. Writing `await db.fetch(...)` means *"I give up the CPU here; give it back when this IO finishes"*. They're **syntactic conveniences** that keep you from writing blocking code by accident. (The flip side: a plain blocking call such as `requests.get()` or `time.sleep()` inside an `async def` never yields, and freezes the whole loop.)

### 🔧 Going deeper: asyncio's actual event loop

asyncio's loop (`BaseEventLoop._run_once` in the standard library) does the same few steps on every iteration:

<Mermaid chart={`flowchart LR
  T["compute poll timeout<br/>0 if callbacks are ready, else next timer"] --> PO["poll<br/>selector.select: epoll / kqueue / IOCP"]
  PO --> IO["IO events<br/>schedule their callbacks"]
  IO --> TM["due timers<br/>call_later, asyncio.sleep"]
  TM --> RUN["run every callback that was in<br/>the ready queue when this step began"]
  RUN --> T
  M["no microtask queue: a resumed task is just<br/>another callback in the same FIFO ready queue"] -.-> RUN`} />

- **There is one FIFO ready queue, not a microtask queue.** When a future completes, the task waiting on it is resumed through `call_soon`, which appends a callback to the same queue as everything else. Callbacks added while the loop is running a batch wait for the **next** iteration, after another poll. So a chain of `call_soon` calls can't starve IO the way Node's `process.nextTick` can. A coroutine that **never actually suspends** can, though (more below).
- **Not everything uses epoll.** asyncio has no async file IO. `asyncio.to_thread`, `loop.run_in_executor(None, ...)` and `loop.getaddrinfo` (the DNS lookup behind every `open_connection` and most HTTP clients) run on the loop's **default `ThreadPoolExecutor`**, which has `min(32, os.process_cpu_count() + 4)` threads (Python 3.13+).
- **Edge case: executor starvation.** Hash passwords with `await asyncio.to_thread(hashlib.scrypt, ...)` during a login spike and the default executor fills up, so **DNS lookups and every other `to_thread` call** queue behind the hashes. Symptom: outbound connections (the hostname lookup) get slow under load even though the CPU isn't maxed. Fixes: give hashing its own executor (`loop.run_in_executor(hash_pool, ...)`), size the default one with `loop.set_default_executor(...)`, or move hashing to a process pool.

### Which callback runs first: call_soon, tasks, timers and sleep(0) ➕

The loop diagram above says *where* callbacks run; to predict real behaviour you also need the exact ordering rules, because code that "defers" work with the wrong primitive either starves IO or runs later than you expect.

#### Coroutines are lazy, and everything shares one queue ➕
**Problem.** Two pieces of code both "run soon": a `loop.call_soon(cb)` callback and a coroutine started with `asyncio.create_task(...)`. Engineers coming from JavaScript also assume that **calling** an `async def` function starts it, then hit ordering bugs (a background job that never ran, a cleanup that runs after the next request).

**Why it happens.** Two rules explain almost everything:
1. **Calling a coroutine function runs nothing.** `child()` only creates a coroutine object. Its body runs when something drives it: `await child()` runs it **inline**, in the current task, up to its first real suspension; `asyncio.create_task(child())` schedules its first step with `call_soon`.
2. **There is one FIFO ready queue.** `call_soon` callbacks, new tasks' first steps and resumed tasks all join it in the order they were scheduled. Timers (`call_later`) are moved into it only when the loop checks timers, after the next poll.

**Mechanism, shown.** This runs as written:

```python title="ordering.py"
import asyncio


async def child(name: str) -> None:
    print(f"{name}: started")
    await asyncio.sleep(0)                      # a real suspension point
    print(f"{name}: resumed")


async def main() -> None:
    loop = asyncio.get_running_loop()
    coro = child("coro")                        # nothing runs yet: just a coroutine object
    loop.call_later(0, print, "call_later(0)")
    loop.call_soon(print, "call_soon")
    task = asyncio.create_task(child("task"))   # first step scheduled, not run
    print("sync")
    await coro                                  # runs 'coro' inline, up to its first suspension
    await task


asyncio.run(main())
```

```text title="Output"
sync
coro: started
call_soon
task: started
coro: resumed
call_later(0)
task: resumed
```

`coro: started` prints before `call_soon` because `await coro` doesn't schedule anything: it runs the coroutine directly until `sleep(0)` suspends the whole `main` task. Then the ready queue runs in FIFO order: the `call_soon` callback, the task's first step, `main`'s resumption. The zero-delay timer only joins after the next poll.

**Implementation guidance.**
- Start background work with `asyncio.create_task` (or better, a `TaskGroup`) and **keep a reference** to the task. The loop only holds weak references to tasks, so a task nobody references can be garbage-collected mid-flight.
- Use `loop.call_soon` only for plain callbacks (protocol code, library internals). From another thread, the only safe way in is `loop.call_soon_threadsafe` or `asyncio.run_coroutine_threadsafe`.

**Edge cases.**
- Never write a test that depends on the interleaving of unrelated tasks. Python 3.12's `asyncio.eager_task_factory` changes it: with it, `create_task` runs the coroutine synchronously up to its first suspension.
- `await` on something that doesn't suspend is **not** a yield. Awaiting a coroutine that returns without awaiting anything, or a future that is already done, continues immediately without giving the loop a turn.

#### `call_later(0, fn)` vs `call_soon(fn)` ➕
**Problem.** Both look like "next iteration", and code that relies on one running first breaks when someone swaps them.

**Why.** `call_soon` appends to the ready queue right away. `call_later(0, ...)` puts a timer on the loop's heap; it's moved to the ready queue during the **next** iteration's timer step, after the poll, behind everything already queued. Unlike Node's `setTimeout(fn, 0)` vs `setImmediate`, the order is deterministic, as the output above shows.

**Implementation rule.** When you want "after what's already queued", use `call_soon`; inside a coroutine, `await asyncio.sleep(0)` is the idiom for "let everyone else run once" (it's special-cased as a bare yield, no timer involved). When you want a real delay, use `asyncio.sleep` or `call_later` with a real duration. Don't use `call_later(0, ...)` as a scheduling primitive.

#### Partitioning CPU work so the loop keeps breathing ➕
**Problem.** A handler must process 200,000 rows in Python (aggregation, CSV building). It takes 400 ms, and for that time no other request runs (section 7). Moving it to a worker process (section 8) is the full fix, but sometimes the job is modest and you just need to stop it from monopolising the loop.

**Why `await` alone doesn't help.** Splitting the work into `async def process_chunk(...)` and calling `await process_chunk(...)` in a loop changes nothing: a coroutine that never awaits anything that suspends runs straight through. Awaiting a coroutine is not a yield to the event loop.

**Mechanism.** Work in time-boxed chunks and `await asyncio.sleep(0)` between them. That puts the task at the back of the ready queue, the loop polls for IO, and other requests make progress.

```python title="partition.py"
import asyncio
import time
from collections.abc import Callable, Sequence


async def process_in_chunks[T](items: Sequence[T], fn: Callable[[T], None], budget_s: float = 0.010) -> None:
    i = 0
    while i < len(items):
        slice_start = time.perf_counter()
        while i < len(items) and time.perf_counter() - slice_start < budget_s:
            fn(items[i])                 # work for ~10 ms
            i += 1
        await asyncio.sleep(0)           # a REAL yield: the loop polls IO, other requests progress,
                                         # and a cancelled request stops here with CancelledError
```

**Edge cases.**
- Total time goes **up** slightly (scheduling overhead), but the **tail latency of everyone else** goes down. That's the trade.
- Shared state can change between chunks, because other handlers run in the gaps. Everything from section 11 about check-then-act across a yield applies.
- If a single item is expensive (one 300 ms regex), chunking can't help; that needs a worker process.

### 🔧 Going deeper: seeing a blocked loop

```python title="block_demo.py"
import asyncio
import time
from contextlib import asynccontextmanager

from fastapi import FastAPI
from fastapi.responses import PlainTextResponse


async def watch_loop_lag(interval: float = 0.010) -> None:
    worst, last_report = 0.0, time.perf_counter()
    while True:
        start = time.perf_counter()
        await asyncio.sleep(interval)
        worst = max(worst, time.perf_counter() - start - interval)   # how late the loop woke us up
        if time.perf_counter() - last_report >= 5:
            print(f"event-loop lag, worst in 5 s: {worst * 1000:.1f} ms")
            worst, last_report = 0.0, time.perf_counter()


@asynccontextmanager
async def lifespan(app: FastAPI):
    watcher = asyncio.create_task(watch_loop_lag())
    yield
    watcher.cancel()


app = FastAPI(lifespan=lifespan)


@app.get("/block", response_class=PlainTextResponse)
async def block() -> str:
    end = time.monotonic() + 2
    while time.monotonic() < end:     # 2 s of CPU work on the ONLY event-loop thread
        pass
    return "blocked for 2s\n"


@app.get("/", response_class=PlainTextResponse)
async def fast() -> str:
    return "fast\n"                   # normally well under 1 ms
```

Start it with `uvicorn block_demo:app --port 3000`, then run `curl localhost:3000/block` in one terminal and `curl localhost:3000/` in another: the "fast" request takes about 2 s, because it can't start until the loop is free. The worst lag jumps to about 2000 ms. Note that this only happens because `block` is an `async def`: FastAPI runs plain `def` endpoints in a thread pool, which keeps the loop free (at the cost of a thread per in-flight call). Running with `PYTHONASYNCIODEBUG=1` also makes asyncio log every callback slower than 100 ms (`loop.slow_callback_duration`). **Alert on event-loop lag in production**; it's the most direct sign of CPU work starving IO.

### Event loop utilization: the saturation metric ➕

Event-loop lag tells you that callbacks are waiting; a second metric tells you **how close the loop is to its capacity** before the lag explodes, which is what you need for autoscaling and load shedding. Node ships it built in; in Python you measure it yourself, and the mechanism is small.

#### Why lag alone misleads ➕
**Problem.** Lag is a *symptom*. A loop can be 90% busy with many short callbacks and still show low lag, then fall off a cliff when traffic grows another 10%. Process CPU% doesn't help either: it mixes the loop thread with the default executor's threads, other threads and C libraries.

**First principles.** The loop is a single server in a queue. Queueing theory says waiting time stays low until utilisation gets close to 100%, then grows very fast. So you want to measure **utilisation of the loop itself**.

#### The mechanism: time spent idle in `select()` ➕
The loop is **idle** exactly when it's blocked in the selector's `select()` call waiting for the OS, and **active** the rest of the time (running callbacks and its own bookkeeping). So time `select()`, and active ÷ (active + idle) over an interval is the loop's utilization, from 0 to 1. A custom selector passed to `asyncio.SelectorEventLoop` measures it with no changes to your app code.

```python title="loop_utilization.py"
import asyncio
import selectors
import time


class MeteredSelector(selectors.DefaultSelector):
    """Adds up the time the loop spends blocked in select(): that's its idle time."""

    def __init__(self) -> None:
        super().__init__()
        self.idle = 0.0

    def select(self, timeout=None):
        start = time.perf_counter()
        try:
            return super().select(timeout)
        finally:
            self.idle += time.perf_counter() - start


SELECTOR = MeteredSelector()


def metered_loop() -> asyncio.AbstractEventLoop:
    return asyncio.SelectorEventLoop(SELECTOR)


class LoopUtilization:
    def __init__(self) -> None:
        self._wall, self._idle = time.perf_counter(), SELECTOR.idle

    def sample(self) -> float:
        """Utilization since the previous sample, from 0.0 to 1.0."""
        wall, idle = time.perf_counter(), SELECTOR.idle
        busy = 1 - (idle - self._idle) / (wall - self._wall)
        self._wall, self._idle = wall, idle
        return busy


async def report_utilization() -> None:
    u = LoopUtilization()
    while True:
        await asyncio.sleep(5)
        metrics.gauge("python.asyncio.loop_utilization", u.sample())   # only the last 5 s


# asyncio.run(uvicorn.Server(config).serve(), loop_factory=metered_loop)
```

#### Using utilization to shed load before latency collapses ➕
**Problem.** When the loop saturates, every request gets slower, including health checks, so the orchestrator may kill the instance during a traffic spike.

**Mechanism.** Read utilization on a short interval and reject *new, low-priority* work with 503 while it's above a threshold, so in-flight requests finish quickly. It's the same idea as the bounded queue in the worker pool (section 8), applied to the main loop.

```python title="shed_load.py"
import asyncio

from fastapi import FastAPI, Request, Response

from loop_utilization import LoopUtilization

app = FastAPI()
busy = False


async def watch_utilization() -> None:     # start it as a task in the app's lifespan
    global busy
    u = LoopUtilization()
    while True:
        await asyncio.sleep(0.5)
        busy = u.sample() > 0.9


@app.middleware("http")
async def shed_load(request: Request, call_next):
    if busy and request.url.path != "/healthz":
        return Response(status_code=503, headers={"Retry-After": "1"})
    return await call_next(request)
```

**Edge cases.**
- Utilization is per event loop. With several uvicorn or gunicorn worker processes, each has its own loop and its own number; aggregate per pod with the max, not the average. It's also a good signal for sizing a worker count.
- The trick hooks the standard library's selector loop. uvloop and Windows' default `ProactorEventLoop` don't use a Python selector, so they need a different measurement (for example, sampling lag instead).
- High utilization with low lag means "busy but coping". High lag with modest utilization usually means a few long callbacks: look for one blocking call, not general overload.
- Thresholds like 0.9 are starting points. Tune them against your latency SLO with a load test (see [lesson 21](/docs/backend-first-principles/21-scaling-performance-part-1)).

## 8. Walkthrough: two requests under each model 🎓

The **sequence of work** is the same in both models. What differs is **how a request is paused and resumed**, and how cheap that is.

### Threading model
1. **Request A** arrives on thread 1. **Parse** the JSON body and query params (CPU: reading bytes into memory).
2. Validate, then run `SELECT * FROM users`:
   - take a TCP connection from the **pool** (or open one),
   - **send** the query bytes over the socket,
   - call **`read`** on the socket and wait for the reply. This is the **blocking** IO call.
3. Thread 1 blocks, so the OS switches to **thread 2**, which is handling **request B** (parse, validate, `SELECT * FROM orders`, send, `read`, block).
4. If another thread exists (thread-per-request, or a free pool thread), the OS runs it. If not, everything waits until some IO completes.
5. Packets arrive at the network card, so the OS **wakes thread 1**. It then:
   - parses the DB's bytes into native structures (JS objects, Python dicts, Go structs),
   - processes them,
   - **serializes to JSON** and sends the HTTP response,
   - **returns to the thread pool**.

```python title="threaded handler (Python, as in the lesson)"
def handle_request(user_id):
    # Looks sequential. The thread really BLOCKS on this line,
    # and the OS quietly runs other threads meanwhile.
    user = db.query("SELECT * FROM users WHERE id = %s", (user_id,))
    return to_json(user)
```

The switching is **invisible in the code**. It reads top to bottom, and the pausing happens in the OS.

### Event-loop model
1. Request A: parse, validate, send the query bytes, **register a callback**, and **return** to the loop. "Return" means *give up the CPU*, not *send the HTTP response*.
2. The loop picks up **request B**: parse, send its query, register its callback, return.
3. Each loop iteration asks epoll/kqueue whether A's or B's socket is readable, and handles other work meanwhile (logging, sending emails…).
4. epoll reports **socket B readable** first, so B's callback runs: parse rows, serialize, respond.
5. Later A's socket is readable, so A's callback runs and responds.

The difference: threads pause and resume using **heavy OS structures** (stacks, saved registers, the instruction pointer). The event loop pauses and resumes using **callbacks**.

### From callbacks to async/await

```python title="before async/await (Python 3.5): callbacks"
def get_user(req, send_response):
    future = db.query("SELECT * FROM users WHERE id = $1", req.user_id)   # starts the IO, returns at once

    def on_done(fut):
        if fut.exception() is not None:
            return send_response(500, {"error": "db"})
        send_response(200, fut.result())                   # runs LATER, when the DB replies

    future.add_done_callback(on_done)
```

Several dependent IO steps (user → orders → external API…) mean a callback inside a callback inside a callback: **callback hell** (Twisted and early Tornado code looked like this).

```python title="after: async/await"
async def get_user(req, send_response):
    user = await db.query("SELECT * FROM users WHERE id = $1", req.user_id)
    send_response(200, user)
```

Mental model: **everything after an `await`, to the end of that function, is the callback** for that IO. You get the same single-threaded, no-switch efficiency with flat, readable code.

### 🔧 Going deeper: overlap independent waits

`await` pauses **this function**, not the server. Inside a handler, sequential awaits still add up:

```python title="sequential vs concurrent"
import asyncio


async def load_page(id: str):
    # Sequential: about 50 + 50 + 50 = 150 ms, because each await waits for the previous one.
    user = await db.get_user(id)
    orders = await db.get_orders(id)
    prefs = await cache.get(f"prefs:{id}")

    # Concurrent: about max(50, 50, 50) = 50 ms. Start all three, then wait once.
    async with asyncio.TaskGroup() as tg:
        user_t = tg.create_task(db.get_user(id))
        orders_t = tg.create_task(db.get_orders(id))
        prefs_t = tg.create_task(cache.get(f"prefs:{id}"))
    user, orders, prefs = user_t.result(), orders_t.result(), prefs_t.result()

    # Same timing, shorter, but with weaker failure handling (see below):
    user, orders, prefs = await asyncio.gather(db.get_user(id), db.get_orders(id), cache.get(f"prefs:{id}"))
```

Edge cases:
- Only parallelize **independent** calls. If `get_orders` needs `user.account_id`, it must wait.
- `asyncio.gather` raises the **first** exception, but the other calls **keep running**: it doesn't cancel them. `TaskGroup` (Python 3.11+) does: the first failure cancels the siblings, waits for them, and raises an `ExceptionGroup` (catch it with `except*`). Use `gather(..., return_exceptions=True)` when you want every result, failures included.
- Firing 500 queries at once doesn't make them faster: they **queue for the DB connection pool** (say 10 connections) and can starve other requests. Cap the fan-out:

```python title="map_limit.py"
import asyncio
from collections.abc import Awaitable, Callable, Sequence
from typing import Any


async def map_limit[T, R](items: Sequence[T], limit: int, fn: Callable[[T], Awaitable[R]]) -> list[R]:
    results: list[Any] = [None] * len(items)
    work = iter(enumerate(items))          # one iterator shared by every worker

    async def worker() -> None:
        for i, item in work:               # safe: next() has no await inside, so no two workers get the same item
            results[i] = await fn(item)

    async with asyncio.TaskGroup() as tg:
        for _ in range(min(limit, len(items))):
            tg.create_task(worker())
    return results


# await map_limit(user_ids, 8, send_email)   # at most 8 in flight
```

An `asyncio.Semaphore(8)` around each call does the same job, but it creates all 500 tasks up front; the worker version keeps only 8 alive.

### Cancelling concurrent work ➕

Starting work concurrently is half the job; the other half is **stopping** it when the result is no longer needed, because abandoned work keeps consuming connections, CPU and downstream capacity. Request-wide deadlines and the cancellation plumbing in middleware are covered in [lesson 10](/docs/backend-first-principles/10-controllers-services-repositories-middleware) and timeouts in [lesson 16](/docs/backend-first-principles/16-error-handling-fault-tolerance); this section is about cancellation *between concurrent tasks*.

#### Why a failed `gather` leaves work running ➕
**Problem.** A handler fans out to three services with `asyncio.gather`. One fails after 20 ms, the handler returns 502, but the other two calls run for another 2 seconds, holding sockets and pool connections for a response nobody will read. Under an outage this doubles the load on the struggling dependency.

**First principles.** Unlike a JavaScript promise, an asyncio **task can be cancelled**: `task.cancel()` throws `CancelledError` into the coroutine at the `await` where it's suspended, so `finally` blocks and `async with` exits run and libraries like httpx close the socket. But someone has to call it. `gather` propagates the first exception and simply stops waiting; it never cancels the others. Cancellation needs an **owner** that knows which tasks belong together. That owner is a `TaskGroup` (structured concurrency).

**Mechanism: fail fast, cancel siblings.** Run the group's tasks inside `async with asyncio.TaskGroup()`. The first failure cancels every sibling, the block waits until they've all finished, and the errors come out as one `ExceptionGroup`.

```python title="all_or_cancel.py"
import asyncio
from collections.abc import Coroutine
from typing import Any

import httpx


async def all_or_cancel[T](*coros: Coroutine[Any, Any, T]) -> list[T]:
    async with asyncio.TaskGroup() as tg:          # first failure cancels every sibling
        tasks = [tg.create_task(c) for c in coros]
    return [t.result() for t in tasks]             # success or failure: nothing outlives the block


async def get_json(client: httpx.AsyncClient, url: str) -> Any:
    r = await client.get(url)
    r.raise_for_status()
    return r.json()


# usage inside a handler. If the request's own task is cancelled (client disconnect, deadline),
# the TaskGroup cancels its children too: cancellation flows down the task tree.
async def user_page(client: httpx.AsyncClient, id: str):
    async with asyncio.timeout(2):
        user, orders = await all_or_cancel(
            get_json(client, f"{USERS}/u/{id}"),
            get_json(client, f"{ORDERS}/u/{id}"),
        )
    return user, orders
```

#### Racing and hedging: cancel the loser ➕
**Problem.** You send the same read to two replicas and take whichever answers first (a **hedged request**, a common tail-latency trick), or you race a cache against the DB. With `asyncio.wait(..., return_when=FIRST_COMPLETED)` alone, the loser keeps running, so hedging silently doubles load.

**Mechanism.** Same idea: own the tasks, and cancel the rest as soon as a winner exists.

```python title="race_and_cancel.py"
import asyncio
from collections.abc import Awaitable, Callable, Coroutine
from typing import Any


async def first_of[T](*coros: Coroutine[Any, Any, T]) -> T:
    tasks = [asyncio.create_task(c) for c in coros]
    errors: list[Exception] = []
    try:
        for next_done in asyncio.as_completed(tasks):
            try:
                return await next_done                  # first SUCCESS wins, failures are skipped
            except Exception as e:
                errors.append(e)
        raise ExceptionGroup("every attempt failed", errors)
    finally:
        for t in tasks:
            t.cancel()                                  # stop the losers
        await asyncio.gather(*tasks, return_exceptions=True)   # and wait until they've cleaned up


async def after[T](delay: float, fn: Callable[[], Awaitable[T]]) -> T:
    await asyncio.sleep(delay)
    return await fn()


# hedge: start the backup only if the primary is slow
async def get_user(id: str):
    return await first_of(
        replica_a.get(id),
        after(0.05, lambda: replica_b.get(id)),
    )
```

Cancelling `after` interrupts its `asyncio.sleep`, so the backup never starts if the primary wins within 50 ms. (The `lambda` matters: `replica_b.get(id)` written directly would create a coroutine object that never runs, and Python warns "coroutine was never awaited".) Only hedge **idempotent reads**; hedging a write can apply it twice.

#### Making your own loops and libraries cancellable ➕
**Problem.** Cancellation reaches httpx, but your own code (a retry loop, a paginated export, a CPU loop) ignores it and keeps going.

**Mechanism.** Python delivers cancellation **at `await` points**, so there's no signal to check, but three rules decide whether it works:
1. A loop must actually reach an `await` that suspends (section 7). A pure CPU loop never sees the cancellation.
2. Never swallow `CancelledError`. It's a `BaseException`, so `except Exception` lets it through, but a bare `except:` or `except BaseException:` catches it and turns a cancellation into a retry.
3. If you catch it for cleanup, re-raise it.

```python title="retry loop that respects cancellation"
import asyncio

import httpx


async def get_with_retries(client: httpx.AsyncClient, url: str, attempts: int = 3) -> httpx.Response:
    for attempt in range(attempts):
        try:
            return await client.get(url)
        except httpx.TransportError:              # NOT bare except: CancelledError must pass through
            if attempt == attempts - 1:
                raise
            await asyncio.sleep(0.1 * 2**attempt)   # an await: a cancelled request stops here too
    raise AssertionError("unreachable")
```

Work handed to a thread is the exception: cancelling `await asyncio.to_thread(fn)` stops the **waiting**, but the thread keeps running `fn` to the end, because Python has no way to interrupt a thread. Calls to a sync SDK such as boto3 made through `to_thread` can't be cancelled; give them their own timeouts instead.

#### Cancelling a running Postgres query ➕
**Problem.** Stopping the Python side of a query doesn't necessarily stop the database. If you just stop waiting, the backend keeps executing a 30-second report, holding locks and a pool connection.

**Mechanism.** Postgres cancels a query through a **separate** request that names the backend process. asyncpg does this for you: when the task awaiting `conn.fetch(...)` is cancelled (by `asyncio.timeout`, a `TaskGroup` or a client disconnect), it opens a short side connection and sends Postgres's cancel request for that backend. A sync driver called through `to_thread` can't, so there you cancel by hand: every connection knows its backend PID, and a second connection can call `pg_cancel_backend`. The canceled query fails with SQLSTATE `57014`.

```python title="cancellable_query.py"
import asyncio

import asyncpg


async def query_with_deadline(pool: asyncpg.Pool, sql: str, *args, timeout: float):
    async with pool.acquire() as conn:
        async with asyncio.timeout(timeout):      # on expiry the task is cancelled inside fetch()...
            return await conn.fetch(sql, *args)   # ...and asyncpg sends a cancel request for this backend


async def cancel_backend(pool: asyncpg.Pool, pid: int) -> bool:
    # the manual version, for a query running elsewhere (another worker, a sync driver):
    # pid comes from conn.get_server_pid() on the connection running the query
    return await pool.fetchval("SELECT pg_cancel_backend($1)", pid)
```

**Edge cases.**
- Manual `pg_cancel_backend` needs a **free pool connection**. If the pool is exhausted, the cancel itself waits. Keep `statement_timeout` (lesson 16) as the backstop.
- The cancel is asynchronous: the query may finish just before it arrives. Treat "canceled" and "completed" as both possible outcomes.

#### Cancellation is not rollback ➕
**Edge case that bites.** Aborting a request that already sent a `POST /charge` doesn't un-charge the card. Cancellation only stops *future* work. Anything with side effects needs idempotency keys and a compensation path (see the withdraw example in section 11, and [lesson 14](/docs/backend-first-principles/14-task-queues-background-jobs) for moving such work to a queue).

### A shared limit for a downstream: semaphores and load shedding ➕

`map_limit` caps the fan-out of **one** call; the next failure mode appears when **many concurrent requests** each fan out to the same dependency, so the per-call limit multiplies by the number of requests in flight.

#### Why per-call limits aren't enough ➕
**Problem.** Each request sends at most 8 calls to a pricing service. At 200 concurrent requests that's 1,600 in-flight calls. The pricing service slows down, your requests stay open longer, more requests pile up, and the in-flight count grows further: a **feedback loop** that turns a slow dependency into an outage of yours.

**First principles.** By Little's law ([lesson 21](/docs/backend-first-principles/21-scaling-performance-part-1)), in-flight work = arrival rate × latency. When a dependency's latency grows, in-flight work grows with it unless something **caps it**. The cap has to be **process-wide per dependency**, not per call.

#### The mechanism: a counting semaphore with a bounded wait ➕
A **semaphore** holds N permits. Acquire takes one (or waits), release returns it. `asyncio.Semaphore` provides that, with waiters woken in FIFO order. Two extra rules make it production-safe: a **maximum queue length** and a **maximum wait time**, so callers fail fast instead of queueing forever.

```python title="bulkhead.py"
import asyncio
from contextlib import asynccontextmanager


class Saturated(Exception):
    """The downstream's queue is full: shed the request (503) instead of queueing."""


class Bulkhead:
    def __init__(self, permits: int, max_queue: int = 100) -> None:
        self._sem = asyncio.Semaphore(permits)
        self._max_queue = max_queue
        self._waiting = 0

    @asynccontextmanager
    async def slot(self, max_wait: float):
        if self._sem.locked() and self._waiting >= self._max_queue:
            raise Saturated("downstream saturated")      # shed instead of queueing
        self._waiting += 1
        try:
            async with asyncio.timeout(max_wait):        # TimeoutError if no permit in time
                await self._sem.acquire()
        finally:
            self._waiting -= 1
        try:
            yield
        finally:
            self._sem.release()                          # exactly once: on success, error or cancellation


# one per dependency, module-level
pricing_limit = Bulkhead(50, max_queue=200)


async def get_price(sku: str):
    async with pricing_limit.slot(max_wait=0.2):         # wait at most 200 ms for a permit
        return await pricing_client.get(sku)
```

#### Sizing the limit ➕
- Start from the dependency's capacity and its normal latency: if pricing handles about 500 req/s per your instance's share and answers in 50 ms, about 25 calls are in flight in steady state. A limit of 2× that (50) absorbs bursts without letting a slowdown grow unbounded.
- For the database, the **connection pool is already the semaphore**. Its acquire timeout (`pool_timeout` in SQLAlchemy, `pool.acquire(timeout=...)` in asyncpg) is the bounded wait. Don't put a second, larger limit in front of it.
- The limit is **per process**. With 10 instances, the dependency sees up to 10 × 50. Size against the total, or use a distributed rate limiter if the provider enforces a global quota.

#### Failure modes of a shared limit ➕
- **Release in `finally`, exactly once.** A missing release leaks a permit forever; after 50 leaks the dependency is unreachable from that instance with no error in its own logs. The context manager makes release structural. If you call `acquire()`/`release()` by hand, use `asyncio.BoundedSemaphore`, which raises `ValueError` on a double release instead of silently minting an extra permit.
- **Separate semaphores per dependency** (the *bulkhead* pattern): one slow service can then exhaust only its own permits, not every outbound call.
- **Nested acquisition of the same semaphore deadlocks** when all permits are held by callers waiting for a second permit. Section 13 covers this shape.

### 🔧 Going deeper: CPU bound work in Python: the GIL, processes and free threading

An event loop can't run CPU work in parallel, and in standard CPython **threads can't either** for pure-Python code, because of the GIL (section 6). You have three tools:
- **Processes** (`ProcessPoolExecutor`): each worker is a separate interpreter with its own GIL, so they run on separate cores. Arguments and results are **pickled** and copied between processes. This is the production default today.
- **Threads** (`asyncio.to_thread`, `ThreadPoolExecutor`): real parallelism only while the work runs in C code that releases the GIL (`hashlib`, `zlib`, numpy, Pillow), or on the **free-threaded** build, where every thread runs bytecode in parallel.
- **Subinterpreters** (`concurrent.futures.InterpreterPoolExecutor`, new in 3.14): several isolated interpreters, each with its own GIL, in one process. Cheaper than processes, but young, and many C extensions don't support them yet.

Create pools **once** at startup and reuse them; starting a worker process takes tens of milliseconds.

```python title="primes.py"
def count_primes(limit: int) -> int:   # stand-in for any heavy pure-Python work
    count = 0
    for n in range(2, limit):
        d = 2
        while d * d <= n:
            if n % d == 0:
                break
            d += 1
        else:
            count += 1
    return count
```

```python title="cpu_pool.py"
import asyncio
import os
from collections.abc import Callable
from concurrent.futures import ProcessPoolExecutor
from concurrent.futures.process import BrokenProcessPool


class Overloaded(Exception):
    """The queue is full: turn it into a 503."""


class CpuPool:
    def __init__(self, size: int | None = None, max_queue: int = 100) -> None:
        self._size = size or max(1, (os.process_cpu_count() or 2) - 1)   # leave a core for the event loop
        self._pool = self._new_pool()
        self._slots = asyncio.Semaphore(self._size + max_queue)          # running + queued jobs

    def _new_pool(self) -> ProcessPoolExecutor:
        return ProcessPoolExecutor(max_workers=self._size, max_tasks_per_child=1_000)  # recycle leaky workers

    async def run[R](self, fn: Callable[..., R], *args) -> R:
        if self._slots.locked():
            raise Overloaded()                         # back-pressure: shed instead of queueing forever
        async with self._slots:
            loop = asyncio.get_running_loop()
            try:
                return await loop.run_in_executor(self._pool, fn, *args)
            except BrokenProcessPool:
                self._pool = self._new_pool()          # a worker died (segfault, OOM kill): replace the pool
                raise

    def close(self) -> None:
        self._pool.shutdown(cancel_futures=True)


# pool = CpuPool()                                     # once, in the app's lifespan
# @app.get("/report")
# async def report():
#     return {"primes": await pool.run(count_primes, 5_000_000)}
```

Notes:
- The semaphore is **back-pressure**. Under heavy load jobs wait instead of oversubscribing the cores, and past `max_queue` the API sheds with 503. `ProcessPoolExecutor`'s own queue is unbounded, so don't rely on it.
- Arguments and results are **pickled and copied** to and from the worker. For large arrays, put the data in `multiprocessing.shared_memory` (numpy can view it directly) and pass only its name.
- `fn` must be importable by the worker (a module-level function, not a lambda or a closure), because the worker process looks it up by name.
- For **very** heavy or long jobs (video transcoding), use a **separate process or service behind a queue** so a crash or memory blowup can't take the API down.

### Where CPU work should run: threads, worker processes or a separate service ➕

The pool above is one of several places CPU work can live in a Python system, and picking the wrong one shows up later as a GIL-bound pool that never speeds up, memory blowups, crashes that take the API down, or a pool that can't scale past one machine.

#### Option 1: threads in the same process ➕
**What it shares.** Everything: one address space, one heap. Data crosses at no cost, because there's nothing to copy.

**When it's the right default.** When the heavy part runs in C code that releases the GIL (password hashing with `hashlib.scrypt`, compression, numpy, image decoding), `asyncio.to_thread` gives real parallelism today with the cheapest possible handoff. On the free-threaded build, pure-Python work qualifies too, as the benchmark above shows. On the standard build, pure-Python CPU work in a thread doesn't run in parallel, and it still slows the event loop, because the loop thread has to win the GIL back every 5 ms.

```python
digest = await asyncio.to_thread(hashlib.scrypt, password, salt=salt, n=2**14, r=8, p=1)  # releases the GIL
```

**Failure modes and how to contain them.**
- A thread **can't be killed or cancelled** from outside. A runaway thread runs until it returns, and cancelling the awaiting task only stops the waiting (section 8).
- A crash in a C extension (a segfault) or an out-of-memory kills the **whole process**, API included.
- Threads have no memory limit of their own; one runaway job can grow until the container is OOM-killed. When you need a cap or a kill switch, use a process.

#### Option 2: a child process (`multiprocessing`, `subprocess`) ➕
**What changes.** A separate OS process with its own memory, file descriptors and crash domain. For Python functions, `ProcessPoolExecutor` (above) handles the IPC; for anything else, `asyncio.create_subprocess_exec` talks to it over stdin and stdout. A Python worker costs tens of MB of memory and noticeable startup time, so you keep a small pool of them alive.

**When it's the right tool.**
- Pure-Python CPU work on the standard (GIL) build.
- The work uses **native code or a binary** you don't fully trust (image libraries, PDF renderers, `ffmpeg`). A segfault ends the child, not the API.
- You need **hard memory limits or OS-level isolation** (separate cgroup, lower privileges).
- The task isn't Python at all: run the tool directly and stream its stdin and stdout.

```python title="run_isolated.py"
import asyncio
import json
import sys
from asyncio.subprocess import PIPE


async def run_isolated(module: str, payload: dict, timeout: float = 30.0, max_mem_mb: int = 512):
    proc = await asyncio.create_subprocess_exec(
        "prlimit", f"--as={max_mem_mb * 1024 * 1024}",   # util-linux (Linux): cap the child's address space
        sys.executable, "-m", module,
        stdin=PIPE, stdout=PIPE, stderr=PIPE,
    )
    try:
        async with asyncio.timeout(timeout):
            out, err = await proc.communicate(json.dumps(payload).encode())
    except TimeoutError:
        proc.kill()                                       # the child doesn't stop on its own
        await proc.wait()
        raise
    if proc.returncode != 0:
        raise RuntimeError(f"worker exited {proc.returncode}: {err.decode()[-500:]}")
    return json.loads(out)
```

**Not to be confused with uvicorn or gunicorn `--workers`.** Those run **copies of your API**, one per core, to scale request handling (and, under the GIL, to use more than one core at all). They don't offload one heavy task; each copy still blocks its own loop if a handler does CPU work.

#### Option 3: a separate service behind a queue ➕
**When the task is long, heavy or bursty** (transcoding, large exports, ML inference), the API should **enqueue a job and return 202**, and a separate worker deployment consumes the queue. This decouples:
- **scaling**: workers scale on queue depth, the API on request rate,
- **failure**: a worker OOM can't touch API latency,
- **hardware**: workers can run on GPU or high-CPU nodes.

The queue mechanics (retries, idempotency, dead letters) are the subject of [lesson 14](/docs/backend-first-principles/14-task-queues-background-jobs).

#### Choosing ➕

| Task shape | Run it in | Why |
|---|---|---|
| Under about 100 ms, in C code that releases the GIL (hashing, compression, numpy) | `asyncio.to_thread` / a thread pool | Cheapest handoff, shared memory, real parallelism |
| Pure-Python CPU work, request needs the result | `ProcessPoolExecutor` (or threads on free-threaded 3.14t) | Separate GILs, real parallelism |
| Native code, untrusted input, needs its own memory cap | Child process pool | Separate crash and memory domain |
| Seconds to hours, or bursty, result can arrive later | Queue + separate worker service | Independent scaling and failure isolation |
| Many cores but the work is IO bound | More uvicorn/gunicorn workers or replicas | More event loops, not offloading |

## 9. Go: goroutines, threads managed by the runtime 🎓

### What a goroutine is
Conceptually a **virtual thread**: a thread-like unit managed by **the Go runtime**, not the OS. Go's docs never call it a virtual thread; it's a **goroutine**. A Go program starts as the main goroutine, which can start others with the `go` keyword.

### Go's HTTP server uses a goroutine per connection
The lesson shows the standard library's `Serve` loop: accept a connection, then **`go c.serve(...)`**, which runs the configured handler in a new goroutine. With OS threads that would be the memory disaster from section 6; with goroutines it's fine.

```go title="simplified from net/http (Go)"
for {
    rw, err := l.Accept()
    if err != nil { /* ... */ }
    c := srv.newConn(rw)
    go c.serve(connCtx) // new goroutine: cheap enough to do for every connection
}
```

🔧 Precisely: it's one goroutine **per connection**. An HTTP/1.1 keep-alive connection serves its requests one after another in that goroutine; HTTP/2 runs each stream's handler in its own goroutine.

### Two layers of scheduling

<Mermaid chart={`flowchart TB
  subgraph RT["Go runtime scheduler (user space)"]
    direction LR
    Q1["run queue<br/>G1 G5 G9"] --> M1
    Q2["run queue<br/>G2 G6"] --> M2

    Q4["run queue<br/>G4"] --> M4
    NP["netpoller (epoll/kqueue)<br/>parks goroutines waiting on sockets"]
  end
  subgraph OSL["OS threads (GOMAXPROCS = number of cores)"]
    M1["M1"] --> C1["core 1"]

  end
  NP -. "socket ready: G back into a run queue" .-> Q1`} />

- **Bottom layer:** a small number of OS threads, `GOMAXPROCS` of them, **defaulting to the number of CPU cores**. With 4 cores you get threads M1–M4. These are what actually run on the cores.
- **Top layer:** the **Go runtime scheduler** puts goroutines into **queues**, one per OS thread conceptually, so **one OS thread runs many goroutines** over time.
- When goroutine **G1 blocks on IO** (a DB query), the runtime **parks G1**, and M1 runs **G2**. When G1's response arrives, G1 becomes runnable and resumes.
- Switching goroutines is roughly **a pointer swap in user space**. No kernel call, no heavy register-and-bookkeeping switch, so you can run **thousands to millions** of goroutines, about **100× more** than OS threads before memory runs out.

```go title="Go handler: looks blocking, isn't (Go)"
func getUser(w http.ResponseWriter, r *http.Request) {
    var u User
    // This goroutine parks here. M1 runs another goroutine meanwhile.
    err := db.QueryRowContext(r.Context(), "SELECT id, name FROM users WHERE id = $1", r.URL.Query().Get("id")).Scan(&u.ID, &u.Name)
    if err != nil { http.Error(w, "not found", http.StatusNotFound); return }
    json.NewEncoder(w).Encode(u)
}
```

So the goroutine model is the **threading model with an extra layer of abstraction**: the Go scheduler instead of the OS scheduler, goroutines instead of OS threads. That's why it's lightweight, and why Go handles both IO bound concurrency and CPU bound parallelism well.

🔧 **Why it's cheap, concretely:**
- A goroutine starts with a stack of about **2 KB** that **grows and shrinks** as needed, versus an MB-scale OS thread stack.
- For **network** IO, the runtime puts the socket in non-blocking mode and uses a **netpoller** (epoll/kqueue/IOCP). A goroutine waiting on a socket is parked, and **no OS thread is blocked**. Go is an **event loop under the hood with thread-style code on top**.
- For a **blocking syscall** (some file IO, cgo), the runtime hands the core to another thread so other goroutines keep running.

🔧 **Java** took the same route: **virtual threads**, final in **JDK 21**, schedule many (M) virtual threads onto a few (N) OS "carrier" threads.

## 10. async/await is a state machine 🎓

Take this function:

```python
async def fetch_user_data(user_id: str):
    user = await db.get_user(user_id)
    orders = await db.get_orders(user["id"])
    return {"user": user, "orders": orders}
```

Conceptually, this is a **state machine**: a `state` variable, saved locals (`user`, `orders`), and a `step` function that runs the code for the current state and moves to the next one when an awaited future completes.

```python title="the same coroutine, written by hand as a state machine"
import asyncio


class FetchUserData:
    def __init__(self, db, user_id: str) -> None:
        self.db, self.user_id = db, user_id
        self.state, self.user, self.orders = 0, None, None
        self.result = asyncio.get_running_loop().create_future()   # what the caller awaits
        self.step(None)

    def step(self, done) -> None:
        try:
            match self.state:
                case 0:
                    self.state = 1
                    asyncio.ensure_future(self.db.get_user(self.user_id)).add_done_callback(self.step)        # await #1
                case 1:
                    self.user = done.result()
                    self.state = 2
                    asyncio.ensure_future(self.db.get_orders(self.user["id"])).add_done_callback(self.step)   # await #2
                case 2:
                    self.orders = done.result()
                    self.result.set_result({"user": self.user, "orders": self.orders})
        except Exception as e:
            self.result.set_exception(e)
```

CPython doesn't generate a class like this. A coroutine object keeps its own **frame**: the locals plus the position of the last instruction executed, which plays the role of `state`. `await` suspends the frame and hands control back to the task, and the task calls `coro.send(None)` to resume exactly where it stopped. `inspect.getcoroutinestate(coro)` shows it moving through `CORO_CREATED`, `CORO_SUSPENDED` and `CORO_CLOSED`.

<Mermaid chart={`stateDiagram-v2
  [*] --> S0 : call fetchUserData
  S0 --> Suspended1 : await get_user, loop is free
  Suspended1 --> S1 : user arrives
  S1 --> Suspended2 : await get_orders, loop is free
  Suspended2 --> S2 : orders arrive
  S2 --> [*] : return user + orders`} />

Between states, **the event loop is free to run other functions**. It just isn't running this one.

This explains two rules:
1. **Why `await` only works inside `async` functions:** `async def` is what makes the function a coroutine function: calling it returns a suspendable coroutine object instead of running the body. A plain `def` has no way to suspend its frame, so there are no states to suspend between. (🔧 The `python -m asyncio` REPL and Jupyter accept top-level `await`, because they run your input inside a coroutine.)
2. **Why blocking the loop is so bad:** a state machine only advances when the loop runs its next step. Block the loop and **every** in-flight state machine is frozen in place.

## 11. The cost of concurrency: shared state 🎓

Most concurrency bugs have a single root cause: **shared state (shared memory)**.

### Race 1: the lost update (threads)
Two threads each run `counter += 1` on a shared `counter = 0`. One increment is really **three steps**:
1. **read** `counter` into a CPU register,
2. **add 1** in the register,
3. **write** the register back to `counter`.

<Mermaid chart={`sequenceDiagram
  participant A as Thread A
  participant C as counter (memory)
  participant B as Thread B
  A->>C: t1 read 0 into register
  B->>C: t2 read 0 into register
  A->>A: t3 register = 1
  B->>B: t4 register = 1
  A->>C: t5 write 1
  B->>C: t6 write 1 (A's increment is lost)
  Note over C: expected 2, actual 1`} />

The steps interleave, so the final value is **1, not 2**. That's a **lost update**, one form of **race condition**: the result depends on timing.

🔧 **Seeing it in Python.** In CPython, `counter += 1` compiles to separate load, add and store bytecodes, so the same interleaving is possible. With the GIL it's **rare**, though: a thread only hands over the GIL at certain points in the interpreter loop, so this naive version usually gets lucky. On the free-threaded build, threads really run at the same time, and updates vanish at once:

```python title="plain_race.py"
import sys
import threading

counter = 0


def inc(n: int) -> None:
    global counter
    for _ in range(n):
        counter += 1


threads = [threading.Thread(target=inc, args=(1_000_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"GIL enabled: {sys._is_gil_enabled()}, expected 4000000, got {counter}")
```

```text title="Output: standard CPython 3.14.6 (GIL build), then free-threaded 3.14.6t; the second number changes on every run"
GIL enabled: True, expected 4000000, got 4000000
GIL enabled: False, expected 4000000, got 1305113
```

The GIL result is luck, not safety: nothing guarantees it, and it changes between Python versions. To make the race reproducible on **any** build, add an explicit yield point between the read and the write. `time.sleep(0)` releases the GIL and lets the other thread run, exactly like the t1–t6 diagram:

```python title="race_threads.py"
import threading
import time

counter = 0
lock = threading.Lock()


def unsafe(n: int) -> None:
    global counter
    for _ in range(n):
        value = counter          # 1. read
        time.sleep(0)            # yield point: lets the other thread run between read and write
        counter = value + 1      # 2 + 3. add, write back


def safe(n: int) -> None:
    global counter
    for _ in range(n):
        with lock:               # the whole read-modify-write is one critical section
            value = counter
            time.sleep(0)
            counter = value + 1


def run(target) -> int:
    global counter
    counter = 0
    threads = [threading.Thread(target=target, args=(10_000,)) for _ in range(2)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return counter


print(f"no lock:   expected 20000, got {run(unsafe)}")
print(f"with lock: expected 20000, got {run(safe)}")
```

```text title="Output: standard CPython 3.14.6 (GIL build); the first number changes on every run"
no lock:   expected 20000, got 10007
with lock: expected 20000, got 20000
```

### Race 2: async/await isn't immune (single thread)
"asyncio runs on one thread, so no races" is **false**. Every `await` that suspends is a point where **other code runs**.

```python title="the lesson's bug (withdraw.py)"
import asyncio

balance = 100


async def process_withdrawal(amount: int) -> None:
    await asyncio.sleep(0.01)              # the call to the payment provider


async def withdraw(amount: int) -> None:
    global balance
    if balance >= amount:                  # 1. check
        await process_withdrawal(amount)   # 2. yield: other tasks run here
        balance -= amount                  # 3. act on a stale check


async def main() -> None:
    await asyncio.gather(withdraw(100), withdraw(100))   # two concurrent tasks
    print(f"balance: {balance}")


asyncio.run(main())
```

```text title="Output"
balance: -100
```

(The lesson's JavaScript calls `withdraw(100)` twice without awaiting. In Python that would run nothing at all, because coroutines are lazy; `gather` wraps both in tasks and runs them concurrently.)

1. Call #1 checks `100 ≥ 100`, true, and awaits (yields).
2. Call #2 runs and checks `100 ≥ 100`, still true, and awaits.
3. Call #1 resumes: `balance = 0`.
4. Call #2 resumes: `balance = 0 − 100 = −100`, an invalid state.

**First principles:** any **check-then-act** sequence that spans a yield point (an `await` in asyncio, a GIL switch or preemption with threads) is a race, because the world can change between the check and the act.

### Fixes the lesson names 🎓

**Locks / mutexes (mutual exclusion):** only one thread may be inside the critical section; others wait for the lock.

```python title="Python (as in the lesson)"
import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    with lock:          # acquire; other threads block here until release
        counter += 1    # read-modify-write is now effectively one step
```

**Channels (Go):** instead of many goroutines touching one variable, they **send messages** to one goroutine that **owns** the variable. Only the owner mutates it, so there's nothing to race on.

```go title="Go: mutex vs channel ownership (Go)"
// Mutex
var mu sync.Mutex
var counter int
func inc() { mu.Lock(); counter++; mu.Unlock() }

// Channel: one owner goroutine, everyone else sends requests
incs := make(chan struct{})
go func() {
    n := 0
    for range incs { n++ } // only this goroutine ever touches n
}()
incs <- struct{}{}
```

🔧 Python's version of channel ownership is a `queue.Queue` (thread-safe) feeding one owner thread, or an `asyncio.Queue` feeding one owner task:

```python title="owner_queue.py"
import queue
import threading

incs: queue.Queue[int | None] = queue.Queue()
total = 0


def owner() -> None:
    global total
    while (item := incs.get()) is not None:   # only this thread ever touches total
        total += item


t = threading.Thread(target=owner)
t.start()

producers = [threading.Thread(target=lambda: [incs.put(1) for _ in range(10_000)]) for _ in range(4)]
for p in producers:
    p.start()
for p in producers:
    p.join()
incs.put(None)                                # sentinel: no more work
t.join()
print(f"total: {total}")
```

```text title="Output"
total: 40000
```

🔧 Run Go tests with `go test -race`. The race detector flags unsynchronized access at runtime. Python has no built-in equivalent; the free-threaded build plus a stress test (many threads, many iterations) is the practical way to shake out unsynchronized state.

### 🔧 Going deeper: fixing it in asyncio and in a real system

**Fix A: make check-and-act atomic in the event loop.** Don't put an `await` between the check and the write. Reserve first, compensate on failure:

```python
async def withdraw(amount: int) -> None:
    global balance
    if balance < amount:
        raise InsufficientFunds()
    balance -= amount                    # check + write with no await between: atomic on the event loop
    try:
        await process_withdrawal(amount)
    except BaseException:                # includes CancelledError: the request was abandoned mid-call
        balance += amount                # compensate if the side effect failed
        raise
```

**Fix B: an async lock** when the critical section must contain awaits. `asyncio.Lock` is built in and wakes waiters in FIFO order:

```python title="account_lock.py"
import asyncio

account_lock = asyncio.Lock()


async def withdraw(amount: int) -> None:
    global balance
    async with account_lock:                 # one withdraw at a time; the others wait here
        if balance < amount:
            raise InsufficientFunds()
        await process_withdrawal(amount)
        balance -= amount
```

Don't use a `threading.Lock` here: acquiring it while another coroutine on the same loop holds it blocks the loop thread, and the holder can never run to release it.

**Fix C, the one production needs: let the database decide.** Real balances live in a DB, and you run **several server instances**. An in-memory lock only protects one process, so make the operation atomic where the data lives:

```sql
-- One statement: the check and the write happen atomically inside the DB.
UPDATE accounts
SET balance = balance - $1
WHERE id = $2 AND balance >= $1
RETURNING balance;            -- 0 rows returned = insufficient funds (or no such account)
```

Alternatives: `SELECT ... FOR UPDATE` inside a transaction (pessimistic locking), or a `version` column checked on update (optimistic locking).

**Fix D, for processes sharing memory:** worker processes writing to `multiprocessing.Value` or `multiprocessing.shared_memory` run truly in parallel, with no GIL between them, and hit exactly the lost update from Race 1. Python has no atomic integers, so take a lock around the read-modify-write. A synchronized `Value` has one built in, but `counter.value += 1` doesn't use it for the whole operation: the read and the write each lock separately.

```python title="shared_counter.py"
from multiprocessing import Process, Value


def work(counter, n: int, use_lock: bool) -> None:
    for _ in range(n):
        if use_lock:
            with counter.get_lock():   # one process at a time for the read-modify-write
                counter.value += 1
        else:
            counter.value += 1         # read, add, write: three steps, even on a synchronized Value


if __name__ == "__main__":
    for use_lock in (False, True):
        counter = Value("i", 0)        # an int in shared memory, visible to every process
        procs = [Process(target=work, args=(counter, 50_000, use_lock)) for _ in range(4)]
        for p in procs:
            p.start()
        for p in procs:
            p.join()
        print(f"use_lock={use_lock}: expected 200000, got {counter.value}")
```

```text title="Output: standard CPython 3.14.6; the first number changes on every run"
use_lock=False: expected 200000, got 76499
use_lock=True: expected 200000, got 200000
```

The same applies to threads on the free-threaded build: shared counters and check-then-act still need a `threading.Lock`.

  R -->|"one loop, awaits inside"| B["asyncio.Lock / queue per key"]

## 12. Locks that span processes and machines ➕

Fix C works when the shared state is a database row; the harder case is mutual exclusion over something that **isn't** a single row (a cron job that must run once across 10 instances, a call to a third-party API that must not happen twice, a file being rebuilt), which needs a lock every instance can see. Row locks (`SELECT ... FOR UPDATE`) and optimistic version columns are covered in depth in [lesson 12](/docs/backend-first-principles/12-databases-postgres); this section covers the general-purpose distributed lock and its traps.

<Mermaid chart={`flowchart TD
  Q{"What must be exclusive?"}
  Q -->|"one DB row"| R["Atomic UPDATE, FOR UPDATE,<br/>version column (lesson 12)"]
  Q -->|"a named job or resource,<br/>and you already run Postgres"| A["Postgres advisory lock"]
  Q -->|"short critical section,<br/>occasional double run is tolerable"| S["Redis SET NX PX<br/>+ safe release"]
  Q -->|"double run is NOT tolerable"| F["Any lock + fencing token<br/>checked by the resource"]`} />

#### Postgres advisory locks: a named mutex in the database you already have ➕
**Problem.** A "rebuild search index" job is triggered by a cron on every instance. It must run on exactly one at a time.

**Mechanism.** Postgres lets you lock an **arbitrary 64-bit number** that means whatever your app decides. Postgres tracks it like any other lock, including deadlock detection, but attaches no meaning to it.
- `pg_try_advisory_lock(key)` returns true or false immediately (non-blocking).
- `pg_advisory_lock(key)` waits.
- **Session-level** locks last until `pg_advisory_unlock` or the connection closes. **Transaction-level** (`pg_advisory_xact_lock`) locks are released automatically at commit or rollback.

```python title="run_exclusive.py"
from collections.abc import Awaitable, Callable

import asyncpg


async def run_exclusive(pool: asyncpg.Pool, name: str, job: Callable[[asyncpg.Connection], Awaitable[None]]) -> bool:
    async with pool.acquire() as conn:                 # ONE connection for lock, work and unlock
        async with conn.transaction():                 # COMMIT on success, ROLLBACK on error: both release the lock
            ok = await conn.fetchval(
                "SELECT pg_try_advisory_xact_lock(hashtextextended($1, 0))", name)   # text name to 64-bit key
            if not ok:
                return False                           # another instance holds it
            await job(conn)
            return True
```

**Why it's often the best choice.** No new infrastructure, and the lock dies with the connection: if the instance crashes, Postgres releases the lock when the TCP session ends. There's no TTL to guess.

**Edge cases.**
- **Session locks and connection pools don't mix.** Lock on one pooled connection and unlock on another, and the unlock silently does nothing. Transaction-level locks avoid this. PgBouncer in transaction mode breaks session advisory locks entirely (lesson 21).
- Holding a transaction open for a long job keeps a snapshot alive, which delays vacuum. For hour-long jobs, use a lease row with an expiry instead.
- Keys share one namespace across the database. Derive them from a prefixed name (`'job:reindex'`) so two features don't collide.

#### A Redis lock done correctly (single instance) ➕
**Problem.** You don't have a shared Postgres (or the lock is very hot) and reach for Redis.

**Mechanism.** Acquire with **one atomic command**: set the key only if absent (`NX`) with an expiry (`PX`) and a **random token** as the value. Release with a **compare-and-delete**, so you only delete the lock if it's still yours.

```python title="redis_lock.py"
import secrets
from collections.abc import Awaitable, Callable

from redis.asyncio import Redis

RELEASE = """if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end"""


async def with_redis_lock[T](redis: Redis, key: str, ttl_ms: int, fn: Callable[[], Awaitable[T]]) -> T | None:
    token = secrets.token_hex(16)
    ok = await redis.set(key, token, px=ttl_ms, nx=True)   # atomic: exists-check + set + expiry
    if not ok:
        return None                                       # someone else holds it
    try:
        return await fn()
    finally:
        await redis.eval(RELEASE, 1, key, token)          # never DEL blindly
```

redis-py ships the same pattern as `redis.lock(key, timeout=...)`: a random token plus Lua scripts for release and extend.

**Why each detail exists.**
- **Expiry:** without it, a crashed holder keeps the lock forever.
- **Random token + compare-and-delete:** holder A pauses longer than the TTL, the lock expires, B acquires it, then A finishes and runs `DEL`, deleting **B's** lock. The token makes A's release a no-op. (Redis 8.4 adds a `DELEX ... IFEQ` command that does the same without a script.)

**Edge case.** Redis replication is **asynchronous**. If the primary acknowledges your lock and crashes before replicating it, the promoted replica has no lock, and a second client acquires it. A single-instance Redis lock is an **efficiency** lock (prevents most duplicate work), not a **correctness** guarantee.

#### Redlock, and why it's debated ➕
**What it is.** Redis's documented algorithm for surviving node failure: run **N independent Redis primaries** (typically 5), try to acquire the same key with the same token on all of them with short per-node timeouts, and consider the lock held only if you got a **majority** (3 of 5) **and** the elapsed time is less than the TTL. Validity = TTL minus elapsed time minus a clock-drift allowance.

**The critique (Martin Kleppmann, 2016).** Redlock's safety depends on **timing assumptions**: bounded network delay, bounded process pauses and clocks that advance at roughly the same rate. Real systems violate all three:
- a **GC pause or VM freeze** longer than the TTL lets the lock expire while the holder still believes it owns it,
- a **wall-clock jump** on a Redis node (NTP correction, manual change) can expire a key early, and Redis TTLs aren't based on a monotonic clock.

In each case two clients act as holders at once. Kleppmann's conclusion: if you need a lock for **efficiency**, a single Redis instance is enough; if you need it for **correctness**, Redlock isn't sufficient, and you need fencing (below) or a consensus system (etcd, ZooKeeper, a database).

**The counterpoint (antirez, Redis's author)** argues the assumptions are reasonable in practice and that fencing needs a resource that can check tokens, in which case that resource could provide the mutual exclusion itself. The Redis docs now link both and **recommend fencing tokens** for long operations. The practical takeaway is the same either way: **no lease-based lock is safe on its own against a paused holder.**

#### Fencing tokens: making a lock safe against paused holders ➕
**Problem.** Every lease-based lock (Redis, Redlock, a lease row, the S3 lease in [object storage Part 1](/docs/backend-first-principles/24-object-storage-part-1)) has the same hole: holder A pauses, the lease expires, B takes over, A wakes up and writes.

<Mermaid chart={`sequenceDiagram
  participant A as Client A
  participant L as Lock service
  participant B as Client B
  participant S as Storage (checks tokens)
  A->>L: acquire
  L-->>A: granted, token 33
  Note over A: long GC pause, lease expires
  B->>L: acquire
  L-->>B: granted, token 34
  B->>S: write with token 34
  S-->>B: ok, highest seen = 34
  A->>S: write with token 33 (stale)
  S-->>A: rejected, 33 is lower than 34`} />

**Mechanism.** The lock service hands out a **monotonically increasing number** with each grant. Every write to the protected resource carries the token, and the **resource** rejects any token lower than the highest it has seen. Safety now lives in the resource's check, not in timing.

```sql title="fenced write in Postgres"
-- the lock grant: an atomic counter
UPDATE locks SET token = token + 1, holder = $2, expires_at = now() + interval '30 seconds'
WHERE name = $1 AND (expires_at < now() OR holder = $2)
RETURNING token;

-- every protected write carries the token; stale holders match 0 rows
UPDATE reports SET body = $1, fence = $2
WHERE id = $3 AND fence < $2;
```

**Edge case.** Fencing only works if the **resource can check the token**. A third-party API that sends an email can't, so for those, combine the lock with an **idempotency key** sent to the provider.

## 13. Deadlock, livelock and starvation in application code ➕

Locks, pools and semaphores fix races but introduce the opposite failure, where tasks **stop making progress**; database deadlocks (SQLSTATE `40P01`, lock ordering) are covered in [lesson 16](/docs/backend-first-principles/16-error-handling-fault-tolerance), and this section covers the shapes that appear in your own Python code, where nothing detects them for you.

#### The four conditions, and why breaking one is enough ➕
A deadlock needs all four **Coffman conditions** at once: **mutual exclusion** (a resource has one holder), **hold and wait** (holding one resource while waiting for another), **no preemption** (nobody can take it away) and **circular wait** (A waits for B, which waits for A). Every prevention technique removes one: lock ordering removes circular wait, timeouts add preemption, acquiring everything up front removes hold-and-wait.

#### Pool-exhaustion deadlock: the one most async Python services hit ➕
**Problem.** Under load, every request hangs forever, CPU is idle, the database shows idle-in-transaction sessions, and there's no error.

**Why.** A function holds a pooled connection (inside a transaction) and, deeper in the call stack, a helper does `pool.execute(...)`, which needs a **second** connection. With a pool of 10 and 10 concurrent requests, each holds one connection and waits for another that will never come free. That's hold-and-wait plus circular wait on the pool.

```python title="the bug"
async def mark_paid(pool: asyncpg.Pool, order_id: str) -> None:
    async with pool.acquire() as conn, conn.transaction():      # holds connection 1 of 10
        await conn.execute("UPDATE orders SET status = $1 WHERE id = $2", "paid", order_id)
        await audit.log("order.paid", order_id)                 # audit.log uses pool.execute: needs ANOTHER connection
```

**Fixes.**
- **Pass the transaction connection down** (`audit.log(conn, ...)`), so a unit of work uses exactly one connection. Repositories that accept an optional connection (or a SQLAlchemy `AsyncSession`) make this natural.
- Give pool acquisition a timeout, so a wait for a connection **fails** instead of hanging: `pool.acquire(timeout=5)` in asyncpg (whose default is to wait forever), `pool_timeout` in SQLAlchemy (30 s by default). That turns a silent deadlock into a visible error (preemption).
- Alert on "pool waiting count above 0 for N seconds".

#### Async-lock deadlock: non-reentrant locks and lock ordering ➕
**Problem.** With the `asyncio.Lock` from section 11, a function that holds `account_lock` calls a helper that also does `async with account_lock:`. The helper waits for a lock its own caller holds, and the caller waits for the helper: it hangs forever.

**Why.** `asyncio.Lock` is **non-reentrant**: it doesn't know the second request comes from the same logical task (and unlike `threading.RLock`, asyncio has no reentrant version). And with two locks, the classic **ordering** deadlock appears: transfer(A, B) locks A then B, transfer(B, A) locks B then A.

**Fixes.**
- Never call code that takes the same lock while holding it. Structure it as an outer function that locks and an inner `..._unlocked` function that assumes the lock is held.
- When you need several locks, **acquire them in a global order** (sort by ID), exactly as the database lesson does for rows.
- Give every acquire a **timeout** (`async with asyncio.timeout(1): await lock.acquire()`, or `lock.acquire(timeout=1)` for a `threading.Lock`), so a bug becomes an error with a stack trace instead of a hung request.

The ordering deadlock, reproduced with two threads; `acquire(timeout=1)` turns the hang into output:

```python title="deadlock.py"
import threading
import time

a, b = threading.Lock(), threading.Lock()


def transfer(name: str, first: threading.Lock, second: threading.Lock) -> None:
    with first:
        time.sleep(0.1)                         # widen the window so both threads hold one lock
        if second.acquire(timeout=1):           # a timeout turns a silent hang into a visible failure
            second.release()
            print(f"{name}: done")
        else:
            print(f"{name}: gave up waiting, deadlock")


t1 = threading.Thread(target=transfer, args=("transfer(A, B)", a, b))
t2 = threading.Thread(target=transfer, args=("transfer(B, A)", b, a))
for t in (t1, t2):
    t.start()
for t in (t1, t2):
    t.join()
```

```text title="Output"
transfer(B, A): gave up waiting, deadlock
transfer(A, B): gave up waiting, deadlock
```

The fix, for asyncio locks:

```python title="ordered multi-lock"
import asyncio
import contextlib
from collections.abc import Awaitable, Callable, Iterable


async def with_locks[T](locks: dict[str, asyncio.Lock], ids: Iterable[str], fn: Callable[[], Awaitable[T]]) -> T:
    async with contextlib.AsyncExitStack() as stack:
        for key in sorted(set(ids)):                    # global order + no duplicate locking
            await stack.enter_async_context(locks[key])
        return await fn()
# transfer(A, B) and transfer(B, A) both lock A first: no cycle is possible
```

#### Livelock: everyone retries, nobody wins ➕
**Problem.** Ten workers try an optimistic update (version check) or a lock, all fail, all wait exactly 100 ms, all retry together, and all fail again. Every worker is busy and nothing completes.

**Why.** Retrying with **deterministic** delays keeps colliding tasks synchronized. Unlike a deadlock, everyone is running, which is why it often looks like "high CPU, zero throughput".

**Fix.** **Randomized** backoff (jitter), as in the `updateJson` retry in [object storage Part 1](/docs/backend-first-principles/24-object-storage-part-1) and the retry helper in lesson 16, plus a cap on attempts. Randomness breaks the symmetry, so one task wins each round.

#### Starvation: progress for most, never for some ➕
**Problem.** The system makes progress overall, but one kind of task waits indefinitely.

**Three shapes you'll meet in asyncio:**
1. **Loop starvation.** A coroutine that loops over awaits that never suspend (coroutines that return immediately, futures that are already done) never lets the loop poll, so IO callbacks never run (section 7).
2. **Executor starvation.** Slow `to_thread` jobs (hashing, file IO, a sync SDK) occupy every thread of the default executor, and DNS lookups wait behind them (section 7).
3. **Unfair queues.** A semaphore or job queue that serves a "priority" lane first can starve the normal lane forever under sustained load. Use **FIFO** within a lane (the semaphore above wakes waiters in arrival order) and **weighted** sharing between lanes, for example serving one normal job for every four priority jobs.

**Detection.** Starvation hides behind healthy averages. Track the **age of the oldest waiting item** per queue, not just its length, and alert on it.

## 14. Recap 🎓

- **IO bound, high-concurrency workloads** (web servers, API gateways, services that call many other services) → lightweight concurrency: **async/await on an event loop**, **goroutines**, **Java virtual threads**. These beat a thread-per-request model.
- **CPU bound workloads** (number crunching, string, image and video manipulation, anything that keeps cores busy) → **threads running in parallel** on multiple cores, not an event loop.
- **Concurrency** keeps the program productive and stops it from wasting CPU while it waits on IO (network card, stdin/stdout, external APIs, databases).
- **Parallelism** uses several cores to do several things at the same instant.
- **Most backend work leans on concurrency.** Some cases need both, or mostly parallelism. If you understand the difference, you can pick the right tool.
- 🔧 **Python threads** are real OS threads: they overlap IO waits well, but with the GIL only one runs Python bytecode at a time. Free-threaded CPython (3.14t) removes that limit; processes sidestep it.
- ➕ **asyncio ordering:** one FIFO ready queue; coroutines are lazy and `create_task` only schedules them. Awaiting a coroutine that doesn't suspend isn't a yield; `await asyncio.sleep(0)` is. Chunk modest CPU work with it.
- ➕ **Measure saturation with loop utilization** (time not spent idle in `select()`), not only lag, and shed low-priority load before the loop hits 100%.
- ➕ **Cancel what you start:** a `TaskGroup` per group of concurrent tasks cancels siblings on the first failure; `gather` doesn't. Cancel the losers of a race. Never swallow `CancelledError`, and remember a thread can't be cancelled. asyncpg cancels the server-side query for you; otherwise use `pg_cancel_backend`. Cancellation is never rollback.
- ➕ **Cap concurrency per downstream, process-wide**, with a semaphore that has a bounded queue and wait time.
- ➕ **Place CPU work deliberately:** threads for GIL-releasing C code (or anything on free-threaded builds), a `ProcessPoolExecutor` for pure-Python work, child processes for native or untrusted work, a queue plus worker service for long jobs.
- ➕ **Cross-machine exclusion:** advisory locks if you have Postgres, a token-checked Redis lock for efficiency, and **fencing tokens** whenever a double run is unacceptable (Redlock alone isn't enough).
- ➕ **Progress failures:** pool-exhaustion and non-reentrant-mutex deadlocks, livelock from synchronized retries, starvation from unfair queues. Timeouts, lock ordering, jitter and FIFO queues prevent them.

## Interview questions

1. **Concurrency vs parallelism in one sentence each?** **Concurrency is structuring work so many tasks make progress by interleaving, even on one core; parallelism is executing several tasks at the same instant on several cores.**
2. **Why does a synchronous server waste about 95% of its resources?** **A typical request spends about 250 ms waiting on 5 network calls and about 10 ms on CPU; during the waits the CPU sits idle, and 100 ms idle is about 300 million instructions not executed.**
3. **What happens when a thread does a blocking read on a socket?** **The OS marks it blocked and switches to another thread; when the data arrives it becomes runnable and resumes once the scheduler picks it.**
4. **Three overheads of OS threads?** **Memory (a per-thread stack, about 8 MB reserved on Linux), creation (a syscall plus kernel setup, µs to ms) and context switches (save and restore registers and bookkeeping, about 1–10 µs each).**
5. **Why is an event loop more efficient for IO bound work?** **One thread, no context switches and no per-request stacks; the OS (epoll/kqueue) reports which sockets are ready and the loop runs their callbacks.**
6. **What's the event loop's main constraint?** **Never block it: any long CPU task freezes every request, timer and IO callback until it finishes.**
7. **What does `await` actually do?** **If the awaited thing isn't ready, it suspends the current coroutine (its frame keeps locals and position), returns control to the event loop, and the task resumes it when the awaited future completes. If it's already done, execution simply continues.**
8. **Why can `await` only appear in `async` functions?** **`async def` makes the function a coroutine function whose frame can be suspended and resumed; a plain function has nothing to suspend.**
9. **How do goroutines differ from OS threads?** **The Go runtime schedules them onto `GOMAXPROCS` OS threads; they start with small growable stacks and switch in user space, so millions are feasible, and network waits use a netpoller instead of blocking a thread.**
10. **Can single-threaded async code have race conditions?** **Yes: any check-then-act that spans an `await` can interleave with other calls, as in the withdraw example that ends at −100.**
11. **How do you fix a balance race across several server instances?** **Make it atomic in the database: `UPDATE ... SET balance = balance - x WHERE balance >= x` (or row locks or optimistic versioning); in-process locks can't see the other instances.**
12. 🔧 **What runs on asyncio's default executor, and why does that matter?** **`asyncio.to_thread`, `run_in_executor(None, ...)` and `loop.getaddrinfo` (DNS for outbound connections) share one thread pool, so many slow `to_thread` jobs such as password hashing can starve DNS lookups; give heavy work its own executor or a process pool.**
13. 🔧 **How would you run a CPU-heavy task in a Python API?** **On the standard GIL build, a reusable `ProcessPoolExecutor` sized to the cores with a bounded queue (threads only help when C code releases the GIL, or on free-threaded 3.14t); for long jobs, a separate worker service behind a message queue.**
14. ➕ **In what order do a `call_soon` callback, a new `create_task` coroutine and a `call_later(0)` callback run?** **In the order they were added to the single FIFO ready queue: `call_soon` and the task's first step in scheduling order; the zero-delay timer only joins the queue after the next poll, so it runs after them. Calling a coroutine function without awaiting or scheduling it runs nothing.**
15. ➕ **Why doesn't `await some_async_helper()` inside a long loop keep the server responsive?** **Awaiting a coroutine that never suspends runs it straight through without returning to the loop, so IO callbacks still can't run. Yield with `await asyncio.sleep(0)`, or move the work to a process.**
16. ➕ **What does event loop utilization tell you that event-loop lag doesn't?** **How close the loop is to saturation (active time ÷ total time, where idle is time spent in `select()`) before latency explodes; it's the better signal for autoscaling and load shedding.**
17. ➕ **How do you stop the other calls when one call in an `asyncio.gather` fails?** **Use a `TaskGroup` instead: the first failure cancels every sibling and raises an `ExceptionGroup`. `gather` raises the first error but leaves the others running.**
18. ➕ **Why isn't a per-call concurrency limit enough to protect a downstream?** **Concurrent requests multiply it; when the dependency slows down, in-flight calls grow with latency (Little's law). Use a process-wide semaphore per dependency with a bounded queue and wait time.**
19. ➕ **Threads vs worker processes vs a separate service for CPU work?** **Threads for C code that releases the GIL (or any code on free-threaded builds): cheap, shared memory, but unkillable; a process pool for pure-Python work, and child processes for native or untrusted code that needs its own crash and memory domain; a queue plus worker service for long or bursty jobs that should scale and fail independently.**
20. ➕ **Why is Redlock controversial, and what makes any lease lock safe?** **Its safety assumes bounded pauses, network delays and clock drift; a GC pause or clock jump can give two clients the lock. Fencing tokens, checked by the protected resource, make stale holders' writes fail.**
21. ➕ **Describe a deadlock that needs no database locks at all.** **Pool exhaustion: every request holds a pooled connection inside a transaction and waits for a second one from the same pool. Fix it by passing the transaction client down and setting a connection-acquire timeout.**
22. ➕ **Livelock vs starvation?** **Livelock: everyone is active but no one progresses, typically synchronized retries (fix with jitter). Starvation: the system progresses but some task never gets its turn, such as an unfair priority queue or a coroutine that never suspends (fix with FIFO and fair scheduling).**
