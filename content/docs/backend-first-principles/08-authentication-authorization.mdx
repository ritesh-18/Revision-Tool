**Authentication (authN) answers "who are you?"** in a given context: a platform, an operating system, a phone. It assigns an **identity** to a **subject**.
**Authorization (authZ) answers "what can you do?"** in that context: your capabilities, or **permissions**.

Everything in this lesson is machinery for answering those two questions reliably, at scale, against attackers.

## 1. A short history of authentication 🎓

The history isn't trivia. Every era solved the previous era's failure, and each solution maps to something you still build today.

<Mermaid chart={`flowchart TD
  P["Pre-industrial<br/>implicit trust: elder vouches, handshake"] -->|"doesn't scale beyond the village"| S["Medieval<br/>wax seals: something you HAVE"]
  S -->|"forgery = first bypass attack"| T["Industrial / telegraph<br/>passphrases: something you KNOW"]
  T --> M["1961 mainframes (CTSS)<br/>passwords, stored in plain text"]
  M -->|"password file printed"| H["Hashing<br/>irreversible, fixed length"]
  H --> C["1970s<br/>Diffie-Hellman, asymmetric crypto, PKI, Kerberos tickets"]
  C --> F["1990s internet<br/>MFA: know + have + are, biometrics"]
  F --> X["21st century<br/>OAuth, JWT, zero trust, passwordless (WebAuthn)"]
  X --> N["Future candidates<br/>decentralized identity, behavioral biometrics, post-quantum crypto"]`} />

### Pre-industrial: implicit trust
Identity **was** recognition. A respected person (the lesson's example: a **village elder**) vouched for you, and a **handshake** sealed the deal as mutual recognition. It was authentication based on **human, contextual trust**.
**Why it failed:** as populations grew and dealings went beyond familiar circles, the elder's word meant nothing to strangers. Trust had to work **independently of personal acquaintance**. That's the move from **implicit** to **explicit** authentication.

### Medieval: seals, "something you have"
A **wax seal** with a unique pattern was pressed onto letters and agreements. It acted as a signature and was the first widely adopted **authentication token**: a physical representation of identity based on **possession**.
**Failure mode:** seals could be **forged**. The lesson calls this the first recorded **authentication bypass attack** (getting past authentication with malicious intent). The response was more sophisticated marks, **watermarks** and **encoded messages** in trade documents, the seed of cryptographic thinking.

### Industrial era: passphrases, "something you know"
The **telegraph** became critical infrastructure and messages needed validation. Operators used **pre-agreed passphrases**, an early **shared secret**. They were **static**: one string, agreed once.
The principle shifted from *something you have* (which can be stolen or forged) to *something you know*.

### 1961, mainframes: the first computer passwords
At **MIT's Project MAC**, the **Compatible Time-Sharing System (CTSS)** let multiple users share one computer without seeing each other's data, so it introduced **passwords**.
They were stored in **plain text**. The weakness became obvious when someone **printed the password file**. That incident is the origin of the rule *never store passwords in plain text*, and of **password hashing**.
🔧 There were actually two famous CTSS incidents: in 1962 a researcher requested a printout of the password file to get more computer time, and in 1966 a bug swapped the message-of-the-day file with the password file, so every user who logged in saw everyone's password.

**Hashing**, as the lesson defines it: an algorithm takes a plain-text string and returns a **fixed-length** string. The length doesn't depend on the input (3 characters or 100). The **same input always gives the same output**, and you **can't reverse it**. Authentication started aligning with the **CIA triad**: confidentiality, integrity, availability.

### 1970s: asymmetric cryptography
**Whitfield Diffie and Martin Hellman**'s **key exchange** let two parties establish a shared secret **over an untrusted channel**. It introduced **asymmetric (public-key) cryptography**, the backbone of modern authentication protocols and of **PKI** (public key infrastructure).
The same era produced **Kerberos**, with **ticket-based** authentication: a **trusted third party** issues tickets that prove both the user's and the service's identity. That's the precursor to today's **token-based** systems.

### 1990s: the internet and MFA
Plain username + password wasn't strong enough against **brute-force** and **dictionary** attacks. **Multi-factor authentication** combines independent factors:

| Factor | Examples |
|---|---|
| Something you **know** | password, PIN |
| Something you **have** | smart card, OTP generator |
| Something you **are** | fingerprint, retina scan |

**Biometrics** (pattern recognition and statistical models over physical traits) were a breakthrough, but brought **false positives and negatives** and the problem of keeping **biometric templates** secure (you can't rotate a fingerprint).

### 21st century and the future
Cloud, mobile and API-based architectures needed more: **OAuth / OAuth 2.0**, **JWTs**, **zero-trust architecture**, and **passwordless** authentication like **WebAuthn**, which uses a public/private key pair held in hardware.
Candidates for the future: **decentralized identity** (for example on blockchains, still experimental), **behavioral biometrics**, and **post-quantum cryptography**: algorithms that stay secure once large quantum computers can break today's RSA and elliptic-curve schemes.

### 🔧 Going deeper: storing passwords correctly today

**Problem:** a database leak shouldn't reveal passwords. Plain text obviously fails. But a **fast** hash (SHA-256) fails too: GPUs compute billions of SHA-256 hashes per second, and identical passwords give identical hashes, so precomputed tables crack them.

**Mechanism:** a **slow, salted, memory-hard** password hash.
- A random **salt** per user makes identical passwords hash differently and kills precomputed tables.
- A **work factor** (time and memory cost) makes each guess expensive. Memory hardness defeats cheap GPU/ASIC parallelism.

OWASP's current recommendation is **Argon2id with at least 19 MiB of memory, 2 iterations, parallelism 1** (scrypt, bcrypt with work factor ≥ 10, or PBKDF2-HMAC-SHA256 with ≥ 600,000 iterations are fallbacks).

```ts title="password.ts"
import argon2 from 'argon2';

export const hashPassword = (pw: string) =>
  argon2.hash(pw, { type: argon2.argon2id, memoryCost: 19456, timeCost: 2, parallelism: 1 });
// → "$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>": salt + params are stored inside the string

export const verifyPassword = (stored: string, pw: string) => argon2.verify(stored, pw);
```

Edge cases: **bcrypt silently ignores bytes after 72**; upgrade old hashes on the next successful login (`argon2.needsRehash`) instead of forcing resets.

### Accepting passwords: length, blocklists and breach checks ➕

Storing a password well doesn't help if the password itself is `Password1!`. Slow hashing only raises the cost per guess; attackers guess the **most common and already-leaked passwords first**, and those fall in seconds whatever the hash.

#### Length and a blocklist instead of composition rules ➕

**Problem.** "At least one uppercase, one digit, one symbol" policies produce `Summer2026!`, which meets every rule and is near the top of every attacker's wordlist.

**Why it happens.** Composition rules push people toward predictable patterns (capital first, digit and symbol at the end). What actually makes a guess expensive is the size of the space the attacker must search, and length grows that space far faster than character classes do.

**Mechanism.** NIST SP 800-63B (revision 4) sets the current baseline for verifiers:
- minimum **15 characters** when the password is the **only** factor, **8** when it's part of MFA;
- allow at least **64 characters**, and accept spaces and Unicode (count each code point as one character);
- **no composition rules** and **no forced periodic changes**, but force a change when there's evidence of compromise;
- compare every new password against a **blocklist** of common, expected and breached passwords, plus context words (the site name, the username).

**Implementation.**

```ts title="password-policy.ts"
import { z } from 'zod';

export const NewPassword = (ctx: { email: string; mfaEnabled: boolean }) =>
  z.string()
    .transform(p => p.normalize('NFKC'))                       // same password typed on different keyboards
    .refine(p => [...p].length >= (ctx.mfaEnabled ? 8 : 15), 'Too short')
    .refine(p => [...p].length <= 128, 'Too long')              // a cap stops hashing-DoS with 1 MB passwords
    .refine(p => !p.toLowerCase().includes(ctx.email.split('@')[0].toLowerCase()), 'Contains your username')
    .refine(p => !COMMON_PASSWORDS.has(p.toLowerCase()), 'This password is too common');
```

**Edge cases.** Normalize the same way at sign-up and at login, or a user with an accented character can't log in from another device. Keep the maximum generous (64 to 128); Argon2 cost doesn't depend much on length, but an unbounded field lets a client send megabytes per attempt. Show the user *why* a password was rejected; this is sign-up, not login, so specific messages are fine.

#### Screening against breached passwords without sending them anywhere ➕

**Problem.** Credential stuffing replays username and password pairs leaked from **other** sites. A password that appears in a breach corpus is effectively public, however long it is.

**Mechanism.** The Have I Been Pwned **range API** uses **k-anonymity**: hash the candidate with SHA-1, send only the **first 5 hex characters**, and receive every leaked-hash suffix with that prefix plus how often it was seen. The comparison happens locally, so neither the password nor its full hash leaves your server. No API key is needed, and an `Add-Padding: true` header pads responses so their size doesn't hint at the prefix.

```ts title="breach-check.ts"
import { createHash } from 'node:crypto';

export async function timesBreached(password: string): Promise<number> {
  const sha1 = createHash('sha1').update(password, 'utf8').digest('hex').toUpperCase();
  const prefix = sha1.slice(0, 5), suffix = sha1.slice(5);
  const res = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`, {
    headers: { 'Add-Padding': 'true' },
    signal: AbortSignal.timeout(2000),
  });
  if (!res.ok) throw new Error('breach check unavailable');
  for (const line of (await res.text()).split('\n')) {
    const [s, count] = line.trim().split(':');
    if (s === suffix) return Number(count);                      // padded rows have count 0
  }
  return 0;
}
```

**Edge cases.**
- Decide the failure mode when the API is down: most systems **fail open** (allow the password, log, re-check later) so sign-up doesn't depend on a third party. For strict environments, mirror the downloadable dataset internally.
- SHA-1 is fine here: it's only an index into a public dataset, not how you store the password.
- Check at sign-up and password change, and optionally at login (the plain password is only available then) to flag accounts whose existing password has since appeared in a breach and ask for a change.

## 2. The three building blocks 🎓

Before the auth types, the lesson introduces three components that appear in every flow: **sessions, JWTs and cookies**.

### 2.1 Sessions

**Problem:** HTTP is **stateless by design**. Each request is an isolated interaction with **no memory** of earlier ones; every request must carry everything the server needs. That was fine for the early web of static pages you just read.
Once the web became dynamic, statelessness became the bottleneck: an e-commerce site must remember **your cart**, and you must **stay logged in** while moving between pages. The web needed **stateful interactions**.

**Mechanism: a session**, a temporary, server-side context per user.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant B as Browser
  participant S as Server
  participant R as Session store (Redis)
  B->>S: POST /login (credentials)
  S->>S: verify credentials
  S->>R: SET sess:8f3a... = userId, role, cart (TTL 15 min)
  S-->>B: Set-Cookie: sid=8f3a...
  B->>S: GET /cart (Cookie: sid=8f3a...)
  S->>R: GET sess:8f3a...
  R-->>S: userId, role, cart
  S-->>B: 200 cart contents
  Note over R: after the TTL the key expires, next request must log in again`} />

1. **Creation:** on login, the server generates a **unique session ID** and stores it with the user's data (role, name, cart, "is authenticated") in a **persistent store**.
2. **Transport:** the session ID is sent to the browser **as a cookie**. Every later request carries the cookie, so the server can look the session up.
3. **Expiry:** sessions are **short-lived**. If the expiry is 15 minutes, a request after that finds no valid session, and a new one has to be created.

**How session storage evolved:**

| Stage | Where sessions lived | Problem it solved / created |
|---|---|---|
| Early | **Files** on the server | Simple, but didn't scale with users |
| Next | **Database** | Faster lookups, survives server restarts |
| Distributed | **Redis / Memcached** (in-memory: RAM instead of disk) | Much faster than DB lookups, shared by many servers |

Sessions are still used today for exactly this purpose.

### 2.2 JWTs (JSON Web Tokens)

**Problem (mid-2000s):** web apps became **globally distributed**, and stateful sessions hurt:
- **Memory:** holding session data for millions of users is expensive.
- **Replication:** servers in different regions must **synchronize** sessions, adding **latency** and **consistency** problems.

**Mechanism:** move the state **into the token**. JWTs (formalized in **2015**) are a **stateless** way to transfer **claims** between parties. The key innovation is that they're **self-contained**: user data (ID, role) **plus a cryptographic signature**, in one Base64-encoded string.

A JWT has three dot-separated parts (the lesson demos this on **jwt.io**):

<Mermaid chart={`flowchart LR
  H["Header<br/>alg: HS256, typ: JWT"] --> D1["."]
  D1 --> P["Payload (claims)<br/>sub, iat, name, role"]
  P --> D2["."]
  D2 --> SG["Signature<br/>HMAC-SHA256(header.payload, secret)"]`} />

| Part | Holds |
|---|---|
| **Header** | Metadata about the token itself, mainly the **signing algorithm** |
| **Payload** | The data. **`sub`** (subject: the user ID, from your DB or an auth provider), **`iat`** (issued at), and optional fields like `name` or `role` (admin, member, editor, viewer) |
| **Signature** | Proves **you issued it** and that it **wasn't tampered with**. Made with a secret key only you hold |

**Why tampering fails (first principles):** the signature is computed over the header and payload with your secret. If anyone edits the payload (say, `role: admin`), recomputing the signature with your secret gives a different value, so verification fails. They can't produce the right signature without the secret.

**Advantages the lesson lists:**
1. **Statelessness:** no server-side storage cost; verification is light and happens on every request.
2. **Scalability:** in microservice and distributed systems, a cookie issued by one server can't be used by a service on another domain. A JWT can be sent to any service, and every instance holding the key can verify it. Scale to many instances without shared session storage.
3. **Portability:** small, URL-friendly, Base64. It fits in a cookie, a header, a URL, or other small storage (local storage works but the lesson says you **shouldn't** use it).

**Challenges:**
1. **Token theft:** whoever holds your JWT **is you** until it expires. The server can't invalidate one token, except by **changing the secret**, which logs out **every** user.
2. **Revocation:** there's no record of issued tokens, so you can't revoke a user's access (compromised account, malicious activity) before expiry.

**The hybrid fix and its paradox:** verify the JWT as usual, then also check a **blacklist** in Redis or the DB to block specific tokens or users. But now every request does a storage lookup again, which raises the obvious question: **why not just use stateful sessions**, which are considered more secure and give revocation for free? The industry argues about this a lot.

**The lesson's advice:** for **medium to large production systems**, use an **auth provider** (the lesson mentions **Auth0** and **Clerk**). Choosing algorithms, hashing, salting and getting every flow right is *their* problem. **Implement your own auth while learning** to understand the trade-offs, but in production go with a provider unless you're very confident in your auth workflows.

### 2.3 Cookies

A **cookie** is a way for the **server to store a small piece of information in the user's browser**. Two properties make it useful for auth:
- **Scoping:** a cookie is only accessible to the server (domain) that set it. A server can't see other servers' cookies. This is a browser security feature.
- **Automatic sending:** once set, the browser attaches it to **every later request** to that server.

So the server can set a cookie containing a session ID or a JWT after login, and the browser returns it on every request **without any client code**. The whole token round trip is driven from the server.

### 🔧 Going deeper: cookie attributes that make this safe

```http
Set-Cookie: __Host-sid=8f3a...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=900
```

| Attribute | Threat it blocks | Mechanism |
|---|---|---|
| `HttpOnly` | **XSS** stealing the token | `document.cookie` can't read it; the browser still sends it |
| `Secure` | Network sniffing / MITM | Sent over HTTPS only |
| `SameSite=Lax` (or `Strict`) | **CSRF** | Not sent on cross-site subrequests (Lax still allows top-level GET navigation). Chromium-based browsers default to Lax when it's missing, so set it explicitly. `None` requires `Secure` |
| `Max-Age` | Tokens living forever | Expires after N seconds; takes precedence over `Expires` |
| `__Host-` prefix | A subdomain overwriting your cookie | Browser only accepts it with `Secure`, `Path=/` and **no** `Domain` |

This is the main reason the lesson prefers cookies over local storage for browser tokens: JavaScript (and therefore any injected script) can read local storage, but not an HttpOnly cookie.

## 3. Stateful authentication 🎓

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Browser
  participant S as Server
  participant R as Redis
  C->>S: email + password
  S->>S: check credentials
  S->>R: store sessionId with user data + expiry
  S-->>C: Set-Cookie (HttpOnly) sessionId
  loop every later request
    C->>S: request + cookie
    S->>R: does sessionId exist? not expired?
    R-->>S: user data
    S-->>C: response (or 401)
  end`} />

1. The client sends credentials (username or email + password).
2. The server checks them. If valid, it creates a **session ID** and bundles it with the user's data.
3. It stores the bundle, usually in **Redis** (fast reads compared with a traditional DB).
4. It returns the session ID in an **HttpOnly cookie**, so JavaScript can't read it.
5. Every following request carries the cookie. The server looks up the ID in Redis, checks existence and expiry, loads the user, and authorizes the call.

The session ID can be any **cryptographically random string**.

### 🔧 Implementation (Express + Redis)

```ts title="session-auth.ts"
import { randomBytes } from 'node:crypto';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL!);
const TTL = 15 * 60; // seconds

export async function login(req, res) {
  const user = await authenticate(req.body.email, req.body.password); // see section 13.2
  if (!user) return res.status(401).json({ error: 'Invalid email or password' });

  const sid = randomBytes(32).toString('base64url');                 // 256 bits: unguessable
  await redis.set(`sess:${sid}`, JSON.stringify({ userId: user.id, role: user.role }), 'EX', TTL);
  await redis.sadd(`user-sessions:${user.id}`, sid);                  // lets us "log out everywhere"

  res.cookie('__Host-sid', sid, { httpOnly: true, secure: true, sameSite: 'lax', path: '/', maxAge: TTL * 1000 });
  res.status(204).end();
}

export async function requireSession(req, res, next) {
  const sid = req.cookies['__Host-sid'];
  const raw = sid && (await redis.get(`sess:${sid}`));
  if (!raw) return res.status(401).json({ error: 'Not authenticated' });
  await redis.expire(`sess:${sid}`, TTL);                             // sliding expiry
  req.user = JSON.parse(raw);
  next();
}

export async function revokeAll(userId: string) {                    // compromised account
  const sids = await redis.smembers(`user-sessions:${userId}`);
  if (sids.length) await redis.del(...sids.map(s => `sess:${s}`), `user-sessions:${userId}`);
}
```

Edge cases: **regenerate the session ID on login** (prevents session fixation, where an attacker plants a known ID before you log in); add an **absolute** lifetime on top of the sliding one; delete the Redis key on logout, don't just clear the cookie.

## 4. Stateless authentication 🎓

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant S as Server (holds secret key)
  C->>S: email + password
  S->>S: check credentials
  S->>S: sign JWT (sub, role, exp) with secret
  S-->>C: JWT
  loop every later request
    C->>S: Authorization: Bearer JWT
    S->>S: verify signature + expiry with secret, no DB lookup
    S-->>C: response, or 401 / 403
  end`} />

1. Credentials go to the server, which checks them.
2. The server creates a **signed JWT** containing user data (ID, role) using its **secret key**. That key must be stored securely; it's used both to sign and to verify.
3. The client sends the JWT back on each request, conventionally in the **`Authorization`** header.
4. The server **verifies** the token with the secret, reads the user ID, and responds. If verification fails it returns **unauthorized** (or forbidden).

It's called **stateless** because the server needs **no persistent store** to authenticate: everything is in the self-contained, signed token.

### 🔧 Implementation (jose)

```ts title="jwt-auth.ts"
import { SignJWT, jwtVerify } from 'jose';
import { randomUUID } from 'node:crypto';

const secret = new TextEncoder().encode(process.env.JWT_SECRET!);  // ≥ 32 random bytes, from a secret manager
const ISS = 'https://api.example.com', AUD = 'example-web';

export const issueAccessToken = (user: { id: string; role: string }) =>
  new SignJWT({ role: user.role })
    .setProtectedHeader({ alg: 'HS256', typ: 'JWT' })
    .setSubject(user.id)
    .setIssuer(ISS).setAudience(AUD)
    .setIssuedAt()
    .setJti(randomUUID())               // unique ID, lets you denylist ONE token
    .setExpirationTime('15m')           // short: limits the theft window
    .sign(secret);

export async function requireJwt(req, res, next) {
  const token = req.headers.authorization?.match(/^Bearer (.+)$/)?.[1];
  if (!token) return res.status(401).json({ error: 'Not authenticated' });
  try {
    const { payload } = await jwtVerify(token, secret, {
      algorithms: ['HS256'],           // pin the algorithm: never trust the header's alg
      issuer: ISS, audience: AUD,
    });
    if (await redis.exists(`deny:${payload.jti}`)) throw new Error('revoked'); // optional hybrid check
    req.user = { id: payload.sub, role: payload.role };
    next();
  } catch {
    res.status(401).json({ error: 'Not authenticated' });
  }
}
```

### 🔧 Going deeper: how production systems escape the revocation problem

**Problem:** long-lived JWTs can't be revoked; per-request denylist lookups throw away statelessness.
**Mechanism:** split one token into two with different lifetimes and storage.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant API as API
  participant DB as Refresh token store
  C->>API: request + access token (15 min, stateless)
  API-->>C: 401 expired
  C->>API: POST /refresh with refresh token (HttpOnly cookie)
  API->>DB: is this refresh token valid and unused?
  DB-->>API: yes
  API->>DB: mark it used, store a NEW refresh token (rotation)
  API-->>C: new access token + new refresh token
  Note over API,DB: reuse of an already-used refresh token = theft, revoke the whole family`} />

- **Access token:** short-lived (minutes), verified statelessly on every request.
- **Refresh token:** long-lived, **stored server-side** (stateful), only checked on `/refresh`.
- **Revoking** a user means deleting their refresh tokens. The worst case is access lasting until the current access token expires (minutes). The DB is hit once per 15 minutes per user, not on every request.
- **Rotation + reuse detection:** each refresh issues a new refresh token. If an old one is presented again, someone copied it, so revoke all of that user's tokens.

JWT pitfalls (RFC 8725): the payload is **only Base64url-encoded, not encrypted**, so never put secrets in it; reject `alg: none` and pin the expected algorithm; validate `iss` and `aud` so a token from another system isn't accepted.

### Revoking on security events: "log out everywhere" done fully ➕

Refresh-token rotation and section 3's `revokeAll` give you the **tools** to end access. What's missing is **when** to use them, and how to cut off already-issued access tokens without a per-token denylist.

#### The events that must end other sessions ➕

**Problem.** A user changes their password because they think they were phished. The attacker's session, opened an hour ago, keeps working, because changing the password only affects **future** logins.

**Why it happens.** A session or token proves "this person authenticated at time T". Nothing ties it to the credential that was used, so replacing the credential doesn't invalidate it.

**Mechanism.** Treat these as **revocation events**, and on each one end every session and refresh token except (optionally) the current one:
- password change or reset;
- MFA enrolled, removed or reset (section 14);
- email address change (the account recovery channel moved);
- the user clicks "log out of all devices", or an admin locks or deletes the account;
- a refresh-token reuse is detected (section 4's theft signal).

Notify the user by email on each event, so an attacker-initiated change is noticed quickly.

**Edge cases.** OWASP's forgot-password guidance says not to log the user in automatically after a reset; make them sign in normally, so the new session is created through the usual checks (MFA included).

#### A per-user token version instead of a per-token denylist ➕

**Problem.** After a revocation event, access tokens already issued are still valid for up to 15 minutes, and you can't list them because you never stored them.

**Mechanism.** Store one small integer per **user**, not per token: `token_version`. Every access token carries the version that was current when it was issued (a `ver` claim). A revocation event increments the counter, and a token is valid only if its `ver` equals the user's current value. That's one cached lookup per user, the cache entry changes only when a revocation event happens, and a single write revokes every token issued before the event.

```ts title="token-version.ts"
// On a revocation event
export async function revokeAllForUser(userId: string): Promise<number> {
  const { rows } = await db.query(
    'UPDATE users SET token_version = token_version + 1 WHERE id = $1 RETURNING token_version', [userId]);
  const ver = rows[0].token_version as number;
  await redis.set(`tokver:${userId}`, String(ver), 'EX', 300);    // hot path reads this
  await revokeAll(userId);                                         // section 3: delete server-side sessions
  await db.query('DELETE FROM refresh_tokens WHERE user_id = $1', [userId]);
  return ver;   // to keep the current device signed in, issue it a new token with this ver
}

// When issuing: new SignJWT({ role: user.role, ver: user.tokenVersion })...

// In requireJwt, after jwtVerify succeeds
async function currentVersion(userId: string): Promise<number> {
  const cached = await redis.get(`tokver:${userId}`);
  if (cached !== null) return Number(cached);
  const { rows } = await db.query('SELECT token_version FROM users WHERE id = $1', [userId]);
  await redis.set(`tokver:${userId}`, String(rows[0].token_version), 'EX', 300);
  return rows[0].token_version;
}
if (payload.ver !== (await currentVersion(payload.sub!))) throw new Error('revoked');
```

**Edge cases.** A cache miss must fall back to the database, never to "accept", or an evicted key silently re-enables old tokens. The database is the source of truth and the cache is written second, so a crash between the two leaves an old version cached until the key expires: keep that TTL short (5 minutes here, about one access-token lifetime). This isn't fully stateless any more, but it's one lookup per user that caches well, rather than a growing list of token IDs.

## 5. Stateful vs stateless: when to choose which 🎓

| | Stateful (sessions) | Stateless (JWT) |
|---|---|---|
| **Pros** | Centralized control; real-time view of active sessions; easy revocation and logout; suits moderate traffic with strict session requirements | Scales horizontally; no session-store dependency; ideal for distributed systems and mobile clients where cookies are awkward |
| **Cons** | Limited scalability; operational complexity and latency in multi-region systems | Revocation is hard: until expiry, the only global kill switch is rotating the secret, which logs everyone out |

**The lesson author's opinion:** most applications should use **stateful** authentication, because it's more secure and makes revoking access easy.

**Hybrid option:** use **stateful** sessions for your **browser web app**, and **stateless** tokens for **mobile apps** and **third-party / server integrations** that need scalability and simplicity.

## 6. API key authentication 🎓

**Problem:** the flows above need a **human**: a login form, a password, a token to store. But sometimes the caller is **a program**, and you want to give it access to your **server** (not your UI) in a controlled way: with **limited permissions** and an **expiry**.

**The lesson's example:** OpenAI. People use the ChatGPT UI, but others want the model **programmatically**: to build their own UI, or to call it from their own server. So the platform lets you click **"Generate API key"**, which returns a **cryptographically random string**. You send it with each request (in a header, depending on the server) and get the same capabilities the platform's own UI uses.

**Machine-to-machine (M2M)** is the key idea:
- **Client-to-server:** a human uses a UI with mouse and keyboard, and the UI calls the server.
- **Machine-to-machine:** *your* server calls *their* server with no human involved. The lesson's example: a user in your app asks to "summarize this paragraph", your server calls the ChatGPT API using your API key, and returns the summary. The provider uses the key to identify you and enforce your **plan, quota and permissions**.

Why API keys fit M2M: **easy to generate** (one click), and the workflow is trivial. Give the machine a secret, it keeps it in an environment variable or secret storage, and sends it on every request. No login form or token dance.

### 🔧 Implementation: issuing and checking API keys safely

```ts title="api-keys.ts"
import { randomBytes, createHash } from 'node:crypto';

// Issue: show the full key ONCE, store only a hash
export async function createApiKey(ownerId: string, scopes: string[]) {
  const secret = randomBytes(32).toString('base64url');
  const key = `sk_live_${secret}`;                        // prefix: easy to recognise in leaks and logs
  await db.apiKey.create({ data: {
    ownerId, scopes,
    prefix: key.slice(0, 12),                             // shown in the UI so users can tell keys apart
    hash: createHash('sha256').update(key).digest('hex'), // high-entropy secret: a fast hash is fine here
    expiresAt: new Date(Date.now() + 90 * 864e5),
  }});
  return key;
}

// Verify: look up by hash (an indexed column), check expiry and scope
export async function requireApiKey(req, res, next) {
  const key = req.header('authorization')?.replace(/^Bearer /, '');
  if (!key) return res.status(401).end();
  const row = await db.apiKey.findUnique({ where: { hash: createHash('sha256').update(key).digest('hex') } });
  if (!row || row.revokedAt || row.expiresAt < new Date()) return res.status(401).end();
  req.principal = { ownerId: row.ownerId, scopes: row.scopes };
  next();
}
```

Why a plain SHA-256 is fine here but not for passwords: a 256-bit random key can't be brute-forced, so slowness adds nothing. Passwords have little entropy and need a slow hash. Also: rate-limit and meter per key, support **multiple keys** per account so they can be rotated without downtime, and run secret scanning on your repos.

## 7. OAuth 2.0 and OpenID Connect 🎓

### 7.1 The problem: too many passwords, and delegation

With per-site username and password:
- **Security risk:** people **reused** passwords (`12345`, `password`), so one breach compromised many accounts.
- **Fatigue:** too many accounts for one person to manage.

Then a new class of problem appeared, **delegation**: one website needing access to **another website's resources**, on the user's behalf:
- a **travel app** reading your **Gmail** to find flight tickets;
- a **social app** importing your **contacts** from Google.

**The first "solution": users shared their passwords** with the third-party app. It was a disaster:
- A password grants **full access** to everything; there's **no way to limit permissions**.
- You **can't revoke** one app's access without changing your password, and since people reused passwords, changing it everywhere.

### 7.2 The mechanism: share tokens, not passwords

In **2007**, engineers from companies like Google and Twitter started standardizing **OAuth** (open authorization). The idea: give the third party a **token with specific permissions** instead of the password. A password gives access to photos, maps history, contacts, calendar, delete everything. A token can be limited to **"read contacts"**, and can't add or delete them.

**The four roles:**

| Role | Meaning | In the example |
|---|---|---|
| **Resource owner** | The user who owns the data | You |
| **Client** | The app requesting access | Facebook |
| **Resource server** | Where the data lives | Google's servers (your contacts) |
| **Authorization server** | Authenticates the user and **issues tokens** | Google's auth server |

**The OAuth 1.0 flow:**

<Mermaid chart={`sequenceDiagram
  autonumber
  participant U as You (resource owner)
  participant C as Client (Facebook)
  participant AS as Authorization server (Google)
  participant RS as Resource server (Google contacts)
  C->>U: redirect to authorization server
  U->>AS: log in + approve requested permissions
  AS-->>C: token
  C->>RS: request contacts with token
  RS-->>C: contacts (only what was approved)`} />

### 7.3 OAuth 2.0 (around 2010–2012)

OAuth 1.0 was revolutionary but **complex to implement**, and its per-request **cryptographic signatures** were **error-prone**. OAuth 2.0 changed two things:

1. **Bearer tokens:** whoever holds the token can use it. Much simpler to implement, but **more vulnerable** (a stolen bearer token works for the thief), so it relies on TLS.
2. **Flows chosen by app type:**

| Flow | For | Status |
|---|---|---|
| **Authorization code** | Server-side apps | The standard flow (🔧 with PKCE, now for every client type) |
| **Implicit** | Browser-only apps | **Discouraged** because of security risks (token in the URL) |
| **Client credentials** | **Machine-to-machine**, no user involved | Standard for service accounts |
| **Device code** | Devices with limited input (e.g. a **smart TV**) | Standard; you approve on your phone |

### 7.4 OpenID Connect: adding authentication

**OAuth is authorization, not authentication.** It answers "may this app read contacts?", not "who is this user?". An access token says nothing standard about identity.

Around **2014**, **OpenID Connect (OIDC)** was built **on top of OAuth 2.0** to fill that gap. It adds an **ID token**, which is a **JWT** (that's why the lesson covered JWTs early) containing:
- the user ID (`sub`), when they logged in (`iat`), the **issuer** (`iss`, which authority issued it),
- profile data the client asked for: name, email, picture.

This is what powers **"Sign in with Google / Facebook / Discord"**: the app takes your identity from Google and stores it or uses it directly, **without running its own password system**.

**The lesson's OIDC example:** a note-taking app with "Sign in with Google" that also wants your **Google Keep** notes.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant U as Browser
  participant N as Note app (client)
  participant G as Google authorization server
  participant K as Google Keep API (resource server)
  U->>N: click Sign in with Google
  N-->>U: redirect to G (scope: openid email profile + keep, state, PKCE challenge)
  U->>G: log in, approve permissions
  G-->>U: redirect back to N with authorization code
  U->>N: code
  N->>G: exchange code (+ client secret, PKCE verifier) at token endpoint
  G-->>N: ID token (JWT: who you are) + access token (what N may do)
  N->>N: verify ID token, create local session for the user
  N->>K: GET notes with access token
  K-->>N: your notes, only within the granted scope`} />

1. The client redirects you to the **authorization server**. You log in **on Google**, not on the note app, and approve the requested permissions (email, name, picture, Keep).
2. The client gets an **authorization code** (the lesson notes that some variants also return an ID token at this step).
3. The client **exchanges the code** for an **access token** (and the ID token, if it didn't have it yet).
4. The **ID token** tells the app **who you are**. The **access token** lets it act **on your behalf**, and **only** for what you approved: fetch your Keep notes, nothing else.

The lesson's metaphor: OAuth 2.0 + OIDC are the **security guards and key makers** of the internet. No app gets more access than it asked for and you granted. Together they turned password-sharing chaos into a secure, interconnected system.

> 🔧 **Transcript note:** the transcript says the code is exchanged "with the resource server". In the spec it's exchanged at the **authorization server's token endpoint**; the resource server only receives the access token afterwards.

### 7.5 🔧 Going deeper: the parameters that make the code flow secure

| Parameter | Attack it stops | How |
|---|---|---|
| `state` | **CSRF on the callback** (attacker makes you log in to *their* account) | Random value stored in your session before redirect, compared on return |
| **PKCE** (`code_challenge` / `code_verifier`) | **Stolen authorization code** (malicious app, logs, referer) | Client sends `SHA256(verifier)` up front; only the holder of `verifier` can redeem the code |
| `nonce` | **ID token replay** | Random value echoed inside the ID token |
| Exact `redirect_uri` match | Code sent to an attacker's URL | Authorization server only redirects to pre-registered URIs |

RFC 9700 (the OAuth 2.0 Security Best Current Practice, Jan 2025) says the implicit grant **SHOULD NOT** be used, the password grant **MUST NOT** be used, public clients **MUST** use PKCE, and public clients' refresh tokens must be sender-constrained or rotated.

```ts title="oidc-callback.ts (simplified)"
import { createHash, randomBytes } from 'node:crypto';
import { createRemoteJWKSet, jwtVerify } from 'jose';

const b64url = (b: Buffer) => b.toString('base64url');
const JWKS = createRemoteJWKSet(new URL('https://www.googleapis.com/oauth2/v3/certs'));

export function startLogin(req, res) {
  const verifier = b64url(randomBytes(32));
  req.session.oauth = { state: b64url(randomBytes(16)), nonce: b64url(randomBytes(16)), verifier };
  const p = new URLSearchParams({
    response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
    scope: 'openid email profile', state: req.session.oauth.state, nonce: req.session.oauth.nonce,
    code_challenge: b64url(createHash('sha256').update(verifier).digest()), code_challenge_method: 'S256',
  });
  res.redirect(`https://accounts.google.com/o/oauth2/v2/auth?${p}`);
}

export async function callback(req, res) {
  const saved = req.session.oauth;
  if (!saved || req.query.state !== saved.state) return res.status(400).send('bad state');

  const tokenRes = await fetch('https://oauth2.googleapis.com/token', {
    method: 'POST',
    headers: { 'content-type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'authorization_code', code: String(req.query.code), redirect_uri: REDIRECT_URI,
      client_id: CLIENT_ID, client_secret: CLIENT_SECRET, code_verifier: saved.verifier,
    }),
  });
  const { id_token, access_token } = await tokenRes.json();

  const { payload } = await jwtVerify(id_token, JWKS, {          // asymmetric: verify with Google's PUBLIC key
    issuer: ['https://accounts.google.com', 'accounts.google.com'], audience: CLIENT_ID,
  });
  if (payload.nonce !== saved.nonce) return res.status(400).send('bad nonce');

  // Link on (issuer, sub), NOT on email: emails change and can be re-assigned
  const user = await upsertUserByIdentity('google', payload.sub!, payload.email as string);
  await createSession(res, user);                                 // then it's normal stateful auth (section 3)
}
```

In production, use a certified OIDC library or your auth provider's SDK; this is here to show what it does.

## 8. Service-to-service authentication ➕

Sections 6 and 7 gave two answers for machine callers: a static API key, or OAuth's client-credentials flow. Inside your own system (dozens of services calling each other), a backend engineer needs to go further, because a long-lived shared secret per service pair is the weakest link in most internal networks.

<Mermaid chart={`flowchart LR
  A["Static API key<br/>long-lived secret"] --> B["Client credentials<br/>short-lived token, still a secret"]
  B --> C["private_key_jwt or mTLS<br/>proof of a private key"]
  C --> D["Workload identity<br/>platform issues the credential"]`} />

### Short-lived tokens from client credentials ➕

**Problem.** The billing service calls the orders service with an API key copied into its environment two years ago. It never expires, it's in three CI systems, and nobody knows which other services also use it.

**Why it happens.** A static key is both the **identity** and the **proof**, forever. Every copy is a full credential, and rotating it means coordinating every holder.

**Mechanism.** Use the OAuth **client credentials** grant against an internal authorization server. The service authenticates once, gets an **access token valid for minutes** with a specific `aud` (the service it may call) and `scope`, and the receiving service verifies the JWT locally with the issuer's public keys (JWKS), as section 4 does for users. Better still, the client proves itself with **`private_key_jwt`** (RFC 7523): it signs a short assertion with its private key instead of sending a shared `client_secret`, so the authorization server stores only a public key.

```ts title="service-token.ts (caller side)"
import { SignJWT, importPKCS8 } from 'jose';
import { randomUUID } from 'node:crypto';

const key = await importPKCS8(process.env.SERVICE_PRIVATE_KEY!, 'ES256');
let cached: { token: string; exp: number } | undefined;

export async function tokenFor(audience: string): Promise<string> {
  if (cached && cached.exp - 60 > Date.now() / 1000) return cached.token;    // refresh a minute early
  const assertion = await new SignJWT({})
    .setProtectedHeader({ alg: 'ES256' })
    .setIssuer('billing-service').setSubject('billing-service')
    .setAudience('https://auth.internal/token').setJti(randomUUID())
    .setIssuedAt().setExpirationTime('1m')
    .sign(key);
  const res = await fetch('https://auth.internal/token', {
    method: 'POST',
    headers: { 'content-type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'client_credentials', scope: 'orders:read', audience,
      client_assertion_type: 'urn:ietf:params:oauth:client-assertion-type:jwt-bearer',
      client_assertion: assertion,
    }),
  });
  const { access_token, expires_in } = await res.json();
  cached = { token: access_token, exp: Date.now() / 1000 + expires_in };
  return access_token;
}
```

**Edge cases.** The receiver must check `aud`: without it, a token minted for the notifications service can be replayed against the payments service. Cache tokens per audience, not globally, and refresh before expiry so a slow authorization server doesn't cause a burst of 401s. (The `audience` parameter isn't in the core OAuth spec; providers name it differently, so check yours.)

### Mutual TLS: the connection itself proves identity ➕

**Problem.** A bearer token is still a bearer token: if it leaks from a log, anyone can use it until it expires.

**Why it happens.** Bearer means possession is the only check. Nothing ties the token to the machine that's supposed to hold it.

**Mechanism.** In ordinary TLS only the server presents a certificate. In **mutual TLS**, the client also presents one, and the server verifies it against a CA it trusts. The private key never leaves the client, so identity is proven by the TLS handshake, not by a copyable string. RFC 8705 adds **certificate-bound access tokens**: the authorization server puts a hash of the client certificate in the token's `cnf` claim (`x5t#S256`), and the resource server rejects the token unless it arrives over a connection using that same certificate. A stolen token is then useless on its own.

```ts title="mtls-server.ts"
import https from 'node:https';
import { readFileSync } from 'node:fs';

https.createServer({
  key: readFileSync('server.key'), cert: readFileSync('server.crt'),
  ca: readFileSync('internal-ca.crt'),     // only certificates from OUR CA
  requestCert: true,
  rejectUnauthorized: true,                // handshake fails without a valid client cert
}, (req, res) => {
  const peer = (req.socket as import('node:tls').TLSSocket).getPeerCertificate();
  const caller = peer.subjectaltname;      // e.g. "URI:spiffe://prod.example/billing"
  if (!ALLOWED_CALLERS.has(caller)) { res.writeHead(403).end(); return; }
  // ...handle the request
}).listen(8443);
```

**Edge cases.**
- If TLS terminates at a load balancer or ingress, your app never sees the client certificate. Either pass it through, or have the proxy verify it and forward the identity in a header that **only** the proxy can set (strip it from incoming requests).
- Certificates expire. Short-lived certificates need automated issuance and rotation; without automation, mTLS turns into outages when a certificate quietly expires.
- mTLS authenticates the **service**. You still need authorization: "billing may call `GET /orders`" is a policy decision, not a TLS one.

### Workload identity: let the platform issue the credentials ➕

**Problem.** Every option so far still needs a secret (a private key or client secret) delivered to the service somehow, and "how do we get the first secret onto the box" is the hard part.

**Mechanism.** The platform already knows which workload is running (which Kubernetes service account, which cloud VM role), so it can **attest** to that and issue short-lived credentials automatically:
- **SPIFFE** standardizes this. Each workload gets an ID like `spiffe://prod.example/billing`, and a local Workload API hands it short-lived **X.509-SVIDs** (certificates for mTLS) or JWT-SVIDs, rotated automatically. Service meshes (Istio, Linkerd) build mTLS between pods on the same idea.
- **Kubernetes projected service-account tokens** are audience-bound, expiring JWTs mounted into the pod, which an external system can verify via the cluster's OIDC issuer.
- **Cloud workload identity federation** exchanges such a platform token for cloud credentials, so no long-lived cloud keys are stored at all.

**Edge cases.** The trust boundary moves to the platform: anyone who can deploy a pod under the `billing` service account **is** billing. Lock down who can create workloads and bind service accounts. Prefer X.509-SVIDs over JWT-SVIDs where possible; SPIFFE itself notes JWT-SVIDs are susceptible to replay.

### Carrying the end user across services ➕

**Problem.** The API gateway authenticated Asha. It calls the orders service, which calls the payments service. Should payments trust that the request is "for Asha"? And what if the orders service is compromised and claims to act for any user?

**Why it happens.** If services forward the user's own token everywhere, every service can use it against every other service. If they drop it and call with only their service identity, downstream services can't check user-level permissions.

**Mechanism.** OAuth **Token Exchange** (RFC 8693): the orders service sends the user's token (`subject_token`) and its own identity (`actor_token`) to the authorization server with `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, and gets back a **new, narrower token** whose `aud` is the payments service. The RFC distinguishes **impersonation** (the new token simply is the user) from **delegation**, where an `act` claim records "orders-service acting for Asha", so both identities are visible and auditable.

```json title="delegated token claims (decoded)"
{
  "sub": "user_42",
  "aud": "payments-service",
  "scope": "payments:create",
  "act": { "sub": "orders-service" },
  "exp": 1790000000
}
```

**Edge cases.** Downscope at each hop: a token for payments shouldn't carry `orders:*` scopes. Don't trust a plain `X-User-Id` header from another service unless the hop is authenticated (mTLS) **and** you accept that a compromised caller can claim any user; signed, audience-bound tokens remove that trust.

## 10. Authorization 🎓

### 10.1 The problem it solves

**Example:** a note-taking app. Logged-in users create, update and delete notes. "Delete" moves a note to a **trash** for 30 days. After that it disappears for the user, but it isn't wiped from the database; it moves to a hidden area the lesson calls the **"dead zone"**.
You, the creator, want an **admin UI** to work with those dead-zone notes. That needs capabilities **ordinary users must not have**.

**Naive fix:** a secret "god mode" string sent with each admin API call. Two problems:
1. **Security:** if anyone intercepts the string, they can wipe the DB or tamper with every user's data.
2. **Management:** to give the same power to friends or maintainers, you either share the string or add more strings and server logic for each. It gets complicated fast and more error-prone.

**Authorization** is the general solution: **specific permissions for specific users**. Not everyone has the same access; some users have more, some less, some a completely different set. In **multi-tenant** systems, an organization's admin assigns read/write to some members and read-only to others.

### 10.2 RBAC: role-based access control

The most widely used technique. Users get **roles**; roles get **permissions**, possibly per resource.

<Mermaid chart={`flowchart LR
  U1["Asha"] --> R1["role: user"]
  U2["Ravi"] --> R2["role: moderator"]
  U3["You"] --> R3["role: admin"]
  R1 --> P1["notes: read, write, delete"]
  R2 --> P1
  R2 --> P2["notes: moderate"]
  R3 --> P1
  R3 --> P3["dead-zone notes: read, restore"]`} />

- Roles like **user**, **admin**, **moderator**, and custom ones you define.
- A user role might get **read**; an admin **read + write**; and so on.
- Permissions can differ **per resource**: all users can read/write/delete their notes, but only admins can access **dead-zone notes**. You can be as granular as you need.

### 10.3 How it flows through a request

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant AN as Auth middleware
  participant AZ as Authorization check
  participant H as Handler
  C->>AN: GET /admin/dead-zone (session cookie or JWT)
  AN->>AN: identify user + role (from token, or DB lookup)
  AN->>AZ: request with user and role attached
  alt role is admin
    AZ->>H: continue
    H-->>C: 200 dead-zone notes
  else role is user
    AZ-->>C: 403 Forbidden
  end`} />

1. On **sign-up**, the server assigns a role (usually `user`; `admin` for special cases).
2. On every request, the client sends its session ID or JWT.
3. **Early in the request cycle**, the server works out the user's role: from the token or with a DB lookup.
4. It **attaches** the identity and role to the request so the next middlewares and handlers can use it (the middleware chain gets its own lesson).
5. The route checks the role: an admin gets the dead-zone notes; a normal user gets **403 Forbidden**, "you don't have permission for this action or resource".

### 🔧 Implementation: Express and NestJS

```ts title="rbac.ts (Express)"
const PERMS = {
  user:      ['notes:read', 'notes:write', 'notes:delete'],
  moderator: ['notes:read', 'notes:write', 'notes:delete', 'notes:moderate'],
  admin:     ['notes:read', 'notes:write', 'notes:delete', 'deadzone:read', 'deadzone:restore'],
} as const;

export const can = (perm: string) => (req, res, next) =>
  (PERMS[req.user.role] as readonly string[])?.includes(perm)
    ? next()
    : res.status(403).json({ error: 'Forbidden' });

app.get('/admin/dead-zone', requireSession, can('deadzone:read'), listDeadZoneNotes);
```

```ts title="roles.guard.ts (NestJS)"
import { CanActivate, ExecutionContext, Injectable, SetMetadata } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext) {
    const roles = this.reflector.getAllAndOverride<string[]>('roles', [ctx.getHandler(), ctx.getClass()]);
    if (!roles) return true;                                  // no @Roles: authN-only route
    const { user } = ctx.switchToHttp().getRequest();
    return roles.includes(user?.role);                         // false → Nest throws 403
  }
}

// @Roles('admin') @Get('admin/dead-zone') listDeadZone() { ... }
```

### 🔧 Edge cases that RBAC alone doesn't cover

- **401 vs 403:** `401 Unauthorized` really means *unauthenticated* (no or invalid credentials; log in). `403 Forbidden` means *authenticated but not allowed*. Some APIs return **404** for resources you can't see, to avoid revealing they exist.
- **Ownership (IDOR):** "role user can delete notes" doesn't mean *any* note. Always scope queries by owner: `WHERE id = $1 AND owner_id = $2`. Broken object-level authorization is the top risk in the OWASP API Top 10.
- **Stale roles in JWTs:** if the role is baked into a 15-minute token, demoting someone takes up to 15 minutes. For sensitive actions, re-check the role from the DB.
- **Multi-tenant:** roles are per organization (`memberships(user_id, org_id, role)`), not global.
- Beyond RBAC: **ABAC** (rules over attributes like department or time) and **ReBAC** (relationships, as in Google Zanzibar-style systems) for fine-grained sharing.

## 11. Authorization beyond roles: tenants, relationships and policies ➕

The edge-case list above names tenants, ABAC and ReBAC in one line each. Each one is a different answer to the same pressure: once permissions depend on **which organization**, **which document** or **which circumstances**, a role-to-permission table stops being enough.

### Tenant isolation as a hard boundary ➕

**Problem.** In a B2B SaaS, one missing `WHERE org_id = $2` in one query shows customer A's invoices to customer B. That's not a bug report, it's a data breach.

**Why it happens.** Section 10's checks live in application code, and every new query is a new chance to forget the tenant filter. Ownership checks (IDOR) protect one row; tenant isolation must protect **every** row in **every** table.

**Mechanism.** Two layers:
1. **Resolve the tenant once** per request from a trusted source (the membership row for the authenticated user and the requested org, never a client-supplied `orgId` alone) and attach it to the request context. Roles are per membership: Asha can be `admin` in one org and `viewer` in another.
2. Make the **database enforce it** with Postgres **row-level security**. Once RLS is enabled on a table, rows are visible only if a policy allows them (no policy means default deny), so a forgotten filter returns nothing instead of everything.

```sql title="rls.sql"
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;      -- table owners bypass RLS unless forced

CREATE POLICY tenant_isolation ON invoices
  USING      (org_id = current_setting('app.org_id')::uuid)   -- which rows are visible
  WITH CHECK (org_id = current_setting('app.org_id')::uuid);  -- which rows may be written
```

```ts title="tenant-tx.ts"
export async function withTenant<T>(orgId: string, fn: (c: PoolClient) => Promise<T>) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query("SELECT set_config('app.org_id', $1, true)", [orgId]); // true = local to this transaction
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (e) { await client.query('ROLLBACK'); throw e; }
  finally { client.release(); }
}
```

**Edge cases.**
- Superusers and roles with `BYPASSRLS` always skip policies. Connect the app as an ordinary role, and keep the migration/owner role separate.
- Use `set_config(..., true)` inside a transaction. A session-level setting on a pooled connection leaks into the next request that borrows it, which is exactly the cross-tenant bug RLS was meant to stop.
- Caches, search indexes and object storage aren't covered by RLS: include the tenant ID in every cache key, index document and object path.

### Relationship-based access control (ReBAC) ➕

**Problem.** Google-Docs-style sharing: a document is visible to its owner, to anyone it was shared with, to members of a group it was shared with, and to anyone who can see the folder it's in. Modelling that as roles explodes, because the permission depends on a **chain of relationships**, not on a user attribute.

**Mechanism.** Store permissions as **relation tuples** and answer checks by walking them. Google's **Zanzibar** paper writes a tuple as `object#relation@user`, where the user can itself be a set (`group:eng#member`):

```txt title="relation tuples"
doc:roadmap#owner@user:asha
doc:roadmap#parent@folder:planning
folder:planning#viewer@group:eng#member
group:eng#member@user:ravi
```

A configuration then says, for example, "viewers of a doc include its owners, its editors, and viewers of its parent folder". The check "can Ravi view `doc:roadmap`?" follows `parent` to the folder, finds the `eng` group as viewer, and finds Ravi in the group. Open-source systems built on this model include OpenFGA, SpiceDB and Ory Keto.

```ts title="rebac-check.ts (OpenFGA SDK style)"
const { allowed } = await fga.check({
  user: 'user:ravi', relation: 'viewer', object: 'doc:roadmap',
});
if (!allowed) throw new ForbiddenException();

// Sharing is a write, not a code change
await fga.write({ writes: [{ user: 'user:meera', relation: 'editor', object: 'doc:roadmap' }] });
```

**Edge cases.**
- **The "new enemy" problem.** The Zanzibar paper's example: Alice removes Bob from a folder, then adds new documents to it. If the check runs against a stale replica of the permission data, Bob can see the new documents. Zanzibar solves it with a consistency token (a **zookie**) stored with each content version; checks must use permission data at least as fresh as that token. Most ReBAC systems expose a similar "at least as fresh as" option; use it after permission changes.
- **Listing is harder than checking.** "Which of 10,000 documents can Ravi see?" can't be answered by 10,000 checks. Use the system's list-objects API or keep a filtered index.
- Your permission store and your main database can now disagree. Write tuples in the same workflow as the data they protect (or via an outbox) so a crash doesn't leave a document without an owner.

### Attribute-based rules and policy engines ➕

**Problem.** "Support agents can view a customer's orders only during an open ticket for that customer, only from the corporate network, and never payment details." Encoding that in role checks spreads `if` statements across every handler, and nobody can audit the full rule set.

**Mechanism.** **ABAC** decides from attributes of the **subject** (department, clearance), the **resource** (owner, classification, tenant), the **action**, and the **context** (time, IP, MFA freshness). Put those rules in one place, as policy-as-code: a **policy engine** such as Open Policy Agent (Rego) or AWS's Cedar takes a request description and returns allow or deny. Handlers then ask one question, and the policy is versioned, reviewed and unit-tested like code.

```txt title="support.cedar"
permit (
  principal in Role::"support",
  action == Action::"viewOrder",
  resource
) when {
  context.openTicketCustomerId == resource.customerId &&
  context.network == "corporate"
};
```

```ts title="authorize.ts"
export async function authorize(principal: Principal, action: string, resource: Resource, ctx: Ctx) {
  const decision = await policyEngine.isAuthorized({ principal, action, resource, context: ctx });
  audit.log({ principal: principal.id, action, resource: resource.id, decision });   // see section 12
  if (decision !== 'allow') throw new ForbiddenException();
}
```

**Edge cases.**
- The engine is only as good as the attributes you give it. Load resource attributes from your database, never from the request body.
- Default to **deny** when the engine is unreachable, and keep it close (a sidecar or in-process library), because it's now on the critical path of every request.
- RBAC, ReBAC and ABAC combine: roles for coarse access, relationships for sharing, attributes for conditions. Start with the simplest model that fits, and add the others when a real rule demands them.

## 12. Impersonation and audit trails ➕

Section 10 gave admins extra powers (the dead-zone notes). Once real people hold those powers, two questions follow: how does support see what a user sees, and how do you prove afterwards who did what.

### Impersonation ("log in as user") done safely ➕

**Problem.** A customer reports a bug that only appears in their account. Support asks for their password, or an engineer runs SQL in production to reproduce it. Both are worse than the bug.

**Why it happens.** The system has no legitimate way for one identity to see the product **as** another identity, so people improvise.

**Mechanism.** Build impersonation as a **separate, visible session type** that keeps **both** identities:
- only a specific permission (`support:impersonate`) can start it, ideally with a reason or ticket ID and a fresh MFA check;
- the session records `actor` (the support agent) and `subject` (the customer), the same idea as RFC 8693's `act` claim;
- it's short-lived (for example 30 minutes), read-only by default, and blocked from the most sensitive actions (changing password, email or MFA, viewing full payment data);
- the UI shows a banner, and the customer can be notified.

```ts title="impersonation.ts"
export async function startImpersonation(req, res) {
  const actor = req.user;
  if (!can(actor, 'support:impersonate')) return res.status(403).end();
  if (!recentMfa(req.session, 5 * 60)) return res.status(401).json({ error: 'step_up_required' });
  const { userId, ticketId } = ImpersonateBody.parse(req.body);

  const sid = randomBytes(32).toString('base64url');
  await redis.set(`sess:${sid}`, JSON.stringify({
    userId,                                   // who the app acts as
    actorId: actor.id, ticketId,              // who is really behind it
    mode: 'impersonation', readOnly: true,
  }), 'EX', 30 * 60);
  await audit.log({ type: 'impersonation.started', actorId: actor.id, subjectId: userId, ticketId });
  res.cookie('__Host-sid', sid, { httpOnly: true, secure: true, sameSite: 'strict', path: '/' });
  res.status(204).end();
}

// Middleware: block sensitive routes during impersonation
export const notWhileImpersonating = (req, res, next) =>
  req.session?.mode === 'impersonation' ? res.status(403).json({ error: 'Not allowed while impersonating' }) : next();
```

**Edge cases.** Every write made during impersonation must log the **actor**, not just the subject, or the audit trail will say the customer did it. Don't let an impersonation session impersonate again, and don't let support impersonate admins.

### Audit logs that hold up later ➕

**Problem.** A customer asks "who changed my payout bank account?", or an auditor asks for every admin who read customer data last quarter. Application logs rotate after 14 days, are full of noise, and anyone with server access could have edited them.

**Why it happens.** Debug logs answer "what did the code do?" for engineers. An audit log answers "who did what to which resource, when, from where, and was it allowed?" for security and compliance, which needs different retention, structure and integrity. (General logging and observability are [lesson 18](/docs/backend-first-principles/18-logging-monitoring-observability).)

**Mechanism.** Write a structured event for every security-relevant action (logins and failures, MFA changes, role and permission changes, impersonation, data exports, admin reads of user data, **denied** authorization checks) to an **append-only** store, kept separate from operational logs.

```sql title="audit.sql"
CREATE TABLE audit_events (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at          timestamptz NOT NULL DEFAULT now(),
  actor_id    text NOT NULL,          -- who really did it (the support agent while impersonating)
  subject_id  text,                   -- whose account or data
  action      text NOT NULL,          -- 'role.granted', 'payout.updated', 'authz.denied'
  resource    text,
  decision    text NOT NULL,          -- 'allow' or 'deny'
  ip          inet,
  request_id  text,
  details     jsonb NOT NULL DEFAULT '{}'
);
-- The app role can only INSERT and SELECT, never UPDATE or DELETE
REVOKE UPDATE, DELETE, TRUNCATE ON audit_events FROM app_user;
```

**Edge cases.**
- Write the audit event **in the same transaction** as the change it describes, or a crash can make a change without its record.
- Don't put secrets or full personal data in `details`: no passwords, tokens or card numbers. Log IDs and which fields changed.
- For tamper evidence, ship events to separate storage the app can't modify (write-once object storage, a separate account), or chain them by storing a hash of the previous event in each row.

## 13. Two security rules for auth endpoints 🎓

### 13.1 Never send specific error messages

**Problem:** friendly messages help attackers:
- "**User not found**" → the attacker learns the email doesn't exist and moves on to the next one in their list.
- "**Incorrect password**" → the username is confirmed; now they only need the password, so they go for brute force or dictionary attacks.
- "**Account locked due to too many attempts**" → also confirms the account exists.

**Rule:** in the authentication flow, every failure returns the **same generic message** (e.g. "Authentication failed"). Keep user-friendly messages for other flows like validation errors.

🔧 Apply it everywhere identity leaks: sign-up ("email already registered") and password reset ("we sent a link") should also answer the same way regardless of whether the account exists, e.g. "If an account exists, we've emailed a link."

### 13.2 Timing attacks

**Problem:** even with identical messages, **response time** can leak which step failed. A typical login does:

<Mermaid chart={`flowchart LR
  A["1. Find user by email"] -->|"not found: return fast (~5 ms)"| X["401"]
  A --> B["2. Account locked?"]
  B -->|"locked"| X
  B --> C["3. Hash provided password,<br/>compare with stored hash (slow: ~100+ ms)"]
  C -->|"mismatch"| X
  C --> OK["200 + session"]`} />

Hashing is deliberately slow. A wrong email returns quickly; a right email with a wrong password returns after the hash (the lesson's example: about 200 ms later). By measuring that difference, an attacker learns **which emails exist** and where to aim brute-force attacks.

**The lesson's two defences:**
1. **Constant-time operations:** use cryptographically safe, constant-time comparison functions, whose execution time doesn't depend on how similar the inputs are.
2. **Simulated delay:** when the user isn't found, wait (`setTimeout` in Node, `time.Sleep` in Go) so the response takes as long as a password check.

### 🔧 Implementation: equalize the work, not just the clock

A fixed sleep is fragile: real hash time varies with load and hardware, so the two distributions still differ. The more robust trick is to **always run the hash**, against a dummy hash when the user doesn't exist.

```ts title="authenticate.ts"
import argon2 from 'argon2';
import { timingSafeEqual } from 'node:crypto';

const DUMMY_HASH = await argon2.hash('dummy-password-never-used', { type: argon2.argon2id }); // computed once

export async function authenticate(email: string, password: string) {
  const user = await db.user.findUnique({ where: { email: email.toLowerCase() } });

  // Always do the expensive step, so "no such user" costs the same as "wrong password"
  const ok = await argon2.verify(user?.passwordHash ?? DUMMY_HASH, password);

  if (!user || !ok || user.lockedUntil > new Date()) {
    if (user) await registerFailedAttempt(user.id);          // lockout counter per ACCOUNT, not per IP
    return null;                                              // caller returns one generic 401
  }
  return user;
}

// For comparing secrets yourself (API key, HMAC, reset token), never use ===
export function safeEqual(a: string, b: string) {
  const A = Buffer.from(a), B = Buffer.from(b);
  return A.length === B.length && timingSafeEqual(A, B);    // timingSafeEqual throws on different lengths
}
```

Why `===` leaks: string comparison stops at the **first differing byte**, so a guess with a correct prefix takes slightly longer, and an attacker can recover a secret byte by byte. `timingSafeEqual` always compares every byte. Pair all of this with **rate limiting** on login (per account and per IP) and with **MFA**, because generic messages only slow enumeration; they don't stop guessing.

## 14. Multi-factor authentication in practice ➕

Section 13 ended on "pair it with MFA". Rate limiting itself (per IP, per account, global) is covered in [lesson 20](/docs/backend-first-principles/20-backend-security); this section is about the second factor that makes a correct stolen password insufficient.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant S as Server
  C->>S: POST /login (email + password)
  S->>S: password OK, MFA enrolled
  S-->>C: 200 mfa_required + short-lived pending session
  C->>S: POST /login/mfa (code or passkey assertion)
  S->>S: verify factor, mark session mfa_at = now
  S-->>C: Set-Cookie full session`} />

**The rule for the flow:** a password-only success must create a **pending** state that can do nothing except finish MFA. Issuing the real session first and "asking for MFA in the UI" lets an attacker skip the second step by calling the API directly.

### TOTP: codes from a shared secret ➕

**Problem.** SMS codes can be intercepted with SIM-swap attacks, where an attacker gets the victim's number moved to their own SIM.

**Mechanism.** **TOTP** (RFC 6238) is HOTP with time as the counter: both sides share a random secret, compute `T = floor((now - T0) / X)` with a default step `X` of **30 seconds** and `T0` the Unix epoch, and derive a short code from `HMAC(secret, T)` (HMAC-SHA-1 by default; SHA-256 and SHA-512 are allowed). Nothing is sent over the phone network, and the code changes every step.

```ts title="totp.ts"
import { createHmac, randomBytes } from 'node:crypto';

export const newSecret = () => randomBytes(20);           // 160 bits; show as base32 in an otpauth:// QR code

function hotp(secret: Buffer, counter: number, digits = 6) {
  const msg = Buffer.alloc(8);
  msg.writeBigUInt64BE(BigInt(counter));
  const mac = createHmac('sha1', secret).update(msg).digest();
  const offset = mac[mac.length - 1] & 0x0f;              // dynamic truncation (RFC 4226)
  const bin = (mac.readUInt32BE(offset) & 0x7fffffff) % 10 ** digits;
  return bin.toString().padStart(digits, '0');
}

export async function verifyTotp(userId: string, secret: Buffer, code: string) {
  const step = Math.floor(Date.now() / 1000 / 30);
  for (const s of [step - 1, step, step + 1]) {            // allow one step of clock drift
    if (safeEqual(hotp(secret, s), code)) {                 // constant time (section 13.2)
      // Reject replays: RFC 6238 says a code MUST NOT be accepted twice after a success
      const fresh = await redis.set(`totp-used:${userId}:${s}`, '1', 'EX', 120, 'NX');
      return fresh === 'OK';
    }
  }
  return false;
}
```

**Edge cases.**
- Store TOTP secrets **encrypted** (not hashed: you need the original to compute codes), with the key in a KMS or secret manager.
- A 6-digit code has only a million values. Rate-limit MFA attempts per account as strictly as passwords, and lock the pending session after a few failures.
- Confirm enrollment by requiring one valid code before turning MFA on, or a mistyped QR scan locks the user out.

### WebAuthn and passkeys: phishing-resistant by design ➕

**Problem.** TOTP stops password reuse but not **real-time phishing**: a fake login page asks for the password and the current code, and relays both to the real site within the 30-second window.

**Why it happens.** A TOTP code isn't bound to any website. The user can type it into the wrong one.

**Mechanism.** **WebAuthn** (passkeys) uses a key pair per site, generated on the user's device or synced through their platform's password manager. To log in, the server sends a random **challenge**, and the authenticator signs it together with data the **browser** fills in, including the **origin**. The server verifies, among other things, that:
- the challenge is the one it issued;
- the origin and the `rpIdHash` match its own domain, so a signature produced on a phishing domain is useless;
- the user-present (and, if required, user-verified) flags are set;
- the signature over the authenticator data and the hash of the client data is valid for the stored public key.

The server only stores a **public key**, so a database leak reveals nothing reusable. OWASP's MFA guidance calls passkeys the preferred phishing-resistant control.

```ts title="webauthn.ts (with @simplewebauthn/server)"
import { generateAuthenticationOptions, verifyAuthenticationResponse } from '@simplewebauthn/server';

export async function options(req, res) {
  const opts = await generateAuthenticationOptions({ rpID: 'example.com', userVerification: 'preferred' });
  req.session.challenge = opts.challenge;                   // one-time, server-side
  res.json(opts);
}

export async function verify(req, res) {
  const cred = await db.passkey.findUnique({ where: { id: req.body.id } });
  if (!cred) return res.status(401).end();
  const { verified, authenticationInfo } = await verifyAuthenticationResponse({
    response: req.body,
    expectedChallenge: req.session.challenge,
    expectedOrigin: 'https://example.com',
    expectedRPID: 'example.com',
    credential: { id: cred.id, publicKey: cred.publicKey, counter: cred.counter },
  });
  delete req.session.challenge;                             // never accept the same challenge twice
  if (!verified) return res.status(401).end();
  await db.passkey.update({ where: { id: cred.id }, data: { counter: authenticationInfo.newCounter } });
  await completeLogin(req, res, cred.userId);
}
```

**Edge cases.**
- Synced passkeys usually report a signature counter of 0. The spec's clone check only applies when counters are non-zero, so don't reject a 0.
- Let users register **several** passkeys (phone, laptop, hardware key), or losing one device means account recovery.
- Use a maintained library; the parsing (CBOR, COSE keys, attestation formats) is where hand-written implementations go wrong.

### Recovery codes and step-up authentication ➕

**Problem.** A user who loses their phone is locked out, and support "just turns off MFA" for anyone who emails convincingly, which makes the support desk the weakest factor.

**Mechanism.**
- At enrollment, issue about ten single-use **recovery codes**, show them once, and store them **hashed** like passwords; mark each one used.
- Treat disabling MFA, changing the recovery email, and adding a new factor as **sensitive actions** that require a fresh MFA check (**step-up**): store `mfa_at` in the session and demand a new verification if it's older than a few minutes.
- Removing or resetting MFA is a revocation event (section 4): end other sessions and notify the user.

```ts title="step-up.ts"
export const requireRecentMfa = (maxAgeSec = 300) => (req, res, next) =>
  req.session.mfaAt && Date.now() / 1000 - req.session.mfaAt < maxAgeSec
    ? next()
    : res.status(401).json({ error: 'step_up_required' });   // client prompts for a code or passkey

app.post('/account/mfa/disable', requireSession, requireRecentMfa(), disableMfa);
```

**Edge cases.** A manual support reset needs identity checks stronger than the factor it replaces, and a waiting period with notifications to every known channel, so the real owner can object.

## 15. Account recovery: password reset, magic links and email change ➕

Every strong login flow has a side door: "forgot password". If that door is weaker than the front, attackers use it, so it needs the same care as login itself.

### Password reset tokens ➕

**Problem.** Reset links that are guessable, reusable, long-lived, or leaked through logs let an attacker take over an account without knowing the password.

**Mechanism.** OWASP's forgot-password guidance, turned into rules:
- the response is **identical** (message and timing) whether or not the account exists (section 13.1);
- the token is **cryptographically random** and long enough to resist brute force, **single-use**, **short-lived**, and stored **hashed**, like an API key (section 6);
- the link uses a hard-coded base URL, never the request's `Host` header;
- the reset page sets `Referrer-Policy: no-referrer` so the token isn't leaked to third-party scripts or links;
- after the reset, revoke other sessions (section 4) and **don't log the user in automatically**;
- don't lock the account because someone requested a reset, or attackers can lock out any user.

```ts title="password-reset.ts"
import { randomBytes, createHash } from 'node:crypto';
const sha256 = (s: string) => createHash('sha256').update(s).digest('hex');

export async function requestReset(email: string) {
  const user = await db.user.findUnique({ where: { email: email.toLowerCase() } });
  if (user) {
    const token = randomBytes(32).toString('base64url');
    await db.passwordReset.create({ data: {
      userId: user.id, tokenHash: sha256(token), expiresAt: new Date(Date.now() + 30 * 60_000),
    }});
    await queue.add('send-reset-email', {                    // async: same response time either way
      userId: user.id, link: `${process.env.APP_URL}/reset?token=${token}`,
    });
  }
  return { message: 'If an account exists for that email, we have sent a reset link.' };
}

export async function completeReset(token: string, newPassword: string) {
  const row = await db.passwordReset.findUnique({ where: { tokenHash: sha256(token) } });
  if (!row || row.usedAt || row.expiresAt < new Date()) throw new BadRequest('Invalid or expired link');
  await db.$transaction([
    db.passwordReset.update({ where: { id: row.id }, data: { usedAt: new Date() } }),
    db.user.update({ where: { id: row.userId }, data: { passwordHash: await hashPassword(newPassword) } }),
  ]);
  await revokeAllForUser(row.userId);                        // section 4: end every existing session
}
```

**Edge cases.**
- Sending the email **synchronously** only for existing accounts reintroduces the timing leak; enqueueing ([lesson 14](/docs/backend-first-principles/14-task-queues-background-jobs)) keeps both paths fast.
- Invalidate older outstanding tokens when a new one is issued or the password changes.
- Email security scanners sometimes open links automatically. A reset link should show a form (a POST completes the reset), never perform the change on GET.
- If the user has MFA, a reset link proves only access to the inbox. Still require the second factor before (or right after) the new password is accepted.

### Magic links and email codes ➕

**Problem.** Passwordless sign-in by email is convenient, but the link now **is** the login, so all the reset-token risks apply with an even bigger payoff.

**Mechanism.** Same token rules (random, hashed, single-use, a few minutes of lifetime), plus:
- **bind the link to the browser that asked for it**: store a random value in a cookie when the user requests the link, and require it when the link is opened, so a link forwarded or leaked to someone else doesn't log them in; if the cookie is missing (opened on another device), fall back to showing a short code the user types into the original tab;
- avoid scanner pre-fetch consuming the link by requiring a click (POST) on the landing page.

**Edge cases.** An email-only login makes the mailbox the single factor. For high-value accounts, combine it with a passkey or TOTP rather than treating it as MFA.

### Changing the email address ➕

**Problem.** An attacker with a hijacked session changes the account email to their own, then uses "forgot password" to take the account permanently.

**Mechanism.** Treat email change as a recovery-channel change: require step-up (password or MFA), send a confirmation link to the **new** address before it takes effect, send a notification with a "this wasn't me" link to the **old** address, and treat the change as a revocation event.

**Edge cases.** Until the new address is confirmed, keep the old one as the login and recovery address. Don't let two accounts claim the same unverified address, or a squatter can block a real user's sign-up.

## 16. Recap 🎓

- **AuthN = who are you; authZ = what can you do**, always within a context.
- History moved from **implicit trust** to **something you have** (seals), **something you know** (passphrases, passwords), **hashing** after plain-text leaks, **asymmetric crypto** and **tickets**, **MFA**, and today **OAuth, JWT, zero trust, passwordless**.
- **Sessions** add memory to stateless HTTP; **JWTs** move that state into a signed, self-contained token; **cookies** let the server store a token in the browser and get it back automatically.
- **Stateful** = easy revocation and control (the author's default for most apps). **Stateless** = scale, at the cost of revocation. A **hybrid** is common.
- **API keys** are for machine-to-machine access. **OAuth 2.0** solves **delegation** with scoped tokens instead of passwords; **OIDC** adds identity via the **ID token** (a JWT).
- **RBAC**: users → roles → permissions, checked early in the request; failure is **403**.
- **Generic auth errors** and **constant-time behaviour** stop attackers from learning which accounts exist.
- In production, seriously consider an **auth provider**.
- ➕ Password policy: **length + blocklist + breach screening** (NIST 800-63B), not composition rules or forced rotation.
- ➕ Password change, MFA change, email change and refresh-token reuse are **revocation events**; a per-user `token_version` cuts off issued JWTs.
- ➕ Between services, prefer **short-lived, audience-bound tokens**, **mTLS** and **workload identity** over static keys; use **token exchange** to carry the user downstream.
- ➕ Beyond RBAC: **tenant isolation** (with Postgres RLS), **ReBAC** for sharing (Zanzibar tuples, the new-enemy problem), **ABAC/policy engines** for conditional rules.
- ➕ **Impersonation** keeps both identities and is limited and logged; **audit logs** are structured, append-only and written with the change.
- ➕ **MFA**: pending state until the second factor; TOTP with replay protection; **passkeys** for phishing resistance; recovery codes and step-up for sensitive actions.
- ➕ **Account recovery** is a side door into the account: hashed, single-use, short-lived tokens, identical responses, no auto-login, and confirmation on both addresses for an email change.

## Interview questions

1. **AuthN vs authZ?** Authentication establishes identity ("who are you"); authorization decides permissions ("what can you do"). AuthN comes first.
2. **Why do sessions exist?** HTTP is stateless. A session stores per-user context server-side, keyed by a random ID that the browser returns in a cookie on every request.
3. **What are the three parts of a JWT and what does the signature guarantee?** Header (algorithm), payload (claims like `sub`, `iat`, `role`), signature. It guarantees the token was issued by the key holder and wasn't modified. It does **not** encrypt the payload.
4. **Why is JWT revocation hard and how do real systems handle it?** No server-side record exists, so a valid token works until expiry. Use short-lived access tokens with server-stored, rotated refresh tokens, plus a `jti` denylist for emergencies.
5. **If you add a Redis denylist to JWTs, what have you lost?** Statelessness: each request does a lookup again, so you've rebuilt sessions with extra complexity.
6. **Which cookie attributes would you set on a session cookie, and why?** `HttpOnly` (XSS), `Secure` (sniffing), `SameSite=Lax` or `Strict` (CSRF), `Max-Age`, and the `__Host-` prefix.
7. **When would you use API keys rather than user tokens?** Machine-to-machine access with no human login: store only a hash, scope and expire keys, and rate-limit per key.
8. **What problem did OAuth solve that password sharing created?** Delegation without handing over full, unrevocable access: scoped tokens that can be revoked individually.
9. **Why isn't OAuth 2.0 enough for "Sign in with Google"?** OAuth is authorization; it has no standard identity. OIDC adds the ID token (a JWT with `iss`, `sub`, `aud`, `nonce`).
10. **What do `state` and PKCE protect against?** `state`: CSRF on the callback. PKCE: an intercepted authorization code being redeemed by someone else.
11. **401 vs 403?** 401: not authenticated or invalid credentials. 403: authenticated but not permitted.
12. **How do you prevent account enumeration on login?** One generic error for every failure, and equal work for both paths (verify against a dummy hash when the user is missing), plus rate limiting.
13. **Why is `===` unsafe for comparing secrets?** It returns at the first mismatching byte, so timing reveals how much of a guess was correct. Use a constant-time comparison.
14. **How should passwords be stored?** With a slow, salted, memory-hard hash: Argon2id (OWASP minimum 19 MiB, t=2, p=1), never plain text or fast hashes.
15. ➕ **How can you check a password against breach data without sending it out?** k-anonymity: send only the first 5 hex characters of its SHA-1 hash to the range API and compare the returned suffixes locally.
16. ➕ **A user changes their password after a phishing scare. What else must happen?** Revoke every other session and refresh token, invalidate issued access tokens (for example by bumping a per-user token version), and notify the user.
17. ➕ **Why is a static API key a poor choice between internal services, and what replaces it?** It never expires and every copy is a full credential. Use short-lived, audience-bound tokens (client credentials with `private_key_jwt`), mTLS, or platform-issued workload identity.
18. ➕ **How would you stop one tenant's data leaking to another in a shared database?** Derive the tenant from the user's membership, scope every query, and enforce it in Postgres with row-level security set per transaction, plus tenant-scoped cache keys.
19. ➕ **What is the "new enemy" problem?** Checking permissions against stale permission data, so a user removed from an ACL can see content added after the removal. Zanzibar fixes it with consistency tokens (zookies).
20. ➕ **Why are passkeys phishing-resistant but TOTP codes aren't?** The browser includes the origin in what the authenticator signs, and the server checks it, so a signature made on a fake domain fails. A TOTP code can be typed into any site and relayed.
21. ➕ **How do you design a password reset token?** Random, at least 128 bits, stored hashed, single-use, expiring in minutes, sent via a link built from a fixed base URL, with the same response whether the account exists or not, and no automatic login afterwards.
22. ➕ **How do you build "log in as user" for support safely?** A separate short-lived session type that records both actor and subject, requires a specific permission and fresh MFA, blocks sensitive actions, and writes every action to the audit log under the actor.
