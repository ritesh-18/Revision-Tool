## 1. What a background task is 🎓

A **background task (or job)** is any code that runs **outside the request-response cycle**. The client sends a request, the server sends a response, and the background work happens separately, on its own schedule.

The defining property: **the result isn't needed immediately**. The request doesn't have to wait for it, so it can be handed to another process and finished there.

---

## 2. The motivating example: sending a verification email 🎓

The flow: a user signs up with email, name and password. The backend validates the input (format, password length and strength), stores the user, generates a verification link or a 6–8 digit code, and must **email it** to prove the address belongs to them.

Sending the email means calling a **third-party email provider** (the lesson mentions Resend, Brevo, Mailgun). You build the HTML template, fill in the link, set recipient, sender and subject, and make an HTTP call to **their** servers. They check your API key and so on, send the mail, and reply with success or failure.

### Problem: doing it synchronously
You **don't control** that provider. It can be slow or down because of a traffic spike or an outage.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant U as User
  participant API as Your backend
  participant DB as Postgres
  participant M as Email provider
  U->>API: POST /signup

  else error caught and swallowed
    API-->>U: 201 "We sent you an email" (it was never sent)

Both outcomes are bad:
1. **No error handling:** the provider failure bubbles up and the **whole signup fails**. The user sees an error for something that was only a side effect.
2. **Error handled:** signup succeeds and the UI says "we sent you an email", **but nothing was sent**. The user has to come back and press *resend*, which is another call to the same provider. If it's still down, the same lie repeats.

There's a third cost even when the provider works: **the user waits** for a network round trip to someone else's server before seeing a response.

### Solution: enqueue the work, respond immediately

<Mermaid chart={`sequenceDiagram
  autonumber
  participant U as User
  participant API as Backend (producer)
  participant Q as Queue (broker)
  participant W as Worker (consumer)
  participant M as Email provider
  U->>API: POST /signup
  API->>API: validate, insert user, create code
  API->>Q: enqueue send-verification-email (JSON payload)
  API-->>U: 201 "Check your inbox"
  Q->>W: deliver job
  W->>W: deserialize, run handler
  W->>M: send email
  alt success
    M-->>W: 200
    W->>Q: ack (job done)
  else failure
    M--xW: 503
    W->>Q: job failed, schedule retry with backoff
  end`} />

1. The API does the essential work, then **serializes** everything the email needs (recipient, name, link, template ID) into a format such as **JSON** and **pushes it onto a queue**.
2. It **returns 200/201 straight away**. The email hasn't been sent yet; the API only recorded that it must be.
3. A **consumer (worker)** running in a **separate process** takes the job off the queue and **deserializes** it into a native structure (an object in JavaScript, a dict in Python, a struct in Go).
4. The worker is configured with **which queue it listens to**, **what data shape it expects**, and a **handler**: the same code that used to run inline. It calls the provider.

Different job types can use different queues: one for email, one for in-app notifications, one for mobile push. Each has its own workers.

**Is the delay a problem?** No. With a quiet queue, the email goes out within milliseconds to a few seconds; under heavy load, maybe 5–10 seconds. Verification links typically expire after 15–20 minutes, so there's plenty of margin.

### When the provider fails: automatic retries
If the provider call fails, the **handler raises an exception**, and the job is marked failed. In the synchronous version, this would have been a 500. In a queue, the framework **puts the job back to be retried**.

The usual retry algorithm is **exponential backoff**: wait, and **double the wait** after each failure, up to a maximum number of attempts. The lesson's numbers: retry after **1 minute**, then **2**, then **4**, then **8**, with a cap of **5 attempts**.

Why this works so well: major providers rarely stay down for minutes. A typical blip lasts seconds, so the first or second retry usually succeeds, and **the user still gets the email even though the provider was down when they signed up**.

🔧 The Celery version:

```python title="celery_app.py"
import os

from celery import Celery

app = Celery("app", broker=os.environ["REDIS_URL"])
app.conf.update(
    task_acks_late=True,                 # ack when the task finishes, not when the worker receives it
    worker_prefetch_multiplier=1,        # don't hoard messages a busy worker can't start yet
    task_ignore_result=True,             # fire-and-forget jobs: keep Redis from growing forever
    result_expires=7 * 24 * 3600,        # tasks that do store results keep them a week for debugging
    broker_transport_options={"visibility_timeout": 3600},   # Redis: unacked messages come back after 1 h
    task_routes={"email.*": {"queue": "email"}, "media.*": {"queue": "media"}},
)
```

```python title="auth_service.py (producer)"
def signup(dto: SignupIn) -> dict:
    user = users.create(dto)                                    # validated, hashed, stored
    code = verification.issue(user.id)
    send_verification_email.apply_async(
        args=[user.id, code],                                   # small payload: IDs, not whole objects
        task_id=f"verify-email-{user.id}-{code}",               # traceable; Celery does NOT dedupe on it (section 7.1)
    )
    return {"id": user.id}                                      # 201, without waiting for the email
```

```python title="email_tasks.py (consumer, separate process)"
# run with: celery -A celery_app worker -Q email --concurrency 10
import os

import httpx

from celery_app import app


class TransientError(Exception):
    """Timeouts, 5xx, 429: a retry will probably work."""


class PermanentError(Exception):
    """Retrying can't help: fail now."""


http = httpx.Client(timeout=10.0)                               # a hung provider must not hang the worker


@app.task(
    name="email.verify",
    autoretry_for=(TransientError, httpx.TransportError),       # TransportError covers timeouts and connection errors
    max_retries=4,                                              # 1 try + 4 retries
    retry_backoff=60,                                           # 1 min, 2 min, 4 min, 8 min
    retry_backoff_max=3600,
    retry_jitter=True,                                          # Celery's default: randomise each delay
)
def send_verification_email(user_id: str, code: str) -> None:
    user = users_repo.get(user_id)
    if user is None:
        raise PermanentError("user deleted")                    # not in autoretry_for → fails immediately

    res = http.post(
        "https://api.resend.com/emails",
        headers={"Authorization": f"Bearer {os.environ['RESEND_KEY']}"},
        json={"from": "no-reply@app.com", "to": user.email, "subject": "Verify your email",
              "html": render_verify(user.name, code)},
    )
    if 400 <= res.status_code < 500 and res.status_code != 429:
        raise PermanentError(f"rejected: {res.status_code}")    # bad request won't fix itself
    if res.is_error:
        raise TransientError(f"provider {res.status_code}")     # 5xx / 429 → retry with backoff
```

🔧 Notes on the code:
- Celery's `retry_backoff` waits `retry_backoff × 2^retries` seconds (capped by `retry_backoff_max`, which defaults to 600 s), and `retry_jitter`, on by default, picks a random delay between 0 and that value, so thousands of failed jobs don't all retry at the same instant. In arq the same idea is `raise Retry(defer=...)` inside the job, bounded by `max_tries`.
- **Not every error deserves a retry.** A 400 from the provider (invalid address) will fail forever; an exception that isn't listed in `autoretry_for` fails the task straight away. Retry only **transient** errors (timeouts, 5xx, 429).

### Benefits so far 🎓
1. **Responsiveness:** the API no longer waits on external services or heavy work, and stops timing out because of them.
2. **Reliability:** built-in **retries** and **failure detection** for work that is likely to fail occasionally.
3. Together: a much better user experience.

## 3. What usually goes into the background 🎓

| Task | Why it's offloaded |
|---|---|
| **Sending emails** | Depends on an external provider (the example above) |
| **Image and video processing** | Resizing an upload into several sizes for phones vs desktops (small, medium, XL, 2XL); transcoding video. CPU-heavy and slow |
| **Generating reports** | E.g. a project-management tool sending a daily, weekly (Sunday 12:00) or monthly summary of completed, pending and sprint tasks as an HTML email or PDF. Runs on a **schedule** (cron); Celery (with beat) and arq (cron jobs) support scheduled jobs |
| **Push notifications** | Food-delivery apps telling you the rider reached the restaurant. Your backend can't push to a phone directly |

**How push notifications work (lesson's explanation):** when the app is installed, the device registers with the **OS vendor's push service** (Google's or Apple's) and gets a device token. Your backend stores that token. To notify a user, the backend calls **Google's or Apple's** service with the token, and **they** deliver the notification. That's an external call, so it goes in a background job.

## 4. Inside a task queue 🎓

**Definition:** a task queue is a system for **managing and distributing background jobs**. It's the engine that lets you hand work off **reliably** to a separate process.

**Analogy:** a **to-do list for your backend**. Application code adds items; workers take them one at a time and do them.

<Mermaid chart={`flowchart LR

  subgraph Broker["Broker: the queue"]

    Q2[["media queue"]]
  end
  subgraph Consumers["Consumers: worker processes"]
    W1["email worker x3"]
    W2["media worker x2"]
  end
  P1 -->|"enqueue: serialize to JSON"| Q1
  P2 -->|"enqueue"| Q2
  Q1 -->|"dequeue"| W1
  Q2 -->|"dequeue"| W2
  W1 -->|"ack"| Q1
  W2 -->|"ack"| Q2`} />

| Part | Job | Key detail |
|---|---|---|
| **Producer** | Your application code. **Creates** the task with all the data the worker will need, **serializes** it (JSON or another format), and pushes it. That's all it does | Pushing is called **enqueuing** |
| **Broker** (the queue) | A **temporary holding area** that stores tasks until a worker is ready | Implemented by RabbitMQ, Redis, or a managed service like **AWS SQS** (useful when you need workers spread across regions without running the broker yourself) |
| **Consumer / worker** | Runs in a **separate process or thread** (same codebase or a separate one), **watches the queue**, takes a task (**dequeuing**), and runs the handler registered for it | You scale it independently of the API |

🔧 **A correction worth knowing:** the lesson mentions **Redis Pub/Sub** as a way to build task queues. Pub/Sub is **fire-and-forget**: if no subscriber is connected at that moment, the message is gone, and there's no acknowledgement or retry. Real Redis-based queues (Celery's Redis transport, arq, RQ, and in other ecosystems Sidekiq and BullMQ) are built on **lists, sorted sets and hashes** (or Streams), which **persist** jobs until they're processed. Don't build a job queue on Pub/Sub.

### Choosing a broker: Postgres, Redis, SQS or Kafka ➕

The lesson names several brokers; the choice between them decides your durability, your latency, and whether enqueuing can be atomic with your business data, so it deserves its own comparison.

#### Postgres as the queue (`FOR UPDATE SKIP LOCKED`)
**Problem:** you already run Postgres, you want "insert the order **and** its job" to commit or fail together (no dual write, section 9.1), and you'd rather not operate another system.

**Why the naive version fails:** a `jobs` table where every worker runs `SELECT ... ORDER BY id LIMIT 1` makes all workers pick the **same** row. Without a lock, two workers run it; with a plain `FOR UPDATE`, all but one worker **block** waiting on that row's lock, so ten workers process one job at a time.

**Mechanism:** `FOR UPDATE SKIP LOCKED` makes each worker **skip** rows another transaction has locked and take the next free one. The Postgres docs say it directly: skipping locked rows gives an inconsistent view, so it isn't for general queries, but it "can be used to avoid lock contention with multiple consumers accessing a queue-like table". Add a **lease** column (`locked_until`), and you have the visibility timeout from section 5 too.

```sql title="jobs.sql"
CREATE TABLE jobs (
  id           bigserial PRIMARY KEY,
  queue        text        NOT NULL,
  payload      jsonb       NOT NULL,
  run_at       timestamptz NOT NULL DEFAULT now(),   -- delayed jobs and backoff
  attempts     int         NOT NULL DEFAULT 0,
  locked_until timestamptz,                          -- lease = visibility timeout
  done_at      timestamptz
);
CREATE INDEX jobs_ready ON jobs (queue, run_at) WHERE done_at IS NULL;
```

```python title="pg_worker.py"
import psycopg
from psycopg.rows import dict_row

# claim up to 10 ready jobs; a crashed worker's lease simply expires and the job becomes claimable again
CLAIM = """
UPDATE jobs SET locked_until = now() + interval '60 seconds', attempts = attempts + 1
WHERE id IN (
  SELECT id FROM jobs
  WHERE queue = 'email' AND done_at IS NULL AND run_at <= now()
    AND (locked_until IS NULL OR locked_until < now())
  ORDER BY run_at
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
RETURNING id, payload, attempts
"""


def work_once(conn: psycopg.Connection) -> None:    # conn opened with autocommit=True, row_factory=dict_row
    for job in conn.execute(CLAIM).fetchall():      # the claim commits at once
        try:
            handle(job["payload"])
            conn.execute("UPDATE jobs SET done_at = now() WHERE id = %s", (job["id"],))
        except Exception:
            delay_sec = min(3600, 30 * 2 ** job["attempts"])                   # exponential backoff
            conn.execute(
                "UPDATE jobs SET locked_until = NULL, run_at = now() + %s * interval '1 second' WHERE id = %s",
                (delay_sec, job["id"]),
            )
```

**Edge cases:**
- **Don't hold the claiming transaction open while the job runs.** The lease pattern above commits the claim at once; a long open transaction holds locks and blocks vacuum.
- **Table bloat:** every claim and completion is an `UPDATE`, which leaves dead row versions. Delete or archive finished jobs regularly and let autovacuum keep up.
- **Polling latency vs load:** polling every 100 ms from 50 workers is a steady query load. `LISTEN`/`NOTIFY` can wake workers when a job is inserted, with polling as the fallback.
- **Throughput ceiling:** fine for hundreds to low thousands of jobs per second on a healthy database; beyond that the queue competes with your OLTP traffic. Libraries such as Procrastinate implement this pattern for Python (pg-boss does the same for Node).

#### Redis-backed queues (Celery, arq)
**Strength:** very low latency, rich features (delays, priorities, chains and groups, rate limits, schedules) without extra infrastructure beyond Redis.

**Why durability is your job:** Redis keeps jobs in RAM. Any `maxmemory-policy` other than **`noeviction`** lets Redis delete queue keys (Celery's per-queue lists, arq's queue sorted set and job keys) under memory pressure, silently losing jobs; BullMQ's production guide states the rule explicitly, and it holds for every Redis-backed queue. Turn on **AOF** persistence too (fsync every second is enough for most apps).

```bash title="redis.conf for a queue instance"
maxmemory-policy noeviction
appendonly yes
appendfsync everysec
```

**Edge cases:**
- **Keep the queue Redis separate from the cache Redis** (the cache wants `allkeys-lru`, the queue needs `noeviction`).
- **With `noeviction`, a full Redis rejects writes**, so `delay()` and `enqueue_job()` start raising. Result retention (`task_ignore_result` and `result_expires` in Celery, `keep_result` in arq) and depth alerts are what keep it from filling.
- **Failover can lose the last second of jobs** (asynchronous replication; see the caching lesson's high-availability section), and enqueuing can't share a transaction with Postgres, so critical jobs still need the outbox (section 9.1).

#### Amazon SQS
**Strength:** fully managed, scales without capacity planning, built-in visibility timeout and dead-letter queues.

**What you must design around:**
- **Standard queues** deliver at least once and may deliver **out of order**. **FIFO queues** keep order per **message group** and deduplicate within a window, at lower throughput.
- **Message size** is capped at **1 MiB** (raised from 256 KiB in August 2025), so large inputs go to S3 and the message carries the key.
- **Short delays only:** per-message `DelaySeconds` goes up to 15 minutes, so a "delete account in 7 days" job needs a scheduler (or EventBridge Scheduler) rather than a delayed message.
- **Long polling** (`WaitTimeSeconds` up to 20) avoids paying for empty receives.

```python title="sqs_worker.py"
import json
from concurrent.futures import ThreadPoolExecutor

import boto3

sqs = boto3.client("sqs")                                       # boto3 clients are thread-safe
pool = ThreadPoolExecutor(max_workers=10)


def process(m: dict) -> None:
    handle(json.loads(m["Body"]))                               # raise → no delete → redelivered
    sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=m["ReceiptHandle"])   # the ack


while running:
    resp = sqs.receive_message(
        QueueUrl=QUEUE_URL, MaxNumberOfMessages=10, WaitTimeSeconds=20, VisibilityTimeout=60,
    )
    for fut in [pool.submit(process, m) for m in resp.get("Messages", [])]:
        if exc := fut.exception():                              # waits for it; a failure only means "not deleted"
            logger.warning("message failed", exc_info=exc)
```

#### Kafka: a log, not a job queue
**Problem:** teams already running Kafka try to use it for background jobs and hit strange stalls.

**Why it happens:** Kafka doesn't acknowledge **individual messages**. A consumer group tracks one **offset per partition**: "everything before position N is done". If message N fails, the consumer can't skip it and come back later without extra machinery, so one poison or slow message **blocks its whole partition** (head-of-line blocking), and parallelism is capped by the number of partitions.

**Mechanism when you must:** retry topics with increasing delays plus a dead-letter topic, all implemented in your consumer code. That's a lot of work you get for free from a job queue.

**Where Kafka is the right tool:** high-volume **event streams** that several independent consumers read (search indexing, analytics, audit), with replay from any point in time, and per-key ordering via partitioning.

| Need | Good fit |
|---|---|
| Enqueue atomically with business data, modest volume, no new infra | Postgres + `SKIP LOCKED` |
| Low latency, delays, priorities, workflows, in Python | Redis + Celery or arq (`noeviction`, AOF) |
| Managed, elastic, AWS-native, no broker to run | SQS (+ DLQ, FIFO when order matters) |
| Durable event stream, many consumers, replay | Kafka (not for per-job retries) |

## 5. Acknowledgements and the visibility timeout 🎓

### Problem
A worker has taken a job off the queue, and then it **crashes**, or the external service hangs. If the queue had already deleted the job, **the job is lost**.

### Mechanism 1: acknowledgements
The job isn't removed when it's handed out. When the worker finishes, it sends an **ack** saying "done, delete it". If it fails, the queue applies its retry rules. Frameworks like Celery, BullMQ and Asynq handle these cases for you.

### Mechanism 2: visibility timeout
While a worker holds a job, the job is **in progress** and **invisible** to other workers. That period is the **visibility timeout**. If no ack arrives before it ends (the worker crashed, hung, or lost its connection), the queue assumes the worker is dead and **makes the job visible again** so another worker can take it.

**Someone must eventually ack every job**, as a success or a failure.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant Q as Queue
  participant W1 as Worker 1
  participant W2 as Worker 2
  W1->>Q: receive job 42
  Note over Q: job 42 invisible, timer starts (e.g. 30 s)
  W1->>W1: processing...
  W1--xW1: process crashes (no ack)
  Note over Q: timeout expires: job 42 visible again
  W2->>Q: receive job 42
  W2->>W2: process
  W2->>Q: ack: delete job 42`} />

🔧 **The engineering consequence: at-least-once delivery.** A worker can finish the work and crash **just before** acking. The timeout then hands the job to someone else, and **the work runs twice**. Queues guarantee *at least once*, not *exactly once*. So **handlers must be idempotent** (section 7).

🔧 **How the timeout is tuned:**
- **AWS SQS:** default visibility timeout **30 seconds**, maximum **12 hours**. Long jobs should extend it while they run (`ChangeMessageVisibility`, a "heartbeat"). Too short → duplicates while a slow job is still running; too long → a crashed job sits idle for a long time before a retry.
- **Celery:** by default a task is acked **when the worker receives it**, so a crash loses it; set `task_acks_late=True` to ack after it finishes. On the **Redis** broker, an unacked message is handed out again once `visibility_timeout` passes (default **1 hour**), even if the first worker is still running it, so set the timeout above your longest task (and above any `countdown`/`eta`, which Celery holds unacked in the worker until it's due). On **RabbitMQ**, an unacked message returns as soon as the worker's connection drops, and the broker's `consumer_timeout` (30 minutes by default) closes channels that hold one for too long.
- **arq:** a worker marks a running job with an "in progress" key that expires after the job's timeout plus 10 seconds; if the worker dies, the key expires and another worker can pick the job up. The Python lesson: an arq worker is **one `asyncio` event loop**, so a CPU-heavy job that **blocks the loop** stalls every other job in that worker, and `job_timeout` can't even interrupt it (cancellation only happens at an `await`). Run CPU-heavy work in a `ProcessPoolExecutor` via `loop.run_in_executor`, or in Celery's **prefork** pool, where each task runs in its own child process. Threads don't help here: on a standard CPython build the **GIL** lets only one thread run Python code at a time.

## 6. The four kinds of tasks 🎓

### 6.1 One-off tasks
Triggered once by an event, and the most common type: verification email after signup, welcome email after verification, password-reset email, a notification when someone messages you.

```python
send_password_reset.delay(user_id, token)
```

### 6.2 Recurring tasks
Run **periodically**:
- **Reports:** daily, monthly or annual stats for users.
- **Cleanup and maintenance:** the lesson's example is stateful auth. Every login creates a row in a `sessions` table; users who log in and out for years leave many **orphaned, inactive sessions**. A job running every month (or every two or three) deletes long-inactive sessions to free space.

🔧 Celery uses **beat**, a separate scheduler process that reads `beat_schedule` and enqueues a task at each tick. The schedule is declared in code, so every deploy simply ships the current version without creating duplicates. arq declares **cron jobs** on the worker instead:

```python title="schedules.py"
from arq import cron
from celery.schedules import crontab

app.conf.timezone = "UTC"
app.conf.beat_schedule = {
    "cleanup-orphan-sessions": {
        "task": "maintenance.cleanup_sessions",
        "schedule": crontab(minute=0, hour=3, day_of_month=1),   # 03:00 UTC on the 1st of every month
        "kwargs": {"older_than_days": 90},
    },
    "weekly-report": {
        "task": "reports.fan_out_weekly",
        # Sunday midnight IST = Saturday 18:30 UTC (India has no DST, so the conversion never changes)
        "schedule": crontab(minute=30, hour=18, day_of_week="sat"),
    },
}


# the arq equivalent lives in the worker settings
class WorkerSettings:
    functions = [cleanup_sessions]
    cron_jobs = [cron(cleanup_sessions, day=1, hour=3, minute=0)]   # unique=True by default
```

```python title="cleanup_tasks.py"
@app.task(name="maintenance.cleanup_sessions")
def cleanup_sessions(older_than_days: int = 90) -> None:
    # delete in small batches so one job never holds big locks or runs for an hour
    with psycopg.connect(DSN, autocommit=True) as conn:
        while True:
            deleted = conn.execute(
                """DELETE FROM sessions WHERE id IN (
                     SELECT id FROM sessions WHERE last_seen_at < now() - make_interval(days => %s) LIMIT 5000
                   )""",
                (older_than_days,),
            ).rowcount
            if deleted == 0:
                break
```

🔧 Edge case: if you run **three API replicas** that each start an in-process scheduler (APScheduler, the `schedule` library, or an `asyncio` loop around `sleep`), the job runs **three times**. The same goes for Celery beat: run **exactly one** beat process (its own single-replica deployment), never one per worker. arq's cron jobs are unique by default: every worker evaluates the schedule, but the job ID is derived from the tick time and stored in Redis, so exactly one job is produced per tick no matter how many workers run.

### 6.3 Schedules, time zones and DST ➕

Recurring tasks look like "a cron expression and done", but as soon as a schedule is meant to follow **someone's local time**, or the scheduler is down at the moment a tick was due, the cron string stops being the whole answer.

#### UTC for the system, the user's zone for the user
**Problem:** "send the weekly report at 9:00 on Monday". A cron pinned to `0 9 * * 1` in UTC means 14:30 in India and 4:00 or 5:00 in New York **depending on the season**, because US offsets change with daylight saving time and India's doesn't.

**Why it happens:** an offset like `-05:00` is not a time zone. A zone such as `America/New_York` is a **set of rules** that maps instants to offsets, and those rules change twice a year (and occasionally by law).

**Mechanism:**
- **System jobs** (cleanup, reindexing, billing runs) are scheduled in **UTC**: they don't care about anyone's wall clock and never hit DST edges.
- **User-facing jobs** store the user's **IANA zone name**, never an offset, and are computed in that zone. For one zone, the scheduler's time zone setting works (Celery's `timezone` and arq's worker `timezone` apply to the whole schedule, and a zone without DST such as IST can simply be converted to UTC, as in section 6.2). For **many** users in many zones, don't create one schedule entry per user; run **one hourly tick in UTC** that selects the users whose local time is now 9:00 on a Monday:

```sql title="due-weekly-reports.sql"
-- runs every hour at :00 UTC (a missed 9:00 tick is caught at 10:00); users.tz holds e.g. 'America/New_York' or 'Asia/Kolkata'
SELECT id
FROM users
WHERE extract(isodow FROM now() AT TIME ZONE tz) = 1          -- Monday in the user's zone
  AND extract(hour   FROM now() AT TIME ZONE tz) >= 9         -- 9 o'clock or later in the user's zone
  AND (last_report_local_date IS NULL
       OR last_report_local_date < (now() AT TIME ZONE tz)::date);   -- not sent yet for this local day
```

The worker that sends the report sets `last_report_local_date` in the same transaction as recording the send, and the job ID includes the local date (`weekly-<userId>-2026-03-09`), so a duplicate tick is a no-op.

**Edge cases:** zones with 30- or 45-minute offsets (India is UTC+5:30, Nepal UTC+5:45) never sit on a whole hour when the tick runs at `:00` UTC, so with the query above Indian users get their report at 9:30. If the exact minute matters, run the tick every 15 minutes and compare minutes too.

#### DST gaps and overlaps
**Problem:** in `America/New_York`, on the spring-forward day the local times **02:00 to 02:59 do not exist**, and on the fall-back day **01:00 to 01:59 happen twice**. A job scheduled for 02:30 local can be skipped; a job at 01:30 can fire twice.

**Why it happens:** the scheduler has to turn "02:30 local" into an instant, and on those two days there are zero or two valid answers. Libraries choose differently. Python's `zoneinfo` doesn't reject a non-existent time: `datetime(2026, 3, 8, 2, 30, tzinfo=ZoneInfo("America/New_York"))` is accepted, uses the pre-transition offset (-05:00) and comes out as 03:30 EDT once converted to UTC and back. For an ambiguous time the `fold` attribute picks the instant (`fold=0`, the default, is the first 01:30, in EDT; `fold=1` is the second, in EST).

**Mechanism:**
1. **Don't schedule user jobs between 01:00 and 03:00 local** unless you must; US and EU transitions both fall in that window.
2. **Make every run idempotent per period**, keyed on the **local date** (or week), as above. A double fire then does nothing.
3. **Prefer "has it run for this period yet?" over "is it exactly time T?"**. The SQL above catches up a skipped run on the next tick, because the condition is "not sent today and it's at or after 9", not "it's exactly 9:00:00".

```python title="local_period_key.py"
from datetime import datetime
from zoneinfo import ZoneInfo


def period_key(user_id: str, tz: str) -> str:
    year, week, _ = datetime.now(ZoneInfo(tz)).isocalendar()   # ISO week in the user's zone
    return f"weekly-{user_id}-{year}-W{week:02d}"

# two fires in the same local week → same job ID → arq's enqueue_job(..., _job_id=key) returns None the second time
```

**Edge cases:** an invalid zone name (typo, or a zone removed from the database) makes `ZoneInfo(...)` raise `ZoneInfoNotFoundError`; validate zones on input against `zoneinfo.available_timezones()`. On Windows and slim container images there may be no system zone database at all, so add the `tzdata` package as a dependency.

#### Missed runs and catch-up
**Problem:** Redis or the scheduler was down from 02:50 to 03:20, and the 03:00 cleanup job was never produced. Nothing errors; the work silently doesn't happen.

**Why it happens:** a schedule produces a job **at** a moment. If nothing was listening at that moment, the trigger is gone. (This is the same fire-and-forget gap as Pub/Sub, at a coarser grain.)

**Mechanism:** make the job work from a **watermark** rather than from its trigger time. Each run processes "everything since the last successful run" and moves the watermark forward only on success. A missed or failed run is then absorbed by the next one.

```python title="watermark_job.py"
from datetime import UTC, datetime, timedelta


def export_events(conn: psycopg.Connection) -> None:
    (last,) = conn.execute("SELECT last FROM watermarks WHERE name = 'export'").fetchone()
    until = datetime.now(UTC) - timedelta(minutes=1)            # leave a minute for late commits
    start = last
    while start < until:
        end = min(start + timedelta(hours=1), until)            # one hour per chunk
        export_range(start, end)                                # idempotent: re-exporting a range overwrites
        conn.execute("UPDATE watermarks SET last = %s WHERE name = 'export'", (end,))
        start = end
```

**Edge cases:** after a long outage the catch-up can be huge; chunking (as above) keeps each step small and retryable. The one-minute margin matters: rows committed slightly late with an earlier timestamp would otherwise fall behind the watermark and never be exported.

### 6.4 Chained tasks (parent-child dependencies)
The lesson's example is an **LMS** (learning platform, like Udemy). An instructor uploads a course video (the upload itself goes straight to S3 via a presigned URL, and the API acknowledges immediately). Then:

<Mermaid chart={`flowchart LR
  U["Video uploaded"] --> E["1. Encode into several<br/>resolutions and formats"]
  E --> T["2a. Generate thumbnails"]
  E --> S["2b. Generate transcript<br/>(subtitles)"]
  T --> TP["3. Resize thumbnails for<br/>devices and networks"]
  TP --> D["Course ready"]
  S --> D`} />

- **Encoding** must finish first.
- **Thumbnail generation** depends on encoding; **thumbnail resizing** depends on thumbnail generation.
- **Transcription** also depends on encoding, but **not** on the thumbnails, so 2a and 2b **run in parallel**.

A task starts only when its parent has **completed successfully**.

🔧 **Two ways to build this in Python:**

**(a) Each step enqueues the next** when it finishes. Simple and flexible (shown with arq, because its job IDs deduplicate):

```python title="media_jobs.py"
async def encode(ctx: dict, video_id: str) -> None:
    await encode_video(video_id)                                # ffmpeg in a subprocess, awaited
    redis = ctx["redis"]                                        # arq passes its Redis pool in ctx
    # fan out to the parallel children
    await redis.enqueue_job("thumbnails", video_id, _job_id=f"thumbs-{video_id}")
    await redis.enqueue_job("transcribe", video_id, _job_id=f"transcribe-{video_id}")


async def thumbnails(ctx: dict, video_id: str) -> None:
    await generate_thumbnails(video_id)
    await ctx["redis"].enqueue_job("resize_thumbnails", video_id, _job_id=f"resize-{video_id}")

# ...


class WorkerSettings:
    functions = [encode, thumbnails, transcribe, resize_thumbnails]
```

The deterministic `_job_id`s matter: if `encode` crashes after enqueuing the children and is retried, the second `enqueue_job` calls return `None` instead of creating duplicates (as long as the earlier job, or its kept result, is still in Redis).

**(b) A Celery canvas.** Celery composes tasks into **workflows**: `chain` runs steps in order, `group` runs them in parallel, and a group followed by another task becomes a **chord**, whose callback runs only when **every** member of the group has succeeded and receives their results as a list. So you model "course ready" as the callback of the parallel branches:

```python title="course_flow.py"
from celery import chain, group


def start_publish_pipeline(video_id: str):
    return chain(
        encode.si(video_id),                                    # .si(): immutable signature, ignores the parent's result
        group(
            chain(thumbnails.si(video_id), resize_thumbnails.si(video_id)),
            transcribe.si(video_id),
        ),
        publish_course_video.s(video_id),                       # chord callback: gets [resize_result, transcribe_result]
    ).apply_async()
```

Unlike BullMQ's flow trees, where a child job can't have two parents, a canvas runs `encode` once and fans out after it. The price: a chord needs a **result backend** (it counts finished group members there, so these tasks must not use `ignore_result`), and if one member fails the callback never runs, so attach an error callback with `link_error` and alert on it.

### 6.5 Batch tasks
One trigger creates **many** tasks.

**Example 1: account deletion.** A large platform may hold a user's data across many tables, shards or regions. Deleting it all inside the request could take 40–50 seconds or more, which is far too long to block an API call.
- The API **responds 200 immediately**, logs the user out, and enqueues `delete-account`.
- Optionally there's a **grace period** (say 3 or 7 days) during which logging back in cancels the deletion.
- The worker then fans out: remove the user from projects they own, delete their profile, delete their assets (logos, cover images), delete the account itself, and send a "your account has been deleted" email.

**Example 2: scheduled reports at midnight.** One scheduled tick creates **thousands** of jobs, one per user, each generating and sending that user's report.

<Mermaid chart={`flowchart TD
  T["delete-account requested"] --> G{"grace period?"}
  G -->|"yes"| DL["delayed job: run in 7 days<br/>cancelled if the user logs back in"]
  G -->|"no"| F["fan-out job"]
  DL --> F
  F --> J1["remove from projects"]
  F --> J2["delete assets in S3"]
  F --> J3["delete profile rows"]
  J1 --> FIN["delete user + send confirmation email"]
  J2 --> FIN
  J3 --> FIN`} />

A 7-day delay is a poor fit for a Celery `countdown`: the worker that receives the message holds it in memory, unacknowledged, until it's due, and on the Redis broker it is handed out again every `visibility_timeout`. arq stores deferred jobs in Redis, in a sorted set scored by run time, so long delays cost nothing:

```python title="account_deletion.py"
from datetime import timedelta

from arq.jobs import Job, JobStatus

# grace period = a deferred job you can cancel
await arq.enqueue_job("delete_account", user_id, _job_id=f"delete-{user_id}", _defer_by=timedelta(days=7))

# on login during the grace period (the worker needs allow_abort_jobs=True;
# the handler should still re-check the user's "deletion requested" flag before deleting anything):
job = Job(f"delete-{user_id}", arq)
if await job.status() == JobStatus.deferred:
    await job.abort(timeout=5)

# midnight report fan-out: page through users and enqueue in chunks
async for ids in page_user_ids(1000):
    await asyncio.gather(*(
        arq.enqueue_job("weekly_report", uid, _job_id=f"weekly-{week_key}-{uid}") for uid in ids
    ))
```

## 7. Design considerations 🎓

### 7.1 Idempotency
**Problem:** jobs are retried after failures, and (section 5) can be delivered twice. A task must be **safe to run more than once** without side effects piling up.

**The lesson's mechanism:** in the delete-account task, run the database changes **inside a transaction**. If something fails halfway (a DB error or a failed external call), the transaction is **rolled back**, so the retry starts from a clean **0%** instead of from a half-deleted state.

🔧 **Transactions only cover the database.** External side effects (an email, a charge, an S3 delete) can't be rolled back. Techniques for those:

| Technique | How it works |
|---|---|
| **Deterministic job IDs** | arq: `enqueue_job(..., _job_id=f"welcome-{user_id}")` returns `None` if that ID is already queued (or its result is still kept), so a double click or a retried producer doesn't create two jobs. Celery does **not** deduplicate on `task_id`; claim a Redis key with `SET NX` before sending, or rely on the check below |
| **Check before acting** | Make each step a no-op if already done: `UPDATE users SET welcome_sent_at = now() WHERE id = $1 AND welcome_sent_at IS NULL RETURNING id`. Zero rows → already sent, skip |
| **Provider idempotency keys** | Payment and some email APIs accept an `Idempotency-Key` header; resending the same key returns the original result instead of acting twice |
| **Naturally idempotent operations** | "Set status to X", "delete if exists", "upsert" are safe to repeat; "increment" and "append" are not |

```python title="idempotent_step.py"
row = conn.execute(
    "UPDATE users SET welcome_sent_at = now() WHERE id = %s AND welcome_sent_at IS NULL RETURNING id",
    (user_id,),
).fetchone()
if row is None:
    return                                                      # a previous run already did this
try:
    send_welcome_email(user_id)
except Exception:
    conn.execute("UPDATE users SET welcome_sent_at = NULL WHERE id = %s", (user_id,))   # release the claim for the retry
    raise
```

### 7.2 Error handling
Everything happens in **another process**, with nobody watching a response. Catch, **log with context**, and let the queue **retry**. Missing an edge case here means silent failures.

### 7.3 Monitoring
You need a live picture of: **how many jobs are queued**, **how many succeeded**, **how many failed**, and **why** (an external service? an internal bug?). The lesson suggests emitting **metrics** on every event and viewing them with **Prometheus + Grafana** (logging and monitoring get their own lesson later).

🔧 With Celery on Redis, each queue is a Redis list named after the queue, so its depth is one `LLEN` you can export (Celery keeps no "failed" set; failures are counted as they happen, section 7.4):

```python title="queue_metrics.py"
import os
import time

import redis
from prometheus_client import Gauge

depth = Gauge("queue_jobs", "jobs per state", ["queue", "state"])
broker = redis.Redis.from_url(os.environ["REDIS_URL"])


def export_depth_forever(queues: tuple[str, ...] = ("email", "media")) -> None:   # run in a small sidecar
    while True:
        for q in queues:
            depth.labels(queue=q, state="waiting").set(broker.llen(q))
        time.sleep(15)
```

### 7.4 Measuring job latency, not just counts ➕

Counts tell you how much is in the queue; what users feel is **how long** a job waited, so the metrics that drive alerts and autoscaling (section 7.6) need to be time-based. (Carrying a trace across the queue with a `traceparent` in the job data is covered in the logging, monitoring and observability lesson.)

#### Wait time vs run time
**Problem:** 10,000 waiting jobs may be fine (they drain in 20 seconds), while 50 waiting jobs may be a disaster (each has been there 30 minutes because every worker is stuck on a hung provider). Depth alone can't tell these apart.

**Why it happens:** depth is a stock; latency depends on depth **and** drain rate. Only time measured per job captures both.

**Mechanism:** Celery exposes the job lifecycle as **signals**: stamp an `enqueued_at` header when the producer publishes (`before_task_publish`), note the start in `task_prerun`, and the end in `task_postrun`. From them:
- **Wait time** = start − the moment the job became ready (`enqueued_at`, or its `eta` if it was delayed): how long a ready job sat in the queue. This is the user-visible delay and the best scaling signal.
- **Run time** = end − start: how long the handler took. Rising run time with steady volume means a dependency is slowing down.
- **Age of the oldest waiting job**: the one number that says "we are behind", even before any job finishes.

```python title="queue_latency.py"
import json
import time
from datetime import datetime

from celery.signals import before_task_publish, task_postrun, task_prerun
from prometheus_client import Gauge, Histogram

wait = Histogram("job_wait_seconds", "ready → active", ["queue", "name"],
                 buckets=[0.1, 0.5, 1, 5, 15, 60, 300, 900])
run = Histogram("job_run_seconds", "active → finished", ["queue", "name", "result"],
                buckets=[0.05, 0.25, 1, 5, 30, 120, 600])
oldest = Gauge("job_oldest_waiting_seconds", "age of oldest waiting job", ["queue"])

_started: dict[str, float] = {}


@before_task_publish.connect
def stamp(headers=None, **_):
    headers["enqueued_at"] = time.time()                        # every publish, including each retry


@task_prerun.connect
def on_start(task_id=None, task=None, **_):
    now = _started[task_id] = time.time()
    req = task.request
    ready_at = getattr(req, "enqueued_at", None) or now         # custom headers appear on task.request
    if req.eta:
        ready_at = max(ready_at, datetime.fromisoformat(req.eta).timestamp())
    queue = (req.delivery_info or {}).get("routing_key", "unknown")
    wait.labels(queue, task.name).observe(now - ready_at)


@task_postrun.connect
def on_end(task_id=None, task=None, state=None, **_):
    if (started := _started.pop(task_id, None)) is not None:
        queue = (task.request.delivery_info or {}).get("routing_key", "unknown")
        run.labels(queue, task.name, "ok" if state == "SUCCESS" else "error").observe(time.time() - started)


def export_oldest_forever(queue: str = "email") -> None:       # in the same sidecar as queue_metrics.py
    while True:
        raw = broker.lindex(queue, -1)                          # Celery LPUSHes and BRPOPs: the tail is the oldest
        enqueued_at = json.loads(raw)["headers"].get("enqueued_at") if raw else None
        oldest.labels(queue).set(time.time() - enqueued_at if enqueued_at else 0)
        time.sleep(15)
```

**Edge cases:**
- **Retries inflate wait time** if you measure from creation: a job retried after 8 minutes of backoff "waited" 8 minutes by design. Here each retry is a new message with its own `enqueued_at` and `eta`, so only the ready-to-start wait is counted; record `task.request.retries` as a label or measure the first attempt separately if you need both views.
- **Label by queue and task name only.** Never by user or job ID: that creates one time series per job.
- **Prefork children are separate processes.** Each has its own copy of these metrics, so run `prometheus_client` in its multiprocess mode (`PROMETHEUS_MULTIPROC_DIR`) for Celery workers.

#### Classifying failures
**Problem:** "failed jobs per minute rose" doesn't say whether to page someone (your code is broken) or wait (the provider is having a bad hour).

**Mechanism:** count failures by **class** with a small fixed set of labels, decided where the error is raised: `transient` (timeouts, 5xx, 429: retry will likely work), `permanent` (validation, 4xx, missing data: `PermanentError`, outside `autoretry_for`), `bug` (anything unexpected). Alert immediately on `bug`, on a rate threshold for `permanent`, and only on sustained levels plus a growing backlog for `transient`.

```python title="failure_class.py"
import httpx
from celery.signals import task_failure, task_retry
from prometheus_client import Counter

failures = Counter("job_failures", "failures by class", ["queue", "name", "class"])   # exported as job_failures_total


def _queue(request) -> str:
    return (getattr(request, "delivery_info", None) or {}).get("routing_key", "unknown")


@task_retry.connect                                             # an attempt failed and will be retried
def on_retry(request=None, reason=None, **_):
    failures.labels(_queue(request), request.task, "transient").inc()


@task_failure.connect                                           # Celery gave up on the task
def on_failure(sender=None, exception=None, **_):
    if isinstance(exception, PermanentError):
        cls = "permanent"
    elif isinstance(exception, (TransientError, httpx.TransportError)):
        cls = "transient"                                       # transient, but the retries ran out
    else:
        cls = "bug"
    failures.labels(_queue(sender.request), sender.name, cls).inc()
```

**Edge cases:** a "transient" error that never stops (a provider permanently rejecting your new API key) looks harmless per attempt; that is what the **final failure** count (`task_failure` fires only once the retries are exhausted) and the dead-letter alerts in section 9.4 are for.

### 7.5 Scalability
When the user base doubles, you need more processing. Design so that you **scale consumers horizontally**: add more worker processes or nodes, with no code change. This works because workers are **stateless** and the broker coordinates who gets which job.

### 7.6 Backpressure and queue-based autoscaling ➕

"Add more workers" needs two more answers: **how many**, and **what happens upstream** when even the maximum isn't enough.

#### How many workers: Little's law
**Problem:** you guess "4 workers, concurrency 10" and either the backlog grows all day or 90% of the slots sit idle.

**Why it happens:** throughput is limited by **concurrency divided by job duration**, not by the number of processes. Little's law states it for any stable system: **in-flight work = arrival rate × time each item spends in the system**.

**Mechanism:** measure arrival rate and run time (section 7.4), then size: `slots needed = jobs per second × average run seconds`, plus headroom for spikes (aim for roughly 60–70% busy). Example: 50 emails per second × 0.4 s per send = 20 busy slots on average; with headroom, about 30 slots, e.g. 3 workers at `--concurrency 10`.

```python title="capacity.py"
import math


def slots_needed(jobs_per_sec: float, avg_run_sec: float, target_utilisation: float = 0.65) -> int:
    return math.ceil(jobs_per_sec * avg_run_sec / target_utilisation)


slots_needed(50, 0.4)   # → 31
```

**Edge cases:**
- **I/O-bound vs CPU-bound.** Email or HTTP jobs mostly wait on the network, so one arq worker (a single event loop) or a Celery worker using the `threads` or `gevent` pool can run dozens concurrently. Image or video jobs burn CPU, and under the GIL threads can't run Python code in parallel, so use Celery's **prefork** pool with concurrency about one per core, and scale with processes.
- **Downstream limits cap you before workers do.** `workers × concurrency` jobs that each use a database connection must fit in the pool and in Postgres `max_connections`; adding workers past that point only adds waiting.

#### Autoscale on backlog, not CPU
**Problem:** a CPU-based autoscaler sees email workers at 5% CPU and never adds replicas, while the backlog grows by thousands per minute.

**Why it happens:** I/O-bound workers are **waiting**, not computing. CPU says nothing about whether the queue is keeping up.

**Mechanism:** scale on the signals from section 7.4: **waiting jobs per replica** or **age of the oldest job**. On Kubernetes, **KEDA** adds event-driven scalers; its Prometheus scaler can scale a deployment on the metrics exported above (it also has a Redis lists scaler that reads a list's length directly, which matches Celery's Redis transport, but priorities split one queue into several lists and arq uses a sorted set instead, so the exported metric is the safer contract).

```yaml title="keda-email-workers.yaml"
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: email-workers }
spec:
  scaleTargetRef: { name: email-worker }      # the Deployment
  minReplicaCount: 1
  maxReplicaCount: 20                          # cap: protect the provider and the database
  cooldownPeriod: 300
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus:9090
        query: sum(queue_jobs{queue="email",state="waiting"})
        threshold: "500"                       # target: about 500 waiting jobs per replica
```

**Edge cases:**
- **Scaling down kills workers mid-job.** Workers must drain on `SIGTERM` (section 9.2), and the pod's grace period must exceed your longest job, or scale-down creates redelivered jobs and duplicates.
- **More workers can make an outage worse.** If the backlog exists because the provider is failing, scaling up multiplies the failing calls. Cap `maxReplicaCount`, and let the rate limiter (section 7.8) bound the call rate regardless of replica count.

#### Backpressure at the producer
**Problem:** during a long provider outage the email queue grows to millions of jobs. Redis (with `noeviction`, as it must be) fills up, and now **every** `delay()` fails, including password resets and payment jobs sharing that Redis.

**Why it happens:** a queue decouples producers from consumers in time, but not in **space**. If consumers stop, the buffer grows until something runs out.

**Mechanism:** decide per job type what happens when its queue is too deep:
- **Critical jobs** (the only record of work owed): never drop. Keep them in a separate Redis or in the outbox table (section 9.1), which has disk-sized capacity.
- **Optional jobs** (analytics events, "someone viewed your profile"): **shed** them, or coalesce them (one "you have new views" job per user per hour instead of one per view).
- **User-triggered heavy work** (exports): reject with `429` or `503` and a `Retry-After`, so the user knows instead of waiting forever.

```python title="enqueue_with_backpressure.py"
import threading
import time
from contextlib import suppress

import redis
from fastapi import HTTPException

MAX_WAITING = 200_000
_cached_depth = 0


def _refresh_depth() -> None:
    global _cached_depth
    while True:
        with suppress(redis.RedisError):
            _cached_depth = broker.llen("exports")
        time.sleep(5)


threading.Thread(target=_refresh_depth, daemon=True).start()   # daemon: never blocks shutdown


def request_export(user_id: str):
    if _cached_depth > MAX_WAITING:
        raise HTTPException(503, "Exports are busy, please try again in a few minutes",
                            headers={"Retry-After": "300"})
    return export_data.apply_async(args=[user_id], task_id=f"export-{user_id}-{today_key()}")
```

**Edge cases:** checking depth on every enqueue costs a Redis call; a cached value refreshed every few seconds (as above) is accurate enough. Shedding must be **visible**: count shed jobs as a metric, or you've built a silent failure.

### 7.7 Ordering
If tasks must run in a particular order, check that your library supports **ordered delivery**. 🔧 Most queues don't guarantee global order once you have several workers or retries (a retried job runs **after** jobs added later). Options: a single worker with concurrency 1 for that queue; SQS FIFO **message groups** (strict order per group key, such as per user); or design the handler to not care (use versions or timestamps and ignore older updates).

### 7.8 Rate limiting
When tasks call external services, **limit how fast you call them**: providers bill per call and enforce their own rate limits. 🔧 Careful with Celery's built-in `rate_limit`: it is enforced **per worker instance, not globally**, so ten workers with `rate_limit="10/s"` can still make 100 calls per second in total. For a true global limit, use a shared bucket in Redis (section 7.9). (arq has no built-in rate limiting.)

```python
@app.task(name="email.send", rate_limit="10/s")   # per worker instance, NOT across all workers
def send_email(payload: dict) -> None: ...
```

### 7.9 Adaptive rate limits against external APIs ➕

A fixed limiter is a guess about the provider's limit; the provider's `429` responses are the truth, so a worker that calls third parties should listen to them, and sometimes needs a separate limit per customer account.

#### Pausing the queue when the provider says 429
**Problem:** your limiter allows 10 per second, but the provider's real limit today is 5 (a shared account, a lower plan, their own incident). Every job hits `429`, burns one of its 5 attempts, backs off, and eventually lands in *failed* for no reason except pacing.

**Why it happens:** a 429 isn't a failure of **this job**; it's a statement about **the whole account** for the next N seconds. Treating it as a per-job error makes every job pay separately for a shared condition.

**Mechanism:** on 429, **pause every worker** for the time the provider asks for, and hand the job back without counting an attempt. Celery has no built-in queue-wide pause, so the pause lives in a **shared Redis key** with a TTL: every task checks it before calling the provider. A paused or rate-limited job is **re-published** with a `countdown` and the current delivery ends with `Ignore`; unlike `self.retry()`, that doesn't use up one of the task's retries. (During the pause, workers still take jobs off the queue and put them back. For a hard stop, `app.control.cancel_consumer("email")` tells every worker to stop consuming the queue until `add_consumer` resumes it.)

```python title="email_tasks.py (adaptive)"
from celery.exceptions import Ignore

PAUSE_KEY = "pause:provider:resend"


def _requeue(task, payload: dict, rate_limited: int, delay_s: float):
    # a fresh message instead of self.retry(): this delay doesn't count against max_retries
    task.apply_async(args=[payload], kwargs={"rate_limited": rate_limited + 1}, countdown=delay_s)
    raise Ignore()


@app.task(name="email.send", bind=True, autoretry_for=(TransientError,), max_retries=4,
          retry_backoff=60, rate_limit="10/s")
def send_email(self, payload: dict, rate_limited: int = 0) -> None:
    if rate_limited > 50:
        raise PermanentError("rate-limited too many times")    # a safety cap
    if (pause_ms := broker.pttl(PAUSE_KEY)) > 0:                # another worker already got a 429
        _requeue(self, payload, rate_limited, pause_ms / 1000)

    res = provider_send(payload)
    if res.status_code == 429:
        header = res.headers.get("retry-after", "")
        retry_after = int(header) if header.isdigit() else 30
        broker.set(PAUSE_KEY, 1, ex=retry_after)                # every worker sees the pause
        _requeue(self, payload, rate_limited, retry_after)
    if res.is_error:
        raise TransientError(f"provider {res.status_code}")
```

**Edge cases:**
- **Unbounded re-queues:** because rate-limited attempts don't count, a provider that returns 429 forever keeps the job alive forever. The `rate_limited` cap above converts that into a visible failure.
- **One pause key per limit.** The pause applies to every job that checks that key. If the same queue sends through two providers with separate limits, a shared key would make a 429 from one pause both; key the pause per provider (or account), or give each its own queue.

#### Limits per customer account
**Problem:** a multi-tenant app sends through **each customer's own** API credentials (their Shopify store, their Slack workspace). Each has its own limit; one global limiter is either too slow for everyone or too fast for some.

**Why it happens:** Celery's `rate_limit` is one bucket per task type per worker, and arq has none at all, so neither knows about accounts.

**Mechanism:** keep a **token bucket per account in Redis** and check it in the handler. If the account has no tokens, put the job back with a `countdown` until the next token is due, re-publishing it and raising `Ignore` so the current delivery is acknowledged without being marked as done or failed. The bucket is a Lua script, registered once with `register_script`, so the read-refill-take sequence is atomic.

```python title="per_account_limit.py"
import time

from celery.exceptions import Ignore

# atomic token bucket: returns 0 if allowed, or ms to wait
take_token = broker.register_script("""
local tokens = tonumber(redis.call('HGET', KEYS[1], 't') or ARGV[1])
local ts = tonumber(redis.call('HGET', KEYS[1], 'ts') or ARGV[3])
local now = tonumber(ARGV[3])
tokens = math.min(tonumber(ARGV[1]), tokens + (now - ts) * tonumber(ARGV[2]) / 1000)
if tokens < 1 then return math.ceil((1 - tokens) * 1000 / tonumber(ARGV[2])) end
redis.call('HSET', KEYS[1], 't', tokens - 1, 'ts', now)
redis.call('PEXPIRE', KEYS[1], 60000)
return 0
""")


@app.task(name="shop.sync", bind=True, acks_late=True)
def sync_shop_task(self, account_id: str, payload: dict) -> None:
    wait_ms = take_token(keys=[f"bucket:{account_id}"], args=[40, 2, int(time.time() * 1000)])
    if wait_ms > 0:                                             # capacity 40, refill 2 per second
        self.apply_async(args=[account_id, payload], countdown=wait_ms / 1000)
        raise Ignore()
    sync_shop(account_id, payload)
```

**Edge cases:**
- **Hot accounts churn the queue:** a tenant with 100,000 jobs and 2 tokens per second keeps bouncing jobs between the queue and the workers, and every job re-published with a `countdown` sits in some worker's memory until it's due. Combine with the fairness approach in section 7.10 so one account's backlog doesn't occupy all the active slots.
- **Use Redis time, or tolerate skew:** `time.time()` comes from each worker's clock. Small skew only slightly changes refill; large skew breaks the bucket. Calling `redis.call('TIME')` inside the script removes the problem.

### 7.10 Priorities and fairness between tenants ➕

FIFO is fair to **jobs** but not to **people**: whoever enqueues the most work goes first, so a queue shared by urgent and bulk work, or by small and large customers, needs explicit rules.

#### Priorities inside one queue
**Problem:** a password-reset email waits behind 200,000 marketing emails added a minute earlier.

**Mechanism:** Celery passes a `priority` with each message, but its meaning depends on the broker. On **RabbitMQ**, the queue must be declared with `x-max-priority`, and a **higher** number runs first (keep the range small, such as 0–9). On the **Redis** transport, priorities are emulated by splitting each queue into several lists (four by default), and a **lower** number runs first. arq has no priorities.

```python
app.conf.broker_transport_options = {
    "visibility_timeout": 3600,
    "priority_steps": list(range(10)),          # Redis: one list per priority level, 0 = most urgent
    "queue_order_strategy": "priority",
}

send_password_reset.apply_async(args=[user_id, token], priority=0)
send_newsletter.apply_async(args=[user_id, issue_id], priority=9)
```

**Edge cases:**
- **Unset priorities are a trap, in opposite directions per broker.** A message sent without a priority counts as 0, which is the **most** urgent on the Redis transport and the **least** urgent on RabbitMQ, and it surprises people either way: if some producers set priorities and others don't, the outcome depends on the broker. Set a priority on everything in a prioritised queue (or set `task_default_priority`).
- **Starvation:** under constant high-priority load, low-priority jobs may never run. If that's unacceptable, use separate queues (next).

#### Separate queues per class of work
**Problem:** priorities still share one pool of workers. If newsletter jobs are slow (big templates, a slow provider), they occupy every active slot, and a password reset with the top priority still waits for a slot to free up.

**Mechanism:** isolate by **queue**, each with its own workers and concurrency: `email-transactional` and `email-bulk`. The bulk queue can be fully stuck without affecting the transactional one. This is the bulkhead idea from the error-handling lesson applied to jobs.

```python
app.conf.task_routes = {
    "email.send_transactional": {"queue": "email-transactional"},
    "email.send_bulk": {"queue": "email-bulk"},
}

# a separate worker process per queue, each with its own concurrency:
#   celery -A celery_app worker -Q email-transactional --concurrency 20
#   celery -A celery_app worker -Q email-bulk --concurrency 5
```

**Edge cases:** isolation costs utilisation: transactional workers sit idle at night while bulk work queues. That's usually the right trade for user-facing paths; for the rest, autoscale per queue (section 7.6).

#### Fairness between tenants
**Problem:** tenant A starts an import that enqueues 500,000 jobs. Tenant B's single job is added after them and waits hours.

**Why it happens:** FIFO order is enqueue order, and one tenant enqueued almost everything.

**Mechanism:** three options, from least to most effort:
1. **Round-robin across tenant buckets:** route each tenant (or a hash of it into, say, 8 buckets) to its own queue and have workers consume all of them; Celery's Redis transport alternates between the queues a worker consumes (`queue_order_strategy: "round_robin"`, its default). Fine for a handful of buckets, not for thousands of tenants. (BullMQ Pro sells this as "groups".)
2. **Cap active jobs per tenant** with a Redis counter: a worker that picks up a job for a tenant already at its cap puts it back with a short delay.
3. **Don't enqueue the whole backlog.** Keep a tenant's work items in a Postgres table and enqueue only a small window per tenant (say 100) at a time; each completion enqueues the next item. The queue then always contains a mix of tenants.

```python title="tenant_cap.py"
import random

from celery.exceptions import Ignore

CAP = 20


@app.task(name="imports.row", bind=True, acks_late=True)
def import_row_task(self, tenant_id: str, row: dict) -> None:
    key = f"active:tenant:{tenant_id}"
    with broker.pipeline() as p:                                # INCR + EXPIRE in one MULTI
        p.incr(key)
        p.expire(key, 600)                                      # leak guard if a worker dies
        n, _ = p.execute()
    if n > CAP:
        broker.decr(key)
        self.apply_async(args=[tenant_id, row], countdown=2 + random.random())
        raise Ignore()
    try:
        import_row(tenant_id, row)
    finally:
        broker.decr(key)
```

**Edge cases:**
- **Counters drift** if a worker is killed between `INCR` and `DECR`; the `EXPIRE` bounds the damage, and a sorted set of leases with timestamps is the more exact version.
- **Option 2 still lets one tenant fill the queue,** so other tenants' jobs sit behind many bounce-backs. For truly large tenants, option 3 (enqueue a window) scales best.

## 8. Best practices from the lesson author's experience 🎓

1. **Keep tasks small and focused.** One task, one unit of work. If a big task fails near the end, the **whole thing re-runs**, wasting CPU; a small task retries only itself. If work depends on other work, use **chained tasks**, so a failing child is retried without redoing its parent. Small tasks are easier to scale, debug and monitor, and easier for the queue to retry.
2. **Avoid long-running tasks.** A task that takes a long time is a sign it should be **split**, either into parallel pieces or into a parent-child chain. 🔧 Long tasks also collide with visibility timeouts and locks (section 5), and make deploys painful (a worker shutting down mid-job).
3. **Use proper error handling and logging.** It gives the queue a chance to retry, and gives you the information to tell an external outage from an internal bug.
4. **Monitor queue length and worker health, with alerts.** If the queue grows past a threshold, you need to scale or investigate; if workers keep dying, find out why.

🔧 Concrete alert rules: waiting jobs above N for 10 minutes (consumers can't keep up); oldest waiting job older than your SLA (e.g. emails older than 2 minutes); failed-jobs rate above normal; zero active workers.

## 9. 🔧 Going deeper: edge cases the lesson doesn't cover

### 9.1 The dual-write problem (DB commit vs enqueue)
In `signup`, two things happen: a DB insert and a queue push. They're **not atomic**:
- Insert commits, then the process crashes before `apply_async()` → **the user never gets an email**.
- You enqueue inside a DB transaction that later **rolls back** → the worker runs for a user that doesn't exist.

**Fix: the transactional outbox.** Write the job into an `outbox` table **in the same transaction** as the business data. A small relay process reads unsent rows, pushes them to the queue, and marks them sent. If the relay crashes, it just resends (and idempotent handlers absorb the duplicate).

### 9.2 Graceful shutdown
On deploy, Kubernetes or your platform sends `SIGTERM`. If the worker exits immediately, active jobs are cut off mid-way and only come back after the lock or visibility timeout expires.

```python
# Celery: SIGTERM already means "warm shutdown": stop consuming, let active tasks finish, then exit.
# Nothing to code; give the pod a grace period longer than your longest task. If the worker is
# killed anyway (SIGKILL), acks_late leaves the message unacked, so the broker redelivers it.

# arq: by default SIGTERM cancels running jobs (they're re-queued and retried later);
# job_completion_wait lets them finish first.
class WorkerSettings:
    functions = [send_email]
    job_completion_wait = 60        # seconds to wait for active jobs after SIGTERM
```

### 9.3 Dead-letter handling
After the last attempt, a job lands in a **failed** state (a log line, a `FAILURE` entry in Celery's result backend, a failed result in arq) or in a **dead-letter queue** (SQS, RabbitMQ). Treat it as an inbox: alert on it, inspect the error, fix the cause, then **retry the jobs by hand**. Never let it grow silently.

### 9.4 Poison messages, quarantine and safe replay ➕

"Retry by hand" hides three engineering questions: how a job that **crashes the worker** ever reaches the failed set, where failed jobs should live so they aren't deleted before anyone looks, and how to replay thousands of them without causing a second incident.

#### Jobs that kill the worker
**Problem:** a job with a malformed 2 GB video, or input that triggers an infinite loop, crashes or freezes the worker process. It is handed to the next worker, which also dies, then the next. One bad message takes down the whole worker fleet in turns.

**Why it happens:** the handler never **raises**, so the normal retry counter never moves. From the queue's point of view the worker simply vanished, so the message is never acked and is delivered again, which looks like an infrastructure blip and is retried.

**Mechanism:**
- **Bound redeliveries.** With `acks_late`, a job that kills its whole worker is redelivered every time. On RabbitMQ, a **quorum queue** with a delivery limit (`x-delivery-limit`) dead-letters a message after that many redeliveries; on Redis, count deliveries yourself (an `INCR` keyed on the task ID at task start) and fail the job past a small threshold. In Celery, leave `task_reject_on_worker_lost` off for risky queues: its docs warn that turning it on can cause exactly this message loop.
- **Contain the crash.** Celery's **prefork** pool already runs each task in a child process: an out-of-memory kill or a segfault takes down that child, the main worker process replaces it, and the task fails with `WorkerLostError`, an error you can see. Add a hard `time_limit` (the pool kills the child) and `--max-memory-per-child` so runaway jobs end too.
- **Bound the work.** Validate inputs (size, duration, page count) **before** heavy processing, and give the processing step its own timeout.

```python title="media_tasks.py"
@app.task(
    name="media.transcode",
    acks_late=True,
    reject_on_worker_lost=False,   # a child killed mid-job → WorkerLostError and FAILURE, not a redelivery loop
    soft_time_limit=1700,          # raises SoftTimeLimitExceeded first, so the task can clean up
    time_limit=1800,               # hard limit: the pool kills the child process
)
def transcode(video_id: str) -> None:
    probe = probe_video(video_id)                               # cheap metadata check before heavy work
    if probe.duration_s > 4 * 3600 or probe.size_bytes > 5 * 1024**3:
        raise PermanentError("input too large")
    run_ffmpeg(video_id)

# celery -A celery_app worker -Q media --pool prefork --concurrency 2 --max-memory-per-child 2000000   (KiB)
```

#### A real dead-letter queue in Celery
**Problem:** Celery has no failed set to browse. A failed task leaves a log line and, if you store results, a `FAILURE` entry that `result_expires` deletes after a day by default (arq keeps a failed result for `keep_result`, one hour by default). The evidence can disappear before anyone looked, and there's no separate place to alert on or browse.

**Mechanism:** when a job has used up its attempts, copy it into a dedicated **DLQ** that no worker consumes, with the error and enough context to act on, then alert on that queue's size. A shared task base class with an `on_failure` handler does it in one place; Celery calls `on_failure` only when it gives up (an `on_retry` handler covers the attempts that will be retried). On RabbitMQ there is also a broker-level route: raising `Reject(reason, requeue=False)` from an `acks_late` task dead-letters the message through the queue's `x-dead-letter-exchange`.

```python title="dead_letter.py"
import json
import time

from celery import Task


class DeadLetterTask(Task):
    def on_failure(self, exc, task_id, args, kwargs, einfo):
        # runs once Celery gives up: retries exhausted, or an error not in autoretry_for
        queue = (self.request.delivery_info or {}).get("routing_key", "default")
        entry = {
            "task": self.name, "task_id": task_id, "args": args, "kwargs": kwargs, "queue": queue,
            "error": {"type": type(exc).__name__, "message": str(exc)},
            "failed_at": time.time(), "retries": self.request.retries,
        }
        broker.lpush(f"dlq:{queue}", json.dumps(entry, default=str))   # no worker reads this list


# use it for every task: Celery("app", broker=..., task_cls=DeadLetterTask)
```

On **SQS**, this is built in: a **redrive policy** with `maxReceiveCount` moves a message to the DLQ after that many receives. Two details from the AWS docs: set `maxReceiveCount` high enough for normal retries, and set the DLQ's retention **longer** than the source queue's, because for standard queues a message's expiry is still based on its **original** enqueue time.

#### Replaying without a second incident
**Problem:** you fix the bug and replay 40,000 dead jobs at once. They all hit the provider in the same minute (rate limit, or worse, your own database), and some of them should never run any more: a 3-day-old verification code, a reminder for a meeting that has passed.

**Mechanism:**
1. **Fix first, then sample.** Replay ten jobs, confirm they succeed, then the rest.
2. **Replay through the normal path**, so the queue's limiter, priorities and idempotency rules apply. Neither Celery nor arq has a bulk "retry failed" command, so replay from the DLQ: re-send each job with a **new** task ID derived from the original (the old one may still exist in logs and results, or in arq's deduplication).
3. **Check expiry before acting.** Put an `expires_at` in time-sensitive payloads, and have handlers drop expired work deliberately (counted as a metric) instead of performing it late.

```python title="replay_dlq.py"
import json
import time


def replay(queue: str = "email", limit: int = 1000, per_second: float = 50) -> None:
    key = f"dlq:{queue}"
    for _ in range(limit):
        raw = broker.lindex(key, -1)                            # oldest first (entries were LPUSHed)
        if raw is None:
            break
        d = json.loads(raw)
        expires_at = (d["kwargs"] or {}).get("expires_at")
        if not (expires_at and time.time() > expires_at):      # too late to matter → just drop it
            app.send_task(d["task"], args=d["args"], kwargs=d["kwargs"], queue=d["queue"],
                          task_id=f"{d['task_id']}-replay-{int(d['failed_at'])}")
        broker.rpop(key)                                        # remove only after sending: a crash means a re-send, not a loss
        time.sleep(1 / per_second)                              # pace the replay
```

**Edge cases:**
- **Idempotency is what makes replay safe.** Some dead jobs may have partly succeeded (email sent, then the status update failed). Handlers that claim work atomically (section 7.1) turn a duplicate into a no-op.
- **Replay breaks ordering.** A replayed "set status to shipped" can land after a newer "set status to delivered". Handlers that compare versions or timestamps (section 7.7) are safe; blind overwrites aren't.

### 9.5 Payload hygiene
Put **IDs** in the payload, not whole objects. The worker loads fresh data when it runs (the user may have changed their email since), payloads stay small in Redis, and you don't copy personal data into the queue.

### 9.6 Evolving job payloads across deploys ➕

Small, ID-only payloads still have a **shape**, and that shape outlives the code that wrote it: a job enqueued today with a 7-day delay will be processed by a version of your worker that doesn't exist yet.

#### Old jobs meet new code
**Problem:** you rename `user_id` to `account_id` and deploy. Jobs already waiting, delayed or sitting in the DLQ still say `user_id`; the new handler raises `KeyError` or `TypeError` and fails (or, worse, a `.get()` returns `None` and it succeeds with wrong data).

**Why it happens:** a queue is a **persistent interface** between two deployments: the producer that ran then and the consumer that runs now. Unlike an API call, both sides are never guaranteed to be on the same version.

**Mechanism:** version every payload, validate it at the top of the handler (Pydantic models work well), and **upcast** old versions to the current shape in one place:

```python title="payloads.py"
from typing import Literal

from pydantic import BaseModel, ValidationError


class WelcomeV1(BaseModel):
    v: Literal[1] | None = None                                 # old jobs have no v field
    user_id: str


class WelcomeV2(BaseModel):
    v: Literal[2]
    account_id: str
    locale: str = "en"


def parse_welcome(data: dict) -> WelcomeV2:
    try:
        return WelcomeV2.model_validate(data)
    except ValidationError:
        pass
    try:
        v1 = WelcomeV1.model_validate(data)
    except ValidationError:
        raise PermanentError("unknown welcome payload") from None   # straight to the DLQ, not retried
    return WelcomeV2(v=2, account_id=v1.user_id)                    # upcast
```

**Edge cases:**
- **Schedules and delayed jobs are payloads too.** Beat entries defined in code change with the deploy, but a schedule stored in a database or in Redis (django-celery-beat, RedBeat) keeps its old arguments until you update it in the same deploy, or every future tick produces old-shaped jobs. Deferred jobs and pending retries already in the queue keep the shape they were written with.
- **Unknown versions should fail permanently and visibly** (as above), not crash-loop.

#### Deploy order: expand, then contract
**Problem:** in a rolling deploy, new producers can enqueue v2 jobs while **old workers** are still consuming. Old code doesn't know v2 and fails them.

**Mechanism:** split the change into steps that are each safe in both directions:
1. **Expand:** deploy workers that accept **both** v1 and v2 (the parser above). Producers still emit v1.
2. **Switch:** deploy producers that emit v2. Any worker can handle either.
3. **Contract:** once no v1 job can still exist (longest delay + all retries + DLQ retention), delete the v1 branch.

**Edge cases:**
- **Rollbacks:** if step 2 is rolled back to code that only knows v1, v2 jobs fail. Keep step 1 deployed long enough that a rollback never goes behind it.
- **Renaming a task name or queue** is the same problem: run consumers for the old and new name side by side until the old one is empty.

## 10. Recap 🎓

- Background tasks let you move **time-consuming and non-critical** work out of the request-response cycle, so APIs stay **responsive**, don't **time out** because of external dependencies, and gain **retries** for work that can fail.
- A task queue has **producers** (enqueue serialized tasks), a **broker** (holds them: RabbitMQ, Redis, SQS) and **consumers** (dequeue, run handlers in separate processes).
- **Acks** and the **visibility timeout** make sure a task is never lost when a worker dies.
- Four kinds: **one-off**, **recurring**, **chained**, **batch**.
- Design for **idempotency**, **error handling**, **monitoring**, **horizontal scaling**, **ordering** and **rate limiting**.
- Keep tasks **small**, avoid **long-running** ones, **log** well, and **alert** on queue length and worker health.
- ➕ **Broker choice:** Postgres with `SKIP LOCKED` (atomic with your data), Redis with Celery or arq (fast, needs `noeviction` and AOF), SQS (managed, 1 MiB messages, 15-minute max delay), Kafka (an event log, poor at per-job retries).
- ➕ **Schedules:** system jobs in UTC, user jobs in the user's IANA zone via an hourly UTC tick; idempotent per local period to survive DST gaps and overlaps; watermarks so missed runs catch up.
- ➕ **Latency metrics:** wait time, run time and oldest-job age beat raw depth; classify failures as transient, permanent or bug.
- ➕ **Capacity:** size slots with Little's law, autoscale on backlog rather than CPU, cap replicas, and apply backpressure at the producer.
- ➕ **Provider limits:** pause every worker on 429 with a shared Redis pause key and re-publish without using a retry; per-account token buckets in a Lua script, re-publishing with a `countdown`.
- ➕ **Fairness:** priorities (unset priorities behave differently per broker), separate queues per class, and per-tenant caps or windows.
- ➕ **Poison jobs and replay:** bound redeliveries, contain crashes in prefork children with time and memory limits, keep a real DLQ, replay paced and idempotently, drop expired work.
- ➕ **Payload evolution:** version payloads, upcast old versions, deploy expand → switch → contract.

## Interview questions

1. **What makes something a candidate for a background job?** **Its result isn't needed to answer the request, and it's slow, heavy or depends on an external service that can fail.**
2. **What goes wrong if you send the signup email synchronously?** **Either signup fails because of an email outage, or the error is swallowed and the user is told an email was sent when it wasn't; and the user waits on a third party either way.**
3. **Name the three parts of a task queue.** **Producer (creates and enqueues serialized tasks), broker (stores them), consumer or worker (dequeues and runs the handler in a separate process).**
4. **What is a visibility timeout?** **The window during which a received job is hidden from other workers; if it isn't acked in time, it becomes visible again so another worker can process it.**
5. **Why must job handlers be idempotent?** **Delivery is at-least-once: a worker can finish the work and die before acking, and retries re-run failed jobs, so the same job can run more than once.**
6. **How do you make an email job idempotent?** **Deterministic job IDs to dedupe enqueues, plus an atomic "claim" update such as setting sent_at only where it's null before sending.**
7. **Explain exponential backoff and why it needs jitter.** **The wait doubles after each failure (1, 2, 4, 8 minutes); jitter randomises it so thousands of failed jobs don't retry at the same instant and overload the recovering service.**
8. **Which errors shouldn't be retried?** **Permanent ones such as a 400 for an invalid address or a deleted user; fail them immediately and retry only timeouts, 5xx and 429.**
9. **Chained vs batch tasks?** **Chained tasks have dependencies (a child starts only after its parent succeeds, with independent children in parallel); batch tasks fan one trigger out into many independent jobs.**
10. **Why is Redis Pub/Sub a poor job queue?** **It's fire-and-forget: no persistence, no ack and no retry; messages published while no worker is listening are lost.**
11. **What is the dual-write problem with enqueuing and how is it solved?** **The DB commit and the queue push aren't atomic, so one can happen without the other; a transactional outbox writes the job in the same DB transaction and a relay publishes it.**
12. **What would you alert on for a queue?** **Waiting jobs above a threshold, age of the oldest waiting job, failure rate, and the number of live workers.**
13. ➕ **How does `FOR UPDATE SKIP LOCKED` turn a table into a queue?** **Each worker skips rows other transactions have locked, so many consumers claim different jobs without blocking; a lease column acts as the visibility timeout.**
14. ➕ **Why must a Redis used as a Celery or arq broker use `noeviction`?** **Any other policy lets Redis delete queue keys under memory pressure, silently losing jobs.**
15. ➕ **Why is Kafka a poor fit for per-job retries?** **It tracks one offset per partition, so a failing message blocks everything behind it unless you build retry topics and a dead-letter topic yourself.**
16. ➕ **How do you send a report at 9:00 local time for users in many zones, across DST?** **Store IANA zone names, run a UTC tick that selects users whose local time has reached 9:00 and who haven't been sent this period, and key the job on the local period so double fires are no-ops.**
17. ➕ **Why autoscale workers on backlog instead of CPU?** **I/O-bound workers wait rather than compute, so CPU stays low while the queue grows; waiting jobs per replica or oldest-job age reflect whether you're keeping up.**
18. ➕ **How many worker slots do you need?** **Little's law: arrival rate × average run time, divided by a target utilisation; then check the database pool and provider limits.**
19. ➕ **How should a worker react to a provider's 429?** **Pause every worker for Retry-After (a shared pause key that each task checks, and a re-publish with a countdown that doesn't consume a retry) instead of failing each job separately.**
20. ➕ **One tenant enqueues 500,000 jobs. How do you keep other tenants fast?** **Round-robin across per-tenant queue buckets, a per-tenant active-job cap, or enqueue only a small window per tenant at a time.**
21. ➕ **A job crashes every worker that runs it. What stops it?** **A delivery limit (RabbitMQ's x-delivery-limit or your own counter) so it reaches the DLQ, a separate child process per task (Celery prefork, with reject_on_worker_lost off) so the crash is contained, and input limits checked before heavy work.**
22. ➕ **How do you change a job's payload shape safely?** **Version the payload, accept old and new in the worker first, switch producers second, and remove the old branch only after no old job can remain.**
