**First principles** here means: break a backend down into its most basic, **universal components** (routing, middleware, validation, data access, auth, logging, error handling...) that exist in **every** backend regardless of language. Once you know those components, a new codebase or a new language becomes "the same parts, different syntax".

## 1. The problem: three situations where engineers get stuck 🎓

1. **A frontend developer is asked to fix a backend bug.** The backend may be in an unfamiliar language. Even if it isn't, the real question is *where do you even start* without getting lost in the code?
2. **You must build an API from scratch.** How do you form a mental map of the codebase, follow its standards and avoid breaking things?
3. **You're a TypeScript or Go backend engineer suddenly asked to work in Rust or Python.** How do you get productive without spending hours reading the docs of every library (FastAPI, Pydantic, Axum, SQLAlchemy, Diesel...)?

**Why these are hard:** if your knowledge is stored as "how framework X does it", none of it transfers. If it's stored as "what problem this component solves", all of it transfers, and only the syntax is new.

---

## 2. Benefit 1: seeing the big picture 🎓

- **Problem:** a large, unfamiliar codebase is overwhelming, and its structure or over-engineering hides where the real logic is.
- **Mechanism:** you mentally **split the system into known parts** (routing layer, core logic, database connections, over-engineered extras) and work on each **in isolation**. Filtering out the noise lets you fix bugs with confidence.
- **Why seniors seem to "just know":** senior engineers and CTOs glance at a codebase and quickly guess where a bug is. The brain is a strong **pattern matcher**, and years of exposure trained it subconsciously.
- **The lesson's point:** you don't have to wait years. Practise it **deliberately from day one** and you can get good at it in roughly **6 months to a year**.

### 🔧 Going deeper: a checklist for reading an unknown backend

Work through it in request order, the same order a request travels:

| Step | Question | Where to look (typical) |
|---|---|---|
| 1 | How does the process start and what does it listen on? | `main.ts`, `server.go`, `Dockerfile`, env config |
| 2 | Where are routes declared? | router files, controllers, decorators |
| 3 | What runs before every handler? | middleware, guards, interceptors |
| 4 | How is input validated? | DTOs, schemas, pipes |
| 5 | Where is the business logic? | services, use cases |
| 6 | How does it talk to the DB? | repositories, ORM models, migrations |
| 7 | How are errors turned into responses? | global error handler or exception filter |

To find a bug, start from the **route** that misbehaves and follow it down this list.

### Finding the code from the symptom ➕

The checklist tells you **how** a codebase is laid out. In an unfamiliar codebase you often don't know **which** route misbehaves yet; you have a symptom (an error message, a wrong number, "it broke last week"). These three techniques get from the symptom to the line, in any language.

#### Search for the evidence, not the concept ➕

- **Problem:** searching for "payment" in a large codebase returns hundreds of files. You need a string that occurs in exactly one place.
- **Mechanism:** errors and responses contain **literal strings** that were written in the source: the error message, the error code, a log message, the URL path. Search for those, and for the route path with its parameters replaced.
- **Implementation:**

```bash
rg -n "Insufficient balance"                     # the exact message the user saw
rg -n "INSUFFICIENT_FUNDS"                        # the error code from the JSON body
rg -n "'/orders/:id/refund'|\"/orders/{id}/refund\"|orders/<int:id>/refund"   # the route, in several framework syntaxes
rg -n --type ts "class .*Refund" -g '!**/*.spec.ts'                           # then the handler, without tests
```

- **Edge cases:** messages are sometimes built dynamically or translated (`t('errors.balance')`), so search for a distinctive **fragment** or the translation key. If a string appears nowhere, it may come from a dependency or a proxy (an Nginx error page, a gateway's JSON), which is itself a useful finding.

#### Follow one request ID through the logs ➕

- **Problem:** the bug happens in production only, and reading code can't tell you which branch the request actually took.
- **Mechanism:** if the system assigns a **request ID** (or trace ID) per request and logs it on every line, all the log lines of one failing request can be pulled together, across services, in order. That's the request's real path through the layers of the checklist.
- **Implementation:** get the ID from the failing response (many APIs return it in a header or the error body), then filter on it:

```bash
curl -si https://api.example.com/orders/42/refund -X POST | grep -i x-request-id
# x-request-id: 7f3c9a...
jq -c 'select(.requestId == "7f3c9a...") | {time, level, msg, route, err}' app.log        # JSON logs
# or in a log platform:  requestId:"7f3c9a..."  (sorted by time)
```

- **Edge cases:** if the codebase has **no** request ID, adding one is often the most valuable first change you can make as a newcomer (a middleware that generates it, logs it, and returns it in a response header). Request context with `AsyncLocalStorage` makes it available everywhere; see the roadmap's request-context section ([Roadmap](/docs/backend-first-principles/01-roadmap)).

#### Find when it broke: git pickaxe, blame and bisect ➕

- **Problem:** "it worked last month". The code is large, but the **change** that broke it is small, if you can find it.
- **Mechanism:** let version control search history for you:
  - **`git log -S`** (the "pickaxe") lists commits that added or removed a given string;
  - **`git blame`** shows who last changed each line, and in which commit (read that commit's message and linked ticket for the **why**);
  - **`git bisect`** binary-searches the history: given a good and a bad commit, it checks out the midpoint until it finds the first bad one, in about log2(N) steps (about 10 tests for 1,000 commits).
- **Implementation:**

```bash
git log -S "balance >= amount" --oneline -- src/      # when did this check appear or disappear?
git blame -L 40,60 src/payments/refund.service.ts     # who changed these lines, in which commit

git bisect start
git bisect bad HEAD
git bisect good v1.42.0
git bisect run npm test -- refund.spec.ts             # automatic: the test's exit code marks good or bad
git bisect reset
```

- **Edge cases:** bisect needs a **reliable, automated** check; a flaky test sends it down the wrong half. Bugs caused by **data or configuration** changes (a new feature flag, a migrated row) don't show up in code history at all, so check deploy and config logs for the same time window.

## 3. Benefit 2: faster onboarding 🎓

- **Mechanism:** if you understand how HTTP works, how databases interact with APIs and how requests flow through middleware, you can find your way around **any** language or framework.
- Once you know the core concepts behind authentication, routing, middleware and database access, **syntax becomes secondary**. You focus on the logic, so you get familiar with a codebase much faster than someone reading it syntax-first.

---

## 4. Benefit 3: "10x faster" in new projects 🎓

- When you start from scratch, first-principles knowledge lets you build **MVPs with production-quality code** quickly, because you understand what the system *needs* instead of copying boilerplate from tutorials.
- You already know how to structure routes, set up database connections, and add caching, error handling and logging **without constantly checking the docs**.

## 5. Benefit 4: less syntax fatigue 🎓

### Problem
After learning a new language's syntax, many people don't know **what to learn next**, or how to apply that syntax to real backend problems. That leads to frustration and burnout.

### The lesson's example: Node.js developer moving to Rust
- The usual approach is to look for a **4–5 hour end-to-end Rust backend project** that also follows production standards. Rust is relatively new and has far fewer project-based resources than Node, so you get stuck: you can write basic programs and handle data structures, but can't cross the threshold to a production project.
- **The first-principles approach:**
  1. You already understand the backend's layers as concepts from Node: routing, middleware, database access, logging, error handling, async code, validation, the repository pattern, handlers, authN and authZ.
  2. Start a Rust project with the **community-recommended layout**.
  3. Target **one component at a time**. For validation, for example, look up how Rust does validation (a library or a standard pattern). You already know what good validation looks like, so you combine the two and get a **production-quality validation module**.
  4. **Repeat** for every module (auth, the REST logic...).
- The lesson's estimate: in **2–3 days** you have a fully fledged, production-quality Rust codebase.

### 🔧 Going deeper: the same component in three languages

A "get user by id" route. The **concept is identical**: match method + path, extract and validate the path parameter, call the data layer, map "not found" to 404.

```ts title="NestJS (TypeScript)"
@Controller('users')
export class UsersController {
  constructor(private readonly users: UsersService) {}

  @Get(':id')
  async findOne(@Param('id', ParseIntPipe) id: number) {   // validation + transformation
    const user = await this.users.findById(id);
    if (!user) throw new NotFoundException();               // error → 404
    return user;
  }
}
```

```go title="Go 1.22+ (net/http)"
mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.Atoi(r.PathValue("id")) // validation + transformation
	if err != nil {
		http.Error(w, "invalid id", http.StatusBadRequest)
		return
	}
	user, err := repo.FindByID(r.Context(), id)
	if errors.Is(err, ErrNotFound) {
		http.Error(w, "not found", http.StatusNotFound) // error → 404
		return
	}
	json.NewEncoder(w).Encode(user)
})
```

```rust title="Rust (Axum 0.8)"
async fn find_one(State(repo): State<Repo>, Path(id): Path<i64>) -> Result<Json<User>, StatusCode> {
    // Path<i64> rejects non-numeric ids with a 400 automatically
    repo.find_by_id(id).await.map(Json).ok_or(StatusCode::NOT_FOUND)
}

let app = Router::new().route("/users/{id}", get(find_one)).with_state(repo);
```

## 6. Benefit 5: choosing the right tool for the job 🎓

- **Problem:** engineers attach themselves to labels ("I'm a Node.js developer", "I'm a Ruby developer"). When a module has very **high concurrency** or **very low latency** requirements, they stay with their usual language and lack the confidence to pick the best tool.
- **Mechanism:** if you understand the core problems backends solve (data persistence, request handling, security, scaling), you choose tools by **the problem**, not your current stack.
- The lesson's examples:

| Need | Tool |
|---|---|
| Caching | Redis |
| Relational data | Postgres |
| Unstructured data | MongoDB |
| Real-time event streaming | Kafka |

### The hidden cost of every new tool ➕

The table maps each need to the best-known specialised tool. The other half of choosing the right tool is knowing what each **additional** system costs, because a backend with Postgres, Redis, MongoDB and Kafka has four systems to run, secure and keep consistent, not one.

#### Every datastore is an operational system ➕

- **Problem:** adding Kafka "for events" feels like adding a library. It isn't: it's a distributed system that must be deployed, upgraded, monitored, backed up, secured and understood at 3 a.m. by whoever is on call.
- **Why (first principles):** the cost of a system isn't the code that calls it, it's the **failure modes** it brings. Each new datastore adds its own ways to lose data, run out of disk, fall behind, or become unreachable, and your service is now down when **any** of them is down.
- **Mechanism:** before adding a system, write down what it will cost, next to what it buys:

| Question | Why it matters |
|---|---|
| Who runs it: managed service or self-hosted? | self-hosted means upgrades, failover and backups are your job |
| How is it backed up and restored, and has a restore been tested? | an untested backup is a hope |
| What happens to the app when it's unavailable? | a cache can be skipped; a queue may block writes |
| What consistency does it give relative to the main database? | see the next subsection |
| Does the team know how to debug it? | the real cost appears during incidents |
| What does Postgres (or what we already run) give us for this today? | often "enough, for now" |

- **Edge cases:** managed services remove the operations work but not the **consistency** and **availability** questions. And "we might need it at scale" is a weak reason when the scale is hypothetical; migrating later, with real numbers, is usually cheaper than running an unneeded system for years.

#### Two stores mean two versions of the truth ➕

- **Problem:** the app writes an order to Postgres and then publishes "order created" to Kafka (or updates Elasticsearch, or a cache). If the process crashes between the two, one system has the order and the other never will.
- **Why:** there's no transaction spanning two independent systems. Any "write A, then write B" can stop half-way, and retrying can apply B twice.
- **Mechanism:** make **one** system the source of truth and derive the others from it reliably: the **transactional outbox** (write the event into a Postgres table in the same transaction, relay it afterwards) or change-data capture from the database's log. Consumers must be **idempotent**, because "reliably" means at-least-once. The outbox is implemented in [Task queues and background jobs](/docs/backend-first-principles/14-task-queues-background-jobs).
- **Edge cases:** caches have the same problem in a milder form (a stale entry after a failed delete), which is why TTLs remain a safety net even with explicit invalidation ([Caching](/docs/backend-first-principles/13-caching)).

#### Start with Postgres, graduate on evidence ➕

- **Problem:** teams adopt a specialised tool for a need their existing database already covers well at their current scale, and pay the costs above for no benefit.
- **Mechanism:** modern Postgres covers a surprising share of the table at small and medium scale, **inside the same transactions** as the rest of your data:

| Need | Postgres feature | Graduate when |
|---|---|---|
| unstructured / flexible documents | `jsonb` columns with GIN indexes | documents dominate and need horizontal scale |
| job queue | `SELECT ... FOR UPDATE SKIP LOCKED` (see [Task queues](/docs/backend-first-principles/14-task-queues-background-jobs)) | very high job throughput, complex routing |
| simple notifications between processes | `LISTEN` / `NOTIFY` | you need durable, replayable streams (that's Kafka's real job) |
| search | `tsvector` full-text search, `pg_trgm` (see [Full-text search](/docs/backend-first-principles/15-full-text-search-elasticsearch)) | relevance tuning, facets, typo tolerance at scale |
| caching | materialised views, a well-indexed query | hot reads exceed what the DB should serve (then Redis) |

- **Implementation:** for example, flexible product attributes without a second database:

```sql
CREATE TABLE products (id bigint PRIMARY KEY, name text NOT NULL, attrs jsonb NOT NULL DEFAULT '{}');
CREATE INDEX products_attrs_gin ON products USING gin (attrs jsonb_path_ops);

-- "red shirts in size M": served by the GIN index, joinable with orders in the same query and transaction
SELECT id, name FROM products WHERE attrs @> '{"color": "red", "size": "M"}';
```

- **Edge cases:** "graduate on evidence" means measured limits (query latency, write throughput, operational pain), not fashion. When you do add a specialised system, keep Postgres as the source of truth where possible, so the new system can be rebuilt from it.

## 7. Benefit 6: more employable 🎓

- Applying backend knowledge **across languages and frameworks** makes you versatile.
- Employers want engineers who think critically and independently, can **join any team** and contribute quickly. Mastering the principles makes you that engineer, not one tied to a specific stack.
- Again, you don't need years: **deliberately practise** the concepts that stay the same in every backend (routing, databases, authentication) to build an internal compass for unfamiliar territory.
- The aim is to solve problems **with confidence and efficiency**, and over time develop an instinct for approaching any backend codebase.

---

## 8. What "principles" means here 🎓

- **Not a list of rules.** Principles are the **foundational components** that the rest of the codebase revolves around, at any size, small or large.
- Together they form a **generic map of the backend territory** that helps you find your way. The rest of the series explores that map, one component at a time.

### Recap 🎓
Learning from first principles lifts you from a **framework-specific developer** to a **software engineer** who understands the problems backends solve. That lets you move between languages, frameworks and architectures easily, whether you're a frontend developer expanding into backend or a backend engineer switching languages.

➕ Two practical complements: get from a symptom to the code with literal-string search, request IDs and git history (pickaxe, blame, bisect); and count the operational and consistency cost of every extra datastore before adding it, starting from what Postgres already does.

## Interview questions

1. **You join a team with a backend in a language you don't know. How do you find a bug fast?** **Start from the failing route and follow the request path: route → middleware → validation → service → data layer → error handler. Those layers exist in every backend, so you only need to learn the syntax for each.**
2. **How would you build your first production service in a new language?** **Use the community layout, then implement one component at a time (routing, validation, data access, auth, logging, errors), combining the pattern you already know with that language's library for it.**
3. **How do you decide between Redis, Postgres, MongoDB and Kafka?** **By the problem: Redis for fast caching, Postgres for relational data with integrity, MongoDB for unstructured documents, Kafka for durable real-time event streams.**
4. ➕ **A user reports an error message. How do you find the code in a codebase you've never seen?** **Search for the literal message, error code or route string; follow the failing request's ID through the logs; if it's a regression, use `git log -S`, `git blame` and `git bisect run` to find the change.**
5. ➕ **What do you weigh before adding Kafka or MongoDB next to Postgres?** **Operations (who runs, backs up and restores it), availability (what happens when it's down), consistency with the main DB (dual writes need an outbox and idempotent consumers), team knowledge, and whether Postgres already covers the need at current scale.**
6. ➕ **Why is "write to Postgres, then publish to Kafka" unsafe, and what fixes it?** **A crash between the two leaves them inconsistent and a retry may publish twice. Write the event to an outbox table in the same transaction and relay it, with idempotent consumers.**
