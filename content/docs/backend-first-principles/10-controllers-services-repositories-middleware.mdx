Earlier lessons followed a request **outside** the server: HTTP, routing, serialization, validation. This lesson follows it **inside** the server, from the moment the operating system hands the bytes to your process until a response goes back. The lesson covers three topics together because they only make sense as one picture: **the three layers** (handler, service, repository), **middleware** (the functions at the boundaries between those layers), and **request context** (the per-request state that crosses those boundaries).

## 1. The request lifecycle inside the server 🎓

### Where the request enters
- Your server process **listens** on a port (3000, 4000, whatever you configured).
- When a TCP connection arrives on that port, the **operating system forwards** it to your process. That moment is the **entry point** of the request.
- From the entry point until the response is written, everything that happens is the **in-server request lifecycle**.

### Routing picks a handler
- The first meaningful step is **routing**: the router matches the method and path (`/users`, `/users/123`, dynamic segments and so on, covered in the routing lesson) and maps the request to a **handler**.
- A handler is just a **function you registered in advance** for that route.

## 2. Why split the work into three layers? 🎓

You **could** do everything in one handler function. Nothing in HTTP or in any framework forces the split. It's a **design pattern**, chosen so that the code base:
- **scales** as the number of endpoints grows,
- is **easier to maintain** and to add features to,
- is **easier to debug**, because each kind of problem has one obvious place to live.

The responsibility line the lesson draws:

| Layer | Owns | Must not know about |
|---|---|---|
| **Handler / controller** | Input and output formats: reading the request, binding, validation, transformation, choosing the status code, writing the response | SQL, business rules |
| **Service** | The actual processing: business logic, orchestration, emails, notifications, external API calls | HTTP: status codes, request objects, headers |
| **Repository** | Building and running database queries, returning the results | Business rules, HTTP |

### 🔧 Going deeper: the first-principles reason
Each layer has **one reason to change**:
- The API contract changes (a new field name, a new status code) → only the controller changes.
- A business rule changes (books need approval before publishing) → only the service changes.
- The database changes (a new index, raw SQL replacing an ORM call) → only the repository changes.

It also makes the service **testable without HTTP**: you call it like any function and give it a fake repository. Section 6 shows this.

## 3. The handler / controller 🎓

### What the handler receives
In every common server stack (the lesson's author has used Go, Node.js and Python), a handler receives **at least two things**, supplied by the runtime or framework, not by you:
- a **request object**: read the method, path params, query params, headers, body;
- a **response object**: set the status, headers and body.

In Express that's `(req, res)`; in Go's `net/http` it's `(w http.ResponseWriter, r *http.Request)`. In FastAPI you rarely touch either directly: you declare typed parameters (path, query, body models, a `Request`, a `Response`) and the framework extracts them for you, and whatever you return becomes the response body.

The router already decided **which API** this is, so the handler knows what it's supposed to do. Its first job is to get the data out.

### Step 1: extract and bind the data
**Problem:** the body arrives as **serialized JSON text**, because JSON is the common format that crosses the frontend/backend boundary over the network. Your language can't work with text; it needs its **native data structure**.

**Mechanism: deserialization, often called binding.**
- **GET:** the inputs are mostly **query params**.
- **POST, PUT, PATCH** (and sometimes DELETE): the inputs are mostly in the **request body**.
- **Go:** you explicitly decode the JSON into a **struct**. **Rust:** into a struct. **Node.js:** a body-parsing middleware upstream of routing (`express.json()`) turns it into a JavaScript object.
- **Python:** with plain `json.loads` you get a `dict`. With **FastAPI**, you usually don't write this step at all: you annotate a handler parameter with a **Pydantic model**, and the framework reads the body, parses the JSON and builds the model instance before your function runs. Binding and validation happen in the same step.

**If binding fails** (malformed JSON, wrong shape), the handler responds **400 Bad Request** and **stops**. The request goes no further.

### Step 2: validate, then transform
The lesson's advice (from the validation lesson): **validate everything that comes from outside**: path params, query params, body. Be as specific as possible: required fields present, formats correct, nothing malicious.

**Transformation** runs after validation. It reshapes valid data so downstream code is convenient and predictable. The lesson's example:
- `GET /books` accepts an optional `sort` query param with values `name` or `date`.
- **Design rule: make query params optional wherever you can** (the next lesson, on API design, expands on this).
- The client sends plain `/books`. Validation passes (the param is optional), so no 400.
- Transformation **sets a default**: `sort = date` (or `name`, depending on requirements).

**Why bother:** without the default, the service would need a branch: "if sort was given, do X, else do Y". Setting defaults at the edge means every downstream layer gets **one shape of data** and follows **one path**. That's more readable and less error-prone.

### Step 3: call the service
The controller calls the service with:
- the **validated, transformed data**, and
- whatever else the service needs, such as **authentication info** (user ID, permissions), which typically comes from request context (section 13).

### Step 4: choose the response
When the service returns (or throws), the controller decides the **status code** and **body**:
- success: **200** (OK), **201** (Created), **204** (No Content: the RESTful convention for a successful DELETE, with an empty body);
- client mistake: **4xx**; server failure: **5xx**;
- an appropriate error message on failure, or the success data (for `GET /books`, the array of books with 200).

So the controller really **controls the data flow** in both directions: client → server and server → client.

### 🔧 Going deeper: a controller in FastAPI + Pydantic

```python title="books/router.py"
from typing import Annotated, Literal

from fastapi import APIRouter, Depends, Query, Response, status
from pydantic import BaseModel, Field, StringConstraints

from .deps import get_books_service, get_current_user  # composition root, section 7.2
from .schemas import BookResponse
from .service import BooksService

router = APIRouter(prefix="/books")


# Step 2: validation + transformation in one model
class ListBooksQuery(BaseModel):
    sort: Literal["name", "date"] = "date"          # optional, defaulted
    limit: int = Field(20, ge=1, le=100)            # "20" from the URL is coerced to int


class CreateBookBody(BaseModel):
    title: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=200)]
    description: Annotated[str, StringConstraints(max_length=5000)] | None = None


BooksDep = Annotated[BooksService, Depends(get_books_service)]


@router.get("", response_model=list[BookResponse])
async def list_books(q: Annotated[ListBooksQuery, Query()], books: BooksDep):
    # Step 1 + 2 already happened: FastAPI bound and validated the query string into q
    return await books.list_books(sort=q.sort, limit=q.limit)  # Step 3; Step 4: 200 + JSON


@router.post("", status_code=status.HTTP_201_CREATED, response_model=BookResponse)
async def create_book(
    body: CreateBookBody,                            # body parsed and validated by FastAPI
    response: Response,
    books: BooksDep,
    user=Depends(get_current_user),                  # from request context, never from the body
):
    book = await books.create_book(user.id, body)
    response.headers["Location"] = f"/books/{book.id}"
    return book
```

FastAPI rejects a body or query string that fails validation **before** your function runs. By default it answers **422 Unprocessable Content**; if your API contract says 400 (as the lesson does), register one handler that reshapes every validation failure:

```python title="main.py (validation errors as 400)"
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(RequestValidationError)
async def validation_failed(request: Request, exc: RequestValidationError) -> JSONResponse:
    return JSONResponse(status_code=400, content={"code": "VALIDATION_FAILED", "issues": exc.errors()})
```

🔧 The same binding step in Go, where it's explicit (labelled, since the lesson mentions Go):

```go title="handler.go"
type CreateBookBody struct {
    Title       string `json:"title"`
    Description string `json:"description"`
}

func (h *Handler) CreateBook(w http.ResponseWriter, r *http.Request) {
    var body CreateBookBody
    dec := json.NewDecoder(http.MaxBytesReader(w, r.Body, 1<<20)) // cap the body at 1 MiB
    dec.DisallowUnknownFields()
    if err := dec.Decode(&body); err != nil {
        http.Error(w, "invalid JSON body", http.StatusBadRequest)   // bind failed: 400 and stop
        return
    }
    // validate, call service, write response...
}
```

🔧 **Edge cases at the binding step**
- **Body size:** cap it (`MaxBytesReader` in Go; in Python, a limit at the reverse proxy such as nginx's `client_max_body_size`, or a small ASGI middleware that counts bytes and answers 413). FastAPI itself has no default body limit, so otherwise one client can make you buffer gigabytes.
- **Wrong `Content-Type`:** FastAPI only parses a Pydantic body parameter as JSON when the request says `application/json`; for anything else the body isn't decoded into the model and validation (correctly) fails.
- **Query params are strings.** `?limit=20` arrives as `"20"`. Pydantic's default (lax) mode coerces it to the `int` the model declares, and rejects `?limit=abc`.

## 4. The service layer 🎓

### Rule: no HTTP in the service
- The service is **just a function**: data in, processing, data out.
- **The test the lesson gives:** looking at a service method, you **shouldn't be able to tell that it's used by an API**. No status codes, no request objects, no "is this valid JSON?".
- Status codes, validation and formats are the **handler's** job. That's where the line is drawn.

### What the service does
- **Business logic:** all the actual processing for the API happens here.
- **Not every service touches the database.** Example: a "send email" service receives an email address, runs the sending logic and returns something like `{ success: true }` to the handler, without calling any repository.
- **Orchestration:** one service method can call **several repository methods**, merge their results, pick the fields each result needs, call external APIs, send notifications and emails, then return the combined result.

### 🔧 Going deeper: how a service reports failure without HTTP
If the service can't return status codes, how does the controller know whether to send 404 or 409? **Domain errors.** The service throws errors that describe *what* went wrong in business terms. A single place (the global error handler, section 11) maps them to HTTP.

```python title="books/service.py"
from typing import Literal


class DomainError(Exception):
    kind = "DOMAIN_ERROR"


class NotFoundError(DomainError):
    kind = "NOT_FOUND"


class ConflictError(DomainError):
    kind = "CONFLICT"


class BooksService:
    def __init__(self, books: BooksRepository, authors: AuthorsRepository, mailer: Mailer) -> None:
        self.books = books
        self.authors = authors
        self.mailer = mailer

    async def list_books(self, *, sort: Literal["name", "date"], limit: int) -> list[Book]:
        return await self.books.find_all(sort=sort, limit=limit)  # simple pass-through is fine

    async def create_book(self, user_id: str, data: NewBookInput) -> Book:
        author = await self.authors.find_by_user_id(user_id)      # orchestration: 2 repositories
        if author is None:
            raise NotFoundError("author profile not found")
        if await self.books.exists_by_title(author.id, data.title):
            raise ConflictError("duplicate title")

        book = await self.books.insert(title=data.title, description=data.description, author_id=author.id)
        await self.mailer.send(author.email, "Your book was created")  # side effect, no HTTP anywhere
        return book
```

🔧 **Transactions belong in the service.** "Insert the book and decrement the author's quota" must succeed or fail together. Only the service knows that these two repository calls form **one business operation**, so it opens the transaction and passes the transaction's connection (or session) down to the repositories.

## 5. The repository layer 🎓

### Single responsibility: talk to the database
- It receives the data to insert, or the **filters and sorting** needed to fetch (for example the `sort` value that came from the handler, through the service).
- It **constructs the database query**, runs it and **returns the result**. Nothing else.

### Rule: one repository method returns one kind of data
- **Don't** write `get_books(id=None)` that returns one book when an ID is passed and all books otherwise.
- **Do** write `find_all(...)` and `find_by_id(id)`: separate methods, each with one predictable return type.
- **Why:** callers (the service) can rely on the shape without checking. Combining results is the **service's** job; the repository stays simple.

### 🔧 Going deeper: a repository with parameterized SQL (asyncpg)

```python title="books/repository.py"
from typing import Literal

import asyncpg

# ORDER BY columns can't be bound as $1 parameters, so map allowed values to fixed SQL
SORT_SQL: dict[str, str] = {"name": "title ASC, id ASC", "date": "created_at DESC, id DESC"}


class BooksRepository:
    def __init__(self, db: asyncpg.Pool) -> None:
        self.db = db

    async def find_all(self, *, sort: Literal["name", "date"], limit: int) -> list[asyncpg.Record]:
        return await self.db.fetch(
            "SELECT id, title, description, author_id, created_at "
            f"FROM books ORDER BY {SORT_SQL[sort]} LIMIT $1",   # only allow-listed SQL is interpolated
            limit,
        )

    async def find_by_id(self, book_id: str) -> asyncpg.Record | None:
        # "not found" is data (None); the service decides what it means
        return await self.db.fetchrow("SELECT * FROM books WHERE id = $1", book_id)

    async def exists_by_title(self, author_id: str, title: str) -> bool:
        row = await self.db.fetchval(
            "SELECT 1 FROM books WHERE author_id = $1 AND title = $2", author_id, title
        )
        return row is not None

    async def insert(self, *, title: str, description: str | None, author_id: str) -> asyncpg.Record:
        return await self.db.fetchrow(
            "INSERT INTO books (title, description, author_id) VALUES ($1, $2, $3) RETURNING *",
            title, description, author_id,
        )
```

🔧 **Edge cases**
- **SQL injection through sorting.** Values (`$1`) can be parameterized, identifiers and `ORDER BY` clauses can't. Never interpolate the client's `sort` string; map it through an allow-list like `SORT_SQL`. The validation layer already restricted it, but the repository shouldn't depend on that.
- **Stable order.** Add a unique tie-breaker (`id`) to every sort, otherwise rows with equal titles can come back in a different order on each call.
- **Return `None` for "not found"** rather than raising an HTTP error. The repository doesn't know whether a missing row is a 404, a 409 or perfectly normal.

## 7. Dependency direction: ports, adapters and the composition root ➕

The test above only works because `BooksService` receives its repositories from outside instead of creating them. This section turns that convenience into a deliberate rule about which way dependencies point.

### 7.1 The service owns the interface (dependency inversion) ➕

**Problem.** If `books/service.py` imports the concrete `BooksRepository` class, and that module imports `asyncpg`, then the business layer depends on Postgres at import time. Swapping the database, adding a cache in front of it, or testing the service means module-level patching (`unittest.mock.patch("books.service.BooksRepository")`), which is brittle and depends on import order.

**Why it happens.** At **runtime** a request flows controller → service → repository. It's tempting to make the **source-code imports** follow the same direction. But that makes the most stable code (business rules) depend on the most volatile code (SQL, drivers, vendor SDKs). Any change in a detail ripples upward into the policy.

**Mechanism.** Invert the import-time dependency. The service declares an interface (in Python, a `typing.Protocol`), in its own vocabulary, for what it **needs** ("a place to store books", "a way to notify an author"). The repository **implements** that interface. Alistair Cockburn called this **ports and adapters** (hexagonal architecture, 2005): the interface is a **port** owned by the application core, and Postgres, an HTTP API or an in-memory fake are interchangeable **adapters**. His stated goal is an application that can be driven equally by users, programs, tests or batch scripts, and developed in isolation from its databases.

<Mermaid chart={`flowchart LR
  subgraph Core["Application core (no framework imports)"]

**Implementation.**

```python title="books/core/ports.py"
# Owned by the core. Written in business terms, not SQL terms.
from dataclasses import dataclass
from datetime import datetime
from typing import Literal, Protocol


@dataclass(frozen=True, slots=True)
class Book:
    id: str
    title: str
    author_id: str
    created_at: datetime


@dataclass(frozen=True, slots=True)
class NewBook:
    title: str
    author_id: str
    description: str | None = None


class BookStore(Protocol):
    async def find_all(self, *, sort: Literal["name", "date"], limit: int) -> list[Book]: ...
    async def exists_by_title(self, author_id: str, title: str) -> bool: ...
    async def insert(self, new: NewBook) -> Book: ...


class Notifier(Protocol):
    async def book_created(self, to: str, book: Book) -> None: ...
```

```python title="books/infra/pg_book_store.py"
import asyncpg

from books.core.ports import Book, NewBook  # the arrow points INTO the core


class PgBookStore:  # satisfies BookStore structurally: no inheritance needed
    def __init__(self, db: asyncpg.Pool) -> None:
        self.db = db

    async def insert(self, new: NewBook) -> Book:
        r = await self.db.fetchrow(
            "INSERT INTO books (title, description, author_id) VALUES ($1, $2, $3) RETURNING *",
            new.title, new.description, new.author_id,
        )
        return Book(id=str(r["id"]), title=r["title"], author_id=str(r["author_id"]), created_at=r["created_at"])

    # find_all, exists_by_title ...
```

A `Protocol` is checked **structurally** by a type checker (mypy, pyright): `PgBookStore` never names `BookStore`, yet passing it where a `BookStore` is expected type-checks as long as the method signatures match. The direction can be enforced mechanically, so it doesn't erode in code review. With `import-linter` (configured in `pyproject.toml`, run as `lint-imports` in CI):

```toml title="pyproject.toml"
[tool.importlinter]
root_package = "books"
include_external_packages = true   # needed to forbid third-party packages

[[tool.importlinter.contracts]]
name = "core-stays-pure"
type = "forbidden"
source_modules = ["books.core"]
forbidden_modules = ["books.infra", "asyncpg", "sqlalchemy", "fastapi", "boto3"]
```

**Edge cases and failure modes.**
- **Interface per class is ceremony.** Introduce a port only where there is a real seam: the database, external APIs, the mailer, the clock, random IDs. A port for a pure helper function buys nothing.
- **Leaky ports.** A port method like `query(sql: str)` or one that returns an `asyncpg.Record` or a SQLAlchemy `Result` hasn't inverted anything; the core still knows it's talking to SQL.
- **Driving side too.** The controller is also an adapter. If a queue worker or CLI can't call the service without building a fake `Request`, HTTP has leaked into the core (see 7.3).

### 7.2 The composition root: build the object graph once ➕

**Problem.** If services construct their own dependencies (`self.repo = BooksRepository(create_async_engine(url))`), every service gets its own connection pool. Ten services with SQLAlchemy's default pool (5 connections plus 10 overflow) can open 150 connections per process, and Postgres has a hard `max_connections` limit. Swapping an adapter for tests also becomes impossible without module patching.

**Why it happens.** Creating an object and using it are two different responsibilities. When they're mixed, the lifecycle of shared resources (one pool, one Redis client, one HTTP agent) is decided in many places instead of one.

**Mechanism.** A **composition root**: a single place at process start (`main.py`, usually the FastAPI `lifespan`) that creates long-lived resources once and wires them into the classes that need them. Everything else receives dependencies through `__init__`. A DI container (or FastAPI's `Depends` system) is a composition root with automation.

**Implementation, by hand:**

```python title="main.py"
import os
from contextlib import asynccontextmanager

import asyncpg
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    pool = await asyncpg.create_pool(os.environ["DATABASE_URL"], max_size=20)  # ONE pool per process
    book_store = PgBookStore(pool)
    author_store = PgAuthorStore(pool)
    notifier = SesNotifier(ses_client)

    app.state.pool = pool                     # shared with the Depends providers below
    app.state.books_service = BooksService(book_store, author_store, notifier)
    yield                                     # the app serves requests here
    await pool.close()                        # shutdown: return every connection


app = FastAPI(lifespan=lifespan)
app.include_router(books_router)
# tests build the same graph with InMemoryBookStore instead of PgBookStore
```

**Implementation, with FastAPI `Depends`.** A `Protocol` is only a static type: FastAPI can't look up "a `BookStore`" by type at runtime. Instead, each dependency is a **provider function**, and the function itself is the key you override in tests:

```python title="books/deps.py"
from typing import Annotated

from fastapi import Depends, Request


def get_book_store(request: Request) -> BookStore:
    return PgBookStore(request.app.state.pool)        # swap here, or override in tests


def get_books_service(
    books: Annotated[BookStore, Depends(get_book_store)],
    authors: Annotated[AuthorStore, Depends(get_author_store)],
    notifier: Annotated[Notifier, Depends(get_notifier)],
) -> BooksService:
    return BooksService(books, authors, notifier)


# test:
#   app.dependency_overrides[get_book_store] = lambda: InMemoryBookStore()
#   client = TestClient(app)
```

**Edge cases and failure modes.**
- **Circular dependencies** (`OrdersService` needs `PaymentsService`, which needs `OrdersService`) show up as `ImportError: cannot import name ... (most likely due to a circular import)`, or as a wiring order where one of the two can't be constructed first. Deferring the import or using a lazy getter silences it, but the real fix is usually extracting the shared logic into a third service or replacing the back-call with an event.
- **Per-request cost adds up.** FastAPI calls dependency functions on **every request** (cached only within that request). Keep providers cheap: build stateless adapters around a shared pool, never create a pool or an HTTP client inside one. Keep request data in a `ContextVar` (section 13) instead of threading it through every service constructor.
- **Pool sizing is per process.** Four replicas × 2 worker processes × `max_size=20` = 160 server connections. Size pools against Postgres's `max_connections` (or put PgBouncer in front), not per service.

### 7.3 Fat controllers and anemic services ➕

**Problem.** Two opposite shapes of the same mistake:
- **Fat controller:** the handler checks business rules (`if author.books_this_month >= plan.limit:`), computes prices, and calls two repositories directly. The rule can't be reused by a queue worker, a CLI, or a GraphQL resolver, and its tests need an HTTP request.
- **Anemic service:** every service method is a one-line pass-through, while the real rules live in controllers or are buried in SQL `WHERE` clauses and triggers.

**Why it happens.** The controller is where the data first appears, so it's the path of least resistance. Over time "just one more `if`" accumulates there.

**Mechanism: a litmus test.** For every rule, ask: **"Could a background job enforce this without faking a request?"** If not, it's in the wrong layer. Move decisions into the service, and move invariants that concern a single entity into the entity itself (what Martin Fowler calls a rich domain model, as opposed to an anemic one where objects are just bags of fields).

**Implementation: before and after.**

```python title="before: rule in the controller"
@router.post("", status_code=201)
async def create_book(body: CreateBookBody, user=Depends(get_current_user)):
    author = await authors_repo.find_by_user_id(user.id)
    count = await books_repo.count_this_month(author.id)
    if author.plan == "free" and count >= 3:                       # rule lives in HTTP
        return JSONResponse(status_code=402, content={"code": "PLAN_LIMIT"})
    return await books_repo.insert(**body.model_dump(), author_id=author.id)
```

```python title="after: rule in the core"
# core/author.py: the invariant lives with the data it protects
from typing import Literal


class Author:
    def __init__(self, id: str, plan: Literal["free", "pro"], books_this_month: int) -> None:
        self.id = id
        self.plan = plan
        self._books_this_month = books_this_month

    def assert_can_publish(self) -> None:
        if self.plan == "free" and self._books_this_month >= 3:
            raise PlanLimitError()


# core/books_service.py: orchestration (a method of BooksService)
async def create_book(self, user_id: str, data: NewBookInput) -> Book:
    author = await self.authors.load_for_publishing(user_id)
    author.assert_can_publish()                    # same rule for HTTP, workers, CLI
    return await self.books.insert(NewBook(title=data.title, description=data.description, author_id=author.id))


# controller: only HTTP. The error handler maps PlanLimitError to 402 or 403.
```

**Edge cases and failure modes.**
- **A thin service is fine** when there are no rules (section 4 already says simple pass-through is fine). The goal isn't more layers, it's **one home per rule**.
- **God services.** The opposite drift: a 3,000-line `UsersService` that does everything. Split by use case (`RegisterUser`, `ChangeEmail`) when a service has many unrelated reasons to change.
- **Database constraints still matter.** Moving rules into code doesn't replace `UNIQUE` or `CHECK` constraints; two concurrent requests can both pass an in-code check. The code gives a friendly error, the constraint guarantees correctness.

## 8. Transactions that span several repositories ➕

Section 4 says the service owns the transaction and "passes the transaction client down". With repositories that each hold a `Pool`, there's no way for them to share one transaction, so this section shows the actual mechanics.

### 8.1 Why `pool.execute` can't run a transaction ➕

**Problem.** This looks correct and silently isn't:

```python title="broken.py"
await pool.execute("BEGIN")
await pool.execute("INSERT INTO books ...")                     # may run on connection #2
await pool.execute("UPDATE authors SET quota = quota - 1 ...")  # may run on connection #3
await pool.execute("COMMIT")                                    # commits nothing useful on connection #4
```

**Why it happens.** A transaction belongs to **one database session**, which means one connection. A pool hands out **whichever connection is free** for each `pool.execute` / `pool.fetch` call, and returns it right after. The asyncpg docs say each `Pool.execute()` / `Pool.fetch()` call "performs this operation using one of its connections": it acquires a connection, runs the statement and releases it. A transaction needs you to acquire the connection yourself and keep it.

**Mechanism.** Check out **one** connection, run every statement of the business operation on it, then commit or roll back and return it to the pool.

**Implementation.**

```python title="db/with_transaction.py"
from collections.abc import Awaitable, Callable

import asyncpg


async def with_transaction[T](
    pool: asyncpg.Pool, fn: Callable[[asyncpg.Connection], Awaitable[T]]
) -> T:
    async with pool.acquire() as conn:          # one connection for the whole unit of work
        async with conn.transaction():          # BEGIN; COMMIT on success, ROLLBACK on any exception
            return await fn(conn)
    # leaving `pool.acquire()` always returns the connection, even when fn raised
```

The two `async with` blocks do what a hand-written `try` / `except` / `finally` would: commit on success, roll back and re-raise on error, and release the connection in every case. SQLAlchemy's equivalent is `async with session.begin():` on an `AsyncSession` (or `async with engine.begin() as conn:` for Core).

**Edge cases.**
- **Acquiring without releasing** (calling `await pool.acquire()` without `async with` and forgetting `await pool.release(conn)`) leaks a connection per failed request. After `max_size` leaks, every request waits on `pool.acquire()` forever. Pass `timeout=` to `acquire()` (SQLAlchemy: `pool_timeout`, 30 seconds by default) so it fails fast instead of hanging.
- **A broken connection** (network drop mid-transaction) is closed rather than reused: asyncpg's pool resets a returned connection and discards it if that fails, and SQLAlchemy's `pool_pre_ping=True` checks a connection before handing it out.

### 8.2 Passing the transaction explicitly (unit of work) ➕

**Problem.** Repositories are constructed once with the pool (section 7.2), but inside a transaction they must use the transaction's connection.

**Mechanism.** Make repositories depend on the smallest thing they need: something with `fetch` / `fetchrow` / `execute` methods. `asyncpg.Pool` and `asyncpg.Connection` both satisfy it, so a small `Protocol` describes both. A **unit of work** creates transaction-bound repositories for the duration of one operation, so the service can't accidentally use a repository outside the transaction.

**Implementation.**

```python title="db/unit_of_work.py"
from collections.abc import Awaitable, Callable
from dataclasses import dataclass
from typing import Any, Protocol

import asyncpg


class Queryable(Protocol):  # satisfied by both asyncpg.Pool and asyncpg.Connection
    async def fetch(self, query: str, *args: Any) -> list[asyncpg.Record]: ...
    async def fetchrow(self, query: str, *args: Any) -> asyncpg.Record | None: ...
    async def execute(self, query: str, *args: Any) -> str: ...


class PgBookStore:
    def __init__(self, db: Queryable) -> None:
        self.db = db
    # ...


class PgAuthorStore:
    def __init__(self, db: Queryable) -> None:
        self.db = db
    # ...


@dataclass(frozen=True, slots=True)
class Repos:
    books: PgBookStore
    authors: PgAuthorStore


class UnitOfWork:
    def __init__(self, pool: asyncpg.Pool) -> None:
        self.pool = pool

    async def run[T](self, fn: Callable[[Repos], Awaitable[T]]) -> T:
        return await with_transaction(
            self.pool,
            lambda tx: fn(Repos(books=PgBookStore(tx), authors=PgAuthorStore(tx))),
        )
```

```python title="books/service.py"
async def create_book(self, user_id: str, data: NewBookInput) -> Book:
    async def work(repos: Repos) -> Book:
        author = await repos.authors.lock_by_user_id(user_id)   # SELECT ... FOR UPDATE
        if author.quota <= 0:
            raise PlanLimitError()
        await repos.authors.decrement_quota(author.id)
        return await repos.books.insert(                        # both writes commit together
            NewBook(title=data.title, description=data.description, author_id=author.id)
        )

    book = await self.uow.run(work)
    await self.notifier.book_created(user_id, book)            # side effect AFTER commit (8.5)
    return book
```

With SQLAlchemy the same idea is one `AsyncSession` per unit of work: open it with `async with session_factory() as session, session.begin():`, construct the repositories with that `session`, and every statement they issue joins the same transaction.

**Edge cases.**
- **The read-check-write race.** Without `FOR UPDATE` (or a conditional `UPDATE ... WHERE quota > 0 RETURNING`), two concurrent requests can both read `quota = 1` and both insert. The transaction alone doesn't prevent that at the default `READ COMMITTED` isolation.
- **Serialization failures.** At `SERIALIZABLE` isolation, Postgres may abort a transaction with SQLSTATE `40001`. The unit of work is the right place for a bounded retry loop, because it can re-run the whole function.

### 8.3 Ambient transactions with `contextvars` ➕

**Problem.** Threading `tx` or `repos` through every method signature is noisy when a service calls helpers that call other repositories several levels down.

**Mechanism.** Store the active transaction connection in request-scoped async context (the same `contextvars.ContextVar` that section 13 uses for request IDs). Repositories ask "is there an active transaction?" and fall back to the pool if not.

**Implementation, asyncpg:**

```python title="db/tx_context.py"
from collections.abc import Awaitable, Callable
from contextvars import ContextVar

import asyncpg

_current_tx: ContextVar[asyncpg.Connection | None] = ContextVar("current_tx", default=None)


def db(pool: asyncpg.Pool) -> asyncpg.Pool | asyncpg.Connection:
    return _current_tx.get() or pool                   # repositories call this per query


async def transactional[T](pool: asyncpg.Pool, fn: Callable[[], Awaitable[T]]) -> T:
    if _current_tx.get() is not None:
        return await fn()                              # already inside one: join it
    async with pool.acquire() as conn, conn.transaction():
        token = _current_tx.set(conn)
        try:
            return await fn()
        finally:
            _current_tx.reset(token)                   # never leak the connection past the block


# repository: await db(self.pool).execute("INSERT ...", ...)
```

**Implementation, SQLAlchemy:** the `AsyncSession` is already the unit of work, so the usual pattern is one session per request, provided by a FastAPI dependency that opens the transaction and commits (or rolls back) when the request finishes. Every repository that receives that session joins the same transaction.

```python title="db/session.py (SQLAlchemy + FastAPI)"
from collections.abc import AsyncIterator
from typing import Annotated

from fastapi import Depends
from sqlalchemy import update
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

engine = create_async_engine("postgresql+asyncpg://app@localhost/books", pool_size=20)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)


async def get_session() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session, session.begin():  # COMMIT on success, ROLLBACK on error
        yield session


# scope="function": tear down (COMMIT) before the response is sent, not after
SessionDep = Annotated[AsyncSession, Depends(get_session, scope="function")]


class BooksService:
    def __init__(self, session: AsyncSession) -> None:
        self.session = session

    async def create_book(self, author_id: str, title: str) -> Book:
        await self.session.execute(
            update(Author).where(Author.id == author_id).values(quota=Author.quota - 1)
        )
        book = Book(title=title, author_id=author_id)
        self.session.add(book)
        await self.session.flush()                         # INSERT now, inside the same transaction
        return book
```

**Edge cases and failure modes.**
- **Commit after the response.** By default a `yield` dependency is request-scoped: its code after `yield` runs *after* the response has been sent. If the `COMMIT` then fails, the client has already received a 200 for data that was never saved. `Depends(get_session, scope="function")` runs the teardown before the response, so a failed commit becomes an error response. The alternative is to commit explicitly in the service. See [Dependency injection](/docs/fastapi/dependency-injection).
- **Invisible scope.** Whether a repository call is inside a transaction is no longer visible in the code. A fire-and-forget task (`asyncio.create_task(...)`) started inside the block copies the current context, so it still sees the transaction's connection; if it finishes after `COMMIT`, it would query a connection that has already been released back to the pool, possibly in the middle of another request's transaction. Never leave un-awaited queries inside a transactional block.
- **Joining vs nesting.** The helper above silently **joins** an outer transaction. That's usually right, but it means an inner "independent" operation (for example writing an audit row that must survive a rollback) can't be expressed. Libraries call this a propagation mode; choose it explicitly.

### 8.4 Nested transactions and savepoints ➕

**Problem.** `ArchiveOrganization` runs in a transaction and calls `ArchiveProject`, which also wants "all or nothing" for its own part, and you'd like a failure in one project to be skippable without losing the whole archive.

**Why it happens.** Postgres has no nested `BEGIN`. Issuing `BEGIN` inside a transaction block only produces a warning and doesn't start anything new, and a later `ROLLBACK` throws away everything.

**Mechanism.** A **savepoint** marks a point inside the current transaction that you can roll back to without aborting the outer transaction.

**Implementation.**

```python title="db/savepoint.py"
from collections.abc import Awaitable, Callable

import asyncpg


async def with_savepoint[T](tx: asyncpg.Connection, fn: Callable[[], Awaitable[T]]) -> T:
    # Inside an open transaction, conn.transaction() issues SAVEPOINT instead of BEGIN:
    # RELEASE SAVEPOINT on success, ROLLBACK TO SAVEPOINT on error (undo only the inner part).
    async with tx.transaction():
        return await fn()
    # the exception still propagates: the caller decides to skip, or let the outer tx fail
```

asyncpg generates the savepoint name itself, so no user input ever reaches the SQL. SQLAlchemy's version is `async with session.begin_nested():`, which emits `SAVEPOINT` / `RELEASE SAVEPOINT` / `ROLLBACK TO SAVEPOINT` the same way. Catch the error **outside** the `async with` block: by then the savepoint has been rolled back and the outer transaction is usable again.

**Edge cases.**
- **After any error, the transaction is aborted.** Postgres rejects every further statement with "current transaction is aborted, commands ignored until end of transaction block" until you `ROLLBACK` or roll back to a savepoint. Catching a unique-violation in code and carrying on without a savepoint doesn't work.
- **Savepoints aren't free.** Thousands of them in one transaction (one per row in a loop) add overhead. Prefer one set-based statement over a per-row savepoint loop.

### 8.5 Keep transactions short: no network calls inside ➕

**Problem.** A transaction that awaits an email provider, a payment API or an S3 upload holds its **row locks** and its **pool connection** for the full duration of that call. A slow provider (or a timeout of 30 seconds) turns into blocked writers and an exhausted pool, and the whole API stalls.

**Why it happens.** The database can't know your process is waiting on someone else; to Postgres the session is just "idle in transaction", holding everything it locked. Postgres's docs also note that a long-open transaction prevents vacuum from removing dead rows, which causes table bloat.

**Mechanism.**
1. Do slow, non-transactional work **before** the transaction (fetch data from an API, compute things) or **after** commit (send the email).
2. When a side effect must happen **if and only if** the commit happened, write an event row in the same transaction and let a worker deliver it (the transactional **outbox**; the REST lesson's archive example implements it, and [Task queues and background jobs](/docs/backend-first-principles/14-task-queues-background-jobs) covers the worker side).
3. Put a hard ceiling on transaction time in the database itself, so a bug can't hold locks forever.

<Mermaid chart={`sequenceDiagram
  participant S as Service
  participant DB as Postgres
  participant E as Email API
  Note over S,E: Wrong way, lock held while waiting on the network
  S->>DB: BEGIN, UPDATE authors (row locked)
  S->>E: send email (2 to 30 s)
  E-->>S: ok
  S->>DB: COMMIT (lock released only now)
  Note over S,E: Right way, commit first and then side effects
  S->>DB: BEGIN, UPDATE, INSERT outbox, COMMIT
  S->>E: worker sends the email later`} />

**Implementation: database-side ceilings.**

```sql title="per-role timeouts"
-- kill sessions that sit idle inside an open transaction
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '10s';
-- cap any single statement
ALTER ROLE app_user SET statement_timeout = '5s';
-- PostgreSQL 17+: cap the whole transaction, including statements and idle time
ALTER ROLE app_user SET transaction_timeout = '15s';
```

**Edge cases.**
- **All three default to 0 (disabled)** in Postgres. Without them, one stuck request can hold a lock indefinitely.
- **Timeouts surface as errors** in your code (the session is terminated). The unit of work must treat that as a rollback and the connection as broken; the `async with` blocks above roll back and return it, and the pool discards a connection that can no longer be reset.
- **Migrations and batch jobs** may legitimately need longer limits; set them per role or per session rather than raising the global default.

## 9. Models at each boundary: DTOs, domain objects and rows ➕

Transactions decide which writes belong together; the other thing crossing layer boundaries is the data itself. Passing one object shape through all three layers causes its own class of bugs.

### 9.1 Three shapes, three reasons to change ➕

**Problem.** The repository returns `SELECT *` rows, the service passes them through, and the controller does `return dict(row)`. Months later someone adds `password_hash` or `internal_notes` to the table, and every endpoint that returns that row starts **leaking** it. Renaming a column breaks the public API. A client sending `{ "isAdmin": true }` gets it written to the database because the body was unpacked straight into an insert with `**payload` (mass assignment).

**Why it happens.** Each layer has a different contract with a different owner:

| Shape | Lives at | Owned by | Changes when |
|---|---|---|---|
| **Request / response DTO** | Controller | API consumers | The public contract changes (versioned) |
| **Domain object** | Service / core | Business rules | A rule or invariant changes |
| **Persistence row** | Repository | The database schema | A column, index or table changes |

When one type serves all three, any change on one side becomes a change on all sides.

**Mechanism.** Give each boundary its own type and **map explicitly** at the edges: the repository maps row → domain object, the controller maps request DTO → service input and domain object → response DTO. ([Serialization and deserialization](/docs/backend-first-principles/07-serialization-deserialization) covers the JSON wire format itself.)

### 9.2 Mapping functions at the edges ➕

**Implementation.**

```python title="books/mappers.py"
from dataclasses import dataclass
from datetime import UTC, datetime
from decimal import Decimal
from typing import Literal
from uuid import UUID

import asyncpg
from pydantic import BaseModel


# Row: what asyncpg returns (snake_case keys, driver types: UUID, int, datetime ...)
# e.g. id, title, author_id, price_cents, created_at, internal_notes


# Domain: what the service works with
@dataclass(frozen=True, slots=True)
class Book:
    id: UUID
    title: str
    author_id: UUID
    price_cents: int
    created_at: datetime


# Response DTO: exactly what the API promises, nothing more
class Price(BaseModel):
    amount: Decimal
    currency: Literal["USD"]


class BookResponse(BaseModel):
    id: str
    title: str
    author_id: str
    price: Price
    created_at: str


def to_book(r: asyncpg.Record) -> Book:
    return Book(
        id=r["id"],
        title=r["title"],
        author_id=r["author_id"],
        price_cents=r["price_cents"],          # bigint arrives as a Python int, exact
        created_at=r["created_at"],
    )


def to_book_response(b: Book) -> BookResponse:
    return BookResponse(
        id=str(b.id),
        title=b.title,
        author_id=str(b.author_id),
        price=Price(amount=Decimal(b.price_cents) / 100, currency="USD"),
        created_at=b.created_at.astimezone(UTC).isoformat(),  # one date format on the wire
    )
# internal_notes never appears: a NEW column is invisible until someone maps it on purpose
```

**Edge cases.**
- **Driver types differ from JSON types.** asyncpg returns `bigint` (including `count(*)`) as a Python `int`, which is arbitrary-precision, so nothing is lost on the server. `numeric` comes back as `decimal.Decimal` and `uuid` as `uuid.UUID`. The loss happens at the **JSON boundary**: JavaScript clients can't represent integers above 2^53 − 1 exactly, so send large IDs and money amounts as strings or as `Decimal`, and never convert money to `float`.
- **Dates.** `timestamptz` becomes a timezone-aware `datetime`; serialize it in one place (the mapper or the Pydantic model) so every endpoint emits UTC ISO 8601.
- **Mapping lists of thousands of rows** is cheap compared to the query, but avoid `copy.deepcopy(x)` or `json.loads(json.dumps(x))`-style round trips as a "mapper".

### 9.3 Output allow-lists, not deny-lists ➕

**Problem.** A deny-list (`user.pop("password_hash"); return user`) fails **open**: every new sensitive column is exposed until someone remembers to delete it too.

**Mechanism.** Allow-list the output: the response type is built field by field (9.2), or validated against an output schema that **strips** unknown keys.

**Implementation.**

```python title="Pydantic output model"
from pydantic import BaseModel, EmailStr  # EmailStr needs the email-validator package


class UserResponse(BaseModel):            # Pydantic ignores unknown keys by default (extra="ignore")
    id: str
    name: str
    email: EmailStr


UserResponse.model_validate(user_dict)    # password_hash, mfa_secret, ... are dropped
```

```python title="FastAPI response_model"
@router.get("/users/{user_id}", response_model=UserResponse)
async def get_user(user_id: str, users: UsersDep):
    return await users.get(user_id)  # FastAPI filters the return value through UserResponse:
                                     # only declared fields survive, whatever the object carries
```

**Edge cases.**
- **Input needs the same treatment.** Unpacking the raw body into an insert (`**await request.json()`) is mass assignment. Validate into a request model with only the allowed fields (`model_config = ConfigDict(extra="forbid")` to reject extras, or the default `"ignore"` to drop them), then build the repository input from it.
- **Nested objects.** An allow-list on the top level doesn't help if a nested `author` object is passed through raw. Map nested objects with their own mappers.
- **Parsing cost.** Running a full model validation on every item of a 1,000-row response adds measurable CPU (Pydantic v2's Rust core makes it cheap, but not free). Plain mapping functions are cheaper; use model validation in tests to check that mappers match the OpenAPI contract.

## 10. Middleware 🎓

### What middleware is
Draw the lifecycle again, but mark **boundaries** between steps: after the entry point, before routing, after routing, before the handler, after the handler. At any of those boundaries you can insert extra functions. Because they run **in the middle** of the lifecycle, between routing, handlers and the response, they're called **middlewares**.

### What a middleware receives
A middleware is a handler with **one extra capability**. It gets three things from the runtime:
1. the **request** object,
2. the **response** object,
3. **`next`**, a function that **passes execution to the next processing context**.

"Next context" rather than "next middleware", because what comes next might be another middleware, the router, or the handler.

In Python's ASGI frameworks the shape is slightly different but the idea is identical. A Starlette/FastAPI HTTP middleware receives the **request** and **`call_next`**. It doesn't get a response object up front: `response = await call_next(request)` runs the rest of the chain and **returns** the response, which the middleware can then modify (add headers) before returning it. A middleware that wants to end the request early simply returns its own `Response` without calling `call_next`.

### What a middleware can do
- **Read** values from the request.
- **Modify** the request (attach data) and the response (set headers).
- **Send a response itself and end the request right there.** The request may never reach routing or the handler. That's how an auth middleware rejects a bad token without wasting work downstream.
- **Every middleware is optional.** Some lifecycles have many; a route might have none at all.

<Mermaid chart={`flowchart LR
  In["Request in"] --> M1["CORS"]
  M1 -->|"next()"| M2["Logging"]
  M2 -->|"next()"| RT["Router"]
  RT -->|"next()"| M3["Auth"]
  M3 -->|"next()"| H["Handler"]
  M3 -->|"bad token: 401"| Out["Response out"]
  H --> Out
  H -. "throws" .-> EH["Global error handler (last)"]
  EH --> Out`} />

### Why middleware exists
**The same reason functions exist: write logic once, reuse it everywhere.**
- A busy backend gets thousands, millions, even billions of requests a day, and has **hundreds or thousands of endpoints**.
- Many operations apply to **every** request: security checks, logging, authentication, parsing, compression.
- **Alternative 1:** copy the code into every handler. Obviously bad.
- **Alternative 2:** write a helper function and **call it in every handler**. Better, but it's **still duplication** (one call per handler), and it's easy to forget one.
- **Middleware:** register the logic **once** in the lifecycle. It runs **before** the request reaches the handler, and it can **reject early** so you don't spend precious server resources on a request that was going to fail anyway.

### 🔧 Going deeper: how `next` is actually implemented
There's no magic. A framework keeps an **ordered list** of functions and an **index**. Calling `call_next()` runs the function at `index + 1`. Not calling it ends the chain. An exception raised anywhere unwinds back through the chain to the error handler wrapped around it.

```python title="tiny_chain.py"
from collections.abc import Awaitable, Callable

type Handler = Callable[[Request], Awaitable[Response]]
type Middleware = Callable[[Request, Handler], Awaitable[Response]]
type ErrorHandler = Callable[[Exception, Request], Awaitable[Response]]


async def run_chain(
    stack: list[Middleware], endpoint: Handler, on_error: ErrorHandler, request: Request
) -> Response:
    async def call_at(i: int, req: Request) -> Response:
        if i == len(stack):
            return await endpoint(req)                    # end of the middleware list: the router/handler
        return await stack[i](req, lambda r: call_at(i + 1, r))  # this is call_next

    try:
        return await call_at(0, request)
    except Exception as exc:                              # any raise, at any depth, lands here
        return await on_error(exc, request)
```

Two consequences follow directly from this implementation:
- **Order is the list order.** That's the next topic.
- **Code after `await call_next(request)`** runs on the way **back out**. That's the "onion model" (Starlette/FastAPI middleware, Django middleware, Koa, Hono), and it's how timing and response logging work.

## 11. Middleware order, and the common middlewares 🎓

### Why order matters
Execution flows **one way** through the array: each middleware hands off with `next`, until something sends the response. So **position decides what a middleware can see and prevent**. Reject early things as early as possible, and put the thing that must observe everyone else's failures **last**.

<Mermaid chart={`flowchart TD
  A["CORS<br/>reject foreign origins first"] --> B["Security headers"]
  B --> C["Request ID + logging"]
  C --> D["Rate limit"]
  D --> E["Body parsing + compression"]
  E --> F["Authentication<br/>writes user into context"]
  F --> G["Route-level checks (permissions)"]
  G --> H["Handler / service / repository"]
  H --> I["Global error handler<br/>always LAST"]`} />

The lesson's typical order: **CORS first → logging → authentication → … → global error handling last**. Spend real thought on the order for your app. The chart above is a 🔧 fuller version; where rate limiting and parsing go is a trade-off, not a rule.

### CORS 🎓
- **What it is:** browsers enforce the same-origin policy. A page on `example.com` may not read responses from other origins **unless the server's response includes headers that allow it**.
- **Server side:** the runtime gives you the request's `Origin`. If it's in your allow-list (typically your frontend's domain), set the allow headers on the response and call `next()`. If not, add nothing; the browser blocks the response.
- **Why middleware:** it must run for **every request**, and it needs **both** the request (to read `Origin`) and the response (to set headers). Code that needs to run on every request and touches req/res is the textbook case for middleware.
- **Why first:** if the origin is not allowed, you want to know as early as possible.

```python title="middleware/cors.py"
from starlette.requests import Request
from starlette.responses import Response

ALLOWED = {"https://app.example.com"}


async def cors(request: Request, call_next) -> Response:
    origin = request.headers.get("origin")
    allowed = origin is not None and origin in ALLOWED

    if request.method == "OPTIONS":                      # 🔧 preflight: answer here, never reach the handler
        response = Response(status_code=204)
        response.headers["Access-Control-Allow-Methods"] = "GET,POST,PATCH,DELETE"
        response.headers["Access-Control-Allow-Headers"] = "Content-Type, Authorization"
        response.headers["Access-Control-Max-Age"] = "600"
    else:
        response = await call_next(request)

    response.headers.append("Vary", "Origin")            # 🔧 caches must not reuse one origin's answer for another
    if allowed:
        response.headers["Access-Control-Allow-Origin"] = origin
        response.headers["Access-Control-Allow-Credentials"] = "true"
    return response

# app.middleware("http")(cors)
# In production, prefer Starlette's built-in CORSMiddleware:
# app.add_middleware(CORSMiddleware, allow_origins=[...], allow_credentials=True, ...)
```

🔧 CORS is enforced **by browsers only**. `curl` or another server ignores it completely, so CORS is not an authorization mechanism.

### Security headers 🎓
Headers like **Content-Security-Policy** should be on every response, so a middleware adds them and calls `next()`. 🔧 In Express, `helmet()` sets a sensible bundle (CSP, `X-Content-Type-Options: nosniff`, HSTS and others); in Python, the `secure` package provides the same bundle for FastAPI/Starlette, or a ten-line middleware sets the headers on `response.headers` after `call_next`.

### Authentication 🎓
- **Problem:** almost every endpoint has to extract a token (JWT, session ID, …) from a header, cookie or payload, then verify it.
- **Failure:** respond **401 Unauthorized** immediately. No `next()`, and the handler never runs.
- **Success:** extract what downstream code needs (**user ID**, **role**: user, admin, sales…, **permissions**), store it in the **request context**, and call `next()`.

```python title="middleware/auth.py"
import jwt  # PyJWT
from starlette.requests import Request
from starlette.responses import JSONResponse, Response


async def authenticate(request: Request, call_next) -> Response:
    header = request.headers.get("authorization", "")
    token = header.removeprefix("Bearer ") if header.startswith("Bearer ") else None
    if not token:
        return JSONResponse({"code": "UNAUTHENTICATED"}, status_code=401)

    try:
        payload = jwt.decode(
            token, JWT_KEY, algorithms=["HS256"], issuer="api.example.com", audience="web"
        )
    except jwt.InvalidTokenError:                       # expired, bad signature, wrong audience...
        return JSONResponse({"code": "INVALID_TOKEN"}, status_code=401)

    request.state.auth = {"user_id": str(payload["sub"]), "role": str(payload["role"])}  # into request context
    return await call_next(request)
```

🔧 In FastAPI, authentication is more often written as a **dependency** (`user = Depends(get_current_user)`) than as a middleware: it still runs before the handler and can raise `HTTPException(401)`, but it is attached per router or per route, and it appears in the OpenAPI docs.

🔧 401 means "who are you?" (missing or invalid credentials). A **403** is for "I know who you are, and you're not allowed", which is a permission check after authentication.

### Rate limiting 🎓
- **Problem:** one client sending a flood of requests in a short time.
- **Mechanism:** you choose a **threshold** and a **window**, for example "more than 30 calls from this IP in 2 seconds". Both numbers are yours to decide (30, 500…).
- **Over the limit:** respond **429 Too Many Requests**. Under it: `next()`.

🔧 Implementation: a **fixed-window counter in Redis**. Every app instance shares the same counter, which is the point: an in-memory counter only limits per instance.

```python title="middleware/rate_limit.py"
import time

from redis.asyncio import Redis
from starlette.requests import Request
from starlette.responses import JSONResponse, Response

LIMIT, WINDOW_S = 30, 2
redis = Redis.from_url("redis://localhost:6379")


async def rate_limit(request: Request, call_next) -> Response:
    window = int(time.time() // WINDOW_S)
    key = f"rl:{request.client.host}:{window}"          # one counter per IP per window
    count = await redis.incr(key)                       # atomic across all instances
    if count == 1:
        await redis.expire(key, WINDOW_S)               # the key cleans itself up
    if count > LIMIT:
        return JSONResponse(
            {"code": "RATE_LIMITED"},
            status_code=429,
            headers={"Retry-After": str(WINDOW_S)},     # RFC 6585: MAY tell the client when to retry
        )
    return await call_next(request)
```

🔧 Edge cases:
- **Behind a load balancer** every request appears to come from the proxy's IP. Run uvicorn with `--proxy-headers --forwarded-allow-ips=<proxy IP>` (only the proxies you trust) so `request.client.host` is read from `X-Forwarded-For`; trusting it from anyone lets clients spoof their IP.
- **Fixed windows allow bursts at the edges** (30 at the end of one window + 30 at the start of the next). Sliding windows or token buckets smooth that out.
- For logged-in traffic, limit **per user ID** too, since many users can share one IP (offices, mobile carriers).

### Advertising the limit to clients: `RateLimit` headers ➕

The middleware above only tells a client about the limit **after** it has been hit; well-behaved clients need to see their remaining quota before that, so they can slow down instead of failing.

#### Why a bare 429 isn't enough ➕
**Problem.** A batch client or SDK that only learns about the limit from a 429 has two bad options: retry immediately (making the overload worse, and with many clients producing a synchronized **retry storm**), or back off for an arbitrary guess. Neither knows the window or the quota.

**Why it happens.** The limit is server-side state the client can't observe. `Retry-After` (RFC 6585 / RFC 9110) only covers the moment of rejection.

**Mechanism.** Return the quota on **every** response. The IETF httpapi working group's draft *RateLimit header fields for HTTP* (draft-11 at the time of writing, still an Internet-Draft, not an RFC) defines two fields using structured-field syntax:
- `RateLimit-Policy`: the policies that apply, each with a quota `q` and window `w` in seconds, for example `"burst";q=100;w=60`;
- `RateLimit`: the current state of a policy, with remaining units `r` and seconds until reset `t`, for example `"burst";r=42;t=17`.

#### Implementation ➕

```python title="middleware/rate_limit.py (with headers)"
import math
import time

POLICY, LIMIT, WINDOW_S = "burst", 30, 2


async def rate_limit(request: Request, call_next) -> Response:
    now_s = time.time()
    window = int(now_s // WINDOW_S)
    auth = getattr(request.state, "auth", None)
    who = auth["user_id"] if auth else request.client.host
    key = f"rl:{who}:{window}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, WINDOW_S)

    remaining = max(0, LIMIT - count)
    reset_in = math.ceil((window + 1) * WINDOW_S - now_s)          # seconds until this window ends
    headers = {
        "RateLimit-Policy": f'"{POLICY}";q={LIMIT};w={WINDOW_S}',
        "RateLimit": f'"{POLICY}";r={remaining};t={reset_in}',
    }

    if count > LIMIT:
        headers["Retry-After"] = str(reset_in)                     # the standardized signal on rejection
        return JSONResponse({"code": "RATE_LIMITED"}, status_code=429, headers=headers)

    response = await call_next(request)
    response.headers.update(headers)
    return response
```

#### Edge cases and failure modes ➕
- **The draft has changed shape across versions.** Earlier drafts used three separate fields (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`), and many APIs still send the older, non-standard `X-RateLimit-*` trio. Libraries such as `express-rate-limit` (Node) or `slowapi` (Python, with its `headers_enabled` option) control which headers they emit. Document the one you choose, and keep it stable for clients.
- **Headers are hints, not promises.** The draft says a positive remaining quota doesn't guarantee the next request will be served; the server may still throttle (for example under global overload).
- **CORS.** Browser JavaScript can't read these headers cross-origin unless you list them in `Access-Control-Expose-Headers`.
- **Don't leak partition keys.** If the policy is per API key or per tenant, don't echo internal identifiers in the header.

### Logging and monitoring 🎓
For every request, record the **path**, **method**, **query params**, possibly the body, and so on, to the terminal or a log file. It's what you debug, audit and report from later.

```python title="middleware/logging.py"
import logging
import time

logger = logging.getLogger("access")


async def request_logger(request: Request, call_next) -> Response:
    start = time.perf_counter_ns()
    response = await call_next(request)               # 🔧 code after this runs on the way out, so the status is known
    ms = (time.perf_counter_ns() - start) / 1e6
    logger.info(
        "request",
        extra={
            "request_id": getattr(request.state, "request_id", None),
            "method": request.method,
            "path": request.url.path,
            "status": response.status_code,
            "ms": round(ms, 1),
        },
    )
    return response
```

🔧 Never log passwords, tokens or full bodies with personal data. Redact before writing.

### Global error handling 🎓
- **Problem:** errors can happen **anywhere**: any middleware, the handler, the service, the repository. You want **one** place that turns them into a well-formed response.
- **Mechanism:** the error handler receives the raw error, decides whether it's a **client error** (4xx) or a **server error** (5xx) (you can put a field on your error types to say which), and sends a **structured** body: a message plus a **code** (sometimes called an ID), so the frontend can show its own user-friendly text per code.
- **It must be the last middleware.** Execution only flows forward. A handler placed **before** the failing code can't see an error thrown **after** it.

🔧 In FastAPI, the global error handler is an **exception handler** registered with `@app.exception_handler(SomeError)`. Any exception raised in a handler, a dependency or the service (async or not) that matches the class is routed to it; a handler for plain `Exception` catches everything else and is turned into the outermost layer (Starlette's `ServerErrorMiddleware`), so it really does run **last**.

```python title="errors.py"
import logging

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

from books.service import DomainError

logger = logging.getLogger(__name__)
STATUS_BY_KIND = {"NOT_FOUND": 404, "CONFLICT": 409, "FORBIDDEN": 403}


def error_body(code: str, message: str, request: Request) -> dict[str, str | None]:
    return {
        "code": code,
        "message": message,
        "request_id": getattr(request.state, "request_id", None),  # the user can quote this to support
    }


def register_error_handlers(app: FastAPI) -> None:
    @app.exception_handler(DomainError)
    async def domain_error(request: Request, exc: DomainError) -> JSONResponse:
        status = STATUS_BY_KIND.get(exc.kind, 400)
        return JSONResponse(error_body(exc.kind, str(exc), request), status_code=status)

    @app.exception_handler(StarletteHTTPException)   # 404 for unknown routes, 405, explicit HTTPExceptions
    async def http_error(request: Request, exc: StarletteHTTPException) -> JSONResponse:
        return JSONResponse(error_body("HTTP_ERROR", str(exc.detail), request), status_code=exc.status_code)

    @app.exception_handler(Exception)                # everything else: a bug, a lost DB connection...
    async def unhandled(request: Request, exc: Exception) -> JSONResponse:
        logger.exception("unhandled error", extra={"request_id": getattr(request.state, "request_id", None)})
        # never leak stack traces or SQL
        return JSONResponse(error_body("INTERNAL_ERROR", "Something went wrong", request), status_code=500)
```

Order matters just as much in Python, with one trap: Starlette's `app.add_middleware()` **prepends**, so the middleware added **last** is the **outermost** one and runs first. Either add them in reverse, or pass the list in reading order to the constructor:

```python title="main.py: order is the whole point"
from fastapi import Depends, FastAPI
from fastapi.middleware.cors import CORSMiddleware
from fastapi.middleware.gzip import GZipMiddleware
from starlette.middleware import Middleware
from starlette.middleware.base import BaseHTTPMiddleware

app = FastAPI(
    middleware=[                                         # outermost first, in reading order
        Middleware(CORSMiddleware, allow_origins=["https://app.example.com"], allow_credentials=True),
        Middleware(BaseHTTPMiddleware, dispatch=security_headers),
        Middleware(BaseHTTPMiddleware, dispatch=request_context),  # request ID, section 13
        Middleware(BaseHTTPMiddleware, dispatch=request_logger),
        Middleware(BaseHTTPMiddleware, dispatch=rate_limit),
        Middleware(GZipMiddleware, minimum_size=1000),
    ],                                                   # no body-parsing middleware: FastAPI parses per route
)
app.include_router(books_router, dependencies=[Depends(get_current_user)])  # auth for /books only
register_error_handlers(app)                             # the Exception handler wraps everything: LAST
```

### Compression 🎓
For large responses (a JSON body with thousands of fields), a middleware compresses the body (gzip and similar). Browsers decompress automatically, so the payload is small **in transit** and back to normal **on the client**.

🔧 The client advertises support with `Accept-Encoding`; the server answers with `Content-Encoding: gzip`. Skip tiny bodies (the overhead isn't worth it) and already-compressed content (images, video). At scale, compression is often done by a reverse proxy or CDN instead.

### Parsing, binding and validation 🎓
Serialization and deserialization, binding, even validation and transformation **can** be delegated to middleware so handlers don't repeat them. Whether you do depends on your code base's conventions.

## 12. Where a cross-cutting concern belongs ➕

Every middleware above works at the **HTTP** level. But not every "applies in many places" concern is an HTTP concern, and putting one at the wrong level is a common design bug.

### 12.1 What a global middleware can't see ➕

**Problem.** You want "only users with `books:write` may call `POST /books`", or a stricter rate limit for `POST /login` than for `GET /books`. Written as one global middleware, it ends up as a growing `if request.url.path.startswith(...)` table that drifts from the real routes.

**Why it happens.** A global middleware registered with `app.add_middleware()` runs **before routing**, so it doesn't know which handler will run, what that route's path parameters are, or what the handler requires. It only sees the raw method and URL.

**Mechanism.** Attach route-specific concerns **to the route**, either as route-level middleware or as **metadata** read by a generic check. Then the requirement sits next to the handler it protects.

**Implementation, FastAPI dependencies:** a route-level check is just an entry in the route's `dependencies` list.

```python title="permissions.py"
from fastapi import Depends, HTTPException, Request


def require_permission(perm: str):
    async def check(request: Request) -> None:
        auth = getattr(request.state, "auth", None) or {}
        if perm not in auth.get("permissions", ()):
            raise HTTPException(status_code=403, detail="FORBIDDEN")
    return check


@router.post("/books", dependencies=[Depends(require_permission("books:write"))])
async def create_book(body: CreateBookBody): ...


@router.post("/login", dependencies=[Depends(rate_limit_strict)])
async def login(body: LoginBody): ...
```

**Implementation, metadata + one generic check:** a decorator writes metadata on the handler function; one router-wide dependency reads it for every route. After routing, Starlette stores the matched route in `request.scope["route"]`, so the check knows **which** handler will run.

```python title="permissions_guard.py"
from fastapi import APIRouter, Depends, HTTPException, Request


def requires(perm: str):
    def mark(endpoint):
        endpoint.required_permission = perm          # metadata on the handler itself
        return endpoint
    return mark


async def permission_guard(request: Request) -> None:
    endpoint = request.scope["route"].endpoint       # knows WHICH handler
    perm = getattr(endpoint, "required_permission", None)
    if perm is None:
        return
    auth = getattr(request.state, "auth", None) or {}
    if perm not in auth.get("permissions", ()):
        raise HTTPException(status_code=403, detail="FORBIDDEN")


router = APIRouter(dependencies=[Depends(permission_guard)])


@router.post("/books")
@requires("books:write")                             # applied first, so FastAPI registers the marked function
async def create_book(body: CreateBookBody): ...
```

**Edge cases.**
- **Default deny.** With metadata-based checks, a route that forgets the decorator is **open**. For sensitive apps, invert it: require every route to declare either a permission or an explicit `@public` marker, and fail at startup otherwise (loop over `app.routes` in the `lifespan` and raise if a route has neither).
- **Object-level checks don't fit here.** "Can this user edit **this** book?" needs the book's owner from the database. That's a service-level rule ([Authentication and authorization](/docs/backend-first-principles/08-authentication-authorization) covers the models); a route guard can only check coarse permissions.

### 12.2 Business-level concerns: wrap the service, not the request ➕

**Problem.** Audit logging ("user X archived organization Y"), retries around a flaky partner API, caching an expensive computation, or opening a transaction are often written as HTTP middleware or interceptors. Then the same service called from a **queue worker** or a **cron job** skips them: no audit row, no retry, no transaction.

**Why it happens.** These concerns are about the **business operation**, not the HTTP request. HTTP is only one of several ways the operation gets invoked (section 7.1's driving adapters).

**Mechanism.** Apply them around the service method itself, with a higher-order function or a method decorator, so they run whichever adapter calls the service.

**Implementation: a plain higher-order wrapper** (a function that takes a function, so it also works as a decorator):

```python title="core/audited.py"
from collections.abc import Awaitable, Callable
from datetime import UTC, datetime
from functools import wraps


def audited[**P, R](
    action: str, fn: Callable[P, Awaitable[R]], audit: AuditLog
) -> Callable[P, Awaitable[R]]:
    @wraps(fn)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        result = await fn(*args, **kwargs)
        c = current_ctx()                                           # section 13
        await audit.record(action=action, actor=(c and c.user_id) or "system", at=datetime.now(UTC))
        return result
    return wrapper


# composition root (7.2): wrap once, every caller gets it
archive = audited("organization.archive", org_service.archive, audit_log)  # bound method, no .bind needed
```

```python title="core/retry.py"
import asyncio
import random
from collections.abc import Awaitable, Callable


async def with_retry[T](fn: Callable[[], Awaitable[T]], attempts: int = 3, base_s: float = 0.1) -> T:
    for i in range(attempts):
        try:
            return await fn()
        except Exception as err:
            if i == attempts - 1 or not is_transient(err):          # only retry what can succeed later
                raise
            await asyncio.sleep(base_s * 2**i * (0.5 + random.random()))  # backoff + jitter
    raise AssertionError("unreachable")
```

**Edge cases.**
- **Retries require idempotency.** Retrying a non-idempotent call (charging a card) can double the effect. Only retry idempotent operations, or ones protected by an idempotency key (see the REST lesson; [Error handling and fault tolerance](/docs/backend-first-principles/16-error-handling-fault-tolerance) covers retry policies).
- **Retries stack.** If the client, your service and the HTTP library each retry 3 times, one failure becomes 27 calls. Retry at one layer only.
- **Order of wrappers matters** just like middleware order: `audited(with_transaction(...))` audits only committed work, while `with_transaction(audited(...))` puts the audit row inside the transaction so it rolls back with it. Pick the one that matches the requirement.

### 12.3 A placement table ➕

| Concern | Needs to know | Put it in |
|---|---|---|
| CORS, security headers, compression, body parsing | Only the raw request and response | Global middleware |
| Request ID, access logs, request deadline | The request lifecycle | Global middleware (first) |
| Authentication | The credentials on the request | Global or router-level middleware |
| Coarse permission, per-route rate limit | Which route is being called | Route-level middleware, or guard + metadata |
| Validation and transformation | The route's input schema | Route-level (pipe, validator), next to the handler |
| Object-level authorization | The resource being touched | Service |
| Transactions, audit, retries, business caching | The business operation | Wrapper or decorator around the service |
| Mapping errors to HTTP | Error type and HTTP semantics | Global error handler (last) |

### 12.4 Failure modes inside the chain ➕

**Problem.** Two bugs are specific to middleware chains and are hard to see in code review.

**1. A middleware that never produces a response.** In callback-style frameworks (Express) this is a missed branch (`if (ok) next()` with no `else`). In Python's `await call_next(request)` style the shape changes: a branch that forgets to `return` anything returns `None`, and Starlette fails with a `TypeError` (a 500, at least visible), but a middleware or dependency that **awaits something with no deadline** (a Redis call to an unreachable host, a lock nobody releases) still leaves the request hanging. Uvicorn has no per-request timeout by default, so the client waits until a load balancer or the client itself gives up with a 502 or 504. Meanwhile the socket, the task and any pool connection stay held.

**2. Responding twice.** A raw ASGI middleware sends its own 401 and then also forwards to the app (a missing `return`), or an error handler tries to send a 500 after a streaming response has already sent its headers. The second `http.response.start` fails in uvicorn with `RuntimeError: Expected ASGI message 'http.response.body', but got 'http.response.start'.`, and Starlette logs "Caught handled exception, but response already started."

**Mechanism.** Make every branch end in exactly one of `return Response(...)` or `return await call_next(request)`, and never try to replace a response that has started streaming. Add a request-level timeout middleware so a hang becomes a clean 503 instead of an open-ended wait.

```python title="middleware/request_timeout.py"
import asyncio

from starlette.requests import Request
from starlette.responses import JSONResponse, Response


def request_timeout(seconds: float):
    async def middleware(request: Request, call_next) -> Response:
        try:
            async with asyncio.timeout(seconds):         # cancels the awaited chain when the deadline passes
                return await call_next(request)
        except TimeoutError:
            return JSONResponse(
                {"code": "REQUEST_TIMEOUT", "request_id": getattr(request.state, "request_id", None)},
                status_code=503,
            )
    return middleware

# app.add_middleware(BaseHTTPMiddleware, dispatch=request_timeout(10))
```

**Edge cases.**
- **Cancellation reaches only `await` points.** Unlike Node, asyncio cancellation does propagate into the handler (a `CancelledError` is raised at its current `await`), but CPU-bound code, a sync `def` endpoint running in the threadpool, or a query already executing on the database server keeps going. Pass the deadline down too (section 13, use 3; a `statement_timeout` for the database). Combine both.
- **Streaming responses** (downloads, SSE) legitimately run for minutes; `call_next` returns as soon as the headers are ready, so this middleware only bounds the time to the first byte. Exempt those routes or use a per-route value.

## 13. Request context 🎓

### The problem
A request passes through many function boundaries: CORS, logging, routing, authentication, permission checks, the handler, the error handler. Information discovered early (who the user is) is needed later (in the handler). How do you get it there **without** making every function pass it explicitly to the next, which would **couple them tightly**?

### The mechanism
**Request context: a key-value store scoped to exactly one request.**
- Every request gets **its own** context. Thousands of concurrent requests from clients around the world each have separate ones.
- Every middleware and handler on that request's path can **read and write** it.
- When the request ends, the context goes away.
- The concept is the same in every language and framework; only the concrete implementation differs.

<Mermaid chart={`flowchart LR
  subgraph Ctx["Context for request 7f3a (lives only as long as this request)"]
    K1["requestId = 7f3a..."]
    K2["userId = u_42"]
    K3["role = admin"]
    K4["deadline / abort signal"]
  end
  RID["Request ID middleware"] -- writes --> K1
  AUTH["Auth middleware"] -- writes --> K2
  AUTH -- writes --> K3
  H["Handler"] -- reads --> K2
  LOG["Logger"] -- reads --> K1
  OUT["Outgoing HTTP call"] -- reads --> K4`} />

### Use 1: identity from authentication 🎓
- The auth middleware verifies the token (or, on a login, the email and password), finds the **user ID**, **role** (user, admin, sales, depending on your RBAC) and **permissions** (read, write…), and stores them in context.
- Downstream, a `POST /books` handler needs a `userId` for the new book row. It takes it **from context**, not from the request body.
- **Why:** if you trust a `userId` field in the payload, a malicious client can just send **someone else's** ID and act as them. The authenticated identity is the only trustworthy source.
- The same context data feeds **permission checks**: is this user allowed to insert a book? Is this user an admin?

### Use 2: request ID for tracing 🎓
- An early middleware generates a **UUID** and stores it in context.
- Every log line for this request includes it.
- Calls to other services (in a microservice architecture) send it along in a header like **`X-Request-ID`**.
- When debugging, you search the logs for that one ID and see **where the request started and every service it touched**.

### Use 3: cancellation, abort signals and deadlines 🎓
Context also carries **cancellation signals and deadlines** to downstream calls, so a slow external service can't keep your request **hanging forever**.

### 🔧 Going deeper: request context in Python

**Option A: hang it on the request object.** Starlette and FastAPI give you `request.state`, a per-request namespace (`request.state.auth`, `request.state.request_id`). Simple, but you have to pass `request` everywhere you need it, which drags HTTP into the service layer.

**Option B: `contextvars.ContextVar`** (standard library since Python 3.7). It's Python's equivalent of thread-local storage for async code: every asyncio task runs in its own copy of the context, and ASGI servers run each request in its own task. A value you `set()` inside the request is visible through `get()` in every function awaited from there, and in tasks it spawns (they copy the context at creation), without passing anything.

```python title="context.py"
import asyncio
import re
import time
import uuid
from contextvars import ContextVar
from dataclasses import dataclass

import httpx
from starlette.requests import Request
from starlette.responses import Response


@dataclass(slots=True)
class Ctx:
    request_id: str
    deadline: float                       # time.monotonic() value after which work should stop
    user_id: str | None = None
    role: str | None = None


_ctx: ContextVar[Ctx | None] = ContextVar("request_ctx", default=None)


def current_ctx() -> Ctx | None:          # usable from ANY layer, no parameters
    return _ctx.get()


SAFE_ID = re.compile(r"[\w-]{8,64}")


async def request_context(request: Request, call_next) -> Response:
    incoming = request.headers.get("x-request-id")
    request_id = incoming if incoming and SAFE_ID.fullmatch(incoming) else str(uuid.uuid4())  # reuse upstream ID if sane

    token = _ctx.set(Ctx(request_id=request_id, deadline=time.monotonic() + 10))  # + a 10 s deadline
    request.state.request_id = request_id
    try:
        response = await call_next(request)  # everything downstream sees this context
    finally:
        _ctx.reset(token)
    response.headers["X-Request-ID"] = request_id
    return response


# auth, after verifying:  c = current_ctx(); c.user_id, c.role = user_id, role


# deep inside a service or HTTP client:
async def call_billing(client: httpx.AsyncClient, path: str) -> httpx.Response:
    c = current_ctx()
    remaining = c.deadline - time.monotonic()
    if remaining <= 0:
        raise TimeoutError("request deadline already passed")
    async with asyncio.timeout(remaining):                     # stop when the request's deadline passes
        return await client.get(
            f"https://billing.internal{path}",
            headers={"X-Request-ID": c.request_id},             # propagate the trace ID
        )
```

A client disconnect also reaches the handler: in an ASGI server the request's task is cancelled (or `await request.is_disconnected()` turns true), so awaits deep in the call stack raise `CancelledError` the same way a deadline does.

🔧 **Edge cases**
- **Mutate the context object; don't replace it**, if code that runs later must see the change. A `ContextVar.set()` only affects the current context copy: one made in a child task, in a sync dependency (FastAPI runs those in a threadpool with a copied context) or in the app below a `BaseHTTPMiddleware` (which runs it in a separate task) is invisible to code outside that copy. Mutating the shared `Ctx` instance is visible to everyone holding it.
- **Don't use a module-level variable** for "the current user". An asyncio server handles many requests concurrently on one thread, so a global would leak one user's identity into another user's request. That's the bug request context exists to prevent. (`threading.local` has the same problem: all those requests share one thread.)
- **Validate an incoming request ID** before reusing it (length and characters), or a client can inject arbitrary text into your logs.
- **Pass the deadline to the database too**, where supported (asyncpg's `timeout=` argument, or `SET LOCAL statement_timeout`), so a cancelled request also stops its expensive query.

🔧 The Go version, for comparison (labelled): `context.Context` is the first argument of every function on the request path, and it carries both values and cancellation.

```go title="context.go"
func (h *Handler) GetBook(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second) // r.Context() is cancelled if the client disconnects
    defer cancel()
    userID := ctx.Value(userIDKey).(string)                        // set by the auth middleware
    book, err := h.svc.GetBook(ctx, userID, chi.URLParam(r, "id")) // ctx flows down to the DB driver
    // ...
}
```

## 14. 🔧 Going deeper: the same ideas in FastAPI

FastAPI (on top of Starlette) gives each idea from this lesson a named building block. A request passes through them in this order:

| Step | FastAPI / Starlette piece | Lesson concept |
|---|---|---|
| 1 | **Middleware** (`app.add_middleware`, outermost first) | Generic middleware: CORS, logging, request ID |
| 2 | **Router** (`APIRouter`, path operations) | Routing |
| 3 | **Dependencies** on the router or route (`Depends(get_current_user)`) | Authentication and authorization (raise `HTTPException(401 / 403)`) |
| 4 | **Parameter parsing** with Pydantic models | Binding, validation and transformation (422 by default) |
| 5 | **Path operation function** | Handler / controller |
| 6 | **Service**, injected with `Depends` or built in the composition root | Service layer |
| 7 | **`response_model`** filtering, then middleware code after `call_next` | Response mapping, on the way out |
| 8 | **Exception handlers** (`@app.exception_handler`) | Global error handler |

Repositories usually wrap a SQLAlchemy `AsyncSession` (or an asyncpg pool) and are injected into the service. For request context, use `request.state` (simple, but HTTP leaks into whatever receives the `Request`), a dependency with `yield` for per-request resources such as the DB session, or a `ContextVar` for values the service layer reads without parameters.

## 15. Recap 🎓

- **Lifecycle:** OS → entry point → routing → handler → service → repository → back to the handler → response.
- **Handler/controller:** bind (deserialize; 400 and stop if it fails) → validate and transform (defaults, so downstream has one path) → call the service with data and auth info → pick the status code and send the response.
- **Service:** the real processing and orchestration; knows nothing about HTTP; may or may not use repositories.
- **Repository:** builds and runs queries; one method returns one kind of data.
- **Middleware:** functions at the boundaries with `req`, `res` and `next` (in Python's ASGI frameworks: `request` and `call_next`, which returns the response); reusable cross-cutting logic; can end the request early; **order matters**. CORS first, global error handler last.
- **Request context:** request-scoped key-value state shared across middleware and handlers without coupling them: identity from auth (never trust a client-sent user ID), request IDs for tracing, cancellation and deadlines.
- ➕ **Dependency direction:** the core declares ports (interfaces, `Protocol`s in Python); repositories and HTTP are adapters; one composition root builds the graph. Business rules live in the service or domain objects, never in controllers.
- ➕ **Transactions across repositories:** one checked-out connection per unit of work, passed explicitly or through a `ContextVar`; savepoints for nesting; no network calls inside; database-side timeouts as a ceiling.
- ➕ **Models per boundary:** request/response DTO, domain object and row are different types with explicit mappers; allow-list outputs.
- ➕ **Cross-cutting placement:** HTTP concerns in global middleware, route-specific ones on the route, business concerns wrapped around the service. Advertise rate limits with `RateLimit` headers.

## Interview questions

1. **Why separate controllers, services and repositories when one function would work?** **It isn't required; it's a pattern. Each layer has one reason to change (API contract, business rules, data access), which makes the code easier to scale, debug and test.**
2. **What are the controller's four jobs, in order?** **Bind/deserialize the input (400 on failure), validate and transform it, call the service, then choose the status code and send the response.**
3. **How can you tell whether a service method is well designed?** **You shouldn't be able to tell it's used by an HTTP API: no status codes, request objects or headers. It reports failures with domain errors.**
4. **Why shouldn't one repository method return a single row or a list depending on an optional parameter?** **Each method should return one predictable kind of data. Combining results is the service's orchestration job.**
5. **Why is a middleware better than a helper function called in every handler?** **The helper call is still duplicated in every handler and easy to forget. Middleware is registered once, runs for every request, and can reject early before the handler spends resources.**
6. **What does `next` do?** **It passes execution to the next processing context, which may be another middleware, the router or the handler. Not calling it ends the chain. In Express, `next(err)` jumps to error handlers; in FastAPI/Starlette, `await call_next(request)` returns the response, and a raised exception travels to the exception handlers.**
7. **Why must the global error handler be registered last?** **Execution flows forward only, so it can only catch errors from code that runs before it.**
8. **Why should CORS run first?** **If the origin isn't allowed, you want to find out before doing any other work.**
9. **Which status codes do the auth and rate-limit middlewares send?** **401 for missing or invalid credentials (403 when authenticated but not permitted); 429 when the rate limit is exceeded, optionally with `Retry-After`.**
10. **What is request context, and why not use a global variable?** **A key-value store scoped to one request and shared across its middleware and handlers. A global would be shared by all concurrent requests, leaking one user's data into another's.**
11. **Why take `userId` from context instead of the request body?** **A client can put any ID in the body and act as another user. Only the authenticated identity is trustworthy.**
12. **How does a request ID help in a microservice system?** **It's generated once, stored in context, logged everywhere and forwarded in a header like `X-Request-ID`, so you can trace one request across every service.**
13. **How do you implement request context in Python?** **`request.state` for simple cases, or a `contextvars.ContextVar`, which each asyncio task (and so each request) sees in its own copy, making the value available to all code awaited from the request without passing parameters.**
14. ➕ **Why should the service define the repository interface rather than import the repository class?** **So import-time dependencies point from details (SQL, drivers) into the business core. The core stays testable with fakes and can be driven by HTTP, workers or tests alike (ports and adapters).**
15. ➕ **Why can't you run `BEGIN` / `COMMIT` through `pool.execute`?** **A transaction lives on one connection, and the pool may give each statement a different one. Acquire one connection (`async with pool.acquire()`), run every statement on it inside `conn.transaction()`, and always release it.**
16. ➕ **How do two repositories share one transaction?** **Construct them with the transaction's connection or `AsyncSession` (a unit of work), or keep the connection in a `ContextVar` and let repositories use it when present.**
17. ➕ **Why is sending an email inside a database transaction a bug?** **The transaction holds locks and a pool connection while waiting on the network, and the email can't be rolled back. Commit first, or write an outbox event in the transaction.**
18. ➕ **Why not return database rows directly from the API?** **New columns (like password hashes) leak automatically, and schema changes break the contract. Map rows to domain objects and allow-list the response DTO.**
19. ➕ **Where should audit logging or retries go, middleware or service?** **Around the service: they belong to the business operation, and middleware would skip them when a worker or cron job calls the same service.**
20. ➕ **What happens if a middleware forgets both to respond and to call `next()`?** **In Express the request hangs until a server, proxy or client timeout fires; in Starlette a missing return fails with a `TypeError` (a 500), and an await with no deadline hangs the same way. Every branch must end in exactly one of the two, and a request timeout bounds the rest.**
