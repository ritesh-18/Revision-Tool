Earlier lessons followed a request **outside** the server: HTTP, routing, serialization, validation. This lesson follows it **inside** the server, from the moment the operating system hands the bytes to your process until a response goes back. The lesson covers three topics together because they only make sense as one picture: **the three layers** (handler, service, repository), **middleware** (the functions at the boundaries between those layers), and **request context** (the per-request state that crosses those boundaries).

## 1. The request lifecycle inside the server 🎓

### Where the request enters
- Your server process **listens** on a port (3000, 4000, whatever you configured).
- When a TCP connection arrives on that port, the **operating system forwards** it to your process. That moment is the **entry point** of the request.
- From the entry point until the response is written, everything that happens is the **in-server request lifecycle**.

### Routing picks a handler
- The first meaningful step is **routing**: the router matches the method and path (`/users`, `/users/123`, dynamic segments and so on, covered in the routing lesson) and maps the request to a **handler**.
- A handler is just a **function you registered in advance** for that route.

## 2. Why split the work into three layers? 🎓

You **could** do everything in one handler function. Nothing in HTTP or in any framework forces the split. It's a **design pattern**, chosen so that the code base:
- **scales** as the number of endpoints grows,
- is **easier to maintain** and to add features to,
- is **easier to debug**, because each kind of problem has one obvious place to live.

The responsibility line the lesson draws:

| Layer | Owns | Must not know about |
|---|---|---|
| **Handler / controller** | Input and output formats: reading the request, binding, validation, transformation, choosing the status code, writing the response | SQL, business rules |
| **Service** | The actual processing: business logic, orchestration, emails, notifications, external API calls | HTTP: status codes, request objects, headers |
| **Repository** | Building and running database queries, returning the results | Business rules, HTTP |

### 🔧 Going deeper: the first-principles reason
Each layer has **one reason to change**:
- The API contract changes (a new field name, a new status code) → only the controller changes.
- A business rule changes (books need approval before publishing) → only the service changes.
- The database changes (a new index, raw SQL replacing an ORM call) → only the repository changes.

It also makes the service **testable without HTTP**: you call it like any function and give it a fake repository. Section 6 shows this.

## 3. The handler / controller 🎓

### What the handler receives
In every common server stack (the lesson's author has used Go, Node.js and Python), a handler receives **at least two things**, supplied by the runtime or framework, not by you:
- a **request object**: read the method, path params, query params, headers, body;
- a **response object**: set the status, headers and body.

In Express that's `(req, res)`; in Go's `net/http` it's `(w http.ResponseWriter, r *http.Request)`.

The router already decided **which API** this is, so the handler knows what it's supposed to do. Its first job is to get the data out.

### Step 1: extract and bind the data
**Problem:** the body arrives as **serialized JSON text**, because JSON is the common format that crosses the frontend/backend boundary over the network. Your language can't work with text; it needs its **native data structure**.

**Mechanism: deserialization, often called binding.**
- **GET:** the inputs are mostly **query params**.
- **POST, PUT, PATCH** (and sometimes DELETE): the inputs are mostly in the **request body**.
- **Go:** you explicitly decode the JSON into a **struct**. **Python:** into a dictionary or a class. **Rust:** into a struct.
- **Node.js:** you usually don't do this in the handler. A body-parsing middleware **upstream of routing** (`express.json()`, formerly `body-parser`) already turned the JSON into a JavaScript object. JavaScript has first-class JSON support (JSON was modelled on JS object syntax); most other languages need explicit work.

**If binding fails** (malformed JSON, wrong shape), the handler responds **400 Bad Request** and **stops**. The request goes no further.

### Step 2: validate, then transform
The lesson's advice (from the validation lesson): **validate everything that comes from outside**: path params, query params, body. Be as specific as possible: required fields present, formats correct, nothing malicious.

**Transformation** runs after validation. It reshapes valid data so downstream code is convenient and predictable. The lesson's example:
- `GET /books` accepts an optional `sort` query param with values `name` or `date`.
- **Design rule: make query params optional wherever you can** (the next lesson, on API design, expands on this).
- The client sends plain `/books`. Validation passes (the param is optional), so no 400.
- Transformation **sets a default**: `sort = date` (or `name`, depending on requirements).

**Why bother:** without the default, the service would need a branch: "if sort was given, do X, else do Y". Setting defaults at the edge means every downstream layer gets **one shape of data** and follows **one path**. That's more readable and less error-prone.

### Step 3: call the service
The controller calls the service with:
- the **validated, transformed data**, and
- whatever else the service needs, such as **authentication info** (user ID, permissions), which typically comes from request context (section 13).

### Step 4: choose the response
When the service returns (or throws), the controller decides the **status code** and **body**:
- success: **200** (OK), **201** (Created), **204** (No Content: the RESTful convention for a successful DELETE, with an empty body);
- client mistake: **4xx**; server failure: **5xx**;
- an appropriate error message on failure, or the success data (for `GET /books`, the array of books with 200).

So the controller really **controls the data flow** in both directions: client → server and server → client.

### 🔧 Going deeper: a controller in Express + zod

```ts title="books.controller.ts"
import { z } from 'zod';
import type { Request, Response, NextFunction } from 'express';
import { BooksService } from './books.service';

// Step 2: validation + transformation in one schema
const ListBooksQuery = z.object({
  sort: z.enum(['name', 'date']).default('date'),        // optional, defaulted
  limit: z.coerce.number().int().min(1).max(100).default(20),
});

const CreateBookBody = z.object({
  title: z.string().trim().min(1).max(200),
  description: z.string().max(5000).optional(),
});

export class BooksController {
  constructor(private readonly books: BooksService) {}

  list = async (req: Request, res: Response) => {
    const parsed = ListBooksQuery.safeParse(req.query);  // req.query is already bound by Express
    if (!parsed.success) return res.status(400).json({ code: 'VALIDATION_FAILED', issues: parsed.error.issues });

    const books = await this.books.listBooks(parsed.data); // Step 3
    return res.status(200).json(books);                    // Step 4
  };

  create = async (req: Request, res: Response) => {
    const parsed = CreateBookBody.safeParse(req.body);     // body bound by express.json()
    if (!parsed.success) return res.status(400).json({ code: 'VALIDATION_FAILED', issues: parsed.error.issues });

    const userId = res.locals.auth.userId;                 // from request context, never from the body
    const book = await this.books.createBook(userId, parsed.data);
    return res.status(201).location(`/books/${book.id}`).json(book);
  };
}
```

🔧 The same binding step in Go, where it's explicit (labelled, since the lesson mentions Go):

```go title="handler.go"
type CreateBookBody struct {
    Title       string `json:"title"`
    Description string `json:"description"`
}

func (h *Handler) CreateBook(w http.ResponseWriter, r *http.Request) {
    var body CreateBookBody
    dec := json.NewDecoder(http.MaxBytesReader(w, r.Body, 1<<20)) // cap the body at 1 MiB
    dec.DisallowUnknownFields()
    if err := dec.Decode(&body); err != nil {
        http.Error(w, "invalid JSON body", http.StatusBadRequest)   // bind failed: 400 and stop
        return
    }
    // validate, call service, write response...
}
```

🔧 **Edge cases at the binding step**
- **Body size:** cap it (`express.json({ limit: '1mb' })`, `MaxBytesReader`). Otherwise one client can make you buffer gigabytes. Express answers 413 when the limit is exceeded.
- **Wrong `Content-Type`:** `express.json()` only parses `application/json`; for anything else `req.body` stays empty, so validation (correctly) fails with 400.
- **Query params are strings.** `?limit=20` arrives as `"20"`. That's why the schema uses `z.coerce.number()`.

## 4. The service layer 🎓

### Rule: no HTTP in the service
- The service is **just a function**: data in, processing, data out.
- **The test the lesson gives:** looking at a service method, you **shouldn't be able to tell that it's used by an API**. No status codes, no request objects, no "is this valid JSON?".
- Status codes, validation and formats are the **handler's** job. That's where the line is drawn.

### What the service does
- **Business logic:** all the actual processing for the API happens here.
- **Not every service touches the database.** Example: a "send email" service receives an email address, runs the sending logic and returns something like `{ success: true }` to the handler, without calling any repository.
- **Orchestration:** one service method can call **several repository methods**, merge their results, pick the fields each result needs, call external APIs, send notifications and emails, then return the combined result.

### 🔧 Going deeper: how a service reports failure without HTTP
If the service can't return status codes, how does the controller know whether to send 404 or 409? **Domain errors.** The service throws errors that describe *what* went wrong in business terms. A single place (the global error handler, section 11) maps them to HTTP.

```ts title="books.service.ts"
export class NotFoundError extends Error { readonly kind = 'NOT_FOUND'; }
export class ConflictError extends Error { readonly kind = 'CONFLICT'; }

export class BooksService {
  constructor(
    private readonly books: BooksRepository,
    private readonly authors: AuthorsRepository,
    private readonly mailer: Mailer,
  ) {}

  listBooks(opts: { sort: 'name' | 'date'; limit: number }) {
    return this.books.findAll(opts);                     // simple pass-through is fine
  }

  async createBook(userId: string, input: { title: string; description?: string }) {
    const author = await this.authors.findByUserId(userId);         // orchestration: 2 repositories
    if (!author) throw new NotFoundError('author profile not found');
    if (await this.books.existsByTitle(author.id, input.title)) throw new ConflictError('duplicate title');

    const book = await this.books.insert({ ...input, authorId: author.id });
    await this.mailer.send(author.email, 'Your book was created');  // side effect, no HTTP anywhere
    return book;
  }
}
```

🔧 **Transactions belong in the service.** "Insert the book and decrement the author's quota" must succeed or fail together. Only the service knows that these two repository calls form **one business operation**, so it opens the transaction and passes the transaction client down to the repositories.

## 5. The repository layer 🎓

### Single responsibility: talk to the database
- It receives the data to insert, or the **filters and sorting** needed to fetch (for example the `sort` value that came from the handler, through the service).
- It **constructs the database query**, runs it and **returns the result**. Nothing else.

### Rule: one repository method returns one kind of data
- **Don't** write `getBooks(id?)` that returns one book when an ID is passed and all books otherwise.
- **Do** write `findAll(...)` and `findById(id)`: separate methods, each with one predictable return type.
- **Why:** callers (the service) can rely on the shape without checking. Combining results is the **service's** job; the repository stays simple.

### 🔧 Going deeper: a repository with parameterized SQL (node-postgres)

```ts title="books.repository.ts"
import type { Pool } from 'pg';

// ORDER BY columns can't be bound as $1 parameters, so map allowed values to fixed SQL
const SORT_SQL = { name: 'title ASC, id ASC', date: 'created_at DESC, id DESC' } as const;

export class BooksRepository {
  constructor(private readonly db: Pool) {}

  async findAll(opts: { sort: keyof typeof SORT_SQL; limit: number }) {
    const { rows } = await this.db.query(
      `SELECT id, title, description, author_id, created_at FROM books ORDER BY ${SORT_SQL[opts.sort]} LIMIT $1`,
      [opts.limit],
    );
    return rows;
  }

  async findById(id: string) {
    const { rows } = await this.db.query('SELECT * FROM books WHERE id = $1', [id]);
    return rows[0] ?? null;                               // "not found" is data; the service decides what it means
  }

  async existsByTitle(authorId: string, title: string) {
    const { rowCount } = await this.db.query('SELECT 1 FROM books WHERE author_id = $1 AND title = $2', [authorId, title]);
    return (rowCount ?? 0) > 0;
  }

  async insert(b: { title: string; description?: string; authorId: string }) {
    const { rows } = await this.db.query(
      'INSERT INTO books (title, description, author_id) VALUES ($1, $2, $3) RETURNING *',
      [b.title, b.description ?? null, b.authorId],
    );
    return rows[0];
  }
}
```

🔧 **Edge cases**
- **SQL injection through sorting.** Values (`$1`) can be parameterized, identifiers and `ORDER BY` clauses can't. Never interpolate the client's `sort` string; map it through an allow-list like `SORT_SQL`. The validation layer already restricted it, but the repository shouldn't depend on that.
- **Stable order.** Add a unique tie-breaker (`id`) to every sort, otherwise rows with equal titles can come back in a different order on each call.
- **Return `null` for "not found"** rather than throwing an HTTP error. The repository doesn't know whether a missing row is a 404, a 409 or perfectly normal.

Because the service only depends on repository **interfaces**, you can test business rules with no HTTP server and no database:

import assert from 'node:assert/strict';

test('createBook rejects a duplicate title', async () => {

  const authors = { findByUserId: async () => ({ id: 'a1', email: 'a@x.com' }) };
  const mailer = { send: async () => {} };

});

## 7. Dependency direction: ports, adapters and the composition root ➕

The test above only works because `BooksService` receives its repositories from outside instead of creating them. This section turns that convenience into a deliberate rule about which way dependencies point.

### 7.1 The service owns the interface (dependency inversion) ➕

**Problem.** If `books.service.ts` imports the concrete `BooksRepository` class, and that file imports `pg`, then the business layer depends on Postgres at compile time. Swapping the database, adding a cache in front of it, or testing the service means module-level mocking (`jest.mock('./books.repository')`), which is brittle and order-dependent.

**Why it happens.** At **runtime** a request flows controller → service → repository. It's tempting to make the **source-code imports** follow the same direction. But that makes the most stable code (business rules) depend on the most volatile code (SQL, drivers, vendor SDKs). Any change in a detail ripples upward into the policy.

**Mechanism.** Invert the compile-time dependency. The service declares an interface, in its own vocabulary, for what it **needs** ("a place to store books", "a way to notify an author"). The repository **implements** that interface. Alistair Cockburn called this **ports and adapters** (hexagonal architecture, 2005): the interface is a **port** owned by the application core, and Postgres, an HTTP API or an in-memory fake are interchangeable **adapters**. His stated goal is an application that can be driven equally by users, programs, tests or batch scripts, and developed in isolation from its databases.

<Mermaid chart={`flowchart LR
  subgraph Core["Application core (no framework imports)"]
    S["BooksService"] --> P["Port: BookStore interface"]
    S --> N["Port: Notifier interface"]
  end
  C["HTTP controller (driving adapter)"] --> S
  W["Queue worker (driving adapter)"] --> S
  PG["PgBookStore (driven adapter)"] -. implements .-> P
  F["InMemoryBookStore (test adapter)"] -. implements .-> P
  M["SesNotifier"] -. implements .-> N`} />

**Implementation.**

```ts title="books/core/ports.ts"
// Owned by the core. Written in business terms, not SQL terms.
export type Book = { id: string; title: string; authorId: string; createdAt: Date };
export type NewBook = { title: string; description?: string; authorId: string };

export interface BookStore {
  findAll(opts: { sort: 'name' | 'date'; limit: number }): Promise<Book[]>;
  existsByTitle(authorId: string, title: string): Promise<boolean>;
  insert(input: NewBook): Promise<Book>;
}

export interface Notifier {
  bookCreated(to: string, book: Book): Promise<void>;
}
```

```ts title="books/infra/pg-book-store.ts"
import type { Pool } from 'pg';
import type { BookStore, Book, NewBook } from '../core/ports';  // the arrow points INTO the core

export class PgBookStore implements BookStore {
  constructor(private readonly db: Pool) {}
  async insert(b: NewBook): Promise<Book> {
    const { rows: [r] } = await this.db.query(
      'INSERT INTO books (title, description, author_id) VALUES ($1, $2, $3) RETURNING *',
      [b.title, b.description ?? null, b.authorId],
    );
    return { id: r.id, title: r.title, authorId: r.author_id, createdAt: r.created_at };
  }
  // findAll, existsByTitle ...
}
```

The direction can be enforced mechanically, so it doesn't erode in code review. With `dependency-cruiser`:

```js title=".dependency-cruiser.cjs"
module.exports = {
  forbidden: [{
    name: 'core-stays-pure',
    severity: 'error',
    from: { path: '^src/.+/core/' },
    to: { path: '(^src/.+/infra/)|(node_modules/(pg|express|@aws-sdk))' },
  }],
};
```

**Edge cases and failure modes.**
- **Interface per class is ceremony.** Introduce a port only where there is a real seam: the database, external APIs, the mailer, the clock, random IDs. A port for a pure helper function buys nothing.
- **Leaky ports.** A port method like `query(sql: string)` or one that returns a `pg` `QueryResult` hasn't inverted anything; the core still knows it's talking to SQL.
- **Driving side too.** The controller is also an adapter. If a queue worker or CLI can't call the service without building a fake `req`, HTTP has leaked into the core (see 7.3).

### 7.2 The composition root: build the object graph once ➕

**Problem.** If services construct their own dependencies (`this.repo = new BooksRepository(new Pool())`), every service gets its own connection pool. Ten services with a default node-postgres pool of 10 connections each can open 100 connections per process, and Postgres has a hard `max_connections` limit. Swapping an adapter for tests also becomes impossible without module mocking.

**Why it happens.** Creating an object and using it are two different responsibilities. When they're mixed, the lifecycle of shared resources (one pool, one Redis client, one HTTP agent) is decided in many places instead of one.

**Mechanism.** A **composition root**: a single place at process start (`main.ts`) that creates long-lived resources once and wires them into the classes that need them. Everything else receives dependencies through the constructor. A DI container like NestJS's is a composition root with automation.

**Implementation, by hand:**

```ts title="main.ts"
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 20 }); // ONE pool per process
const bookStore = new PgBookStore(pool);
const authorStore = new PgAuthorStore(pool);
const notifier = new SesNotifier(sesClient);

const booksService = new BooksService(bookStore, authorStore, notifier);
const booksController = new BooksController(booksService);

app.get('/books', booksController.list);
// tests build the same graph with InMemoryBookStore instead of PgBookStore
```

**Implementation, in NestJS.** TypeScript interfaces don't exist at runtime, so Nest can't inject "a `BookStore`" by type. You bind an **injection token** to an implementation:

```ts title="books.module.ts"
export const BOOK_STORE = Symbol('BOOK_STORE');

@Module({
  providers: [
    BooksService,
    { provide: BOOK_STORE, useClass: PgBookStore },   // swap here, or override in tests
  ],
  controllers: [BooksController],
})
export class BooksModule {}

@Injectable()
export class BooksService {
  constructor(@Inject(BOOK_STORE) private readonly books: BookStore) {}
}

// test: Test.createTestingModule({ imports: [BooksModule] })
//         .overrideProvider(BOOK_STORE).useValue(new InMemoryBookStore()).compile()
```

**Edge cases and failure modes.**
- **Circular dependencies** (`OrdersService` needs `PaymentsService`, which needs `OrdersService`) show up as `undefined` constructor arguments or Nest's "can't resolve dependencies" error. `forwardRef()` silences it, but the real fix is usually extracting the shared logic into a third service or replacing the back-call with an event.
- **Scope bubbles up.** In NestJS, a request-scoped provider makes every provider that depends on it request-scoped too, so the whole chain is rebuilt per request. Keep request data in `AsyncLocalStorage` (section 13) instead of making core services request-scoped.
- **Pool sizing is per process.** Four replicas × `max: 20` = 80 server connections. Size pools against Postgres's `max_connections` (or put PgBouncer in front), not per service.

### 7.3 Fat controllers and anemic services ➕

**Problem.** Two opposite shapes of the same mistake:
- **Fat controller:** the handler checks business rules (`if (author.booksThisMonth >= plan.limit)`), computes prices, and calls two repositories directly. The rule can't be reused by a queue worker, a CLI, or a GraphQL resolver, and its tests need an HTTP request.
- **Anemic service:** every service method is a one-line pass-through, while the real rules live in controllers or are buried in SQL `WHERE` clauses and triggers.

**Why it happens.** The controller is where the data first appears, so it's the path of least resistance. Over time "just one more `if`" accumulates there.

**Mechanism: a litmus test.** For every rule, ask: **"Could a background job enforce this without faking a request?"** If not, it's in the wrong layer. Move decisions into the service, and move invariants that concern a single entity into the entity itself (what Martin Fowler calls a rich domain model, as opposed to an anemic one where objects are just bags of fields).

**Implementation: before and after.**

```ts title="before: rule in the controller"
create = async (req: Request, res: Response) => {
  const author = await authorsRepo.findByUserId(res.locals.auth.userId);
  const count = await booksRepo.countThisMonth(author.id);
  if (author.plan === 'free' && count >= 3) return res.status(402).json({ code: 'PLAN_LIMIT' }); // rule lives in HTTP
  res.status(201).json(await booksRepo.insert({ ...req.body, authorId: author.id }));
};
```

```ts title="after: rule in the core"
// core/author.ts: the invariant lives with the data it protects
export class Author {
  constructor(readonly id: string, readonly plan: 'free' | 'pro', private booksThisMonth: number) {}
  assertCanPublish() {
    if (this.plan === 'free' && this.booksThisMonth >= 3) throw new PlanLimitError();
  }
}

// core/books.service.ts: orchestration
async createBook(userId: string, input: NewBookInput) {
  const author = await this.authors.loadForPublishing(userId);
  author.assertCanPublish();                       // same rule for HTTP, workers, CLI
  return this.books.insert({ ...input, authorId: author.id });
}

// controller: only HTTP. The error handler maps PlanLimitError to 402 or 403.
```

**Edge cases and failure modes.**
- **A thin service is fine** when there are no rules (section 4 already says simple pass-through is fine). The goal isn't more layers, it's **one home per rule**.
- **God services.** The opposite drift: a 3,000-line `UsersService` that does everything. Split by use case (`RegisterUser`, `ChangeEmail`) when a service has many unrelated reasons to change.
- **Database constraints still matter.** Moving rules into code doesn't replace `UNIQUE` or `CHECK` constraints; two concurrent requests can both pass an in-code check. The code gives a friendly error, the constraint guarantees correctness.

## 8. Transactions that span several repositories ➕

Section 4 says the service owns the transaction and "passes the transaction client down". With repositories that each hold a `Pool`, there's no way for them to share one transaction, so this section shows the actual mechanics.

### 8.1 Why `pool.query` can't run a transaction ➕

**Problem.** This looks correct and silently isn't:

```ts title="broken.ts"
await pool.query('BEGIN');
await pool.query('INSERT INTO books ...');      // may run on connection #2
await pool.query('UPDATE authors SET quota = quota - 1 ...'); // may run on connection #3
await pool.query('COMMIT');                     // commits nothing useful on connection #4
```

**Why it happens.** A transaction belongs to **one database session**, which means one connection. A pool hands out **whichever connection is free** for each `pool.query`. The node-postgres docs are explicit: you must use the same client instance for all statements in a transaction, and must not use transactions with `pool.query`.

**Mechanism.** Check out **one** client, run every statement of the business operation on it, then commit or roll back and return it to the pool.

**Implementation.**

```ts title="db/with-transaction.ts"
import type { Pool, PoolClient } from 'pg';

export async function withTransaction<T>(pool: Pool, fn: (tx: PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect();          // one connection for the whole unit of work
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK').catch(() => {}); // the connection may already be broken
    throw err;
  } finally {
    client.release();                           // always return it, or the pool runs dry
  }
}
```

**Edge cases.**
- **Forgetting `release()`** leaks a connection per failed request. After `max` leaks, every request waits on `pool.connect()` forever. Set `connectionTimeoutMillis` on the pool so it fails fast instead of hanging.
- **A broken connection** (network drop mid-transaction) should be released with `client.release(err)` so the pool destroys it instead of reusing it.

### 8.2 Passing the transaction explicitly (unit of work) ➕

**Problem.** Repositories are constructed once with the pool (section 7.2), but inside a transaction they must use the transaction's client.

**Mechanism.** Make repositories depend on the smallest thing they need: something with a `query` method. `Pool` and `PoolClient` both satisfy it. A **unit of work** creates transaction-bound repositories for the duration of one operation, so the service can't accidentally use a repository outside the transaction.

**Implementation.**

```ts title="db/unit-of-work.ts"
import type { Pool, PoolClient, QueryResult } from 'pg';

export interface Queryable { query(text: string, params?: unknown[]): Promise<QueryResult> }

export class PgBookStore { constructor(private readonly db: Queryable) {} /* ... */ }
export class PgAuthorStore { constructor(private readonly db: Queryable) {} /* ... */ }

export type Repos = { books: PgBookStore; authors: PgAuthorStore };

export class UnitOfWork {
  constructor(private readonly pool: Pool) {}
  run<T>(fn: (repos: Repos) => Promise<T>): Promise<T> {
    return withTransaction(this.pool, (tx: PoolClient) =>
      fn({ books: new PgBookStore(tx), authors: new PgAuthorStore(tx) }));
  }
}
```

```ts title="books.service.ts"
async createBook(userId: string, input: NewBookInput) {
  const book = await this.uow.run(async ({ books, authors }) => {
    const author = await authors.lockByUserId(userId);   // SELECT ... FOR UPDATE
    if (author.quota <= 0) throw new PlanLimitError();
    await authors.decrementQuota(author.id);
    return books.insert({ ...input, authorId: author.id }); // both writes commit together
  });
  await this.notifier.bookCreated(userId, book);           // side effect AFTER commit (8.5)
  return book;
}
```

**Edge cases.**
- **The read-check-write race.** Without `FOR UPDATE` (or a conditional `UPDATE ... WHERE quota > 0 RETURNING`), two concurrent requests can both read `quota = 1` and both insert. The transaction alone doesn't prevent that at the default `READ COMMITTED` isolation.
- **Serialization failures.** At `SERIALIZABLE` isolation, Postgres may abort a transaction with SQLSTATE `40001`. The unit of work is the right place for a bounded retry loop, because it can re-run the whole function.

### 8.3 Ambient transactions with `AsyncLocalStorage` ➕

**Problem.** Threading `tx` or `repos` through every method signature is noisy when a service calls helpers that call other repositories several levels down.

**Mechanism.** Store the active transaction client in request-scoped async context (the same `AsyncLocalStorage` that section 13 uses for request IDs). Repositories ask "is there an active transaction?" and fall back to the pool if not.

**Implementation, plain Node:**

```ts title="db/tx-context.ts"
import { AsyncLocalStorage } from 'node:async_hooks';
import type { Pool, PoolClient } from 'pg';

const txStore = new AsyncLocalStorage<PoolClient>();

export const db = (pool: Pool) => txStore.getStore() ?? pool;   // repositories call this per query

export function transactional<T>(pool: Pool, fn: () => Promise<T>): Promise<T> {
  if (txStore.getStore()) return fn();                          // already inside one: join it
  return withTransaction(pool, (client) => txStore.run(client, fn));
}

// repository: await db(this.pool).query('INSERT ...', [...])
```

**Implementation, NestJS:** the `@nestjs-cls/transactional` plugin provides a `@Transactional()` method decorator and a `TransactionHost` whose `tx` property is the active transaction, with adapters for Prisma, TypeORM, Knex, Kysely, Drizzle and others.

```ts title="books.service.ts (NestJS)"
@Injectable()
export class BooksService {
  constructor(private readonly txHost: TransactionHost<TransactionalAdapterPrisma>) {}

  @Transactional()
  async createBook(authorId: string, title: string) {
    await this.txHost.tx.author.update({ where: { id: authorId }, data: { quota: { decrement: 1 } } });
    return this.txHost.tx.book.create({ data: { title, authorId } });
  }
}
```

**Edge cases and failure modes.**
- **Invisible scope.** Whether a repository call is inside a transaction is no longer visible in the code. A fire-and-forget promise started inside `run()` and finishing after `COMMIT` would query a client that has already been released back to the pool, possibly in the middle of another request's transaction. Never leave un-awaited queries inside a transactional block.
- **Joining vs nesting.** The helper above silently **joins** an outer transaction. That's usually right, but it means an inner "independent" operation (for example writing an audit row that must survive a rollback) can't be expressed. Libraries call this a propagation mode; choose it explicitly.

### 8.4 Nested transactions and savepoints ➕

**Problem.** `ArchiveOrganization` runs in a transaction and calls `ArchiveProject`, which also wants "all or nothing" for its own part, and you'd like a failure in one project to be skippable without losing the whole archive.

**Why it happens.** Postgres has no nested `BEGIN`. Issuing `BEGIN` inside a transaction block only produces a warning and doesn't start anything new, and a later `ROLLBACK` throws away everything.

**Mechanism.** A **savepoint** marks a point inside the current transaction that you can roll back to without aborting the outer transaction.

**Implementation.**

```ts title="db/savepoint.ts"
let seq = 0;
export async function withSavepoint<T>(tx: PoolClient, fn: () => Promise<T>): Promise<T> {
  const name = `sp_${++seq}`;                          // generated, never user input
  await tx.query(`SAVEPOINT ${name}`);
  try {
    const r = await fn();
    await tx.query(`RELEASE SAVEPOINT ${name}`);
    return r;
  } catch (err) {
    await tx.query(`ROLLBACK TO SAVEPOINT ${name}`);   // undo only the inner part
    throw err;                                         // caller decides: skip, or let the outer tx fail
  }
}
```

**Edge cases.**
- **After any error, the transaction is aborted.** Postgres rejects every further statement with "current transaction is aborted, commands ignored until end of transaction block" until you `ROLLBACK` or roll back to a savepoint. Catching a unique-violation in code and carrying on without a savepoint doesn't work.
- **Savepoints aren't free.** Thousands of them in one transaction (one per row in a loop) add overhead. Prefer one set-based statement over a per-row savepoint loop.

### 8.5 Keep transactions short: no network calls inside ➕

**Problem.** A transaction that awaits an email provider, a payment API or an S3 upload holds its **row locks** and its **pool connection** for the full duration of that call. A slow provider (or a timeout of 30 seconds) turns into blocked writers and an exhausted pool, and the whole API stalls.

**Why it happens.** The database can't know your process is waiting on someone else; to Postgres the session is just "idle in transaction", holding everything it locked. Postgres's docs also note that a long-open transaction prevents vacuum from removing dead rows, which causes table bloat.

**Mechanism.**
1. Do slow, non-transactional work **before** the transaction (fetch data from an API, compute things) or **after** commit (send the email).
2. When a side effect must happen **if and only if** the commit happened, write an event row in the same transaction and let a worker deliver it (the transactional **outbox**; the REST lesson's archive example implements it, and [Task queues and background jobs](/docs/backend-first-principles/14-task-queues-background-jobs) covers the worker side).
3. Put a hard ceiling on transaction time in the database itself, so a bug can't hold locks forever.

<Mermaid chart={`sequenceDiagram
  participant S as Service
  participant DB as Postgres
  participant E as Email API
  Note over S,E: Wrong way, lock held while waiting on the network
  S->>DB: BEGIN, UPDATE authors (row locked)
  S->>E: send email (2 to 30 s)
  E-->>S: ok
  S->>DB: COMMIT (lock released only now)
  Note over S,E: Right way, commit first and then side effects
  S->>DB: BEGIN, UPDATE, INSERT outbox, COMMIT
  S->>E: worker sends the email later`} />

**Implementation: database-side ceilings.**

```sql title="per-role timeouts"
-- kill sessions that sit idle inside an open transaction
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '10s';
-- cap any single statement
ALTER ROLE app_user SET statement_timeout = '5s';
-- PostgreSQL 17+: cap the whole transaction, including statements and idle time
ALTER ROLE app_user SET transaction_timeout = '15s';
```

**Edge cases.**
- **All three default to 0 (disabled)** in Postgres. Without them, one stuck request can hold a lock indefinitely.
- **Timeouts surface as errors** in your code (the session is terminated). The unit of work's `catch` must treat that as a rollback and the client as broken (`release(err)`).
- **Migrations and batch jobs** may legitimately need longer limits; set them per role or per session rather than raising the global default.

## 9. Models at each boundary: DTOs, domain objects and rows ➕

Transactions decide which writes belong together; the other thing crossing layer boundaries is the data itself. Passing one object shape through all three layers causes its own class of bugs.

### 9.1 Three shapes, three reasons to change ➕

**Problem.** The repository returns `SELECT *` rows, the service passes them through, and the controller does `res.json(row)`. Months later someone adds `password_hash` or `internal_notes` to the table, and every endpoint that returns that row starts **leaking** it. Renaming a column breaks the public API. A client sending `{ "isAdmin": true }` gets it written to the database because the body was spread straight into an insert (mass assignment).

**Why it happens.** Each layer has a different contract with a different owner:

| Shape | Lives at | Owned by | Changes when |
|---|---|---|---|
| **Request / response DTO** | Controller | API consumers | The public contract changes (versioned) |
| **Domain object** | Service / core | Business rules | A rule or invariant changes |
| **Persistence row** | Repository | The database schema | A column, index or table changes |

When one type serves all three, any change on one side becomes a change on all sides.

**Mechanism.** Give each boundary its own type and **map explicitly** at the edges: the repository maps row → domain object, the controller maps request DTO → service input and domain object → response DTO. ([Serialization and deserialization](/docs/backend-first-principles/07-serialization-deserialization) covers the JSON wire format itself.)

### 9.2 Mapping functions at the edges ➕

**Implementation.**

```ts title="books/mappers.ts"
// Row: what node-postgres returns (snake_case, driver types)
type BookRow = { id: string; title: string; author_id: string; price_cents: string; created_at: Date; internal_notes: string | null };

// Domain: what the service works with
export type Book = { id: string; title: string; authorId: string; priceCents: number; createdAt: Date };

// Response DTO: exactly what the API promises, nothing more
export type BookResponse = { id: string; title: string; authorId: string; price: { amount: number; currency: 'USD' }; createdAt: string };

export const toBook = (r: BookRow): Book => ({
  id: r.id,
  title: r.title,
  authorId: r.author_id,
  priceCents: Number(r.price_cents),          // bigint arrives as a string, see below
  createdAt: r.created_at,
});

export const toBookResponse = (b: Book): BookResponse => ({
  id: b.id,
  title: b.title,
  authorId: b.authorId,
  price: { amount: b.priceCents / 100, currency: 'USD' },
  createdAt: b.createdAt.toISOString(),       // one date format on the wire
});
// internal_notes never appears: a NEW column is invisible until someone maps it on purpose
```

**Edge cases.**
- **`bigint` and `numeric` come back as strings** from node-postgres by default, because JavaScript numbers can't represent every 64-bit integer exactly. That includes `count(*)`. Convert in the mapper (or register a type parser), and use `BigInt` or keep the string when values can exceed `Number.MAX_SAFE_INTEGER`.
- **Dates.** `timestamptz` becomes a JS `Date`; serialize with `toISOString()` in one place so every endpoint emits UTC ISO 8601.
- **Mapping lists of thousands of rows** is cheap compared to the query, but avoid `JSON.parse(JSON.stringify(x))`-style deep copies as a "mapper".

### 9.3 Output allow-lists, not deny-lists ➕

**Problem.** A deny-list (`delete user.passwordHash; res.json(user)`) fails **open**: every new sensitive column is exposed until someone remembers to delete it too.

**Mechanism.** Allow-list the output: the response type is built field by field (9.2), or validated against an output schema that **strips** unknown keys.

**Implementation.**

```ts title="zod output schema"
const UserResponse = z.object({ id: z.string(), name: z.string(), email: z.string().email() }); // zod strips unknown keys by default
res.json(UserResponse.parse(user));          // passwordHash, mfaSecret, ... are dropped
```

```ts title="NestJS with class-transformer"
export class UserResponseDto {
  @Expose() id!: string;
  @Expose() name!: string;
}
// return plainToInstance(UserResponseDto, user, { excludeExtraneousValues: true });
// only @Expose() fields survive
```

**Edge cases.**
- **Input needs the same treatment.** Spreading `req.body` into an insert is mass assignment. Validate into a request DTO with only the allowed fields (`.strict()` or stripping), then build the repository input from it.
- **Nested objects.** An allow-list on the top level doesn't help if a nested `author` object is passed through raw. Map nested objects with their own mappers.
- **Parsing cost.** Running a full schema parse on every item of a 1,000-row response adds measurable CPU. Plain mapping functions are cheaper; use schema parsing in tests to check that mappers match the OpenAPI contract.

## 10. Middleware 🎓

### What middleware is
Draw the lifecycle again, but mark **boundaries** between steps: after the entry point, before routing, after routing, before the handler, after the handler. At any of those boundaries you can insert extra functions. Because they run **in the middle** of the lifecycle, between routing, handlers and the response, they're called **middlewares**.

### What a middleware receives
A middleware is a handler with **one extra capability**. It gets three things from the runtime:
1. the **request** object,
2. the **response** object,
3. **`next`**, a function that **passes execution to the next processing context**.

"Next context" rather than "next middleware", because what comes next might be another middleware, the router, or the handler.

### What a middleware can do
- **Read** values from the request.
- **Modify** the request (attach data) and the response (set headers).
- **Send a response itself and end the request right there.** The request may never reach routing or the handler. That's how an auth middleware rejects a bad token without wasting work downstream.
- **Every middleware is optional.** Some lifecycles have many; a route might have none at all.

<Mermaid chart={`flowchart LR
  In["Request in"] --> M1["CORS"]
  M1 -->|"next()"| M2["Logging"]
  M2 -->|"next()"| RT["Router"]
  RT -->|"next()"| M3["Auth"]
  M3 -->|"next()"| H["Handler"]
  M3 -->|"bad token: 401"| Out["Response out"]
  H --> Out
  H -. "throws" .-> EH["Global error handler (last)"]
  EH --> Out`} />

### Why middleware exists
**The same reason functions exist: write logic once, reuse it everywhere.**
- A busy backend gets thousands, millions, even billions of requests a day, and has **hundreds or thousands of endpoints**.
- Many operations apply to **every** request: security checks, logging, authentication, parsing, compression.
- **Alternative 1:** copy the code into every handler. Obviously bad.
- **Alternative 2:** write a helper function and **call it in every handler**. Better, but it's **still duplication** (one call per handler), and it's easy to forget one.
- **Middleware:** register the logic **once** in the lifecycle. It runs **before** the request reaches the handler, and it can **reject early** so you don't spend precious server resources on a request that was going to fail anyway.

### 🔧 Going deeper: how `next` is actually implemented
There's no magic. A framework keeps an **ordered array** of functions and an **index**. Calling `next()` runs the function at `index + 1`. Not calling it ends the chain. Calling `next(err)` skips ahead to error handlers.

```ts title="tiny-chain.ts"
type Next = (err?: unknown) => void;
type Mw = (req: Req, res: Res, next: Next) => void | Promise<void>;
type ErrMw = (err: unknown, req: Req, res: Res, next: Next) => void;

export function runChain(stack: Mw[], onError: ErrMw, req: Req, res: Res) {
  let i = -1;
  const next: Next = (err) => {
    if (err) return onError(err, req, res, () => {});     // jump straight to the error handler
    i++;
    const fn = stack[i];
    if (!fn) return;                                       // end of chain: nobody responded (framework sends 404)
    Promise.resolve()
      .then(() => fn(req, res, next))
      .catch(next);                                        // async throw becomes next(err)
  };
  next();
}
```

Two consequences follow directly from this implementation:
- **Order is the array order.** That's the next topic.
- **Code after `await next()`** in an async middleware runs on the way **back out**. That's the "onion model" (Koa, Hono, NestJS interceptors), and it's how timing and response logging work.

## 11. Middleware order, and the common middlewares 🎓

### Why order matters
Execution flows **one way** through the array: each middleware hands off with `next`, until something sends the response. So **position decides what a middleware can see and prevent**. Reject early things as early as possible, and put the thing that must observe everyone else's failures **last**.

<Mermaid chart={`flowchart TD
  A["CORS<br/>reject foreign origins first"] --> B["Security headers"]
  B --> C["Request ID + logging"]
  C --> D["Rate limit"]
  D --> E["Body parsing + compression"]
  E --> F["Authentication<br/>writes user into context"]
  F --> G["Route-level checks (permissions)"]
  G --> H["Handler / service / repository"]
  H --> I["Global error handler<br/>always LAST"]`} />

The lesson's typical order: **CORS first → logging → authentication → … → global error handling last**. Spend real thought on the order for your app. The chart above is a 🔧 fuller version; where rate limiting and parsing go is a trade-off, not a rule.

### CORS 🎓
- **What it is:** browsers enforce the same-origin policy. A page on `example.com` may not read responses from other origins **unless the server's response includes headers that allow it**.
- **Server side:** the runtime gives you the request's `Origin`. If it's in your allow-list (typically your frontend's domain), set the allow headers on the response and call `next()`. If not, add nothing; the browser blocks the response.
- **Why middleware:** it must run for **every request**, and it needs **both** the request (to read `Origin`) and the response (to set headers). Code that needs to run on every request and touches req/res is the textbook case for middleware.
- **Why first:** if the origin is not allowed, you want to know as early as possible.

```ts title="cors.middleware.ts"
const ALLOWED = new Set(['https://app.example.com']);

export function cors(req: Request, res: Response, next: NextFunction) {
  const origin = req.headers.origin;
  res.vary('Origin');                                     // 🔧 caches must not reuse one origin's answer for another
  if (origin && ALLOWED.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Access-Control-Allow-Credentials', 'true');
  }
  if (req.method === 'OPTIONS') {                          // 🔧 preflight: answer here, never reach the handler
    res.setHeader('Access-Control-Allow-Methods', 'GET,POST,PATCH,DELETE');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');
    res.setHeader('Access-Control-Max-Age', '600');
    return res.sendStatus(204);
  }
  next();
}
```

🔧 CORS is enforced **by browsers only**. `curl` or another server ignores it completely, so CORS is not an authorization mechanism.

### Security headers 🎓
Headers like **Content-Security-Policy** should be on every response, so a middleware adds them and calls `next()`. 🔧 In Express, `helmet()` sets a sensible bundle (CSP, `X-Content-Type-Options: nosniff`, HSTS and others).

### Authentication 🎓
- **Problem:** almost every endpoint has to extract a token (JWT, session ID, …) from a header, cookie or payload, then verify it.
- **Failure:** respond **401 Unauthorized** immediately. No `next()`, and the handler never runs.
- **Success:** extract what downstream code needs (**user ID**, **role**: user, admin, sales…, **permissions**), store it in the **request context**, and call `next()`.

```ts title="auth.middleware.ts"
import { jwtVerify } from 'jose';

export async function authenticate(req: Request, res: Response, next: NextFunction) {
  const header = req.headers.authorization ?? '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  if (!token) return res.status(401).json({ code: 'UNAUTHENTICATED' });

  try {
    const { payload } = await jwtVerify(token, JWT_KEY, { issuer: 'api.example.com', audience: 'web' });
    res.locals.auth = { userId: String(payload.sub), role: String(payload.role) }; // into request context
    next();
  } catch {
    return res.status(401).json({ code: 'INVALID_TOKEN' });  // expired, bad signature, wrong audience...
  }
}
```

🔧 401 means "who are you?" (missing or invalid credentials). A **403** is for "I know who you are, and you're not allowed", which is a permission check after authentication.

### Rate limiting 🎓
- **Problem:** one client sending a flood of requests in a short time.
- **Mechanism:** you choose a **threshold** and a **window**, for example "more than 30 calls from this IP in 2 seconds". Both numbers are yours to decide (30, 500…).
- **Over the limit:** respond **429 Too Many Requests**. Under it: `next()`.

🔧 Implementation: a **fixed-window counter in Redis**. Every app instance shares the same counter, which is the point: an in-memory counter only limits per instance.

```ts title="rate-limit.middleware.ts"
const LIMIT = 30, WINDOW_S = 2;

export async function rateLimit(req: Request, res: Response, next: NextFunction) {
  const window = Math.floor(Date.now() / 1000 / WINDOW_S);
  const key = `rl:${req.ip}:${window}`;                 // one counter per IP per window
  const count = await redis.incr(key);                  // atomic across all instances
  if (count === 1) await redis.expire(key, WINDOW_S);   // the key cleans itself up
  if (count > LIMIT) {
    res.setHeader('Retry-After', String(WINDOW_S));     // RFC 6585: MAY tell the client when to retry
    return res.status(429).json({ code: 'RATE_LIMITED' });
  }
  next();
}
```

🔧 Edge cases:
- **Behind a load balancer** every request appears to come from the proxy's IP. Configure `app.set('trust proxy', 1)` (exactly the number of proxies you trust) so `req.ip` is read from `X-Forwarded-For`; trusting it blindly lets clients spoof their IP.
- **Fixed windows allow bursts at the edges** (30 at the end of one window + 30 at the start of the next). Sliding windows or token buckets smooth that out.
- For logged-in traffic, limit **per user ID** too, since many users can share one IP (offices, mobile carriers).

### Advertising the limit to clients: `RateLimit` headers ➕

The middleware above only tells a client about the limit **after** it has been hit; well-behaved clients need to see their remaining quota before that, so they can slow down instead of failing.

#### Why a bare 429 isn't enough ➕
**Problem.** A batch client or SDK that only learns about the limit from a 429 has two bad options: retry immediately (making the overload worse, and with many clients producing a synchronized **retry storm**), or back off for an arbitrary guess. Neither knows the window or the quota.

**Why it happens.** The limit is server-side state the client can't observe. `Retry-After` (RFC 6585 / RFC 9110) only covers the moment of rejection.

**Mechanism.** Return the quota on **every** response. The IETF httpapi working group's draft *RateLimit header fields for HTTP* (draft-11 at the time of writing, still an Internet-Draft, not an RFC) defines two fields using structured-field syntax:
- `RateLimit-Policy`: the policies that apply, each with a quota `q` and window `w` in seconds, for example `"burst";q=100;w=60`;
- `RateLimit`: the current state of a policy, with remaining units `r` and seconds until reset `t`, for example `"burst";r=42;t=17`.

#### Implementation ➕

```ts title="rate-limit.middleware.ts (with headers)"
const POLICY = 'burst', LIMIT = 30, WINDOW_S = 2;

export async function rateLimit(req: Request, res: Response, next: NextFunction) {
  const nowS = Date.now() / 1000;
  const window = Math.floor(nowS / WINDOW_S);
  const key = `rl:${res.locals.auth?.userId ?? req.ip}:${window}`;
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, WINDOW_S);

  const remaining = Math.max(0, LIMIT - count);
  const resetIn = Math.ceil((window + 1) * WINDOW_S - nowS);       // seconds until this window ends
  res.setHeader('RateLimit-Policy', `"${POLICY}";q=${LIMIT};w=${WINDOW_S}`);
  res.setHeader('RateLimit', `"${POLICY}";r=${remaining};t=${resetIn}`);

  if (count > LIMIT) {
    res.setHeader('Retry-After', String(resetIn));                 // the standardized signal on rejection
    return res.status(429).json({ code: 'RATE_LIMITED' });
  }
  next();
}
```

#### Edge cases and failure modes ➕
- **The draft has changed shape across versions.** Earlier drafts used three separate fields (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`), and many APIs still send the older, non-standard `X-RateLimit-*` trio. Libraries such as `express-rate-limit` let you pick which format to emit. Document the one you choose, and keep it stable for clients.
- **Headers are hints, not promises.** The draft says a positive remaining quota doesn't guarantee the next request will be served; the server may still throttle (for example under global overload).
- **CORS.** Browser JavaScript can't read these headers cross-origin unless you list them in `Access-Control-Expose-Headers`.
- **Don't leak partition keys.** If the policy is per API key or per tenant, don't echo internal identifiers in the header.

### Logging and monitoring 🎓
For every request, record the **path**, **method**, **query params**, possibly the body, and so on, to the terminal or a log file. It's what you debug, audit and report from later.

```ts title="logging.middleware.ts"
export function requestLogger(req: Request, res: Response, next: NextFunction) {
  const start = process.hrtime.bigint();
  res.on('finish', () => {                               // 🔧 runs after the response, so status and duration are known
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    logger.info({ requestId: res.locals.requestId, method: req.method, path: req.path, status: res.statusCode, ms });
  });
  next();
}
```

🔧 Never log passwords, tokens or full bodies with personal data. Redact before writing.

### Global error handling 🎓
- **Problem:** errors can happen **anywhere**: any middleware, the handler, the service, the repository. You want **one** place that turns them into a well-formed response.
- **Mechanism:** the error handler receives the raw error, decides whether it's a **client error** (4xx) or a **server error** (5xx) (you can put a field on your error types to say which), and sends a **structured** body: a message plus a **code** (sometimes called an ID), so the frontend can show its own user-friendly text per code.
- **It must be the last middleware.** Execution only flows forward. A handler placed **before** the failing code can't see an error thrown **after** it.

🔧 In Express, an error handler is recognised by having **four parameters**, and it's registered after all routes. Express 5 automatically forwards rejected promises from async handlers to it.

```ts title="error.middleware.ts"
const MAP = { NOT_FOUND: 404, CONFLICT: 409, FORBIDDEN: 403 } as const;

export function errorHandler(err: any, req: Request, res: Response, _next: NextFunction) {
  const fromLib = Number(err?.status);                    // e.g. express.json(): 400 bad JSON, 413 too large
  const status = MAP[err?.kind as keyof typeof MAP] ?? (fromLib >= 400 && fromLib < 500 ? fromLib : 500);
  if (status >= 500) logger.error({ err, requestId: res.locals.requestId }, 'unhandled error');
  if (res.headersSent) return res.end();                  // too late to change the status
  res.status(status).json({
    code: err?.kind ?? 'INTERNAL_ERROR',
    message: status >= 500 ? 'Something went wrong' : err.message, // never leak stack traces or SQL
    requestId: res.locals.requestId,                      // the user can quote this to support
  });
}

// app.ts: order is the whole point
app.use(cors);
app.use(helmet());
app.use(requestId);
app.use(requestLogger);
app.use(rateLimit);
app.use(express.json({ limit: '1mb' }));
app.use(compression());
app.use('/books', authenticate, booksRouter);
app.use(errorHandler);                                    // LAST
```

### Compression 🎓
For large responses (a JSON body with thousands of fields), a middleware compresses the body (gzip and similar). Browsers decompress automatically, so the payload is small **in transit** and back to normal **on the client**.

🔧 The client advertises support with `Accept-Encoding`; the server answers with `Content-Encoding: gzip`. Skip tiny bodies (the overhead isn't worth it) and already-compressed content (images, video). At scale, compression is often done by a reverse proxy or CDN instead.

### Parsing, binding and validation 🎓
Serialization and deserialization, binding, even validation and transformation **can** be delegated to middleware so handlers don't repeat them. Whether you do depends on your code base's conventions.

## 12. Where a cross-cutting concern belongs ➕

Every middleware above works at the **HTTP** level. But not every "applies in many places" concern is an HTTP concern, and putting one at the wrong level is a common design bug.

### 12.1 What a global middleware can't see ➕

**Problem.** You want "only users with `books:write` may call `POST /books`", or a stricter rate limit for `POST /login` than for `GET /books`. Written as one global middleware, it ends up as a growing `if (req.path.startsWith(...))` table that drifts from the real routes.

**Why it happens.** A global middleware registered with `app.use()` runs **before routing**, so it doesn't know which handler will run, what that route's path parameters are, or what the handler requires. It only sees the raw method and URL.

**Mechanism.** Attach route-specific concerns **to the route**, either as route-level middleware or as **metadata** read by a generic check. Then the requirement sits next to the handler it protects.

**Implementation, Express:** route-level middleware is just an extra argument.

```ts title="permissions.ts"
export const requirePermission = (perm: string) =>
  (req: Request, res: Response, next: NextFunction) =>
    res.locals.auth?.permissions?.includes(perm) ? next() : res.status(403).json({ code: 'FORBIDDEN' });

router.post('/books', requirePermission('books:write'), booksController.create);
router.post('/login', rateLimitStrict, authController.login);
```

**Implementation, NestJS:** a decorator writes metadata on the handler; one guard reads it for every route.

```ts title="permissions.guard.ts"
export const RequirePermission = (perm: string) => SetMetadata('permission', perm);

@Injectable()
export class PermissionGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}
  canActivate(ctx: ExecutionContext) {
    const perm = this.reflector.get<string>('permission', ctx.getHandler()); // knows WHICH handler
    if (!perm) return true;
    const user = ctx.switchToHttp().getRequest().user;
    return user?.permissions?.includes(perm) ?? false;                   // false -> 403
  }
}

// @Post() @RequirePermission('books:write') create(@Body() dto: CreateBookDto) { ... }
```

**Edge cases.**
- **Default deny.** With metadata-based checks, a route that forgets the decorator is **open**. For sensitive apps, invert it: require every route to declare either a permission or an explicit `@Public()` marker, and fail at startup otherwise.
- **Object-level checks don't fit here.** "Can this user edit **this** book?" needs the book's owner from the database. That's a service-level rule ([Authentication and authorization](/docs/backend-first-principles/08-authentication-authorization) covers the models); a route guard can only check coarse permissions.

### 12.2 Business-level concerns: wrap the service, not the request ➕

**Problem.** Audit logging ("user X archived organization Y"), retries around a flaky partner API, caching an expensive computation, or opening a transaction are often written as HTTP middleware or interceptors. Then the same service called from a **queue worker** or a **cron job** skips them: no audit row, no retry, no transaction.

**Why it happens.** These concerns are about the **business operation**, not the HTTP request. HTTP is only one of several ways the operation gets invoked (section 7.1's driving adapters).

**Mechanism.** Apply them around the service method itself, with a higher-order function or a method decorator, so they run whichever adapter calls the service.

**Implementation: a plain higher-order wrapper** (no decorator configuration needed):

```ts title="core/audited.ts"
export function audited<A extends unknown[], R>(
  action: string,
  fn: (...args: A) => Promise<R>,
  audit: AuditLog,
): (...args: A) => Promise<R> {
  return async (...args) => {
    const result = await fn(...args);
    await audit.record({ action, actor: ctx()?.userId ?? 'system', at: new Date() }); // ctx(): section 13
    return result;
  };
}

// composition root (7.2): wrap once, every caller gets it
const archive = audited('organization.archive', orgService.archive.bind(orgService), auditLog);
```

```ts title="core/retry.ts"
export async function withRetry<T>(fn: () => Promise<T>, attempts = 3, baseMs = 100): Promise<T> {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (err) {
      if (i >= attempts - 1 || !isTransient(err)) throw err;          // only retry what can succeed later
      await new Promise((r) => setTimeout(r, baseMs * 2 ** i * (0.5 + Math.random()))); // backoff + jitter
    }
  }
}
```

**Edge cases.**
- **Retries require idempotency.** Retrying a non-idempotent call (charging a card) can double the effect. Only retry idempotent operations, or ones protected by an idempotency key (see the REST lesson; [Error handling and fault tolerance](/docs/backend-first-principles/16-error-handling-fault-tolerance) covers retry policies).
- **Retries stack.** If the client, your service and the HTTP library each retry 3 times, one failure becomes 27 calls. Retry at one layer only.
- **Order of wrappers matters** just like middleware order: `audited(withTransaction(...))` audits only committed work, while `withTransaction(audited(...))` puts the audit row inside the transaction so it rolls back with it. Pick the one that matches the requirement.

### 12.3 A placement table ➕

| Concern | Needs to know | Put it in |
|---|---|---|
| CORS, security headers, compression, body parsing | Only the raw request and response | Global middleware |
| Request ID, access logs, request deadline | The request lifecycle | Global middleware (first) |
| Authentication | The credentials on the request | Global or router-level middleware |
| Coarse permission, per-route rate limit | Which route is being called | Route-level middleware, or guard + metadata |
| Validation and transformation | The route's input schema | Route-level (pipe, validator), next to the handler |
| Object-level authorization | The resource being touched | Service |
| Transactions, audit, retries, business caching | The business operation | Wrapper or decorator around the service |
| Mapping errors to HTTP | Error type and HTTP semantics | Global error handler (last) |

### 12.4 Failure modes inside the chain ➕

**Problem.** Two bugs are specific to middleware chains and are hard to see in code review.

**1. A middleware that neither responds nor calls `next()`.** A missed branch (`if (ok) next()` with no `else`) leaves the request hanging. The client waits until some timeout fires: Node's `server.requestTimeout` defaults to 300,000 ms (5 minutes), and a load balancer or the client may give up earlier with a 502 or 504. Meanwhile the socket and any resources stay held.

**2. Responding twice.** A middleware sends a 401 and then also calls `next()` (a missing `return`), or a handler responds and then throws. The second write fails with Node's `ERR_HTTP_HEADERS_SENT` ("Cannot set headers after they are sent to the client").

**Mechanism.** Make every branch end in exactly one of `return res...` or `return next()`, and guard error handlers with `res.headersSent` (section 11's error handler already does). Add a request-level timeout middleware so a hang becomes a clean 503 instead of a five-minute wait.

```ts title="request-timeout.middleware.ts"
export function requestTimeout(ms: number) {
  return (req: Request, res: Response, next: NextFunction) => {
    const timer = setTimeout(() => {
      if (!res.headersSent) res.status(503).json({ code: 'REQUEST_TIMEOUT', requestId: res.locals.requestId });
    }, ms);
    res.on('close', () => clearTimeout(timer));   // fires on finish and on client disconnect
    next();
  };
}
```

**Edge cases.**
- **The timeout response doesn't stop the work.** The handler keeps running after the 503 unless it also listens to the request's abort signal (section 13, use 3). Combine both.
- **Streaming responses** (downloads, SSE) legitimately run for minutes; exempt those routes or use a per-route value.

## 13. Request context 🎓

### The problem
A request passes through many function boundaries: CORS, logging, routing, authentication, permission checks, the handler, the error handler. Information discovered early (who the user is) is needed later (in the handler). How do you get it there **without** making every function pass it explicitly to the next, which would **couple them tightly**?

### The mechanism
**Request context: a key-value store scoped to exactly one request.**
- Every request gets **its own** context. Thousands of concurrent requests from clients around the world each have separate ones.
- Every middleware and handler on that request's path can **read and write** it.
- When the request ends, the context goes away.
- The concept is the same in every language and framework; only the concrete implementation differs.

<Mermaid chart={`flowchart LR
  subgraph Ctx["Context for request 7f3a (lives only as long as this request)"]
    K1["requestId = 7f3a..."]
    K2["userId = u_42"]
    K3["role = admin"]
    K4["deadline / abort signal"]
  end
  RID["Request ID middleware"] -- writes --> K1
  AUTH["Auth middleware"] -- writes --> K2
  AUTH -- writes --> K3
  H["Handler"] -- reads --> K2
  LOG["Logger"] -- reads --> K1
  OUT["Outgoing HTTP call"] -- reads --> K4`} />

### Use 1: identity from authentication 🎓
- The auth middleware verifies the token (or, on a login, the email and password), finds the **user ID**, **role** (user, admin, sales, depending on your RBAC) and **permissions** (read, write…), and stores them in context.
- Downstream, a `POST /books` handler needs a `userId` for the new book row. It takes it **from context**, not from the request body.
- **Why:** if you trust a `userId` field in the payload, a malicious client can just send **someone else's** ID and act as them. The authenticated identity is the only trustworthy source.
- The same context data feeds **permission checks**: is this user allowed to insert a book? Is this user an admin?

### Use 2: request ID for tracing 🎓
- An early middleware generates a **UUID** and stores it in context.
- Every log line for this request includes it.
- Calls to other services (in a microservice architecture) send it along in a header like **`X-Request-ID`**.
- When debugging, you search the logs for that one ID and see **where the request started and every service it touched**.

### Use 3: cancellation, abort signals and deadlines 🎓
Context also carries **cancellation signals and deadlines** to downstream calls, so a slow external service can't keep your request **hanging forever**.

### 🔧 Going deeper: request context in Node.js

**Option A: hang it on the request or response object.** Express gives you `res.locals` (and people often add `req.user`). Simple, but you have to pass `req` everywhere you need it, which drags HTTP into the service layer.

**Option B: `AsyncLocalStorage`** (stable since Node 16.4). It's Node's equivalent of thread-local storage for async code: a value set with `run()` is visible through `getStore()` in every async operation started inside that callback, including awaits, timers and promise chains, without passing anything.

```ts title="context.ts"
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';

type Ctx = { requestId: string; userId?: string; role?: string; signal: AbortSignal };
export const als = new AsyncLocalStorage<Ctx>();
export const ctx = () => als.getStore();                 // usable from ANY layer, no parameters

export function requestContext(req: Request, res: Response, next: NextFunction) {
  const incoming = req.header('x-request-id');
  const requestId = incoming && /^[\w-]{8,64}$/.test(incoming) ? incoming : randomUUID(); // reuse upstream ID if sane
  res.setHeader('X-Request-ID', requestId);

  const controller = new AbortController();
  res.on('close', () => { if (!res.writableFinished) controller.abort(); }); // client went away
  const signal = AbortSignal.any([controller.signal, AbortSignal.timeout(10_000)]); // + a 10 s deadline

  res.locals.requestId = requestId;
  als.run({ requestId, signal }, () => next());           // everything downstream runs inside this store
}

// auth middleware, after verifying: Object.assign(ctx()!, { userId, role })

// deep inside a service or HTTP client:
export async function callBilling(path: string) {
  const c = ctx()!;
  return fetch(`https://billing.internal${path}`, {
    headers: { 'X-Request-ID': c.requestId },             // propagate the trace ID
    signal: c.signal,                                     // abort if the client left or the deadline passed
  });
}
```

🔧 **Edge cases**
- **Mutate the store object; don't replace it.** Code already running holds a reference to the object from `run()`.
- **Don't use a module-level variable** for "the current user". Node serves many requests concurrently on one thread, so a global would leak one user's identity into another user's request. That's the bug request context exists to prevent.
- **Validate an incoming request ID** before reusing it (length and characters), or a client can inject arbitrary text into your logs.
- **Pass the signal to the database driver too**, where supported, so a cancelled request also stops its expensive query.

🔧 The Go version, for comparison (labelled): `context.Context` is the first argument of every function on the request path, and it carries both values and cancellation.

```go title="context.go"
func (h *Handler) GetBook(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second) // r.Context() is cancelled if the client disconnects
    defer cancel()
    userID := ctx.Value(userIDKey).(string)                        // set by the auth middleware
    book, err := h.svc.GetBook(ctx, userID, chi.URLParam(r, "id")) // ctx flows down to the DB driver
    // ...
}
```

## 14. 🔧 Going deeper: the same ideas in NestJS

NestJS gives each idea from this lesson its own named building block. Its documented request lifecycle runs in this order:

| Step | NestJS piece | Lesson concept |
|---|---|---|
| 1 | **Middleware** (global, then module) | Generic middleware: CORS, logging, request ID |
| 2 | **Guards** | Authentication and authorization middleware (return false → 403 by default) |
| 3 | **Interceptors**, before the handler | Onion-style middleware: timing, logging |
| 4 | **Pipes** | Binding, validation and transformation (`ValidationPipe`, `ParseIntPipe`) |
| 5 | **Controller** method | Handler / controller |
| 6 | **Service** (a provider) | Service layer |
| 7 | **Interceptors**, after the handler | Response mapping, on the way out |
| 8 | **Exception filters** | Global error handler |

Repositories are usually a TypeORM or Prisma wrapper injected into the service. For request context, use `@Injectable({ scope: Scope.REQUEST })` (simple, but it re-creates the provider chain on every request) or an `AsyncLocalStorage`-based library such as `nestjs-cls`.

## 15. Recap 🎓

- **Lifecycle:** OS → entry point → routing → handler → service → repository → back to the handler → response.
- **Handler/controller:** bind (deserialize; 400 and stop if it fails) → validate and transform (defaults, so downstream has one path) → call the service with data and auth info → pick the status code and send the response.
- **Service:** the real processing and orchestration; knows nothing about HTTP; may or may not use repositories.
- **Repository:** builds and runs queries; one method returns one kind of data.
- **Middleware:** functions at the boundaries with `req`, `res` and `next`; reusable cross-cutting logic; can end the request early; **order matters**. CORS first, global error handler last.
- **Request context:** request-scoped key-value state shared across middleware and handlers without coupling them: identity from auth (never trust a client-sent user ID), request IDs for tracing, cancellation and deadlines.
- ➕ **Dependency direction:** the core declares ports (interfaces); repositories and HTTP are adapters; one composition root builds the graph. Business rules live in the service or domain objects, never in controllers.
- ➕ **Transactions across repositories:** one checked-out connection per unit of work, passed explicitly or through `AsyncLocalStorage`; savepoints for nesting; no network calls inside; database-side timeouts as a ceiling.
- ➕ **Models per boundary:** request/response DTO, domain object and row are different types with explicit mappers; allow-list outputs.
- ➕ **Cross-cutting placement:** HTTP concerns in global middleware, route-specific ones on the route, business concerns wrapped around the service. Advertise rate limits with `RateLimit` headers.

## Interview questions

1. **Why separate controllers, services and repositories when one function would work?** **It isn't required; it's a pattern. Each layer has one reason to change (API contract, business rules, data access), which makes the code easier to scale, debug and test.**
2. **What are the controller's four jobs, in order?** **Bind/deserialize the input (400 on failure), validate and transform it, call the service, then choose the status code and send the response.**
3. **How can you tell whether a service method is well designed?** **You shouldn't be able to tell it's used by an HTTP API: no status codes, request objects or headers. It reports failures with domain errors.**
4. **Why shouldn't one repository method return a single row or a list depending on an optional parameter?** **Each method should return one predictable kind of data. Combining results is the service's orchestration job.**
5. **Why is a middleware better than a helper function called in every handler?** **The helper call is still duplicated in every handler and easy to forget. Middleware is registered once, runs for every request, and can reject early before the handler spends resources.**
6. **What does `next` do?** **It passes execution to the next processing context, which may be another middleware, the router or the handler. Not calling it ends the chain; in Express, `next(err)` jumps to error handlers.**
7. **Why must the global error handler be registered last?** **Execution flows forward only, so it can only catch errors from code that runs before it.**
8. **Why should CORS run first?** **If the origin isn't allowed, you want to find out before doing any other work.**
9. **Which status codes do the auth and rate-limit middlewares send?** **401 for missing or invalid credentials (403 when authenticated but not permitted); 429 when the rate limit is exceeded, optionally with `Retry-After`.**
10. **What is request context, and why not use a global variable?** **A key-value store scoped to one request and shared across its middleware and handlers. A global would be shared by all concurrent requests, leaking one user's data into another's.**
11. **Why take `userId` from context instead of the request body?** **A client can put any ID in the body and act as another user. Only the authenticated identity is trustworthy.**
12. **How does a request ID help in a microservice system?** **It's generated once, stored in context, logged everywhere and forwarded in a header like `X-Request-ID`, so you can trace one request across every service.**
13. **How do you implement request context in Node.js?** **`res.locals` or `req` properties for simple cases, or `AsyncLocalStorage`, which makes the store available to all async code started inside `run()` without passing parameters.**
14. ➕ **Why should the service define the repository interface rather than import the repository class?** **So compile-time dependencies point from details (SQL, drivers) into the business core. The core stays testable with fakes and can be driven by HTTP, workers or tests alike (ports and adapters).**
15. ➕ **Why can't you run `BEGIN` / `COMMIT` through `pool.query`?** **A transaction lives on one connection, and the pool may give each query a different one. Check out one client, run every statement on it, and always release it.**
16. ➕ **How do two repositories share one transaction?** **Construct them with the transaction's client (a unit of work), or keep the client in `AsyncLocalStorage` and let repositories use it when present.**
17. ➕ **Why is sending an email inside a database transaction a bug?** **The transaction holds locks and a pool connection while waiting on the network, and the email can't be rolled back. Commit first, or write an outbox event in the transaction.**
18. ➕ **Why not return database rows directly from the API?** **New columns (like password hashes) leak automatically, and schema changes break the contract. Map rows to domain objects and allow-list the response DTO.**
19. ➕ **Where should audit logging or retries go, middleware or service?** **Around the service: they belong to the business operation, and middleware would skip them when a worker or cron job calls the same service.**
20. ➕ **What happens if a middleware forgets both to respond and to call `next()`?** **The request hangs until a server, proxy or client timeout fires. Every branch must end in exactly one of the two.**
