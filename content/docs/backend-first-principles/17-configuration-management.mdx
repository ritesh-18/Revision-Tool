Most people hear "config" and think of a database password in a `.env` file. The lesson's point is that configuration is much bigger: it decides **how the same code behaves** in every place it runs. This page walks through what config is, the kinds of config, where it lives, why it differs per environment, and how to keep it safe and correct.

## 1. What configuration management is 🎓

**Definition:** a systematic way to **organise, store, access and maintain all the settings** of a backend application. The key word is *all*.

The lesson calls config the **DNA of your application**: the code is the same everywhere, but the config decides how it behaves in each environment.

### The "car is just the engine" mistake
Thinking config means only secrets (DB URL, JWT secret, email provider API key) is like saying a car is just its engine. The engine matters most, but you're ignoring the other 90%. Config also controls:
- **how the app starts up** and **connects to external services**;
- **how it behaves per environment**;
- **logging**: whether it logs, what it logs, and where;
- **where metrics go** (performance and business metrics);
- **which features are on** for this deployment, and **for which users**.

### Worked example: an e-commerce backend 🎓
| Config | Example | Why it's config, not code |
|---|---|---|
| DB connection | host, port, user, password, timeouts | Different per environment, secret |
| Payment processor | Stripe API key | Secret, different per environment (test vs live key) |
| Feature flags | new checkout flow on or off, and for whom | Must change without a redeploy |
| Performance tuning | DB connection pool size | Depends on the machine and the traffic |
| Security settings | session timeout (30 s, 60 s, ...) | A policy decision, not logic |
| Business rules | maximum order amount per user | Business changes it, engineers shouldn't have to |

## 2. Config values have different characteristics 🎓

Not every config value is the same kind of thing. Three axes matter, and each one drives a storage decision:

| Axis | Values | Engineering consequence |
|---|---|---|
| **Sensitivity** | secret (leak = damage or loss) vs non-secret (just controls behaviour) | Secrets go to an encrypted store with access control; non-secrets can live in Git |
| **Change frequency** | changes often vs once a month or quarter | Frequently changing values need runtime reload (flags), rare ones can be read at startup |
| **Environment dependence** | same in dev, staging and prod vs different | Shared values become defaults in code or a base file; per-env values are overrides |

## 3. Why it gets hard: distributed systems and config chaos 🎓

### Problem
Modern backends don't run alone. They are one part of a system with **other services, databases, caches (Redis), message queues, third-party integrations, auth providers, email** and so on. Every one of those integration points needs config, and not only "how to connect":
- **how to handle failures** (timeouts, retries),
- **how to optimise performance** (pool sizes, concurrency),
- **how to stay secure** (credentials, TLS).

Multiply that by environments and instances, and the number of values explodes.

### What happens without a system: configuration chaos
1. **Hard-coded values scattered** across the codebase instead of one central place.
2. **Inconsistent behaviour** across environments (it works on staging, breaks in prod).
3. **Security holes** from secrets committed to code.
4. **Debugging nightmares**: you can't reproduce the issue because you don't know which value was active, so you can't tell which config caused which break.

### Why the stakes are higher on the backend
A misconfigured **frontend** shows the wrong dialog or redirects to the wrong route. A misconfigured **backend** can **expose customer data**, **process payments incorrectly** or **take the whole platform down**. Backends also run on very different targets (cloud providers, on-prem servers, containers, serverless and edge functions), each with its own way of supplying config.

### The mechanism that solves it 🔧
The fix is to make config a **single, typed, validated object** built once at startup from well-defined sources, and to make the rest of the code read only from that object.

## 4. Types of configuration 🎓

Knowing the type tells you **how to store it, how to secure it and who may access it**.

### 4.1 Application settings (the most common)
Log level, port, connection pool size, timeouts.

- **Timeouts, with the lesson's example:** your server's request timeout is **60 s**. An endpoint generates an AI image and returns it as base64, which takes about **80 s** on average. The request is cut off and the client gets **504 Gateway Timeout**. The fix is a config change (or moving the work to a background job), not a code change.
- **Log level:** `debug` in development so you see everything; `info` in production so valuable production logs aren't cluttered.
- **Port:** often `8080` locally; in production it depends on the setup (VPS, Kubernetes, PaaS that injects `PORT`).
- **Pool size:** most backends use **connection pooling** to reuse DB connections; the maximum pool size is a tuning knob.

🔧 **Why timeouts must be configured as a chain.** Every hop has its own timeout: load balancer, server, DB driver, outbound HTTP client. If the load balancer's idle timeout is shorter than your handler's work, the client gets 504 from the LB while your server keeps working for nothing. Order them so **inner timeouts are shorter than outer ones**.

### 4.2 Database config
Host, port, username, password, database name, combined into a **connection URL** the app uses at runtime. Plus extras like **query or statement timeouts**.

### 4.3 External services
Email providers (the lesson mentions **Mailchimp** and **Resend**), payment processors (**Stripe**), auth providers (**Clerk**). Usually an **API key** to initialise the client, plus base URLs and webhooks secrets.

### 4.4 Feature flags
**Problem:** you've built a new checkout flow on a new API. You don't want to ship it to everyone at once. You want A/B testing, or to enable it only for users in the **US** and keep it off for users in **India**.

**Mechanism:** the code contains both paths, and a **flag evaluated at request time** picks one. Flipping the flag changes behaviour **without a deploy**.

🔧 **How percentage rollouts are actually engineered.** A random number per request would flip users between the old and new flow on every refresh. Instead, hash a stable ID into a bucket so the same user always lands in the same group:

```ts title="flags.ts"
import { createHash } from 'node:crypto';

type FlagRule = { enabled: boolean; countries?: string[]; rolloutPercent?: number };

function bucket(flagKey: string, userId: string): number {
  // stable 0..99 per (flag, user); salting with the flag key keeps rollouts independent
  const h = createHash('sha256').update(`${flagKey}:${userId}`).digest();
  return h.readUInt32BE(0) % 100;
}

export function isEnabled(flagKey: string, rule: FlagRule, user: { id: string; country: string }) {
  if (!rule.enabled) return false;                                     // kill switch
  if (rule.countries && !rule.countries.includes(user.country)) return false;
  if (rule.rolloutPercent === undefined) return true;
  return bucket(flagKey, user.id) < rule.rolloutPercent;              // 10 means 10% of users
}

// usage: rules come from a flag service or DB, cached in memory and refreshed every ~30 s
const checkoutRule: FlagRule = { enabled: true, countries: ['US'], rolloutPercent: 25 };
if (isEnabled('new-checkout', checkoutRule, req.user)) return newCheckout(req);
return oldCheckout(req);
```

Edge cases: cache flag rules locally so the flag service being down doesn't take checkout down (fail to the **safe default**); delete flags once a rollout finishes, or the code fills with dead branches.

### 4.5 Kill switches and flag hygiene ➕

The rollout flag above answers "who gets the new code". Production also needs flags that answer "how do I turn this off **right now**, during an incident", and a way to keep the growing pile of flags under control.

#### Release flags vs operational kill switches ➕
**Problem.** A recommendation widget calls a slow ML service. During a traffic spike that service starts timing out, every product page waits on it, and the database pool fills up behind those requests. A redeploy to remove the call takes 15 minutes you don't have.

**Why it happens.** A rollout flag is temporary and decides between two versions of a feature. What you need here is a different kind of flag: a long-lived **operational switch** around a non-essential dependency, which lets an on-call engineer shed that work without touching code. Martin Fowler's feature-toggle taxonomy separates the two: *release toggles* live for days or weeks; *ops toggles* can live for years.

**Mechanism.** Wrap each optional dependency in a switch whose **off path is a cheap, correct degradation** (show bestsellers from cache instead of personalised picks). The switch must be readable in milliseconds and must not depend on the thing it protects.

```ts title="kill-switch.ts"
import { z } from 'zod';

const SnapshotSchema = z.object({ version: z.number().int(), flags: z.record(z.string(), z.boolean()) });
type Snapshot = z.infer<typeof SnapshotSchema> & { fetchedAt: number };

// the value used when we have never reached the flag store: pick the SAFE direction per switch
const DEFAULTS = { 'recs.personalised': true, 'payments.newProvider': false } as const;
let snapshot: Snapshot | null = null;

async function refresh() {
  try {
    const res = await fetch(config.flags.url, { signal: AbortSignal.timeout(2_000) });
    const next = SnapshotSchema.parse(await res.json());              // reject malformed pushes
    if (!snapshot || next.version > snapshot.version) snapshot = { ...next, fetchedAt: Date.now() };
  } catch (err) {
    logger.warn({ err, ageMs: snapshot ? Date.now() - snapshot.fetchedAt : null }, 'flag refresh failed, keeping last good');
  }
}
await refresh();
setInterval(refresh, 10_000).unref();                                  // propagation delay is at most about 10 s

export const flag = (key: keyof typeof DEFAULTS) => snapshot?.flags[key] ?? DEFAULTS[key];

// usage
const recs = flag('recs.personalised') ? await recsClient.forUser(user.id) : await cache.bestsellers();
```

**Edge cases.**
- **Which way is "safe" differs per switch.** For an optional widget, the safe default is usually *on* (normal behaviour). For a risky new payment provider, the safe default is *off*. Write the default next to the key so nobody has to guess.
- **Test the off path.** A kill switch that was never flipped is a code path that was never run. Flip it in staging as part of the release checklist, or in a game day.
- **Version numbers** stop an older snapshot (served by a lagging replica of the flag store) from overwriting a newer one.

#### Propagation delay: how fast "off" really is ➕
**Problem.** The on-call flips the switch, but pods keep calling the failing service for another minute.

**Why it happens.** Each instance holds its own in-memory copy. With polling, the worst-case delay is the **poll interval plus the store's own replication lag**. With 40 pods polling every 60 s, some pods react almost at once and some react a minute later.

**Mechanism.** Choose the interval from the reaction time you need during an incident (10 s polling above), or use **push** (a watch on Consul or etcd keys, server-sent events from a flag service) with polling as the fallback. Expose the snapshot version as a metric, `flags_snapshot_version`, so a dashboard shows when the whole fleet has converged.

**Edge cases.** Push connections drop silently; always keep a poll as the safety net. Never block request handling on a flag fetch: requests read the in-memory snapshot only.

#### Flag debt: making old flags expire ➕
**Problem.** After a year the codebase has 300 flags, half of them permanently on, and nobody knows which are safe to delete. Every flag doubles the number of code paths someone has to reason about.

**Mechanism.** Treat flags as code with an owner and an expiry date, and let CI enforce it.

```ts title="flags.registry.ts"
export const FLAGS = {
  'new-checkout':       { type: 'release', owner: 'checkout-team', expires: '2026-12-01' },
  'recs.personalised':  { type: 'ops',     owner: 'discovery-team', expires: null },   // long-lived by design
} as const;
```

```ts title="scripts/check-flags.ts (runs in CI)"
import { FLAGS } from '../src/flags.registry';
const today = new Date().toISOString().slice(0, 10);
const expired = Object.entries(FLAGS).filter(([, f]) => f.type === 'release' && f.expires && f.expires < today);
if (expired.length) {
  console.error('Expired release flags, remove them:', expired.map(([k]) => k).join(', '));
  process.exit(1);
}
```

**Edge cases.** Typing `flag()` with `keyof typeof FLAGS` means a deleted flag becomes a compile error at every call site, so removal is safe. Remove the flag from the store **after** the code that reads it is gone, never before, or old pods fall back to their default mid-rollout.

### 4.6 Per-tenant configuration ➕

The examples so far set one value per environment. A B2B backend usually also needs values that differ **per customer** inside the same environment.

#### The override hierarchy ➕
**Problem.** Enterprise tenants get a 10 MB upload limit, free tenants 2 MB, and one large customer negotiated 50 MB. Putting that in env vars means one variable per tenant and a redeploy per contract.

**Why it happens.** Environment config is keyed by *where the code runs*. Tenant config is keyed by *who the request is for*, which is only known at request time. It is data, so it belongs in a database, with the same layering idea as section 5.5.

**Mechanism.** Resolve each key through a fixed chain: **code default, then plan default, then tenant override**, with the most specific value winning.

```ts title="tenant-config.ts"
import { z } from 'zod';

// every overridable key has a schema with bounds, so a tenant row can't hold a dangerous value
const TenantKeys = {
  uploadMaxMb:        z.number().int().min(1).max(100),
  sessionTimeoutMin:  z.number().int().min(5).max(24 * 60),
  ssoRequired:        z.boolean(),
} as const;
type Key = keyof typeof TenantKeys;

const CODE_DEFAULTS = { uploadMaxMb: 2, sessionTimeoutMin: 60, ssoRequired: false };
const PLAN_DEFAULTS: Record<string, Partial<typeof CODE_DEFAULTS>> = { free: {}, enterprise: { uploadMaxMb: 10 } };

export async function tenantConfig<K extends Key>(tenant: { id: string; plan: string }, key: K) {
  const override = await overrides.get(tenant.id);                     // cached row, see below
  const raw = override?.[key] ?? PLAN_DEFAULTS[tenant.plan]?.[key] ?? CODE_DEFAULTS[key];
  return TenantKeys[key].parse(raw) as z.infer<(typeof TenantKeys)[K]>;
}
```

**Edge cases.** Validate **on write** (the admin API that saves an override) and **on read**, because rows written before a schema change can still be out of bounds. Keep security-sensitive keys bounded (a tenant must not be able to set the session timeout to a year).

#### Caching and invalidation ➕
**Problem.** Reading the overrides table on every request adds a query to every request; caching it means a support engineer changes a limit and the customer still sees the old one.

**Mechanism.** Cache per tenant in memory with a short TTL (30–60 s), and on write publish an invalidation message (Redis pub/sub, or a `version` column that the cache compares) so instances drop the entry immediately. See [13-caching](/docs/backend-first-principles/13-caching) for invalidation patterns.

**Edge cases.** An unbounded in-memory cache with 50,000 tenants grows without limit; use an LRU with a size cap. If the overrides store is down, serve the cached value or the plan default, never fail the request.

#### Audit and blast radius ➕
**Problem.** "Why can tenant 42 upload 80 MB files?" Nobody knows who set it or when.

**Mechanism.** Store each override with `updated_by`, `updated_at` and a reason, and append every change to an audit table. Because one tenant's values can only affect that tenant, a bad override has a blast radius of one customer, which is the main operational advantage over a global value.

### 4.7 The rest 🎓
| Type | Examples |
|---|---|
| **Infra config** | everything DevOps owns: instance sizes, replicas, networking |
| **Security config** | JWT secret, session secret, anything security-related |
| **Performance tuning** | in Go, env vars like the maximum number of CPUs the runtime uses (`GOMAXPROCS`); 🔧 in Node, `UV_THREADPOOL_SIZE` or `--max-old-space-size` |
| **Business rules** | logic rules you enforce in the app but want to change centrally, e.g. max order amount |

## 5. Where config is stored 🎓

Where you store a value depends on **security, speed and environment**.

### 5.1 Environment variables (the most common)
- Environment variables are a **feature of the operating system**: every process gets a key-value map from its parent. You don't build this.
- **Locally**, a `.env` file plus a library (the famous one is **dotenv**) reads the file and loads the values into the process environment, so you don't run `export` by hand. Popular in Node, but available in Python, Go and others.
- **In deployed environments** (containers, Kubernetes, PaaS), the platform injects env vars when it starts your app.

**The deploy-time flow the lesson describes:**

  autonumber
  participant CI as Deploy pipeline
  participant SM as Secrets manager
  participant RT as Runtime (container / pod)
  participant App as Your app
  CI->>SM: fetch secrets for this environment
  SM-->>CI: values (over TLS)
  CI->>RT: start process with env vars set
  RT->>App: process starts, env is already populated
  App->>App: read env, build config, start serving`} />

🔧 **Node specifics:**
- Node 20.6+ can load a file natively: `node --env-file=.env dist/main.js` (the flag goes **before** the script). It's simpler than dotenv (no multi-line values or variable expansion).
- **Every env var is a string.** `process.env.ENABLE_X = "false"` is a non-empty string, so `if (process.env.ENABLE_X)` is **true**. That's one of the biggest reasons for the validation step in section 8.
- Commit a `.env.example` with keys and dummy values; put `.env` in `.gitignore`.

### 5.2 Files: JSON, YAML, TOML
- **JSON:** no comments, which is a real problem for config people need to understand.
- **YAML:** the popular choice because you can **comment** each value and share knowledge with the team.
- **TOML:** a newer format, also widely used.

**What the code tour shows:** the lesson opens two open-source projects.
- A Go authentication provider (it sounds like **Authelia**) keeps everything in one `configuration.yml`: server, log level (`debug`), storage, notifications, identity, regulation, session. Searching the repo turns up config files in many places.
- **Apache Incubator Answer** has fixed app settings in YAML: server port, the database (SQLite for local), Swagger UI config.

The takeaway: a YAML file is the norm in open-source projects for non-secret config.

### 5.3 Key-value stores
Lightweight and simple, and they behave much like environment variables (flat keys). Dedicated cloud-native tools exist, such as **Consul** and **etcd**.

🔧 Their real advantage is **watching**: the app can subscribe to a key and react when it changes, which is how runtime-changeable config (flags, rate limits) is usually delivered.

### 5.4 Cloud secret managers
**HashiCorp Vault**, **AWS Parameter Store** (and Secrets Manager), **Azure Key Vault**, **Google Secret Manager**.

Why companies use them: deployments are **distributed** (Kubernetes, autoscaling, sometimes several clouds at once). A central store that already supports all those environments, with docs and integrations, is easier than inventing your own. For serious production traffic it makes a lot of sense.

### 5.5 Hybrid: one loader, several sources, a fixed priority 🎓
In practice you combine sources. One module loads config at startup, pulls from several places, and builds the runtime settings object. You **decide in advance which source wins**, and you can load sources conditionally per environment. The lesson's example ordering: AWS Parameter Store first, then `config.yaml`, then environment variables.

🔧 **Implementation (TypeScript):**

```ts title="config/load.ts"
import { readFileSync, existsSync } from 'node:fs';
import { parse } from 'yaml';
import { SSMClient, GetParametersByPathCommand } from '@aws-sdk/client-ssm';
import { ConfigSchema, type AppConfig } from './schema';

function readYaml(path: string) {
  return existsSync(path) ? parse(readFileSync(path, 'utf8')) ?? {} : {};
}

// map flat env vars onto the nested shape: DB__POOL_MAX=50 -> db.poolMax
function fromEnv(env: NodeJS.ProcessEnv) {
  return {
    env: env.NODE_ENV,
    port: env.PORT,
    logLevel: env.LOG_LEVEL,
    db: { url: env.DATABASE_URL, poolMax: env.DB__POOL_MAX, statementTimeoutMs: env.DB__STATEMENT_TIMEOUT_MS },
    stripe: { secretKey: env.STRIPE_SECRET_KEY },
    jwt: { secret: env.JWT_SECRET },
    features: { newCheckout: env.FEATURE_NEW_CHECKOUT },       // always present, so inner defaults apply
  };
}

async function fromParameterStore(prefix: string) {
  const ssm = new SSMClient({});
  const out: Record<string, string> = {};
  let NextToken: string | undefined;
  do {                                                          // paginated
    const page = await ssm.send(new GetParametersByPathCommand({ Path: prefix, WithDecryption: true, Recursive: true, NextToken }));
    for (const p of page.Parameters ?? []) out[p.Name!.slice(prefix.length)] = p.Value!;
    NextToken = page.NextToken;
  } while (NextToken);
  return { db: { url: out['DATABASE_URL'] }, stripe: { secretKey: out['STRIPE_SECRET_KEY'] }, jwt: { secret: out['JWT_SECRET'] } };
}

// deep merge where undefined never overwrites a real value
function merge(...layers: any[]): any {
  const result: any = {};
  for (const layer of layers) {
    for (const [k, v] of Object.entries(layer ?? {})) {
      if (v === undefined) continue;
      result[k] = v && typeof v === 'object' && !Array.isArray(v) ? merge(result[k], v) : v;
    }
  }
  return result;
}

export async function loadConfig(): Promise<AppConfig> {
  const envName = process.env.NODE_ENV ?? 'development';
  const layers = [
    readYaml('config/config.yaml'),
    readYaml(`config/config.${envName}.yaml`),
    fromEnv(process.env),
  ];
  if (envName === 'production') layers.push(await fromParameterStore(`/shop/${envName}/`)); // conditional source

  const parsed = ConfigSchema.safeParse(merge(...layers));
  if (!parsed.success) {
    console.error('Invalid configuration:\n' + parsed.error.issues.map(i => `  ${i.path.join('.')}: ${i.message}`).join('\n'));
    process.exit(1);                                           // fail fast, before serving traffic
  }
  return Object.freeze(parsed.data);
}
```

Edge cases:
- **Document the precedence** in the README. "Why is prod using pool size 10?" is answered by knowing which layer won.
- Make `undefined` never overwrite a value (as above), or an unset env var wipes the YAML value.
- At boot, **log the final config with secrets redacted**. When debugging, you'll know exactly what the process ran with, which is the "can't reproduce" problem from section 3.

## 6. Why config differs per environment 🎓

The code is the same in every environment; **each environment has different priorities**, so the config values differ.

| Environment | Number one priority | Typical config consequences |
|---|---|---|
| **Development** (localhost) | developer productivity, debugging | `debug` logs, pretty console output, local DB |
| **Test** (e.g. a GitHub Actions run) | automated validation, quality assurance | throwaway DB, fake external services, deterministic settings |
| **Staging** | behave as much like production as possible | same shape of config as prod, but cheaper |
| **Production** | reliability, security, performance | `info` logs, JSON output, real secrets, tuned pools |

That's the payoff of centralised config: **behaviour changes without touching application code**. With hard-coded values you'd have to edit and redeploy code.

### The pool-size example 🎓
- **Dev: max pool 10.** Plenty on a modern laptop while you develop and test.
- **Prod: max pool 50.** A large user base and traffic spikes.
- **Staging: max pool 2.** Staging should mirror prod, but a full copy costs as much as prod. Only developers and testers use it, so the team accepts a bit of latency to **save cloud cost**. Staging has a second priority: minimise cost.

🔧 **Pool size has a hard upper bound you must calculate.** Postgres has a `max_connections` limit for the whole server. If prod runs 8 pods with pool 50, that's 400 connections. Exceed the server limit and new connections fail. So: `pods × poolMax + other clients ≤ max_connections` (with headroom), or put a pooler like PgBouncer in front. Autoscaling makes this worse: more pods means more connections, so set pool size with the **max replica count** in mind.

🔧 **Kubernetes way to supply per-env values:** non-secret values in a `ConfigMap`, secrets in a `Secret` (or synced from a secrets manager), both injected as env vars. The image stays identical across environments; only these objects differ.

```yaml title="deployment.yaml (excerpt)"
envFrom:
  - configMapRef: { name: shop-api-config }     # LOG_LEVEL, DB__POOL_MAX, ...
  - secretRef:    { name: shop-api-secrets }    # DATABASE_URL, STRIPE_SECRET_KEY, JWT_SECRET
```

Note that env vars from a ConfigMap are read only when the container starts: changing the ConfigMap does nothing until the pods restart.

## 7. Security 🎓

### 7.1 Never hard-code secrets
Production DB URL, Clerk key, email provider key, payment key: never in the codebase. Git history keeps them forever, everyone with repo access sees them, and they ship inside builds.

🔧 If a secret was ever committed, **rotate it**. Deleting the line doesn't remove it from history. Add a secret scanner (for example gitleaks) to CI and pre-commit.

### 7.2 Prefer a cloud secrets manager
Vault, AWS Parameter Store, Azure Key Vault, Google Secret Manager. The lesson says it's fine to over-engineer security here. These services handle:
- **encryption at rest**: values are encrypted before they're stored, wherever they're stored;
- **encryption in transit** when you fetch them.

🔧 A precision note on "in transit": with these services the transport is **TLS**, and access is controlled by **authenticating the caller** (an IAM role, a Kubernetes service account, a Vault token). The service decrypts with its own managed keys (KMS) and returns the value over TLS to an authorised caller. What you protect on your side is the **identity** that's allowed to read, not a private key that decrypts the payload.

### 7.3 Access control: least privilege
In a larger team, decide who can see what:
- **Frontend engineers:** only what the frontend needs (the backend API URL, public keys for frontend integrations).
- **Backend engineers:** databases, Redis, Elasticsearch and similar.
- **DevOps only:** credentials for cloud infrastructure (e.g. EC2 access).

🔧 Apply the same rule to **services**: the API's runtime role can read `/shop/prod/api/*`, not the billing worker's secrets.

### 7.4 Rotation
Rotate API keys, secrets and JWT secrets periodically so a leaked value has a limited lifetime.

🔧 **How to rotate without logging everyone out.** If you replace the JWT secret in one step, every existing token fails verification instantly. Use a **key ID** and accept two keys during an overlap window:

```ts title="jwt-keys.ts"
import jwt from 'jsonwebtoken';

// config.jwt.keys = { "2026-09": "old-secret", "2026-10": "new-secret" }, config.jwt.activeKid = "2026-10"
export function sign(payload: object) {
  const kid = config.jwt.activeKid;
  return jwt.sign(payload, config.jwt.keys[kid], { keyid: kid, expiresIn: '15m' });
}

export function verify(token: string) {
  const decoded = jwt.decode(token, { complete: true });
  const kid = decoded?.header.kid;
  const key = kid ? config.jwt.keys[kid] : undefined;
  if (!key) throw new Error('unknown signing key');
  return jwt.verify(token, key);
}
// rotation: 1) add the new key  2) make it active  3) wait longer than the token lifetime  4) remove the old key
```

Database passwords rotate the same way: create the new credential, roll it out, then revoke the old one. Never an in-place swap.

### 7.5 Rotating secrets inside running processes ➕

The JWT example works because your own code controls both keys. With credentials issued by **someone else** (the database, Stripe, a cloud provider) you also have to answer: how do processes that are already running pick up the new value?

#### Why a running process keeps the old secret ➕
**Problem.** The secrets manager rotates the DB password at 03:00. At 03:00:01 new connections from every pod fail authentication, even though the new password is sitting in the secrets manager.

**Why it happens.** Section 5 loads config **once at startup** into a frozen object, and env vars are copied into the process when it starts. Nothing tells the process that the source changed. Existing pooled connections keep working (Postgres checks the password only when a connection is opened), which hides the problem until the pool opens a new connection.

**Mechanism.** Two things together: the credential itself must be rotated so that **old and new are both valid for a while**, and the app must **re-read** the secret before the old one is revoked.

#### Alternating users: two valid credentials at all times ➕
**Problem.** "Single-user" rotation changes the password of the one DB user in place. Between the change and every pod re-reading it, connections fail.

**Mechanism.** AWS Secrets Manager's **alternating-users** strategy keeps two DB users (`app_a`, `app_b`). Each rotation updates the password of the user that is **not** currently in use, then switches the secret to point at it. The rotation tracks versions with staging labels: the new version is created as `AWSPENDING`, tested, then promoted to `AWSCURRENT`, and the old one becomes `AWSPREVIOUS` and still works.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant R as Rotation job
  participant SM as Secrets manager
  participant DB as Postgres
  participant App as App pods
  App->>SM: read AWSCURRENT (user app_a)
  R->>DB: set new password for app_b (not in use)
  R->>SM: store as AWSPENDING, test login
  R->>SM: promote: app_b is AWSCURRENT, app_a is AWSPREVIOUS
  Note over App: pods still using app_a keep working
  App->>SM: cache TTL expires, re-read AWSCURRENT
  App->>DB: new connections log in as app_b`} />

**Edge cases.** Both users need identical grants, and objects they create must be owned by a shared role, or tables created by `app_a` are unreadable by `app_b`. The rotation interval must be longer than your secret cache TTL, or a pod can still be using a user whose password just changed again.

#### Re-reading secrets in Node: TTL cache plus refresh on auth failure ➕
**Mechanism.** Wrap the secret in a small cache with a TTL, and when the database rejects a login, force a refresh once and rebuild the pool.

```ts title="db-credentials.ts"
import { SecretsManagerClient, GetSecretValueCommand } from '@aws-sdk/client-secrets-manager';
import { Pool } from 'pg';

const sm = new SecretsManagerClient({});
let cached: { value: { username: string; password: string }; at: number } | null = null;
const TTL_MS = 5 * 60_000;

async function getCreds(force = false) {
  if (!force && cached && Date.now() - cached.at < TTL_MS) return cached.value;
  const out = await sm.send(new GetSecretValueCommand({ SecretId: config.db.secretId }));   // AWSCURRENT by default
  cached = { value: JSON.parse(out.SecretString!), at: Date.now() };
  return cached.value;
}

let pool = await buildPool();
async function buildPool() {
  const { username, password } = await getCreds();
  return new Pool({ host: config.db.host, user: username, password, max: config.db.poolMax });
}

export async function query(sql: string, params: unknown[]) {
  try {
    return await pool.query(sql, params);
  } catch (err: any) {
    if (err.code !== '28P01') throw err;                  // 28P01 = invalid_password in Postgres
    await getCreds(true);                                  // credentials rotated under us
    const old = pool;
    pool = await buildPool();
    old.end().catch(() => {});                             // let borrowed clients finish, then close
    return pool.query(sql, params);                        // retry once, never in a loop
  }
}
```

**Edge cases.**
- Many pods hitting auth failures at once all call the secrets manager at the same moment; add jitter to the TTL so refreshes spread out, and respect its API rate limits.
- Retry **once**. A loop turns a genuinely wrong password into a tight loop of failed logins, which can trip lockout or alerting on the database side.
- Never log the fetched value; log the version ID instead.

#### Kubernetes: mounted files update, env vars don't ➕
**Problem.** The secret is synced into a Kubernetes `Secret`, but pods still use the old value.

**Why it happens.** Kubernetes copies env vars into the container at start, so values from a ConfigMap or Secret consumed as env vars **never change until the pod restarts**. Values mounted as a **volume** are updated in place by the kubelet after a delay (its sync period plus cache propagation), except when mounted with `subPath`, which never updates.

**Mechanism.** Pick one of two patterns deliberately:
- **Mount as files and watch them**: read the file on each refresh instead of `process.env`, so the TTL cache above picks up the new value with no restart.
- **Restart on change**: put a hash of the secret in a pod template annotation (Helm's `checksum/config` pattern, or a controller such as Reloader). A changed hash changes the pod template, so Kubernetes does a normal rolling update with graceful shutdown (see [19-graceful-shutdown](/docs/backend-first-principles/19-graceful-shutdown)).

```yaml title="deployment.yaml (excerpt, Helm)"
template:
  metadata:
    annotations:
      checksum/secrets: {{ include (print $.Template.BasePath "/secret.yaml") . | sha256sum }}
```

**Edge cases.** The volume approach updates files with a symlink swap; a watcher on the file path itself can miss it, so watch the directory or simply re-read on a timer.

## 8. Validation: the most important takeaway 🎓

### Problem
A common pattern: load `.env`, then read `process.env.SOMETHING` wherever needed. Nobody checks the values. A **required variable missing in production** doesn't crash on boot. It shows up later as a strange failure (an `undefined` URL, a `NaN` timeout, a feature silently off), and it's hard to trace back to config. The lesson's author learned this the hard way.

### Mechanism
Validate **every config value, from every source** (Parameter Store, YAML, env) **at startup, before the app serves traffic**, with a real validation library: **zod** in TypeScript, **go-playground/validator** in Go. Decide for each value whether it's **required**, **optional**, or has a **default** in code. If anything is invalid, **refuse to start**.

Why that's the right place: a deployment that can't boot is caught by the orchestrator's health checks and never receives traffic (the old version keeps serving). A deployment that boots with bad config **does** receive traffic and fails for real users.

<Mermaid chart={`flowchart LR
  L["Load all sources"] --> V{"Schema valid?"}
  V -->|no| E["Print every bad key<br/>exit 1"]
  E --> K["Pod never ready<br/>old version keeps serving"]
  V -->|yes| T["Typed config<br/>(numbers are numbers,<br/>booleans are booleans)"]
  T --> S["Start server"]`} />

🔧 **Implementation:**

```ts title="config/schema.ts"
import { z } from 'zod';

const bool = z.enum(['true', 'false']).transform(v => v === 'true');   // "false" really becomes false

export const ConfigSchema = z.object({
  env: z.enum(['development', 'test', 'staging', 'production']).default('development'),
  port: z.coerce.number().int().min(1).max(65535).default(8080),
  logLevel: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  requestTimeoutMs: z.coerce.number().int().positive().default(60_000),
  db: z.object({
    url: z.string().url(),                                              // required: no default
    poolMax: z.coerce.number().int().min(1).max(200).default(10),
    statementTimeoutMs: z.coerce.number().int().positive().default(5_000),
  }),
  stripe: z.object({ secretKey: z.string().startsWith('sk_') }),
  jwt: z.object({ secret: z.string().min(32, 'JWT secret must be at least 32 chars') }),
  features: z.object({ newCheckout: bool.default('false') }),
}).superRefine((c, ctx) => {
  // cross-field rules: things a per-field check can't see
  if (c.env === 'production' && c.stripe.secretKey.startsWith('sk_test_'))
    ctx.addIssue({ code: 'custom', path: ['stripe', 'secretKey'], message: 'test key in production' });
  if (c.env === 'production' && c.logLevel === 'debug')
    ctx.addIssue({ code: 'custom', path: ['logLevel'], message: 'debug logging in production' });
});

export type AppConfig = z.infer<typeof ConfigSchema>;
```

```ts title="main.ts"
const config = await loadConfig();         // exits if invalid
logger.info({ config: redact(config) }, 'config loaded');
const app = await createApp(config);       // pass config in; never read process.env deeper in the code
await app.listen(config.port);
```

🔧 **NestJS:** `ConfigModule.forRoot({ validate: (raw) => ConfigSchema.parse(...) })` runs the same check at bootstrap, and you inject a typed config service instead of touching `process.env`.

Edge cases:
- **Report all errors at once**, not one per deploy attempt.
- `z.coerce.number()` turns an empty string into `0`; for values where 0 is invalid, add `.positive()` as above.
- Validate **runtime-reloaded** values too (flags, business rules). A bad push should be rejected and the last good value kept.

### Safe defaults vs fail-fast: deciding which values may default ➕

Validation forces a decision for every key: required, optional or defaulted. The lesson says to make it; this is how to make it well.

#### The dangerous default ➕
**Problem.** The schema above has `env: ... .default('development')`. If a production deployment forgets to set `NODE_ENV`, the app boots happily as **development**: debug logging, pretty output, maybe a local mock payment client. Validation passed because the default filled the gap.

**Why it happens.** A default turns "missing" into "valid". That's helpful when the default is correct everywhere, and harmful when the default is only correct on a laptop. Developers pick defaults that make local setup easy, which are exactly the wrong values for production.

**Mechanism.** One rule: **a value may have a default only if that default is safe in production.** Everything else is required, or has a default that is applied only outside production.

| Value | Default? | Why |
|---|---|---|
| port, log format, request timeout | yes | same safe value everywhere |
| `NODE_ENV` / environment name | **no** in deployed environments | a wrong default silently changes many behaviours |
| DB URL, API keys, JWT secret | **no** | a default secret is a known secret |
| TLS verification, CORS origins, cookie `secure` flag | default to the **strict** value | the permissive value must be an explicit choice |
| pool size, cache TTL | yes, conservative | too small is slow, too large can exhaust the DB |

```ts title="config/schema.ts (excerpt)"
const isDeployed = process.env.DEPLOYED === 'true';            // set by the platform, never by developers

const EnvName = z.enum(['development', 'test', 'staging', 'production']);
export const env = isDeployed ? EnvName : EnvName.default('development');   // required when deployed

export const http = z.object({
  corsOrigins: z.array(z.string().url()).default([]),           // strict: nothing allowed unless listed
  tlsRejectUnauthorized: bool.default('true'),                  // turning it off must be explicit
});
```

**Edge cases.** Code defaults, YAML base values and env vars can all "default" the same key; keep each default in one layer only, or the precedence from section 5.5 becomes impossible to reason about.

### Config as code: review, CI tests and drift detection ➕

Startup validation catches bad config when a pod boots, which is already in a real environment. The cheaper place to catch it is the pull request.

#### Validate every environment's config in CI ➕
**Problem.** Someone edits `config.production.yaml` and sets `poolMax: "fifty"`. Nothing fails until the production deploy, where the new pods crash-loop on validation.

**Why it happens.** Validation runs where the config is loaded, and production config is only loaded in production.

**Mechanism.** Run the **same schema** against every environment's files in CI, with fake values standing in for secrets (CI should never hold production secrets).

```ts title="scripts/check-config.ts"
import { ConfigSchema } from '../src/config/schema';
import { readYaml, merge } from '../src/config/load';        // export these two helpers from load.ts

const FAKE_SECRETS = {
  db: { url: 'postgres://ci:ci@localhost:5432/ci' },
  stripe: { secretKey: 'sk_live_ci_placeholder' },
  jwt: { secret: 'x'.repeat(32) },
};

let failed = false;
for (const env of ['development', 'test', 'staging', 'production']) {
  const merged = merge(readYaml('config/config.yaml'), readYaml(`config/config.${env}.yaml`), { env }, FAKE_SECRETS);
  const result = ConfigSchema.safeParse(merged);
  if (!result.success) {
    failed = true;
    console.error(`[${env}]`, result.error.issues.map(i => `${i.path.join('.')}: ${i.message}`).join('; '));
  }
}
process.exit(failed ? 1 : 0);
```

**Edge cases.** The fake secrets must satisfy the same rules as real ones (the production cross-field check rejects `sk_test_`, hence the placeholder shape). This check proves the shape is valid, not that the values are right; the canary deploy still has to prove that.

#### Drift between environments ➕
**Problem.** Staging works, production breaks, and the cause is a key that exists in staging's config but not production's, or was set by hand in the cloud console months ago.

**Why it happens.** Every environment is edited separately, often by different people, and manual changes in a console leave no trace in Git. Over time the environments stop having the **same set of keys**, which is the real meaning of drift (values are supposed to differ; keys are not).

**Mechanism.**
- **Key parity check in CI**: load each environment's merged config and compare the key sets. A key present in one environment but missing from another fails the build unless it's on an explicit allow-list.
- **GitOps for infrastructure config**: tools such as Argo CD compare the live Kubernetes objects (ConfigMaps, Deployments) with Git and mark the app *OutOfSync* when someone edits the cluster by hand; with `selfHeal` enabled they revert the manual change.
- **Secrets managers**: compare the list of parameter **names** under `/shop/staging/` and `/shop/prod/` on a schedule (names, never values) and alert on differences.

```ts title="scripts/check-key-parity.ts"
const keys = (o: object, p = ''): string[] =>
  Object.entries(o).flatMap(([k, v]) => (v && typeof v === 'object' && !Array.isArray(v) ? keys(v, `${p}${k}.`) : [`${p}${k}`]));

const ENV_ONLY_KEYS = new Set(['debug.sqlLogging']);           // keys that may legitimately exist in one env only

// byEnv: { development: mergedConfig, staging: mergedConfig, ... } built as in check-config.ts
export function findDrift(byEnv: Record<string, object>) {
  const keySets = Object.fromEntries(Object.entries(byEnv).map(([env, cfg]) => [env, new Set(keys(cfg))]));
  const all = new Set(Object.values(keySets).flatMap(s => [...s]));
  const problems: string[] = [];
  for (const key of all) {
    if (ENV_ONLY_KEYS.has(key)) continue;
    for (const [env, set] of Object.entries(keySets)) if (!set.has(key)) problems.push(`${env} is missing ${key}`);
  }
  return problems;                                               // non-empty fails the build
}
```

**Edge cases.** Defaults in code hide drift: a key "missing" from production YAML may be intentionally defaulted. Compare the **merged** config, not the raw files.

#### Review and audit: who changed what, and when ➕
**Problem.** A config change in production caused an outage. Who made it, what was the previous value, and how do you roll back?

**Mechanism.**
- Keep non-secret config in Git and require review for production files with a `CODEOWNERS` entry (for example `config/config.production.yaml @platform-team`). Rollback becomes `git revert` plus a deploy.
- For secrets managers, rely on their audit trail: AWS records Parameter Store and Secrets Manager API calls (who called `PutParameter`, when) in CloudTrail, and Vault has audit devices. Versioned parameters let you see and restore the previous value.
- Ship config changes like code: one environment at a time, staging before production, watching error rates in between.

**Edge cases.** Emergency changes made directly in a console during an incident are normal; the rule is that they get written back to Git afterwards, otherwise the next deploy silently reverts the fix.

## 9. 🔧 Going deeper: topics beyond the lesson

### 9.1 The Twelve-Factor rule
Twelve-Factor's config factor says: config is everything that **varies between deploys**, and it should live **in the environment, not in code**. The test: could you open-source the repo right now without leaking a credential? If not, config is mixed into code.

### 9.2 Build-time vs runtime config
Frontend bundlers inline env vars **at build time** (e.g. variables prefixed for the client). Anything inlined is public and baked into that image. Backends should read config **at runtime**, so one image can be promoted from staging to prod unchanged. If your Docker image has to be rebuilt per environment, config has leaked into the build.

### 9.3 Runtime reload
Startup-only config needs a restart to change, which is fine for DB URLs. Flags and business rules need hot reload: poll or watch the store, validate the new value, swap an in-memory reference atomically, and keep the last good value if the store is unreachable.

### 9.4 Dynamic reload and its risks ➕

The previous paragraph says *how* to hot reload. Hot reload also introduces failure modes that startup-only config can't have, and these are worth knowing before you make a value reloadable.

#### Inconsistency inside one request ➕
**Problem.** A checkout handler reads `maxOrderAmount` at the start to validate the cart, and again later to decide whether manual review is needed. A reload lands in between, so one request sees two different limits and takes a path that neither config allows.

**Why it happens.** A request is a sequence of reads spread over time. If each read goes to "the current config", any reload during the request splits it across two versions.

**Mechanism.** Give each request a **snapshot**: capture the current config object once when the request starts and read only from it. Since each reload builds a new frozen object and swaps one reference, holding the old reference is free.

```ts title="config/live.ts"
import { AsyncLocalStorage } from 'node:async_hooks';

let current: Readonly<RuntimeConfig> = await loadRuntimeConfig();       // validated + frozen
const requestSnapshot = new AsyncLocalStorage<Readonly<RuntimeConfig>>();

export function onReload(next: unknown) {
  const parsed = RuntimeConfigSchema.safeParse(next);
  if (!parsed.success) { logger.error({ issues: parsed.error.issues }, 'rejected config push'); return; }
  current = Object.freeze(parsed.data);                                  // one reference swap, atomic in JS
  logger.info({ version: current.version }, 'config reloaded');
}

export const snapshotMiddleware = (_req, _res, next) => requestSnapshot.run(current, next);
export const cfg = () => requestSnapshot.getStore() ?? current;         // same object for the whole request
```

**Edge cases.** Long-lived work (a 20-minute export job) holds an old snapshot for its whole life; decide whether that's correct or whether the job should re-read at checkpoints.

#### Not every value can be reloaded ➕
**Problem.** Someone changes `db.poolMax` in the dynamic store, the app logs "config reloaded", and nothing changes.

**Why it happens.** Some values are consumed once to **build an object**: the pool size when the pool is created, the port when the server binds, the log level when the logger is built. Updating the number afterwards doesn't rebuild the object.

**Mechanism.** Mark every key as either `reloadable` or `restart-required` in the schema, and refuse (or warn loudly about) dynamic changes to restart-required keys. For a reloadable key that feeds an object, reload must also **rebuild** it: pino supports changing `logger.level` at runtime, for example, while a pg pool must be replaced as in section 7.5.

**Edge cases.** Rebuilding resources under load (a new pool) briefly doubles connections to the database; check the `max_connections` budget from section 6.

#### A config push is a deploy ➕
**Problem.** A bad rate-limit value pushed to the dynamic store reaches **every instance within seconds**. A bad code deploy, by comparison, goes through a rolling update, canary and health checks.

**Why it happens.** Hot reload removes the rollout machinery that protects code deploys. Schema validation catches values that are malformed, but a well-formed wrong value (rate limit 10 instead of 10,000) passes validation and still breaks production.

**Mechanism.** Give risky dynamic keys the same safety as deploys:
- **Staged rollout of the value**: apply it to one region, cell or percentage of instances first (the same hashing idea as section 4.4, keyed on instance ID), watch error rates, then widen.
- **Change limits**: reject pushes that move a value by more than a set factor (for example more than 10x) without an explicit override.
- **One-step rollback**: keep the previous versions in the store so "revert" is a single action.

**Edge cases.** During a staged rollout the fleet intentionally runs two configs; logs and traces should carry the config `version`, so a spike can be tied to the instances running the new value.

### 9.5 Never log secrets
Structured loggers can redact paths (`db.url`, `*.secretKey`, `authorization` headers). Config dumps, error messages that include connection strings and crash reports are the usual leak paths.

## 10. Recap 🎓

- Config management is the systematic handling of **all** settings, not just secrets. It's the app's DNA: the same code behaves differently because of config.
- Values differ in **sensitivity, change frequency and environment dependence**, and that decides where they're stored.
- In distributed systems, without a system you get **config chaos**: scattered hard-coded values, inconsistent environments, leaked secrets, unreproducible bugs. Backend misconfig is far more damaging than frontend misconfig.
- **Types:** app settings, DB, external services, feature flags, infra, security, performance tuning, business rules.
- **Sources:** env vars (most common), YAML/JSON/TOML files, key-value stores (Consul, etcd), cloud secret managers (Vault, Parameter Store, Key Vault, Secret Manager), usually combined with a **defined priority**.
- **Environments** have different priorities (dev productivity, test validation, staging fidelity at low cost, prod reliability), hence different values (pool 10 / 2 / 50).
- **Security:** never hard-code secrets, use a secrets manager, least-privilege access, rotate.
- **Always validate config at startup**, whatever the source. If you take one thing from the lesson, take this.
- ➕ **Kill switches** are long-lived ops flags around optional dependencies, with a safe default per switch and a known propagation delay; release flags get an owner and an expiry enforced in CI.
- ➕ **Per-tenant config** resolves code default, then plan, then tenant override, with bounded schemas, a short cache plus invalidation, and an audit trail.
- ➕ **Rotating third-party secrets** needs two valid credentials at once (alternating users, staging labels) and an app that re-reads secrets (TTL cache, refresh on auth failure). Env vars from Kubernetes objects only change on restart; mounted volumes update in place.
- ➕ **Defaults** are allowed only when they are safe in production; secrets and the environment name must be required, and security settings default to strict.
- ➕ **Config as code**: validate every environment's config in CI, check key parity to catch drift, require review on production files and keep an audit trail.
- ➕ **Hot reload** needs per-request snapshots, a list of restart-only keys, and the same staged rollout and rollback as a code deploy.

## Interview questions

1. **What does configuration management cover beyond secrets?** **Startup and connection behaviour, per-environment behaviour, logging, metrics destinations, feature flags, timeouts, pool sizes, business rules.**
2. **Why is backend misconfiguration more dangerous than frontend misconfiguration?** **It can leak customer data, mis-process payments or take the platform down; frontend misconfig usually shows the wrong UI.**
3. **A request takes 80 s and the server timeout is 60 s. What does the client see, and how do you fix it?** **504 Gateway Timeout. Raise the timeout (consistently across every hop) or, better, move the work to a background job and poll or notify.**
4. **How do you decide where a config value lives?** **By sensitivity (secret → secrets manager), change frequency (runtime → flag or KV store) and environment dependence (per-env → env var or override file; shared → defaults).**
5. **Why do staging and prod use different pool sizes if staging should mirror prod?** **Staging also optimises for cost; it gets few users, so a small pool is acceptable. 🔧 And pool size × replicas must stay under the DB's connection limit.**
6. **Why is `if (process.env.FEATURE)` a bug?** **Env vars are strings; "false" is truthy. Parse and validate into real booleans at startup.**
7. **Why validate config at startup instead of when a value is used?** **A pod that can't boot never gets traffic, so the old version keeps serving; a pod with bad config fails for real users later, far from the cause.**
8. **How do you rotate a JWT secret without logging everyone out?** **Key IDs: verify with old and new keys, sign with the new one, remove the old one after the token lifetime has passed.**
9. **How do you roll a feature out to 25% of US users consistently?** **Filter by country, then hash flag key + user ID into 0–99 and enable if the bucket is under 25. The same user always gets the same result.**
10. **What does a secrets manager give you over a `.env` file on a server?** **Encryption at rest, TLS in transit, central access control and audit, rotation support and one source for every environment and cloud.**
11. ➕ **How is a kill switch different from a rollout flag, and what should it default to when the flag store is unreachable?** **A kill switch is a long-lived ops flag that lets on-call disable an optional dependency without a deploy. Each switch defaults to its own safe direction (normal behaviour for an optional widget, off for a risky new path), and instances keep the last good snapshot.**
12. ➕ **The secrets manager rotated the DB password and new connections fail. What went wrong, and how do you design rotation to avoid it?** **The app read the secret once at startup and the old password stopped working immediately. Use alternating users so the previous credential stays valid, re-read secrets with a TTL cache, and refresh once on an auth failure.**
13. ➕ **You updated a Kubernetes Secret but pods still use the old value. Why?** **Env vars are set at container start and never update; only volume mounts (not `subPath`) are refreshed by the kubelet. Restart via a checksum annotation or read the mounted file.**
14. ➕ **Why is `NODE_ENV` defaulting to `development` a production risk?** **A missing variable silently becomes a valid development config (debug logging, dev clients). Values whose default is unsafe in production must be required in deployed environments.**
15. ➕ **How do you catch config drift between staging and production?** **Compare the key sets of each environment's merged config in CI, use GitOps drift detection for cluster objects, and compare secret names (not values) between environments.**
16. ➕ **Why can hot-reloading config be more dangerous than deploying code?** **A pushed value reaches every instance at once, skipping canaries and health checks. Snapshot config per request, validate pushes, roll values out gradually and keep one-step rollback.**
