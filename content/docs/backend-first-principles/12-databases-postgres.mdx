## 1. Why databases exist: persistence 🎓

### Problem
A program's variables live in memory. When the process stops (you close the app, the server restarts, the container is redeployed), that memory is gone. The lesson's example is a **to-do app**: you add items, tick some off, close the app, and you expect to see exactly that state when you open it again, maybe days later or on another device. Without persistence, every launch would start from an empty list.

### Definition
**Persistence** means storing data so that it **outlives the program that created it** and comes back in the same, expected state, across time and across locations.

### What counts as a "database"?
The word is very broad. In the loosest sense, **any structured storage** is a database:
- the **contact list** on your phone,
- the browser's **localStorage**, **sessionStorage** and **cookies** (the lesson opens DevTools on Excalidraw and shows the key–value entries it saved),
- even a **text file** of notes.

The common pattern: a persistent system that lets you **Create, Read, Update and Delete** data (CRUD).

## 2. Why backend databases live on disk 🎓

In backend work, "database" almost always means a **disk-based** database (HDD or SSD), not RAM.

| | RAM (primary memory) | Disk (secondary memory, HDD or SSD) |
|---|---|---|
| Speed | Very fast | Much slower |
| Typical size on a machine | 8–128 GB | 512 GB – 2 TB and more |
| Cost per GB | High | Low |
| Survives power loss | No | Yes |

**The trade-off a database makes:** it needs **a lot of space** and **durability**, and it can accept some loss of speed. So traditional databases (relational ones like Postgres and non-relational ones like MongoDB) store their data on **disk**.

**Where RAM comes in:** when speed matters more than capacity, we use a **cache** (Redis or an in-process cache) that keeps hot data in memory. That's why caching and databases are separate layers.

<Mermaid chart={`flowchart LR
  API["Backend"] -->|"hot data, microseconds"| C[("Cache in RAM<br/>Redis, in-memory")]
  API -->|"source of truth, milliseconds"| DB[("Postgres on disk")]
  C -. "miss: read from DB, then fill cache" .-> DB`} />

The lesson deliberately skips *how* a database lays bytes out on disk (pages, storage algorithms). For a backend engineer, the important part is knowing which layer is fast and which is durable.

🔧 **How Postgres gets speed from a slow disk anyway:** it reads and writes in fixed **8 KB pages**, keeps recently used pages in a RAM area called **shared buffers**, and makes commits durable by appending to a sequential **write-ahead log (WAL)** before touching the table files. Sequential appends are cheap even on spinning disks, and the data pages can be flushed later.

## 3. What a DBMS does 🎓

Storing bytes on disk isn't enough. You need software that makes **CRUD efficient over hundreds of gigabytes**. That software is a **Database Management System (DBMS)**. Its core responsibilities:

1. **Data organization:** lay data out so that reads, writes and updates stay fast as the data grows.
2. **Access:** offer CRUD operations to clients.
3. **Integrity:** keep the data **accurate, valid and consistent**. The lesson's example: an e-commerce `orders` table stores the payment amount as a number. If someone tries to put a string like `'something'` into that column, the DBMS must **reject** it.
4. **Security:** protect data from unauthorized access, with users, roles and permissions.

It also handles scaling, replication, load balancing and more, but those four are the foundation.

```sql
-- 🔧 Integrity enforced by the DBMS, not by your code
CREATE TABLE orders (id bigint PRIMARY KEY, amount numeric(10,2) NOT NULL);
INSERT INTO orders VALUES (1, 'something');
-- ERROR:  invalid input syntax for type numeric: "something"
```

## 4. Why not just use text files? 🎓

Before DBMSs, people stored data in plain files. The lesson names three problems. Each one maps to a mechanism a real database provides.

### 4.1 Parsing
- **Problem:** to find one customer, your application has to read the file, split it into lines, split each line into fields, and compare every field. That's **slow** (especially in JavaScript, Python or Ruby compared to Rust) and **error-prone**: a parsing bug can corrupt data or return wrong information to customers.
- **Why it happens:** a text file has no index and no query engine, so every lookup is a **full scan done by your code**.
- **What a DBMS does instead:** it stores rows in a binary format it already understands, keeps **indexes** (section 13) to jump straight to matching rows, and runs the search **inside the database** close to the data. You just describe what you want in SQL.

### 4.2 No structure
- **Problem:** a text file accepts anything in any format. You **can't enforce** "this field is always a number".
- **What a DBMS does instead:** a **schema** with **types** and **constraints** (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys) that are checked on every write.

### 4.3 Concurrency: the lost update
The lesson's example: a file holds `amount = 40`. Two people edit it at the same time. One wants **+20**, the other **−20**. The correct final value is **40**.

<Mermaid chart={`sequenceDiagram
  participant A as User A (+20)
  participant F as amount.txt
  participant B as User B (-20)
  A->>F: read amount
  F-->>A: 40
  B->>F: read amount
  F-->>B: 40
  A->>A: compute 40 + 20 = 60
  B->>B: compute 40 - 20 = 20
  A->>F: write 60
  B->>F: write 20
  Note over F: final value 20 (or 60 if the order flips)<br/>correct answer is 40, one update is lost`} />

- **Why it happens (first principles):** each user does **read → compute → write** as three separate steps. Nothing stops the other user from reading the **old** value between someone's read and write. The last writer silently overwrites the other's work, and *which* write lands last depends on CPU scheduling, so the result isn't even predictable.
- **What you need:** some way to make read-compute-write behave as **one indivisible step** for a given piece of data, or to detect that someone else got there first. A text file can't do that.

🔧 **The mechanisms Postgres gives you** (in order of preference):

**Fix 1: let the database do the arithmetic (atomic update).** Don't read the value into your app at all. A single `UPDATE` reads and writes the row while holding a **row lock**, so concurrent updates queue up behind each other.

```sql
UPDATE accounts SET amount = amount + 20 WHERE id = 1;   -- user A
UPDATE accounts SET amount = amount - 20 WHERE id = 1;   -- user B, waits for A's row lock, then applies to 60
-- final: 40
```

In the default isolation level (**Read Committed**), when B's `UPDATE` finds a row that A is changing, it **waits** for A to commit, then **re-reads the new version** of the row and applies its change to that. That's why `amount = amount - 20` is safe.

**Fix 2: when the app must compute, lock the row first (pessimistic).**

```sql
BEGIN;
SELECT amount FROM accounts WHERE id = 1 FOR UPDATE;   -- B blocks here until A commits
-- app computes the new value
UPDATE accounts SET amount = $1 WHERE id = 1;
COMMIT;
```

**Fix 3: detect the conflict instead of blocking (optimistic).** Add a `version` column and only write if nobody changed it since you read it.

```sql
UPDATE accounts SET amount = $1, version = version + 1
WHERE id = 1 AND version = $2;    -- 0 rows updated means someone else won: re-read and retry
```

<Mermaid chart={`sequenceDiagram
  participant A as Tx A
  participant PG as Postgres row id=1
  participant B as Tx B
  A->>PG: UPDATE amount = amount + 20
  Note over PG: A holds the row lock, new version 60 uncommitted
  B->>PG: UPDATE amount = amount - 20
  Note over B: waits for A's lock
  A->>PG: COMMIT
  PG-->>B: lock granted, re-read latest committed row (60)
  B->>PG: write 40, COMMIT
  Note over PG: final 40, no update lost`} />

Edge cases:
- **Fix 1 only works if the new value can be expressed in SQL.** Business rules that need app logic need Fix 2 or 3.
- **Fix 2 can deadlock** if two transactions lock rows in opposite orders. Postgres detects the cycle and aborts one of them; always lock rows in a consistent order (for example, by id).
- **Fix 3 needs a retry loop** in the app (see section 14).

## 5. Relational vs non-relational 🎓

### Relational (Postgres, MySQL, SQL Server, SQLite)
- Data lives in **tables** made of **rows** and **columns**.
- Tables are linked by **relationships**, implemented with **foreign keys**.
- The **schema is predefined and strict**: every column and its data type must be declared before data goes in.
- **Payoff:** data integrity. At any moment you can rely on each column's type and on the relationships between tables.
- You talk to it in **SQL** (Structured Query Language).

### Non-relational (MongoDB is the best-known example)

| Relational | MongoDB |
|---|---|
| Table | Collection |
| Row | Document |
| Every row has the same columns | Every document can have a different shape |

- **Advantage:** a **flexible schema**. Great for prototypes, when you want to move fast without designing a schema first.
- **Disadvantage:** the database doesn't enforce structure or relationships, so **integrity becomes your application's job**. Application code changes often, which makes it easy to introduce inconsistent data with a bug.

### Choosing by use case (the lesson's examples)

<Mermaid chart={`flowchart TD
  Q{"What does the data look like?"}
  Q -->|"Well-defined entities, relationships, must stay accurate"| R["Relational<br/>e.g. CRM: customers, contacts, sales opportunities"]
  Q -->|"Unpredictable, mixed content shapes"| N["Document store<br/>e.g. CMS: articles with images, code blocks, embeds"]
  N -.->|"Postgres JSONB covers this too"| R`} />

- **CRM** (customer relationship management): contacts, deals and sales opportunities must be **accurate and consistent**, and you'll run **complex queries** across relationships. A relational database fits.
- **CMS** (content management system, like Sanity, behind a blog): you write an article in the CMS, and the website fetches it at runtime instead of you committing a file and redeploying. An article may contain images, code blocks, YouTube embeds and so on, so the shape isn't known up front. A document database like MongoDB fits.

## 6. Why Postgres 🎓

Most relational databases offer similar features and all of them scale, so you need a tie-breaker. The lesson's reasons for Postgres:

1. **Open source and free**, so companies can self-host it on their own servers.
2. **Sticks closely to the SQL standard**, so queries written in standard SQL port to MySQL or SQL Server with small changes. Migrating later is realistic.
3. **Extensible and feature-rich**: the documentation runs to roughly 1,400 pages, covers almost any SaaS need, and there's a strong **extension** ecosystem.
4. **Reliable and scalable.**
5. **Excellent JSON support** (the deciding factor). Postgres has a `jsonb` type with indexing and querying, so the main reason to pick MongoDB, storing arbitrary JSON, disappears. A CMS-style "dump whatever content the user sent" column is just a `jsonb` column.

**Performance comparisons** (articles saying MySQL is faster at X) don't matter until you serve millions of users and are optimizing a specific bottleneck. Until then, Postgres's features make it the default choice.

**What the lesson skips:** SQL basics (`CREATE TABLE`, `SELECT`, `ORDER BY`, `GROUP BY` and so on). Learn them from any SQL or Postgres basics course first, then come back. The lesson only covers the concepts that matter in backend systems. It uses **TablePlus**, a GUI client, for all its demos.

🔧 Example of the JSONB point:

```sql
CREATE TABLE articles (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), body jsonb NOT NULL);
CREATE INDEX articles_body_gin ON articles USING gin (body jsonb_path_ops);

-- all articles containing a YouTube embed block
SELECT id FROM articles WHERE body @> '{"blocks": [{"type": "youtube"}]}';
```

## 7. Postgres data types 🎓

The lesson walks through a `data_types_demo` table with one column per type, then inserts a row covering all of them.

### 7.1 Auto-incrementing ids: `serial` and `bigserial`
- `serial` is an **integer that fills itself in**: if you omit the column on `INSERT`, Postgres takes the next number from a sequence (1, 2, 3, …).
- `bigserial` is the same thing with a much larger range. In production, when an auto-increment id is the **primary key** (the unique field that identifies a row), prefer `bigserial`.

🔧 Under the hood, `serial` creates a **sequence** and sets the column's default to `nextval(...)`. Numbers can have **gaps**: a rolled-back insert still consumes a value. Modern Postgres prefers the SQL-standard identity syntax:

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

### 7.2 Integers: `smallint`, `integer`, `bigint`
Same idea, different capacity. Pick by the largest value you'll ever store.

| Type | Bytes | Max value |
|---|---|---|
| `smallint` | 2 | 32,767 |
| `integer` | 4 | about 2.1 billion |
| `bigint` | 8 | about 9.2 × 10^18 |

🔧 Correct ordering: `smallint` is the smallest, then `integer`, then `bigint` (in the video the order is said slightly mixed up). The docs recommend `integer` as the usual default.

### 7.3 Exact vs approximate numbers
- `decimal(10,2)` and `numeric(10,2)` are equivalent. **Precision 10** is the total number of digits; **scale 2** is the number of digits after the decimal point. So `12345678.90` fits (10 digits, 2 after the point), but adding one more digit doesn't.
- `real`, `double precision` (and `float`) are **floating-point**: stored in binary, so many decimal values are **approximations**.

**The rule:** if accuracy matters, as with **prices** and money that flow through many calculations and systems, use `numeric`/`decimal`. If tiny discrepancies don't matter, as with a measured **area** like `567.8987`, use floating point. Floats are **faster** to store and compute with, which is why scientific computing prefers them.

🔧 Why floats are inexact, in one query:

```sql
SELECT 0.1::double precision + 0.2::double precision = 0.3;  -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3;                    -- true
```

0.1 has no finite binary representation, the same way 1/3 has no finite decimal one. `numeric` stores decimal digits, so it's exact but slower.

### 7.4 Strings: `char`, `varchar`, `text`

| Type | Behaviour | When to use |
|---|---|---|
| `char(10)` | Always stores exactly 10 characters: `'ab'` is **padded** with 8 spaces | Almost never. Only fixed-width codes, e.g. day codes `'MO'`, `'TU'` in `char(2)` |
| `varchar(255)` | Stores up to 255 characters, only the length you actually use. Longer → error | When you truly need a DB-level length limit |
| `text` | Like `varchar` without a limit | **The default for strings** |

**Why the lesson recommends `text`:**
1. The **Postgres docs themselves** say there's no performance difference between the three (apart from `char` padding cost), and that `text` or `varchar` should be used.
2. Myths like "`varchar(255)` is faster" or "you can't index `text`" come from **other databases** (MySQL, SQL Server, SQLite) and don't apply to Postgres.
3. **`255` is a MySQL habit.** In Postgres it has no special meaning, but a reader of your migration will assume it does and waste time hunting for the reason.
4. **Changing a length later means a migration**, which is risky on a big table. Enforce lengths in **application validation** instead. Backend engineers reach the database through a **driver** and application code, unlike data analysts who type SQL directly, so the app layer is the natural place for this rule.

🔧 Facts from the docs: `char(n)` is usually the **slowest** of the three because of padding, and the longest string Postgres can store is about **1 GB** (the video guesses a lower figure). If you do want a DB-level limit with `text`, a `CHECK (char_length(name) <= 200)` can be changed later without rewriting the table type.

### 7.5 Everything else

| Type | Stores | Example |
|---|---|---|
| `boolean` | true / false | `true` |
| `date` | a calendar date | `'2026-10-02'` |
| `time` | time of day | `'14:30:00'` |
| `timestamp` | date + time, no zone | `'2026-10-02 14:30:00'` |
| `timestamptz` | date + time + time zone | `'2026-10-02 14:30:00+05:30'` |
| `interval` | a duration | `'10 days'`, `'1 week'` |
| `uuid` | a 128-bit unique id; popular for primary keys | `'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'` |
| `json` | JSON stored as text | `'{"a": 1}'` |
| `jsonb` | JSON stored in Postgres's own binary format | `'{"a": 1}'` |
| arrays | an array of any type | `'{1,2,3}'::int[]` |
| `inet`, `macaddr`, `point`, `xml` | network addresses, MAC addresses, geometry, XML | rarely needed in typical backends |

**`json` vs `jsonb`:** use **`jsonb`** almost always. It's parsed once on write into a binary format, so queries and indexing are much faster. 🔧 `json` keeps the exact input text (whitespace, key order, duplicate keys); `jsonb` normalizes it (keys reordered, only the last duplicate kept). Only choose `json` if you must preserve the original text exactly.

🔧 **`timestamptz` doesn't actually store the zone.** It converts your input to UTC and converts back to the session's time zone on output. That's exactly what you want for `created_at`: one unambiguous instant. Plain `timestamp` silently drops the offset, which causes bugs when servers or users are in different zones.

### 7.6 Modelling with `jsonb` ➕

Sections 6 and 7.5 establish that `jsonb` is fast and indexable. What they leave open is the design question: when a `jsonb` column is the right model, how to index it so queries actually use the index, and how to change documents without losing data.

#### 7.6.1 When `jsonb` is the right model, and when it isn't ➕
**Problem:** "flexible schema" is tempting, so teams put whole entities into one `data jsonb` column. Months later nothing stops `"priority": "high"` sitting next to `"priority": 3`, a referenced user id points at a deleted user, and queries filtering on a key are slow and badly planned.

**Why it happens (first principles):** everything section 9 relies on works at the **column** level. Types, `NOT NULL`, foreign keys, `UNIQUE` and enums all attach to columns. Inside a document, Postgres only knows "this is valid JSON". On top of that, `ANALYZE` gathers statistics on the column as a whole, not per key, so the planner's row estimates for a condition like `data->>'status' = 'open'` are rough guesses unless you index that expression (an expression index gets its own statistics).

**Mechanism: a hybrid model.** Anything you **filter, join, sort, constrain or reference** becomes a real column. `jsonb` holds what is genuinely variable or opaque to the database: CMS content blocks, per-integration settings, a raw webhook payload kept for debugging, user-defined custom fields.

```sql
CREATE TABLE integrations (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id uuid NOT NULL REFERENCES projects ON DELETE CASCADE,  -- relational: FK, indexed, joined
  provider   text NOT NULL CHECK (provider IN ('slack', 'github', 'jira')),
  settings   jsonb NOT NULL DEFAULT '{}'
             CHECK (jsonb_typeof(settings) = 'object'),            -- at least guarantee the top-level shape
  created_at timestamptz NOT NULL DEFAULT now()
);
```

When one key inside a document turns out to be queried all the time, **promote it**. A stored generated column keeps it in sync automatically and can carry an ordinary B-tree index:

```sql
ALTER TABLE articles ADD COLUMN slug text GENERATED ALWAYS AS (body->>'slug') STORED;
CREATE UNIQUE INDEX articles_slug_uq ON articles (slug);
```

In Python, validate the document with a Pydantic model before it is written, because the database won't check its inner shape:

```python
from typing import Literal

from pydantic import BaseModel, Field


class SlackSettings(BaseModel):
    channel: str = Field(min_length=1)
    notify_on: list[Literal["created", "completed"]]


settings = SlackSettings.model_validate(payload)  # raises ValidationError on a bad shape
await pool.execute(
    "INSERT INTO integrations (project_id, provider, settings) VALUES ($1, $2, $3::jsonb)",
    project_id, "slack", settings.model_dump_json(),
)
```

**Edge cases:**
- Adding a **stored generated column rewrites the whole table** under an `ACCESS EXCLUSIVE` lock (the `ALTER TABLE` docs list it next to volatile defaults). On a big table, use the expand/contract approach from section 8 instead: plain column, batched backfill, then a trigger or app code to keep it in sync.
- Old documents don't get new keys. Code reading `settings.notifyOn` must handle "missing", or you run a backfill.

#### 7.6.2 Indexing `jsonb`: GIN operator classes vs expression indexes ➕
**Problem:** you create `USING gin (body)` and the query `WHERE body->>'status' = 'published'` still does a sequential scan.

**Why it happens:** an index serves **specific operators**. A GIN index on a `jsonb` column serves containment and existence operators such as `@>` and `?`. The expression `body->>'status' = 'published'` is a text equality on a computed value, which is a different operator on a different expression, so the GIN index is useless for it.

**Mechanism: pick the index by the query shape.**

| Query shape | Index |
|---|---|
| `body @> '...'` (contains), jsonpath `@?` / `@@` | GIN with `jsonb_path_ops`: smaller and usually faster |
| also key existence: `body ? 'key'` and its any-of / all-of variants | GIN with the default `jsonb_ops` |
| equality or range on one key: `body->>'status' = $1` | B-tree **expression index** on `(body->>'status')` |
| containment on one sub-tree only | GIN on the sub-expression, e.g. `((body->'tags'))` |

```sql
CREATE INDEX articles_body_path_gin ON articles USING gin (body jsonb_path_ops);    -- @> queries
CREATE INDEX articles_status_idx    ON articles ((body->>'status'));                -- equality on one key
CREATE INDEX articles_tags_gin      ON articles USING gin ((body->'tags'));         -- only the tags sub-tree
```

**Edge cases:**
- The query must use **exactly the indexed expression**. `body->>'status'` and `body #>> '{status}'` mean the same thing but are different expressions to the planner.
- `jsonb_path_ops` doesn't support the key-exists operators, and per the docs it is poor at matching structures with no values (such as an empty object), which turn into full-index scans.
- GIN indexes **can't do index-only scans** (section 13 ➕), and every write updates many index entries, one per key and value. Index the sub-tree you query, not the whole document, when you can.

#### 7.6.3 Changing documents safely ➕
**Problem:** a handler reads `settings`, changes one key in Python and writes the whole object back. Two requests do this at once and one change disappears: the lost update from section 4.3, now hidden inside a JSON document.

**Why it happens:** even if you change one key, an `UPDATE` writes a **new version of the entire row** (MVCC, section 14.2), including the whole `jsonb` value. There's no in-place partial update on disk, and the row lock covers the whole row. The docs warn that large documents therefore raise lock contention between updaters.

**Mechanism: do the merge inside one SQL statement**, so the read-modify-write happens under the row lock (section 4.3, Fix 1):

```sql
-- shallow merge of the keys sent by the client
UPDATE integrations SET settings = settings || $1::jsonb WHERE id = $2 RETURNING settings;

-- set one nested key (subscripting creates missing intermediate objects)
UPDATE integrations SET settings['slack']['channel'] = to_jsonb($1::text) WHERE id = $2;
```

**Edge cases:**
- `||` is a **shallow** merge: a top-level key sent by the client replaces the whole nested object under that key; it doesn't deep-merge.
- `jsonb_set(doc, path, NULL)` returns **NULL**, because the function is strict, so `SET settings = jsonb_set(settings, '{x}', $1)` with a null parameter wipes the entire column. Use `jsonb_set_lax`, which lets you choose what a null does, or validate first.
- **asyncpg doesn't serialize Python objects to JSON for you.** By default it expects a **string** for a `json`/`jsonb` parameter, so passing a `dict` fails, and a Python `list` bound to an array-typed parameter becomes a Postgres array, not JSON. Either `json.dumps(...)` (or `model_dump_json()`) every value bound to a `jsonb` parameter, or register a codec once per connection with `conn.set_type_codec("jsonb", encoder=json.dumps, decoder=json.loads, schema="pg_catalog")`. (psycopg 3 instead requires wrapping the value: `Jsonb(data)`.)
- Values bigger than about 2 kB are moved out of line (TOAST), and each update writes a fresh copy. Frequently changing counters belong in their own column, not inside a large document.

## 8. Migrations 🎓

### Problem
In production you can't just open TablePlus and run `CREATE TABLE` by hand:
- there's **no record** of what changed, when, or who did it,
- there's **no way to reproduce** the same schema on another environment (dev, staging, a teammate's laptop),
- there's **no way to go back** if a change breaks production.

### Mechanism
A **migration** is a plain `.sql` file containing schema changes (`CREATE TABLE`, `CREATE INDEX`, `DROP TABLE`, `CREATE TYPE` …). The files live in your repo (for example `db/migrations/`) and are named so they **sort in order**, either with numbers (`1.sql`, `2.sql`) or, more commonly, **timestamps**.

A **migration tool** (the lesson uses **dbmate**; golang-migrate is another) reads the folder in order and runs each file against the database in your environment.

- **Up migration:** applies the change (create the table, add the index).
- **Down migration:** **undoes exactly that change**, so you can **roll back** to the previous schema if something breaks. (Some modern workflows skip down migrations and only roll forward, but up + down is the classic approach.)

**How the tool knows what's already applied:** it creates its own table (dbmate calls it `schema_migrations`) with a `version` column. Each applied file's version is recorded. On the next run, only files with a newer version are executed. Without this, re-running file 1 would fail with "table already exists".

<Mermaid chart={`flowchart TD
  F["db/migrations/<br/>20240101_create_users.sql<br/>20240102_seed_data.sql<br/>20240103_indexes_triggers.sql"] --> T["dbmate up"]
  T --> Q{"version already in<br/>schema_migrations?"}
  Q -->|yes| S["skip file"]
  Q -->|no| R["run the migrate:up section<br/>insert version row"]
  R --> DB[("Postgres")]
  RB["dbmate rollback"] --> D["run the migrate:down section of the latest file<br/>delete its version row"]
  D --> DB`} />

**Why migrations are worth it:**
1. **History:** the migration folder is committed to git with the code, so the schema's whole history is reviewable.
2. **Rollback:** down migrations let you return to a known state.

### What the demo shows
- A `.env` file with `DATABASE_URL`, which dbmate reads.
- `dbmate new create_users_table` creates `db/migrations/<timestamp>_create_users_table.sql`, with two marked sections: everything after the `migrate:up` comment is the up migration, everything after `migrate:down` is the down migration.
- `dbmate up` applies it and reports the time taken. Refreshing TablePlus shows the new tables plus `schema_migrations`.

```bash
# .env
DATABASE_URL="postgres://postgres:postgres@localhost:5432/pm_app?sslmode=disable"

dbmate new create_users_table   # new timestamped file
dbmate up                       # apply pending migrations
dbmate rollback                 # 🔧 run the down section of the latest migration
dbmate status                   # 🔧 which files are applied
```

🔧 **Edge cases:**
- **Never edit a migration that has already run** in a shared environment. The tool won't re-run it, so environments drift apart. Write a new migration instead.
- Postgres supports **transactional DDL**: dbmate wraps each migration in a transaction by default, so a failing file leaves nothing half-applied. The exception is statements that can't run inside a transaction, such as `CREATE INDEX CONCURRENTLY` (section 13).
- A down migration that drops a table **destroys its data**. Rolling back is for schema mistakes, not a backup (backups are section 15 ➕).

### Zero-downtime migrations on a live database ➕

The lesson runs its migrations against an empty local database. Run the same kind of file against a production table that is serving traffic and it can stall every request, so the next thing to learn is how to change a schema while the app keeps working.

#### The lock queue: how an "instant" `ALTER TABLE` takes production down ➕
**Problem:** you deploy `ALTER TABLE tasks ADD COLUMN archived_at timestamptz;`. Adding a nullable column is a metadata-only change that should take milliseconds. Instead, every endpoint that touches `tasks` times out for two minutes.

**Why it happens (first principles):** every statement takes a **table-level lock**. A plain `SELECT` takes `ACCESS SHARE`, the weakest mode. Most `ALTER TABLE` forms take **`ACCESS EXCLUSIVE`**, which conflicts with **every** mode, including `ACCESS SHARE`. Two facts then combine:
1. The `ALTER` can't start while any transaction still holds a lock on `tasks`, for example a two-minute analytics query, or a session sitting "idle in transaction" after a `SELECT`.
2. Lock requests **queue**. A new `SELECT` conflicts with the `ALTER` that is **waiting** in front of it, so it queues behind the `ALTER`, even though it doesn't conflict with the long query that is actually running.

So one slow reader plus one waiting `ALTER` blocks all new traffic to the table until the slow reader finishes.

<Mermaid chart={`sequenceDiagram
  participant Q as Long report query
  participant T as tasks table locks
  participant M as Migration ALTER TABLE
  participant A as API requests
  Q->>T: ACCESS SHARE (granted, runs 2 min)
  M->>T: request ACCESS EXCLUSIVE
  Note over M: waits for the report
  A->>T: SELECT needs ACCESS SHARE
  Note over A: queued behind the waiting ALTER<br/>every new request piles up here
  Q-->>T: report finishes, lock released
  T-->>M: ALTER granted, runs in milliseconds
  T-->>A: queued requests finally proceed`} />

**Mechanism: never wait long for a lock.** Set **`lock_timeout`** in the migration session. If the lock isn't granted within a few seconds, the statement fails with SQLSTATE `55P03` (`lock_not_available`) instead of building a queue, and you retry later. Add a **`statement_timeout`** so a migration can't run unbounded. Both default to 0 (disabled), and the docs advise against setting them globally in `postgresql.conf`, so set them per session or per transaction.

```sql title="db/migrations/20240201000000_add_archived_at.sql"
-- migrate:up
SET LOCAL lock_timeout = '3s';        -- give up instead of queueing traffic behind us
SET LOCAL statement_timeout = '30s';
ALTER TABLE tasks ADD COLUMN archived_at timestamptz;

-- migrate:down
SET LOCAL lock_timeout = '3s';
ALTER TABLE tasks DROP COLUMN archived_at;
```

`SET LOCAL` only lasts until the end of the current transaction, which is exactly the migration file, since dbmate wraps each file in one. A deploy script can retry on that error:

```python title="scripts/migrate_with_retry.py"
import subprocess
import time

for attempt in range(1, 11):
    result = subprocess.run(["dbmate", "up"], capture_output=True, text=True)
    if result.returncode == 0:
        break
    if "lock timeout" not in result.stderr or attempt == 10:      # only retry lock timeouts
        raise SystemExit(result.stderr)
    time.sleep(2 * attempt)                                       # back off, let the blocker finish
```

With Alembic instead of dbmate, the same loop wraps `["alembic", "upgrade", "head"]`, and the `SET LOCAL` lines go at the top of the revision's `upgrade()` as `op.execute("SET LOCAL lock_timeout = '3s'")` (on Postgres Alembic wraps the whole run in one transaction by default; pass `transaction_per_migration=True` to `context.configure()` in `env.py` to get one per revision, like dbmate).

To see what is blocking a waiting migration:

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, state, now() - xact_start AS tx_age, left(query, 80)
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

**Edge cases:**
- `lock_timeout` applies **per lock acquisition**. A migration touching three tables collects locks one by one and holds them all until commit. Keep one risky table change per file, and keep the file short.
- Long transactions are the usual cause. Set **`idle_in_transaction_session_timeout`** for application roles so a forgotten `BEGIN` can't hold locks for hours (section 14.3 ➕ covers the same problem for VACUUM).
- An **anti-wraparound autovacuum** (section 14.3 ➕) holds a lock that conflicts with `ALTER TABLE` and, unlike normal autovacuum, doesn't cancel itself for you. Your `lock_timeout` turns that into a clean retry instead of an outage.

#### Expand and contract: changing shape while two app versions run ➕
**Problem:** you rename `users.full_name` to `display_name` in one migration and deploy. For a few minutes, old app instances (still rolling out) query `full_name` and fail with "column does not exist".

**Why it happens:** the schema change is **atomic and instant**; the code rollout is **gradual**. During a rolling deploy, old and new code run against the same database at the same time, and a rollback brings old code back again. Any change that the old code can't tolerate breaks someone.

**Mechanism: split one breaking change into several compatible ones.**

<Mermaid chart={`flowchart LR
  E["1. Expand<br/>add display_name, nullable"] --> W["2. Deploy code<br/>write both columns,<br/>read old"]
  W --> B["3. Backfill<br/>copy old rows in batches"]
  B --> R["4. Deploy code<br/>read new, still write both"]
  R --> C1["5. Deploy code<br/>stop writing old"]
  C1 --> C["6. Contract<br/>drop full_name, add NOT NULL"]`} />

Every step is safe to roll back to the step before it, because at every point both the current and the previous app version find the columns they expect.

```python title="step 2: dual write"
await pool.execute(
    "UPDATE users SET full_name = $1, display_name = $1 WHERE id = $2",
    name, user_id,
)
```

**Edge cases:**
- **Never contract in the same release as the code change.** Wait until no running version (and no version you might roll back to) reads the old column.
- A trigger can do the dual write instead of app code (`NEW.display_name := NEW.full_name`), which also covers scripts and other services. Remove it in the contract step.
- **ORM migration generators** may turn a rename into "drop column, add column", which loses the data. Alembic's `alembic revision --autogenerate` does exactly that for a renamed column, so always review the generated revision (replace the pair with `op.alter_column(..., new_column_name=...)`, or split it into expand/contract steps), and preview the SQL with `alembic upgrade head --sql` before applying.
- Type changes such as `integer` to `bigint` rewrite the table under `ACCESS EXCLUSIVE`. Use the same expand/contract dance: new column, dual write, backfill, swap.

#### Adding columns, defaults and `NOT NULL` safely ➕
**Problem:** `ALTER TABLE tasks ADD COLUMN public_id uuid NOT NULL DEFAULT gen_random_uuid();` locks a 50-million-row table for minutes.

**Why it happens:** the cost depends on whether Postgres must **touch every row**:
- A **non-volatile default** (a constant like `false` or `'medium'`) is evaluated once and stored in the table's metadata. Existing rows return it when read, so the `ALTER` is fast even on huge tables.
- A **volatile default** (`gen_random_uuid()`, `clock_timestamp()`) has to produce a different value per row, so the **whole table and its indexes are rewritten** while holding `ACCESS EXCLUSIVE`.
- `SET NOT NULL` must prove that no row is null, so by default it **scans the whole table** under `ACCESS EXCLUSIVE`.

**Mechanism:** keep the expensive part out of the exclusive lock.

```sql
-- 1. fast: nullable column, no volatile default
ALTER TABLE tasks ADD COLUMN public_id uuid;
ALTER TABLE tasks ALTER COLUMN public_id SET DEFAULT gen_random_uuid();  -- applies to new rows only, no rewrite

-- 2. backfill existing rows in batches (next subsection)

-- 3. prove NOT NULL without a long exclusive lock
ALTER TABLE tasks ADD CONSTRAINT tasks_public_id_nn CHECK (public_id IS NOT NULL) NOT VALID;  -- brief lock, no scan
ALTER TABLE tasks VALIDATE CONSTRAINT tasks_public_id_nn;  -- scans, but only SHARE UPDATE EXCLUSIVE: reads and writes continue
ALTER TABLE tasks ALTER COLUMN public_id SET NOT NULL;     -- skips the scan: the valid CHECK already proves it
ALTER TABLE tasks DROP CONSTRAINT tasks_public_id_nn;
```

Step 3 works because the docs state that `SET NOT NULL` skips its table scan when a **valid `CHECK` constraint proves no null can exist**. PostgreSQL 18 also allows `NOT VALID` on not-null constraints directly, which shortens the dance on new versions.

**Edge cases:**
- `NOT VALID` still checks **new and updated rows** from the moment it is added. Only existing rows are left unchecked until `VALIDATE`.
- `VALIDATE` fails if any old row violates the rule. Find and fix them first (`SELECT count(*) FROM tasks WHERE public_id IS NULL`).
- Each of these statements still needs a brief `ACCESS EXCLUSIVE` lock to start, so the `lock_timeout` rule above applies to every one of them.

#### Foreign keys and `CHECK` constraints: `NOT VALID`, then `VALIDATE` ➕
**Problem:** `ALTER TABLE tasks ADD CONSTRAINT tasks_project_fk FOREIGN KEY (project_id) REFERENCES projects;` blocks writes on **both** tables while it checks every existing task.

**Why it happens:** `ADD FOREIGN KEY` takes a `SHARE ROW EXCLUSIVE` lock on the table **and on the referenced table**, which blocks inserts, updates and deletes on both, then scans all existing rows to verify them, holding those locks for the whole scan.

**Mechanism:** split "start enforcing" from "verify history", exactly as with `NOT NULL`:

```sql
-- migration A: brief lock, enforces the FK for all new writes immediately
ALTER TABLE tasks ADD CONSTRAINT tasks_project_fk
  FOREIGN KEY (project_id) REFERENCES projects NOT VALID;

-- migration B: full scan, but VALIDATE only takes SHARE UPDATE EXCLUSIVE
ALTER TABLE tasks VALIDATE CONSTRAINT tasks_project_fk;
```

**Edge cases:**
- Index the child column (`tasks.project_id`) **before** relying on the FK in production. Deletes on the parent look up children, as section 13 explains.
- Until `VALIDATE` succeeds, the planner can't rely on the constraint, and the data may still contain orphans. Treat `NOT VALID` as a temporary state, not the end result.

#### Building indexes without blocking writes ➕
**Problem:** section 13's `CREATE INDEX` blocks every insert, update and delete on the table for the whole build, which can be many minutes on a large table.

**Mechanism: `CREATE INDEX CONCURRENTLY`.** It takes only `SHARE UPDATE EXCLUSIVE`, so writes continue. The price: it scans the table twice in separate transactions, waits for every transaction that started before it (so a long-running transaction delays it), and **can't run inside a transaction block**. dbmate supports this with a per-file flag:

```sql title="db/migrations/20240202000000_idx_tasks_assigned.sql"
-- migrate:up transaction:false
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_tasks_assigned_to ON tasks (assigned_to);

-- migrate:down transaction:false
DROP INDEX CONCURRENTLY IF EXISTS idx_tasks_assigned_to;
```

For a unique constraint, build the unique index concurrently, then attach it as a constraint, which only needs a brief lock:

```sql
CREATE UNIQUE INDEX CONCURRENTLY users_email_uq_idx ON users (email);
ALTER TABLE users ADD CONSTRAINT users_email_uq UNIQUE USING INDEX users_email_uq_idx;
```

**Edge cases:**
- **A failed concurrent build leaves an `INVALID` index behind.** It isn't used by queries but still costs write overhead on every insert and update. Find such indexes with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`, then drop and recreate them (or `REINDEX INDEX CONCURRENTLY`).
- **`IF NOT EXISTS` only checks the name**, so a re-run after a failure silently skips over the invalid index. Check `indisvalid` after the migration.
- Put **one concurrent statement per file**. Without the transaction wrapper, if the second statement fails the first one stays applied.

#### Backfilling data in batches ➕
**Problem:** `UPDATE tasks SET public_id = gen_random_uuid() WHERE public_id IS NULL;` on 50 million rows runs as one transaction for an hour.

**Why it happens:** one statement is one transaction. Until it commits, it **holds row locks on every row it updated** (so normal updates to those tasks wait), it writes a new version of every row (MVCC), which roughly doubles the table until VACUUM catches up, it produces a burst of WAL that replicas must replay, and if it fails at minute 59 everything rolls back and you start again.

**Mechanism: many small transactions**, each touching a bounded batch, each idempotent, so the job can stop and resume anywhere.

```sql
-- one batch: pick 5,000 rows that still need work, update them, commit
WITH batch AS (
  SELECT id FROM tasks
  WHERE public_id IS NULL
  ORDER BY id
  LIMIT 5000
  FOR UPDATE SKIP LOCKED          -- don't wait on rows the app is updating right now
)
UPDATE tasks t SET public_id = gen_random_uuid()
FROM batch WHERE t.id = batch.id;
```

```python title="scripts/backfill_public_id.py"
while True:
    status = await pool.execute(BATCH_SQL)   # each call is its own short transaction; returns e.g. "UPDATE 5000"
    if status == "UPDATE 0":                 # nothing left: done
        break
    await asyncio.sleep(0.2)                 # leave room for autovacuum and replicas
```

**Edge cases:**
- **The `updated_at` trigger from section 12 fires on every backfilled row**, so every task suddenly looks "recently edited" and the default sort of the UI changes. Either add a `WHEN` condition to the trigger, or set a session flag such as `SET app.backfill = 'on'` that the trigger function checks with `current_setting('app.backfill', true)`.
- Run backfills as a **job**, not inside the migration tool: the migration framework would run them in one transaction, which defeats the point.
- Watch replica lag and dead tuples (`pg_stat_user_tables.n_dead_tup`) while it runs, and slow down if either grows.

The **down section drops everything in reverse order**: tables before the types they use, and child tables before parents (a parent can't be dropped while a foreign key still points at it).

### 9.1 Enums 🎓
**Problem:** `projects.status` should only ever be `active`, `completed` or `archived`. With a `text` column, any string goes in.

**Mechanism:** `CREATE TYPE ... AS ENUM (...)` defines a type with a **fixed set of allowed values**. Use it as the column type, and any other value fails **at the database**.

Two reasons to use it:
1. **Data integrity:** the DB rejects bad values even if an app path, a script or a teammate forgets to validate. Validating in app code as well is fine; the DB is the last line of defence.
2. **Documentation** (the lesson rates this as the more important one): someone onboarding reads the migration and immediately sees the three allowed statuses. With `text`, they'd have to search all the application code to discover the rule.

Enum columns usually get a **default** (`DEFAULT 'active'`), so the app doesn't have to send it.

```sql
INSERT INTO projects (name, owner_id, status) VALUES ('X', '...', 'something');
-- ERROR:  invalid input value for enum project_status: "something"
```

🔧 **Edge cases:**
- Adding a value is easy: `ALTER TYPE task_status ADD VALUE 'blocked';`. **Removing or renaming** a value is hard (renaming is possible, removing requires recreating the type). If the list changes often, use a `CHECK (status IN (...))` constraint or a lookup table instead.
- Enums sort in **declaration order**, not alphabetically. That can be useful (`ORDER BY status` gives pending, in progress, completed).

### 9.2 Primary keys 🎓
Every table gets an `id` that **uniquely identifies a row**. Example: `GET /users/:id` must find exactly one user from the id in the URL.

Declaring `PRIMARY KEY` implicitly gives you **`NOT NULL` + `UNIQUE`**. Inserting a duplicate or a null id fails at the database. (It also makes the column the default target of foreign keys, see 9.6.)

`DEFAULT gen_random_uuid()` means the app normally **doesn't send an id**: Postgres generates a random UUID on insert.

🔧 **UUID vs bigint keys:**
- UUIDs can be generated anywhere (even client-side), don't leak row counts (`/users/1043` tells a competitor how many users you have), and merge cleanly across databases.
- Random (v4) UUIDs insert at **random positions** in the primary-key B-tree, which spreads writes across the index and hurts cache locality on very large tables. Postgres 18 adds a built-in `uuidv7()`, which is **time-ordered**, so new keys land at the right edge of the index like a sequence would.

### 9.3 `NOT NULL` by default 🎓
**Problem:** in Postgres every column **allows NULL unless you say otherwise**. A buggy script or code path can fill the table with nulls, and every query afterwards has to handle "maybe missing".

**Rule of thumb from the lesson:** **more than 70% of your columns should be `NOT NULL`**. Only leave a column nullable when "unknown or absent" is a real, meaningful state (a user's optional bio, a task with no due date).

🔧 Why nulls are expensive mentally: SQL uses three-valued logic. `NULL = NULL` is `NULL` (not true), `WHERE phone <> '123'` silently **excludes** rows where `phone` is null, and `NOT IN (subquery)` returns nothing if the subquery contains a null.

### 9.4 The `users` table 🎓
- `email text NOT NULL UNIQUE`: two users can't share an email. A second insert with the same email fails with a **unique constraint violation**.
- `full_name text NOT NULL`.
- `password_hash text NOT NULL`: never store the plain password, store its hash.
- `created_at timestamptz NOT NULL DEFAULT now()`: when the row was created; filled in automatically.
- `updated_at`: when the row last changed; useful, for example, to sort a table in the UI by most recently edited. Keeping it correct is solved with a trigger in section 12.

🔧 **Two engineering details here:**
- Email uniqueness should usually be **case-insensitive** (`Alice@x.com` and `alice@x.com` are the same inbox). Either normalize to lowercase in the app before insert, or enforce it in the DB with a unique index on an expression: `CREATE UNIQUE INDEX users_email_lower_uq ON users (lower(email));`
- **Unique violations are a normal app path, not a crash.** The driver reports SQLSTATE `23505`. Map it to `409 Conflict` ("email already registered") rather than a 500. Don't do "SELECT to check, then INSERT": two concurrent sign-ups can both pass the SELECT. Let the constraint decide.

```python
import asyncpg

try:
    return await pool.fetchrow(
        "INSERT INTO users (email, full_name, password_hash) VALUES ($1, $2, $3) "
        "RETURNING id, email, full_name, created_at",
        email.lower(), full_name, password_hash,
    )
except asyncpg.UniqueViolationError as e:   # SQLSTATE 23505 (e.sqlstate == "23505")
    raise ConflictError("Email already registered") from e
```

### 9.5 Naming conventions 🎓
- **Table names are plural**: `users`, `user_profiles`, `projects`. (Singular also works; follow your team's convention, but plural is the common industry standard.)
- **Everything is lowercase `snake_case`**: `full_name`, `password_hash`, `created_at`.
- **Why not camelCase?** Postgres **folds unquoted identifiers to lowercase**. If you write `fullName`, Postgres creates and looks up `fullname`. To keep the capital you must write `"fullName"` in double quotes **every time**, in every query, which makes application SQL ugly and error-prone. snake_case avoids the problem entirely.

🔧 Python's own convention is snake_case too, so model attributes usually match column names one to one. Where they don't (or where the JSON API uses camelCase), map at the boundary: SQLAlchemy's `mapped_column("full_name")` lets the attribute name differ from the column, and Pydantic's `alias_generator=to_camel` produces camelCase JSON keys from snake_case fields.

### 9.6 One-to-one: `user_profiles` 🎓
**Problem:** a user's profile (avatar, bio, phone, and later social links, websites, portfolio projects …) is the part of a user that **keeps growing** and changes often. Putting it all in `users` means frequent migrations on your most important table and constant rewrites of user rows for unrelated edits.

**Mechanism:** move it to its own table where **each user has at most one profile row**. The same pattern is used for user preferences and metadata.

**How 1:1 is implemented:** the child table doesn't need its own `id`. Its `user_id` is **both the primary key and a foreign key** to `users.id`. Primary key means "at most one row per user"; foreign key means "the user must exist". The profile columns are **nullable**, because a user may never fill them in.

### 9.7 Foreign keys and referential integrity 🎓
`owner_id uuid NOT NULL REFERENCES users ON DELETE RESTRICT`

- `REFERENCES users` is short for `REFERENCES users(id)`: when you omit the column, Postgres uses the referenced table's **primary key**.
- **The foreign key constraint itself:** you can't insert an `owner_id` that doesn't exist in `users`. Even a perfectly valid UUID fails if no user has it. That's what prevents orphan rows.
- **`ON DELETE ...`** decides what happens to the child rows when the parent row is deleted. This is **referential integrity**: using the relationship to protect data across tables.

| Rule | Deleting a user who still owns projects… | Used in this schema for |
|---|---|---|
| `RESTRICT` | **fails**: delete the projects first | `projects.owner_id` |
| `CASCADE` | also deletes the child rows | `tasks.project_id`, `project_members.*` |
| `SET NULL` | sets the FK column to null in the child rows (fails if the column is `NOT NULL`) | `tasks.assigned_to` |
| `SET DEFAULT` | sets the FK column to its default value | not used |

<Mermaid chart={`flowchart TD
  D["DELETE FROM users WHERE id = 1"] --> P{"projects with owner_id = 1?<br/>ON DELETE RESTRICT"}
  P -->|yes| X["ERROR: violates foreign key constraint<br/>nothing is deleted"]
  P -->|no| T{"tasks with assigned_to = 1?<br/>ON DELETE SET NULL"}
  T --> T2["assigned_to becomes NULL<br/>tasks stay"]
  T2 --> M{"project_members with user_id = 1?<br/>ON DELETE CASCADE"}
  M --> M2["membership rows deleted"]
  M2 --> OK["user row deleted"]`} />

🔧 **Edge cases:**
- The default when you write nothing is **`NO ACTION`**, which behaves like `RESTRICT` except that the check can be **deferred** to the end of the transaction (with `DEFERRABLE` constraints). `RESTRICT` checks immediately.
- `CASCADE` is convenient but can delete far more than expected (project → tasks → anything that cascades from tasks). For important data, many teams use **soft deletes** (`deleted_at timestamptz`) and `RESTRICT`.
- Every `DELETE` on a parent has to **look up matching child rows**. Without an index on the child's FK column, that's a full scan of the child table per deleted parent. See section 13.

### 9.8 One-to-many: `tasks` 🎓
- `project_id uuid NOT NULL REFERENCES projects ON DELETE CASCADE`: a task **must** belong to a project (no orphan tasks), and deleting a project deletes its tasks.
- **How 1:N is implemented:** the "many" side holds a **plain foreign key** (not a primary key) pointing to the "one" side. Many task rows can carry the same `project_id`.
- `priority integer NOT NULL DEFAULT 1 CHECK (priority BETWEEN 1 AND 5)`: a **`CHECK` constraint** is a custom rule evaluated on every insert or update; the write only succeeds if the rule is true, so a value like 55 is rejected.
- `status task_status NOT NULL DEFAULT 'pending'`.
- `due_date date`: a date only, no time or zone, and optional.
- `assigned_to uuid REFERENCES users ON DELETE SET NULL`: optional; if the assignee's account is deleted, the task survives, unassigned.

The constraints the lesson has now shown: `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`.

### 9.9 Many-to-many: `project_members` 🎓
**How to recognise M:N:** the relationship makes sense **read both ways**. A user can be in many projects, and a project has many users.

**Mechanism: a linking (junction) table** whose only job is to record pairs.
- Columns `project_id` and `user_id`, each a **foreign key** with `ON DELETE CASCADE` (delete either side and the membership disappears).
- No separate `id`. Instead, **`PRIMARY KEY (project_id, user_id)`**, a **composite primary key**. "User 1 is in project 2" is a single fact that can't exist twice, and the primary key's implicit `UNIQUE` + `NOT NULL` enforce exactly that.
- **Attributes of the relationship go here.** `role` (owner, admin, member, default member) belongs to "this user *in this project*", not to the user or the project alone.

| Relationship | Implementation |
|---|---|
| 1:1 | child's PK = FK to parent (`user_profiles.user_id`) |
| 1:N | plain FK on the many side (`tasks.project_id`) |
| M:N | linking table with a composite PK of two FKs (`project_members`) |

🔧 Adding a member idempotently (a double-click shouldn't create an error or a duplicate):

```sql
INSERT INTO project_members (project_id, user_id, role)
VALUES ($1, $2, 'member')
ON CONFLICT (project_id, user_id) DO NOTHING;
```

### 9.10 Constraints as business rules ➕

Section 9.8 ended with five constraint types. Postgres can enforce richer rules than "not null" and "unique", and every rule the database enforces is a rule that no buggy code path, script or second service can break.

#### 9.10.1 What `CHECK` can and can't express ➕
**Problem:** you want "a completed task must have a `completed_at`", and also "a project can have at most 3 admins". The first works as a `CHECK`; the second silently doesn't.

**Why it happens:** a `CHECK` is evaluated **on one row, at the moment that row is written**. The docs restrict it to columns of the current row, with no subqueries and only immutable functions. A rule that depends on **other rows** can't be checked there, because a change to those other rows never re-runs it.

**Mechanism:** use `CHECK` for row-local invariants, written as implications ("if A then B" is `NOT A OR B`):

```sql
ALTER TABLE tasks ADD COLUMN completed_at timestamptz;
ALTER TABLE tasks ADD CONSTRAINT tasks_completed_has_time
  CHECK (status <> 'completed' OR completed_at IS NOT NULL);
ALTER TABLE projects ADD CONSTRAINT projects_name_len
  CHECK (char_length(name) BETWEEN 1 AND 200);
```

For cross-row rules, use the tools below (partial unique indexes, exclusion constraints), or a transaction at `SERIALIZABLE` / with row locks (section 14).

In the API, a violation arrives as SQLSTATE **`23514`** (`check_violation`) with the constraint name, which you can map to a 422 with a precise message:

```python
try:
    await tasks_repo.update_status(task_id, status)
except asyncpg.CheckViolationError as e:                 # SQLSTATE 23514
    if e.constraint_name == "tasks_completed_has_time":
        raise UnprocessableError("A completed task needs completed_at") from e
    raise
```

**Edge cases:**
- Hiding a query inside a function called from `CHECK` appears to work, but the rule isn't re-checked when the other table changes, and dump/restore can fail because tables are loaded in an order the function doesn't expect.
- `CHECK` passes when the expression is **NULL**. `CHECK (priority > 0)` accepts a null priority; combine it with `NOT NULL` when null isn't allowed.

#### 9.10.2 Partial unique indexes: uniqueness for a subset of rows ➕
**Problem:** "every project has exactly one owner" in `project_members`. A plain `UNIQUE (project_id, role)` would also forbid two `member` rows in the same project.

**Mechanism:** a **unique index with a `WHERE` clause** enforces uniqueness only among the rows matching the predicate:

```sql
CREATE UNIQUE INDEX project_members_one_owner ON project_members (project_id) WHERE role = 'owner';
```

A second owner for the same project now fails with `23505`, while any number of members are fine. The same pattern gives "unique among non-deleted rows" for soft deletes (9.11 ➕).

**Edge cases:**
- To use it as an upsert target, repeat the predicate: `ON CONFLICT (project_id) WHERE role = 'owner' DO ...`, otherwise Postgres can't infer the index.
- "At most one" is enforceable this way; "**at least** one owner" isn't. That needs a check in the transaction that removes or demotes an owner.

#### 9.10.3 Exclusion constraints: no overlapping ranges ➕
**Problem:** a user shouldn't have two time-boxed work sessions that overlap. Two concurrent requests each check "no overlap" with a `SELECT`, both see none, both insert. The race is the same one as "SELECT, then INSERT" for unique emails (9.4).

**Why it happens:** a `UNIQUE` constraint can only compare values with `=`. Overlap is a different operator, `&&`, and an app-level check is a read-then-write race.

**Mechanism: `EXCLUDE`**, a generalisation of `UNIQUE`: "no two rows may have these columns all matching under these operators". It is backed by a GiST index. The `btree_gist` extension lets GiST handle plain equality on scalar types like `uuid`:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE work_sessions (
  id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users ON DELETE CASCADE,
  during  tstzrange NOT NULL,                       -- '[start, end)': start inclusive, end exclusive
  EXCLUDE USING gist (user_id WITH =, during WITH &&)
);

INSERT INTO work_sessions (user_id, during) VALUES ($1, tstzrange($2, $3, '[)'));
-- overlapping insert for the same user → SQLSTATE 23P01 (exclusion_violation)
```

The database checks overlap atomically for concurrent inserts, the same way a unique index handles concurrent duplicates.

**Edge cases:**
- Use **half-open ranges** `[)`, so a session ending at 10:00 and one starting at 10:00 don't count as overlapping.
- Exclusion constraints **can't be the target of `ON CONFLICT DO UPDATE`** (only `DO NOTHING`).
- Map `23P01` to `409 Conflict`. GiST indexes are slower to update than B-trees, which is fine for booking-style tables but worth knowing on hot write paths.

#### 9.10.4 Deferrable constraints: checking at commit ➕
**Problem:** tasks have a `position` column with `UNIQUE (project_id, position)` for manual ordering. Swapping two tasks, or `UPDATE tasks SET position = position + 1 WHERE project_id = $1`, fails with a unique violation even though the final state is valid.

**Why it happens:** a non-deferrable unique constraint is checked **as each row is modified**, not at the end of the statement. Midway through the update, row 1 has moved to position 2 while the old row 2 is still there. (The docs point out this is stricter than the SQL standard.)

**Mechanism:** declare the constraint **`DEFERRABLE`**, then defer it in the transactions that need it, so it is checked at `COMMIT` against the final state:

```sql
ALTER TABLE tasks ADD COLUMN position integer;
ALTER TABLE tasks ADD CONSTRAINT tasks_position_uq
  UNIQUE (project_id, position) DEFERRABLE INITIALLY IMMEDIATE;

BEGIN;
SET CONSTRAINTS tasks_position_uq DEFERRED;
UPDATE tasks SET position = 2 WHERE id = $1;
UPDATE tasks SET position = 1 WHERE id = $2;
COMMIT;   -- uniqueness checked here
```

The same mechanism lets you insert two rows that reference each other (circular foreign keys) inside one transaction.

**Edge cases:**
- **The error now comes from `COMMIT`**, not from the `UPDATE`. Code that only wraps the statements in try/catch must also handle a failing commit.
- `NOT NULL` and `CHECK` can't be deferred; only `UNIQUE`, `PRIMARY KEY`, `EXCLUDE` and foreign keys can.
- A deferrable unique constraint **can't be used as an `ON CONFLICT` arbiter**, and the docs warn it can be noticeably slower than an immediate one. Use it only where you need it.
- ORM schema languages often can't declare deferrable constraints (Prisma's can't). SQLAlchemy can (`UniqueConstraint(..., deferrable=True, initially="IMMEDIATE")`), but Alembic's autogenerate doesn't reliably detect changes to these options, so add or change them in an explicit migration.

### 9.11 Soft deletes and their pitfalls ➕

Section 9.7 mentions soft deletes as a safer alternative to `CASCADE`. They solve accidental data loss, but each one quietly removes a guarantee the database gave you for free.

#### 9.11.1 The mechanism ➕
**Problem:** a user deletes a project by mistake and support can't bring it back. Auditors want to see what existed last month.

**Mechanism:** instead of `DELETE`, set a timestamp, and treat rows with a value as gone:

```sql
ALTER TABLE projects ADD COLUMN deleted_at timestamptz;
UPDATE projects SET deleted_at = now() WHERE id = $1 AND deleted_at IS NULL;
```

Everything below is a guarantee that stops working once you do this.

#### 9.11.2 Pitfall: unique constraints still see deleted rows ➕
**Why:** the `UNIQUE` index on `users.email` contains soft-deleted rows too, so someone who deleted their account can never sign up again with the same email.

**Fix:** make uniqueness apply only to live rows with a partial unique index (9.10.2 ➕):

```sql
ALTER TABLE users DROP CONSTRAINT users_email_key;
CREATE UNIQUE INDEX users_email_live_uq ON users (lower(email)) WHERE deleted_at IS NULL;
```

#### 9.11.3 Pitfall: every query must remember the filter ➕
**Why:** the database no longer hides deleted rows; your code does. One forgotten `AND deleted_at IS NULL` in a report, a join or a new endpoint shows deleted data, which can be a privacy incident.

**Fix:** centralise the filter. A view gives raw SQL one place to read from, and a partial index keeps live-row queries fast:

```sql
CREATE VIEW live_projects AS SELECT * FROM projects WHERE deleted_at IS NULL;
CREATE INDEX idx_projects_owner_live ON projects (owner_id) WHERE deleted_at IS NULL;
```

With SQLAlchemy, a `do_orm_execute` event plus `with_loader_criteria` can add the filter to every ORM `SELECT` on the model, so a new endpoint can't forget it:

```python
from sqlalchemy import event
from sqlalchemy.orm import Session, with_loader_criteria


@event.listens_for(Session, "do_orm_execute")
def _hide_soft_deleted(execute_state) -> None:
    if execute_state.is_select and not execute_state.execution_options.get("include_deleted", False):
        execute_state.statement = execute_state.statement.options(
            with_loader_criteria(Project, Project.deleted_at.is_(None), include_aliases=True)
        )

# opt out explicitly where deleted rows are wanted (admin, audit):
# await session.execute(select(Project).execution_options(include_deleted=True))
```

#### 9.11.4 Pitfall: foreign keys and cascades stop meaning anything ➕
**Why:** a soft-deleted project is still a real row, so `tasks.project_id` still points at it, `ON DELETE CASCADE` never fires, and nothing stops a new task being added to a deleted project.

**Fix:** soft-delete the children in the **same transaction** as the parent, and check the parent's state in the write paths that create children (`INSERT ... SELECT ... WHERE EXISTS (SELECT 1 FROM projects WHERE id = $1 AND deleted_at IS NULL)`).

#### 9.11.5 Pitfall: privacy law and unbounded growth ➕
**Why:** "deleted" data is still stored, still in backups, and still returned to anyone who forgets the filter. Regulations such as GDPR give users a right to erasure, which a soft delete doesn't satisfy. Meanwhile the table and its indexes grow forever.

**Alternative: move rows to an archive table** in one atomic statement, keeping the live table clean and the archive easy to purge on a schedule:

```sql
WITH gone AS (
  DELETE FROM projects WHERE id = $1 RETURNING *
)
INSERT INTO projects_archive SELECT gone.*, now() AS archived_at FROM gone;
```

Real `DELETE` means FKs and cascades work again (tasks are removed or blocked as the schema says), so archive the children first if you need them.

## 10. Seeding test data 🎓

**Problem:** in production, data arrives through real user flows (sign-up forms, creating projects). During development you need realistic data **now** to test queries and endpoints.

**Mechanism: seeding**, a script that inserts test data. Best practice is a **separate migration file** (`dbmate new seed_data`), which sorts after the schema migration because its timestamp is larger.

The lesson's seed uses **CTEs** (common table expressions, `WITH name AS (...)`) chained with **`RETURNING`**, so the ids that Postgres generates in one insert feed the next insert without hard-coding UUIDs:

```sql title="db/migrations/20240102000000_seed_data.sql"
-- migrate:up
WITH inserted_users AS (
  INSERT INTO users (email, full_name, password_hash) VALUES
    ('john@example.com',  'John Doe',    'hash1'),
    ('jane@example.com',  'Jane Smith',  'hash2'),
    ('alice@example.com', 'Alice Brown', 'hash3')
  RETURNING id, email
),
inserted_profiles AS (
  INSERT INTO user_profiles (user_id, avatar_url, bio, phone)
  SELECT id,
         'https://example.com/avatar.png',
         CASE email
           WHEN 'john@example.com' THEN 'Backend engineer'
           WHEN 'jane@example.com' THEN 'Product manager'
           ELSE 'Designer'
         END,
         '+1-555-0100'
  FROM inserted_users
  RETURNING user_id
)
INSERT INTO projects (name, description, owner_id)
SELECT 'Project of ' || email, 'Seeded project', id FROM inserted_users;

-- migrate:down
TRUNCATE project_members, tasks, projects, user_profiles, users;
```

After `dbmate up`, every table has rows to query.

🔧 **Edge case:** if seed data lives in a migration, it also runs in **production** unless you stop it. Common approaches: keep seeds in a separate folder run only by a `python -m scripts.seed` command, or guard them with an environment check. The `TRUNCATE` down migration above would be dangerous on a real database.

### 11.1 `GET /v1/users`: list users with their profiles

**Requirement:** each user should arrive with their profile **embedded**, in **one API call** (the frontend shouldn't make a second request per user), from **one database call**.

How the lesson builds the query:
1. **Start writing from `FROM`, not `SELECT`.** Decide where the data comes from first.
2. **Alias tables** (`users u`, `user_profiles up`) so you can refer to them briefly.
3. **Join on the foreign key:** `u.id = up.user_id`.
4. **`LEFT JOIN`, not `INNER JOIN`.** A user who never edited their profile has **no** `user_profiles` row. An inner join only returns rows that match on **both** sides, so that user would vanish from the list. A left join keeps every row from the left table (`users`) and fills the right side with nulls when there's no match. (Inner and left joins are the two you'll use most.)
5. **`to_jsonb(up.*)`** turns the whole matching profile row into one JSON object, returned as a `profile` column.
6. **Always `ORDER BY`.** A relational database returns rows in **no guaranteed order**. List endpoints should sort by default; here, newest first.

```sql
SELECT u.*, to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
ORDER BY u.created_at DESC;
```

<Mermaid chart={`flowchart LR

  P["user_profiles<br/>John, Jane"] --> J

  J --> R2["Jane + profile"]
  J --> R3["Alice + profile NULL<br/>kept because LEFT"]
  J -.->|"INNER JOIN would drop"| R3`} />

**What the demo shows:** every column of `users` plus a `profile` JSON column containing the profile fields. After serialization (a `dict` / Pydantic model step in Python, a struct mapping step in Go) this is the response of `GET /v1/users`.

🔧 **Two production fixes to this query:**
- **Don't send `password_hash` to the frontend.** `u.*` includes it. Name the columns you return.
- **Pick the JSON keys explicitly** with `jsonb_build_object`, so adding a column to `user_profiles` later doesn't silently change your API contract.

```sql
SELECT u.id, u.email, u.full_name, u.created_at,
       CASE WHEN up.user_id IS NULL THEN NULL
            ELSE jsonb_build_object('avatarUrl', up.avatar_url, 'bio', up.bio, 'phone', up.phone)
       END AS profile
FROM users u
LEFT JOIN user_profiles up ON up.user_id = u.id
ORDER BY u.created_at DESC, u.id DESC;
```

The `u.id` tie-breaker matters for pagination (11.4): two users created in the same microsecond must still have a stable order.

### 11.2 `GET /v1/users/:userId` and parameterized queries 🎓

Same query, plus `WHERE u.id = $1`. The interesting part is **how the id gets into the query**.

**Problem: SQL injection.** If you build SQL by **concatenating strings**, user input becomes part of the SQL **code**:

```python
# ❌ never do this
sql = f"SELECT * FROM users WHERE id = '{user_id}'"   # user_id straight from the URL
# attacker sends:  x'; DELETE FROM users; --
# database receives: SELECT * FROM users WHERE id = 'x'; DELETE FROM users; --'
```

**Why it happens (first principles):** the database receives **one string** and has to parse it to find out what's code and what's data. If the data contains quote characters and SQL keywords, the parser can't tell they came from the user.

**Mechanism: parameterized queries.** You send the SQL text with **empty slots** (`$1`, `$2` in Postgres) and send the **values separately**. The lesson's framing: the value goes into the slot as plain data and is never given the power to act as SQL. 🔧 More precisely, with the Postgres extended protocol the query text is **parsed and planned before the values arrive**. The values travel in a separate message and are bound as data of the column's type, so `x'; DELETE ...` is simply a (non-matching) string, never executed.

<Mermaid chart={`flowchart TD
  subgraph Concat["String concatenation"]
    A1["SQL + user input glued into one string"] --> A2["Parser sees attacker's DELETE as code"] --> A3["Data destroyed"]
  end
  subgraph Param["Parameterized query"]
    B1["Parse: SELECT ... WHERE id = $1"] --> B2["Plan is fixed: one comparison"]
    B3["Bind: $1 = user input as a value"] --> B2
    B2 --> B4["Input can only ever be compared, never executed"]
  end`} />

In the TablePlus demo, the parameter is written as a named slot and the GUI prompts for its value (wrapped in single quotes because it's a string). In real code, your **driver or ORM** fills the slots. The id flows **route → handler → service → repository**, and the repository passes it as a parameter.

```python title="users/repository.py (asyncpg)"
async def find_user_with_profile(pool: asyncpg.Pool, user_id: UUID) -> asyncpg.Record | None:
    return await pool.fetchrow(
        """
        SELECT u.id, u.email, u.full_name, u.created_at, to_jsonb(up.*) AS profile
        FROM users u
        LEFT JOIN user_profiles up ON up.user_id = u.id
        WHERE u.id = $1
        """,
        user_id,                    # values travel separately from the SQL text
    )                               # None → handler returns 404
```

🔧 ORMs parameterize for you: with SQLAlchemy, `await session.get(User, user_id)` or `select(User).where(User.id == user_id)` always sends the value as a bound parameter. Their **raw** escape hatches are where injection creeps back in: `text("... WHERE id = :id")` with `{"id": user_id}` is safe, `text(f"... WHERE id = '{user_id}'")` is not. psycopg 3 has the same split: `cur.execute("... WHERE id = %s", (user_id,))` is safe, an f-string is not.

🔧 **Edge case:** if `user_id` isn't a valid UUID, Postgres throws `invalid input syntax for type uuid` (SQLSTATE `22P02`), which becomes a 500 unless you **validate the param** in the handler and return 400 or 404. In FastAPI, typing the path parameter as `user_id: UUID` does that validation before the handler runs (asyncpg also refuses a non-UUID string for a `uuid` parameter on the client side).

### 11.3 Dynamic filtering and sorting 🎓
List endpoints usually accept query parameters. The lesson's design for `GET /v1/users`:

| Query param | Meaning | Default |
|---|---|---|
| `page` | which page (starts at 1 for the user) | 1 |
| `limit` | rows per page | 10 (or 20) |
| `letter` | filter: names starting with this letter | not applied |
| `sortBy` | one of an **allowed list**: `full_name`, `email`, `created_at` | `created_at` |
| `sortOrder` | `asc` or `desc` | `desc` |

Key rules:
- **An absent filter isn't sent as null.** The backend checks whether the param is present and **only adds that `WHERE` condition if it is**. The query is built dynamically.
- **Sorting is restricted to an allow-list** of columns; the user can't sort by any field they like.
- **List endpoints should almost always be paginated.**

The filter: `u.full_name ILIKE $1 || '%'`. `ILIKE` is the case-insensitive version of `LIKE`, and `%` matches "anything after", so `J` matches John Doe and Jane Smith.

**What the demo shows:** `J` returns John Doe and Jane Smith; `x` returns nothing; `a` returns Alice Brown. Sorting by `u.email` descending gives John then Jane; ascending flips it. (The sort column has to be written with the same alias as the query, `u.email`.)

🔧 **An important correction for real code: you can't parameterize identifiers or keywords.** Parameters stand for **values only**. If you send `ORDER BY $1 $2` with `$1 = 'u.email'` through a real driver, either the statement fails to parse (`$2` can't be a keyword like `DESC`) or Postgres sorts by the **constant string** `'u.email'`, which is the same for every row, so nothing is sorted. GUIs like TablePlus substitute text before sending, which is why it seems to work in the demo. The safe mechanism is to **map the user's choice through an allow-list** to a hard-coded SQL fragment:

```python title="list_users.py"
import re

import asyncpg

SORT_COLUMNS = {"full_name": "u.full_name", "email": "u.email", "created_at": "u.created_at"}


def _int_or(value: str | None, default: int) -> int:
    try:
        return int(value) if value else default
    except ValueError:
        return default


async def list_users(pool: asyncpg.Pool, q: dict[str, str]) -> list[asyncpg.Record]:
    page = max(1, _int_or(q.get("page"), 1))
    limit = min(100, max(1, _int_or(q.get("limit"), 10)))          # cap it: limit=1000000 is a DoS
    sort_col = SORT_COLUMNS.get(q.get("sortBy", ""), SORT_COLUMNS["created_at"])  # identifier from allow-list only
    sort_dir = "ASC" if q.get("sortOrder") == "asc" else "DESC"      # keyword from a fixed set only

    where: list[str] = []
    values: list[object] = []
    if letter := q.get("letter"):
        escaped = re.sub(r"([\\%_])", r"\\\1", letter[:1])            # user's % or _ must not act as wildcards
        values.append(escaped + "%")
        where.append(f"u.full_name ILIKE ${len(values)}")

    values += [limit, (page - 1) * limit]
    where_sql = f"WHERE {' AND '.join(where)}" if where else ""
    sql = f"""
        SELECT u.id, u.email, u.full_name, u.created_at, to_jsonb(up.*) AS profile
        FROM users u
        LEFT JOIN user_profiles up ON up.user_id = u.id
        {where_sql}
        ORDER BY {sort_col} {sort_dir}, u.id {sort_dir}
        LIMIT ${len(values) - 1} OFFSET ${len(values)}"""

    return await pool.fetch(sql, *values)
```

In a FastAPI handler, a Pydantic query model (`sortBy: Literal["full_name", "email", "created_at"] = "created_at"`, `limit: int = Field(10, ge=1, le=100)`) does the parsing and clamping before this function is called; the allow-list mapping stays here anyway, because the repository shouldn't trust its caller.

Only **values** (`letter`, `limit`, `offset`) are parameters; **identifiers and keywords** come from code you wrote.

### 11.4 Pagination with `LIMIT` and `OFFSET` 🎓
- `LIMIT n` returns at most n rows; `OFFSET k` skips the first k rows.
- The **user's page starts at 1**, but the **database offset starts at 0**. The backend translates between them.

**What the demo shows:** with the `J` filter (two results) and `limit = 1`: offset 0 returns Jane Smith, offset 1 returns John Doe.

🔧 With a limit above 1 the translation is `offset = (page - 1) × limit`, not `page - 1`. The demo's limit of 1 makes the two coincide.

🔧 **Two problems with OFFSET at scale and the mechanism that fixes them:**
1. **It gets slower with each page.** The skipped rows still have to be produced and thrown away inside the server, so page 10,000 reads about 100,000 rows to return 10.
2. **Rows shift between requests.** If a new user signs up while someone is on page 1, every row moves down by one and page 2 repeats a row.

**Keyset (cursor) pagination** remembers the **last row's sort key** and asks for rows after it. With an index on the sort key, each page is an index seek, so page 10,000 costs the same as page 1, and inserts don't shift anything.

```sql
-- first page
SELECT id, full_name, created_at FROM users ORDER BY created_at DESC, id DESC LIMIT 10;

-- next page: $1, $2 = created_at and id of the last row the client received
SELECT id, full_name, created_at FROM users
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

The trade-off: you can't jump straight to "page 37". That's fine for infinite scroll and feeds; offset is fine for small admin tables.

### 11.5 `POST /v1/users`: create 🎓
A plain `INSERT` with parameters, and **`RETURNING *`** so the database sends back the created row (with its generated `id`, `created_at` and so on) in the same round trip. The password hash is computed in the backend before the insert.

```sql
INSERT INTO users (email, full_name, password_hash)
VALUES ($1, $2, $3)
RETURNING *;
```

**What the demo shows:** inserting `test@gmail.com` returns one row, and the users table now contains it.

### 11.6 `PATCH /v1/users/:userId/profile`: partial update 🎓
**Requirement:** the profile form lets the user change any subset of `bio`, `phone`, `avatar_url`. **Only the fields that were sent are updated**; the rest stay untouched.

**Mechanism:** the backend checks which allowed fields are present in the payload and builds the `SET` clause from just those. If the user sent `bio` and `phone`, the constructed query is:

```sql
UPDATE user_profiles
SET bio = $1, phone = $2
WHERE user_id = $3
RETURNING *;
```

🔧 A generic, injection-safe builder (again: column names from an allow-list, values as parameters):

```python title="update_profile.py"
UPDATABLE = {"bio": "bio", "phone": "phone", "avatar_url": "avatar_url"}  # payload key -> column


async def update_profile(pool: asyncpg.Pool, user_id: UUID, patch: dict[str, str | None]) -> asyncpg.Record:
    sets: list[str] = []
    values: list[object] = []
    for key, column in UPDATABLE.items():
        if key in patch:                                   # present (even if None) → update it
            values.append(patch[key])
            sets.append(f"{column} = ${len(values)}")
    if not sets:
        raise BadRequestError("Nothing to update")
    values.append(user_id)
    row = await pool.fetchrow(
        f"UPDATE user_profiles SET {', '.join(sets)} WHERE user_id = ${len(values)} RETURNING *",
        *values,
    )
    if row is None:
        raise NotFoundError("Profile not found")
    return row
```

With Pydantic, `patch = body.model_dump(exclude_unset=True)` gives exactly this dict: only the fields the client actually sent, including the ones it sent as `null`.

🔧 **Edge cases:**
- **"Absent" vs "null" are different intents.** `{}` means don't touch; `{ "bio": null }` means clear the bio. Check with `key in patch` (or `exclude_unset=True`), not `patch.get("bio") is not None`.
- The user may have **no profile row yet** (that's why the list query used a LEFT JOIN). An `UPDATE` would match 0 rows. An **upsert** creates or updates in one atomic statement: `INSERT INTO user_profiles (user_id, bio) VALUES ($1, $2) ON CONFLICT (user_id) DO UPDATE SET bio = EXCLUDED.bio RETURNING *;`

**What the demo shows:** the bio and phone change, but **`updated_at` is still equal to `created_at`**. Nothing updated it. That's the next problem.

### 11.7 Upserts, `RETURNING` and CTE pitfalls ➕

The page already uses `ON CONFLICT` (9.9, 11.6) and the seed chains CTEs with `RETURNING` (section 10). Both are everyday tools in API code, and both have rules that surprise people in production.

#### 11.7.1 How `ON CONFLICT` decides, and why it beats "check, then write" ➕
**Problem:** "create the profile if missing, otherwise update it" written as `SELECT`, then `INSERT` or `UPDATE`, sometimes fails with a unique violation under load. Catching `23505` and then running an `UPDATE` is also racy, because the conflicting row can be deleted in between.

**Why it happens:** two separate statements leave a gap in which another transaction can act. Only a single statement that is atomic with respect to the unique index closes it.

**Mechanism:** `INSERT ... ON CONFLICT` uses a **unique index as the arbiter**. For each proposed row, Postgres either inserts it, or finds the existing conflicting row, locks it, and runs the `DO UPDATE` (or skips it with `DO NOTHING`). The docs guarantee one of those two outcomes even under heavy concurrency. Inside `DO UPDATE`, **`EXCLUDED`** is the row you tried to insert.

```sql
INSERT INTO user_profiles (user_id, bio, phone)
VALUES ($1, $2, $3)
ON CONFLICT (user_id) DO UPDATE
  SET bio = EXCLUDED.bio, phone = EXCLUDED.phone
  WHERE user_profiles.bio IS DISTINCT FROM EXCLUDED.bio
     OR user_profiles.phone IS DISTINCT FROM EXCLUDED.phone   -- skip no-op writes
RETURNING *;
```

**Edge cases:**
- The conflict target must match a **unique index or constraint**. For a partial unique index, repeat its `WHERE` (9.10.2 ➕). Deferrable unique constraints can't be arbiters.
- With `DO UPDATE ... WHERE`, rows that fail the condition are **still locked**, just not updated.
- **Sequences and defaults are evaluated before the conflict is detected**, so a conflicting insert still burns a sequence value (more gaps, see 7.1), and `BEFORE INSERT` triggers still run (their effects show up in `EXCLUDED`).
- **ORM "save or update" helpers are often not upserts.** SQLAlchemy's `session.merge()` runs a `SELECT` followed by an `INSERT` or `UPDATE`, so it can raise a unique-constraint error under concurrency (Prisma's `upsert` has the same caveat outside the conditions its docs list). When it matters, use the Postgres dialect's real upsert, `sqlalchemy.dialects.postgresql.insert(...).on_conflict_do_update(...)`, or retry on the error.

#### 11.7.2 "command cannot affect row a second time" ➕
**Problem:** a bulk import upserts 1,000 rows in one statement and fails with `ON CONFLICT DO UPDATE command cannot affect row a second time`.

**Why it happens:** the input itself contains two rows with the **same key**. Postgres refuses to update one existing row twice in a single statement, because the result would depend on processing order.

**Mechanism:** deduplicate the batch before sending it (keep the last occurrence in the app), or in SQL with `DISTINCT ON`:

```sql
INSERT INTO users (email, full_name, password_hash)
SELECT DISTINCT ON (email) email, full_name, password_hash
FROM jsonb_to_recordset($1::jsonb) AS r(email text, full_name text, password_hash text)
ON CONFLICT (email) DO UPDATE SET full_name = EXCLUDED.full_name;
```

Note that `DISTINCT ON` without `ORDER BY` keeps an arbitrary row per key. Add `ORDER BY email, ...` if "which duplicate wins" matters.

#### 11.7.3 What `RETURNING` gives back ➕
**Problem:** the idempotent "add member" from 9.9 uses `ON CONFLICT DO NOTHING RETURNING *`. When the member already exists, the API gets **zero rows** and returns 500 because it expected one.

**Why it happens:** `RETURNING` only returns rows the statement **inserted or updated**. A skipped row produced no output.

**Mechanism, three options:**
1. Treat zero rows as "already existed" and read the row with a follow-up `SELECT`.
2. Use a no-op `DO UPDATE SET role = project_members.role` so the row is always returned. The cost: it writes a new row version, takes a row lock and fires update triggers (section 12's trigger would bump `updated_at`).
3. On **PostgreSQL 18**, `RETURNING` can reference `old` and `new`. For a fresh insert `old` is null, so the API can tell "created" (201) from "updated" (200) in one round trip:

```sql
INSERT INTO user_profiles (user_id, bio) VALUES ($1, $2)
ON CONFLICT (user_id) DO UPDATE SET bio = EXCLUDED.bio
RETURNING new.*, (old.user_id IS NULL) AS created;
```

#### 11.7.4 Data-modifying CTEs share one snapshot ➕
**Problem:** in one statement you `UPDATE` rows in a CTE and then `SELECT` from the same table in the main query, expecting to see the change. You see the old values.

**Why it happens:** all sub-statements in a `WITH` run **with the same snapshot**, conceptually at the same time. They can't see each other's changes to the tables; the docs say the **only** way to pass data between them is `RETURNING`. They also run to completion even if nothing reads their output.

```sql
WITH bumped AS (
  UPDATE tasks SET priority = priority + 1 WHERE project_id = $1 RETURNING id, priority
)
SELECT id, priority FROM tasks WHERE project_id = $1;   -- old priorities: same snapshot
-- correct: SELECT id, priority FROM bumped;
```

That is why the seed in section 10 works: each insert reads the previous one's `RETURNING` output, never the table.

**Edge cases:**
- Two sub-statements must **not modify the same row**. That isn't supported and the result is unpredictable.
- For read-only CTEs, PostgreSQL 12+ **inlines** a CTE referenced once into the main query, so the planner can push filters into it. A CTE referenced more than once is computed once and stored. Use `AS MATERIALIZED` to force computing it once (an "optimization fence"), or `AS NOT MATERIALIZED` to force inlining.

## 12. Triggers: keeping `updated_at` correct automatically 🎓

### Problem
`updated_at` is only useful if it changes on **every** update. Two options:
1. **Manual:** every `UPDATE` in your app also sets `updated_at = now()` (or passes it as a parameter). Easy to forget in one code path or one script, and then the column lies.
2. **Database trigger:** a rule in the database that says "when this event happens, run this action". The database enforces it for every writer.

### Mechanism
A **trigger** has two parts:
1. A **trigger function** (in PL/pgSQL) that sets `NEW.updated_at` to the current time and returns `NEW`. `NEW` is the version of the row about to be written.
2. A **`CREATE TRIGGER`** on each table: **before** each row is updated, call that function.

Because it runs **BEFORE** the row is written and returns the modified `NEW`, the timestamp is part of the same write, with no second update.

<Mermaid chart={`sequenceDiagram
  participant App
  participant PG as Postgres
  participant TF as set_updated_at()
  App->>PG: UPDATE user_profiles SET bio = $1 WHERE user_id = $2
  PG->>PG: build NEW row (bio changed)
  PG->>TF: BEFORE UPDATE FOR EACH ROW
  TF->>TF: NEW.updated_at := now()
  TF-->>PG: RETURN NEW
  PG->>PG: write row with new bio + new updated_at
  PG-->>App: UPDATE 1`} />

```sql title="db/migrations/20240103000000_indexes_and_triggers.sql (trigger part)"
-- migrate:up
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER set_users_updated_at           BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
CREATE TRIGGER set_user_profiles_updated_at   BEFORE UPDATE ON user_profiles
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
CREATE TRIGGER set_projects_updated_at        BEFORE UPDATE ON projects
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
CREATE TRIGGER set_tasks_updated_at           BEFORE UPDATE ON tasks
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
CREATE TRIGGER set_project_members_updated_at BEFORE UPDATE ON project_members
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

-- migrate:down
DROP TRIGGER IF EXISTS set_project_members_updated_at ON project_members;
DROP TRIGGER IF EXISTS set_tasks_updated_at ON tasks;
DROP TRIGGER IF EXISTS set_projects_updated_at ON projects;
DROP TRIGGER IF EXISTS set_user_profiles_updated_at ON user_profiles;
DROP TRIGGER IF EXISTS set_users_updated_at ON users;
DROP FUNCTION IF EXISTS set_updated_at();
```

Each trigger gets a **clear name** so the down migration can drop it precisely.

**What the demo shows:** after `dbmate up`, running the profile update again ("updated bio 3") makes `updated_at` jump to the current date and time of the recording.

🔧 **Details and edge cases:**
- The `BEGIN ... END` in a PL/pgSQL function marks the **function body block**; it does **not** start a new transaction (the video describes it as starting one). The trigger runs inside the transaction of the `UPDATE` that fired it, so if that update rolls back, so does the timestamp.
- `now()` is the **start time of the current transaction**, so every row changed in one transaction gets the same timestamp. Use `clock_timestamp()` if you need the actual wall-clock moment.
- The trigger fires even when an `UPDATE` changes nothing. To skip no-op updates, add a condition: `CREATE TRIGGER ... BEFORE UPDATE ON users FOR EACH ROW WHEN (OLD.* IS DISTINCT FROM NEW.*) EXECUTE FUNCTION set_updated_at();`
- **Don't put business logic in triggers.** It's invisible from application code and hard to test. Small, mechanical invariants like `updated_at` are the sweet spot.

## 13. Indexes 🎓

### Problem
Look again at the list query: it **joins** on `u.id = up.user_id` (an equality condition) and **sorts** by a column. The `GET /users/:id` query **filters** with `WHERE u.id = $1`. Every one of these needs to find specific rows quickly.

### Why it's slow without an index (first principles)
Rows aren't stored on disk in a neat, sorted list. The GUI shows them sequentially, but physically each row sits **somewhere** in the table's files. To find the task whose id is X, the only brute-force option is a **sequential scan**: visit every row, compare its id, and keep going until the end (there could be more matches). With 6 rows that's instant. With a million or a billion rows, it's a lot of disk reads for a single lookup.

### The book analogy
A book's **index page** says "chapter 4 starts on page 54". To read chapter 4 you don't flip through 50 pages; you look it up and jump straight there.

### Mechanism
A database index is a **separate, ordered lookup structure**: for each value of the indexed column, it stores **where the row lives** on disk. A lookup searches the index (fast, because it's ordered and compact), gets the row's location, and reads that one place.

<Mermaid chart={`flowchart TD
  Q["WHERE id = 'X'"] --> C{"index on id?"}
  C -->|no| S["Seq Scan<br/>read every page of the table<br/>compare id on each row<br/>cost grows with N"]
  C -->|yes| I["Index Scan<br/>walk the ordered index to 'X'<br/>get its location: page 812, slot 4"]
  I --> H["read just that heap page"]
  S --> R["result"]
  H --> R`} />

🔧 **What the "ordered lookup table" really is: a B-tree.** Postgres's default index is a **B-tree**: a shallow, wide, balanced tree. Each node is one 8 KB page holding hundreds of keys, so even a billion rows is only about 4 levels deep. A lookup reads root → internal → leaf → table page: a handful of page reads instead of millions. The leaves are kept **in sorted order and linked together**, which is why the same index also serves range queries (`>`, `<`, `BETWEEN`) and `ORDER BY`.

<Mermaid chart={`flowchart TD
  R["root page<br/>keys: M"] --> A["internal page<br/>keys: D, H"]
  R --> B["internal page<br/>keys: R, W"]
  A --> L1["leaf: A..C"]
  A --> L2["leaf: D..G"]
  A --> L3["leaf: H..L"]
  B --> L4["leaf: M..Q"]
  B --> L5["leaf: R..V"]
  B --> L6["leaf: W..Z"]
  L1 --> L2 --> L3 --> L4 --> L5 --> L6
  L3 -.->|"(page, slot) pointer"| T[("table heap row")]`} />

### Sort order 🎓
The second property of an index is its **order** (ascending or descending). `GET /users` sorts by `created_at DESC` by default, so the lesson creates the index as `created_at DESC`. The database can then read rows **already in the required order** instead of collecting everything and sorting.

🔧 Nuance: a single-column B-tree can be read **backwards** just as efficiently, so for one column `DESC` vs `ASC` rarely matters. Direction matters for **multi-column** indexes with **mixed** directions, for example `ORDER BY priority ASC, created_at DESC` needs an index on `(priority ASC, created_at DESC)`.

### When to create an index: the lesson's rule of thumb 🎓
Consider an index on a column when it appears in:
1. a **`WHERE`** clause,
2. a **`JOIN`** condition,
3. an **`ORDER BY`**,

**and** the query runs **frequently** enough that its speed matters.

### Why not index everything? 🎓
Every index is a **second copy of that column's data that must stay in sync**. Every `INSERT` adds an entry to each index on the table, and every `UPDATE` of an indexed column changes index entries. That's extra write work and extra disk. So: create indexes for real, frequent query patterns, **monitor** performance, and **drop** indexes whose queries stopped being frequent.

### Primary keys vs foreign keys 🎓
- **Primary keys are indexed automatically.** `users.id`, `projects.id` need nothing extra.
- **Foreign keys are *not* indexed automatically.** In a join like `projects p LEFT JOIN tasks t ON t.project_id = p.id`, the `p.id` side is already indexed (PK), but `t.project_id` isn't. Index it yourself.

### The lesson's index migration

```sql title="db/migrations/20240103000000_indexes_and_triggers.sql (index part)"
-- migrate:up
CREATE INDEX idx_users_email                ON users (email);             -- lookups/joins by email
CREATE INDEX idx_users_created_at           ON users (created_at DESC);   -- GET /users default sort
CREATE INDEX idx_tasks_project_id           ON tasks (project_id);        -- tasks of a project (join)
CREATE INDEX idx_tasks_assigned_to          ON tasks (assigned_to);       -- tasks of a user (join)
CREATE INDEX idx_tasks_created_at           ON tasks (created_at DESC);   -- GET /tasks default sort
CREATE INDEX idx_tasks_status               ON tasks (status);            -- ?status=pending filter
CREATE INDEX idx_project_members_project_id ON project_members (project_id);
CREATE INDEX idx_project_members_user_id    ON project_members (user_id);

-- migrate:down
DROP INDEX IF EXISTS idx_project_members_user_id;
DROP INDEX IF EXISTS idx_project_members_project_id;
DROP INDEX IF EXISTS idx_tasks_status;
DROP INDEX IF EXISTS idx_tasks_created_at;
DROP INDEX IF EXISTS idx_tasks_assigned_to;
DROP INDEX IF EXISTS idx_tasks_project_id;
DROP INDEX IF EXISTS idx_users_created_at;
DROP INDEX IF EXISTS idx_users_email;
```

The reasoning for each, from the lesson:
- **`users.email`**: an API that finds a user by email, or a join on email.
- **`users.created_at DESC`** and **`tasks.created_at DESC`**: the default "newest first" sort of the list endpoints, which are called often.
- **`tasks.project_id`**: "all tasks of a project" joins `projects.id` (already indexed as PK) with `tasks.project_id` (an FK, not indexed).
- **`tasks.assigned_to`**: "all tasks of a user", the same reasoning with `users.id`.
- **`tasks.status`**: the `GET /tasks?status=pending` filter.
- **`project_members.project_id` / `user_id`**: same logic for membership lookups in both directions.

🔧 **Three of these are redundant or weak, and the reasons are good to know:**
1. **`idx_users_email` duplicates an index you already have.** `email` is `UNIQUE`, and Postgres enforces `UNIQUE` **with a unique index it creates automatically**. The docs say a manual index on a unique column just duplicates it. Drop it (or, better, replace the unique constraint with the `lower(email)` unique index from 9.4).
2. **`idx_project_members_project_id` duplicates the composite primary key.** The PK index on `(project_id, user_id)` is sorted by `project_id` first, so it already serves `WHERE project_id = $1`. A multi-column B-tree helps queries on its **leading** column(s). The `user_id` index **is** needed, because `user_id` is the second column.
3. **`idx_tasks_status` alone has low selectivity.** With only four values, "pending" might be 40% of all tasks, and reading 40% of a table through an index is slower than a sequential scan, so the planner may ignore it. Real queries filter by project too: a **composite** index `(project_id, status)` or a **partial** index serves them far better.

```sql
-- 🔧 better-shaped indexes for the real access patterns
CREATE INDEX idx_tasks_project_status_created ON tasks (project_id, status, created_at DESC);
CREATE INDEX idx_tasks_open ON tasks (assigned_to) WHERE status IN ('pending', 'in_progress'); -- partial: only open tasks
```

### 🔧 Going deeper: proving an index is used with `EXPLAIN`
Never guess; ask the planner. `EXPLAIN` shows the plan; `EXPLAIN ANALYZE` actually runs the query and adds real timings.

```sql
EXPLAIN ANALYZE SELECT * FROM tasks WHERE project_id = '6f1c...';

-- before the index:
--  Seq Scan on tasks  (cost=0.00..2041.00 rows=10 width=120) (actual time=0.015..9.871 rows=10 loops=1)
--    Filter: (project_id = '6f1c...'::uuid)
--    Rows Removed by Filter: 99990

-- after CREATE INDEX idx_tasks_project_id:
--  Index Scan using idx_tasks_project_id on tasks  (cost=0.42..8.60 rows=10 width=120) (actual time=0.021..0.030 rows=10 loops=1)
--    Index Cond: (project_id = '6f1c...'::uuid)
```

How to read it:
- `cost=startup..total` is the planner's **estimate**, in arbitrary units (one sequential page read = 1.0).
- `rows=` is the estimated row count; in `actual time=... rows=... loops=...` the numbers are measured. If estimate and actual are far apart, statistics are stale: run `ANALYZE tasks`.
- `Rows Removed by Filter: 99990` is the signature of a missing index: 99,990 rows read for nothing.
- Add `BUFFERS` (`EXPLAIN (ANALYZE, BUFFERS)`) to see pages served from cache (`shared hit`) vs read from disk (`shared read`).
- On a tiny table (like the 6-row demo) the planner **correctly** prefers a seq scan, since reading one page is cheaper than walking an index. Test on realistic data volumes.

### 🔧 Going deeper: other index types and the `ILIKE` filter
- The list filter `full_name ILIKE 'j%'` usually **can't use a plain B-tree**: the default index uses locale collation rules, and `ILIKE` is case-insensitive. Options: a B-tree on `lower(full_name) text_pattern_ops` and query `lower(full_name) LIKE lower($1) || '%'`, or the `pg_trgm` extension with a **GIN** trigram index, which also handles `%middle%` searches.
- **GIN** indexes also power `jsonb` containment (`@>`) and array queries; **GiST** handles geometric and range types; **BRIN** is a tiny index for huge, naturally ordered tables (logs by time).
- On a live production table, `CREATE INDEX` blocks writes for the whole build. Use **`CREATE INDEX CONCURRENTLY`**, which doesn't block writes but can't run inside a transaction block (so it needs its own migration, with the tool's transaction wrapping turned off for that file).

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY idx_users_full_name_trgm ON users USING gin (full_name gin_trgm_ops);
```

### Index techniques beyond the basics ➕

The lesson's indexes are single-column B-trees, and the notes above name the other index types in one line each. In production, the difference between an index that helps and one that is only write overhead usually comes down to the details below. (Safe index builds on live tables are covered in section 8 ➕.)

#### Partial indexes: index only the rows you query ➕
**Problem:** 95% of tasks are `completed` and nobody queries them on hot paths, yet a full index on `assigned_to` stores an entry for every one of them.

**Mechanism:** a `WHERE` clause on the index keeps only matching rows, so the index is smaller, stays in cache, and is cheaper to maintain (rows outside the predicate never touch it):

```sql
CREATE INDEX idx_tasks_open_by_assignee ON tasks (assigned_to, due_date)
WHERE status IN ('pending', 'in_progress');
```

**Why it sometimes isn't used (first principles):** the planner may only use a partial index if it can **prove** that the query's `WHERE` implies the index's predicate. `WHERE status = 'pending' AND assigned_to = $1` proves it. `WHERE status = $1 AND assigned_to = $2` doesn't, because `$1` could be `'completed'`. That bites with prepared statements: once Postgres switches to a **generic plan** (see "Generic vs custom plans" below), it plans without knowing `$1` and can't use the partial index.

**Edge cases:**
- Write the predicate's values as **literals in the SQL text** (they are constants from your code, not user input), and bind only the truly variable parts.
- The predicate may only use immutable functions, so `WHERE due_date > now()` isn't allowed.

#### Expression indexes: index what you actually compare ➕
**Problem:** `WHERE lower(email) = lower($1)` scans the table even though `email` is indexed.

**Why it happens:** the index stores `email`, not `lower(email)`. To the planner these are different values with different ordering.

**Mechanism:** index the expression itself (section 9.4 did this for uniqueness):

```sql
CREATE INDEX idx_users_email_lower ON users (lower(email));
CREATE INDEX idx_tasks_due_month   ON tasks (date_trunc('month', due_date::timestamp));
```

**Edge cases:**
- The query must use the **same expression**. `lower(email)` matches; `upper(email)` or `email ILIKE $1` doesn't.
- Only **immutable** functions are allowed. That rules out anything depending on the session time zone, such as `date_trunc` on a `timestamptz` (which is why the example casts a `date` to `timestamp`).
- The expression is computed on every insert and update of the row. ANALYZE collects statistics for the expression, which also improves row estimates for queries using it.

#### Covering indexes and index-only scans ➕
**Problem:** an index finds 5,000 matching rows instantly, then the query spends most of its time fetching 5,000 scattered table pages just to read one more column.

**Why it happens:** a normal index scan uses the index to find row locations, then reads the **heap** (table) page for each row to get the other columns, and to check MVCC visibility (section 14.2): the index alone doesn't know whether a row version is visible to your snapshot.

**Mechanism: index-only scans.** If every column the query needs is in the index, and the page is marked **all-visible in the visibility map**, Postgres can answer from the index without touching the heap. The visibility map is a tiny bitmap (the docs say about four orders of magnitude smaller than the table), maintained by VACUUM. `INCLUDE` adds payload columns that are stored in the index but aren't part of the key:

```sql
CREATE INDEX idx_tasks_project_cover ON tasks (project_id, created_at DESC) INCLUDE (title, status);

EXPLAIN (ANALYZE)
SELECT title, status, created_at FROM tasks WHERE project_id = $1 ORDER BY created_at DESC LIMIT 20;
-- Index Only Scan using idx_tasks_project_cover on tasks ...
--   Heap Fetches: 0        <- every page was all-visible, no table reads
```

**Edge cases:**
- **`Heap Fetches` climbing** means the visibility map is out of date: the table is updated faster than VACUUM marks pages all-visible. Tune autovacuum for that table (section 14.3 ➕).
- Supported for B-tree, and for GiST and SP-GiST with some operator classes. **GIN can't do index-only scans.**
- Included columns make the index bigger and, if they change often, cost write work. Include small, stable columns only.

#### GIN: inverted indexes for "contains" queries ➕
**Problem:** "tasks tagged `urgent`" on a `text[]` column, "articles containing a YouTube block" on `jsonb`, or `ILIKE '%term%'` on names. A B-tree orders whole values, so it can't answer "which values **contain** this element".

**Mechanism:** a **GIN** (generalized inverted index) works like the index at the back of a book: for every element (array item, JSON key or value, trigram of a string) it stores the list of rows that contain it. A query looks up each element and intersects the row lists.

```sql
ALTER TABLE tasks ADD COLUMN tags text[] NOT NULL DEFAULT '{}';
CREATE INDEX idx_tasks_tags ON tasks USING gin (tags);

SELECT id, title FROM tasks WHERE tags @> ARRAY['urgent'];   -- uses the GIN index
```

**Edge cases:**
- **Writes are expensive**: one row with 20 tags means 20 index entries. By default GIN uses `fastupdate`, which first appends new entries to a **pending list** and merges them later in bulk. Inserts get cheaper, but searches also have to scan the pending list, so search latency can creep up between merges. VACUUM (and autovacuum) flushes it.
- GIN supports neither ordering nor index-only scans, so `ORDER BY created_at LIMIT 20` on top of a GIN filter still needs a sort. For full-text search at scale, see [Full-text search with Elasticsearch](/docs/backend-first-principles/15-full-text-search-elasticsearch).

#### GiST: ranges, geometry and "nearest" ➕
**Problem:** "which bookings overlap this interval", "which stores are near this point". Neither is a sort order, so B-tree can't help.

**Mechanism:** a **GiST** index is a balanced tree of **bounding boxes**: each internal entry describes a region (a range, a rectangle) that covers everything beneath it, so a search only descends into subtrees whose region can match. It powers range overlap `&&`, geometric containment, the exclusion constraints in 9.10.3 ➕, and nearest-neighbour ordering with the distance operator `<->`.

```sql
CREATE INDEX idx_sessions_during ON work_sessions USING gist (during);
SELECT * FROM work_sessions WHERE during && tstzrange($1, $2);
```

**Edge cases:**
- GiST is often **lossy**: it returns candidates that are then rechecked against the real condition. In `EXPLAIN` this shows up as `Rows Removed by Index Recheck`.
- Updates are slower than B-tree. Use GiST where its operators are needed, not as a general index.

#### BRIN: tiny indexes for huge, append-only tables ➕
**Problem:** an `audit_events` table gains millions of rows a day and is queried by time range. A B-tree on `created_at` is gigabytes in size and slows every insert.

**Why BRIN works (first principles):** rows in an append-only table are physically stored roughly **in insertion order**, so `created_at` rises along with the page number. BRIN (block range index) stores only the **minimum and maximum value per range of pages** (128 pages per range by default). A query for one hour reads the summaries, skips every range whose min/max can't contain the hour, and scans only the few matching ranges.

```sql
CREATE INDEX idx_audit_created_brin ON audit_events USING brin (created_at);

-- is the column physically correlated with storage order? close to 1 or -1 is good
SELECT correlation FROM pg_stats WHERE tablename = 'audit_events' AND attname = 'created_at';
```

**Edge cases:**
- **Useless when values are scattered** (random UUIDs, frequently updated columns): every range's min/max covers almost everything, so nothing is skipped.
- BRIN is lossy by design: it returns whole page ranges that are then filtered. It suits range scans over large spans, not single-row lookups.
- New pages are summarised by VACUUM, or automatically with the `autosummarize` storage parameter.

#### Index bloat and finding indexes that don't earn their cost ➕
**Problem:** the indexes on `tasks` are three times the size of the table, and write latency keeps rising.

**Why it happens:** updates that change indexed columns leave **dead index entries** pointing at dead row versions. VACUUM removes them, but B-tree pages that were split stay allocated, so an index that once grew rarely shrinks. Separately, indexes added for old features keep costing write work long after the feature's queries are gone.

**Mechanism:** measure, then drop or rebuild.

```sql
-- indexes never used since statistics were last reset (check every replica too: stats are per server)
SELECT relname AS table, indexrelname AS index, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

-- rebuild a bloated index without blocking writes (PostgreSQL 12+)
REINDEX INDEX CONCURRENTLY idx_tasks_project_id;
```

**Edge cases:**
- **Don't drop an unused index that enforces a constraint** (primary key, unique), even if `idx_scan` is 0. It exists for correctness, not for reads.
- An index unused on the primary may serve read queries on a replica ([Scaling Part 2](/docs/backend-first-principles/22-scaling-performance-part-2)).
- Indexing a column that changes on every update (like `updated_at`, maintained by the trigger in section 12) also makes every update of the table a non-HOT update (section 14.3 ➕). Index it only if you really query by it.

### Query planning and finding slow queries ➕

The `EXPLAIN` notes above show how to confirm an index is used. Real slow queries are usually about something else: the planner picked the wrong join or scan because its estimates were wrong, or a query is fast alone but runs ten thousand times a minute. This is how to find and diagnose them.

#### Reading `EXPLAIN (ANALYZE, BUFFERS)` like a profiler ➕
**Problem:** a 40-line plan, and you need to know which line is the problem.

**Mechanism: read it as a tree.** Each node pulls rows from its children (indented below it). Start from the most-indented nodes and work up. For each node, compare:
- **estimated `rows` vs actual `rows`.** A gap of 10× or more is the most common root cause of a bad plan, because every decision above that node was made with the wrong numbers.
- **`actual time` × `loops`.** Times and rows are **per loop**. An inner index scan showing 0.05 ms with `loops=20000` costs 1 second in total.
- **`Buffers: shared hit=... read=...`**. `hit` pages came from Postgres's cache, `read` came from the OS or disk. A plan that reads 200,000 buffers to return 20 rows is doing too much work, however fast it looks on a warm cache. Since PostgreSQL 18, `EXPLAIN ANALYZE` includes buffer counts by default.

The join node also tells a story:

| Join | How it works | Good when |
|---|---|---|
| Nested Loop | for each outer row, look up matches in the inner side (ideally via index) | the outer side is small |
| Hash Join | build a hash table from one side, probe it with the other | larger inputs, no useful order |
| Merge Join | walk two inputs already sorted on the join key | both sides come sorted (e.g. from indexes) |

A Nested Loop over an outer side estimated at 10 rows that actually returns 50,000 is the classic bad plan caused by a wrong estimate.

```sql
-- EXPLAIN ANALYZE really executes the statement: wrap writes in a transaction you roll back
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE tasks SET status = 'cancelled' WHERE project_id = $1;
ROLLBACK;
```

**Edge cases:**
- `Sort Method: external merge  Disk: ...` means the sort didn't fit in `work_mem` and spilled to disk. Either add an index that provides the order, or raise `work_mem` **for that session**, not globally (section 14.7 ➕ explains why).
- Plans on a laptop with 100 rows say nothing about production. Use realistic data, or run `EXPLAIN` (without `ANALYZE`) against production.

#### Statistics: why the planner's estimates go wrong ➕
**Problem:** a query that filters `WHERE project_id = $1 AND assigned_to = $2` is estimated at 1 row, actually returns 3,000, and gets a terrible nested loop.

**Why it happens (first principles):** the planner doesn't look at your data when planning; it reads **statistics** that `ANALYZE` collected from a sample: per column, the most common values with their frequencies, a histogram, and the number of distinct values (visible in `pg_stats`). Two limits cause most bad estimates:
1. **Staleness.** After a big import or delete, statistics describe the old data until autovacuum's ANALYZE runs (by default once about 10% of the table has changed).
2. **Independence.** For multiple conditions, the planner **multiplies** their selectivities as if the columns were independent. If tasks in a project are mostly assigned to that project's few members, the columns are correlated, and the product is far too small.

**Mechanism:**

```sql
ANALYZE tasks;                                                    -- refresh now, e.g. after a bulk load

ALTER TABLE tasks ALTER COLUMN assigned_to SET STATISTICS 500;   -- more detail for a skewed column (default target is 100)

CREATE STATISTICS tasks_project_assignee (dependencies, ndistinct, mcv)
  ON project_id, assigned_to FROM tasks;                          -- teach the planner about the correlation
ANALYZE tasks;
```

**Edge cases:**
- Functional-dependency statistics only help **equality and `IN`** conditions with constants; the docs note they aren't used for ranges or `LIKE`.
- A bulk-load script should run `ANALYZE` itself before the app starts querying the new data.

#### `pg_stat_statements`: finding the queries worth fixing ➕
**Problem:** the database CPU sits at 90%, and no single request looks slow.

**Why it happens:** the expensive queries are often the **frequent** ones, not the slowest. A 2 ms query run 50,000 times a minute costs more than a 3-second report run once an hour. Per-request logs don't show that total.

**Mechanism:** the `pg_stat_statements` extension records every statement **normalised** (constants replaced by `$1`, `$2`, so all calls of one query are grouped) with call counts, total and mean time, rows and buffer usage. It must be loaded at server start (`shared_preload_libraries`); most managed Postgres services enable it.

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT left(query, 100)                        AS query,
       calls,
       round(total_exec_time::numeric, 0)     AS total_ms,
       round(mean_exec_time::numeric, 2)      AS mean_ms,
       rows / nullif(calls, 0)                AS rows_per_call,
       round(100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS cache_hit_pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

SELECT pg_stat_statements_reset();   -- start a fresh measurement window after a fix
```

Work down the list: each top entry gets the `EXPLAIN (ANALYZE, BUFFERS)` treatment above. A high `calls` count with tiny `rows_per_call` often points to an **N+1 pattern** in application code (one query per item in a loop), and the fix is to batch it into one query with a join or `WHERE id = ANY($1)`.

**Edge cases:**
- It shows **what** is expensive, not **why**. For the plan of a slow call in production, the `auto_explain` module can log plans of statements over a duration threshold.
- Seeing other users' query text needs superuser or the `pg_read_all_stats` role.

#### Generic vs custom plans for prepared statements ➕
**Problem:** a query is fast for its first five calls, then suddenly slow for some users, with no deploy and no data change.

**Why it happens:** for a prepared statement, Postgres plans the **first five executions** with the actual parameter values (custom plans). Then it builds a **generic plan** without knowing the values, and keeps using it if its estimated cost isn't much worse than the average custom plan. With skewed data, a generic plan that suits the average project can be terrible for the one project with a million tasks. Drivers that use prepared statements hit this, and Python's async drivers do so by default: asyncpg prepares **every** query and keeps it in a per-connection statement cache (100 statements by default), and psycopg 3 prepares a query once it has run `prepare_threshold` times (5 by default) on a connection. SQLAlchemy's `postgresql+asyncpg` dialect uses asyncpg's prepared statements the same way.

```python
# asyncpg: this text is prepared once per connection and reused on every later call
rows = await pool.fetch("SELECT * FROM tasks WHERE project_id = $1", project_id)

# the knobs, if you need them:
# asyncpg.create_pool(dsn, statement_cache_size=0)      # no reuse of prepared statements
# psycopg.AsyncConnection.connect(dsn, prepare_threshold=None)  # never prepare
```

**Mechanism:** confirm by comparing `EXPLAIN` for the prepared statement with real values, then, if the generic plan is the culprit, force re-planning per execution for that role or session:

```sql
ALTER ROLE reporting_app SET plan_cache_mode = force_custom_plan;   -- or SET plan_cache_mode in one session
```

**Edge cases:**
- `force_custom_plan` costs planning time on every call. Use it where data skew is real, not globally.
- This is also why partial indexes with parameterised predicates stop being used after a few calls (see above).

## 14. 🔧 Going deeper: transactions, isolation and MVCC

The lesson raises the concurrency problem (section 4.3) but doesn't cover the machinery. Here it is, because every backend relies on it.

### 14.1 Transactions (ACID)
**Problem:** "create a project and add its owner as a member" is two `INSERT`s. If the server crashes between them, you have a project with no owner membership.

**Mechanism:** wrap them in a **transaction**: `BEGIN; ... COMMIT;`. Either **all** statements take effect or **none** do (`ROLLBACK`, or automatically on error).
- **Atomicity:** all or nothing.
- **Consistency:** constraints hold at commit.
- **Isolation:** concurrent transactions don't see each other's half-done work.
- **Durability:** once `COMMIT` returns, the change survives a crash (it's in the WAL on disk).

```python title="create_project.py (asyncpg)"
async def create_project(pool: asyncpg.Pool, owner_id: UUID, name: str) -> asyncpg.Record:
    async with pool.acquire() as conn:          # a transaction must stay on ONE connection
        async with conn.transaction():          # BEGIN ... COMMIT, or ROLLBACK if anything raises
            project = await conn.fetchrow(
                "INSERT INTO projects (name, owner_id) VALUES ($1, $2) RETURNING *", name, owner_id
            )
            await conn.execute(
                "INSERT INTO project_members (project_id, user_id, role) VALUES ($1, $2, 'owner')",
                project["id"], owner_id,
            )
            return project
    # leaving `acquire()` always returns the connection to the pool
```

The classic bug here: calling `pool.execute("BEGIN")` and then `pool.execute(...)` again. Each pool-level call may use a **different connection**, so the statements aren't in the same transaction. SQLAlchemy's equivalent is `async with session.begin(): ...` on an `AsyncSession` (one session = one connection for the transaction):

```python title="create_project.py (SQLAlchemy 2.x async)"
async def create_project(session_factory: async_sessionmaker[AsyncSession], owner_id: UUID, name: str) -> Project:
    async with session_factory() as session, session.begin():   # COMMIT on success, ROLLBACK on error
        project = Project(name=name, owner_id=owner_id)
        session.add(project)
        await session.flush()                                    # INSERT now so project.id is known
        session.add(ProjectMember(project_id=project.id, user_id=owner_id, role="owner"))
    return project
```

### 14.2 MVCC: how readers and writers don't block each other
**Problem:** if a long report reads the `tasks` table while users keep updating tasks, should the report wait? Should the updates wait?

**Mechanism: Multi-Version Concurrency Control.** An `UPDATE` in Postgres doesn't overwrite the row in place. It writes a **new version** of the row and marks the old one as replaced by that transaction. Each statement (or transaction) works from a **snapshot**: it sees the versions that were committed when the snapshot was taken. So **reading never blocks writing and writing never blocks reading**. Only two writers to the **same row** wait for each other (the row lock from section 4.3).

🔧 **Consequence:** old row versions pile up until **VACUUM** removes them (autovacuum does this in the background). Heavy update workloads, or a transaction left open for hours, cause **bloat**. Keep transactions short and never leave one open while waiting on a network call.

### 14.3 VACUUM, autovacuum and transaction ID wraparound ➕

14.2 ends with "VACUUM reclaims old versions later". How it does that, what stops it, and the one failure that can force the whole database to stop accepting writes are things every backend engineer running Postgres eventually meets.

#### 14.3.1 Dead tuples and what VACUUM actually does ➕
**Problem:** a `tasks` table with 1 million live rows takes 6 GB on disk, and sequential scans keep getting slower although the row count hasn't changed.

**Why it happens (first principles):** with MVCC every `UPDATE` writes a new row version and every `DELETE` only marks the old one as deleted. The old versions (**dead tuples**) stay on their pages until nobody can see them any more. Scans still read those pages, so the table **bloats**.

**Mechanism:** plain `VACUUM` finds versions that are invisible to every running transaction and marks their space as **reusable** for future inserts and updates on that table. It also updates the **visibility map** (needed for index-only scans, section 13 ➕) and runs alongside normal reads and writes (`SHARE UPDATE EXCLUSIVE` lock). It does **not** return the space to the operating system, except for empty pages at the very end of the file.

`VACUUM FULL` rewrites the table compactly and does give space back, but it takes **`ACCESS EXCLUSIVE`** for the whole rewrite (no reads, no writes) and needs room for a full extra copy. The docs advise avoiding it in favour of regular vacuuming. If a production table really must shrink online, teams use the third-party `pg_repack` extension.

```sql
-- how much dead weight does each table carry, and when was it last vacuumed?
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

#### 14.3.2 When autovacuum runs, and tuning it per table ➕
**Problem:** autovacuum is on (the default), yet a hot table still bloats.

**Why it happens:** autovacuum vacuums a table once its dead tuples exceed **`autovacuum_vacuum_threshold` + `autovacuum_vacuum_scale_factor` × rows**, which defaults to 50 + 20% of the table. For a 50-million-row table that's 10 million dead tuples before anything happens. (PostgreSQL 18 adds `autovacuum_vacuum_max_threshold`, default 100 million, as an upper cap.) ANALYZE runs on its own threshold, 10% of the table by default. Autovacuum also throttles itself so it doesn't hog I/O, so on a heavily updated table it can fall behind.

**Mechanism: tune the big, busy tables individually** with storage parameters, so they get vacuumed after a fixed fraction instead of 20%:

```sql
ALTER TABLE tasks SET (
  autovacuum_vacuum_scale_factor  = 0.01,   -- vacuum after ~1% of rows are dead
  autovacuum_analyze_scale_factor = 0.02
);
```

**Edge cases:**
- **Never disable autovacuum** to "save I/O". Bloat grows, statistics go stale, and wraparound protection (14.3.5 ➕) eventually runs anyway, at the worst time.
- Insert-only tables (logs, events) also need vacuuming, for the visibility map and freezing. Postgres has separate insert-based thresholds for that.

#### 14.3.3 What blocks cleanup: the oldest snapshot ➕
**Problem:** autovacuum runs every minute on `tasks`, but `n_dead_tup` never drops.

**Why it happens:** VACUUM can only remove versions that **no transaction can still see**. One session that opened a transaction an hour ago (a report, a forgotten `BEGIN`, a debugging session in a GUI) holds an old snapshot, and every row version created since then must be kept for it. The same happens with an abandoned replication slot, or a replica with `hot_standby_feedback` running long queries.

**Mechanism: find and limit long transactions.**

```sql
SELECT pid, usename, state, now() - xact_start AS tx_age, left(query, 80) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 5;
```

```sql
-- server-side safety nets for the application role
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '60s';  -- kill sessions idle inside a transaction
ALTER ROLE app_user SET transaction_timeout = '5min';                 -- PostgreSQL 17+: cap any transaction
```

In application code, the usual cause is awaiting something slow **inside** a transaction:

```python
async with pool.acquire() as conn, conn.transaction():
    await conn.execute("UPDATE orders SET status = $1 WHERE id = $2", "paying", order_id)
    await payment_provider.charge(order)   # ❌ seconds or minutes with a transaction open
```

Do the network call before or after, and keep the transaction to database work only. (A connection acquired without `async with` and never released has the same effect if it was left inside a transaction.)

#### 14.3.4 HOT updates and `fillfactor` ➕
**Problem:** updating only `status` on a task still writes entries into every index on `tasks`, so updates get slower with every index you add.

**Why it happens:** a new row version normally has a new physical location, so every index needs an entry pointing at it.

**Mechanism: Heap-Only Tuple (HOT) updates.** If an update changes **no indexed column** (BRIN indexes don't count) **and** the new version fits on the **same page**, Postgres chains the new version from the old one on that page and adds no index entries at all. Dead versions in HOT chains can even be cleaned up during ordinary page access, without waiting for VACUUM. Leaving free space on each page makes HOT more likely:

```sql
ALTER TABLE tasks SET (fillfactor = 85);   -- new pages keep 15% free for updated versions

-- how many updates were HOT?
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables WHERE relname = 'tasks';
```

**Edge cases:**
- `fillfactor` only affects pages written after the change; existing pages are filled as they are.
- An index on a frequently updated column (such as `updated_at`) makes **every** update non-HOT. That's a real cost to weigh before adding such an index.

#### 14.3.5 Transaction ID wraparound ➕
**Problem:** a busy database suddenly rejects every write with `database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`.

**Why it happens (first principles):** each writing transaction gets a **32-bit transaction ID** (XID), and row versions record the XIDs that created and deleted them. Visibility compares XIDs with circular arithmetic: from any XID, about 2 billion are "in the past" and 2 billion "in the future". If an old row's creating XID fell more than 2 billion behind, it would suddenly look like it comes from the future, and the row would vanish. To prevent that, VACUUM **freezes** old rows, marking them as visible to everyone regardless of XID.

**Mechanism and the safety levels:**
- When a table's oldest unfrozen XID is older than **`autovacuum_freeze_max_age`** (default 200 million), autovacuum starts an **anti-wraparound vacuum** on it, even if autovacuum is otherwise disabled.
- At **`vacuum_failsafe_age`** (default 1.6 billion), VACUUM skips non-essential work to finish freezing as fast as possible.
- With **40 million** XIDs left, the server logs warnings. With **3 million** left, it refuses to assign new XIDs: no writes until the database is vacuumed.

```sql
-- how close is each database? Alert well before 1 billion.
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY xid_age DESC;
```

**Edge cases:**
- Wraparound trouble is almost always caused by something **blocking** VACUUM: a long transaction, an abandoned replication slot, or a prepared transaction left open (14.3.3 ➕).
- Anti-wraparound autovacuum doesn't step aside for other lock requests, so a migration that needs `ACCESS EXCLUSIVE` will wait behind it. That's the lock queue from section 8 ➕, and why migrations set `lock_timeout`.

### 14.4 Isolation levels in Postgres

| Level | What you're protected from | Typical use |
|---|---|---|
| **Read Committed** (default) | Dirty reads. Each **statement** gets a fresh snapshot, so two `SELECT`s in one transaction can see different data | Most CRUD |
| **Repeatable Read** | Also non-repeatable reads and (in Postgres) phantoms: the whole **transaction** uses one snapshot | Consistent reports, multi-step reads |
| **Serializable** | Everything: the result equals some one-at-a-time order of the transactions | Invariants spanning many rows ("at most 3 admins per project") |

Postgres accepts `READ UNCOMMITTED` but treats it as Read Committed, so you never see uncommitted data.

At **Repeatable Read** and **Serializable**, Postgres doesn't block conflicting transactions; it **aborts** one with SQLSTATE **`40001`** (serialization failure). **Your app must retry the whole transaction:**

```python
import asyncio
import random
from collections.abc import Awaitable, Callable

import asyncpg


async def with_serializable_retry[T](
    pool: asyncpg.Pool, fn: Callable[[asyncpg.Connection], Awaitable[T]], max_attempts: int = 5
) -> T:
    for attempt in range(1, max_attempts + 1):
        try:
            async with pool.acquire() as conn, conn.transaction(isolation="serializable"):
                return await fn(conn)            # COMMIT happens when the block exits
        except asyncpg.SerializationError:       # SQLSTATE 40001, raised by a statement or by COMMIT
            if attempt == max_attempts:
                raise
            await asyncio.sleep(0.02 * attempt * random.random())  # jittered backoff
    raise AssertionError("unreachable")
```

### 14.5 Locking in depth ➕

Section 4.3 used `SELECT ... FOR UPDATE` for one row, and isolation levels decide what a transaction sees. Locks are the other half: they decide who **waits**. Table locks and their queue were covered with migrations in section 8 ➕; this part is about row locks and locks you define yourself.

#### 14.5.1 Row-lock strengths, and why `FOR NO KEY UPDATE` exists ➕
**Problem:** a handler does `SELECT * FROM projects WHERE id = $1 FOR UPDATE` before renaming the project. Meanwhile every request that adds a task to that project hangs until the rename commits.

**Why it happens:** inserting a task checks the foreign key `tasks.project_id`, and that check takes a **`FOR KEY SHARE`** lock on the parent project row, meaning "don't delete this row or change its key while I reference it". `FOR UPDATE` is the strongest row lock and conflicts with `FOR KEY SHARE`, so the inserts wait.

**Mechanism: take the weakest lock that protects what you're doing.**

| Lock | Taken by | Blocks |
|---|---|---|
| `FOR UPDATE` | `SELECT ... FOR UPDATE`, `DELETE`, an `UPDATE` that changes a unique-indexed column | every other row lock, including FK checks |
| `FOR NO KEY UPDATE` | `SELECT ... FOR NO KEY UPDATE`, an `UPDATE` that doesn't change key columns | other updaters, but **not** FK checks |
| `FOR SHARE` | `SELECT ... FOR SHARE` | updates and deletes, not other sharers |
| `FOR KEY SHARE` | FK checks, `SELECT ... FOR KEY SHARE` | only deletes and key changes |

```sql
BEGIN;
SELECT name FROM projects WHERE id = $1 FOR NO KEY UPDATE;   -- tasks can still be inserted for this project
UPDATE projects SET name = $2 WHERE id = $1;
COMMIT;
```

**Edge cases:**
- A plain `UPDATE` already picks the right strength automatically. The explicit choice only matters for the "read, decide in app, then write" pattern.
- `FOR UPDATE NOWAIT` fails immediately with `55P03` instead of waiting, which suits "someone else is editing this" UIs. `lock_timeout` gives a bounded wait instead.

#### 14.5.2 `SKIP LOCKED`: a job queue in Postgres ➕
**Problem:** five worker processes poll a `jobs` table. With `SELECT ... FOR UPDATE LIMIT 1`, all five pick the **same** oldest job, four of them wait for its lock, and throughput equals one worker.

**Why it happens:** every worker computes the same "oldest pending job" and queues on that row's lock.

**Mechanism:** **`SKIP LOCKED`** makes a locking query skip rows that another transaction has locked, so each worker claims a **different** job without waiting. The docs point out this gives an inconsistent view of the table, which is fine for a queue but wrong for general reads.

```sql
CREATE TABLE jobs (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind       text NOT NULL,
  payload    jsonb NOT NULL,
  status     text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'running', 'done', 'failed')),
  run_at     timestamptz NOT NULL DEFAULT now(),
  attempts   integer NOT NULL DEFAULT 0,
  locked_at  timestamptz
);
CREATE INDEX idx_jobs_ready ON jobs (run_at) WHERE status = 'pending';   -- partial: only the queue's head

-- claim one job atomically
UPDATE jobs SET status = 'running', locked_at = now(), attempts = attempts + 1
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'pending' AND run_at <= now()
  ORDER BY run_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING id, kind, payload;
```

```python title="worker.py"
while True:
    job = await pool.fetchrow(CLAIM_SQL)
    if job is None:                                             # queue empty
        await asyncio.sleep(1)
        continue
    try:
        await HANDLERS[job["kind"]](json.loads(job["payload"]))  # jsonb arrives as str unless a codec is set
        await pool.execute("UPDATE jobs SET status = 'done' WHERE id = $1", job["id"])
    except Exception:
        await pool.execute(
            "UPDATE jobs SET status = 'pending', run_at = now() + interval '1 minute' * attempts WHERE id = $1",
            job["id"],                                          # retry later with growing delay
        )
```

**Edge cases:**
- **A worker that crashes after claiming** leaves the job `running` forever. Add a reaper that resets jobs whose `locked_at` is older than a timeout, and make handlers **idempotent**, because a job can run twice.
- Holding the transaction open for the whole job instead (claim and work inside one transaction) makes crash recovery automatic, but holds a connection and an old snapshot for the job's duration (14.3.3 ➕). Short claim transactions are usually better.
- A queue table is updated constantly, so it bloats fast. Delete or archive finished jobs and tune its autovacuum (14.3.2 ➕).

#### 14.5.3 Advisory locks: locking things that aren't rows ➕
**Problem:** a nightly billing job runs in every app instance, and only one should do it. Or: imports for the same tenant must not run concurrently, but there's no single row to lock.

**Mechanism:** **advisory locks** are locks on an **application-chosen number**. Postgres just guarantees that only one session holds a given key exclusively. The transaction-level variants release automatically at commit or rollback, which makes them the safe default:

```python
BILLING_LOCK = 42_001    # pick fixed, documented keys


async def run_nightly_billing(pool: asyncpg.Pool) -> None:
    async with pool.acquire() as conn, conn.transaction():
        locked = await conn.fetchval("SELECT pg_try_advisory_xact_lock($1)", BILLING_LOCK)
        if not locked:
            return                                  # another instance is running it
        await charge_all_accounts(conn)
    # COMMIT happens when the block exits: the lock is released here (ROLLBACK on error releases it too)
```

For per-entity locks, use the two-integer form, for example `pg_advisory_xact_lock(1, tenant_number)` where the first number names the kind of lock.

**Edge cases:**
- **Session-level advisory locks and connection pools don't mix well.** `pg_advisory_lock` stays held after the transaction, so if your code forgets `pg_advisory_unlock`, the lock lives on in a pooled connection that some other request is now using. Session-level locks also stack: locking twice needs two unlocks.
- Behind **PgBouncer in transaction mode**, session-level advisory locks don't work at all (14.7 ➕). Use the `_xact_` variants.
- Advisory locks only coordinate code that **uses** them. Any code path that skips the call isn't protected.

#### 14.5.4 Deadlocks: detection and prevention ➕
**Problem:** two requests each move tasks between projects. Occasionally one fails with `deadlock detected`.

**Why it happens:** transaction A locks task 1 and then wants task 2; transaction B locked task 2 and wants task 1. Neither can proceed. After waiting **`deadlock_timeout`** (1 second by default), Postgres checks for such a cycle and aborts one transaction with SQLSTATE **`40P01`**.

<Mermaid chart={`flowchart LR
  A["Tx A<br/>holds task 1"] -->|"waits for"| T2["task 2"]
  B["Tx B<br/>holds task 2"] -->|"waits for"| T1["task 1"]
  T2 -.->|"held by"| B
  T1 -.->|"held by"| A`} />

**Mechanism:**
1. **Lock in a consistent order**, so a cycle can't form. Sort the ids and lock them in one statement: `SELECT id FROM tasks WHERE id = ANY($1) ORDER BY id FOR UPDATE`.
2. Keep transactions short, so the window is small.
3. Treat `40P01` like `40001`: **retry the whole transaction** (the `with_serializable_retry` helper in 14.4 can catch both, `asyncpg.SerializationError` and `asyncpg.DeadlockDetectedError`).

**Edge cases:**
- Foreign-key checks and triggers take locks too, so a deadlock can involve rows your code never mentions. The server log names both statements involved.
- Lowering `deadlock_timeout` makes detection faster but runs the check more often under normal waits. Fixing the lock order is the real fix.

#### 14.5.5 Seeing who blocks whom ➕
**Problem:** requests hang, and you need to know which session is holding them up, right now.

**Mechanism:**

```sql
SELECT w.pid                  AS waiting_pid,
       left(w.query, 60)      AS waiting_query,
       b.pid                  AS blocking_pid,
       b.state                AS blocking_state,
       now() - b.xact_start   AS blocking_tx_age,
       left(b.query, 60)      AS blocking_query
FROM pg_stat_activity w
JOIN pg_stat_activity b ON b.pid = ANY (pg_blocking_pids(w.pid))
WHERE w.wait_event_type = 'Lock';

SELECT pg_cancel_backend(12345);     -- cancel the blocker's current query
SELECT pg_terminate_backend(12345);  -- end the whole session (rolls back its transaction)
```

**Edge cases:**
- A blocker in state `idle in transaction` has no running query to cancel. Only `pg_terminate_backend` frees its locks; the long-term fix is `idle_in_transaction_session_timeout` (14.3.3 ➕).
- `pg_blocking_pids` is fairly expensive. Use it for diagnosis, not in a tight monitoring loop.

### 14.6 Connection pooling
Each Postgres connection is a separate **server process** with its own memory, and opening one costs a TCP plus auth handshake. So a backend keeps a **pool** of reusable connections (`asyncpg.create_pool(dsn, max_size=10)`, SQLAlchemy's `create_async_engine(url, pool_size=5, max_overflow=10)`, psycopg's `AsyncConnectionPool(max_size=10)`), and at larger scale puts **PgBouncer** in front. Size the pool to what the database can handle (total across all app instances must stay below `max_connections`), not to your request rate.

### 14.7 Connection limits, pool sizing and PgBouncer ➕

14.6 says "size the pool to what the database can handle". Turning that into numbers, and knowing what breaks when a pooler sits between the app and Postgres, is what keeps a deploy or an autoscaling event from exhausting the database.

#### 14.7.1 Why connections are a scarce resource ➕
**Problem:** traffic doubles, the platform scales the API from 4 to 12 instances, and new requests fail with `sorry, too many clients already`.

**Why it happens (first principles):** each Postgres connection is a separate **operating-system process** with its own memory. The server allows **`max_connections`** at once (typically 100 by default, settable only at server start), and **3** of those are reserved for superusers. Raising the limit doesn't add CPU cores: past a point, more concurrent queries mean more context switching and lock contention, not more throughput. Memory adds a second limit: `work_mem` (the memory a single sort or hash step may use before spilling to disk) is granted **per operation**, so one complex query can use several multiples of it, and 500 connections each running such queries can exhaust RAM.

**Mechanism:** treat connections as a **budget** shared by every client of the database, and keep the number of **active** connections near what the hardware can actually run in parallel. Raise `work_mem` only for the sessions that need it (`SET LOCAL work_mem = '256MB'` inside a reporting transaction), not globally.

#### 14.7.2 Pool sizing math ➕
**Problem:** each service author picks `max_size=50` "to be safe", and together they exceed the server's limit.

**Mechanism: work backwards from the server.**

```text
usable     = max_connections - superuser_reserved_connections - headroom
           = 100 - 3 - 12                (headroom: migrations, cron jobs, admin sessions, a GUI)
           = 85
per pod    = floor(usable / max_pods_after_autoscaling)
           = floor(85 / 12) = 7
```

Then check that 7 is enough with **Little's law**: connections busy at once ≈ request rate × time each request **holds** a connection. At 300 requests per second per pod, with each request holding a connection for 4 ms of queries, that's 300 × 0.004 = **1.2** connections busy on average. A pool of 7 has plenty of slack. The number that blows up pool needs isn't traffic; it's **holding time**: a transaction that awaits an external API for 500 ms needs 100 times as many connections.

```python title="db.py (SQLAlchemy 2.x async)"
import os

from sqlalchemy.ext.asyncio import create_async_engine

engine = create_async_engine(
    os.environ["DATABASE_URL"],                    # postgresql+asyncpg://...
    pool_size=int(os.environ.get("PG_POOL_MAX", "7")),  # from the budget above, not a guess
    max_overflow=0,                                # default 10 would silently exceed the budget
    pool_timeout=2,                                # default 30 s: fail fast and return 503 instead
    pool_recycle=1800,                             # replace connections older than 30 min
    pool_pre_ping=True,                            # detect connections the server or a proxy has closed
)
```

With raw asyncpg the same budget is `asyncpg.create_pool(dsn, min_size=1, max_size=7, max_inactive_connection_lifetime=30)`, plus `timeout=2` on each `pool.acquire()` (asyncpg's default `max_size` is 10).

**Edge cases:**
- **Serverless functions** each get their own pool, so 200 concurrent invocations × pool of 5 = 1,000 connections. Use a pooler (PgBouncer, or your provider's) and a pool of 1 per function.
- During a **rolling deploy**, old and new pods run together, briefly doubling connections. Leave headroom for that.
- If you add read replicas, each has its own budget ([Scaling Part 2](/docs/backend-first-principles/22-scaling-performance-part-2)).

#### 14.7.3 PgBouncer pool modes and what transaction mode breaks ➕
**Problem:** you put PgBouncer in front of Postgres so that 2,000 client connections share 50 server connections. Then random bugs appear: a `SET` seems to be ignored, `LISTEN` never receives notifications, an advisory lock is held by the wrong request.

**Why it happens:** in **transaction mode**, PgBouncer gives a client a server connection only **for the duration of one transaction** and then hands that connection to someone else. Anything that lives in the **session** (beyond one transaction) ends up on a connection another client is now using, or is lost.

| Mode | Server connection returned to the pool | Session state safe? |
|---|---|---|
| session (PgBouncer's default) | when the client disconnects | yes, but little sharing |
| transaction | when each transaction ends | no |
| statement | after each statement | no, and multi-statement transactions are refused |

PgBouncer's feature table lists what **doesn't work in transaction mode**: `SET`/`RESET`, `LISTEN`, session-level advisory locks, SQL-level `PREPARE`/`DEALLOCATE`, `WITH HOLD` cursors and temp tables that outlive a transaction.

**Mechanism:** keep all state inside a transaction.
- `SET LOCAL statement_timeout = '5s'` inside a transaction instead of `SET`, or put the setting on the role (`ALTER ROLE app_user SET ...`).
- Transaction-level advisory locks (`pg_advisory_xact_lock`, 14.5.3 ➕).
- `LISTEN` and migrations through a **direct** connection that bypasses PgBouncer. A common split: a pooled `DATABASE_URL` for the app and a separate direct URL that Alembic's `env.py` reads for migrations.

#### 14.7.4 Prepared statements through PgBouncer ➕
**Problem:** after switching to transaction pooling, queries randomly fail with `prepared statement "s1" does not exist` or `prepared statement "s1" already exists`.

**Why it happens:** a **protocol-level prepared statement** (what asyncpg creates for **every** query and caches per connection, and what psycopg 3 creates after `prepare_threshold` executions) is stored in the **server connection** that prepared it. In transaction mode the next execution may land on a different server connection, where that name doesn't exist, or exists with a different query. asyncpg names the resulting error in its message and suggests the fix.

**Mechanism:**
- **PgBouncer 1.21+** tracks protocol-level prepared statements itself when **`max_prepared_statements`** is non-zero (current docs list 200 as the default) and re-prepares them transparently on whichever server connection a transaction lands on. Note it handles protocol-level prepares, **not** SQL `PREPARE` statements.
- On older PgBouncer versions, turn statement reuse off on the client: `asyncpg.create_pool(dsn, statement_cache_size=0)` (with SQLAlchemy, `connect_args={"statement_cache_size": 0, "prepared_statement_cache_size": 0}`), or `prepare_threshold=None` in psycopg 3.

```ini title="pgbouncer.ini"
[pgbouncer]
pool_mode = transaction
default_pool_size = 20
max_prepared_statements = 200
```

**Edge cases:**
- Unnamed parameterized queries (psycopg 3 below its `prepare_threshold`, or node-postgres without a `name`) are parsed and bound within one round trip, so they work in transaction mode on any version. asyncpg with `statement_cache_size=0` switches to unnamed prepared statements, which is why it works too.
- PgBouncer's `default_pool_size` is **per user and database pair**. The server-connection budget from 14.7.2 still applies to PgBouncer's total.

## 15. Backups, point-in-time recovery and restore drills ➕

Section 14 ends with durability: a committed change survives a crash because it's in the WAL. Durability doesn't protect you from the other ways data dies: a `DELETE` without a `WHERE`, a bad migration, a corrupted disk, a deleted cloud instance. For those you need backups, and a backup only counts once you have restored it.

### 15.1 Logical backups with `pg_dump` ➕
**Problem:** you need a copy of one database that you can restore elsewhere: to staging, to a newer Postgres version, or after someone drops a table.

**Mechanism:** `pg_dump` exports a database as SQL (or a compressed archive) describing its schema and data. It runs inside one transaction snapshot, so the dump is **internally consistent** even while the app keeps writing, and it doesn't block normal reads and writes (only exclusive-lock operations such as most `ALTER TABLE`s wait for it).

```bash
pg_dump -Fc -f pm_app.dump "$DATABASE_URL"                       # custom format: compressed, restorable selectively
pg_restore -j 4 --no-owner -d "$STAGING_DATABASE_URL" pm_app.dump # parallel restore into another database
pg_dumpall --globals-only -f globals.sql                         # roles and tablespaces: pg_dump skips them
```

**Edge cases:**
- **Restore point = when the dump started.** Everything written after that is lost. A nightly dump means up to 24 hours of lost data (your RPO, recovery point objective, is a day).
- Restoring a large dump means re-inserting every row and **rebuilding every index**, which can take hours (your RTO, recovery time objective).
- `pg_dump` doesn't include roles; without `pg_dumpall --globals-only` the restore fails on missing owners and grants.
- A dump running for hours is a long transaction, with the vacuum effects from 14.3.3 ➕. Run it against a replica when you can.

### 15.2 Physical backups and WAL archiving: point-in-time recovery ➕
**Problem:** at 14:32 a script deletes most of the `tasks` table. The last dump is from 02:00. You want the database exactly as it was at 14:31.

**Why it's possible (first principles):** the WAL (section 2) is a complete, ordered record of every change. If you have a copy of the data files from some moment (a **base backup**) **plus every WAL segment since then**, you can start from the copy and **replay** the history up to any chosen moment.

<Mermaid chart={`flowchart LR
  BB["Base backup<br/>Sunday 02:00"] --> R["Restore data files"]
  W["Archived WAL segments<br/>Sunday 02:00 to now"] --> P["Replay WAL"]
  R --> P
  P --> T{"recovery_target_time<br/>14:31"}
  T --> N["Database as of 14:31<br/>new timeline starts"]`} />

**Mechanism:** with `archive_mode = on`, Postgres hands each completed WAL segment (16 MB by default) to an `archive_command` (or archive module) that copies it to durable storage. `pg_basebackup` takes the base backup from a running server. To recover: restore the base backup, set `restore_command` and `recovery_target_time`, create `recovery.signal` and start the server. It replays WAL up to the target and then starts a **new timeline**, so the history from the "bad" branch can't be mixed in.

```ini title="postgresql.conf (primary)"
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /mnt/archive/%f && cp %p /mnt/archive/%f'   # must return 0 only on success
```

```ini title="postgresql.conf (restored copy)"
restore_command = 'cp /mnt/archive/%f %p'
recovery_target_time = '2026-10-02 14:31:00+00'
```

In practice most teams use a tool such as pgBackRest or WAL-G for this, or a managed service's built-in PITR. The mechanism underneath is the same. PostgreSQL 17+ also supports **incremental** base backups (`pg_basebackup --incremental`, merged with `pg_combinebackup`).

**Edge cases:**
- **The archive command's exit code is trusted completely.** If it returns 0 without having stored the file, Postgres recycles the segment and the gap makes every later recovery stop at that point. If it keeps failing, WAL piles up in `pg_wal` until the disk fills and the server shuts down. **Monitor archiving** (`pg_stat_archiver` shows the last failure).
- You can only recover to a time **after the base backup finished**. Keep several base backups, and retain WAL back to the oldest one.
- A replica is **not a backup**: the accidental `DELETE` replicates to it within milliseconds.

### 15.3 Restore drills: a backup you haven't restored is a hope ➕
**Problem:** the backup job has shown "success" for a year. On the day you need it, the restore fails: the archive is missing segments, the encryption key is on the deleted server, or the restore takes 9 hours when the business expected 1.

**Why it happens:** backup jobs verify that **a file was written**, not that **a working database comes back from it**. Every failure mode above is invisible until you try a restore.

**Mechanism: restore regularly and automatically**, and measure it.
1. On a schedule (weekly is common), restore the latest backup into a throwaway instance, using **only** the documented runbook.
2. Run checks against it: the migration version matches, row counts are close to production, and a few known recent rows exist.
3. Record how long it took (your real RTO) and how old the newest data is (your real RPO), and alert when either drifts from what you promised.

```python title="scripts/verify_restore.py"
import asyncio
import os
from datetime import UTC, datetime

import asyncpg

EXPECTED_MIGRATION = os.environ["EXPECTED_MIGRATION"]
MAX_RPO_MINUTES = 60


async def main() -> None:
    conn = await asyncpg.connect(os.environ["RESTORED_DATABASE_URL"])
    try:
        version = await conn.fetchval("SELECT max(version) FROM schema_migrations")
        t = await conn.fetchrow("SELECT count(*) AS n, max(created_at) AS newest FROM tasks")
    finally:
        await conn.close()

    if version != EXPECTED_MIGRATION:
        raise SystemExit(f"schema version {version}, expected {EXPECTED_MIGRATION}")
    lag_min = (datetime.now(UTC) - t["newest"]).total_seconds() / 60
    if lag_min > MAX_RPO_MINUTES:
        raise SystemExit(f"newest row is {lag_min:.0f} min old")
    print(f"restore OK: {t['n']} tasks, newest {t['newest']}")


asyncio.run(main())
```

**Edge cases:**
- Store backups **in a different account or region** from the database, with deletion protection. An attacker or a mistake that deletes the database often has access to backups stored next to it.
- Backups contain everything, including password hashes and personal data, so encrypt them and include them in your data-retention and erasure policy (9.11.5 ➕).

## 16. Recap 🎓

The lesson closes by noting that writing the queries for every remaining endpoint of the project management API would take hours more; with the reasoning above you can do it yourself as practice. What it covers is **about 80% of what a backend engineer does with databases day to day**:

1. Look at an **API** and the **payload** it receives.
2. **Build a query dynamically** from what's present (filters, sorts, partial updates).
3. Pass all user values through **parameterized queries**.
4. **Execute** it and return the data.

And the building blocks behind that:
- **Persistence** on **disk** (cheap and large) vs **RAM** (fast; used for caches).
- A **DBMS** organizes data, provides CRUD, enforces **integrity** and handles **security**. Text files fail on parsing, structure and concurrency.
- **Relational** for structured, related data that must stay correct; **document** stores for unpredictable shapes. **Postgres with `jsonb`** covers both, and is open source, standard-compliant and extensible.
- **Types:** `bigserial` or `uuid` ids, `numeric` for money, floats for approximate measurements, **`text`** for strings, **`timestamptz`** for time, **`jsonb`** for JSON.
- **Migrations**: ordered, version-controlled SQL files with **up** and **down** sections, tracked in `schema_migrations`.
- **Schema design:** enums (integrity + documentation), primary keys (implicit not null + unique), **`NOT NULL` by default**, `UNIQUE`, `CHECK`, foreign keys with **`RESTRICT` / `CASCADE` / `SET NULL`**, and the three relationship shapes **1:1, 1:N, M:N** (linking table with a composite key). Plural, snake_case names.
- **Seeding** with CTEs + `RETURNING` for development data.
- **Queries:** start from `FROM`, alias, **`LEFT JOIN`** when the right side may be missing, `to_jsonb` to embed, **always `ORDER BY`**, `ILIKE` filters, `LIMIT`/`OFFSET` pagination, `INSERT ... RETURNING`, dynamic partial `UPDATE`.
- **Triggers** keep `updated_at` correct for every writer.
- **Indexes** turn full scans into fast lookups for columns in `WHERE`, `JOIN` and `ORDER BY` on frequent queries. PKs are indexed automatically, **FKs aren't**, and every index costs write overhead.

What a backend engineer adds on top of the lesson (➕):
- ➕ **`jsonb` modelling** (7.6): columns for anything you filter, join or constrain, `jsonb` for genuinely variable data. Index by query shape (GIN `jsonb_path_ops` for `@>`, B-tree expression index for one key), and merge documents inside SQL.
- ➕ **Zero-downtime migrations** (section 8): the lock queue behind `ACCESS EXCLUSIVE`, `lock_timeout`, expand/contract, constant defaults, `NOT VALID` + `VALIDATE`, `CREATE INDEX CONCURRENTLY`, batched backfills.
- ➕ **Constraints as business rules** (9.10): row-local `CHECK`, partial unique indexes, exclusion constraints for overlaps, deferrable constraints checked at commit.
- ➕ **Soft deletes** (9.11): partial unique indexes, a central filter, manual cascades, or an archive table instead.
- ➕ **Upserts and CTEs** (11.7): `ON CONFLICT` is atomic, input keys must be unique, `RETURNING` skips untouched rows, data-modifying CTEs share one snapshot.
- ➕ **Index techniques** (section 13): partial, expression and covering indexes, index-only scans and the visibility map, GIN, GiST, BRIN, bloat and unused indexes.
- ➕ **Query planning** (section 13): read `EXPLAIN (ANALYZE, BUFFERS)` bottom-up, fix bad estimates with `ANALYZE` and extended statistics, find expensive queries with `pg_stat_statements`, watch for generic plans.
- ➕ **VACUUM** (14.3): dead tuples, autovacuum thresholds, long transactions that block cleanup, HOT updates, XID wraparound.
- ➕ **Locking** (14.5): row-lock strengths, `SKIP LOCKED` queues, advisory locks, deadlocks, finding blockers.
- ➕ **Connection budgets** (14.7): pool size from `max_connections` and Little's law, PgBouncer transaction mode limits, prepared statements through a pooler.
- ➕ **Backups** (section 15): `pg_dump` for logical copies, base backup + WAL archive for point-in-time recovery, automated restore drills.

## Interview questions

1. **Why are databases disk-based while caches live in RAM?** **Disk is cheap, large and survives power loss; RAM is fast but small and expensive. The database is the durable source of truth; the cache holds hot copies for speed.**
2. **Name the core responsibilities of a DBMS.** **Organizing data for efficient access, providing CRUD, enforcing integrity, and security (plus scaling and replication).**
3. **What is a lost update and how do you prevent it in Postgres?** **Two read-compute-write cycles overlap and the later write overwrites the earlier one. Prevent it with an atomic `UPDATE ... SET x = x + n`, with `SELECT ... FOR UPDATE` inside a transaction, or with optimistic version checks plus retry.**
4. **When would you pick MongoDB over Postgres, and why might you not need to?** **When the data's shape is unpredictable (CMS content). Postgres's indexed `jsonb` covers that while keeping relational integrity for everything else.**
5. **`numeric` vs `double precision` for a price?** **`numeric`: it's exact in decimal. Floats are binary approximations (0.1 + 0.2 isn't 0.3); they're faster and fine for measurements where tiny errors don't matter.**
6. **`varchar(255)` vs `text` in Postgres?** **No performance difference. `255` is a MySQL habit that misleads readers and needs a migration to change. Use `text` and validate length in the app (or with a `CHECK`).**
7. **`json` vs `jsonb`?** **`jsonb` is parsed into a binary format on write: faster queries and GIN indexing, but it doesn't keep key order, whitespace or duplicate keys. Prefer `jsonb`.**
8. **What problem do migrations solve, and how does the tool know what's already applied?** **Versioned, reviewable, reproducible schema changes with rollback. The tool records each applied version in a table such as `schema_migrations` and only runs newer files.**
9. **Why use an enum for `status`?** **The database rejects invalid values, and the migration documents the allowed values at a glance.**
10. **What does `PRIMARY KEY` imply?** **`NOT NULL` + `UNIQUE`, backed by an automatically created unique index.**
11. **How do you model 1:1, 1:N and M:N?** **1:1: the child's PK is also an FK to the parent. 1:N: a plain FK on the many side. M:N: a linking table with two FKs forming a composite PK, plus any attributes of the relationship (like `role`).**
12. **Explain `ON DELETE RESTRICT`, `CASCADE` and `SET NULL`.** **RESTRICT blocks deleting a parent that still has children; CASCADE deletes the children too; SET NULL keeps the children and clears their FK (the column must be nullable).**
13. **Why `LEFT JOIN` for users and profiles?** **Users without a profile row would disappear with an inner join; a left join keeps them with null profile fields.**
14. **How do parameterized queries prevent SQL injection?** **The SQL text is parsed before the values arrive; values are bound separately as data, so they can never change the query's structure.**
15. **Can you parameterize `ORDER BY` columns?** **No, parameters are values only. Map user input through an allow-list to hard-coded column names and `ASC`/`DESC`.**
16. **What's wrong with large `OFFSET`s, and what's the alternative?** **Skipped rows are still computed, so deep pages get slow, and inserts shift rows between pages. Use keyset pagination: `WHERE (created_at, id) < (last values)` with an index.**
17. **How do you keep `updated_at` correct?** **A `BEFORE UPDATE ... FOR EACH ROW` trigger whose function sets `NEW.updated_at = now()` and returns `NEW`.**
18. **What is an index and what does it cost?** **An ordered structure (a B-tree by default) mapping column values to row locations, turning full scans into a few page reads. It costs disk space and extra work on every insert and update.**
19. **Which columns get indexed automatically?** **Primary keys and unique constraints. Foreign keys don't; index them yourself when they're used in joins or deletes.**
20. **How do you check whether a query uses an index?** **`EXPLAIN ANALYZE`: look for `Index Scan` vs `Seq Scan` and `Rows Removed by Filter`.**
21. **What is MVCC?** **Updates write new row versions; each statement reads a consistent snapshot. Readers and writers don't block each other; only writers to the same row wait. VACUUM cleans up old versions.**
22. **What is Postgres's default isolation level, and what must you do at Serializable?** **Read Committed. At Repeatable Read or Serializable, retry the whole transaction on SQLSTATE `40001`.**
23. ➕ **When should data go in a `jsonb` column, and how do you index it?** **When its shape is genuinely variable and the database doesn't need to constrain or join on it. Use GIN (`jsonb_path_ops`) for containment queries and a B-tree expression index for equality on one key. Promote frequently queried keys to real columns.**
24. ➕ **Why can adding a column take production down even though it's instant?** **`ALTER TABLE` needs `ACCESS EXCLUSIVE`. It waits behind any long transaction on the table, and every new query queues behind the waiting `ALTER`. Set `lock_timeout` in migrations and retry.**
25. ➕ **How do you add a `NOT NULL` column or a foreign key to a large live table?** **Add it nullable (constant defaults are metadata-only), backfill in batches, add a `CHECK ... NOT VALID` or FK `NOT VALID`, `VALIDATE` it (weaker lock), then `SET NOT NULL`, which skips the scan thanks to the valid check.**
26. ➕ **What is expand/contract?** **Splitting a breaking schema change into compatible steps (add new, dual write, backfill, switch reads, stop old writes, drop old) so old and new app versions both work during a rolling deploy.**
27. ➕ **What happens if `CREATE INDEX CONCURRENTLY` fails?** **It leaves an `INVALID` index that queries ignore but writes still maintain. Find it via `pg_index.indisvalid`, drop it and rebuild.**
28. ➕ **How would you enforce "no overlapping bookings per user"?** **An exclusion constraint with GiST: `EXCLUDE USING gist (user_id WITH =, during WITH &&)`, with `btree_gist` for the equality part.**
29. ➕ **What breaks when you introduce soft deletes?** **Unique constraints (fix with partial unique indexes), every query must filter, FKs and cascades no longer fire, and erasure obligations still require real deletes.**
30. ➕ **Why can `ON CONFLICT DO NOTHING RETURNING *` return no rows?** **`RETURNING` only returns rows that were inserted or updated. A skipped conflicting row produces nothing.**
31. ➕ **What is an index-only scan and what can stop it?** **Answering a query from the index alone when all needed columns are in it and the page is all-visible in the visibility map. Pages changed since the last VACUUM force heap fetches.**
32. ➕ **When is BRIN a good choice?** **Huge tables whose column values follow physical storage order, such as append-only events by timestamp. It stores min/max per page range and is tiny, but useless for scattered values.**
33. ➕ **The planner estimates 1 row and gets 50,000. What do you check?** **Stale statistics (`ANALYZE`), correlated columns (`CREATE STATISTICS`), skewed columns (higher statistics target), and whether a generic plan is being used for a prepared statement.**
34. ➕ **How do you find the queries that cost the most?** **`pg_stat_statements`, ordered by `total_exec_time`. Frequent cheap queries often cost more than rare slow ones.**
35. ➕ **What stops VACUUM from removing dead tuples?** **Any transaction or snapshot that can still see them: long or idle-in-transaction sessions, abandoned replication slots, prepared transactions, standby feedback.**
36. ➕ **What is transaction ID wraparound?** **XIDs are 32-bit and compared circularly, so very old rows must be frozen by VACUUM. If freezing falls too far behind, Postgres stops assigning XIDs and refuses writes.**
37. ➕ **How do you build a job queue on Postgres for several workers?** **Claim jobs with `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING`, add a reaper for stuck jobs and make handlers idempotent.**
38. ➕ **When would you use an advisory lock?** **To make sure only one process does something that isn't a single row, like a scheduled job or a per-tenant import. Prefer the transaction-level variants with pools and PgBouncer.**
39. ➕ **How do you size a connection pool?** **Divide `max_connections` minus reserved slots and headroom by the maximum number of app instances, then check with Little's law (rate × connection holding time) that it's enough.**
40. ➕ **What breaks behind PgBouncer in transaction mode?** **Session state: `SET`, `LISTEN`, session advisory locks, SQL `PREPARE`, held cursors. Protocol-level prepared statements need PgBouncer 1.21+ with `max_prepared_statements`.**
41. ➕ **What is point-in-time recovery?** **Restoring a base backup and replaying archived WAL up to a chosen moment, e.g. just before an accidental delete.**
42. ➕ **Why run restore drills?** **Backup jobs only prove a file was written. Regular automated restores prove the backup works and measure the real recovery time and data loss.**
