Backend engineers spend a lot of time designing APIs, and the same questions keep coming back: **plural or singular paths? PUT or PATCH? Which method for an action that isn't create, read, update or delete? Which status code?** The lesson's explanation for the confusion: the standards were written when the web was mostly **multi-page applications (MPAs)**, where the server rendered every page. Today most frontends are **single-page applications (SPAs)** that download their JavaScript once, route on the client and talk to the backend through JSON APIs.

The lesson's goal is **not to invent new standards**. It extracts a consistent set of rules from the existing ones, so you can stop debating them and spend your time on business logic. This lesson covers only **REST**; RPC and GraphQL are other options.

## 1. History: why REST exists 🎓

### The web is invented (1990–1991)
In 1990 **Tim Berners-Lee** started the **World Wide Web** project to share knowledge globally. Within about a year he had built:
1. **URI**: the uniform resource identifier;
2. **HTTP**: the protocol clients and servers talk over;
3. **HTML**: the markup that forms a page's skeleton;
4. the **first web server**;
5. the **first web browser**;
6. the **first WYSIWYG HTML editor**, built into that browser.

All six are still with us in evolved forms (HTTP went from 1.1 to 2 and 3, there are many servers and browsers).

### The problem: exponential growth
The user base grew so fast that the web was **heading for breakdown**. It hadn't been designed for that scale, so new techniques, standards and components were needed.

### The fix: Roy Fielding's constraints
Around **1993**, **Roy Fielding**, co-founder of the **Apache HTTP Server** project, worried about this scalability problem and proposed a set of **constraints**. Each one is a solution to a specific scaling problem:

| Constraint | What it says | The scaling problem it solves |
|---|---|---|
| **Client–server** | Separate the UI and user experience (client, the frontend) from data storage and business logic (server, the backend) | Each side can **evolve independently** |
| **Uniform interface** | One standardized way for all components to communicate. Four sub-constraints: resource identification, manipulation of resources through representations, self-descriptive messages, hypermedia as the engine of application state (HATEOAS) | Any client can talk to any server without custom agreements |
| **Layered system** | A hierarchy of layers, each seeing only the layer it talks to directly | You can insert **load balancers and proxies** without changing the core system |
| **Cache** | Responses must be **labelled cacheable or not** | Clients reuse responses → less server load, better network efficiency, faster responses |
| **Stateless** | Every request carries **all** information needed to process it; the server keeps no client context between requests | **Any server** behind a load balancer (round robin etc.) can handle **any** request → horizontal scaling |
| **Code on demand** (optional) | The server can send executable code (JavaScript) to extend the client | Flexibility; rarely the focus |

Fielding then worked with Berners-Lee on the specification of **HTTP/1.1**. In **2000**, after the crisis had been averted, Fielding named and described the web's architectural style in his **PhD dissertation**: **REST, Representational State Transfer**. The lesson recommends reading the dissertation for the context behind all of this.

## 2. What "Representational State Transfer" means 🎓

### Representational
A **resource** (data, an object) is **represented in some format**: JSON (most common today), XML, HTML. **The same resource can have different representations for different clients.** A user with `id`, `name`, `createdAt` can be sent as JSON to another server, or as HTML to a browser.

### State
The resource's **current condition**: its attributes at this moment. Example: an Amazon shopping cart's state is its items, their quantities and the total price. That state moves between client and server with each API call.

### Transfer
The **movement of representations** between client and server, over HTTP, using its methods (GET, POST, PUT, PATCH, DELETE, OPTIONS, HEAD…). When you GET a web page, a representation is transferred from server to client.

**Put together:** resources have representations in various formats; their state is transferred between client and server by exchanging those representations; and the whole system follows the constraints above so that it scales.

The lesson's advice: you don't need to memorize this theory, but it explains where everything came from.

### 🔧 Going deeper: one resource, several representations
The mechanism for choosing a representation is **content negotiation**: the client sends `Accept`, the server picks a format and states it in `Content-Type`.

```python title="negotiation.py"
from html import escape

from fastapi import Request
from fastapi.encoders import jsonable_encoder
from fastapi.responses import HTMLResponse, JSONResponse, Response


@app.get("/users/{user_id}")
async def get_user(user_id: str, request: Request) -> Response:
    user = await users.find_by_id(user_id)
    if user is None:
        return JSONResponse({"code": "USER_NOT_FOUND"}, status_code=404)
    accept = request.headers.get("accept", "*/*")             # simplified: ignores q-values
    if "text/html" in accept:
        return HTMLResponse(f"<h1>{escape(user.name)}</h1>")
    if "application/json" in accept or "*/*" in accept:
        return JSONResponse(jsonable_encoder(user))
    return Response(status_code=406)                            # 406 Not Acceptable
```

## 3. URL design 🎓

### Anatomy of a URL

<Mermaid chart={`flowchart LR
  S["scheme<br/>https"] --> A["authority / domain<br/>api.example.com"]
  A --> V["version<br/>/v1"]
  V --> P["path = resource<br/>/books/harry-potter"]
  P --> Q["query<br/>?sortBy=name"]
  Q --> F["fragment<br/>the part after the hash sign"]`} />

- **Scheme:** `http` or the encrypted `https`.
- **Authority / domain:** possibly with a subdomain.
- **Path:** the **resource** you want. Each `/` expresses a **hierarchical relationship**.
- **Query parameters:** key-value pairs, usually on GETs, that give the server extra information such as filters.
- **Fragment:** tells the browser which section of the page to scroll to. 🔧 Browsers never send the fragment to the server.

### What an API URL looks like (industry convention, not a rule)
```text
https://api.example.com/v1/books
```
- an **`api.` subdomain**,
- a **version** in the path (`v1`, `v2`),
- then the **resource**.

The lesson's example is an API for a Goodreads-like platform (books, authors, reviews).

### Rule 1: resources are always plural
- List all books: `GET /v1/books`.
- One book: `GET /v1/books/:id`, **still plural**.
- **The common mistake:** writing `/book/123` because you're fetching one book. The path segment names the **collection** (`books`), and the ID picks **one member of it**: first level of hierarchy = the collection, second level = an item in it.

### Rule 2: lowercase, and no spaces or underscores
URLs travel through many server environments, client environments and operating systems, so avoid anything that can break or be mismatched: **no spaces, no underscores, no capital letters**.

**Slugs:** a human-readable, URL-safe version of some property of a resource, for example a book's name.
1. Lowercase it: `Harry Potter` → `harry potter`.
2. Replace spaces with hyphens: `harry-potter`.
3. Use it: `/books/harry-potter`.

### 🔧 Going deeper: slugs in practice

```python title="slugify.py"
import re
import unicodedata


def slugify(text: str) -> str:
    text = unicodedata.normalize("NFKD", text)
    text = "".join(c for c in text if not unicodedata.combining(c))   # strip accents: "Café" -> "Cafe"
    text = re.sub(r"[^a-z0-9]+", "-", text.lower())                    # anything else becomes a hyphen
    return text.strip("-")[:80]                                        # trim hyphens at the ends
```

Edge cases:
- **Collisions:** two books called "Harry Potter". Put a unique index on `slug` and append a suffix on conflict (`harry-potter-2`), or combine slug and ID (`/books/9f2c-harry-potter`).
- **Renames:** if the title changes, the slug changes and old links break. Keep old slugs in a table and answer with **301** to the new URL, or look up by the stable ID.
- **IDs are the stable identity.** Slugs are for readability and SEO.

🔧 **Versioning strategies:** a path version (`/v1`) is the most visible and easiest to route and cache. A header version (for example `Accept: application/vnd.example.v2+json`) keeps URLs clean but is harder to test in a browser. Whichever you choose, bump the version only for **breaking** changes; adding an optional field isn't one.

## 4. API evolution: compatibility, versioning and deprecation ➕

The `/v1` in the URL only helps if you know exactly what forces a `/v2`, how to serve both at once, and how to retire the old one. That lifecycle is most of the real work of versioning.

### 4.1 What counts as a breaking change ➕

**Problem.** You can't redeploy your clients. A mobile app version stays installed for years; a partner's integration was written once and nobody touches it. Any change that makes their existing code fail is an outage for them, even if your tests pass.

**Why it happens.** The contract isn't only your OpenAPI file; it's **everything a client can observe**: field names, types, nullability, enum values, defaults, status codes, error codes, ordering, even response time. Clients come to depend on all of it.

**Mechanism.** Classify every change before you ship it, and only make **additive** changes within a version. On the client side, the matching rule is the **tolerant reader**: ignore unknown fields, don't fail on unknown enum values.

| Change | Breaking? | Why |
|---|---|---|
| Add an optional request field | No | Old clients don't send it; the server default applies |
| Add a response field | No, for tolerant readers | Clients with strict decoders (rejecting unknown keys) will break |
| Add an enum value to a response field | Often yes | A client `switch` with no default branch hits an unhandled case |
| Make an optional request field required | Yes | Old requests now fail validation |
| Rename or remove a field | Yes | Old code reads `undefined` |
| Change a type (number to string, object to array) | Yes | Parsing fails |
| Change a default (page size 20 to 50) | Yes, semantically | Same request, different behaviour |
| Tighten validation (max length 200 to 100) | Yes | Previously valid requests fail |
| Change a status or error code | Yes | Client error handling is keyed on them |

**Implementation: catch breaking changes in CI.** Diff the OpenAPI spec of the pull request against the one in production. The open-source `oasdiff` tool has a `breaking` command for exactly this:

```bash title="ci: check-api-compat.sh"
git show origin/main:openapi.yaml > /tmp/base.yaml
oasdiff breaking /tmp/base.yaml openapi.yaml   # lists changes that break existing clients
# fail the job if the list is non-empty (see the tool's docs for the exact exit-code flag)
```

**Edge cases.**
- **Declare future enum growth.** Document that enums may gain values, and in your own SDKs map unknown values to an `unknown` case instead of throwing.
- **Behaviour without a schema change** (a new rate limit, a slower endpoint, a different sort order) is invisible to spec diffing. Review it as a contract change anyway.
- **Bug fixes can break clients** that relied on the bug. If a client is known to depend on it, treat the fix like any other breaking change.

### 4.2 Versioning strategies compared ➕

**Problem.** When a breaking change is unavoidable, old and new clients must be served at the same time by the same deployment.

**Mechanism.** The client states which contract it wants. The options differ in **where** it states it and **how fine-grained** the versions are:

| Strategy | Example | Strengths | Costs |
|---|---|---|---|
| Path segment | `/v1/organizations` | Visible, easy to route at the gateway, cache-friendly, testable in a browser | Coarse: one breaking change bumps everything; URLs of the same resource differ per version |
| Media type | `Accept: application/vnd.example.v2+json` | URLs stay stable; versions per representation | Harder to test by hand; caches must `Vary: Accept` |
| Date-based header, pinned per client | `Stripe-Version: 2024-06-20` | Fine-grained, many small versions; each account is pinned to the version it integrated with | Needs a transform layer and a registry of versions |

Stripe is the well-known example of the third: requests without the header use the account's **default** (pinned) API version, the header overrides it per request, and since 2024 Stripe ships monthly releases without breaking changes plus breaking "major" releases twice a year.

**Implementation: one current model, transforms at the edge.** Don't fork your controllers per version. Keep **one** internal model (the newest) and apply small, ordered transforms to convert the response down to what an older version expects:

```python title="versioning.py"
import re
from collections.abc import Callable
from dataclasses import dataclass
from typing import Annotated, Any

from fastapi import Depends, Header, HTTPException, Response

type Body = dict[str, Any]


@dataclass(frozen=True)
class Change:
    version: str
    down: Callable[[Body], Body]       # converts FROM this version TO the previous one


def owner_to_owner_id(o: Body) -> Body:
    rest = {k: v for k, v in o.items() if k != "owner"}
    return {**rest, "ownerId": o["owner"]["id"]}


# newest first. Each entry undoes exactly one breaking change.
CHANGES = [
    Change("2026-03-01", owner_to_owner_id),
    Change("2025-09-01", lambda o: {**o, "status": "active" if o["status"] == "paused" else o["status"]}),
]
LATEST = CHANGES[0].version
VERSION_RE = re.compile(r"\d{4}-\d{2}-\d{2}")


async def resolve_version(
    response: Response,
    auth: CurrentAuth,
    api_version: Annotated[str | None, Header()] = None,       # reads the "Api-Version" header
) -> str:
    v = api_version or auth.pinned_version or LATEST
    if not VERSION_RE.fullmatch(v):
        raise HTTPException(400, detail={"code": "INVALID_API_VERSION"})
    response.headers["Api-Version"] = v                         # echo what was applied
    return v


ApiVersion = Annotated[str, Depends(resolve_version)]


def render(body: Body, version: str) -> Body:
    for change in CHANGES:                                      # walk back, newest to oldest
        if change.version > version:                            # ISO dates compare correctly as strings
            body = change.down(body)
    return body


# handler: async def get_org(org_id: UUID, version: ApiVersion): return render(to_org_response(org), version)
```

**Edge cases.**
- **Requests need transforms too** (old field names coming in must be converted **up** to the current model before validation).
- **Webhooks and events are part of the contract.** An event payload delivered to an old integration must use that integration's version as well.
- **Side-effect differences can't be transformed.** If v2 sends an email that v1 didn't, the version must reach the service as a parameter, which is a sign to keep such differences rare.
- **Pick one strategy per API.** Mixing path versions and header versions doubles the test matrix.

### 4.3 Deprecation and sunset signals ➕

**Problem.** You announce in a changelog that `/v1` will be removed, and on removal day a third of the traffic still uses it. Nobody reads changelogs; code and monitoring do read headers.

**Mechanism.** Put the lifecycle **in the protocol**, on every response from a deprecated endpoint:
- **`Deprecation`** (RFC 9745, March 2025): the resource is or will be deprecated, as a structured-field date: `Deprecation: @1688169599` (a Unix timestamp).
- **`Sunset`** (RFC 8594): when the resource is expected to stop responding, as an HTTP-date. RFC 9745 says the sunset time must not be earlier than the deprecation time.
- **`Link`** with `rel="deprecation"` (RFC 9745) or `rel="sunset"` (RFC 8594) pointing to human-readable migration docs.
- After the sunset date, answer **410 Gone** (RFC 9110: the resource is no longer available and the condition is likely permanent) with a problem body that links to the migration guide.

<Mermaid chart={`flowchart LR
  A["Announce + docs"] --> B["Deprecation header<br/>on every response"]
  B --> C["Measure usage<br/>per client"]
  C --> D["Contact remaining clients<br/>optional brownouts"]
  D --> E["Sunset date reached"]
  E --> F["410 Gone + link<br/>to migration guide"]`} />

**Implementation.**

```python title="deprecation.py"
from datetime import UTC, datetime
from email.utils import format_datetime

from fastapi import APIRouter, Depends, Request, Response
from fastapi.responses import JSONResponse


class EndpointSunset(Exception):
    def __init__(self, docs: str) -> None:
        self.docs = docs


@app.exception_handler(EndpointSunset)
async def sunset_handler(request: Request, exc: EndpointSunset) -> JSONResponse:
    return JSONResponse(
        {
            "type": "https://api.example.com/problems/endpoint-sunset",
            "title": "This endpoint has been removed",
            "status": 410,
            "detail": f"See {exc.docs}",
        },
        status_code=410,
        media_type="application/problem+json",
    )


def deprecated(*, since: datetime, sunset: datetime, docs: str):
    async def mark(request: Request, response: Response) -> None:
        if datetime.now(UTC) >= sunset:
            raise EndpointSunset(docs)
        response.headers["Deprecation"] = f"@{int(since.timestamp())}"
        response.headers["Sunset"] = format_datetime(sunset, usegmt=True)       # HTTP-date format
        response.headers.append("Link", f'<{docs}>; rel="deprecation"; type="text/html"')
        route = request.scope.get("route")
        metrics.increment("deprecated_call", route=getattr(route, "path", None),
                          client=getattr(request.state, "client_id", None))      # who still calls it?
    return Depends(mark)


v1 = APIRouter(prefix="/v1", dependencies=[deprecated(
    since=datetime(2026, 1, 1, tzinfo=UTC),
    sunset=datetime(2026, 12, 31, tzinfo=UTC),
    docs="https://developer.example.com/migrate-v2",
)])
```

**Edge cases.**
- **Usage data decides the date, not the calendar.** Log the version and client ID of every call, and contact the remaining callers directly before the sunset.
- **Brownouts.** Some providers switch a deprecated endpoint off for short, announced windows before the final date, so that integrations nobody monitors fail loudly while there's still time to fix them.
- **CORS:** browser code can only read `Deprecation`, `Sunset` and `Link` if they're listed in `Access-Control-Expose-Headers`.
- **Sunset is a hint.** RFC 8594 says clients should treat the timestamp as a hint, so don't rely on it alone; keep the 410 response informative.

## 5. Idempotency and the HTTP methods 🎓

### Definition
An operation is **idempotent** if performing it **many times has the same effect as performing it once**. For APIs: no matter how many times the client sends the request, the **resulting state on the server** is the same.

The five main methods for moving data are **GET, POST, PUT, PATCH, DELETE**. (HEAD fetches only headers; OPTIONS is used, among other things, in the CORS preflight.)

### GET: idempotent
Fetching the list of books 1 or 1,000 times changes nothing on the server.
- **Objection:** "Someone else might add a book between my calls, so the response changes."
- **Answer:** idempotency is about the **side effect your request causes**, not about the response staying identical. Your GETs cause no change, whatever other clients do.

### PUT vs PATCH: semantics
- **PATCH: partial update.** To rename a user, send only `name`; the server updates that field.
- **PUT: full replacement.** Send the **whole** representation (`id`, `name`, `createdAt`, …); the server replaces its current version with it.
- People often use them interchangeably. That's tolerable for an **internal** API, but for a **public** API stick to the standard. Integrators **assume** you follow it, and a PUT that behaves like a PATCH sends them down the wrong path.

### PUT and PATCH: idempotent (the lesson's view)
Set the name from `A` to `B`: the first call changes `A` → `B`. The second call changes `B` → `B`. A million calls later the name is still `B`. Same payload, same final state.

### DELETE: idempotent
- First call: user 1 is deleted.
- Second call: the user doesn't exist, so the server returns **404**.
- **But the second call changed nothing.** One effect, on the first call only. A million calls give a million 404s and still that one deletion. So DELETE is idempotent, even though the **responses** differ.

### POST: not idempotent
- `POST /books` with a name, description, weight, dimensions → a new book.
- Run the exact same request (say, the same `curl`) again → **another** book with **identical data but a different ID**, because IDs (UUID or serial) are generated by the database.
- (Unless you have a uniqueness rule, such as unique names, which would make the second call fail. In practice books can share names; they are told apart by ID.)
- 1,000 calls → 1,000 books. **Each call has a new side effect**, so POST is not idempotent.

### POST is also the open-ended method
Some operations aren't fetch, create, update or delete. Example: an API that **sends an email** with a body like `{ "target": "someone@example.com" }`. That's a **custom action**. Because cases like this exist, POST is left **open-ended**, and custom actions go under POST.

### 🔧 Going deeper: what RFC 9110 actually says
- **Idempotent:** GET, HEAD, OPTIONS, TRACE, **PUT, DELETE**. The definition is about the **intended effect** of repeated identical requests; the status code may differ on repeats, which matches the lesson's DELETE example.
- **Safe** (essentially read-only): GET, HEAD, OPTIONS, TRACE. Every safe method is idempotent, not the other way round: DELETE is idempotent but certainly not safe.
- **PATCH is not guaranteed idempotent.** RFC 5789 states that PATCH is "neither safe nor idempotent". It's idempotent only when the patch **sets** values (like the lesson's `name: B`). A patch that **appends** to an array or **increments** a counter gives a different result each time. So POST is not the only non-idempotent method; PATCH may be too, and so is CONNECT.

### 🔧 Going deeper: why idempotency is an engineering problem, not trivia
**Problem:** a client sends `POST /payments`. The server charges the card, but the response is lost (mobile network drop, a proxy timeout). The client can't know whether the charge happened. If it retries, POST runs again and the customer pays twice. If it doesn't, the payment may be lost.

**Why it happens:** over a network you can't tell "the request never arrived" from "the response never came back". Retries are the only cure for lost messages, and retries are only safe for idempotent operations.

**Mechanism: an idempotency key.** The client generates a unique key per **logical operation** (a UUID), sends it in an `Idempotency-Key` header, and reuses the **same key** on every retry. The server stores the outcome under that key and **replays** it for repeats instead of running the operation again. This header is described in an IETF httpapi draft (now expired, but widely used, for example by payment APIs). The draft suggests **409** while the first request with that key is still processing, **422** when the key is reused with a different payload, and **400** when a required key is missing.

  C->>API: POST /payments + Idempotency-Key k1

  C->>API: retry POST /payments + same key k1

```python title="idempotency.py"
import hashlib
import json
import logging
from dataclasses import dataclass
from typing import Annotated, Any

from fastapi import Depends, Header, HTTPException, Request
from fastapi.responses import JSONResponse
from sqlalchemy import text
from sqlalchemy.exc import SQLAlchemyError

logger = logging.getLogger(__name__)

# CREATE TABLE idempotency_keys (
#   user_id text, key text, request_hash text NOT NULL,
#   status text NOT NULL DEFAULT 'in_progress',     -- in_progress | done
#   response_status int, response_body jsonb,
#   created_at timestamptz NOT NULL DEFAULT now(),
#   PRIMARY KEY (user_id, key)                      -- keys are scoped per user
# );


@dataclass
class Idempotency:
    user_id: str
    key: str
    replay: JSONResponse | None = None             # set when this key was already completed

    async def store(self, status: int, body: Any) -> JSONResponse:
        """Record the first real response under the key, then return it."""
        try:
            async with engine.begin() as conn:
                await conn.execute(text(
                    "UPDATE idempotency_keys SET status = 'done', response_status = :status,"
                    " response_body = :body WHERE user_id = :user_id AND key = :key"
                ), {"status": status, "body": json.dumps(body), "user_id": self.user_id, "key": self.key})
        except SQLAlchemyError:
            logger.exception("failed to store idempotent response")
        return JSONResponse(body, status_code=status)


async def idempotent(
    request: Request,
    auth: CurrentAuth,
    idempotency_key: Annotated[str | None, Header()] = None,
) -> Idempotency:
    if not idempotency_key:
        raise HTTPException(400, detail={"code": "IDEMPOTENCY_KEY_REQUIRED"})
    raw = await request.body()
    canonical = json.dumps(json.loads(raw) if raw else None, sort_keys=True, separators=(",", ":"))
    request_hash = hashlib.sha256(canonical.encode()).hexdigest()
    params = {"user_id": auth.user_id, "key": idempotency_key, "hash": request_hash}

    async with engine.begin() as conn:
        inserted = (await conn.execute(text(
            "INSERT INTO idempotency_keys (user_id, key, request_hash) VALUES (:user_id, :key, :hash)"
            " ON CONFLICT DO NOTHING RETURNING key"
        ), params)).first()
        if inserted is not None:
            return Idempotency(auth.user_id, idempotency_key)               # first time: run the handler
        row = (await conn.execute(text(
            "SELECT * FROM idempotency_keys WHERE user_id = :user_id AND key = :key"
        ), params)).mappings().one()                                        # we have seen this key before

    if row["request_hash"] != request_hash:
        raise HTTPException(422, detail={"code": "IDEMPOTENCY_KEY_REUSED"})
    if row["status"] == "in_progress":
        raise HTTPException(409, detail={"code": "REQUEST_IN_PROGRESS"})
    replay = JSONResponse(row["response_body"], status_code=row["response_status"])
    return Idempotency(auth.user_id, idempotency_key, replay=replay)        # replay, do not re-run


Idem = Annotated[Idempotency, Depends(idempotent)]


@app.post("/payments", status_code=201)
async def create_payment(body: PaymentIn, idem: Idem):
    if idem.replay:
        return idem.replay
    payment = await payments.charge(body)
    return await idem.store(201, payment.model_dump(mode="json"))
```

Edge cases:
- **Crash between the charge and storing the response:** the key stays `in_progress` forever. Production versions store the key **in the same database transaction** as the business write, or add a lock timeout after which the key can be retried.
- **Don't cache 5xx responses** as final. Let the client retry those.
- **Expire keys** (24 hours is common) with a cleanup job, and document the policy.
- Raw request bytes depend on key order and whitespace. Hash a **canonical** form (`json.dumps(..., sort_keys=True)`, as above) so a client that reorders fields still matches.

## 6. The design workflow: interface first 🎓

### Design before you code
Before any business logic, design the **interface**: the routes, methods, payloads and responses that clients (browsers, other servers) will use. It should be **intuitive, pleasant to use and unambiguous**, and follow REST standards.

### Why standards matter
Imagine an API that ignores them on purpose: POST where PUT belongs, DELETE used to fetch data. An integrator then has only **two ways** to learn how it behaves:
1. **read your code** (if it's open source or they're in your organization), or
2. **trial and error**: call it and see what happens.

Both leave huge room for confusion, wrong assumptions and bugs. With a shared standard, most behaviour is **already known**. Even if the standard is followed only about **80%** of the time, integration takes far less time, there are fewer bugs, and you need fewer sync calls with the people integrating. Add documentation and an interactive playground and there's almost no guesswork left.

### The workflow

<Mermaid chart={`flowchart LR
  W["Wireframes / user stories<br/>(Figma, product team)"] --> N["Extract nouns<br/>= resources"]
  N --> S["Database schema<br/>(next lesson)"]
  S --> A["List actions per resource<br/>CRUD + custom"]
  A --> I["Design the interface<br/>in an API client"]
  I --> C["Only then: code it"]`} />

1. **Start from the UI designs** (Figma or whatever your designers use, wireframes, user stories). They show how **end users** (not the frontend engineer) interact with data. That links the top of the stack (users) to the bottom (the database).
2. **Find the nouns. They're your resources.** It's a simplification, but a reliable rule of thumb. For a **project-management SaaS** like Jira or Linear: **projects, users, organizations, tasks, tags**.
3. **Design the database schema** (the subject of the next lesson). For this demo, three tables: **organization**, **project** (belongs to an organization), **task** (belongs to a project).
4. **List the actions** clients need on each resource. Start from the CRUD template: list, get one, create, update, delete. Then add custom actions.
5. **Design the interface** in an API client. The lesson uses **Insomnia**, a lighter alternative to Postman.

## 8. Pagination 🎓

### The problem
A list endpoint that returns **every** row runs into three costs:
1. **Serialization is expensive.** Turning 1,000 organizations into JSON costs CPU and adds latency.
2. **Users feel it.** A slow response means a visible 3–4 second delay in the UI.
3. **It's wasted.** The screen shows maybe 10–20 items at first; the user has to scroll to see more.

### The mechanism
Return **one portion (page)** at a time, in a defined order (for example latest first by `createdAt`). When the user clicks page 2 or scrolls (infinite scroll), the client asks for the next portion. Network, client and server all do less work, and the user isn't overwhelmed.

### The response shape

```json title="GET /organizations?limit=2&page=1"
{
  "data": [ { "id": "…", "name": "org5" }, { "id": "…", "name": "org4" } ],
  "total": 5,
  "page": 1,
  "totalPages": 3
}
```

| Field | Meaning | What the client uses it for |
|---|---|---|
| `data` | The items on this page | Rendering |
| `total` | Count of **all** matching rows, independent of the page | "Showing 10 of 50" |
| `page` | Which portion this is | Current page indicator |
| `totalPages` | `ceil(total ÷ limit)` | Page buttons; infinite scroll **stops when `page` equals `totalPages`** |

### The parameters
- **`limit`**: how many items per page.
- **`page`**: which portion.
- **Defaults when the client sends neither:** `page = 1`, `limit = 10` or `20`. A missing param must never cause a validation error.

### What the demo shows 🎓
Five organizations (org1 to org5, created in that order), `limit=2`:
- `page=1` → **org5, org4** (newest first), `total 5`, `totalPages 3`;
- `page=2` → **org3, org2**;
- `page=3` → **org1** alone, the last page.

Without any params it returns all five, because the default limit (10 or so) is bigger than the data.

### 🔧 Going deeper: implementing offset pagination

```python title="organizations_repository.py"
import math

from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession

SORT_COLUMNS = {"createdAt": "created_at", "name": "name", "status": "status"}


async def list_organizations(db: AsyncSession, q: ListOrgsQuery) -> dict:
    where: list[str] = []
    params: dict[str, object] = {}
    if q.status:
        where.append("status = :status")
        params["status"] = q.status
    if q.name:
        where.append("name = :name")
        params["name"] = q.name
    where_sql = "WHERE " + " AND ".join(where) if where else ""

    col = SORT_COLUMNS[q.sort_by]                              # allow-listed identifier, never raw input
    direction = "ASC" if q.sort_order == "asc" else "DESC"
    offset = (q.page - 1) * q.limit

    rows = (await db.execute(text(f"""
        SELECT * FROM organizations {where_sql}
        ORDER BY {col} {direction}, id {direction}              -- unique tie-breaker = stable pages
        LIMIT :limit OFFSET :offset
    """), {**params, "limit": q.limit, "offset": offset})).mappings().all()
    total = (await db.execute(
        text(f"SELECT count(*) FROM organizations {where_sql}"), params,
    )).scalar_one()

    return {"data": [dict(r) for r in rows], "total": total, "page": q.page,
            "totalPages": math.ceil(total / q.limit)}
```

Edge cases:
- **Cap `limit`** (for example at 100). Otherwise `?limit=1000000` brings back the exact problem pagination exists to solve.
- **Always sort by something unique.** PostgreSQL's docs warn that without an `ORDER BY` that gives a unique order, `LIMIT`/`OFFSET` returns an unpredictable subset, and different pages can overlap or skip rows.
- **Large offsets are slow.** PostgreSQL still computes every skipped row, so `OFFSET 1000000` reads a million rows to throw them away.
- **Drift:** if a row is inserted while the user is paging, everything shifts by one, and the user sees an item twice or misses one.
- **`count(*)` on big tables is expensive.** Cache it, estimate it, or drop `total` for infinite-scroll UIs.

### 🔧 Going deeper: cursor (keyset) pagination
For feeds and infinite scroll, use a **cursor**: "give me 20 items after this one" instead of "skip N".

<Mermaid chart={`flowchart LR
  subgraph Offset["Offset: page=50000"]
    direction TB
    O1["scan + discard 999,980 rows"] --> O2["return 20"]
    O3["insert during paging: rows shift"]
  end
  subgraph Cursor["Cursor: after createdAt + id"]
    direction TB
    C1["index seek to the cursor"] --> C2["read the next 20"]
    C3["inserts do not shift later pages"]
  end`} />

```python title="cursor_pagination.py"
import base64
import json
from datetime import datetime
from typing import TypedDict

from sqlalchemy import text


class Cursor(TypedDict):
    created_at: str
    id: str


def encode(c: Cursor) -> str:
    return base64.urlsafe_b64encode(json.dumps(c).encode()).decode()


def decode(s: str) -> Cursor:
    return json.loads(base64.urlsafe_b64decode(s))


async def list_after(db: AsyncSession, limit: int, after: str | None = None) -> dict:
    c = decode(after) if after else None
    rows = (await db.execute(text("""
        SELECT * FROM organizations
        WHERE (CAST(:created_at AS timestamptz) IS NULL
               OR (created_at, id) < (:created_at, CAST(:id AS uuid)))   -- row comparison uses the index
        ORDER BY created_at DESC, id DESC
        LIMIT :limit
    """), {
        "created_at": datetime.fromisoformat(c["created_at"]) if c else None,
        "id": c["id"] if c else None,
        "limit": limit + 1,                                             # fetch one extra to know if there's more
    })).mappings().all()
    has_more = len(rows) > limit
    data = [dict(r) for r in rows[:limit]]
    next_cursor = (
        encode({"created_at": data[-1]["created_at"].isoformat(), "id": str(data[-1]["id"])})
        if has_more and data else None
    )
    return {"data": data, "nextCursor": next_cursor}
```

Trade-off: cursors can't jump to "page 37", and there's no cheap `total`. Use offset for admin tables with page numbers, and cursors for feeds and large data sets.

## 9. Sorting 🎓

### The parameters
- **`sortBy`**: the field to sort on (`name`, `status`, `id`, `createdAt`… whatever fields of the resource you choose to support).
- **`sortOrder`**: `asc` or `desc`.

### What the demo shows 🎓
- `sortBy=name` alone → org5, 4, 3, 2, 1: **no visible change**, because `sortOrder` defaulted to **descending**, and the names happen to sort the same way as creation time.
- Add `sortOrder=asc` → org1, 2, 3, 4, 5.

### Rule: always apply a default sort
- **Default:** `sortBy = createdAt`, `sortOrder = desc`, i.e. latest first, which is what users naturally expect from a list.
- **Even when the client sends `sortBy` without `sortOrder`**, default the order to `desc`.
- **Why it's required, not just nice:** the database doesn't store or return rows in any guaranteed sequence. Without an explicit sort, the same request can return rows in a **different order each time**. (🔧 PostgreSQL's documentation says exactly this: SQL promises no order without `ORDER BY`.)

🔧 Implementation notes (see the repository above):
- `sortBy` must be **allow-listed** and mapped to a column. You can't bind an identifier as a `$1` parameter, so interpolating the raw value is SQL injection.
- Map API names (`createdAt`, camelCase) to column names (`created_at`).
- Index the columns you allow sorting on, or every sorted page is a full sort.

## 10. Filtering 🎓

### The mechanism
Use the **field name as the query parameter**:
- `GET /organizations?status=archived` → only archived organizations;
- `?status=active` → only active ones;
- `?name=…` → filter by name. Several filters combine.

The demo creates org6 with `status: archived` (201), then shows the status filter returning only it, and the active filter excluding it. This backs UI elements like a status switch.

### Rule: an empty list is 200, not 404 🎓
- `?status=somethingRandom` matches nothing. The response is **200** with `data: []`, `total: 0`, `page: 1`, `totalPages: 0`.
- **Why:** a list request doesn't ask for a **particular** resource; it asks for a list, and an empty list is a valid list.
- **404 is only for when the client asked for a specific resource** (by ID) that doesn't exist.

### 🔧 Going deeper: filter edge cases
- **Unknown enum values.** The lesson's demo returns an empty list for a nonsense status. A stricter option is to validate filter values against the enum and return **400**, which tells the integrator about their typo instead of silently showing nothing. Pick one behaviour and use it everywhere.
- **Partial matching:** for search-style filters, use `name ILIKE $1` with `'%' + escaped + '%'`, and escape `%` and `_` in user input. Leading-wildcard searches can't use a normal B-tree index; use a trigram index (`pg_trgm`) when the table is large.
- **Multi-value filters:** `?status=active,archived` (or repeated params) → `status = ANY($1)`.
- **Unknown params:** decide whether to ignore them or reject them with 400. Rejecting catches typos like `?stauts=active`.

## 11. Field selection and expansion ➕

Pagination, sorting and filtering control **which rows** a list returns. The remaining two dimensions are **which fields** come back for each row and **which related resources** come with it.

### 11.1 Sparse fieldsets: `fields=` ➕

**Problem.** A mobile list screen shows a project's name and status, but `GET /projects` returns 30 fields per item, including a long `description` and computed statistics. Over a slow connection, most of the payload is waste, and computing the statistics costs the server too.

**Why it happens.** One representation is designed for every client. The detail view needs everything; the list view needs a few fields. Without a way to ask, every client gets the union.

**Mechanism.** Let the client name the fields it wants. Two established conventions:
- **JSON:API** uses `fields[TYPE]` with a comma-separated list: `GET /articles?include=author&fields[articles]=title,body&fields[people]=name`.
- **Google's API guidelines (AIP-157)** describe a **field mask** (default `*`, all fields) passed as a query parameter or header, or a simpler **view** enum (`BASIC`, `FULL`) when only a few variants are needed.

A view enum is often the better start: two or three named shapes are easier to document, cache and test than arbitrary combinations.

**Implementation.**

```python title="fields.py"
from typing import Annotated

from fastapi import Depends, HTTPException
from sqlalchemy import text

PROJECT_FIELDS = {                             # API name -> SQL expression. The allow-list.
    "id": "id",
    "name": "name",
    "status": "status",
    "description": "description",
    "organizationId": 'organization_id AS "organizationId"',
    "createdAt": 'created_at AS "createdAt"',
}


def parse_fields(raw: str | None) -> list[str]:
    if not raw:
        return list(PROJECT_FIELDS)                                   # default: everything
    requested = [f.strip() for f in raw.split(",")]
    bad = [f for f in requested if f not in PROJECT_FIELDS]
    if bad:
        raise HTTPException(400, f"unknown fields: {', '.join(bad)}")
    return list(dict.fromkeys(["id", *requested]))                    # id is always included, no duplicates


def fields_param(fields: str | None = None) -> list[str]:          # reads ?fields=name,status
    return parse_fields(fields)


Fields = Annotated[list[str], Depends(fields_param)]


async def list_projects(db: AsyncSession, fields: list[str], limit: int) -> list[dict]:
    select = ", ".join(PROJECT_FIELDS[f] for f in fields)             # built only from the allow-list
    result = await db.execute(
        text(f"SELECT {select} FROM projects ORDER BY created_at DESC, id DESC LIMIT :limit"),
        {"limit": limit},
    )
    return [dict(r) for r in result.mappings()]
# GET /projects?fields=name,status  ->  [{"id": "...", "name": "...", "status": "planned"}]
```

**Edge cases.**
- **Never interpolate the raw field names into SQL.** Like `sortBy`, they're identifiers and can't be bound as parameters; map them through the allow-list.
- **Authorization per field.** `fields=email,salary` must not reveal fields the caller couldn't see in the full representation. Apply field-level permissions after selection, not before.
- **Computed fields** (`taskCount`) may need other columns or a join. Map each API field to its dependencies, and skip the expensive computation when the field isn't requested. That's where the server-side saving comes from.
- **Caching.** The field list is part of the URL, so HTTP caches key on it automatically, but many different combinations lower the hit rate. Normalise the order (`name,status` and `status,name` should be one cache entry) or prefer views.

### 11.2 Expansion: `include=` / `expand=` ➕

**Problem.** The client lists 20 projects and then needs each project's organization name. It makes 1 list call plus 20 `GET /organizations/:id` calls: an N+1 problem across the network, where each round trip can cost tens or hundreds of milliseconds on mobile.

**Why it happens.** REST resources reference each other by ID. That keeps representations small and cacheable, but the client pays in round trips whenever it needs the related data.

**Mechanism.** Let the client ask the server to embed related resources:
- **JSON:API** `include=` takes comma-separated relationship paths with dots for depth (`include=comments.author`), and says a server that can't satisfy a path **MUST** respond with 400.
- **Stripe** `expand[]=customer` replaces an ID with the full object, supports dot paths (with `data.` to reach into lists) and limits expansion to **four levels** deep.

**Implementation: batch, don't loop.** Expand with **one extra query** for the whole page, not one query per row:

```python title="expand.py"
from fastapi import HTTPException
from sqlalchemy import text

EXPANDABLE = {"organization"}


async def list_projects_expanded(db: AsyncSession, limit: int, expand: list[str]) -> list[dict]:
    unknown = [e for e in expand if e not in EXPANDABLE]
    if unknown:
        raise HTTPException(400, f"cannot expand: {', '.join(unknown)}")   # 400, like JSON:API

    result = await db.execute(
        text("SELECT * FROM projects ORDER BY created_at DESC, id DESC LIMIT :limit"), {"limit": limit},
    )
    projects = [dict(r) for r in result.mappings()]
    if "organization" not in expand:
        return projects

    ids = list({p["organization_id"] for p in projects})
    orgs = await db.execute(
        text("SELECT id, name, status FROM organizations WHERE id = ANY(:ids)"), {"ids": ids},
    )                                                                       # one query, any page size
    by_id = {o["id"]: dict(o) for o in orgs.mappings()}
    return [{**p, "organization": by_id.get(p["organization_id"])} for p in projects]
```

**Edge cases.**
- **Authorization on the expanded resource.** Being allowed to see a project doesn't automatically mean being allowed to see its organization's private fields. Expanded objects go through the same visibility rules as a direct `GET`.
- **Depth and fan-out limits.** `expand=tasks.comments.author` on a 100-item page can turn one request into hundreds of thousands of rows. Cap the depth, cap expanded list sizes, and count expansions toward the client's rate limit.
- **Shape stability.** A field that is sometimes an ID string and sometimes an object complicates typed clients (Stripe's TypeScript types model these fields as a union). Alternatively, keep `organizationId` as is and add a separate `organization` field only when expanded.
- **When clients need arbitrary graphs on every screen,** the API is drifting toward what GraphQL does natively (section 20).

## 12. Update, get one, delete 🎓

### Update: `PATCH /organizations/:id`
- The `:id` is a **dynamic parameter** (from the routing lesson). The demo copies org6's ID from the list response.
- **Body:** only the fields to change, for example `{ "status": "active" }`.
- **Response: 200** (nothing was created) with the **updated** entity.
- **The lesson's experience:** the author has rarely used PUT. Full replacement was common in the MPA era; SPAs work with JSON and nearly always update a few fields, so **PATCH** fits the meaning better and is the best practice.

### Get one: `GET /organizations/:id`
No body; **200** with the entity.

### Delete: `DELETE /organizations/:id`
- No body sent, **no body returned**, status **204 No Content**.
- Meaning: "it worked (2xx), and there's nothing to send back, because the thing is gone."

### After delete 🎓
- The list no longer contains org6.
- `GET /organizations/:id` for the deleted ID → **404** with a message like "organization not found". **This is the ideal case for 404:** a specific resource was requested and it doesn't exist.

### 🔧 Going deeper: implementing PATCH correctly

```python title="organizations_patch.py"
from typing import Annotated, Self

from pydantic import BaseModel, ConfigDict, Field, StringConstraints, model_validator
from sqlalchemy import text


class PatchOrg(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=200)] | None = None
    description: Annotated[str, Field(max_length=5000)] | None = None   # null = "clear it", absent = "leave it"

    @model_validator(mode="after")
    def check_fields(self) -> Self:
        if not self.model_fields_set:                       # the keys the client actually sent
            raise ValueError("at least one field is required")
        if "name" in self.model_fields_set and self.name is None:
            raise ValueError("name cannot be null")
        return self


COLUMN = {"name": "name", "description": "description"}


async def update_organization(
    db: AsyncSession, org_id: UUID, patch: PatchOrg, expected_version: int | None = None,
) -> dict:
    changes = patch.model_dump(exclude_unset=True)          # absent keys are left out: don't touch those columns
    sets = [f"{COLUMN[field]} = :{field}" for field in changes]
    params: dict[str, object] = {"id": org_id, **changes}
    sql = f"UPDATE organizations SET {', '.join(sets)}, updated_at = now(), version = version + 1 WHERE id = :id"
    if expected_version is not None:
        params["expected_version"] = expected_version
        sql += " AND version = :expected_version"

    row = (await db.execute(text(f"{sql} RETURNING *"), params)).mappings().first()
    if row is not None:
        await db.commit()
        return dict(row)
    exists = (await db.execute(text("SELECT 1 FROM organizations WHERE id = :id"), {"id": org_id})).first()
    raise PreconditionFailed() if exists else NotFound()    # 412 or 404
```

Edge cases:
- **Absent vs `null`.** In a JSON patch body, a missing key means "don't change it" and `null` means "set it to empty". Treat them differently: `model_dump(exclude_unset=True)` keeps only the keys the client actually sent, including explicit `null`s.
- **Lost updates.** Two people edit the same organization; the second save silently overwrites the first. Fix it with **optimistic concurrency**: return an `ETag` (or a `version`), have the client send `If-Match`, and update only if it still matches, otherwise **412 Precondition Failed**. RFC 5789 recommends exactly this for PATCH.
- **`status` is deliberately not patchable** here. Archiving has side effects (section 14), so letting PATCH flip `status` to `archived` would bypass them.
- **Delete semantics:** consider a **soft delete** (`deleted_at`) when other rows reference the organization or you need an audit trail. Return 404 for soft-deleted rows so that clients see the same behaviour either way.

## 13. Conditional requests: `ETag`, `If-Match`, 412 and 428 ➕

The PATCH edge cases above name optimistic concurrency with `If-Match` in one line. This section is the full contract around it: how the server issues validators, how it enforces them on writes, and how the same headers make reads cheaper.

### 13.1 Issuing validators, and conditional GET ➕

**Problem.** The client needs a compact token that identifies **which version** of a resource it holds, so it can later ask "has this changed?" or "only apply my change if it hasn't".

**Mechanism.** The `ETag` response header carries an **entity tag**, an opaque quoted string. RFC 9110 distinguishes:
- **strong** validators (`"v7"`): change whenever the representation changes;
- **weak** validators (`W/"v7"`): change only when the meaning changes, and may stay the same across byte-level differences.

Two cheap ways to generate one: from a **version column** that every update increments (the PATCH code above already does `version = version + 1`), or a **hash** of the serialized body. The version column is better for writes because it's tied to the row, not to one representation of it.

On reads, a client sends the tag back in `If-None-Match`. If it still matches, the server answers **304 Not Modified** with no body, saving serialization and bandwidth. (HTTP caching as a whole is covered in [Caching](/docs/backend-first-principles/13-caching).)

```python title="organizations_get.py"
from uuid import UUID

from fastapi import HTTPException, Request
from fastapi.encoders import jsonable_encoder
from fastapi.responses import JSONResponse, Response


def etag_of(org: dict) -> str:
    return f'"{org["id"]}-v{org["version"]}"'                         # strong


@router.get("/{org_id}")
async def get_org(org_id: UUID, request: Request) -> Response:
    org = await org_service.get(org_id)
    if org is None:
        raise HTTPException(404, detail={"code": "ORGANIZATION_NOT_FOUND"})
    tag = etag_of(org)
    headers = {"ETag": tag, "Cache-Control": "private, no-cache"}     # may store, must revalidate every time
    inm = request.headers.get("if-none-match")
    if inm and tag in [t.strip().removeprefix("W/") for t in inm.split(",")]:
        return Response(status_code=304, headers=headers)             # weak comparison is allowed here
    return JSONResponse(jsonable_encoder(org), headers=headers)
```

Note that FastAPI doesn't add `ETag` headers to JSON responses or answer `If-None-Match` for you (Starlette only does that for files it serves), unlike Express, which generates weak body-hash tags by default. Setting the header yourself, as above, gives you a version-based tag that the write path can check too.

### 13.2 Conditional writes: `If-Match` → 412, missing → 428 ➕

**Problem.** Alice and Bob both load organization v7. Alice renames it and saves (v8). Bob, still looking at v7, also edits the name and saves: if the server accepts it blindly, Alice's change silently disappears. (With PUT, Bob overwrites **every** field Alice touched, even ones he never edited.) That's the **lost update** problem.

**Why it happens.** HTTP is stateless (section 1). The server has no idea which version the client looked at unless the client says so.

**Mechanism.**
- The client sends `If-Match: "<id>-v7"` with its write.
- The server applies the write **only if** the current version still matches, in the same SQL statement (`WHERE version = $n`), otherwise **412 Precondition Failed**.
- `If-Match` uses **strong comparison** (RFC 9110), so a weak `W/` tag can never satisfy it. That's another reason to derive write validators from a version column, not from a body hash that a proxy might weaken.
- To make the check **mandatory**, reject writes without `If-Match` with **428 Precondition Required** (RFC 6585, created exactly for the lost-update problem).

<Mermaid chart={`sequenceDiagram
  autonumber
  participant A as Alice
  participant B as Bob
  participant API as API
  A->>API: GET /organizations/42
  API-->>A: 200, ETag v7
  B->>API: GET /organizations/42
  API-->>B: 200, ETag v7
  A->>API: PATCH name, If-Match v7
  API-->>A: 200, ETag v8
  B->>API: PATCH name, If-Match v7
  API-->>B: 412 Precondition Failed
  B->>API: GET again, merge, PATCH with If-Match v8
  API-->>B: 200, ETag v9`} />

```python title="if_match.py"
import re
from typing import Annotated
from uuid import UUID

from fastapi import Depends, Header, HTTPException, Response

STRONG_TAG = re.compile(r'"[^"]+-v(\d+)"')                            # strong tags only: W/ never matches


async def require_if_match(if_match: Annotated[str | None, Header()] = None) -> int | None:
    if not if_match:
        raise HTTPException(428, detail={"code": "PRECONDITION_REQUIRED",
                                         "message": "send If-Match with the ETag you last read"})
    if if_match.strip() == "*":
        return None                                                    # "any current version"
    m = STRONG_TAG.fullmatch(if_match.strip())
    if not m:
        raise HTTPException(412, detail={"code": "PRECONDITION_FAILED"})
    return int(m.group(1))


ExpectedVersion = Annotated[int | None, Depends(require_if_match)]


@router.patch("/{org_id}")
async def patch_org(org_id: UUID, body: PatchOrg, expected_version: ExpectedVersion,
                    db: DbSession, response: Response) -> dict:
    org = await update_organization(db, org_id, body, expected_version)
    response.headers["ETag"] = etag_of(org)                           # the client's new baseline
    return org
# update_organization (section 12) raises PreconditionFailed -> 412 when the version moved on
```

### 13.3 Edge cases and failure modes ➕

- **CORS hides `ETag`.** It isn't a CORS-safelisted response header, so browser JavaScript on another origin sees `null` unless the server sends `Access-Control-Expose-Headers: ETag` (and `If-Match` must be in `Access-Control-Allow-Headers` for the preflight).
- **Proxies can weaken tags.** Some reverse proxies turn a strong `ETag` into a weak one when they compress the response on the fly, since the bytes changed. A weakened tag then fails every `If-Match`. Version-based tags checked by your own code, or compression done before the tag is set, avoid this.
- **Lists.** An `ETag` on a collection (`GET /organizations`) is useful for 304s, but don't use it for `If-Match` on individual items; each item has its own version.
- **DELETE too.** `DELETE` with `If-Match` prevents deleting something that someone just changed. Apply the same middleware.
- **412 needs a recovery path.** Return the current `ETag` (or the current entity) with the 412 so the client can show a merge dialog instead of a dead end.

## 14. Custom actions 🎓

### Archive an organization
**The trap:** "archiving is just setting `status` to `archived`, so it's a PATCH."

**Why it isn't:** archiving an organization in a real product **triggers work**:
- the projects under it may have to be removed or changed,
- the users in it may need notifications or emails,
- the tasks under all those projects may have to be deleted.

Flipping one field doesn't perform any of that. Even though the end state includes a status change, **the operation is an action**, not a field update.

**The design:** custom actions use **POST**, on a path that follows the hierarchy all the way down:

```text
POST /organizations/:id/archive
```

All organizations → one specific organization → the action to perform on it. The demo returns org5 with `status: archived` and **200**.

**Rule: don't assume POST means 201.** This POST created nothing, so it returns 200.

### 🔧 Going deeper: implementing archive safely

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant API as Archive endpoint
  participant DB as Postgres
  participant W as Outbox worker
  C->>API: POST /organizations/:id/archive
  API->>DB: BEGIN, SELECT org FOR UPDATE
  alt already archived
    API->>DB: COMMIT (no changes)
    API-->>C: 200 + org (idempotent no-op)
  else active
    API->>DB: UPDATE org, UPDATE its projects
    API->>DB: INSERT outbox event organization.archived
    API->>DB: COMMIT
    API-->>C: 200 + archived org
    W->>DB: poll outbox
    W->>W: email members, clean up tasks
  end`} />

```python title="organizations_service.py"
import json
from uuid import UUID

from sqlalchemy import text


async def archive_organization(org_id: UUID, actor_id: str) -> dict:
    # BEGIN ... COMMIT when the block exits normally, ROLLBACK if anything raises
    async with SessionLocal() as db, db.begin():
        org = (await db.execute(
            text("SELECT * FROM organizations WHERE id = :id FOR UPDATE"), {"id": org_id},
        )).mappings().first()
        if org is None:
            raise NotFound("organization not found")
        if org["status"] == "archived":
            return dict(org)                                          # repeat = no-op

        archived = (await db.execute(text(
            "UPDATE organizations SET status = 'archived', updated_at = now() WHERE id = :id RETURNING *"
        ), {"id": org_id})).mappings().one()
        await db.execute(text(
            "UPDATE projects SET status = 'archived', updated_at = now() WHERE organization_id = :id"
        ), {"id": org_id})
        await db.execute(text(                                        # slow side effects go through an outbox
            "INSERT INTO outbox (topic, payload) VALUES ('organization.archived', :payload)"
        ), {"payload": json.dumps({"orgId": str(org_id), "actorId": actor_id})})
        return dict(archived)
```

Why these choices:
- **One transaction:** the organization and its projects change together or not at all.
- **`FOR UPDATE`:** two concurrent archive calls can't both run the side effects.
- **Outbox instead of sending emails inline:** an email can't be rolled back. Writing an event in the same transaction and letting a worker send it means emails go out **if and only if** the archive committed, and a slow mail provider doesn't slow down the API.
- **Already archived → 200 no-op.** That makes the action safe to retry. (Some APIs return 409 instead. Either is defensible; be consistent.)

## 15. Long-running operations: 202 Accepted and a status resource ➕

The archive action stays fast because the slow follow-up work goes to an outbox and the client doesn't wait for it. When the client **does** need the result of slow work (export a project to PDF, import 50,000 tasks from CSV, provision a workspace), the API needs a way to say "started, check back later".

### 15.1 The contract: 202, `Location`, and an operation resource ➕

**Problem.** A synchronous `POST /projects/:id/export` that takes 90 seconds hits load-balancer and client timeouts (often 30 to 60 s), ties up a server worker or connection for the whole time, and on timeout the client doesn't know whether to retry, which may start a second export.

**Why it happens.** HTTP is request/response: the response is the only channel to report the outcome, and it can't stay open indefinitely across every proxy between client and server.

**Mechanism.** Split "accept the work" from "report the outcome":
1. `POST /projects/:id/exports` validates the request, records an **operation**, enqueues a job, and returns **202 Accepted**. RFC 9110 defines 202 as "accepted for processing, but the processing has not been completed", and suggests the response describe the request's current status and point to a status monitor.
2. The response includes `Location: /operations/:opId` (the status resource) and a `Retry-After` hint for polling.
3. `GET /operations/:opId` returns `status` (`pending`, `running`, `succeeded`, `failed`), progress, and when done, the result or a link to it. Google's AIP-151 describes the same shape: an operation with a `done` flag, metadata for progress, and the response or error once finished.

<Mermaid chart={`sequenceDiagram
  autonumber

  participant Q as Queue

  participant DB as Postgres
  C->>API: POST /projects/42/exports
  API->>DB: INSERT operation (pending)
  API->>Q: enqueue job with opId
  API-->>C: 202 + Location /operations/op_1 + Retry-After 5

  API-->>C: 200 succeeded + result link`} />

**Implementation.**

```sql title="operations.sql"
CREATE TABLE operations (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id     uuid NOT NULL,                       -- who may read it
  kind         text NOT NULL,                       -- 'project.export'
  status       text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','running','succeeded','failed','cancelled')),
  progress     int  NOT NULL DEFAULT 0,
  result       jsonb,                               -- e.g. { "downloadUrl": ... }
  error        jsonb,                               -- problem details on failure
  heartbeat_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
```

```python title="exports_routes.py"
from uuid import UUID

from fastapi import HTTPException, Response
from sqlalchemy import text


@router.post("/projects/{project_id}/exports", status_code=202)
async def start_export(project_id: UUID, auth: CurrentAuth, idem: Idem, db: DbSession):  # section 5's Idempotency-Key
    if idem.replay:
        return idem.replay
    await project_service.assert_can_export(auth.user_id, project_id)
    op = (await db.execute(text(
        "INSERT INTO operations (owner_id, kind) VALUES (:owner, 'project.export') RETURNING id, status"
    ), {"owner": auth.user_id})).mappings().one()
    await db.commit()
    await queue.enqueue_job("project_export", op_id=str(op["id"]), project_id=str(project_id))
    res = await idem.store(202, {"id": str(op["id"]), "status": op["status"]})
    res.headers["Location"] = f"/operations/{op['id']}"
    res.headers["Retry-After"] = "5"
    return res


@router.get("/operations/{op_id}")
async def get_operation(op_id: UUID, auth: CurrentAuth, db: DbSession, response: Response) -> dict:
    op = (await db.execute(text(
        "SELECT id, status, progress, result, error, created_at FROM operations"
        " WHERE id = :id AND owner_id = :owner"
    ), {"id": op_id, "owner": auth.user_id})).mappings().first()          # scoped to the owner
    if op is None:
        raise HTTPException(404, detail={"code": "OPERATION_NOT_FOUND"})
    if op["status"] in ("pending", "running"):
        response.headers["Retry-After"] = "5"
    return dict(op)
```

### 15.2 Polling vs push ➕

**Problem.** Polling every second from thousands of clients is a lot of cheap but pointless requests; polling every minute makes the UI feel slow.

**Mechanism.**
- **Polling with server-chosen intervals:** `Retry-After` on each status response lets the server slow clients down under load or as the job runs longer.
- **Push** when the client can receive it: a webhook for server-to-server integrations ([Webhooks](/docs/backend-first-principles/30-webhooks)), or SSE / WebSockets for browsers ([Real-time backends](/docs/backend-first-principles/26-real-time-backends)). Keep the status resource anyway: push messages get lost, and the status resource is the source of truth a client can always re-check.
- **On completion,** some APIs answer the status request with **303 See Other** and a `Location` pointing to the result resource. Returning the result link inside a 200 body is simpler for most clients; pick one and document it.

### 15.3 Failure modes ➕

- **Worker crash leaves `running` forever.** The worker updates `heartbeat_at` periodically; a sweeper marks operations whose heartbeat is older than a threshold as `failed` (or re-enqueues them if the job is idempotent).
- **Duplicate starts.** A client that retries the POST after a lost 202 must not start a second export. Protect the start endpoint with an `Idempotency-Key` (section 5) so the retry returns the same operation.
- **Cancellation.** Offer `POST /operations/:opId/cancel` (a custom action, section 14). The worker checks for `cancelled` between steps; cancellation is cooperative, so the response is "cancel requested", not "stopped".
- **Access control on the status resource.** Operation IDs leak through logs and browser history; always check ownership (the `owner_id` filter above), or the status URL becomes an insecure direct object reference.
- **Retention.** Keep finished operations for a documented period (for example 7 days), then delete them and return 404, and expire any result download links at the same time ([Object storage](/docs/backend-first-principles/24-object-storage-part-1) covers presigned links).

## 16. Bulk and batch endpoints ➕

Long-running operations deal with one slow request. The opposite problem is many small ones: a client importing 500 tasks shouldn't make 500 round trips, and each one shouldn't open its own transaction.

### 16.1 Atomic or partial success: decide first ➕

**Problem.** In a batch of 500 creates, item 137 fails validation. Did the other 499 get created? If the API doesn't say, the client can't safely retry, and either loses data or creates duplicates.

**Why it happens.** A single HTTP status code describes **one** outcome. A batch has 500 outcomes.

**Mechanism.** Choose one of two semantics per endpoint, and document it:
- **Atomic (all or nothing):** validate everything, then write everything in one transaction. Any failure → a 4xx and **nothing** is written. Google's AIP-233 says a **synchronous** batch create **must** be atomic, precisely because a sync response status can't convey partial failure.
- **Partial success:** each item succeeds or fails independently; the response is **200** with a per-item result array in request order. This fits imports where one bad row shouldn't block the rest, and usually belongs on an asynchronous (202) operation.

Avoid **207 Multi-Status** for this. It's a WebDAV status code (RFC 4918) with an XML body format, and generic HTTP clients don't treat it specially.

**Implementation: atomic batch create.**

```python title="tasks_batch.py"
from typing import Annotated
from uuid import UUID

from pydantic import BaseModel, ConfigDict, Field, StringConstraints
from pydantic.alias_generators import to_camel
from sqlalchemy import text


class NewTask(BaseModel):
    model_config = ConfigDict(extra="forbid", alias_generator=to_camel)   # clientRef, projectId in JSON

    client_ref: Annotated[str, Field(max_length=64)]                     # the caller's own ID for each item
    project_id: UUID
    title: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=200)]


class BatchCreateTasks(BaseModel):
    model_config = ConfigDict(extra="forbid")

    items: Annotated[list[NewTask], Field(min_length=1, max_length=500)]  # documented hard limit


@router.post("/tasks/batch", status_code=201)
async def batch_create_tasks(body: BatchCreateTasks, auth: CurrentAuth, db: DbSession) -> dict:
    items = body.items                                                    # validation failure: 400, nothing written
    await task_service.assert_can_write_projects(auth.user_id, {i.project_id for i in items})

    async with db.begin():                                                # BEGIN/COMMIT on one connection (lesson 10, section 8)
        rows = (await db.execute(text("""
            INSERT INTO tasks (project_id, title, client_ref, created_by)
            SELECT u.project_id, u.title, u.client_ref, :created_by
            FROM unnest(CAST(:project_ids AS uuid[]), CAST(:titles AS text[]), CAST(:client_refs AS text[]))
                 AS u(project_id, title, client_ref)
            RETURNING id, project_id, title, client_ref
        """), {                                                           # one statement for all rows
            "project_ids": [i.project_id for i in items],
            "titles": [i.title for i in items],
            "client_refs": [i.client_ref for i in items],
            "created_by": auth.user_id,
        })).mappings().all()
    return {"data": [dict(r) for r in rows]}
```

**Implementation: partial-success response shape.**

```json title="POST /tasks/import  (partial success)"

  "results": [
    { "clientRef": "row-1", "status": 201, "data": { "id": "6c1e..." } },
    { "clientRef": "row-2", "status": 400, "error": { "code": "VALIDATION_FAILED", "detail": "title is required" } },
    { "clientRef": "row-3", "status": 201, "data": { "id": "9a4b..." } }
  ],
  "succeeded": 2,
  "failed": 1
```

### 16.2 Limits, routing and payload design ➕

**Problem.** Without limits, one batch request of 100,000 items holds a transaction open for minutes, exceeds the body-size limit (413) or the gateway timeout, and starves other requests.

**Mechanism and rules.**
- **Cap the item count** (500 above) and make the cap part of the contract, so clients chunk on their side. Keep the body limit (set at the reverse proxy or in a middleware, since FastAPI has none built in) consistent with it.
- **Return results in request order and echo a client reference** (`clientRef`) per item, so the client can match outcomes without relying on positions.
- **Route naming.** Google's guidelines use a custom-method suffix (`POST /v1/publishers/1/books:batchCreate`). FastAPI accepts that, but a path parameter such as `/books/{book_id}` matches any text up to the next `/`, colons included, so route order decides which handler wins; a plain sub-path like `POST /tasks/batch` is less error-prone. Whatever you pick, reserve the name so `batch` can never collide with a resource ID route (`/tasks/{task_id}`): register it **before** `/{task_id}`, or type `task_id` as a `UUID`.
- **Batch reads** are often a better fix than batch writes: `GET /tasks?ids=a,b,c` turns N lookups into one filtered list (section 10's multi-value filter).

### 16.3 Retrying a batch safely ➕

**Problem.** The response to an atomic batch create is lost. Retrying creates 500 duplicates.

**Mechanism.** Make each **item** idempotent, not just the request:
- Store the client's `clientRef` with a unique constraint scoped to the caller, and insert with `ON CONFLICT DO NOTHING`, then read back the existing rows. A retry returns the same IDs.
- Or protect the whole request with an `Idempotency-Key` (section 5), which replays the stored response.

```sql title="per-item idempotency"
ALTER TABLE tasks ADD COLUMN created_by uuid NOT NULL, ADD COLUMN client_ref text;
CREATE UNIQUE INDEX tasks_client_ref_uq ON tasks (created_by, client_ref) WHERE client_ref IS NOT NULL;
-- INSERT ... ON CONFLICT (created_by, client_ref) WHERE client_ref IS NOT NULL DO NOTHING
```

**Edge cases.**
- **Per-item authorization.** Check every referenced project, not just the first. A batch is a classic place for one forbidden item to slip in among allowed ones.
- **Rate limits.** Count a batch as N units of quota (or by cost), otherwise batching becomes a way around the limit.
- **Triggers and side effects** (emails, webhooks) per item multiply. Emit one summarized event per batch where it makes sense.

## 17. Demo: project endpoints and consistency 🎓

The second pass (projects) is faster and is meant to make the patterns stick. The demo first organises Insomnia requests into folders per resource (org, project).

### The endpoints
- **Create:** `POST /projects` with `name`, `organizationId`, `status` (for example `planned`), `description`. Again excluding `id`, `createdAt`, `updatedAt`. → **201** with the entity.
- **List:** `GET /projects`, same URL as create. Supports the same pagination (`limit=1&page=2` returns the next project), sorting and filters.
- **Get one:** `GET /projects/:id` → 200.
- **Update:** `PATCH /projects/:id` with `{ "description": "new description" }` → 200 with the updated entity.
- **Delete:** `DELETE /projects/:id` → 204, empty body.
- **Clone (custom action):** `POST /projects/:id/clone`.

### The clone action
- **Why not let the client call create with a copy of the fields?** It could fake a clone that way, but **the client doesn't know what "clone" means on the server**: perhaps all the project's tasks must be cloned too, perhaps the owner gets an email. That knowledge belongs on the server, so it's an explicit action.
- It may take **no body**, or a body with fields the client wants to **override** in the copy.
- The demo first hits a **404 "project not found"** (it used the ID of the project it had just deleted). With a valid ID it returns **201**, because cloning **creates** a new resource with a new ID.
- **Rule:** the status code follows **what happened**, not the method. A custom-action POST returns 201 if it created something, 200 if it didn't.

### Rule: JSON fields in camelCase 🎓
Request and response bodies use **camelCase** keys (`organizationId`, `createdAt`). It's the established JSON convention, so clients don't have to guess.

### Rule: be consistent everywhere 🎓
- **Problem:** after integrating **one** endpoint, a frontend engineer **assumes** the rest work the same way. If organizations use `description` and projects use `dsc`, or organizations are `/organizations` but projects are `/project`, their first call fails with a validation error or a 404, and they have to dig through docs or ask you.
- **Rule:** once you've chosen a style for routes, query params, payload keys and responses, **use it across every resource and endpoint**. Same concept → same name.
- The lesson calls consistency **one of the most important characteristics of a good backend engineer**.

After organizations and projects, **tasks** would follow the same pattern: list, get, create, update, delete, plus any custom action. The pattern is the same however many resources you have.

### 🔧 Going deeper: nested routes vs a foreign key in the body
The lesson sends `organizationId` in the body of `POST /projects`. The other common style nests the route: `POST /organizations/:orgId/projects`.

| | `organizationId` in body | Nested route |
|---|---|---|
| URL shows ownership | No | Yes |
| Easy to list across all orgs | Yes (`GET /projects?organizationId=…`) | Needs a second route |
| Authorization check | Must check membership of the org in the body | Natural: check `:orgId` in a route middleware |

Rule of thumb: nest **at most one level** (`/organizations/:id/projects`, then `/projects/:id` for the item), so URLs don't become `/orgs/1/projects/2/tasks/3/tags/4`. Either way, verify the organization exists and the caller belongs to it. Return 404 (or 422) for a missing organization, never a 500 from a foreign-key violation.

## 18. 🔧 Going deeper: a consistent error format

Consistency applies to errors as well. RFC 9457 (Problem Details, which replaced RFC 7807) defines a standard JSON error body with the media type `application/problem+json`:

```json title="HTTP/1.1 404 Not Found  (Content-Type: application/problem+json)"
{
  "type": "https://api.example.com/problems/organization-not-found",
  "title": "Organization not found",
  "status": 404,
  "detail": "No organization with id 3f1c... exists.",
  "instance": "/organizations/3f1c...",
  "code": "ORGANIZATION_NOT_FOUND",
  "requestId": "7f3a2c..."
}
```

`type`, `title`, `status`, `detail` and `instance` are the standard members. You may add your own (`code`, `requestId`, a list of validation `errors`). A stable machine-readable `code` is what lets the frontend show its own user-friendly message.

## 19. Best practices 🎓

### 1. Interactive documentation
Provide **interactive docs** with **Swagger / OpenAPI** from the **start of planning**: you use it to test, integrators use it as documentation and as a playground. How consistently you create, maintain and update your OpenAPI docs is one of the things that **sets a backend engineer apart**.

```yaml title="openapi.yaml (excerpt)"
paths:
  /organizations:
    get:
      summary: List organizations
      parameters:
        - { name: page, in: query, schema: { type: integer, minimum: 1, default: 1 } }
        - { name: limit, in: query, schema: { type: integer, minimum: 1, maximum: 100, default: 20 } }
        - { name: sortBy, in: query, schema: { type: string, enum: [createdAt, name, status], default: createdAt } }
        - { name: sortOrder, in: query, schema: { type: string, enum: [asc, desc], default: desc } }
        - { name: status, in: query, schema: { type: string, enum: [active, archived] } }
      responses:
        '200':
          description: A page of organizations
          content:
            application/json:
              schema: { $ref: '#/components/schemas/OrganizationPage' }
```

🔧 Generating the spec from code keeps the docs from drifting away from the real behaviour. FastAPI does it out of the box: it builds `/openapi.json` (and the Swagger UI at `/docs`) from your routes and Pydantic models.

### 2. Intuitive and consistent
Routes, dynamic params, custom actions and JSON payloads all follow **one pattern**. Ideally that's the global REST convention. If for some reason you don't follow it, **follow something and stick to it**. Changing style between endpoints is a huge pain for integrators.

### 3. Sane defaults, for GETs and POSTs
- **List APIs:** `page = 1`, `limit = 10` or `20`, `sortBy = createdAt`, `sortOrder = desc`.
- **Create APIs:** require only what's **absolutely needed**, and default the rest. Example: a new organization is obviously `active`, so if the client omits `status`, the server sets it. With `description` optional too, `{ "name": "Acme" }` alone creates a valid organization.

### 4. No abbreviations
No `dsc` for `description`. You know what you meant while designing; integrators don't have that context. Keep payload keys and query params readable.

### 5. Design first, in its own session
A REST API is **designed** before it's coded. Dedicate a **separate session** to designing the interface, with an OpenAPI playground or an API client like Insomnia or Postman, **without thinking about the language or framework**. Seeing the API from the consumer's side leads to better, more intuitive decisions. That's why the whole lesson never touches implementation code.

## 20. When REST isn't the best fit: GraphQL and gRPC ➕

The lesson deliberately covers only REST and names RPC and GraphQL as other options. Once the REST rules are clear, it's worth knowing which concrete problems push teams to the other two, and what those choices cost.

### 20.1 GraphQL: the client chooses the shape ➕

**Problem.** A dashboard screen needs a project, its organization's name, its 10 latest tasks and each task's assignee. In REST that's either several round trips, or `expand`/`fields` parameters (section 11) that grow into a home-made query language, or a bespoke `GET /dashboard` endpoint per screen.

**Mechanism.** GraphQL publishes a **typed schema** of the whole data graph behind a single endpoint. The client sends a query describing exactly the fields and relations it wants, and gets back JSON of that shape. Each field is backed by a **resolver** function on the server.

```graphql title="query"
query Dashboard($id: ID!) {
  project(id: $id) {
    name
    organization { name }
    tasks(first: 10) { title assignee { name } }
  }
}
```

**The costs, each a direct consequence of that mechanism:**
- **N+1 on the server.** Resolving `assignee` once per task means 10 user lookups. The standard fix (described in GraphQL's own performance guide) is batching with a tool like **DataLoader**, which collects keys requested in the same tick and loads them in one query.
- **HTTP caching is harder.** Queries are usually POSTed to one URL, so CDNs and browser caches can't key on them. The GraphQL docs suggest GET for queries and **persisted queries** (the client sends a hash, the server looks up the stored document) to get caching back.
- **Expensive queries are easy to write.** A deeply nested query can fan out enormously. You need demand control: paginated list fields, depth and breadth limits, and query-cost analysis, plus rate limiting by cost rather than by request count.
- **Errors don't map to status codes.** A partially failed query typically returns HTTP 200 with an `errors` array next to `data`, so status-code-based monitoring and the error handling from this lesson don't carry over directly.

```python title="dataloader.py (Strawberry)"
import strawberry
from sqlalchemy import text
from strawberry.dataloader import DataLoader


# one loader per request, so its cache never leaks between users
def make_loaders(db: AsyncSession) -> dict[str, DataLoader]:
    async def load_users(ids: list[str]) -> list[User | None]:
        rows = await db.execute(text("SELECT * FROM users WHERE id = ANY(:ids)"), {"ids": ids})
        by_id = {str(u["id"]): User.from_row(u) for u in rows.mappings()}
        return [by_id.get(i) for i in ids]          # same order and length as the keys

    return {"user_by_id": DataLoader(load_fn=load_users)}


@strawberry.type
class Task:
    title: str
    assignee_id: strawberry.Private[str]

    @strawberry.field
    async def assignee(self, info: strawberry.Info) -> User | None:
        return await info.context["loaders"]["user_by_id"].load(self.assignee_id)
```

### 20.2 gRPC: typed RPC for service-to-service calls ➕

**Problem.** Internal services call each other thousands of times per second. JSON is verbose to encode and decode, the contract between teams lives in prose docs, and each client hand-writes its HTTP calls.

**Mechanism.** gRPC defines services and messages in a **Protocol Buffers** IDL, generates typed clients and servers for many languages, sends compact binary messages over **HTTP/2**, and supports streaming in either or both directions, plus per-call deadlines that propagate to downstream calls.

```protobuf title="projects.proto"
syntax = "proto3";
package projects.v1;

service Projects {
  rpc GetProject (GetProjectRequest) returns (Project);
  rpc WatchTasks (WatchTasksRequest) returns (stream TaskEvent);   // server streaming
}

message GetProjectRequest { string id = 1; }
message Project { string id = 1; string name = 2; string status = 3; }
```

**The costs:**
- **Browsers can't call it directly.** Browser clients go through **gRPC-Web** and a translating proxy (the gRPC docs use Envoy), so public browser-facing APIs usually stay REST or GraphQL.
- **Binary on the wire** means no `curl` and no reading payloads in browser dev tools; you need `grpcurl` or similar tooling, and server reflection or the `.proto` files.
- **Load balancing.** HTTP/2 keeps one long-lived connection with many multiplexed calls, so a connection-level (L4) load balancer sends all of a client's calls to one backend. You need request-level (L7) balancing or client-side balancing.
- **Evolution rules are different.** Field **numbers**, not names, are the contract: never reuse or renumber a field, and mark removed ones as `reserved`.

### 20.3 Choosing ➕

| Need | Usually the best fit | Why |
|---|---|---|
| Public API for unknown third parties | REST | Universally understood, cacheable, works with any HTTP client, OpenAPI tooling |
| Many client screens with very different data needs | GraphQL | Clients pick fields and relations in one round trip |
| High-volume internal calls, streaming, polyglot teams | gRPC | Compact binary, generated typed clients, deadlines |
| Browser app talking to its own backend | REST or GraphQL | Native in browsers, no proxy needed |

They also combine well: gRPC between internal services, with a REST or GraphQL layer at the edge for browsers and partners. Whichever you pick, the contract-first habit from section 19 still applies (an OpenAPI file, a GraphQL schema or `.proto` files; see [OpenAPI](/docs/backend-first-principles/29-openapi)).

## 21. Recap 🎓

- **REST** came from Fielding's constraints for scaling the web (client–server, uniform interface, layered system, cache, stateless, optional code on demand), named in his 2000 dissertation.
- **Representational state transfer:** resources have representations; their state is transferred between client and server over HTTP.
- **URLs:** `https://api.example.com/v1/books/:id`, **plural** resources, lowercase, hyphenated slugs, `/` for hierarchy.
- **Idempotency:** GET, PUT, DELETE are idempotent; POST isn't; POST also carries custom actions. (🔧 PATCH is only idempotent when it sets values.)
- **Workflow:** wireframes → nouns/resources → DB schema → actions → interface design → code.
- **CRUD map:** collection routes for list and create, item routes for get, update and delete. The method picks the controller.
- **Status codes:** 201 for creates, 200 for reads, updates and non-creating actions, 204 for deletes, 404 only for a specific missing resource; an empty list is 200.
- **List APIs:** pagination (`page`, `limit` → `data`, `total`, `page`, `totalPages`), sorting (`sortBy`, `sortOrder`, default `createdAt desc`), filtering (field-named params).
- **Custom actions:** `POST /resources/:id/action`, because the server knows the side effects; the status follows what happened (archive 200, clone 201).
- **Best practices:** interactive OpenAPI docs, consistency, sane defaults, no abbreviations, camelCase JSON, design before code.
- ➕ **API evolution:** only additive changes within a version, breaking changes caught by diffing the spec in CI; versions resolved at the edge with transforms; `Deprecation` and `Sunset` headers, then 410 Gone.
- ➕ **Field selection and expansion:** allow-listed `fields` (or views) and `include`/`expand` loaded with one batched query, with depth limits and per-field authorization.
- ➕ **Conditional requests:** strong `ETag` from a version column; `If-None-Match` → 304 on reads; `If-Match` → 412 on stale writes, 428 when it's missing.
- ➕ **Long-running work:** 202 + `Location` to an operation resource, polled with `Retry-After` or pushed; heartbeats, idempotent starts, owner checks.
- ➕ **Bulk endpoints:** decide atomic vs partial success up front; cap the size; per-item `clientRef` for matching and idempotent retries.
- ➕ **Alternatives:** GraphQL for client-shaped reads (at the cost of caching, N+1 and query-cost control), gRPC for typed, high-volume internal calls (not directly from browsers).

## Interview questions

1. **Why is `GET /books/123` better than `GET /book/123`?** **The path names the collection (`books`), and the ID picks one member of it. Plural is used consistently for both list and item routes.**
2. **Is GET idempotent if another client adds rows between your calls?** **Yes. Idempotency is about the side effect your request causes on the server, not about getting an identical response.**
3. **Why is DELETE idempotent when the second call returns 404?** **The second call changes nothing. RFC 9110 defines idempotency by intended effect; the status code may differ on repeats.**
4. **Is PATCH idempotent?** **Not by definition (RFC 5789 says neither safe nor idempotent). A patch that sets fields is idempotent in practice; one that increments or appends isn't.**
5. **When do you use PUT vs PATCH?** **PUT replaces the whole representation; PATCH changes some fields. Modern SPAs nearly always use PATCH, and public APIs should respect the semantics.**
6. **How do you make a POST safe to retry?** **An `Idempotency-Key` header: store the outcome under the key, replay it for repeats, return 409 while the first is in progress and 422 if the key is reused with a different body.**
7. **Archiving sets `status` to archived. Why not a PATCH?** **Archiving has server-side side effects (projects, notifications, tasks). It's an action: `POST /organizations/:id/archive`.**
8. **Does every POST return 201?** **No. 201 only if a resource was created (clone). Non-creating actions (archive) return 200.**
9. **A filter matches nothing. 404 or 200?** **200 with an empty `data` array. 404 is for a specific resource that doesn't exist.**
10. **Why must a list API sort by default?** **Without `ORDER BY` the database guarantees no order, so results and pages can change between calls. Default to `createdAt desc`, with a unique tie-breaker.**
11. **What are the problems with offset pagination, and the alternative?** **Large offsets still scan the skipped rows, and inserts shift pages. Cursor (keyset) pagination seeks by `(createdAt, id)` instead.**
12. **What does a 201 response need besides the body?** **A `Location` header with the new resource's URI (RFC 9110 says MUST).**
13. **What does statelessness buy you?** **Any server behind a load balancer can handle any request, because each request carries everything needed to process it.**
14. **Why design the interface before coding?** **Seeing it as a consumer leads to intuitive, consistent APIs, and the design (OpenAPI) doubles as documentation and a playground.**
15. ➕ **Is adding a new enum value to a response a breaking change?** **Often, yes: clients with exhaustive switches or strict decoders fail on an unknown value. Document that enums can grow, or treat it as breaking.**
16. ➕ **How do you support several API versions without duplicating controllers?** **Keep one current internal model and apply ordered per-version transforms at the edge (the date-pinned approach Stripe uses), resolving the version from a header or the client's pinned default.**
17. ➕ **How do you retire an endpoint?** **Send `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) headers with a `Link` to migration docs, measure remaining usage per client, then answer 410 Gone after the sunset date.**
18. ➕ **How do you prevent the lost-update problem in a REST API?** **Return a strong `ETag`, require `If-Match` on writes (428 if missing), and apply the write only if the version still matches, otherwise 412.**
19. ➕ **An export takes two minutes. What does the API return?** **202 Accepted with `Location` to an operation resource and `Retry-After`. The client polls (or gets a webhook) until the operation is succeeded or failed.**
20. ➕ **Item 137 of a 500-item batch fails. What should happen?** **It depends on the documented semantics: atomic batches write nothing and return 4xx; partial-success batches return per-item results in request order, matched by a client reference.**
21. ➕ **Why can't a GraphQL API rely on HTTP caching and status codes as easily as REST?** **Queries are usually POSTed to one URL and partial failures come back as 200 with an `errors` array. GET plus persisted queries restores caching.**
22. ➕ **Why isn't gRPC used for public browser APIs?** **Browsers can't speak native gRPC; they need gRPC-Web through a translating proxy. It shines for internal, high-volume, typed service-to-service calls.**
