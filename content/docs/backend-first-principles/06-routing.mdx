## 1. What routing is 🎓

- **Method = what.** `GET` means fetch, `POST` means create, and so on.
- **Route (URL path) = where.** `/users` says which resource.
- **The server maps the pair to a handler**: a set of instructions that runs the business logic and database operations, then returns a response.

> **Routing = mapping (method, URL path) to server-side logic.**

<Mermaid chart={`flowchart LR
  R["GET /api/books"] --> RT{Router}
  RT -->|"GET + /api/books"| H1["listBooks handler"]
  RT -->|"POST + /api/books"| H2["createBook handler"]
  RT -->|"GET + /api/users/:id"| H3["getUser handler"]
  H1 --> BL["business logic + DB"] --> RES["response"]`} />

### What the demo shows 🎓
The demo uses **Burp Suite** to inspect traffic from a small React app.
- `GET /api/books` returns a list (filler data). `books` is the **resource**, a term that comes back in the REST lesson.
- `POST /api/books` uses **the same path** but a different method. It creates a book and returns the list.
- **Takeaway:** the server combines **method + path** into one unique key. `GET /api/books` and `POST /api/books` are two different routes that **never clash**; the method tells them apart.

### 🔧 Going deeper: how a router actually matches

The simplest router is a list that it scans in order. Building one shows the mechanism every framework uses:

```python title="tiny_router.py"
from collections.abc import Callable
from dataclasses import dataclass
from typing import Any
from urllib.parse import parse_qs, unquote, urlsplit

type Handler = Callable[[dict[str, str], dict[str, list[str]]], Any]


@dataclass
class Route:
    method: str
    parts: list[str]
    handler: Handler


routes: list[Route] = []


def add(method: str, path: str, handler: Handler) -> None:
    routes.append(Route(method, [p for p in path.split("/") if p], handler))


def match(method: str, raw_url: str) -> tuple[int, Any]:
    url = urlsplit(raw_url)
    segs = [s for s in url.path.split("/") if s]
    path_matched = False

    for route in routes:
        if len(route.parts) != len(segs):
            continue
        params: dict[str, str] = {}
        for part, seg in zip(route.parts, segs, strict=True):
            if part.startswith(":"):
                params[part[1:]] = unquote(seg, errors="strict")
            elif part != seg:
                break
        else:  # every segment matched
            path_matched = True
            if route.method == method:
                return 200, route.handler(params, parse_qs(url.query))
    return (405, None) if path_matched else (404, None)  # path exists with another method → 405


add("GET", "/api/books", lambda p, q: ["book a", "book b"])
add("POST", "/api/books", lambda p, q: "created")
add("GET", "/api/users/:id", lambda p, q: {"id": p["id"]})
```

Some routers (e.g. **find-my-way**, used by Node's Fastify) store routes in a **radix tree** keyed by path segments, so matching costs roughly the length of the path instead of the number of routes. Starlette, and so FastAPI, still scans its route list in **registration order**, testing one compiled regex per route (as Express does), which is why order matters (section 3).

### Inside a radix-tree router ➕

The sentence above says radix trees are fast. Here is why, and what they change about which route wins, because that decides how your app behaves when two routes overlap.

#### The structure and the lookup ➕

- **Problem:** the list scan above costs one comparison per route **for every request**. With 500 routes, a request that matches the last one (or none, a 404) pays 500 comparisons, and for regex-based routes each comparison runs a regular expression.
- **Mechanism:** a **radix tree** (compressed prefix tree) stores routes by their **shared prefixes**. Each node holds a chunk of path text; a request walks down from the root, consuming its path as it matches each node. Parameters are special child nodes that consume one segment. The cost depends on the **length of the path**, not on how many routes exist.

<Mermaid chart={`flowchart TD
  R["/api/"] --> B["books"]
  R --> U["users/"]
  U --> ME["me (static)"]
  U --> ID[":id (param)"]
  ID --> P["/posts"]
  B --> BS["/search"]
  R --> F["files/* (wildcard)"]`} />

- **Implementation:** a minimal version shows the idea (one segment per node for clarity; real routers also compress shared character prefixes):

```python title="segment_tree.py"
from collections.abc import Callable
from dataclasses import dataclass, field
from typing import Any

type Handler = Callable[[dict[str, str]], Any]


@dataclass
class Node:
    statics: dict[str, Node] = field(default_factory=dict)
    param: tuple[str, Node] | None = None  # (name, child)
    wildcard: Handler | None = None
    handlers: dict[str, Handler] = field(default_factory=dict)


root = Node()


def add(method: str, path: str, handler: Handler) -> None:
    n = root
    for seg in filter(None, path.split("/")):
        if seg == "*":
            n.wildcard = handler
            return
        if seg.startswith(":"):
            if n.param is None:
                n.param = (seg[1:], Node())
            n = n.param[1]
        else:
            n = n.statics.setdefault(seg, Node())
    n.handlers[method] = handler


def find(
    n: Node, segs: list[str], i: int = 0, params: dict[str, str] | None = None
) -> tuple[Node, dict[str, str]] | None:
    params = params or {}
    if i == len(segs):
        return (n, params) if n.handlers else None
    static = n.statics.get(segs[i])  # 1. static first
    if static is not None and (via_static := find(static, segs, i + 1, params)):
        return via_static
    if n.param is not None:  # 2. then the parameter
        name, child = n.param
        if found := find(child, segs, i + 1, {**params, name: segs[i]}):
            return found
    return None  # (3. wildcard handling omitted)
```

- **Edge cases:** the speed difference only matters at scale. For a typical service with 50 routes, the router is a tiny fraction of request time compared with a single database query. Choose a framework for other reasons; just know where the ordering rules come from.

#### Priority and backtracking ➕

- **Problem:** with a tree, "registration order" no longer exists, so the router needs a fixed rule for overlaps such as `/users/me` vs `/users/:id`.
- **Mechanism:** at each node, radix routers try **static** children first, then the **parametric** child, then the **wildcard**. That's why section 3's `me` vs `:id` conflict disappears in Fastify. If the static branch matches a segment but fails **deeper down**, a correct router **backtracks** and tries the parametric branch: with `/users/me/settings` and `/users/:id/posts` registered, `/users/me/posts` must still reach `:id/posts` with `id = "me"`. The `find` function above does this by falling through to the `param` branch when the static recursion returns `None`.
- **Edge cases:** routers differ in exactly these corners (backtracking support, multiple parameters in one segment, regex constraints), so a route table that works in one framework can behave differently after a migration. Write a test for every overlapping pair of routes you rely on.

#### Regex routes and ReDoS ➕

- **Problem:** order-based routers compile each path string into a **regular expression**: Express via `path-to-regexp`, Starlette (FastAPI) via `starlette.routing.compile_path`. Python's `re` runs on the event-loop thread and holds the GIL while it matches, so a pattern that backtracks badly on a crafted URL **blocks every request** on the process.
- **Real case:** **CVE-2024-45296**. Paths with two parameters in one segment separated by something other than `.` (for example `/flights/:from-:to`) compiled into a backtracking regex. A long, crafted URL froze the server. Express 4 fixed it in **4.20.0** by upgrading `path-to-regexp`; Express 5's newer `path-to-regexp` no longer allows regex syntax inside path strings at all. Starlette compiles `/flights/{src}-{dst}` to `^/flights/(?P<src>[^/]+)\-(?P<dst>[^/]+)$`: not exponential, but quadratic on a segment made of dashes. Measured on Python 3.14: 0.013 s for 2,000 characters, 0.055 s for 4,000, 0.22 s for 8,000, each of them stalling the whole event loop.
- **Mechanism:** avoid ambiguous patterns, keep URLs bounded, and validate inside the handler instead of in the route pattern:

```python
from typing import Annotated

from fastapi import Path


# ❌ two params in one segment, regex-shaped matching
@app.get("/flights/{src}-{dst}")
async def flights_ambiguous(src: str, dst: str): ...


# ✅ one param per segment, then validate
AirportCode = Annotated[str, Path(pattern=r"^[A-Z]{3}$")]


@app.get("/flights/{src}/{dst}")
async def flights(src: AirportCode, dst: AirportCode) -> list[Flight]:  # bad codes → 422
    return await search_flights(src, dst)
```

- **Edge cases:** the same risk applies to any regex you run yourself with `re` if it has nested quantifiers. Pydantic's `pattern` constraint is safer: by default it uses the Rust `regex` crate, which matches in linear time (look-arounds need `regex_engine="python-re"`, which brings backtracking back). Keep the framework updated (`uvx pip-audit` flags known CVEs in your dependencies), and cap URL length at the proxy (see the HTTP lesson's limits section, [HTTP](/docs/backend-first-principles/05-http)).

### HEAD and OPTIONS: methods the router answers for you ➕

The router doesn't only dispatch the methods you register. Most frameworks answer two methods **on their own**, which surprises people when they show up in logs or collide with CORS.

#### Automatic HEAD ➕

- **Problem:** HTTP says every resource that supports GET should support HEAD (the same headers, no body), but nobody wants to write two handlers.
- **Mechanism:** frameworks disagree. Express runs your **GET handler** for a HEAD request and drops the body; Starlette's plain `Route` adds HEAD to every GET route. FastAPI's path operations **don't**: `HEAD` on an `@app.get` route gets **405** (`Allow: GET`). You opt in per route, either by listing both methods or with a separate, cheap HEAD handler.
- **Implementation:** for an expensive GET, register a cheap HEAD route next to it:

```python
from fastapi import Response


@app.head("/reports/{report_id}")
async def report_head(report_id: str) -> Response:  # no report generation
    meta = await reports.meta(report_id)
    if meta is None:
        return Response(status_code=404)
    return Response(headers={"Content-Length": str(meta.bytes), "ETag": f'"{meta.version}"'})


@app.get("/reports/{report_id}")
async def report(report_id: str) -> Report:
    return await generate_report(report_id)


# or let the GET handler serve HEAD too (the server drops the body):
# @app.api_route("/reports/{report_id}", methods=["GET", "HEAD"])
```

- **Edge cases:** monitoring tools and link checkers often use HEAD, so with FastAPI they see 405s, and once HEAD is routed to the GET handler, an expensive GET can be triggered far more often than your users call it. If a HEAD reaches a GET handler that **changes state** (it shouldn't, but it happens), HEAD now changes state too.

#### Automatic OPTIONS, and why it matters for 405 and CORS ➕

- **Problem:** a client (or a browser preflight) asks `OPTIONS /api/books`: "what can I do here?".
- **Mechanism:** Express's router answers an unhandled `OPTIONS` itself with an **`Allow`** header. FastAPI doesn't: without a route or middleware for it, `OPTIONS /api/books` gets **405**. What Starlette's router does do on its own is return **405 with an `Allow` header** for any method the path doesn't support, but `Allow` lists only the methods of the **first** route whose path matched: with `@app.get` and `@app.post` as two functions, `DELETE /api/books` gets `Allow: GET`, leaving out POST.
- **Implementation:** to answer OPTIONS and send a complete `Allow`, handle the leftover methods on that path explicitly:

```python
from fastapi import Request, Response
from fastapi.responses import JSONResponse

ALLOW = {"Allow": "GET, POST, OPTIONS"}


@app.get("/api/books")
async def list_books() -> list[Book]: ...


@app.post("/api/books", status_code=201)
async def create_book(book: BookIn) -> Book: ...


@app.api_route("/api/books", methods=["PUT", "PATCH", "DELETE", "OPTIONS"], include_in_schema=False)
async def books_other_methods(request: Request) -> Response:
    if request.method == "OPTIONS":
        return Response(status_code=204, headers=ALLOW)
    return JSONResponse({"error": f"{request.method} not allowed"}, status_code=405, headers=ALLOW)
```

- **Edge cases:** a plain 405 or the OPTIONS route above carries **no CORS headers**, so browser preflights must be answered by `CORSMiddleware` before they reach the router; in Starlette all middleware runs before routing, so that part is automatic. The trap is auth: if an auth **middleware** wraps the app outside CORS, it rejects preflights (which carry no credentials) with 401. Make `CORSMiddleware` the outermost layer (added last), then auth, then routes (the HTTP lesson's CORS section).

## 2. Static routes 🎓

- **Definition:** a route with **no variable parts**. `/api/books` is a constant string; you always send exactly that, and it always returns the same *kind* of data.
- The two demo requests above (`GET` and `POST /api/books`) are static routes.

### What counts as "the same path"? ➕

A static route is a constant string, but "does this request match it?" is less obvious than it looks. `/api/books`, `/api/books/`, `/API/Books` and `/api//books` are four different strings, and frameworks, proxies and caches disagree about which of them are equal.

#### Trailing slashes ➕

- **Problem:** a client calls `/api/books/` and your route is `/api/books`. Depending on the framework, it either works or returns 404.
- **Mechanism:** FastAPI (Starlette) matches strictly but **redirects** by default: with `redirect_slashes=True`, a request to `/api/books/` for a route `/api/books` (or the other way round) gets a **307** to the other form. Express's router is **non-strict** (`strict: false`): both match the same route. Fastify is strict (`ignoreTrailingSlash: false`): they are **different** routes, so one of them 404s.

```python
app = FastAPI(redirect_slashes=False)  # FastAPI: /books/ for a /books route is a plain 404, no redirect
router = APIRouter(redirect_slashes=False)  # the same switch per router
```

- **Edge cases:** "works either way" isn't free. Caches, CDNs and analytics treat the two URLs as separate entries, and relative links resolve differently (`./reviews` from `/books/` is `/books/reviews`, from `/books` it's `/reviews`). The automatic 307 also builds its `Location` from the scheme and host the app sees, so behind a proxy without trusted `X-Forwarded-*` headers it can redirect an HTTPS client to `http://`. Pick one form and redirect the other (below).

#### Case sensitivity ➕

- **Problem:** RFC 3986 makes the **path case-sensitive** (only scheme and host are case-insensitive), yet Express matches **case-insensitively** by default (`caseSensitive: false`), while Starlette (FastAPI) and Fastify are case-sensitive.
- **Why it matters for security:** if a reverse proxy and the app disagree, rules can be bypassed. Nginx `location` matching is case-sensitive. With `location /admin { deny all; }` in Nginx and an Express app behind it, a request to **`/ADMIN`** doesn't match the Nginx rule, is forwarded, and Express happily routes it to the `/admin` handler.
- **Implementation:** enforce access rules **in the app** (where routing actually happens), and keep matching strict so the two layers agree (FastAPI already is):

```python
from fastapi import APIRouter, Depends

admin = APIRouter(prefix="/admin", dependencies=[Depends(require_admin)])  # the real protection lives next to the routes
app.include_router(admin)  # Starlette matches case-sensitively: /Admin is a 404, never the admin handler
```

- **Edge cases:** path **parameters** keep their original case either way (`/users/Asha` gives `id = "Asha"`), so normalise values such as usernames or slugs yourself before looking them up.

#### One canonical URL: redirect the rest ➕

- **Problem:** if `/books`, `/books/` and `/Books` all return the same content, search engines index duplicates, caches store duplicates, and logs split one endpoint into several.
- **Mechanism:** choose **one canonical form** and redirect every variant to it, keeping the query string. Use **301** (permanent) for GET, and **308** when the method and body must be preserved (a 301 may turn a POST into a GET).

```python title="canonical.py"
import re

from starlette.middleware.base import BaseHTTPMiddleware
from starlette.responses import RedirectResponse


class CanonicalPathMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        path = request.url.path
        canonical = re.sub(r"/{2,}", "/", path).lower()  # collapse // and lowercase
        if len(canonical) > 1:
            canonical = canonical.removesuffix("/")  # drop one trailing slash
        if canonical == path:
            return await call_next(request)
        target = canonical + (f"?{request.url.query}" if request.url.query else "")
        return RedirectResponse(target, status_code=301 if request.method in ("GET", "HEAD") else 308)


app.add_middleware(CanonicalPathMiddleware)
```

- **Edge cases:** only lowercase paths you own entirely; IDs or file keys that are legitimately case-sensitive (`/files/AbC123`) must be left alone, so in real code apply the lowercase rule to specific prefixes. For **APIs**, many teams prefer a `404` for the wrong form over a redirect, because API clients often don't follow redirects for non-GET methods. Redirects are mostly for browser-facing URLs.

#### Normalization and decoding mismatches ➕

- **Problem:** before matching, someone has to **decode** `%xx` escapes and deal with `//` and `..`. When the proxy and the app do this differently, the URL the proxy checked is not the URL the app routed.
- **Mechanism (what each layer does):** browsers remove `.` and `..` segments before sending; curl does too unless you pass `--path-as-is`; Nginx decodes, resolves `..` and merges slashes for its **own** `location` matching; uvicorn hands the app a **percent-decoded** `scope["path"]` (the raw bytes stay in `scope["raw_path"]`), and Starlette routes on that decoded string, so an encoded slash (`/files/a%2Fb`) becomes a real `/` and no longer matches a one-segment parameter.
- **Implementation:** handle malformed input with a 400, not a crash or a silent guess. Starlette doesn't fail on an undecodable escape: `/users/%E0%A4%A` is decoded with replacement characters, and the handler receives `"\ufffd%A"` with a 200. A hand-written router that decodes strictly (like the tiny router in section 1, `unquote(seg, errors="strict")`) raises `UnicodeDecodeError` and returns a **500** unless you catch it:

```python
from urllib.parse import unquote


def safe_decode(segment: str) -> str | None:
    try:
        return unquote(segment, errors="strict")
    except UnicodeDecodeError:
        return None


# in match(): value = safe_decode(seg); if value is None: return 400, None
```

- **Edge cases:** test your **real** proxy plus app with odd paths (`curl --path-as-is 'https://api.example.com/api/public/../admin'`, `/%2e%2e/`, `//admin`, `/ADMIN`) and check that protected routes stay protected. Starlette puts no length limit on a path parameter, so bound the ones you accept (`Path(max_length=64)`); Fastify, by contrast, 404s parameters longer than `maxParamLength` (100 characters by default), which can surprise clients that put long tokens in paths.

## 3. Dynamic routes and path parameters 🎓

### The idea
`GET /api/users/123` fetches **one** user. The `123` is the user's ID, and it changes per request.

On the server this is declared with a **placeholder**, conventionally a **colon** (`/api/users/:id` in Express, Rails or Gin). FastAPI writes the same placeholder in **braces**:

```python
@router.get("/api/users/{id}")
async def get_user(id: str): ...
```

- It matches `GET` + `/api` + `/users` + **any string** in the third segment.
- The server **extracts** that segment and puts it in a slot named `id`, which the handler can use (e.g. to load the user from the DB). In the demo, the handler just echoes the ID back to prove it received it.
- The placeholder idea is used across the industry, whether the server is in Java, Python, Node.js, Go or Rust; only the syntax differs (`:id`, `{id}`, Flask's `<id>`).
- **Readability:** the route reads like a sentence: *get* data, *from users*, *the one with ID 123*. That human-readable structure is what REST aims for.
- **Terminology:** the dynamic segment is a **path parameter** (or **route parameter**), because it sits inside the path after a `/`.

### Path parameters are always strings 🎓
Even though `123` looks like a number, everything in a path (numbers, special characters) arrives as a **string**. Converting it is your job.

### 🔧 Going deeper: turning the string into a trusted value
**Problem:** the raw `id` segment is `"123"`, `"abc"` or `"1; DROP TABLE"`. Passing it straight to the DB either errors deep in your code (a 500 for what is really a client mistake) or, with string-built SQL, opens an injection hole.

**Mechanism:** validate and transform at the edge of the handler, then use parameterised queries.

```python title="users.py (FastAPI)"
from typing import Annotated

from fastapi import APIRouter, Path

router = APIRouter(prefix="/api/users")


@router.get("/{user_id}")
async def find_one(user_id: Annotated[int, Path(gt=0)]) -> User:  # "abc" → 422, "123" → 123
    return await users.find_by_id(user_id)  # SELECT ... WHERE id = %s
```

```python title="Starlette + Pydantic, by hand"
from pydantic import PositiveInt, TypeAdapter, ValidationError
from starlette.requests import Request
from starlette.responses import JSONResponse

user_id_adapter = TypeAdapter(PositiveInt)


async def get_user_endpoint(request: Request) -> JSONResponse:  # Route("/api/users/{id}", get_user_endpoint)
    try:
        user_id = user_id_adapter.validate_python(request.path_params["id"])  # "123" → 123
    except ValidationError:
        return JSONResponse({"error": "invalid id"}, status_code=400)
    user = await get_user(user_id)
    if user is None:
        return JSONResponse({"error": "user not found"}, status_code=404)
    return JSONResponse(user)
```

### 🔧 Edge case: route order and conflicts
`GET /api/users/me` and `GET /api/users/:id` **both** match `/api/users/me`.
- **Starlette/FastAPI** (like Express) picks whichever was **registered first**. Register `me` before `{user_id}`, or `me` gets treated as an ID (and an `int` parameter returns a confusing 422).
- **Radix-tree routers** such as Fastify always prefer the **static** segment over the parametric one, so order doesn't matter there.
- With `APIRouter`s, the order is the order of the decorated functions in the file and of the `include_router` calls, so put `@router.get("/me")` above `@router.get("/{user_id}")`.

➕ Dynamic routes also matter for observability: label logs and metrics with the **route template** (`/api/users/{user_id}`, from `request.scope["route"].path`), never the raw path, or every user ID becomes its own time series. See [Logging, monitoring and observability](/docs/backend-first-principles/18-logging-monitoring-observability).

## 4. Query parameters 🎓

### The idea
`GET /api/search?query=some+value`
- The **route** the server matches is still just `/api/search` (plus the method).
- After the `?` come **key=value pairs**: the **query parameters**.

### Why they exist (first principles)
- `POST`, `PUT` and `PATCH` have a **request body** to carry user-supplied values.
- In REST, a **`GET` has no body**. So how do you send values with it?
- You *could* force them into the path, e.g. `/api/search/some value`. It technically works, but path parameters have a job: **semantic expression** ("the user whose ID is 123"). A search string isn't an identity of a resource. Stuffing it into the path is hard to maintain and defeats the purpose of readable REST routes.
- **Query parameters** are the container for that **metadata about the request**.

<Mermaid chart={`flowchart TD
  Q{"Where does this value go?"}
  Q -->|"Identifies a resource (user 123)"| P["Path parameter<br/>/api/users/123"]
  Q -->|"Modifies how a GET reads data<br/>(search, page, filter, sort)"| QP["Query parameter<br/>/api/books?page=2"]
  Q -->|"Data to create or update"| B["Request body<br/>POST / PUT / PATCH"]`} />

### The lesson's example: pagination
`GET /api/books` returns one page plus **metadata**, for example:

```json
{
  "data": [ "...20 books..." ],
  "total": 100,
  "currentPage": 1,
  "totalPages": 5,
  "limit": 20
}
```

- The server applies a **default limit** (20 here) and starts at page 1, so the first request needs no query parameters.
- The client reads the metadata (100 total ÷ 20 per page = **5 pages**) and fetches the next one with **`/api/books?page=2`**.
- The same mechanism carries **filters** (by a user-defined field) and **sorting** (field and ascending or descending order).

### 🔧 Going deeper: implementing it safely

```python title="books.py (FastAPI + Pydantic + psycopg)"
import asyncio
import math
from typing import Annotated, Literal

from fastapi import Query
from psycopg import sql
from pydantic import BaseModel, Field, StringConstraints


class ListQuery(BaseModel):
    page: int = Field(1, ge=1)
    limit: int = Field(20, ge=1, le=100)  # cap it: limit=1000000 is a DoS
    sort: Literal["title", "created_at"] = "created_at"  # allow-list: never interpolate raw input
    order: Literal["asc", "desc"] = "desc"
    author: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)] | None = None


async def fetch_all(query: sql.Composable, params: dict) -> list[dict]:
    async with pool.connection() as conn:  # pool created with row_factory=dict_row
        cur = await conn.execute(query, params)
        return await cur.fetchall()


@app.get("/api/books")
async def list_books(q: Annotated[ListQuery, Query()]) -> dict:  # invalid → 422 listing every error
    where = sql.SQL("WHERE author = %(author)s") if q.author else sql.SQL("")
    direction = sql.SQL("ASC" if q.order == "asc" else "DESC")  # identifiers can't be %s parameters
    params = {"author": q.author, "limit": q.limit, "offset": (q.page - 1) * q.limit}

    rows, count = await asyncio.gather(
        fetch_all(
            sql.SQL("SELECT * FROM books {} ORDER BY {} {}, id LIMIT %(limit)s OFFSET %(offset)s").format(
                where, sql.Identifier(q.sort), direction
            ),
            params,
        ),
        fetch_all(sql.SQL("SELECT count(*)::int AS n FROM books {}").format(where), params),
    )
    total = count[0]["n"]
    return {"data": rows, "total": total, "currentPage": q.page, "totalPages": math.ceil(total / q.limit), "limit": q.limit}
```

🔧 Edge cases worth knowing:
- **Encoding:** in a query string a space can be sent as `+` or `%20`; Starlette's query parser (`urllib.parse.parse_qsl`) decodes both. A literal `+` must be sent as `%2B`, or it turns into a space.
- **Repeated keys:** `?tag=a&tag=b`. FastAPI gives a `str` parameter the **last** value (`"b"`) and silently drops the other; declare `tag: Annotated[list[str], Query()]` to receive all of them. (Express's default parser does the opposite and turns the string you expected into an array.) Decide which one you accept.
- **Stable sort:** add a unique tie-breaker (`, id`) to `ORDER BY`, otherwise rows with equal sort values can repeat or vanish between pages.
- **Deep pages:** `OFFSET 100000` still reads and discards 100,000 rows. For large tables, use **cursor (keyset) pagination**: `WHERE created_at < $cursor ORDER BY created_at DESC LIMIT 20`.
- **URLs get logged** by proxies, CDNs and browsers. Never put tokens or secrets in query parameters.

## 5. Nested routes 🎓

Not a separate *type* of routing, but a practice you see in every medium-complexity REST API: nesting resources to express relationships.

`GET /api/users/123/posts/456`: one static part and **two path parameters**. Every prefix is a meaningful route of its own, matched to a **different handler**:

| Route | Meaning |
|---|---|
| `/api/users` | all users |
| `/api/users/123` | user 123 |
| `/api/users/123/posts` | all posts of user 123 |
| `/api/users/123/posts/456` | post 456 of user 123 |

<Mermaid chart={`flowchart LR
  U["/api/users"] --> U1["/api/users/:userId"]
  U1 --> P["/api/users/:userId/posts"]
  P --> P1["/api/users/:userId/posts/:postId"]`} />

### 🔧 Going deeper: the nesting implies an authorization check
**Problem:** `/users/123/posts/456` *claims* that post 456 belongs to user 123. If the handler only does `SELECT * FROM posts WHERE id = 456`, then `/users/999/posts/456` returns the same post, and the URL lies.

**Mechanism:** use **every** path parameter in the query, so the relationship is enforced by the data layer:

```sql
SELECT * FROM posts WHERE id = $1 AND user_id = $2;   -- 0 rows → 404
```

Also check that the **caller** may see user 123's posts at all. Skipping that is the classic **IDOR / broken object-level authorization** bug. A good guideline is to nest only **one level** (`/users/:id/posts`) and expose the child directly (`/posts/:id`) after that.

### Mounting nested routes as sub-routers ➕

The table above lists nested routes one by one. In a real codebase they're **grouped**: each resource gets its own router (or controller), mounted under a prefix. That grouping has one well-known trap with path parameters. (Which middleware runs for which group, and in what order, is covered in [Controllers, services, repositories and middleware](/docs/backend-first-principles/10-controllers-services-repositories-middleware).)

#### Prefix mounting ➕

- **Problem:** defining every route with its full path (`/api/v1/users/:userId/posts/:postId`) repeats prefixes everywhere, and moving a group (a new API version, a new parent resource) means editing every line.
- **Mechanism:** a router defines paths **relative** to where it's mounted. The prefix is stripped before the sub-router matches, so the same router can be mounted in several places.

```python title="routes.py (FastAPI)"
from fastapi import APIRouter

posts = APIRouter(prefix="/{user_id}/posts")


@posts.get("")
async def list_posts_of_user(user_id: int) -> list[Post]: ...  # GET /api/v1/users/{user_id}/posts


@posts.get("/{post_id}")
async def get_post_of_user(user_id: int, post_id: int) -> Post: ...  # GET /api/v1/users/{user_id}/posts/{post_id}


users = APIRouter(prefix="/users")


@users.get("/{user_id}")
async def get_user(user_id: int) -> User: ...


users.include_router(posts)  # nested group
app.include_router(users, prefix="/api/v1")  # the whole tree under one prefix
```

Express does the same with `express.Router()` and `app.use('/prefix', router)`; NestJS with the controller path and `RouterModule`.

- **Edge cases:** `include_router` flattens everything into one route list, so `request.url.path` and `request.scope["route"].path` are always the **full** path. A sub-application attached with `app.mount("/v1", sub_app)` is different: it's a separate ASGI app with its own middleware and exception handlers, and it doesn't appear in the parent's OpenAPI schema.

#### Parent parameters in a prefix ➕

- **Problem:** the prefix `/{user_id}/posts` matches the user ID, but a handler only receives the path parameters **it declares**. If `list_posts_of_user` leaves `user_id` out of its signature, nothing complains: the route still matches, and a query without the filter returns **every** user's posts: exactly the broken object-level authorization from the previous subsection.
- **Why:** FastAPI injects values by name from the function signature; a path parameter that isn't declared is matched and then dropped. (Express has the mirror-image problem: a child router doesn't see the parent's `:userId` unless it's created with `express.Router({ mergeParams: true })`.)
- **Mechanism:** declare and type every parameter of the **full** path in every handler, so a missing or wrong value fails with a 422 instead of silently widening a query.
- **Implementation:** the declared handler, plus a test that fails loudly when any route forgets a parameter:

```python
import re


async def list_posts_of_user(user_id: int) -> list[Post]:  # declared and typed: "abc" → 422
    async with pool.connection() as conn:
        cur = await conn.execute("SELECT * FROM posts WHERE user_id = %s ORDER BY id", (user_id,))
        return await cur.fetchall()


def test_every_path_param_is_declared() -> None:
    for path, operations in app.openapi()["paths"].items():
        in_template = set(re.findall(r"{(\w+)", path))
        for method, op in operations.items():
            declared = {p["name"] for p in op.get("parameters", []) if p["in"] == "path"}
            assert declared == in_template, f"{method.upper()} {path}: {in_template - declared} not declared"
```

- **Edge cases:** type checkers won't catch this: nothing compares the path string with the signature. Next to the test above, add one integration test per nested route that asserts user A's posts URL never returns user B's posts.

## 6. Route versioning and deprecation 🎓

### The demo
- `GET /api/v1/products` returns items shaped `{ id, name, price }`.
- `GET /api/v2/products` returns items shaped `{ id, title, price }`.

### The problem it solves
A response format is a **contract**. Say the API served a web app, then a new **React Native / Android / Flutter** client arrives with new requirements and the response must change. Changing it in place **breaks every existing client**.

**Options:**
1. A new path such as `/api/new-products`: messy, and the name says nothing.
2. **Versioning:** keep `v1` exactly as it was and serve the new shape at `v2`. It states the intent clearly and doesn't require renaming the route.

### The deprecation workflow
1. Ship `v2`.
2. Announce that `v1` is **deprecated** (e.g. tell the frontend teams).
3. Give clients a **migration window** to move their calls to `v2`.
4. Remove `v1` completely. (The lesson phrases this as v2 eventually becoming "the" version.)

This gives you a stable process for shipping **breaking changes**.

<Mermaid chart={`stateDiagram-v2
  [*] --> Active: v1 released
  Active --> Deprecated: v2 released, v1 announced deprecated
  Deprecated --> Deprecated: clients migrate during the window
  Deprecated --> Removed: sunset date passes
  Removed --> [*]: v1 returns 410 or 404`} />

### 🔧 Going deeper: implementing it

**URI versioning in FastAPI:** one router per version, each under its own prefix:

```python title="main.py"
app.include_router(products_v1, prefix="/api/v1")  # → /api/v1/products
app.include_router(products_v2, prefix="/api/v2")  # → /api/v2/products
```

```python title="products.py"
from decimal import Decimal
from typing import Annotated

from fastapi import APIRouter, Depends
from pydantic import BaseModel


class ProductV1(BaseModel):
    id: int
    name: str
    price: Decimal


class ProductV2(BaseModel):
    id: int
    title: str
    price: Decimal


Svc = Annotated[ProductService, Depends(get_product_service)]

products_v1 = APIRouter(prefix="/products", deprecated=True, dependencies=[Depends(deprecate_v1)])
products_v2 = APIRouter(prefix="/products")


@products_v1.get("")
async def list_v1(svc: Svc) -> list[ProductV1]:
    return [ProductV1(id=p.id, name=p.title, price=p.price) for p in await svc.list()]


@products_v2.get("")
async def list_v2(svc: Svc) -> list[ProductV2]:
    return await svc.list()  # { id, title, price }
```

Both versions share **one service**; only the **response mapping** differs. Don't fork the business logic per version.

**Machine-readable deprecation:** besides telling people (and `deprecated=True`, which marks the operations in the OpenAPI docs), tell clients in headers on every `v1` response, with a router-level dependency:

```python title="deprecation.py"
from fastapi import Response


async def deprecate_v1(response: Response) -> None:
    response.headers["Deprecation"] = "@1767225600"  # RFC 9745: deprecated since this Unix time
    response.headers["Sunset"] = "Wed, 30 Jun 2027 23:59:59 GMT"  # RFC 8594: when it stops working
    response.headers["Link"] = '</api/v2/products>; rel="successor-version"'
```

Then **log calls to v1 per client** so you know who still needs to migrate before you remove it. After removal, `410 Gone` is more informative than `404`.

**Other versioning styles** (covered later in the series): a header (`Accept: application/vnd.example.v2+json` or a custom header) or a query string (`?version=2`). URI versioning is the most visible and the easiest to cache and debug.

## 7. Catch-all routes 🎓

- **The demo:** `GET /api/v3/products`, a route the server has **no handler** for.
- **Mechanism:** after all the real routes, register a final wildcard such as `/*`. Any request that fell through every other matcher lands there, and its handler returns a **friendly "route not found" message**.
- **Why:** without it you get the framework's default (the lesson calls it an empty or null response). A clear message tells the client this endpoint doesn't exist.

<Mermaid chart={`flowchart TD
  REQ["GET /api/v3/products"] --> R1{"matches /api/v1/products?"}
  R1 -->|no| R2{"matches /api/v2/products?"}
  R2 -->|no| R3{"... other routes ..."}
  R3 -->|no| C["catch-all handler<br/>404 Route not found"]`} />

### 🔧 Going deeper: catch-all in FastAPI

```python title="main.py (FastAPI)"
from fastapi import Request
from fastapi.responses import JSONResponse


# ...all real routes first...
@app.api_route("/{full_path:path}", methods=["GET", "POST", "PUT", "PATCH", "DELETE"], include_in_schema=False)
async def route_not_found(request: Request, full_path: str) -> JSONResponse:  # the :path converter also matches "/"
    return JSONResponse(
        {"error": "Route not found", "method": request.method, "path": request.url.path}, status_code=404
    )
```

- Starlette's path syntax: `{name}` matches one segment (`[^/]+`), `{name:path}` matches the rest of the path including slashes, and `int`, `float` and `uuid` convertors restrict a segment's shape. (Express 5 writes the catch-all as `/{*splat}`; Express 4 used `*`.)
- **FastAPI** already returns a JSON 404 for unknown routes (`{"detail":"Not Found"}`). To customise the body, register an exception handler for Starlette's `HTTPException` (status 404) instead of a wildcard route. The wildcard has a cost: it **fully** matches `DELETE /api/books`, and Starlette prefers a full match over a path-only match, so the automatic 405 for that path becomes your 404.
- **404 vs 405:** if the **path exists** but not with that method (e.g. `DELETE /api/books`), the correct response is **`405 Method Not Allowed`** with an `Allow: GET, POST` header. Starlette does this automatically (with the incomplete-`Allow` caveat from section 1); many frameworks return 404 by default; the tiny router in section 1 shows how to tell them apart.
- **SPA fallback:** when the same server also serves a single-page app, the catch-all for **non-API paths** returns `index.html` (the client-side router handles it), while unknown `/api/*` paths still return a JSON 404. Mixing those up turns API typos into `200 OK` HTML responses.

## 8. Recap 🎓

| Concept | Example | Purpose |
|---|---|---|
| Routing | method + path → handler | the **where** of a request |
| Static route | `/api/books` | constant path |
| Dynamic route / path param | `/api/users/:id` | identifies a specific resource; value arrives as a string |
| Query param | `/api/search?query=x`, `?page=2` | metadata for GETs: search, pagination, filter, sort |
| Nested route | `/api/users/123/posts/456` | expresses relationships between resources |
| Versioning | `/api/v1/...`, `/api/v2/...` | breaking changes without breaking clients |
| Deprecation | announce, migration window, remove | retire old versions safely |
| Catch-all | `/*` last | friendly response for unknown routes |
| ➕ Radix tree | static, then param, then wildcard | lookup cost follows path length; overlaps resolved by priority, with backtracking |
| ➕ Regex routes | `/:a-:b` | ReDoS risk (CVE-2024-45296); one param per segment, validate in the handler |
| ➕ HEAD / OPTIONS | Express, Starlette `Route`: GET serves HEAD; FastAPI: 405 with `Allow` | register HEAD explicitly (cheap for expensive GETs); CORS middleware outermost |
| ➕ Same path? | `/books` vs `/books/` vs `/Books` | know your framework's defaults; one canonical form; proxy and app must agree |
| ➕ Sub-routers | `users.include_router(posts)` | prefixes in one place; declare every path parameter or the parent ID is silently ignored |

That's enough to open a backend codebase, understand its routing, change it and add new routes.

## Interview questions

1. **What does a router use to pick a handler?** **The HTTP method plus the URL path. `GET /books` and `POST /books` are different routes.**
2. **Path parameter vs query parameter: when do you use which?** **Path parameters identify a resource (`/users/123`). Query parameters modify how a GET reads data: search, pagination, filters, sorting.**
3. **Why must you validate path parameters even if they "look like" numbers?** **They always arrive as strings. Convert and validate at the edge (400 on failure) and use parameterised queries.**
4. **`/users/me` and `/users/:id` both exist. What can go wrong?** **In order-based routers (Express, Starlette/FastAPI), whichever is registered first wins, so `me` may be treated as an ID. Register static routes first; radix-tree routers prefer static segments automatically.**
5. **What's the security risk of `/users/:userId/posts/:postId`?** **Loading the post by `postId` alone ignores ownership (IDOR). Filter by both IDs and check that the caller may access that user's data.**
6. **How do you ship a breaking response change?** **Version the API (`/v2`), keep v1 unchanged, mark v1 deprecated (announce plus `Deprecation`/`Sunset` headers), give a migration window, monitor v1 usage, then remove it.**
7. **What should a request for a non-existent route return?** **A clear 404 from a catch-all registered last. If the path exists with other methods, 405 with an `Allow` header.**
8. **Why is `OFFSET` pagination slow on page 5,000?** **The DB still reads and discards every skipped row. Use keyset (cursor) pagination for deep pages.**
9. ➕ **Why is a radix-tree router's lookup independent of the number of routes, and how does it resolve `/users/me` vs `/users/:id`?** **It walks the request path through nodes keyed by shared prefixes, so cost depends on path length. At each node it tries static children first, then the parameter, then the wildcard, backtracking if a static branch fails deeper.**
10. ➕ **How can a route pattern take down a server?** **Order-based routers compile paths to regexes. An ambiguous pattern like `/:a-:b` produced a catastrophically backtracking regex in Express (CVE-2024-45296), and Starlette's `{a}-{b}` is quadratic; either one blocks the event loop on a crafted URL. Keep one parameter per segment and keep the framework updated.**
11. ➕ **What does FastAPI do with HEAD and OPTIONS requests you didn't register?** **Both get 405, with an `Allow` header listing the methods of the first route that matched the path (Express and Starlette's plain `Route` serve HEAD from the GET handler instead). Register HEAD explicitly, cheaply for expensive GETs, and make `CORSMiddleware` the outermost layer so preflights get CORS headers.**
12. ➕ **Nginx denies `/admin`, yet `/ADMIN` reaches the admin handler. Why?** **Nginx location matching is case-sensitive, Express routing is case-insensitive by default (Starlette's isn't). Enforce authorization in the app and enable case-sensitive routing so both layers agree.**
13. ➕ **A FastAPI route under `/users/{user_id}/posts` returns every user's posts. Why?** **The handler didn't declare `user_id`, so FastAPI matched it and never passed it, and the query ran without the filter. Declare and type every path parameter, and test that every route declares all of them.**
