## 1. The two core ideas of HTTP 🎓

### Idea 1: statelessness

**What it means:** the server keeps **no memory of past interactions**. Each request carries everything needed to process it (URL, method, headers...). After responding, the server forgets the request. The next request from the same client is a **new, unrelated event**.

**Consequence: self-contained requests.** If the server must know who you are (e.g. to return your profile), **every** request has to include credentials such as a **cookie or token**.

**Why it's designed this way (benefits):**
- **Simplicity:** the server doesn't need to store session information, which would cost resources and complexity.
- **Scalability:** any server can handle any request, so load can be spread across many servers. No single server owns a client's session.
- **Resilience:** if a server crashes, there's no in-memory session to lose or restore.

**But apps do need state** (logins, shopping carts). Developers add it **on top** of HTTP with **cookies, sessions or tokens** (covered later in the series).

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant LB as Load balancer
  participant S1 as Server 1
  participant S2 as Server 2
  C->>LB: GET /profile + Cookie or Bearer token
  LB->>S1: forward
  S1-->>C: 200 profile (S1 then forgets)
  C->>LB: GET /orders + same token again
  LB->>S2: forward (a different server is fine)
  S2-->>C: 200 orders`} />

🔧 **Where the state actually lives:** "stateless" refers to the **protocol and the app servers**. The state moves to either the **client** (a signed token such as a JWT, verified on every request) or a **shared store** (a session ID in a cookie, looked up in Redis or Postgres by any server). Keeping sessions in one server's memory breaks the scalability benefit, because the next request may land on another server.

### Idea 2: the client-server model
- The **client** (browser, mobile app, another server) **initiates** communication and supplies everything the server needs: URL, headers, body.
- The **server** hosts resources (websites, APIs, files) and **waits** for requests. It processes each one and returns a response: a page, JSON, a file, an error message...
- **Rule:** in HTTP, communication is **always initiated by the client**. The server only responds.

🔧 That rule is why "server pushes data to the browser" needs a workaround: polling, Server-Sent Events (a long-lived response) or WebSockets (an upgraded connection). All of them start with a client request.

### HTTP vs HTTPS
For these notes, treat them as **interchangeable**. HTTPS is HTTP with **encryption and certificates (TLS)**. The principles are the same; the extra parts belong more to network engineering. Section 20 covers TLS briefly.

## 2. The transport underneath 🎓

- **Problem:** before any message can be sent, client and server need a **connection mechanism**.
- HTTP **doesn't strictly require** a connection-based transport. It requires a **reliable** one: messages must not be lost silently (at minimum, errors must be reported).
- Of the two common internet transports, **TCP** (reliable, connection-based) and **UDP** (no delivery guarantee), TCP fits. So HTTP traditionally runs over **TCP**, which opens connections with a **three-way handshake**.

### Where this sits: the OSI model
- Backend engineers mostly work at **layer 7, the application layer**, where HTTP lives.
- TCP handshakes, TLS encryption and so on belong to lower layers. They're good to know, but the lesson deliberately doesn't go down that rabbit hole.

🔧 The handshake costs, which explain the version history below:

<Mermaid chart={`sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: SYN
  S-->>C: SYN-ACK
  C->>S: ACK (1 round trip spent)
  C->>S: TLS ClientHello
  S-->>C: TLS ServerHello + certificate (TLS 1.3, 1 more round trip)
  C->>S: GET /api/users (finally)
  S-->>C: 200 OK`} />

On a 100 ms round-trip link, that's about **200 ms before the first byte of the request** is even sent. Opening a new connection per request is expensive.

## 3. HTTP versions 🎓

| Version | What it changed | Problem it solved |
|---|---|---|
| **1.0** | a **new connection per request** | (baseline) every request paid the full handshake |
| **1.1** | **persistent connections**, chunked transfer encoding, better caching | reuse one TCP connection for many requests |
| **2.0** | **multiplexing** (many requests and responses at once on one connection), **binary framing** instead of text, **header compression (HPACK)**, **server push** | one slow response no longer blocks others at the HTTP level; headers stop being resent in full |
| **3.0** | built on **QUIC**, a transport over **UDP** instead of TCP | faster connection setup, lower latency, better behaviour under packet loss, multiplexing **without head-of-line blocking** |

### 🔧 Head-of-line blocking, explained
- In **HTTP/1.1**, a connection carries one response at a time. Browsers open about 6 connections per host to work around it.
- **HTTP/2** interleaves many streams on **one TCP connection**. But TCP delivers bytes **strictly in order**: if one packet is lost, **every stream waits** for its retransmission, even streams whose data already arrived. That's TCP-level head-of-line blocking, which HTTP/2 still has.
- **HTTP/3 / QUIC** implements streams **in the transport itself** (over UDP), so a lost packet only stalls the stream it belonged to.

🔧 **Server push is effectively dead:** Chrome disabled HTTP/2 server push by default in **Chrome 106**, as it rarely improved performance. The recommended replacements are **`103 Early Hints`** and `<link rel="preload">`.

**The practical takeaway (lesson):** client and server establish some kind of connection, and messages are sent and received over it. That's enough to work at the application level.

## 4. HTTP/2 and HTTP/3 in practice ➕

The table above says what each version changed. In production, though, the version is picked **separately on every hop**, and that has direct consequences for how a Node backend is deployed, debugged and attacked.

<Mermaid chart={`flowchart LR
  B["Browser"] -->|"h3 over QUIC/UDP<br/>or h2 over TLS/TCP"| CDN["CDN / load balancer"]
  CDN -->|"HTTP/1.1 keep-alive pool<br/>(or h2 for gRPC)"| NX["Nginx"]
  NX -->|"HTTP/1.1"| APP["Node app<br/>node:http"]`} />

#### How a connection picks HTTP/2: ALPN ➕

- **Problem:** HTTP/1.1, HTTP/2 and HTTPS all share port 443. HTTP/2 is a binary protocol, so if the client starts speaking h2 and the server expects h1 text, the first byte is already garbage. The two sides must agree on a version **before** the first request byte.
- **Why it can't be negotiated in HTTP itself:** an "upgrade" exchange in HTTP would cost a round trip and require speaking one version first.
- **Mechanism:** **ALPN** (Application-Layer Protocol Negotiation, RFC 7301) puts the choice inside the TLS handshake that happens anyway. The ClientHello lists the protocols the client supports (`h2`, `http/1.1`); the server picks one in its reply. No extra round trip. Browsers only use HTTP/2 **over TLS**; the cleartext variant (`h2c`) exists, but browsers don't implement it.
- **Implementation:** check what a server negotiates.

```bash
curl -sS -o /dev/null -w '%{http_version}\n' https://example.com          # 2 or 1.1 (or 3)
openssl s_client -connect example.com:443 -servername example.com -alpn h2,http/1.1 </dev/null 2>/dev/null | grep -i alpn
# ALPN protocol: h2
```

```ts title="h2-server.ts (Node's own HTTP/2 server)"
import { createSecureServer } from 'node:http2';
import { readFileSync } from 'node:fs';

createSecureServer({
  key: readFileSync('key.pem'), cert: readFileSync('fullchain.pem'),
  allowHTTP1: true,                         // ALPN offers h2 and http/1.1; old clients still work
}, (req, res) => res.end(`you spoke HTTP/${req.httpVersion}`)).listen(8443);
```

- **Edge cases:** ALPN is negotiated with **whoever terminates TLS**. If the load balancer terminates it, "we support HTTP/2" is a property of the LB, not of your app. And if a client doesn't send ALPN at all (some old libraries), it gets HTTP/1.1.

#### Why your Node app usually speaks HTTP/1.1 to its proxy ➕

- **Problem:** you enable HTTP/2 on the load balancer and expect your Express app to receive HTTP/2. It doesn't, and that is normal.
- **Why (first principles):** HTTP/2's wins (multiplexing, header compression, one connection instead of six) matter on the **long, high-latency, lossy** link between the user and the edge. Between the proxy and your app, the network is short and fast, and the proxy keeps a **pool of warm HTTP/1.1 keep-alive connections**, so there are no handshakes left to save. Also, Nginx's proxy module only speaks **HTTP/1.0 or 1.1** to upstreams, and Express is built on `node:http`'s HTTP/1.1 API.
- **Mechanism:** the proxy terminates h2 or h3, turns every stream into an ordinary HTTP/1.1 request, and sends it over a reused upstream connection.
- **Implementation:** the one Nginx setting people miss. `proxy_http_version` **defaults to 1.0**, which means a new upstream connection per request:

```nginx title="nginx upstream keep-alive"
upstream app {
    server 127.0.0.1:3000;
    keepalive 32;                         # idle connections kept open per worker
}
server {
    listen 443 ssl;
    http2 on;                             # h2 toward clients (nginx 1.25.1+ syntax)
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;           # default is 1.0: no keep-alive upstream
        proxy_set_header Connection "";   # don't forward "Connection: close"
    }
}
```

- **Edge cases:** without upstream keep-alive, a busy proxy opens thousands of short connections, leaving sockets in `TIME_WAIT` and eventually running out of local ports. The keep-alive 502 bug in section 15 applies to this pool too.

#### gRPC rides on HTTP/2 ➕

- **Problem:** service-to-service calls want typed contracts, compact binary payloads and streaming in both directions.
- **Mechanism:** gRPC maps every call onto **one HTTP/2 stream**: a `POST /package.Service/Method` with `content-type: application/grpc`, length-prefixed Protobuf messages in DATA frames, and the call's result in **trailers** (headers sent after the body: `grpc-status`, `grpc-message`).
- **Why it needs HTTP/2:** trailers and full bidirectional streaming on a single request are first-class in HTTP/2. Browsers' `fetch` can't read trailers, which is why browsers need **gRPC-Web** through a translating proxy.
- **Implementation:** what a unary call looks like on the wire (simplified):

```http
:method: POST
:path: /orders.v1.OrderService/GetOrder
content-type: application/grpc
te: trailers

(DATA: 1-byte compressed flag + 4-byte length + protobuf bytes)

(trailers) grpc-status: 0
```

- **Edge cases:** an **L4 (TCP) load balancer** balances **connections**, not requests. A gRPC client keeps one long-lived HTTP/2 connection, so every call from that client lands on the same backend and new replicas get no traffic. Use an L7 balancer that understands HTTP/2 (Envoy, an ALB target group with the gRPC protocol version, Nginx `grpc_pass`) or client-side balancing. Any hop that downgrades to HTTP/1.1 breaks gRPC entirely.

#### HTTP/3: Alt-Svc discovery and the UDP fallback ➕

- **Problem:** HTTP/3 runs over QUIC on **UDP**, so it can't be negotiated inside a TCP connection's TLS handshake the way ALPN picks h2. How does a browser learn that UDP 443 is worth trying?
- **Mechanism:** the server advertises it on a normal h1/h2 response with **`Alt-Svc: h3=":443"; ma=86400`** ("the same origin is also available over HTTP/3 on UDP 443, remember for a day"). The browser tries QUIC on later connections. A DNS **HTTPS record** (RFC 9460) can advertise `h3` before the first connection.
- **Why fallback is built in:** many corporate networks block or throttle UDP 443. Browsers race or fall back to TCP, so h3 can only ever make things faster, never break them.
- **Implementation:** in practice you let the CDN do h3. On your own Nginx (1.25+):

```nginx
server {
    listen 443 quic reuseport;            # UDP
    listen 443 ssl;                       # TCP stays: it's the fallback
    http2 on;
    add_header Alt-Svc 'h3=":443"; ma=86400';
}
```

- **Edge cases:** the cloud firewall from lesson 3 must allow **UDP** 443, not just TCP. If it doesn't, nothing breaks visibly; clients just never use h3, which makes the mistake easy to miss. Load balancers in front must support UDP/QUIC too.

#### The HTTP/2 Rapid Reset attack (CVE-2023-44487) ➕

- **Problem:** in October 2023, attackers used one HTTP/2 feature to produce the largest DDoS attacks seen at the time (Google reported a peak of about **398 million requests per second**).
- **Why it works (first principles):** HTTP/2 lets a client open a stream and **cancel it immediately** with a `RST_STREAM` frame. The cancelled stream no longer counts toward the server's concurrent-stream limit, but the server has already parsed the headers, allocated state and maybe dispatched the request upstream. Sending "open, cancel, open, cancel..." costs the client almost nothing per request and costs the server real work, without ever hitting the concurrency cap.
- **Mechanism that solves it:** servers now **count resets per connection** and close abusive connections with `GOAWAY`. Node.js shipped the fix (a rate limit on `RST_STREAM` in its bundled nghttp2) in **18.18.2 and 20.8.1**.
- **Implementation:** don't expose a self-managed HTTP/2 endpoint without keeping it patched; better, terminate h2 at a managed CDN or load balancer. Check your runtime:

```bash
node -p "process.versions.node + ' nghttp2 ' + process.versions.nghttp2"
```

- **Edge cases:** the general lesson is that **protocol features are attack surface**. Each new capability (streams, header compression, server push) adds a way to make the server do more work than the client. Keep the component that faces the internet narrow and patched.

## 5. Anatomy of an HTTP message 🎓

A **request** is what the client sends; a **response** is what the server sends back. Both are text (in HTTP/1.1) with the same overall shape:

```http title="request"
POST /api/users HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0 ...
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Content-Length: 39
Accept: application/json

{"name":"Asha","email":"asha@site.com"}
```

```http title="response"
HTTP/1.1 201 Created
Date: Fri, 02 Oct 2026 10:00:00 GMT
Content-Type: application/json
Content-Length: 52
Location: /api/users/42

{"id":42,"name":"Asha","email":"asha@site.com"}
```

| Part | Request | Response |
|---|---|---|
| Start line | **method**, **resource URL**, **HTTP version** | **HTTP version**, **status code** + reason (`200 OK`) |
| Headers | key-value metadata, including **Host** (the target domain) | key-value metadata |
| Blank line | marks **the end of headers**, start of body | same |
| Body | data the client sends (optional) | the resource or error (optional) |

🔧 **See it raw yourself:**

```bash
curl -v https://api.example.com/users        # > lines are the request, < lines the response
```

🔧 **Edge case: how does the receiver know where the body ends?** Either `Content-Length` (exact byte count) or `Transfer-Encoding: chunked` (size-prefixed chunks, a zero-size chunk at the end). If both are present and a proxy and server disagree about which one wins, you get **request smuggling**, a real attack class. Never hand-craft these headers in your app; let the server library manage them.

### URL anatomy and percent-encoding ➕

The start line carries the request **target**, and many real bugs come from not knowing which part of a URL is which, which parts reach the server, and how each part is encoded.

```text
https://ana:pw@api.example.com:8443/v1/files/report%202026.pdf?q=caf%C3%A9&tag=a&tag=b#page=3
```

| Part | In the example | Reaches the server? | Notes |
|---|---|---|---|
| scheme | `https` | decides TCP port and TLS, not sent as text | |
| userinfo | `ana:pw` | no: curl turns it into `Authorization: Basic`, `fetch` rejects URLs that contain it | never put credentials in URLs |
| host, port | `api.example.com`, `8443` | as the **`Host` header** (and TLS SNI), not in the request line | host names are case-insensitive |
| path | `/v1/files/report%202026.pdf` | yes, in the request line | case-sensitive by spec (RFC 3986) |
| query | `q=caf%C3%A9&tag=a&tag=b` | yes, in the request line | logged by every proxy and CDN |
| fragment | `page=3` (after `#`) | **never**, it stays in the browser | so the server can't route on it |

On the wire, the request line holds only path and query (`GET /v1/files/report%202026.pdf?q=caf%C3%A9 HTTP/1.1`); the authority travels in `Host`.

#### Percent-encoding: which characters and which function ➕

- **Problem:** characters such as `/ ? # & = +` and spaces have **structural meaning** in a URL. A filename containing `&` or a search term containing `#` would split the URL in the wrong place.
- **Mechanism:** data is **percent-encoded**: each byte of its **UTF-8** encoding becomes `%XX`. `é` is two bytes, so it becomes `%C3%A9`.
- **Implementation:** pick the function by what you're encoding.

```ts
encodeURIComponent('a/b c&d');            // 'a%2Fb%20c%26d'  one path segment or one query value
encodeURI('https://x.com/a b?q=1');       // 'https://x.com/a%20b?q=1'  keeps / ? & : whole URLs only
new URLSearchParams({ q: 'a b+c' }).toString();   // 'q=a+b%2Bc'  form encoding: space becomes +

const url = new URL('https://api.example.com/v1/search');
url.searchParams.set('q', userInput);     // encodes correctly, whatever the input
```

- **Edge cases:**
  - `+` means a space **only in the query string** (form encoding). In a path, `+` is a literal plus.
  - **Double decoding** is a classic security bug: `%252e%252e%252f` decodes once to `%2e%2e%2f` and twice to `../`. If a proxy decodes once for its security check and the app decodes again, a path that looked safe becomes a traversal.
  - An encoded slash (`%2F`) inside a path segment is decoded, rejected or kept by different proxies and frameworks. Avoid designing APIs that need it.

#### Building outbound URLs safely ➕

- **Problem:** ``fetch(`${BILLING}/customers/${id}`)`` with `id = '../admin/export'` calls a **different endpoint** of the internal service than you meant. This is path injection, a cousin of SSRF.
- **Mechanism:** encode every user-supplied piece as a **single segment** and let the `URL` class assemble the result, then check the result still points where you intended.

```ts title="outbound-url.ts"
export function billingUrl(customerId: string) {
  const url = new URL('https://billing.internal/v1/customers/');
  url.pathname += encodeURIComponent(customerId);           // '../admin' becomes '..%2Fadmin', one segment
  if (url.origin !== 'https://billing.internal') throw new Error('unexpected origin');
  return url;
}
```

- **Edge case:** `new URL(input, base)` with `input = '//evil.com/x'` resolves to **`https://evil.com/x`**: a protocol-relative reference replaces the host. Never pass user input as the first argument with a trusted base.

### Exercise: an HTTP/1.1 server on a raw TCP socket ➕

The quickest way to internalise message anatomy is to do the framing yourself: read bytes from a TCP socket, find the blank line, parse the head, read exactly `Content-Length` bytes of body and write a response by hand.

```ts title="raw-http.ts (learning only, never production)"
import { createServer, type Socket } from 'node:net';

const MAX_HEAD = 16 * 1024;
const MAX_BODY = 1024 * 1024;
const REASON: Record<number, string> = {
  200: 'OK', 400: 'Bad Request', 413: 'Content Too Large', 431: 'Request Header Fields Too Large', 501: 'Not Implemented',
};

createServer((socket) => {
  let buf = Buffer.alloc(0);

  socket.on('data', (chunk) => {
    buf = Buffer.concat([buf, chunk]);
    while (true) {                                            // one chunk may hold half a request, or two
      const end = buf.indexOf('\r\n\r\n');                    // the blank line ends the head
      if (end === -1) {
        if (buf.length > MAX_HEAD) reply(socket, 431, 'headers too large', true);
        return;                                               // wait for more bytes
      }
      const [requestLine, ...lines] = buf.subarray(0, end).toString('latin1').split('\r\n');
      const [method, target, version] = requestLine.split(' ');
      const headers = new Map<string, string>();
      for (const line of lines) {
        const i = line.indexOf(':');
        headers.set(line.slice(0, i).trim().toLowerCase(), line.slice(i + 1).trim());   // names are case-insensitive
      }
      if (headers.has('transfer-encoding')) return reply(socket, 501, 'chunked bodies not supported', true);
      const length = Number(headers.get('content-length') ?? 0);
      if (!Number.isInteger(length) || length < 0) return reply(socket, 400, 'bad Content-Length', true);
      if (length > MAX_BODY) return reply(socket, 413, 'body too large', true);
      if (buf.length < end + 4 + length) return;              // body hasn't fully arrived yet

      const body = buf.subarray(end + 4, end + 4 + length).toString('utf8');
      buf = buf.subarray(end + 4 + length);                   // keep pipelined bytes for the next loop
      const close = version === 'HTTP/1.0' || headers.get('connection')?.toLowerCase() === 'close';
      reply(socket, 200, JSON.stringify({ method, target, headers: Object.fromEntries(headers), body }), close);
      if (close) return;
    }
  });
}).listen(8080);

function reply(socket: Socket, status: number, body: string, close: boolean) {
  const bytes = Buffer.from(body, 'utf8');
  socket.write(
    `HTTP/1.1 ${status} ${REASON[status]}\r\n` +
    `Content-Type: application/json; charset=utf-8\r\n` +
    `Content-Length: ${bytes.length}\r\n` +                   // bytes, not string characters
    `Connection: ${close ? 'close' : 'keep-alive'}\r\n\r\n`);
  socket.write(bytes);
  if (close) socket.end();
}
```

```bash
curl -v localhost:8080/hello -d 'name=asha'
# two pipelined requests in one TCP write: the loop answers both
printf 'GET /a HTTP/1.1\r\nHost: x\r\n\r\nGET /b HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n' | nc localhost 8080
```

What it teaches, and why real servers are much bigger:
- **TCP is a byte stream, not a message stream.** A `data` event can contain a partial head, a whole request plus half of the next, or two pipelined requests. Every parser needs a buffer and a loop.
- **Every unbounded buffer is a denial of service.** Without `MAX_HEAD`, a client that never sends the blank line grows `buf` forever; without `MAX_BODY`, one `Content-Length: 99999999999` does the same. Real servers cap the head, the body and the time (section 19).
- **Framing is the security boundary.** Supporting chunked encoding correctly, rejecting conflicting `Content-Length` values and handling obsolete line folding are exactly where request smuggling bugs live. That is why you use `node:http` (built on the hardened `llhttp` parser) in production.

## 6. Where the time goes: the request lifecycle and a timing toolkit ➕

Once you can read a message, the next practical skill is answering "**which hop** made this request slow?". Every request pays a sequence of costs, and each tool below measures some of them.

<Mermaid chart={`flowchart LR
  D["DNS lookup<br/>0 ms cached<br/>20-100 ms cold"] --> T["TCP connect<br/>1 round trip"]
  T --> S["TLS 1.3<br/>1 round trip"]
  S --> P["CDN / LB / proxy<br/>about 1 ms each"]
  P --> A["App: parse, auth,<br/>validation, logic"]
  A --> DB["DB queries<br/>about 1-10 ms each"]
  DB --> R["Response transfer<br/>size / bandwidth"]`} />

Rough orders of magnitude for a client and server in the same region; across continents each round trip is 70 to 200 ms. On a **reused** connection the first three boxes disappear, which is why keep-alive (section 15) matters so much.

#### `curl -w`: a per-phase timing breakdown ➕

- **Problem:** "the API is slow" doesn't say whether the time went to DNS, the handshake, the server's work or the download.
- **Mechanism:** curl records a timestamp at the end of each phase, measured **cumulatively from the start**, and `-w` prints them.

```bash title="timing.sh"
cat > curl-format.txt <<'EOF'
   dns:       %{time_namelookup}s
   connect:   %{time_connect}s
   tls:       %{time_appconnect}s
   ttfb:      %{time_starttransfer}s
   total:     %{time_total}s
   http:      %{http_version}  status %{http_code}  size %{size_download}B
EOF
curl -sS -o /dev/null -w @curl-format.txt https://api.example.com/v1/books
```

| Subtract | What it measures |
|---|---|
| `time_connect - time_namelookup` | TCP handshake, about one network round trip |
| `time_appconnect - time_connect` | TLS handshake |
| `time_starttransfer - time_appconnect` | sending the request plus **server processing**: the backend's share (TTFB) |
| `time_total - time_starttransfer` | downloading the body |

- **Edge cases:** the values are cumulative, so read differences, not raw numbers. `time_appconnect` is 0 for plain HTTP. One sample tells you little: the first run includes a cold DNS lookup. Loop it (`for i in $(seq 20); do curl ...; done`) and look at the spread.

#### DevTools Timing tab and `Server-Timing` ➕

- **Problem:** browsers add phases curl doesn't have, and the server's own time is a black box in "Waiting for server response".
- **Mechanism:** the Network panel's **Timing** tab shows *Queueing* and *Stalled* (waiting for a free connection: HTTP/1.1 allows about 6 per host, and requests are prioritised), *DNS Lookup*, *Initial connection*, *SSL*, *Request sent*, *Waiting for server response* (TTFB) and *Content Download*. Your server can fill in the black box with a **`Server-Timing`** header, which DevTools displays in the same tab.

```ts title="server-timing.ts"
import onHeaders from 'on-headers';                       // same helper morgan and compression use

app.use((req, res, next) => {
  const marks: string[] = [];
  res.locals.time = async <T,>(name: string, fn: () => Promise<T>) => {
    const t0 = performance.now();
    try { return await fn(); } finally { marks.push(`${name};dur=${(performance.now() - t0).toFixed(1)}`); }
  };
  onHeaders(res, () => {                                   // runs just before the headers are written
    if (req.user?.isStaff && marks.length) res.setHeader('Server-Timing', marks.join(', '));
  });
  next();
});

// in a handler: const rows = await res.locals.time('db', () => pool.query(sql, args));
// response header: Server-Timing: db;dur=41.3, render;dur=2.1
```

- **Edge cases:** long *Stalled* times usually mean too many parallel requests to one HTTP/1.1 origin, not a slow server. `Server-Timing` exposes internals (which queries you run and how long they take), so send it only to staff or in non-production. For cross-origin requests, the browser hides the details unless the server also sends `Timing-Allow-Origin`.

#### HAR files: capturing a session to share ➕

- **Problem:** the bug only reproduces on a customer's machine, and "it's slow" or "it fails sometimes" isn't something you can debug from a description.
- **Mechanism:** a **HAR** (HTTP Archive) file is JSON describing every request in a session: URLs, headers, bodies, status codes and per-phase timings. The user exports it from the Network panel; you read it in DevTools (drag it in) or with `jq`:

```bash
jq -r '.log.entries[] | [.response.status, (.timings.wait|floor), .request.method, .request.url] | @tsv' session.har \
  | sort -k2 -n -r | head        # slowest server waits first
```

- **Edge cases:** HAR files are **credentials**. In October 2023, attackers who broke into Okta's support system used session tokens from customer-uploaded HAR files to hijack sessions. Chromium-based browsers (Chrome 130+) now export **sanitized** HARs by default, without `Cookie`, `Set-Cookie` and `Authorization`, but tokens in **query strings**, request bodies and response bodies (PII) are still included. Ask for the minimum, store them like secrets and delete them after the investigation.

#### `--resolve`, `--http2` and friends: testing one hop at a time ➕

- **Problem:** you need to hit **one specific server** behind DNS and the CDN: a new box before the DNS cutover, a single replica, or the origin directly.
- **Why `curl https://10.0.0.5/` doesn't work:** the TLS handshake then sends no proper SNI and the certificate doesn't match an IP, and the `Host` header is wrong, so the server picks the wrong virtual host.
- **Mechanism:** `--resolve host:port:address` pins the name to an IP **inside curl only**, while SNI, certificate checks and `Host` stay correct.

```bash
curl -v --resolve api.example.com:443:203.0.113.10 https://api.example.com/healthz   # this exact server
curl -v --connect-to api.example.com:443:origin.internal:443 https://api.example.com/ # different host:port
curl -sS -o /dev/null -w '%{http_version}\n' --http2   https://api.example.com/        # force-try h2
curl -sS -o /dev/null -w '%{http_version}\n' --http1.1 https://api.example.com/        # compare with h1
curl --http3 https://api.example.com/                  # only if your curl build has HTTP/3 support
```

- **Edge cases:** `--resolve` matches the exact `host:port`, so a redirect to another host goes through normal DNS again. Avoid `-k` (skip certificate checks) while debugging, because it hides exactly the certificate problems you might be chasing (section 21).

## 7. HTTP headers 🎓

### What they are
**Key-value pairs** of metadata sent with a request or response.

### Why a separate section? The parcel analogy
When you send a parcel, the address, phone number, state and PIN code go **on the outside**, not inside the box. Everyone handling it along the way needs that information, and opening the box at every step to read it would make no sense.

Headers are the outside of the parcel: proxies, load balancers, caches, the server and the browser can read **how to handle the message** without parsing the body.

<Mermaid chart={`flowchart LR
  C[Client] -->|"headers: Host, Authorization,<br/>Accept-Encoding"| P["Proxy / CDN"]
  P -->|"reads Host to route<br/>reads Cache-Control to cache"| S[Server]
  S -->|"reads Authorization, Accept<br/>body only parsed if needed"| H[Handler]`} />

### The four categories 🎓

| Category | Purpose | Examples |
|---|---|---|
| **Request headers** | tell the server about the client's environment, preferences and capabilities | `User-Agent` (browser, Postman, mobile app, another server), `Authorization` (e.g. a bearer token), `Accept` (JSON, text, HTML?) |
| **General headers** | metadata about the message itself, in requests and responses | `Date`, `Cache-Control` (`no-cache`, `max-age`), `Connection` (keep-alive or close) |
| **Representation headers** | how to interpret the **body** | `Content-Type` (media type), `Content-Length` (bytes), `Content-Encoding` (`gzip`, `deflate`), `ETag` (a unique identifier, mostly for caching) |
| **Security headers** | control browser behaviour to prevent attacks | see below |

**Security headers in the lesson:**

| Header | Attack it prevents | Mechanism |
|---|---|---|
| `Strict-Transport-Security` (HSTS) | **protocol downgrade** to plain HTTP | browser remembers to use only HTTPS for this host |
| `Content-Security-Policy` | **XSS** (cross-site scripting) | allow-list of sources for scripts, styles, images |
| `X-Frame-Options` | **clickjacking** | forbids embedding the page in an `iframe` |
| `X-Content-Type-Options: nosniff` | **MIME-type sniffing** | browser trusts `Content-Type` instead of guessing |
| `Set-Cookie` with `HttpOnly`, `Secure` | cookie theft | `HttpOnly`: JavaScript can't read it. `Secure`: only sent over HTTPS |

🔧 In Node, these are usually set by **Helmet**:

```ts title="main.ts"
import helmet from 'helmet';
app.use(helmet());   // sets CSP, HSTS, X-Content-Type-Options, X-Frame-Options (via frame-ancestors) and more

res.cookie('sid', sessionId, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 7 * 24 * 3600_000 });
```

### More security headers ➕

The lesson's five headers are the core set; a few more control what the browser leaks and what other origins may do with your pages and resources. All of them matter mainly for responses a browser **renders or embeds** (HTML, images, scripts); a pure JSON API needs fewer of them, but the same Helmet defaults apply to it.

#### Referrer-Policy ➕

- **Problem:** when a page loads an image or a user clicks a link, the browser sends the current page's URL in the `Referer` header. If that URL contains a secret (`/reset-password?token=...`, a share link), the third party receiving the request now has it.
- **Mechanism:** `Referrer-Policy` limits what is sent. Browsers default to `strict-origin-when-cross-origin` (full URL same-origin, only the origin cross-origin, nothing on HTTPS to HTTP downgrades). Helmet sets the stricter `no-referrer`.

```ts
app.use(helmet.referrerPolicy({ policy: 'strict-origin-when-cross-origin' }));   // or keep Helmet's 'no-referrer'
```

- **Edge cases:** the default still sends the **full URL to your own origin**, including your analytics and logs. Keep tokens out of URLs where possible, and after a token link lands, remove the token from the address bar (`history.replaceState`). `no-referrer` breaks analytics and some CSRF defences that check `Referer`.

#### Permissions-Policy ➕

- **Problem:** a compromised third-party script or an embedded iframe can ask for the camera, microphone, geolocation or payment APIs under your origin's name.
- **Mechanism:** `Permissions-Policy` turns features off (or allow-lists origins) for the page **and every frame inside it**. Helmet does **not** set it by default.

```ts
app.use((_req, res, next) => {
  res.setHeader('Permissions-Policy', 'camera=(), microphone=(), geolocation=(), payment=(), usb=()');  // () = nobody
  next();
});
```

- **Edge cases:** the syntax differs from the older `Feature-Policy` header (now superseded). A frame needs both the parent's policy and its own `allow` attribute to use a feature.

#### CSP `frame-ancestors` vs `X-Frame-Options` ➕

- **Problem:** `X-Frame-Options` only knows `DENY` and `SAMEORIGIN`; its `ALLOW-FROM` form is obsolete and ignored by modern browsers. You can't say "only my partner's site may embed this widget".
- **Mechanism:** the CSP directive **`frame-ancestors`** takes an allow-list and, when present, **supersedes** `X-Frame-Options` in modern browsers.

```ts
app.use(helmet({
  contentSecurityPolicy: { directives: { 'frame-ancestors': ["'self'", 'https://partner.example.com'] } },
  frameguard: { action: 'sameorigin' },            // X-Frame-Options kept for very old browsers
}));
```

- **Edge cases:** `frame-ancestors` is **ignored in a `meta` tag**; it only works as a response header. Set it on every HTML response, including error pages, or an attacker frames the one page you forgot.

#### CORP, COOP and COEP ➕

- **Problem:** Spectre-class CPU side channels let a page read memory from its own process. If a malicious page can load **your** resource (an image, a JSON response used as a script) into its process, it may read the bytes. Separately, a page opened with `window.open` keeps a handle (`window.opener`) to its opener, which enables tab-nabbing and cross-window leaks.
- **Mechanism:**
  - **`Cross-Origin-Resource-Policy`** (on your resources): who may load this response at all (`same-origin`, `same-site`, `cross-origin`).
  - **`Cross-Origin-Opener-Policy: same-origin`** (on your pages): put this document in its own browsing-context group, cutting the `window.opener` link to cross-origin windows.
  - **`Cross-Origin-Embedder-Policy: require-corp`** (on your pages): this page may only load cross-origin resources that opt in via CORP or CORS. With COOP and COEP together the page becomes **cross-origin isolated**, which unlocks `SharedArrayBuffer` and precise timers.
- **Implementation:** Helmet sets `Cross-Origin-Resource-Policy: same-origin` and `Cross-Origin-Opener-Policy: same-origin` by default. Loosen them deliberately where needed:

```ts
// public assets served to other origins (e.g. avatars shown on app.example.com from api.example.com)
app.use('/avatars', helmet.crossOriginResourcePolicy({ policy: 'same-site' }), express.static('avatars'));
// pages that rely on OAuth or payment popups talking back via window.opener
app.use('/login', helmet.crossOriginOpenerPolicy({ policy: 'same-origin-allow-popups' }));
```

- **Edge cases:** the most common surprise after adding Helmet is **images or files from your API no longer loading** on your frontend's origin: that's CORP `same-origin`. COOP `same-origin` breaks popup-based sign-in flows that use `window.opener`. Turn on COEP only if you need cross-origin isolation, because every third-party embed must then opt in.

#### The HSTS preload trap ➕

- **Problem:** HSTS only protects a browser that has **already** seen the header once. The very first visit can still be downgraded.
- **Mechanism:** the **HSTS preload list** is compiled into browsers. To be accepted, a domain must redirect HTTP to HTTPS and send `max-age` of at least **31536000** (one year) with **`includeSubDomains`** and **`preload`**.
- **The trap:** `includeSubDomains` covers **every** subdomain, including the internal tool, the old status page or the device admin page that only works over HTTP. Once preloaded, those stop working in every browser, and removal "takes months" to reach users (hstspreload.org's own warning). Note that Helmet's default HSTS already includes `includeSubDomains`.
- **Implementation:** ramp up instead of jumping straight to preload.

```ts
// week 1: short max-age, no subdomains. Then raise it, then add includeSubDomains, then preload.
app.use(helmet.hsts({ maxAge: 300, includeSubDomains: false }));
// final:  helmet.hsts({ maxAge: 63072000, includeSubDomains: true, preload: true })
```

- **Edge cases:** browsers ignore HSTS received over plain HTTP, so it must be on the HTTPS responses. Inventory every subdomain (DNS zone, certificate transparency logs) before adding `includeSubDomains`.

#### CRLF and header injection ➕

- **Problem:** code that puts user input into a header (a redirect `Location`, a `Content-Disposition` filename, a cookie value) lets an attacker include `\r\n`. A CR LF ends the header line, so the attacker can **add headers** (a `Set-Cookie` for session fixation) or end the head and write a **body** (response splitting: XSS, cache poisoning).
- **Mechanism:** never let CR or LF into a header value. Modern Node refuses: `res.setHeader('Location', 'a\r\nSet-Cookie: x=1')` throws `ERR_INVALID_CHAR`, which turns the attack into a 500. That's safe, but you should validate before it gets that far.
- **Implementation:**

```ts title="safe-headers.ts"
const SAFE_REDIRECTS = new Set(['/dashboard', '/settings']);
app.get('/login/done', (req, res) => {
  const next = String(req.query.next ?? '/dashboard');
  res.redirect(SAFE_REDIRECTS.has(next) ? next : '/dashboard');         // allow-list: also stops open redirects
});

app.get('/files/:id/download', async (req, res) => {
  const file = await files.get(req.params.id);
  const ascii = file.name.replace(/[^\x20-\x7e]|["\\]/g, '_');          // fallback for old clients
  res.setHeader('Content-Disposition',
    `attachment; filename="${ascii}"; filename*=UTF-8''${encodeURIComponent(file.name)}`);   // RFC 6266 / 8187
  res.sendFile(file.path);
});
```

- **Edge cases:** proxies, other languages and hand-written raw responses (like the exercise in section 5) may not protect you. Non-ASCII characters in header values are also rejected by Node, which is why filenames need the `filename*` encoding. The same CR LF trick against **log files** (fake log lines) is prevented by structured JSON logging.

### `charset` in Content-Type ➕

- **Problem:** a body is bytes; text needs an encoding to turn back into characters. If the sender writes UTF-8 and the receiver decodes it as Latin-1, `José` becomes `JosÃ©` (mojibake).
- **Mechanism:** for text types, the `charset` parameter says which encoding was used: `Content-Type: text/html; charset=utf-8`. **JSON is different:** RFC 8259 requires UTF-8 for JSON exchanged between systems and defines **no** `charset` parameter for `application/json`; adding one has no effect on compliant receivers. Express's `res.json()` still sends `application/json; charset=utf-8`, which is harmless.
- **Implementation:** the real bug is usually on the **reading** side, when a multi-byte character is split across two TCP chunks:

```ts
// ❌ decodes each chunk on its own: a 2-byte 'é' split across chunks becomes two garbage characters
let text = ''; req.on('data', (c: Buffer) => { text += c.toString('utf8'); });

// ✅ join the bytes first, decode once (or req.setEncoding('utf8'), which buffers partial characters)
const chunks: Buffer[] = []; req.on('data', (c: Buffer) => chunks.push(c));
req.on('end', () => { const text = Buffer.concat(chunks).toString('utf8'); });
```

- **Edge cases:** `Content-Length` counts **bytes**, not characters: `'é'.length` is 1, `Buffer.byteLength('é')` is 2. Always send a charset for `text/html` and `text/plain`; without it, browsers guess, and guessing has historically enabled XSS (the UTF-7 attacks).

### Two ideas behind headers 🎓

**1. Extensibility.** You can add or customise headers **without changing the protocol**. Adding metadata can change the whole interaction:
- security enhancements (`Strict-Transport-Security` forces secure connections),
- **custom headers** for your own needs (e.g. `X-Custom-Header`; 🔧 common real ones are `X-Request-Id` and `Idempotency-Key`),
- content negotiation (`Accept`, `Accept-Language`, `Accept-Encoding`).

**2. Headers as a remote control.** They let the client send **instructions** that change how the server responds:
- **Content negotiation:** `Accept: text/html` gets HTML, `Accept: application/json` gets JSON.
- **Caching and expiry:** the server uses `Cache-Control` or `Expires` to say how long the client may cache a resource.
- **Authentication:** the `Authorization` header drives access-control decisions.

## 8. HTTP methods 🎓

### Why methods exist
Methods state the **intent** of a request, so every request doesn't mean the same thing. That gives each action a clear meaning.

| Method | Intent | Body? |
|---|---|---|
| `GET` | **fetch** data; must **not modify** anything on the server | no |
| `POST` | **create** data | yes (how else would you send the data?) |
| `PATCH` | **update part** of a resource (e.g. change just the name) | yes |
| `PUT` | **replace** the resource **completely** with the body | yes |
| `DELETE` | **delete** a resource | usually no |

**PATCH vs PUT:** think of PATCH as **selective replacement** (only the sent fields change) and PUT as **complete replacement**. Many developers use PUT where they mean PATCH, which goes against the semantics. **Rule of thumb from the lesson: use PATCH unless you specifically need PUT.**

🔧 What the difference means concretely:

```http
GET /users/42           → { "name": "Asha", "email": "a@x.com", "bio": "Hi" }

PATCH /users/42  { "name": "Asha K" }
                        → { "name": "Asha K", "email": "a@x.com", "bio": "Hi" }

PUT /users/42    { "name": "Asha K" }
                        → { "name": "Asha K" }        (email and bio are gone: full replacement)
```

### Idempotency 🎓
**Idempotent** = calling it **many times has the same effect as calling it once**.

| Method | Idempotent? | Why |
|---|---|---|
| `GET` | yes | fetching never changes the data, so every call gives the same result |
| `PUT` | yes | replacing old data with the same new data N times leaves the same final state |
| `DELETE` | yes | a resource can only be deleted once; after that, the state is the same (deleted) |
| `POST` | **no** | submitting "create note" twice creates **two notes** |

<Mermaid chart={`flowchart LR
  subgraph PUTx3["PUT /notes/7 x3"]
    direction TB
    a1["state: note 7 = X"] --> a2["state: note 7 = X"] --> a3["state: note 7 = X"]
  end
  subgraph POSTx3["POST /notes x3"]
    direction TB
    b1["notes: 1"] --> b2["notes: 2"] --> b3["notes: 3"]
  end`} />

### 🔧 Going deeper: why idempotency matters, and fixing POST
**Problem:** networks fail **after** the server did the work but **before** the client saw the response. The client can't tell "never arrived" from "done, reply lost". For idempotent methods, it simply **retries**. Proxies and HTTP clients do this automatically. For `POST`, a retry can mean **double payment** or a **duplicate order**.

**Two definitions to keep apart (RFC 9110):**
- **Safe** = read-only (`GET`, `HEAD`, `OPTIONS`). Safe methods are also idempotent.
- **Idempotent** = repeatable with the same effect (safe methods + `PUT` + `DELETE`). Note that `DELETE` may return `204` the first time and `404` after, and still be idempotent: idempotency is about **server state**, not the response.
- `PATCH` is **not guaranteed** idempotent (`{"op":"increment"}` isn't).

**Mechanism to make POST safely retryable: an idempotency key.** The client generates a unique key per logical operation and sends it on every retry. The server stores the first result under that key and replays it:

```ts title="idempotency.ts"
// table: idempotency_keys(key text primary key, user_id, status int, body jsonb, created_at)
export async function withIdempotency(req: Request, res: Response, work: () => Promise<{ status: number; body: unknown }>) {
  const key = req.header('Idempotency-Key');
  if (!key) return res.status(400).json({ error: 'Idempotency-Key header required' });

  // claim the key atomically; only one request wins
  const claimed = await pool.query(
    `INSERT INTO idempotency_keys (key, user_id) VALUES ($1, $2) ON CONFLICT (key) DO NOTHING RETURNING key`,
    [key, req.user.id],
  );

  if (claimed.rowCount === 0) {
    const prev = await pool.query('SELECT status, body FROM idempotency_keys WHERE key = $1 AND user_id = $2', [key, req.user.id]);
    if (!prev.rows[0]?.status) return res.status(409).json({ error: 'request with this key still in progress' });
    return res.status(prev.rows[0].status).json(prev.rows[0].body);   // replay, don't redo
  }

  const result = await work();
  await pool.query('UPDATE idempotency_keys SET status = $2, body = $3 WHERE key = $1', [key, result.status, result.body]);
  return res.status(result.status).json(result.body);
}
```

Edge cases: expire keys after a while (e.g. 24 h); if `work()` throws, delete the key so a retry can try again; scope keys per user so one user can't replay another's result.

### Safe methods in practice ➕

The 🔧 notes above define **safe** and **idempotent** as two separate properties. Idempotency is about retries; the "safe" half has consequences of its own that bite real backends.

#### GET must not change state ➕

- **Problem:** many things send GET requests **without a user deciding to**: browser prefetching, search crawlers, link-preview bots (Slack, Teams, WhatsApp unfurling a pasted link), corporate email scanners that open every link in an incoming mail, and caches. If `GET /unsubscribe?u=42` or `GET /magic-login?token=...` changes state, those bots unsubscribe users and **burn one-time login tokens** before the human clicks.
- **Why:** RFC 9110 defines GET as **safe**: the client doesn't request, and isn't responsible for, any state change. Every tool above relies on that promise.
- **Mechanism:** a GET may only **show** something. The state change goes behind a POST, which bots don't send.
- **Implementation:** the confirm-page pattern for one-time links:

```ts title="magic-link.ts"
app.get('/magic-login', (req, res) => {                 // safe: just renders a button
  res.type('html').send(`<form method="post" action="/magic-login">
    <input type="hidden" name="token" value="${escapeHtml(String(req.query.token ?? ''))}">
    <button>Sign in</button></form>`);
});

app.post('/magic-login', express.urlencoded({ extended: false }), async (req, res) => {
  const session = await consumeLoginToken(req.body.token);   // the one-time token is used up HERE
  if (!session) return res.status(400).send('Link expired');
  res.cookie('sid', session.id, { httpOnly: true, secure: true, sameSite: 'lax' }).redirect('/');
});
```

- **Edge cases:** "safe" still allows harmless side effects such as logging and metrics. There's also a **CSRF** angle: `SameSite=Lax` cookies **are** sent on top-level GET navigations from other sites, so a state-changing GET is open to CSRF even with Lax cookies. Keeping GET safe is part of the CSRF defence.

#### HEAD ➕

- **Problem:** link checkers, download managers and some caches want a resource's size, type or ETag **without** downloading it.
- **Mechanism:** `HEAD` returns exactly the headers a GET would, with no body.
- **Implementation:** Express answers HEAD automatically by running your **GET** handler and discarding the body. For an expensive GET (a report built from a heavy query), that does all the work for nothing. Register a cheap HEAD route first:

```ts
app.head('/reports/:id', async (req, res) => {        // must be registered BEFORE app.get for the same path
  const meta = await reports.meta(req.params.id);         // size + version only, no CSV generation
  if (!meta) return res.sendStatus(404);
  res.set({ 'Content-Type': 'text/csv', 'Content-Length': String(meta.bytes), ETag: `"${meta.version}"` }).end();
});
app.get('/reports/:id', streamReport);
```

- **Edge cases:** the headers must match what GET would send, or clients make wrong decisions (a download manager trusting a wrong `Content-Length`). A HEAD response never has a body, even if your code writes one; Node drops it.

#### GET with a body ➕

- **Problem:** a search with dozens of filters doesn't fit comfortably in a query string, and URLs have length limits (section 19). Putting a JSON body on a GET is tempting.
- **Why it's unreliable:** RFC 9110 says content in a GET has **no generally defined semantics** and may cause some implementations to **reject the request** (because a body on GET has been used for request smuggling). In practice, `fetch` throws a `TypeError` for a GET with a body, some proxies and CDNs drop the body, and caches key only on the URL, so two different bodies would share one cached answer.
- **Mechanism (alternatives):**
  1. `POST /books/search` with a JSON body. It works everywhere, but POST isn't cacheable by default and isn't automatically retried, so document it as safe and accept an `Idempotency-Key` if needed.
  2. Create a saved search: `POST /searches` returns `201` with `Location: /searches/abc`, then `GET /searches/abc/results` is cacheable and shareable.
  3. The **`QUERY`** method, an IETF draft for a safe, idempotent request **with** a body. Promising, but not yet supported widely enough to rely on.
- **Implementation:**

```ts
const Search = z.object({ authors: z.array(z.string()).max(50), yearFrom: z.number().int().optional(), tags: z.array(z.string()).max(100) });
app.post('/books/search', express.json({ limit: '32kb' }), async (req, res) => {
  const q = Search.parse(req.body);                      // validation errors → 400 in the error handler
  res.set('Cache-Control', 'no-store').json(await books.search(q));
});
```

- **Edge cases:** some well-known APIs (Elasticsearch's `_search`) accept GET with a body and also accept POST for the same thing. If you consume one, use the POST form from Node and browsers.

## 9. OPTIONS and CORS 🎓

### The problem CORS solves
- Browsers enforce the **same-origin policy**: by default, a page may only make requests to **its own origin** (scheme + host + port).
- **CORS** (Cross-Origin Resource Sharing) is the **browser-enforced** mechanism that lets a server **opt in**: it states which other origins may access its resources, and how.
- Without CORS, a request from a web app on `example.com` to `api.another-example.com` is blocked by the browser.

The **`OPTIONS`** method is rarely called by you directly. You see it in the Network tab as **preflight** requests, where the browser uses it to **ask the server about its capabilities** for a cross-origin request.

There are two flows: **simple** and **preflighted**.

### Flow 1: the simple request 🎓
Frontend on `example.com`, API on `api.example.com`, a `GET` request:

<Mermaid chart={`sequenceDiagram
  autonumber
  participant JS as Page JS (example.com)
  participant B as Browser
  participant S as API (api.example.com)
  JS->>B: fetch GET /data
  B->>S: GET /data + Origin example.com (added automatically)
  S->>S: Is this origin allowed by my policy?
  alt allowed
    S-->>B: 200 + Access-Control-Allow-Origin example.com (or *)
    B-->>JS: response delivered
  else not allowed
    S-->>B: 200 without the CORS header
    B-->>JS: blocked, CORS error in console
  end`} />

1. The browser **adds the `Origin` header** automatically.
2. The method is a **simple** one (`GET`, `POST` or `HEAD`).
3. The server checks `Origin` against its CORS policy. If allowed, it adds **`Access-Control-Allow-Origin`** with the client's origin, or `*` (all origins).
4. The browser sees that the page's origin differs from the API's, so it checks for that header. If it matches (or is `*`), the response goes through to the JavaScript. If it's **missing**, the browser **blocks the response** and you get a **CORS error** in the console and Network tab.

🔧 **Key insight:** in the simple flow the **request still reaches the server and runs**. CORS only stops the **JavaScript from reading the response**. That's why CORS is **not** a server-side security control: for state-changing requests, you still need authentication and CSRF protection.

### Flow 2: the preflighted request 🎓
**When does the browser preflight?** When the request is **cross-origin** and **at least one** of these is true:
1. The method is **not** `GET`, `POST` or `HEAD` (e.g. `PUT`, `DELETE`).
2. It has **non-simple headers**, e.g. `Authorization` or a custom header.
3. Its `Content-Type` is **not** one of `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`. **So `application/json` triggers a preflight**, which means most real API calls are preflighted.

**The preflight exchange:**

<Mermaid chart={`sequenceDiagram

- **Request:** method `OPTIONS`, the target URL, `Host`, `Origin`, **`Access-Control-Request-Method`** ("do you support PUT on this route?") and **`Access-Control-Request-Headers`** ("do you accept the `Authorization` header?"). **No body.**
- **Response** (if the server handles CORS; otherwise the browser blocks the real request): **`204 No Content`** (there's nothing to return; the information is in the headers) with four key headers:
  1. `Access-Control-Allow-Origin`: the client's origin or `*`.
  2. `Access-Control-Allow-Methods`: e.g. `PUT, DELETE`.
  3. `Access-Control-Allow-Headers`: e.g. `Authorization`.
  4. `Access-Control-Max-Age`: how long the browser may **cache this answer** (the lesson's example: 24 hours) so it doesn't preflight every request. That saves bandwidth for both sides.
- The browser ticks off each condition, then sends the **original request**, and the server responds normally.

### What the demo shows 🎓
The demo uses **Burp Suite** (an HTTP interception tool popular with ethical hackers) to inspect the traffic. There's intentionally **no code**: the concepts don't depend on the server's language.
- **Frontend** on `localhost:5173`, **API** on `localhost:3000`. **Different ports = different origins**, so it's cross-origin even on the same machine.
- **Simple request:** the response contains `Access-Control-Allow-Origin` with the frontend's origin, so the data renders.
- **Header removed** on the server (cache disabled in DevTools to force a fresh request): the browser **blocks** the response with a CORS error.
- **Preflighted request** (CORS re-enabled): the Network tab shows `OPTIONS` **first**, then the real `PUT`. The `PUT` met **all three** preflight conditions (non-simple method, `Authorization` header, JSON body); any one would have been enough.
  - The preflight response: `204`, allowed origin, `Access-Control-Allow-Methods: GET, POST, PUT, DELETE`, `Access-Control-Allow-Headers: Content-Type, Authorization`, `Content-Length: 0`.
  - `Access-Control-Max-Age` is **0** in the demo so every request preflights, which makes testing easier.

### 🔧 Going deeper: implementing CORS correctly in Node

```ts title="cors.ts (Express, no library)"
const ALLOWED = new Set(['https://app.example.com', 'http://localhost:5173']);

app.use((req, res, next) => {
  const origin = req.header('Origin');
  if (origin && ALLOWED.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);    // echo the specific origin
    res.setHeader('Access-Control-Allow-Credentials', 'true'); // only if you use cookies
  }
  res.append('Vary', 'Origin');                               // the response differs per Origin

  if (req.method === 'OPTIONS' && req.header('Access-Control-Request-Method')) {
    res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, PATCH, DELETE');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');
    res.setHeader('Access-Control-Max-Age', '7200');
    return res.sendStatus(204);                               // answer the preflight, skip the handlers
  }
  next();
});
```

In NestJS the same is `app.enableCors({ origin: [...], credentials: true, maxAge: 7200 })`.

Edge cases (MDN):
- **`*` doesn't work with credentials.** If the request sends cookies, the server must echo an **explicit origin**, not `*`.
- **`Vary: Origin` is required** when you echo the origin dynamically. Otherwise a CDN may cache the response with one site's `Allow-Origin` and serve it to another, causing random CORS failures.
- **Browsers cap `Max-Age`:** Firefox at **24 hours**, Chromium at **2 hours**. The default without the header is **5 seconds**.
- **The preflight must succeed before auth.** If your auth middleware runs before CORS and rejects `OPTIONS` with 401 (preflights carry no `Authorization`), every call fails with a CORS error. Put CORS **first**.
- **Never reflect any `Origin` blindly** together with `Allow-Credentials: true`. That lets any website make authenticated calls and read the responses.

## 10. Status codes 🎓

### Why they exist
- **Problem:** without them, a client would have to **guess** the outcome from the body ("if it worked I'd expect this structure, if it crashed maybe a null object..."). That's inconsistent and inefficient.
- **Mechanism:** a **standardised 3-digit code** tells the client the result at a glance, so it can react, e.g. on **401** log the user out and ask them to sign in again, or on **400** ask the user to fix the form.
- **Standardisation:** the codes are the same whether the server is in Python, Go, Rust, JavaScript or Ruby. Successful? 200. Created something? 201. A **universal language** for clients and servers.

| First digit | Class |
|---|---|
| **1xx** | informational |
| **2xx** | success |
| **3xx** | redirection |
| **4xx** | client error |
| **5xx** | server error |

### 1xx 🎓
- **`100 Continue`**: the server has received the headers and the client may send the body. Used for **large uploads**: the client sends headers first (🔧 with `Expect: 100-continue`), and only sends the big body if the server accepts.
- **`101 Switching Protocols`**: the server switches protocol at the client's request, e.g. **HTTP → WebSocket**.

These are rare day to day. Focus on 2xx, 4xx and 5xx.

### 2xx: success 🎓

| Code | Meaning | Typical use |
|---|---|---|
| `200 OK` | success, here's the resource or the action's result | a successful `GET` |
| `201 Created` | success, **a new resource was created** | `POST`, form submissions (🔧 add a `Location` header pointing to the new resource) |
| `204 No Content` | success, **no body** | preflight responses, `DELETE` |

### 3xx: redirection 🎓

| Code | Meaning | Lesson's example |
|---|---|---|
| `301 Moved Permanently` | the resource has a **new URL for good**; use it from now on | `/user` renamed to `/person`; a 301 keeps old clients working |
| `302 Found` | **temporary** redirect; keep using the original URL in future | redirect a route for a few hours during a campaign, then revert |
| `304 Not Modified` | the resource hasn't changed since you last fetched it; use your cache | conditional `GET` with ETags (section 11) |

🔧 **Method-preserving redirects:** 301 and 302 historically let clients change `POST` into `GET` on the redirect. If the method must be kept (e.g. a redirected `POST` upload), use **`307 Temporary Redirect`** or **`308 Permanent Redirect`**. Also note that browsers cache 301s aggressively, so a mistaken 301 is hard to undo.

### 4xx: client errors 🎓
As a backend engineer you'll deal with these most, because they describe something the **client** did.

| Code | Meaning | When to return it |
|---|---|---|
| `400 Bad Request` | the request data is invalid or illogical | expected a number, got an array; expected an email, got a phone number |
| `401 Unauthorized` | **not authenticated**: no valid credentials | JWT missing or expired |
| `403 Forbidden` | authenticated, but **not allowed** | user A tries to delete user B's resource |
| `404 Not Found` | resource doesn't exist (wrong URL or deleted) | the most famous code |
| `405 Method Not Allowed` | the route exists, but not with this method | `PUT` on a route that only accepts `GET`/`POST`, often a frontend typo (PATCH vs PUT) |
| `409 Conflict` | the request conflicts with current state | folder names must be unique and the name already exists |
| `429 Too Many Requests` | rate limit exceeded | e.g. limit of 60 requests per second per client |

🔧 Details from RFC 9110 / RFC 6585 that make these responses correct:
- **401** should include a **`WWW-Authenticate`** header saying which scheme to use (e.g. `Bearer`).
- **405** **must** include an **`Allow`** header listing the supported methods.
- **429** (and 503) should include **`Retry-After`**, so well-behaved clients back off for the right time.
- **403 vs 404 for hiding existence:** if even revealing that a resource exists is a leak (e.g. another user's private document), return **404** instead of 403.
- 🔧 **`422 Unprocessable Content`** is common for "well-formed JSON, but fails validation"; many APIs use 400 for both. Pick one and be consistent.

### 5xx: server errors 🎓

| Code | Meaning | Who returns it |
|---|---|---|
| `500 Internal Server Error` | something unexpected broke (an unhandled exception) | your app; better than an empty response or a hanging request |
| `501 Not Implemented` | the method or feature isn't supported (yet) | your app, to state the intention |
| `502 Bad Gateway` | a **proxy** got an **invalid response** from the upstream server | proxies and load balancers (e.g. Nginx), not usually you |
| `503 Service Unavailable` | temporarily unable to handle requests (high traffic, maintenance) | your app or infra; the client should retry later |
| `504 Gateway Timeout` | the **upstream didn't respond in time** | the proxy, e.g. Nginx got no answer from your app |

The lesson's claim: this set covers about **95%** of real use.

### What the demo shows 🎓
A frontend fires a batch of requests at a mock server. Each request is preceded by an `OPTIONS` **preflight** (cross-origin). The responses: `200 OK`, `201 Created`, `400` ("missing required data"), `401`, `403` ("you do not have access"), `404` ("the requested resource could not be found"), `409` ("resource already exists"), `500` and `503` ("please try again later"). Note that the **500 says only "Internal Server Error"**: it doesn't leak internal details to the client, **for security reasons**.

### 🔧 Going deeper: mapping errors to codes in one place
**Problem:** if every handler picks its own codes and bodies, clients get inconsistent errors, and unexpected exceptions leak stack traces.

**Mechanism:** throw **typed errors** from the business logic and convert them in **one** error handler (registered last in Express; an exception filter in NestJS).

```ts title="errors.ts"
export class AppError extends Error {
  constructor(public status: number, public code: string, message: string, public headers: Record<string, string> = {}) { super(message); }
}
export const NotFound  = (what: string) => new AppError(404, 'NOT_FOUND', `${what} not found`);
export const Conflict  = (msg: string)  => new AppError(409, 'CONFLICT', msg);
export const Forbidden = ()             => new AppError(403, 'FORBIDDEN', 'You do not have access');
export const TooMany   = (sec: number)  => new AppError(429, 'RATE_LIMITED', 'Too many requests', { 'Retry-After': String(sec) });

// last middleware
app.use((err: unknown, req: Request, res: Response, _next: NextFunction) => {
  if (err instanceof AppError) {
    res.set(err.headers);
    return res.status(err.status).json({ error: { code: err.code, message: err.message } });
  }
  req.log.error({ err, requestId: req.id }, 'unhandled error');                    // full detail in logs only
  res.status(500).json({ error: { code: 'INTERNAL', message: 'Internal Server Error', requestId: req.id } });
});
```

Folder-uniqueness (409) done right: rely on a **unique constraint**, not a "check then insert" (two concurrent requests can both pass the check):

```ts
try {
  await pool.query('INSERT INTO folders (owner_id, name) VALUES ($1, $2)', [userId, name]);
} catch (e: any) {
  if (e.code === '23505') throw Conflict('A folder with that name already exists');   // Postgres unique_violation
  throw e;
}
```

### Status codes beyond the lesson's set ➕

The lesson's list covers most day-to-day responses. These six come up as soon as a backend does asynchronous work, serves files, retires endpoints or runs behind Nginx under load, and each one changes how clients should behave.

#### 202 Accepted + Location for async work ➕

- **Problem:** some requests take minutes (exports, video processing, "delete all my data"). Holding the HTTP request open that long hits every proxy timeout on the way (section 19).
- **Mechanism:** `202 Accepted` means "the request is valid and queued; it hasn't been done yet". By convention the response points to a **status resource** with `Location`, and the client polls it. RFC 9110 says the 202 representation should describe the current status and point to a status monitor.

```ts title="exports.ts"
app.post('/exports', async (req, res) => {
  const job = await exportQueue.add('export', { userId: req.user.id }, { jobId: req.header('Idempotency-Key') ?? undefined });
  res.status(202).location(`/exports/${job.id}`).set('Retry-After', '5').json({ id: job.id, status: 'queued' });
});

app.get('/exports/:id', async (req, res) => {
  const job = await exportQueue.getJob(req.params.id);
  if (!job || job.data.userId !== req.user.id) return res.sendStatus(404);
  const state = await job.getState();                                // waiting, active, completed, failed
  if (state === 'completed') return res.redirect(303, job.returnvalue.downloadUrl);   // 303: GET the result
  res.set('Retry-After', '5').json({ id: job.id, status: state });
});
```

- **Edge cases:** 202 is **non-committal**: the job can still fail, so the status resource needs a `failed` state with a reason. `Retry-After` paces polling. Make the submit idempotent (here the `Idempotency-Key` becomes the job ID), or a retried POST starts two exports. For the queue itself, see [Task queues](/docs/backend-first-principles/14-task-queues-background-jobs).

#### 206 Partial Content ➕

- **Problem:** resuming a broken download, seeking in a video or downloading a big file in parallel pieces all need **part** of a resource.
- **Mechanism:** the server advertises `Accept-Ranges: bytes`; the client sends `Range: bytes=1000000-1999999`; the server replies **`206 Partial Content`** with `Content-Range: bytes 1000000-1999999/52428800`. A range outside the file gets **`416 Range Not Satisfiable`**.
- **Implementation:** Express's `res.sendFile` and `express.static` handle ranges for you. Object storage does too; see [Object storage part 2](/docs/backend-first-principles/object-storage-part-2) for the range-request deep dive.
- **Edge cases:** if the file changes between two range requests, a client could stitch together pieces of two versions. Clients prevent that with `If-Range: "etag"` (send the range only if the ETag still matches, otherwise the whole new file), which needs a **strong** ETag.

#### 410 Gone ➕

- **Problem:** `404` can mean "typo", "never existed" or "deleted". For a retired API version or a deliberately removed resource, clients and crawlers should stop asking.
- **Mechanism:** `410 Gone` says the removal is **intentional and permanent**. RFC 9110 makes it heuristically cacheable, and search engines drop such URLs faster.

```ts
app.all('/api/v1/{*rest}', (_req, res) =>
  res.status(410).json({ error: 'API v1 was removed on 2027-06-30', successor: '/api/v2' }));
```

- **Edge cases:** for one user's deleted private data, 410 **confirms the resource existed**, which can leak information; use 404 there. The versioning workflow that ends in 410 is in [Routing](/docs/backend-first-principles/06-routing).

#### 415 Unsupported Media Type ➕

- **Problem:** a client sends XML, a form post or forgets `Content-Type`. `express.json()` only parses `application/json`, so it silently skips the body and `req.body` is `undefined` (Express 5) or `{}`. Validation then fails with a confusing 400, or worse, passes because every field is optional.
- **Mechanism:** reject a body you can't interpret with **`415`**, which tells the client exactly what's wrong.

```ts
export const requireJson = (req: Request, res: Response, next: NextFunction) => {
  const hasBody = req.headers['content-length'] !== '0' && (req.headers['content-length'] || req.headers['transfer-encoding']);
  if (hasBody && !req.is('application/json')) {
    return res.status(415).json({ error: 'Content-Type must be application/json' });
  }
  next();
};
app.use(['/api'], requireJson, express.json({ limit: '100kb' }));
```

- **Edge cases:** `req.is()` handles parameters such as `; charset=utf-8`. Requiring `application/json` has a security bonus: cross-origin JSON requests always need a CORS **preflight** (section 9), while a form post (`text/plain`, `application/x-www-form-urlencoded`) doesn't, so accepting only JSON removes a CSRF path.

#### 499: the client gave up (Nginx) ➕

- **Problem:** your Nginx logs show `499` but your app logs show successful `200`s for the same requests.
- **Mechanism:** 499 is **Nginx-specific** and never sent on the wire: Nginx logs it when the **client closed the connection** before the response was ready (the user navigated away, or the client's timeout was shorter than your processing). Your app kept working on a request nobody was waiting for.
- **Implementation:** detect the disconnect and stop work:

```ts title="abort-on-close.ts"
app.use((req, res, next) => {
  const ac = new AbortController();
  res.on('close', () => { if (!res.writableFinished) ac.abort(); });   // closed before we finished sending
  res.locals.signal = ac.signal;
  next();
});

app.get('/search', async (req, res) => {
  const upstream = await fetch(searchUrl(req.query), { signal: res.locals.signal });  // cancelled with the client
  res.json(await upstream.json());
});
```

- **Edge cases:** cancelling stops **reads** cleanly, but a write that already committed **did happen** even though the client saw an error. The client will probably retry, which is why writes need idempotency (section 8). A spike in 499s usually means **p99 latency exceeded the client's timeout**; see the timeout-alignment rule in section 19. For Postgres, a `statement_timeout` bounds query time even when the driver can't cancel on abort.

#### 503 + Retry-After vs 500 ➕

- **Problem:** both mean "server-side failure", but clients should react in opposite ways.
- **Mechanism:**
  - **500**: a bug. Retrying the same request will most likely fail the same way; don't retry automatically.
  - **503**: **temporary** inability (overload, maintenance, a dependency is down). Retry later, ideally after `Retry-After` (seconds, or an HTTP date).
- **Implementation:** load shedding. When the server is saturated, a fast 503 is far better than letting every request queue up and time out:

```ts title="load-shed.ts"
let inFlight = 0;
const MAX_IN_FLIGHT = 200;

app.use((req, res, next) => {
  if (inFlight >= MAX_IN_FLIGHT) {
    return res.status(503).set('Retry-After', '2').json({ error: 'Server busy, retry shortly' });  // costs microseconds
  }
  inFlight++;
  res.on('close', () => { inFlight--; });
  next();
});
```

- **Edge cases:** a **health check** that returns 503 makes the load balancer remove the instance, which is what you want during shutdown but not when a shared dependency is down (every instance goes unhealthy at once). Don't map bugs to 503 to "encourage retries": that multiplies load on an already failing system. **429** is "you, specifically, slow down"; **503** is "everyone, slow down". CDNs can serve stale content on 5xx with `stale-if-error` (section 11).

## 11. HTTP caching 🎓

### What it is and why
Store copies of responses and **reuse** them, so the client doesn't download unchanged data again. Benefits: **faster loads**, **less bandwidth**, **lower server load**.

### What the demo shows 🎓
**First request:** `GET /api/resource`. The response (`200` with a body) includes three headers:

| Header | Meaning |
|---|---|
| `Cache-Control: max-age=10` | cache this response for at most **10 seconds** |
| `ETag: "3141"` | an identifier for this **version** of the resource; normally a **hash of the response** (a random number in the demo) |
| `Last-Modified: <date>` | when the resource last changed |

**Second request (fetch again):** the browser sends **conditional** headers:
- `If-None-Match: "3141"`: "send the resource only if its ETag is no longer this one",
- `If-Modified-Since: <date>`: "...or if it changed after this date".

The server checks them, sees **nothing changed**, and replies **`304 Not Modified`** with **no body**. The browser uses its cached copy.

**After an update:** the demo uses a `POST` to update the resource (ideally `PATCH`/`PUT`). The server returns `200` and a **new ETag** (`"2943"`). The next `GET` still sends the **old** ETag (`3141`); it doesn't match, so the server returns **`200` with the new body** and the new ETag. A fetch after that sends `2943`, which matches, so it's **`304`** again.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant B as Browser cache
  participant S as Server
  B->>S: GET /api/resource
  S-->>B: 200 + body + ETag 3141 + Last-Modified + max-age=10
  B->>S: GET + If-None-Match 3141
  S-->>B: 304 Not Modified (no body, reuse cache)
  Note over S: resource updated, ETag becomes 2943
  B->>S: GET + If-None-Match 3141
  S-->>B: 200 + new body + ETag 2943
  B->>S: GET + If-None-Match 2943
  S-->>B: 304 Not Modified`} />

### The lesson's opinion
- In production this gets complicated: the server must **manage ETags correctly**. Forget to change one after an update and clients keep using **stale data**.
- Client-side caching libraries such as **React Query** give the client full control over when to use cached data and when to refetch (at what interval, etc.). The author considers that **a better solution** than traditional HTTP caching for app data, while HTTP caching is fine for **simple** use cases.

### 🔧 Going deeper: how to make ETags impossible to forget
**Problem:** a hand-maintained version number goes stale when someone forgets to bump it.

**Mechanism:** derive the ETag **from the response bytes**, so it changes automatically whenever the content changes. Express already does this: `res.send`/`res.json` compute a (weak) ETag and answer `304` when the request's `If-None-Match` matches. Done by hand:

```ts title="etag.ts"
import { createHash } from 'node:crypto';

app.get('/api/resource', async (req, res) => {
  const body = JSON.stringify(await loadResource());
  const etag = `"${createHash('sha1').update(body).digest('base64url')}"`;   // content-derived

  res.setHeader('ETag', etag);
  res.setHeader('Cache-Control', 'private, max-age=0, must-revalidate');     // always revalidate, cheaply
  if (req.header('If-None-Match') === etag) return res.status(304).end();    // no body sent
  res.type('json').send(body);
});
```

Note: this saves **bandwidth**, not **server work**, because the response is still built to hash it. To save work too, use a stored version: e.g. a `version` or `updated_at` column bumped **by the same UPDATE statement** that changes the row, and compare it before loading the full data.

🔧 **`Cache-Control` directives you'll actually use:**

| Directive | Meaning |
|---|---|
| `max-age=N` | fresh for N seconds; no request at all during that time |
| `no-cache` | **may** store, but **must revalidate** (ETag check) before every use. It does *not* mean "don't cache" |
| `no-store` | never store anywhere (sensitive data) |
| `private` | only the user's browser may cache; shared caches and CDNs may not (per-user data) |
| `public`, `s-maxage=N` | shared caches (CDNs) may store it; `s-maxage` applies to them |
| `immutable` | will never change; skip revalidation (content-hashed static files) |

🔧 **Strong vs weak ETags:** `"abc"` means byte-for-byte identical; `W/"abc"` means semantically equivalent (e.g. same data, different compression). Weak ETags are fine for `If-None-Match`; range requests need strong ones.

🔧 **Edge case: `Last-Modified` has 1-second resolution.** Two updates in the same second look identical. When both are present, servers should prefer `If-None-Match`.

### Shared caches and CDNs ➕

Everything above happens in **one user's browser cache**. A CDN or a reverse-proxy cache sits between **all** users and your server and is shared by them, which changes what is safe to cache and how things go wrong. (Server-side application caching with Redis is its own lesson: [Caching](/docs/backend-first-principles/13-caching).)

<Mermaid chart={`flowchart LR
  U1["User A browser<br/>private cache"] --> CDN["CDN edge<br/>shared cache"]
  U2["User B browser<br/>private cache"] --> CDN
  CDN -->|"miss or revalidation"| O["Origin: your app"]`} />

#### Private vs shared: who may store what ➕

- **Problem:** a response cached at the CDN is served to **the next person** who asks for the same URL. If it contained user A's data, user B now sees it.
- **Mechanism (RFC 9111):** `private` means only the user's own cache may store it; `public` and `s-maxage` explicitly allow shared caches. There is one built-in safety net: a shared cache must not reuse a response to a request that carried an **`Authorization`** header unless the response explicitly allows it (`public`, `s-maxage` or `must-revalidate`).
- **The gap in that safety net:** it covers `Authorization`, **not cookies**. With cookie sessions, a personalised `GET /me` is just a URL to the CDN. Marking it `private` (or `no-store`) is your job.

```ts
app.get('/api/catalog', (_req, res) => {                  // same for everyone
  res.set('Cache-Control', 'public, max-age=60, s-maxage=300').json(catalog);
});
app.get('/api/me', requireAuth, (req, res) => {           // per user, cookie-authenticated
  res.set('Cache-Control', 'private, no-cache').json(req.user);   // browser may keep it, CDN never
});
```

- **Edge cases:** never let a shared cache store a response with **`Set-Cookie`**: depending on the CDN's configuration, it can hand one user's fresh session cookie to everyone. Configure the CDN to bypass the cache when `Set-Cookie` is present, and don't set cookies on cacheable routes.

#### The cache key ➕

- **Problem:** the cache must decide when two requests are "the same". Too coarse, and users get the wrong variant; too fine, and nothing is ever a hit.
- **Mechanism:** by default the key is roughly **method + host + path + query string** (each CDN documents its exact default). `Vary` adds request headers to the key: `Vary: Accept-Encoding` stores a gzip and a Brotli copy.
- **Implementation:** keep the key small and canonical:
  - vary only on what really changes the response (`Accept-Encoding`, sometimes `Accept-Language`), never on `User-Agent` or `Cookie`, which make almost every request unique;
  - in the CDN's cache-key settings, sort query parameters and drop tracking parameters such as `utm_*` and `fbclid`, so `?a=1&b=2` and `?b=2&a=1&utm_source=x` share one entry.
- **Edge cases:** `Vary: Origin` (from the CORS section) multiplies entries by the number of origins, which is fine for a handful of known origins. A response that varies on something **not** in the key is the root cause of cache poisoning, below.

#### Age and how stale a response really is ➕

- **Problem:** you set `max-age=60` but users see data several minutes old.
- **Mechanism:** a shared cache adds an **`Age`** header saying how many seconds the response has spent in caches. A browser receiving `Cache-Control: max-age=60` with `Age: 50` treats it as fresh for only **10** more seconds. But `s-maxage=300` lets the CDN keep serving it for 5 minutes, and the browser can then add its own `max-age` on top: worst-case staleness is roughly `s-maxage + max-age`.
- **Implementation:** inspect it from outside:

```bash
curl -sI https://www.example.com/api/catalog | grep -iE '^(age|cache-control|x-cache|cf-cache-status|etag):'
# age: 187   cf-cache-status: HIT   (the hit/miss header name is CDN-specific)
```

- **Edge cases:** to change data **now**, don't wait for TTLs: purge the CDN by URL or tag on write, or use content-addressed URLs (`app.3f9a1c.js`) with `immutable` so new content gets a new key.

#### stale-while-revalidate and stale-if-error ➕

- **Problem:** at the moment an entry expires, the next user waits for the origin (a latency spike), and when many entries expire together, the origin gets a burst. When the origin is down, expired entries turn into errors.
- **Mechanism (RFC 5861):**
  - `stale-while-revalidate=N`: for N seconds after expiry, serve the stale copy **immediately** and refresh it in the background.
  - `stale-if-error=N`: for N seconds after expiry, if the origin errors (5xx or unreachable), serve the stale copy instead of the error.

```ts
res.set('Cache-Control', 'public, max-age=30, s-maxage=60, stale-while-revalidate=120, stale-if-error=86400');
```

- **Edge cases:** support differs: major CDNs honour both, browsers support `stale-while-revalidate` but `stale-if-error` is not reliably implemented in browsers. Only use them for data where "a little stale" is acceptable (catalogues, public profiles), never for balances or permissions.

#### Cache poisoning via unkeyed headers ➕

- **Problem:** the app uses a request header that is **not part of the cache key** to build the response. Classic case: building absolute URLs from `X-Forwarded-Host`. An attacker sends `X-Forwarded-Host: evil.example`, your page comes back with `<script src="https://evil.example/app.js">`, the CDN caches it under the normal URL, and **every** visitor gets the attacker's script.

<Mermaid chart={`sequenceDiagram
  participant A as Attacker
  participant C as CDN cache
  participant O as Origin
  participant V as Victim
  A->>C: GET / + X-Forwarded-Host evil.example
  C->>O: miss, forward (header not in cache key)
  O-->>C: HTML with script from evil.example
  C-->>A: cached under key GET /
  V->>C: GET /
  C-->>V: HIT, poisoned HTML`} />

- **Mechanism:** never let unkeyed input shape a cacheable response. Take the public base URL from **configuration**, and strip `X-Forwarded-*` headers at the edge unless your own proxies set them.

```ts
// ❌ const base = `${req.protocol}://${req.get('x-forwarded-host') ?? req.get('host')}`;
// ✅
const BASE_URL = config.PUBLIC_BASE_URL;                  // e.g. https://www.example.com, validated at startup
```

- **Edge cases:** the same bug class includes unkeyed **query parameters** that some CDNs exclude from the key, and **web cache deception** (a CDN caching `/account/settings/x.css` as a static file even though the app served the private settings page for it). Test by sending odd headers to a cache-busted URL and checking whether they appear in the response.

## 12. Conditional writes: If-Match and 412 ➕

Caching used ETags so clients can skip re-downloading. The **same validator**, sent on a **write**, stops two clients from silently overwriting each other. (The REST lesson mentions this briefly; here is the full mechanism: [REST API design](/docs/backend-first-principles/11-rest-api-design).)

#### The lost-update problem ➕

- **Problem:** Alice and Bob both open document 7 (version 4). Alice changes the title and saves. Bob, still looking at version 4, changes the body and saves. Bob's request carries the **old title**, so Alice's change disappears. Nobody gets an error.
- **Why (first principles):** HTTP is stateless. Each client edits a **copy** that goes stale the moment someone else writes, and the server has no idea which version the client based its change on, so the last write wins.

<Mermaid chart={`sequenceDiagram
  participant A as Alice
  participant S as Server
  participant B as Bob
  A->>S: GET /docs/7
  S-->>A: 200 + ETag 4
  B->>S: GET /docs/7
  S-->>B: 200 + ETag 4
  A->>S: PUT /docs/7 + If-Match 4
  S-->>A: 200 + ETag 5
  B->>S: PUT /docs/7 + If-Match 4
  S-->>B: 412 Precondition Failed, current is 5
  Note over B: reload, merge, retry with If-Match 5`} />

#### If-Match → 412 Precondition Failed ➕

- **Mechanism:** the client sends back the ETag it based its edit on: `If-Match: "4"`. The server applies the write **only if the current ETag still equals it** (strong comparison); otherwise it returns **`412 Precondition Failed`** and changes nothing. This is **optimistic concurrency**: no locks are held while users think; conflicts are detected at write time.
- **Implementation:** the check and the write must be **one atomic statement**. A `SELECT` followed by an `UPDATE` has a race between them; a version check inside the `UPDATE ... WHERE` doesn't:

```ts title="docs.controller.ts (Express + pg)"
const etagOf = (version: number) => `"${version}"`;

app.patch('/api/docs/:id', express.json(), async (req, res) => {
  const ifMatch = req.header('If-Match');
  if (!ifMatch) return res.status(428).json({ error: 'If-Match header required' });   // see 428 below
  const m = /^"(\d+)"$/.exec(ifMatch.trim());                  // our ETags are strong: "<version>"
  if (!m) return res.status(412).json({ error: 'ETag does not match' });              // W/"..." or garbage

  const { rows } = await pool.query(
    `UPDATE docs SET title = COALESCE($3, title), body = COALESCE($4, body),
            version = version + 1, updated_at = now()
      WHERE id = $1 AND version = $2
  RETURNING id, title, body, version`,
    [req.params.id, Number(m[1]), req.body.title ?? null, req.body.body ?? null],
  );

  if (rows.length === 0) {                                     // either it doesn't exist or the version moved on
    const cur = await pool.query('SELECT version FROM docs WHERE id = $1', [req.params.id]);
    if (cur.rowCount === 0) return res.sendStatus(404);
    return res.status(412).set('ETag', etagOf(cur.rows[0].version))
      .json({ error: 'Document changed since you loaded it', currentVersion: cur.rows[0].version });
  }
  res.set('ETag', etagOf(rows[0].version)).json(rows[0]);
});
```

Two related forms: **`If-Match: *`** means "only if it exists at all", and **`If-None-Match: *`** on a `PUT` means "only if it does **not** exist yet", which makes create-if-absent safe when two clients race to create the same resource (the loser gets 412).

#### 428 Precondition Required ➕

- **Problem:** optimistic concurrency only works if clients **send** `If-Match`. One old client that doesn't brings the lost update back.
- **Mechanism:** RFC 6585's **`428 Precondition Required`** tells the client "this resource requires a conditional request". The handler above returns it when `If-Match` is missing, so skipping the check is impossible.
- **Edge cases:** introducing 428 on an existing API is a **breaking change** for clients that never sent `If-Match`. Roll it out like any breaking change: log unconditional writes per client first, then enforce (or enforce only on a new API version).

#### Failure modes and design choices ➕

- **Weak ETags never satisfy `If-Match`.** It uses strong comparison, so `W/"4"` can't match. Watch out for proxies: **Nginx turns strong ETags into weak ones when it gzips a response**, after which every conditional write from a browser fails with 412. Either derive write ETags from a version the client reads from the body, or keep compression from rewriting them.
- **Derive the ETag from the stored version, not from the response bytes.** A hash of the JSON changes whenever field order, formatting or an unrelated computed field changes, causing spurious 412s.
- **Give clients something to do with a 412.** Return the current ETag (as above), and in the UI reload, show what changed and let the user re-apply their edit. For fields that can be merged automatically (counters, sets), prefer atomic operations (`UPDATE ... SET likes = likes + 1`) over read-modify-write.
- **`DELETE` deserves `If-Match` too**: deleting a document someone updated a second ago is also a lost update.

## 13. Content negotiation 🎓

### What it is
A mechanism by which client and server **agree on the best format** for the data. The client states its preferences; the server responds with a match, or a **fallback** if it can't.

| Type | Request header | Example |
|---|---|---|
| **Media type** | `Accept` | `application/json`, `application/xml` |
| **Language** | `Accept-Language` | `en`, `es` |
| **Encoding** | `Accept-Encoding` | `gzip`, `deflate`, `br`, `zstd` |

### What the demo shows 🎓
- **Default:** English + JSON + gzip. The request carries `Accept-Language: en`, `Accept: application/json`, and the browser's `Accept-Encoding: gzip, deflate, br, zstd`. The response is JSON in English.
- **Switch to Spanish:** only `Accept-Language` changes, and the server responds **in Spanish**.
- **Switch to XML** (still Spanish): `Accept: application/xml`, and the response is **XML in Spanish**.
- **Benefit:** the client states its preferences and the server adapts, which makes the client's life easier.

<Mermaid chart={`sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: GET /greeting<br/>Accept application/xml<br/>Accept-Language es
  S->>S: pick best match per header
  S-->>C: 200<br/>Content-Type application/xml<br/>Content-Language es<br/>Vary Accept, Accept-Language`} />

### 🔧 Going deeper: implementing it
Preferences can carry **quality weights**: `Accept-Language: es;q=1.0, en;q=0.5`. Don't parse that by hand; Express's `req.accepts` / `req.acceptsLanguages` (built on the `negotiator` package) does it.

```ts title="negotiate.ts"
const messages = { en: 'Hello', es: 'Hola' } as const;

app.get('/greeting', (req, res) => {
  const lang = (req.acceptsLanguages('en', 'es') || 'en') as keyof typeof messages;  // fallback: en
  res.vary('Accept').vary('Accept-Language');                                        // tell caches
  res.set('Content-Language', lang);

  res.format({
    'application/json': () => res.json({ message: messages[lang] }),
    'application/xml':  () => res.type('application/xml').send(`<greeting>${messages[lang]}</greeting>`),
    default:            () => res.status(406).send('Not Acceptable'),                // no format matches
  });
});
```

- **`406 Not Acceptable`** is the standard answer when nothing matches (many APIs instead fall back to JSON).
- **`Vary`** is essential: without it, a CDN might cache the Spanish XML and serve it to an English JSON client.

## 14. HTTP compression 🎓

Compression falls under the same umbrella: the encoding part of content negotiation.

### What the demo shows 🎓
The JSON response is replaced with a large file of **11,000 entries**.
- **With compression** (server uses gzip because the client sent `Accept-Encoding: gzip`, and the response says `Content-Encoding: gzip`): about **3.8 MB** transferred.
- **Compression disabled:** the same file is about **26 MB**.

That's roughly a **7x** difference. Multiply by every client and it's a huge amount of bandwidth. The browser **decompresses** transparently and gets exactly the same data.

<Mermaid chart={`sequenceDiagram
  participant B as Browser
  participant S as Server
  B->>S: GET /big.json + Accept-Encoding gzip, br
  S->>S: compress body with gzip
  S-->>B: 200 + Content-Encoding gzip + Vary Accept-Encoding<br/>about 3.8 MB on the wire
  B->>B: decompress, JS sees the original 26 MB JSON`} />

### 🔧 Going deeper: where and how to compress
- **Why JSON compresses so well:** it repeats the same keys and structure thousands of times, and gzip/Brotli replace repeats with short back-references.
- **Where:** usually at the **reverse proxy or CDN** (Nginx `gzip on;`, or the CDN's settings), so app CPU is spent on business logic. In Node, the `compression` middleware does it in-process:

```ts
import compression from 'compression';
app.use(compression({ threshold: 1024 }));   // skip tiny bodies: headers + CPU cost more than they save
```

- **Don't recompress** already-compressed formats (JPEG, PNG, MP4, ZIP); it wastes CPU for no gain.
- **Brotli (`br`)** usually compresses text better than gzip; great for **static assets compressed ahead of time**. For dynamic responses, gzip at a moderate level is a good CPU/size trade-off.
- **Security edge case:** compressing responses that mix **secrets** (e.g. CSRF tokens) with **attacker-controlled input** over HTTPS enables the **BREACH** attack. Keep secrets out of compressed, reflected responses, or disable compression for those.

## 15. Persistent connections 🎓

### The problem
In **HTTP 1.0**, every request-response cycle needed its **own connection**. Opening and closing TCP connections is **slow and resource-intensive** (section 2).

### The mechanism
**HTTP 1.1** introduced **persistent connections**: one TCP connection is **reused** for many requests and responses, until one side decides to close it.

Key points:
1. In HTTP 1.1, connections are **persistent by default**. You don't do anything; they stay open unless explicitly closed. Fewer connections means lower latency and fewer resources.
2. The **`Connection: keep-alive`** header can still be sent to explicitly ask the server to keep it open, and the `Keep-Alive` header can add options: a **`timeout`** (how long an idle connection stays open) and **`max`** (how many requests before closing).
3. **`Connection: close`** closes the connection after the response. That was HTTP 1.0's default, and it can still be forced in 1.1.

You usually won't touch these; the defaults work.

<Mermaid chart={`sequenceDiagram
  participant C as Client
  participant S as Server
  Note over C,S: HTTP 1.0
  C->>S: handshake, GET /a, close
  C->>S: handshake, GET /b, close
  Note over C,S: HTTP 1.1 keep-alive
  C->>S: handshake once
  C->>S: GET /a
  S-->>C: 200
  C->>S: GET /b (same connection)
  S-->>C: 200
  Note over C,S: idle timeout, then close`} />

### 🔧 Going deeper: the keep-alive 502 bug behind a load balancer
**Problem:** your app sits behind a load balancer (e.g. AWS ALB) that keeps idle connections to your app open and reuses them. **Node's default `server.keepAliveTimeout` is 5 seconds**; an ALB's default idle timeout is **60 seconds**. Node closes an idle connection at 5 s; the ALB, believing it's still open, sends the next request on it at the same moment and gets a reset. The user sees an **intermittent 502** that never shows up in your app logs.

**Fix:** the **upstream** (your app) must keep connections open **longer** than the proxy:

```ts title="main.ts"
const server = app.listen(3000);
server.keepAliveTimeout = 65_000;   // > ALB idle timeout (60 s)
server.headersTimeout   = 66_000;   // must be larger than keepAliveTimeout
```

🔧 Note: `Connection` and `Keep-Alive` are **HTTP/1.x-only**. HTTP/2 and HTTP/3 forbid connection-specific headers (Safari refuses responses that contain them), so don't set them manually.

## 16. Proxies and forwarded headers ➕

The keep-alive bug above is one symptom of a bigger fact: in production your app almost never talks to the client directly. The TCP peer is a load balancer, so **everything the app knows about the client** (its IP, whether it used HTTPS, which host name it typed) comes from headers that a proxy wrote, or that an attacker wrote and a proxy passed along.

<Mermaid chart={`flowchart LR
  C["Client 203.0.113.7<br/>may send its own fake<br/>X-Forwarded-For"] --> LB["Load balancer 10.0.1.5<br/>appends client IP"]
  LB --> NX["Nginx 127.0.0.1<br/>appends LB IP"]
  NX --> APP["App sees TCP peer 127.0.0.1<br/>reads X-Forwarded-For<br/>from the right"]`} />

#### X-Forwarded-For, -Proto and -Host ➕

- **Problem:** after TLS termination at the proxy, the app sees the **proxy's** IP, plain `http`, and possibly an internal host name. Rate limiting, audit logs, redirects to `https://...` and absolute URLs are all wrong.
- **Mechanism:** each proxy adds what it saw:
  - `X-Forwarded-For: 203.0.113.7, 10.0.1.5`: a list, **each proxy appends** the address it received the connection from;
  - `X-Forwarded-Proto: https`: the scheme the client used;
  - `X-Forwarded-Host: api.example.com`: the original `Host`.
- **The key insight:** the list is only trustworthy **from the right**. Entries appended by your own proxies are facts; anything to their left was supplied by the client and can say anything.
- **Implementation:** Nginx's usual `$proxy_add_x_forwarded_for` **appends** to whatever the client sent. If Nginx is the first hop facing the internet, overwrite instead:

```nginx
# Nginx is the edge: discard anything the client claimed
proxy_set_header X-Forwarded-For   $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host  $host;
# Nginx behind a trusted LB: append, and let the app count hops
# proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

- **Edge cases:** a client can send the header several times; servers join repeated headers into one comma-separated list, so the parsing rule ("count from the right") still holds.

#### The standard `Forwarded` header ➕

- **Problem:** the `X-Forwarded-*` family was never standardised, and each header is separate, so a hop could update one and not the others.
- **Mechanism:** RFC 7239 defines one header with all fields per hop: `Forwarded: for=203.0.113.7;proto=https;host=api.example.com, for=10.0.1.5`. IPv6 addresses are quoted and bracketed (`for="[2001:db8::1]"`), and a proxy may use obfuscated identifiers instead of real IPs.
- **Implementation:** most stacks, including Express's `trust proxy` (via the `proxy-addr` package), still read **`X-Forwarded-For`**, not `Forwarded`. If your edge emits `Forwarded`, either have it also emit `X-Forwarded-*` or parse it yourself with the same right-to-left rule.
- **Edge case:** when both are present and disagree, an attacker is often controlling one of them. Have the edge strip whichever family you don't use.

#### Express `trust proxy`, configured exactly ➕

- **Problem:** with `trust proxy` off (the default), `req.ip` is the proxy's IP and `req.protocol` is `http`. With `trust proxy` set to `true`, Express trusts **every** hop, so `req.ip` becomes the **leftmost** address: whatever the client typed.
- **Mechanism:** Express walks `X-Forwarded-For` **from right to left**, skipping addresses it trusts; the first untrusted one is the client. You define "trusted" as a hop count or a list of proxy addresses.

```ts title="main.ts"
app.set('trust proxy', 1);                          // exactly one proxy (Nginx or one LB) in front
// app.set('trust proxy', 2);                       // CDN → LB → app
// app.set('trust proxy', ['loopback', '10.0.0.0/8']);   // trust by address: robust when hop count varies
// app.set('trust proxy', true);                    // ❌ trusts everything: req.ip is client-controlled

// NestJS (Express adapter)
const nest = await NestFactory.create<NestExpressApplication>(AppModule);
nest.set('trust proxy', 1);
```

With it set correctly, `req.ip`, `req.ips`, `req.protocol`, `req.secure` and `req.hostname` all use the forwarded values.

- **Edge cases:** the right value changes when the **infrastructure** changes. Put a CDN in front of the ALB and `trust proxy: 1` now returns the CDN's IP, so every user shares one rate-limit bucket. Some CDNs send their own client-IP header (e.g. Cloudflare's `CF-Connecting-IP`); trust it only if the origin accepts connections **exclusively** from that CDN's IP ranges.

#### Spoofed client IPs: what breaks, and a test for it ➕

- **Problem:** if `req.ip` can be spoofed, everything keyed on IP breaks: rate limits (rotate a fake IP per request), brute-force lockouts, audit logs ("the attacker came from 127.0.0.1"), geo rules, and admin routes allow-listed to an office IP (`X-Forwarded-For: <office IP>`).
- **Mechanism:** test the exact behaviour of your stack, end to end, through the real proxies.

```bash
# from outside, through the real edge: req.ip in the app logs must be YOUR address, not 1.2.3.4
curl -s -H 'X-Forwarded-For: 1.2.3.4' https://api.example.com/debug/whoami
```

```ts title="trust-proxy.spec.ts (supertest, simulating one trusted proxy)"
it('ignores client-supplied X-Forwarded-For entries', async () => {
  const res = await request(app).get('/debug/whoami')
    .set('X-Forwarded-For', '1.2.3.4, 198.51.100.9');     // 1.2.3.4 is forged; 198.51.100.9 was appended by our proxy
  expect(res.body.ip).toBe('198.51.100.9');
});
```

- **Edge cases:** IP-based controls are **weak** by nature (NAT puts thousands of users behind one IP; attackers rent many IPs). Use them as one signal, never as the only authentication for an admin route.

#### Host-header attacks: password-reset poisoning ➕

- **Problem:** the app builds an absolute link from the request: ``const link = `https://${req.get('host')}/reset?token=${token}` ``. An attacker requests a password reset **for the victim's email** with `Host: evil.example` (or `X-Forwarded-Host: evil.example`). The victim receives a genuine email from you containing `https://evil.example/reset?token=...`. One click, and the attacker has a valid reset token.

<Mermaid chart={`sequenceDiagram
  participant A as Attacker
  participant S as Your app
  participant V as Victim inbox
  A->>S: POST /forgot-password email=victim + Host evil.example
  S->>V: email with link to evil.example/reset?token=abc
  V->>A: victim clicks, token arrives at evil.example
  A->>S: POST /reset token=abc, new password`} />

- **Mechanism:** the request's `Host` is **user input**. Build links from a **configured** base URL, and make the edge reject unknown hosts before they reach the app.

```ts
const link = new URL(`/reset?token=${encodeURIComponent(token)}`, config.PUBLIC_BASE_URL);   // never from req
```

```nginx
server {                                     # catch-all for any Host you don't serve
    listen 443 ssl default_server;
    ssl_reject_handshake on;                 # nginx 1.19.4+: refuse TLS for unknown names
}
server {                                     # plain HTTP equivalent
    listen 80 default_server;
    return 444;                              # nginx: close the connection without a response
}
```

- **Edge cases:** the same untrusted `Host` also feeds **cache poisoning** (section 11), routing to internal virtual hosts on shared proxies, and open redirects built from `req.hostname`. With `trust proxy` enabled, Express's `req.hostname` reads `X-Forwarded-Host`, so a proxy that passes the client's value through re-opens the hole.

## 17. The backend as an HTTP client ➕

So far the backend has been the **server**. But almost every backend is also an HTTP **client**: it calls payment providers, email APIs, object storage and other internal services. Every rule above applies in reverse, and the defaults of Node's HTTP clients are tuned for scripts, not for servers under load. (Retry policies, backoff and circuit breakers are covered in [Error handling and fault tolerance](/docs/backend-first-principles/16-error-handling-fault-tolerance); this section is about the HTTP mechanics underneath.)

#### Timeouts on every call ➕

- **Problem:** global `fetch` (undici) has **no overall timeout**. Its defaults are a 10 s connect timeout and **300 s** each for receiving headers and body. If a provider hangs, every request of yours that calls it hangs for up to 5 minutes, holding memory, a socket and maybe a DB transaction. Requests pile up, and **your** service fails because **theirs** is slow.
- **Why:** a client can't tell "slow" from "never answering" without a deadline. Only a timeout turns an unbounded wait into a fast, handleable error.
- **Mechanism:** give every outbound call a deadline **shorter than your own request budget** (section 19), and cancel it when your client disconnects.
- **Implementation:**

```ts title="http-client.ts"
import { Agent, setGlobalDispatcher } from 'undici';

setGlobalDispatcher(new Agent({
  connect: { timeout: 2_000 },     // TCP + TLS handshake
  headersTimeout: 5_000,           // time to first response headers
  bodyTimeout: 10_000,             // max gap between body chunks (not a total limit)
}));

export async function getJson(url: string, opts: { timeoutMs?: number; signal?: AbortSignal } = {}) {
  const deadline = AbortSignal.timeout(opts.timeoutMs ?? 3_000);                       // total deadline
  const signal = opts.signal ? AbortSignal.any([deadline, opts.signal]) : deadline;    // or the client left
  const res = await fetch(url, { signal, headers: { accept: 'application/json' } });
  if (!res.ok) throw new UpstreamError(res.status, await res.text().catch(() => ''));
  return res.json();                                                                   // body read is covered by the signal too
}
```

- **Edge cases:** `AbortSignal.timeout` rejects with a `DOMException` named **`TimeoutError`**, while a manual abort gives `AbortError`; log them differently. `bodyTimeout` is an **idle** timeout, so a server trickling one byte every 9 s never trips it; only the total deadline does. A timeout does **not** cancel the work on the other side: the payment may still go through, which is why retries need idempotency.

#### Connection reuse with a keep-alive agent ➕

- **Problem:** a new connection per call pays DNS, TCP and TLS every time (section 2): tens of milliseconds and real CPU for the TLS handshake. At high rates, closed connections pile up in `TIME_WAIT` and can exhaust local ports.
- **Mechanism:** an **agent** (a connection pool per origin) keeps idle connections open and reuses them. Global `fetch` pools connections by default. `node:http`'s global agent has used keep-alive (5 s idle timeout) only since **Node 19**; older code, and libraries that create their own `http.Agent`, may still open a connection per request.
- **Implementation:**

```ts
import { Agent } from 'undici';
import https from 'node:https';

// undici / fetch: one pool per upstream with explicit limits
export const paymentsPool = new Agent({ connections: 50, keepAliveTimeout: 4_000, pipelining: 1 });
await fetch('https://api.payments.example/v1/charges', { dispatcher: paymentsPool, signal: AbortSignal.timeout(5_000) });

// node:http based libraries (axios, older SDKs)
export const keepAliveAgent = new https.Agent({ keepAlive: true, maxSockets: 50, timeout: 5_000 });
```

- **Edge cases:**
  - This is the **mirror image** of the 502 bug in section 15: if the upstream closes idle connections after 5 s and your pool keeps them for 10 s, you'll reuse a dead socket and get **`ECONNRESET`**. Keep the client's idle timeout **shorter** than the server's (undici also honours the server's `Keep-Alive: timeout=...` hint).
  - `maxSockets` defaults to **Infinity** for `http.Agent`: a traffic spike opens unlimited connections and can take down a fragile upstream. Set a limit; requests then queue in the pool.
  - Long-lived pooled connections don't notice **DNS changes**; after a failover, the old IP keeps getting traffic until connections are recycled.

#### Which failures are retryable ➕

- **Problem:** retrying everything doubles payments; retrying nothing turns every transient blip into a user-facing error.
- **Mechanism:** the deciding question is **"could the server have started processing?"** If the request provably never arrived, a retry is always safe. If it might have arrived, only retry methods that are **idempotent** or carry an **`Idempotency-Key`** (section 8).

| Failure | Did the request reach the server? | Retry |
|---|---|---|
| DNS failure (`ENOTFOUND`, `EAI_AGAIN`) | no | `EAI_AGAIN` (temporary) yes; `ENOTFOUND` usually a config bug |
| `ECONNREFUSED`, connect timeout | no, no connection was made | yes, any method |
| `ECONNRESET` on a **reused** idle socket, before any response byte | probably not, but not provable | idempotent or keyed requests only |
| `ECONNRESET` / timeout while waiting for the response | **maybe**, the server may have done the work | idempotent or keyed requests only |
| `429`, `503` | reached, rejected before processing | yes, after `Retry-After` |
| `502`, `504` | the proxy reached the server, which may have processed it | idempotent or keyed requests only |
| `500` | reached, it failed | usually no: it's a bug and will fail again |
| other `4xx` | reached, rejected | no: fix the request |

- **Implementation:**

```ts title="retryable.ts"
const NOT_SENT = new Set(['ECONNREFUSED', 'EAI_AGAIN', 'UND_ERR_CONNECT_TIMEOUT']);
const MAYBE_SENT = new Set(['ECONNRESET', 'UND_ERR_SOCKET', 'UND_ERR_HEADERS_TIMEOUT', 'ETIMEDOUT']);

export function canRetry(err: unknown, opts: { idempotent: boolean }) {
  if (err instanceof UpstreamError) {
    if (err.status === 429 || err.status === 503) return true;
    if (err.status === 502 || err.status === 504) return opts.idempotent;
    return false;
  }
  const code = (err as any)?.cause?.code ?? (err as any)?.code;          // fetch wraps errors: TypeError('fetch failed') with .cause
  if (NOT_SENT.has(code)) return true;
  if (MAYBE_SENT.has(code) || (err as any)?.name === 'TimeoutError') return opts.idempotent;
  return false;
}
```

- **Edge cases:** retry in **one layer** only: if the SDK, your code and the service mesh each retry 3 times, one failure becomes 27 attempts. Count retries against your total deadline, not per attempt.

#### `ECONNRESET` vs `ETIMEDOUT` vs a 5xx: reading the error ➕

- **Problem:** "the call failed" isn't actionable. The error type tells you **which hop** to look at.
- **Mechanism (what each means at the TCP level):**
  - **`ECONNREFUSED`**: the host answered the SYN with a RST: the machine is up but **nothing listens on that port** (app crashed, wrong port).
  - **`ETIMEDOUT`** (or a connect timeout): **no answer at all**. Packets are being dropped: a firewall or security group (lesson 3), a wrong IP, a dead host.
  - **`ECONNRESET`** (undici: `UND_ERR_SOCKET`, "other side closed"): a connection existed and the peer **reset** it: the process died mid-request, an LB or NAT idle timeout killed it, or you reused a socket the server had just closed.
  - **A 5xx** is a complete HTTP response: the network path is fine and **some HTTP server answered**. Check whether it came from the upstream app or a proxy in front of it (502/504 usually from the proxy).
- **Implementation:** log enough to tell them apart:

```ts
try {
  return await getJson(url);
} catch (err: any) {
  log.warn({
    upstream: new URL(url).host,
    code: err.cause?.code ?? err.code,           // ECONNRESET, UND_ERR_CONNECT_TIMEOUT, ...
    name: err.name,                              // TimeoutError, AbortError, TypeError
    status: err.status,                          // set by UpstreamError for HTTP errors
  }, 'upstream call failed');
  throw err;
}
```

- **Edge cases:** since Node 20, connections try IPv6 and IPv4 addresses in parallel ("happy eyeballs", `autoSelectFamily`), so a connect failure can surface as an **`AggregateError`** holding one error per address; look inside `.errors`. Bursts of `ECONNRESET` exactly at an idle interval (every ~5 s, every 60 s) almost always mean mismatched keep-alive timeouts, not a flaky network.

## 18. Handling large requests and responses 🎓

### Large requests: `multipart/form-data` 🎓
**The demo:** select a picture and upload it. The request:
- `POST` with a `Content-Length`,
- **`Content-Type: multipart/form-data; boundary=----WebKitFormBoundary...`**.

**The boundary** is a delimiter string that separates the **parts** of the body. Searching the body for it, you find it **before** the file's binary data and again **at the end**. The server reads the parts, gets the file and responds with some details to confirm the upload. The lesson's guidance: **use multipart requests to send files** to the server.

🔧 **A precise note on what "parts" means:** in `multipart/form-data`, each part is **one form field** (a text field, or one whole file), **not** a fragment of the file. The whole body still travels in **one HTTP request**; TCP splits it into packets underneath. The boundary exists so binary data and text fields can sit in one body without needing to escape anything. A raw body looks like this:

```http
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----X7f
Content-Length: 48213

------X7f
Content-Disposition: form-data; name="title"

Holiday photo
------X7f
Content-Disposition: form-data; name="file"; filename="beach.jpg"
Content-Type: image/jpeg

(binary JPEG bytes...)
------X7f--
```

(The final boundary ends with `--`.) Splitting one large file into separately uploaded chunks is a different technique: **multipart upload** in object storage, covered in the object storage lessons.

🔧 **Implementation: stream it, and cap it.** Don't buffer uploads in memory; stream them and enforce limits so one request can't exhaust RAM or disk:

```ts title="upload.ts (Express + multer)"
import multer from 'multer';

const upload = multer({
  storage: multer.diskStorage({ destination: '/tmp/uploads' }),   // streamed to disk, not held in RAM
  limits: { fileSize: 10 * 1024 * 1024, files: 1, fields: 10 },   // 10 MB, one file
  fileFilter: (_req, file, cb) => cb(null, ['image/jpeg', 'image/png'].includes(file.mimetype)),
});

app.post('/upload', upload.single('file'), (req, res) => {
  if (!req.file) return res.status(400).json({ error: 'file required (jpeg or png)' });
  res.status(201).json({ name: req.file.originalname, size: req.file.size });
});
// note: mimetype comes from the client; check the magic bytes before trusting it
```

### Large responses: streaming in chunks 🎓
**The demo:** a large text file on the server is **streamed** to the client. Clicking "stream data" shows chunks arriving **continuously**, each appended on screen until the whole file is built.
- The request is a normal `GET`.
- The response headers that matter:
  - **`Content-Type: text/event-stream`**: the data will arrive as a stream of **events**,
  - **`Connection: keep-alive`**: keep the connection open until everything is sent.
- The client keeps **appending** each chunk to rebuild the file.

🔧 **Precise version:** two related mechanisms are at work here.
- **Chunked transfer encoding** (HTTP/1.1) lets **any** response be sent in pieces when the total size isn't known up front (`Transfer-Encoding: chunked`). In Node, every `res.write()` before `res.end()` sends a chunk.
- **Server-Sent Events** (`text/event-stream`) is a **format on top of** a long-lived streamed response: lines of `data: ...` separated by blank lines, read in the browser by `EventSource`, which also **reconnects automatically**.

```ts title="stream.ts"
import { createReadStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';

// 1. plain chunked download: constant memory, whatever the file size
app.get('/big.txt', async (req, res) => {
  res.type('text/plain');
  await pipeline(createReadStream('./big.txt'), res);       // pipeline handles backpressure + client aborts
});

// 2. Server-Sent Events: a stream of messages
app.get('/events', (req, res) => {
  res.set({ 'Content-Type': 'text/event-stream', 'Cache-Control': 'no-cache', Connection: 'keep-alive' });
  res.flushHeaders();
  let i = 0;
  const timer = setInterval(() => res.write(`id: ${++i}\ndata: ${JSON.stringify({ chunk: i })}\n\n`), 1000);
  req.on('close', () => clearInterval(timer));              // stop work when the client goes away
});
```

**Why `pipeline` matters (backpressure):** if you `res.write()` a 2 GB file faster than a slow client can receive, Node buffers it all **in memory**. Streams pause reading when the socket's buffer is full and resume when it drains. Also, for SSE through **Nginx**, disable proxy buffering for that route (`proxy_buffering off;` or the `X-Accel-Buffering: no` header), or events arrive in bursts.

## 19. Limits and timeouts as protection ➕

Multer's limits above protect one upload route. The same idea applies to **every** part of every request: each part a client controls (body, headers, URL, and how slowly it sends them) needs a ceiling, because each unbounded part lets one client use up memory or connections meant for everyone. These limits exist at several hops, and they need to agree.

| What | Status when exceeded | Node.js default | Nginx default | Express default |
|---|---|---|---|---|
| body size | `413 Content Too Large` | no limit in `node:http` | `client_max_body_size 1m` | `express.json()` 100 kb |
| header size | `431 Request Header Fields Too Large` | `maxHeaderSize` 16 KiB (all headers together) | `large_client_header_buffers 4 8k` (one line over 8k: 400) | same as Node |
| URL length | `414 URI Too Long` | no separate setting (see below) | request line over 8k: 414 | same as Node |
| time to send headers | `408 Request Timeout` | `headersTimeout` 60 s | `client_header_timeout 60s` | same as Node |
| time to send whole request | `408 Request Timeout` | `requestTimeout` 300 s | `client_body_timeout 60s` (between reads) | same as Node |

#### Body size → 413 ➕

- **Problem:** a JSON parser must hold the whole body in memory before parsing it. A 2 GB "JSON" body, or a thousand 50 MB ones in parallel, exhausts the process.
- **Mechanism:** count bytes **as they arrive** and abort past a limit with **`413`** (RFC 9110 renamed it from "Payload Too Large" to "Content Too Large"). body-parser does this whether the client sends `Content-Length` or a chunked body, so lying about the length doesn't help.
- **Implementation:** a small global limit, raised only on the routes that need it, and a JSON error instead of the default HTML:

```ts title="limits.ts"
app.post('/api/imports', express.json({ limit: '5mb' }), importHandler);   // registered before the global parser
app.use(express.json({ limit: '100kb' }));                                  // everything else

app.use((err: any, _req: Request, res: Response, next: NextFunction) => {
  if (err?.type === 'entity.too.large') return res.status(413).json({ error: `Body exceeds ${err.limit} bytes` });
  if (err?.type === 'entity.parse.failed') return res.status(400).json({ error: 'Malformed JSON' });
  next(err);
});
```

- **Edge cases:** the **smallest limit on the path wins**. If the app allows 5 MB but Nginx still has its 1 MB default, users get Nginx's HTML 413 page and your app never logs anything. Set `client_max_body_size` per `location` to match. For really large files, skip the backend entirely and upload to object storage with presigned URLs ([Object storage part 1](/docs/backend-first-principles/24-object-storage-part-1)).

#### Header size → 431 ➕

- **Problem:** headers are parsed before your code runs, so the server must buffer them. Without a cap, one client sends megabytes of headers.
- **Mechanism:** Node rejects a head larger than **`maxHeaderSize` (16 KiB)** with **`431`**. Raise it per server (`http.createServer({ maxHeaderSize: 32 * 1024 })`) or process-wide with `--max-http-header-size`.
- **The usual cause in real life:** **cookie bloat**. Analytics and A/B-testing cookies set on the parent domain (`.example.com`), or a large JWT stored in a cookie, are sent with **every** request to every subdomain. One day a user's cookies cross 16 KiB and that user, only that user, gets 431s on everything.
- **Implementation:** keep session cookies small (an opaque session ID, not a JWT with every permission), scope cookies to the narrowest domain and path, and log 431s so you notice:

```ts
server.on('clientError', (err: NodeJS.ErrnoException, socket) => {
  if (err.code === 'HPE_HEADER_OVERFLOW') log.warn({ code: err.code }, 'header too large, likely cookie bloat');
  if (socket.writable) socket.end('HTTP/1.1 431 Request Header Fields Too Large\r\nConnection: close\r\n\r\n');
});
```

- **Edge cases:** each hop has its own limit (CDN, LB, Nginx, Node). A request that passes Nginx's per-line 8k rule can still fail Node's 16 KiB total. Raising the limit treats the symptom; shrinking the cookies fixes it.

#### URL length → 414 ➕

- **Problem:** long URLs come from filters packed into query strings, or from attackers probing parsers.
- **Mechanism:** RFC 9110 recommends that senders and recipients support URIs of **at least 8000 octets**; beyond that, nothing is guaranteed, and a server answers **`414 URI Too Long`**. Nginx returns 414 when the request line doesn't fit in one of its 8k header buffers. Node has no separate URL setting; a very long request line runs into the same `maxHeaderSize` parsing budget as the headers, so expect a 431 rather than a 414 from Node itself.
- **Implementation:** keep URLs well under 8000 bytes. When a query naturally grows beyond that (hundreds of IDs, complex filters), switch to `POST /search` or a saved-search resource (section 8, "GET with a body").
- **Edge cases:** CDNs and API gateways often have **lower** limits than your servers, and URLs end up in logs, analytics and `Referer` headers, so long URLs also mean large logs and potential data leaks.

#### Slow clients: headersTimeout, requestTimeout and slowloris ➕

- **Problem:** **slowloris** opens many connections and sends the headers one byte at a time, a few seconds apart, never finishing. Each request is "in progress", so the server keeps every socket open. In a process-per-connection server that exhausts the workers within seconds; in Node it costs a socket, a file descriptor and buffers each, all from a single cheap client.
- **Why size limits don't help:** the attacker sends very **little**; it's the **time** that is unbounded.
- **Mechanism:** deadlines on receiving the request. Node's **`headersTimeout`** (default **60 s**) limits the time to receive the complete head, and **`requestTimeout`** (default **300 s**) the whole request. Both answer `408` and destroy the socket; Node checks them every `connectionsCheckingInterval` (30 s by default), so they fire a little late.
- **Implementation:** if Node faces the internet directly, tighten them. Behind Nginx you're largely protected already, because Nginx **buffers the whole request** (`proxy_request_buffering on` by default) before it opens an upstream connection, so slow clients tie up cheap Nginx connections instead of your app.

```ts title="main.ts"
const server = app.listen(3000);
// Node facing the internet directly, no proxy in front:
server.headersTimeout = 20_000;     // full head within 20 s
server.requestTimeout = 60_000;     // full request (incl. body) within 60 s
// Behind an ALB instead, keep section 15's values (keepAliveTimeout 65 s, headersTimeout 66 s):
// the proxy absorbs slow clients, and the keep-alive rule takes priority.
```

- **Edge cases:** a low `requestTimeout` also kills **legitimate slow uploads** from mobile networks, and it applies to the whole server, not per route. Large uploads belong on direct-to-storage uploads anyway. Remember that body-time limits don't cover **responses**: a slow reader on a big download is handled by streaming with backpressure (section 18), not by these timeouts.

#### The timeout-alignment rule ➕

- **Problem:** every hop has its own timeouts. When they're set independently, you get wasted work (the DB keeps running a query whose caller gave up long ago) and misleading errors (a 504 from the LB while your logs show a `200` a few seconds later).
- **Mechanism, the rule:** **request timeouts shrink as you go deeper**: each layer must give up **before** the layer above it does, so it can still return a meaningful error. **Idle (keep-alive) timeouts grow as you go deeper**: the upstream keeps idle connections open longer than the downstream that reuses them (the 502 bug).

<Mermaid chart={`flowchart LR
  C["Client<br/>30 s"] --> CDN["CDN origin timeout<br/>30 s"]
  CDN --> NX["Nginx proxy_read_timeout<br/>25 s"]
  NX --> APP["App request budget<br/>20 s"]
  APP --> HTTP["Outbound fetch<br/>3 s x 2 attempts"]
  APP --> DB["Postgres statement_timeout<br/>5 s"]`} />

- **Implementation:** set each value explicitly, in one place, and enforce an app-level budget:

```ts title="timeouts.ts"
export const pool = new Pool({ connectionString: config.DATABASE_URL, statement_timeout: 5_000 });   // node-postgres

app.use((req, res, next) => {
  const timer = setTimeout(() => {
    if (!res.headersSent) res.status(503).set('Retry-After', '1').json({ error: 'Request timed out' });
  }, 20_000);                                                // answer before Nginx's 25 s gives a bare 504
  res.on('close', () => clearTimeout(timer));
  next();
});
```

- **Edge cases:** **retries multiply time**: 3 attempts of 3 s plus backoff must still fit inside the 20 s budget. If an inner timeout is **longer** than an outer one, the outer layer returns an error while the inner one keeps going and may **commit**: the user sees a failure for a write that actually happened. Long-running work doesn't fit any request timeout and belongs in a background job (202, section 10).

## 20. SSL, TLS and HTTPS 🎓

You rarely work with these directly, but should know what they are.

| Term | What it is |
|---|---|
| **SSL** | the **original** protocol for securing client-server communication. Encrypts data so passwords or card numbers can't be intercepted. Now **outdated** because of security vulnerabilities, and replaced by TLS |
| **TLS** | the **modern, more secure successor**. Encrypts data **in transit** against interception and tampering. Uses **certificates** to **authenticate the server** and set up an encrypted connection. Updated regularly; the current recommended version is **TLS 1.3** |
| **HTTPS** | **HTTP over TLS** (originally over SSL). When you visit an HTTPS site, TLS encrypts the traffic between browser and server, protecting credentials and other sensitive data |

<Mermaid chart={`flowchart LR
  A["HTTP message"] --> T["TLS layer<br/>encrypt + integrity check"]
  T --> TCP["TCP"]
  TCP --> NET["Network (attacker sees only ciphertext)"]
  CERT["Server certificate<br/>signed by a CA"] -. "proves server identity" .-> T`} />

🔧 **What TLS actually guarantees:**
- **Confidentiality** (encryption): eavesdroppers see only ciphertext.
- **Integrity**: tampering is detected.
- **Authentication**: the certificate, signed by a trusted CA and matching the host name, proves you're talking to the real server and not a man in the middle.
- It does **not** hide **which host** you connect to (the IP is visible, and the name usually is too, through SNI), and it doesn't protect data once it's on the server.

🔧 **Practical setup:** terminate TLS at the reverse proxy or load balancer (Let's Encrypt via Certbot, or a managed certificate), redirect HTTP to HTTPS with a **301**, then add **HSTS** so browsers never try plain HTTP again.

## 21. TLS for backend engineers: handshake, chains, mTLS and expiry ➕

The section above says what TLS guarantees. Backend engineers end up debugging its **mechanics**: why a handshake costs what it costs, why a certificate works in Chrome but not in Node, how services authenticate each other, and why certificates still take whole sites down.

#### The TLS 1.3 handshake, step by step ➕

- **Problem:** before encrypting, client and server must agree on keys **over a network an attacker can read**, and the client must verify it's talking to the real server.
- **Mechanism:** TLS 1.3 does it in **one round trip** (TLS 1.2 needed two):

<Mermaid chart={`sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: ClientHello with versions, cipher suites, key share, SNI api.example.com, ALPN h2
  S-->>C: ServerHello with chosen suite + key share
  Note over C,S: both derive the same secret from the two key shares (ECDHE)
  S-->>C: encrypted certificate chain, CertificateVerify signature, Finished
  C->>C: verify chain to a trusted root, host name, signature
  C->>S: encrypted Finished + first HTTP request
  S-->>C: HTTP response`} />

1. The client sends its **key share** right away, guessing the key-exchange group, which is what saves the round trip.
2. Both sides compute the shared secret with **ephemeral (EC)DHE**, so every connection gets fresh keys: stealing the server's private key later doesn't decrypt recorded traffic (**forward secrecy**, mandatory in TLS 1.3).
3. The server's private key is used only to **sign** the handshake (`CertificateVerify`), proving it owns the certificate.
- **Implementation:** inspect a real handshake:

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com -tls1_3 -alpn h2 </dev/null 2>/dev/null \
  | grep -E 'Protocol|Cipher|ALPN|Verify return code'
```

```ts
import tls from 'node:tls';
const s = tls.connect({ host: 'api.example.com', port: 443, servername: 'api.example.com', ALPNProtocols: ['h2', 'http/1.1'] }, () => {
  console.log(s.getProtocol(), s.alpnProtocol, s.authorized ? 'chain ok' : s.authorizationError);   // TLSv1.3 h2 chain ok
  s.end();
});
```

- **Edge cases:** without **SNI** the server can't know which certificate to present and sends its default one, causing a name mismatch (the reason `curl https://<ip>` fails; use `--resolve`, section 6). Node's default minimum is TLS 1.2; there's rarely a reason to accept anything older.

#### 0-RTT and replay ➕

- **Problem:** even one round trip hurts on mobile networks. TLS 1.3 lets a **resuming** client send application data in its very first flight ("early data", **0-RTT**).
- **Why it's dangerous:** early data is encrypted but **not protected against replay**. An attacker who records the first flight can resend it, and the server can't tell the copy from the original. A replayed `POST /transfer` executes twice.
- **Mechanism:** allow early data only for requests that are **safe to repeat** (safe methods). The TLS terminator marks such requests (Nginx forwards `$ssl_early_data`; several CDNs send `Early-Data: 1`), and the app answers anything non-idempotent with **`425 Too Early`** (RFC 8470), which makes the client retry after the full handshake.

```ts
app.use((req, res, next) => {
  const early = req.header('Early-Data') === '1';
  if (early && !['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return res.sendStatus(425);   // retry after handshake
  next();
});
```

```nginx
ssl_early_data on;                               # off by default in nginx
proxy_set_header Early-Data $ssl_early_data;     # "1" while the handshake is incomplete
```

- **Edge cases:** "safe" here means the GET really has no side effects (section 8). If you can't audit that, leave 0-RTT **off**; it's an optimisation, not a requirement.

#### Certificate chains and the missing-intermediate bug ➕

- **Problem:** the site works in Chrome, but `curl`, Node, Java services or older Android devices fail with **"unable to verify the first certificate"** (Node: `UNABLE_TO_VERIFY_LEAF_SIGNATURE`).
- **Why (first principles):** clients trust a small set of **root** CAs. Roots don't sign site certificates directly; **intermediates** do. The server must send its **leaf certificate plus the intermediates**, so the client can build the chain up to a root it already has. Browsers often paper over a missing intermediate (they cache intermediates they've seen, or fetch them via the certificate's AIA URL). Most non-browser clients don't, so the bug hides until a backend or mobile client hits it.

<Mermaid chart={`flowchart LR
  L["Leaf: api.example.com<br/>sent by server"] -->|"signed by"| I["Intermediate CA<br/>must also be sent"]
  I -->|"signed by"| R["Root CA<br/>already in client trust store"]`} />

- **Implementation:** serve the full chain and check how many certificates the server actually presents:

```nginx
ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;   # leaf + intermediates, NOT cert.pem
ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
```

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts </dev/null 2>/dev/null | grep -c 'BEGIN CERTIFICATE'
# 1 means the intermediate is missing; 2 or more is expected
```

- **Edge cases:** never "fix" verification errors with `NODE_TLS_REJECT_UNAUTHORIZED=0` or `rejectUnauthorized: false`: that turns off server authentication completely and makes man-in-the-middle trivial. For an internal CA, add it with `NODE_EXTRA_CA_CERTS=/path/ca.pem` instead. Chains also break when a **root** expires: when Let's Encrypt's old `DST Root CA X3` expired in September 2021, devices with outdated trust stores started failing even though the sites' own certificates were valid.

#### mTLS for service-to-service authentication ➕

- **Problem:** inside a VPC it's tempting to trust anything that can reach a service. But one compromised pod, or one leaked API key (a bearer secret that works from anywhere), then gives access to everything.
- **Mechanism:** in **mutual TLS** the **client** also presents a certificate, and the server verifies it against an internal CA. The service's identity is proven cryptographically on every connection, and the private key never travels over the network.

```ts title="mtls-server.ts"
import https from 'node:https';
import { readFileSync } from 'node:fs';

const ALLOWED_CLIENTS = new Set(['orders-service', 'billing-worker']);

https.createServer({
  key: readFileSync('server.key'), cert: readFileSync('server.crt'),
  ca: readFileSync('internal-ca.crt'),       // trust only our CA for client certs
  requestCert: true, rejectUnauthorized: true,
}, (req, res) => {
  const cn = (req.socket as import('node:tls').TLSSocket).getPeerCertificate().subject?.CN;
  if (!cn || !ALLOWED_CLIENTS.has(String(cn))) { res.writeHead(403).end(); return; }   // authn by TLS, authz here
  res.end(JSON.stringify({ hello: cn }));
}).listen(8443);
```

```ts title="mtls-client.ts"
import { Agent } from 'undici';
const mtls = new Agent({ connect: { key: readFileSync('orders.key'), cert: readFileSync('orders.crt'), ca: readFileSync('internal-ca.crt') } });
await fetch('https://inventory.internal:8443/stock', { dispatcher: mtls, signal: AbortSignal.timeout(2_000) });
```

- **Edge cases:**
  - **Rotation is the hard part.** Revocation (CRLs, OCSP) is unreliable, so internal setups use **short-lived** certificates renewed automatically. Service meshes (Istio, Linkerd) issue and rotate them and do mTLS transparently between sidecars.
  - If a load balancer terminates TLS, your app never sees the client certificate. LBs that support mTLS forward it in a header (AWS ALB: `X-Amzn-Mtls-Clientcert`), and the app must make sure clients can't send that header themselves (the same trust rule as `X-Forwarded-For`, section 16).
  - Authenticating the caller is not authorising it: still check **what** that service may do.

#### Certificate-expiry monitoring ➕

- **Problem:** an expired certificate is a **total** outage: every client refuses to connect, and there's no graceful degradation. It keeps happening even with automated renewal.
- **Why renewals fail silently:** the ACME challenge breaks (port 80 closed by a new firewall rule, a DNS provider token expired), or renewal succeeds but the server is **never reloaded** and keeps serving the old certificate from memory. And external reminders are disappearing: **Let's Encrypt stopped sending expiry emails on 4 June 2025**.
- **Why it's getting more important:** CA/Browser Forum ballot SC-081 shortens the maximum public certificate lifetime from 398 days to **200 days (from 15 March 2026), 100 days (15 March 2027) and 47 days (15 March 2029)**. Renewal becomes something that happens constantly, so it must be automated and **monitored**.
- **Mechanism:** monitor the certificate **actually served**, from outside, for every host name and every load balancer, and alert well before expiry.

```ts title="check-certs.ts (run from cron or CI, alert on non-zero exit)"
import tls from 'node:tls';

const HOSTS = ['api.example.com', 'www.example.com', 'admin.example.com'];
const WARN_DAYS = 21;

const daysLeft = (host: string) => new Promise<number>((resolve, reject) => {
  const s = tls.connect({ host, port: 443, servername: host, timeout: 5_000 }, () => {
    const cert = s.getPeerCertificate(true);
    let earliest = new Date(cert.valid_to).getTime();
    for (let c: any = cert.issuerCertificate; c && c !== c.issuerCertificate; c = c.issuerCertificate) {
      earliest = Math.min(earliest, new Date(c.valid_to).getTime());   // intermediates expire too
    }
    s.end();
    resolve(Math.floor((earliest - Date.now()) / 86_400_000));
  });
  s.on('error', reject).on('timeout', () => s.destroy(new Error('timeout')));
});

let failed = false;
for (const host of HOSTS) {
  const d = await daysLeft(host).catch((e) => { console.error(host, e.message); return -1; });
  if (d < WARN_DAYS) { failed = true; console.error(`${host}: ${d} days left`); }
}
process.exit(failed ? 1 : 0);
```

```bash
# certbot: reload nginx after every successful renewal, so the new cert is actually served
certbot renew --deploy-hook "systemctl reload nginx"
```

- **Edge cases:** check **each** server behind a load balancer and each region (one stale instance serves an old certificate to a fraction of users). Internal mTLS certificates expire too, with even shorter lifetimes. Prometheus users get the same signal from the blackbox exporter's `probe_ssl_earliest_cert_expiry` metric.

## Interview questions

1. **What does "HTTP is stateless" mean, and how do logins work then?** **The server keeps no memory between requests, so each request carries its own credentials (cookie or token). State lives in a signed token or a shared session store any server can read.**
2. **What changed in HTTP/1.1, 2 and 3?** **1.1: persistent connections and chunked encoding. 2: multiplexed binary streams on one connection plus HPACK header compression. 3: QUIC over UDP, removing TCP-level head-of-line blocking and speeding up connection setup.**
3. **Why do headers exist separately from the body?** **So every hop (proxies, caches, the server, the browser) can read handling metadata without parsing the body, like the address written on a parcel.**
4. **PUT vs PATCH?** **PUT replaces the whole resource with the body (idempotent). PATCH changes only the fields sent and isn't guaranteed idempotent.**
5. **Which methods are idempotent, and why does it matter?** **GET, HEAD, OPTIONS, PUT, DELETE. Clients and proxies may retry them safely after a network failure. Make POST retryable with an idempotency key.**
6. **When does the browser send a CORS preflight?** **For a cross-origin request with a non-simple method (e.g. PUT/DELETE), a non-safelisted header (e.g. Authorization), or a Content-Type outside form-urlencoded, multipart/form-data and text/plain, so any JSON request.**
7. **Does CORS protect your server?** **No. It's enforced by browsers and only stops JavaScript from reading responses; simple requests still execute on the server. Use auth and CSRF protection.**
8. **Why can't you use `Access-Control-Allow-Origin: *` with cookies, and why add `Vary: Origin`?** **Credentialed requests require an explicit origin. When you echo origins dynamically, `Vary: Origin` stops caches from serving one origin's CORS headers to another.**
9. **401 vs 403?** **401: not authenticated (missing or invalid credentials). 403: authenticated but not permitted.**
10. **502 vs 504?** **Both come from a proxy. 502: the upstream returned an invalid response or the connection failed. 504: the upstream didn't respond within the timeout.**
11. **Walk through ETag revalidation.** **The server sends `ETag`; the client later sends `If-None-Match` with it; if the version still matches, the server returns 304 with no body and the client uses its cache, otherwise 200 with the new body and ETag.**
12. **`no-cache` vs `no-store`?** **`no-cache` allows storing but requires revalidation before each use; `no-store` forbids storing at all.**
13. **Why might an app behind an ALB return random 502s?** **The app's keep-alive timeout (Node default 5 s) is shorter than the ALB's idle timeout (60 s), so the ALB reuses a connection the app just closed. Set the app's keepAliveTimeout higher than the LB's.**
14. **What is the multipart boundary for?** **It separates the parts (fields and files) of a `multipart/form-data` body so binary data can be sent without escaping.**
15. **How do you send a 2 GB file without running out of memory?** **Stream it (`pipeline(createReadStream(file), res)`), which respects backpressure and sends chunks as the client can receive them.**
16. ➕ **Your Express app sits behind an HTTP/2 load balancer. Which HTTP version does it receive, and why is that fine?** **HTTP/1.1. The LB terminates h2 (negotiated with ALPN) and forwards over pooled keep-alive connections; h2's gains matter on the long client link, not the short LB-to-app hop. Make sure the proxy uses HTTP/1.1 keep-alive upstream (Nginx defaults to 1.0).**
17. ➕ **Why can a gRPC service behind an L4 load balancer end up using only one replica?** **gRPC multiplexes all calls over one long-lived HTTP/2 connection, and an L4 balancer balances connections, not requests. Use an L7 balancer or client-side balancing.**
18. ➕ **The API is slow for one customer. How do you find which hop is slow?** **`curl -w` with namelookup, connect, appconnect and starttransfer times; DevTools Timing (Stalled vs Waiting) plus a `Server-Timing` header; a sanitized HAR file; `--resolve` to hit individual servers.**
19. ➕ **Why must a magic-login link not log the user in on GET?** **GET is safe by definition, so email scanners, link previews and prefetchers follow it and burn the one-time token. The GET renders a button; the POST consumes the token.**
20. ➕ **How do you prevent lost updates in a REST API?** **Return an ETag derived from a version column; require `If-Match` on writes (428 if missing); do the check inside the `UPDATE ... WHERE version = $2`; return 412 if no row matched.**
21. ➕ **Why is `Cache-Control: private` your responsibility with cookie sessions?** **RFC 9111 stops shared caches from reusing responses to requests with `Authorization`, but not with cookies. A personalised cookie-authenticated GET would otherwise be cached by the CDN and served to other users.**
22. ➕ **What is web cache poisoning via an unkeyed header?** **The app builds a cacheable response from a header the cache doesn't key on (e.g. `X-Forwarded-Host`), so one attacker request stores a malicious variant that every user then receives.**
23. ➕ **What does `app.set('trust proxy', true)` get wrong?** **It trusts every hop, so `req.ip` becomes the leftmost `X-Forwarded-For` entry, which the client controls. Set the exact hop count or the proxies' addresses.**
24. ➕ **How does password-reset poisoning work, and how do you prevent it?** **The attacker requests a reset for the victim with a forged `Host`; the app builds the link from it, so the victim's email points to the attacker's domain with a valid token. Build links from a configured base URL and reject unknown hosts at the proxy.**
25. ➕ **Which outbound failures can you retry for a non-idempotent POST?** **Only those where the request provably never reached the server: DNS failures, connection refused, connect timeouts, and 429/503 rejections. After ECONNRESET or a response timeout, retry only with an idempotency key.**
26. ➕ **What is slowloris and what stops it?** **Many connections sending headers extremely slowly to tie up the server. Header and request deadlines (Node's `headersTimeout`, `requestTimeout`) and a buffering reverse proxy in front.**
27. ➕ **State the timeout-alignment rule.** **Request timeouts shrink as you go deeper (client > proxy > app budget > DB and outbound calls), so each layer fails before its caller does; idle keep-alive timeouts grow as you go deeper.**
28. ➕ **Why is TLS 1.3 0-RTT dangerous?** **Early data can be replayed by an attacker. Only accept it for safe, idempotent requests and answer others with 425 Too Early.**
29. ➕ **A site works in Chrome, but Node clients fail with "unable to verify the first certificate". Why?** **The server sends only the leaf certificate. Browsers fill in the missing intermediate themselves; Node doesn't. Serve the full chain (`fullchain.pem`).**
30. ➕ **Why do certificate outages still happen with automated renewal, and what do you monitor?** **Renewals fail silently (broken challenge, server not reloaded) and lifetimes are shrinking toward 47 days. Monitor the certificate actually served on every host and instance, including intermediates, and alert weeks before expiry.**
