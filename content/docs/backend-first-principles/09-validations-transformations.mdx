This lesson is less about theory and more about **a set of rules to keep in mind while designing APIs**, mostly for **data integrity and security**. The core idea fits in one sentence: **check and normalize every piece of client input at the entry point, before any real logic runs.**

## 1. Where validation lives: the three layers 🎓

A typical backend splits a request's work into layers:

| Layer | Responsibility |
|---|---|
| **Controller** | Everything HTTP: reading the request, **validating input**, choosing status codes (success or error), shaping the response format. Calls the service. |
| **Service** | Business logic for the API: may call one or more repository methods, send notifications or emails, call webhooks … |
| **Repository** | Talking to persistent storage: queries, inserts, deletes, in Postgres, Redis or any other store |

**Why split controller and service?** So HTTP concerns (status codes, input format, validation) stay in one layer and the business logic doesn't care whether it was called from HTTP, a queue or a CLI.

### The exact spot

<Mermaid chart={`flowchart LR
  C["Client<br/>JSON body, query, path params, headers"] --> R["Route matching"]
  R --> V["Validation + transformation pipeline"]
  V -->|"invalid"| E["400 Bad Request<br/>list of field errors"]
  V -->|"valid, typed, normalized"| CT["Controller logic"]
  CT --> S["Service"]
  S --> RP["Repository"]
  RP --> DB[(Database)]`} />

After the router has matched the route and picked the controller method, and **before any significant logic runs** (before the service is called, before the database is touched), the request goes through the **validation and transformation pipeline**.

What gets validated: **everything the client controls**. The JSON body, **query parameters**, **path parameters**, **headers**.

## 2. What validation does, and why at the entry point 🎓

### The mechanism
The pipeline is usually a **middleware or a reusable utility** that you give a **schema** for each API. Take a requirement: the body must contain a `name` that is a string of **5 to 100 characters**. The pipeline checks in layers and stops with a clear error at the first failure for that field:

<Mermaid chart={`flowchart TD
  A{"Is name present?"} -->|"no"| E1["400: name is required"]
  A -->|"yes"| B{"Is it a string?"}
  B -->|"no, e.g. an array or boolean"| E2["400: expected string, received boolean"]
  B -->|"yes"| C{"Length 5 to 100?"}
  C -->|"too short / too long"| E3["400: length must be 5 to 100"]
  C -->|"yes"| OK["Pass to controller"]`} />

You can make the schema as strict as you need; this is just the basic idea.

### The problem it prevents (the lesson's example)
Suppose there's **no validation** and a client sends `name: 0` (a number) to a "create book" API:

1. The controller passes it to the service, the service to the repository.
2. The repository runs an `INSERT` into the `books` table.
3. The column was defined as `name TEXT NOT NULL`. Postgres checks data types and **rejects the insert**.
4. The error bubbles up as an unexpected exception, and the client gets **500 Internal Server Error**: "something went wrong on our side".

That's a terrible experience for a simple form, and it's **wrong**: the client made the mistake, not the server. With validation at the entry point, the same request gets **400 Bad Request** with a message saying what to fix, and nothing deeper ever runs.

**First-principles reason:** every layer below the controller is written assuming its inputs have a known shape. Validating once at the boundary turns "any bytes from the internet" into "data that satisfies our invariants", so the system never enters an **unexpected state**.

> 🔧 **Edge case: sometimes it's worse than a 500.** Whether `0` fails depends on the driver and column type. `node-postgres` sends parameters as text, so `0` inserted into a `TEXT` column becomes the string `"0"` and **succeeds silently**: bad data is now stored. Going the other way (a string into an `INTEGER` column) fails with `invalid input syntax for type integer`. Silent coercion is the stronger argument for validating at the edge: the database can't catch what it can legally convert.

## 4. The three types of validation 🎓

These aren't strict categories, but they're the ones you'll meet most often.

| Type | Question it asks | Examples from the lesson |
|---|---|---|
| **Syntactic** | Does the value have the right **structure**? | Email = local part + `@` + domain + TLD. Phone = country code + the right number of digits for that country. Date in `YYYY-MM-DD` |
| **Semantic** | Does the value **make sense**? | Date of birth can't be in the **future**. Age `365` is impossible (at least for now) |
| **Type** | Is it the right **data type**? | string, number, boolean, array, nested object (whose fields are again typed) |

🔧 OWASP uses the same split: **syntactic** validation enforces the format of structured fields, **semantic** validation enforces correctness in the business context (e.g. a start date before an end date). It also recommends **allowlists** (define exactly what's allowed) over denylists (try to list what's bad).

## 5. Transformation 🎓

### The problem
A paginated API: `GET /bookmarks?page=2&limit=20`. The rules:
- `page` is a **number**, greater than 0 and less than 500;
- `limit` is a **number**, greater than 0 and less than 10,000 (never return more than that at once).

But **every query-parameter value reaches the server as a string**. A query string is just text in the URL; it has no types. So the server receives `page: "2"` and `limit: "20"`, and the very first rule (*must be a number*) fails. The client did nothing wrong.

### The mechanism
It's the **server's** job to **cast** (force a value of one type into another) `"2"` → `2` **before** the validation rules run. That step is a **transformation**: changing data into the shape the server expects.

Transformation can also run **after** validation, e.g. normalizing a valid email to lower case.

<Mermaid chart={`flowchart LR
  Q["?page=2#amp;limit=20<br/>page: string 2, limit: string 20"] --> T1["Transform: cast to number"]
  T1 --> V["Validate: integer, range"]
  V --> T2["Transform: defaults, normalize"]
  T2 --> H["Controller gets page: 2, limit: 20 as numbers"]`} />

**Why put validation and transformation in one pipeline:** all knowledge about **input data** lives in one place. You don't have to search the codebase for what an API requires or what was done to the data before the business logic saw it.

## 6. What the remaining demos show 🎓

Each demo calls an endpoint first with an **empty body**. A nice side effect: **validation errors act as documentation**. Even without API docs, the error list tells a client which fields exist and what they must contain.

### Semantic
- Required: `dateOfBirth` and `age` (the empty body says age expected a number, received nothing).
- `1995-06-12` and age `43` → success, and the server echoes the values.
- Change the year to **2026** → "**date of birth cannot be in the future**".
- Age **430** → "**number must be less than or equal to 120**". The accepted range is **1 to 120** (a one-year-old won't call the API, but the rule is about plausibility).

### Complex (cross-field)
- Fields: `password`, `passwordConfirmation`, `married`.
- Two different passwords → "**passwords don't match**" on `passwordConfirmation`, and "**must contain at least 8 characters**" on `password`.
- Fix both → success.
- Set `married: true` → "**partner name is required when married is true**". Add `partner` → success.
- Called "complex" because the rules **depend on other fields**: two fields must be equal; one field is **conditionally required** based on another.

### Transformation
- Send an email in **mixed case**, a phone **without the leading `+`**, and a date in some format.
- The response shows the email **lower-cased**, the phone **with `+` prepended**, and the date **reformatted**. The server reshaped the data for the service layer's needs before using it.

### Type
- Fields: `stringField`, `numberField`, `arrayField`, `booleanField`.
- Send strings everywhere → "expected number / array / boolean, received string".
- Fix to `10`, an array `[1, 2]`, and `false` → a new error: **array element 0 expected string**. Element-level rules apply too.
- Use `["1", "2"]` → success.

## 7. 🔧 Going deeper: implementing the pipeline in Node.js

### A reusable Express middleware with Zod

```ts title="validate.ts"
import { z, ZodType } from 'zod';
import type { Request, Response, NextFunction } from 'express';

type Schemas = { body?: ZodType; query?: ZodType; params?: ZodType; headers?: ZodType };

export const validate = (schemas: Schemas) => (req: Request, res: Response, next: NextFunction) => {
  const issues: { location: string; path: string; message: string }[] = [];
  const valid: Record<string, unknown> = {};

  for (const location of ['params', 'query', 'body', 'headers'] as const) {
    const schema = schemas[location];
    if (!schema) continue;
    const result = schema.safeParse(req[location]);          // collects ALL errors, doesn't throw
    if (result.success) valid[location] = result.data;       // the TRANSFORMED data
    else for (const i of result.error.issues)
      issues.push({ location, path: i.path.join('.'), message: i.message });
  }

  if (issues.length) return res.status(400).json({ error: 'ValidationError', issues });
  (req as any).valid = valid;   // handlers read req.valid.query etc. (Express 5's req.query is read-only)
  next();
};
```

### The lesson's schemas, written out

```ts title="schemas.ts"
import { z } from 'zod';

// Syntactic
const isRealDate = (s: string) => {
  const d = new Date(`${s}T00:00:00Z`);
  return !Number.isNaN(d.getTime()) && d.toISOString().slice(0, 10) === s;  // rejects 2025-02-30
};
export const syntactic = z.object({
  email: z.string().email(),
  phone: z.string().regex(/^\+?[1-9]\d{7,14}$/, 'Invalid phone number'),   // E.164-style: up to 15 digits
  date:  z.string().regex(/^\d{4}-\d{2}-\d{2}$/).refine(isRealDate, 'Invalid date'),
});

// Semantic: evaluate "now" at request time, not when the module loads
export const semantic = z.object({
  dateOfBirth: z.coerce.date().refine(d => d <= new Date(), 'Date of birth cannot be in the future'),
  age: z.number().int().min(1).max(120),
});

// Complex / cross-field
export const signup = z.object({
  password: z.string().min(8),
  passwordConfirmation: z.string(),
  married: z.boolean(),
  partner: z.string().trim().min(1).optional(),
})
  .refine(d => d.password === d.passwordConfirmation,
          { message: "Passwords don't match", path: ['passwordConfirmation'] })
  .refine(d => !d.married || !!d.partner,
          { message: 'Partner name is required when married is true', path: ['partner'] });

// Transformation
export const contact = z.object({
  email: z.string().trim().toLowerCase().email(),
  phone: z.string().trim().transform(p => (p.startsWith('+') ? p : `+${p}`)),
  date:  z.coerce.date().transform(d => d.toISOString()),
});

// Type
export const types = z.object({
  stringField: z.string(),
  numberField: z.number(),
  arrayField: z.array(z.string()),
  booleanField: z.boolean(),
});

// Query params: cast first (strings → numbers), then range-check, with defaults
export const pagination = z.object({
  page:  z.coerce.number().int().min(1).max(500).default(1),
  limit: z.coerce.number().int().min(1).max(10_000).default(20),
});
```

```ts title="routes.ts"
app.get('/bookmarks', validate({ query: pagination }), async (req, res) => {
  const { page, limit } = (req as any).valid.query as z.infer<typeof pagination>; // numbers now
  res.json(await bookmarkService.list({ page, limit }));
});
```

## 8. 🔧 Going deeper: edge cases worth engineering for

**Coercion traps**
- `z.coerce.boolean()` uses `Boolean(input)`, so the string `"false"` becomes **`true`** (any non-empty string is truthy). Parse booleans from query strings explicitly (`z.enum(['true','false']).transform(v => v === 'true')`), or use Zod 4's `z.stringbool()`.
- `z.coerce.number()` turns `""` into `0` and `"  "` into `0`; decide whether an empty param means "missing" or "zero".
- Repeated query keys (`?tag=a&tag=b`) arrive as an **array**, a single one as a **string**. Normalize with `z.union([z.string(), z.array(z.string())]).transform(v => [v].flat())`.

**Unknown fields and mass assignment**
- By default Zod's `z.object` **strips** unknown keys. That matters: if a sign-up body includes `"role": "admin"` and your code does `db.user.create({ data: req.body })`, unvalidated extra fields go straight into the DB. Only ever pass **parsed** data to the service.
- Use `z.strictObject` (or NestJS `forbidNonWhitelisted`) if you'd rather reject unknown fields than drop them silently.

**Normalization choices**
- Lower-casing emails: technically the local part can be case-sensitive, but in practice nearly every provider treats it case-insensitively, so normalizing (and a unique index on the normalized value) prevents duplicate accounts like `Asha@x.com` and `asha@x.com`.
- **Trim** strings before length checks, or `"     "` passes a min-length rule.
- Dates: agree on **ISO 8601** and store **UTC**. A date-of-birth is a calendar date with no time zone; don't turn it into a midnight timestamp that shifts by a day in another zone.
- Phone numbers: store in **E.164** (`+` country code + number, at most 15 digits). A library like `libphonenumber-js` validates per-country lengths, which a regex can't.

**Cross-field refinements**
- In Zod, an object-level `.refine` only runs once every field is individually valid. So "passwords don't match" won't appear in the same response as "password too short". That's often acceptable; if not, use `superRefine` on a looser schema.

**Status codes and limits**
- `400 Bad Request` is the common choice for validation failures. Some APIs use `422 Unprocessable Content` for "well-formed JSON, invalid values" and keep 400 for malformed syntax. Pick one and be consistent.
- Cap the **body size** (`express.json({ limit })`), string lengths and array lengths. A schema without maximums still lets a client send a 50 MB string.

**Defence in depth**
- Validation at the edge doesn't replace **database constraints**. Keep `NOT NULL`, `CHECK (age BETWEEN 1 AND 120)`, `UNIQUE` and foreign keys: they protect you from bugs, scripts and other services that bypass your API.
- Validation isn't **output encoding**. A perfectly valid string can still be dangerous in HTML or SQL; use parameterized queries and escape on output.

### ReDoS: when the validator becomes the attack ➕

The schemas above lean on regular expressions (phone, date, email). A badly written regex turns validation, the thing meant to protect the server, into a way to stop it.

#### How one request can pin a CPU ➕

**Problem.** A request with a 40-character string in one field makes the server stop responding for seconds or minutes.

**Why it happens (first principles).** JavaScript's regex engine is a **backtracking** engine. When a pattern has ambiguous ways to match the same text, typically **nested quantifiers** like `(a+)+` or overlapping alternatives like `(a|a)*`, and the input almost matches but fails at the end, the engine tries every way of splitting the input before giving up. The number of splits grows **exponentially** with input length. And Node runs your JavaScript on one thread, so while one regex backtracks, every other request waits.

```ts title="redos-demo.ts (don't ship this)"
const bad = /^(\w+\s?)*$/;                    // nested quantifier: \w+ inside (...)*
const input = 'a'.repeat(30) + '!';            // almost matches, fails on the last char
console.time('regex');
bad.test(input);                               // grows ~2x per extra 'a': seconds at ~30 chars
console.timeEnd('regex');
```

**Edge cases.** This isn't only about hand-written patterns. Library validators have shipped vulnerable regexes too: Zod versions before 3.22.3 had a ReDoS in their email regex (CVE-2023-4316). Keep validation libraries updated like any other security dependency.

#### Defences ➕

**Mechanism.** Remove either the ambiguity or the attacker's control of input size:
1. **Cap the length first, and stop there if it fails.** A 40-character limit makes even a poor pattern bounded. Note that Zod runs **all** checks on a string by default and collects every issue, so `.max(64).regex(...)` still runs the regex on a 1 MB string. Put the regex behind `.pipe()`, which only runs the second schema when the first one passed.
2. **Write unambiguous patterns.** Anchor them, avoid quantified groups that contain quantifiers, and make alternatives mutually exclusive. `^\+?[1-9]\d{7,14}$` from section 7 is safe: each position can match only one way.
3. **Lint for it.** Tools like `safe-regex` or ESLint's `regexp` plugin flag super-linear patterns in CI.
4. **Use a linear-time engine** for patterns you don't control (for example user-defined search filters). `re2` (Google's RE2 via a Node binding) guarantees linear time by not supporting backreferences and lookarounds.
5. **Prefer parsers to regexes** for complex formats: a URL parser (`new URL()`), `libphonenumber-js` for phones, a date library for dates.

```ts title="safe-order.ts"
import { z } from 'zod';
import RE2 from 're2';

export const Slug = z.string().max(64)
  .pipe(z.string().regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/));   // regex never sees > 64 chars, and is unambiguous

const userPattern = new RE2(req.valid.query.pattern);   // user-supplied pattern: linear time, no catastrophic backtracking
```

**Edge cases.** Body-size limits don't help here: the malicious input is tiny. Only per-field length limits and safe patterns do. If you can't fix a pattern quickly, run the check with a timeout in a worker thread, so at worst one worker is stuck rather than the event loop.

## 9. Unicode: strings that look equal but aren't ➕

Section 8's normalization advice (trim, lower-case) assumes one character is one character. With Unicode it often isn't, and that breaks length rules, uniqueness checks and what users see.

### Normalization forms: same text, different bytes ➕

**Problem.** A user signs up as `José` on a phone. Later, logging in from a laptop, they type `José` and it doesn't match. A unique index on `username` happily accepts both spellings as different users, even though they look identical on screen.

**Why it happens (first principles).** Unicode can represent many characters in more than one way. `é` can be one code point (U+00E9, precomposed) or two (`e` + U+0301, a combining acute accent). They look identical and are **canonically equivalent**, but their bytes differ, so `===`, hashes and database indexes treat them as different strings. Which form arrives depends on the operating system, keyboard and app the text was typed in.

**Mechanism.** **Normalize** to one form at the boundary, before validating length or checking uniqueness:
- **NFC** (canonical composition) changes no visible meaning. Use it for names, free text and anything you display.
- **NFKC** also folds **compatibility** variants: the ligature `ﬁ` becomes `fi`, fullwidth `Ａ` becomes `A`, superscript `⁵` becomes `5`. That's useful for identifiers, but it changes meaning in some text, and the Unicode standard warns against applying it blindly to arbitrary text.

Normalization is **idempotent** (normalizing twice equals normalizing once), so it's safe to do it at every boundary.

```ts title="unicode-schemas.ts"
import { z } from 'zod';

export const DisplayName = z.string()
  .transform(s => s.normalize('NFC').trim())
  .pipe(z.string().min(1).max(50));           // validate AFTER normalizing

export const Username = z.string()
  .transform(s => s.normalize('NFKC').toLowerCase().trim())
  .pipe(z.string().regex(/^[\p{L}\p{Nd}_]{3,30}$/u, 'Letters, digits and _ only'));
```

**Edge cases.** Normalize **stored** data the same way, or old rows never match new input; a one-off backfill plus a `CHECK` constraint keeps it consistent. Never normalize passwords differently at sign-up and at login.

### Length: code units, code points or characters ➕

**Problem.** A "max 10 characters" rule rejects a 6-emoji name, and a database column accepts a name the API rejected.

**Why it happens.** "Length" has three meanings:
- JavaScript's `.length` counts **UTF-16 code units**: `'😀'.length` is 2;
- spreading a string (`[...s].length`) counts **code points**, which is what Postgres `varchar(n)` and `char_length()` count;
- users count **graphemes** (what looks like one character): a family emoji or a flag is several code points joined together but displays as one.

**Mechanism.** Pick the unit that matches the purpose, and make the API and the database agree:
- **storage limits:** count code points, matching `varchar(n)`;
- **UI-facing limits** ("max 10 characters"): count graphemes with `Intl.Segmenter`;
- **byte limits** (a header, a key in another system): count UTF-8 bytes with `Buffer.byteLength(s, 'utf8')`.

```ts title="length.ts"
const graphemes = (s: string) =>
  [...new Intl.Segmenter('en', { granularity: 'grapheme' }).segment(s)].length;

export const Bio = z.string()
  .transform(s => s.normalize('NFC'))
  .refine(s => [...s].length <= 500, 'Too long')          // matches bio varchar(500)
  .refine(s => graphemes(s) >= 1, 'Required');
```

**Edge cases.** Zod's `.max()` uses `.length`, so it counts UTF-16 code units: an emoji-heavy string hits the limit early. That's the safe direction for a database limit, but surprising to users; document the unit.

### Usernames and lookalikes: case folding, confusables, mixed scripts ➕

**Problem.** Someone registers `pаypal` with a Cyrillic `а` (U+0430) and impersonates the real `paypal` account. Another registers `ADMIN` when `admin` exists.

**Why it happens.** Different code points can render the same (**confusables**), and case rules are language-specific: `'I'.toLowerCase()` is `i` in English but the correct lower case is dotless `ı` in Turkish. Normalization doesn't fix either, because the strings really are different characters.

**Mechanism.** For identifiers other people see (usernames, handles, workspace slugs):
1. Use a defined profile for identifiers rather than ad-hoc rules. The IETF **PRECIS** framework (RFC 8264, with username profiles in RFC 8265) restricts identifiers to letters and digits and specifies case mapping and normalization.
2. Compare a **case-folded, normalized** form for uniqueness, and store it in its own indexed column.
3. Detect confusables with Unicode **UTS #39**: compute `skeleton(x)`, a form where lookalike characters map to one prototype; two strings are confusable if their skeletons are equal. Store the skeleton with a unique index to block lookalike registrations.
4. Reject **mixed-script** identifiers (Latin mixed with Cyrillic) unless you have a reason to allow them, or restrict to a single script per identifier.

```sql title="usernames.sql"
CREATE TABLE users (
  id            uuid PRIMARY KEY,
  username      text NOT NULL,                 -- as the user typed it (display)
  username_key  text NOT NULL UNIQUE,          -- NFKC + case-folded (login and uniqueness)
  username_skel text NOT NULL UNIQUE           -- UTS #39 skeleton (blocks lookalikes)
);
```

**Edge cases.** Use locale-independent lower-casing (`toLowerCase()`, never `toLocaleLowerCase()` with a user's locale) for keys, or the same name maps to different keys on different servers. Skeleton matching is deliberately over-inclusive, so expect some false positives and give users a clear message.

### Invisible and control characters ➕

**Problem.** Two usernames look identical but one contains a zero-width space. A product name contains a right-to-left override that makes `exe.pdf` display as something else. An insert fails with a database error.

**Why it happens.** Unicode includes characters that render as nothing (zero-width space U+200B, zero-width joiner U+200D), **bidirectional controls** that reorder how text displays (U+202E right-to-left override, the trick behind the "Trojan Source" attacks), and C0 control characters including the NUL byte. Postgres `text` can't store NUL at all, and `jsonb` rejects `\u0000` for the same reason, so a NUL that reaches the database becomes a 500.

**Mechanism.** For single-line fields, use an allowlist of character categories (the OWASP Input Validation Cheat Sheet recommends exactly this): letters, marks, numbers, punctuation, symbols and the plain space. Reject everything in the "Other" categories (`\p{C}`: controls, format characters, unassigned) except where you have a reason to allow them.

```ts title="no-invisible.ts"
const SINGLE_LINE = /^[\p{L}\p{M}\p{N}\p{P}\p{S}\p{Zs}]*$/u;     // no \p{C}: controls, format chars, NUL
const MULTI_LINE  = /^[\p{L}\p{M}\p{N}\p{P}\p{S}\p{Zs}\n\t]*$/u;

export const ProductName = z.string().max(120)
  .transform(s => s.normalize('NFC').trim())
  .pipe(z.string().min(1).regex(SINGLE_LINE, 'Contains invisible or control characters'));
```

**Edge cases.** Some format characters are legitimate: the zero-width joiner builds many emoji sequences, and some scripts need U+200C or U+200D to render correctly. For free text, allow ZWJ and ZWNJ but strip or reject bidi overrides; for identifiers, reject all of them.

## 10. Frontend validation vs backend validation 🎓

**The mistake:** treating frontend form validation as a replacement for backend validation.

| | Frontend validation | Backend validation |
|---|---|---|
| **Purpose** | **User experience**: immediate feedback in the form | **Security and data integrity** |
| **Can it be bypassed?** | Yes, trivially | No, it's the gate |
| **Required?** | Nice to have | **Mandatory, for every API** |

**Why the backend can't rely on it:** your server has many clients. A polished web app may validate perfectly, but someone can call the API directly with **Postman or Insomnia** (as the demos did), a script, or a modified client. There's **no frontend at all** in that path. If the backend depended on frontend checks, it would break as soon as the client changed.

So design server-side validation to be **as strict and specific as possible**, without thinking about what the client checks.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant U as User
  participant F as Web form
  participant P as Postman / script
  participant API as API (server validation)
  U->>F: type bad email
  F-->>U: inline error, no request sent
  U->>F: fix email, submit
  F->>API: POST valid payload
  API-->>F: 200
  P->>API: POST anything at all
  API-->>P: 400 with field errors`} />

**What the final demo shows:** the same endpoints have a small frontend. With a bad email, pressing submit **sends no API request** at all; the browser's form validation flags the field. After fixing it (a proper `…@gmail.com`), submit sends the request, the network panel shows the payload, and the server answers **200**. The frontend gives instant feedback; the backend enforces the rules.

🔧 **Share one schema** between frontend and backend (e.g. a Zod schema in a shared package used by the React form and the API). The UX checks and the security checks then can't drift apart, but the backend still runs its own copy on every request.

## 11. Validating at every trust boundary, not only HTTP requests ➕

The frontend isn't the only source of data your code shouldn't trust. The same rule ("parse at the boundary, then trust the typed result") applies wherever bytes enter the process from somewhere you don't control in that moment.

<Mermaid chart={`flowchart LR
  H["HTTP requests"] --> B{"Boundary:<br/>parse with a schema"}
  Q["Queue messages and events"] --> B
  T["Third-party API responses"] --> B
  S["Your own stored JSON and cache"] --> B
  B -->|"typed, trusted"| L["Business logic"]
  L --> O{"Output boundary:<br/>response schema"}
  O --> R["HTTP response"]`} />

Three boundaries already have their own lessons, so only pointers here: **configuration** is validated at startup ([lesson 17](/docs/backend-first-principles/17-configuration-management)), **webhooks** are signature-checked over the raw body before parsing ([lesson 30](/docs/backend-first-principles/30-webhooks)), and **uploaded files** are checked by size and magic bytes, never by the client's `Content-Type` ([lesson 24](/docs/backend-first-principles/24-object-storage-part-1)).

### Queue and event payloads ➕

**Problem.** A producer deploys a change that renames `userId` to `user_id`. Every consumer job now throws `Cannot read properties of undefined` deep in a handler, the queue retries each one several times, and the failures look like infrastructure problems.

**Why it happens.** A message on a queue is **serialized input from another process**, written by a different deploy, possibly hours ago. TypeScript types on the consumer side are a compile-time promise about data that was never checked at runtime.

**Mechanism.** Parse every message against a schema at the start of the handler, and treat a schema failure differently from a transient failure: a malformed message (a **poison message**) will fail the same way on every retry, so send it straight to a **dead-letter queue** instead of retrying.

```ts title="worker.ts (BullMQ)"
import { Worker, UnrecoverableError } from 'bullmq';
import { z } from 'zod';

const SendWelcome = z.object({
  v: z.literal(1),
  userId: z.string().uuid(),
  locale: z.enum(['en', 'hi', 'de']).default('en'),
});

new Worker('emails', async (job) => {
  const parsed = SendWelcome.safeParse(job.data);
  if (!parsed.success) {
    // Retrying won't fix bad data: fail permanently and keep the payload for inspection
    throw new UnrecoverableError(`invalid payload: ${parsed.error.issues.map(i => i.path.join('.')).join(', ')}`);
  }
  await sendWelcomeEmail(parsed.data);   // typed and trusted from here on
}, { connection });
```

**Edge cases.** BullMQ has no separate dead-letter queue: `UnrecoverableError` moves the job straight to the **failed** set, which plays that role (SQS and RabbitMQ have real DLQs). Put a version field in the payload and keep accepting the previous version during deploys ([lesson 7](/docs/backend-first-principles/07-serialization-deserialization) covers versioned payloads). Alert on dead-lettered messages: a sudden spike almost always means a producer and consumer disagree after a deploy. Background-job mechanics (retries, idempotency) are in [lesson 14](/docs/backend-first-principles/14-task-queues-background-jobs).

### Responses from third-party APIs ➕

**Problem.** A payment provider starts returning `amount` as a string instead of a number for one currency. Your code adds it to a total and stores `"100" + 50 = "10050"`.

**Why it happens.** An external API is a boundary you don't control. Its documentation describes intent, not every response you'll get: fields go missing in error cases, types change between versions, and enums gain values.

**Mechanism.** Validate the fields you **use** (not the entire response), be tolerant of additions, and convert failures into a clear, logged error at the integration edge instead of a confusing bug three layers later.

```ts title="payments-client.ts"
const ChargeResponse = z.object({
  id: z.string(),
  status: z.enum(['succeeded', 'pending', 'failed']).catch('pending'),   // unknown status: treat as pending, then reconcile
  amount: z.number().int().nonnegative(),                                 // minor units
}).passthrough();                                                         // keep fields we don't model

export async function getCharge(id: string) {
  const res = await fetch(`${BASE}/charges/${encodeURIComponent(id)}`, { signal: AbortSignal.timeout(5000) });
  if (!res.ok) throw new UpstreamError('payments', res.status);
  const parsed = ChargeResponse.safeParse(await res.json());
  if (!parsed.success) {
    logger.error({ issues: parsed.error.issues, chargeId: id }, 'payments response failed schema');
    throw new UpstreamError('payments', 502);
  }
  return parsed.data;
}
```

**Edge cases.** Decide per field whether to fail or degrade: a missing optional display field can default, but a malformed **amount** must stop the flow. Watch for silent fallbacks like `.catch()` hiding real changes; count them in metrics.

### Data you read back from your own storage ➕

**Problem.** A JSONB `settings` column has rows written by five past releases, some by a script and one by a hotfix that stored `"true"` instead of `true`. Code that assumes the current shape crashes for those users only.

**Why it happens.** The database checks a `jsonb` column only for being valid JSON. Caches (Redis), files and JSONB are the same as a queue: serialized data written by some past version of some program.

**Mechanism.** Parse semi-structured data with a schema **on read** (in the repository layer, so services get typed objects), with defaults for fields added later. Where possible, also constrain it in the database:

```sql title="settings-check.sql"
ALTER TABLE users ADD CONSTRAINT settings_shape CHECK (
  jsonb_typeof(settings) = 'object'
  AND (NOT settings ? 'darkMode' OR jsonb_typeof(settings -> 'darkMode') = 'boolean')
);
```

**Edge cases.** For a cache, treat a parse failure as a **miss**: delete the key and reload from the source of truth instead of returning an error. A `CHECK` constraint added later fails if existing rows violate it; clean the data first, or add it as `NOT VALID` and run `VALIDATE CONSTRAINT` after a backfill.

### Your own responses: output validation ➕

**Problem.** A refactor adds `passwordHash` to the user object returned by the repository, and every endpoint that returns a user now leaks it. Or a field that the contract says is always a string is sometimes `null`, and the mobile app crashes.

**Why it happens.** Input validation protects your server from clients. Nothing, by default, protects **clients** from your server: the response is whatever object the handler happened to build.

**Mechanism.** Give each endpoint a **response schema** and pass every response through it. An allowlist schema drops fields you didn't declare (stopping leaks) and fails loudly when the shape is wrong (stopping contract breaks). Fastify does this natively: a response schema is compiled into its serializer, which outputs only the declared properties and is faster than `JSON.stringify`. NestJS achieves the same with `ClassSerializerInterceptor` and `@Exclude()`/`@Expose()` on response DTOs. In Express, a small helper works:

```ts title="respond.ts"
const UserResponse = z.object({ id: z.string(), email: z.string().email(), name: z.string() });   // strips extras

export const send = <T extends z.ZodTypeAny>(res: Response, schema: T, data: unknown, status = 200) => {
  const result = schema.safeParse(data);
  if (!result.success) {
    logger.error({ issues: result.error.issues }, 'response failed its schema');   // our bug, not the client's
    return res.status(500).json({ error: 'InternalError' });
  }
  return res.status(status).json(result.data);
};

app.get('/users/:id', async (req, res) => send(res, UserResponse, await users.find(req.params.id)));
```

**Edge cases.** Parsing big responses costs CPU; if that matters, enforce the full check in development and tests and keep only field stripping in production. Generating these schemas from (or into) an OpenAPI document keeps docs and code in sync ([lesson 29](/docs/backend-first-principles/29-openapi)).

## 12. Recap 🎓

- Validation and transformation run at the **entry point**: after route matching, **before** the controller's logic, the service or the database.
- Validate **every input**: body, query, path params, headers.
- Without it, bad input becomes a **500** deep in the stack (or silently bad data); with it, the client gets a clear **400**.
- Types: **syntactic** (structure: email, phone, date), **semantic** (makes sense: no future birth dates, ages 1–120), **type** (string, number, boolean, array, object), plus **complex** cross-field rules.
- **Transformation** reshapes data: casting query strings to numbers, lower-casing emails, adding `+` to phones, formatting dates. Keep it in the same pipeline as validation.
- **Frontend validation is UX; backend validation is security and integrity.** Never skip the backend.
- ➕ **ReDoS:** backtracking regexes can take exponential time on tiny inputs. Cap length before the regex (with `.pipe()` in Zod), write unambiguous patterns, lint them, use RE2 for untrusted patterns.
- ➕ **Unicode:** normalize (NFC for text, NFKC for identifiers) before length and uniqueness checks; know which length unit you count; block lookalikes, mixed scripts and invisible or control characters in identifiers.
- ➕ **Every trust boundary** gets a schema: queue messages (poison messages fail permanently), third-party responses, stored JSONB and cache entries, and your **own responses** (output schemas stop leaks).

## Interview questions

1. **Where should input validation happen, and why there?** At the controller entry point, right after routing and before business logic, so every layer below can trust its inputs and errors are returned as 400 rather than surfacing as 500s.
2. **Syntactic vs semantic validation?** Syntactic checks structure (is this a valid email or date format). Semantic checks meaning in context (a birth date can't be in the future, start must precede end).
3. **Why does `?page=2` fail a "must be a number" rule, and what's the fix?** Query values always arrive as strings. Transform (cast) them to numbers before validating.
4. **What's a cross-field validation? Give two examples.** A rule involving several fields: password confirmation must equal password; partner is required when `married` is true.
5. **Why isn't frontend validation enough?** Anyone can call the API directly (Postman, curl, scripts). Frontend checks are for UX; backend checks are for security and integrity.
6. **What goes wrong with `z.coerce.boolean()` on query strings?** It uses JavaScript truthiness, so `"false"` becomes `true`. Parse the literal strings explicitly.
7. **How does validation help prevent mass-assignment bugs?** Parsing against a schema strips or rejects unknown fields like `role`, and only the parsed object is passed on.
8. **If you validate in the API, do you still need DB constraints?** Yes: defence in depth against bugs and other writers that bypass the API.
9. **400 or 422 for validation errors?** Either is defensible; 400 is most common, 422 signals well-formed but semantically invalid content. Be consistent and return per-field errors.
10. ➕ **How can a 40-character input take down a Node server?** A regex with nested quantifiers backtracks exponentially when the input almost matches, blocking the single JavaScript thread. Cap length before matching, avoid ambiguous patterns, or use a linear-time engine.
11. ➕ **Two usernames look identical but your unique index accepts both. Why?** They use different code point sequences (precomposed vs combining characters, or a Cyrillic lookalike). Normalize and case-fold into a key column, and compare UTS #39 skeletons to block confusables.
12. ➕ **What does `'😀'.length` return, and why does it matter for validation?** 2, because JavaScript counts UTF-16 code units. Postgres `varchar(n)` counts code points and users count graphemes, so pick the unit deliberately.
13. ➕ **A queue job fails schema validation. Should it be retried?** No. Bad data fails the same way every time; fail it permanently (dead-letter or failed set), keep the payload, and alert.
14. ➕ **Why validate your own API responses?** An allowlist response schema stops accidental leaks (like a new `passwordHash` field) and catches contract breaks before clients do.
