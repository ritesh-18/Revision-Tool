This is a short "set your expectations" lesson. It explains **how the whole learning journey is organised** and why it's ordered that way. The core idea: **learn the concept first, then the implementation, then put everything together in real projects.**

## 1. Phase 1: the story and philosophy of the backend 🎓

### What it is
This playlist tells the **story** of backend engineering: the philosophies behind it, the big questions it answers, how its internals work, and how the different components and machines **collaborate**.

### Why start here (first principles)
- Languages, runtimes, frameworks and libraries **abstract** a lot away. If you only ever see the abstraction, you don't know what problem it's solving, so you can't carry the knowledge to another stack.
- Seeing the **big picture of a production-grade backend** first means that later, when you see a framework feature, you recognise *which principle it implements*.
- The output of this phase is **language-agnostic skill**: knowledge that sits above any framework you use day to day.

## 2. Phase 2: implementation 🎓

### What it is
Once the foundations are clear and you can see the **common patterns** behind every backend, that's the right moment to look at **real code**: how each principle looks and works in practice.

- This is where you pick a **language and ecosystem**.
- The plan is **two versions**, **Node.js** and **Go**, because those are the two languages the author uses daily.
- It's a separate playlist. **Most videos in Phase 1 get a matching implementation video** in Phase 2.

### The lesson's example
A Phase 1 video on **databases** covers drivers, migrations and the related concepts in general. Its Phase 2 counterpart deep-dives on **Postgres** with a real driver:
- Node.js: **postgres.js** (the `postgres` package)
- Go: **pgx**

🔧 What that "concept → implementation" mapping looks like for one principle, connection pooling, in Python (the language of these notes, with **psycopg 3**) next to Go:

| Concept (Phase 1) | Python (psycopg 3) | Go (Phase 2) |
|---|---|---|
| Reuse a fixed set of DB connections instead of opening one per request | `AsyncConnectionPool(url, max_size=10)` | `pgxpool.New(ctx, url)` with `pool_max_conns` |
| Parameterised queries prevent SQL injection | `await conn.execute("select * from users where id = %s", (user_id,))` | `pool.Query(ctx, "select ... where id = $1", id)` |

The concept column never changes. Only the syntax column does, which is the whole point of the series.

## 3. Phase 3: production-level projects 🎓

### What it is
Everything comes together: the concepts, the language-specific deep dives and the philosophies. You build **several production-grade projects end to end**, following industry standards and best practices, and you can follow along.

### The promise
If you take the whole journey, internalise it and build the projects, you should be able to **call yourself a backend engineer** and build real systems:
- systems that **scale** from zero users to a million,
- systems that people can **maintain** over a long time.

## 4. 🔧 Going deeper: how to study this series

The lesson describes the structure; here is a practical way to use it.

1. **Per Phase 1 video, write down the problem first.** For each concept, answer: what breaks without it, and why? For example: "Without a connection pool, every request pays a TCP + auth handshake to Postgres and the DB runs out of connection slots."
2. **Build a tiny proof before the full implementation.** One file, no framework (e.g. a raw `asyncio` socket server or `http.server` for the HTTP lesson). It makes the abstraction visible.
3. **Then map it to your daily stack.** For a FastAPI reader: routing becomes path operations and `APIRouter`, validation becomes Pydantic models, middleware becomes ASGI middleware and dependencies (`Depends`), request context becomes `contextvars` or request-scoped dependencies.
4. **Keep one running project.** Add each concept to the same small API as you learn it. By the end of the series it becomes your own Phase 3 project.

### Going to the primary sources ➕

The loop above starts from a video and ends in your framework. Between the two sit the **primary sources** that both are built on: the specifications and the framework's own code. Reading them is what lets you settle "is this behaviour a bug or the standard?" without guessing.

#### Reading an RFC ➕

- **Problem:** blog posts and answers disagree (is `DELETE` with a body allowed? must a 405 include `Allow`?), and many repeat outdated rules.
- **Why it happens:** the protocols backends speak (HTTP, TLS, JSON, URIs, OAuth) are defined in **RFCs**, which get revised and replaced over the years. Secondary sources copy whichever version their author read.
- **Mechanism:** go to the current RFC and read it with three habits:
  1. **Check it's current.** The header of every RFC on rfc-editor.org shows **"Obsoleted by"** and **"Updated by"**. HTTP/1.1's semantics moved from RFC 2616 (1999) to RFCs 7230-7235 (2014) to **RFC 9110-9112** (2022); quoting 2616 today is quoting a dead document.
  2. **Read the requirement keywords literally.** Capitalised **MUST**, **SHOULD** and **MAY** have defined meanings (BCP 14: RFC 2119 and RFC 8174). MUST is an absolute requirement; SHOULD means "do it unless you have a good, understood reason not to"; MAY is truly optional. "The server SHOULD send `Retry-After`" and "the server MUST send `Allow`" are very different obligations.
  3. **Check the errata.** Mistakes found after publication are listed per RFC, and verified errata are effectively part of the text.
- **Implementation:** a quick way in, from the terminal:

```bash
# rfc-editor.org publishes each RFC's metadata as JSON: status, what it obsoletes, what replaced it, errata
curl -s https://www.rfc-editor.org/rfc/rfc9110.json | jq '{title, status, pub_date, obsoletes, obsoleted_by, updated_by, errata_url}'
# then read the section you need, e.g. "9.3.5 DELETE" or "15.5.6 405 Method Not Allowed"
```

- **Edge cases:** an RFC's **status** matters: "Proposed Standard" and "Internet Standard" are normative, "Informational" and "Experimental" are not, and an **Internet-Draft** (like the HTTP `QUERY` method) can still change completely. Real implementations also deviate from specs; when a browser or framework disagrees with the RFC, MDN's compatibility tables and the framework's issue tracker tell you what actually happens.

#### Reading the framework's source ➕

- **Problem:** the docs say what a framework does in the common case, not what happens at the edges (which middleware runs on a 404? does `@app.get` answer HEAD?). Experiments help, but reading the code gives a definite answer in minutes.
- **Why it works:** every framework feature is one of the universal components from Phase 1 implemented in plain code. Once you know what a router or a body parser must do, its source is short and readable.
- **Mechanism:** start from the public API you call and follow it down: find where it's defined, set a breakpoint, step through one real request.
- **Implementation:**

```bash
# where is it decided whether a GET route also answers HEAD?
grep -n '"HEAD"' .venv/Lib/site-packages/starlette/routing.py        # Starlette's Route adds HEAD to every GET route
grep -n "self.methods" .venv/Lib/site-packages/fastapi/routing.py    # FastAPI's APIRoute doesn't: HEAD on a GET path operation gets 405
# step through a real request with the debugger
uv run python -m pdb -m uvicorn app.main:app                         # or put breakpoint() in your handler, then `up` into the framework
```

```python
# or ask the framework itself, at runtime
import fastapi
import starlette

print(fastapi.__file__, fastapi.__version__)  # which copy is actually loaded
print(starlette.__file__, starlette.__version__)
```

- **Edge cases:** read the source of the **version you run** (`uv pip show fastapi starlette`, then that tag on GitHub), not `main`, which may already behave differently. Treat internals as internals: understanding them is the goal, depending on undocumented behaviour in your own code is not.

## Interview questions

1. **Why learn backend concepts before a framework?** **Frameworks abstract the concepts away. If you know the concept (e.g. pooling, routing, validation), you can recognise and reuse it in any stack instead of relearning everything per framework.**
2. **What does "language-agnostic" backend knowledge mean in practice?** **Knowing the problem and the mechanism (e.g. "parameterised queries keep data out of the SQL text") so that only the syntax changes when you switch from Python to Go.**
3. ➕ **Two sources disagree about an HTTP rule. How do you settle it?** **Find the current RFC (check "Obsoleted by"; HTTP semantics is RFC 9110, not 2616), read the MUST/SHOULD/MAY wording literally per RFC 2119/8174, check the errata, then check how real browsers or your framework actually behave.**
4. ➕ **How do you find out what your framework does in an edge case the docs don't cover?** **Read the source of the exact version you run (from your virtualenv's `site-packages` or that git tag) and step through one real request with a debugger.**
