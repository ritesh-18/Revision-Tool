## 1. Why a roadmap is needed 🎓

### What backend engineering actually is
Much more than a set of CRUD APIs. The author's definition: building **reliable, scalable, fault-tolerant and maintainable** codebases and **efficient systems**.

### The problem with how people learn it
1. **Too many resources, no order.** There are thousands of resources. How do you decide what to learn, prioritise, and see how the concepts connect? This is why it takes people **years**.
2. **Limited starting point.** Most people start from a narrow course (college, bootcamp, a short course) and fill the gaps by **trial and error** and help from colleagues. The author did the same: searching for resources, reading many backend books, and studying **hundreds of open-source codebases**. That's very time-consuming.
3. **The framework lens.** People learn backend *through* one framework (Express, Spring Boot, Ruby on Rails) and see every problem through that ecosystem, which leaves **blind spots**.
   - **The lesson's example:** you've used Rails for years, then your company migrates to **Go for performance**. How much of your knowledge transfers if you never understood the underlying systems?

### The solution
A list of videos built on the **foundational concepts** of backend systems, drawn from books and open-source codebases, in an order where each one builds on the previous ones.

## 2. How a request reaches the backend 🎓

**Covered:** a high-level view of how a request travels from the **browser** through network hops and **firewalls** over the internet to a backend on a remote **AWS** server, how the server responds, and what the response looks like. Goal: a vivid picture of how a client and a server communicate.

🔧 **Problem → mechanism:** the browser knows a name, the network routes by IP, and the app listens on a local port. **DNS** maps name to IP, a **firewall** decides which ports are reachable, and a **reverse proxy** forwards to the app. (Lesson 3 traces this in detail.)

## 3. HTTP 🎓

**Covered:** the role of HTTP and how communication is established; **raw HTTP messages**; **headers** (request, representation, general, security); **methods** (GET, POST, PUT, DELETE: when to use each, their semantics); the **CORS** flow, **simple vs preflighted** requests; **responses** and **status codes**; **HTTP caching** (ETags, max-age); **HTTP/1.1 vs 2 vs 3**; **content negotiation**; **persistent connections**; **compression** (gzip, deflate, br, and which is most common); **SSL/TLS and HTTPS**.

🔧 **Problem → mechanism:** two programs on different machines, written in different languages, must agree on how to ask for and return data. HTTP is a **shared, stateless, text-based (in 1.1) contract**: a method for intent, a path for the target, headers for metadata, a status code for the outcome.

## 4. Routing 🎓

**Covered:** how routing maps **URLs to server-side logic**, its link to HTTP methods; **path parameters** and **query parameters**; route types: **static, dynamic, nested, hierarchical, catch-all/wildcard, regex-based**; **API versioning** techniques, how to **deprecate** a version, industry practice; **route grouping** (for versioning, permissions, shared middleware); **securing** routes; **optimising route-matching performance**.

🔧 **Problem → mechanism:** one server, hundreds of endpoints. A router uses **method + path** as the key to pick a handler, extracting variable segments as parameters. Fast routers store routes in a **radix tree** so lookup cost depends on path length, not route count.

## 5. Serialization and deserialization 🎓

**Covered:**
- **Serialization:** before sending data over the network, the server converts it from native structures into a shared format. **Deserialization:** converting received data back into native structures.
- Why it's needed: **interoperability** between languages.
- Formats: **text** (JSON, XML) vs **binary** (Protobuf), performance differences, when to use which, and how different languages implement them.
- **JSON in depth:** structure; types (string, number, boolean, array, object); nested objects and collections; deserialising into native structures (a Python dict, a Go struct, a JS object).
- **Common errors:** missing or extra fields, `null` values, **date serialization and time-zone issues**, custom serialization.
- **Error handling:** invalid data, conversion errors, unknown fields.
- **Security:** injection attacks; **validate before deserialising** and use **JSON Schema** validation.
- **Performance:** compressing serialized data, dropping unnecessary fields, text vs binary.
- **The trade-off:** text is **readable** (you can inspect the payload), binary is **faster** but not human-readable.

🔧 **Problem → mechanism:** memory layouts differ between languages (a Go struct isn't a JS object), so you can't send raw memory. Both sides agree on a **wire format** and convert at the boundary.

🔧 **Edge case worth knowing now:** JSON has no date type and JS numbers lose precision above 2^53, so send dates as **ISO 8601 strings in UTC** and large IDs (e.g. Postgres `bigint`) as **strings**:

```ts
JSON.stringify({ at: new Date() });          // {"at":"2026-10-02T10:00:00.000Z"}, UTC, unambiguous
JSON.parse('{"id": 9007199254740993}').id;    // 9007199254740992, silently wrong
```

## 6. Authentication and authorization 🎓

**Covered:** why we need them; **stateful vs stateless** authentication; **basic** auth, **bearer tokens**; **sessions, JWTs, cookies**; **OAuth** and **OpenID Connect**; **API keys**; **multi-factor** authentication; **salting, hashing** and cryptographic techniques; **ABAC, RBAC, ReBAC**; security best practices (securing cookies, avoiding **CSRF, XSS, MITM**); **audit logging** (auth events, failed logins, privilege escalation, access to sensitive resources); **obscuring auth error messages** to avoid leaking information; **consistent responses** across failure modes, **rate limiting and account lockout**; and **timing attacks**.

### The lesson's timing-attack example
An error for a **wrong password** can take slightly **longer** than an error for an **unknown username**, because checking a password requires a slow **hash** computation. An attacker measuring those tiny differences can learn which usernames are valid. It's hard to exploit, but you don't want to leave any hole.

🔧 **Mechanism that removes the timing signal:** do the **same expensive work in both branches**, and compare secrets in constant time:

```ts title="login.ts"
import bcrypt from 'bcrypt';
import { timingSafeEqual } from 'node:crypto';

const DUMMY_HASH = await bcrypt.hash('not-a-real-password', 12);   // computed once at startup

export async function login(email: string, password: string) {
  const user = await users.findByEmail(email.toLowerCase());
  // always run bcrypt, even when the user doesn't exist → same timing either way
  const ok = await bcrypt.compare(password, user?.passwordHash ?? DUMMY_HASH);
  if (!user || !ok) throw new Unauthorized('Invalid credentials');  // one generic message
  return issueSession(user);
}

// comparing tokens / API keys: never use === (it stops at the first differing byte)
export const safeEqual = (a: string, b: string) => {
  const A = Buffer.from(a), B = Buffer.from(b);
  return A.length === B.length && timingSafeEqual(A, B);
};
```

## 7. Validation and transformation 🎓

**Covered:**
- **Syntactic validation:** is it a valid email, phone number, date format?
- **Semantic validation:** a date of birth **can't be in the future**; age must be **between 1 and 120**.
- **Type validation:** is it a string, an integer, an array, an object?
- **Client-side vs server-side:** client-side gives **instant feedback** (UX). **Server-side is the real security**, because it's the gateway to your business logic, so it's required even if the client validates.
- **Fail fast:** return early to avoid unnecessary work. Keep frontend and backend validation **consistent**.
- **Transformations:** **type casting** (query and path parameters always arrive as **strings**, so an ID must become a number before reaching the handler), **date formats** (the frontend may send a different format or you may expect a timestamp).
- **Normalization:** lowercase emails, trim whitespace, add a country code to phone numbers.
- **Sanitization:** clean user strings to prevent attacks such as **SQL injection**.
- **Complex logic:** **relationship** validation (password and confirm password must match), **conditional** validation (a partner-name field only required if `married` is true), **chained** validation (lowercase → remove special characters → check length).
- **Errors:** meaningful messages so users can fix input; **aggregate all errors** in one response; **obscure** sensitive ones ("invalid credentials" instead of "invalid password"); handle failed transformations (invalid JSON, a failed date conversion) gracefully.
- **Performance:** return early, avoid redundant validation.

🔧 **One schema can express every one of those categories.** Here they are with zod:

```ts title="signup.schema.ts"
import { z } from 'zod';

export const Signup = z.object({
  email: z.string().trim().toLowerCase().email(),                       // normalize + syntactic
  age: z.coerce.number().int().min(1).max(120),                         // transform + type + semantic
  dob: z.coerce.date().refine(d => d <= new Date(), 'date of birth cannot be in the future'),
  password: z.string().min(12),
  confirmPassword: z.string(),
  married: z.boolean(),
  partnerName: z.string().trim().optional(),
})
  .refine(v => v.password === v.confirmPassword, { path: ['confirmPassword'], message: 'passwords do not match' }) // relationship
  .refine(v => !v.married || !!v.partnerName, { path: ['partnerName'], message: 'required when married' });      // conditional

// safeParse collects ALL issues → return them together with a 400
```

🔧 **On sanitization vs SQL injection:** the reliable defence is **parameterised queries** (`WHERE email = $1`), which keep data out of the SQL text entirely. Sanitising strings is a secondary layer, not the fix.

## 8. Middleware 🎓

**Covered:** what middleware is and when to use it; its role in the request cycle (**pre-request** and **post-response**); **chaining**: each middleware runs in sequence and passes control on until the request reaches its handler; **ordering**; how the **`next` function** works; **exiting early** (short-circuiting the pipeline, e.g. for 404s).

**The lesson's recommended order:** **log** the request → **authenticate** → **validate** → **route handling** → **error handling**.

**Common middleware:**
- **Security:** headers such as `X-Content-Type-Options`, `Strict-Transport-Security`, `Content-Security-Policy`; **CORS** headers; **CSRF** protection; **rate limiting**.
- **Authentication:** reuse route-protection logic across the app.
- **Logging and monitoring:** request logging, **structured** logging for observability and easier production debugging.
- **Error handling:** catch and format errors for **consistent API responses**.
- **Compression / performance:** compress response bodies.
- **Body parsing:** JSON, URL-encoded forms, file uploads (**multipart** data).
- **Performance and security:** keep middleware lightweight; order affects both performance and security.

<Mermaid chart={`flowchart LR
  R[Request] --> L["Logger"] --> SEC["Security headers + CORS"] --> RL["Rate limit"] --> AU["Auth"] --> V["Validation"] --> H["Handler"]
  AU -. "401, short-circuit" .-> E["Error handler"]
  V -. "400, short-circuit" .-> E
  H -. "throws" .-> E
  H --> RES[Response]
  E --> RES`} />

🔧 **Why order matters, concretely:**
- Put **CORS before auth**, or browser preflights (which carry no credentials) get 401s.
- Put **rate limiting before** expensive work (auth DB lookups, body parsing of huge payloads).
- In Express, the **error handler must be registered last** and take four arguments, or it's never called.

```ts title="app.ts (Express)"
app.use(requestLogger);          // 1. see everything, including rejected requests
app.use(helmet(), cors(corsOpts));
app.use(rateLimit({ windowMs: 60_000, limit: 100 }));
app.use(express.json({ limit: '1mb' }));
app.use('/api', authenticate);   // short-circuits with 401 by calling next(err) or responding
app.use('/api', routes);         // validation runs per route
app.use(notFound);               // nothing matched → 404
app.use(errorHandler);           // (err, req, res, next): must be last
```

## 9. Request context 🎓

**Covered:** the metadata passed through middleware, controllers and services: a **request-scoped state** that's only valid for that request. Its life cycle; **sharing data across layers without coupling** them. Components:
- **request metadata:** method, URL, headers, query parameters, body;
- **session and user info:** the auth middleware loads the user and **injects it** into the context for the rest of the request;
- **tracking info:** unique **request IDs, trace IDs**;
- **request-specific data:** cached data, permission checks.

Use cases (auth, rate limiting, tracing, logging), the link with middleware, **timeouts** (request, custom) and **cancellation signals**. Best practices: keep it **lightweight**, **clean it up** after the request to avoid **memory leaks**, and don't **over-rely** on it or use it to couple components.

🔧 **Mechanism in Node:** there's no thread per request, so "request-local" storage needs `AsyncLocalStorage`, which follows a request across every `await`:

```ts title="context.ts"
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';

type Ctx = { requestId: string; userId?: string; signal: AbortSignal };
export const ctx = new AsyncLocalStorage<Ctx>();

app.use((req, res, next) => {
  const ac = new AbortController();
  res.on('close', () => { if (!res.writableEnded) ac.abort(); });       // client left → cancel work
  const requestId = req.header('x-request-id') ?? randomUUID();
  res.setHeader('x-request-id', requestId);
  ctx.run({ requestId, signal: ac.signal }, next);                       // everything downstream sees it
});

// anywhere, without passing req around:
export const log = (msg: string) => console.log(JSON.stringify({ msg, requestId: ctx.getStore()?.requestId }));
```

Go has the same idea built in: `context.Context`, passed as the first argument, carrying deadlines, cancellation and request-scoped values.

## 10. Handlers, controllers and CRUD 🎓

**Covered:** the **MVC** pattern; the responsibilities of **handlers, controllers and services**; reducing code with middleware; **centralised error handling** and **consistent success and error formats**.

**CRUD ↔ HTTP methods:**

| Operation | Method | Typical status |
|---|---|---|
| Create, submissions | `POST` | `201 Created`, or `400` for a bad request |
| Read a list or one item | `GET` | `200` |
| Update | `PUT` / `PATCH` | `200` |
| Delete | `DELETE` | `200` / `204` |

Also: **pagination**, a **search API**, **sorting** and **filtering**; best practices (**strict validation**, consistent responses, **limiting payloads**, **redacting sensitive fields**, error handling, authN/authZ).

### REST 🎓
RESTful architecture: designing APIs **around resources**, following **HTTP semantics**, filtering and pagination, **versioning** styles (**URI, header, query string, media type**), designing with the **OpenAPI** spec in mind, content negotiation, meaningful error messages, client-side caching with **ETags**, optimising large requests and responses.

🔧 **Problem → mechanism:** if handlers contain SQL, validation and HTTP details all mixed together, nothing is reusable or testable. Split responsibilities: the **controller** speaks HTTP (parse, call, map result to status), the **service** holds the rules, the **repository** talks to the DB.

## 11. Databases 🎓

**Covered:** **relational vs non-relational** and when to use which; theory: **ACID** and the **CAP theorem**; basic querying and **joins**; design best practices (**schema design**, **indexing**); optimisation (**query optimisation, caching, connection pooling**); data integrity (**constraints and validations**, **transactions and concurrency**); **ORMs**: how they work, whether to use one, the trade-offs; **migrations**.

🔧 **Example of why transactions + constraints matter:** "transfer 100 from A to B" is two UPDATEs. If the process dies between them, money vanishes. A **transaction** makes both happen or neither; a `CHECK (balance >= 0)` **constraint** makes the DB itself reject an overdraft, even under concurrent requests.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';   -- CHECK (balance >= 0) can abort here
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;
```

### Zero-downtime schema changes ➕

The roadmap lists **migrations**, and the DevOps topic below warns that rolling deploys need backward-compatible ones. What neither spells out is **how** to change the schema of a table that is serving traffic, which is where most migration outages come from.

#### Why one ALTER TABLE can stop the whole app ➕

- **Problem:** a migration that runs in milliseconds on your laptop freezes production for minutes, and every request touching that table times out.
- **Why (first principles):** most `ALTER TABLE` forms need an **`ACCESS EXCLUSIVE`** lock, which conflicts with everything, even plain `SELECT`s. If a long-running query or an idle open transaction already holds a lock on the table, the `ALTER` **waits**, and every new query on the table queues **behind the waiting ALTER**. A fast migration plus one slow report query equals a full outage.

<Mermaid chart={`sequenceDiagram
  participant R as Slow report query
  participant M as Migration ALTER TABLE
  participant A as App queries
  R->>R: holds a lock for 2 minutes
  M->>M: waits for ACCESS EXCLUSIVE
  A->>A: every new SELECT queues behind the ALTER
  Note over A: app requests time out until R finishes`} />

- **Mechanism:** never let a migration wait indefinitely. Set a short **`lock_timeout`**, so the migration fails fast (and can be retried) instead of blocking traffic:

```sql
SET lock_timeout = '3s';          -- give up quickly if the lock isn't free
SET statement_timeout = '15min';  -- but allow long data work once running
ALTER TABLE orders ADD COLUMN coupon_code text;   -- metadata-only: fast once the lock is acquired
```

- **Edge cases:** in Postgres 11+, `ADD COLUMN` with a constant (non-volatile) default is metadata-only, but a **volatile** default such as `gen_random_uuid()` rewrites the whole table, and so do most column **type changes**. Check what a statement does before running it on a large table, and retry a `lock_timeout` failure in a loop with a pause.

#### Expand and contract ➕

- **Problem:** during a rolling deploy, the **old** and the **new** version of the app run at the same time against **one** database. Renaming `users.name` to `users.full_name` in one migration breaks whichever version doesn't know the current column name.
- **Mechanism:** split every breaking change into steps where each schema version works with **two** consecutive app versions: first **expand** (add the new structure alongside the old), migrate, then **contract** (remove the old one) once no running code uses it.

| Step | Deploy | Schema | App |
|---|---|---|---|
| 1 | migration | add `full_name` (nullable) | old app ignores it |
| 2 | app v2 | | writes **both** columns, still reads `name` |
| 3 | backfill job | copy `name` into `full_name` in batches | |
| 4 | app v3 | | reads `full_name`, still writes both |
| 5 | app v4 | | stops writing `name` |
| 6 | migration | drop `name` | |

- **Implementation:** the backfill in small batches, so it never holds long locks or creates one huge transaction:

```ts title="backfill-full-name.ts"
let updated: number;
do {
  const r = await pool.query(`
    UPDATE users SET full_name = name
     WHERE id IN (SELECT id FROM users WHERE full_name IS NULL AND name IS NOT NULL LIMIT 5000)`);
  updated = r.rowCount ?? 0;
  await new Promise((res) => setTimeout(res, 100));   // let replication and normal traffic breathe
} while (updated > 0);
```

- **Edge cases:** it takes several deploys, which feels slow, but each step is individually safe and **rollback-able**: rolling back app v3 to v2 still works because both columns are kept in sync. ORMs that select columns by a cached schema, or `SELECT *` into strict types, can break on a merely **added** column, so test step 1 against the old app too.

#### Constraints and indexes without blocking writes ➕

- **Problem:** `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)` or a foreign key validates every existing row while holding a lock that blocks writes, and `SET NOT NULL` scans the whole table.
- **Mechanism:** split **declaring** a rule from **checking** old rows. `NOT VALID` adds the constraint instantly and enforces it for **new** writes; `VALIDATE CONSTRAINT` checks old rows later under a weaker lock that allows reads and writes. Indexes use `CREATE INDEX CONCURRENTLY` (the databases lesson covers it: [Databases](/docs/backend-first-principles/12-databases-postgres)).

```sql
-- 1. enforce for new rows immediately (brief lock)
ALTER TABLE orders ADD CONSTRAINT orders_amount_positive CHECK (amount > 0) NOT VALID;
-- 2. check existing rows without blocking writes
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_positive;

-- NOT NULL without a long scan under ACCESS EXCLUSIVE (Postgres 12+):
ALTER TABLE users ADD CONSTRAINT users_full_name_nn CHECK (full_name IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT users_full_name_nn;
ALTER TABLE users ALTER COLUMN full_name SET NOT NULL;     -- uses the valid CHECK, skips the scan
ALTER TABLE users DROP CONSTRAINT users_full_name_nn;
```

- **Edge cases:** `CREATE INDEX CONCURRENTLY` can't run inside a transaction and leaves an **invalid** index behind if it fails; drop it and retry. Migration tools that wrap every file in a transaction need that disabled for those statements.

🔧 **Dependency inversion in practice:** the service depends on an **interface**, not on Postgres, so you can test it with an in-memory fake:

```ts
interface OrderRepo { findById(id: string): Promise<Order | null>; save(o: Order): Promise<void> }

class OrderService {
  constructor(private readonly repo: OrderRepo) {}       // NestJS injects the real one, tests inject a fake
  async cancel(id: string) {
    const order = await this.repo.findById(id);
    if (!order) throw new NotFoundError('order');
    if (order.status === 'SHIPPED') throw new ConflictError('shipped orders cannot be cancelled'); // business rule
    await this.repo.save({ ...order, status: 'CANCELLED' });
  }
}
```

## 13. Caching 🎓

**Covered:** why caching is needed and how it differs from DB persistence; types (**in-memory, browser, database** caching; **client-side vs server-side**); strategies (**cache-aside, write-through, write-behind/write-back, read-through**); eviction (**LRU, LFU, TTL, FIFO**); invalidation (**manual, TTL-based, event-based**); **levels**: L1 in-memory, L2 network/distributed, and **hierarchical caching** (hot data in a small fast L1, less frequent data in a larger, slower L2); web caching (static assets, API responses via headers); DB caching (e.g. storing **heavy join results in Redis**); **hit/miss ratio** and how to improve it.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant A as App
  participant R as Redis
  participant DB as Postgres
  A->>R: GET report 42
  alt hit
    R-->>A: cached JSON
  else miss
    R-->>A: nil
    A->>DB: heavy join query
    DB-->>A: rows
    A->>R: SET report 42 with TTL 300 s
  end
  Note over A,DB: on update, write DB then DEL report 42 (invalidate)`} />

🔧 **Cache-aside**, the most common strategy, in code, with the classic edge case handled:

```ts title="cache-aside.ts"
export async function getReport(id: string) {
  const key = `report:${id}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);

  const rows = await runHeavyJoin(id);
  await redis.set(key, JSON.stringify(rows), { EX: 300 + Math.floor(Math.random() * 60) }); // TTL + jitter
  return rows;
}

export async function updateReport(id: string, data: Patch) {
  await db.update(id, data);
  await redis.del(`report:${id}`);   // delete AFTER the write; deleting before lets a reader re-cache stale data
}
```

The jitter spreads expiry times so thousands of keys don't expire at the same instant and stampede the DB.

## 15. Task queues and scheduling 🎓

**Covered:**
- **Queuing use cases:** sending emails, processing images, third-party integrations (payments, webhooks), offloading heavy computation (batch processing).
- **The lesson's example:** a user clicks **"clear all my data"**. That means running queries against many tables and can take a while. Instead of blocking the request, **respond immediately** and push a **background job** into the queue.
- **Scheduling use cases:** **DB backups**, recurring notifications and reminders, data synchronisation, maintenance (clearing logs or caches).
- **Components:** **producer, queue, consumer, broker, backend** (result store).
- Task **dependencies** (chains, parent-child), **task groups** (run concurrently, wait for all), **error handling and retries**, **prioritisation** and **rate limiting** (e.g. payment processing before notifications).

<Mermaid chart={`flowchart LR
  P["Producer<br/>(API handler)"] -->|"enqueue job"| B[("Broker<br/>e.g. Redis")]
  B --> Q1["high priority queue<br/>payments"]
  B --> Q2["low priority queue<br/>notifications"]
  Q1 --> W["Consumers / workers"]
  Q2 --> W
  W -->|"result / status"| RB[("Result backend")]
  W -->|"failed N times"| DLQ["Dead-letter queue"]`} />

🔧 **The "clear my data" example with BullMQ:**

```ts title="clear-data.ts"
import { Queue, Worker } from 'bullmq';
const queue = new Queue('user-data', { connection });

// producer: the handler returns immediately
app.post('/me/clear-data', async (req, res) => {
  const job = await queue.add('clear', { userId: req.user.id }, {
    jobId: `clear-${req.user.id}`,           // dedupe: a double click doesn't enqueue twice
    attempts: 5, backoff: { type: 'exponential', delay: 2_000 },
  });
  res.status(202).json({ jobId: job.id });    // 202 Accepted: "will be done"
});

// consumer: must be idempotent, because a retry may re-run a half-finished job
new Worker('user-data', async job => {
  for (const table of ['comments', 'posts', 'likes', 'uploads']) {
    await db.query(`DELETE FROM ${table} WHERE user_id = $1`, [job.data.userId]);   // safe to repeat
  }
}, { connection });
```

## 20. Graceful shutdown 🎓

**Covered:** why it's needed and how it works; use cases (**server restarts**, **scaling in** cloud environments, **microservices**, **long-running jobs**); **signal handling** (`SIGTERM`, `SIGINT`, `SIGKILL`); the steps: **capture the signal → stop accepting requests → finish in-flight requests → close external resources** (DB connections, open files) → **terminate**.

<Mermaid chart={`stateDiagram-v2
  [*] --> Serving
  Serving --> Draining: SIGTERM or SIGINT received
  Draining --> Closing: in-flight requests finished
  Draining --> Forced: timeout exceeded
  Closing --> [*]: DB pool + queues closed, exit 0
  Forced --> [*]: exit 1`} />

🔧 Implementation (note that `SIGKILL` **can't be caught**; Kubernetes sends it after the grace period, 30 s by default):

```ts title="shutdown.ts"
let shuttingDown = false;
app.get('/healthz', (_req, res) => res.sendStatus(shuttingDown ? 503 : 200)); // LB stops routing to us

async function shutdown(signal: string) {
  if (shuttingDown) return;
  shuttingDown = true;
  log.info({ signal }, 'shutting down');
  const force = setTimeout(() => process.exit(1), 25_000).unref();  // must finish before SIGKILL

  await new Promise<void>(r => server.close(() => r()));   // stop accepting, wait for in-flight
  await Promise.allSettled([pool.end(), worker.close(), redis.quit()]);
  clearTimeout(force);
  process.exit(0);
}
process.on('SIGTERM', () => void shutdown('SIGTERM'));
process.on('SIGINT', () => void shutdown('SIGINT'));
```

`server.close()` waits for **open** keep-alive connections too; on Node 19+ idle ones are closed automatically, or call `server.closeIdleConnections()`.

## 21. Security 🎓

**Covered:** avoiding **SQL injection, NoSQL injection, XSS, CSRF, broken authentication, insecure deserialization**; secure-design principles (**least privilege, defense in depth, fail-secure defaults, separation of duties, security by design**); input **validation and sanitization**; **rate limits**; **Content Security Policy**; **CORS**; **SameSite cookies**; **monitoring security events**.

🔧 **Defense in depth, by example:** XSS is stopped by **output encoding** (templates escape by default), then by a **CSP** that blocks inline scripts if encoding is missed, then by **HttpOnly** cookies so a script that still runs can't steal the session. Each layer covers the failure of the one before.

### Personal data and privacy engineering ➕

Security keeps attackers out. A related duty the roadmap doesn't list is handling **personal data** correctly even when nobody attacks: knowing where it is, not spreading it, deleting it when asked and not keeping it forever. Laws such as the GDPR (right to erasure, Article 17; storage limitation, Article 5) make this a backend requirement, and most of the work is in data flow, not legal text.

#### Know where personal data lives ➕

- **Problem:** a user asks "what do you store about me?" or "delete my account", and nobody can list every table, cache, index, bucket and third party that holds their data.
- **Why it happens:** personal data spreads by default. An email address is copied into an orders table, a search index, a CRM sync, log lines and an analytics event, and each copy was added by a different person for a good reason.
- **Mechanism:** a **data inventory**: every place that stores personal data is registered, with its owner, its purpose and how to delete from it. Keep it **in the code**, next to the schema, so it's reviewed with every change.
- **Implementation:** tag columns in the schema and generate the inventory from the database itself:

```sql
COMMENT ON COLUMN users.email        IS 'pii:contact retention:account';
COMMENT ON COLUMN users.date_of_birth IS 'pii:sensitive retention:account';
COMMENT ON COLUMN orders.ship_address IS 'pii:contact retention:7y-tax';

-- inventory: every tagged column in the database
SELECT c.table_name, c.column_name, col_description(format('%I.%I', c.table_schema, c.table_name)::regclass, c.ordinal_position) AS tag
  FROM information_schema.columns c
 WHERE c.table_schema = 'public'
   AND col_description(format('%I.%I', c.table_schema, c.table_name)::regclass, c.ordinal_position) LIKE 'pii:%';
```

- **Edge cases:** the database is the easy part. List the **non-database** copies explicitly (Redis keys, Elasticsearch indexes, S3 prefixes, queues, email provider, analytics, backups), and add a CI check that fails when a new column has no tag.

#### Keep personal data out of logs and analytics ➕

- **Problem:** logs are copied to several systems, kept for months and readable by many engineers. One `log.info({ body: req.body })` on the signup route puts every new user's email and password into all of them.
- **Mechanism:** log **identifiers, not content**. Use the internal user ID instead of the email; where you must correlate by a personal value (e.g. "how many failed logins for this email?"), log a **keyed hash** (HMAC with a secret) rather than a plain hash, because plain hashes of emails can be reversed by hashing a list of known emails.
- **Implementation:**

```ts title="logger.ts"
import pino from 'pino';
import { createHmac } from 'node:crypto';

export const log = pino({
  redact: { paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.email', '*.phone'], censor: '[redacted]' },
});
export const pseudonym = (value: string) =>
  createHmac('sha256', process.env.LOG_PSEUDONYM_KEY!).update(value.trim().toLowerCase()).digest('hex').slice(0, 16);

log.warn({ userId: user?.id, emailHash: pseudonym(email) }, 'login failed');   // correlatable, not readable
```

- **Edge cases:** redaction lists only catch the field names you thought of; free-text fields (`message`, error strings that echo input, URLs with query parameters) still leak. Prefer logging an explicit allow-list of fields over dumping objects. More on structured logging in [Logging, monitoring and observability](/docs/backend-first-principles/18-logging-monitoring-observability).

#### Deleting a user from every copy ➕

- **Problem:** "delete my account" runs `DELETE FROM users WHERE id = $1`, and the person still appears in search results, cached profile pages, the CRM, exported files and next month's restored backup.
- **Mechanism:** treat erasure as a **workflow**, not a query: record the request, delete or anonymise in the primary database in one transaction, then fan out idempotent jobs to every other store in the inventory, and track each one until all are done. It's the "clear all my data" task-queue example (section 15) with a checklist.

```ts title="erasure.ts"
export async function requestErasure(userId: string) {
  await db.tx(async (t) => {
    await t.query(`INSERT INTO erasure_requests (user_id, status) VALUES ($1, 'pending')`, [userId]);
    await t.query(`UPDATE orders SET ship_address = NULL, customer_name = 'deleted user' WHERE user_id = $1`, [userId]); // keep the order for tax, drop the person
    await t.query(`DELETE FROM users WHERE id = $1`, [userId]);
  });
  for (const target of ['search-index', 'cache', 'object-storage', 'crm', 'email-provider']) {
    await erasureQueue.add(target, { userId }, { jobId: `${target}:${userId}`, attempts: 10, backoff: { type: 'exponential', delay: 60_000 } });
  }
}
```

- **Edge cases:** **backups** can't be edited row by row. Common answers are short backup retention (deleted data disappears when the last backup containing it expires) plus re-applying the erasure list after any restore, or **crypto-shredding**: encrypt each user's sensitive fields with a per-user key and delete the key. Some data must be **kept** for legal reasons (invoices), so anonymise those rows instead of deleting them.

#### Retention: delete on a schedule ➕

- **Problem:** data kept "just in case" grows forever. Every old row is more to secure, more to leak and more to erase, and keeping personal data longer than needed is itself a violation of the storage-limitation principle.
- **Mechanism:** every personal-data table gets a **retention period** (from the inventory tags above) and a job that enforces it automatically.
- **Implementation:** a nightly batched delete (for very large time-series tables, partitioning and dropping old partitions is cheaper; see [Scaling and performance part 2](/docs/backend-first-principles/22-scaling-performance-part-2)):

```ts title="retention.job.ts"
const RULES = [
  { table: 'login_events', column: 'created_at', keep: '90 days' },
  { table: 'password_reset_tokens', column: 'created_at', keep: '1 day' },
] as const;                                                        // fixed allow-list: identifiers can't be $-params

for (const r of RULES) {
  let n: number;
  do {
    const res = await pool.query(
      `DELETE FROM ${r.table} WHERE ctid IN (SELECT ctid FROM ${r.table} WHERE ${r.column} < now() - $1::interval LIMIT 10000)`,
      [r.keep]);
    n = res.rowCount ?? 0;
  } while (n > 0);
}
```

- **Edge cases:** run it with a lock so only one instance executes it, alert when it fails (a silently broken retention job is invisible for months), and remember that the space of deleted rows only becomes reusable after `VACUUM` runs.

## 22. Scaling and performance 🎓

**Covered:** metrics (**response time, resource utilisation**); finding **bottlenecks**; caching and DB optimisation (avoid **N+1 queries**, use joins properly, **lazy loading** where appropriate); **indexes** on frequently queried fields (foreign keys, search fields); **batch processing** for large datasets; **avoiding memory leaks** (close file handles and DB connections, clean up after long processes); reducing **payload size** and using **compression**; **performance testing and profiling**. 🔧 **The N+1 problem in one picture:** listing 50 posts with their authors as `1 query for posts + 50 queries for authors` = 51 round trips. One join, or one `WHERE id = ANY($1)` with all 50 IDs, does it in 1 or 2.

```ts
const posts = await db.query('SELECT * FROM posts ORDER BY created_at DESC LIMIT 50');
// ❌ N+1: for (const p of posts.rows) p.author = await getUser(p.author_id);
const ids = [...new Set(posts.rows.map(p => p.author_id))];
const authors = await db.query('SELECT id, name FROM users WHERE id = ANY($1)', [ids]);   // ✅ 1 extra query
```

## 23. Concurrency and parallelism 🎓

**Covered:** the difference between them; **concurrency helps I/O-bound** tasks; **parallelism helps CPU-bound** tasks.

🔧 **In Node terms:** one event loop gives you **concurrency**: while one request waits for Postgres, others run. It gives you **no parallelism** for CPU work: hashing a large file or resizing an image blocks every other request. For that, use `worker_threads`, child processes, or more instances.

```ts
// I/O-bound: concurrent waits overlap, ~max(latencies) instead of the sum
const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);

// CPU-bound: move it off the event loop
import { Worker } from 'node:worker_threads';
const worker = new Worker(new URL('./resize.worker.js', import.meta.url), { workerData: { path } });
```

## 29. Webhooks 🎓

**Covered:** use cases (**notifications, third-party integrations**); **API vs webhook** for the same need: with an API you often **poll** (client-initiated), with a webhook the server **pushes** (server-initiated); components (**webhook URL, event triggers, payload, HTTP method, response handling**); best practices (**signature verification**, **HTTPS**, **respond quickly**, **retry logic**, **logging**); testing with **ngrok**; real examples (**Stripe** payments, **GitHub**, **Slack**, **Discord**, **Twilio**).

<Mermaid chart={`sequenceDiagram
  participant P as Provider (e.g. Stripe)
  participant API as Your webhook endpoint
  participant Q as Queue
  P->>API: POST /webhooks/stripe + signature header + event JSON
  API->>API: verify HMAC signature on the RAW body
  API->>API: seen this event id before? then skip
  API->>Q: enqueue event
  API-->>P: 200 quickly
  Note over P: no 2xx or timeout means retry later with backoff`} />

🔧 **Signature verification, the core mechanism:** the provider signs the raw body with a shared secret (HMAC-SHA256). You recompute and compare in constant time. It **must** use the **raw bytes**: re-serialising parsed JSON changes whitespace and breaks the signature.

```ts title="webhook.ts"
import { createHmac, timingSafeEqual } from 'node:crypto';

app.post('/webhooks/acme', express.raw({ type: 'application/json' }), async (req, res) => {
  const expected = createHmac('sha256', process.env.WEBHOOK_SECRET!).update(req.body).digest('hex');
  const given = String(req.header('x-signature') ?? '');
  if (given.length !== expected.length || !timingSafeEqual(Buffer.from(given), Buffer.from(expected))) {
    return res.sendStatus(401);
  }
  const event = JSON.parse(req.body.toString('utf8'));
  await queue.add('webhook', event, { jobId: event.id });   // providers retry: dedupe by event id
  res.sendStatus(200);                                      // respond fast; process in the worker
});
```

(Real providers also sign a **timestamp** to block replays; use their SDK, e.g. `stripe.webhooks.constructEvent`.)

## Interview questions

1. **How would you define backend engineering beyond CRUD?** **Building reliable, scalable, fault-tolerant, maintainable systems: correct data handling, security, observability, graceful failure and performance, not only endpoints.**
2. **How can a login endpoint leak which usernames exist?** **Through different error messages or different response times (hashing only when the user exists). Use one generic message and always run the hash, e.g. against a dummy hash.**
3. **Why is server-side validation required if the client already validates?** **The client is under the user's control and can be bypassed; the server is the gateway to business logic.**
4. **Give a sensible middleware order.** **Logging → security headers/CORS → rate limiting → body parsing → auth → validation → handler → 404 → error handler (last).**
5. **What is request context and how do you implement it in Node?** **Request-scoped state (request ID, user, cancellation) available across layers; `AsyncLocalStorage` (or Go's `context.Context`).**
6. **Cache-aside: on update, delete the cache before or after writing the DB?** **After. Deleting first lets a concurrent reader re-populate the cache with the old value before the write lands.**
7. **Why move "delete all my data" to a task queue?** **It's slow and failure-prone; respond 202 immediately and let an idempotent worker do it with retries.**
8. **What are the steps of graceful shutdown?** **Catch SIGTERM/SIGINT → fail health checks → stop accepting new connections → finish in-flight work → close DB/queue connections → exit, with a forced timeout before SIGKILL.**
9. **Concurrency vs parallelism?** **Concurrency overlaps waiting (I/O-bound work); parallelism runs computation simultaneously on multiple cores (CPU-bound work).**
10. **How do you verify a webhook?** **Recompute the HMAC of the raw body with the shared secret, compare in constant time, check the timestamp, dedupe by event ID, respond 2xx fast and process asynchronously.**
11. ➕ **A migration that takes 50 ms locally froze production. What happened?** **The `ALTER TABLE` needed an ACCESS EXCLUSIVE lock, waited behind a long-running query, and every new query queued behind it. Set a short `lock_timeout` and retry.**
12. ➕ **How do you rename a column with zero downtime during rolling deploys?** **Expand and contract: add the new column, dual-write, backfill in batches, switch reads, stop writing the old column, then drop it, each step compatible with the previous app version.**
13. ➕ **How do you add a CHECK or NOT NULL constraint to a large live table?** **Add it `NOT VALID` (enforced for new rows instantly), then `VALIDATE CONSTRAINT` under a lock that allows writes; for NOT NULL, a validated CHECK lets `SET NOT NULL` skip the scan.**
14. ➕ **A user asks you to delete all their data. What has to happen?** **A tracked workflow: delete or anonymise in the primary DB, then idempotent jobs for every other copy (search, caches, object storage, third parties), with backups handled by short retention or crypto-shredding, and legally required records anonymised instead of deleted.**
15. ➕ **Why log an HMAC of an email instead of a SHA-256 hash?** **A plain hash of an email can be reversed by hashing lists of known emails; a keyed hash can't without the secret, yet still lets you correlate events.**
