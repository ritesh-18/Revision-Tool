## 1. The problem: two languages, one conversation 🎓

### The setup
- The **client** is a browser running a JavaScript app (React, Angular, Vue, it doesn't matter).
- The **server** runs on localhost or in a cloud (AWS, GCP, Azure). The lesson picks **Rust** for it on purpose.
- They talk over a network protocol: HTTP (REST), gRPC or WebSockets. The series sticks with **HTTP**.

An HTTP request is a method + URL, then headers, then a body. The client puts its data in the **body**.

### Why this is a real problem (first principles)
The client wants to send something like an object with a `name` string. But:
- **JavaScript is dynamic and interpreted.** An object is a runtime hash map; a number is always a 64-bit float.
- **Rust is compiled and strictly typed.** Data lives in `struct`s with fixed field types and a fixed memory layout; integers come in exact widths (`u8`, `i64` …).

A JavaScript object's **in-memory representation means nothing to a Rust process.** It's pointers into the V8 heap of a different machine. You can't send memory; you can only send **bytes**, and both sides must agree on what those bytes mean.

The same is true for the response going the other way: the Rust struct must become something the JavaScript client can read, so it can render UI or run its own logic.

## 2. Where the network fits: the OSI model 🎓

The lesson recommends a **high-level** familiarity with the OSI model, not mastery. You don't need packet formats or frame layouts to be a good backend engineer.

- The **top** layer is the **application layer** (where HTTP and your JSON live).
- The **bottom** layer is the **physical layer** (bits as voltages, light in optical fibre, radio).
- Both client and server have the full stack. Data goes **down** the stack on the sender (into segments, IP packets, frames, bits) and **up** the stack on the receiver.

<Mermaid chart={`flowchart TB
  subgraph Client["Client (JavaScript)"]
    direction TB
    CA["Application: JS object to JSON text"] --> CL["Transport / Network / Data link"] --> CP["Physical: bits"]
  end
  subgraph Server["Server (Rust)"]
    direction TB
    SP["Physical: bits"] --> SL["Data link / Network / Transport"] --> SA["Application: JSON text to Rust struct"]
  end
  CP -- "voltages, light, radio" --> SP`} />

**The mental model the lesson wants you to keep:** as a backend engineer, your responsibility ends at the application layer. The client emits JSON, the server receives JSON. Whatever the layers in between turn it into (frames, packets, 0s and 1s), it is **JSON again by the time your code reads it**. The intermediate steps are not your concern.

🔧 Precisely: what your code receives is a **byte sequence** (the HTTP body) plus a `Content-Type` header saying how to interpret it. "Receiving JSON" means "receiving UTF-8 bytes that a JSON parser can turn into values".

## 3. The fix: agree on a common standard 🎓

If you had to design this yourself, the obvious answer is a **shared set of rules** that both sides commit to:

1. **Before sending**, the sender converts its native data into the agreed format. This is **serialization**.
2. The formatted data travels over the network.
3. **On receipt**, the receiver converts the agreed format into its own native types (a Rust `struct`, a JS object). This is **deserialization**.
4. The response goes through the same two steps in the other direction.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant JS as Client (JavaScript)
  participant Net as Network
  participant RS as Server (Rust)
  JS->>JS: serialize: object to JSON text
  JS->>Net: HTTP body (bytes)
  Net->>RS: same bytes
  RS->>RS: deserialize: JSON to struct
  RS->>RS: business logic
  RS->>RS: serialize: struct to JSON
  RS-->>JS: HTTP response body
  JS->>JS: deserialize: JSON to object, render UI`} />

**The lesson's definition:** serialization and deserialization convert data **to and from a common format** so that, during **transmission or storage**, it stays **language-agnostic** (domain-agnostic). Machines in different languages and environments can all make sense of it.

🔧 The "storage" half matters too: writing a JSON column to Postgres, putting a message on a queue, caching an object in Redis, or writing a log line are all serialization. Anything that crosses a **process boundary** or **outlives the process** must become bytes.

### Two families of serialization formats 🎓

<Mermaid chart={`flowchart TD
  S["Serialization standards"] --> T["Text-based<br/>human readable"]
  S --> B["Binary<br/>compact, machine-oriented"]
  T --> J["JSON"]

- **Text-based:** JSON, YAML, XML. You can read them in a terminal. YAML and XML show up more in config files and older APIs than in HTTP bodies.
- **Binary:** **Protobuf** is the most popular (the transcript also mentions "others", most likely Avro).

### 🔧 Going deeper: text vs binary, why both exist

| | JSON | Protobuf |
|---|---|---|
| Schema | None required; field names travel with every message | Required `.proto` file; fields are sent as **numbers**, not names |
| Size | Larger: keys repeated, numbers written as decimal text | Smaller: varint integers, no keys |
| Speed | Parse text, allocate strings | Decode fixed tags, usually faster |
| Debuggability | Read it in DevTools, `curl` it | Needs the schema to decode |
| Evolution | Add fields freely; old clients ignore them (if they're written to) | Add fields with new numbers; never reuse a number |
| Typical home | Browser ↔ API | Service ↔ service (gRPC), high-volume pipelines |

The trade-off is **human readability and zero setup vs bytes on the wire and CPU**. For a browser talking to your API, readability usually wins; between internal services handling millions of messages, binary often does.

```proto title="book.proto"
syntax = "proto3";
message Book {
  int32  id     = 1;   // on the wire: tag 1 + varint, no "id" text
  string title  = 2;
  string author = 3;
}
```

### Protobuf on the wire ➕

The table above says Protobuf is "smaller and faster". This section shows where the savings come from, because the same rules explain its compatibility guarantees and its sharp edges.

#### Tags and wire types: how a message works without field names ➕

**Problem.** JSON repeats every key name in every message. `{"id":150,"title":"Dune"}` is 25 bytes, and 18 of them are punctuation and key text; only 7 are the values.

**Why it happens.** A schema-less format has to be self-describing: the reader has nothing else to tell it which value is which field, so the names must travel with the data.

**Mechanism.** Protobuf moves the names into the `.proto` file that both sides compile in, and sends a small numeric **tag** in front of each value. The tag is a varint computed as `(field_number << 3) | wire_type`. The wire type is a 3-bit code that tells the parser how many bytes follow, so it can skip a field it doesn't know:

| Wire type | ID | Used for |
|---|---|---|
| VARINT | 0 | `int32`, `int64`, `uint32`, `uint64`, `sint32`, `sint64`, `bool`, `enum` |
| I64 | 1 | `fixed64`, `sfixed64`, `double` |
| LEN | 2 | `string`, `bytes`, nested messages, packed repeated fields (followed by a length varint) |
| I32 | 5 | `fixed32`, `sfixed32`, `float` |

**Implementation.** `Book { id: 150, title: "Dune" }` encodes to 9 bytes:

```txt title="Book on the wire (hex)"
08          tag: field 1, wire type 0  -> (1 << 3) | 0 = 0x08
96 01       varint 150
12          tag: field 2, wire type 2  -> (2 << 3) | 2 = 0x12
04          length: 4 bytes follow
44 75 6E 65 "Dune" in UTF-8
```

A minimal tag reader in Python shows how little work decoding is:

```python title="read_tag.py (sketch)"
def read_varint(buf: bytes, pos: int) -> tuple[int, int]:
    value = shift = 0
    while True:
        byte = buf[pos]
        pos += 1
        value |= (byte & 0x7F) << shift  # low 7 bits are payload
        shift += 7
        if not byte & 0x80:  # high bit clear = this was the last byte
            return value, pos


tag, _ = read_varint(bytes([0x12]), 0)
field_number = tag >> 3  # 2
wire_type = tag & 0x7  # 2 (LEN)
read_varint(bytes([0x96, 0x01]), 0)  # (150, 2): the id from the example above
```

**Edge cases.** Field numbers 1 to 15 fit in a one-byte tag; 16 and above need two. Put frequently sent fields in the low range. And a capture of Protobuf traffic is unreadable without the matching `.proto`: keep schemas in a registry or a shared repo, or debugging production payloads becomes guesswork.

#### Varints, and why a negative `int32` costs 10 bytes ➕

**Problem.** Fixed 4- or 8-byte integers waste space, because most real numbers (IDs, counts, lengths) are small.

**Why it happens.** A 64-bit slot holding the value 3 is 62 zero bits of padding.

**Mechanism.** A **varint** stores 7 bits of the number per byte and uses the top bit of each byte as a "more bytes follow" flag. Values below 128 take one byte. The catch: `int32` and `int64` encode negatives in two's complement, so `-1` has all its high bits set and always uses the maximum **10 bytes**. The `sint32`/`sint64` types fix this with **ZigZag** encoding, which maps signed to unsigned by interleaving: 0 → 0, -1 → 1, 1 → 2, -2 → 3. The formula for 32 bits is `(n << 1) ^ (n >> 31)`.

**Implementation.** Choose the type by the value's distribution:

```proto title="types.proto"
message Reading {
  sint32 temperature_delta = 1;  // often negative: ZigZag keeps -3 to 1 byte
  uint64 user_id           = 2;  // never negative
  fixed64 hash_prefix      = 3;  // uniformly large: varint needs 9 or 10 bytes, fixed is always 8
}
```

**Edge cases.** You can't switch a field between `int32` and `sint32` later: the bytes on the wire mean different numbers. And `int64`/`uint64` values are exact in Python's `protobuf` package (they decode to `int`), but a JavaScript client hits the same 2^53 limit as with JSON numbers (`protobufjs` returns a `Long` object or a string), which is also why Protobuf's JSON mapping writes 64-bit integers as strings.

#### Presence, defaults and unknown fields ➕

**Problem.** In proto3, a reader that sees `count = 0` can't tell whether the sender wrote 0 or didn't set the field at all.

**Why it happens.** For plain ("implicit presence") scalar fields, proto3 doesn't write default values (0, false, empty string) to the wire at all, to save bytes. Absent and default decode to the same thing.

**Mechanism.** Mark fields where "not set" means something with `optional`. That gives **explicit presence**: the generated code gets a `has` check, and an explicit 0 is sent. For forward compatibility, parsers keep **unknown fields** (tags their schema doesn't define) and write them back out when re-serializing, so a middle service on an old schema doesn't destroy data it doesn't understand.

```proto title="patch.proto"
message UpdateStock {
  string sku = 1;
  optional int32 quantity = 2;   // unset = "don't change", 0 = "sold out"
}

enum Status {
  STATUS_UNSPECIFIED = 0;        // proto3 enums must start at 0: make 0 mean "unknown"
  STATUS_ACTIVE = 1;
}
```

**Edge cases.** Unknown fields are **lost** when you convert a message to JSON or copy it field by field, so a gateway that does Protobuf → JSON → Protobuf silently drops new fields. Unknown enum values are kept as their integer in most languages; code that `switch`es over the enum needs a default branch.

## 5. JSON: the rules you need 🎓

**JSON = JavaScript Object Notation.** It looks like a JavaScript object, which explains the name, but it isn't tied to JavaScript. It's used in HTTP bodies, **config files**, and **logs** (structured logging), among other things. Its main selling point is that it was designed to be **human-readable**.

The rules from the lesson:
1. An object starts with an opening brace and ends with a closing brace.
2. **Keys are always strings in double quotes.** No other type can be a key.
3. A **value** can be a string, a number, a boolean, an array, or **another object** (nesting).
4. A nested object follows exactly the same rules.

```json title="user.json"
{
  "name": "Asha",
  "age": 29,
  "isAdmin": false,
  "tags": ["backend", "postgres"],
  "address": {
    "country": "India",
    "phone": 3456
  }
}
```

🔧 The full value set also includes **`null`**. Things JSON **does not** have: comments, trailing commas, single-quoted strings, `undefined`, dates, binary data, `NaN`/`Infinity`. Those gaps cause most real-world serialization bugs (sections 9 and 10).

## 6. What the demo shows 🎓

The demo reuses the books app from the HTTP lesson, with **Burp Suite** capturing traffic between the browser and the API.

**Request:** `POST /api/books`. The body is JSON: an object with double-quoted keys `id` (a **number**), `title` and `author` (**strings**).

**Response:** another JSON object whose single key holds an **array**, and each array element is an **object** with number and string values (the list of books, including the one just added).

The client parses that response and **renders the list** on the page. The client happens to be JavaScript here, but it could be PHP or anything else; the JSON in the middle doesn't change.

The point of the demo: there isn't much "theory" in serialization. It's a **phenomenon you need to know exists**. Client → JSON → server parses and understands → server responds in JSON → client parses and understands. That whole round trip is serialization and deserialization.

## 7. 🔧 Going deeper: what each side actually does

### Python / FastAPI

```python title="books.py"
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from starlette.middleware.body_limit import RequestBodyLimitMiddleware

app = FastAPI()
app.add_middleware(RequestBodyLimitMiddleware, max_body_size=100_000)  # larger bodies get 413 (Starlette 1.x)


@app.post("/api/books")
async def create_book(request: Request) -> JSONResponse:
    # Deserialization: read the bytes, json.loads (malformed JSON raises here → a 500 unless you catch it)
    body = await request.json()  # parsed, but NOT yet trusted (see lesson 9)
    # ...validate, then store
    books = [{"id": 1, "title": "Dune", "author": "Frank Herbert"}]
    return JSONResponse({"books": books}, status_code=201)  # Serialization: json.dumps + Content-Type: application/json
```

Under the hood, `request.json()` does what you'd do by hand. (Declare a typed body parameter instead, e.g. a Pydantic model, and FastAPI turns malformed JSON into a 422 rather than a crash.)

```python
raw = await request.body()  # bytes from the socket (Starlette joins the ASGI http.request messages)
text = raw.decode("utf-8")  # bytes → characters (JSON must be UTF-8)
value = json.loads(text)  # characters → Python values (raises JSONDecodeError on bad syntax)
```

### The same contract in Rust (what the lesson's server would do)

```rust title="main.rs (Rust, axum + serde)"
use axum::{routing::post, Json, Router};
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]           // JSON → struct; wrong types are rejected here
struct NewBook { id: u32, title: String, author: String }

#[derive(Serialize)]             // struct → JSON
struct Book { id: u32, title: String, author: String }

async fn create(Json(b): Json<NewBook>) -> Json<Vec<Book>> {
    Json(vec![Book { id: b.id, title: b.title, author: b.author }])
}

fn app() -> Router { Router::new().route("/api/books", post(create)) }
```

Notice the asymmetry: Rust's deserializer **refuses** `"id": "abc"` because the field is a `u32`. Python's `json.loads` (like the client's `JSON.parse`) accepts any well-formed JSON and gives you whatever types were sent: `dict`, `list`, `str`, `int`, `float`, `bool` or `None`. Checking them is a separate step; in FastAPI a Pydantic model plays serde's role, which is exactly what lesson 9 covers.

## 8. Big payloads: serializing without freezing the server ➕

Section 7's `request.json()` and `JSONResponse` hold the whole body in memory and convert it in one call. That's right for normal API requests, and wrong as soon as a payload gets large.

### Why `json.loads` blocks the event loop ➕

**Problem.** An import endpoint receives a 50 MB JSON file. While it parses, every other request on that worker process waits: health checks time out, and latency spikes for unrelated users.

**Why it happens (first principles).** `json.loads` and `json.dumps` are synchronous and O(n) in the input size. An asyncio server runs every `async def` handler on **one event-loop thread**, so a long synchronous call stops that thread from doing anything else (and on the standard CPython build the GIL means a worker thread wouldn't parse any faster). Measured on Python 3.14 (free-threaded build) for a 61 MB array of 560,000 small objects: 0.58 s to `json.loads` and 0.51 s to `json.dumps`. Memory is the second cost: the raw buffer, the decoded string and the resulting object tree all exist at once, often several times the payload size.

**Mechanism.** Keep the per-call work bounded:
1. **Cap** body size on ordinary routes (section 7's `max_body_size=100_000`, or `client_max_body_size` in Nginx), so a single request can't block for long.
2. For endpoints that legitimately move large data, **stream**: parse incrementally as bytes arrive, or write output piece by piece, so each event-loop iteration handles a small chunk.
3. Don't send very large files through the API at all. Let the client upload to object storage directly and process the file in a background job ([lesson 24](/docs/backend-first-principles/24-object-storage-part-1), [lesson 14](/docs/backend-first-principles/14-task-queues-background-jobs)).

**Edge cases.** The limit must cover **decompressed** size. Starlette and uvicorn don't decompress request bodies at all (`GZipMiddleware` only compresses responses), so if you accept `Content-Encoding: gzip` yourself, enforce the limit while inflating (`zlib.decompressobj().decompress(chunk, max_length)`): a check on `Content-Length` alone is fooled by a small compressed body that expands enormously.

### Streaming a request: parse element by element ➕

**Problem.** A client legitimately sends an array of 200,000 books to import.

**Mechanism.** A **streaming parser** (in Python, `ijson`) reads the body as a stream of tokens and emits each array element as soon as it's complete. Memory then depends on the size of one element, not the whole file, and each element can be validated and written in batches.

```python title="import_books.py"
import ijson
from fastapi import HTTPException, Request


@app.post("/api/books/import", status_code=201)
async def import_books(request: Request) -> dict[str, int]:  # no body parameter: FastAPI doesn't read it for us
    if request.headers.get("content-type", "").split(";")[0] != "application/json":
        raise HTTPException(415)
    count = 0
    batch: list[Book] = []
    items = ijson.sendable_list()
    parser = ijson.items_coro(items, "item")  # emits each element of the top-level array

    async def handle_parsed() -> None:
        nonlocal count
        for value in items:  # one array element at a time
            batch.append(Book.model_validate(value))  # validate each item (lesson 9)
            count += 1
            if count > 200_000:
                raise HTTPException(413, "too many items")
            if len(batch) == 500:
                await insert_batch(batch)
                batch.clear()
        items.clear()

    async for chunk in request.stream():  # bytes as they arrive, never the whole body
        parser.send(chunk)
        await handle_parsed()
    parser.close()  # raises if the JSON was truncated or malformed
    await handle_parsed()
    if batch:
        await insert_batch(batch)
    return {"imported": count}
```

**Edge cases.**
- An error at item 150,000 leaves 149,500 rows written. Decide up front: wrap the import in one transaction, load into a staging table and swap, or make it idempotent and report how far it got.
- A streaming route needs its own limits: count bytes as chunks arrive and cap the size of any single element; a stream of one 2 GB string is still a 2 GB string.
- If the client disconnects mid-upload, `request.stream()` raises `ClientDisconnect`, the handler unwinds and the parser is dropped with it; nothing is left half-open, but rows already inserted stay inserted (first bullet).

### Streaming a response: NDJSON and database cursors ➕

**Problem.** An export endpoint does `SELECT * FROM books` and `return rows`. With a million rows, the process holds every row object plus one giant string before sending the first byte.

**Why a plain JSON array is awkward.** A JSON array is only valid once its closing bracket arrives, so neither side can treat the data as finished records until the end.

**Mechanism.** Use a **line-delimited** format: one complete JSON value per line, commonly called **NDJSON** or JSON Lines (the IETF standard for a similar idea is RFC 7464, `application/json-seq`, which prefixes each record with an ASCII record-separator character). Read rows from Postgres through a **server-side cursor** so the database hands them over in batches, and write each one as it arrives. `StreamingResponse` gives you **backpressure**: it sends each chunk with `await send(...)`, and uvicorn holds that `await` while the socket's write buffer is full, so if the client reads slowly, the generator (and with it the cursor) stops fetching instead of buffering everything in memory.

```python title="export_books.py"
import json

from fastapi.responses import StreamingResponse
from psycopg.rows import dict_row


@app.get("/api/books/export")
async def export_books() -> StreamingResponse:
    async def ndjson():
        async with pool.connection() as conn:  # one pooled connection for the whole export
            async with conn.cursor(name="books_export", row_factory=dict_row) as cur:  # server-side cursor
                cur.itersize = 1000  # rows fetched per round trip
                await cur.execute("SELECT id::text AS id, title, author FROM books ORDER BY id")
                async for row in cur:
                    yield json.dumps(row) + "\n"

    return StreamingResponse(ndjson(), media_type="application/x-ndjson")
```

**Edge cases.**
- Once the status line and headers are sent you **can't change them to a 500**. A failure halfway just truncates the stream. Give clients a way to detect that: a final summary line with a row count, or a trailer they check.
- If the client disconnects, Starlette cancels the generator, and the `async with` blocks close the cursor and return the connection. A long cursor still holds one pooled connection (and, in a transaction, an old snapshot) for the whole export. Run big exports as background jobs that write a file, and give the client a download link.
- `application/x-ndjson` isn't an IANA-registered type; document it in your API spec so clients know to split on newlines.

## 9. 🔧 Going deeper: edge cases that bite

`json.dumps` and `json.loads` aren't perfect inverses, and some values don't serialize at all. What happens on a round trip (real output, Python 3.14):

| Value in Python | After `json.dumps` | Why it matters |
|---|---|---|
| `datetime(...)` | **raises** `TypeError: Object of type datetime is not JSON serializable` | Convert explicitly (`.isoformat()`); it parses back as a **string**, not a `datetime` |
| `{"x": float("nan"), "y": float("inf")}` | `{"x": NaN, "y": Infinity}` | **Not valid JSON**: other parsers (including the browser's) reject it. Pass `allow_nan=False` |
| `{1: "a"}` | `{"1": "a"}` | Keys come back as **strings** |
| `(1, 2)` | `[1, 2]` | Comes back as a **list** |
| `set`, `Decimal`, `bytes` | **raise** `TypeError` | Must convert first (list, string, Base64) |
| `9007199254740993` (above 2^53) | `9007199254740993` | Exact in Python, but most other parsers read numbers as doubles (`9007199254740992` in a browser); send big IDs as **strings** |

```python
import json
import re
from datetime import datetime

# Big integer IDs (e.g. Postgres BIGINT, Twitter-style snowflakes): send as strings
payload = {"id": str(row["id"])}

# Dates: agree on ISO 8601 in UTC, and revive them on read
ISO_INSTANT = re.compile(r"^\d{4}-\d{2}-\d{2}T")


def revive_dates(obj: dict) -> dict:
    return {k: datetime.fromisoformat(v) if isinstance(v, str) and ISO_INSTANT.match(v) else v for k, v in obj.items()}


data = json.loads(text, object_hook=revive_dates)  # or declare the field as datetime in a Pydantic model
```

Other things worth knowing:
- **Duplicate keys** (`"role"` twice): the JSON spec says behaviour is unpredictable. `json.loads` keeps the last one (`{'role': 'admin'}` for `"user"` then `"admin"`; pass `object_pairs_hook` to detect duplicates); another parser may keep the first. Attackers use these mismatches between a proxy and a backend.
- **Serialization leaks data.** `return dict(user_row)` sends **every column**, including `password_hash`. Serialize an explicit response shape (a Pydantic `response_model`), not your database row.
- **Deserialization is untrusted input.** A well-formed JSON body can still have wrong types, huge strings, or keys like `__class__`. Always cap the body size and validate the parsed value against a schema.
- **Never deserialize with code execution.** Formats that rebuild arbitrary objects (Python `pickle`, Java native serialization, `eval` on JSON text) let an attacker run code. JSON parsers only produce plain data, which is a big part of why JSON is safe as a wire format.
- ➕ **Signing or hashing JSON needs exact bytes.** `json.dumps` output depends on key order, separators (`", "` and `": "` by default) and number formatting, so two equal objects can hash differently. Verify signatures over the **raw received bytes** ([lesson 30](/docs/backend-first-principles/30-webhooks) shows this for webhooks); if you must hash a structure you built yourself, use a canonical form such as RFC 8785 (JCS: sorted keys, no whitespace, ECMAScript number formatting).

### Class pollution: when parsed JSON meets a merge ➕

The `__class__` bullet above deserves its own explanation, because it turns "JSON is plain data" into a privilege-escalation bug in real Python codebases. (JavaScript has the same class of bug under the name **prototype pollution**, through the `__proto__` key.)

#### How a JSON key reaches a class ➕

**Problem.** A request body of `{"__class__": {"is_admin": true}}` makes `Settings().is_admin` return `True` for every instance in the process.

**Why it happens (first principles).** In Python, every object exposes **dunder attributes**: `obj.__class__` is its class, `obj.__init__.__globals__` is the dict of module globals where the class was defined. `json.loads` itself is safe: it produces a `dict` with a plain string key `"__class__"`, and nothing is polluted yet. The damage happens later, when code copies that dict onto **objects** with `getattr`/`setattr` (a "merge user settings into the config object" helper). `getattr(settings, "__class__")` returns the shared class, and a recursive merge then writes attacker-chosen attributes onto it.

```python title="pollution_demo.py (do not use this merge)"
import json


class Settings:
    def __init__(self) -> None:
        self.theme = "light"


body = json.loads('{"__class__": {"is_admin": true}}')
list(body)  # ['__class__']: a plain dict key, harmless so far


def naive_merge(target, src: dict) -> None:
    for key, value in src.items():
        if isinstance(value, dict):
            if isinstance(target, dict):
                child = target.setdefault(key, {})
            else:
                child = getattr(target, key, None)  # getattr(settings, "__class__") is the Settings class
                if child is None:
                    child = {}
                    setattr(target, key, child)
            naive_merge(child, value)
        elif isinstance(target, dict):
            target[key] = value
        else:
            setattr(target, key, value)


naive_merge(Settings(), body)  # e.g. "merge user settings into defaults"
Settings().is_admin  # True: EVERY instance now inherits is_admin
```

**Edge cases.** Merging into **dicts** only (`{**defaults, **body}`, `dict.update`, a recursive merge that only uses `[]`) is safe: there, `"__class__"` is just a key. The danger starts the moment keys become **attribute names**. The payload `{"__init__": {"__globals__": {"DEBUG": true}}}` reaches further by another path: through the bound method to the module's globals, so the same merge flips the module-level `DEBUG` flag to `True`.

#### Defences, from strongest to backstop ➕

**Mechanism.** Stop the dangerous key before any merge, and make the prototype harder to modify.

1. **Validate before you merge.** A Pydantic model (lesson 9) outputs only the fields you declared (`extra="ignore"` drops the rest, `extra="forbid"` rejects them), so `__class__` never reaches your code. For free-form maps (user metadata, settings), validate keys against an allowlist pattern that can't start with an underscore, such as `^[a-zA-Z][a-zA-Z0-9_]{0,63}$`.
2. **Reject at parse time.** `json.loads` accepts an `object_pairs_hook` that sees every key of every object before the dict is built; reject dunder (or any non-allowlisted) keys there.
3. **Keep dynamic keys as dict keys**, never as attribute names: `setattr(obj, user_supplied_key, ...)` is the bug.
4. **Harden the objects.** Python has no runtime switch like Node's `--disable-proto`. Frozen dataclasses, frozen Pydantic models (`ConfigDict(frozen=True)`) and `__slots__` make `setattr` on **instances** fail, though they don't protect the class object itself.

```python title="safe_json.py"
import json
import re
from typing import Any

SAFE_KEY = re.compile(r"[A-Za-z][A-Za-z0-9_]{0,63}")  # tighten or loosen to your schema


def reject_unsafe_keys(pairs: list[tuple[str, Any]]) -> dict[str, Any]:
    for key, _ in pairs:
        if not SAFE_KEY.fullmatch(key):  # __class__, __init__, __globals__ never get through
            raise ValueError(f"unsafe key: {key!r}")
    return dict(pairs)


def safe_loads(raw: bytes) -> Any:
    return json.loads(raw, object_pairs_hook=reject_unsafe_keys)  # ValueError (incl. JSONDecodeError) → 400


settings = dict(validated_prefs)  # dynamic keys stay dict keys, never attributes
```

**Edge cases.** Libraries that set values by a user-supplied path (`"a.b.c"`) or merge dicts into objects are where this hides; pydash had exactly this bug (CVE-2023-26145), as did lodash's `merge`/`defaultsDeep` on the JavaScript side. Keep dependencies patched and run `pip-audit` in CI.

## 10. Types JSON doesn't have: time, money and binary ➕

Section 9 showed that dates and big numbers don't survive a naive round trip. The real job is to **agree on a representation** for each kind of value, write it into the API contract, and convert at the boundary.

### Instants, calendar dates and wall-clock times ➕

**Problem.** An event booked for "10:00 in Mumbai" shows as 04:30 to some users, a date of birth arrives one day early, and a meeting moves by an hour after a daylight-saving change.

**Why it happens.** "Time" is three different things, and JSON has a type for none of them:
- an **instant**: one point on the global timeline (when a payment happened);
- a **calendar date**: a day with no time zone (a birthday, an invoice due date);
- a **local time in a zone**: what the clock on the wall shows somewhere (a 10:00 meeting in `Asia/Kolkata`), whose mapping to an instant depends on rules that can change.

Python has a type for each (an **aware** `datetime` for an instant, `date`, and a **naive** `datetime` plus a `ZoneInfo`), but nothing stops you from mixing them up: a naive `datetime` treated as an instant (or the other way round) is what creates the off-by-one-day and off-by-one-hour bugs.

**Mechanism.** Use a distinct string format and a distinct database type for each:

| Kind | JSON | Postgres |
|---|---|---|
| Instant | RFC 3339 in UTC, e.g. `"2026-10-02T09:30:00Z"` | `timestamptz` |
| Calendar date | `"1995-06-12"` | `date` |
| Local time in a zone | local time + IANA zone, e.g. `"2026-11-03T10:00:00+05:30[Asia/Kolkata]"` (RFC 9557 syntax), or two fields | `timestamp` + a `text` zone column |

**Implementation.** psycopg already maps each Postgres type to the matching Python type: `date` → `datetime.date`, `timestamp` → a **naive** `datetime`, `timestamptz` → an **aware** `datetime` (in the session's `TimeZone`). The bugs come from mixing the kinds at the API boundary, so declare which kind each field is and let Pydantic reject the wrong one:

```python title="time_fields.py"
from datetime import date, datetime
from zoneinfo import ZoneInfo

from pydantic import AwareDatetime, BaseModel, NaiveDatetime


class Payment(BaseModel):
    paid_at: AwareDatetime  # instant: "2026-10-02T09:30:00" is rejected ("Input should have timezone info")


class Person(BaseModel):
    date_of_birth: date  # calendar date: "1995-06-12", never shifted


class Meeting(BaseModel):
    starts_at_local: NaiveDatetime  # wall-clock time...
    time_zone: str  # ...plus the IANA zone, e.g. "Asia/Kolkata"

    def starts_at(self) -> datetime:  # resolve to an instant only when needed, with current DST rules
        return self.starts_at_local.replace(tzinfo=ZoneInfo(self.time_zone))
```

**Edge cases.**
- For future events in a zone, store the **local time and the zone name**, not just an offset or a UTC instant: governments change DST rules, and only the zone name lets you recompute.
- RFC 9557 clarified that `Z` means "UTC is known, the local offset is unknown", while `+00:00` means UTC is the actual local reference. Most systems treat them the same, but don't infer a user's zone from either.
- Run servers with `TZ=UTC` so local-time conversions in libraries are at least predictable.

### Money and decimals ➕

**Problem.** `0.1 + 0.2` is `0.30000000000000004`, and a price serialized as a JSON number can come back as a slightly different value after passing through a float-based client.

**Why it happens.** JSON numbers are decimal text, but most parsers (including Python's `json.loads`, unless you pass `parse_float=Decimal`) convert them to IEEE-754 binary doubles, which can't represent most decimal fractions exactly. Postgres `numeric` is exact ([lesson 12](/docs/backend-first-principles/12-databases-postgres)), and that exactness is lost the moment the value becomes a `float` (or a JavaScript number in the client).

**Mechanism.** Never put money in a JSON number. Two common contracts:
1. an **integer in minor units** plus currency: `{"amount": 1999, "currency": "USD"}` for $19.99;
2. a **decimal string** plus currency: `{"amount": "19.99", "currency": "USD"}`.

Either way, the number of minor units depends on the currency (ISO 4217): JPY has 0 decimal places, USD 2, and KWD or BHD 3. So "multiply by 100" is a bug for some currencies.

**Implementation.** psycopg returns `numeric` as an exact `decimal.Decimal` and `bigint` as an exact `int`, so nothing is lost on read. Keep amounts as decimal strings on the wire and do arithmetic in integer minor units:

```python title="money.py"
from decimal import Decimal
from typing import Literal, Self

from pydantic import BaseModel, Field, model_validator

MINOR_UNITS = {"USD": 2, "EUR": 2, "INR": 2, "JPY": 0, "KWD": 3}


class Money(BaseModel):
    amount: str = Field(pattern=r"^-?\d{1,15}(\.\d{1,3})?$")
    currency: Literal["USD", "EUR", "INR", "JPY", "KWD"]

    @model_validator(mode="after")
    def check_decimal_places(self) -> Self:
        _, _, fraction = self.amount.partition(".")
        if len(fraction) > MINOR_UNITS[self.currency]:
            raise ValueError("Too many decimal places for this currency")
        return self

    def to_minor(self) -> int:
        return int(Decimal(self.amount).scaleb(MINOR_UNITS[self.currency]))  # "19.99" USD → 1999, exact


# Serialize back as a string, e.g. str(Decimal(minor).scaleb(-digits)): json.dumps refuses a Decimal anyway
```

**Edge cases.** Decide rounding rules (half-up, banker's rounding) when you divide, e.g. splitting a bill three ways, and put the leftover minor unit somewhere explicit. Percentages and exchange rates need more precision than the currency, so give them their own decimal string fields.

### Binary data ➕

**Problem.** JSON strings must be Unicode text, so raw bytes (an image, a signature, an encrypted blob) can't go in directly.

**Mechanism.** Encode bytes as **Base64** (or **Base64url**, which swaps `+` and `/` for `-` and `_` and is safe in URLs and headers). Base64 turns every 3 bytes into 4 characters, so payloads grow by about **33%**, and both sides must hold the encoded and decoded copies in memory.

```python
import base64

payload = {"signature": base64.urlsafe_b64encode(sig_bytes).rstrip(b"=").decode()}  # base64url, no padding


def decode_b64url(value: str, expected_len: int) -> bytes:
    raw = base64.b64decode(value + "=" * (-len(value) % 4), altchars=b"-_", validate=True)  # strict
    if len(raw) != expected_len:
        raise ValueError("wrong length")
    return raw
```

**Edge cases.**
- `json.dumps(b"...")` raises `TypeError`, which is the good case. Pydantic is less obvious: a `bytes` field serializes as **UTF-8 text** by default, so arbitrary bytes fail with `PydanticSerializationError: invalid utf-8 sequence`. Set `ser_json_bytes="base64"` in the model config, or use `Base64Bytes`. Encode explicitly.
- Validate before and after decoding. Python's `base64.b64decode` and `urlsafe_b64decode` are lenient by default: they **discard** characters outside the alphabet (`b64decode("aGk=!!!")` returns `b'hi'`) instead of failing. Pass `validate=True`, as above. Check the string with a regex such as `^[A-Za-z0-9_-]+$` and check the decoded length (a 32-byte key must decode to exactly 32 bytes).
- For anything bigger than a few kilobytes, don't embed it. Use `multipart/form-data` or a presigned object-storage upload and pass a key in JSON ([lesson 24](/docs/backend-first-principles/24-object-storage-part-1)).

## 11. Evolving the contract: compatibility over time ➕

Everything so far assumed both sides use the **same** shape. In production the writer and the reader are deployed at different times, and stored data outlives the code that wrote it, so the format has to survive change.

### Backward and forward compatibility ➕

**Problem.** You add a field and deploy the API. Mobile apps released last year still parse responses with the old model, and messages written yesterday are still in the queue.

**Why it happens.** Serialization couples two programs through a format, but you can never upgrade every reader and every stored byte at the same instant. During a rolling deploy, old and new versions of your own service run side by side for minutes.

**Mechanism.** Name the two directions precisely and decide which ones each format must support:
- **Backward compatible:** **new** code can read data written by **old** code (yesterday's queue messages, last year's JSONB rows).
- **Forward compatible:** **old** code can read data written by **new** code (old app versions reading your new responses).

<Mermaid chart={`flowchart LR
  OW["Old writer"] -->|"backward compatibility:<br/>new reader must cope"| NR["New reader"]
  NW["New writer"] -->|"forward compatibility:<br/>old reader must cope"| OR["Old reader"]`} />

**Deploy-order rule that follows:** when a change needs both, deploy readers first (they accept old and new shapes), then writers, then remove the old shape once nothing produces it.

### Safe and breaking changes in JSON APIs ➕

**Mechanism.** Forward compatibility in JSON depends on the **tolerant reader** principle: clients ignore fields they don't know. With that, most additions are safe:

| Change | Safe? | Why |
|---|---|---|
| Add an optional response field | Yes, if readers ignore unknown keys | Old clients skip it |
| Add an optional request field with a default | Yes | Old clients never send it; the server uses the default |
| Add a **required** request field | **No** | Every old client now gets 400 |
| Rename or remove a field | **No** | Old readers lose data; do it as add new, migrate, then remove |
| Change a type (`"id": 1` to `"id": "1"`) | **No** | Strict parsers reject it |
| Add a value to an enum | **Often no** | Clients with an exhaustive `switch` crash or show nothing |

**Implementation.** Make your own consumers tolerant on purpose, and keep strictness where it protects you (incoming requests):

```python title="client_schemas.py"
from typing import Literal

from pydantic import BaseModel, ConfigDict, field_validator


# Reading ANOTHER service's response: tolerate additions
class Payment(BaseModel):  # extra="ignore" is the default: unknown keys are dropped, not errors
    id: str
    status: Literal["pending", "paid", "failed", "unknown"]

    @field_validator("status", mode="before")
    @classmethod
    def unknown_status(cls, value: object) -> object:
        return value if value in ("pending", "paid", "failed") else "unknown"  # new enum values don't crash us


# Validating requests TO you: strict, unknown keys rejected (lesson 9)
class CreatePayment(BaseModel):
    model_config = ConfigDict(extra="forbid")
    amount: str
    currency: str
```

**Edge cases.** A breaking change still needs a new API version or a new field name; how to version URLs and headers is covered in [lesson 11](/docs/backend-first-principles/11-rest-api-design). Document that clients must ignore unknown fields, otherwise every addition is a negotiation.

### Evolving Protobuf schemas ➕

**Problem.** Someone deletes field 3 and, months later, reuses number 3 for a new field of a different type. Old messages in storage now decode garbage into the new field.

**Why it happens.** On the wire there are only numbers (section 4). The field **number** and wire type are the contract; the name is just for humans.

**Mechanism.** The official rules: adding and removing fields is safe; changing an existing field's number is not; and when you delete a field you must **reserve** its number (and ideally its name) so it can never be reused.

```proto title="book.proto (v2)"
message Book {
  reserved 3;                 // author was field 3: never reuse it
  reserved "author";
  int32  id      = 1;
  string title   = 2;
  repeated string authors = 4; // the replacement gets a NEW number
}
```

**Edge cases.** Some type changes are wire-compatible (`int32`, `int64`, `uint32`, `uint64` and `bool` all use varints) but values can be truncated when an old reader sees a large number. Run a breaking-change checker such as `buf breaking` in CI so these rules are enforced by a machine, not by memory.

### Versioned payloads for queues, caches and stored JSON ➕

**Problem.** A worker deployed with a new job shape picks up a job enqueued an hour ago in the old shape and crashes. A JSONB column contains five historical shapes. A cache returns an object serialized by the previous release.

**Why it happens.** HTTP responses are consumed immediately, but **stored** serialized data has no expiry date on its format. Any code that reads it must handle every shape that was ever written and not yet deleted.

**Mechanism.** Put an explicit **version** in an envelope, keep a parser for each version still in circulation, and **upcast** old versions to the current one at the read boundary so business logic only sees the latest shape.

```python title="job_payload.py"
from typing import Annotated, Literal

from pydantic import BaseModel, Field, TypeAdapter


class V1(BaseModel):
    v: Literal[1]
    user_id: str
    email: str


class V2(BaseModel):
    v: Literal[2]
    user_id: str
    locale: str = "en"


Payload = TypeAdapter(Annotated[V1 | V2, Field(discriminator="v")])


def read_job(raw: object) -> V2:
    match Payload.validate_python(raw):
        case V1(user_id=user_id):
            return V2(v=2, user_id=user_id, locale="en")  # upcast: v1 had no locale
        case V2() as current:
            return current


def write_job(user_id: str, locale: str) -> dict:
    return V2(v=2, user_id=user_id, locale=locale).model_dump()
```

**Edge cases.**
- During a rolling deploy, **old** workers may receive **new** jobs. Ship the reader for v2 one release before any producer writes v2.
- Include the format version in **cache keys** (`user:v3:42`) so a deploy reads a fresh key instead of a stale shape.
- Delete a version's reader only after the data is gone: queues drained, caches expired, and JSONB rows migrated with a backfill.

## 12. Recap 🎓

- Client and server can be written in **completely different languages** with incompatible types. Memory can't be shared, only bytes.
- The fix is a **common standard**: the sender **serializes** native data into it, the receiver **deserializes** it into its own types, in both directions.
- As a backend engineer, think at the **application layer**: JSON goes out, JSON comes in. The OSI layers in between aren't your concern.
- Formats are **text-based** (JSON, YAML, XML) or **binary** (Protobuf, …). **JSON** dominates HTTP APIs.
- JSON rules: braces, **double-quoted string keys**, values that are strings, numbers, booleans, arrays or nested objects.
- ➕ Protobuf replaces key names with **tags** (`(field_number << 3) | wire_type`) and packs integers as **varints**; field numbers are the contract.
- ➕ `json.loads`/`json.dumps` are synchronous: cap body sizes, and **stream** (element-by-element parsing, NDJSON with cursors) when payloads are large.
- ➕ Parsed JSON can carry `__class__`; **class pollution** (JavaScript's prototype pollution) happens in naive attribute merges. Validate first, reject dunder keys at parse time, keep dynamic keys in dicts.
- ➕ Pick explicit representations for **instants, calendar dates, zoned times, money and bytes**; never send money as a JSON number.
- ➕ Formats evolve: know **backward vs forward compatibility**, add rather than change, reserve Protobuf numbers, and **version** stored payloads.

## Interview questions

1. **What are serialization and deserialization?** Converting native in-memory data to a common, language-neutral format (serialize) and back into native types (deserialize), for transmission or storage.
2. **Why can't a JS client just send its object to a Rust server?** An object is a runtime memory structure specific to that process and language. Only bytes cross the network, and both sides must agree on what the bytes mean.
3. **Text vs binary formats: when do you pick each?** Text (JSON) for readability, debuggability and zero-setup browser APIs. Binary (Protobuf) for smaller payloads and faster parsing between services, at the cost of needing a schema.
4. **What are JSON's rules for keys and values?** Keys are double-quoted strings. Values are strings, numbers, booleans, null, arrays or nested objects.
5. **Name three things that don't survive a `json.dumps` → `json.loads` round trip.** Tuples (become lists), integer dict keys (become strings), `NaN`/`Infinity` (written as invalid JSON). `datetime`, `Decimal`, `set` and `bytes` don't serialize at all (`TypeError`).
6. **Why send a 64-bit ID as a string in JSON?** Most JSON parsers read numbers as IEEE-754 doubles, which are exact only up to 2^53; larger IDs get silently rounded.
7. **Why is returning a raw database row dangerous?** It serializes every column, including secrets like password hashes. Serialize an explicit response shape.
8. **Is a successfully parsed JSON body safe to use?** No. Parsing only proves the syntax is valid; types, ranges and size still need validation.
9. ➕ **How does Protobuf identify a field without its name?** Each value is preceded by a varint tag, `(field_number << 3) | wire_type`. The wire type tells the parser how to read or skip the value; the number maps it to the schema.
10. ➕ **Why can a 50 MB JSON upload hurt unrelated users on a Python async server?** `json.loads` is synchronous and O(n) on the event-loop thread, so every other request on that worker waits. Cap sizes, stream large payloads, or move them to object storage and a background job.
11. ➕ **`json.loads` only builds dicts, so where does class pollution come from?** From code that later copies the parsed dict onto objects with `getattr`/`setattr`, e.g. a recursive merge: `getattr(obj, "__class__")` resolves to the class (and `__init__.__globals__` to module globals) and attacker keys land on it.
12. ➕ **How should an API send a price?** As an integer in minor units or a decimal string, always with a currency code, and with the currency's own number of decimal places (ISO 4217). Never as a float.
13. ➕ **Backward vs forward compatibility?** Backward: new code reads data written by old code. Forward: old code reads data written by new code. Tolerant readers and additive changes give you both.
14. ➕ **You delete a Protobuf field. What must you do?** Reserve its number (and name) so it's never reused with a different meaning, and give any replacement a new number.
