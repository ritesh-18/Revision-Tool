## 1. What a test is, and why you write one 🎓

**A test is a second program that runs your program and makes claims about what happened.** It calls your code with inputs you chose in advance, looks at the output, and complains (throws, fails, panics) if it isn't what you expected.

People write tests for several reasons: as **guidance** (TDD, writing the test first so the goal is clear), as **documentation**, but above all **to catch regressions**.

**Regression:** a bug you already fixed (or a feature that used to work) that **comes back**. Someone changes a function, an interface or a piece of logic months later, and an old behaviour silently breaks. That's normal in a team. Tests make it **visible immediately** instead of via a user complaint.

**Scope of this lesson:** what a **backend engineer writes and runs themselves**, roughly **80%** of the testing in a normal team. Not covered: corporate manual QA, test-management tools, mobile testing, front-end browser automation.

### The codebase under test 🎓
The same task board as the real-time lesson, about **11 Go files**:

| Package | Role |
|---|---|
| `cmd/board` | The executable. `main` is the **only** place that wires everything together |
| `internal/board` | The domain: tasks, columns, moves |
| `internal/hub` | Rooms (one per board); each subscriber in a room has its own counter |
| `internal/bus` | An **interface with two methods** and **two implementations**: in-process (used in tests) and Redis (used in production) |
| `internal/store` | An interface with three methods, backed by Postgres |
| `internal/httpapi` | The route table: one file lists every endpoint |

The `bus` package shows a core use of interfaces: **one API, two implementations behind it**, so tests can swap one in. The codebase starts with **no tests**.

## 2. A test is a program; a runner writes its `main` 🎓

### Without any framework
Call some backend function from another function (call it "the test"), and write `if (output !== 20) throw new Error(...)`. **That is a test.** Everything else is convenience.

### Why frameworks exist
Hand-writing conditions, runners and mocks for every test doesn't scale. Libraries solve those problems once for everyone. What a language or framework gives you is mainly a **test runner**: a program that **finds** all your test files, **runs** them and **reports** what passed and failed.

### What the demo shows 🎓
- The first test creates a board, moves a task between columns and checks where it ended up. The expectation is wrong **on purpose**: the runner prints the **file, line number, what it wanted and what it got** (the task was in `doing`, the test wanted `done`). Fix the expectation, rerun, and it passes instantly.
- `go test -work` keeps the build folder. Inside is a file called **`_testmain.go`** that **the tool wrote**, not you: `package main`, a list of every test function it found, and a `func main` that calls `testing.MainStart` then `os.Exit`.
- `go test -x` prints every command the tool runs: it links a binary called **`board.test`**, then runs it.

**So:** `go test` **writes a `main`, compiles it into a program and executes it.** That is what any runner does, in any language.

```ts title="board.test.ts"
  const board = Board.withTasks([{ id: 't1', column: 'todo' }]);
  board.move('t1', 'doing');
  expect(board.task('t1').column).toBe('doing');
});
```

## 3. Assertions, and failure messages that help 🎓

**An assertion is a check that fails (or stops) the test when its condition isn't true.** Most languages use a library for them (`assertEquals`, `assertNotEquals`, ...). Go's standard library has none: you write an `if` and call `t.Errorf` with a message you compose yourself.

**Rule:** whatever the language, make the failure message say **what was checked, what was expected and what actually happened**, with enough context to debug without rerunning.

```go title="Go (from the lesson's style)"
if got := b.Task("t1").Column; got != "done" {
    t.Errorf("Move(t1, done): column = %q, want %q", got, "done")
}
```

```ts title="Jest: compare whole objects so the diff carries the context"
// ❌ on failure you only see "Expected: 200, Received: 409"
expect(res.status).toBe(200);

// ✅ on failure Jest prints the whole diff, including the error body the API returned
expect({ status: res.status, body: res.body }).toEqual({ status: 200, body: expect.objectContaining({ column: 'done' }) });
```

🔧 Jest's `expect` takes no custom message argument, so **name the test after the behaviour** (`'rejects todo -> done without doing'`) and prefer specific matchers (`toEqual`, `toMatchObject`, `toThrow(/must pass through doing/)`) so the diff itself is the message.

## 4. Snapshot assertions and their traps ➕

Snapshots are the most popular shortcut for writing assertions in Jest, and they fail the rule above (say what was expected) in specific, predictable ways, so they deserve their own look.

#### 4.1 What a snapshot actually asserts ➕

**Problem.** A `GET /boards/412` response has 40 fields. Writing `toEqual` for all of them is tedious, so the test says `expect(res.body).toMatchSnapshot()`. Six months later it fails on a pull request, and the reviewer sees a 200-line diff and presses `u` to update.

**Why (first principles).** A snapshot assertion is "**the output equals whatever it was last time**". The expected value isn't written by a person who decided what's correct; it's **recorded** from the code's own output on its first run. So a snapshot is a **change detector** (the same idea as section 11), applied to output instead of interactions: it tells you **something changed**, not **whether the change is wrong**. If the first recording contained a bug, the snapshot now protects the bug.

**Mechanism.** Use snapshots where "did anything change?" **is** the question and a human can review the diff in seconds:
- Small, stable, serialised output: a generated SQL string, an error payload, an OpenAPI document (lesson 29), a CLI's `--help`.
- Prefer **inline snapshots** (`toMatchInlineSnapshot`), which write the expected value into the test file so reviewers see it in the PR, over `.snap` files nobody opens.
- For behaviour that matters (the column is `done`, the price is 90), write explicit assertions.

**Implementation.**

```ts title="snapshots used well"
// ✅ small, stable, reviewable: the error contract clients depend on
test('invalid move error shape', async () => {
  const res = await request(app).post('/tasks/t1/move').send({ to: 'done' });
  expect(res.body).toMatchInlineSnapshot(`
    {
      "code": "INVALID_TRANSITION",
      "message": "must pass through doing",
    }
  `);
});

// ❌ 40 fields, nobody reviews it, and the business rule is buried in it
expect(res.body).toMatchSnapshot();

// ✅ assert the rule explicitly, snapshot nothing
expect(res.body).toMatchObject({ id: 't1', column: 'doing' });
```

**Edge cases.** A snapshot of a **large** object is effectively "assert nothing specific" with extra steps. If a snapshot changes in most PRs, delete it and write the two or three assertions that matter.

#### 4.2 Non-deterministic fields and CI behaviour ➕

**Problem.** The snapshot contains `id: "8f3c..."` and `createdAt: "2026-10-02T09:14:..."`. It fails on every run, so someone adds `jest -u` to the test script, which silently **accepts any change**.

**Why (first principles).** A snapshot compares **every byte**, so any value that differs per run (UUIDs, timestamps, random ordering of a `Set`) makes it fail for reasons unrelated to behaviour. And by default, Jest **writes** a missing snapshot instead of failing, so a snapshot that was never committed passes in CI.

**Mechanism.**
- Pass **property matchers** for the volatile fields: `toMatchSnapshot({ id: expect.any(String), createdAt: expect.any(Date) })`. Jest checks those fields by type and snapshots the rest.
- Better: make the values deterministic at the source with an injected clock and ID generator (section 16.3 and 16.5).
- Run CI with **`--ci`**: Jest then **fails** on a new snapshot instead of storing it, so a missing `.snap` file can't pass.

**Implementation.**

```ts
test('created task payload', async () => {
  const task = await svc.create({ title: 'Write tests', column: 'todo' });
  expect(task).toMatchSnapshot({ id: expect.any(String), createdAt: expect.any(Date) });
});
```

```json title="package.json"
{ "scripts": { "test": "jest", "test:ci": "jest --ci" } }
```

**Edge cases.** Never put `-u` in a script; updating snapshots should be a deliberate local action whose diff is reviewed. Sort collections before snapshotting if their order isn't part of the contract.

## 5. Regressions and CI 🎓

The payoff of a test suite: in **CI** (e.g. GitHub Actions), the whole suite runs on **every PR before it merges**. If any test fails, the new code reintroduced an old bug, and you know **before** users do. That lets a team **move fast** without fear, because the suite enforces that every past bug **stays fixed**.

🔧 A minimal workflow with a real Postgres for the medium tests:

```yaml title=".github/workflows/test.yml"
name: test
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm test -- --ci --coverage   # Testcontainers starts Postgres itself (Docker is available on ubuntu runners)
```

## 6. Keeping the suite fast in CI: workers, isolation and sharding ➕

A suite that runs on every PR is only useful while it's **fast enough that nobody routes around it**, and the cheap ways to speed it up (more parallelism) break tests that share state.

#### 6.1 What Jest runs in parallel, and what it shares ➕

**Problem.** The suite takes 14 minutes. Someone adds `--maxWorkers=8` and half the database tests start failing at random.

**Why (first principles).** Jest runs **test files** in parallel in separate **worker processes** (by default, the number of cores minus one in single-run mode), while tests **inside one file** run one after another. Each worker has its own module registry, so in-memory globals are isolated per file. But **everything outside the process is shared**: the one Postgres container, the one Redis, the file system, fixed ports. Two files that both `TRUNCATE tasks` or both listen on port 3000 now collide. Parallelism didn't create the bug; it exposed shared external state (the "test order dependency" cause in section 20).

**Mechanism.** Give every parallel unit its **own copy** of each external resource, or prove it doesn't need one:
- Ports: listen on `0` and read the assigned port.
- Files: a temp directory per test (`fs.mkdtemp`).
- Database: per test or per worker (6.2).
- Redis: a key prefix or a logical DB number per worker.

**Implementation.**

```ts title="test/worker-env.ts (setupFiles)"
const worker = Number(process.env.JEST_WORKER_ID ?? 1);   // 1-based, and 1 for every test with --runInBand
process.env.REDIS_KEY_PREFIX = `test:w${worker}:`;
process.env.TMP_ROOT = require('node:os').tmpdir() + `/board-tests-w${worker}`;
```

**Edge cases.** CI runners often have **2 to 4 cores**, and Jest's default can overload them while containers also need CPU. `--maxWorkers=50%` is a reasonable start; measure, don't guess.

#### 6.2 Database isolation per worker: schema per worker ➕

**Problem.** Section 16 shows two isolation strategies: a **transaction per test** (fast, but code that opens its own connections or commits can't use it) and a **database per test from a template** (fully isolated, but thousands of `CREATE DATABASE` calls on a large suite, and cleanup to manage). There's a middle option that suits many suites.

**Why (first principles).** Isolation only has to hold between things that run **at the same time**. Tests in one Jest worker run sequentially, so they can share a database **with each other** as long as each test cleans up, and only **different workers** need to be separated. Postgres **schemas** are cheap namespaces inside one database, and `search_path` controls which one unqualified table names resolve to.

**Mechanism.** At worker start, create schema `w1`, `w2`, ... and run migrations into it (or clone from a template database per worker, once). Point the worker's pool at it with `search_path`. Between tests in that worker, truncate.

**Implementation.**

```ts title="test/db-per-worker.ts"
import { Pool } from 'pg';

const schema = `w${process.env.JEST_WORKER_ID ?? 1}`;
export const pool = new Pool({ connectionString: process.env.TEST_DATABASE_URL, options: `-c search_path=${schema}` });

beforeAll(async () => {
  await pool.query(`DROP SCHEMA IF EXISTS ${schema} CASCADE`);
  await pool.query(`CREATE SCHEMA ${schema}`);
  await runMigrations(pool);                                  // migrations create tables in search_path
});

afterEach(async () => {
  const { rows } = await pool.query(`SELECT tablename FROM pg_tables WHERE schemaname = $1 AND tablename <> 'migrations'`, [schema]);
  if (rows.length) await pool.query(`TRUNCATE ${rows.map((r) => `"${r.tablename}"`).join(', ')} RESTART IDENTITY CASCADE`);
});

afterAll(() => pool.end());
```

| Strategy | Isolation | Cost per test | Fits code that commits or opens connections |
|---|---|---|---|
| Transaction per test | Per test | Lowest | No |
| Template DB per test | Per test | A few ms plus a `CREATE DATABASE` | Yes |
| Schema per worker + truncate | Per worker | A `TRUNCATE` | Yes |

**Edge cases.**
- Migrations that hard-code `public.` bypass `search_path`; keep table names unqualified, or migrate a template database per worker instead.
- Running migrations once **per file** (this `beforeAll` runs per test file) can dominate time; move the schema creation into a per-worker cache or a `globalSetup` that prepares `w1` to `wN` up front.

#### 6.3 Sharding across CI machines and running the slow tests first ➕

**Problem.** One machine, fully parallel, still takes 9 minutes because it has 4 cores. You want results in 3.

**Why (first principles).** Workers divide work across **cores**; to go further you divide it across **machines**. Jest's `--shard=i/n` (1-based) splits the test files into `n` groups and runs group `i`, so `n` CI jobs each run a slice. The total CPU time is the same, but wall-clock time drops roughly by `n`, minus the fixed cost each job pays (checkout, `npm ci`, container start).

**Mechanism.** A CI **matrix** with one job per shard, each with its own containers (so isolation is automatic across machines). Merge the coverage reports at the end.

**Implementation.**

```yaml title=".github/workflows/test.yml (sharded)"
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix: { shard: [1, 2, 3, 4] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npx jest --ci --shard=${{ matrix.shard }}/4 --coverage --coverageDirectory=coverage/${{ matrix.shard }}
      - uses: actions/upload-artifact@v4
        with: { name: coverage-${{ matrix.shard }}, path: coverage/${{ matrix.shard }} }
```

**Edge cases.**
- Shards are balanced by **file**, not by time; one 3-minute file can make one shard the long pole. Split very slow files.
- Coverage thresholds (section 21) must be checked on the **merged** report, not per shard, or each shard fails for code that other shards cover.
- On local runs, `--changedSince=origin/main` runs only tests related to changed files, which is a good pre-push check but **not** a replacement for the full suite in CI (it relies on a static dependency graph).

## 7. Kinds of tests by scope 🎓

### Unit tests
**A test of one unit of code in isolation.** What's a unit: a function, a struct, a package, a service? **There's no universal answer**; you learn to recognise it. If a function calls two or three others, you can let it call the **real** ones or hand it **mocks**, and **both** count as unit tests.

### What the demo shows: one behaviour, four ways 🎓
The same "move a task" behaviour is tested four ways:

| # | Setup | Time |
|---|---|---|
| 1 | Board with a **mock bus** (just records what it was asked to publish) | about 0 s |
| 2 | **Real bus + real hub**: the move actually reaches a subscriber | about 0 s |
| 3 | A **real HTTP server on a real port**, a real POST, reading the real response | about 0 s |
| 4 | Same check against a **real Postgres** | **10.5 s**, mostly the container booting |

**The lesson:** the expensive part of a test **isn't how much logic it covers**; test 3 went through the entire HTTP stack and still took about zero. **What costs time is leaving the process** and going into external territory.

### Integration and end-to-end tests 🎓
- **Integration test:** checks **two or more parts working together**. Usually one part is your code and the other is **something you didn't write**, like a database.
- **End-to-end (E2E) test:** goes through the whole system **the way a real user would**: log in first, keep that session, open the dashboard, call the API, create a task. An integration test may **bypass** steps (call internal logic directly, skip the auth middleware); an E2E test **must follow the user's path**.

### The test pyramid 🎓

<Mermaid chart={`flowchart TB
  E2E["E2E: few<br/>slow, expensive, follow the user's journey"]
  INT["Integration: some<br/>real DB / real services"]
  UNIT["Unit: many<br/>fast, cheap, in-process"]
  E2E --- INT --- UNIT`} />

The pyramid is **about cost**: wide cheap base, narrow expensive top. "Expensive" means CPU, memory and time, not just money. The higher you go, the slower and costlier each test is.

### A more practical model: what a test is allowed to touch 🎓
Instead of "how much of the system does this test cover?", ask **"how much is it allowed to touch?"**

| Size | May touch | May not touch |
|---|---|---|
| **Small** | One process only | Network, database, file system, `sleep` |
| **Medium** | Things **on the same machine**: Postgres or Redis in local containers | Anything off the machine (the internet) |
| **Large** | Anything | Nothing is off limits |

**Why it's better:** nobody can objectively check whether a test is "really a unit test", since nobody agrees on the definition. But **the machine can check whether a test opened a socket.** So size becomes an **enforceable rule**, not an opinion.

**It also attacks flakiness:** most nondeterminism comes from **outside the machine** (other services, their clocks, the network). Keep tests on the machine and you can push determinism to its peak.

🔧 Enforcing "small" in Jest: block real network in unit tests.

```ts title="test/setup-small.ts (jest setupFiles for the unit project)"
import nock from 'nock';
nock.disableNetConnect();           // any real HTTP call now throws
nock.enableNetConnect('127.0.0.1'); // remove this line for strictly in-process tests
```

```js title="jest.config.js"
module.exports = {
  projects: [
    { displayName: 'small',  testMatch: ['<rootDir>/src/**/*.test.ts'],     setupFiles: ['<rootDir>/test/setup-small.ts'] },
    { displayName: 'medium', testMatch: ['<rootDir>/test/**/*.int.test.ts'] },  // may start containers
  ],
};
```

### Other names are variations, not new kinds 🎓
| Name | Question it answers |
|---|---|
| **Regression** | Does a specific bug we fixed stay fixed? |
| **Functional** | Does the feature meet its specification? (the test-first idea from TDD) |
| **Performance** | How fast, and how much CPU and memory? |
| **Security** | Does the program bypass a security layer or leak private data (containers, file system, cookies)? |

They're all **variations of unit, integration or E2E**: a regression test can be a unit test; a security test can be E2E. The lesson's mental model is just **scope**: in-process, in-machine, or touching the internet.

## 8. Pyramid, trophy or honeycomb: how to split the effort ➕

The pyramid above says **what each kind of test costs**; two later models argue about **where the confidence comes from**, and backend teams regularly fight about them, so it's worth knowing what each one claims and when it's right.

#### 8.1 The testing trophy and the honeycomb ➕

**Problem.** A team follows the pyramid literally: thousands of unit tests, each mocking every collaborator, and a handful of E2E tests. Coverage is high, yet bugs keep shipping in exactly the places where components meet: the SQL, the serialisation, the HTTP layer, the queue payload.

**Why (first principles).** A test gives confidence only about **what it actually executes**. A unit test with a mocked repository says nothing about the query; a mocked HTTP client says nothing about headers. When most of your code is **glue between components** (typical for a CRUD-heavy backend), most of your bugs live in the glue, and the pyramid's wide base is testing the part that rarely breaks.

**Mechanism.** Two models shift the weight toward integration tests:
- **Testing trophy** (Kent C. Dodds, 2018, inspired by Guillermo Rauch's "Write tests. Not too many. Mostly integration."): from bottom to top **static** checks (types, lint), **unit**, **integration** (the biggest part), **E2E**. Static analysis is free confidence, so it sits at the base.
- **Testing honeycomb** (Spotify, 2018, for microservices): mostly **integration tests** of one service with its real database, few **implementation-detail** (unit) tests, and as few **integrated** tests as possible. Spotify defines an integrated test as one that passes or fails based on **another system's** correctness.

<Mermaid chart={`flowchart LR
  subgraph Pyr["Pyramid"]
    P1["E2E: few"] --- P2["Integration: some"] --- P3["Unit: most"]
  end
  subgraph Tro["Trophy"]
    T1["E2E: few"] --- T2["Integration: most"] --- T3["Unit: some"] --- T4["Static: base"]
  end
  subgraph Hon["Honeycomb"]
    H1["Integrated: almost none"] --- H2["Integration: most"] --- H3["Implementation detail: few"]
  end`} />

**Implementation.** In this page's vocabulary, "integration" in the trophy and honeycomb is mostly the lesson's **medium** test: the real service in-process, real Postgres in a container, HTTP calls through the real router.

```ts title="tasks.int.test.ts (the honeycomb's main kind of test)"
test('moving a task to done is persisted and returned', async () => {
  const app = await createApp({ databaseUrl: await freshDb(), bus: new InProcessBus() });
  const { body: task } = await request(app).post('/boards/412/tasks').send({ title: 'Write tests' }).expect(201);
  await request(app).post(`/tasks/${task.id}/move`).send({ to: 'doing' }).expect(200);
  const { body } = await request(app).get(`/tasks/${task.id}`).expect(200);
  expect(body).toMatchObject({ id: task.id, column: 'doing' });
});
```

**Edge cases.** The models agree more than the arguments suggest: all three want E2E tests **few**, and all three are about **cost versus confidence**. The pyramid is right where logic is dense (pricing, permissions, state machines in the functional core, section 14); the trophy and honeycomb are right where code is mostly wiring. Pick per module, not per company.

#### 8.2 Choosing per module: a decision rule ➕

**Problem.** "Mostly integration" applied everywhere makes a pricing engine's 200 rule combinations into 200 slow database tests; "mostly unit" applied everywhere leaves the repository layer untested.

**Why (first principles).** The right level is the **cheapest test that can fail for the bug you're worried about**. A rounding bug in `priceFor()` can be caught by a pure function call. A missing unique constraint can only be caught by a real database. A broken auth middleware ordering can only be caught by a request through the real router.

**Mechanism.** For each module ask where its bugs live:

| Where the bugs live | Cheapest test that catches them | Example on the board |
|---|---|---|
| Branching logic and calculations | Small (pure function) | `canMove`, `priceFor` |
| SQL, constraints, transactions | Medium (real Postgres) | `PgTaskRepo` |
| Wiring: routing, middleware, serialisation | Medium (HTTP through the app) | `POST /tasks/:id/move` |
| Cross-service agreements | Contract tests (section 13) | Billing service calling the board API |
| The user journey across systems | Large (E2E), a few | Sign up, pay, create a board |

**Implementation.** Encode the decision in the Jest projects from section 7, so each kind runs with the right setup and the slow ones can be sharded (section 6):

```js title="jest.config.js"
module.exports = {
  projects: [
    { displayName: 'small',  testMatch: ['<rootDir>/src/**/*.test.ts'], setupFiles: ['<rootDir>/test/setup-small.ts'] },
    { displayName: 'medium', testMatch: ['<rootDir>/test/**/*.int.test.ts'], globalSetup: '<rootDir>/test/pg-global-setup.ts' },
    { displayName: 'contract', testMatch: ['<rootDir>/test/**/*.pact.test.ts'] },
  ],
};
```

**Edge cases.** Revisit the split when bugs escape: every production bug should come with a question, "what is the cheapest test that would have caught this?", and that's the test to add.

## 9. Performance and load tests in CI ➕

Section 7 lists performance tests as a variation of the main kinds; this section shows how to make them **pass or fail** automatically, because a performance test that only produces a graph someone might look at never stops a regression. (How to scale once you find a bottleneck is in the scaling lessons, 21 and 22.)

#### 9.1 Micro-benchmarks for hot functions ➕

**Problem.** Someone rewrites the board serialiser and it's now 5 times slower. Every test still passes, because tests check **what** a function returns, not **how long** it takes.

**Why (first principles).** Time is an output like any other, but a noisy one: CI machines are shared, JIT warm-up changes the first iterations, and garbage collection pauses land randomly. A single timing is meaningless; you need many iterations, warm-up, and comparison against a **baseline**, with a tolerance wide enough to ignore noise.

**Mechanism.** Benchmark only the few **hot paths** (serialisation of a large board, the permission check run per event), with a benchmarking tool that handles warm-up and statistics, and fail only on large regressions (for example more than 30% slower than `main`).

**Implementation.** With Vitest's `bench` or a standalone tool such as `tinybench`:

```ts title="bench/serialise.bench.ts (tinybench)"
import { Bench } from 'tinybench';
import { serialiseBoard } from '../src/board/serialise';

const board = makeBoard({ tasks: 5_000 });                   // realistic size, built once
const bench = new Bench({ time: 1_000, warmupTime: 200 });
bench.add('serialiseBoard 5k tasks', () => { serialiseBoard(board); });
await bench.run();

const { mean } = bench.tasks[0].result!.latency;             // milliseconds (result shape of current tinybench)
const baseline = JSON.parse(await readFile('bench/baseline.json', 'utf8'))['serialiseBoard 5k tasks'];
if (mean > baseline * 1.3) { console.error(`regression: ${mean.toFixed(2)} ms vs ${baseline} ms`); process.exit(1); }
```

**Edge cases.** Store the baseline from the **same kind of runner** as CI, not your laptop. If the job flaps, widen the tolerance or move it to a dedicated runner; a flaky benchmark trains the same "just rerun" habit as a flaky test (section 20).

#### 9.2 Load tests with pass/fail thresholds ➕

**Problem.** The API is fast with one user. At 300 requests per second the connection pool saturates and p95 latency goes from 40 ms to 4 s. Nothing in the test suite could see that, because every test makes one request at a time.

**Why (first principles).** Many performance failures are about **contention**, not speed: pool limits, lock waits, queueing in front of a slow dependency. They only appear when requests **overlap**, so you have to generate concurrent load against a deployed environment that resembles production (same instance sizes, realistic data volume).

**Mechanism.** A load-testing tool such as **k6** describes a traffic shape (ramp to N users, hold, ramp down) and declares **thresholds** on its metrics, for example p95 duration under 300 ms and error rate under 1%. If a threshold fails, k6 exits with a non-zero code, so the CI job fails like a broken test.

**Implementation.**

```js title="load/move-task.k6.js"
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [{ duration: '2m', target: 200 }, { duration: '5m', target: 200 }, { duration: '1m', target: 0 }],
  thresholds: {
    http_req_duration: ['p(95)<300'],      // ms
    http_req_failed: ['rate<0.01'],        // under 1% errors
  },
};

export default function () {
  const res = http.post(`${__ENV.API}/tasks/${randomTaskId()}/move`, JSON.stringify({ to: 'doing' }),
    { headers: { 'content-type': 'application/json', authorization: `Bearer ${__ENV.TOKEN}` } });
  check(res, { 'status is 200': (r) => r.status === 200 });
}
```

```yaml title=".github/workflows/load.yml (nightly, against staging)"
on: { schedule: [{ cron: '0 2 * * *' }] }
jobs:
  load:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: grafana/setup-k6-action@v1
      - run: k6 run -e API=${{ secrets.STAGING_API }} -e TOKEN=${{ secrets.LOAD_TOKEN }} load/move-task.k6.js
```

**Edge cases.**
- Run load tests **nightly or before releases**, not on every PR; they're slow and need a real environment.
- Use data volumes like production; a query that's fast on 100 rows can be a sequential scan on 10 million.
- Watch the **generator** too: if the load machine's CPU is pegged, the latencies you measure are its own.

## 10. Why code is hard to test, and test doubles 🎓

### The problem
The move handler: apply the move to the board, then **publish an event on the bus** so other browsers find out (from the real-time lesson). In a real backend it would also **write to Postgres**, perhaps **call a payment provider** to check credits, and **send an email**. How do you test that without a database, a real charge and a real email?

**Answer:** give the function something that **looks and acts like** the external service. That stand-in is a **test double**, named after the **stunt double** in films: someone else does the risky stunt, and on screen it looks like the actor.

### The five doubles 🎓
"Test double" is the category. Most people call all five "mocks", but they're different tools:

| Double | What it does | Example |
|---|---|---|
| **Dummy** | Passed only because the signature needs it; **never used** | A no-op logger for a service constructor |
| **Stub** | Returns a **canned answer**, whatever you ask, however often | `getUser(7)` always returns a fixed user object |
| **Spy** | A stub that also **records** how it was called | Records "rename X to Y" was requested |
| **Mock** | Has **expectations set beforehand**; fails if they aren't met | "`save` must be called exactly once with this argument" |
| **Fake** | A **working but non-production implementation** with the same inputs and outputs | Saves users in an in-memory `Map` instead of Postgres |

```ts title="the five doubles in TypeScript"
// Dummy: satisfies the constructor, never consulted
const dummyLogger: Logger = { info() {}, warn() {}, error() {} };

// Stub: fixed answer
const usersStub: UserRepo = { findById: async () => ({ id: '7', name: 'Asha', plan: 'free' }) } as UserRepo;

// Spy: fixed answer + records calls
const calls: unknown[] = [];
const usersSpy = { ...usersStub, rename: async (id: string, name: string) => { calls.push({ id, name }); } };

// Mock: expectations are part of the double (Jest)
const bus = { publish: jest.fn() };
// ...later: expect(bus.publish).toHaveBeenCalledTimes(1)

// Fake: real behaviour, wrong storage for production
class InMemoryUserRepo implements UserRepo {
  private rows = new Map<string, User>();
  async create(u: User) { this.rows.set(u.id, u); return u; }
  async findById(id: string) { return this.rows.get(id) ?? null; }
}
```

## 11. State verification vs interaction verification 🎓

### Two ways to check the end of a test
- **State verification:** ask the system **what state it's in now**. Is the task in `done`? Did the sequence number go up by one?
- **Interaction (behaviour) verification:** ask the double **what it saw**. Was `publish` called once, with an event of type `task.moved`?

### The problem with interaction checks
Someone refactors the handler to publish **one combined event instead of two**. From outside, **nothing changed**: every browser sees the same board.
- The **state** test doesn't notice, correctly, because the end state is identical.
- The **interaction** test **fails**, because the number of calls changed.

A test that fails when the implementation changes but the behaviour doesn't is a **change-detector test** (Google's testing blog has a well-known post on it). It punishes refactoring and teaches the team to ignore red builds.

<Mermaid chart={`flowchart TD
  R["Refactor: publish 1 combined event instead of 2<br/>(external behaviour unchanged)"] --> S["State test:<br/>task in done? seq + 1?"]
  R --> I["Interaction test:<br/>publish called 2 times?"]
  S --> SP["PASS (correct)"]
  I --> IF["FAIL (false alarm = change detector)"]`} />

### The rule 🎓
**Assert on what the system *is* now, not on *how* it got there.** Use interaction checks only when the interaction **is** the behaviour, e.g. "the welcome email is sent **exactly once**".

```ts title="state over interaction"
// ✅ state: survives refactors
test('moving to doing updates column and bumps seq', async () => {
  const bus = new InProcessBus();                 // real in-process implementation
  const board = new Board(bus);
  board.add({ id: 't1', column: 'todo' });
  board.move('t1', 'doing');
  expect(board.task('t1').column).toBe('doing');
  expect(board.seq).toBe(1);
});

// ✅ interaction is legitimate here: "exactly once" IS the requirement
test('signup sends exactly one welcome email', async () => {
  const mailer = { send: jest.fn().mockResolvedValue(undefined) };
  await new SignupService(new InMemoryUserRepo(), mailer).signup('a@x.io');
  expect(mailer.send).toHaveBeenCalledTimes(1);
});
```

## 12. Don't mock what you don't own 🎓

### The problem
Your service calls a **payment provider**. You don't want to charge a real card ten times a day, so you mock their client: "when `charge` is called with these arguments, return `{ data, success, message, newBalance }`". Tests pass, you deploy, **production fails**.

**Why (first principles):** every answer the test saw was **written by you**: the shape of the success object, the field names, what happens on a duplicate charge, which errors come back in which format. The test only proved your code agrees **with your own guess** about the provider.

### The fix: two steps 🎓
1. **Wrap the third party in a small interface you own**, using **your** types: your success object, your failure object, your error messages. Use that wrapper in production **and** in tests. Now you own the interface, so you're allowed to fake it.
2. Write **a few small contract tests against the provider's sandbox** that check **the wrapper**: request shape, response shape, success and failure shapes still match the real platform. They're fast and touch no real payment data.

<Mermaid chart={`flowchart LR
  subgraph App["Your code"]
    S["BillingService"] --> P["PaymentGateway (your interface)"]
  end
  P --> A["StripeGateway adapter"]
  A --> X["Stripe API"]
  T1["Many fast tests"] -.->|"fake PaymentGateway"| S
  T2["Few contract tests"] -.->|"against sandbox"| A`} />

```ts title="payment-gateway.ts"
export type ChargeResult =
  | { ok: true; chargeId: string }
  | { ok: false; reason: 'card_declined' | 'insufficient_funds' | 'duplicate' | 'unknown' };

export interface PaymentGateway {
  charge(input: { customerId: string; amountCents: number; idempotencyKey: string }): Promise<ChargeResult>;
}

export class StripeGateway implements PaymentGateway {
  constructor(private stripe: Stripe) {}
  async charge({ customerId, amountCents, idempotencyKey }) {
    try {
      const pi = await this.stripe.paymentIntents.create(
        { customer: customerId, amount: amountCents, currency: 'usd', confirm: true /* ... */ },
        { idempotencyKey },
      );
      return { ok: true, chargeId: pi.id } as const;
    } catch (e: any) {
      if (e.code === 'card_declined') return { ok: false, reason: 'card_declined' } as const;
      return { ok: false, reason: 'unknown' } as const;
    }
  }
}

// tests use this, and it's legal because PaymentGateway is ours
export class FakeGateway implements PaymentGateway {
  charges: unknown[] = [];
  next: ChargeResult = { ok: true, chargeId: 'ch_fake_1' };
  async charge(input) { this.charges.push(input); return this.next; }
}
```

```ts title="stripe-gateway.contract.test.ts (runs against the sandbox, nightly or on adapter changes)"
const gw = new StripeGateway(new Stripe(process.env.STRIPE_TEST_KEY!));
test('declined test card maps to card_declined', async () => {
  const r = await gw.charge({ customerId: TEST_CUSTOMER_DECLINING, amountCents: 500, idempotencyKey: randomUUID() });
  expect(r).toEqual({ ok: false, reason: 'card_declined' });
});
```

## 13. Consumer-driven contract tests between your own services ➕

Section 12 handles a **third party** you can't change, by testing against its sandbox; between **two services your company owns** you can do better, because the consumer can tell the provider exactly what it relies on, and the provider's CI can check that before it deploys.

#### 13.1 The problem: two green suites, one broken system ➕

**Problem.** The billing service calls the board service's `GET /boards/:id` and reads `owner.email`. The board team renames it to `owner.contactEmail`. Their tests pass (they updated them). Billing's tests pass (they use a fake board client returning `owner.email`). Both deploy. Invoices stop sending.

**Why (first principles).** Each suite verifies one side against **its own belief** about the interface. Nothing checks that the two beliefs **match**. The only test that would catch it is an E2E test with both services running, which is slow, flaky and usually shared, and tells you **after** the merge.

**Mechanism.** **Consumer-driven contract testing** splits that E2E test into two fast halves that share a file:
1. **Consumer side:** billing's test runs its real HTTP client against a **mock provider** started by the tool. The test declares each interaction it needs (request, and the parts of the response it reads). The tool records them as a **contract** (a "pact" JSON file).
2. **Provider side:** the board service's CI **replays** every interaction from every consumer's contract against the **real** board service and checks the responses match.

The contract is **consumer-driven**: it lists only what consumers actually use, so the provider learns which fields it can change freely.

<Mermaid chart={`sequenceDiagram
  participant C as Billing tests
  participant M as Pact mock provider
  participant B as Pact Broker
  participant P as Board service CI
  C->>M: real client calls GET /boards/412
  M-->>C: response from declared interaction
  C->>B: publish contract (billing to board)
  P->>B: fetch contracts for board
  P->>P: replay each interaction against the real service
  P->>B: publish verification result
  Note over B: can-i-deploy checks both sides before release`} />

#### 13.2 Consumer side: recording the contract ➕

**Problem.** The consumer test must exercise the **real** client code (URL building, headers, parsing) without the real provider, and its expectations must be precise enough to catch the rename but loose enough not to break on unrelated values.

**Why (first principles).** If the contract says "the response is exactly this JSON", every change of an ID or a date breaks it, and teams stop trusting it. What billing relies on is the **shape**: an `owner` object with an `email` string. Matchers express shape instead of values.

**Mechanism.** Pact's JavaScript library starts a mock server per test, you point the real client at `mockserver.url`, and matchers such as `like` (same type) and `eachLike` (array of this shape) describe the response.

**Implementation.**

```ts title="board-client.pact.test.ts (in the billing service)"
import path from 'node:path';
import { Pact, Matchers, SpecificationVersion } from '@pact-foundation/pact';
import { BoardClient } from '../src/board-client';

const { like } = Matchers;
const provider = new Pact({
  consumer: 'billing',
  provider: 'board',
  dir: path.resolve(process.cwd(), 'pacts'),
  spec: SpecificationVersion.SPECIFICATION_VERSION_V4,
});

test('reads the board owner email', async () => {
  await provider
    .addInteraction()
    .given('board 412 exists with an owner')
    .uponReceiving('a request for board 412')
    .withRequest('GET', '/boards/412', (b) => { b.headers({ Accept: 'application/json' }); })
    .willRespondWith(200, (b) => {
      b.headers({ 'Content-Type': 'application/json' });
      b.jsonBody({ id: like('412'), owner: { email: like('asha@example.com') } });   // only what billing reads
    })
    .executeTest(async (mockserver) => {
      const board = await new BoardClient(mockserver.url).getBoard('412');
      expect(board.ownerEmail).toBe('asha@example.com');
    });
});
```

**Edge cases.** Declare only fields the consumer **reads**; adding "nice to have" fields turns the contract back into a snapshot of the provider. Test error interactions too (`404` for a missing board), since those are the ones teams forget.

#### 13.3 Provider side: verification and `can-i-deploy` ➕

**Problem.** A contract file nobody verifies is documentation. The board team needs their CI to **fail** if a change breaks a consumer, before merge, and a way to know which versions of each service are compatible when deploying.

**Why (first principles).** Contracts and services version independently. Billing v41 may depend on a field board v100 removed, while billing v42 doesn't. "Is it safe to deploy board v100 to production?" depends on **which consumer versions are in production right now**, so you need a record of verification results per version pair.

**Mechanism.** Consumers **publish** contracts to a **Pact Broker** (or a hosted equivalent), tagged with their version and branch. The provider's CI fetches them, starts the real service, sets up each `given(...)` **provider state** through a hook, replays the requests, and publishes the result. Before any deploy, `can-i-deploy` asks the broker whether this version has been verified against the versions **currently deployed** in that environment.

**Implementation.**

```ts title="pact.verify.test.ts (in the board service)"
import { Verifier } from '@pact-foundation/pact';

test('board honours its consumers', async () => {
  const app = await startBoardApp({ databaseUrl: await freshDb() });
  await new Verifier({
    provider: 'board',
    providerBaseUrl: app.url,
    pactBrokerUrl: process.env.PACT_BROKER_URL,
    consumerVersionSelectors: [{ deployedOrReleased: true }, { mainBranch: true }],
    publishVerificationResult: process.env.CI === 'true',
    providerVersion: process.env.GIT_SHA,
    stateHandlers: {
      'board 412 exists with an owner': async () => {
        await seedBoard({ id: '412', owner: { email: 'asha@example.com' } });   // factories, section 17
      },
    },
  }).verifyProvider();
  await app.close();
});
```

```bash
# in the deploy pipeline of either service
pact-broker can-i-deploy --pacticipant board --version "$GIT_SHA" --to-environment production
```

**Edge cases.**
- Contracts test the **interface**, not the provider's behaviour: they check that `owner.email` comes back as a string, not that it's the correct owner. Keep the provider's own tests for that.
- If the services are always deployed together from one repo, a normal integration test across both may be simpler; contract testing pays off when teams and release cycles are **independent**.
- For message-based integrations (events on a queue, webhooks from lesson 30), Pact also supports message contracts; the same rename problem applies to event payloads.

## 14. Designing for testability 🎓

### Problem: a function that builds its own dependencies
The handler was hard to test because it **created its own DB client and Redis client** and opened the connections itself. If a function constructs what it depends on, **callers can't replace it**.

### Mechanism 1: dependency injection
**Pass dependencies in** (as parameters or constructor arguments) instead of creating them inside. Frameworks for DI all do the same thing; they just make the wiring nicer as a codebase grows. NestJS is one.

```ts title="before vs after"
// ❌ untestable: reaches out and creates its own world
export async function moveTask(id: string, to: Column) {
  const db = new Pool({ connectionString: process.env.DATABASE_URL });
  const redis = new Redis(process.env.REDIS_URL!);
  /* ... */
}

// ✅ injectable
@Injectable()
export class MoveTaskService {
  constructor(private readonly tasks: TaskRepo, private readonly bus: EventBus) {}
  async move(id: string, to: Column) { /* ... */ }
}
```

```ts title="move-task.service.test.ts (NestJS testing module)"
const moduleRef = await Test.createTestingModule({
  providers: [MoveTaskService, { provide: TaskRepo, useClass: InMemoryTaskRepo }, { provide: EventBus, useClass: InProcessBus }],
}).compile();
const svc = moduleRef.get(MoveTaskService);
```

### Mechanism 2: functional core, imperative shell 🎓
Push **all decisions, calculations and business rules** into **pure functions**: values in, values out. Keep **all talking to the outside world** (HTTP, DB, providers) in a **thin layer around them**.
- **Functional core:** trivial to test, because there is **nothing to mock**; you own everything.
- **Imperative shell:** hard to test, but **so thin there's little to test**.

Structured this way, you're far more likely to actually write tests.

## 15. Property-based testing for the functional core ➕

A functional core is easy to test, but example tests still only check the inputs **you thought of**; property-based testing lets the machine search for the inputs you didn't, and pure functions are exactly where it works best.

#### 15.1 From examples to properties ➕

**Problem.** `paginate(items, { offset, limit })` has tests for page 1, the last partial page and past the end (section 22's mutation fix). It still breaks for `limit = 0`, or for an offset in the middle of the last page, because nobody wrote those examples.

**Why (first principles).** An example test asserts one point of the input space. Bugs live at **boundaries and combinations** (zero, one, maximum, negative, empty, duplicates), and the number of combinations grows faster than anyone writes examples. What you usually know isn't the output for every input but **rules that must hold for all inputs**: a page is never longer than `limit`; concatenating all pages gives back the original list; a move followed by its reverse leaves the board unchanged.

**Mechanism.** A property-based testing library such as **fast-check** generates many random inputs from **arbitraries** (descriptions of input spaces), runs your property on each (100 runs by default), and fails as soon as one input breaks it.

**Implementation.**

```ts title="paginate.property.test.ts"
import fc from 'fast-check';
import { paginate } from './paginate';

test('pages never exceed limit', () => {
  fc.assert(fc.property(
    fc.array(fc.integer()), fc.nat(50), fc.integer({ min: 1, max: 20 }),
    (items, offset, limit) => paginate(items, { offset, limit }).length <= limit,
  ));
});

test('walking all pages returns the original list in order', () => {
  fc.assert(fc.property(fc.array(fc.integer()), fc.integer({ min: 1, max: 20 }), (items, limit) => {
    const out: number[] = [];
    for (let offset = 0; offset < items.length; offset += limit) out.push(...paginate(items, { offset, limit }));
    expect(out).toEqual(items);
  }));
});
```

**Edge cases.** A property that **re-implements** the function (`expect(paginate(x)).toEqual(myOwnPaginate(x))`) just duplicates the bug. Good properties are **simpler than the code**: invariants (length bounds, totals never negative), **round trips** (`parse(serialise(x))` equals `x`), and comparisons against a slow but obviously correct **oracle**.

#### 15.2 Shrinking and reproducing a failure ➕

**Problem.** A random input that fails is often huge (an array of 73 numbers), and the next run, with different random inputs, may pass. Neither helps you debug.

**Why (first principles).** Randomness is only useful if it's **controlled**. The generator is seeded, so the same seed produces the same sequence of inputs, and the library knows how each arbitrary can be made **smaller** (shorter arrays, numbers closer to zero).

**Mechanism.** On failure, fast-check **shrinks** the input: it tries simpler variants that still fail until it reaches a minimal **counterexample**, then reports it together with the **seed** and **path** that reproduce it. You pass those back to replay the exact case, and you usually turn it into a permanent example test.

**Implementation.**

```text
Property failed after 12 tests
{ seed: 1427365120, path: "11:2:0", endOnFailure: true }
Counterexample: [[0],0,1]
Shrunk 5 time(s)
```

```ts
// reproduce exactly, while debugging
const pagesNeverExceedLimit = fc.property(
  fc.array(fc.integer()), fc.nat(50), fc.integer({ min: 1, max: 20 }),
  (items, offset, limit) => paginate(items, { offset, limit }).length <= limit,
);
fc.assert(pagesNeverExceedLimit, { seed: 1427365120, path: '11:2:0', endOnFailure: true });

// then pin it forever as a regular regression test
test('single item, first page', () => expect(paginate([0], { offset: 0, limit: 1 })).toEqual([0]));
```

**Edge cases.** In CI, log the seed of every run (fast-check does on failure) so a one-off failure can still be replayed. Don't raise `numRuns` into the thousands on every PR; run a heavier configuration nightly.

#### 15.3 Stateful properties: model-based tests of a state machine ➕

**Problem.** The board is a **state machine**: create, move, archive, restore. Bugs appear only after particular **sequences** (archive, then move, then restore), which example tests rarely cover.

**Why (first principles).** A sequence of commands is just another input, so it can be generated too. The property is "after any sequence of valid commands, the real system agrees with a **simple model** of it" (for example, a `Map` from task ID to column).

**Mechanism.** fast-check's **model-based testing** (`fc.commands` with `fc.modelRun`) generates command sequences, applies each command to both the model and the real system, and checks they agree after every step; on failure it shrinks the **sequence** to the shortest one that breaks.

**Implementation.**

```ts title="board.model.test.ts"
import fc from 'fast-check';

type Model = { columns: Map<string, Column> };

class MoveCommand implements fc.Command<Model, Board> {
  constructor(readonly id: string, readonly to: Column) {}
  check = (m: Readonly<Model>) => m.columns.has(this.id);
  run(m: Model, board: Board) {
    const from = m.columns.get(this.id)!;
    if (canMove(from, this.to)) {
      board.move(this.id, this.to);
      m.columns.set(this.id, this.to);
    } else {
      expect(() => board.move(this.id, this.to)).toThrow();
    }
    expect(board.task(this.id).column).toBe(m.columns.get(this.id));
  }
  toString = () => `move(${this.id}, ${this.to})`;
}

test('board agrees with the model for any move sequence', () => {
  const ids = ['t1', 't2', 't3'];
  const cmd = fc.tuple(fc.constantFrom(...ids), fc.constantFrom<Column>('todo', 'doing', 'done'))
    .map(([id, to]) => new MoveCommand(id, to));
  fc.assert(fc.property(fc.commands([cmd], { maxCommands: 50 }), (cmds) => {
    const setup = () => ({
      model: { columns: new Map(ids.map((id) => [id, 'todo' as Column])) },
      real: Board.withTasks(ids.map((id) => ({ id, column: 'todo' }))),
    });
    fc.modelRun(setup, cmds);
  }));
});
```

**Edge cases.** Keep the model **much simpler** than the system, or you'll be debugging the model. Model-based tests against a **real database** are possible but slow; run them on the functional core in CI and against the repository nightly.

## 16. What to replace in tests, and what not to 🎓

### 16.1 The database: keep it real 🎓

**The tempting move:** the DB is slow, so wrap it with an **in-memory** version (maps and structs). Node people do in-memory replacements, Go people write fake repositories, Java people use **H2**. You gain **speed and convenience**.

**What you give up is fidelity.** Think about which bugs actually live in the data layer:
- a wrong column name,
- a missing index that makes a query slow,
- a **unique constraint** you forgot to add or to handle,
- a transaction that doesn't do what you think,
- a JSON operator that exists in Postgres but not in the fake (or vice versa).

**Every one of those lives in Postgres, not in your logic, and Postgres is exactly the layer you replaced.** So the fake can't catch them.

**The fix:** use a **real database** in tests, and **make it cheap**. Two techniques:

#### Technique A: a transaction per test
Open a transaction at the start, run the test inside it, **roll back** at the end. The DB is untouched, the next test starts clean, and it's fast. **Requirement:** the code under test must accept a **transaction handle** instead of creating its own connection, which is dependency injection again.

```ts title="tx-per-test.ts"
import { Pool, PoolClient } from 'pg';

let pool: Pool;
let tx: PoolClient;

beforeAll(() => { pool = new Pool({ connectionString: process.env.TEST_DATABASE_URL }); });
afterAll(() => pool.end());

beforeEach(async () => { tx = await pool.connect(); await tx.query('BEGIN'); });
afterEach(async () => { await tx.query('ROLLBACK'); tx.release(); });

test('unique email is enforced by the real constraint', async () => {
  const repo = new PgUserRepo(tx);                       // repo takes a Queryable, not a Pool
  await repo.create({ email: 'a@x.io' });
  await expect(repo.create({ email: 'a@x.io' })).rejects.toMatchObject({ code: '23505' }); // unique_violation
});
```

🔧 Edge cases: if the code under test runs its own `BEGIN`/`COMMIT`, make your unit-of-work helper use a **`SAVEPOINT`** when it's already inside a transaction. Code that opens a **second connection** won't see the uncommitted rows, so it doesn't fit this technique; use technique B for it.

#### Technique B: a template database per test
Postgres can create a database **as a copy of another**. Run **all migrations once** on a template, then have **each test create its own database from the template** in a few milliseconds. Because every test has its own DB, tests can **run in parallel**.

#### Real Postgres from test code: Testcontainers
**Testcontainers** (SDKs in nearly every language) starts a **real container from your test code** and gives you its address.

**What the demo shows:** Testcontainers starts **Postgres 18**, waits until it accepts connections: started at :58, ready at :05, so **about 7 s**, **once for the whole package, not per test**. Then **nine tests**, each creating its own database from the template, run in **a few milliseconds each**. Total for the package: **10.5 s**, about 7 s of setup and about 3 s of actual tests.

```ts title="test/pg.ts (Testcontainers + template databases)"
import { PostgreSqlContainer, StartedPostgreSqlContainer } from '@testcontainers/postgresql';
import { Client } from 'pg';
import { randomUUID } from 'node:crypto';

let container: StartedPostgreSqlContainer;

export async function startPg() {                        // jest globalSetup: once per run
  container = await new PostgreSqlContainer('postgres:17').start();
  const admin = new Client({ connectionString: container.getConnectionUri() });
  await admin.connect();
  await admin.query('CREATE DATABASE board_template');
  await runMigrations(uriFor('board_template'));        // migrations run ONCE
  await admin.end();                                    // template must have no open connections when copied
}

export async function freshDb() {                       // per test or per file: milliseconds
  const name = `t_${randomUUID().replace(/-/g, '')}`;
  const admin = new Client({ connectionString: container.getConnectionUri() });
  await admin.connect();
  await admin.query(`CREATE DATABASE ${name} TEMPLATE board_template`);
  await admin.end();
  return uriFor(name);
}

const uriFor = (db: string) => container.getConnectionUri().replace(/\/[^/]+$/, `/${db}`);
```

### 16.2 The network: wrap it, or stand up a real server 🎓
For someone else's API, the earlier rule holds: **wrap it in your own interface and fake that**. But sometimes you want to test **your HTTP client code itself**: headers, retries, how you parse responses. Then start a **real HTTP server on a real port inside the test** and point your client at it, so the request really goes over TCP as in production. Go has `httptest`. In Node, **MSW** intercepts at the network layer, so you don't even replace your client.

```ts title="geo-client.test.ts (MSW)"
import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

const server = setupServer(
```

### 16.3 Time: never sleep 🎓

**The problem:** you call something that finishes **in the background**, so the test `sleep`s **100 ms** and then checks. It passes on your laptop and in review, then **fails in CI**. **Why:** the CI machine is loaded, and the background work took **110 ms**. Your logic was right; **the clock** was the problem.

**The naive fix** is a longer sleep. It doesn't fix anything permanently (a busier day breaks it again) and it makes every run slower.

**Two real fixes:**
1. **Wait for a condition, not a duration.** Wait for a signal that the work is done: a channel in Go, a callback, promise or event in Node.
2. **Inject the clock.** Code asks a clock object for "now" and for timers; tests pass a **controllable** clock and move time forward explicitly, gaining full control over times and timeouts.

```ts title="fix 1: wait for the signal"
// ❌ flaky
service.enqueueReindex(boardId);
await new Promise(r => setTimeout(r, 100));
expect(await index.has(boardId)).toBe(true);

// ✅ deterministic: the code exposes completion
const done = once(service.events, 'reindexed');   // node:events once() returns a promise
service.enqueueReindex(boardId);
await done;
expect(await index.has(boardId)).toBe(true);
```

```ts title="fix 2: control the clock (Jest fake timers)"
test('session expires after 30 minutes idle', async () => {
  jest.useFakeTimers();
  jest.setSystemTime(new Date('2026-01-01T10:00:00Z'));
  const sessions = new SessionStore();               // uses Date.now() and setTimeout internally
  const id = sessions.create('u1');

  await jest.advanceTimersByTimeAsync(29 * 60_000);
  expect(sessions.get(id)).not.toBeNull();

  await jest.advanceTimersByTimeAsync(2 * 60_000);
  expect(sessions.get(id)).toBeNull();
  jest.useRealTimers();
});
```

🔧 For code you write from scratch, an explicit `Clock` interface (`now()`, `setTimeout()`) injected through the constructor is clearer than global fake timers, and it works the same in any test runner.

### 16.4 Hermetic tests 🎓
A test that **brings its whole environment with it** and doesn't rely on a hand-set-up database or a service that "should be running" is **hermetic** (sealed). It starts everything it needs and stops it when done. That's what lets the same suite run **anywhere**: your laptop, an SSH box, GitHub Actions. **Testcontainers is being hermetic about the database; an injected clock is being hermetic about time.**

### 16.5 Randomness, IDs and the environment: the other hidden inputs ➕

Time is one input your code reads without a parameter; randomness, generated IDs and the machine's settings are three more, and they cause the same "passes here, fails there" problems.

#### Seeded randomness ➕

**Problem.** A feature picks a random reviewer for a task, or adds jitter to retries (as the real-time and webhooks lessons recommend). The test either can't assert which reviewer was picked, or asserts one and fails one run in five.

**Why (first principles).** `Math.random()` is an input that differs on every run. A test can only make claims about outputs whose inputs it **controls**, exactly as with `Date.now()`.

**Mechanism.** Inject a random source (`() => number`) the same way you inject the clock. Production passes `Math.random`; tests pass either a fixed sequence or a **seeded** generator, so a "random" run is reproducible.

**Implementation.**

```ts title="random.ts"
export type Rng = () => number;                       // returns a number in [0, 1)

export function seeded(seed: number): Rng {           // mulberry32: tiny, deterministic
  return () => {
    seed |= 0; seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export const backoffMs = (attempt: number, rng: Rng) => {
  const base = Math.min(30_000, 500 * 2 ** attempt);
  return base / 2 + rng() * (base / 2);               // jittered
};
```

```ts title="random.test.ts"
test('jitter stays inside [base/2, base)', () => {
  const rng = seeded(42);
  for (let i = 0; i < 1000; i++) {
    const d = backoffMs(3, rng);
    expect(d).toBeGreaterThanOrEqual(2000);
    expect(d).toBeLessThan(4000);
  }
});
test('extremes', () => {
  expect(backoffMs(3, () => 0)).toBe(2000);
  expect(backoffMs(3, () => 0.999999)).toBeLessThan(4000);
});
```

**Edge cases.** Security-sensitive randomness (tokens, secrets) must still use `crypto.randomBytes` in production; inject an ID or token **generator** there rather than a seeded PRNG, so the test seam can never leak into production code paths.

#### Generated IDs and ordering ➕

**Problem.** The test creates two tasks and expects them in creation order, sorted by `id`. With random UUIDs (v4) the order is random, so the test passes half the time.

**Why (first principles).** A v4 UUID carries no order. Sorting by it is sorting by chance. Similarly, rows returned without an `ORDER BY` have **no guaranteed order** in Postgres, even if they usually come back in insertion order on a small table.

**Mechanism.** Assert on **sets** when order isn't part of the contract (`expect.arrayContaining`, or sort before comparing). When it is, the code must define it (`ORDER BY created_at, id`), and tests should create data with **distinct, controlled** timestamps through the injected clock. If you need IDs that sort by time, use time-ordered IDs (UUIDv7) and still inject the generator.

**Implementation.**

```ts
// ❌ relies on accidental order
expect(await repo.list(boardId)).toEqual([taskA, taskB]);

// ✅ order isn't the contract: compare as a set
expect(await repo.list(boardId)).toEqual(expect.arrayContaining([taskA, taskB]));

// ✅ order IS the contract: the query defines it and the test controls the timestamps
clock.set('2026-01-01T10:00:00Z'); const a = await svc.create({ title: 'a' });
clock.set('2026-01-01T10:00:01Z'); const b = await svc.create({ title: 'b' });
expect((await svc.listNewestFirst(boardId)).map((t) => t.id)).toEqual([b.id, a.id]);
```

**Edge cases.** Two rows with the **same** `created_at` (same millisecond, or a frozen fake clock) still have no defined order unless the query adds a tie-breaker such as `id`.

#### Time zone, locale and machine settings ➕

**Problem.** "Tasks due today" passes on a laptop in India and fails in CI, which runs in UTC; or a formatted amount reads `1,234.50` locally and `1.234,50` on a colleague's machine.

**Why (first principles).** `new Date().getDate()`, `toLocaleString()` and `Intl` all read the process's **time zone and locale** from the environment. It's an input like any other, set by the machine instead of by the test.

**Mechanism.** Pin the environment for the whole suite (`TZ=UTC`), and write explicit tests for the time zones your users are in, passing the zone as a parameter instead of relying on the machine's.

**Implementation.**

```json title="package.json (cross-env sets it on every OS, before Jest and its workers start)"
{ "scripts": { "test": "cross-env TZ=UTC jest" } }
```

```ts
test('due today respects the user time zone, not the server one', () => {
  const now = new Date('2026-03-01T20:00:00Z');                 // 01:30 on 2 March in Kolkata, still 1 March in UTC
  expect(isDueToday({ due: '2026-03-02' }, now, 'Asia/Kolkata')).toBe(true);
  expect(isDueToday({ due: '2026-03-02' }, now, 'UTC')).toBe(false);
});
```

**Edge cases.** Include a **DST** transition in tests for scheduling code (a "daily at 02:30" job doesn't exist on the spring-forward day in zones with DST); section 18.3 comes back to this.

## 17. Test data: builders and factories ➕

Section 16 made the database real and isolated; the next problem is **filling it**, because every medium test needs rows, and how you create them decides whether tests stay readable as the schema grows.

#### 17.1 The problem with hand-written fixtures ➕

**Problem.** Each test inserts its data by hand: a user, a workspace, a board, three tasks, 30 lines of `INSERT` before the one line that matters. Then a migration adds a `NOT NULL` column to `tasks`, and **140 tests** break, none of which cared about that column.

**Why (first principles).** A test should state **only the facts that matter for its claim** ("a task in `todo` on a board Leo can't edit"). Everything else is **incidental** data required by the schema. When incidental data is spelled out in every test, two things go wrong: readers can't tell which values matter, and every schema change has to be repeated in every test. Shared static fixture files (one big `seed.sql`) solve the repetition but make tests depend on each other's data, which is the order-dependency problem of section 20.

**Mechanism.** Put the **defaults in one place**, and let each test override only what it cares about. Two patterns:
- A **builder** returns valid in-memory objects with sensible defaults (`aTask().inColumn('done').build()`), for small tests.
- A **factory** does the same and **persists** the object, creating required parents (workspace, board) automatically, for medium tests.

#### 17.2 Implementing a factory with overrides and sequences ➕

**Problem.** Defaults must be **valid** (pass constraints) and **unique** where the schema demands it (two users can't share an email), and parents must be created only when the test didn't provide one.

**Why (first principles).** Uniqueness can't come from constants, so each factory needs a **sequence** (a counter). Parent creation must be **lazy**: if the test passes `boardId`, using it is the whole point.

**Mechanism.** A small function per entity: merge defaults with overrides, take a sequence number, create missing parents, insert, return the row. Libraries such as `fishery` package this pattern; a hand-written one is a few lines.

**Implementation.**

```ts title="test/factories.ts"
import type { Queryable } from '../src/db';

let seq = 0;
const next = () => ++seq;

export function factories(db: Queryable) {
  const f = {
    async user(over: Partial<User> = {}) {
      const n = next();
      return db.one<User>(`INSERT INTO users (email, name) VALUES ($1, $2) RETURNING *`,
        [over.email ?? `user${n}@example.test`, over.name ?? `User ${n}`]);
    },
    async board(over: Partial<Board> & { ownerId?: string } = {}) {
      const ownerId = over.ownerId ?? (await f.user()).id;               // parent only if not given
      return db.one<Board>(`INSERT INTO boards (name, owner_id) VALUES ($1, $2) RETURNING *`,
        [over.name ?? `Board ${next()}`, ownerId]);
    },
    async task(over: Partial<Task> = {}) {
      const boardId = over.boardId ?? (await f.board()).id;
      return db.one<Task>(`INSERT INTO tasks (board_id, title, column_name) VALUES ($1, $2, $3) RETURNING *`,
        [boardId, over.title ?? `Task ${next()}`, over.column ?? 'todo']);
    },
  };
  return f;
}
```

```ts title="only the facts that matter are visible"
test('a viewer cannot move tasks', async () => {
  const make = factories(tx);
  const leo = await make.user();
  const task = await make.task({ column: 'todo' });
  await grant(tx, leo.id, task.boardId, 'viewer');

  await expect(new MoveTaskService(tx).move(leo, task.id, 'doing')).rejects.toThrow(/forbidden/);
});
```

**Edge cases.**
- The sequence is a module variable, so it restarts in every test **file** (Jest gives each file its own module registry). That's fine while every test starts from clean data (transaction per test, template DB, or schema per worker with truncation, sections 16.1 and 6.2). If rows can outlive a test, add `process.env.JEST_WORKER_ID` and a random suffix to unique values.
- When a new `NOT NULL` column arrives, you change **one default** in the factory, and 140 tests keep passing.

#### 17.3 Keeping factories honest ➕

**Problem.** Factories drift into a second, hidden source of business logic: the `task` factory sets `seq` and `updated_at` by itself, so tests pass while the real service that should set them is broken. Or defaults are so rich (every task gets labels, comments, assignees) that every test pays for data it doesn't use.

**Why (first principles).** A factory is test infrastructure; if it does the job of production code, tests verify the factory instead of the code. And every extra row is time multiplied by every test.

**Mechanism.**
- Factories create **minimal valid** rows; associations are opt-in (`make.task({ withComments: 3 })`).
- When the state you need is produced by real behaviour (a task that was moved, an archived board), create it **through the service**, not by writing the end state directly.
- Run each factory once in a test of its own, so a schema change that breaks a factory fails in one obvious place.

**Implementation.**

```ts
test('factories produce valid rows', async () => {
  const make = factories(tx);
  await expect(make.task()).resolves.toMatchObject({ column: 'todo' });
});

// state produced by behaviour, through the service
const task = await make.task();
await moveSvc.move(owner, task.id, 'doing');                 // not: make.task({ column: 'doing', seq: 1 })
```

**Edge cases.** For small tests, builders that return plain objects (no DB) keep the same "override only what matters" style; keep their defaults in sync with the factories by sharing one `defaults` object.

## 18. Testing background jobs, queues and scheduled tasks ➕

Section 16.3 showed how to wait for background work in a test; real backends push a lot of work into **queues and cron jobs** (task queues lesson, 14), and those have their own failure modes that ordinary request tests never exercise.

#### 18.1 Test the handler as a function, and the wiring separately ➕

**Problem.** A test enqueues a "send weekly digest" job and then waits for an email to show up. It's slow, needs Redis and a worker running, and when it fails you can't tell if the bug is in the digest logic, the payload serialisation or the worker setup.

**Why (first principles).** A job has two layers: the **handler** (given this payload, do this work) and the **wiring** (serialising the payload into Redis, the worker picking it up, retries). They fail for different reasons, so test them at different sizes, the same split as functional core and imperative shell (section 14).

**Mechanism.**
- Export the handler as a plain function with injected dependencies, and test it directly: **small or medium**, no queue at all.
- Write **one or two** medium tests per queue that go through the real queue (Redis from Testcontainers) to prove the wiring and payload shape.

**Implementation.**

```ts title="digest.job.ts"
export type DigestPayload = { userId: string; weekOf: string };   // JSON only: what survives Redis

export async function handleDigest(p: DigestPayload, deps: { tasks: TaskRepo; mailer: Mailer; clock: Clock }) {
  const items = await deps.tasks.completedInWeek(p.userId, p.weekOf);
  if (items.length === 0) return { sent: false };
  await deps.mailer.send(p.userId, renderDigest(items, deps.clock.now()));
  return { sent: true };
}

// wiring, thin
new Worker('digest', (job) => handleDigest(job.data, prodDeps), { connection });
```

```ts title="digest.job.int.test.ts (the wiring, once)"
import { Queue, QueueEvents, Worker } from 'bullmq';
import { RedisContainer } from '@testcontainers/redis';

test('a digest job goes through the real queue', async () => {
  const redis = await new RedisContainer('redis:7').start();
  const connection = { host: redis.getHost(), port: redis.getPort() };
  const mailer = new FakeMailer();
  const worker = new Worker('digest', (job) => handleDigest(job.data, { tasks: fakeTasksWithOneDone, mailer, clock }), { connection });
  const queue = new Queue('digest', { connection });
  const events = new QueueEvents('digest', { connection });

  const job = await queue.add('weekly', { userId: 'u1', weekOf: '2026-09-28' });
  await expect(job.waitUntilFinished(events, 5_000)).resolves.toEqual({ sent: true });   // wait for the signal (with a cap), not a duration
  expect(mailer.sent).toHaveLength(1);

  await worker.close(); await queue.close(); await events.close(); await redis.stop();
});
```

**Edge cases.** Payloads go through **JSON**: a `Date` becomes a string, a `Map` becomes `{}`, `undefined` fields disappear. The wiring test is where that shows up, so pass a payload that contains every field type you use.

#### 18.2 Idempotency and retries: run it twice ➕

**Problem.** The worker crashes after sending the email but before marking the job complete. The queue retries. The user gets two digests. Every test ran the handler exactly once, so none caught it.

**Why (first principles).** Queues deliver **at least once** (the same reasoning as webhooks: the acknowledgement can be lost), so every handler will eventually run **twice** on the same payload in production. That's a behaviour, so it needs a test.

**Mechanism.** For every handler with side effects, add a test that runs it **twice** with the same payload and asserts the side effect happened **once**. Add a test that **fails partway** (a fake that throws on the second call) and then retries, asserting the final state is correct.

**Implementation.**

```ts
test('running the digest twice sends one email', async () => {
  const mailer = new FakeMailer();
  const deps = { tasks: realRepo(tx), mailer, clock, sentLog: new PgSentLog(tx) };
  const p = { userId: 'u1', weekOf: '2026-09-28' };
  await handleDigest(p, deps);
  await handleDigest(p, deps);                                  // the retry production will eventually do
  expect(mailer.sent).toHaveLength(1);
});

test('a crash after the side effect does not duplicate it on retry', async () => {
  const mailer = new FakeMailer();
  const sentLog = new PgSentLog(tx);
  const original = sentLog.markDone.bind(sentLog);
  jest.spyOn(sentLog, 'markDone').mockRejectedValueOnce(new Error('crash')).mockImplementation(original);
  const deps = { tasks: realRepo(tx), mailer, clock, sentLog };
  const p = { userId: 'u1', weekOf: '2026-09-28' };

  await expect(handleDigest(p, deps)).rejects.toThrow('crash');  // email sent, completion not recorded
  await handleDigest(p, deps);                                    // the queue's retry
  expect(mailer.sent).toHaveLength(1);                            // fails until the handler records intent before sending
});
```

**Edge cases.** The second test usually **fails** on the first try, and that's the point: it forces a design (record a "digest for week W" row with a unique constraint before sending, or use the provider's idempotency key) instead of hoping retries never happen.

#### 18.3 Scheduled jobs: test the schedule as data ➕

**Problem.** A cron expression `30 2 * * *` ("02:30 daily") lives in a decorator. Nobody can test it without waiting until 02:30, so a typo (`30 2 * * 0`, Sundays only) ships, and so does the fact that it runs at 02:30 **UTC**, which is the middle of the working day for some customers.

**Why (first principles).** A schedule is a function from "now" to "next run time", and its correctness can be checked without waiting, the same way an injected clock replaces sleeping. The job body and the schedule are separate concerns.

**Mechanism.**
- Keep the schedule as **data** next to the job, and test "given now, the next runs are ..." with a cron parsing library, including a **time zone** and a **DST** day.
- Test the job body like any handler (18.1), passing the "as of" time explicitly so a job that runs late (after downtime) processes the **right window**.
- In production, guard against **double runs** across instances (a lock or a unique "run for window W" row), and test that guard by invoking the job twice.

**Implementation.**

```ts title="schedules.ts"
export const schedules = {
  weeklyDigest: { cron: '0 8 * * 1', tz: 'Asia/Kolkata' },     // Mondays 08:00 India time
} as const;
```

```ts title="schedules.test.ts"
import { CronExpressionParser } from 'cron-parser';             // cron-parser v5 API

test('weekly digest fires Mondays 08:00 Kolkata = 02:30 UTC', () => {
  const it = CronExpressionParser.parse(schedules.weeklyDigest.cron, {
    currentDate: new Date('2026-10-02T00:00:00Z'),               // a Friday
    tz: schedules.weeklyDigest.tz,
  });
  expect(it.next().toDate().toISOString()).toBe('2026-10-05T02:30:00.000Z');
  expect(it.next().toDate().toISOString()).toBe('2026-10-12T02:30:00.000Z');
});

test('a late run still processes the intended window', async () => {
  const runAt = new Date('2026-10-05T09:00:00Z');                // ran 6.5 h late after an outage
  const window = digestWindowFor(runAt, schedules.weeklyDigest.tz);
  expect(window).toEqual({ from: '2026-09-28', to: '2026-10-04' });
});
```

**Edge cases.** Kolkata has no DST, which is why it's a stable example; for zones that do (Europe, US), add a test on the transition dates, where a local time can be skipped or happen twice. Decide on purpose whether a missed run (the service was down at the scheduled time) should be **caught up** or **skipped**, and test that decision.

## 19. Test-driven development (TDD) 🎓

TDD is **a way of working, not a kind of test**. You still write unit, integration and E2E tests; you just write them **before** the code.

### The loop
<Mermaid chart={`flowchart LR
  R["RED<br/>write a test for behaviour that doesn't exist<br/>run it, watch it fail"] --> G["GREEN<br/>smallest code that passes<br/>(ugly is allowed)"]
  G --> F["REFACTOR<br/>clean up, run again, still green"]
  F --> R`} />

**Why each phase exists:**
- **Red is for design.** Writing the test first forces you to **use the function before it exists**, from the caller's side. If the test is awkward or ugly to write, the **API** is wrong, and you find out in minutes instead of after the implementation.
- **Red then green is for proof.** If you write the code first and then the test, the test usually **passes first time**, and you learn nothing: did it pass because the code is right, or because it doesn't check what it should? Seeing it fail first proves it can fail. (Kent Beck lists this among the properties he wants from tests.)
- **Refactor is mandatory.** You were allowed to write bad code in green **only because** you come back here. It's the step most people skip.

### What the demo shows 🎓
**Requirement:** a task can't go straight from `todo` to `done`; it must pass through `doing`.
1. **Red:** a test takes a `todo` task, moves it to `done` and expects an error. It fails: it expected an error and got `nil`, because the move succeeded.
2. **Green:** add **one `if`** inside `Move`. Green.
3. **Refactor:** that `if` is a **business rule** sitting in the middle of a method that also locks a mutex, bumps a sequence number and trims a history buffer. Extract it into **`canMove(from, to)`**: two columns in, nothing else. Rerun the package: still green.

```ts title="TDD in TypeScript, same three steps"
// 1. RED
test('todo cannot jump straight to done', () => {
  const b = Board.withTasks([{ id: 't1', column: 'todo' }]);
  expect(() => b.move('t1', 'done')).toThrow(/must pass through doing/);
});

// 2. GREEN (inside Board.move, quick and dirty)
if (task.column === 'todo' && to === 'done') throw new Error('must pass through doing');

// 3. REFACTOR: pure rule, the functional core
export function canMove(from: Column, to: Column): boolean {
  return !(from === 'todo' && to === 'done');
}
// Board.move: if (!canMove(task.column, to)) throw new InvalidMove('must pass through doing');
```

### The debate 🎓
- **Kent Beck** (who wrote the TDD book) published a short article in **2023** on what the loop actually means, because of all the arguing (🔧 "Canon TDD").
- **Ian Cooper, "TDD, Where Did It All Go Wrong"**: people read "unit" as **class**, wrote one test class per production class and mocked everything else, so **every refactor broke hundreds of tests** and many gave up. His point: **the unit is the behaviour**. Test the **public interface of a module**; then you can rearrange its insides freely and the tests stay green. This is the same idea as state over interaction.
- **DHH, "TDD is dead. Long live testing." (2014)**: against test-first as dogma and against designing systems around mockability; test against the real thing. It led to public conversations between him, Kent Beck and Martin Fowler (🔧 the "Is TDD Dead?" series).

### The lesson author's opinion 🎓
**TDD is a great tool when you know what the answer looks like but not yet how to build it.** A **JSON parser** (string in, object out: expectations are trivial to write, the implementation is the hard part), a **pricing rule**, a **state machine**.

**It's the wrong tool when you don't yet know what the answer should look like**: exploring a space, trying several approaches and going with what feels right. In the author's view that's true for a lot of backend feature work, full of trade-offs and design decisions, so TDD has real uses but not everywhere.

## 20. Flaky tests 🎓

### Why a flaky test is worse than no test
A **flaky test** passes and fails on the **same code**. A **missing** test is a known hole. A **flaky** one changes **team behaviour**: CI fails, someone says "that one's flaky, just rerun", it passes, everyone moves on. That becomes a habit, so the day a **real** failure shows up, the first reaction is **rerun**, not investigate.

### Where flakiness comes from 🎓
A **2014 study by Luo and colleagues** took **201 real fixes for flaky tests** from open-source projects and sorted them by cause. The top three:

| Cause | What it is | Fix (from earlier in the lesson) |
|---|---|---|
| **Async wait** | The test starts something and waits for it the wrong way | Wait for a **condition**, not a duration (section 16.3) |
| **Concurrency** | Two things inside the test race each other | Synchronisation primitives (Go has `testing/synctest`; other ecosystems have their own) |
| **Test order dependency** | Test B passes only because test A ran first and left state behind | New: see below |

### Test order dependency 🎓
**Problem:** test B passes only when it runs after test A, because A created a DB row, set a global, or wrote a file that B depends on. Run B alone and it fails.

**Why it's dangerous:** as long as the suite always runs in the same order, it's green. The moment someone **adds a test in the middle** or **turns on parallelism** to speed things up, it starts failing.

🔧 Find and prevent it:

```bash
npx jest --randomize            # shuffle test order within files (Jest 29.2+)
npx jest --runInBand --randomize --seed=1234   # reproduce a specific failing order
npx jest path/to/b.test.ts -t "B"              # run B alone: does it pass?
```

The structural fix is the database work above: **each test owns its data** (transaction per test, or its own DB from the template), and **no shared mutable globals** (reset modules or inject state).

### What to do with a flaky test 🎓
1. **Delete it.** It wasn't helping and was creating future problems. Deleting tests pays off more often than people expect.
2. **Quarantine it:** move it out of the blocking suite into a separate one that still runs, tagged with **an owner, a date and a reason**.
3. **Add a retry.** Not good practice in tests.

**The author's choice: quarantine** with name, date and reason, so when it fails again you know who wrote it and why, and can talk to them about the right fix.

```ts title="quarantine convention"
/** QUARANTINED 2026-09-14 by @asha: races with the reindex worker (issue #812). Not in the blocking suite. */
describe.skip('search reindex consistency', () => { /* ... */ });
```

🔧 Better than `skip`: a separate Jest project (e.g. `testMatch: ['**/*.quarantine.test.ts']`) that runs in a non-blocking CI job, so you still see whether it's getting better or worse.

## 21. Measuring the suite: coverage 🎓

### How coverage is measured (mechanism)
**Code coverage is the percentage of your code executed while the tests ran.** To get it, the tool **rewrites your code before building**: it splits each function into **basic blocks** (straight runs with no branches), inserts a **counter** at the top of each, runs the tests, then reads the counters. A block at **zero** never ran.

🔧 In Node, Jest instruments with Istanbul (Babel) by default, or uses V8's built-in coverage with `coverageProvider: 'v8'`.

### The limit of coverage
It records **whether code ran**, not **whether anything checked the result**. A test that calls every function and **asserts nothing** gets **100%**.

### Line vs branch coverage 🎓
A function with one `if` and no `else`. A test where the condition is **true** executes every line: **line coverage 100%**. But the **false** direction never ran: **branch coverage 50%**. Same code, same test, different numbers.

```ts
function discount(total: number, isMember: boolean) {
  let d = 0;
  if (isMember) d = total * 0.1;   // only the true branch is tested below
  return total - d;
}
test('member discount', () => expect(discount(100, true)).toBe(90));
// lines: 100%, branches: 50% (isMember = false never ran)
```

### Does coverage predict quality? 🎓
Everyone quotes **80%**. A **2014 ICSE study** (🔧 Inozemtseva and Holmes, "Coverage Is Not Strongly Correlated with Test Suite Effectiveness") took large real Java programs, generated **thousands of test suites** of different sizes, and measured each suite's coverage and **how many real faults it caught**.

**"Controlling for suite size":** if you just correlate coverage with faults found you get a strong link, but mostly because **bigger suites both cover more and find more**. So they **held size fixed** and asked whether the higher-coverage suite of two same-size suites found more bugs. **Answer: only a low to moderate correlation**, varying by system. **A fixed coverage target doesn't give you an effective suite.**

### Three practical takeaways 🎓
1. Rough guide: **60% acceptable, 75% commendable, 90% exemplary**, with **no ideal number** for every product. (🔧 These figures are the ones published in Google's *Code Coverage Best Practices*.)
2. **What isn't covered matters more than what is.** The value of the report is in the **red lines**, not the percentage.
3. **Mandating 100%** makes engineers write **low-value tests just to hit the number**, and then stop improving.

🔧 A sensible Jest config: a floor that prevents backsliding, not a target to game.

```js title="jest.config.js"
module.exports = {
  collectCoverageFrom: ['src/**/*.ts', '!src/**/*.module.ts', '!src/main.ts'],
  coverageThreshold: { global: { branches: 70, lines: 75 } },   // a floor, not a goal
};
```

## 22. Testing your tests: mutation testing 🎓

### The mechanism
A mutation tool **damages your code on purpose** and checks whether your tests **notice**.
1. Make a small change somewhere: `>` becomes `>=`, `+` becomes `-`, a return value becomes `0`. Each damaged version is a **mutant**.
2. Run the suite against each mutant.
3. A test fails → the mutant is **killed** (good: the tests noticed). Everything passes → the mutant **survived** (the tests don't really check that code).
4. **Score = percentage of mutants killed.**

<Mermaid chart={`flowchart TD
  S["Source: i less-or-equal offset + limit"] --> M["Mutant: i less-than offset + limit"]
  M --> T["Run the test suite"]
  T -->|"some test fails"| K["Killed: tests guard this logic"]
  T -->|"all tests pass"| SV["Survived: assertion gap found"]
  K & SV --> SC["Score = killed / total"]`} />

### What the demo shows 🎓
A pagination module: takes a list and returns one page. Its tests assert only: returns something, returns an array, doesn't throw, length is greater than zero. **Line coverage: 100%**, so by coverage alone the job is done.

**Stryker** makes **19 mutants**, one at a time, and runs the suite against each. **Score: 52.63%**: **9 of 19 survived**. One survivor changed the loop condition from `i <= offset + limit` to `i < offset + limit`, which changes **how many items are returned**, and every test still passed.

🔧 The fix is assertions that pin the behaviour, and Stryker setup for a TS/Jest project:

```ts title="paginate.test.ts (kills the mutants)"
const items = Array.from({ length: 10 }, (_, i) => i);
test('returns exactly one page', () => {
  expect(paginate(items, { offset: 0, limit: 3 })).toEqual([0, 1, 2]);
  expect(paginate(items, { offset: 9, limit: 3 })).toEqual([9]);       // last partial page
  expect(paginate(items, { offset: 10, limit: 3 })).toEqual([]);       // past the end
});
```

```json title="stryker.config.json"
{
  "testRunner": "jest",
  "checkers": ["typescript"],
  "mutate": ["src/**/*.ts", "!src/**/*.test.ts"],
  "reporters": ["html", "clear-text", "progress"],
  "thresholds": { "high": 80, "low": 60, "break": 50 }
}
```

```bash
npx stryker run     # slow: runs the suite once per mutant, so run it nightly or on changed files
```

## 23. Measuring the code: complexity 🎓

### Cyclomatic complexity
**The number of independent paths through a piece of code**, from **Thomas McCabe's 1976 paper**. You can compute it by hand: draw the function as a graph where each straight run of statements is a **node** and each jump is an **edge**.

> `complexity = edges − nodes + 2`

**Shortcut:** `1 + number of decision points` (one for the function, plus one per `if`, loop, `case`, and each `&&` / `||` in a condition). No branches = 1; one `if` = 2.

**Threshold:** the common advice is **10**, which McCabe himself proposed as **reasonable, not magical**. He also noted a case where the limit seems unreasonable: a **big flat `switch`** over many independent cases. A 20-case switch scores **21**, yet it's easy to read.

### Cognitive complexity
Invented by **SonarSource** to measure **how hard code is to understand**, not how many paths it has. It adds **nothing** for a flat `switch` (easy to read) but **grows with nesting**: an `if` inside a loop inside an `if` is far harder to hold in your head than three `if`s in a row.

| Code shape | Cyclomatic | Cognitive |
|---|---|---|
| Long flat `switch` | High | Low |
| Three levels of nesting | Moderate | High |

```ts title="same cyclomatic, very different cognitive"
// cyclomatic 4, cognitive 3: flat, readable
function label(s: Status) {
  if (s === 'todo') return 'To do';
  if (s === 'doing') return 'In progress';
  if (s === 'done') return 'Done';
  return 'Unknown';
}

// cyclomatic 4, cognitive 6: each level of nesting costs more
function notify(users: User[], board: Board) {
  for (const u of users) {               // +1
    if (u.active) {                      // +2 (nested once)
      if (board.watchers.has(u.id)) {    // +3 (nested twice)
        send(u);
      }
    }
  }
}
```

### What the demo shows 🎓
On the hub package: by **cyclomatic** complexity the hub's `Run` method scores **8**, third behind the two stream handlers. By **cognitive** complexity the same method scores **19** and jumps to the **top**, level with the WebSocket handler. Reading the code confirms it: **eight ways into the function**, deeply nested, hard to follow.

**Takeaway:** **don't trust either tool blindly.** Treat the numbers as **flags** pointing at code worth a look, then decide as a team.

🔧 Turning both into flags in a TS project:

```js title="eslint.config.js"
import sonarjs from 'eslint-plugin-sonarjs';
export default [
  {
    plugins: { sonarjs },
    rules: {
      complexity: ['warn', 10],                          // cyclomatic (core ESLint rule)
      'sonarjs/cognitive-complexity': ['warn', 15],      // cognitive
      'max-depth': ['warn', 3],
    },
  },
];
```

## 24. Finding problems without running anything 🎓

| Tool | What it does | What it doesn't do |
|---|---|---|
| **Linter** | Finds **patterns** known to be wrong: a condition that's always true because of an upstream assignment, an error returned by a call that you never check | Check syntax (that's the compiler) or prove your logic correct (no universal way to without expectations) |
| **Formatter** | Rewrites code into the team's standard layout | Change behaviour at all |
| **Type checker** | Catches using types wrongly: arithmetic on something declared as a string. Built into Go, TypeScript and Rust, usually surfaced in the editor | Catch logic bugs where the types line up |
| **Static analysis** | A more advanced linter: **checks code without running it** by following a value from one point through the program and checking conditions along the way | Replace tests |

Code quality is **subjective**; the author couldn't find objective metrics for it. In TypeScript, **ESLint** rules help to an extent; Go has its own linters. Beyond that there's no deterministic way to decide whether code is "high quality".

🔧 The typical Node/TS pipeline, cheapest first:

```json title="package.json"
{
  "scripts": {
    "format:check": "prettier --check .",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "jest",
    "test:mutation": "stryker run",
    "ci": "npm run format:check && npm run lint && npm run typecheck && npm test"
  }
}
```

## 25. Recap 🎓

- A test is **a program that runs your program and makes claims**; a runner just **writes the `main`**, runs tests and reports. Main purpose: **catching regressions**, in CI on every PR.
- Classify tests by **what they may touch** (process, machine, anything). Cost comes from **leaving the process**, not from how much logic is covered.
- Five doubles: **dummy, stub, spy, mock, fake**. Prefer **state verification**; interaction checks only when the interaction **is** the requirement, or you build **change detectors**.
- **Don't mock what you don't own**: wrap third parties in your own interface, plus a few sandbox contract tests.
- **Inject dependencies**; put logic in a **functional core** with a thin **imperative shell**.
- **Keep the database real** (fidelity), and make it cheap: **transaction per test** or **template DB per test**, via **Testcontainers**. For the network, wrap it or run a real local server (MSW). For time, **wait for conditions** and **inject the clock**. Together: **hermetic** tests.
- **TDD** (red, green, refactor) shines when you know the answer but not the implementation.
- **Flaky tests** train teams to ignore failures. Top causes: async waits, concurrency, **test order dependency**. Quarantine with owner, date and reason.
- **Coverage** says what ran, not what was checked; read the red lines. **Mutation testing** tests your tests.
- **Cyclomatic** and **cognitive** complexity, linters, formatters, type checkers and static analysis are **flags**, not verdicts.

**Beyond the lesson** ➕
- ➕ **Snapshots** are recorded change detectors: keep them small and inline, use property matchers for volatile fields, run CI with `--ci`, never script `-u`.
- ➕ **Fast CI:** parallel workers share everything outside the process, so isolate ports, files, Redis and the DB (**schema per worker** via `JEST_WORKER_ID`); **shard** across machines with `--shard=i/n` and merge coverage.
- ➕ **Trophy and honeycomb** move the weight to integration tests where code is mostly wiring; choose the **cheapest test that can fail for the bug** per module.
- ➕ **Performance in CI:** benchmark a few hot paths against a baseline with a wide tolerance; run k6 load tests nightly with **thresholds** that fail the job.
- ➕ **Consumer-driven contracts** (Pact) between your own services: the consumer records what it reads, the provider replays it in CI, and `can-i-deploy` checks compatibility with what's deployed.
- ➕ **Property-based testing** (fast-check) checks rules over generated inputs, **shrinks** failures to minimal counterexamples with a replayable seed, and can generate command sequences against a model.
- ➕ **Hidden inputs:** inject randomness and ID generators, never rely on accidental order, pin `TZ` and test explicit time zones.
- ➕ **Factories** keep defaults in one place so tests state only what matters, and create state through real behaviour.
- ➕ **Jobs and cron:** test handlers as functions and the queue wiring once; **run every handler twice**; test schedules as data with time zones and late runs.

## Interview questions

1. **Why can a bad test be worse than no test?** **It gives false confidence; a flaky one also trains the team to rerun instead of investigate.**
2. **What does a test runner actually do?** **Finds tests, generates an entry point (`_testmain.go` in Go), compiles and runs it, and reports results.**
3. **What makes a test slow?** **Leaving the process (database containers, network), not the amount of logic it exercises.**
4. **Small vs medium vs large tests?** **Small: one process, no network, DB, FS or sleep. Medium: anything on the same machine. Large: anything. It's enforceable, unlike "unit".**
5. **Stub vs mock vs fake?** **Stub: canned answers. Mock: pre-set expectations that fail the test if unmet. Fake: a working lightweight implementation (an in-memory repo).**
6. **What is a change-detector test?** **One that fails when the implementation changes but behaviour doesn't, typically from interaction verification. Prefer asserting on state.**
7. **Why "don't mock what you don't own"?** **A mock of a third party only encodes your assumptions about it. Wrap it in your own interface, fake that, and contract-test the adapter against the sandbox.**
8. **Why not use an in-memory DB in tests?** **You lose fidelity: constraints, indexes, transactions and SQL dialect bugs live in the real DB. Use real Postgres with transaction-per-test or template databases.**
9. **How do you fix a test that sleeps 100 ms?** **Wait for a completion signal, or inject a controllable clock (fake timers).**
10. **What's the purpose of the red step in TDD?** **Designing the API from the caller's side, and proving the test can fail.**
11. **Why is 100% line coverage not enough?** **Coverage records execution, not assertions; branch coverage can be lower; mutation testing shows whether tests actually check behaviour.**
12. **Cyclomatic vs cognitive complexity?** **Cyclomatic counts independent paths (1 + decisions); cognitive measures readability and penalises nesting, not flat switches.**
13. ➕ **What's wrong with snapshotting a whole API response?** **The expected value is recorded, not decided, so it detects any change without saying whether it's wrong; big diffs get rubber-stamped with `-u`. Snapshot small stable output inline and assert behaviour explicitly.**
14. ➕ **Tests pass alone but fail with more Jest workers. Why, and how do you fix it?** **Workers isolate memory but share external resources (DB, Redis, ports, files). Give each worker its own copy: port 0, temp dirs, key prefixes, and a schema or database per worker or per test.**
15. ➕ **Testing pyramid vs testing trophy?** **The pyramid puts most tests at the unit level because they're cheap; the trophy (and Spotify's honeycomb) puts most at integration level because glue code is where bugs live. Pick per module: the cheapest test that can catch the bug you fear.**
16. ➕ **How do you make a load test part of CI?** **Declare thresholds (for example p95 latency and error rate) so the tool exits non-zero when they're breached; run it nightly or pre-release against a production-like environment.**
17. ➕ **What problem does consumer-driven contract testing solve that a provider sandbox test doesn't?** **Between your own services, it checks that both sides' beliefs about the API match: the consumer records exactly what it uses, the provider verifies those interactions in its CI, and can-i-deploy blocks incompatible releases.**
18. ➕ **What is property-based testing and what is shrinking?** **Asserting rules that hold for all inputs and letting a library generate many inputs; on failure it reduces the input to a minimal counterexample and reports a seed to replay it.**
19. ➕ **Why do tests sorted by UUID fail randomly?** **v4 UUIDs carry no order, and rows without ORDER BY have no guaranteed order. Compare as sets, or make the query define the order and control timestamps in the test.**
20. ➕ **Why use factories instead of fixture files?** **Defaults live in one place, each test overrides only the facts that matter, schema changes are fixed once, and tests don't depend on shared seed data.**
21. ➕ **How do you test a queue worker?** **Test the handler as a function with injected dependencies, one integration test through the real queue for wiring, and always run the handler twice (and crash it midway) to prove at-least-once delivery is safe.**
