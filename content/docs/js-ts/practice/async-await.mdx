> How `async`/`await` really works, error handling, sequential vs parallel patterns, and async utilities you may be asked to write.

## A1. What does an `async` function return? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Definition:** calling an `async` function *always* returns a **native Promise**, no matter what the body does.

| Body does | Returned promise |
|---|---|
| `return 5` | fulfilled with `5` |
| returns nothing | fulfilled with `undefined` |
| `return somePromise` | follows (adopts) `somePromise` |
| `throw err` (anywhere, even before the first `await`) | rejected with `err` |

```js
async function getLtp() {
  return 2450.5;
}
const p = getLtp();
p instanceof Promise;        // true
p.then(v => console.log(v)); // 2450.5 (later, in a microtask)
```

**Why it matters:** the caller can never read the value synchronously. `const price = getLtp()` gives you a Promise, not a number. You must `await` it or use `.then`.

**Pitfalls**
- Forgetting `await` gives you bugs like `if (await isMarketOpen())` written as `if (isMarketOpen())`. A Promise object is always truthy, so the check always passes.
- The body up to the first `await` still runs **synchronously** when you call the function. Only the *result* arrives asynchronously.

**Interview tip:** say "an async function is sugar for a function that returns `new Promise` and resolves it with the return value or rejects it with the thrown error".

**Takeaway:** an async function always returns a Promise. Its `return` value fulfils that Promise and a `throw` rejects it.

</details>

## A2. Is the return value of an `async` function a number? · `easy` · 🖨️ Output

```js
async function getLtp() {
  console.log('fetching');
  return 2500;
}

const result = getLtp();
console.log(typeof result);
console.log(result instanceof Promise);
result.then(v => console.log('LTP ' + v));
console.log('rendering');
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
fetching
object
true
rendering
LTP 2500
```

1. Calling `getLtp()` runs its body **synchronously** up to the end (there is no `await`), so `fetching` prints first.
2. `return 2500` does not hand back `2500`. It fulfils the Promise that the async function created. `result` is that Promise, so `typeof result` is `"object"` and `instanceof Promise` is `true`.
3. `.then(...)` registers a callback. The promise is already fulfilled, so a reaction job is queued in the **microtask queue**. It does not run yet.
4. `rendering` prints, because synchronous code always finishes first.
5. The call stack is now empty, so the microtask runs and prints `LTP 2500`.

**Takeaway:** an async function returns a Promise even when the body never awaits. Read the value with `await` or `.then`.

</details>

## A3. What exactly does `await` do? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Definition:** `await expr` turns `expr` into a promise (`PromiseResolve`), **suspends** the surrounding async function, and gives control back to the caller. When that promise settles, the function's continuation is scheduled as a **microtask**:
- fulfilled: `await` evaluates to the value
- rejected: `await` **throws** the reason at that line

```js
async function placeOrder() {
  console.log('1: validate');
  const quote = await getQuote('TCS'); // pauses here, the caller continues
  console.log('3: got', quote);        // resumes later in a microtask
}
placeOrder();
console.log('2: UI stays responsive');
```

**Why it matters:** `await` does **not** block the thread. It pauses only *this* function. Other code, rendering and event handlers keep running while you wait.

**Pitfalls**
- Even `await 5` or `await alreadyResolvedPromise` pauses. The code after it always runs in a later microtask, never synchronously.
- `await` is only valid inside async functions (and at the top level of ES modules).
- Code *after* the call to an async function does not wait for it unless the caller awaits too.

**Interview tip:** describe it as "a yield point. The function's local state is saved, and a microtask resumes it once the promise settles."

**Takeaway:** `await` pauses only its own async function, never the thread. The function always resumes in a later microtask.

</details>

## A4. Log order around `await null` · `easy` · 🖨️ Output

```js
async function loadWatchlist() {
  console.log('A');
  await null;
  console.log('B');
}

loadWatchlist();
console.log('C');
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
A
C
B
```

1. `loadWatchlist()` starts running synchronously and prints `A`.
2. `await null` wraps `null` in an already-fulfilled promise, but the function **still pauses**. Its continuation is queued as a microtask.
3. Control goes back to the caller, which prints `C`.
4. The script finishes, the stack empties, and the microtask resumes the function, which prints `B`.

| Phase | Output |
|---|---|
| sync: function body before `await` | A |
| sync: rest of script | C |
| microtask: continuation | B |

**Takeaway:** everything after an `await` runs asynchronously, even when the awaited value is not a promise.

</details>

## A5. Awaiting non-promises and thenables · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Rule:** `await v` works on *any* value. Internally it calls `PromiseResolve(v)`:
- **Native promise:** used as-is.
- **Thenable** (any object with a callable `then` method): wrapped in a new promise. Its `then(resolve, reject)` is called **in a later microtask** to adopt its state.
- **Anything else** (`5`, `null`, `{}`): wrapped in a promise that is already fulfilled with that value.

```js
async function demo() {
  const a = await 42;                                  // 42
  const b = await { then(res) { res('from thenable'); } };
  const c = await { price: 10 };                       // plain object, returned as-is
  console.log(a, b, c.price);
}
```

**Why it matters:**
- Old libraries (jQuery Deferred, some SDKs) return thenables. `await` works with them anyway.
- You can write code that accepts "a value or a promise" and simply `await` it.

**Pitfalls**
- An object that *accidentally* has a `then` method (for example a query builder) gets treated as a thenable. `await` may call it, and if `then` never calls `resolve`, the function hangs forever.
- `await` on a non-promise still costs a microtask, so it is never synchronous.

**Interview tip:** mention that this "thenable assimilation" is what lets different promise libraries work together.

**Takeaway:** `await` accepts any value. Thenables are adopted by calling their `then`, and other values are wrapped in a fulfilled promise.

</details>

## A6. `try/catch` around an awaited rejection · `easy` · 🖨️ Output

```js
async function fetchQuote(symbol) {
  if (symbol === 'XYZ') throw new Error('Unknown symbol ' + symbol);
  return 100;
}

async function show(symbol) {
  try {
    const price = await fetchQuote(symbol);
    console.log(symbol + ': ' + price);
  } catch (e) {
    console.log('Error: ' + e.message);
  }
}

show('INFY').then(() => show('XYZ'));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
INFY: 100
Error: Unknown symbol XYZ
```

1. `show('INFY')` calls `fetchQuote('INFY')`, which returns a promise fulfilled with `100`. After the `await`, `price` is `100` and `INFY: 100` prints.
2. When `show('INFY')` finishes, `.then` calls `show('XYZ')`.
3. `fetchQuote('XYZ')` throws, so its promise is **rejected** (an async function never throws at the call site).
4. `await` on a rejected promise **throws the reason** at that line, so control jumps into `catch`, which prints `Error: Unknown symbol XYZ`.
5. The rejection was handled, so there is no "Uncaught (in promise)" message.

**Takeaway:** `await` converts a rejection back into a thrown exception, so a normal `try/catch` handles async errors.

</details>

## A7. Error handling with `try/catch/finally` in async functions · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**How it works:** inside an async function, a rejected `await` throws. That lets you use normal `try/catch/finally`:

```js
async function submitOrder(order) {
  setLoading(true);
  try {
    const res = await api.place(order);   // a rejection jumps to catch
    showToast('Placed #' + res.id);
    return res;
  } catch (err) {
    showToast('Order failed: ' + err.message);
    throw err;                            // rethrow if the caller must know
  } finally {
    setLoading(false);                    // runs on success AND on failure
  }
}
```

**Why it matters:** `finally` is the right place for cleanup such as spinners, releasing locks, closing sockets and clearing timers.

**Pitfalls**
- `try/catch` only catches promises that are **awaited inside the try block**. `try { doAsync(); }` without `await` catches nothing.
- If `catch` swallows the error (no rethrow), the returned promise **fulfils** with `undefined`. Callers then think it succeeded.
- A `return` inside `finally` overrides the earlier return or throw. Avoid it.
- Callers of a function that can reject must handle it too: `submitOrder(o).catch(...)` or await it inside their own try.

**Alternative:** `const [err, data] = await to(promise)` helpers, or `.catch()` on a single call: `const data = await fetchX().catch(() => fallback)`.

**Takeaway:** only awaited promises are caught. Use `finally` for cleanup and rethrow when the caller needs to know about the failure.

</details>

## A8. Process orders sequentially vs in parallel · `easy` · 💻 Coding

Write two helpers:

- `processSequentially(items, worker)`: calls the async `worker(item)` **one at a time**, waiting for each call to finish before starting the next.
- `processInParallel(items, worker)`: starts **all** calls at once.

Both must resolve with an array of results **in input order**.

```js
await processSequentially(['o1', 'o2'], placeOrder); // ['o1:ok', 'o2:ok']
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function processSequentially(items, worker) {
  const results = [];
  for (const item of items) {
    results.push(await worker(item)); // wait before starting the next one
  }
  return results;
}

async function processInParallel(items, worker) {
  return Promise.all(items.map(item => worker(item))); // start all, wait for all
}
```

**Test**

```js
const wait = ms => new Promise(r => setTimeout(r, ms));
const orders = [{ id: 'o1', ms: 60 }, { id: 'o2', ms: 20 }, { id: 'o3', ms: 40 }];
let log = [];
async function placeOrder(o) {
  log.push('start ' + o.id);
  await wait(o.ms);
  log.push('end ' + o.id);
  return o.id + ':ok';
}

(async () => {
  const seq = await processSequentially(orders, placeOrder);
  console.log('sequential results: ' + seq.join(','));
  console.log('sequential log: ' + log.join(' | '));

  log = [];
  const par = await processInParallel(orders, placeOrder);
  console.log('parallel results: ' + par.join(','));
  console.log('parallel log: ' + log.join(' | '));

  const empty = await processSequentially([], placeOrder);
  console.log('empty: ' + empty.length);
})();
```

**Output**

```text
sequential results: o1:ok,o2:ok,o3:ok
sequential log: start o1 | end o1 | start o2 | end o2 | start o3 | end o3
parallel results: o1:ok,o2:ok,o3:ok
parallel log: start o1 | start o2 | start o3 | end o2 | end o3 | end o1
empty: 0
```

**Approach**
- *Sequential:* `await` inside a `for...of` loop pauses the loop, so each worker starts only after the previous one finishes. Total time is the sum of the durations (60 + 20 + 40 ms).
- *Parallel:* `items.map(worker)` starts every call immediately, and `Promise.all` waits for all of them. Total time is the longest duration (60 ms). `Promise.all` keeps **input order** in its results even though `o2` finishes first (see the log).

**Edge cases:** an empty array gives `[]` in both cases (`Promise.all([])` fulfils immediately). If one worker rejects, sequential stops at that item. Parallel rejects fast, but the other calls keep running.

**Complexity:** O(n) time and space for both, apart from the waiting.

**Common mistakes**
- Using `items.forEach(async ...)`. `forEach` ignores the returned promises, so nothing is awaited.
- Pushing results in completion order instead of index order.
- Using sequential processing for independent requests, which makes a slow waterfall.

**Takeaway:** use `for...of` + `await` when the order or rate of calls matters, and `Promise.all(map)` when the calls are independent.

</details>

## A9. Async arrow functions, methods and other syntax forms · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Every function form can be async:**

```js
async function declared() {}                 // declaration
const expr = async function () {};           // expression
const arrow = async (symbol) => fetchLtp(symbol); // arrow (implicit return)
const one = async x => x * 2;                // single parameter

const api = {
  async getQuote(s) { /* ... */ },           // object method
};

class Portfolio {
  async refresh() { /* ... */ }              // class method
  static async load(id) { /* ... */ }        // static method
  async *streamTicks() { /* ... */ }         // async generator method
}
```

**Why it matters:** async arrows are the usual choice for callbacks (`items.map(async x => ...)`, event handlers). Like normal arrows, they use the `this` of the surrounding scope, which helps inside class methods.

**Pitfalls**
- An **async arrow that returns an object literal** needs parentheses: `async () => ({ ok: true })`.
- **Not allowed as async:** `constructor`, getters and setters (`async get price()` is a SyntaxError).
- `await` is not allowed in a *nested* normal function inside an async function. The nested callback must be async itself.
- `async` must come before the arrow's parameters: `async x => ...`, not `x => async ...`.

**Interview tip:** point out that `arr.map(async ...)` returns an array of **promises**, not values, which is why it is usually paired with `Promise.all`.

**Takeaway:** declarations, expressions, arrows and methods can all be async. Constructors, getters and setters cannot.

</details>

## A10. Does `try/catch` catch an async function that throws? · `easy` · 🖨️ Output

```js
async function cancelOrder() {
  throw new Error('order already filled');
}

try {
  cancelOrder();
  console.log('no sync error');
} catch (e) {
  console.log('caught sync');
}

cancelOrder().catch(e => console.log('caught async: ' + e.message));
console.log('end of script');
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
no sync error
end of script
caught async: order already filled
Uncaught (in promise) Error: order already filled
```

1. `cancelOrder()` throws inside an **async** function. The error does not propagate synchronously. The returned promise is **rejected** instead.
2. So the `try` block sees no exception. `no sync error` prints and `catch` is skipped. The rejected promise from this first call is never handled.
3. The second call's rejected promise gets a `.catch` handler, and a reaction job is queued.
4. `end of script` prints (sync code first).
5. The microtask runs and prints `caught async: order already filled`.
6. After the microtasks drain, the engine sees that the **first** promise is still rejected with no handler and reports it: `Uncaught (in promise) Error: order already filled`.

**Takeaway:** a plain `try/catch` around an un-awaited async call catches nothing. Either `await` the call inside the try or attach `.catch`.

</details>

## A11. Top-level `await` · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Definition:** ES2022 allows `await` at the **top level of ES modules** (`<script type="module">`, `.mjs` files, or `"type": "module"` in package.json), outside any async function.

```js
// config.mjs
const res = await fetch('/api/config');
export const config = await res.json();

// app.mjs
import { config } from './config.mjs'; // app.mjs waits until config.mjs has finished evaluating
```

**Why it matters:** it removes the `(async () => { ... })()` wrapper for startup code, such as loading config, feature flags, dynamic `import()` with a fallback, or database connections in scripts.

**How it behaves:** a module that uses top-level await pauses its own evaluation. **Modules that import it wait** until it finishes. Unrelated sibling modules can keep evaluating.

**Pitfalls**
- It is a **SyntaxError in classic scripts** and CommonJS (`require`). There you still need an async IIFE.
- A slow top-level await **delays everything that imports that module**, including app startup.
- Two modules that import each other and both use top-level await can deadlock.
- Bundlers need a modern build target to support it.

```js
// classic script / CommonJS equivalent
(async () => {
  const cfg = await loadConfig();
  start(cfg);
})().catch(console.error);
```

**Takeaway:** top-level await works only in ES modules and blocks the modules that import it. Elsewhere, wrap the code in an async IIFE.

</details>

## A12. Awaiting a thenable · `easy` · 🖨️ Output

```js
const priceFeed = {
  then(resolve) {
    console.log('then called');
    resolve(42);
  },
};

(async () => {
  console.log('before');
  const value = await priceFeed;
  console.log('value ' + value);
})();

console.log('sync end');
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
before
sync end
then called
value 42
```

1. The async IIFE runs synchronously and prints `before`.
2. `await priceFeed` sees an object with a callable `then`, so the object is a **thenable**. The engine creates a promise for it and queues a *PromiseResolveThenableJob*. It does **not** call `then` synchronously.
3. The IIFE is suspended, and `sync end` prints.
4. Microtask 1: the job calls `priceFeed.then(resolve, reject)`, which prints `then called` and resolves with `42`. That queues the continuation.
5. Microtask 2: the function resumes with `value = 42` and prints `value 42`.

**Takeaway:** `await` adopts any thenable by calling its `then` in a later microtask, never synchronously.

</details>

## A13. `withTimeout(promise, ms)` using async/await · `easy` · 💻 Coding

Implement `withTimeout(promise, ms)`:

- It resolves or rejects with `promise` if that settles within `ms` milliseconds.
- Otherwise it rejects with `Error('Timed out after <ms>ms')`.
- It must **clear its timer** when finished, so no timers are left pending.

```js
await withTimeout(getQuote('TCS'), 100); // quote, or a timeout error
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function withTimeout(promise, ms) {
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error('Timed out after ' + ms + 'ms')), ms);
  });
  try {
    return await Promise.race([promise, timeout]);
  } finally {
    clearTimeout(timer); // always clean up, whoever won
  }
}
```

**Test**

```js
const wait = (ms, value) => new Promise(r => setTimeout(() => r(value), ms));
const failAfter = (ms, msg) => new Promise((_, rej) => setTimeout(() => rej(new Error(msg)), ms));

(async () => {
  console.log('fast: ' + await withTimeout(wait(20, 'quote 101.5'), 100));

  try {
    await withTimeout(wait(200, 'too late'), 50);
  } catch (e) {
    console.log('slow: ' + e.message);
  }

  try {
    await withTimeout(failAfter(10, 'exchange down'), 100);
  } catch (e) {
    console.log('rejected: ' + e.message);
  }

  console.log('plain value: ' + await withTimeout(7, 50));
})();
```

**Output**

```text
fast: quote 101.5
slow: Timed out after 50ms
rejected: exchange down
plain value: 7
```

**Approach:** race the real promise against a promise that rejects after `ms`. `Promise.race` settles the same way as whichever input settles first. `return await` inside `try` makes sure `finally` runs **after** the race settles, so the timer is always cleared.

**Edge cases**
- A rejection before the timeout passes through unchanged (`exchange down`).
- A non-promise value works because `Promise.race` resolves every input.
- The slow promise still runs to completion in the background. A timeout **does not cancel** work. Use `AbortController` for real cancellation.

**Complexity:** O(1) extra work and memory.

**Common mistakes**
- Not clearing the timer. It keeps the Node process alive, or fires a stray rejection later.
- Writing `return Promise.race(...)` without `await`. Then `finally` runs immediately, before the race settles, and clears the timer too early.
- Creating the timeout promise without the `race`. Its rejection goes unhandled.

**Takeaway:** a timeout is a race between the work and a timer. Always clear the timer, and remember that a timeout does not stop the work.

</details>

## A14. `return promise` vs `return await promise` inside `try/catch` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Rule:** outside `try` blocks, `return p` and `return await p` give the same result (the async function's promise follows `p`). **Inside `try`**, they behave differently:

- `return await p`: the function waits **inside the try**. A rejection is thrown *there*, so `catch` and `finally` see it.
- `return p`: the function hands `p` over and leaves the `try` immediately. `finally` runs *before* `p` settles, and a later rejection **skips your `catch`** and goes straight to the caller.

```js
async function getPrice(sym) {
  try {
    return await api.ltp(sym);   // correct: the fallback works
  } catch {
    return cache.get(sym);
  }
}

async function broken(sym) {
  try {
    return api.ltp(sym);         // a rejection is not caught here
  } catch {
    return cache.get(sym);       // never runs for async failures
  }
}
```

**Other points**
- `return await` also keeps the function in **async stack traces**, which helps debugging.
- The ESLint rule `no-return-await` is deprecated. Modern guidance (`@typescript-eslint/return-await`) *requires* `return await` inside try/catch.
- Outside try, the difference is only timing: the extra microtask ticks were mostly removed by a 2019 spec optimisation.

**Takeaway:** inside `try/catch/finally`, always write `return await`. Otherwise rejections bypass your handler.

</details>

## A15. `return` vs `return await` with a fallback · `medium` · 🖨️ Output

```js
async function fetchLtp() {
  throw new Error('API down');
}

async function withoutAwait() {
  try {
    return fetchLtp();
  } catch {
    return 'fallback-1';
  }
}

async function withAwait() {
  try {
    return await fetchLtp();
  } catch {
    return 'fallback-2';
  }
}

(async () => {
  try {
    console.log(await withoutAwait());
  } catch (e) {
    console.log('escaped: ' + e.message);
  }
  console.log(await withAwait());
})();
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
escaped: API down
fallback-2
```

1. In `withoutAwait`, `fetchLtp()` returns a **rejected promise**. It does not throw synchronously, so `try` completes normally by returning that promise.
2. The `catch` is never entered. `withoutAwait()`'s own promise adopts the rejection.
3. The caller awaits it, the rejection is thrown in the IIFE, and the outer `catch` prints `escaped: API down`.
4. In `withAwait`, `await fetchLtp()` throws **inside** the `try`, so the local `catch` runs and returns `'fallback-2'`.
5. The IIFE prints `fallback-2`.

**Takeaway:** a local `catch` can only handle a rejection that is awaited inside its `try`, so write `return await` there.

</details>

## A16. Sequential vs parallel `await` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Sequential:** each `await` waits for the previous one to finish. Total time is the **sum** of the durations.
**Parallel:** start all the operations first, then await them. Total time is the **longest** duration.

```js
// sequential: ~300 ms if each call takes 100 ms
const profile = await getProfile();
const holdings = await getHoldings();
const orders = await getOrders();

// parallel: ~100 ms
const [profile, holdings, orders] = await Promise.all([
  getProfile(), getHoldings(), getOrders(),
]);
```

**When to use sequential**
- A later call **depends** on an earlier result (`getOrders(profile.clientId)`).
- You must respect rate limits or ordering (placing orders one by one).
- The server cannot handle the concurrent load.

**When to use parallel:** the calls are independent, such as loading dashboard widgets or fetching quotes for several symbols.

**Pitfalls**
- Writing sequential awaits by habit is the most common async performance bug (a "waterfall").
- `Promise.all` rejects on the first failure. Use `Promise.allSettled` if partial data is fine.
- Unbounded parallelism (`Promise.all` over 5,000 items) can overload the API. Use a concurrency limit.

**Interview tip:** draw both timelines and mention that `Promise.all` keeps the result order equal to the input order.

**Takeaway:** await in sequence only when there is a dependency or a limit. Otherwise start everything and `await Promise.all`.

</details>

## A17. Sequential vs parallel timers · `medium` · 🖨️ Output

```js
const wait = (ms, label) =>
  new Promise(r => setTimeout(() => { console.log(label); r(label); }, ms));

async function sequential() {
  await wait(100, 'seq-1');
  await wait(50, 'seq-2');
}

async function parallel() {
  const a = wait(100, 'par-1');
  const b = wait(50, 'par-2');
  await a;
  await b;
}

sequential();
parallel();
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
par-2
seq-1
par-1
seq-2
```

Timers scheduled at t = 0:
- `sequential()` creates only **seq-1 (100 ms)**. `seq-2` is not created until seq-1 has finished.
- `parallel()` creates **par-1 (100 ms)** and **par-2 (50 ms)** straight away.

| Time | Event | Output |
|---|---|---|
| 50 ms | par-2 fires | par-2 |
| 100 ms | seq-1 fires (created before par-1) | seq-1 |
| 100 ms | par-1 fires | par-1 |
| 100 ms | `sequential` resumes and schedules seq-2 for 150 ms | |
| 150 ms | seq-2 fires | seq-2 |

`parallel` finishes at about 100 ms. `sequential` needs about 150 ms because the second timer only starts after the first one ends. Timers with the same delay fire in the order they were created.

**Takeaway:** an async operation starts when you *call* it, not when you *await* it. Start the calls early to run them in parallel.

</details>

## A18. Pitfall: `const a = f(); const b = g(); await a; await b;` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**The pattern:** starting two promises and then awaiting them one after the other *does* run them in parallel, but the error handling is fragile.

```js
async function loadDashboard() {
  const quotesP = getQuotes();     // takes 2 s
  const newsP = getNews();         // rejects after 100 ms
  const quotes = await quotesP;    // still waiting here...
  const news = await newsP;        // ...so nothing is handling newsP yet
}
```

**What goes wrong:** `newsP` rejects while the function is still paused on `quotesP`. At that moment **nothing has attached a handler** to `newsP`, so:
- browsers log **"Uncaught (in promise)"** and fire `unhandledrejection`
- Node (v15+) **crashes the process** by default
- if `quotesP` also rejects first, `newsP`'s rejection is never observed at all

A later `await newsP` inside `try/catch` does not undo the report, because it arrives too late.

**Fix:** attach the handlers together, straight away:
```js
const [quotes, news] = await Promise.all([getQuotes(), getNews()]);
// or, when partial results are fine:
const results = await Promise.allSettled([getQuotes(), getNews()]);
```

**Interview tip:** explain that `Promise.all` subscribes to *every* promise immediately, which is why it is the safe way to await promises that run in parallel.

**Takeaway:** never leave a started promise without a handler while you await something else. Combine them with `Promise.all` or `allSettled`.

</details>

## A20. `await` in `for...of` vs `forEach` vs `map` + `Promise.all` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

| Pattern | Runs | Waits? | Results |
|---|---|---|---|
| `for (const x of arr) await f(x)` | one after another | yes | collect them yourself |
| `arr.forEach(async x => await f(x))` | all at once | **no** | lost |
| `await Promise.all(arr.map(f))` | all at once | yes | array in input order |
| `for await (const v of arr.map(f))` | all at once | yes, one by one in order | streamed one at a time |

```js
  await placeOrder(order);
}

// parallel: independent work
```

**Pitfalls**
- `Promise.all(arr.map(...))` on a huge array fires every request at once. Use batches or a pool.
- `reduce` with `async` needs the accumulator to be awaited: `acc = await acc`.

**Takeaway:** `for...of` runs work in sequence and `map` + `Promise.all` runs it in parallel. Never use `forEach` for async work.

## A22. Async retry with exponential backoff · `medium` · 💻 Coding

Implement `retry(fn, options)`:

- Call `fn(attempt)` (attempt starts at 0) and return its resolved value.
- On failure, wait `baseDelay * factor ** attempt` ms and try again, up to `retries` extra times.
- Call `onRetry(error, attemptNumber, delay)` before each wait, if provided.
- After the last failure, reject with the **last error**.
- Defaults: `retries = 3`, `baseDelay = 10`, `factor = 2`.

```js
await retry(() => placeOrder(o), { retries: 2 }); // up to 3 attempts in total
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
const sleep = ms => new Promise(r => setTimeout(r, ms));

async function retry(fn, { retries = 3, baseDelay = 10, factor = 2, onRetry } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(attempt); // await so that rejections land in catch
    } catch (err) {
      if (attempt >= retries) throw err;
      const delay = baseDelay * factor ** attempt;
      if (onRetry) onRetry(err, attempt + 1, delay);
      await sleep(delay);
    }
  }
}
```

**Test**

```js

  let calls = 0;
  const flaky = async () => {
    calls++;
    if (calls < 3) throw new Error('503 from OMS');
    return 'order accepted';
  };
  console.log('flaky: ' + await retry(flaky, { onRetry: logRetry }) + ' after ' + calls + ' calls');

  let attempts = 0;
  try {
    await retry(async () => { attempts++; throw new Error('fail ' + attempts); }, { retries: 2, onRetry: logRetry });
  } catch (e) {
    console.log('gave up: ' + e.message + ', attempts=' + attempts);
  }

  const noRetry = await retry(async a => 'first try, attempt ' + a, { retries: 0 });
  console.log(noRetry);

  try {
    await retry(() => { throw new TypeError('sync throw'); }, { retries: 1, baseDelay: 5 });
  } catch (e) {
    console.log('sync error handled: ' + e.name);
  }
})();
```

**Output**

```text
  retry #1 in 10ms (503 from OMS)
  retry #2 in 20ms (503 from OMS)
flaky: order accepted after 3 calls
  retry #1 in 10ms (fail 1)
  retry #2 in 20ms (fail 2)
gave up: fail 3, attempts=3
first try, attempt 0
sync error handled: TypeError
```

**Approach:** an endless `for` loop with `try { return await fn() }`. A success returns straight out of the loop. A failure either rethrows (no retries left) or waits for an exponentially growing delay (10, 20, 40 ms, ...) before the next attempt.

**Edge cases**
- `retries: 0` means exactly one attempt.
- A synchronous throw inside `fn` is caught too, because it happens inside the `try`.
- The error you get at the end is the **last** one (`fail 3`), which is usually the most relevant.

**Complexity:** at most `retries + 1` calls. The total wait is `baseDelay * (factor^retries - 1) / (factor - 1)`. O(1) memory.

**Common mistakes**
- `return fn()` without `await`: the rejection skips `catch`, so nothing is retried.
- Retrying errors that cannot succeed (400, validation failures). In real code, add a `shouldRetry(err)` check.
- No **jitter**. In production, add a random offset so many clients do not retry at the same moment.

**Takeaway:** `return await` inside a loop's `try` is the core of async retry. Grow the delay each time and rethrow the last error.

</details>

## A23. Async work in class constructors: the factory pattern · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Problem:** a `constructor` cannot be `async` (SyntaxError), and it must return the instance, not a promise. If you start async work inside it, callers get an object that is **not ready yet**, and its errors go unhandled.

```js

  constructor() {
    this.socket = null;
    this.connect(); // fire-and-forget: a race condition and an unhandled rejection
  }
}
```

**Fix: a static async factory**
```js
class MarketFeed {
  constructor(socket, symbols) {    // cheap, synchronous, and always valid
    this.socket = socket;
    this.symbols = symbols;
  }
  static async create(url) {
    const socket = await openSocket(url);
    const symbols = await socket.request('symbols');
    return new MarketFeed(socket, symbols);
  }
}
const feed = await MarketFeed.create(WS_URL); // fully ready here
```

**Alternatives**
- An explicit `await feed.init()` step (easy to forget).
- Store a `this.ready = this.#init()` promise and have methods `await this.ready` first.
- Returning a promise from the constructor is technically possible, but it breaks `instanceof` expectations and confuses readers. Avoid it.

**Interview tip:** name it the "async factory" or "static create" pattern, and mention that the constructor stays cheap and synchronous, which also makes it easy to test.

**Takeaway:** do the async setup in `static async create()` and pass the results into a plain synchronous constructor.

## A25. Process items in batches · `medium` · 💻 Coding

Implement `processInBatches(items, batchSize, worker)`:

- Split `items` into chunks of `batchSize`.
- Run each chunk **in parallel** with `worker(item, index)`, but wait for a chunk to finish before starting the next.
- Resolve with all results in input order.
- Throw `RangeError` if `batchSize < 1`.

```js
await processInBatches(symbols, 2, fetchQuote); // at most 2 requests at a time
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function processInBatches(items, batchSize, worker) {
  if (!(batchSize >= 1)) throw new RangeError('batchSize must be >= 1');
  const results = [];
  for (let start = 0; start < items.length; start += batchSize) {
    const batch = items.slice(start, start + batchSize);
    const batchResults = await Promise.all(
      batch.map((item, j) => worker(item, start + j))
    );
    results.push(...batchResults);
  }
  return results;
}
```

```js
  console.log('max concurrent: ' + maxActive);
```

**Approach:** step through the array `batchSize` items at a time. For each slice, `await Promise.all`, which runs the slice in parallel and blocks the next slice until it is finished. Passing `start + j` gives the worker the item's global index.

**Edge cases**

- An empty input returns `[]` without calling the worker.
- Checking `!(batchSize >= 1)` also rejects `NaN`, which would otherwise loop forever.

## A26. Async functions inside React `useEffect` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Rule:** the `useEffect` callback must return **nothing or a cleanup function**. An `async` function returns a Promise, so `useEffect(async () => ...)` is wrong. React warns about it, and your cleanup never runs.

**Correct pattern:** define an async function *inside* the effect, call it, and handle stale results or cancellation in the cleanup.

```js
useEffect(() => {
  const controller = new AbortController();

  async function loadQuote() {
    try {
      setStatus('loading');
      const res = await fetch('/api/quote/' + symbol, { signal: controller.signal });
      const data = await res.json();
      setQuote(data);          // does not run after an abort
      setStatus('done');
    } catch (err) {
      if (err.name !== 'AbortError') setStatus('error');
    }
  }

  loadQuote();
  return () => controller.abort(); // runs when symbol changes or on unmount
}, [symbol]);
```

**Why it matters:** when the user switches from TCS to INFY quickly, a slow TCS response can arrive **after** the INFY one and overwrite it (a race condition). Aborting, or an `ignore` flag set in the cleanup, prevents that.

**Pitfalls**
- Missing dependencies cause stale closures.
- React 18 StrictMode runs effects twice in development, so your cleanup must be correct.
- Unhandled rejections inside the inner function must be caught.
- For real apps, prefer a data library (React Query or SWR) that handles caching and races.

**Takeaway:** never make the effect callback itself async. Call an inner async function and cancel or ignore stale work in the cleanup.

</details>

## A28. Poll until a condition is met (max attempts) · `medium` · 💻 Coding

Implement `pollUntil(check, { interval, maxAttempts })`:

- Call the async `check(attempt)` (attempt starts at 1).
- If it returns a **truthy** value, resolve with `{ result, attempts }`.
- Otherwise wait `interval` ms and try again, at most `maxAttempts` times in total.
- Do **not** sleep after the final attempt. Then reject with `Error('Condition not met after N attempts')`.
- If `check` throws, reject straight away with that error.

Use case: poll an order's status until it is `FILLED`.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
const sleep = ms => new Promise(r => setTimeout(r, ms));

async function pollUntil(check, { interval = 20, maxAttempts = 5 } = {}) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const result = await check(attempt);
    if (result) return { result, attempts: attempt };
    if (attempt < maxAttempts) await sleep(interval);
  }
  throw new Error('Condition not met after ' + maxAttempts + ' attempts');
}
```

**Test**

```js

  const { result, attempts } = await pollUntil(async n => {
    const status = statuses[n - 1];
    console.log('attempt ' + n + ': ' + status);
    return status === 'FILLED' && status;
  }, { interval: 15 });
  console.log('done: ' + result + ' in ' + attempts);

  try {
    await pollUntil(async () => false, { interval: 5, maxAttempts: 3 });
  } catch (e) {
    console.log(e.message);
  }

  try {
    await pollUntil(async n => { if (n === 2) throw new Error('order not found'); return null; }, { interval: 5 });
  } catch (e) {
    console.log('check failed: ' + e.message);
  }

  const first = await pollUntil(async () => 'ready');
  console.log('immediate: ' + first.result + ' in ' + first.attempts);
})();
```

```text

attempt 2: PARTIAL
attempt 3: FILLED

```

**Approach:** a counted `for` loop. Await the check, return as soon as it gives a truthy value, and sleep between attempts. Because the loop uses `await`, a throw inside `check` rejects the whole `pollUntil` promise with no extra code.

**Edge cases**
- Success on the first attempt returns immediately without sleeping.
- No sleep after the last attempt, so a failure is not delayed for nothing.
- Falsy but meaningful results (`0`, `''`) count as "not ready". Use an explicit predicate if you need them.

**Complexity:** at most `maxAttempts` calls. Worst-case time is about `(maxAttempts - 1) * interval` plus the time the checks take.

**Common mistakes**
- Using `setInterval`, which can overlap slow checks. The loop above never starts a new check before the previous one finishes.
- Polling forever with no limit.
- Not making polling cancellable. In a UI, pass an `AbortSignal` and stop when the component unmounts.

**Takeaway:** polling is a bounded loop of await check, then sleep. Stop on success, on error, or when attempts run out.

## A29. `Promise.all` vs `Promise.allSettled` (and `any`/`race`) with async/await · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

| Combinator | Fulfils when | Rejects when | Use case |
|---|---|---|---|
| `Promise.all` | **all** fulfil (value array) | **first** rejection | every result is required |
| `Promise.allSettled` | **all settle** (never rejects) | never | partial success is fine |
| `Promise.any` | **first** fulfilment | all reject (`AggregateError`) | fastest healthy mirror |
| `Promise.race` | first to settle | first to settle (if it rejects) | timeouts |

```js
// dashboard: show whatever loaded
const results = await Promise.allSettled([getHoldings(), getNews(), getIpoList()]);
const [holdings, news, ipos] = results.map(r =>
  r.status === 'fulfilled' ? r.value : null
);
results
  .filter(r => r.status === 'rejected')
  .forEach(r => logError(r.reason));

// order placement: all legs must succeed
try {
  const [leg1, leg2] = await Promise.all([placeLeg(a), placeLeg(b)]);
} catch (e) {
  // one leg failed; the other may still be running or may have succeeded
}
```

**Pitfalls**
- `Promise.all` failing fast does **not** cancel the other operations. They keep running, and their results are ignored.
- With `allSettled`, you must check `status` yourself. Failures are silent otherwise.
- `Promise.any([])` rejects with an `AggregateError`, while `Promise.all([])` fulfils with `[]`.

**Takeaway:** use `all` when every result is required and `allSettled` when partial data is acceptable. Neither one cancels the losing operations.

</details>

## A30. `asyncMap`, `asyncFilter` and `asyncReduce` · `medium` · 💻 Coding

Implement three helpers for async callbacks:

- `asyncMap(arr, fn)`: runs `fn(item, index, arr)` **in parallel** and resolves with the results in order.
- `asyncFilter(arr, predicate)`: evaluates the async predicates in parallel and keeps the items whose predicate resolved truthy, in their original order.
- `asyncReduce(arr, fn, initial)`: runs **sequentially**, awaiting each step. If `initial` is omitted, use the first element. An empty array with no initial value must throw `TypeError`, like `Array.prototype.reduce`.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function asyncMap(arr, fn) {
  return Promise.all(arr.map((item, i) => fn(item, i, arr)));
}

async function asyncFilter(arr, predicate) {
  const keep = await asyncMap(arr, predicate);
  return arr.filter((_, i) => keep[i]);
}

async function asyncReduce(arr, fn, ...rest) {
  let i = 0;
  let acc;
  if (rest.length > 0) {
    acc = rest[0];
  } else {
    if (arr.length === 0) throw new TypeError('Reduce of empty array with no initial value');
    acc = arr[0];
    i = 1;
  }
  for (; i < arr.length; i++) {
    acc = await fn(acc, arr[i], i, arr);
  }
  return acc;
}
```

```text
no initial: 123
TypeError: Reduce of empty array with no initial value
filter empty: 0
```

**Approach**
- `asyncMap`: plain `map` returns promises, and `Promise.all` turns them into ordered values. Items finish in reverse order here (the delays shrink), but the output keeps input order.
- `asyncFilter`: first resolve all the booleans, then filter **synchronously** using them. Calling `arr.filter(async ...)` directly would keep everything, because a promise is always truthy.
- `asyncReduce`: each step needs the previous accumulator, so it has to be sequential. A `for` loop with `await` does that.

**Edge cases**
- The rest parameter tells "no initial value" apart from `initial === undefined`.
- Empty input with no initial value gives a `TypeError`, matching the native method.
- Empty filter input returns `[]`.

**Complexity:** map and filter take O(n) with all calls in parallel. Reduce takes O(n) with the calls one after another.

**Common mistakes:** `filter(async ...)`; using `reduce(async (acc) => ...)` without awaiting `acc`; running a reduce in parallel when each step depends on the last.

**Takeaway:** map and filter can run in parallel with `Promise.all`. Reduce needs a sequential `for` + `await` loop.

</details>

## A31. Timeouts with `Promise.race` in async code · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Idea:** race the real work against a timer that rejects.

```js
async function withTimeout(work, ms) {
  let id;
  const timer = new Promise((_, reject) => {
    id = setTimeout(() => reject(new Error('Timeout ' + ms + 'ms')), ms);
  });
  try {
    return await Promise.race([work, timer]);
  } finally {
    clearTimeout(id);
  }
}

const quote = await withTimeout(getQuote('NIFTY'), 2000);
```

**Key facts**
- `Promise.race` settles the same way as the **first input to settle**, whether it fulfils or rejects.
- The losing promise **keeps running**. A race does not cancel anything. For an HTTP call, pass an `AbortSignal` and call `controller.abort()` on timeout, so the request is actually cancelled.
- Modern platforms offer `AbortSignal.timeout(ms)`: `fetch(url, { signal: AbortSignal.timeout(2000) })`.

**Pitfalls**
- **Forgetting `clearTimeout`** leaks timers. In Node, the process stays alive until the timer fires.
- `return Promise.race(...)` without `await` makes `finally` run too early.
- `Promise.race([])` stays pending forever.
- Showing "timed out" while the order was actually placed on the server. For non-idempotent actions, check the real status before retrying.

**Interview tip:** always mention that a timeout does not cancel the work, and explain how you would cancel it with `AbortController`.

**Takeaway:** `Promise.race` puts a deadline on waiting, not on the work itself. Clear the timer, and abort the work if it matters.

</details>

## A33. `once(emitter, event)`: resolve on the first event · `medium` · 💻 Coding

Implement `once(emitter, event)`, which returns a promise that:

- resolves with an **array of the event's arguments** the first time `event` fires
- rejects if the emitter emits `'error'` first (unless you are waiting for `'error'` itself)
- **removes all of its listeners** once it settles

The emitter has `on(name, fn)`, `off(name, fn)` and `emit(name, ...args)`.

```js
const [price] = await once(feed, 'tick');
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function once(emitter, event) {
  return new Promise((resolve, reject) => {
    const onEvent = (...args) => {
      cleanup();
      resolve(args);
    };
    const onError = err => {
      cleanup();
      reject(err);
    };
    const cleanup = () => {
      emitter.off(event, onEvent);
      if (event !== 'error') emitter.off('error', onError);
    };
    emitter.on(event, onEvent);
    if (event !== 'error') emitter.on('error', onError);
  });
}
```

**Test**

```js

  constructor() { this.listeners = {}; }
  on(name, fn) { (this.listeners[name] = this.listeners[name] || []).push(fn); }
  off(name, fn) { this.listeners[name] = (this.listeners[name] || []).filter(f => f !== fn); }
  emit(name, ...args) { (this.listeners[name] || []).slice().forEach(fn => fn(...args)); }
  count(name) { return (this.listeners[name] || []).length; }
}

  console.log('listeners left: tick=' + feed.count('tick') + ' error=' + feed.count('error'));

  setTimeout(() => socket.emit('error', new Error('socket closed')), 10);
  try {
    await once(socket, 'open');
  } catch (e) {
    console.log('rejected: ' + e.message);
  }
  console.log('listeners left: open=' + socket.count('open') + ' error=' + socket.count('error'));
```

**Output**


**Approach:** wrap the event API in `new Promise`. Register the event listener and an `'error'` listener. Whichever fires first calls `cleanup()` to remove **both** listeners, then settles the promise.

**Edge cases**
- The second `tick` is ignored: the listener has already been removed, and a promise can settle only once anyway.
- Events with no arguments resolve with `[]`.
- When waiting for `'error'` itself, we must not also treat it as a failure, hence the `event !== 'error'` checks.
- The emitter copies its listener list before calling listeners, so removing a listener during `emit` is safe.

**Complexity:** O(1) per call, apart from the emitter's own add and remove cost.

**Common mistakes**
- Forgetting to remove the error listener, so every call leaks one listener.
- Resolving with only the first argument, which loses the rest.
- Not supporting cancellation. Node's `events.once` also accepts `{ signal }` to stop waiting.

**Takeaway:** turning an event into a promise means subscribing, settling on the first event or error, and always unsubscribing.

## A34. Converting callback and `.then` code to async/await · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Step 1: wrap callback APIs in promises** ("promisify"):
```js
function readConfig(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, 'utf8', (err, data) => (err ? reject(err) : resolve(data)));
  });
}
// Node has this built in: util.promisify(fs.readFile), or fs.promises
```

**Step 2: flatten `.then` chains**
```js
// before
function loadPortfolio(id) {
  return getUser(id)
    .then(user => getHoldings(user.accountId))
    .then(holdings => enrich(holdings))
    .catch(err => { log(err); return []; });
}

// after
async function loadPortfolio(id) {
  try {
    const user = await getUser(id);
    const holdings = await getHoldings(user.accountId);
    return await enrich(holdings);
  } catch (err) {
    log(err);
    return [];
  }
}
```

**Benefits:** one linear flow, normal `try/catch`, intermediate values stay in scope (no nesting just to keep `user` around), and stack traces are easier to read.

**Pitfalls**
- In a promisified callback, call `resolve` or `reject` **exactly once**. Extra calls are silently ignored.
- Callbacks that fire many times (streams, events) are not a good fit for a single promise. Use async iterators or events.
- Do not add sequential awaits where the old code ran calls in parallel.
- Keep the `return await` inside `try` so the `catch` still covers the last step.

**Takeaway:** promisify the callbacks, then replace each `.then` with an `await` and `.catch` with `try/catch`, keeping independent calls in parallel.

</details>

## A35. Fetch with retry + timeout (mocked `fetch`) · `medium` · 💻 Coding

Write `fetchJson(fetchFn, url, { retries, timeout, backoff })`:

- Each attempt calls `fetchFn(url, { signal })` and **aborts** it with an `AbortController` if it takes longer than `timeout` ms.
- If `!res.ok`, throw an error with `status` and message `'HTTP <status>'`.
- **Retry** only timeouts and 5xx responses, up to `retries` extra times, waiting `backoff * 2 ** attempt` ms between attempts. Do not retry 4xx.
- A final timeout error has the message `'Timeout after <timeout>ms'`.
- Resolve with `await res.json()`.

Use a mocked `fetch` that respects `signal`, so no real network is needed.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
const sleep = ms => new Promise(r => setTimeout(r, ms));

async function fetchOnce(fetchFn, url, timeout) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeout);
  try {
    const res = await fetchFn(url, { signal: controller.signal });
    if (!res.ok) {
      const err = new Error('HTTP ' + res.status);
      err.status = res.status;
      throw err;
    }
    return await res.json();
  } finally {
    clearTimeout(timer);
  }
}

async function fetchJson(fetchFn, url, { retries = 2, timeout = 100, backoff = 20 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fetchOnce(fetchFn, url, timeout);
    } catch (err) {
      const isTimeout = err.name === 'AbortError';
      const retryable = isTimeout || err.status >= 500;
      if (!retryable || attempt >= retries) {
        throw isTimeout ? new Error('Timeout after ' + timeout + 'ms') : err;
      }
      await sleep(backoff * 2 ** attempt);
    }
  }
}
```

**Test**


**Approach:** keep the two concerns separate.
1. `fetchOnce` handles **one attempt with a deadline**. It creates an `AbortController`, sets a timer that calls `abort()`, turns non-OK responses into errors, and always clears the timer in `finally`.
2. `fetchJson` is the **retry loop**. It classifies each error: an `AbortError` (timeout) or `status >= 500` is retryable, and anything else is thrown immediately.

**Why abort instead of `Promise.race`:** aborting actually cancels the in-flight request, and the mock clears its timer, just as a real `fetch` releases the connection.

**Edge cases**
- 4xx fails after 1 call (retrying cannot fix a bad request).
- Exhausted retries rethrow the last error, and a timeout is reported with a clear message.
- `return await` inside the `try` is required, or rejections skip the retry logic.

**Complexity:** at most `retries + 1` requests. Worst-case time is about `(retries + 1) * timeout` plus the backoff delays.

**Common mistakes:** reusing one `AbortController` across attempts (once aborted, it stays aborted); not clearing the timer; retrying non-idempotent POSTs such as order placement without an idempotency key.

**Takeaway:** use a fresh `AbortController` per attempt for the timeout, retry only transient errors, and always clear the timer.

## A36. Async errors in event handlers · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Problem:** DOM and emitter code calls your handler and **ignores what it returns**. If the handler is `async` and throws, the error becomes a **rejected promise that nobody handles**:
- a global `try/catch` or `window.onerror` does not see it (it goes to `unhandledrejection` instead)
- React error boundaries do **not** catch errors from event handlers or async code at all

```js
buyButton.addEventListener('click', async () => {
  const order = await placeOrder(form); // if this rejects: "Uncaught (in promise)"
  showConfirmation(order);
});
```

**Fix: handle errors inside the handler**
```js
buyButton.addEventListener('click', async () => {
  buyButton.disabled = true;               // also prevents double orders
  try {
    const order = await placeOrder(form);
    showConfirmation(order);
  } catch (err) {
    showError('Order failed: ' + err.message);
    reportError(err);
  } finally {
    buyButton.disabled = false;
  }
});

// safety net for anything you missed
window.addEventListener('unhandledrejection', e => reportError(e.reason));
```

**Pitfalls**
- `event.preventDefault()` must be called **before** the first `await`. Afterwards, the browser has already carried out the default action.
- Rapid double clicks start two async runs. Disable the button, or use a lock or an in-flight flag.
- In React, set error state with `setState` so the UI (or a boundary) can show it.

**Takeaway:** nobody awaits an async event handler, so it must catch its own errors. Call `preventDefault` before the first `await`.

</details>

## A38. Performance pitfalls: async waterfalls · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Waterfall:** independent async calls are awaited one after another, so the total time is the **sum** of the calls instead of the **longest** one.

```js
// ~900 ms for three 300 ms calls
async function loadDashboard(userId) {
  const user = await getUser(userId);
  const indices = await getIndices();        // does not need user
  const news = await getMarketNews();        // does not need user
  const holdings = await getHoldings(user.accountId);
  return { user, indices, news, holdings };
}

// ~600 ms: start independent work early and only wait where needed
async function loadDashboard(userId) {
  const indicesP = getIndices();
  const newsP = getMarketNews();
  const user = await getUser(userId);
  const [indices, news, holdings] = await Promise.all([
    indicesP, newsP, getHoldings(user.accountId),
  ]);
  return { user, indices, news, holdings };
}
```
(Be careful: `indicesP` and `newsP` have no handler while `getUser` is pending. If one of them rejects early, you get an unhandled rejection. Attach a handler early, or group the work with `Promise.all` as in the next example.)

A clean way to express the dependency:
```js
const [user, indices, news] = await Promise.all([getUser(id), getIndices(), getMarketNews()]);
```

**Other performance traps**
- `await` inside a loop over many independent items. Use `Promise.all` or a concurrency pool.
- Unbounded parallelism (thousands of requests) causes throttling, 429 responses or memory pressure.
- Repeated identical requests. Deduplicate or cache in-flight promises.
- In React, waterfalls between parent and child components. Fetch in parallel at the route level.

**Interview tip:** name it a "request waterfall", show it in DevTools' Network tab (staircase-shaped bars), and fix it by drawing the dependency graph.

**Takeaway:** await only where there is a real dependency. Start independent work early and join it with `Promise.all`.

</details>

## A39. `allWithProgress`: wait for all with a progress callback · `medium` · 💻 Coding

Implement `allWithProgress(promises, onProgress)`:

- Behaves like `Promise.all`: resolves with the values in input order, and rejects on the first failure.
- Calls `onProgress(done, total)` once with `(0, total)` at the start, then each time **any** input fulfils.
- Accepts plain values as well as promises.

Use case: a "Loading watchlist 3/5" indicator.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function allWithProgress(promises, onProgress) {
  const total = promises.length;
  let done = 0;
  onProgress(0, total);
  return Promise.all(

      const value = await p;
      done++;
      onProgress(done, total);
      return value;
    })
  );
}
```

**Test**

## A40. Async iterators and `for await...of` · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Protocol:** an object is **async iterable** if it has a `[Symbol.asyncIterator]()` method. That method returns an iterator whose `next()` returns a **promise** of `{ value, done }`.

`for await (const x of source)` awaits each `next()` result and runs the loop body **one item at a time**. It works on:
- async iterables (async generators, Node streams, `ReadableStream` in modern runtimes)
- **sync iterables of promises** (arrays): each element is awaited in order

```js
const tickStream = {
  [Symbol.asyncIterator]() {
    let n = 0;
    return {
      async next() {
        if (n === 3) return { value: undefined, done: true };
        await sleep(100);
        return { value: { symbol: 'NIFTY', tick: ++n }, done: false };
      },
      async return() {             // called on break, return or throw
        console.log('unsubscribe');
        return { value: undefined, done: true };
      },
    };
  },
};

for await (const t of tickStream) {
  render(t);
  if (t.tick === 2) break;         // triggers return(), which cleans up
}
```

**Pitfalls**
- Only allowed where `await` is allowed (async functions, module top level).
- `for await` over an **array of promises** awaits them in array order. If a later promise rejects while an earlier one is still pending, that rejection is **unhandled** at first. Prefer `Promise.all` for arrays.
- The items are processed **one at a time**. Use a pool if you need parallelism.

**Takeaway:** `for await` pulls promised values one by one from an async iterator, and `break` calls `return()` so the source can clean up.

</details>

**Takeaway:** `for await` over an array returns results in array order, not in the order they settle. A slow first item holds back all the others.

## A42. Async generators (`async function*`) · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Definition:** an `async function*` can use both `await` and `yield`. Calling it returns an **async generator object**, which is both an async iterator and an async iterable, so `for await` can consume it.

```js
async function* candles(symbol) {
  let cursor = null;
  try {
    do {
      const page = await api.getCandles(symbol, cursor); // await inside
      for (const c of page.data) yield c;                // yield one item at a time
      cursor = page.next;
    } while (cursor);
  } finally {
    console.log('closed');                               // runs on break too
  }
}

for await (const candle of candles('TCS')) {
  if (candle.close > 4000) break;                        // stops fetching more pages
}
```

**Key behaviours**
- **Lazy / pull-based:** no work happens until the consumer calls `next()`. Breaking early means later pages are never fetched.
- **Queued requests:** calling `next()` several times without awaiting queues the calls. The generator still runs them one at a time.
- `yield promise` in an async generator **awaits** the promise first, so consumers never receive a promise as the value.
- `yield*` can delegate to another async **or** sync iterable.
- `break` or `return` calls `gen.return()`, which runs `finally` blocks. That is useful for closing sockets and cursors.

**Use cases:** pagination, reading streams in chunks, WebSocket message streams, and producing items with backpressure.

**Takeaway:** async generators give you lazy async streams that consumers pull from with `for await`, with cleanup in `finally`.

</details>

## A44. `asyncPool`: concurrency limiter · `hard` · 💻 Coding

Implement `asyncPool(limit, items, iteratorFn)`:

- Runs `iteratorFn(item, index)` for every item, with **at most `limit`** calls running at the same time.
- A new call starts **as soon as any slot frees up** (not batch by batch).
- Resolves with the results in **input order**, and rejects if any call rejects.

```js

```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function asyncPool(limit, items, iteratorFn) {
  if (!(limit >= 1)) throw new RangeError('limit must be >= 1');
  const results = new Array(items.length);
  let nextIndex = 0;

  async function worker() {
    while (nextIndex < items.length) {
      const i = nextIndex++;          // claim an index synchronously, so no two workers take the same one
      results[i] = await iteratorFn(items[i], i);
    }
  }

  const workers = [];
  for (let w = 0; w < Math.min(limit, items.length); w++) workers.push(worker());
  await Promise.all(workers);
  return results;
}
```

## A45. Cancellation with `AbortController` · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Why it's needed:** promises have no built-in cancel. A timeout or `Promise.race` only stops *waiting*. `AbortController` is the standard way to tell the running work to **stop**.

```js
const controller = new AbortController();
const { signal } = controller;

async function loadChart(symbol, signal) {
  const res = await fetch('/api/chart/' + symbol, { signal }); // fetch rejects with AbortError
  signal.throwIfAborted();                                    // check between steps
  const data = await res.json();
  return transform(data);
}

loadChart('TCS', signal).catch(err => {
  if (err.name === 'AbortError') return;                      // expected, stay quiet
  showError(err);
});

controller.abort(); // e.g. the user switched symbol or the component unmounted
```

**Supporting cancellation in your own code**
- Check `signal.aborted` or call `signal.throwIfAborted()` between steps.
- Listen with `signal.addEventListener('abort', onAbort, { once: true })` to stop timers and sockets, and **remove the listener** when done.
- Reject with an error whose `name` is `'AbortError'` (or `signal.reason`).

**Helpers:** `AbortSignal.timeout(ms)` and `AbortSignal.any([s1, s2])` (combines signals). `controller.abort(reason)` sets `signal.reason`.

**Pitfalls**
- A controller is **single-use**. Once aborted, it stays aborted, so create a new one per request.
- Aborting does not undo work the server has already done (an order may already be placed).
- Treat `AbortError` as a normal outcome, not as a failure to report.

**Takeaway:** pass an `AbortSignal` through your async functions, check it between steps, and treat `AbortError` as a normal result.

</details>

## A46. Cancellable async task with `AbortSignal` · `hard` · 💻 Coding

Implement:

1. `sleep(ms, signal)`: resolves after `ms`, or rejects **immediately** with an `AbortError` when `signal` aborts. It must clear its timer and remove its listener.
2. `runSteps(steps, signal, onStep)`: runs `steps` (`{ name, ms }`) one after another using `sleep`, calls `onStep(name)` after each step, and resolves with the names of the completed steps. It must throw `AbortError` if the signal is already aborted or becomes aborted.

An `AbortError` is an `Error` with `name = 'AbortError'`.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function abortError() {
  const e = new Error('Operation aborted');
  e.name = 'AbortError';
  return e;
}

function sleep(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal && signal.aborted) return reject(abortError());
    const onAbort = () => {
      clearTimeout(timer);
      reject(abortError());
    };
    const timer = setTimeout(() => {
      if (signal) signal.removeEventListener('abort', onAbort);
      resolve();
    }, ms);
    if (signal) signal.addEventListener('abort', onAbort, { once: true });
  });
}

async function runSteps(steps, signal, onStep = () => {}) {
  const done = [];
  for (const step of steps) {
    if (signal.aborted) throw abortError();
    await sleep(step.ms, signal);
    done.push(step.name);
    onStep(step.name);
  }
  return done;
}
```

**Test**

```js

    console.log('should not finish');
  } catch (e) {

  }

  c3.abort();
  try {

  } catch (e) {
```

**Output**

```text

  step done: reserve-margin
  step done: send-to-exchange
full: validate,reserve-margin,send-to-exchange
  step done: validate
  step done: reserve-margin
cancelled: AbortError (Operation aborted)
pre-aborted: AbortError

```

**Approach**
- `sleep` races its timer against the signal. Whichever happens first cleans up the other: the timer removes the abort listener, and the abort handler clears the timer. That way no timers or listeners leak.
- `runSteps` checks `signal.aborted` before each step (cheap, and it catches an already-aborted signal) and passes the signal into every wait, so an abort **in the middle of a step** rejects immediately instead of waiting for the step to end.

**Trace for the cancelled run:** validate ends at 50 ms and reserve-margin at 100 ms. `send-to-exchange` would end at 200 ms, but the abort at 130 ms rejects its `sleep`, and the error propagates out of the loop.

**Edge cases:** an already-aborted signal rejects straight away. Aborting after the work finished has no effect, because the listener was removed.

**Complexity:** O(steps) time. O(1) listeners at any moment.

**Common mistakes**
- Only checking `aborted` between steps, so a cancel is not seen until the current step ends.
- Never removing the listeners, which leaks memory on long-lived signals.
- Swallowing `AbortError` inside the task, so the caller cannot tell a cancelled run from a completed one.

**Takeaway:** cancellation is cooperative. Pass the signal down, react to `abort` inside every wait, and clean up on both paths.

## A48. Async task queue with concurrency · `hard` · 💻 Coding

Build a `TaskQueue` class:

- `new TaskQueue(concurrency)`: at most `concurrency` tasks run at once. Throw `RangeError` if it is &lt; 1.
- `add(task)`: `task` is a function that returns a promise (or throws). `add` returns a promise that settles with that task's result.
- Tasks start in **FIFO** order as slots free up. A failing task must not stop the queue.
- `size` is the number of **waiting** tasks, and `pending` is the number of **running** tasks.
- `onIdle()` resolves when nothing is running or waiting.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
class TaskQueue {
  constructor(concurrency = 1) {
    if (!(concurrency >= 1)) throw new RangeError('concurrency must be >= 1');
    this.concurrency = concurrency;
    this.running = 0;
    this.waiting = [];
    this.idleWaiters = [];
  }

  get size() { return this.waiting.length; }
  get pending() { return this.running; }

  add(task) {
    return new Promise((resolve, reject) => {
      this.waiting.push({ task, resolve, reject });
      this._pump();
    });
  }

  onIdle() {
    if (this.running === 0 && this.waiting.length === 0) return Promise.resolve();
    return new Promise(resolve => this.idleWaiters.push(resolve));
  }

  _pump() {
    while (this.running < this.concurrency && this.waiting.length > 0) {
      const { task, resolve, reject } = this.waiting.shift();
      this.running++;
      this._run(task).then(resolve, reject).finally(() => {
        this.running--;
        this._pump();
      });
    }
    if (this.running === 0 && this.waiting.length === 0) {
      this.idleWaiters.splice(0).forEach(fn => fn());
    }
  }

  async _run(task) {
    return task(); // an async wrapper turns a sync throw into a rejection
  }
}
```

**Test**

**Approach:** keep a FIFO array of `{ task, resolve, reject }`. `_pump` starts tasks while there are free slots. Each task's result is forwarded to the promise that `add` returned. **Complexity:** `add` is O(1) amortised (`shift` is O(n) in theory; use a linked list or head index for very large queues). O(n) memory for waiting tasks.

**Common mistakes**
- Passing already-started promises instead of task *functions*, so the limit is meaningless.
- Freeing the slot only on success, so one failure stalls the queue.

**Takeaway:** a queue stores task functions and their resolvers, starts tasks while slots are free, and refills a slot in `finally`.

## A49. Async mutex / lock · `hard` · 💻 Coding

Two async withdrawals from the same trading account read the balance, wait (a network call), then write. Without coordination, both can succeed even though the funds only cover one (a lost update).

Implement `Mutex`:
- `lock()`: resolves with a `release` function once the lock is yours. Waiters get the lock in FIFO order.
- `runExclusive(fn)`: acquires the lock, runs `fn`, and **always** releases it (even if `fn` throws), then settles with `fn`'s result.

Show the race without the mutex and the fix with it.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
class Mutex {
  constructor() {
    this._tail = Promise.resolve();
  }

  lock() {
    let release;
    const released = new Promise(resolve => { release = resolve; });
    const acquired = this._tail.then(() => release);
    this._tail = released; // the next caller waits for this holder to release
    return acquired;
  }

  async runExclusive(fn) {
    const release = await this.lock();
    try {
      return await fn();
    } finally {
      release();
    }
  }
}
```

**Test**

```js
      balance = current - amount;        // write
      return label + ': ok';
    },
    get balance() { return balance; },
  };
}

  ]);
  console.log('with lock: ' + r2.map(r => r.value || r.reason.message).join(', ') + ' | balance ' + safe.balance);

  const m = new Mutex();
  await Promise.all([1, 2, 3].map(async n => {
    const release = await m.lock();
    order.push('in' + n);

    order.push('out' + n);
```

**Race without the lock:** A and B both read `100` before either writes. After the delay, both pass the check and both write `20`, so 160 was withdrawn from 100. That is a lost update.

**Approach:** the mutex keeps a promise chain `_tail`. `lock()` creates a new `released` promise, gives the caller its resolver **after the previous holder releases** (`_tail.then(...)`), and makes `released` the new tail. Every caller joins the back of the chain, so waiters run in FIFO order and only one critical section runs at a time. **Edge cases**
- `runExclusive` releases in `finally`, so an error in B's critical section (the rejection above) does not keep the lock held. The final call proves the lock still works.
- Calling `release` twice is harmless (resolving a promise again does nothing).

**Complexity:** O(1) per lock. Memory is one promise per waiter.

**Common mistakes:** using a boolean flag with `while (locked) await ...` (busy waiting and starvation); forgetting to release on error, which causes a deadlock; taking the same lock again inside the critical section (the mutex is not re-entrant, so it deadlocks).

**Takeaway:** JavaScript has one thread, but async code still interleaves at every `await`. Protect read-await-write sequences with a promise-chain mutex.

```js
const bad = placeOrder(0);
const good = placeOrder(5);
console.log('after calls');

good.then(q => console.log('good resolved ' + q));
bad.catch(e => console.log('bad rejected: ' + e.name));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
validating 0
validating 5
after calls
placed 5
bad rejected: RangeError
good resolved 5
```

1. `placeOrder(0)` runs synchronously and prints `validating 0`, then throws. The throw becomes an **already rejected** promise `bad`. No exception reaches the caller.
2. `placeOrder(5)` prints `validating 5`, reaches `await null` and pauses. Its continuation (C5) is queued.
3. `after calls` prints.
4. `good.then(...)` is registered, but `good` is still pending, so nothing is queued yet.
5. `bad.catch(...)` is registered on an already rejected promise, so its reaction (R) is queued **now**, after C5. Queue: [C5, R].
6. C5 runs: `placed 5` prints, and the function returns, which fulfils `good` and queues its callback (G). Queue: [R, G].
7. R prints `bad rejected: RangeError`, then G prints `good resolved 5`.

The rejection is handled within the same run, so nothing is reported as unhandled.

**Takeaway:** an async function runs synchronously up to its first `await`. A reaction is queued only once its promise has settled and a handler is attached.

</details>

## A51. How async/await relates to generators · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Core idea:** async/await is essentially **generators + promises + an automatic runner**, built into the language. A generator can pause at `yield` and be resumed with a value. If you yield promises and a runner resumes the generator with each promise's result, you get async/await.

```js
function run(genFn, ...args) {
  return new Promise((resolve, reject) => {
    const it = genFn(...args);
    function step(method, arg) {
      let result;
      try {
        result = it[method](arg);                // resume: next(value) or throw(err)
      } catch (err) {
        return reject(err);                      // the generator threw
      }
      if (result.done) return resolve(result.value);
      Promise.resolve(result.value).then(
        v => step('next', v),                    // like await: resume with the value
        e => step('throw', e)                    // like await: throw at the yield point
      );
    }
    step('next');
  });
}

// generator version
const getPortfolio = id => run(function* () {
  const user = yield fetchUser(id);
  const holdings = yield fetchHoldings(user.acc);
  return holdings;
});

// equivalent async version
async function getPortfolio2(id) {
  const user = await fetchUser(id);
  return fetchHoldings(user.acc);
}
```

**Mapping:** `await` ≈ `yield`, the async function ≈ runner + generator, and a rejection ≈ `it.throw(err)` (which is why `try/catch` works).

**History:** libraries like `co` (used by Koa v1) did exactly this. Babel and TypeScript still compile async functions for old targets into generator or state-machine code (`__awaiter`, `regenerator-runtime`).

**Differences:** native async functions always return native promises, cannot be resumed manually from outside, and engines optimise them (for example the extra-tick removal for `await` in 2019).

**Takeaway:** async/await is a generator whose `yield`s are awaited promises, resumed automatically by a built-in runner that uses microtasks.

</details>

## A52. Rate limiter: at most N calls per time window · `hard` · 💻 Coding

Market-data APIs often allow only **N requests per window**. Implement `createRateLimiter(limit, windowMs)`, which returns `schedule(fn)`:

- `schedule` returns a promise for `fn()`'s result.
- At most `limit` calls may **start** within any rolling `windowMs` window (a sliding log).
- Extra calls wait in FIFO order and start automatically when allowed.
- Errors from `fn` are passed to the caller and do not break the limiter.

Example: limit 2 per 100 ms, and 5 calls scheduled at once start at roughly 0, 0, 100, 100 and 200 ms.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createRateLimiter(limit, windowMs) {
  const startTimes = [];
  const waiting = [];
  let timer = null;

  function drain() {
    timer = null;
    const now = Date.now();
    while (startTimes.length && now - startTimes[0] >= windowMs) startTimes.shift();

    while (waiting.length && startTimes.length < limit) {
      const { fn, resolve, reject } = waiting.shift();
      startTimes.push(now);
      (async () => fn())().then(resolve, reject);
    }

    if (waiting.length && timer === null) {
      const waitMs = Math.max(0, windowMs - (now - startTimes[0]));
      timer = setTimeout(drain, waitMs);
    }
  }

  return function schedule(fn) {
    return new Promise((resolve, reject) => {
      waiting.push({ fn, resolve, reject });
      if (timer === null) drain();
    });
  };
}
```

**Test**

```js
const schedule = createRateLimiter(2, 100);
let started = 0;
const quote = sym => async () => {
  started++;
  if (sym === 'BAD') throw new Error('symbol BAD not found');
  return sym + ':ok';
};

const calls = ['TCS', 'INFY', 'BAD', 'ITC', 'LT'].map(s =>
  schedule(quote(s)).catch(e => 'error(' + e.message + ')')
);

setTimeout(() => console.log('by 50ms started: ' + started), 50);
setTimeout(() => console.log('by 150ms started: ' + started), 150);
setTimeout(() => console.log('by 250ms started: ' + started), 250);

setTimeout(async () => {
  const results = await Promise.all(calls); // all settled by now
  console.log(results.join(', '));
}, 280);
```

**Output**

```text
by 50ms started: 2
by 150ms started: 4
by 250ms started: 5
TCS:ok, INFY:ok, error(symbol BAD not found), ITC:ok, LT:ok
```

**Approach: sliding log.** Keep the start times of recent calls. On every `drain`:
1. Remove timestamps older than the window.
2. Start waiting calls while fewer than `limit` calls started inside the window, and record each start time.
3. If calls are still waiting, set **one** timer for the moment the oldest timestamp leaves the window.

**Trace (limit 2, 100 ms):** at 0 ms, TCS and INFY start. At about 100 ms, both timestamps expire, so BAD and ITC start. At about 200 ms, LT starts. The checkpoints at 50, 150 and 250 ms therefore see 2, 4 and 5 calls started. At 280 ms the results are printed in call order, and BAD's error went only to its own caller.

**Edge cases**
- A synchronous throw in `fn` is turned into a rejection by the async wrapper.
- If the timer fires slightly early, `drain` finds no free slot and simply sets another short timer.
- Only one timer exists at a time.

**Complexity:** O(1) amortised per call. Memory is O(limit + waiting).

**Common mistakes**
- A fixed window that resets every `windowMs`, which allows up to 2×limit calls around the boundary.
- Limiting completions instead of starts.
- One `setTimeout` per waiting call (a timer storm).
- Letting one failure reject the limiter for everyone.

**Takeaway:** a sliding-log limiter records start times, drops expired ones, and sets a single timer for the next free slot.

</details>

## A53. Debounced async search that ignores stale responses · `hard` · 💻 Coding

Build `createSearch(api, onResults, delay)` for a stock-search box:

- Returns `search(query)`. Calls are **debounced**: `api(query)` runs only after `delay` ms with no new `search` call.
- Responses can arrive out of order. Only the response for the **latest** query may reach `onResults(query, results)`. Older responses must be ignored (log them for the demo).
- Errors from the latest query go to `onResults(query, null, error)`. Errors from stale queries are ignored.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createSearch(api, onResults, delay = 50, onStale = () => {}) {
  let timer = null;
  let latestId = 0;

  return function search(query) {
    const id = ++latestId;
    clearTimeout(timer);
    timer = setTimeout(async () => {
      try {
        const results = await api(query);
        if (id === latestId) onResults(query, results);
        else onStale(query);
      } catch (err) {
        if (id === latestId) onResults(query, null, err);
        else onStale(query);
      }
    }, delay);
  };
}
```

**Test**

```js
const wait = ms => new Promise(r => setTimeout(r, ms));
const universe = ['RELIANCE', 'RELINFRA', 'TCS', 'TATAMOTORS', 'TATASTEEL'];
const latency = { REL: 10, TAT: 120, TATA: 10, X: 10 };

async function api(q) {
  console.log('api called: ' + q);
  await wait(latency[q]);
  if (q === 'X') throw new Error('bad query');
  return universe.filter(s => s.startsWith(q));
}

const search = createSearch(
  api,
  (q, results, err) => console.log(err ? 'error for ' + q + ': ' + err.message : 'show ' + q + ' -> ' + results.join(',')),
  30,
  q => console.log('ignored stale: ' + q)
);

(async () => {
  search('R');
  search('RE');
  search('REL');
  await wait(80);

  search('TAT');
  await wait(40);
  search('TATA');
  await wait(200);

  search('X');
})();
```

**Output**

```text
api called: REL
show REL -> RELIANCE,RELINFRA
api called: TAT
api called: TATA
show TATA -> TATAMOTORS,TATASTEEL
ignored stale: TAT
api called: X
error for X: bad query
```

**Two separate protections**
1. **Debounce:** each call clears the previous timer. Typing `R`, `RE`, `REL` quickly makes a **single** API call, for `REL`.
2. **Stale-response guard:** every call gets an increasing `id`. When a response arrives, it is shown only if its `id` is still the latest.

**Timeline for the race:** `TAT` is sent at about 110 ms and is slow (120 ms). `TATA` is typed 40 ms later, *after* the debounce window, so both requests are in flight. `TATA` answers first and is shown. When `TAT` finally answers, its id is out of date, so it is ignored instead of overwriting the newer list.

**Edge cases:** errors follow the same latest-only rule, and the `X` error is shown because it is the latest query. A new keystroke also makes an in-flight response stale.

**Complexity:** O(1) per keystroke, apart from the API call.

**Common mistakes**
- Debounce alone does not fix out-of-order responses. You still need the id or `AbortController` guard.
- Comparing the query text instead of an id. Typing `TAT`, then `TATA`, then `TAT` again would wrongly accept an old response.
- In production, also **abort** the stale request (`AbortController`) to save bandwidth, and cache results.

**Takeaway:** debounce reduces how many requests you send, and a latest-request id (or abort) makes sure only the newest response is shown.

</details>

## A54. Nested async functions vs a `.then` chain · `hard` · 🖨️ Output

```js
async function inner() {
  console.log('inner start');
  await null;
  console.log('inner end');
}

async function outer() {
  console.log('outer start');
  await inner();
  console.log('outer end');
}

outer();

Promise.resolve()
  .then(() => console.log('p1'))
  .then(() => console.log('p2'));

console.log('sync');
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
outer start
inner start
sync
inner end
p1
outer end
p2
```

1. `outer()` prints `outer start` and calls `inner()`, which prints `inner start` and pauses at `await null`. That queues **I** (inner's continuation). `inner()` returns a *pending* native promise.
2. `outer` awaits that pending promise. Awaiting a native promise costs no extra ticks, so outer's continuation is attached as a reaction and waits for inner to finish.
3. The chain queues **p1**. Queue: [I, p1].
4. `sync` prints.

| Tick | Runs | Output | Queue after |
|---|---|---|---|
| 1 | I: inner resumes and returns, so its promise fulfils and outer's continuation **O** is queued | inner end | [p1, O] |
| 2 | p1, which queues p2 | p1 | [O, p2] |
| 3 | O | outer end | [p2] |
| 4 | p2 | p2 | [] |

**Takeaway:** `await asyncFn()` resumes one tick after that inner function finishes. Walk through the microtask queue as a FIFO and nested ordering becomes predictable.

</details>
