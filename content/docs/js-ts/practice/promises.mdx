## P1. What is a Promise and what are its three states? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A **Promise** is an object that stands in for a value that will be available *later* (or never). It gives async code one standard way to say "here is the result" or "here is why it failed".

**The three states**
| State | Meaning | Can it change? |
|---|---|---|
| `pending` | Work is still in progress | Yes, to one of the two below |
| `fulfilled` | Finished with a **value** | No |
| `rejected` | Failed with a **reason** (usually an `Error`) | No |

"Settled" means fulfilled **or** rejected. Once settled, a promise is **immutable**: its state and value never change again.

```js
const quote = new Promise((resolve, reject) => {
  setTimeout(() => resolve({ symbol: 'INFY', ltp: 1520 }), 100);
});
quote.then(q => console.log(q.ltp)); // 1520 after ~100 ms
```

**Why it matters:** before promises, every library had its own callback style. Promises make results composable (`then` chains, `Promise.all`) and are the foundation of `async/await`.

**Pitfalls**
- You cannot read the state synchronously; there is no `promise.state` property.
- A promise is *not* the work itself; the work already started when the promise was created.

**Interview tip:** say "pending, fulfilled, rejected; settled is final" and mention that handlers always run asynchronously, even for an already-settled promise.

**Takeaway:** a Promise is a one-time, immutable container for a future value or error.

</details>

## P2. Chained `.then` values · `easy` · 🖨️ Output

```js
Promise.resolve(100)
  .then(price => price * 2)
  .then(price => price + 5)
  .then(price => {
    console.log(price);
  });
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
205
```

1. `Promise.resolve(100)` is already fulfilled with `100`.
2. The first `.then` receives `100` and returns `200`. That return value fulfills the **next** promise in the chain.
3. The second `.then` receives `200` and returns `205`.
4. The last `.then` logs `205`.

Every `.then` creates a new promise, and whatever the callback returns becomes that new promise's value.

**Takeaway:** in a chain, each callback's return value is the input of the next `.then`.

</details>

## P3. Does the Promise executor run synchronously? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Yes.** The function you pass to `new Promise(executor)` runs **immediately and synchronously**, inside the constructor call. Only the `.then/.catch/.finally` callbacks are deferred (to the microtask queue).

```js
console.log('A');
new Promise(resolve => {
  console.log('B');   // runs right now
  resolve();
  console.log('C');   // still runs: resolve() does not return or stop the executor
});
console.log('D');
// A B C D
```

**Why it matters**
- Heavy synchronous work inside an executor blocks the main thread. Wrapping CPU work in a promise does **not** make it async.
- If the executor throws synchronously, the promise becomes **rejected** instead of the error escaping.

**Pitfalls**
- Code after `resolve()` still executes. Write `return resolve(x)` if you want to stop.
- An error thrown later inside a `setTimeout` callback in the executor is **not** caught by the promise, because it happens outside the executor call.

**Interview tip:** people often confuse "the promise is async" with "the executor is async". Only the reactions are async.

**Takeaway:** the executor is synchronous; only the handlers run later.

</details>

## P4. Executor logs vs `.then` logs · `easy` · 🖨️ Output

```js
console.log('start');

const order = new Promise(resolve => {
  console.log('executor');
  resolve('filled');
  console.log('after resolve');
});

order.then(status => console.log(status));

console.log('end');
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
start
executor
after resolve
end
filled
```

1. `start` is logged.
2. The constructor calls the executor right away: `executor` is logged.
3. `resolve('filled')` fulfills the promise, but the executor keeps going: `after resolve` is logged.
4. `.then` is registered. The promise is already fulfilled, so a reaction job goes into the **microtask queue**. It does not run yet.
5. `end` is logged, and the synchronous script finishes.
6. The microtask queue runs: `filled` is logged.

**Takeaway:** executors run synchronously and `resolve` does not stop them; `.then` callbacks always wait for the current script to finish.

</details>

## P5. Can a promise be resolved or rejected more than once? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**No.** The first call to `resolve` or `reject` wins. Any later call is **silently ignored**, with no error and no warning.

```js
const p = new Promise((resolve, reject) => {
  resolve('BUY executed');
  reject(new Error('too late'));   // ignored
  resolve('SELL executed');        // ignored
});
p.then(console.log); // "BUY executed"
```

Behind the scenes, `resolve` and `reject` share one "already resolved" flag. Once either is called, both become no-ops.

**Why it matters:** this rule is what makes patterns like **timeouts** (`Promise.race`) and **first response wins** safe. Whichever path settles first decides the outcome.

**Pitfalls**
- Because the extra calls are ignored silently, bugs such as "callback fired twice" can hide. Add a guard or a log if you need to spot them.
- `resolve(otherPromise)` also counts as "resolved" even though the promise stays *pending* until `otherPromise` settles. A later `reject()` is still ignored.

**Interview tip:** point out that `throw` after `resolve()` inside the executor is also swallowed. The constructor catches it and calls `reject`, which does nothing.

**Takeaway:** a promise settles once; every later resolve/reject is a no-op.

</details>

## P6. Resolve once, ignore the rest · `easy` · 🖨️ Output

```js
const p = new Promise((resolve, reject) => {
  resolve('first');
  resolve('second');
  reject(new Error('late failure'));
  throw new Error('thrown after resolve');
});

p.then(v => console.log('value: ' + v))
 .catch(e => console.log('caught: ' + e.message));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
value: first
```

1. `resolve('first')` settles the promise as fulfilled.
2. `resolve('second')` and `reject(...)` are ignored because the promise is already resolved.
3. The `throw` is caught by the Promise constructor, which then calls `reject`. That call is ignored too, so nothing reaches the console.
4. The `.then` logs `value: first`. The `.catch` is skipped because nothing rejected.

**Takeaway:** only the first settle counts; later resolves, rejects, and even throws in the executor are ignored.

</details>

## P7. Why does `.then` return a new promise? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

`p.then(onFulfilled, onRejected)` always returns a **brand-new promise**, `p2`. It never returns `p` itself. `p2` settles based on what the handler does:

| Handler does | `p2` becomes |
|---|---|
| returns a plain value `v` | fulfilled with `v` |
| returns a promise/thenable | follows it (same state and value) |
| throws `e` | rejected with `e` |
| handler missing for this state | copies `p`'s state (pass-through) |

```js
const p = Promise.resolve(10);
const p2 = p.then(x => x * 3);
console.log(p === p2);      // false
p2.then(console.log);       // 30
```

**Why it matters:** this is what makes **chaining** possible. Each step can transform the value, switch to another async operation, or turn into an error.

**Pitfalls**
- Calling `p.then(a); p.then(b);` is **branching**, not chaining. Both get `p`'s value, and `b` never sees what `a` returned.
- An error inside `a` in that branching style rejects a promise nobody listens to, which causes an unhandled rejection.

**Interview tip:** draw the chain as a list of separate promises. It explains error propagation right away.

**Takeaway:** each `.then` makes a new promise whose outcome depends on what its handler returns or throws.

</details>

## P8. `.catch` recovers and the chain continues · `easy` · 🖨️ Output

```js
Promise.reject(new Error('Order rejected by RMS'))
  .then(() => console.log('A: order placed'))
  .catch(err => {
    console.log('caught: ' + err.message);
    return 'fallback-order';
  })
  .then(v => console.log('then: ' + v));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
caught: Order rejected by RMS
then: fallback-order
```

1. The starting promise is rejected.
2. The first `.then` has no rejection handler, so the rejection passes straight through, and `A` is never logged.
3. `.catch` handles the error, logs it, and **returns** `'fallback-order'`. Returning normally from a catch handler **fulfills** the next promise.
4. The final `.then` receives the fallback and logs it.

**Takeaway:** `.catch` is a recovery point: after it runs without throwing, the chain is back on the success path.

</details>

## P9. Implement `sleep(ms)` · `easy` · 💻 Coding

Write `sleep(ms, value)`, which returns a promise that fulfills with `value` (default `undefined`) after `ms` milliseconds.

**Requirements**
- It must never reject.
- It should work with `await` and with `.then`.

**Example**
```js
await sleep(100);                 // pauses ~100 ms
const v = await sleep(50, 'hi');  // 'hi'
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function sleep(ms, value) {
  return new Promise(resolve => setTimeout(resolve, ms, value));
}
```

**Test**

```js
(async () => {
  console.log('before');
  await sleep(30);
  console.log('after 30ms');
  const v = await sleep(10, 'tick');
  console.log('value: ' + v);
  const none = await sleep(5);
  console.log(typeof none);

  // Shorter sleeps finish first, even when started later
  const log = [];
  await Promise.all([
    sleep(60).then(() => log.push('slow')),
    sleep(20).then(() => log.push('fast')),
  ]);
  console.log(log.join(','));
})();
```

**Output**

```text
before
after 30ms
value: tick
undefined
fast,slow
```

**Approach:** wrap `setTimeout` in a promise. The extra arguments to `setTimeout` are passed to the callback, so `setTimeout(resolve, ms, value)` calls `resolve(value)`.

**Edge cases**
- With no `value`, it resolves with `undefined`.
- `ms` of 0 or less still waits for at least one macrotask, so it is never synchronous.
- Timers are a *minimum* delay, not a guarantee. A busy main thread delays them.

**Complexity:** O(1) time and space per call.

**Common mistakes**
- Writing `setTimeout(resolve(value), ms)`, which calls `resolve` immediately.
- Expecting `sleep` to block the thread. It only pauses the current `async` function; other code keeps running.

</details>

## P10. `Promise.resolve()` and `Promise.reject()` · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

These are shortcuts for making already-settled promises.

- **`Promise.resolve(x)`**
  - If `x` is a *native promise* from the same constructor, it returns **`x` itself** (same object).
  - If `x` is a *thenable* (has a `then` method), it returns a new promise that **adopts** it.
  - Otherwise it returns a promise fulfilled with `x`.
- **`Promise.reject(r)`** always returns a **new rejected** promise with reason `r`. It does **not** unwrap `r`, even when `r` is a promise.

```js
const p = Promise.resolve(5);
console.log(Promise.resolve(p) === p); // true

const cached = price => price != null
  ? Promise.resolve(price)                  // same return type in both branches
  : Promise.reject(new Error('no price'));
```

**Why it matters:** these let a function **always return a promise**, even on a synchronous fast path such as a cache hit. Callers do not need to handle two return shapes.

**Pitfalls**
- `Promise.reject(x)` with nobody listening causes an unhandled rejection.
- Always reject with an `Error` object so you get a stack trace. Don't reject with a string.

**Interview tip:** mention that `Promise.resolve(value)` is the safe way to "normalize" a value that may or may not be a promise. Custom `Promise.all` code uses exactly that.

**Takeaway:** `resolve` normalizes and unwraps; `reject` always wraps the reason as-is.

</details>

## P11. `.finally` passes the value through · `easy` · 🖨️ Output

```js
Promise.resolve(101)
  .finally(arg => {
    console.log('finally arg: ' + arg);
    return 999;
  })
  .then(v => console.log('value: ' + v));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
finally arg: undefined
value: 101
```

1. The `.finally` callback is **always called with no arguments**, so `arg` is `undefined`.
2. The callback returns `999`, but **`.finally` ignores normal return values**. The original fulfillment value `101` passes through.
3. The next `.then` receives `101`.

(Only a **throw**, or a returned **rejected** promise, inside `finally` changes the outcome.)

**Takeaway:** `finally` is for cleanup: it does not see the result and cannot replace it by returning.

</details>

## P12. From callback hell to promise chains · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Callback hell** (the "pyramid of doom") happens when each async step needs the previous result, so callbacks nest deeper and deeper. Each level repeats its own error handling.

```js
// Callbacks
login(user, (err, session) => {
  if (err) return showError(err);
  getFunds(session, (err, funds) => {
    if (err) return showError(err);
    placeOrder(session, funds, (err, order) => {
      if (err) return showError(err);
      render(order);
    });
  });
});

// Promises: flat, one error handler
login(user)
  .then(session => getFunds(session).then(funds => placeOrder(session, funds)))
  .then(render)
  .catch(showError);
```

**What promises fix**
- **Flat structure:** returning a promise from `.then` flattens the next step.
- **One error path:** a throw or rejection anywhere jumps to the nearest `.catch`.
- **Trust:** a callback API could call you twice, never, or synchronously. A promise settles once and always calls handlers asynchronously.
- **Composition:** `Promise.all`, `race` and similar helpers work on any promise.

**Pitfall:** nesting `.then` inside `.then` without a reason brings the pyramid back. Nest only when you need a value from an earlier step, as shown above, or use `async/await`.

**Interview tip:** the strongest argument is **inversion of control**. With callbacks you hand your continuation to third-party code; with promises you keep control.

**Takeaway:** promises flatten async flow, centralize error handling, and give you guarantees that callbacks don't.

</details>

## P13. Pitfall: forgetting to `return` inside `.then` · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A `.then` callback with a block body `{ ... }` that does not `return` gives `undefined` to the next step. **Worse**, if it starts async work without returning that promise, the chain **doesn't wait** for it, and any error from that work is **not caught** by the chain's `.catch`.

```js
// Bug
getOrder(id)
  .then(order => {
    fetchLtp(order.symbol);        // not returned: fire-and-forget
  })
  .then(ltp => console.log(ltp))   // undefined, and runs too early
  .catch(handle);                  // fetchLtp's rejection is NOT caught here

// Fix
getOrder(id)
  .then(order => fetchLtp(order.symbol))   // concise arrow returns implicitly
  .then(ltp => console.log(ltp))
  .catch(handle);
```

**How to spot it:** a chain that logs `undefined`, steps that finish out of order, or "Unhandled promise rejection" warnings even though you have a `.catch`.

**Prevention**
- Prefer concise arrows (`x => doThing(x)`).
- Use the ESLint rules `promise/always-return` and `@typescript-eslint/no-floating-promises`.
- Switch to `async/await`, where a missing `await` is easier to see.

**Interview tip:** the "floating promise" is one of the most common production bugs. Say you would lint for it.

**Takeaway:** if a `.then` step starts async work, return its promise, or the chain neither waits for it nor catches its errors.

</details>

## P14. The missing `return` · `easy` · 🖨️ Output

```js
const fetchPrice = symbol => Promise.resolve(2500);

Promise.resolve('RELIANCE')
  .then(symbol => {
    fetchPrice(symbol).then(p => console.log('price ' + p));
  })
  .then(v => console.log('next step got: ' + typeof v));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
price 2500
next step got: undefined
```

1. **Microtask 1:** the first `.then` callback runs. It calls `fetchPrice`, which is already fulfilled, so the inner `.then` job is **queued**. The callback returns nothing, so its promise is fulfilled with `undefined`, and the outer next step is **queued after** the inner job.
2. **Microtask 2:** the inner job logs `price 2500`.
3. **Microtask 3:** the outer step logs `next step got: undefined`.

The price was fetched, but it never reached the chain because it was not returned. Here the inner log happens to come first only because `fetchPrice` resolves immediately. With a real network call, the outer step would run long before the price arrived.

**Takeaway:** without `return`, the next `.then` gets `undefined` and does not wait for the inner work.

</details>

## P15. Two chains interleave tick by tick · `easy` · 🖨️ Output

```js
Promise.resolve()
  .then(() => console.log('a1'))
  .then(() => console.log('a2'))
  .then(() => console.log('a3'));

Promise.resolve()
  .then(() => console.log('b1'))
  .then(() => console.log('b2'))
  .then(() => console.log('b3'));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
a1
b1
a2
b2
a3
b3
```

A later `.then` is queued only when the promise before it settles. So the two chains take turns.

| Microtask queue at start of tick | Runs | Queues |
|---|---|---|
| a1, b1 | a1 | a2 |
| b1, a2 | b1 | b2 |
| a2, b2 | a2 | a3 |
| b2, a3 | b2 | b3 |
| a3, b3 | a3, b3 | - |

Chain A does **not** run to completion first, because each step waits for a fresh microtask.

**Takeaway:** independent promise chains advance one step per microtask, so their logs interleave.

</details>

## P16. Returning a value vs returning a promise inside `.then` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

What you return from a `.then` handler decides **when** and **with what** the next step runs.

- **Return a plain value** (number, object, `undefined`): the next promise fulfills with it on the next microtask.
- **Return a promise or thenable:** the next promise **adopts** it. It stays pending until the returned promise settles and then copies its result. The chain **waits**.
- **Return a rejected promise**: this works like `throw`. The chain jumps to the next rejection handler.

```js
getSymbol()
  .then(sym => sym.toUpperCase())       // value: next step runs right away
  .then(sym => fetchQuote(sym))         // promise: next step waits for the quote
  .then(quote => quote.ltp)
  .then(ltp => ltp > 0 ? ltp : Promise.reject(new Error('bad ltp')));
```

**Pitfalls**
- Returning an **array of promises** does *not* wait for them. An array is a plain value. Use `return Promise.all(arr)`.
- Returning a promise costs **two extra microtask ticks** compared with returning a value. This only matters in ordering puzzles.
- A handler can never produce a promise *of* a promise. Nested promises are always flattened.

**Interview tip:** "promises auto-flatten" is the one-line answer. `.then` behaves like both `map` and `flatMap`.

**Takeaway:** return a value to pass it on; return a promise to wait for it; arrays of promises need `Promise.all`.

</details>

## P17. How errors propagate and where `.catch` recovers · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A rejection (or a `throw` inside any handler) **skips every fulfillment handler** until it reaches the first **rejection handler** (`.catch(fn)` or the second argument of `.then`).

```js
placeOrder()
  .then(validate)        // throws: skip the next two
  .then(send)            // skipped
  .then(confirm)         // skipped
  .catch(err => {        // handles it
    log(err);
    return { status: 'FAILED' };   // recovery: the chain fulfills again
  })
  .then(render);         // runs with { status: 'FAILED' }
```

**Rules**
1. `.catch(fn)` is exactly `.then(undefined, fn)`.
2. If the catch handler **returns** normally, the chain is **fulfilled** again (recovered).
3. If it **rethrows** (or returns a rejected promise), the error keeps propagating.
4. A `.catch` only covers the steps **above** it. Errors in steps below it need another catch.

**Pitfalls**
- A `.catch` in the middle of a chain can hide errors by accident. Later steps run as if all were fine, often with `undefined`.
- Errors thrown **asynchronously** (for example, inside a `setTimeout` callback) are not part of the chain and are not caught.

**Interview tip:** describe it as `try/catch` for async code. Where you place `.catch` decides what is covered, the same way the `try` block does.

**Takeaway:** errors skip ahead to the nearest rejection handler; returning from it recovers, rethrowing continues.

</details>

## P18. A throw skips ahead to `.catch` · `medium` · 🖨️ Output

```js
Promise.resolve(1)
  .then(v => {
    console.log('step 1 got ' + v);
    throw new Error('boom');
  })
  .then(() => console.log('step 2'))
  .then(() => console.log('step 3'))
  .catch(e => console.log('caught ' + e.message))
  .then(() => console.log('done'));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
step 1 got 1
caught boom
done
```

1. Step 1 logs and then throws, so its promise **rejects** with `boom`.
2. Steps 2 and 3 have no rejection handler. The rejection passes through them and neither logs.
3. `.catch` receives the error and logs `caught boom`. It returns `undefined`, so its promise **fulfills**.
4. The final `.then` runs and logs `done`.

**Takeaway:** a thrown error skips fulfillment handlers until a catch handles it; after that, the chain continues normally.

</details>

## P19. `.then(onOk, onErr)` vs `.then(onOk).catch(onErr)` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

They look alike but cover **different errors**.

| | `p.then(ok, err)` | `p.then(ok).catch(err)` |
|---|---|---|
| `p` rejects | `err` runs | `err` runs |
| `ok` throws | **not** caught by `err` (next promise rejects) | caught by `err` |

In `.then(ok, err)`, both handlers are attached to the **same** promise `p`, and only one of them ever runs. `err` cannot see errors from its sibling `ok`.

```js
fetchQuote()
  .then(
    q => { if (!q.ltp) throw new Error('empty quote'); },
    e => console.log('network error', e)   // won't see "empty quote"
  );

fetchQuote()
  .then(q => { if (!q.ltp) throw new Error('empty quote'); })
  .catch(e => console.log('any error', e)); // sees both
```

**When the two-argument form is useful:** when you want to handle **only** the source's failure differently, and you don't want a fallback to also swallow bugs in `ok`. For example, "if the fetch fails, use the cache; if parsing fails, let it crash loudly".

**Interview tip:** the classic trick question asks "what happens if the success handler throws?" Answer: with the two-argument form, it becomes an unhandled rejection unless something further down catches it.

**Takeaway:** `.catch` after `.then` also guards the success handler; the second argument of `.then` guards only the original promise.

</details>

## P20. Success handler throws in `.then(ok, err)` · `medium` · 🖨️ Output

```js
Promise.resolve('ok')
  .then(
    v => { throw new Error('from success handler'); },
    e => console.log('sibling handler: ' + e.message)
  )
  .catch(e => console.log('downstream catch: ' + e.message));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
downstream catch: from success handler
```

1. The source promise is fulfilled, so only the **first** handler runs. The sibling rejection handler is never called for this promise.
2. The success handler throws, so the promise returned by `.then` **rejects**.
3. The downstream `.catch` is attached to that rejected promise and logs the message.

Without the trailing `.catch`, this would be an unhandled rejection even though the `.then` "has an error handler".

**Takeaway:** the second argument of `.then` never catches errors thrown by the first argument.

</details>

## P21. Non-function arguments to `.then` are ignored · `medium` · 🖨️ Output

```js
Promise.resolve(1)
  .then(2)
  .then(Promise.resolve(3))
  .then(v => console.log(v));

Promise.reject(new Error('x'))
  .catch('not a function')
  .then(null, e => console.log('still rejected: ' + e.message));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
still rejected: x
1
```

1. The spec says that if an argument to `.then` is not a **function**, it is replaced by a pass-through (an identity function for fulfillment, a "thrower" for rejection).
2. `.then(2)` and `.then(Promise.resolve(3))` are both non-functions, so the value `1` passes through unchanged. The last `.then` logs `1`.
3. In the second chain, `.catch('not a function')` is also ignored, so the rejection passes through. `.then(null, handler)` catches it.
4. **Order:** a pass-through step still takes one microtask. Chain 1's logging callback is its **3rd** link (tick 3). Chain 2's handler is only its **2nd** link (tick 2). So `still rejected: x` is logged first, even though chain 1 was written first.

**Takeaway:** `.then` and `.catch` silently ignore non-function arguments; always pass a callback, not a value or a promise.

</details>

## P22. What exactly does `.finally` do? · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

`p.finally(fn)` runs `fn` when `p` settles, **whether it fulfilled or rejected**. It is meant for cleanup: hiding a spinner, releasing a lock, closing a socket.

**Semantics (ES2018)**
1. `fn` is called with **no arguments**, so it can't tell success from failure.
2. If `fn` returns normally (any value), the original **value or reason passes through** unchanged.
3. If `fn` returns a promise, the chain **waits** for it. If that promise fulfills, the original result still passes through.
4. If `fn` **throws** or returns a **rejected** promise, that new error **replaces** the original outcome, even a successful one.

```js
setLoading(true);
fetchPortfolio()
  .then(render)
  .catch(showError)
  .finally(() => setLoading(false));   // runs in both cases
```

It works roughly like this:
```js
p.then(
  v => Promise.resolve(fn()).then(() => v),
  r => Promise.resolve(fn()).then(() => { throw r; })
);
```

**Pitfalls**
- You can't use `finally` to change a successful value. Use `.then` for that.
- A bug inside cleanup code (a throw) **hides** the real error. Keep `finally` callbacks simple.
- `finally` does **not** handle a rejection. If there's no `.catch`, the rejection still continues.

**Takeaway:** `finally` runs on both paths, sees no arguments, and passes the result through unless it throws.

</details>

## P23. A throw inside `.finally` overrides success · `medium` · 🖨️ Output

```js

  .finally(() => {

  .catch(e => console.log('catch: ' + e.message));

  .catch(e => console.log('reason kept: ' + e.message));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
cleanup
catch: cleanup failed
reason kept: fetch failed
```

**What happens:** the first chain rejects with `cleanup failed`, even though the source succeeded. The second chain keeps its original reason, because a `finally` that returns normally doesn't change the outcome.

**Why the logs appear in this order:** internally, `finally` wraps your callback. When the callback returns normally, the wrapper returns `Promise.resolve(result).then(() => { throw reason })`, which is a **promise**, and adopting a promise costs extra ticks. When the callback throws, the wrapper throws straight away, so there are no extra ticks.

| Tick | Chain 1 (callback throws) | Chain 2 (callback returns) |
|---|---|---|
| 1 | logs `cleanup`, throws, and the finally promise rejects immediately | callback returns; the wrapper returns an inner promise |
| 2 | `.then` is skipped (a pass-through still costs a tick) | the finally promise starts adopting the inner promise |
| 3 | `.catch` logs `catch: cleanup failed` | adoption finishes, and the promise rejects with the original reason |
| 4 | | `.catch` logs `reason kept: fetch failed` |

Chain 2 looks shorter, but its normal-return `finally` is slower by two microtasks.

**Takeaway:** throwing in `finally` replaces the result; returning a value does not. A skipped `.then` still costs a microtask.

</details>

## P24. `Promise.all` vs `allSettled` vs `race` vs `any` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

All four take an **iterable** and return one promise. They differ in **when** that promise settles and **with what**.

| Combinator | Fulfills when | Rejects when | Result |
|---|---|---|---|
| `Promise.all` | **all** fulfill | **first** rejection (fail-fast) | values in **input order** |
| `Promise.allSettled` (ES2020) | **all** settle | never | `[{status, value \| reason}]` |
| `Promise.race` | first to **settle** is a fulfillment | first to settle is a rejection | that first outcome |
| `Promise.any` (ES2021) | **first** fulfillment | **all** reject | value, or `AggregateError` |

**Empty input:** `all([])` and `allSettled([])` fulfill with `[]`. `any([])` rejects with `AggregateError`. `race([])` stays **pending forever**.

```js
// Trading dashboard
const [holdings, funds] = await Promise.all([getHoldings(), getFunds()]);   // need both
const widgets = await Promise.allSettled([news(), ipo(), mf()]);            // show what loaded
const quote = await Promise.any([nseFeed(), bseFeed()]);                   // first good source
const res = await Promise.race([api(), timeout(3000)]);                    // deadline
```

**Pitfalls**
- None of them **cancel** the losers. The other operations keep running.
- `all` rejects fast, but the other promises still settle, and their later rejections count as handled.
- Non-promise values in the input are wrapped with `Promise.resolve`.

**Interview tip:** explain the pair "`race` = first settled, `any` = first fulfilled". Then give the empty-array behaviour.

**Takeaway:** `all` needs everything, `allSettled` reports everything, `race` takes the first outcome, `any` takes the first success.

</details>

## P26. Implement `promisify(fn)` · `medium` · 💻 Coding

Many older APIs use Node-style **error-first callbacks**: `fn(...args, (err, result) => {})`.

Write `promisify(fn)`, which returns a function that:
- accepts the same arguments (without the callback) and returns a Promise,
- **rejects** if `err` is truthy and otherwise **fulfills** with `result`,
- keeps `this`, so methods still work,
- rejects if `fn` throws synchronously.

**Example**
```js
const getQuoteAsync = promisify(getQuote);
getQuoteAsync('TCS').then(q => console.log(q)); // 3900
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function promisify(fn) {
  return function promisified(...args) {
    return new Promise((resolve, reject) => {
      // The constructor turns a synchronous throw into a rejection
      fn.call(this, ...args, (err, result) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
  };
}
```

**Test**

**Details**
- A regular `function` wrapper (not an arrow) and `fn.call(this, ...)` keep method calls working.
- Calling `fn` **inside** the executor means a synchronous throw becomes a rejection automatically.

**Edge cases:** callbacks with several result values (Node's `util.promisify` keeps only the first unless the function defines `util.promisify.custom`). APIs whose callback is not the last argument need a custom wrapper.

## P27. Microtasks, macrotasks, and when promise callbacks run · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

The event loop has two main kinds of queues:

- **Macrotask (task) queue:** `setTimeout`, `setInterval`, I/O, UI events, `MessageChannel`.
- **Microtask queue:** promise reactions (`then/catch/finally`), `queueMicrotask`, `MutationObserver`, and the continuation after `await`.

**The loop, simplified**
1. Run one macrotask (the initial script counts as one).
2. **Drain the whole microtask queue**, including microtasks that other microtasks add.
3. Render if needed, then pick the next macrotask.

```js
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('micro'));
console.log('sync');
// sync, micro, timeout
```

**Why it matters**
- Promise callbacks run **before** any timer, even a 0 ms timer.
- An endless chain of microtasks **starves** rendering and timers, and the page freezes.
- Code after `await` runs as a microtask, so it always runs after the current synchronous code.

**Pitfalls:** `setTimeout(fn, 0)` is not "run next". Browsers also clamp nested timers to at least 4 ms.

**Interview tip:** a good order to state is "sync → all microtasks → one macrotask → all microtasks → ...". Then trace the snippet.

**Takeaway:** promise handlers are microtasks, and all microtasks run before the next timer or render.

</details>

## P29. Implement `Promise.all` · `medium` · 💻 Coding

Write `promiseAll(iterable)` with the same behaviour as `Promise.all`:
- It fulfills with an array of values in **input order** once every item fulfills.
- It **rejects immediately** with the first rejection reason.
- Non-promise values are treated as already fulfilled.
- An empty iterable fulfills with `[]`.
- It accepts any iterable (arrays, Sets, generators).

**Example**
```js
promiseAll([1, Promise.resolve(2), sleep(10).then(() => 3)]) // -> [1, 2, 3]
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function promiseAll(iterable) {
  return new Promise((resolve, reject) => {
    const results = [];
    let count = 0;
    let remaining = 0;

    for (const item of iterable) {
      const index = count++;
      remaining++;
      Promise.resolve(item).then(value => {
        results[index] = value;
        remaining--;
        if (remaining === 0) resolve(results);
      }, reject);
    }

    if (count === 0) resolve(results);
  });
}
```

**Test**

```js
const delay = (ms, v, fail) =>
  new Promise((res, rej) => setTimeout(() => (fail ? rej(new Error(v)) : res(v)), ms));

(async () => {
  const r1 = await promiseAll([delay(30, 'A'), 'B', Promise.resolve('C'), delay(10, 'D')]);
  console.log(r1.join(','));

  const r2 = await promiseAll([]);
  console.log('empty: ' + JSON.stringify(r2));

  try {
    await promiseAll([delay(50, 'slow'), delay(10, 'orders failed', true), delay(20, 'x', true)]);
  } catch (e) {
    console.log('rejected: ' + e.message);
  }

  const r3 = await promiseAll(new Set([1, 2, 3]));
  console.log('set: ' + r3.join(','));

  function* gen() { yield delay(5, 'g1'); yield 'g2'; }
  console.log('generator: ' + (await promiseAll(gen())).join(','));

  const r4 = await promiseAll([undefined, null]);
  console.log('length ' + r4.length + ': ' + JSON.stringify(r4));
})();
```

**Output**

```text
A,B,C,D
empty: []
rejected: orders failed
set: 1,2,3
generator: g1,g2
length 2: [null,null]
```

**Approach:** wrap every item with `Promise.resolve`. Store each value at its **captured index** and count how many are still pending. Resolve when that count reaches 0. Pass `reject` directly as the rejection handler, so the first rejection wins and later ones are ignored.

**Edge cases**
- **Empty input:** the loop never runs, so resolve `[]` right away. Without that check the promise would hang.
- **Iterables:** `for...of` works for arrays, Sets and generators, and `Promise.resolve` handles plain values.
- **Holes:** `undefined` values are real results, so count them instead of checking `results.length`.

**Complexity:** O(n) time and O(n) space.

**Common mistakes**
- Using `results.push`, which records completion order instead of input order.
- Checking `results.length === n`. Assigning `results[5]` first makes the length 6 already.
- Using `index` from a `var` loop, where all callbacks share one variable.
- Forgetting the empty case.

</details>

Write `promiseAllSettled(iterable)`:

## P32. Implement `Promise.race` · `medium` · 💻 Coding

Write `promiseRace(iterable)`, which settles the same way as the **first** input to settle.
- Non-promise values count as already fulfilled. In a race they win against pending promises, and against each other the earliest in the input wins.
- An empty iterable returns a promise that stays **pending forever** (same as the native one).

**Example**
```js
promiseRace([sleep(50, 'slow'), sleep(10, 'fast')]) // -> 'fast'
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function promiseRace(iterable) {
  return new Promise((resolve, reject) => {
    for (const item of iterable) {
      // The first call to resolve/reject wins; later calls are ignored
      Promise.resolve(item).then(resolve, reject);
    }
  });
}
```

**Test**

```js

  new Promise((res, rej) => setTimeout(() => (fail ? rej(new Error(v)) : res(v)), ms));

(async () => {
  console.log(await promiseRace([delay(50, 'slow'), delay(10, 'fast')]));

  try {
    await promiseRace([delay(50, 'ok'), delay(10, 'error first', true)]);
  } catch (e) {
    console.log('rejected: ' + e.message);
  }

  console.log(await promiseRace([delay(10, 'pending one'), 'plain value', 'second plain']));

  let settled = false;
  promiseRace([]).then(() => { settled = true; }, () => { settled = true; });
  await delay(30);
  console.log('empty settled? ' + settled);

  // Matches native behaviour
  const native = await Promise.race([delay(20, 'n1'), delay(5, 'n2')]);

```

```text

plain value

```

**Approach:** attach `resolve` and `reject` of one outer promise to every input. A promise can only settle once, so whichever input settles first decides the result, and all later calls do nothing.

**Edge cases**
- **Plain values:** `Promise.resolve('x')` is already fulfilled, so its reaction is queued in input order and wins against any pending promise.
- **Empty input:** no handlers are attached, so the promise stays pending forever. This matches the spec.
- **Losers are not cancelled:** timers and network calls keep running.

**Complexity:** O(n) time to attach handlers, O(1) extra space.

**Common mistakes**
- Adding an explicit "done" flag. It isn't needed, because resolve-once already handles this.
- Calling `item.then` directly, which breaks for plain values.
- Rejecting on empty input. Native `race` does not do that.

</details>

## P33. `Promise.any` and `AggregateError` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

`Promise.any(iterable)` (ES2021) fulfills with the **first fulfilled** value and **ignores rejections**, unless *every* input rejects. In that case it rejects with an **`AggregateError`**.

`AggregateError` is a subclass of `Error` with an **`errors`** array that holds all the rejection reasons **in input order** (not in the order they failed).

```js
Promise.any([primaryFeed(), backupFeed(), cachedQuote()])
  .then(quote => render(quote))
  .catch(err => {
    if (err instanceof AggregateError) {
      err.errors.forEach(e => console.warn(e.message));   // every source failed
    }
  });
```

**any vs race**
- `race`: the first **settled** input wins, even a failure.
- `any`: the first **successful** input wins. Failures only matter if all of them fail.

**Edge cases**
- `Promise.any([])` rejects immediately (asynchronously) with an `AggregateError` whose `errors` is `[]`.
- You can create one yourself: `new AggregateError([e1, e2], 'msg')`.

**Pitfalls**
- The exact `message` text differs between engines, so check `instanceof AggregateError` or `err.name` instead.
- The remaining inputs are not cancelled after one succeeds.

**Interview tip:** a good use case is **redundant data sources** (several CDNs or quote feeds) where you only need one to work.

**Takeaway:** `any` = first success; if everything fails, you get an `AggregateError` with all the reasons.

</details>

## P35. Implement `Promise.any` · `medium` · 💻 Coding

Write `promiseAny(iterable)`:

- If **all** inputs reject, it rejects with `new AggregateError(errors, 'All promises were rejected')`, where `errors` is in **input order**.
- Empty input rejects with an `AggregateError` whose `errors` is empty.

**Example**
```js
promiseAny([Promise.reject(1), sleep(20, 'ok')]) // -> 'ok'
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function promiseAny(iterable) {

    for (const item of iterable) {

      pending++;

        errors[index] = reason;
        pending--;
        if (pending === 0) {
          reject(new AggregateError(errors, 'All promises were rejected'));
        }

    }
  });

```

```js
  new Promise((res, rej) => setTimeout(() => (fail ? rej(new Error(v)) : res(v)), ms));

(async () => {
  console.log(await promiseAny([delay(10, 'e1', true), delay(30, 'second source'), delay(50, 'third')]));

  try {
    await promiseAny([delay(30, 'A failed', true), delay(10, 'B failed', true)]);
  } catch (e) {
    console.log(e.constructor.name + ': ' + e.message);
    console.log(e.errors.map(x => x.message).join(','));
  }

  try {
    await promiseAny([]);
  } catch (e) {
    console.log('empty -> ' + (e instanceof AggregateError) + ', errors=' + e.errors.length);
  }

  console.log(await promiseAny([Promise.reject(new Error('no')), 7]));
})();
```

**Output**

```text
second source
AggregateError: All promises were rejected
A failed,B failed
empty -> true, errors=0
7
```

**Approach:** this is the mirror image of `Promise.all`. Pass `resolve` directly, so the first fulfillment wins. Collect rejection reasons **by index** and count the ones still pending. When that count reaches zero, every input has rejected, so reject with an `AggregateError`.

**Edge cases**
- **Empty input:** reject straight away. Without this check the promise would hang forever.
- **Error order:** assign by index, so `errors` follows input order even when failures arrive out of order.
- **Plain values:** they are wrapped with `Promise.resolve`, so they fulfill immediately and win.

**Complexity:** O(n) time and space.

**Common mistakes**
- Using `errors.push`, which gives failure order instead of input order.
- Rejecting on the first failure, which is `race` behaviour.
- Checking `errors.length === n`, which breaks with sparse assignment.

</details>

## P36. Unhandled promise rejections · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A rejection is **unhandled** when a promise rejects and no rejection handler is attached by the time the host checks, which is roughly after the current microtask checkpoint.

**What hosts do**
- **Browsers** fire the `unhandledrejection` event on `window` and log "Uncaught (in promise)". If a handler is attached later, they fire `rejectionhandled`.
- **Node.js (v15+)** by default treats an unhandled rejection like an uncaught exception: it prints the error and **exits the process** with code 1. `process.on('unhandledRejection', ...)` lets you override that.

```js
window.addEventListener('unhandledrejection', event => {
  reportToSentry(event.reason);   // central logging
  event.preventDefault();         // hide the default console error
});
```

**Common causes**
- A floating promise, such as `saveOrder();` with no `await` or `.catch`.
- `p.then(a); p.catch(b);` is fine for `p`, but the promise returned by `p.then(a)` also rejects, and nobody handles it.
- Throwing inside `.then` at the end of a chain with no `.catch`.
- Attaching `.catch` later inside a `setTimeout`.

**Pitfall:** a global handler is a safety net for logging, not your error handling strategy.

**Interview tip:** mention that React Query, Axios interceptors and similar libraries still need a final handler at the call site, or a global reporter.

**Takeaway:** every promise chain needs a final handler; hosts report (and Node may crash on) rejections nobody handles.

</details>

## P38. The explicit-construction (deferred) anti-pattern · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

The **explicit-construction anti-pattern** means wrapping something that is **already a promise** in `new Promise(...)`.

```js
// Anti-pattern
function getLtp(symbol) {
  return new Promise((resolve, reject) => {
    fetch('/api/ltp/' + symbol)
      .then(res => res.json())
      .then(data => resolve(data.ltp));
    // missing .catch(reject): a network error leaves the promise pending forever
  });
}

// Better: return the existing chain
function getLtp(symbol) {
  return fetch('/api/ltp/' + symbol)
    .then(res => res.json())
    .then(data => data.ltp);
}
```

**Why it's bad**
- **Lost errors:** it's easy to forget `.catch(reject)`, which leaves the promise pending forever while the inner rejection goes unhandled.
- **Extra code** and extra allocations, with nothing gained.
- A throw inside the inner `.then` is not turned into a rejection of the outer promise.

**When `new Promise` is right:** only when you wrap a **non-promise** API, such as callbacks, events, `setTimeout` or `XMLHttpRequest`. Then do it at the lowest level, and keep the executor small.

**Interview tip:** if you see `resolve(` inside a `.then`, that's the smell. With async code, `async function` plus `return` removes the need completely.

**Takeaway:** don't wrap promises in `new Promise`; return the chain. Use the constructor only to adapt callback or event APIs.

</details>

## P39. Promisifying callback and event APIs · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Promisifying** means wrapping an API that reports results with callbacks or events so that it returns a Promise instead.

**1. Error-first callbacks (Node style)**
```js
const readFileAsync = (path) =>
  new Promise((resolve, reject) =>
    fs.readFile(path, 'utf8', (err, data) => (err ? reject(err) : resolve(data))));
// or: const { promisify } = require('node:util');  or: fs.promises.readFile
```

**2. Separate success and error callbacks (browser style)**
```js
const getPosition = () =>
  new Promise((resolve, reject) =>
    navigator.geolocation.getCurrentPosition(resolve, reject));
```

**3. One-off events**
```js
const loadImage = src =>
  new Promise((resolve, reject) => {
    const img = new Image();
    img.onload = () => resolve(img);
    img.onerror = () => reject(new Error('failed to load ' + src));
    img.src = src;   // attach the handlers BEFORE starting the work
  });

const firstTick = ws => new Promise(resolve =>
  ws.addEventListener('message', resolve, { once: true }));
```

**What to keep in mind**
- **One-shot only:** a promise settles once, so streams (like live WebSocket prices) fit better with callbacks, observables or async iterators.
- **Clean up** listeners and timers on both paths.
- **Keep `this`** when you wrap methods (`fn.call(this, ...)`).
- Attach listeners **before** you start the work, or you may miss a synchronous event.

**Interview tip:** mention `util.promisify` and the built-in promise APIs (`fs/promises`, `timers/promises`) in Node.

**Takeaway:** wrap each one-shot callback or event at the lowest level, map success to `resolve` and failure to `reject`, and clean up.

</details>

## P40. Implement `withTimeout(promise, ms)` · `medium` · 💻 Coding

Write `withTimeout(promise, ms)`:
- If `promise` settles within `ms`, pass its result or error through unchanged.
- Otherwise reject with an error whose `name` is `'TimeoutError'` and whose message is `'Timed out after <ms>ms'`.
- **Clear the timer** once the promise settles, so no stray timers are left.

**Example**
```js
withTimeout(fetchQuote('TCS'), 2000).catch(e => e.name); // 'TimeoutError' if slow
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function withTimeout(promise, ms) {
  let timerId;
  const timeout = new Promise((_, reject) => {
    timerId = setTimeout(() => {
      const err = new Error('Timed out after ' + ms + 'ms');
      err.name = 'TimeoutError';
      reject(err);
    }, ms);
  });

  return Promise.race([promise, timeout]).finally(() => clearTimeout(timerId));
}
```

**Test**

```js
const delay = (ms, v, fail) =>
  new Promise((res, rej) => setTimeout(() => (fail ? rej(new Error(v)) : res(v)), ms));

(async () => {
  console.log(await withTimeout(delay(20, 'quote in time'), 100));

  try {
    await withTimeout(delay(200, 'too slow'), 50);
  } catch (e) {
    console.log(e.name + ': ' + e.message);
  }

  try {
    await withTimeout(delay(10, 'server error', true), 100);
  } catch (e) {
    console.log('passed through: ' + e.name + ' ' + e.message);
  }

  console.log(await withTimeout(Promise.resolve('instant'), 0));
  console.log(await withTimeout('plain value', 50));

  // The timer is cleared: this line should run right after the result, with no hanging 300ms timer
  const start = Date.now();
  await withTimeout(delay(10, 'fast'), 300);
  console.log('cleared quickly: ' + (Date.now() - start < 200));
})();
```

**Output**

```text
quote in time
TimeoutError: Timed out after 50ms
passed through: Error server error
instant
plain value
cleared quickly: true
```

**Approach:** race the real promise against a timer promise that only rejects. Then use `.finally` to `clearTimeout`, so a fast result doesn't leave a pending timer that keeps a Node process alive or wastes resources.

**Edge cases**
- **Already settled input:** its reaction is queued before the timer can fire, so it wins even with `ms = 0`.
- **Plain values** work because `Promise.race` wraps them.
- **The original error passes through** unchanged. `finally` doesn't change the outcome.
- **No cancellation:** the slow operation still runs after the timeout. Combine this with `AbortController` to stop it for real.

**Complexity:** O(1).

**Common mistakes**
- Not clearing the timer, which leaves timers piling up in long-running apps.
- Resolving (instead of rejecting) on timeout, so callers can't tell it apart from success.
- Using a plain string as the error, which gives no `name` or stack.

</details>

## P41. Why promises are eager, not lazy · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A promise **does not represent a task you can start later**. By the time you have a promise object, the work is **already running**, because the executor runs inside the constructor. Promises are **eager**, and they also **cache** their result: calling `.then` many times doesn't redo the work.

```js
const order = placeOrder('BUY', 'TCS');   // the request is sent NOW
// ... even if no one ever calls order.then(...)

// Lazy version: a function that returns a promise (a "task" or "thunk")
const orderTask = () => placeOrder('BUY', 'TCS');
// nothing is sent until orderTask() is called
```

**Why it matters**
- **Concurrency control / retries / sequencing** need the lazy version. You can't retry or limit a promise that has already started. That's why pools and `retry` take **functions** that return promises.
- `Promise.all([a(), b()])` starts both **at once**. If you want them one after another, start each only after the previous one finishes.
- Because results are cached, the same promise is a handy **memoized** value: store the promise in a cache so parallel callers share one request.

**Comparison:** RxJS Observables and many "Task" types are lazy and can be restarted. Promises are neither.

**Interview tip:** when asked to "retry a promise", point out that you have to retry the **function that creates it**.

**Takeaway:** creating a promise starts the work; wrap it in a function when you need to control when (or how often) it runs.

</details>

## P43. Run async tasks in sequence (loop and `reduce`) · `medium` · 💻 Coding

You get an array of **task functions**. Each one returns a promise. Run them **one after another**: the next starts only after the previous one fulfills. Return a promise of all results in order.

Write two versions:
1. `runSequential(tasks)` using `async/await` and a loop.
2. `runSequentialReduce(tasks)` using only `.then` and `Array.prototype.reduce`.

If a task rejects, stop and reject with that error. Remaining tasks must **not** start.

**Example:** placing three basket orders one by one.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
async function runSequential(tasks) {
  const results = [];
  for (const task of tasks) {
    results.push(await task());
  }
  return results;
}

function runSequentialReduce(tasks) {
  return tasks.reduce(
    (chain, task) => chain.then(results =>
      task().then(value => {
        results.push(value);
        return results;
      })
    ),
    Promise.resolve([])
  );
}
```

**Test**

```js
const log = [];
const makeTask = (name, ms, fail) => () => {
  log.push('start ' + name);
  return new Promise((res, rej) => setTimeout(() => {
    log.push('end ' + name);
    fail ? rej(new Error(name + ' failed')) : res(name);
  }, ms));
};

(async () => {
  const r1 = await runSequential([makeTask('A', 30), makeTask('B', 10), makeTask('C', 20)]);
  console.log('loop: ' + r1.join(','));
  console.log(log.join(' > '));

  log.length = 0;
  const r2 = await runSequentialReduce([makeTask('X', 20), makeTask('Y', 5)]);
  console.log('reduce: ' + r2.join(','));
  console.log(log.join(' > '));

  log.length = 0;
  try {
    await runSequentialReduce([makeTask('P', 5), makeTask('Q', 5, true), makeTask('R', 5)]);
  } catch (e) {
    console.log('stopped: ' + e.message + ' | ' + log.join(' > '));
  }

  log.length = 0;
  await runSequential([makeTask('S', 5, true), makeTask('T', 5)]).catch(e => console.log('stopped: ' + e.message + ' | ' + log.join(' > ')));

  console.log('empty: ' + JSON.stringify(await runSequential([])) + ' ' + JSON.stringify(await runSequentialReduce([])));
})();
```

**Output**

```text
loop: A,B,C
start A > end A > start B > end B > start C > end C
reduce: X,Y
start X > end X > start Y > end Y
stopped: Q failed | start P > end P > start Q > end Q
stopped: S failed | start S > end S
empty: [] []
```

**Loop version:** `await` inside `for...of` pauses each iteration until the task finishes. A rejection throws out of the loop, so later tasks never start.

**Reduce version:** start from `Promise.resolve([])` and add one `.then` link per task. Each link calls `task()` **inside** the callback, so the task starts only after the previous link fulfills. A rejection skips every later link, because they have no rejection handlers.

**Edge cases:** empty input gives `[]`. It is important that the input is **functions**, not promises, since promises would already be running at the same time.

**Complexity:** O(n) time (the total duration is the sum of the task times), O(n) space.

**Common mistakes**
- `tasks.forEach(async t => await t())`. `forEach` ignores the returned promises, so everything runs in parallel.
- Passing `tasks.map(t => t())` (already started promises) into the reducer.
- Writing `chain.then(task)` when `task` expects no arguments or you need to collect results. That runs in order but loses the values.

</details>

## P44. Nested `.then` vs flat chains (and sharing values) · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A common beginner pattern is to nest `.then` calls when they could simply be chained:

```js
// Nested ("promise hell")
login().then(session => {
  getFunds(session).then(funds => {
    placeOrder(funds).then(order => render(order));   // errors here are not caught
  });
}).catch(handle);

// Flat
login()
  .then(session => getFunds(session))
  .then(funds => placeOrder(funds))
  .then(render)
  .catch(handle);
```

**Problems with nesting**
- Inner promises are not **returned**, so the outer `.catch` never sees their errors, and the outer chain doesn't wait.
- The pyramid comes back, and it gets harder to read.

**When nesting is fine:** when a later step needs a value from an **earlier** step. Keep the nested chain small and **return** it:
```js
login().then(session =>
  getFunds(session).then(funds => placeOrder(session, funds))   // returned
);
```
Other options: pass an object along (`.then(funds => ({ session, funds }))`), use `Promise.all([session, getFunds(session)])`, or use `async/await` so all values stay in scope.

**Interview tip:** the rule is "**always return, flatten when you can, nest only for closure access**".

**Takeaway:** flatten chains by returning promises; if you must nest for scope, return the inner chain so errors and timing still flow outward.

</details>

## P45. Returning a promise from `.then` costs extra ticks · `hard` · 🖨️ Output

```js
Promise.resolve()
  .then(() => {
    console.log('A1');
    return Promise.resolve('x');
  })
  .then(v => console.log('A2 ' + v));

  .then(() => console.log('B1'))
  .then(() => console.log('B2'))
```

**Output**

```text

B1
B2
B3
A2 x
B4
```

When a handler returns a **native promise**, the spec doesn't adopt it right away. It queues a **NewPromiseResolveThenableJob**, which calls `.then` on the returned promise, and that `.then` queues **another** job. That's two extra microtasks.

| Tick | Runs | Queues |
|---|---|---|
| 1 | A1 (returns a promise), B1 | ResolveThenableJob, B2 |
| 2 | ResolveThenableJob: calls `x.then(...)`, B2 | inner reaction, B3 |

| 4 | A2 x, B4 | - |

## P46. Resolving with another promise or thenable (adoption) · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

When you call `resolve(x)` (or return `x` from a handler), the promise does **not** always fulfill with `x`. The **Promise Resolution Procedure** says:

1. If `x` is the promise itself, **reject** with `TypeError` (a chaining cycle).
2. If `x` is an object or function, read `x.then` once. If reading it throws, reject.
3. If `then` is a function, `x` is a **thenable**. The promise **adopts** it: a job calls `then.call(x, resolveFn, rejectFn)` on a later microtask. Only the first of those callbacks counts, and a throw after one was called is ignored.
4. Otherwise, fulfill with `x`.

```js
const legacyDeferred = {
  then(onOk, onErr) { setTimeout(() => onOk('filled'), 10); }
};
new Promise(r => r(legacyDeferred)).then(console.log);   // 'filled'

const p = new Promise(r => r(Promise.reject(new Error('no'))));
p.catch(e => console.log(e.message));   // resolved, but rejected: 'no'
```

**Consequences**
- "Resolved" ≠ "fulfilled". A promise resolved with a pending promise is still **pending**, and it can still end up **rejected**.
- Any object with a `then` method gets treated as a thenable. That's a pitfall if your data objects happen to have a `then` property.
- This is how jQuery Deferreds, Bluebird and other promise libraries **interoperate** with native promises.

**Interview tip:** "Promises/A+ duck-types on `then`" is the key phrase. Mention the cycle `TypeError` for bonus points.

**Takeaway:** resolving with a thenable makes the promise follow it; resolved does not mean fulfilled.

</details>

## P50. Retry with exponential backoff · `hard` · 💻 Coding

Write `retry(fn, { retries = 3, baseDelay = 100, factor = 2, onRetry } = {})`:
- Call `fn(attempt)` (attempt starts at 0). If its promise fulfills, resolve with the value.
- If it rejects and retries are left, wait `baseDelay * factor ** attempt` ms, call `onRetry?.(err, attempt + 1, delay)`, and try again.
- After `retries` extra attempts (`retries + 1` calls in total), reject with the **last** error.
- `fn` may also throw synchronously. Treat that as a failure too.

**Example:** retrying an order-status API that has short outages. The delays are 100, 200, 400 ms.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
const wait = ms => new Promise(resolve => setTimeout(resolve, ms));

async function retry(fn, { retries = 3, baseDelay = 100, factor = 2, onRetry } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(attempt);          // await is needed so rejections land in catch
    } catch (err) {
      if (attempt >= retries) throw err;
      const delay = baseDelay * factor ** attempt;
      await wait(delay);
      if (onRetry) onRetry(err, attempt + 1, delay);
    }
  }
}
```

**Test**

**Approach:** a loop with `try/catch` around `await fn(attempt)`. On failure, rethrow if the attempts are used up. Otherwise wait `baseDelay * factor^attempt` and loop again. Because `fn` is a **function**, each attempt starts fresh work (promises can't be restarted).

**Key detail:** it must be `return await fn()`, not `return fn()`. Without `await`, the rejected promise is returned **past** the `catch` block and never retried.

**Edge cases**
- A synchronous throw inside `fn` is caught by the same `try`.
- `retries: 0` means exactly one call.
- The error is the **last** one, which is usually the most relevant.

**Production additions:** add **jitter** (a random part of the delay) so many clients don't retry in sync, set a max delay cap, retry only transient errors (5xx and network errors, not 4xx), and support an `AbortSignal`.

**Complexity:** at most `retries + 1` calls. The total wait is a geometric series, `base * (factor^retries - 1) / (factor - 1)`.

**Common mistakes:** retrying a promise instead of a function, the missing `await`, and off-by-one errors in the attempt count.

## P51. Cancelling async work with `AbortController` · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

Promises have **no built-in cancellation**. The standard way to cancel is **`AbortController`**: the caller holds the controller, and the async function receives its **`signal`**.

```js
const controller = new AbortController();

fetch('/api/option-chain?symbol=NIFTY', { signal: controller.signal })
  .then(r => r.json())
  .then(render)
  .catch(err => {
    if (err.name === 'AbortError') return;   // expected, so ignore it
    showError(err);
  });

controller.abort();   // e.g. the user switched to another symbol
```

**Making your own functions abortable**
```js
function sleep(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);
    const id = setTimeout(resolve, ms);
    signal?.addEventListener('abort', () => {
      clearTimeout(id);          // actually stop the work
      reject(signal.reason);     // a DOMException named "AbortError" by default
    }, { once: true });
  });
}
```

**Useful helpers:** `AbortSignal.timeout(ms)` for deadlines, `AbortSignal.any([s1, s2])` to combine signals, `signal.throwIfAborted()`, and `controller.abort(reason)` for a custom reason.

**Pitfalls**
- Aborting only rejects the promise. The underlying work stops **only if** the API supports the signal.
- Check `signal.aborted` before starting, and remove listeners when you're done.
- In React, abort inside the effect cleanup to avoid race conditions and state updates on unmounted components.

**Interview tip:** the search-as-you-type example (cancel the previous request whenever the query changes) shows you understand the problem.

**Takeaway:** promises can't cancel themselves; pass an `AbortSignal` so the caller can stop the work and the promise rejects with `AbortError`.

</details>

## P52. Cancellable promise wrapper · `hard` · 💻 Coding

Write `makeCancellable(promise)`, which returns `{ promise, cancel, isCancelled }`:
- `promise` settles like the original, **unless** `cancel(reason?)` was called first. In that case it rejects with an error named `'CancelError'` (message: the reason, or `'Cancelled'`).
- After cancel, the original result is ignored, even if it arrives later.
- Calling `cancel` after the promise has settled does nothing.
- `isCancelled()` returns whether cancel took effect.

Also write `cancellableDelay(ms, signal)`, which resolves after `ms` but rejects with `signal.reason` (and clears its timer) when the `AbortSignal` fires, including when it was already aborted.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function makeCancellable(source) {
  let cancelled = false;
  let settled = false;
  let rejectOuter;

  const promise = new Promise((resolve, reject) => {
    rejectOuter = reject;
    Promise.resolve(source).then(
      value => { settled = true; resolve(value); },
      error => { settled = true; reject(error); }
    );
  });

  return {
    promise,
    cancel(reason = 'Cancelled') {
      if (settled || cancelled) return;
      cancelled = true;
      const err = new Error(reason);
      err.name = 'CancelError';
      rejectOuter(err);
    },
    isCancelled: () => cancelled,
  };
}

function cancellableDelay(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal && signal.aborted) return reject(signal.reason);
    const onAbort = () => {
      clearTimeout(id);
      reject(signal.reason);
    };
    const id = setTimeout(() => {
      if (signal) signal.removeEventListener('abort', onAbort);
      resolve(ms);
    }, ms);
    if (signal) signal.addEventListener('abort', onAbort, { once: true });
  });
}
```

**Test**

```js
  const b = makeCancellable(delay(10, 'quote'));
  console.log('b: ' + (await b.promise));

  console.log('no signal: ' + (await cancellableDelay(15)));

  const def = new AbortController();
```

**makeCancellable:** create an outer promise that forwards the source's result, and keep its `reject` so `cancel` can settle it early. Because a promise settles only once, a late source result is ignored automatically. The `settled` flag makes `cancel` a no-op after completion, so `isCancelled` stays accurate.

**Limitation:** this only **ignores** the result. The underlying work keeps running. That is why the second helper uses an **AbortSignal**, which actually clears the timer.

**cancellableDelay details**
- It checks `signal.aborted` **before** starting, because an already-aborted signal never fires `abort` again.
- It uses `{ once: true }` and removes the listener on success to avoid leaks with long-lived signals.
- `controller.abort()` with no argument makes `signal.reason` a `DOMException` named `AbortError`.

**Complexity:** O(1).

**Common mistakes**
- Rejecting with a string, so callers can't check `name`.
- Forgetting the pre-aborted case.
- Assuming the wrapper stops network calls. Pass the signal to `fetch` for that.

## P53. `Promise.withResolvers()` (ES2024) · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

`Promise.withResolvers()` returns `{ promise, resolve, reject }`, a promise together with the functions that settle it, **outside** of an executor. This is the standard version of the old **"deferred"** pattern.

```js
// Before
let resolve, reject;
const promise = new Promise((res, rej) => { resolve = res; reject = rej; });

// ES2024
const { promise, resolve, reject } = Promise.withResolvers();
```

**Good use cases:** settling from **somewhere else**, such as event handlers, message ports, or request/response matching.
```js
const pending = new Map();   // orderId -> resolvers
function placeOrder(order) {
  const { promise, resolve, reject } = Promise.withResolvers();
  pending.set(order.id, { resolve, reject });
  socket.send(JSON.stringify(order));
  return promise;
}
socket.onmessage = ({ data }) => {
  const msg = JSON.parse(data);
  const entry = pending.get(msg.orderId);
  if (!entry) return;
  pending.delete(msg.orderId);
  msg.ok ? entry.resolve(msg) : entry.reject(new Error(msg.reason));
};
```

**Pitfalls**
- Unlike the executor, a **synchronous throw** in the code that sets up the work is **not** turned into a rejection automatically.
- It's easy to leave a promise **pending forever**, so add timeouts and clean up maps.
- It's generic: `Promise.withResolvers.call(MyPromiseSubclass)` works with subclasses.

**Support:** Chrome 119+, Firefox 121+, Safari 17.4+, Node 22+. Add a polyfill for older targets.

**Takeaway:** `withResolvers` gives you a promise plus its settle functions, which is ideal when the result arrives from a different place than where the promise is created.

</details>

## P54. Polyfill `Promise.withResolvers` · `hard` · 💻 Coding

Write `withResolvers()` so that it can be installed as `Promise.withResolvers` when that's missing:
- It returns `{ promise, resolve, reject }`.
- It uses `this` as the constructor (so subclasses work), with `Promise` as the default when `this` is not a constructor.
- Install it **only if** the native method doesn't exist.

Then use it to build a tiny **request tracker**: `track(id)` returns a promise, and `settle(id, ok, payload)` resolves or rejects it later.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function withResolvers() {
  const C = typeof this === 'function' ? this : Promise;
  let resolve, reject;
  const promise = new C((res, rej) => {
    resolve = res;
    reject = rej;
  });
  return { promise, resolve, reject };
}

if (typeof Promise.withResolvers !== 'function') {
  Object.defineProperty(Promise, 'withResolvers', {
    value: withResolvers,
    writable: true,
    configurable: true,
  });
}

function createTracker() {
  const pending = new Map();
  return {
    track(id) {
      const d = withResolvers.call(Promise);
      pending.set(id, d);
      return d.promise;
    },
    settle(id, ok, payload) {
      const d = pending.get(id);
      if (!d) return false;
      pending.delete(id);
      if (ok) d.resolve(payload);
      else d.reject(new Error(payload));
      return true;
    },
    size: () => pending.size,
  };
}
```

**Approach:** the executor runs synchronously, so we can copy `resolve` and `reject` into outer variables before the constructor returns. Using `this` as the constructor matches the spec, where `withResolvers` is generic and works for subclasses.

## P55. Concurrency-limited promise pool · `hard` · 💻 Coding

Write `promisePool(tasks, limit)`:
- `tasks` is an array of **functions** that return promises.
- Run at most `limit` tasks at the same time. When one finishes, start the next.
- Resolve with all results in **input order**.
- If any task rejects, reject with that error and **don't start** any more tasks. Tasks already running may finish.
- `limit` greater than the number of tasks, and empty input, must both work.

**Use case:** fetching historical candles for 50 symbols while the API allows only 3 parallel requests.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function promisePool(tasks, limit) {
  return new Promise((resolve, reject) => {
    const results = new Array(tasks.length);
    let next = 0;       // index of the next task to start
    let done = 0;       // how many tasks have fulfilled
    let failed = false;

    if (tasks.length === 0) return resolve(results);

    const startNext = () => {
      if (failed || next >= tasks.length) return;
      const index = next++;
      Promise.resolve()
        .then(() => tasks[index]())          // a sync throw becomes a rejection
        .then(value => {
          results[index] = value;
          done++;
          if (done === tasks.length) resolve(results);
          else startNext();
        }, err => {
          failed = true;
          reject(err);
        });
    };

    for (let i = 0; i < Math.min(limit, tasks.length); i++) startNext();
  });
}
```

**Approach:** a worker-style scheduler. Start `min(limit, n)` tasks. Each time one fulfills, save the result at its index and start the next task. Because a new task starts only when an old one finishes, at most `limit` run at once.

- **Fail-fast:** the `failed` flag stops new tasks from starting, while running ones finish on their own.
- **Sync throws:** calling the task inside `.then` turns a throw into a rejection.

- Using `results.push`, which gives completion order.

## P56. Promise-returning debounce · `hard` · 💻 Coding

Write `debounceAsync(fn, wait)`, which returns a debounced function that **returns a promise**:
- Each call restarts a `wait` ms timer. Only when calls stop for `wait` ms is `fn` called, **once**, with the **last** call's arguments.
- **Every caller** from that burst gets a promise that settles with that single call's result (or error).
- A later burst starts a new group.

**Use case:** a stock search box. Typing "T", "TA", "TAT" should trigger one API call, and every caller awaiting a result gets the result for "TAT".

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function debounceAsync(fn, wait) {
  let timer = null;
  let waiters = [];          // callers waiting on the current burst

  return function debounced(...args) {
    const ctx = this;
    clearTimeout(timer);

    return new Promise((resolve, reject) => {
      waiters.push({ resolve, reject });

      timer = setTimeout(() => {
        const group = waiters;
        waiters = [];
        timer = null;
        Promise.resolve()
          .then(() => fn.apply(ctx, args))    // last call's args and this
          .then(
            value => group.forEach(w => w.resolve(value)),
            error => group.forEach(w => w.reject(error))
          );
      }, wait);
    });
  };
}
```

**Approach:** each call adds its `resolve/reject` to a `waiters` list and restarts the timer. - **Sync throw or rejection in `fn`:** calling it inside `.then` covers both, and every waiter is rejected.

- Using the **first** call's arguments.
- Clearing `waiters` after `fn` resolves instead of before it's called.

## P57. `firstFulfilledByPriority(promises)` · `hard` · 💻 Coding

You query several quote sources, ordered by **priority** (index 0 is the most trusted). Write `firstFulfilledByPriority(promises)`:
- Resolve with `{ index, value }` of the **highest-priority input that fulfills**.
- A lower-priority result may be used **only after** every higher-priority input has **rejected**. If a higher one is still pending, wait for it.
- Resolve **as early as possible**: don't wait for lower-priority inputs once the answer is known.
- If all reject, reject with an `AggregateError` of all reasons in input order. Empty input rejects the same way.

**Example**
```
[ reject@30ms, fulfil 'B'@50ms, fulfil 'C'@10ms ]  -> { index: 1, value: 'B' } at ~50ms
```

**Solution**

```js
function firstFulfilledByPriority(promises) {
  return new Promise((resolve, reject) => {
    const items = Array.from(promises);
    const n = items.length;
    const states = new Array(n);          // undefined = pending
    let cursor = 0;                       // highest priority still undecided

    const advance = () => {
      while (cursor < n && states[cursor]) {
        const s = states[cursor];
        if (s.ok) return resolve({ index: cursor, value: s.value });
        cursor++;
      }
      if (cursor === n) {
        reject(new AggregateError(states.map(s => s.reason), 'All sources failed'));
      }
    };

    items.forEach((item, i) => {
      Promise.resolve(item).then(
        value => { states[i] = { ok: true, value }; advance(); },
        reason => { states[i] = { ok: false, reason }; advance(); }
      );
    });

    if (n === 0) advance();
  });
}
```

**Test**

**Approach:** record each input's outcome by index, and keep a **cursor** at the highest-priority input that hasn't been decided yet. After every settlement, move the cursor forward:
- If the cursor's input is **pending**, stop and wait.
- If it **rejected**, move to the next one.
- If it **fulfilled**, resolve. It's the best possible answer, since everything before it failed.
- If the cursor passes the end, every input rejected, so reject with an `AggregateError`.

**Why it's correct and fast:** the answer depends only on the inputs up to the first fulfilled one. As soon as those are known, we resolve. Lower-priority inputs are never waited on.

**Edge cases:** empty input rejects immediately. Plain values count as fulfilled. Extra `resolve` or `reject` calls after settling are harmless.

**Complexity:** O(n) total. The cursor only moves forward, so all `advance` calls together cost O(n). Space is O(n).

**Common mistakes**
- Using `Promise.any`, which returns the **fastest** success, not the highest-priority one.
- Awaiting the inputs one by one, which is correct but adds no parallelism benefit and can't notice early failures in bulk. It's also easy to leave rejections unhandled that way.
- Waiting for all inputs with `allSettled` before deciding, which is slower than needed.

## P58. Build a minimal `MyPromise` class · `hard` · 💻 Coding

Implement `MyPromise` from scratch (no use of native `Promise` inside the class):
- `new MyPromise(executor)`: the executor runs synchronously, a throw inside it rejects, and the promise settles only once.
- `then(onFulfilled, onRejected)`: returns a new MyPromise. Callbacks run **asynchronously** (use `queueMicrotask`). Non-function arguments pass the result through. A returned value, thenable, or throw decides the new promise's outcome.
- **Adoption:** resolving with any thenable (including native promises) follows it. Resolving with itself rejects with `TypeError`.
- `catch(onRejected)` and `finally(onFinally)`, with the standard semantics.
- Static `MyPromise.resolve(value)` and `MyPromise.reject(reason)`.
- It must work with `await`.

<summary><b>Solution & explanation</b></summary>

**Solution**

```js
class MyPromise {
  #state = 'pending';
  #value = undefined;
  #reactions = [];

  constructor(executor) {
    let alreadyResolved = false;
    const resolve = value => {
      if (alreadyResolved) return;
      alreadyResolved = true;
      this.#resolveWith(value);
    };
    const reject = reason => {
      if (alreadyResolved) return;
      alreadyResolved = true;
      this.#settle('rejected', reason);
    };
    try {
      executor(resolve, reject);
    } catch (err) {
      reject(err);
    }
  }

  // Promise Resolution Procedure
  #resolveWith(x) {
    if (x === this) {
      return this.#settle('rejected', new TypeError('Chaining cycle detected for promise'));
    }
    if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
      let then;
      try {
        then = x.then;
      } catch (err) {
        return this.#settle('rejected', err);
      }
      if (typeof then === 'function') {
        let called = false;
        queueMicrotask(() => {
          try {
            then.call(
              x,
              y => { if (!called) { called = true; this.#resolveWith(y); } },
              r => { if (!called) { called = true; this.#settle('rejected', r); } }
            );
          } catch (err) {
            if (!called) { called = true; this.#settle('rejected', err); }
          }
        });
        return;
      }
    }
    this.#settle('fulfilled', x);
  }

  #settle(state, value) {
    if (this.#state !== 'pending') return;
    this.#state = state;
    this.#value = value;
    const reactions = this.#reactions;
    this.#reactions = [];
    reactions.forEach(r => this.#schedule(r));
  }

  #schedule({ onFulfilled, onRejected, resolve, reject }) {
    queueMicrotask(() => {
      const fulfilled = this.#state === 'fulfilled';
      const handler = fulfilled ? onFulfilled : onRejected;
      if (typeof handler !== 'function') {
        return fulfilled ? resolve(this.#value) : reject(this.#value);
      }
      try {
        resolve(handler(this.#value));
      } catch (err) {
        reject(err);
      }
    });
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      const reaction = { onFulfilled, onRejected, resolve, reject };
      if (this.#state === 'pending') this.#reactions.push(reaction);
      else this.#schedule(reaction);
    });
  }

  catch(onRejected) {
    return this.then(undefined, onRejected);
  }

  finally(onFinally) {
    if (typeof onFinally !== 'function') return this.then(onFinally, onFinally);
    return this.then(
      value => MyPromise.resolve(onFinally()).then(() => value),
      reason => MyPromise.resolve(onFinally()).then(() => { throw reason; })
    );
  }

  static resolve(value) {
    if (value instanceof MyPromise) return value;
    return new MyPromise(resolve => resolve(value));
  }

  static reject(reason) {
    return new MyPromise((_, reject) => reject(reason));
  }
}
```

**Design**
- **State:** `#state`, `#value`, and a list of pending **reactions**. `#settle` changes the state once and schedules all waiting reactions.
- **Resolve once:** a shared `alreadyResolved` flag in the constructor covers `resolve`, `reject` and the executor throw. Resolving with a pending thenable counts as resolved too.
- **then:** returns a new `MyPromise` whose `resolve/reject` are stored with the handlers. `#schedule` always uses `queueMicrotask`, so handlers never run synchronously, even for promises that are already settled.
- **Resolution procedure (`#resolveWith`):** check for a self-cycle, read `then` only once (a getter could throw), call it in a microtask with first-call-wins guards, and fulfill with plain values. This is what makes interop with native promises and `await` work: a native `await` treats `MyPromise` as a thenable.
- **finally:** built on `then`. It waits for the cleanup's promise and passes the original result through, unless the cleanup throws or rejects.

**Edge cases tested:** sync executor, settle-once, pass-through for non-functions, adopting MyPromise, native and plain thenables, the cycle `TypeError`, all `finally` rules, several reactions on one promise, and static helpers.

**Complexity:** O(1) per `then` and O(k) to flush k reactions.

**Common mistakes:** running handlers synchronously, resolving the *outer* promise with a thenable without unwrapping it, forgetting the pass-through for missing handlers, and letting a thenable call both of its callbacks.
