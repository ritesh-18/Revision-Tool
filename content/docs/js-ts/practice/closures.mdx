## C1. What is a closure? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Definition:** a closure is a function together with the lexical environment it was created in. Because of that link, the function can keep reading and updating variables of its outer scope even after the outer function has returned.

**Why it matters:** closures are how JavaScript gives you private state, factories, callbacks that remember context, memoization, debounce/throttle and React hooks.

```js
function makeGreeter(broker) {
  const prefix = 'Welcome to ' + broker; // lives in makeGreeter's scope
  return function (name) {
    return prefix + ', ' + name;          // still reachable later
  };
}
const greet = makeGreeter('Angel One');
greet('Asha'); // 'Welcome to Angel One, Asha'
```

`makeGreeter` has finished running, but `prefix` is not garbage-collected because the returned function still references it.

**Pitfalls:**
- A closure keeps a live link to the **variable**, not a copy of its value.
- Whatever is captured stays in memory as long as the closure is reachable.

**Interview tip:** avoid the vague "a function inside a function". Say: "a function plus a reference to the scope where it was *defined*, which it can use wherever it is *called*."

**Takeaway:** a closure is a function that remembers the variables of the scope it was defined in.

</details>

## C2. Inner function outlives its parent · `easy` · 🖨️ Output

```js
function createWatchlist(name) {
  const symbols = [];
  return function add(symbol) {
    symbols.push(symbol);
    return name + ': ' + symbols.join(',');
  };
}

const addTech = createWatchlist('Tech');
addTech('INFY');
console.log(addTech('TCS'));
console.log(createWatchlist('Banks')('HDFC'));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
Tech: INFY,TCS
Banks: HDFC
```

1. `createWatchlist('Tech')` creates a new scope that holds `name = 'Tech'` and an empty `symbols` array, then returns `add`.
2. The outer call has finished, but `add` still points to that scope, so `symbols` stays alive.
3. `addTech('INFY')` pushes into the same array. `addTech('TCS')` pushes again, so the array is now `INFY,TCS`. The first log is `Tech: INFY,TCS`.
4. `createWatchlist('Banks')` is a **separate call** with its own new `symbols` array. Calling the returned function straight away gives `Banks: HDFC`.

**Takeaway:** each call to the outer function creates a new set of captured variables, and they last as long as the inner function does.

</details>

## C3. Lexical scope vs dynamic scope · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Lexical (static) scope:** the variables a function can see are decided by **where the function is written** in the source code. JavaScript uses lexical scope.

**Dynamic scope:** the variables are decided by **who calls the function** at runtime, by searching the call stack. Some older Lisps and Bash work this way. JavaScript does not.

```js
const exchange = 'NSE';
function printExchange() {
  console.log(exchange);   // looks where printExchange was DEFINED
}
function run() {
  const exchange = 'BSE';  // the caller's variable is ignored
  printExchange();
}
run(); // 'NSE'
```

**Why it matters:** closures work because of lexical scope. You can tell what a function will capture just by reading the code.

**Pitfall:** `this` is the part that *feels* dynamic. For normal functions, `this` depends on how the function is called. That is a different mechanism from variable lookup. Arrow functions take `this` lexically.

**Interview tip:** say it like this: "Scope is lexical; `this` is dynamic (except for arrow functions)."

**Takeaway:** in JavaScript, variable lookup depends on where code is written, never on who calls it.

</details>

## C4. The caller's variable is not visible · `easy` · 🖨️ Output

```js
var symbol = 'NIFTY';

function show() {
  console.log(symbol);
}

function run() {
  var symbol = 'SENSEX';
  show();
  return function () {
    console.log(symbol);
  };
}

const inner = run();
inner();
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
NIFTY
SENSEX
```

1. `show` is declared at the top level, so its outer scope is the global scope. It is not linked to `run`'s scope.
2. `run` declares its own `symbol = 'SENSEX'` and calls `show()`. `show` looks for `symbol` along **its own** scope chain (show → global) and finds `'NIFTY'`.
3. The anonymous function returned by `run` is written *inside* `run`. Its lookup goes anonymous → run → global, so it finds `'SENSEX'` first.

**Takeaway:** a function's scope chain depends on where it is defined, not where it is called.

</details>

## C5. makeAdder and makeMultiplier · `easy` · 💻 Coding

Write two factory functions:

- `makeAdder(x)` returns a function that takes `y` and returns `x + y`.
- `makeMultiplier(factor)` returns a function that takes `value` and returns `value * factor`.

Every returned function must remember its own `x` or `factor`.

```js
const addBrokerage = makeAdder(20);
addBrokerage(100); // 120
const withGst = makeMultiplier(1.18);
withGst(100).toFixed(2); // '118.00'
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function makeAdder(x) {
  return function (y) {
    return x + y;
  };
}

function makeMultiplier(factor) {
  return (value) => value * factor;
}
```

**Test**

```js
const addBrokerage = makeAdder(20);
console.log(addBrokerage(100));
console.log(addBrokerage(0));

const double = makeMultiplier(2);
const triple = makeMultiplier(3);
console.log(double(7), triple(7));

const withGst = makeMultiplier(1.18);
console.log(withGst(100).toFixed(2));

console.log(makeAdder(-5)(5));
console.log(makeMultiplier(0)(999));
```

**Output**

```text
120
20
14 21
118.00
0
0
```

**Approach:** each factory call creates a new scope that holds its argument. The returned function closes over that scope, so `double` and `triple` keep separate `factor` values.

**Edge cases:** negative numbers, zero, and floating-point results. `100 * 1.18` is `118.00000000000001` in IEEE-754, so round with `toFixed` before you show money. In real trading code, store amounts in paise (integers).

**Complexity:** O(1) time and O(1) space per factory call.

**Common mistakes:**
- Returning `x + y` straight away instead of returning a function.
- Storing `x` in a shared outer variable, so the last factory call overwrites earlier ones.

This is the simplest form of **partial application**: fix one argument now and pass the rest later.

</details>

## C6. The scope chain · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Definition:** every running piece of code has a *lexical environment*. It holds a record of local bindings plus a reference to the **outer** environment. Linked together, these form the **scope chain**. To resolve an identifier, the engine checks the current record, then the outer one, and so on up to the global scope. If the name is not found anywhere, it throws a `ReferenceError`.

```js
const market = 'NSE';                 // global
function portfolio() {
  const owner = 'Asha';               // portfolio scope
  function holding() {
    const qty = 10;                   // holding scope
    return owner + ' ' + qty + ' @' + market; // walks up the chain
  }
  return holding();
}
```

**Key facts:**
- The chain is fixed when a function is **created**, not when it is called.
- Inner scopes can **shadow** outer names. The nearest binding wins.
- Blocks (`{}`) create scopes for `let`, `const` and `class`. `var` ignores blocks and is scoped to the function.
- Writing to an undeclared name in sloppy mode creates an accidental global. Strict mode throws instead.

**Interview tip:** describe the chain as "a linked list of environments that a closure holds a pointer into".

**Takeaway:** name lookup goes outward through nested environments, and the first match wins.

</details>

## C7. createCounter with increment / decrement / reset · `easy` · 💻 Coding

Implement `createCounter(initial = 0)`. It returns an object with:

- `increment()` adds 1 and returns the new value
- `decrement()` subtracts 1 and returns the new value
- `reset()` sets the count back to `initial` and returns it
- a read-only `value` getter

Code outside must not be able to change the count directly. Counters must be independent of each other.

```js
const c = createCounter(5);
c.increment(); // 6
c.reset();     // 5
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createCounter(initial = 0) {
  let count = initial;
  return {
    increment() {
      count += 1;
      return count;
    },
    decrement() {
      count -= 1;
      return count;
    },
    reset() {
      count = initial;
      return count;
    },
    get value() {
      return count;
    },
  };
}
```

**Test**

```js
const c = createCounter(5);
console.log(c.increment(), c.increment());
console.log(c.decrement());
console.log(c.value);
console.log(c.reset());
console.log(typeof c.count);

c.value = 100; // no setter: ignored in sloppy mode
console.log(c.value);

const d = createCounter();
d.decrement();
console.log(d.value, c.value);
```

**Output**

```text
6 7
6
6
5
undefined
5
-1 5
```

**Approach:** `count` is a local variable of `createCounter`. The three methods and the getter all close over the **same** `count`, so they share it. Code outside can only reach it through those methods.

**Edge cases:**
- `reset` goes back to the given `initial` value, not to 0.
- Assigning to `c.value` does nothing because there is no setter. In strict mode it would throw a `TypeError`.
- `d` comes from a separate call, so its `count` has no link to `c`.

**Complexity:** O(1) time for each operation, O(1) space.

**Common mistakes:** storing `count` as a property (`this.count`), which anyone can change. Declaring `count` outside the factory, which makes every counter share one value.

</details>

## C8. Shared counter vs factory counters · `easy` · 🖨️ Output

```js
let shared = 0;
const incA = () => ++shared;
const incB = () => ++shared;

function factory() {
  let own = 0;
  return () => ++own;
}
const incC = factory();
const incD = factory();

incA(); incB(); incA();
incC(); incC(); incD();

console.log(shared, incA(), incB());
console.log(incC(), incD());
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
3 4 5
3 2
```

1. `incA` and `incB` both close over the **same** `shared` variable. Three calls take it to 3.
2. `incC` and `incD` come from two separate `factory()` calls, so each has its own `own`. After the calls, `incC`'s `own` is 2 and `incD`'s is 1.
3. Arguments are evaluated left to right. `shared` is read as 3, then `incA()` makes it 4, then `incB()` makes it 5. The output is `3 4 5`.
4. `incC()` goes to 3 and `incD()` goes to 2.

**Takeaway:** functions share state only when they close over the same binding. A new call to the outer function gives new bindings.

</details>

## C9. When are closures created? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Short answer:** every time a function object is created, whether from a declaration, an expression, an arrow, or a method. At that moment it stores a reference to the current lexical environment (the spec calls this internal slot `[[Environment]]`). So in JavaScript, **every function is a closure**, including functions defined at the top level (they close over the global scope).

```js
function makeLogger(tag) {
  return (msg) => tag + ': ' + msg; // a NEW arrow + NEW env link per call
}
const a = makeLogger('ORDER');
const b = makeLogger('ORDER');
a === b; // false: two function objects, two environments
```

**Consequences:**
- Creating functions inside a loop or a render function makes a new function object each time. This matters for React `memo`/`useCallback` checks and for listener removal (`removeEventListener` needs the *same* reference).
- The captured environment is chosen when the function is **created**. The variable values are read when the function **runs**.

**Interview tip:** people usually say "a closure" when an inner function actually uses outer variables after the outer call has returned. Mention that, but also say that technically every function has the link.

**Takeaway:** a closure is created whenever a function is created, and it captures the environment of that moment.

</details>

## C10. IIFE and the module pattern · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**IIFE** (Immediately Invoked Function Expression) is a function that is defined and called at once: `(function () { ... })()`. Before ES6 there was no block scope, so an IIFE was the standard way to create a private scope and avoid polluting globals.

**Module pattern:** an IIFE that keeps state private and returns a public API. The API methods are closures over that private state.

```js
const OrderBook = (function () {
  const orders = [];                 // private
  function validate(o) { return o.qty > 0; }
  return {                           // public API
    place(o) { if (validate(o)) orders.push(o); return orders.length; },
    count() { return orders.length; },
  };
})();
OrderBook.place({ qty: 5 }); // 1
OrderBook.orders;            // undefined
```

**Variants:** the *revealing module pattern* defines every function privately and returns `{ place: place, count: count }`.

**Today:** ES modules (`import`/`export`) give file-level scope and singletons natively, so IIFEs are rarer. You still see them in bundler output, in UMD libraries, and as async IIFEs used where top-level await is not allowed.

**Pitfall:** without a leading `;`, an IIFE right after a line that has no semicolon can be parsed as a function call on that line.

**Takeaway:** an IIFE creates a private scope right away, and the module pattern returns closures that are the only way into that scope.

</details>

## C11. Module pattern with an IIFE · `easy` · 🖨️ Output

```js
const PriceFeed = (function () {
  let ticks = 0;
  const prices = {};
  function update(symbol, price) {
    ticks++;
    prices[symbol] = price;
  }
  return {
    update,
    last: (symbol) => prices[symbol],
    ticks: () => ticks,
  };
})();

PriceFeed.update('INFY', 1500);
PriceFeed.update('INFY', 1512);
PriceFeed.ticks = 99;

console.log(PriceFeed.last('INFY'));
console.log(typeof PriceFeed.prices, PriceFeed.ticks);
console.log(typeof PriceFeed);
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
1512
undefined 99
object
```

1. The IIFE runs at once and returns an object. `PriceFeed` is that object, not a function, so `typeof PriceFeed` is `'object'`.
2. Two `update` calls set `prices.INFY` to 1512 and `ticks` to 2 inside the private scope.
3. `PriceFeed.last('INFY')` reads the private `prices` through the closure and returns `1512`.
4. `prices` was never exposed, so `PriceFeed.prices` is `undefined`.
5. `PriceFeed.ticks = 99` replaces the **property** on the returned object (the object is not frozen). Now `PriceFeed.ticks` is the number 99. The private `ticks` variable is still 2, but nothing can read it now.

**Takeaway:** the returned API object can still be changed. To lock it, use `Object.freeze`.

</details>

## C12. Unique ID generator with a prefix · `easy` · 💻 Coding

Write `createIdGenerator(prefix = 'id', start = 1)`. It returns a function that gives a new ID on every call, in the format `<prefix>-<number padded to 4 digits>`.

- Each generator has its own sequence.
- The counter must not be reachable from outside.

```js
const nextOrderId = createIdGenerator('ORD');
nextOrderId(); // 'ORD-0001'
nextOrderId(); // 'ORD-0002'
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createIdGenerator(prefix = 'id', start = 1) {
  let next = start;
  return function nextId() {
    const id = prefix + '-' + String(next).padStart(4, '0');
    next += 1;
    return id;
  };
}
```

**Test**

```js
const nextOrderId = createIdGenerator('ORD');
const nextTradeId = createIdGenerator('TRD', 9999);

console.log(nextOrderId());
console.log(nextOrderId());
console.log(nextTradeId());
console.log(nextTradeId());
console.log(nextOrderId());
console.log(createIdGenerator()());
console.log(typeof nextOrderId.next);
```

**Output**

```text
ORD-0001
ORD-0002
TRD-9999
TRD-10000
ORD-0003
id-0001
undefined
```

**Approach:** `next` and `prefix` live in the factory's scope. Each call builds the ID from the current `next` and then increments it.

**Edge cases:**
- `padStart` only adds padding. Numbers longer than 4 digits (`10000`) are left as they are.
- Two generators never affect each other.
- `nextId.next` is not a property, so the counter cannot be changed from outside.

**Complexity:** O(1) per call (padding is bounded).

**Common mistakes:** keeping the counter in a module-level variable, so all prefixes share one sequence. Incrementing before reading, which makes the sequence start at 2.

**Real world:** use this for client-side temporary order IDs or React list keys. For IDs that must be unique across tabs or servers, use `crypto.randomUUID()`.

</details>

## C13. Data privacy and encapsulation with closures · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Idea:** variables declared inside a function cannot be reached from outside. If you return only functions that use them, those functions become the **only interface** to the data. This gives real privacy, which a naming convention like `_balance` does not.

```js
function createWallet() {
  let balance = 0;                       // truly private
  return {
    add(amount) {
      if (amount <= 0) throw new RangeError('Invalid amount');
      balance += amount;
    },
    get balance() { return balance; },   // read-only view
  };
}
const w = createWallet();
w.add(100);
w.balance = 1e9;   // no setter, so this is ignored
w.balance;         // 100
```

**Why it matters:**
- The object keeps its **rules** (for example, no negative balance) because every change goes through validation.
- It reduces coupling: you can change the internal representation without breaking callers.

**Pitfalls:**
- If you return a private *object or array* directly, callers can mutate it. Return a copy (`list.slice()`) instead.
- Each instance creates its own copies of the methods, which uses more memory than prototype methods.
- Private closure state cannot be inspected in tests except through the API. That is usually a good thing.

**Takeaway:** closures give real privacy. Expose behaviour, not the data itself.

</details>

## C14. Implement `once(fn)` · `easy` · 💻 Coding

Implement `once(fn)`. It returns a function that calls `fn` only the **first** time. Later calls return the result of that first call.

- Pass the arguments and `this` of the first call through to `fn`.
- Release the reference to `fn` after it runs, so it can be garbage-collected.

```js
const connect = once((url) => 'connected:' + url);
connect('wss://feed-1'); // 'connected:wss://feed-1'
connect('wss://feed-2'); // 'connected:wss://feed-1'
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function once(fn) {
  let called = false;
  let result;
  return function (...args) {
    if (!called) {
      called = true;
      result = fn.apply(this, args);
      fn = null; // let the original function be garbage-collected
    }
    return result;
  };
}
```

**Test**

```js
let connections = 0;
const connect = once((url) => {
  connections++;
  return 'connected:' + url;
});
console.log(connect('wss://feed-1'));
console.log(connect('wss://feed-2'));
console.log(connections);

const account = {
  id: 'A1',
  init: once(function () {
    return 'init ' + this.id;
  }),
};
console.log(account.init());

let runs = 0;
const nothing = once(() => {
  runs++;
});
console.log(nothing(), nothing(), runs);
```

**Output**

```text
connected:wss://feed-1
connected:wss://feed-1
1
init A1
undefined undefined 1
```

**Approach:** a `called` flag and a cached `result` live in the closure. The wrapper is a normal `function`, not an arrow, so it gets the caller's `this` and passes it on with `apply`.

**Edge cases:**
- `fn` returns `undefined`. Checking `result === undefined` would run `fn` again, so use a separate flag.
- `fn` throws. Here `called` is already `true`, so later calls return `undefined`. If you want a retry after an error, set the flag only after `fn` succeeds.
- Setting `fn = null` releases whatever the original function captured.

**Complexity:** O(1) per call.

**Common mistakes:** using an arrow function as the wrapper (this loses `this`), and not caching the return value.

**Uses:** SDK initialisation, opening one WebSocket, one-time analytics events. For DOM events, `addEventListener(type, fn, { once: true })` does this for you.

</details>

## C15. `var` in a loop with `setTimeout` · `easy` · 🖨️ Output

```js
for (var i = 0; i < 3; i++) {
  setTimeout(function () {
    console.log('order', i);
  }, 10);
}
console.log('loop done, i =', i);
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
loop done, i = 3
order 3
order 3
order 3
```

1. `var i` is scoped to the function (here, the script), so there is **one** `i` for the whole loop.
2. The loop schedules three callbacks. All three close over that single `i`.
3. The loop ends when `i` becomes 3. `i` is still reachable after the loop (no block scope), so the synchronous log prints `loop done, i = 3`.
4. About 10 ms later the callbacks run and read `i` at that moment, which is `3`, three times.

**Takeaway:** callbacks read a variable's value when they run, and a `var` loop has only one variable.

</details>

## C16. `let` in a loop with `setTimeout` · `easy` · 🖨️ Output

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log('order', i), 10);
}
try {
  console.log(i);
} catch (e) {
  console.log(e.name);
}
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
ReferenceError
order 0
order 1
order 2
```

1. For `for (let ...)`, the spec creates a **new binding of `i` for each iteration**. The current value is copied into the new binding before the increment runs.
2. Each arrow function closes over its own iteration's `i`: 0, 1 and 2.
3. `i` is block-scoped to the loop, so reading it afterwards throws a `ReferenceError`. The `catch` prints its name, and this happens synchronously before any timer.
4. The timers then fire in order and print 0, 1, 2.

**Takeaway:** `let` in a `for` header gives each iteration its own binding, so each closure sees a different value.

</details>

## C17. Closures in loops: `var` vs `let` · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**The problem:** functions created inside a loop, such as event handlers or timers, run later. With `var`, every one of them shares **one** variable, so they all see its final value.

**Why `let` fixes it:** for a `for (let i ...; ...; ...)` loop, the engine makes a new environment for each iteration and copies the current `i` into it (spec step *CreatePerIterationEnvironment*). Each closure captures a different binding.

```js
const handlers = [];
for (var i = 0; i < 3; i++) handlers.push(() => i);
handlers.map((h) => h()); // [3, 3, 3]

const fixed = [];
for (let j = 0; j < 3; j++) fixed.push(() => j);
fixed.map((h) => h());    // [0, 1, 2]
```

**Other fixes when you must use `var`:** an IIFE that takes `i` as a parameter, `setTimeout(fn, ms, i)` with extra arguments, `fn.bind(null, i)`, or `forEach` (every callback call has its own parameter).

**Traps:**
- `for...in` and `for...of` with `let` or `const` also create a new binding per iteration. With `var` they do not.
- A `let` declared **outside** the loop (`let i; for (i = 0; ...)`) is still just one binding.

**Takeaway:** a closure captures a binding, and only per-iteration `let`/`const` gives you a fresh binding each time around.

</details>

## C18. Fix the classic `var` + `setTimeout` loop three ways · `medium` · 💻 Coding

This loop prints `3,3,3` but should print `0,1,2`:

```js
for (var i = 0; i < 3; i++) setTimeout(() => out.push(i), 10);
```

Write three functions, each fixing it in a different way. Each should collect the values and then call `done(label, values)` once all three timers have fired:

1. `withLet(done)` uses block scoping.
2. `withIIFE(done)` keeps `var` but uses an IIFE.
3. `withTimerArg(done)` keeps `var` and passes the value as an extra `setTimeout` argument.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function withLet(done) {
  const out = [];
  for (let i = 0; i < 3; i++) {
    setTimeout(() => {
      out.push(i);
      if (out.length === 3) done('let', out);
    }, 10);
  }
}

function withIIFE(done) {
  const out = [];
  for (var i = 0; i < 3; i++) {
    (function (j) {
      setTimeout(function () {
        out.push(j);
        if (out.length === 3) done('iife', out);
      }, 20);
    })(i);
  }
}

function withTimerArg(done) {
  const out = [];
  for (var i = 0; i < 3; i++) {
    setTimeout(
      function (j) {
        out.push(j);
        if (out.length === 3) done('timer-arg', out);
      },
      30,
      i
    );
  }
}
```

**Test**

```js
const report = (label, values) => console.log(label + ': ' + values.join(','));

withLet(report);
withIIFE(report);
withTimerArg(report);

// the original bug, for comparison
const broken = [];
for (var k = 0; k < 3; k++) {
  setTimeout(() => {
    broken.push(k);
    if (broken.length === 3) report('broken', broken);
  }, 40);
}
```

**Output**

```text
let: 0,1,2
iife: 0,1,2
timer-arg: 0,1,2
broken: 3,3,3
```

**Approach:** each fix makes sure every callback has its **own** binding that holds the value:
1. **`let`**: each loop iteration gets a new `i`.
2. **IIFE**: calling a function creates a new scope. The parameter `j` gets a copy of the current `i`.
3. **Extra `setTimeout` arguments**: arguments after the delay are passed to the callback, so `i` is evaluated when `setTimeout` is called. `setTimeout(fn.bind(null, i), 30)` works the same way.

**Edge cases:** the timers use different delays (10/20/30/40 ms), so the order of the reports is predictable.

**Complexity:** O(n) timers and O(n) space in every version.

**Common mistakes:**
- Writing `setTimeout(fn(i), 10)`. This *calls* `fn` straight away and passes its return value as the callback.
- Putting `let j = i` outside the loop body, which gives only one binding again.
- Using an IIFE that takes no parameter and still reads `i`, which fixes nothing.

</details>

## C19. Factory functions vs constructors/classes · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Factory function:** a normal function that builds and returns an object. Closures give it private state, and you do not need `new` or `this`.

```js
function createOrder(symbol, qty) {
  let status = 'OPEN';                          // private
  return {
    symbol,
    qty,
    fill() { status = 'FILLED'; },
    getStatus: () => status,                    // no 'this' needed
  };
}
const o = createOrder('TCS', 5);
const { getStatus } = o;
getStatus();  // 'OPEN': still works after being detached
```

**Pros:**
- Real privacy without `#fields`.
- No problems with `this` binding. Methods can be passed as callbacks directly.
- Easy to build from parts by spreading or merging objects.

**Cons:**
- Each instance gets its **own copies** of the methods, which uses more memory than shared prototype methods. That matters for thousands of objects, such as order-book rows.
- `instanceof` does not work, and there is no inheritance chain.
- Private state is harder to inspect in DevTools (look under "Closure" in the scope pane).

**Interview tip:** choose factories for small numbers of objects with rich behaviour (services, stores). Choose classes when you create many instances or need inheritance.

**Takeaway:** factories use closures for privacy and avoid `this`, at the cost of one copy of each method per object.

</details>

- has a `reset()` method that sets the count back to 0


<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function countCalls(fn) {
  let calls = 0;
  function wrapped(...args) {
    calls++;
    return fn.apply(this, args);

  wrapped.getCount = () => calls;
  wrapped.reset = () => {
    calls = 0;
  };
  return wrapped;
}
```

**Test**

```text
0 2

```

**Edge cases:**

- `this` is passed on with `apply`. That is why `wrapped` is a `function`, not an arrow.

**Common mistakes:** putting `calls++` after `fn.apply` (a throwing call is then not counted), or storing the count as `wrapped.count`, which anyone can overwrite.

## C22. Partial application vs currying · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Partial application:** fix *some* arguments of a function now and get back a function that takes the *rest*, all at once.

**Currying:** turn an n-argument function into a chain of functions that each take one argument: `f(a, b, c)` becomes `f(a)(b)(c)`. Practical "auto-curry" helpers also accept several arguments per step.

```js
const charge = (rate, qty, price) => rate * qty * price;

// partial application
const withRate = (rate) => (qty, price) => charge(rate, qty, price);
withRate(0.0003)(10, 1500);           // 4.5 (approximately, floating point)
const viaBind = charge.bind(null, 0.0003);  // also partial application

// currying
const curried = (rate) => (qty) => (price) => charge(rate, qty, price);
curried(0.0003)(10)(1500);
```

Both depend on **closures**. Each returned function remembers the arguments given so far.

**When to use:** configure a function once and reuse it (a logger with a tag, a formatter with a locale, an API client with a base URL). Currying also helps with point-free composition (`pipe`, `map`).

**Pitfalls:** `fn.length` ignores rest parameters and any parameter from the first default value onwards, so generic `curry` helpers can miscount arity. Deep currying makes stack traces harder to read.

**Interview tip:** "Currying always gives unary steps. Partial application fixes any number of arguments once."

**Takeaway:** both techniques use closures to remember earlier arguments. Currying is the stricter one-argument-at-a-time form.

</details>

## C23. Generic `curry(fn)` for any arity · `medium` · 💻 Coding

Implement `curry(fn, arity = fn.length)`. The curried function:

- collects arguments over one or more calls, each call taking any number of arguments
- calls `fn` as soon as it has at least `arity` arguments
- can be reused: a partially applied function must not share state between later calls

```js
const total = curry((price, qty, fee) => price * qty + fee);
total(100)(2)(5);   // 205
total(100, 2)(5);   // 205
total(100)(2, 5);   // 205
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function curry(fn, arity = fn.length) {
  return function curried(...args) {
    if (args.length >= arity) {
      return fn.apply(this, args);
    }
    return (...more) => curried.apply(this, args.concat(more));
  };
}
```

**Test**

```js
const total = curry((price, qty, fee) => price * qty + fee);
console.log(total(100)(2)(5), total(100, 2)(5), total(100)(2, 5), total(100, 2, 5));

const at100 = total(100);
console.log(at100(1)(0), at100(3)(0));

const sum4 = curry((a, b, c, d) => a + b + c + (d === undefined ? 0 : d));
console.log(sum4(1)(2)(3)(4), sum4(1, 2, 3, 4, 99));

console.log(curry(() => 42)());

function withDefault(a, b = 10) {
  return a + b;
}
console.log(withDefault.length, typeof curry(withDefault, 2)(1), curry(withDefault, 2)(1)(2));
```

**Output**

```text
205 205 205 205
100 300
10 10
42
1 function 3
```

**Approach:** `curried` checks how many arguments it has. If it has enough, it calls `fn`. If not, it returns a new arrow function that closes over the arguments so far (`args`) and calls `curried` again with the combined list. `args.concat(more)` builds a **new** array, so `at100(1)` and `at100(3)` do not affect each other.

**Edge cases:**
- Zero arity: `curry(() => 42)()` calls `fn` straight away.
- Extra arguments are passed on to `fn`. `sum4` ignores the 5th, so the result is still 10.
- `fn.length` stops at the first default or rest parameter (`withDefault.length === 1`), so the caller passes `arity` explicitly.

**Complexity:** O(n) to collect n arguments. Each step copies the argument array (O(n^2) in the worst case, which is fine for small arity).

**Common mistakes:** using `args.push(...)` on a shared array, which breaks reuse. Comparing with `===` instead of `>=`. Forgetting that a call with zero arguments returns another function unless arity is 0.

</details>

## C24. Shadowing and the TDZ inside closures · `medium` · 🖨️ Output

```js
const qty = 10;

function order() {
  const qty = 20;
  function fill() {
    const qty = 30;
    return () => qty;
  }
  return [fill()(), qty].join(',');
}
console.log(order(), qty);

let price = 100;
function quote() {
  try {
    return price;
  } catch (e) {
    return e.name;

```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text

ReferenceError
```

1. **Shadowing:** each scope declares its own `qty`. The arrow returned by `fill` finds the nearest one, which is 30. `order`'s own `qty` is 20. The global `qty` is still 10. The first line is `30,20 10`.

## C26. Memoization using closures · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Memoization** caches a function's results by input, so repeated calls return the cached result without recomputing. The cache must survive between calls but stay private, and a closure does exactly that.

```js
function memoize(fn) {
  const cache = new Map();          // private, persists across calls
  return function (n) {
    if (cache.has(n)) return cache.get(n);
    const value = fn(n);
    cache.set(n, value);
    return value;
  };
}
const slowRisk = (qty) => { /* heavy calculation */ return qty * 1.5; };
const risk = memoize(slowRisk);
```

**Rules:**
- Memoize only **pure** functions (same input gives the same output, with no side effects).
- Choose the key carefully. With several arguments, use `JSON.stringify(args)` or a custom resolver. Objects used as `Map` keys are compared by reference.
- Check with `cache.has`, not with a truthy check, so that `0`, `''` and `undefined` results are cached too.

**Pitfalls:**
- **Unbounded growth.** A cache keyed by price ticks grows forever. Add an LRU or TTL limit, or use a `WeakMap` for object keys.
- Stale data when the function secretly depends on outside state.

**React link:** `useMemo` and `React.memo` do the same thing per component, keyed on dependencies.

**Takeaway:** a memoizer is a closure over a private cache. Use it for pure functions and keep the cache bounded.

</details>

## C29. Closures and `this` · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Key rule:** closures capture **variables**. `this` is not a normal variable. A regular `function` gets its own `this` from **how it is called**, so an inner regular function does **not** see the outer function's `this`.

**Arrow functions** have no `this` of their own. They resolve `this` lexically, like any captured variable, from the surrounding function.

```js
const ticker = {
  symbol: 'INFY',
  start() {
    setTimeout(function () {
      console.log(this && this.symbol); // not the ticker: 'this' is lost
    }, 0);
    setTimeout(() => console.log(this.symbol), 0); // 'INFY'
    const self = this;                  // pre-ES6 fix
    setTimeout(function () { console.log(self.symbol); }, 0);
  },
};
```

**Fixes for losing `this` in callbacks:** an arrow function, `const self = this`, `.bind(this)`, or class fields with arrow functions (`handleClick = () => {}`).

**Pitfalls:**
- Arrow functions used as **object methods** get `this` from the outer scope (often module or global), not from the object.
- Arrow functions cannot be rebound with `call`, `apply` or `bind`.
- A method that returns an arrow function still depends on how *that method* was called.

**Takeaway:** regular functions get `this` from the call site, and arrow functions capture it lexically like a closed-over variable.

</details>

## C31. Private bank account with validation · `medium` · 💻 Coding

Implement `createAccount(owner, opening = 0)`. It returns a **frozen** object with:

- `getBalance()`
- `getHistory()`, which returns a **copy** of entries like `'D:500'` and `'W:200'`

```js
function createAccount(owner, opening = 0) {
  if (typeof opening !== 'number' || !Number.isFinite(opening) || opening < 0) {
    throw new RangeError('Invalid opening balance');

  let balance = opening;
  const history = [];

  function assertAmount(amount) {
    if (typeof amount !== 'number' || !Number.isFinite(amount) || amount <= 0) {
      throw new RangeError('Amount must be a positive number');
    }

  return Object.freeze({
    owner,
    deposit(amount) {
      assertAmount(amount);
      balance += amount;
      history.push('D:' + amount);
      return balance;

    withdraw(amount) {
      assertAmount(amount);
      if (amount > balance) throw new Error('Insufficient funds');
      balance -= amount;
      history.push('W:' + amount);
      return balance;

    getBalance() {
      return balance;
    },
    getHistory() {
      return history.slice();

  });
}
```

- Validate **before** changing anything, so a failed withdrawal leaves the balance and history unchanged.
- Reject strings (`'100'` would concatenate), `NaN`, `Infinity`, zero and negative numbers.
- `getHistory` returns a copy, so callers cannot rewrite the audit trail.

**Complexity:** O(1) per operation, plus O(n) for copying the history.

**Common mistakes:**
- Returning `history` itself.
- Using `this.balance`, which is public and breaks when the method is detached.
- Forgetting that floating-point money is unreliable. Real systems store paise as integers or use a decimal library.

</details>

## C32. Stack and Queue with private storage · `medium` · 💻 Coding

Implement two factories whose storage cannot be reached from outside:

- `createStack()` with `push(x)` (returns the size), `pop()`, `peek()`, `size()`, `isEmpty()`, and `toArray()` (returns a copy, bottom to top)
- `createQueue()` with `enqueue(x)` (returns the size), `dequeue()`, `peek()`, `size()`, and `isEmpty()`. `dequeue` must run in **O(1)**, so do not use `Array.prototype.shift`.

`pop`, `peek` and `dequeue` return `undefined` when the structure is empty.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createStack() {
  const items = [];
  return {
    push(x) {
      items.push(x);
      return items.length;
    },
    pop() {
      return items.pop();
    },
    peek() {
      return items[items.length - 1];
    },
    size() {
      return items.length;
    },
    isEmpty() {
      return items.length === 0;
    },
    toArray() {
      return items.slice();
    },
  };
}

function createQueue() {
  const store = new Map();
  let head = 0;
  let tail = 0;
  return {
    enqueue(x) {
      store.set(tail, x);
      tail++;
      return tail - head;
    },
    dequeue() {
      if (head === tail) return undefined;
      const x = store.get(head);
      store.delete(head);
      head++;
      return x;
    },
    peek() {
      return head === tail ? undefined : store.get(head);
    },
    size() {
      return tail - head;
    },
    isEmpty() {
      return head === tail;
    },
  };
}
```

**Test**

```js

console.log(s.isEmpty(), s.pop(), s.peek());
console.log(s.push('BUY'), s.push('SELL'), s.push('MODIFY'));
console.log(s.pop(), s.peek(), s.size());
const copy = s.toArray();
copy.push('HACK');
console.log(s.toArray().join('>'), typeof s.items);

const q = createQueue();
console.log(q.dequeue(), q.peek(), q.isEmpty());
console.log(q.enqueue('ORD-1'), q.enqueue('ORD-2'), q.enqueue('ORD-3'));
console.log(q.dequeue(), q.dequeue(), q.size());
q.enqueue('ORD-4');
console.log(q.peek(), q.size());
console.log(q.dequeue(), q.dequeue(), q.dequeue(), q.isEmpty());
q.enqueue(0);
console.log(q.peek(), q.size());
```

**Output**

```text
true undefined undefined
1 2 3
MODIFY SELL 2
BUY>SELL undefined
undefined undefined true
1 2 3
ORD-1 ORD-2 1
ORD-3 2
ORD-3 ORD-4 undefined true
0 1
```

**Approach:** each factory call creates its own private storage (`items` array, or a `Map` with `head`/`tail` pointers) that only the returned methods can reach.

**Why pointers for the queue:** `Array.prototype.shift` moves every remaining element down, which is O(n). Keeping a `head` index and deleting the dequeued entry makes `dequeue` O(1). Keys are never reused, so old entries never collide with new ones.

**Edge cases:**
- Empty `pop`, `peek` and `dequeue` return `undefined`.
- `peek` on an empty queue checks `head === tail` instead of trusting `store.get`.
- A falsy value (`0`) stored in the queue is still returned correctly.
- `toArray` returns a copy, so pushing to it does not change the stack.

**Complexity:** all operations are O(1), except `toArray`, which is O(n). Space is O(n).

**Common mistakes:** returning the internal array, using `shift` in hot paths (for example, a queue of order events), and checking emptiness with `!store.get(head)`, which breaks for falsy values.

</details>

## C33. Closures in event handlers and callbacks · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Every callback is a closure.** Event handlers, `setTimeout` callbacks, `.then` handlers and array callbacks can all use the variables around them, so you do not have to pass everything through arguments.

```js
function renderRow(order, rowEl) {
  const btn = rowEl.querySelector('.cancel');
  btn.addEventListener('click', () => {
    cancelOrder(order.id);          // 'order' captured per row
    rowEl.classList.add('muted');
  });
}

```

**Why it matters:** per-item context (`order`, `rowEl`) is attached to the right handler without `data-*` lookups or global state.

**Pitfalls:**
- **Removing listeners:** `removeEventListener` needs the *same* function reference. An inline arrow function cannot be removed later, so store it or use `AbortController` (`{ signal }`).
- **Memory:** a handler keeps everything it captured alive (DOM nodes, big arrays) until the listener is removed or the element is collected.
- **Stale values:** a handler created once keeps reading variables from that moment's scope. In React this is the "stale closure" problem.
- **Event delegation** (one listener on a parent) can be lighter than thousands of closures for large lists such as an option chain.

**Takeaway:** callbacks carry their context through closures. Keep a reference so you can remove them, and be careful about what they keep in memory.

## C36. Debounce with `cancel()` · `medium` · 💻 Coding

Implement `debounce(fn, wait)`:

- Every call restarts a `wait` ms timer. `fn` runs once, after calls have stopped for `wait` ms, with the **latest** arguments and `this`.
- `debounced.cancel()` drops any pending call.
- `debounced.pending()` returns `true` while a call is scheduled.

```js
const search = debounce((q) => console.log('search:', q), 50);
search('R'); search('RE'); search('REL');
// ~50 ms later → search: REL
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function debounce(fn, wait) {
  let timerId = null;
  let lastArgs;
  let lastThis;

  function debounced(...args) {
    lastArgs = args;
    lastThis = this;
    clearTimeout(timerId);
    timerId = setTimeout(() => {
      timerId = null;
      fn.apply(lastThis, lastArgs);
    }, wait);
  }

  debounced.cancel = () => {
    clearTimeout(timerId);
    timerId = null;
  };
  debounced.pending = () => timerId !== null;

  return debounced;
}
```

**Test**

```js
const search = debounce((q) => console.log('search:', q), 50);

search('R');
search('RE');
search('REL');
console.log('pending:', search.pending());

setTimeout(() => {
  search('TCS');
  search.cancel();
  console.log('pending after cancel:', search.pending());
}, 100);

const box = {
  label: 'watchlist',
  onType: debounce(function (q) {
    console.log(this.label + ' <- ' + q);
  }, 30),
};
setTimeout(() => {
  box.onType('IN');
  box.onType('INFY');
}, 130);

setTimeout(() => console.log('done'), 250);
```

**Output**

```text
pending: true
search: REL
pending after cancel: false
watchlist <- INFY
done
```

**Approach:** the closure holds `timerId` and the latest call context. Each call clears the old timer and starts a new one, so only the last call in a burst survives. `cancel` clears the timer and resets the state.

**Timeline:** at 0 ms, three calls leave one timer, and `fn` runs at about 50 ms with `'REL'`. At 100 ms, `'TCS'` is scheduled and cancelled straight away. At 130 ms, two quick calls on `box` run once at about 160 ms, with `this === box`.

**Edge cases:** keep `this` (use a `function` wrapper, not an arrow). Set `timerId = null` when the timer fires, so `pending()` stays accurate. `clearTimeout(null)` is safe.

**Complexity:** O(1) per call and O(1) space.

**Common mistakes:**
- Declaring `timerId` inside `debounced`, which creates a new variable each call, so nothing is ever cleared.
- Using the *first* call's arguments.
- Forgetting to cancel on component unmount, which leaks memory and can call `setState` on an unmounted component.

**Extensions:** `leading` and `trailing` options, `flush()`, `maxWait` (lodash).

</details>

## C37. Throttle with an injectable clock · `medium` · 💻 Coding

Implement `throttle(fn, interval, now = () => Date.now())` (leading edge):

- The first call runs `fn` straight away.
- After that, `fn` runs only when at least `interval` ms have passed since the **last run**. Calls in between are ignored and return `undefined`.
- Pass on `this` and the arguments, and return `fn`'s result when it runs.
- `now` can be injected so tests can use a fake clock.

```js
// interval 100, calls at t = 0, 10, 99, 100, 150, 250
// runs at 0, 100, 250
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function throttle(fn, interval, now = () => Date.now()) {
  let lastRun = -Infinity;
  return function (...args) {
    const t = now();
    if (t - lastRun >= interval) {
      lastRun = t;
      return fn.apply(this, args);
    }
    return undefined;
  };
}
```

**Test**

```js
let clock = 0;
const fakeNow = () => clock;

const ran = [];
const onTick = throttle((price) => {
  ran.push(clock + ':' + price);
  return 'rendered ' + price;
}, 100, fakeNow);

const results = [];
[[0, 1500], [10, 1501], [99, 1502], [100, 1503], [150, 1504], [250, 1505]].forEach(([t, p]) => {
  clock = t;
  results.push(String(onTick(p)));
});
console.log(ran.join(' | '));
console.log(results.join(','));

clock = 1000;
const chart = {
  id: 'NIFTY',
  redraw: throttle(function () {
    return this.id + ' redrawn';
  }, 50, fakeNow),
};
console.log(chart.redraw(), chart.redraw());

const realThrottled = throttle(() => 'ok', 1000);
console.log(realThrottled(), realThrottled());
```

**Output**

```text
0:1500 | 100:1503 | 250:1505
rendered 1500,undefined,undefined,rendered 1503,undefined,rendered 1505
NIFTY redrawn undefined
ok undefined
```

**Approach:** the closure stores `lastRun`, which starts at `-Infinity` so the first call always runs. Each call compares the current time with `lastRun`, and `lastRun` changes only when `fn` actually runs.

**Timeline (interval 100):** 0 runs. 10 and 99 are ignored (less than 100 since 0). 100 runs (exactly 100 counts). 150 is ignored. 250 runs (150 since 100).

**Why inject `now`:** tests become deterministic and fast, with no real waiting. The last two calls show that the default `Date.now` clock still works.

**Edge cases:** the boundary uses `>=`. `this` is passed on. The same logic works per instance (`chart.redraw`).

**Complexity:** O(1) per call.

**Common mistakes:** confusing throttle with debounce. Throttle runs at a steady rate *during* a burst, while debounce waits until the burst ends. Another mistake is starting `lastRun` at `0`, which skips the first call when the clock value is small.

**Extension:** a *trailing* option also schedules one final call with the latest arguments, so the last price tick is never lost. That is what live price widgets usually need.

</details>

## C39. Closures in async code · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**Rule:** a closure keeps a live link to a variable. An async callback (timer, promise, fetch, WebSocket message) reads that variable **when the callback runs**, which may be long after it was created.

```js
let selectedSymbol = 'INFY';
async function loadQuote() {
  const symbolAtRequest = selectedSymbol;          // snapshot
  const quote = await fetchQuote(symbolAtRequest);
  if (symbolAtRequest !== selectedSymbol) return;  // user switched: ignore stale response
  render(quote);
}
```

**Common bugs:**
- **Race conditions:** the user changes the selected symbol while a request is in flight, and the old response overwrites the new one. Take a snapshot and compare, use a request ID, or cancel with `AbortController`.
- **Loop + await:** `var` in a loop body shares one binding across awaits. Use `let`/`const`.
- **Stale closures:** a `setInterval` callback created once keeps seeing the variables from the moment it was created.

**Useful facts:**
- An `async` function keeps its local scope alive across `await` points. Local variables work normally after an `await`.
- `try/finally` inside the closure is the right place for cleanup, such as resetting a loading flag.

**Interview tip:** for a search box, explain "debounce + abort previous request + ignore stale responses". Closures are what make all three possible.

**Takeaway:** async callbacks read captured variables late. Snapshot what you need and guard against stale responses.

</details>

## C42. Closures, garbage collection and memory leaks · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**How GC relates to closures:** a variable in a captured environment stays alive as long as **any** closure that references that environment is reachable. The closure is kept alive by whatever holds it: a timer, a listener, a cache, or a global.

**Typical leaks:**
1. **Timers that are never cleared:** `setInterval(() => update(bigData), 1000)` keeps `bigData` alive forever.
2. **Listeners that are never removed** on `window`, `document` or a WebSocket, especially after a component unmounts.
3. **Large objects captured by accident:**
```js
function attach(btn) {
  const history = loadFullTickHistory();  // e.g. 50 MB
  const last = history[history.length - 1];
  btn.onclick = () => show(last);          // only needs 'last'
}
```
   Modern V8 keeps only the variables that inner functions actually use. However, **every closure created in the same scope shares one context object**. If *any* sibling closure (even an unused one) references `history`, it stays alive for all of them. Copy only what you need, or set `history = null`.
4. **Caches that grow forever** (memoize keyed by timestamp).
5. **Detached DOM nodes** kept alive by closures.

**Fixes:** `clearInterval` and `removeEventListener` in cleanup (React `useEffect` return), `AbortController` signals, `WeakMap`/`WeakRef` for per-object caches, bounded LRU caches, and setting large references to null.

**How to find leaks:** Chrome DevTools → Memory → compare heap snapshots and look at the "retainers" path through `(closure)` / `context`.

**Takeaway:** a closure is freed only when nothing references it, so clean up timers and listeners and avoid capturing large data.

</details>

## C43. Stale closures in React hooks · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

**What happens:** each render is a new function call with its own `props` and `state` constants. Handlers and effects created during a render close over **that render's** values. If a callback outlives its render (an interval, a subscription, a memoized callback with missing dependencies), it keeps using old values. This is a *stale closure*.

```jsx
function LivePnL() {
  const [ticks, setTicks] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setTicks(ticks + 1);        // BUG: 'ticks' is always 0 from the first render
    }, 1000);
    return () => clearInterval(id);
  }, []);                         // empty deps: the effect never sees new values
}
```

**Fixes:**
1. **Functional updater:** `setTicks((t) => t + 1)`. React passes the latest state, so nothing stale is read.
2. **Correct dependency arrays:** add `ticks` to the dependencies so the effect is recreated. Here that resets the interval on every tick, which is acceptable but noisy. Follow the `react-hooks/exhaustive-deps` lint rule.
3. **`useRef` for the latest value:** `latest.current = value` on every render, and callbacks read `latest.current`. A ref is a mutable box that stays the same across renders.
4. **`useReducer`:** `dispatch` never changes, and the reducer always gets the current state.
5. React 19.2's **`useEffectEvent`** creates effect-only handlers that always read the latest props and state.

**Pitfall:** `useCallback(fn, [])` gives you a stable reference but freezes the values `fn` sees.

**Takeaway:** hooks capture the values of one render. Use updater functions, correct dependencies or refs so long-lived callbacks see current data.

</details>

## C45. Closures vs class private fields (`#x`) · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

Both give **real** privacy, but they work differently.

```js
// closure-based
function createPosition(qty) {
  let _qty = qty;
  return { add(n) { _qty += n; }, get qty() { return _qty; } };
}

// class-based (ES2022)
class Position {
  #qty;
  constructor(qty) { this.#qty = qty; }
  add(n) { this.#qty += n; }
  get qty() { return this.#qty; }
  static isPosition(o) { return #qty in o; }   // brand check
}
```

| | Closures | `#private` fields |
|---|---|---|
| Methods | one copy **per instance** | shared on the prototype |
| Memory for many instances | higher | lower |
| `this` problems | none (no `this` needed) | detached methods lose `this` |
| Access from other instances | impossible | allowed inside the class body (`other.#qty`) |
| Inheritance / `instanceof` | no | yes |
| Accessing a missing field | not applicable | `TypeError` (brand check) |
| Works with `Proxy` | yes | a proxy has no private fields, so a method call through it throws |

**Which to choose:** use closures for small singletons, hooks-style utilities, and callbacks passed around without `bind`. Use `#fields` for many instances (for example, 10k order rows) and for class hierarchies.

**Pitfall:** `_underscore` properties are *not* private. TypeScript's `private` keyword is checked only at compile time.

**Takeaway:** both are truly private. Closures avoid `this` but copy methods per object. `#fields` share methods and support inheritance.

</details>

## C46. Sliding-window rate limiter · `hard` · 💻 Coding

Implement `createRateLimiter(limit, windowMs)`. It returns `tryAcquire(now)`, which:

- returns `true` and records the call if fewer than `limit` calls were allowed in the half-open window `(now - windowMs, now]`
- otherwise returns `false` and does **not** record the call

The timestamp `now` is passed in so tests are deterministic. Also write `createUserLimiter(limit, windowMs)`, which returns `(userId, now) => boolean` with a separate limit per user. Use closures for all state.

```js
const allow = createRateLimiter(3, 1000);
allow(0); allow(100); allow(200); // true true true
allow(300);                         // false
allow(1000);                        // true (the call at t=0 has expired)
```

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createRateLimiter(limit, windowMs) {
  const hits = []; // timestamps of allowed calls, oldest first
  return function tryAcquire(now) {
    while (hits.length > 0 && now - hits[0] >= windowMs) {
      hits.shift();
    }
    if (hits.length < limit) {
      hits.push(now);
      return true;
    }
    return false;
  };
}

function createUserLimiter(limit, windowMs) {
  const perUser = new Map();
  return function (userId, now) {
    if (!perUser.has(userId)) {
      perUser.set(userId, createRateLimiter(limit, windowMs));
    }
    return perUser.get(userId)(now);
  };
}
```

**Test**

```js
const allow = createRateLimiter(3, 1000);
const times = [0, 100, 200, 300, 999, 1000, 1050, 1100, 1200, 1201];
console.log(times.map((t) => t + ':' + (allow(t) ? 'Y' : 'N')).join(' '));

const orderApi = createUserLimiter(2, 500);
console.log(
  [
    orderApi('asha', 0),
    orderApi('asha', 10),
    orderApi('asha', 20),
    orderApi('ravi', 20),
    orderApi('ravi', 30),
    orderApi('ravi', 40),
    orderApi('asha', 500),
  ].join(',')
);

const none = createRateLimiter(0, 1000);
console.log(none(0), none(5000));
```

**Output**

```text
0:Y 100:Y 200:Y 300:N 999:N 1000:Y 1050:N 1100:Y 1200:Y 1201:N
true,true,false,true,true,false,true
false false
```

**Approach:** the closure keeps a list of allowed timestamps. On each call, drop entries that fall outside the window (`now - t >= windowMs`), then allow the call if there is room. Rejected calls are **not** recorded, so a client that keeps retrying does not lock itself out for longer.

**Trace (3 per 1000 ms):** 0, 100 and 200 are allowed. 300 and 999 are rejected (3 calls in the window). At 1000 the entry for 0 expires, so it is allowed. 1050 is rejected. At 1100 the entry for 100 expires, so it is allowed. At 1200 the entry for 200 expires, so it is allowed. 1201 is rejected.

**Per user:** a `Map` of limiters, each with its own closure. `asha` and `ravi` do not affect each other.

**Edge cases:** `limit = 0` always rejects. Timestamps are assumed never to go backwards.

**Complexity:** amortised O(1) per call, although `shift` is O(n) in the worst case (use a ring buffer or head index for large limits). Space is O(limit) per user.

**Alternatives:** a *fixed window* counter is cheaper but allows bursts at window edges. A *token bucket* allows controlled bursts. Real broker APIs (for example, orders per second) enforce limits on the server, and a client limiter only avoids making calls that would be rejected.

**Common mistakes:** recording rejected calls, using `>` instead of `>=` for expiry, and sharing one `hits` array between users.

</details>

## C47. Cache with TTL (time-to-live) · `hard` · 💻 Coding

Implement `createTTLCache(defaultTtl, now = () => Date.now())`. It returns an object with:

- `set(key, value, ttl = defaultTtl)`. The entry expires at `now() + ttl`.
- `get(key)` returns the value, or `undefined` if the key is missing or expired. Expired entries are deleted when read.
- `has(key)` returns a boolean and must be correct even when the stored value is `undefined`.
- `delete(key)`
- `size()` removes expired entries first, then returns the count.

An entry counts as expired when `now() >= expiresAt`. All state must be private.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createTTLCache(defaultTtl, now = () => Date.now()) {
  const store = new Map();

  function liveEntry(key) {
    const entry = store.get(key);
    if (!entry) return null;
    if (now() >= entry.expiresAt) {
      store.delete(key);
      return null;
    }
    return entry;
  }

  return {
    set(key, value, ttl = defaultTtl) {
      store.set(key, { value, expiresAt: now() + ttl });
    },
    get(key) {
      const entry = liveEntry(key);
      return entry ? entry.value : undefined;
    },
    has(key) {
      return liveEntry(key) !== null;
    },
    delete(key) {
      return store.delete(key);
    },
    size() {
      for (const key of [...store.keys()]) liveEntry(key);
      return store.size;
    },
  };
}
```

**Test**

```js
let t = 0;
const quotes = createTTLCache(1000, () => t);

quotes.set('NIFTY', 22000);
quotes.set('SENSEX', 73000, 5000);
quotes.set('EMPTY', undefined, 3000);

t = 500;
console.log(quotes.get('NIFTY'), quotes.size());

t = 1000;
console.log(quotes.get('NIFTY'), quotes.has('NIFTY'), quotes.has('SENSEX'));
console.log(quotes.has('EMPTY'), quotes.get('EMPTY'), quotes.size());

quotes.set('NIFTY', 22100);
t = 1999;
console.log(quotes.get('NIFTY'));

t = 3000;
console.log(quotes.has('EMPTY'), quotes.size());

console.log(quotes.delete('SENSEX'), quotes.delete('SENSEX'), quotes.size());

t = 10000;
quotes.set('BANKNIFTY', 48000, 0);
console.log(quotes.get('BANKNIFTY'), typeof quotes.store);
```

**Output**

```text
22000 3
undefined false true
true undefined 2
22100
false 1
true false 0
undefined undefined
```

**Approach:** a private `Map` stores `{ value, expiresAt }` entries. The helper `liveEntry` is the only place that checks expiry, and it deletes expired entries when they are read (*lazy expiration*). `has` checks whether an entry exists instead of looking at the value, so an `undefined` value is still reported correctly.

**Trace:** at t=1000, NIFTY (expires at 1000) is gone because the check uses `>=`. Setting NIFTY again at t=1000 makes it expire at 2000, so it is still there at 1999. EMPTY expires at 3000. By then NIFTY has also expired, so only SENSEX is left. A TTL of `0` means the entry is already expired.

**Why inject `now`:** tests are deterministic, and fake timers are not needed.

**Complexity:** `get`, `set`, `has` and `delete` are O(1). `size` is O(n). Memory is not freed for keys that are never read again, so production caches add a periodic sweep (`setInterval` that is cleared on dispose) or an LRU limit.

**Common mistakes:** using `get(key) !== undefined` for `has`, comparing with `>` at the boundary, storing `ttl` instead of an absolute `expiresAt`, and deleting from a `Map` while iterating a live iterator without understanding the effect (copying the keys first is simpler).

**Use case:** caching LTP/quote API responses for a few seconds to avoid repeated calls while the user switches tabs.

</details>

## C48. Closure-based pub/sub · `hard` · 💻 Coding

Implement `createPubSub()`. It returns an object with:

- `subscribe(topic, handler)`, which returns an `unsubscribe` function. That function returns `true` the first time and `false` after that. Subscribing the same handler twice creates two subscriptions.
- `publish(topic, payload)`, which calls every current subscriber and returns how many were called. A handler that throws must not stop the others. Log `handler error: <message>` instead. Handlers that unsubscribe during a publish must not affect who receives **that** publish.
- `subscriberCount(topic)`

The subscription registry must be private.

<details>
<summary><b>Solution & explanation</b></summary>

**Solution**

```js
function createPubSub() {
  const topics = new Map(); // topic -> Set of subscription records

  return {
    subscribe(topic, handler) {
      if (!topics.has(topic)) topics.set(topic, new Set());
      const subs = topics.get(topic);
      const record = { handler }; // unique object, so duplicate handlers are allowed
      subs.add(record);
      let active = true;
      return function unsubscribe() {
        if (!active) return false;
        active = false;
        subs.delete(record);
        if (subs.size === 0 && topics.get(topic) === subs) topics.delete(topic);
        return true;
      };
    },

    publish(topic, payload) {
      const subs = topics.get(topic);
      if (!subs) return 0;
      const snapshot = [...subs];
      snapshot.forEach((record) => {
        try {
          record.handler(payload);
        } catch (err) {
          console.log('handler error: ' + err.message);
        }
      });
      return snapshot.length;
    },

    subscriberCount(topic) {
      const subs = topics.get(topic);
      return subs ? subs.size : 0;
    },
  };
}
```

**Test**

```js
const bus = createPubSub();

const offA = bus.subscribe('price:INFY', (p) => console.log('A got ' + p));
const offB = bus.subscribe('price:INFY', (p) => {
  console.log('B got ' + p);
  offB(); // unsubscribe itself after the first message
});
bus.subscribe('price:INFY', () => {
  throw new Error('bad widget');
});

console.log('delivered:', bus.publish('price:INFY', 1500));
console.log('delivered:', bus.publish('price:INFY', 1510));
console.log(offA(), offA());
console.log('count:', bus.subscriberCount('price:INFY'));
console.log('delivered:', bus.publish('price:TCS', 3900));

let hits = 0;
const counter = () => hits++;
const off1 = bus.subscribe('tick', counter);
bus.subscribe('tick', counter);
bus.publish('tick');
off1();
bus.publish('tick');
console.log('hits:', hits, 'count:', bus.subscriberCount('tick'), typeof bus.topics);
```

**Output**

```text
A got 1500
B got 1500
handler error: bad widget
delivered: 3
A got 1510
handler error: bad widget
delivered: 2
true false
count: 1
delivered: 0
hits: 3 count: 1 undefined
```

**Approach:** `topics` is private to each bus. Every `unsubscribe` is its own closure over the specific `record`, its `subs` set and an `active` flag, so it removes exactly one subscription and works only once.

**Key details:**
- **Copy before publishing** (`[...subs]`): B unsubscribes during the first publish but still counts for that delivery (3). It is gone for the second (2).
- **Error isolation:** `try/catch` around each handler, so one broken widget cannot stop the price updates for the others.
- **Duplicate handlers:** each subscription gets its own wrapper object, so `counter` subscribed twice is called twice. Removing one subscription leaves the other: 2 + 1 = 3 hits.
- An empty topic is removed from the map to avoid leaks, but only if the map still points to the same set.

**Complexity:** subscribe and unsubscribe are O(1). Publish is O(k) for k subscribers.

**Common mistakes:** storing handlers directly in a `Set` (duplicates collapse), iterating the live set while handlers change it, an `unsubscribe` that removes *all* copies of a handler, and forgetting to unsubscribe in component cleanup, which is a classic closure memory leak.

</details>

## C49. Named function expression binding · `hard` · 🖨️ Output

```js
const factorial = function fact(n) {
  fact = null; // silently ignored in sloppy mode
  return n <= 1 ? 1 : n * fact(n - 1);
};
console.log(factorial(4));

const strictOne = function inner() {
  'use strict';
  try {
    inner = 1;
  } catch (e) {
    return e.name;
  }
  return 'assigned';
};
console.log(strictOne());
console.log(typeof fact, typeof inner);
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
24
TypeError
undefined undefined
```

1. A **named function expression** gets a special scope between the function and its outer scope. That scope contains one **immutable** binding, the function's own name (`fact`), which the function closes over.
2. In sloppy mode, assigning to that immutable binding is **silently ignored**, so `fact` still refers to the function and the recursion works: 4·3·2·1 = 24.
3. In strict mode, the same assignment throws a `TypeError`. The `catch` returns its name.
4. The name is visible **only inside** the function. In the outer scope `fact` and `inner` are undeclared, and `typeof` on an undeclared name returns `'undefined'` without throwing.

**Takeaway:** a function expression's own name is a private, read-only binding that only its body can see, which makes it safe to use for recursion.

</details>

## C50. Closures in default parameters get their own scope · `hard` · 🖨️ Output

```js
var x = 'global';

function f(read = () => x) {
  var x = 'body';
  return read() + ' / ' + x;
}
console.log(f());

function g(y, read = () => y) {
  var y = 'body';
  return read() + ' / ' + y;
}
console.log(g('param'));

function h(z, write = (v) => { z = v; }) {
  write('changed');
  return z;
}
console.log(h('original'));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
global / body
param / body
changed
```

1. When a function has default-value expressions, the spec evaluates the parameters in **their own scope**, and the body's `var` declarations get a **separate** scope.
2. In `f`, the default arrow is created in the parameter scope. `x` is not a parameter, so the lookup goes to the global `x` and never sees the body's `var x`. Result: `global / body`.
3. In `g`, `y` **is** a parameter. The body's `var y` is a new binding that starts with a copy of the parameter's value and is then set to `'body'`. The arrow still reads the parameter binding, which is `'param'`.
4. In `h`, there is no `var z` in the body, so the body and the arrow both use the **parameter** binding. The write is visible and the function returns `changed`.

**Takeaway:** closures in default parameters capture the parameter scope, not the variables declared in the function body.

</details>

## C51. Performance considerations of closures · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

Closures are cheap in modern engines, but they do cost something.

**Costs:**
- **Allocation:** each time a closure is created, the engine allocates a function object, plus a context object if the scope has captured variables. Creating closures inside hot loops or on every render can add GC pressure.
- **Memory retention:** captured variables live as long as the closure. V8 puts only the *captured* variables into a heap "context", but closures from the same scope share it (see the memory-leak question).
- **Methods per instance:** factory functions create N copies of each method, while class or prototype methods are shared.
- **Identity changes:** a new inline callback on every render breaks `React.memo` and dependency checks, which causes extra re-renders. This is often a bigger cost than the allocation itself.

**Usually fine:** calling a closure is as fast as calling a normal function. Reading a captured variable is a small, constant-cost context lookup.

**Practical guidance for a trading UI:**
- Use one delegated listener for a large option-chain table instead of 5,000 row closures.
- Keep callbacks stable with `useCallback` only when a memoized child or an effect needs it.
- Move pure helpers out of components so they are not recreated on every render.
- Measure with the Performance and Memory panels before you optimise.

**Interview tip:** say "readability first; closures cost allocation and retained memory, so I watch out for them in hot paths and long-lived callbacks."

**Takeaway:** closures are fast to call, but creating them repeatedly and keeping large scopes alive can hurt performance.

</details>

## C52. Closures in middleware and function composition · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

Middleware systems (Redux, Express, Koa, axios interceptors) are built from **nested closures** that capture configuration and the next step in the chain.

```js
function applyMiddleware(dispatch, ...middlewares) {
  // compose from right to left: each layer captures the 'next' below it
  return middlewares.reduceRight((next, mw) => mw(next), dispatch);
}

const logger = (tag) => (next) => (action) => {
  console.log(tag, 'before', action.type);
  const result = next(action);           // 'next' and 'tag' come from closures
  console.log(tag, 'after', action.type);
  return result;
};

const riskCheck = (maxQty) => (next) => (action) =>
  action.qty > maxQty ? 'BLOCKED' : next(action);

const send = applyMiddleware(
  (a) => 'SENT ' + a.type,
  logger('[order]'),
  riskCheck(1000)
);
send({ type: 'BUY', qty: 5 });    // logs before/after, returns 'SENT BUY'
send({ type: 'BUY', qty: 5000 }); // 'BLOCKED'
```

**What each closure holds:** `tag` and `maxQty` (config), `next` (the rest of the pipeline), and in Redux also `store` (`getState`, `dispatch`).

**Why it is designed this way:** each layer is independent and reusable. The order is set once when the chain is built, and each call is just nested function calls.

**Pitfalls:** calling `next` twice or never, confusing `reduce` with `reduceRight` (execution order), and capturing `store.getState()` once instead of calling it when needed (a stale value).

**Takeaway:** middleware is curried closures. Each layer remembers its config and the `next` function below it.

</details>

## C53. Common closure interview traps · `hard` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

A checklist of traps interviewers like to use:

1. **`var` in loops with async callbacks** prints the final value N times. Fix with `let`, an IIFE, or extra `setTimeout` arguments.
2. **A `let` declared outside the loop** still gives one shared binding.
3. **Captured variable vs value:** a closure reads the *current* value. Pass it as a parameter to take a snapshot. Objects are still shared by reference.
4. **Assuming a call is shared state:** `makeCounter()()` twice creates two counters.
5. **`this` is not captured** by regular functions. Arrow functions inherit it from where they are created.
6. **Scope depends on where code is written, not where it is called.**
7. **Shadowing and the TDZ:** a later `let x` in the same scope makes an earlier `x` read throw, even when an outer `x` exists.
8. **Calling instead of passing:** `setTimeout(log(i), 100)` runs `log` immediately.
9. **Stale closures** in hooks and intervals. Use functional updates or refs.
10. **Memory leaks:** timers and listeners that are never removed keep captured data alive.
11. **Default-parameter scope** is separate from body `var`s.
12. **`once`/`memoize` with falsy results:** use a flag or `has`, not a truthy check.

```js
const fns = [];
for (var i = 0; i < 3; i++) fns[i] = () => i;
fns[0](); // 3, not 0
```

**How to answer:** say the rule first ("one binding vs per-iteration bindings"), then trace the values step by step, then give the fix. Interviewers care more about the reasoning than the final number.

**Takeaway:** almost every closure trap comes down to *which binding* is captured and *when* it is read.

</details>
