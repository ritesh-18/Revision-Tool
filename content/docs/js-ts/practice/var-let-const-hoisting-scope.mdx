> Hoisting, the Temporal Dead Zone, block vs function scope, redeclaration rules and loop bindings.

## V1. `var` vs `let` vs `const`: the comparison table · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

| Feature | `var` | `let` | `const` |
|---|---|---|---|
| Scope | Function (or script/global) | Block `{ }` | Block `{ }` |
| Hoisted? | Yes, initialised to `undefined` | Yes, but **uninitialised** (TDZ) | Yes, but **uninitialised** (TDZ) |
| Access before declaration | `undefined` | `ReferenceError` | `ReferenceError` |
| Re-declare in same scope | Allowed | `SyntaxError` | `SyntaxError` |
| Re-assign | Allowed | Allowed | `TypeError` |
| Must initialise | No | No | **Yes** (`const x;` is a SyntaxError) |
| Top-level in a browser classic script | Becomes `window` property | Not on `window` | Not on `window` |
| Fresh binding per loop iteration | No | Yes | Yes (`for...of` / `for...in`) |

```js
function demo() {
  if (true) {
    var a = 1;   // function-scoped
    let b = 2;   // block-scoped
    const c = 3; // block-scoped, cannot be reassigned
  }
  console.log(a);        // 1
  console.log(typeof b); // "undefined" (b is not in scope here)
}
```

`const` makes the **binding** constant, not the value: `const order = {}` still allows `order.qty = 5`.

**Takeaway:** Default to `const`, use `let` when you must reassign, and avoid `var` in new code.

</details>

## V2. What exactly is hoisting? · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

Before running any code in a scope, the engine does a **creation phase**: it scans the scope and creates bindings for every declaration. "Hoisting" is the name for this behaviour — the code does not move; the bindings simply exist from the start of the scope.

| Declaration | Binding created at scope start? | Initial value |
|---|---|---|
| `var x` | Yes | `undefined` |
| `function f() {}` | Yes | The whole function object |
| `let x` / `const x` | Yes | *uninitialised* (TDZ) |
| `class C {}` | Yes | *uninitialised* (TDZ) |
| `var f = function () {}` | Only `f`, as `undefined` | Function assigned later |
| `import` | Yes (module) | Live binding, ready before code runs |

```js
console.log(total);  // undefined   (var)
console.log(greet()); // "hi"       (function declaration)
var total = 10;
function greet() { return 'hi'; }
```

The engine treats this as:
```js
function greet() { return 'hi'; }
var total;
console.log(total);
console.log(greet());
total = 10;
```

Only **declarations** are hoisted, never **assignments**.

**Takeaway:** Every declaration is hoisted; what differs is whether the binding starts as `undefined`, the full function, or uninitialised.

</details>

## V3. Temporal Dead Zone (TDZ) explained · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

The **TDZ** is the time between entering a scope and the line where a `let`/`const`/`class` declaration is evaluated. During that time the binding exists but is uninitialised, and **any** read or write throws a `ReferenceError`.

```js
{
  // TDZ for "qty" starts here
  console.log(typeof qty); // ReferenceError — even typeof throws
  let qty = 5;             // TDZ ends here
  console.log(qty);        // 5
}
```

Key points:
- It is **temporal** (about time), not spatial. A function declared *above* the `let` can read it, as long as it is **called** after the declaration runs.
- `typeof undeclaredName` returns `"undefined"`, but `typeof` on a TDZ binding throws.
- `let x = x;` throws, because the right side runs while `x` is still in the TDZ.
- Default parameters have their own TDZ: `function f(a = b, b = 1)` throws when `a` needs its default.
- V8 message: `Cannot access 'qty' before initialization`. Firefox says `can't access lexical declaration 'qty' before initialization`; Safari uses different wording again.

Why it exists: it catches bugs where a value is used before it is set, and gives `const` a sensible meaning (it can never be observed as `undefined` first).

**Takeaway:** `let`/`const`/`class` are hoisted but unusable until their declaration line runs.

</details>

## V4. Block scope vs function scope · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

| Construct | Creates a scope for `var`? | Creates a scope for `let`/`const`? |
|---|---|---|
| `function` body | Yes | Yes |
| `{ ... }` block, `if`, `else` | No | Yes |
| `for (let i ...)` | No | Yes (plus a fresh copy per iteration) |
| `switch` body | No | Yes, **one** block shared by all `case`s |
| `try` / `catch` blocks | No | Yes |
| Module file | Yes (module scope) | Yes |

```js
function report() {
  for (var i = 0; i < 2; i++) {}
  for (let j = 0; j < 2; j++) {}
  console.log(i);        // 2 — var leaked out of the loop
  console.log(typeof j); // "undefined" — j stayed inside
}
```

Before ES6, developers used an IIFE, `(function () { ... })()`, to get a private scope. With `let`/`const` a plain block is enough.

**Takeaway:** `var` only respects function boundaries; `let`/`const` respect every pair of braces.

</details>

## V5. Global `var` in browser scripts vs modules vs Node · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

Where a top-level declaration ends up depends on how the file is loaded:

| Environment | Top-level `var x` / `function f` | Top-level `let` / `const` / `class` |
|---|---|---|
| Browser classic `<script>` | Property of `window` (`window.x`) | Global, but **not** on `window` (declarative record) |
| Browser `<script type="module">` | Module-scoped, not on `window` | Module-scoped |
| Node CommonJS file | Local to the module wrapper function | Local to the module |
| Node ES module | Module-scoped | Module-scoped |

```html
<script>
  var broker = 'Angel';
  let app = 'SmartAPI';
  console.log(window.broker); // "Angel"
  console.log(window.app);    // undefined
</script>
```

Consequences in the browser:
- A global `var name` can clash with the existing `window.name` property (always a string).
- Two classic scripts share the same global scope, so their `var`s can overwrite each other; a `let` re-declared in a second script throws a SyntaxError.
- `var` globals cannot be removed with `delete`.

In Node's CommonJS each file is wrapped in a function, so top-level `var` is **not** on `globalThis`.

**Takeaway:** Only classic browser scripts put `var` on `window`; modules keep everything private.

</details>

## V6. Function declarations vs function expressions vs arrows · `medium` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

| Form | Hoisted as | Callable before its line? |
|---|---|---|
| `function f() {}` | Full function | Yes |
| `var f = function () {}` | `f = undefined` | No — `TypeError: f is not a function` |
| `let f = () => {}` / `const f = ...` | Uninitialised | No — `ReferenceError` (TDZ) |
| `var f = function g() {}` | `f = undefined`; `g` exists only inside the function | No |
| `class C {}` | Uninitialised | No — `ReferenceError` |

Name conflicts in one scope, in the creation phase:
1. Parameters are bound first.
2. Function declarations are bound next and **override** a parameter or `var` with the same name (the last declaration of that name wins).
3. `var` declarations with the same name are ignored, because the name already exists.
4. Then the code runs, and any **assignment** replaces the function.

```js
console.log(typeof fee); // "function"
var fee = 20;
function fee() {}
console.log(typeof fee); // "number"
```

A named function expression's name (`g` above) is a read-only binding inside its own body.

**Takeaway:** Only function declarations are usable before their line; expressions follow the rules of the variable that holds them.

</details>

## V7. Best practices for declarations · `easy` · 🧠 Concept

<details>
<summary><b>Answer</b></summary>

1. **`const` by default**, `let` when reassignment is needed, **no `var`** (ESLint: `prefer-const`, `no-var`).
2. **Declare at the top of the block** where the variable is used, so you never read one in the TDZ.
3. **Keep scopes small**: declare loop counters with `for (let i ...)`, not outside the loop.
4. **Always use strict mode** (ES modules and classes already are). It turns implicit globals into errors and keeps block-level functions block-scoped.
5. **Don't depend on hoisting** for readability. Define helpers before use, or call them from an entry function at the bottom.
6. **Don't declare functions inside `if` blocks** in sloppy code. Their Annex B behaviour is legacy and confusing. Use `const fn = ...` instead.
7. **`const` does not freeze** the value. Use `Object.freeze` (shallow) or immutable update patterns, for example for a Redux order-book state.
8. **Avoid shadowing** outer names (ESLint: `no-shadow`), especially names like `name`, `status` and `event` that are browser globals.

```js
// good
const MAX_QTY = 500;
let filled = 0;
for (const order of orders) {
  filled += order.qty;
}
```

**Takeaway:** `const` first, `let` if needed, strict mode always, and declare before use.

</details>

## V8. `var` is hoisted as `undefined` · `easy` · 🖨️ Output

```js
console.log(ltp);
var ltp = 2950;
console.log(ltp);
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
undefined
2950
```

How the engine sees it:
```js
var ltp;          // declaration hoisted, value undefined
console.log(ltp); // undefined
ltp = 2950;       // assignment stays where it was
console.log(ltp); // 2950
```
- Line 1: the binding exists but has not been assigned yet, so it prints `undefined`.
- Line 2: the assignment has run, so it prints `2950`.

**Takeaway:** `var` declarations are hoisted; their assignments are not.

</details>

```js
try {
  console.log(margin);
} catch (e) {
  console.log(e.message);
}
try {
  console.log(brokerage);
} catch (e) {
  console.log(e.message);
}

```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
margin is not defined
Cannot access 'brokerage' before initialization
```

- `margin` is not declared anywhere, so the lookup fails: `margin is not defined`.
- `brokerage` **is** declared (with `const`, further down). The binding exists but is in the TDZ, so the message is `Cannot access 'brokerage' before initialization`.

Both are `ReferenceError`s, but the message tells you which case you hit. Firefox and Safari word them differently.

</details>

## V11. `typeof` does NOT protect you in the TDZ · `medium` · 🖨️ Output

```js
console.log(typeof notDeclared);
try {
  console.log(typeof orderId);
} catch (e) {
  console.log(e.name);
}
let orderId = 101;
console.log(typeof orderId);
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
undefined
ReferenceError
number
```

- `typeof notDeclared`: no binding exists, so the result is `"undefined"`.
- `typeof orderId`: a binding **does** exist (from `let`), but it is uninitialised. The TDZ check happens before `typeof` gets the value, so it throws a `ReferenceError`, which the catch block logs.
- After `let orderId = 101` runs, `typeof orderId` is `number`.

**Takeaway:** `typeof` only protects against names that are not declared at all, not against names in the TDZ.

</details>

## V12. Function expression with `var`: TypeError · `easy` · 🖨️ Output

```js
console.log(typeof placeOrder);
placeOrder();
var placeOrder = function () {
  console.log('placed');
};
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
undefined
Uncaught TypeError: placeOrder is not a function
```

How the engine sees it:
```js
var placeOrder;                  // undefined
console.log(typeof placeOrder);  // "undefined"
placeOrder();                    // calling undefined
placeOrder = function () { ... };
```
- Only the `var` is hoisted, so the first line prints `undefined`.
- Calling `undefined` throws `TypeError: placeOrder is not a function`. It is a **TypeError**, not a ReferenceError, because the variable exists. Its value is just the wrong type.

**Takeaway:** A function expression stored in a `var` is `undefined` until the assignment runs.

</details>

## V15. `var` without initializer does not overwrite a function · `medium` · 🖨️ Output

```js
var segment;
function segment() {
  return 'NSE';
}
var segment;
console.log(typeof segment);
console.log(segment());
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
function
NSE
```

Both `var segment;` lines are declarations **without assignment**. Hoisting turns them into no-ops, because `segment` already exists and holds the function.
- `typeof segment` is `function`.
- `segment()` returns `NSE`.

Only an actual assignment (`segment = ...`) would replace the function.

**Takeaway:** Redeclaring with `var` never resets a value; only assignments change it.

</details>

## V16. Local `var` in an `if (false)` still shadows · `medium` · 🖨️ Output

```js
var symbol = 'NIFTY';
function showSymbol() {
  console.log(symbol);
  if (false) {
    var symbol = 'SENSEX';
  }
  console.log(symbol);
}
showSymbol();
console.log(symbol);
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
undefined
undefined
NIFTY
```

`var` ignores blocks, and hoisting happens even when a block never runs. How the engine sees `showSymbol`:
```js
function showSymbol() {
  var symbol;           // local, shadows the global
  console.log(symbol);  // undefined
  if (false) { symbol = 'SENSEX'; } // never runs
  console.log(symbol);  // undefined
}
```
- Lines 1 and 2: the local `symbol` shadows the outer one and is never assigned.
- Line 3: outside the function, the outer `symbol` is still `NIFTY`.

**Takeaway:** A `var` anywhere in a function, even in unreachable code, creates a local binding for the whole function.

</details>

## V17. Hoisting inside a nested function · `medium` · 🖨️ Output

```js
var count = 10;
function outer() {
  console.log(count);
  function inner() {
    console.log(count);
    var count = 5;
    console.log(count);
  }
  inner();
  console.log(count);
}
outer();
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
10
undefined
5
10
```

- `outer` has no local `count`, so it reads the outer one: `10`.
- `inner` declares `var count`, which is hoisted to the top of `inner`:
```js
function inner() {
```

- Back in `outer`, the outer `count` was never changed: `10`.

</details>

## V18. Parameter, `var` and function declaration share one name · `hard` · 🖨️ Output

```js
function calc(price) {
  console.log(typeof price);
  var price = 10;
  console.log(price);
  function price() {}
  console.log(price);
}

```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
function
10
10
```

Creation phase for `calc(5)`:
1. Parameter `price = 5`.
2. Function declaration `price` **replaces** that value with the function.

```js
function calc(price) {
```

## V24. `switch` cases share one block · `medium` · 🖨️ Output

```js
function label(code) {
  switch (code) {
    case 1:
      let side = 'BUY';
      return side;
    case 2:
      side = 'SELL';
      return side;
  }
}
console.log(label(1));
console.log(label(2));
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
BUY
Uncaught ReferenceError: Cannot access 'side' before initialization
```

The whole `switch` body is **one** block, so `side` belongs to all cases.
- `label(1)`: the `let` line runs, and `side` is initialised to `BUY`.
- `label(2)`: execution jumps straight to `case 2` and skips the `let` line. `side` is declared in this block but was never initialised in this call, so assigning to it throws a TDZ `ReferenceError`.

Fix: wrap each case body in its own braces: `case 1: { let side = ...; }`.

**Takeaway:** `let` in a `case` is scoped to the whole `switch`; use braces per case.

</details>

## V25. Same `let` name in two `case`s: SyntaxError · `medium` · 🖨️ Output

```js
try {
  new Function("switch (1) { case 1: let msg = 'a'; break; case 2: let msg = 'b'; }");
} catch (e) {
  console.log(e.name);
  console.log(e.message);
}
try {
  new Function("switch (1) { case 1: { let msg = 'a'; break; } case 2: { let msg = 'b'; } }");
  console.log('braces OK');
} catch (e) {
  console.log(e.name);
}
```

<details>
<summary><b>Output & explanation</b></summary>

**Output**

```text
SyntaxError
Identifier 'msg' has already been declared
braces OK
```

`new Function(...)` parses its source at runtime, so we can catch the parse error. Written directly in the file, this error would stop the whole script before anything runs.
- First body: both `let msg` are in the **same** switch block, so parsing fails with `SyntaxError: Identifier 'msg' has already been declared` (V8 wording).
- Second body: each case has its own `{ }` block, so the two `msg` bindings are separate and parsing succeeds.

**Takeaway:** Redeclaring a `let` in one block is a parse-time SyntaxError; braces per `case` avoid it.

</details>

## V27. Redeclaring `let` or mixing `var`/`let` · `medium` · 🖨️ Output

```js
const sources = [
  'let a = 1; let a = 2;',
  'var b = 1; let b = 2;',
  'const c = 1; var c = 2;',
  'var d = 1; var d = 2;',
];
for (const src of sources) {
  try {
    new Function(src);
    console.log('ok');
  } catch (e) {
    console.log(e.name + ': ' + e.message);
```
