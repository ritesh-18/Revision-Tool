Python has a small set of syntax and built-in functions (`len(x)`, `a + b`, `x[i]`, `x in y`, `for`, `with`, `f(...)`, `==`, `if x:`) and a large, documented contract that says which **special method** each of them calls. That contract is the **data model**. Special methods have double underscores on both sides, so people call them "dunder" methods (`__len__` reads "dunder len").

Learn the contract and you can make your own classes behave exactly like built-in types: summable, sortable, sliceable, hashable, usable in `with` and `for`. This is how NumPy arrays support `a @ b`, how Pydantic models compare with `==`, and how SQLAlchemy builds `User.age > 18` into SQL.

<Callout title="Version note">
  Every snippet on this page was run with **CPython 3.14.6**. One 3.14 change matters here: using `NotImplemented` in a boolean context now raises `TypeError` (it was deprecated in 3.9).
</Callout>

## Syntax is sugar for special methods

### What it is

Each piece of syntax is translated into a call of a dunder method **looked up on the type** of the operand:

| You write | Python calls (roughly) |
|---|---|
| `len(x)` | `type(x).__len__(x)` |
| `x[k]`, `x[k] = v`, `del x[k]` | `__getitem__`, `__setitem__`, `__delitem__` |
| `v in x` | `__contains__`, else iterate with `__iter__`, else `__getitem__` |
| `for v in x` | `iter(x)` calls `__iter__`, then `__next__` repeatedly |
| `a + b` | `a.__add__(b)`, else `b.__radd__(a)` |
| `a += b` | `a.__iadd__(b)`, else falls back to `a + b` |
| `a == b`, `a < b` | `__eq__`, `__lt__` (with reflected fallbacks) |
| `hash(x)`, dict keys, set members | `__hash__` |
| `if x:`, `bool(x)` | `__bool__`, else `__len__`, else `True` |
| `f(...)` | `type(f).__call__(f, ...)` |
| `x.attr` | `__getattribute__`, then `__getattr__` on failure |
| `x.attr = v` | `__setattr__` |
| `with x:` | `__enter__` / `__exit__` |
| `repr(x)`, `str(x)`, `format(x, spec)` | `__repr__`, `__str__`, `__format__` |

```python
nums = [3, 1, 2]
print(len(nums), type(nums).__len__(nums))
print(nums[0], type(nums).__getitem__(nums, 0))
print(2 in nums, type(nums).__contains__(nums, 2))
print(1 + 2, (1).__add__(2))
print(str(nums) == type(nums).__repr__(nums))
```

```text title="Output"
3 3
3 3
True True
3 3
True
```

### How it works underneath

For built-in types, CPython does not look these methods up by name at all. Every type object has C-level **slots** (`tp_as_sequence->sq_length`, `tp_as_number->nb_add`, `tp_richcompare`, `tp_hash`, `tp_call`...). `len(x)` reads `type(x)`'s length slot and calls the C function directly, which is why `len()` on a list is fast. When **you** define `__len__` in a Python class, `type` fills the slot with a small wrapper that calls your Python method. Either way, the interpreter goes through the **type**, never the instance. That detail has consequences, covered [at the end](#why-special-method-lookup-bypasses-the-instance).

You should **call the built-in**, not the dunder: write `len(x)`, not `x.__len__()`. The built-ins add checks (for example `len` insists on a non-negative `int`) and the operators implement the fallback dance between both operands.

<Callout title="Coming from JS">
  JS has a handful of hooks of this kind: `Symbol.iterator` (for `for...of`), `Symbol.toPrimitive` and `valueOf` (for `+` and comparisons), `toString`, `Symbol.hasInstance`, and `Proxy` traps. But JS has **no operator overloading**: `a + b` on two objects always coerces to primitives. Python lets a class define what `+`, `==`, `[]`, `in` and calling mean, which is why `Decimal`, `datetime`, `pathlib.Path` (`base / "file.txt"`) and NumPy feel like part of the language.
</Callout>

## Containers: `__len__`, `__getitem__`, `__contains__`

### Sequence protocol with two methods

Implement `__len__` and `__getitem__` and you get a surprising amount for free:

```python
class Deck:
    ranks = "23456789TJQKA"
    suits = "SHDC"

    def __init__(self):
        self._cards = [r + s for s in self.suits for r in self.ranks]

    def __len__(self):
        return len(self._cards)

    def __getitem__(self, index):
        return self._cards[index]

d = Deck()
print(len(d))
print(d[0], d[-1])
print(d[:3])                    # slicing for free: index is a slice object
print("AS" in d, "ZZ" in d)     # `in` falls back to iteration via __getitem__
print(list(reversed(d))[:2])    # reversed uses __len__ + __getitem__
import random
random.seed(1)
print(random.choice(d))
for card in d[:2]:
    print("card", card)
```

```text title="Output"
52
2S AC
['2S', '3S', '4S']
True False
['AC', 'KC']
TS
card 2S
card 3S
```

Iteration works because, with no `__iter__`, `iter()` falls back to the **old sequence protocol**: call `__getitem__(0)`, `__getitem__(1)`, ... until `IndexError`. Modern code should define `__iter__` explicitly; see [iterators and iterables](/docs/python/iterators-and-iterables).

### What `__getitem__` actually receives

The brackets pass whatever is inside them as **one** object. Slices become `slice` objects, and commas build a tuple:

```python
class Probe:
    def __getitem__(self, key):
        return key

p = Probe()
print(p[3])
print(p[1:10:2])
print(p[::-1])
print(p["user", 42])
print(p[1:2, ::3])
```

```text title="Output"
3
slice(1, 10, 2)
slice(None, None, -1)
('user', 42)
(slice(1, 2, None), slice(None, None, 3))
```

That is how NumPy supports `arr[1:3, ::2]` and pandas supports `df.loc["a", "col"]`. Dict-like classes get the key as is; for missing keys raise `KeyError`, and for sequences raise `IndexError` (that is what stops the fallback iteration).

### `__contains__`: make `in` fast

Without `__contains__`, `in` does a linear scan using iteration. Define it when you can answer faster:

```python
class Range10:
    def __iter__(self):
        print("  (iterating)")
        return iter(range(10))

class FastRange10(Range10):
    def __contains__(self, x):
        print("  (O(1) check)")
        return isinstance(x, int) and 0 <= x < 10

print(7 in Range10())
print(7 in FastRange10())
print(list(FastRange10())[:3])
```

```text title="Output"
  (iterating)
True
  (O(1) check)
True
  (iterating)
[0, 1, 2]
```

<Callout title="Coming from JS">
  Python's `in` asks "is this value in the container" (`array.includes(x)`, `set.has(x)`, `map.has(k)` for dicts). It is **not** JS's `in`, which checks for a property key. `"length" in []` is `true` in JS; in Python `"append" in []` is just `False`.
</Callout>

If you are building a full container, inherit from `collections.abc.Sequence` or `MutableMapping`: implement the few abstract methods and the ABC supplies `__contains__`, `__iter__`, `index`, `count`, `get`, `items` and so on. See [ABCs and protocols](/docs/python/abcs-and-protocols).

## Arithmetic operators and `NotImplemented`

### How `a + b` is evaluated

1. If `type(b)` is a **subclass** of `type(a)` and overrides `__radd__`, try `b.__radd__(a)` first (so subclasses can take control).
2. Otherwise try `a.__add__(b)`.
3. If that is missing or returns the special singleton **`NotImplemented`**, try `b.__radd__(a)` (the "reflected" method), if the types differ.
4. If that also is missing or returns `NotImplemented`, raise `TypeError: unsupported operand type(s)`.

`NotImplemented` is not an error; it is a return value meaning "I don't know how to handle this type, ask the other operand". Never **raise** `NotImplementedError` from an operator method; that stops the negotiation.

```python
class Money:
    def __init__(self, cents, currency="EUR"):
        self.cents = cents
        self.currency = currency

    def __repr__(self):
        return f"Money({self.cents}, {self.currency!r})"

    def __add__(self, other):
        print(f"  {self!r}.__add__({other!r})")
        if isinstance(other, Money):
            if other.currency != self.currency:
                raise ValueError("currency mismatch")
            return Money(self.cents + other.cents, self.currency)
        if other == 0:                 # lets sum() start from 0
            return self
        return NotImplemented

    def __radd__(self, other):
        print(f"  {self!r}.__radd__({other!r})")
        return self.__add__(other)

a, b = Money(500), Money(250)
print(a + b)
print(0 + a)                           # int.__add__ fails, so Money.__radd__ runs
print(sum([a, b, Money(5)]))
try:
    a + "oops"
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
  Money(500, 'EUR').__add__(Money(250, 'EUR'))
Money(750, 'EUR')
  Money(500, 'EUR').__radd__(0)
  Money(500, 'EUR').__add__(0)
Money(500, 'EUR')
  Money(500, 'EUR').__radd__(0)
  Money(500, 'EUR').__add__(0)
  Money(500, 'EUR').__add__(Money(250, 'EUR'))
  Money(750, 'EUR').__add__(Money(5, 'EUR'))
Money(755, 'EUR')
  Money(500, 'EUR').__add__('oops')
TypeError: unsupported operand type(s) for +: 'Money' and 'str'
```

`sum()` starts with `0`, so `0 + Money(...)` must work. `int.__add__(Money)` returns `NotImplemented`, Python then tries `Money.__radd__(0)`, and our class handles the zero. For `a + "oops"`, `Money.__add__` returned `NotImplemented` and `str` has no `__radd__`, so Python raised the standard error message.

The same pattern applies to every binary operator: `-` (`__sub__`/`__rsub__`), `*` (`__mul__`), `@` (`__matmul__`), `/` (`__truediv__`), `//` (`__floordiv__`), `%` (`__mod__`), `**` (`__pow__`), bitwise `&`, `^`, the pipe operator (`__or__`, which is how `dict1 | dict2` and `int | str` work), and the shifts. Unary operators are `__neg__`, `__pos__`, `__abs__` and `__invert__`.

### In-place operators

`a += b` tries `a.__iadd__(b)` first. If it is not defined, Python falls back to `a = a + b`, creating a new object. Mutable types implement `__iadd__` to modify themselves and **must return `self`**, because the result is assigned back to the name.

```python
class Bag:
    def __init__(self):
        self.items = []
    def __add__(self, other):
        print("  __add__ (new object)")
        new = Bag(); new.items = self.items + list(other)
        return new
    def __iadd__(self, other):
        print("  __iadd__ (in place)")
        self.items.extend(other)
        return self                    # must return the object!

b = Bag(); before = id(b)
b += [1, 2]
print(b.items, id(b) == before)
c = b + [3]
print(c.items, c is b)

t = (1, 2); tid = id(t)
t += (3,)                              # tuple has no __iadd__: falls back to __add__
print(t, id(t) == tid)
```

```text title="Output"
  __iadd__ (in place)
[1, 2] True
  __add__ (new object)
[1, 2, 3] False
(1, 2, 3) False
```

This is why `lst += [x]` mutates a list that other names also reference, while `tup += (x,)` rebinds the name to a new tuple. Forgetting `return self` in `__iadd__` silently sets the variable to `None`.

## Calling objects: `__call__`

Any object whose type defines `__call__` can be called like a function. `callable(x)` checks for it. Classes are callable because `type` defines `__call__` (that is what runs `__new__` and `__init__`, see [classes and instances](/docs/python/classes-and-instances)).

```python
class RateLimiter:
    def __init__(self, limit):
        self.limit = limit
        self.calls = 0

    def __call__(self, user):
        self.calls += 1
        return self.calls <= self.limit

allow = RateLimiter(limit=2)
print([allow("ana") for _ in range(3)])
print(callable(allow), callable(RateLimiter), callable(42))
print(allow.calls)
```

```text title="Output"
[True, True, False]
True True False
3
```

Callable objects are a clean alternative to closures when the "function" needs inspectable state or configuration: middleware, retry policies, class-based [decorators](/docs/python/decorators), PyTorch modules (`model(x)` calls `model.__call__`, which runs `forward`).

<Callout title="Coming from JS">
  In JS only functions are callable, so stateful callables are closures or functions with properties. Python separates "callable" from "function": any object can opt in with `__call__`. FastAPI's dependency injection, for example, accepts any callable, including a configured class instance.
</Callout>

## Truthiness: `__bool__` and `__len__`

`if x:` and `bool(x)` follow this order:

1. If the type defines `__bool__`, call it. It **must** return a `bool`.
2. Else, if it defines `__len__`, the object is falsy when the length is `0`.
3. Else the object is truthy.

```python
class Empty:
    pass

class Queue:
    def __init__(self, items):
        self.items = items
    def __len__(self):
        print("  __len__ called")
        return len(self.items)

class Connection:
    def __init__(self, open_):
        self.open = open_
    def __bool__(self):
        print("  __bool__ called")
        return self.open
    def __len__(self):
        return 99

print(bool(Empty()))
print(bool(Queue([])), bool(Queue([1])))
print(bool(Connection(False)))
if not Queue([]):
    print("queue is empty")
```

```text title="Output"
True
  __len__ called
  __len__ called
False True
  __bool__ called
False
  __len__ called
queue is empty
```

```python
class Bad:
    def __bool__(self):
        return 1
try:
    bool(Bad())
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
TypeError: __bool__ should return bool, returned int
```

**Trap:** defining `__len__` makes empty instances falsy, so `if result:` may mean "not None" in your head but "non-empty" to Python. Write `if result is not None:` when that is what you mean. This bites with ORM querysets, empty Pydantic collections and NumPy arrays (which raise on `bool()` of multi-element arrays precisely to avoid ambiguity).

<Callout title="Coming from JS">
  In JS every object is truthy, including `[]` and `{}`; only the primitives `false`, `0`, `-0`, `0n`, `""`, `null`, `undefined` and `NaN` are falsy. In Python, empty containers (`[]`, `{}`, `set()`, `""`) and zero numbers are falsy, and your own classes can decide. `if (arr.length)` in JS becomes `if arr:` in Python.
</Callout>

## Comparisons, `NotImplemented` and `total_ordering`

### The six rich comparison methods

`==` `!=` `<` `<=` `>` `>=` map to `__eq__`, `__ne__`, `__lt__`, `__le__`, `__gt__`, `__ge__`. Their **reflections** are swapped: if `a < b` gets `NotImplemented` from `a.__lt__(b)`, Python tries `b.__gt__(a)`. For `==` and `!=` the reflection is the same method on the other operand.

If both sides return `NotImplemented`:

- `==` falls back to **identity** (`a is b`), and `!=` to `a is not b`.
- Ordering operators raise `TypeError`.

```python
class Loud:
    def __init__(self, name):
        self.name = name
    def __eq__(self, other):
        print(f"  {self.name}.__eq__({getattr(other, 'name', other)!r})")
        return NotImplemented
    def __lt__(self, other):
        print(f"  {self.name}.__lt__")
        return NotImplemented
    def __gt__(self, other):
        print(f"  {self.name}.__gt__")
        return NotImplemented

a, b = Loud("a"), Loud("b")
print(a == b)          # both return NotImplemented: falls back to identity
print(a == a)
try:
    a < b
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
  a.__eq__('b')
  b.__eq__('a')
False
  a.__eq__('a')
  a.__eq__('a')
True
  a.__lt__
  b.__gt__
TypeError: '<' not supported between instances of 'Loud' and 'Loud'
```

You only need `__eq__`: the default `object.__ne__` calls `__eq__` and inverts the result (unless it is `NotImplemented`).

### Return `NotImplemented`, not `False`

Returning `False` for an unknown type is a common mistake. It answers on behalf of a type you know nothing about and prevents the other operand from being asked:

```python
class Meters:
    def __init__(self, v):
        self.v = v
    def __eq__(self, other):
        if isinstance(other, Meters):
            return self.v == other.v
        return False                   # wrong: closes the door on other types

class Feet:
    def __init__(self, v):
        self.v = v
    def __eq__(self, other):
        if isinstance(other, Meters):
            return abs(self.v * 0.3048 - other.v) < 1e-9
        return NotImplemented

print(Feet(10) == Meters(3.048))
print(Meters(3.048) == Feet(10))   # Meters says False, Feet never asked
```

```text title="Output"
True
False
```

Equality is now asymmetric. Also note the 3.14 change: since `NotImplemented` raises `TypeError` in a boolean context, code like `if self.__eq__(other):` breaks. Use the operator (`self == other`), or check `result is NotImplemented`.

### `functools.total_ordering`

Define `__eq__` and one ordering method; the decorator fills in the other three:

```python
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, text):
        self.parts = tuple(int(p) for p in text.split("."))

    def __repr__(self):
        return f"Version('{'.'.join(map(str, self.parts))}')"

    def __eq__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts == other.parts

    def __lt__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts < other.parts

    def __hash__(self):
        return hash(self.parts)

vs = [Version("1.10.0"), Version("1.2.3"), Version("1.2")]
print(sorted(vs))
print(Version("2.0") > Version("1.9.9"), Version("1.0") <= Version("1.0"))
print(max(vs))
print(Version("1.0") == "1.0")
try:
    Version("1.0") < "1.0"
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
[Version('1.2'), Version('1.2.3'), Version('1.10.0')]
True True
Version('1.10.0')
False
TypeError: '<' not supported between instances of 'Version' and 'str'
```

Comparing tuples gives correct semantic-version order (`1.10` after `1.2`), which plain string comparison would get wrong. `sorted`, `min` and `max` only need `__lt__`. In practice, [dataclasses](/docs/python/dataclasses-slots-and-enums) with `order=True` generate all of this for you.

<Callout title="Coming from JS">
  JS `==` and `===` on objects compare **references**, always; there is no way to customise them, so libraries ship `isEqual` helpers. Python `==` calls `__eq__` (value equality, customisable), and `is` is the reference check, like `===` on objects. JS `<` on objects calls `valueOf`/`toString` and compares the primitives; Python raises `TypeError` unless the class defines ordering.
</Callout>

## `__eq__` and `__hash__`: the contract

### The rule

Objects that compare equal **must** have the same hash. Dicts and sets find an entry by hash first and only then confirm with `==`. If two equal objects hashed differently, a lookup could miss.

To protect you, Python does this: **if a class defines `__eq__` but not `__hash__`, its `__hash__` is set to `None`**, making instances unhashable.

```python
class User:
    def __init__(self, id):
        self.id = id
    def __eq__(self, other):
        return isinstance(other, User) and self.id == other.id

print(User.__hash__)
try:
    {User(1)}
except TypeError as e:
    print("TypeError:", e)

class HashableUser(User):
    def __hash__(self):
        return hash(self.id)

print(len({HashableUser(1), HashableUser(1), HashableUser(2)}))
print({HashableUser(1): "ana"}[HashableUser(1)])

class Plain:
    pass
p = Plain()
print(p == p, p == Plain(), hash(p) == hash(p))
```

```text title="Output"
None
TypeError: cannot use 'User' as a set element (unhashable type: 'User')
2
ana
True False True
```

A class with neither method inherits `object`'s identity-based `__eq__` and `__hash__`: every instance is equal only to itself, which is consistent.

### The mutable-key trap

Hash only **immutable** fields. If a field used in `__hash__` changes after the object was put in a dict or set, the entry sits in the wrong bucket and becomes unreachable:

```python
class Key:
    def __init__(self, v):
        self.v = v
    def __eq__(self, other):
        return isinstance(other, Key) and self.v == other.v
    def __hash__(self):
        return hash(self.v)

k = Key(1)
cache = {k: "cached"}
k.v = 2                                 # mutate a field used in __hash__
print(cache.get(k), cache.get(Key(1)), cache.get(Key(2)))
print(k in cache, list(cache))
```

```text title="Output"
None None None
False [<__main__.Key object at 0x000001DBFB518D70>]
```

The entry is still in the dict, but no key can reach it: `k` and `Key(2)` hash to the bucket for `2`, and `Key(1)` reaches the right bucket but fails the `==` check. Guidelines:

- Value objects used as keys should be immutable: `@dataclass(frozen=True)`, `NamedTuple`, or properties without setters.
- Build the hash from the same fields as `__eq__`, typically `hash((self.a, self.b))`.
- Mutable objects that define value equality should stay unhashable (leave `__hash__` as `None`), like `list` and `dict`.

<Callout title="Coming from JS">
  A JS `Map` or `Set` keys objects by **reference**, so two "equal" objects are two different keys, and there is no hash hook. Python dicts and sets key by `__hash__` plus `__eq__`, so value objects work as keys (`{(1, 2): "a"}[(1, 2)]` finds the entry). The price is the contract above.
</Callout>

## Attribute hooks: `__getattr__`, `__getattribute__`, `__setattr__`

### `__getattr__`: the fallback

`__getattr__(self, name)` runs **only when normal lookup fails** (instance dict, class, bases and descriptors all came up empty). That makes it cheap and safe for dynamic attributes and delegation:

```python
class Config:
    def __init__(self, data):
        self._data = data
        self.source = "env"

    def __getattr__(self, name):           # only called when normal lookup FAILS
        print(f"  __getattr__({name!r})")
        try:
            return self._data[name]
        except KeyError:
            raise AttributeError(f"no config key {name!r}") from None

c = Config({"db_url": "postgres://", "debug": True})
print(c.source)                            # found normally, no hook call
print(c.db_url)
print(getattr(c, "timeout", 30))
print(hasattr(c, "debug"))
```

```text title="Output"
env
  __getattr__('db_url')
postgres://
  __getattr__('timeout')
30
  __getattr__('debug')
True
```

Always raise `AttributeError` (not `KeyError`) for missing names, or `getattr(obj, name, default)` and `hasattr` stop working.

**Trap: recursion during copying or unpickling.** `copy` and `pickle` create the object **without** calling `__init__`, then probe it for attributes. Inside `__getattr__`, `self.data` does not exist yet, so it calls `__getattr__("data")`, which looks up `self.data` again, and so on:

```python
class Broken:
    def __init__(self):
        self.data = {}
    def __getattr__(self, name):
        return self.data[name]

import copy
try:
    copy.copy(Broken())
except RecursionError as e:
    print("RecursionError:", e)
```

```text title="Output"
RecursionError: Stack overflow (used 1952 kB)
```

(The exact message depends on the version and platform; 3.14 reports a C stack overflow here. On older versions it says "maximum recursion depth exceeded".) Guard with `if name.startswith("_"): raise AttributeError(name)`, or read internals with `self.__dict__` / `object.__getattribute__(self, "data")`.

### `__getattribute__`: the interceptor

`__getattribute__` runs for **every** attribute access, successful or not, including method lookups. `object.__getattribute__` is where the normal lookup algorithm (data descriptors, instance dict, class, `__getattr__` fallback) actually lives. Overriding it is powerful and dangerous: any `self.x` inside it recurses, so you must delegate to `super().__getattribute__(name)`.

```python
class Traced:
    def __init__(self):
        self.x = 1

    def __getattribute__(self, name):      # called for EVERY attribute access
        if not name.startswith("__"):
            print(f"  get {name!r}")
        return super().__getattribute__(name)

    def hello(self):
        return self.x

t = Traced()
print(t.x)
print(t.hello())
```

```text title="Output"
  get 'x'
1
  get 'hello'
  get 'x'
1
```

Use `__getattr__` for almost everything; reach for `__getattribute__` only for tracing, lazy proxies or security wrappers, and measure the cost because it slows every access.

| | `__getattr__` | `__getattribute__` |
|---|---|---|
| When it runs | only after normal lookup fails | on every attribute access |
| Default implementation | none | `object.__getattribute__` (the whole lookup algorithm) |
| Recursion risk | when touching attributes that might not exist yet | on any `self.x` inside it |
| Typical use | dynamic attributes, delegation, lazy loading | tracing, access control, proxies |

### Delegation with `__getattr__`

A proxy that forwards everything to a wrapped object is a few lines:

```python
class Proxy:
    """Delegates everything to a wrapped object, logging method calls."""
    def __init__(self, target):
        object.__setattr__(self, "_target", target)

    def __getattr__(self, name):
        attr = getattr(self._target, name)
        if callable(attr):
            def wrapper(*args, **kwargs):
                print(f"  call {name}{args}")
                return attr(*args, **kwargs)
            return wrapper
        return attr

p = Proxy([3, 1, 2])
p.append(0)
p.sort()
print(p._target)
try:
    len(p)
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
  call append(0,)
  call sort()
[0, 1, 2, 3]
TypeError: object of type 'Proxy' has no len()
```

Notice `len(p)` failed even though the wrapped list has a length. The reason is the subject of the [last section](#why-special-method-lookup-bypasses-the-instance).

### `__setattr__` and `__delattr__`

`__setattr__(self, name, value)` runs for **every** assignment `obj.name = value`, including the ones inside `__init__`. To actually store the value, call `super().__setattr__(name, value)` or `object.__setattr__(self, name, value)`; writing `self.name = value` inside it recurses forever.

```python
class Frozen:
    def __init__(self, **fields):
        for k, v in fields.items():
            object.__setattr__(self, k, v)     # bypass our own __setattr__

    def __setattr__(self, name, value):
        raise AttributeError(f"{type(self).__name__} is immutable")

    def __delattr__(self, name):
        raise AttributeError(f"{type(self).__name__} is immutable")

f = Frozen(id=1, name="ana")
print(f.id, f.name)
try:
    f.name = "bob"
except AttributeError as e:
    print("AttributeError:", e)

class Tracked:
    def __init__(self):
        self.changes = []
        self.name = "ana"
    def __setattr__(self, name, value):
        if name != "changes":
            self.changes.append(name)
        super().__setattr__(name, value)

t = Tracked()
t.name = "bob"; t.email = "b@x.com"
print(t.changes, t.__dict__)
```

```text title="Output"
1 ana
AttributeError: Frozen is immutable
['name', 'name', 'email'] {'changes': ['name', 'name', 'email'], 'name': 'bob', 'email': 'b@x.com'}
```

`Frozen` uses exactly the trick `@dataclass(frozen=True)` uses in its generated `__init__`. `Tracked` is a toy version of what ORMs do for dirty tracking (though real ORMs usually use [descriptors](/docs/python/descriptors-and-metaclasses) per field, which is cheaper and more targeted).

<Callout title="Coming from JS">
  These hooks cover what a JS `Proxy` does with its `get`, `set` and `deleteProperty` traps, but they live on the class rather than on a wrapper object. `__getattr__` corresponds to a `get` trap that only fires for missing properties, and `__getattribute__` to a `get` trap that fires for everything. Per-property interception (JS `get x()`/`set x(v)`) is a `property` or descriptor in Python.
</Callout>

## Iteration and context managers, briefly

Two protocols are big enough for their own pages:

- **Iteration**: `__iter__` returns an iterator; the iterator's `__next__` returns the next value or raises `StopIteration`. `for`, unpacking, `list()`, `sum()` and comprehensions all use it. Writing `__iter__` as a generator (with `yield`) is usually simplest. Details in [iterators and iterables](/docs/python/iterators-and-iterables) and [generators](/docs/python/generators-and-yield).
- **Context managers**: `with x as y:` calls `x.__enter__()` (its return value becomes `y`) and guarantees `x.__exit__(exc_type, exc, tb)` runs, even on exceptions; returning a true value from `__exit__` suppresses the exception. The async versions are `__aenter__`/`__aexit__`, and async iteration uses `__aiter__`/`__anext__`. Details in [context managers](/docs/python/context-managers).

Other dunders you will meet: `__format__` (used by f-string format specs), `__index__` (lets an object be used as a list index or with `bin()`), `__int__`/`__float__`, `__copy__`/`__deepcopy__`, `__reduce__` (pickling), `__class_getitem__` (enables `list[int]`), `__set_name__`, `__get__`/`__set__` ([descriptors](/docs/python/descriptors-and-metaclasses)), `__init_subclass__` and `__match_args__` (positional patterns in `match`).

## Putting it together: a `Vector` that feels built-in

A 2D vector that supports printing, formatting, unpacking, arithmetic, `abs`, truthiness, equality, hashing and pattern matching:

```python
import math
from numbers import Real

class Vector:
    __match_args__ = ("x", "y")

    def __init__(self, x=0.0, y=0.0):
        self.x = float(x)
        self.y = float(y)

    # representation
    def __repr__(self):
        return f"Vector({self.x!r}, {self.y!r})"

    def __str__(self):
        return f"({self.x}, {self.y})"

    def __format__(self, spec):
        return f"({format(self.x, spec)}, {format(self.y, spec)})"

    # container-ish behaviour
    def __iter__(self):
        yield self.x
        yield self.y

    def __len__(self):
        return 2

    def __getitem__(self, i):
        return (self.x, self.y)[i]

    # truthiness and size
    def __abs__(self):
        return math.hypot(self.x, self.y)

    def __bool__(self):
        return bool(self.x or self.y)

    # arithmetic
    def __add__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return Vector(self.x + other.x, self.y + other.y)

    def __sub__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return Vector(self.x - other.x, self.y - other.y)

    def __mul__(self, k):
        if not isinstance(k, Real):
            return NotImplemented
        return Vector(self.x * k, self.y * k)

    def __rmul__(self, k):
        return self * k

    def __neg__(self):
        return Vector(-self.x, -self.y)

    def __matmul__(self, other):          # dot product with @
        if not isinstance(other, Vector):
            return NotImplemented
        return self.x * other.x + self.y * other.y

    # comparison and hashing (treat as immutable value)
    def __eq__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return tuple(self) == tuple(other)

    def __hash__(self):
        return hash((self.x, self.y))

v, w = Vector(3, 4), Vector(1, 2)
print(v, repr(v), f"{v:.2f}")
print(v + w, v - w, v * 2, 2 * v, -v)
print(abs(v), v @ w, bool(Vector()), bool(v))
x, y = v
print(x, y, len(v), v[0], list(v), 4.0 in v)
print(v == Vector(3, 4), v == (3, 4), {v, Vector(3, 4)})
print(sum([v, w], Vector()))
match v:
    case Vector(0, 0):
        print("origin")
    case Vector(x, 0) | Vector(0, x):
        print("on an axis")
    case Vector(x, y):
        print(f"general point x={x} y={y}")
try:
    v * "a"
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
(3.0, 4.0) Vector(3.0, 4.0) (3.00, 4.00)
(4.0, 6.0) (2.0, 2.0) (6.0, 8.0) (6.0, 8.0) (-3.0, -4.0)
5.0 11.0 False True
3.0 4.0 2 3.0 [3.0, 4.0] True
True False {Vector(3.0, 4.0)}
(4.0, 6.0)
general point x=3.0 y=4.0
TypeError: can't multiply sequence by non-int of type 'Vector'
```

Points worth noticing:

- `2 * v` works because `int.__mul__(Vector)` returns `NotImplemented` and `Vector.__rmul__` takes over.
- `sum([v, w], Vector())` passes a start value, so we did not need the `0` special case from `Money`.
- `v == (3, 4)` is `False`: our `__eq__` returned `NotImplemented` for a tuple, and so did `tuple.__eq__`, so Python fell back to identity.
- `v * "a"` shows the negotiation leaking through: `Vector.__mul__` declined, then `str.__rmul__` was tried, and the error message comes from `str`'s sequence-repeat code.
- In real code you would make `x` and `y` read-only (properties or a frozen dataclass) since the class is hashable; mutating them would break the hash contract.

## Why special-method lookup bypasses the instance

### What happens

For normal attributes, the instance dict is consulted. For **implicit** special-method calls (`len(x)`, `x + y`, `repr(x)`, `with x`, `for ... in x`), CPython looks the method up **on the type only**. Instance attributes and even `__getattr__`/`__getattribute__` are ignored.

```python
class Thing:
    def __len__(self):
        return 1

t = Thing()
t.__len__ = lambda: 42          # instance attribute
print(t.__len__())              # explicit attribute access sees it
print(len(t))                   # len() goes straight to the type

def fake_repr(self):
    return "patched on the class"
Thing.__repr__ = fake_repr
print(repr(t))

class NoLen:
    pass
n = NoLen()
n.__len__ = lambda: 3
try:
    len(n)
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
42
1
patched on the class
TypeError: object of type 'NoLen' has no len()
```

`__getattr__` is not consulted either, which is why the `Proxy` above could not forward `len()`:

```python
class Dyn:
    def __getattr__(self, name):
        print(f"  __getattr__({name!r})")
        return lambda *a: 99

d = Dyn()
print(d.__len__())
try:
    len(d)
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
  __getattr__('__len__')
99
TypeError: object of type 'Dyn' has no len()
```

### Why Python does this

1. **Speed.** Implicit calls go through the C slots on the type object (a pointer dereference), skipping dict lookups on the instance and the `__getattribute__` machinery. Operators are executed constantly, so this matters.
2. **Correctness for classes themselves.** Classes are objects too. `repr(int)` must call `type.__repr__(int)` (giving `<class 'int'>`), not `int.__repr__`, which is the method for *integers* and would fail without an instance. Looking up on the type avoids this "metaclass confusion".
3. **Consistency.** The slot is set when the class is created or modified, so behaviour depends on the class, not on per-instance accidents.

The consequence for proxies and mocks: you must define each special method **on the class**. That is why `unittest.mock.MagicMock` exists separately from `Mock` (it pre-defines the dunders), and why generic proxy libraries list every operator explicitly.

## Interview questions

1. **What happens when you evaluate `a + b`?** **Python calls `a.__add__(b)`. If that is missing or returns `NotImplemented`, it tries `b.__radd__(a)`, and raises `TypeError` if that also fails. If `b`'s type is a subclass of `a`'s and overrides the reflected method, `b.__radd__(a)` is tried first.**
2. **What is the difference between `NotImplemented` and `NotImplementedError`?** **`NotImplemented` is a singleton returned from operator and comparison methods to say "try the other operand". `NotImplementedError` is an exception for abstract methods that subclasses must override. Since 3.14, using `NotImplemented` in a boolean context raises `TypeError`.**
3. **Why does defining `__eq__` make a class unhashable?** **Equal objects must have equal hashes. If a class overrides `__eq__` without `__hash__`, Python sets `__hash__` to `None` so the inherited identity hash cannot break dicts and sets. Define `__hash__` from the same immutable fields to make it hashable.**
4. **How does Python decide whether an object is truthy?** **It calls `__bool__` if defined (it must return a bool), otherwise `__len__` (zero means falsy), otherwise the object is truthy.**
5. **`__getattr__` vs `__getattribute__`?** **`__getattr__` runs only after normal lookup fails; `__getattribute__` runs on every access and contains the normal lookup itself. Overriding `__getattribute__` requires delegating to `super().__getattribute__` to avoid recursion.**
6. **Why doesn't `len(obj)` use an instance attribute named `__len__`, or `__getattr__`?** **Implicit special-method calls look up the method on the type (via C slots), bypassing the instance and `__getattribute__`, for speed and so that calls on classes go to the metaclass rather than to methods meant for instances.**
7. **Why should `__iadd__` return `self`?** **`a += b` is executed as `a = a.__iadd__(b)`, so the return value is rebound to `a`. Returning nothing would set `a` to `None`.**
8. **What do you need to implement to make a class iterable and indexable?** **`__iter__` for iteration (or the legacy fallback of `__getitem__` with integer indexes raising `IndexError`), `__getitem__` for indexing and slicing (slices arrive as `slice` objects), and `__len__` for `len()`. `__contains__` is optional and speeds up `in`.**

## Recap

- The data model maps syntax and built-ins to dunder methods: `len` to `__len__`, `+` to `__add__`/`__radd__`, `[]` to `__getitem__`, `in` to `__contains__`, calls to `__call__`.
- Call the built-in or operator, never the dunder directly.
- Binary operators negotiate: return `NotImplemented` (not `False`, not an exception) for types you don't handle. In-place operators fall back to the binary version.
- Truthiness: `__bool__`, then `__len__`, then `True`.
- `==` falls back to identity, ordering raises; `total_ordering` fills in missing comparisons.
- Defining `__eq__` sets `__hash__` to `None`. Hash only immutable fields, the same ones used for equality.
- `__getattr__` is a cheap fallback; `__getattribute__` intercepts everything; `__setattr__` sees every assignment. Delegate to `object`/`super()` to store and fetch.
- Implicit special-method lookup goes to the **type**, bypassing the instance and `__getattr__`, so define protocol methods on the class.
