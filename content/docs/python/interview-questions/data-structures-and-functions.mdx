This page mixes two areas interviewers love to combine: how the built-in containers work (and what their operations cost), and how functions capture and share state. Several of the most famous Python trick questions live here. All outputs come from CPython 3.14.

## Containers and complexity

### 1. How is a Python `list` implemented, and what do its operations cost? **Medium**

**Short answer:** A `list` is a dynamic array of pointers to objects. Indexing and `append` are O(1) (append is amortised, thanks to over-allocation); `insert(0, x)`, `pop(0)` and `x in lst` are O(n). For a queue, use `collections.deque`.

CPython keeps a `PyObject **` array plus a length and a capacity. When the array is full, `append` grows it by roughly 12.5% plus a small constant, so the occasional O(n) copy is spread across many cheap appends. Inserting or removing at the front shifts every pointer.

```python
import sys

lst = []
sizes = []
for i in range(10):
    lst.append(i)
    sizes.append(sys.getsizeof(lst))
print(sizes)
```

```text title="Output"
[88, 88, 88, 88, 120, 120, 120, 120, 184, 184]
```

The size only jumps now and then: each jump is a reallocation that leaves spare slots.

| Operation | `list` | `deque` |
|---|---|---|
| `x[i]` | O(1) | O(n) in the middle |
| append / pop at the right | O(1) amortised | O(1) |
| insert / pop at the left | O(n) | O(1) |
| `x in seq` | O(n) | O(n) |

**Likely follow-up:** "Why does `sys.getsizeof` of a list not include its items?" It only measures the list object and its pointer array, not the objects the pointers refer to. Each list slot costs 8 bytes on a 64-bit build no matter what it points at.

<Callout type="info" title="Coming from JS">
  Similar to a V8 array in the fast "packed elements" mode, but a Python list always holds pointers to boxed objects. There are no unboxed numeric arrays; use `array.array` or NumPy for that.
</Callout>

See [lists and tuples](/docs/python/lists-and-tuples) and the [collections module](/docs/python/collections-module).

### 2. When would you use a tuple instead of a list? **Easy**

**Short answer:** Use a tuple for a fixed-size record of related values (a row, a coordinate, a function's multiple return values) and a list for a variable-length collection of similar items. Tuples are immutable, hashable when their items are, and slightly smaller and faster to create.

Because a tuple's size is fixed, CPython allocates it in one block with no spare capacity, and constant tuples like `(1, 2, 3)` are built once at compile time and stored in the code object. For readable records, `typing.NamedTuple` or a dataclass is better than bare indexes.

```python
import sys
from typing import NamedTuple

print(sys.getsizeof([1, 2, 3]), sys.getsizeof((1, 2, 3)))

class Point(NamedTuple):
    x: int
    y: int

p = Point(3, 4)
print(p, p.x, p[1])
locations = {p: "home"}
print(locations[Point(3, 4)])
x, y = p
print(x + y)
```

```text title="Output"
88 72
Point(x=3, y=4) 3 4
home
7
```

**Likely follow-up:** "How do you make a one-element tuple?" With a trailing comma: `(1,)`. The comma makes the tuple, not the parentheses; `(1)` is just the int `1`.

### 3. How does a `dict` work internally, and is it ordered? **Hard**

**Short answer:** A dict is a hash table using open addressing. Since CPython 3.6 it uses a "compact" layout: a small sparse array of indices plus a dense array of `(hash, key, value)` entries in insertion order. Insertion order has been a language guarantee since Python 3.7. Lookups, inserts and deletes are O(1) on average.

On lookup, CPython hashes the key, uses the low bits of the hash to pick a slot in the index array, and follows a perturbed probe sequence until it finds an entry whose hash matches and whose key is identical or `==`. The table is resized when it is about two-thirds full. Since entries are appended to the dense array, iteration naturally follows insertion order and memory use is lower than in the old sparse design.

```python
d = {}
d["banana"] = 1
d["apple"] = 2
d["cherry"] = 3
print(list(d))
del d["banana"]
d["banana"] = 4          # re-inserted: goes to the end
print(list(d))
print(d | {"apple": 99, "date": 5})
```

```text title="Output"
['banana', 'apple', 'cherry']
['apple', 'cherry', 'banana']
{'apple': 99, 'cherry': 3, 'banana': 4, 'date': 5}
```

**Likely follow-up:** "What is the worst case?" O(n) per operation if many keys collide. That is why `str` and `bytes` hashes are randomised per process (`PYTHONHASHSEED`): an attacker cannot precompute colliding keys to slow down a server that parses JSON into dicts.

<Callout type="info" title="Coming from JS">
  Like a JS `Map`, a dict keeps insertion order for every key type. Plain JS objects put integer-like keys first; Python dicts never reorder.
</Callout>

See [dicts and sets](/docs/python/dicts-and-sets).

### 4. What makes an object hashable, and why can't a list be a dict key? **Medium**

**Short answer:** An object is hashable if it has a `__hash__` that never changes during its lifetime and an `__eq__` consistent with it (equal objects must have equal hashes). Lists are mutable, so their hash would change when they change and the dict could no longer find them; Python sets `list.__hash__` to `None`.

A dict stores the hash with each entry. If a key's hash changed after insertion, the lookup would probe the wrong slot. Immutable built-ins are hashable; containers are hashable only if everything inside them is. User classes are hashable by identity by default.

```python
print(hash((1, 2)) == hash((1, 2)))
try:
    {[1, 2]: "x"}
except TypeError as e:
    print("TypeError:", e)
try:
    hash((1, [2]))
except TypeError as e:
    print("TypeError:", e)
print(hash(-1), hash(-2))
print({frozenset({1, 2}): "ok"})
```

```text title="Output"
True
TypeError: cannot use 'list' as a dict key (unhashable type: 'list')
TypeError: unhashable type: 'list'
-2 -2
{frozenset({1, 2}): 'ok'}
```

The more descriptive dict-key message is new in Python 3.14; older versions print only `unhashable type: 'list'`.

**Likely follow-up:** "Why is `hash(-1)` equal to `hash(-2)`?" In CPython's C API, `-1` is the error return value of the hash function, so a real hash of `-1` is replaced by `-2`. It is harmless because dicts always confirm a match with `==`. Implementation detail, but a nice one to know.

See question 10 of [OOP and the data model](/docs/python/interview-questions/oop-and-data-model) for what happens to `__hash__` when you define `__eq__`.

### 5. Why is `x in my_set` faster than `x in my_list`? **Easy**

**Short answer:** A set is a hash table, so membership is O(1) on average; a list must compare against each element, O(n). For repeated membership checks (deduplication, allow-lists, visited nodes), convert to a set first.

Sets use the same hashing approach as dicts but store only keys. They also give you fast algebra: union `|`, intersection `&`, difference `-` and symmetric difference `^`. Sets are unordered, so don't rely on their print order.

```python
import timeit

items = list(range(100_000))
as_set = set(items)
t_list = timeit.timeit(lambda: 99_999 in items, number=200)
t_set = timeit.timeit(lambda: 99_999 in as_set, number=200)
print(t_set < t_list / 100)

admins = {"ana", "bo"}
online = {"bo", "cy"}
print(sorted(admins & online), sorted(admins | online), sorted(admins - online))
print(list(dict.fromkeys(["b", "a", "b", "c", "a"])))   # dedupe, keep order
```

```text title="Output"
True
['bo'] ['ana', 'bo', 'cy'] ['ana']
['b', 'a', 'c']
```

**Likely follow-up:** "How do you deduplicate while keeping order?" `set` loses order, so use `dict.fromkeys(items)` as shown: dict keys are unique and ordered.

### 6. What happens if you modify a dict while iterating over it? **Medium**

**Short answer:** Adding or removing keys during iteration raises `RuntimeError: dictionary changed size during iteration`. Changing the values of existing keys is fine. Iterate over a snapshot (`list(d)`) or build a new dict with a comprehension.

Dict iterators remember the dict's size and a version counter; if the size changes mid-loop, the next step raises. Lists don't check, which is worse: removing items while looping over a list silently skips elements.

```python
scores = {"ana": 90, "bo": 40, "cy": 75}
try:
    for name in scores:
        if scores[name] < 50:
            del scores[name]
except RuntimeError as e:
    print("RuntimeError:", e)

scores = {"ana": 90, "bo": 40, "cy": 75}
passed = {k: v for k, v in scores.items() if v >= 50}
print(passed)

nums = [1, 2, 2, 3]
for n in nums:
    if n == 2:
        nums.remove(n)
print(nums)      # one 2 survived: the loop skipped it
```

```text title="Output"
RuntimeError: dictionary changed size during iteration
{'ana': 90, 'cy': 75}
[1, 2, 3]
```

**Likely follow-up:** "Which tools from `collections` would you reach for with dicts?" `defaultdict` for grouping (`groups[key].append(x)`), `Counter` for tallies and `most_common`, and `ChainMap` for layered configuration. See the [collections module](/docs/python/collections-module).

## Copying and shared references

### 7. What is the difference between a shallow and a deep copy? **Easy**

**Short answer:** A shallow copy creates a new outer container but fills it with references to the same inner objects. A deep copy (`copy.deepcopy`) recursively copies the inner objects too, so nothing mutable is shared.

`list(x)`, `x[:]`, `x.copy()`, `dict(d)` and `copy.copy` are shallow. `deepcopy` keeps a memo dict of objects already copied, which handles shared and cyclic references. Classes can customise both with `__copy__` and `__deepcopy__`.

```python
import copy

config = {"name": "api", "hosts": ["a", "b"]}
shallow = config.copy()
deep = copy.deepcopy(config)

config["hosts"].append("c")
config["name"] = "renamed"
print(shallow)
print(deep)
```

```text title="Output"
{'name': 'api', 'hosts': ['a', 'b', 'c']}
{'name': 'api', 'hosts': ['a', 'b']}
```

**Likely follow-up:** "Why didn't `shallow['name']` change?" Rebinding `config["name"]` replaced a reference in `config` only. The shallow copy kept its own reference to the old string. Only mutation of a shared object (the hosts list) shows through.

<Callout type="info" title="Coming from JS">
  `{ ...obj }` and `[...arr]` are shallow copies; `copy.deepcopy` is the Python version of `structuredClone`, but it can also copy arbitrary class instances.
</Callout>

See [copying, mutability and identity](/docs/python/copying-mutability-and-identity).

### 8. Why does `grid = [[0] * 3] * 3` behave strangely when you set `grid[0][0] = 1`? **Medium**

**Short answer:** `* 3` on the outer list repeats the *reference* to the same inner list three times, so all three rows are one object and the assignment shows up in every row. Build the rows with a comprehension so each row is created separately.

The inner `[0] * 3` is fine because it repeats references to the immutable `0`. The outer multiplication copies three pointers to one list.

```python
grid = [[0] * 3] * 3
grid[0][0] = 1
print(grid)
print(grid[0] is grid[1])

grid = [[0] * 3 for _ in range(3)]
grid[0][0] = 1
print(grid)
```

```text title="Output"
[[1, 0, 0], [1, 0, 0], [1, 0, 0]]
True
[[1, 0, 0], [0, 0, 0], [0, 0, 0]]
```

**Likely follow-up:** "Same bug elsewhere?" `dict.fromkeys(keys, [])` shares one list between all keys. Use `{k: [] for k in keys}` or a `defaultdict(list)`.

<Callout type="info" title="Coming from JS">
  The JS twin is `new Array(3).fill([])`, which also fills with one shared array.
</Callout>

### 9. What does `t = (1, [2]); t[1] += [3]` do? **Hard**

**Short answer:** It raises `TypeError: 'tuple' object does not support item assignment`, *and* the list inside the tuple is modified anyway. After the error, `t` is `(1, [2, 3])`.

`t[1] += [3]` compiles to three steps: load `t[1]`, call `list.__iadd__` (which extends the list in place and returns it), then store the result back with `t[1] = result`. The in-place extend succeeds; the store fails because tuples don't support item assignment.

```python
t = (1, [2])
try:
    t[1] += [3]
except TypeError as e:
    print("TypeError:", e)
print(t)

t[1].extend([4])     # no assignment step, so no error
print(t)
```

```text title="Output"
TypeError: 'tuple' object does not support item assignment
(1, [2, 3])
(1, [2, 3, 4])
```

**Likely follow-up:** "How can you prove the three steps?" Run `dis.dis("t[1] += [3]")`: you'll see `BINARY_OP` with the `+=` argument followed by `STORE_SUBSCR`. The lesson: augmented assignment always includes an assignment.

### 10. Why is `def add(item, items=[])` a bug? **Easy**

**Short answer:** Default values are evaluated once, when the `def` statement runs, and stored on the function object. Every call that omits `items` shares the same list, so it keeps growing. Use `None` as the default and create the list inside.

The defaults live in `func.__defaults__`. This is by design (it is also what makes the old `def f(x, cache={})` memoisation trick work), but with mutable values it is almost always a bug.

```python
def add(item, items=[]):
    items.append(item)
    return items

print(add("a"))
print(add("b"))
print(add.__defaults__)

def add_fixed(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items

print(add_fixed("a"), add_fixed("b"))
```

```text title="Output"
['a']
['a', 'b']
(['a', 'b'],)
['a'] ['b']
```

**Likely follow-up:** "Does the same happen with dataclasses or Pydantic?" `@dataclass` refuses a list default (`ValueError: mutable default ... use default_factory`), so you write `field(default_factory=list)`. Pydantic deep-copies mutable defaults per instance, so `tags: list[str] = []` is safe in a Pydantic model.

<Callout type="info" title="Coming from JS">
  JS evaluates default parameters on every call, so `function add(item, items = [])` is safe in JS. This is one of the first habits to unlearn.
</Callout>

See [functions and arguments](/docs/python/functions-and-arguments).

## Function arguments

### 11. Explain `/`, `*`, `*args` and `**kwargs` in a function signature. **Medium**

**Short answer:** Parameters before `/` are positional-only, parameters after `*` (or after `*args`) are keyword-only, `*args` collects extra positional arguments into a tuple and `**kwargs` collects extra keyword arguments into a dict.

The full order is: positional-only, `/`, positional-or-keyword, `*args` or a bare `*`, keyword-only, `**kwargs`. Positional-only parameters let a library rename them without breaking callers; keyword-only parameters force call sites to be explicit, which is great for boolean flags.

```python
def query(sql, /, *params, timeout=30, **options):
    return sql, params, timeout, options

print(query("SELECT ?", 1, 2, timeout=5, retries=3))

def connect(host, *, ssl=True):
    return host, ssl

print(connect("db", ssl=False))
try:
    connect("db", False)
except TypeError as e:
    print("TypeError:", e)
try:
    query(sql="SELECT 1")
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
('SELECT ?', (1, 2), 5, {'retries': 3})
('db', False)
TypeError: connect() takes 1 positional argument but 2 were given
TypeError: query() missing 1 required positional argument: 'sql'
```

**Likely follow-up:** "Why does the last call fail?" Because `sql` is positional-only, `sql="SELECT 1"` doesn't fill it; the keyword ends up in `**options` instead and `sql` is missing.

<Callout type="info" title="Coming from JS">
  JS has only positional parameters, so you fake keyword arguments with an options object. Python gives you both natively, with errors for typos in keyword names.
</Callout>

### 12. What do `*` and `**` do at a call site and in literals? **Easy**

**Short answer:** At a call site, `*iterable` spreads items as positional arguments and `**mapping` spreads key-value pairs as keyword arguments. In literals they unpack into lists, tuples, sets and dicts. In assignments, a starred name collects the rest.

```python
def greet(greeting, name, punctuation="!"):
    return f"{greeting}, {name}{punctuation}"

args = ["Hello", "Ada"]
kwargs = {"punctuation": "?"}
print(greet(*args, **kwargs))

defaults = {"debug": False, "port": 8000}
overrides = {"port": 9000}
print({**defaults, **overrides})
print(defaults | overrides)

first, *middle, last = [1, 2, 3, 4, 5]
print(first, middle, last)
```

```text title="Output"
Hello, Ada?
{'debug': False, 'port': 9000}
{'debug': False, 'port': 9000}
1 [2, 3, 4] 5
```

**Likely follow-up:** "What happens if a key appears both in `**kwargs` and as an explicit keyword?" The call raises `TypeError: got multiple values for keyword argument`. Merging dicts with `|` or `{**a, **b}` instead lets the right-hand side win.

<Callout type="info" title="Coming from JS">
  `*` and `**` together cover JS spread `...`. Rest in destructuring works the same way, except a Python starred target can sit in the middle (`first, *middle, last`), which JS doesn't allow.
</Callout>

## Scope and closures

### 13. What is LEGB, and why does this code raise `UnboundLocalError`? **Medium**

**Short answer:** LEGB is the order Python searches for a name: Local, Enclosing function scopes, Global (module) and Built-ins. Whether a name is local is decided at *compile time*: any assignment to it anywhere in a function makes it local for the whole function, so reading it before the assignment raises `UnboundLocalError`.

The compiler scans the function body; if it finds `count = ...` or `count += ...`, it emits fast-local load and store instructions for `count`. At runtime the local slot is still empty when the first read happens.

```python
count = 0

def increment():
    try:
        count += 1
    except UnboundLocalError as e:
        print("UnboundLocalError:", e)

increment()

def increment_global():
    global count
    count += 1

increment_global()
print(count)
```

```text title="Output"
UnboundLocalError: cannot access local variable 'count' where it is not associated with a value
1
```

**Likely follow-up:** "Can you shadow a built-in?" Yes, and it is a common bug: `list = [1, 2]` at module level hides the built-in `list` for the rest of the module, because Global is searched before Built-ins.

<Callout type="info" title="Coming from JS">
  This resembles the temporal dead zone for `let`, but in Python there are no block scopes: `if` and `for` bodies do not create a scope, only functions, classes, modules and comprehensions do.
</Callout>

See [scope, LEGB and closures](/docs/python/scope-legb-and-closures).

### 14. What is the difference between `global` and `nonlocal`? **Medium**

**Short answer:** `global x` makes assignments to `x` target the module-level name. `nonlocal x` makes them target the nearest enclosing function's variable. Without either declaration, assigning creates a new local.

`nonlocal` requires that the name already exists in an enclosing function scope (not the module). You only need these declarations for rebinding; mutating an object (like appending to an outer list) never needs them.

```python
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1
        return count
    return increment

counter = make_counter()
print(counter(), counter(), counter())

def make_log():
    entries = []
    def log(msg):
        entries.append(msg)      # mutation: no nonlocal needed
        return entries
    return log

log = make_log()
log("a")
print(log("b"))
```

```text title="Output"
1 2 3
['a', 'b']
```

**Likely follow-up:** "Would you use `global` in a web service?" Rarely. Module globals are shared by every request in the process (and every thread), so mutable global state needs locks and breaks with multiple workers. Prefer dependency injection or an explicit object.

### 15. What is a closure, and where does Python store the captured variables? **Medium**

**Short answer:** A closure is an inner function that remembers variables from the enclosing scope after that scope has returned. CPython stores each captured variable in a *cell* object, shared by the outer and inner function, and attaches the cells to the inner function as `__closure__`.

The compiler marks variables used by inner functions as "cell variables". Rather than a plain local slot, the value lives in a cell, and both functions read and write through it. That is why closures see later changes to the variable, not a snapshot.

```python
def make_multiplier(factor):
    def multiply(x):
        return x * factor
    return multiply

double = make_multiplier(2)
print(double(21))
print(double.__code__.co_freevars)
print(double.__closure__[0].cell_contents)
```

```text title="Output"
42
('factor',)
2
```

**Likely follow-up:** "Closures or classes for state?" Closures are lighter for one behaviour plus a bit of state (decorators, callbacks, factories). A class wins when you have several operations on the state or need introspection and testing hooks.

<Callout type="info" title="Coming from JS">
  Same concept as JS closures. The one difference is rebinding: you need `nonlocal` to assign to a captured variable in Python, whereas JS lets you assign to it directly.
</Callout>

### 16. Why does `[f() for f in [lambda: i for i in range(3)]]` give `[2, 2, 2]`? **Hard**

**Short answer:** Closures capture *variables*, not values. All three lambdas share one cell for `i`, and they are called after the loop has finished, when `i` is `2`. Fix it by binding the current value as a default argument (`lambda i=i: i`) or with `functools.partial`.

This is called late binding: the variable is looked up when the function runs, not when it is defined. Default arguments, by contrast, are evaluated at definition time, which is why the `i=i` trick works.

```python
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])

funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])

from functools import partial
def show(i):
    return i
funcs = [partial(show, i) for i in range(3)]
print([f() for f in funcs])
```

```text title="Output"
[2, 2, 2]
[0, 1, 2]
[0, 1, 2]
```

**Likely follow-up:** "Where does this happen for real?" Registering callbacks or routes in a loop, for example building handlers for a list of event names, or creating tasks with `asyncio.create_task(handler())` closures in a loop where the handler reads the loop variable later.

<Callout type="info" title="Coming from JS">
  This is the classic `var` in a `for` loop bug from JS. JS fixed it with `let`, which creates a fresh binding per iteration. Python has no per-iteration binding, so the bug is still live.
</Callout>

## Decorators and functools

### 17. What is a decorator, and why should you use `functools.wraps`? **Medium**

**Short answer:** A decorator is a callable that takes a function and returns a replacement; `@deco` above `def f` is just `f = deco(f)`. `functools.wraps` copies the original's `__name__`, `__doc__`, `__module__`, `__qualname__` and `__wrapped__` onto the wrapper, so logging, debugging, `help()` and frameworks that inspect signatures still work.

The usual shape is a wrapper closure that accepts `*args, **kwargs`, runs code before and after, and forwards the call. FastAPI, for example, reads a handler's signature to build dependencies and the OpenAPI schema, and `inspect.signature` follows `__wrapped__` to find it.

```python
import functools
import inspect

def log_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__} with {args} {kwargs}")
        result = func(*args, **kwargs)
        print(f"{func.__name__} returned {result!r}")
        return result
    return wrapper

@log_calls
def add(a: int, b: int = 0) -> int:
    """Add two numbers."""
    return a + b

add(2, b=3)
print(add.__name__, add.__doc__)
print(inspect.signature(add))
```

```text title="Output"
calling add with (2,) {'b': 3}
add returned 5
add Add two numbers.
(a: int, b: int = 0) -> int
```

**Likely follow-up:** "When do decorators run?" At definition time, once, when the module is imported. The wrapper runs on every call. That is why registration decorators like `@app.get("/")` work: the side effect happens at import.

<Callout type="info" title="Coming from JS">
  Python decorators are plain higher-order functions applied at definition time. They work on any function, unlike TypeScript/NestJS decorators, which are limited to classes and their members.
</Callout>

See [decorators](/docs/python/decorators).

### 18. How do you write a decorator that takes arguments, like `@retry(times=3)`? **Hard**

**Short answer:** Add one more layer: `retry(times=3)` is called first and must *return* the actual decorator, which then receives the function. So you get three nested functions: the factory, the decorator and the wrapper.

`@retry(times=3)` desugars to `f = retry(times=3)(f)`. The factory's arguments are captured by closure in both inner layers.

```python
import functools

def retry(times, exceptions=(Exception,)):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    print(f"attempt {attempt} failed: {e}")
            raise RuntimeError(f"{func.__name__} failed after {times} attempts")
        return wrapper
    return decorator

calls = {"n": 0}

@retry(times=3, exceptions=(ConnectionError,))
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ConnectionError("timeout")
    return "ok"

print(flaky())
```

```text title="Output"
attempt 1 failed: timeout
attempt 2 failed: timeout
ok
```

**Likely follow-up:** "How would you support both `@retry` and `@retry(times=3)`?" Make the first parameter optional: `def retry(func=None, *, times=3)`. If `func` is given, apply the decorator straight away; otherwise return the decorator. Also, if the decorated function is `async def`, the wrapper must be `async def` too and `await` the call, otherwise it returns an un-awaited coroutine.

### 19. How does `functools.lru_cache` work, and what are its pitfalls? **Medium**

**Short answer:** It memoises a function in a dict keyed by its arguments, evicting the least recently used entry when `maxsize` is reached (`functools.cache` is the unbounded version). Arguments must be hashable, cached results are shared mutable objects, and decorating a method caches `self` too, which keeps instances alive.

The key is built from the positional and keyword arguments, so `f(1, 2)` and `f(1, b=2)` are cached separately. The C implementation is thread-safe in the sense that the cache won't corrupt, but two threads may compute the same value at once.

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(80))
print(fib.cache_info())

@lru_cache
def load_tags(user):
    return ["a", "b"]

tags = load_tags("ana")
tags.append("oops")
print(load_tags("ana"))      # the cached list was mutated
try:
    load_tags(["not", "hashable"])
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
23416728348467685
CacheInfo(hits=78, misses=81, maxsize=128, currsize=81)
['a', 'b', 'oops']
TypeError: unhashable type: 'list'
```

**Likely follow-up:** "How do you cache a method safely?" Use `functools.cached_property` for per-instance computed attributes, or keep the cache on the instance. In a web app, an in-process cache is per worker process; for shared caching across workers use Redis.

See [lambdas and functools](/docs/python/lambdas-and-functools).

### 20. What are `functools.partial` and `functools.singledispatch` used for? **Medium**

**Short answer:** `partial` freezes some arguments of a callable and returns a new callable, handy for callbacks and `map`. `singledispatch` turns a function into a generic function that picks an implementation based on the type of its first argument, which is a clean replacement for long `isinstance` chains.

`partial` objects store `func`, `args` and `keywords`, and unlike a lambda they bind values immediately (no late-binding surprise). `singledispatch` looks up the argument's class in a registry, walking the MRO, so a handler for a base class also covers subclasses.

```python
from functools import partial, singledispatch
from datetime import date
from decimal import Decimal

def power(base, exponent):
    return base ** exponent

square = partial(power, exponent=2)
print(list(map(square, [1, 2, 3])))

@singledispatch
def to_json(value):
    raise TypeError(f"cannot serialise {type(value).__name__}")

@to_json.register
def _(value: date):
    return value.isoformat()

@to_json.register
def _(value: Decimal):
    return str(value)

print(to_json(date(2026, 10, 13)), to_json(Decimal("9.99")))
try:
    to_json(object())
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
[1, 4, 9]
2026-10-13 9.99
TypeError: cannot serialise object
```

**Likely follow-up:** "What about methods?" Use `functools.singledispatchmethod`, which dispatches on the first argument after `self`. And `functools.reduce` folds an iterable into one value, though a plain loop or `sum`/`math.prod` is usually clearer.
