This section is a question bank for Python backend and AI engineering interviews, written for engineers who already know JavaScript or TypeScript well. Each question gives you the answer you would say first, then the mechanism behind it, a runnable example, and the follow-up an interviewer is likely to ask next.

## How each question is laid out

1. **Short answer:** one or two sentences you can say in the first ten seconds.
2. **The mechanism:** what CPython actually does, because "why" is what separates a senior answer from a memorised one.
3. **Code and output:** a small example with its real output. Try to predict the output before reading it.
4. **Likely follow-up:** the next question an interviewer usually asks, with its answer.
5. **Coming from JS:** where the JavaScript or TypeScript equivalent behaves differently, so your Node instincts don't mislead you.

## How to use this bank

- **First pass:** read only the question titles and answer each one out loud before opening the short answer. Mark the ones you hesitated on.
- **Second pass:** for the marked questions, run the code yourself and change it until you can predict the output every time.
- **Before the interview:** reread the Hard questions and the classic traps. They come up again and again: mutable default arguments, late-binding closures, `is` with small integers, `[[0] * 3] * 3`, `a += b` on a tuple holding a list, `__hash__` becoming `None` when you define `__eq__`, `finally` overriding a `return`, and MRO order in a diamond.
- **For backend roles:** make sure you can explain, without notes, when to use asyncio versus threads in a FastAPI service and how to keep a CPU-heavy endpoint from blocking the event loop (questions 6 to 8 of the concurrency page).

## A good answer has three parts

Interviewers rarely want only the fact. Structure your answer as **mechanism, then example, then trade-off**:

1. **Mechanism:** say what Python does under the hood. "Default values are evaluated once, when `def` runs, and stored on the function object."
2. **Example:** make it concrete. "So `def add(x, items=[])` shares one list across calls and it keeps growing."
3. **Trade-off:** show judgement. "The fix is a `None` default. Dataclasses refuse mutable defaults for this reason and make you use `default_factory`, and Pydantic copies defaults per instance."

If you don't know an answer, reason out loud from the mechanism you do know (names point at objects, everything is an object, special methods are looked up on the type). That usually earns more credit than a guess.
