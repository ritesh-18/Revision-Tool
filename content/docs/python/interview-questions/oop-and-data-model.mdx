Python's object model is small and consistent: classes are objects, methods are functions that become bound through descriptors, and almost every operator or built-in maps to a dunder method. Interviewers use these questions to find out whether you know that machinery or only the syntax. All outputs come from CPython 3.14.

## Classes and instances

### 1. What is `self`, and how does `obj.method()` get it? **Easy**

**Short answer:** `self` is just the first parameter of a method, the instance the method was called on. `obj.method(x)` is effectively `type(obj).method(obj, x)`: accessing the function through the instance creates a *bound method* that remembers `obj` and passes it as the first argument.

There is nothing magic about the name `self`; it is a convention. What is special is that functions are descriptors: when you look one up on an instance, its `__get__` returns a bound method object holding `__self__` and `__func__` (see question 18).

```python
class Greeter:
    def __init__(self, name):
        self.name = name
    def greet(self, punctuation):
        return f"Hi, {self.name}{punctuation}"

g = Greeter("Ada")
print(g.greet("!"))
print(Greeter.greet(g, "?"))
bound = g.greet
print(bound.__self__ is g, bound.__func__ is Greeter.greet)
```

```text title="Output"
Hi, Ada!
Hi, Ada?
True True
```

**Likely follow-up:** "Can you lose `self` like you lose `this` in JS?" No. Once you take `g.greet`, the bound method carries the instance with it, so passing `g.greet` as a callback works correctly. There is no need for `.bind()` or arrow functions.

<Callout type="info" title="Coming from JS">
  Python has no dynamic `this`. Binding happens at attribute access, not at call time, so `const f = obj.method; f()` style bugs don't exist in Python.
</Callout>

See [classes and instances](/docs/python/classes-and-instances).

### 2. What is the difference between `__new__` and `__init__`? **Medium**

**Short answer:** `__new__` is a static method that *creates* and returns the instance; `__init__` *initialises* an instance that already exists and must return `None`. You rarely override `__new__`, except for subclassing immutable types (where the value must be set at creation), singletons or caching instances.

Calling `MyClass(args)` invokes `type.__call__`, which calls `MyClass.__new__(MyClass, args)` and then, if the result is an instance of `MyClass`, calls `__init__` on it with the same arguments.

```python
class Celsius(float):
    def __new__(cls, value):
        print("__new__ called")
        return super().__new__(cls, round(value, 1))
    def __init__(self, value):
        print("__init__ called, value already", float(self))

t = Celsius(21.456)
print(t, isinstance(t, float))

class Upper(str):
    def __init__(self, value):
        self = value.upper()      # rebinding self does nothing

print(Upper("abc"))
```

```text title="Output"
__new__ called
__init__ called, value already 21.5
21.5 True
abc
```

**Likely follow-up:** "What happens if `__new__` returns an object of another type?" Then `__init__` is skipped. That is also how you'd implement a cache that returns an existing instance, although a factory function or class method is usually clearer.

### 3. What is the difference between class attributes and instance attributes? **Easy**

**Short answer:** Class attributes live in the class's `__dict__` and are shared by all instances; instance attributes live in each instance's `__dict__`. Reading `obj.x` checks the instance first and falls back to the class, but assigning `obj.x = ...` always creates an instance attribute. A mutable class attribute is therefore shared state, a classic bug.

```python
class Dog:
    species = "canis"        # shared, immutable: fine
    tricks = []              # shared, mutable: bug

    def __init__(self, name):
        self.name = name

    def add_trick(self, trick):
        self.tricks.append(trick)

a, b = Dog("rex"), Dog("fido")
a.add_trick("sit")
print(b.tricks)

a.species = "wolf"           # creates an instance attribute
print(a.species, b.species, Dog.species)
print(a.__dict__)
```

```text title="Output"
['sit']
wolf canis canis
{'name': 'rex', 'species': 'wolf'}
```

**Likely follow-up:** "When are class attributes useful?" For constants, defaults and per-class configuration (like `model_config` in Pydantic or `__tablename__` in SQLAlchemy). Mutable per-object state always belongs in `__init__`.

<Callout type="info" title="Coming from JS">
  A class attribute is like a property on the `prototype`, not a class field. TS class fields (`tricks = []`) are per-instance; the Python line `tricks = []` in the class body is not.
</Callout>

### 4. What is the difference between an instance method, a `@classmethod` and a `@staticmethod`? **Easy**

**Short answer:** An instance method receives the instance (`self`). A class method receives the class (`cls`), even when called on an instance, which makes it ideal for alternative constructors that work with subclasses. A static method receives nothing extra; it is a plain function namespaced in the class.

```python
from datetime import date

class User:
    def __init__(self, name, born):
        self.name, self.born = name, born

    @classmethod
    def from_dict(cls, data):
        return cls(data["name"], date.fromisoformat(data["born"]))

    @staticmethod
    def is_valid_name(name):
        return name.isalpha()

    def age_on(self, day):
        return day.year - self.born.year

class Admin(User):
    pass

admin = Admin.from_dict({"name": "ana", "born": "1990-05-01"})
print(type(admin).__name__, admin.age_on(date(2026, 10, 13)))
print(User.is_valid_name("ana42"))
```

```text title="Output"
Admin 36
False
```

**Likely follow-up:** "Why `cls(...)` instead of `User(...)` in `from_dict`?" So that `Admin.from_dict` returns an `Admin`. Hard-coding the class name breaks subclassing.

### 5. What does `@property` do, and why don't Python classes need getters and setters? **Easy**

**Short answer:** `@property` turns a method into a computed attribute, with optional setter and deleter. Because you can switch a plain attribute to a property later without changing any caller, Python code starts with public attributes and adds properties only when it needs validation or computation.

```python
class Account:
    def __init__(self, balance):
        self.balance = balance       # goes through the setter

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value

    @property
    def is_empty(self):
        return self._balance == 0

acc = Account(10)
acc.balance -= 4
print(acc.balance, acc.is_empty)
try:
    acc.balance = -1
except ValueError as e:
    print("ValueError:", e)
try:
    acc.is_empty = True
except AttributeError as e:
    print("AttributeError:", e)
```

```text title="Output"
6 False
ValueError: balance cannot be negative
AttributeError: property 'is_empty' of 'Account' object has no setter
```

**Likely follow-up:** "How is `property` implemented?" It is a data descriptor: a class with `__get__`, `__set__` and `__delete__`. See question 17.

<Callout type="info" title="Coming from JS">
  Equivalent to `get balance()` and `set balance(v)` in a JS class. Python has no enforced `#private` fields; `_balance` is private by convention only.
</Callout>

## Inheritance

### 6. In a diamond `class D(B, C)` where `B` and `C` both inherit from `A`, which method runs? **Medium**

**Short answer:** Python uses the C3 linearisation to compute a Method Resolution Order (MRO). For the diamond it is `D, B, C, A, object`: left-to-right in the bases list, and a shared base comes only after all its subclasses. The first class in the MRO that defines the method wins.

C3 guarantees three things: a class comes before its parents, the order of bases you wrote is preserved, and the result is consistent for every class in the hierarchy. If no such order exists, the class definition fails with a `TypeError`.

```python
class A:
    def who(self):
        return "A"

class B(A):
    pass

class C(A):
    def who(self):
        return "C"

class D(B, C):
    pass

print([cls.__name__ for cls in D.__mro__])
print(D().who())

try:
    class X(A, B):     # A before its own subclass B: impossible
        pass
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
['D', 'B', 'C', 'A', 'object']
C
TypeError: Cannot create a consistent method resolution order (MRO) for bases A, B
```

Note the trick: `B` doesn't define `who`, so you might expect `A.who` via depth-first search. C3 puts `C` before `A`, so `C.who` wins.

**Likely follow-up:** "How does `super()` relate to the MRO?" See the next question.

See [inheritance, MRO and super](/docs/python/inheritance-mro-and-super).

### 7. What does `super()` actually call? **Hard**

**Short answer:** `super()` does not mean "my parent class". It returns a proxy that looks up the method in the *next class after the current one in the MRO of the instance's actual type*. In multiple inheritance this lets every class in a diamond run exactly once, provided each one calls `super()` (cooperative inheritance).

Zero-argument `super()` is shorthand for `super(CurrentClass, self)`; the compiler provides the current class through a hidden `__class__` cell.

```python
class Base:
    def setup(self):
        print("Base.setup")

class Logging(Base):
    def setup(self):
        print("Logging.setup")
        super().setup()

class Metrics(Base):
    def setup(self):
        print("Metrics.setup")
        super().setup()

class Service(Logging, Metrics):
    def setup(self):
        print("Service.setup")
        super().setup()

Service().setup()
```

```text title="Output"
Service.setup
Logging.setup
Metrics.setup
Base.setup
```

`Logging` doesn't inherit from `Metrics`, yet its `super().setup()` called `Metrics.setup`, because that is next in `Service`'s MRO. `Base.setup` runs once, not twice.

**Likely follow-up:** "What's the catch?" Cooperative methods must share a compatible signature, usually by accepting and forwarding `**kwargs`, because you don't know which class `super()` will reach. That is why mixins in frameworks like Django take `**kwargs`.

<Callout type="info" title="Coming from JS">
  JS classes have single inheritance, so `super.method()` always means the parent. In Python it means "next in the MRO", which can be a sibling.
</Callout>

### 8. What is the difference between `_name` and `__name` attributes? **Easy**

**Short answer:** A single underscore is a convention meaning "internal, don't touch"; nothing enforces it. A double underscore (without trailing underscores) triggers name mangling: inside a class `Foo`, `__name` becomes `_Foo__name`, which prevents accidental clashes with subclasses. Neither gives real privacy.

```python
class Base:
    def __init__(self):
        self._internal = "convention"
        self.__token = "base-secret"

class Child(Base):
    def __init__(self):
        super().__init__()
        self.__token = "child-secret"   # does not overwrite Base's

c = Child()
print(sorted(vars(c)))
print(c._Base__token)
```

```text title="Output"
['_Base__token', '_Child__token', '_internal']
base-secret
```

**Likely follow-up:** "Then how do you protect data?" You don't, at the language level; Python trusts the caller ("we are all consenting adults"). Use a leading underscore, properties for validation, and keep secrets out of objects that get logged or serialised.

<Callout type="info" title="Coming from JS">
  JS `#private` fields are truly inaccessible from outside. Python has no equivalent; `__x` is closer to a naming trick than to `#x`.
</Callout>

## The data model

### 9. What is the difference between `__repr__` and `__str__`? **Easy**

**Short answer:** `__repr__` is the unambiguous developer representation, used by the REPL, debuggers, containers and `!r` in f-strings; ideally it looks like the code to recreate the object. `__str__` is the friendly user-facing text used by `print` and `str()`. If you only write one, write `__repr__`: `str` falls back to it.

```python
class Money:
    def __init__(self, amount, currency):
        self.amount, self.currency = amount, currency
    def __repr__(self):
        return f"Money({self.amount!r}, {self.currency!r})"
    def __str__(self):
        return f"{self.amount:.2f} {self.currency}"

m = Money(9.5, "EUR")
print(m)
print(repr(m))
print([m])
print(f"{m!r} / {m}")
```

```text title="Output"
9.50 EUR
Money(9.5, 'EUR')
[Money(9.5, 'EUR')]
Money(9.5, 'EUR') / 9.50 EUR
```

**Likely follow-up:** "Why does a list print with `repr` of its items?" So that `["1", 1]` is distinguishable from `[1, 1]`. Containers always use `repr` for their contents.

See [the data model and dunder methods](/docs/python/data-model-dunder-methods).

### 10. Why does defining `__eq__` make instances unhashable? **Medium**

**Short answer:** If a class defines `__eq__` without `__hash__`, Python sets `__hash__ = None`, because the default identity-based hash would break the rule that equal objects must have equal hashes. To make the class hashable again, define `__hash__` from the same fields used in `__eq__`, and only for fields that never change.

The default `object.__hash__` is derived from `id`. If two different objects compare equal but hash differently, a set could hold both and a dict lookup could miss. Python avoids this silently wrong behaviour by turning hashing off.

```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented
        return (self.x, self.y) == (other.x, other.y)

print(Point.__hash__)
try:
    {Point(1, 2)}
except TypeError as e:
    print("TypeError:", e)

class HashablePoint(Point):
    def __hash__(self):
        return hash((self.x, self.y))

print(len({HashablePoint(1, 2), HashablePoint(1, 2)}))
```

```text title="Output"
None
TypeError: cannot use 'Point' as a set element (unhashable type: 'Point')
1
```

(The descriptive "cannot use ... as a set element" wording is new in Python 3.14.)

**Likely follow-up:** "Why return `NotImplemented` instead of `False`?" It tells Python to try the reflected operation on the other operand (`other.__eq__(self)`) and only then fall back to identity. Returning `False` would block another class from handling the comparison. `@dataclass(frozen=True)` writes a consistent `__eq__` and `__hash__` for you.

### 11. How do you make a class work with `+`, `len`, `in`, indexing and `for` loops? **Medium**

**Short answer:** Implement the matching dunder methods: `__add__` (and `__radd__` for the reversed case), `__len__`, `__contains__`, `__getitem__` and `__iter__`. Built-ins and operators are thin wrappers that look these methods up on the *type*, not the instance.

For `a + b`, Python calls `type(a).__add__(a, b)`; if that returns `NotImplemented` (or doesn't exist), it tries `type(b).__radd__(b, a)`. `in` uses `__contains__`, falling back to iteration. `for` uses `__iter__`, falling back to the old `__getitem__` protocol.

```python
class Vector:
    def __init__(self, *coords):
        self.coords = coords
    def __add__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return Vector(*(a + b for a, b in zip(self.coords, other.coords)))
    def __radd__(self, other):
        return self if other == 0 else NotImplemented   # lets sum() work
    def __len__(self):
        return len(self.coords)
    def __getitem__(self, i):
        return self.coords[i]
    def __repr__(self):
        return f"Vector{self.coords}"

v = Vector(1, 2) + Vector(3, 4)
print(v, len(v), v[0], 4 in v, list(v))
print(sum([Vector(1, 1), Vector(2, 2)]))
try:
    Vector(1) + 5
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
Vector(4, 6) 2 4 True [4, 6]
Vector(3, 3)
TypeError: unsupported operand type(s) for +: 'Vector' and 'int'
```

`in` and `list()` worked without `__contains__` or `__iter__`, through the `__getitem__` fallback.

**Likely follow-up:** "Can you add a dunder method to an instance at runtime?" You can set it, but implicit calls ignore it, because Python looks special methods up on the type. `obj.__len__ = lambda: 3` doesn't make `len(obj)` work.

<Callout type="info" title="Coming from JS">
  JS has no operator overloading at all (only `Symbol.iterator`, `Symbol.toPrimitive` and friends). Python's data model is like having a symbol hook for every operator.
</Callout>

## Dataclasses, slots and enums

### 12. What does `@dataclass` generate, and what do `frozen` and `default_factory` do? **Easy**

**Short answer:** `@dataclass` reads the class's annotated fields and generates `__init__`, `__repr__` and `__eq__` (and optionally ordering, `__hash__`, `__slots__` and keyword-only init). `frozen=True` blocks assignment after creation and makes instances hashable; `field(default_factory=list)` gives each instance its own mutable default.

It is code generation at class-creation time, so there is no runtime cost per attribute access and no validation of types.

```python
from dataclasses import dataclass, field, asdict, replace

@dataclass(frozen=True)
class Order:
    id: int
    customer: str
    items: list[str] = field(default_factory=list)

o = Order(1, "ana", ["book"])
print(o)
print(o == Order(1, "ana", ["book"]))
try:
    o.customer = "bo"
except Exception as e:
    print(type(e).__name__, e)
print(replace(o, customer="bo"))
print(asdict(o))
print(Order(2, "cy", "not a list"))   # no type validation
```

```text title="Output"
Order(id=1, customer='ana', items=['book'])
True
FrozenInstanceError cannot assign to field 'customer'
Order(id=1, customer='bo', items=['book'])
{'id': 1, 'customer': 'ana', 'items': ['book']}
Order(id=2, customer='cy', items='not a list')
```

**Likely follow-up:** "Is that frozen order hashable?" Its `__hash__` exists, but calling `hash(o)` fails because the tuple of fields includes a list. Use a `tuple` for the items if you need it in a set.

See [dataclasses, slots and enums](/docs/python/dataclasses-slots-and-enums).

### 13. When would you use a dataclass, a `NamedTuple`, a `TypedDict` or a Pydantic model? **Medium**

**Short answer:** Dataclass for internal domain objects with behaviour; `NamedTuple` for small immutable records that should also behave like tuples; `TypedDict` to type-annotate plain dicts (like JSON you pass through) with no runtime cost; Pydantic at trust boundaries (request bodies, config, LLM output) where data must be validated and coerced.

| Tool | Runtime validation | Mutable | Main use |
|---|---|---|---|
| `@dataclass` | No | Yes (unless frozen) | Internal domain objects |
| `NamedTuple` | No | No | Lightweight records, tuple unpacking |
| `TypedDict` | No (types only) | It is a dict | Typing JSON-shaped dicts |
| Pydantic `BaseModel` | Yes | Yes (configurable) | API input/output, settings |

```python
from typing import TypedDict
from pydantic import BaseModel

class UserDict(TypedDict):
    id: int
    name: str

class UserModel(BaseModel):
    id: int
    name: str

raw = {"id": "42", "name": "ana"}
as_typed: UserDict = raw          # only a hint: nothing is checked
print(type(as_typed).__name__, as_typed["id"].__class__.__name__)
model = UserModel.model_validate(raw)
print(model, type(model.id).__name__)
```

```text title="Output"
dict str
id=42 name='ana' int
```

**Likely follow-up:** "Why not use Pydantic everywhere?" Validation costs CPU on every construction, and internal code that already holds trusted, typed objects doesn't need it. Validate at the edges, use plain dataclasses inside.

<Callout type="info" title="Coming from JS">
  `TypedDict` is a TS `interface` over a plain object: erased at runtime. Pydantic plays the role of Zod or `class-validator`.
</Callout>

See [Pydantic and runtime validation](/docs/python/pydantic-and-runtime-validation).

### 14. What does `__slots__` do, and when is it worth it? **Medium**

**Short answer:** `__slots__` declares a fixed set of attribute names. Instances then store attributes in fixed slots instead of a per-instance `__dict__`, which saves memory and makes attribute access slightly faster, but you can no longer add arbitrary attributes. It is worth it when you create millions of small objects.

Each slot becomes a member descriptor on the class pointing at a fixed offset in the instance's memory. With `@dataclass(slots=True)` you get the same without writing the tuple yourself.

```python
import sys

class WithDict:
    def __init__(self, x, y):
        self.x, self.y = x, y

class WithSlots:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

a, b = WithDict(1, 2), WithSlots(1, 2)
print(hasattr(a, "__dict__"), hasattr(b, "__dict__"))
print(sys.getsizeof(a) + sys.getsizeof(a.__dict__) > sys.getsizeof(b))
try:
    b.z = 3
except AttributeError as e:
    print("AttributeError:", e)
print(type(WithSlots.__dict__["x"]).__name__)
```

```text title="Output"
True False
True
AttributeError: 'WithSlots' object has no attribute 'z' and no __dict__ for setting new attributes
member_descriptor
```

**Likely follow-up:** "Any gotchas?" A subclass without its own `__slots__` gets a `__dict__` again, `vars(obj)` and other tools that expect a `__dict__` stop working, and multiple inheritance from two classes with non-empty slots fails with a layout conflict.

### 15. Why use `Enum` (or `StrEnum`) instead of string constants? **Easy**

**Short answer:** Enum members are unique singletons with a name and a value, so typos become `AttributeError`s instead of silent bugs, type checkers can check exhaustiveness, and you can iterate over them. `StrEnum` (3.11+) members are also real strings, which makes JSON serialisation and comparison with raw strings easy.

```python
from enum import Enum, StrEnum, auto

class Status(StrEnum):
    PENDING = auto()
    PAID = auto()

class Color(Enum):
    RED = 1
    CRIMSON = 1     # alias: same value

print(Status.PAID, Status.PAID == "paid", Status("pending"))
print([s.name for s in Status])
print(Color.CRIMSON is Color.RED, list(Color))
try:
    Status("refunded")
except ValueError as e:
    print("ValueError:", e)
```

```text title="Output"
paid True pending
['PENDING', 'PAID']
True [<Color.RED: 1>]
ValueError: 'refunded' is not a valid Status
```

**Likely follow-up:** "How do enums work with `match`?" Use dotted names: `case Status.PAID:`. A bare `case PAID:` would be a capture pattern that matches anything.

<Callout type="info" title="Coming from JS">
  Much closer to a TS string-literal union plus a runtime object than to a numeric TS `enum`. `StrEnum` is the natural replacement for `type Status = "pending" | "paid"`.
</Callout>

## Interfaces and protocols

### 16. What is the difference between an abstract base class and a `Protocol`? **Medium**

**Short answer:** An ABC is *nominal*: a class must inherit from it (or be registered), and it cannot be instantiated until all `@abstractmethod`s are implemented. A `Protocol` is *structural*: any class with the right methods matches it for the type checker, with no inheritance needed, which is static duck typing.

ABCs enforce their contract at instantiation time and can provide shared implementation. Protocols are mainly for type checkers; at runtime they do nothing unless decorated with `@runtime_checkable`, and then `isinstance` only checks that the methods exist, not their signatures.

```python
from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable

class Repository(ABC):
    @abstractmethod
    def get(self, id: int) -> dict: ...

    def get_many(self, ids):            # shared implementation
        return [self.get(i) for i in ids]

class Incomplete(Repository):
    pass

try:
    Incomplete()
except TypeError as e:
    print("TypeError:", e)

@runtime_checkable
class SupportsClose(Protocol):
    def close(self) -> None: ...

class Connection:                       # no inheritance at all
    def close(self) -> None:
        print("closed")

print(isinstance(Connection(), SupportsClose))
```

```text title="Output"
TypeError: Can't instantiate abstract class Incomplete without an implementation for abstract method 'get'
True
```

**Likely follow-up:** "Which do you prefer for dependency injection in a service?" Protocols, usually: the service declares the small interface it needs, and any implementation (real database, in-memory fake for tests) satisfies it without importing a base class. Use an ABC when you want to share code or force explicit opt-in.

<Callout type="info" title="Coming from JS">
  `Protocol` is how TypeScript interfaces already work: structural typing. ABCs are closer to an `abstract class` in TS, except Python checks them at runtime.
</Callout>

See [ABCs and protocols](/docs/python/abcs-and-protocols).

## Descriptors and metaclasses

### 17. What is a descriptor, and how do data and non-data descriptors differ? **Hard**

**Short answer:** A descriptor is an object stored as a class attribute that defines `__get__`, `__set__` or `__delete__`, which lets it take over attribute access on instances. A *data* descriptor defines `__set__` or `__delete__` and takes priority over the instance `__dict__`; a *non-data* descriptor (only `__get__`) can be shadowed by an instance attribute. `property`, methods, `classmethod`, `staticmethod` and `__slots__` are all descriptors.

The lookup done by `object.__getattribute__` for `obj.x` is: find `x` in the type's MRO; if it is a data descriptor, call its `__get__`; else if `x` is in `obj.__dict__`, return that; else if the class attribute is a non-data descriptor, call its `__get__`; else return the class attribute. `__set_name__` tells a descriptor which attribute name it was assigned to.

```python
class Positive:
    def __set_name__(self, owner, name):
        self.private = "_" + name
    def __get__(self, obj, objtype=None):
        if obj is None:
            return self
        return getattr(obj, self.private)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.private[1:]} must be positive")
        setattr(obj, self.private, value)

class Product:
    price = Positive()
    quantity = Positive()
    def __init__(self, price, quantity):
        self.price, self.quantity = price, quantity

p = Product(9.99, 3)
print(p.price, p.quantity, vars(p))
try:
    p.quantity = 0
except ValueError as e:
    print("ValueError:", e)
p.__dict__["price"] = -1     # data descriptor still wins
print(p.price)
```

```text title="Output"
9.99 3 {'_price': 9.99, '_quantity': 3}
ValueError: quantity must be positive
9.99
```

**Likely follow-up:** "Where do you see descriptors in real libraries?" SQLAlchemy columns (`User.name == "x"` builds SQL on the class, returns a value on an instance), Django model fields, `functools.cached_property` (a non-data descriptor that writes the result into the instance `__dict__`, so later lookups skip it).

See [descriptors and metaclasses](/docs/python/descriptors-and-metaclasses).

### 18. How do functions become bound methods? **Hard**

**Short answer:** Plain functions are non-data descriptors. When you access `obj.method`, the lookup finds the function on the class and calls `function.__get__(obj, type(obj))`, which returns a bound method object holding the function and the instance. Accessed on the class, `__get__(None, cls)` just returns the function itself.

```python
class Greeter:
    def hello(self):
        return f"hello from {type(self).__name__}"

def standalone(self):
    return "standalone"

g = Greeter()
manual = Greeter.__dict__["hello"].__get__(g, Greeter)
print(manual, manual())
print(Greeter.hello)

g.extra = standalone                # stored on the instance: no binding
try:
    g.extra()
except TypeError as e:
    print("TypeError:", e)
Greeter.extra = standalone          # stored on the class: binds
print(Greeter().extra())
```

```text title="Output"
<bound method Greeter.hello of <__main__.Greeter object at 0x...>> hello from Greeter
<function Greeter.hello at 0x...>
TypeError: standalone() missing 1 required positional argument: 'self'
standalone
```

(Memory addresses vary on every run; they are shown as `0x...`.)

**Likely follow-up:** "Is a new bound method created on every access?" Conceptually yes, `g.hello is g.hello` is `False`. CPython optimises the common `obj.method()` call pattern to skip creating the bound object, which is why method calls are cheap.

### 19. What is a metaclass, and when would you write one? **Hard**

**Short answer:** A metaclass is the class of a class: classes are instances of `type` by default, and a metaclass customises how classes are created (by overriding `type.__new__` or `__init__`). You rarely need one. `__init_subclass__` and class decorators cover most cases such as registration and validation, and are much simpler.

When Python executes a `class` statement it collects the body into a namespace dict, then calls `metaclass(name, bases, namespace)`. Metaclasses power ORMs, Pydantic's model construction and `Enum`. Their downside is that two metaclasses from different libraries conflict when you combine them.

```python
print(type(int), type(type))

class PluginMeta(type):
    registry = {}
    def __new__(mcls, name, bases, ns):
        cls = super().__new__(mcls, name, bases, ns)
        if bases:
            mcls.registry[name.lower()] = cls
        return cls

class Plugin(metaclass=PluginMeta):
    pass

class CsvExporter(Plugin):
    pass

print(PluginMeta.registry)

class Handler:
    handlers = {}
    def __init_subclass__(cls, /, route, **kwargs):
        super().__init_subclass__(**kwargs)
        Handler.handlers[route] = cls.__name__

class Users(Handler, route="/users"):
    pass

print(Handler.handlers)
```

```text title="Output"
<class 'type'> <class 'type'>
{'csvexporter': <class '__main__.CsvExporter'>}
{'/users': 'Users'}
```

**Likely follow-up:** "How can you create a class without the `class` statement?" Call `type` directly: `type("Point", (), {"x": 0})`. That is all the `class` statement does under the hood (plus running the body).

### 20. What is the difference between `__getattr__` and `__getattribute__`? **Medium**

**Short answer:** `__getattribute__` runs on *every* attribute access and implements the normal lookup; overriding it is rarely a good idea. `__getattr__` is called only when the normal lookup fails, which makes it the safe hook for proxies, lazy attributes and friendly error messages.

```python
class Settings:
    def __init__(self, values):
        self._values = values
    def __getattr__(self, name):
        try:
            return self._values[name]
        except KeyError:
            raise AttributeError(f"no setting named {name!r}") from None

s = Settings({"debug": True, "port": 8000})
print(s.debug, s.port)
print(s._values is not None)      # found normally: __getattr__ not called
try:
    s.timeout
except AttributeError as e:
    print("AttributeError:", e)
print(getattr(s, "timeout", 30))
```

```text title="Output"
True 8000
True
AttributeError: no setting named 'timeout'
30
```

**Likely follow-up:** "Why must `__getattr__` raise `AttributeError` and not `KeyError`?" Because `getattr` with a default, `hasattr` and many libraries rely on `AttributeError` to mean "not there". Raising anything else breaks them. Modules can define a module-level `__getattr__` too (PEP 562), which is handy for deprecation warnings and lazy imports.

<Callout type="info" title="Coming from JS">
  `__getattr__` is like a JS `Proxy` with only a `get` trap for missing properties; `__getattribute__` is a `get` trap for all of them.
</Callout>
