Python's numeric model is smaller and stricter than JavaScript's. There are separate `int` and `float` types, ints never overflow, there is no implicit string-to-number coercion, and some operators (`//`, `%`, `and`, `or`) behave differently from their JS look-alikes. This page covers what each type is, how it is stored, and where the traps are.

<Callout type="info">
Snippets were run on **CPython 3.14.6**. Object sizes from `sys.getsizeof` and some error messages are CPython and version specific.
</Callout>

## The numeric tower

| Type | Literal examples | What it is |
|---|---|---|
| `int` | `42`, `-7`, `1_000_000`, `0xFF`, `0o17`, `0b1010` | Exact integer, unlimited size |
| `float` | `3.14`, `1e-3`, `float("inf")` | 64-bit IEEE 754 double |
| `complex` | `3 + 4j` | Pair of floats |
| `bool` | `True`, `False` | Subclass of `int` (1 and 0) |
| `decimal.Decimal` | `Decimal("19.99")` | Exact decimal arithmetic (stdlib) |
| `fractions.Fraction` | `Fraction(1, 3)` | Exact rational numbers (stdlib) |

Mixed arithmetic "widens" to the more general type: `int` op `float` gives `float`, `float` op `complex` gives `complex`. `Decimal` deliberately refuses to mix with `float` (shown below).

<Callout title="Coming from JS">
JavaScript has one `number` type (a double) plus `bigint`, and you have to choose between them with an `n` suffix. In Python, `int` is **always** exact and unbounded, so there is no `Number.MAX_SAFE_INTEGER`, no silent precision loss above `2**53` for integer math, and no `n` suffix. Also `"5" * 2` is `"55"` (string repetition), `"5" + 2` is a `TypeError`, and `"5" - 2` is a `TypeError`. Python never converts strings to numbers for you; use `int("5")`.
</Callout>

## `int`: arbitrary precision

```python
big = 2 ** 100
print(big, type(big))
print(2**64 + 1, -(2**63) - 1)
print(1_000_000 * 3, 0xFF, 0o17, 0b1010)
```

```text title="Output"
1267650600228229401496703205376 <class 'int'>
18446744073709551617 -9223372036854775809
3000000 255 15 10
```

Underscores in literals are just visual separators (`1_000_000`), like `1_000_000` in JS.

### How CPython stores big ints

A CPython int is a variable-length object: a header followed by an array of **digits**. Each "digit" is a 32-bit C integer that holds 30 bits of the value (base `2**30`). Since 3.12 the header packs the sign and the number of digits into one field (`lv_tag`).

```python
import sys
print(sys.int_info)
for n in (0, 1, 2**30 - 1, 2**30, 2**60, 2**90, 10**100):
    print(f"{n.bit_length():>4} bits -> {sys.getsizeof(n)} bytes")
```

```text title="Output"
sys.int_info(bits_per_digit=30, sizeof_digit=4, default_max_str_digits=4300, str_digits_check_threshold=640)
   0 bits -> 28 bytes
   1 bits -> 28 bytes
  30 bits -> 28 bytes
  31 bits -> 32 bytes
  61 bits -> 36 bytes
  91 bits -> 40 bytes
 333 bits -> 72 bytes
```

Every 30 more bits costs 4 more bytes. Even the integer `1` costs 28 bytes, because it is a full heap object with a refcount, a type pointer and a size field. That overhead is why a Python `list` of a million ints uses far more memory than a NumPy array or `array.array("q")` of the same numbers, which store raw 8-byte machine ints.

<Mermaid chart={`flowchart LR
  subgraph O["int object 2**60 (36 bytes)"]
    H1["ob_refcnt"] --> H2["ob_type -> int"] --> H3["lv_tag: sign + 3 digits"] --> D0["digit 0<br/>bits 0-29"] --> D1["digit 1<br/>bits 30-59"] --> D2["digit 2<br/>bit 60"]
  end`} />

Consequences:

- Small-int arithmetic has a fast path (values that fit in one digit), and the specializing interpreter adds int-only fast versions of `+`, `-` and comparisons.
- Big-int arithmetic costs time proportional to the number of digits (multiplication uses Karatsuba above a threshold). `2 ** 1_000_000` is fine; it is just slower.
- Ints are immutable, so `n += 1` allocates a new object unless the result is a cached small int (-5 to 256).

### The int-to-str digit limit

Converting between `int` and decimal `str` is quadratic in the number of digits, which was a denial-of-service vector (send a 1 MB number in JSON, burn CPU). Since 3.11 (and backported security releases), conversion is capped at 4300 digits by default:

```python
print(len(str(2**10000)))
try:
    int("9" * 5000)
except ValueError as e:
    print("ValueError:", e)
```

```text title="Output"
3011
ValueError: Exceeds the limit (4300 digits) for integer string conversion: value has 5000 digits; use sys.set_int_max_str_digits() to increase the limit
```

Hex, octal and binary conversions are not limited, since those are linear.

## `float`: IEEE 754 doubles

A Python `float` is a C `double`: 1 sign bit, 11 exponent bits, 52 fraction bits. Exactly the same as a JavaScript `number`, so all the classic floating-point behaviour carries over.

```python
import math, sys
print(0.1 + 0.2, 0.1 + 0.2 == 0.3)
print(f"{0.1:.20f}")
print((0.1).as_integer_ratio())
print(sys.float_info.max, sys.float_info.epsilon)
```

```text title="Output"
0.30000000000000004 False
0.10000000000000000555
(3602879701896397, 36028797018963968)
1.7976931348623157e+308 2.220446049250313e-16
```

`0.1` cannot be represented in binary, just as 1/3 cannot be written in decimal. The stored value is the nearest double, which is a tiny bit above 0.1. `repr` shows the **shortest** string that round-trips to the same double, which is why `0.1` prints as `0.1` while `0.1 + 0.2` (a different double) prints with all its digits.

### Comparing floats: `math.isclose`

```python
print(math.isclose(0.1 + 0.2, 0.3))
print(math.isclose(1e-10, 0.0), math.isclose(1e-10, 0.0, abs_tol=1e-9))
```

```text title="Output"
True
False True
```

`isclose` uses a **relative** tolerance by default (`rel_tol=1e-09`), which scales with the magnitude of the numbers. Relative tolerance is useless when comparing against zero, so pass `abs_tol` in that case.

### `inf`, `nan` and errors

```python
inf = float("inf"); nan = float("nan")
print(inf, -inf, inf + 1, inf - inf, 1e308 * 10)
print(nan == nan, nan != nan, math.isnan(nan), nan is nan)
print(sorted([3, nan, 1, 2]))
```

```text title="Output"
inf -inf inf nan inf
False True True True
[3, nan, 1, 2]
```

- NaN is not equal to anything, including itself. Test with `math.isnan(x)`.
- **Sorting a list containing NaN gives garbage**, because every comparison with NaN is `False`, which breaks the ordering assumptions of the sort. Filter NaNs out first.

Where JavaScript returns `Infinity` or `NaN`, Python usually **raises**:

```python
try:
    1.0 / 0
except ZeroDivisionError as e:
    print("ZeroDivisionError:", e)
try:
    math.exp(1000)
except OverflowError as e:
    print("OverflowError:", e)
try:
    float(2**1024)
except OverflowError as e:
    print("OverflowError:", e)
try:
    math.sqrt(-1)
except ValueError as e:
    print("ValueError:", e)
```

```text title="Output"
ZeroDivisionError: division by zero
OverflowError: math range error
OverflowError: int too large to convert to float
ValueError: expected a nonnegative input, got -1.0
```

(Before 3.14 the float division message was `float division by zero` and `math.sqrt(-1)` said `math domain error`. Plain float multiplication like `1e308 * 10` still overflows silently to `inf`.)

<Callout title="Coming from JS">
`1 / 0` is `Infinity` in JS and a `ZeroDivisionError` in Python. `Math.sqrt(-1)` is `NaN` in JS and a `ValueError` in Python. Python follows "errors should never pass silently". Libraries like NumPy go back to IEEE behaviour (returning `inf` and `nan` with a warning), which is what you want for vectorized math.
</Callout>

### int and float compare exactly

Comparisons between `int` and `float` are mathematically exact, not "convert to float then compare":

```python
print(2**53 + 1 == float(2**53 + 1), int(float(2**53 + 1)))
```

```text title="Output"
False 9007199254740992
```

`float(2**53 + 1)` rounds to `2**53`, and Python correctly reports that it differs from the exact int. In JS, `2**53 + 1 === 2**53` is `true` because both sides are already doubles.

## `decimal.Decimal` for money

`Decimal` stores numbers in base 10, so `0.1` is exactly `0.1`. It also lets you control precision and rounding mode, which is what financial rules require.

```python
from decimal import Decimal, ROUND_HALF_UP, getcontext, localcontext

print(Decimal("0.1") + Decimal("0.2"), Decimal("0.1") + Decimal("0.2") == Decimal("0.3"))
print(Decimal(0.1))

price = Decimal("19.99"); qty = 3; tax = Decimal("0.0825")
subtotal = price * qty
total = subtotal * (1 + tax)
print(subtotal, total)
print(total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))
```

```text title="Output"
0.3 True
0.1000000000000000055511151231257827021181583404541015625
59.97 64.917525
64.92
```

Rules for using `Decimal` correctly:

- **Construct from strings**, never from floats. `Decimal(0.1)` faithfully converts the already-wrong binary double, as shown above.
- Mixing with `int` is fine; mixing with `float` raises, to stop you from reintroducing binary error:

```python
try:
    Decimal("1.1") + 1.1
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
TypeError: unsupported operand type(s) for +: 'decimal.Decimal' and 'float'
```

- `quantize` rounds to a fixed exponent (`Decimal("0.01")` means 2 decimal places) with an explicit rounding mode. Do this at defined points (per line item, or at the end), as your business rules say.
- Precision is set by a **context** (default 28 significant digits), which is thread-local and context-variable aware. Change it locally with `localcontext`:

```python
print(getcontext().prec)
print(Decimal(1) / Decimal(3))
with localcontext() as ctx:
    ctx.prec = 5
    print(Decimal(1) / Decimal(3))
```

```text title="Output"
28
0.3333333333333333333333333333
0.33333
```

- `Decimal` remembers trailing zeros: `Decimal("1.10") == Decimal("1.1")` is `True`, but it prints as `1.10`.

Alternatives in backend systems: store money as **integer minor units** (cents) in an `int`, which is fast and exact, and use `Decimal` (mapped to SQL `NUMERIC`) when you need fractional cents, currency conversion or tax rules. Pydantic and SQLAlchemy both support `Decimal` fields.

<Callout title="Coming from JS">
In Node you reach for `decimal.js`, `big.js` or `dinero.js`. Python ships `decimal` in the standard library (implemented in C via `libmpdec`, so it is fast).
</Callout>

## `fractions.Fraction`

`Fraction` represents exact rationals as a numerator and denominator in lowest terms:

```python
from fractions import Fraction
print(Fraction(1, 3) + Fraction(1, 6))
print(Fraction("0.1") + Fraction("0.2") == Fraction(3, 10))
print(Fraction(0.1))
print(Fraction(0.1).limit_denominator(1000))
```

```text title="Output"
1/2
True
3602879701896397/36028797018963968
1/10
```

Useful for exact ratios (aspect ratios, probabilities, music timing). It gets slow when denominators grow, so it is rarely used in hot code.

## `complex`

```python
z = 3 + 4j
print(z, type(z), z.real, z.imag, abs(z), z.conjugate(), z * 1j)
import cmath; print(cmath.sqrt(-1))
print((-1) ** 0.5)
```

```text title="Output"
(3+4j) <class 'complex'> 3.0 4.0 5.0 (3-4j) (-4+3j)
1j
(6.123233995736766e-17+1j)
```

Python uses `j` for the imaginary unit (the engineering convention). Note that `(-1) ** 0.5` returns a complex number instead of raising, while `math.sqrt(-1)` raises. Use `cmath` for complex math.

## `bool` is an `int`

```python
print(True + True, True * 10, isinstance(True, int), sum([True, False, True]))
```

```text title="Output"
2 10 True 2
```

`sum(x > 0 for x in values)` is a common idiom to count matches. The flip side: `isinstance(True, int)` is `True`, so validation code that accepts ints will also accept booleans unless you check `type(x) is int` or reject `bool` explicitly (Pydantic's strict mode does this).

## Division: `/`, `//` and `%`

| Operator | Name | Result |
|---|---|---|
| `/` | true division | always `float` (for ints) |
| `//` | floor division | rounds **toward negative infinity** |
| `%` | modulo | sign follows the **divisor** |

```python
print(7 / 2, 6 / 2, type(6 / 2))
print(7 // 2, -7 // 2, 7 // -2, 7.0 // 2)
print(7 % 3, -7 % 3, 7 % -3, -7 % -3)
```

```text title="Output"
3.5 3.0 <class 'float'>
3 -4 -4 3.0
1 2 -2 -1
```

`//` and `%` are defined together so that this identity always holds:

```text
a == (a // b) * b + (a % b)
```

Because `//` floors (rounds down, toward negative infinity), `-7 // 2` is `-4`, not `-3`. Then `%` must make the identity true: `-7 - (-4 * 2) = 1`. In general, with a positive divisor the result of `%` is always in `range(0, b)`, which is exactly what you want for wrapping:

```python
print(-1 % 24, (0 - 3) % 7)    # hour before midnight, 3 days before Monday(0)
```

```text title="Output"
23 4
```

If you need C/JS-style truncation, use `math.fmod` (remainder with the sign of the dividend) and `int(a / b)` or `math.trunc`:

```python
import math
print(math.fmod(-7, 3), int(-7 / 3), math.trunc(-3.5))
```

```text title="Output"
-1.0 -2 -3
```

(`int(a / b)` goes through a float, so it loses precision for big ints. For exact truncating division of big ints, divide the absolute values with `//` and reapply the sign. Related trick: `-(-a // b)` is exact **ceiling** division, handy for "how many pages".)

### `divmod`

`divmod(a, b)` returns `(a // b, a % b)` in one call (one division internally):

```python
print(divmod(17, 5), divmod(-17, 5))
q, r = divmod(-17, 5); print(q * 5 + r)
```

```text title="Output"
(3, 2) (-4, 3)
-17
```

Classic use: `minutes, seconds = divmod(total_seconds, 60)`.

<Callout title="Coming from JS">
JS `/` on integers gives a float like Python's `/`, but JS has no `//`: you write `Math.floor(a / b)` or `Math.trunc(a / b)`. JS `%` is a **remainder** that takes the sign of the dividend, so `-7 % 3` is `-1` in JS and `2` in Python. Porting modular arithmetic (array index wrapping, hashing, calendar math) between the two languages is a classic source of off-by-one bugs.
</Callout>

## Exponentiation: `**` and `pow`

```python
print(2 ** 10, 2 ** -1, 2 ** 0.5, (-8) ** (1/3))
print(-2 ** 2, (-2) ** 2, 2 ** 3 ** 2)
print(pow(2, 10, 1000), pow(3, -1, 7))
```

```text title="Output"
1024 0.5 1.4142135623730951 (1.0000000000000002+1.7320508075688772j)
-4 4 512
24 5
```

- `**` binds tighter than unary minus on its left: `-2 ** 2` is `-(2 ** 2)`.
- `**` is **right-associative**: `2 ** 3 ** 2` is `2 ** 9`.
- int to a negative power gives a float.
- Three-argument `pow(base, exp, mod)` does fast modular exponentiation without building the huge intermediate number (used in cryptography). With exponent `-1` it computes the modular inverse (3.8+).

## Operator precedence

From **highest** to **lowest** binding (the ones that matter in practice):

| Level | Operators |
|---|---|
| 1 | `(...)`, `[...]`, `{...}`, calls, subscripts, attribute access |
| 2 | `await` |
| 3 | `**` |
| 4 | unary `+x`, `-x`, `~x` |
| 5 | `*`, `@`, `/`, `//`, `%` |
| 6 | `+`, `-` |
| 7 | `<<`, `>>` |
| 8 | `&` |
| 9 | `^` |
| 10 | bitwise or (the vertical bar operator) |
| 11 | comparisons: `<`, `>`, `==`, `!=`, `in`, `not in`, `is`, `is not` |
| 12 | `not` |
| 13 | `and` |
| 14 | `or` |
| 15 | conditional expression `x if c else y` |
| 16 | `lambda` |
| 17 | walrus `:=` |

```python
print(not 1 == 2, 1 + 2 * 3, (1 + 2) * 3, 3 & 1 == 1)
```

```text title="Output"
True 7 9 True
```

<Callout title="Coming from JS">
In Python, bitwise operators bind **tighter** than comparisons, so `3 & 1 == 1` is `(3 & 1) == 1`, which is `True`. In JS (and C), `==` binds tighter than `&`, so `3 & 1 == 1` is `3 & true`, which is `1`. Python fixed this long-standing C wart. `not` is also lower than comparisons, so `not a == b` means `not (a == b)`.
</Callout>

## Chained comparisons

Python lets you chain comparisons like math notation. `a < b < c` means `a < b and b < c`, except `b` is evaluated **only once**.

```python
x = 5
print(1 < x < 10, 1 < x > 3, 1 < x < 3)
a, b, c = 1, 2, 3
print(a < b < c, (a < b) < c, 3 > 2 > 1, (3 > 2) > 1)
print(1 == 1 in [1])
```

```text title="Output"
True True False
True True True False
True
```

- `3 > 2 > 1` is `True` in Python. In JS, `3 > 2 > 1` is `(true) > 1`, which is `1 > 1`, which is `false`.
- Chaining applies to **all** comparison operators, including `in`, `is` and `==`. That makes `1 == 1 in [1]` mean `1 == 1 and 1 in [1]`. Writing such mixed chains is legal but confusing; stick to ranges like `0 <= i < n`.

## `and`, `or`, `not`: short-circuit and return operands

`and` and `or` do **not** return booleans. They return one of their operands:

- `x or y`: if `x` is truthy return `x`, else return `y`.
- `x and y`: if `x` is falsy return `x`, else return `y`.
- `not x` always returns a real `bool`.

```python
print(0 or "default", "" or [] or None, 3 and 4, 0 and 1 / 0, [] and "x")
print(not [], not "x", type(not 0))
```

```text title="Output"
default None 4 0 []
True False <class 'bool'>
```

`0 and 1 / 0` never evaluates `1 / 0` because `and` stopped at the falsy `0`. You can see the short-circuiting directly:

```python
def side(v):
    print(f"eval {v}"); return v
print(side(0) and side(1))
print(side(1) or side(2))
```

```text title="Output"
eval 0
0
eval 1
1
```

### The `or` default trap

`value or default` is a common idiom, but it treats **every** falsy value as missing:

```python
name = None
print(name or "anonymous")
port = 0
print(port or 8080, port if port is not None else 8080)
```

```text title="Output"
anonymous
8080 0
```

<Callout title="Coming from JS">
Python's `or` is JS's `||` and Python's `and` is JS's `&&`: both return operands and short-circuit. Python has **no `??`** operator, so for "default only if `None`" write `x if x is not None else default`. Also there are no `&&`, `||` or `!` symbols; using `&` or the bitwise-or symbol by mistake gives bitwise results, not boolean logic (and with different precedence).
</Callout>

## Bitwise operators

They work on ints as if they were in **two's complement with infinitely many sign bits**:

```python
print(6 & 3, 6 | 3, 6 ^ 3, ~6, 1 << 10, 1024 >> 3, -16 >> 2)
print(bin(6), bin(-6), (255).bit_count(), (-1) & 0xFF)
print(2**70 >> 60, 1 << 100)
```

```text title="Output"
2 7 5 -7 1024 128 -4
0b110 -0b110 8 255
1024 1267650600228229401496703205376
```

- `~x` is `-x - 1`.
- `>>` is an arithmetic (sign-preserving) shift. There is no `>>>` because there is no fixed width. To emulate 32-bit unsigned behaviour, mask: `x & 0xFFFFFFFF`.
- `1 << 100` just works. In JS, bitwise operators truncate to 32-bit signed ints, so `1 << 32` is `1`.
- `bin(-6)` shows a minus sign, not two's complement bits, because there is no fixed width to show.

Flags pattern (in real code prefer `enum.IntFlag`):

```python
READ, WRITE, EXEC = 1, 2, 4
perms = READ | WRITE
print(perms & WRITE != 0, bool(perms & EXEC))
```

```text title="Output"
True False
```

## The walrus operator `:=`

An **assignment expression** (3.8+, PEP 572) assigns and returns the value in one expression. It is useful when you would otherwise compute something twice or need an extra line before a condition.

```python
data = [1, 5, 12, 7, 30]
if (n := len(data)) > 3:
    print(f"list too long ({n} elements)")
print([y for x in data if (y := x * 2) > 10])
```

```text title="Output"
list too long (5 elements)
[24, 14, 60]
```

Typical uses:

```python
while (chunk := stream.read(8192)):
    process(chunk)

if (m := re.match(r"(\d+)-(\d+)", text)) is not None:
    start, end = m.groups()
```

Rules and traps:

- It has the **lowest** precedence of all, so you usually need parentheses: `if n := len(data) > 3` binds `n` to `len(data) > 3` (a bool).
- It is not allowed as a plain top-level statement (`x := 5` is a `SyntaxError`); use `=` there.
- Inside a comprehension, the walrus binds in the **enclosing** function scope, not the comprehension's scope, so `y` is still available after the list comprehension above.

## `round` and banker's rounding

```python
print(round(0.5), round(1.5), round(2.5), round(3.5), round(-0.5), round(-1.5))
print(round(2.675, 2), f"{2.675:.20f}")
print(round(1234.5678, -2), round(7), type(round(7.6)), type(round(7.6, 1)))
```

```text title="Output"
0 2 2 4 0 -2
2.67 2.67499999999999982236
1200.0 7 <class 'int'> <class 'float'>
```

- `round` uses **round half to even** ("banker's rounding"): exact halves go to the nearest even number. It avoids the upward bias of always rounding .5 up when you sum many rounded values.
- `round(2.675, 2)` gives `2.67` not because of the rounding rule but because `2.675` is stored as `2.67499999...`.
- `round(x)` with no digits returns an `int`; `round(x, n)` returns a `float`.
- For "school" rounding or money, use `Decimal` with `ROUND_HALF_UP`:

```python
from decimal import Decimal, ROUND_HALF_UP
print(Decimal("2.5").quantize(Decimal("1"), rounding=ROUND_HALF_UP))
```

```text title="Output"
3
```

Related truncation functions differ on negatives:

```python
print(math.floor(-2.5), math.ceil(-2.5), math.trunc(-2.5), int(-2.5))
```

```text title="Output"
-3 -2 -2 -2
```

<Callout title="Coming from JS">
`Math.round(2.5)` is `3` and `Math.round(-2.5)` is `-2` (half rounds toward positive infinity). Python's `round(2.5)` is `2`. `int(x)` truncates toward zero like `Math.trunc`. If a test compares against values produced by JS, this difference will bite.
</Callout>

## Converting and formatting numbers

```python
print(int("42"), int("  42\n"), int("ff", 16), int("0b101", 0), int(3.99), float("1e-3"))
try:
    int("4.2")
except ValueError as e:
    print("ValueError:", e)
print(f"{1234567.891:,.2f}", f"{0.075:.1%}", f"{255:#x}", f"{42:08b}")
```

```text title="Output"
42 42 255 5 3 0.001
ValueError: invalid literal for int() with base 10: '4.2'
1,234,567.89 7.5% 0xff 00101010
```

`int()` is strict: it strips whitespace but rejects `"4.2"` or `"42px"`, unlike JS `parseInt("42px")` which returns `42`. Base `0` means "infer from the prefix". The format mini-language is covered in the strings page.

## Interview questions

**Can Python ints overflow?**
**No. `int` is arbitrary precision: CPython stores it as an array of 30-bit digits that grows as needed. Only memory and time limit size (plus a 4300-digit default cap on decimal string conversion).**

**Why is `0.1 + 0.2 != 0.3` and how do you compare floats?**
**Floats are IEEE 754 binary doubles and 0.1 and 0.2 have no exact binary form, so the rounding errors add up. Compare with `math.isclose` (adding `abs_tol` near zero), or use `Decimal` when exact decimal values matter.**

**What is `-7 // 2` and `-7 % 2` in Python, and why?**
**`-4` and `1`. `//` floors toward negative infinity, and `%` is defined so that `(a // b) * b + a % b == a`, which gives the result the sign of the divisor.**

**What does `x or y` return?**
**Not necessarily a bool: it returns `x` if `x` is truthy, otherwise `y`, and it does not evaluate `y` if it does not need to. `and` returns the first falsy operand or the last one.**

**Why does `round(2.5)` return 2?**
**Python's `round` uses round-half-to-even (banker's rounding) to avoid systematic bias. Use `Decimal.quantize` with `ROUND_HALF_UP` for half-up rounding.**

**How should you handle money in Python?**
**Use `decimal.Decimal` built from strings with explicit `quantize` and rounding modes, or integer minor units (cents). Never use binary floats.**

**What does `1 < x < 10` do?**
**It is a chained comparison meaning `1 < x and x < 10`, with `x` evaluated once.**

**What is the walrus operator for?**
**`:=` assigns inside an expression, for example `while (chunk := f.read(1024)):` or to reuse a computed value in a comprehension filter. It has the lowest precedence, so parenthesize it.**

## Recap

- `int` is exact and unbounded (30-bit digits in CPython); `float` is an IEEE double with all the usual traps; `bool` is a subclass of `int`.
- Python raises on division by zero and most math domain errors instead of returning `Infinity` or `NaN`.
- Use `math.isclose` for floats, `Decimal` (from strings) or integer cents for money, `Fraction` for exact ratios.
- `/` always gives a float, `//` floors, `%` takes the divisor's sign, and `divmod` gives both.
- `**` is right-associative and binds tighter than unary minus. Bitwise operators bind tighter than comparisons.
- Comparisons chain. `and` and `or` short-circuit and return operands; there is no `??`.
- `round` is banker's rounding; `int()` truncates and parses strictly.
