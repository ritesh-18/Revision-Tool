Python's branching tools are a short list: `if`/`elif`/`else`, the conditional expression, and since 3.10 the `match` statement. `match` looks like a JavaScript `switch` but is a different and much more powerful thing: **structural pattern matching**, which checks the *shape* of data and pulls values out of it at the same time. Most of this page is about getting `match` right.

<Callout type="info">
Snippets were run on **CPython 3.14.6**. `match` requires Python 3.10+.
</Callout>

## `if`, `elif`, `else`

```python
def classify(status):
    if status < 200:
        return "info"
    elif status < 300:
        return "success"
    elif status < 400:
        return "redirect"
    else:
        return "error"

print([classify(s) for s in (101, 204, 302, 404)])
```

```text title="Output"
['info', 'success', 'redirect', 'error']
```

- The condition can be any object; it is tested by **truthiness** (see the object model page). `if items:` means "if not empty".
- No parentheses around the condition, a colon at the end, and the block is defined by indentation.
- `elif` is one keyword. There is no `else if` (writing `else:` followed by a nested `if` works but adds a level of indentation).
- Branches do not create a new scope. A variable assigned inside an `if` block is visible after it (if that branch ran). Only functions, classes, modules and comprehensions create scopes.

```python
if user_is_admin:
    role = "admin"
print(role)   # NameError if the branch did not run
```

<Callout title="Coming from JS">
There are no block scopes like `let` and `const` give you in JS. Variables in Python are function-scoped (closer to `var`, but without hoisting to `undefined`: reading a name before it is assigned raises an error). There is also no `switch` with fall-through; `match` never falls through.
</Callout>

### Guard clauses

Python style favours early returns over deep nesting ("Flat is better than nested"):

```python
def charge(order):
    if order is None:
        raise ValueError("order required")
    if order.paid:
        return
    if not order.items:
        raise ValueError("empty order")
    ...  # main logic at one indentation level
```

## Conditional expressions

Python's ternary puts the condition in the middle: `value_if_true if condition else value_if_false`.

```python
n = 7
label = "even" if n % 2 == 0 else "odd"
print(label)
print("big" if n > 100 else "medium" if n > 5 else "small")
```

```text title="Output"
odd
medium
```

- Only the chosen branch is evaluated.
- Chaining is right-associative (`a if c1 else b if c2 else d`). More than one level hurts readability; use `if`/`elif` or a dict lookup instead.
- It is an expression, so it works in arguments, returns, comprehensions and lambdas.

<Callout title="Coming from JS">
`cond ? a : b` becomes `a if cond else b`. The reversed order reads like English ("a, if cond, otherwise b") but takes some getting used to.
</Callout>

## The `match` statement

`match` takes a **subject** value and tries a series of `case` **patterns** top to bottom. The first pattern that matches (and whose optional guard is true) runs, and no other case runs. If nothing matches, nothing happens (no error).

A pattern is **not an expression**. It is a small declarative language describing the shape of a value. The same syntax that would build a value (`[x, y]`, `{"k": v}`, `Point(x, y)`) *deconstructs* one in a pattern, binding names along the way. This is the same idea as destructuring in JS, combined with conditional checks.

<Mermaid chart={`flowchart TB
  S["Evaluate subject once"] --> C1{"case 1 pattern<br/>matches?"}
  C1 -->|"yes"| G1{"guard true?<br/>(if any)"}
  G1 -->|"yes"| B1["run case 1 body, done"]
  G1 -->|"no"| C2
  C1 -->|"no"| C2{"case 2 pattern<br/>matches?"}
  C2 -->|"yes"| B2["run case 2 body, done"]
  C2 -->|"no"| W{"case _ ?"}
  W -->|"present"| BW["run wildcard body"]
  W -->|"absent"| N["do nothing"]`} />

The compiler turns patterns into ordinary bytecode checks (there are dedicated instructions such as `MATCH_SEQUENCE`, `MATCH_MAPPING`, `MATCH_CLASS` and `GET_LEN`). It is not a jump table: cases are tested in order, so put specific cases before general ones.

### Literal patterns and the wildcard

```python
def http_status(code):
    match code:
        case 200 | 201 | 204:
            return "ok"
        case 301 | 302:
            return "redirect"
        case 404:
            return "not found"
        case _:
            return "other"

print([http_status(c) for c in (201, 302, 404, 500)])
```

```text title="Output"
['ok', 'redirect', 'not found', 'other']
```

- Literal patterns: numbers, strings, bytes, `None`, `True`, `False` (and since 3.15, a unary `+` before a number is allowed).
- Numbers and strings are compared with **`==`**. `None`, `True` and `False` are compared with **`is`**.
- `_` is the **wildcard**: it matches anything and binds nothing. `case _:` is the default branch.
- `|` makes an **OR pattern**: the case matches if any alternative matches.

The `==` vs `is` rule has visible consequences:

```python
match 1.0:
    case 1: print("1.0 matches literal 1 (==)")
match True:
    case 1: print("True matches 1")
match 1:
    case True: print("never")
    case _: print("1 does not match True (identity for singletons)")
```

```text title="Output"
1.0 matches literal 1 (==)
True matches 1
1 does not match True (identity for singletons)
```

### Capture patterns

A bare name in a pattern is a **capture pattern**: it always matches and binds the value to that name.

```python
match point:
    case (0, y):      # literal 0, capture y
        ...
```

Bindings are ordinary assignments in the enclosing scope, so they remain after the `match` (even from a case that partially matched and then failed, so do not rely on them unless the case succeeded).

### The capture vs constant trap

This is the number one `match` mistake. Coming from `switch`, you might write:

```python
NOT_FOUND = 404
status = 200

match status:
    case NOT_FOUND:
        print("treated as not found!")

print(NOT_FOUND)
```

```text title="Output"
treated as not found!
200
```

`case NOT_FOUND:` is **not** "compare with the constant". It is a capture pattern: it matches anything and **rebinds** `NOT_FOUND` to the subject. The constant has been overwritten with 200.

Python catches the most obvious form of this at compile time, when a capture pattern is followed by more cases:

```python
NOT_FOUND = 404
def check(code):
    match code:
        case NOT_FOUND:
            return "not found"
        case _:
            return "other"
```

```text title="Output"
    case NOT_FOUND:
         ^^^^^^^^^
SyntaxError: name capture 'NOT_FOUND' makes remaining patterns unreachable
```

The rule: **only dotted names are treated as constants (value patterns)**. So use an enum, a class attribute or a module attribute:

```python
from enum import IntEnum
from http import HTTPStatus

class Status(IntEnum):
    OK = 200
    NOT_FOUND = 404

def check(code):
    match code:
        case Status.NOT_FOUND:     # dotted name: compared with ==
            return "not found"
        case HTTPStatus.OK:
            return "ok"
        case _:
            return "other"

print(check(404), check(200), check(500))
```

```text title="Output"
not found ok other
```

If the value is in a plain local or global variable, compare it in a guard instead: `case x if x == limit:`.

### Sequence patterns

Sequence patterns match lists, tuples, `range`, `collections.deque` and other sequences, checking the length and each element. `*name` captures the rest (like JS rest syntax), and `*_` ignores it.

```python
def handle(command):
    match command.split():
        case []:
            return "empty"
        case ["quit" | "exit"]:
            return "bye"
        case ["go", direction]:
            return f"going {direction}"
        case ["drop", *items] if items:
            return f"dropping {items}"
        case ["drop"]:
            return "drop what?"
        case _:
            return f"unknown: {command!r}"

for c in ("", "quit", "go north", "drop sword shield", "drop", "dance now"):
    print(handle(c))
```

```text title="Output"
empty
bye
going north
dropping ['sword', 'shield']
drop what?
unknown: 'dance now'
```

Details:

- `[a, b]` and `(a, b)` mean the same thing in a pattern; both match a list **or** a tuple of length 2.
- **`str`, `bytes` and `bytearray` are deliberately not matched by sequence patterns**, even though they are sequences, because matching `"abc"` as `[a, b, c]` is almost never intended:

```python
match "abc":
    case [*chars]: print("sequence!", chars)
    case _: print("str is not matched as a sequence")
```

```text title="Output"
str is not matched as a sequence
```

- Iterators and generators are not sequences and are not matched (patterns never consume an iterator).
- Only one starred name per sequence pattern.

### Mapping patterns

Mapping patterns match dicts (any `collections.abc.Mapping`). They check that the listed **keys exist** and that their values match sub-patterns. **Extra keys are ignored**, which makes them ideal for JSON payloads. `**rest` captures the remaining keys.

```python
def describe(event):
    match event:
        case {"type": "click", "pos": (x, y)}:
            return f"click at {x},{y}"
        case {"type": "key", "key": str(k), **rest}:
            return f"key {k!r}, extra={rest}"
        case {"type": t}:
            return f"unhandled type {t}"
        case _:
            return "not an event"

print(describe({"type": "click", "pos": (3, 4), "ts": 1}))
print(describe({"type": "key", "key": "a", "shift": True}))
print(describe({"type": "scroll"}))
print(describe([1, 2]))
print(describe({"type": "click", "pos": [3, 4]}))
```

```text title="Output"
click at 3,4
key 'a', extra={'shift': True}
unhandled type scroll
not an event
click at 3,4
```

Note the asymmetry: sequence patterns require an **exact length** (unless starred), mapping patterns only require the **listed keys**. Mapping keys must be literals or dotted value patterns, not captures. A missing key simply fails the case; it never raises `KeyError` (lookups use `.get()` semantics internally).

### Class patterns

A class pattern `ClassName(...)` first checks `isinstance(subject, ClassName)`, then matches attributes:

- **Keyword sub-patterns** `Point(x=0, y=yy)` look up attributes by name.
- **Positional sub-patterns** `Point(0, yy)` are mapped to attribute names through the class's `__match_args__` tuple.

Dataclasses (and named tuples) generate `__match_args__` automatically from their fields:

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float

@dataclass
class Circle:
    center: Point
    r: float

@dataclass
class Rect:
    corner: Point
    w: float
    h: float

print(Point.__match_args__)

def area(shape):
    match shape:
        case Circle(Point(0, 0), r):
            return f"origin circle r={r}"
        case Circle(r=r):
            return 3.14159 * r * r
        case Rect(w=w, h=h) if w == h:
            return f"square {w * h}"
        case Rect(_, w, h):
            return w * h
        case _:
            raise TypeError(f"not a shape: {shape!r}")

print(area(Circle(Point(0, 0), 2)), area(Circle(Point(1, 1), 1)),
      area(Rect(Point(0, 0), 3, 3)), area(Rect(Point(0, 0), 2, 5)))
```

```text title="Output"
('x', 'y')
origin circle r=2 3.14159 square 9 10
```

Patterns nest freely: `Circle(Point(0, 0), r)` checks the type, the nested type, two literal coordinates and captures the radius, all in one line.

For a regular class, define `__match_args__` yourself, otherwise positional sub-patterns fail:

```python
class Vec:
    __match_args__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

match Vec(1, 0):
    case Vec(0, 0): print("zero")
    case Vec(x, 0): print(f"on x-axis at {x}")

class NoArgs:
    def __init__(self): self.a = 1

try:
    match NoArgs():
        case NoArgs(1): pass
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
on x-axis at 1
TypeError: NoArgs() accepts 0 positional sub-patterns (1 given)
```

#### Type checks with built-in classes

Built-in types like `int`, `str`, `float`, `bool`, `list`, `dict` accept **one positional sub-pattern that matches the whole subject**. So `int(n)` means "is an int, bind it to `n`", and `int()` means "is an int":

```python
def kind(v):
    match v:
        case bool(): return "bool"
        case int(n) if n < 0: return "negative int"
        case int() | float(): return "number"
        case str() as s if not s: return "empty string"
        case str(): return "string"
        case [int(), *_] as lst: return f"int list of {len(lst)}"
        case None: return "none"
        case _: return type(v).__name__

print([kind(v) for v in (True, -3, 2.5, "", "hi", [1, 2], None, {1})])
```

```text title="Output"
['bool', 'negative int', 'number', 'empty string', 'string', 'int list of 2', 'none', 'set']
```

`bool()` comes first because `True` is also an instance of `int`. Order matters.

<Callout title="Coming from JS">
A class pattern is `instanceof` plus destructuring in one step. In TypeScript you would write a discriminated union and `switch (shape.kind)`; in Python you can match on the class directly, and type checkers (mypy, Pyright) understand `match` for narrowing and can even warn about non-exhaustive matches over enums and unions when you use `typing.assert_never` in the `case _` branch.
</Callout>

### Guards

A guard is an `if` after the pattern. The pattern matches first (binding names), then the guard is evaluated; if it is false, matching continues with the **next case**. Guards are where you put conditions patterns cannot express, such as comparisons with variables:

```python
LIMIT = 10
def over(n):
    match n:
        case x if x > LIMIT:
            return "over"
        case _:
            return "fine"

print(over(11), over(3))
```

```text title="Output"
over fine
```

### OR patterns and `as`

`|` combines alternatives at any nesting level, and `as` binds the value matched by a sub-pattern:

```python
match ("err", 500):
    case ("ok", code) | ("created", code):
        print("good", code)
    case ("err", 500 | 503 as code):
        print("server error", code)
```

```text title="Output"
server error 500
```

Every alternative of an OR pattern must bind the **same set of names**, otherwise some names would be undefined depending on which side matched:

```python
match (1, 2):
    case (x, 1) | (2, y):
        pass
```

```text title="Output"
    case (x, 1) | (2, y):
         ^^^^^^^^^^^^^^^
SyntaxError: alternative patterns bind different names
```

### Pattern kinds summary

| Pattern | Example | Matches when |
|---|---|---|
| Literal | `404`, `"quit"`, `None` | subject `==` literal (`is` for `None`, `True`, `False`) |
| Capture | `x` | always; binds `x` |
| Wildcard | `_` | always; binds nothing |
| Value | `Status.OK` | subject `==` that dotted name's value |
| Sequence | `[a, b, *rest]` | non-str sequence with matching length and items |
| Mapping | `{"type": t, **rest}` | mapping containing the keys, values match |
| Class | `Point(x, y=0)` | `isinstance` plus attribute sub-patterns |
| OR | two patterns joined by the bar symbol | any alternative matches |
| AS | `[x, y] as pair` | sub-pattern matches; binds the whole value |
| Group | `(pattern)` | parentheses for grouping |

### When to use `match` (and when not)

Use it for:

- Parsing commands, tokens, or ASTs where you branch on **shape**.
- Handling JSON-like payloads and messages by type and structure (webhooks, event buses, LLM tool calls).
- Dispatch over a union of dataclasses or enums.

Do not use it for:

- Simple equality on one value with a few branches; `if`/`elif` or a dict mapping keys to handlers is shorter.
- Range checks (`if code < 300`); patterns cannot express `<` without guards.
- Validation of untrusted input; use Pydantic, which produces useful error messages. `match` silently falls through to `case _`.

## `pass`

`pass` is a statement that does nothing. It exists because Python's grammar requires at least one statement in a block:

```python
def todo(): pass
class Empty: pass
def later(): ...
print(todo(), Empty, later())
```

```text title="Output"
None <class '__main__.Empty'> None
```

`...` (the `Ellipsis` object) works as a placeholder too and is conventional in type stubs and protocols. In an `except` block, a bare `pass` swallows the error; prefer `contextlib.suppress(SomeError)` to make the intent explicit, and never `except: pass` without naming the exception.

## `assert`

`assert condition, message` raises `AssertionError(message)` when `condition` is falsy. It documents and checks **internal invariants**: things that should be impossible if your code is correct.

```python
def withdraw(balance, amount):
    assert amount > 0, f"amount must be positive, got {amount}"
    return balance - amount

print(withdraw(100, 30))
try:
    withdraw(100, -5)
except AssertionError as e:
    print("AssertionError:", e)
print("__debug__ =", __debug__)
```

```text title="Output"
70
AssertionError: amount must be positive, got -5
__debug__ = True
```

Run the same file with `python -O`:

```text title="Output"
70
__debug__ = False
```

The call with `-5` now succeeds silently. Under `-O`, the compiler **removes `assert` statements entirely** (and code inside `if __debug__:` blocks), so the message expression is not even evaluated.

Rules:

- **Never use `assert` for input validation, authorization or anything that must always run.** Someone will deploy with `-O` (or `PYTHONOPTIMIZE=1`) and the check vanishes. Raise `ValueError`, `PermissionError` or a custom exception instead.
- **Never put side effects in an assert** (`assert db.save(x)`): under `-O` the save never happens.
- The message is only evaluated if the assertion fails, so an expensive message is fine.
- **Do not wrap the condition and message in parentheses**: `assert (cond, "msg")` asserts a non-empty tuple, which is always true. Python warns:

```text title="Output"
SyntaxWarning: assertion is always true, perhaps remove parentheses?
```

- In tests, plain `assert` is the norm: **pytest** rewrites assert statements at import time to show detailed failure diffs, so `assert result == expected` gives a readable message without special assertion methods.

<Callout title="Coming from JS">
`assert` is like Node's `assert.ok(cond, msg)`, except it is a language statement and can be stripped by a flag. There is no equivalent of stripping `console.assert` in Node; the closest analogy is build-time removal of dev-only checks in front-end bundlers.
</Callout>

## Interview questions

**How is `match` different from a C or JS `switch`?**
**It does structural pattern matching: cases check types, sequence lengths, mapping keys and attributes, and bind values while matching. It never falls through, and only the first matching case runs.**

**What is the capture vs constant trap in `match`?**
**A bare name in a pattern (`case LIMIT:`) is a capture that matches anything and rebinds the name. Only dotted names (`Color.RED`, `module.CONST`) are compared as values. Use enums or a guard.**

**What is `__match_args__`?**
**A class attribute tuple that maps positional sub-patterns in a class pattern to attribute names. Dataclasses and named tuples generate it automatically.**

**Do mapping patterns require an exact set of keys?**
**No. They require the listed keys to be present with matching values and ignore extra keys. Use `**rest` to capture the rest. Sequence patterns, in contrast, require an exact length unless they use a star.**

**Why does `case [a, b, c]` not match the string `"abc"`?**
**Sequence patterns deliberately exclude `str`, `bytes` and `bytearray` to avoid accidental character-by-character matching.**

**Why should you not validate user input with `assert`?**
**Running Python with `-O` removes all assert statements, so the check silently disappears. Raise a proper exception instead.**

**What does `x if cond else y` evaluate?**
**Only `cond` and the chosen branch. It is an expression, Python's ternary, with the condition in the middle.**

## Recap

- `if`/`elif`/`else` test truthiness; branches do not create scopes. The conditional expression is `a if cond else b`.
- `match` tests patterns in order. Literals compare with `==` (singletons with `is`), bare names capture, `_` matches anything.
- Sequence patterns check length (str is excluded), mapping patterns check only listed keys, class patterns use `isinstance` plus attributes and `__match_args__`.
- Guards add arbitrary conditions; OR alternatives must bind the same names; `as` binds a sub-match.
- Use dotted names or enums for constants in patterns, never bare names.
- `pass` and `...` are placeholders. `assert` is for invariants and tests, and disappears under `-O`.
