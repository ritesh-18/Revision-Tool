---
title: "Copying, Mutability and Identity"
description: What assignment, shallow copies and deep copies really do to references, the classic aliasing traps, and the patterns for writing APIs that don't leak mutable state.
---

Almost every "Python changed my data behind my back" bug comes from one fact: **variables are names bound to objects, and assignment never copies**. Once that model is solid, shallow vs deep copy, the `[[0]*3]*3` trap, mutable default arguments and defensive copying all become the same idea seen from different angles. (The names-and-objects model itself is introduced on [Names, objects and the object model](/docs/python/names-objects-and-the-object-model).)

<Callout type="info">
Snippets run on **CPython 3.14.6**. Identity results for small ints and strings are *CPython details* (caching and interning), not language rules.
</Callout>

## 1. Assignment binds, it never copies

`b = a` makes the name `b` refer to the **same object** as `a`. No new object is created. If that object is mutable, a change through either name is visible through both.

```python
a = [1, 2, 3]
b = a
b.append(4)
print(a, a is b, id(a) == id(b))
```

```text title="Output"
[1, 2, 3, 4] True True
```

Compare with **rebinding**: an operation that creates a new object and points one name at it leaves the other name alone.

```python
a = [1, 2, 3]
b = a
b = b + [4]
print(a, b, a is b)
```

```text title="Output"
[1, 2, 3] [1, 2, 3, 4] False
```

For immutable objects there is no visible difference, because nothing can be mutated: `x += 1` on an int always creates a new int and rebinds.

```python
x = 1000
y = x
x += 1
print(x, y)
```

```text title="Output"
1001 1000
```

Function calls follow exactly the same rule (sometimes called "call by sharing" or "pass by object reference"): the parameter is a new name bound to the caller's object. Mutating it is visible to the caller; rebinding it is not.

```python
def mutate(items):
    items.append("added")
def rebind(items):
    items = ["new list"]
data = ["orig"]
mutate(data)
rebind(data)
print(data)
```

```text title="Output"
['orig', 'added']
```

<Callout title="Coming from JS">
This is identical to how JS treats objects and arrays: `const b = a` shares the reference, and passing an object to a function lets the function mutate it but not reassign the caller's variable. The difference is that in Python **everything** is an object reference, including numbers and strings; they just happen to be immutable, so sharing them is harmless.
</Callout>

## 2. Shallow copy vs deep copy

- A **shallow copy** creates a new container and fills it with **the same references** the original holds. One level deep.
- A **deep copy** recursively copies the container and everything reachable from it, so the result shares no mutable state with the original.

### All the ways to make a shallow copy

Every one of these creates a new outer object and shares the inner ones:

```python
import copy
orig = [1, [2, 3]]
copies = {
    "slice": orig[:],
    "list()": list(orig),
    "copy()": orig.copy(),
    "copy.copy": copy.copy(orig),
    "unpack": [*orig],
}
for name, c in copies.items():
    print(f"{name:10} new outer: {c is not orig}  shared inner: {c[1] is orig[1]}")
```

```text title="Output"
slice      new outer: True  shared inner: True
list()     new outer: True  shared inner: True
copy()     new outer: True  shared inner: True
copy.copy  new outer: True  shared inner: True
unpack     new outer: True  shared inner: True
```

The dict equivalents behave the same:

```python
import copy
d = {"user": {"name": "Asha"}, "tags": ["a"]}
for name, c in {"dict()": dict(d), "d.copy()": d.copy(), "{**d}": {**d}, "copy.copy": copy.copy(d)}.items():
    print(f"{name:10} shared nested: {c['user'] is d['user']}")
```

```text title="Output"
dict()     shared nested: True
d.copy()   shared nested: True
{**d}      shared nested: True
copy.copy  shared nested: True
```

Same for `set(s)`, `s.copy()`, and the dict merge operators.

### The shallow-copy trap in practice

A typical backend scenario: you clone a config template per tenant, tweak the clone, and accidentally modify the template for everyone.

```python
config = {"name": "svc", "tags": ["api"], "limits": {"rps": 100}}
clone = config.copy()
clone["name"] = "svc-2"
clone["tags"].append("beta")
clone["limits"]["rps"] = 5
print(config)
print(clone)
```

```text title="Output"
{'name': 'svc', 'tags': ['api', 'beta'], 'limits': {'rps': 5}}
{'name': 'svc-2', 'tags': ['api', 'beta'], 'limits': {'rps': 5}}
```

Replacing a top-level key (`name`) was isolated; mutating a nested object (`tags`, `limits`) was not, because both dicts point at the same nested objects.

### `copy.deepcopy`

```python
import copy
config = {"name": "svc", "tags": ["api"], "limits": {"rps": 100}}
clone = copy.deepcopy(config)
clone["tags"].append("beta")
clone["limits"]["rps"] = 5
print(config)
print(clone)
```

```text title="Output"
{'name': 'svc', 'tags': ['api'], 'limits': {'rps': 100}}
{'name': 'svc', 'tags': ['api', 'beta'], 'limits': {'rps': 5}}
```

How it works underneath:

- It keeps a **memo dict** mapping `id(original)` to its copy. Before copying an object it checks the memo, so an object referenced twice is copied once (shared structure is **preserved**) and **cycles don't recurse forever**.
- Immutable atoms (ints, strings, `None`, functions, classes) are returned as-is; tuples are only rebuilt if something inside them actually needed copying.
- For other objects it uses, in order: a `__deepcopy__` method, a registered handler in `copyreg`, or the pickle protocol (`__reduce_ex__`), which for plain classes means "make a new instance and deep-copy its `__dict__`".

```python
import copy
shared = [1, 2]
data = {"a": shared, "b": shared}
d2 = copy.deepcopy(data)
print(d2["a"] is d2["b"], d2["a"] is shared)
node = {"name": "root"}
node["self"] = node
n2 = copy.deepcopy(node)
print(n2["self"] is n2, n2 is node)
```

```text title="Output"
True False
True False
```

```python
import copy
t = (1, "x", (2, 3))
print(copy.copy(t) is t, copy.deepcopy(t) is t)
t2 = (1, [2])
print(copy.deepcopy(t2) is t2)
s = "hello"
print(copy.deepcopy(s) is s)
def f(): pass
print(copy.deepcopy(f) is f)
```

```text title="Output"
True True
False
True
True
```

Because it falls back to the pickle protocol, `deepcopy` **fails on objects that can't be pickled**, like locks, sockets, open files and DB connections. A service object holding a client will blow up:

```python
import copy, threading
class Client:
    def __init__(self):
        self.lock = threading.Lock()
try:
    copy.deepcopy(Client())
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
TypeError: cannot pickle '_thread.lock' object
```

### Deep copy is slow; sometimes a different tool is better

```python
import timeit
setup = "import copy, json; data = {'items': [{'id': i, 'tags': ['a', 'b']} for i in range(1000)]}"
print("deepcopy  ", round(timeit.timeit("copy.deepcopy(data)", setup, number=100), 3))
print("json trip ", round(timeit.timeit("json.loads(json.dumps(data))", setup, number=100), 3))
print("shallow   ", round(timeit.timeit("copy.copy(data)", setup, number=100), 5))
```

```text title="Output"
deepcopy   0.266
json trip  0.092
shallow    2e-05
```

`deepcopy` is generic Python code doing memo bookkeeping for every object, so it's slow on big structures. A JSON round trip can be faster for plain JSON-shaped data but loses tuples, sets, datetimes and custom classes. Often the best answer is to **not need a deep copy**: build new structures instead of mutating (`{**cfg, "limits": {**cfg["limits"], "rps": 5}}`), or use immutable data.

<Callout title="Coming from JS">
- `[...arr]`, `arr.slice()`, `{...obj}` and `Object.assign({}, obj)` are all **shallow**, exactly like `list(a)`, `a[:]`, `{**d}` and `d.copy()`.
- `structuredClone(obj)` is the JS deep copy. Like `deepcopy` it handles cycles and shared references, and like `deepcopy` it refuses some things (functions, DOM nodes). Unlike `deepcopy`, it drops class prototypes; `deepcopy` keeps the class and can be customised per class.
- `JSON.parse(JSON.stringify(x))` has the same lossy trade-offs as `json.loads(json.dumps(x))`.
</Callout>

## 3. Nested-structure traps

### `[[0] * 3] * 3`

Sequence repetition copies **references**. For immutable elements that's fine; for mutable ones you get n aliases of one object.

```python
grid = [[0] * 3] * 3
print([id(row) == id(grid[0]) for row in grid])
grid[1][1] = 5
print(grid)
good = [[0] * 3 for _ in range(3)]
good[1][1] = 5
print(good)
```

```text title="Output"
[True, True, True]
[[0, 5, 0], [0, 5, 0], [0, 5, 0]]
[[0, 0, 0], [0, 5, 0], [0, 0, 0]]
```

The inner `[0] * 3` is safe: it repeats references to the immutable int `0`, and assigning `row[0] = 9` rebinds one slot to a different int rather than mutating the shared `0`.

```python
row = [0] * 3
row[0] = 9
print(row)
```

```text title="Output"
[9, 0, 0]
```

The comprehension evaluates `[0] * 3` once **per iteration**, producing independent rows.

<Mermaid chart={`flowchart LR
  G["grid (outer list)"] --> R0["slot 0"]
  G --> R1["slot 1"]
  G --> R2["slot 2"]
  R0 --> INNER["ONE inner list [0, 5, 0]"]
  R1 --> INNER
  R2 --> INNER
`} />

### `dict.fromkeys` with a mutable default

Same trap, different API: the default value object is shared by every key.

```python
d = dict.fromkeys(["a", "b"], [])
d["a"].append(1)
print(d)
d = {k: [] for k in ["a", "b"]}
d["a"].append(1)
print(d)
```

```text title="Output"
{'a': [1], 'b': [1]}
{'a': [1], 'b': []}
```

### Shallow copies of objects

`copy.copy` on an instance makes a new instance whose `__dict__` holds the same attribute values, so list attributes are shared:

```python
import copy
class Job:
    def __init__(self, name, steps):
        self.name = name
        self.steps = steps
j = Job("build", ["lint", "test"])
s = copy.copy(j)
dcp = copy.deepcopy(j)
j.steps.append("deploy")
print(s.steps, dcp.steps)
```

```text title="Output"
['lint', 'test', 'deploy'] ['lint', 'test']
```

## 4. Customising copies: `__copy__` and `__deepcopy__`

Define these when the default behaviour is wrong for your class, typically because an attribute is a resource that must not be shared or can't be copied (sockets, locks, caches), or because copying something is expensive and unnecessary.

- `__copy__(self)` takes no arguments and returns the shallow copy.
- `__deepcopy__(self, memo)` receives the memo dict. Register the new object in `memo` **before** copying children (so cycles resolve to it), and pass `memo` along to nested `copy.deepcopy` calls.

```python
import copy
class Connection:
    def __init__(self, dsn):
        self.dsn = dsn
        self.socket = f"<socket to {dsn}>"
        self.settings = {"timeout": 5}
    def __copy__(self):
        new = Connection.__new__(Connection)
        new.__dict__.update(self.__dict__)
        new.socket = None
        return new
    def __deepcopy__(self, memo):
        new = Connection.__new__(Connection)
        memo[id(self)] = new
        new.dsn = self.dsn
        new.socket = None
        new.settings = copy.deepcopy(self.settings, memo)
        return new
c = Connection("pg://db")
s = copy.copy(c)
d = copy.deepcopy(c)
print(s.socket, s.settings is c.settings)
print(d.socket, d.settings is c.settings)
```

```text title="Output"
None True
None False
```

Both copies get a fresh (unconnected) socket slot; only the deep copy gets its own settings dict. `Connection.__new__(Connection)` creates an instance **without** running `__init__`, which would otherwise open a real connection.

For immutable value objects, Python 3.13 added `copy.replace(obj, **changes)`, a generic "copy with some fields changed" that works on dataclasses, named tuples and any class implementing `__replace__`:

```python
import copy
from dataclasses import dataclass
@dataclass(frozen=True)
class Settings:
    host: str
    port: int = 5432
s = Settings("db")
print(copy.replace(s, port=6543), s)
```

```text title="Output"
Settings(host='db', port=6543) Settings(host='db', port=5432)
```

## 5. Identity vs equality

- `a is b` asks "are these the **same object**?" It compares `id(a) == id(b)` (in CPython, the memory address). It cannot be overridden.
- `a == b` asks "do these have **equal values**?" It calls `a.__eq__(b)`, which each type defines (and you can define for your classes).

```python
a = [1, 2]
b = [1, 2]
print(a == b, a is b)
c = a
print(c is a)
x = None
print(x is None)
```

```text title="Output"
True False
True
True
```

### Why `is None`, never `== None`

`None` is a singleton, so identity is the precise test. `==` can be hijacked by a class's `__eq__` (ORMs and NumPy do this deliberately, returning query expressions or arrays):

```python
class AlwaysEqual:
    def __eq__(self, other):
        return True
x = AlwaysEqual()
print(x == None, x is None)
```

```text title="Output"
True False
```

Use `is` for singletons (`None`, `True`/`False` in rare cases, sentinel objects you created with `object()`), and `==` for everything else.

### Don't use `is` for numbers or strings

CPython caches small ints (-5 to 256) and interns many strings, so `is` sometimes "works" by accident:

```python
a = 256
b = int("256")
print(a is b)
a = 257
b = int("257")
print(a == b, a is b)
s1 = "hello"
s2 = "".join(["hel", "lo"])
print(s1 == s2, s1 is s2)
```

```text title="Output"
True
True False
True False
```

The results depend on the implementation, how the value was created and even compile-time constant folding. Since 3.8 the compiler emits a `SyntaxWarning` when `is` or `is not` is used with literals such as numbers and strings (`x is 257`). Always use `==` for values.

### Identity shortcuts in containers

`in` and `list ==` check identity **before** equality for each element (`x is y or x == y`). That's normally invisible, but it shows up with NaN, which is not equal to itself:

```python
nan = float("nan")
lst = [nan]
print(nan == nan, nan in lst, lst == [nan], [float("nan")] == [float("nan")])
```

```text title="Output"
False True True False
```

### `id()` values get reused

An `id` is unique only **among objects alive at the same time**. Once an object is freed, its address (and therefore its id) can be handed to a new object:

```python
print(id([]) == id([]))
```

```text title="Output"
True
```

The first list is freed right after `id()` returns, and the second list is allocated in the same spot. Never store `id()` values as long-lived keys for objects you don't also keep alive.

<Callout title="Coming from JS">
JS `===` on objects is an identity check, and on primitives a value check. Python splits those cleanly: `is` is always identity, `==` is always value equality (customisable). `Object.is(NaN, NaN)` is `true` in JS; in Python `nan is nan` is also `True` for the same object, but `nan == nan` is `False`, the same as JS `NaN === NaN`.
</Callout>

## 6. Mutable default arguments

Default values are evaluated **once**, when the `def` statement runs, and stored on the function object (`__defaults__`). A mutable default is therefore shared across every call that doesn't pass the argument:

```python
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags
print(add_tag("a"))
print(add_tag("b"))
print(add_tag.__defaults__)
def add_tag_fixed(tag, tags=None):
    if tags is None:
        tags = []
    tags.append(tag)
    return tags
print(add_tag_fixed("a"), add_tag_fixed("b"))
```

```text title="Output"
['a']
['a', 'b']
(['a', 'b'],)
['a'] ['b']
```

The `None` sentinel pattern is the standard fix. In a long-running server this bug is nasty: state leaks **between requests** for as long as the worker process lives. The full story, including the same trap with dataclass fields (`field(default_factory=list)`), is on [Functions and arguments](/docs/python/functions-and-arguments).

<Callout title="Coming from JS">
JS default parameters are evaluated **on every call** (`function f(tags = [])` gets a fresh array each time), so this trap doesn't exist in JS. It's one of the first things that bites JS developers in Python.
</Callout>

## 7. Defensive copying in APIs

Because objects are shared by reference, a class that stores a caller's list, or returns its internal list, lets outside code change its internal state without going through its methods.

**Leaky version:** the caller still holds the same list.

```python
class LeakyOrder:
    def __init__(self, items):
        self.items = items
incoming = ["book"]
o = LeakyOrder(incoming)
incoming.clear()
print(o.items)
```

```text title="Output"
[]
```

**Defensive version:** copy on the way **in**, expose an immutable view on the way **out**.

```python
class Order:
    def __init__(self, items):
        self._items = list(items)
    @property
    def items(self):
        return tuple(self._items)
incoming = ["book", "pen"]
o = Order(incoming)
incoming.append("hacked")
print(o.items)
try:
    o.items.append("x")
except AttributeError as e:
    print("AttributeError:", e)
```

```text title="Output"
('book', 'pen')
AttributeError: 'tuple' object has no attribute 'append'
```

`list(items)` also has a nice side effect: it accepts any iterable (generator, tuple, set) and normalises it.

The same discipline applies to functions. A helper that "normalises" a dict in place surprises callers who still use the original:

```python
def normalise(user):
    user["email"] = user["email"].lower()
    return user
raw = {"email": "A@X.IO"}
clean = normalise(raw)
print(raw, clean is raw)
def normalise_pure(user):
    return {**user, "email": user["email"].lower()}
raw = {"email": "A@X.IO"}
clean = normalise_pure(raw)
print(raw, clean)
```

```text title="Output"
{'email': 'a@x.io'} True
{'email': 'A@X.IO'} {'email': 'a@x.io'}
```

Guidelines:

- A function should **either** mutate its argument and return `None` (like `list.sort`), **or** return a new object and leave the input alone (like `sorted`). Doing both hides the mutation.
- Copy at **trust boundaries** (constructors, public setters, cached values handed out to many callers). Don't copy everywhere; it costs time and memory.
- For caches: if you return a cached mutable object (e.g. a dict from `lru_cache`), one caller mutating it corrupts the cache for everyone. Return immutable data or a copy.

## 8. Immutability patterns

Python has no `const` for objects and no deep freeze, but it has immutable building blocks:

| Need | Immutable choice | Notes |
|---|---|---|
| fixed sequence | `tuple` | shallow: contents may still be mutable |
| set of members | `frozenset` | hashable, supports set algebra |
| record with fields | `typing.NamedTuple` or `@dataclass(frozen=True)` | frozen dataclasses raise on assignment |
| read-only dict view | `types.MappingProxyType` | live view, not a copy |
| text, numbers, bytes | `str`, `int`, `bytes` | already immutable; `bytearray` is the mutable one |

### `types.MappingProxyType`

A read-only **view** over a dict. Writes through the proxy fail; the owner can still change the underlying dict, and the proxy reflects it. This is how class `__dict__` is exposed (`type.__dict__` returns a mappingproxy).

```python
from types import MappingProxyType
_settings = {"env": "prod", "debug": False}
SETTINGS = MappingProxyType(_settings)
print(SETTINGS["env"])
try:
    SETTINGS["debug"] = True
except TypeError as e:
    print("TypeError:", e)
_settings["debug"] = True
print(SETTINGS["debug"])
print(type(SETTINGS.copy()).__name__)
```

```text title="Output"
prod
TypeError: 'mappingproxy' object does not support item assignment
True
dict
```

Use it to publish module-level configuration or registries that other modules should read but not modify. It's shallow: a list stored as a value can still be mutated through the proxy.

### Frozen dataclasses

```python
from dataclasses import dataclass, FrozenInstanceError
@dataclass(frozen=True)
class Money:
    amount: int
    currency: str
m = Money(10, "USD")
try:
    m.amount = 20
except FrozenInstanceError as e:
    print("FrozenInstanceError:", e)
print(hash(m) == hash(Money(10, "USD")))
```

```text title="Output"
FrozenInstanceError: cannot assign to field 'amount'
True
```

Frozen dataclasses are hashable by value, safe to share between threads and coroutines, and safe to cache. To "change" one, create a new instance with `copy.replace` or `dataclasses.replace`.

### Shallow immutability, one more time

Every built-in immutable container is shallow. A tuple containing a list is neither fully immutable nor hashable, and augmented assignment on its mutable element produces the famous "error *and* mutation":

```python
t = ([1],)
try:
    t[0] += [2]
except TypeError as e:
    print("TypeError:", e)
print(t)
```

```text title="Output"
TypeError: 'tuple' object does not support item assignment
([1, 2],)
```

For truly immutable data, make it immutable **all the way down**: tuples of tuples, frozensets, frozen dataclasses whose fields are themselves immutable.

<Callout title="Coming from JS">
- `const` in JS freezes the **binding**, not the object; Python has no `const` at all (a `Final` type hint is checked only by type checkers).
- `Object.freeze` is shallow, like Python's tuple and `MappingProxyType`. Unlike `Object.freeze`, which silently ignores writes in sloppy mode, Python's immutable types always raise.
- There's no built-in equivalent of Immer; the idiomatic approach is building new dicts/tuples with unpacking, or frozen dataclasses with `replace`.
</Callout>

## Interview questions

1. **What does `b = a` do for a list?**
   **It binds a second name to the same list object; no copy is made, so mutations through either name are visible through both.**

2. **What's the difference between a shallow and a deep copy?**
   **A shallow copy creates a new container holding the same element references; a deep copy recursively copies all reachable mutable objects so nothing is shared.**

3. **How does `deepcopy` handle cycles and shared references?**
   **It keeps a memo dict from `id(original)` to copy; already-copied objects are reused, so cycles terminate and shared substructures stay shared in the copy.**

4. **Why does `[[0] * 3] * 3` misbehave, and what's the fix?**
   **The outer `*` repeats a reference to one inner list; use `[[0] * 3 for _ in range(3)]` to create independent rows.**

5. **When should you use `is` instead of `==`?**
   **For identity checks against singletons and sentinels such as `None`; use `==` for value comparison, never `is` for numbers or strings.**

6. **Why is `def f(x=[])` a bug?**
   **Defaults are evaluated once at definition time, so the same list is shared across calls; use `None` as the default and create the list inside the function.**

7. **How do you expose a dict read-only?**
   **Wrap it in `types.MappingProxyType`, a live read-only view; or copy it, or use frozen dataclasses for structured data.**

8. **When would you implement `__deepcopy__`?**
   **When some attributes must not be copied or shared (sockets, locks, caches) or can't be pickled; register the new object in `memo` first and pass `memo` to nested deepcopy calls.**

## Recap

- Names are bound to objects; **assignment and argument passing never copy**. Mutating is shared, rebinding is local.
- Slicing, `list()`, `dict()`, `.copy()`, unpacking and `copy.copy` are all **shallow**: new outer container, shared inner objects.
- `copy.deepcopy` recursively copies using a memo (handles cycles and shared refs), falls back to pickling, and is slow; often building new data is better.
- Repetition (`*`) and `dict.fromkeys` share one mutable object across slots; use comprehensions.
- `__copy__` / `__deepcopy__` customise copying; `copy.replace` (3.13+) copies immutable records with changes.
- `is` tests identity (use for `None`), `==` tests value; small-int and string identity results are CPython accidents.
- Mutable default arguments are evaluated once and shared across calls.
- Copy defensively at boundaries, return immutable views, and reach for `tuple`, `frozenset`, `MappingProxyType` and frozen dataclasses, remembering they are all **shallow**.
