---
title: "asyncio output"
description: Predict the print order of asyncio snippets with tasks, gather, create_task, cancellation, TaskGroup failures and blocking calls.
---

asyncio runs one task at a time on one thread. A task runs until it reaches an `await` that actually **suspends** (a sleep, I/O, or waiting on a future that is not done yet), and then the event loop runs the next ready callback in FIFO order. Every snippet below is deterministic. Where tasks need to wait, they use `await asyncio.sleep(0)`, which yields exactly one turn of the loop, so the output never depends on timing.

Read each snippet, write down the exact output, then open the answer.

<Callout type="info">
  The key difference from JavaScript: in JS, every `await` goes through the microtask queue, even on an already-resolved value. In Python, `await some_coroutine()` is just a function call until something inside it truly suspends.
</Callout>

### Q 1 · Easy

```python
import asyncio

async def greet():
    print("hello")
    return 42

async def main():
    coro = greet()
    print("created", type(coro).__name__)
    print(await coro)

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
created coroutine
hello
42
```

Explanation: Calling an `async def` function runs **none** of its body. It returns a coroutine object, much like calling a generator function. The body only runs when the coroutine is awaited (or wrapped in a task). This is a big difference from JavaScript, where calling an async function runs it synchronously up to the first `await` and returns a Promise. If you forget the `await` in Python, the code silently never runs, apart from a "coroutine was never awaited" warning.

</details>

### Q 2 · Easy

```python
import asyncio

async def step(n):
    print("start", n)
    await asyncio.sleep(0)
    print("end", n)

async def main():
    await step(1)
    await step(2)

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
start 1
end 1
start 2
end 2
```

Explanation: `await` waits for the awaited coroutine to **finish** before moving on. There is only one task here (`main`), so even though `step` yields to the loop at `sleep(0)`, nothing else is waiting to run and `main` simply resumes. Sequential awaits give sequential execution, the same as `await` in a JavaScript loop.

</details>

### Q 3 · Medium

```python
import asyncio

async def step(n):
    print("start", n)
    await asyncio.sleep(0)
    print("end", n)

async def main():
    await asyncio.gather(step(1), step(2))

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
start 1
start 2
end 1
end 2
```

Explanation: `gather` wraps each coroutine in a **task** and schedules them in argument order. Task 1 runs until `sleep(0)` suspends it, then task 2 gets its turn and also suspends, then task 1 resumes, and so on. The output interleaves at every real suspension point. This is like `Promise.all` in JavaScript, except that the coroutines do not start until `gather` schedules them.

</details>

### Q 4 · Medium

```python
import asyncio

async def work(name, ticks):
    for _ in range(ticks):
        await asyncio.sleep(0)
    print("finished", name)
    return name

async def main():
    results = await asyncio.gather(work("slow", 3), work("fast", 1))
    print(results)

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
finished fast
finished slow
['slow', 'fast']
```

Explanation: Tasks **finish** in the order their work completes: "fast" needs one turn of the loop and "slow" needs three. But `gather` returns results in the order the awaitables were **passed in**, not completion order. This is the same as `Promise.all`. If you want results as they complete, use `asyncio.as_completed`.

</details>

### Q 5 · Medium

```python
import asyncio

async def child():
    print("child runs")

async def main():
    asyncio.create_task(child())
    print("task created")
    print("main still running")
    await asyncio.sleep(0)
    print("main after sleep")

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
task created
main still running
child runs
main after sleep
```

Explanation: `create_task` only **schedules** the coroutine. The task cannot start until the currently running task gives up control, which `main` does not do until `await asyncio.sleep(0)`. At that point the loop runs `child` (it was queued first), then resumes `main`. In JavaScript, the body of an async function called without `await` runs immediately up to its first `await`, so `child runs` would print first.

</details>

### Q 6 · Medium

```python
import asyncio

async def say(msg):
    print(msg)

async def main():
    for m in "abc":
        asyncio.create_task(say(m))
    print("scheduled")
    await asyncio.sleep(0)
    print("main resumes")

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
scheduled
a
b
c
main resumes
```

Explanation: The event loop's ready queue is **FIFO**. The three tasks are queued in creation order. When `main` suspends at `sleep(0)`, its own wake-up is queued **behind** them, so all three run to completion before `main` continues. Each `say` finishes in a single step because it never suspends.

</details>

### Q 7 · Medium

```python
import asyncio

async def child():
    print("child start")
    await asyncio.sleep(1)
    print("child end")

async def main():
    asyncio.create_task(child())
    await asyncio.sleep(0)
    print("main done")

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
child start
main done
```

Explanation: `asyncio.run` runs until the **main coroutine** finishes, then cancels every task that is still pending and closes the loop. `child` starts during `main`'s `sleep(0)`, then suspends for one second. `main` finishes immediately, so `child` is cancelled while sleeping and `child end` never prints. A Node.js process, by contrast, stays alive while timers are pending. In Python, fire-and-forget tasks must be awaited or kept in a `TaskGroup`. Also keep a reference to them, because the loop holds tasks only weakly.

</details>

### Q 8 · Medium

```python
import asyncio

async def other():
    print("other task")

async def no_suspend():
    print("no_suspend body")

async def main():
    asyncio.create_task(other())
    await no_suspend()
    print("after no_suspend")
    await asyncio.sleep(0)
    print("end")

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
no_suspend body
after no_suspend
other task
end
```

Explanation: `await no_suspend()` does **not** yield to the event loop. Awaiting a coroutine directly runs it inline, like a function call, and since it never reaches a real suspension point it returns straight away. `other` only gets to run at `sleep(0)`. In JavaScript, every `await` gives up control through the microtask queue, even when the awaited value is already available, so other queued work gets a chance to run at that point. Python switches tasks only at a real suspension.

</details>

### Q 9 · Medium

```python
import asyncio
import time

async def blocker():
    print("blocker start")
    time.sleep(0.2)
    print("blocker end")

async def ticker():
    for i in range(3):
        print("tick", i)
        await asyncio.sleep(0)

async def main():
    await asyncio.gather(blocker(), ticker())

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
blocker start
blocker end
tick 0
tick 1
tick 2
```

Explanation: `time.sleep` is a normal **blocking** call. It holds the only thread, so the event loop cannot switch tasks for 0.2 seconds, and `ticker` cannot even start until `blocker` returns. The order is fixed by scheduling, not timing: `blocker` was scheduled first and never suspends. Blocking calls in async code (synchronous HTTP clients, `time.sleep`, heavy CPU work) freeze every task. Use `await asyncio.sleep` or offload the work with `asyncio.to_thread`. This is the same as a long synchronous loop blocking Node's event loop.

</details>

### Q 10 · Hard

```python
import asyncio

async def worker():
    try:
        print("worker start")
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("worker cancelled")
        raise
    finally:
        print("worker cleanup")

async def main():
    t = asyncio.create_task(worker())
    await asyncio.sleep(0)
    t.cancel()
    print("cancel requested")
    try:
        await t
    except asyncio.CancelledError:
        print("main saw CancelledError")
    print(t.cancelled())

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
worker start
cancel requested
worker cancelled
worker cleanup
main saw CancelledError
True
```

Explanation: `t.cancel()` does not stop the task immediately. It only **requests** cancellation, so `cancel requested` prints first. When the task next runs, `CancelledError` is raised at the `await` where it is suspended. The task's `except` and `finally` blocks run, and re-raising lets the task end in the cancelled state. Awaiting a cancelled task raises `CancelledError` in the awaiter. `CancelledError` inherits from `BaseException`, so a bare `except Exception` does not swallow it. JavaScript promises have no built-in cancellation. `AbortController` is cooperative and opt-in.

</details>

### Q 11 · Hard

```python
import asyncio

async def worker():
    print("worker body")

async def main():
    t = asyncio.create_task(worker())
    t.cancel()
    try:
        await t
    except asyncio.CancelledError:
        print("cancelled before first step")
    print(t.cancelled())

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
cancelled before first step
True
```

Explanation: The task was cancelled before the event loop ever gave it a turn. When its first step runs, the pending cancellation is delivered right away, so the coroutine body **never starts** and `worker body` never prints. Code before the first `await` in a coroutine is therefore not guaranteed to run once you hand it to `create_task`.

</details>

### Q 12 · Hard

```python
import asyncio

async def ok():
    try:
        await asyncio.sleep(1)
        print("ok finished")
    except asyncio.CancelledError:
        print("ok cancelled")
        raise

async def bad():
    await asyncio.sleep(0)
    raise ValueError("boom")

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ok())
            tg.create_task(bad())
            print("tasks scheduled")
        print("never reached")
    except* ValueError as eg:
        print("caught", eg.exceptions)

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
tasks scheduled
ok cancelled
caught (ValueError('boom'),)
```

Explanation: `TaskGroup` (Python 3.11+) is structured concurrency. When one child fails, the group **cancels all the other children**, waits for them to finish, and then raises an `ExceptionGroup` containing the failures. Cancelled siblings are not included. That is why you catch it with `except*` and why `ok` prints `ok cancelled` instead of finishing. Compare this with the next question, where `gather` leaves siblings running. In JavaScript, `Promise.all` rejects on the first failure but cannot stop the other promises.

</details>

### Q 13 · Hard

```python
import asyncio

async def fail():
    await asyncio.sleep(0)
    raise ValueError("bad")

async def slow():
    for _ in range(3):
        await asyncio.sleep(0)
    print("slow finished anyway")
    return "slow"

async def main():
    print(await asyncio.gather(fail(), slow(), return_exceptions=True))
    try:
        await asyncio.gather(fail(), slow())
    except ValueError as e:
        print("gather raised:", e)
    for _ in range(5):
        await asyncio.sleep(0)
    print("main end")

asyncio.run(main())
```

<details>
<summary>Answer</summary>

```text title="Output"
slow finished anyway
[ValueError('bad'), 'slow']
gather raised: bad
slow finished anyway
main end
```

Explanation: With `return_exceptions=True`, `gather` waits for everything and puts exception objects into the result list in argument order. Without it, `gather` raises the **first** exception as soon as it happens, but it does **not cancel** the other awaitables. The second `slow` keeps running in the background and prints after `main` has already handled the error. That is exactly `Promise.all` behaviour, and it is the main reason to prefer `TaskGroup` in new code.

</details>
