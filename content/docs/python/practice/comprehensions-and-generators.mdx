---
title: "Comprehensions and generators"
description: Predict the output of snippets about comprehension scope, generator laziness and exhaustion, yield ordering, send and close.
---

Comprehensions are eager and have their own scope. Generators and iterators are lazy, single-pass and stateful: nothing runs until something asks for the next value, and once a value is consumed it is gone. Most surprises below come from forgetting one of those properties.

Read each snippet, write down the exact output, then open the answer.

### Q 1 · Easy

```python
print([x * x for x in range(6) if x % 2])
print({x % 3 for x in range(10)})
print({k: v for k, v in [("a", 1), ("b", 2), ("a", 3)]})
```

<details>
<summary>Answer</summary>

```text title="Output"
[1, 9, 25]
{0, 1, 2}
{'a': 3, 'b': 2}
```

Explanation: The list comprehension keeps odd `x` (where `x % 2` is truthy) and squares them. The set comprehension collapses duplicates, leaving only the three possible remainders. The dict comprehension assigns keys in order, so the second `"a"` **overwrites** the value but keeps the key's original position. Dicts preserve insertion order, much like a JavaScript `Map`.

</details>

### Q 2 · Easy

```python
print([(a, b) for a in range(2) for b in "xy"])
print([[a * b for b in range(3)] for a in range(1, 3)])
```

<details>
<summary>Answer</summary>

```text title="Output"
[(0, 'x'), (0, 'y'), (1, 'x'), (1, 'y')]
[[0, 1, 2], [0, 2, 4]]
```

Explanation: Multiple `for` clauses in one comprehension nest **left to right**, exactly like nested `for` statements written in the same order, so the first clause is the outer loop. A comprehension **inside** the expression part is different: it builds one inner list per outer item, giving a list of lists.

</details>

### Q 3 · Easy

```python
def noisy(x):
    print("computing", x)
    return x * 2

gen = (noisy(x) for x in range(3))
print("created")
print(next(gen))
print("done")
```

<details>
<summary>Answer</summary>

```text title="Output"
created
computing 0
0
done
```

Explanation: Parentheses make a **generator expression**, which does no work when created. Each `next()` runs the body just far enough to produce one value. Only `noisy(0)` ever runs, and the other two values are never computed. With square brackets, all three `computing` lines would print before `created`.

</details>

### Q 4 · Medium

```python
gen = (x for x in range(3))
print(list(gen))
print(list(gen))
print(sum(gen))
```

<details>
<summary>Answer</summary>

```text title="Output"
[0, 1, 2]
[]
0
```

Explanation: A generator is an **iterator**, and iterators are single-pass. The first `list()` drains it. Later consumers immediately get `StopIteration` and see an empty sequence, so `list` gives `[]` and `sum` gives 0, with no error. This silently breaks code that passes a generator to two functions. JavaScript generators behave the same way once they are done.

</details>

### Q 5 · Medium

```python
it = iter([1, 2, 3, 4, 5])
print(3 in it)
print(list(it))
```

<details>
<summary>Answer</summary>

```text title="Output"
True
[4, 5]
```

Explanation: On a list, `in` is a search that leaves the list alone. On an iterator, `in` has to **consume** items until it finds a match. It used up 1, 2 and 3 to answer `True`, so only 4 and 5 are left.

</details>

### Q 6 · Medium

```python
def gen():
    print("start")
    yield 1
    print("middle")
    yield 2
    print("end")

g = gen()
print("before")
for v in g:
    print("got", v)
```

<details>
<summary>Answer</summary>

```text title="Output"
before
start
got 1
middle
got 2
end
```

Explanation: Calling a generator function runs **none** of its body. It just returns a generator object, which is why `before` prints first. Each iteration resumes the body until the next `yield`, then pauses. After `yield 2` the loop asks once more, the body runs to the end (printing `end`), the function returns, and that `StopIteration` ends the `for` loop. This matches JavaScript `function*` semantics.

</details>

### Q 7 · Medium

```python
def g():
    yield 1
    return "finished"

it = g()
print(next(it))
try:
    next(it)
except StopIteration as e:
    print("StopIteration value:", e.value)
print(list(g()))
```

<details>
<summary>Answer</summary>

```text title="Output"
1
StopIteration value: finished
[1]
```

Explanation: A `return` inside a generator ends the iteration, and the returned value is attached to the `StopIteration` exception as `.value`. Normal consumers like `list()` and `for` swallow the `StopIteration` and **discard** that value. It is only reachable by catching the exception yourself or through `yield from`. JavaScript exposes the same thing as the final `{ value: "finished", done: true }` result.

</details>

### Q 8 · Medium

```python
def inner():
    yield 1
    yield 2
    return "inner done"

def outer():
    result = yield from inner()
    print("result:", result)
    yield 3

print(list(outer()))
```

<details>
<summary>Answer</summary>

```text title="Output"
result: inner done
[1, 2, 3]
```

Explanation: `yield from` forwards every value from `inner` straight to the consumer and evaluates to `inner`'s **return value** once it finishes. The `print` runs while `list()` is still collecting, which is why `result: inner done` appears before the list itself is printed. JavaScript's `yield*` expression evaluates to the delegate's return value in the same way.

</details>

### Q 9 · Medium

```python
def count():
    for i in range(5):
        print("yield", i)
        yield i

g = count()
for x in g:
    if x == 1:
        break
print("resume")
for x in g:
    print("got", x)
    if x == 3:
        break
```

<details>
<summary>Answer</summary>

```text title="Output"
yield 0
yield 1
resume
yield 2
got 2
yield 3
got 3
```

Explanation: `break` stops the loop but does not reset or close the generator, which stays paused at `yield 1`. The second loop calls `iter(g)`, which returns `g` itself, and continues from where it paused, so iteration resumes at 2. Iterating a **list** twice starts from the beginning each time. Iterating the same generator twice continues where it left off.

</details>

### Q 10 · Medium

```python
def show(tag, x):
    print(tag, x)
    return x

evens = filter(lambda x: show("filter", x) % 2 == 0, range(4))
doubled = map(lambda x: show("map", x) * 2, evens)
print("pipeline built")
print(list(doubled))
```

<details>
<summary>Answer</summary>

```text title="Output"
pipeline built
filter 0
map 0
filter 1
filter 2
map 2
filter 3
[0, 4]
```

Explanation: `map` and `filter` are lazy iterators in Python 3. Building the pipeline runs nothing. When `list()` pulls from `map`, `map` pulls from `filter`, which pulls from `range`. Each item flows through the whole chain before the next one starts, so the output **interleaves** stages and odd values never reach `map`. JavaScript's `arr.filter().map()` is eager and would print all `filter` lines first, then all `map` lines.

</details>

### Q 11 · Hard

```python
it = iter(range(5))
pairs = list(zip(it, "ab"))
print(pairs)
print(next(it))
```

<details>
<summary>Answer</summary>

```text title="Output"
[(0, 'a'), (1, 'b')]
3
```

Explanation: `zip` pulls from its arguments **left to right** on each round. On the third round it successfully takes `2` from `it`, then finds `"ab"` exhausted and stops. That `2` has already been consumed and is silently lost, so the next value from `it` is 3. Put the shortest iterable first (or use `zip(..., strict=True)` to catch length mismatches) when the leftover items matter.

</details>

### Q 12 · Hard

```python
nums = [1, 2, 3]
limit = 2
gen = (n for n in nums if n > limit)

nums = [10, 20]
limit = 0
print(list(gen))
```

<details>
<summary>Answer</summary>

```text title="Output"
[1, 2, 3]
```

Explanation: A generator expression evaluates its **outermost iterable immediately**, when it is created, so it holds the original `[1, 2, 3]` list object. Rebinding `nums` afterwards does not matter. Everything else, including the `if` condition, runs lazily, so `limit` is looked up at consumption time, when it is already 0. The result is every element of the original list.

</details>

### Q 13 · Hard

```python
def acc():
    total = 0
    while True:
        x = yield total
        print("received", x)
        total += x

g = acc()
print(next(g))
print(g.send(5))
print(g.send(10))
```

<details>
<summary>Answer</summary>

```text title="Output"
0
received 5
5
received 10
15
```

Explanation: `x = yield total` does two things at two different times. It first **emits** `total` and pauses. When the generator is resumed, the whole `yield` expression evaluates to the value passed in. `next(g)` runs up to the first `yield` and emits 0. `send(5)` resumes, so `x` becomes 5. The generator prints, updates `total`, loops, and emits 5 at the next `yield`, which becomes the return value of `send`. The value you send is always answered by the **next** value yielded. JavaScript's `gen.next(5)` works the same way.

</details>

### Q 14 · Hard

```python
def g():
    x = yield
    print(x)

gen = g()
gen.send("hi")
```

<details>
<summary>Answer</summary>

```text title="Output"
Traceback (most recent call last):
  ...
TypeError: can't send non-None value to a just-started generator
```

Explanation: A new generator is paused **before** its first line, not at a `yield`, so there is no `yield` expression to receive the value. Python refuses with `TypeError`, and you must "prime" the generator with `next(gen)` or `gen.send(None)` first. JavaScript silently discards the argument to the first `next()` instead of raising.

</details>

### Q 15 · Hard

```python
def g():
    try:
        yield 1
        yield 2
    finally:
        print("cleanup")

gen = g()
print(next(gen))
gen.close()
print("after close")
print(next(gen, "exhausted"))
```

<details>
<summary>Answer</summary>

```text title="Output"
1
cleanup
after close
exhausted
```

Explanation: `close()` raises `GeneratorExit` **inside** the generator at the paused `yield`. The exception unwinds through the `try`, so `finally` runs and prints `cleanup` before `close()` returns. The generator is then finished, so `next(gen, default)` returns the default instead of raising `StopIteration`. CPython also calls `close()` when an unfinished generator is garbage-collected, which is why `finally` in generators is a reasonable place for cleanup. This corresponds to `gen.return()` in JavaScript.

</details>

### Q 16 · Hard

```python
fs = [lambda: i for i in range(3)]
gs = (lambda: i for i in range(3))

print([f() for f in fs])
print([g() for g in gs])
```

<details>
<summary>Answer</summary>

```text title="Output"
[2, 2, 2]
[0, 1, 2]
```

Explanation: Both versions create lambdas that close over the same `i` (late binding). The list comprehension runs to completion first, so every lambda sees the final `i`, which is 2. The generator expression is lazy: the outer comprehension takes one lambda and **calls it immediately**, while the generator is still paused with `i` at that iteration's value. Same closures, different timing, different output.

</details>
