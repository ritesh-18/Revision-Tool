---
title: "OOP, MRO and dunders"
description: Predict the output of snippets about class versus instance attributes, MRO and super chains, attribute hooks and special methods.
---

Attribute lookup in Python follows a fixed algorithm: data descriptors on the type, then the instance `__dict__`, then the class and its bases in MRO order, and finally `__getattr__`. Operators and built-ins such as `len()` look up dunder methods **on the type**, not the instance. Most questions here are that algorithm in disguise.

Read each snippet, write down the exact output, then open the answer.

### Q 1 · Easy

```python
class Dog:
    sound = "woof"

a, b = Dog(), Dog()
a.sound = "yip"
print(a.sound, b.sound, Dog.sound)

Dog.sound = "arf"
print(a.sound, b.sound)
```

<details>
<summary>Answer</summary>

```text title="Output"
yip woof woof
yip arf
```

Explanation: `sound` is a **class attribute**, stored once on `Dog`. Assigning `a.sound = ...` creates an **instance attribute** in `a.__dict__` that shadows the class one for `a` only. `b` has no instance attribute, so reads fall through to the class and see the change to `Dog.sound`. This resembles a property on a JavaScript prototype being shadowed by an own property.

</details>

### Q 2 · Easy

```python
class Cart:
    items = []

    def add(self, x):
        self.items.append(x)

c1, c2 = Cart(), Cart()
c1.add("apple")
print(c2.items)
print(c1.items is Cart.items)
```

<details>
<summary>Answer</summary>

```text title="Output"
['apple']
True
```

Explanation: `self.items` finds no instance attribute, so the lookup falls through to the class attribute, and `.append` **mutates** that single shared list. No assignment to `self.items` ever happens, so no per-instance list is created. Every `Cart` shares one cart. Initialise mutable state in `__init__` (`self.items = []`). This is the class-level version of the mutable default argument trap.

</details>

### Q 3 · Easy

```python
class P:
    def __init__(self, x):
        self.x = x
    def __repr__(self):
        return f"P({self.x!r})"
    def __str__(self):
        return f"point {self.x}"

p = P("a")
print(p)
print([p])
print(f"{p} {p!r}")
```

<details>
<summary>Answer</summary>

```text title="Output"
point a
[P('a')]
point a P('a')
```

Explanation: `print` and f-strings call `str()`, which uses `__str__`. Containers always format their **elements** with `repr()`, so the list shows `P('a')`. The `!r` conversion forces `repr()`. Inside `__repr__`, `!r` on `self.x` adds the quotes around the string. JavaScript has only `toString()` for this. Python keeps a human-readable form and a developer form separate.

</details>

### Q 4 · Easy

```python
class Base:
    def __init__(self):
        self.ready = True

class Child(Base):
    def __init__(self):
        self.name = "c"

c = Child()
print(c.name)
print(hasattr(c, "ready"))
```

<details>
<summary>Answer</summary>

```text title="Output"
c
False
```

Explanation: Defining `__init__` in a subclass **replaces** the parent's, and Python never calls the parent's initialiser automatically. `Base.__init__` never runs, so `ready` is never set. You have to call `super().__init__()` explicitly. JavaScript is stricter: a derived class constructor must call `super()` before using `this`, otherwise it throws.

</details>

### Q 5 · Medium

```python
class Key:
    def __init__(self, v):
        self.v = v
    def __eq__(self, other):
        return isinstance(other, Key) and self.v == other.v

print(Key(1) == Key(1))
print(Key.__hash__)
try:
    {Key(1)}
except TypeError as e:
    print("TypeError:", e)
```

<details>
<summary>Answer</summary>

```text title="Output"
True
None
TypeError: cannot use 'Key' as a set element (unhashable type: 'Key')
```

Explanation: If a class defines `__eq__` without defining `__hash__`, Python sets `__hash__` to `None`. Objects that compare equal must have equal hashes, and the default identity-based hash would break that rule, so Python makes the class **unhashable** instead. Instances can no longer be set members or dict keys. Define `__hash__` from the same fields used in `__eq__` (or use `@dataclass(frozen=True)`). JavaScript `Set` and `Map` always use identity for objects and have no equivalent hook. (The wording of the message is from Python 3.14. Older versions print just `unhashable type: 'Key'`.)

</details>

### Q 6 · Medium

```python
class A:
    def __init__(self, v):
        self.v = v
    def __eq__(self, other):
        print("A.__eq__ called")
        return self.v == other.v

a1, a2 = A(1), A(1)
print(a1 != a2)
```

<details>
<summary>Answer</summary>

```text title="Output"
A.__eq__ called
False
```

Explanation: The class defines no `__ne__`, but the default `object.__ne__` calls `__eq__` and inverts the result (unless it is `NotImplemented`). So `!=` still goes through the custom `__eq__`, which prints and returns `True`, and the final answer is `False`. You only need to define `__ne__` yourself when it should not be the exact opposite of `__eq__`.

</details>

### Q 7 · Medium

```python
class A:
    def who(self): return "A"

class B(A):
    def who(self): return "B"

class C(A):
    def who(self): return "C"

class D(B, C):
    pass

print(D().who())
print([k.__name__ for k in D.__mro__])
```

<details>
<summary>Answer</summary>

```text title="Output"
B
['D', 'B', 'C', 'A', 'object']
```

Explanation: Python builds a single linear **method resolution order** with the C3 algorithm. Bases are searched in the order listed (`B` before `C`), and a shared ancestor (`A`) comes only after **all** of its subclasses. Attribute lookup walks this list and stops at the first class defining `who`, which is `B`. JavaScript has only single prototype chains, so diamonds cannot occur there.

</details>

### Q 8 · Medium

```python
class Lazy:
    def __init__(self):
        self.real = 1
    def __getattr__(self, name):
        return f"<missing {name}>"

o = Lazy()
print(o.real)
print(o.other)
print(getattr(o, "x", "default"))
```

<details>
<summary>Answer</summary>

```text title="Output"
1
<missing other>
<missing x>
```

Explanation: `__getattr__` is a **fallback**: it is called only after normal lookup (instance dict, class, bases) fails with `AttributeError`. `real` is found normally, so the hook is never used for it. For missing names the hook returns a value, so `getattr(o, "x", "default")` never sees an `AttributeError` and never uses its default. This is similar to a JavaScript `Proxy` `get` trap, except that it only fires for missing properties.

</details>

### Q 9 · Medium

```python
class Money:
    def __init__(self, c):
        self.c = c
    def __add__(self, other):
        return Money(self.c + other.c)
    def __radd__(self, other):
        print("radd with", other)
        return self if other == 0 else NotImplemented
    def __repr__(self):
        return f"Money({self.c})"

print(sum([Money(1), Money(2)]))
```

<details>
<summary>Answer</summary>

```text title="Output"
radd with 0
Money(3)
```

Explanation: `sum` starts from `0`, so its first step is `0 + Money(1)`. `int.__add__` does not know `Money` and returns `NotImplemented`, so Python tries the **reflected** method on the right operand: `Money(1).__radd__(0)`. That returns `Money(1)`. After that, `Money(1) + Money(2)` uses the normal `__add__`. The reflected-operand protocol is how Python implements mixed-type operators without JavaScript's implicit coercion.

</details>

### Q 10 · Medium

```python
class Counter:
    count = 0
    def hit(self):
        self.count += 1

a, b = Counter(), Counter()
a.hit()
a.hit()
b.hit()
print(a.count, b.count, Counter.count)
print(a.__dict__, Counter.__dict__["count"])
```

<details>
<summary>Answer</summary>

```text title="Output"
2 1 0
{'count': 2} 0
```

Explanation: `self.count += 1` means `self.count = self.count + 1`. The **read** finds the class attribute (0) the first time, but the **write** always goes to the instance `__dict__`. Each instance therefore gets its own counter, and the class attribute stays 0. Compare this with the `Cart` question: a mutating method call shares state, while an augmented assignment on an int shadows it.

</details>

### Q 11 · Hard

```python
class A:
    def hello(self):
        print("A")

class B(A):
    def hello(self):
        print("B enter")
        super().hello()
        print("B exit")

class C(A):
    def hello(self):
        print("C enter")
        super().hello()
        print("C exit")

class D(B, C):
    def hello(self):
        print("D enter")
        super().hello()
        print("D exit")

D().hello()
```

<details>
<summary>Answer</summary>

```text title="Output"
D enter
B enter
C enter
A
C exit
B exit
D exit
```

Explanation: `super()` does not mean "my parent class". It means "the **next class after mine in the MRO of the instance's type**". For a `D` instance the MRO is `D, B, C, A, object`, so `super()` inside `B.hello` reaches `C`, not `A`, even though `B` does not inherit from `C`. Every method runs exactly once and `A` runs last. This cooperative chaining only works if every class in the chain calls `super()`. JavaScript's `super` is fixed to the lexical parent.

</details>

### Q 12 · Hard

```python
class A: pass
class B(A): pass

try:
    class C(A, B): pass
except TypeError as e:
    print(e)
```

<details>
<summary>Answer</summary>

```text title="Output"
Cannot create a consistent method resolution order (MRO) for bases A, B
```

Explanation: `class C(A, B)` asks for `A` to come before `B` in the MRO, but `B` is a subclass of `A`, and C3 requires every class to come before its own bases. Both constraints cannot hold at once, so class creation fails with a `TypeError` at the moment the `class` statement runs. Writing `class C(B, A)` (or just `class C(B)`) works.

</details>

### Q 13 · Hard

```python
class Spy:
    def __init__(self):
        self.x = 1
    def __getattribute__(self, name):
        print("get", name)
        return super().__getattribute__(name)
    def __getattr__(self, name):
        print("fallback", name)
        return 0

s = Spy()
print(s.x)
print(s.y)
```

<details>
<summary>Answer</summary>

```text title="Output"
get x
1
get y
fallback y
0
```

Explanation: `__getattribute__` runs for **every** attribute access through the instance. `__getattr__` runs only if `__getattribute__` raises `AttributeError`. For `s.x` the normal lookup succeeds. For `s.y` it raises, so Python calls the fallback. Note that `self.x = 1` in `__init__` uses `__setattr__`, not `__getattribute__`, so it prints nothing. Inside `__getattribute__` you must delegate to `super()`, because reading `self.anything` there would call the hook again and recurse forever.

</details>

### Q 14 · Hard

```python
class Box:
    def __len__(self):
        return 1

b = Box()
b.__len__ = lambda: 99
print(len(b), b.__len__())
```

<details>
<summary>Answer</summary>

```text title="Output"
1 99
```

Explanation: Built-ins and operators look up special methods **on the type**, bypassing the instance dict. `len(b)` calls `type(b).__len__(b)` and gets 1. The explicit attribute access `b.__len__` follows normal lookup, finds the instance attribute first, and calls the lambda. This is why monkey-patching dunders onto single instances does not work, and why you must define them on the class.

</details>

### Q 15 · Hard

```python
class Temp:
    def __init__(self):
        self.__dict__["c"] = 100

    @property
    def c(self):
        return 0

t = Temp()
print(t.c, t.__dict__["c"])
```

<details>
<summary>Answer</summary>

```text title="Output"
0 100
```

Explanation: `property` is a **data descriptor** (it defines `__get__` and `__set__`), and data descriptors on the class take priority over the instance `__dict__`. Even though the instance dict holds `c = 100`, `t.c` calls the property getter. A plain function or class attribute (a non-data descriptor or plain value) would be shadowed by the instance dict instead. This precedence rule is what makes properties reliable.

</details>

### Q 16 · Hard

```python
class A:
    def __init__(self):
        self.__secret = 1

a = A()
print(a.__dict__)
try:
    print(a.__secret)
except AttributeError as e:
    print("AttributeError:", e)
print(a._A__secret)
```

<details>
<summary>Answer</summary>

```text title="Output"
{'_A__secret': 1}
AttributeError: 'A' object has no attribute '__secret'
1
```

Explanation: Names with two leading underscores (and at most one trailing underscore) that appear **inside a class body** are rewritten by the compiler to `_ClassName__name`. This is name mangling, meant to avoid accidental clashes in subclasses, not to provide privacy. The access `a.__secret` is outside the class, so it is not mangled and finds nothing, while the mangled name works. JavaScript's `#private` fields are truly inaccessible from outside. Python's are not.

</details>
