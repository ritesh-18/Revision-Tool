title: "Exceptions and context managers"
description: Predict the output of snippets about try/except/else/finally ordering, finally overriding return, exception chaining and with blocks.
---

These questions are about **control flow during failure**: the order in which `try`, `except`, `else` and `finally` blocks run, what `finally` can override, how Python chains one exception onto another, and how `with` blocks call `__enter__` and `__exit__`.

Read each snippet, write down the exact output, then open the answer. Tracebacks are trimmed: `...` replaces the file and line frames.

### Q 1 · Easy

```python
def run(x):
    try:
        print("try")
        r = 10 / x
    except ZeroDivisionError:
        print("except")
    else:
        print("else", r)
    finally:
        print("finally")

run(2)
run(0)
```

<details>
<summary>Answer</summary>

```text title="Output"
try
else 5.0
finally
try
except
finally
```

Explanation: `else` runs only when the `try` block finished **without** an exception, and `finally` runs in every case, last. Putting success-only code in `else` instead of at the end of `try` keeps the `except` from accidentally catching errors raised by that code. JavaScript's `try/catch/finally` has no `else` clause.

</details>

### Q 2 · Easy

```python
try:
    int("x")
except Exception:
    print("Exception")
except ValueError:
    print("ValueError")

try:
    {}["k"]
except LookupError as e:
    print(type(e).__name__, e)
```

<details>
<summary>Answer</summary>

```text title="Output"
Exception
KeyError 'k'
```

Explanation: `except` clauses are tested **top to bottom** and the first one that matches wins. A clause matches if the exception is an instance of that class or any subclass. `ValueError` is a subclass of `Exception`, so the broad clause catches it and the specific one is dead code. Always order clauses from specific to general. `KeyError` is a subclass of `LookupError`, so the second handler catches it, and `str()` of a `KeyError` shows the key with quotes.

</details>

### Q 3 · Medium

```python
def f():
    try:
        return "try"
    finally:
        print("finally runs")

print(f())
```

<details>
<summary>Answer</summary>

```text title="Output"
finally runs
try
```

Explanation: `return "try"` evaluates its value and then, before the function actually returns, the `finally` block runs. The `print` therefore happens first, and only afterwards does the caller receive `"try"` and print it. JavaScript behaves the same way here.

</details>

### Q 4 · Medium

```python
def f():
    x = [1]
    try:
        return x
    finally:
        x.append(2)

def g():
    x = 1
    try:
        return x
    finally:
        x = 2

print(f(), g())
```

<details>
<summary>Answer</summary>

```text title="Output"
[1, 2] 1
```

Explanation: The return value is computed and saved **before** `finally` runs. In `f` the saved value is a reference to the list, so mutating the list in `finally` changes what the caller sees. In `g` the saved value is the int object 1. Rebinding the local `x` to 2 afterwards does not change the object that was already saved for return. Mutation versus rebinding again.

</details>

### Q 5 · Medium

```python
try:
    {}["id"]
except KeyError:
    raise ValueError("bad payload")
```

<details>
<summary>Answer</summary>

```text title="Output"
Traceback (most recent call last):
  ...
KeyError: 'id'

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  ...
ValueError: bad payload
```

Explanation: Raising inside an `except` block sets the new exception's `__context__` to the one being handled. This is **implicit chaining**. The traceback prints the original error first, then "During handling of the above exception, another exception occurred:", then the new one. The wording tells the reader the second error may be an accident in the handler. JavaScript errors have no automatic chaining (only the opt-in `cause` option).

</details>

### Q 6 · Medium

```python
def load():
    try:
        int("abc")
    except ValueError as e:
        raise RuntimeError("config broken") from e

try:
    load()
except RuntimeError as err:
    print(repr(err))
    print(repr(err.__cause__))
    print(err.__suppress_context__)
```

<details>
<summary>Answer</summary>

```text title="Output"
RuntimeError('config broken')
ValueError("invalid literal for int() with base 10: 'abc'")
True
```

Explanation: `raise ... from e` is **explicit chaining**. It sets `__cause__` to the original exception and `__suppress_context__` to `True`, so if this went uncaught the traceback would say "The above exception was the direct cause of the following exception:" instead of the "During handling" wording. This is the Python equivalent of `new Error("config broken", { cause: e })` in JavaScript.

</details>

### Q 7 · Medium

```python
class CM:
    def __init__(self, name):
        self.name = name
    def __enter__(self):
        print("enter", self.name)
        return self.name.upper()
    def __exit__(self, exc_type, exc, tb):
        print("exit", self.name, exc_type)
        return False

with CM("a") as x, CM("b") as y:
    print("body", x, y)
```

<details>
<summary>Answer</summary>

```text title="Output"
enter a
enter b
body A B
exit b None
exit a None
```

Explanation: `as` binds the **return value of `__enter__`**, not the context manager object, so `x` is `"A"`. A `with` statement with several managers is the same as nested `with` blocks: they are entered left to right and exited in **reverse** order, like a stack. With no exception, `__exit__` receives three `None`s. The closest JavaScript feature is `using` declarations with `Symbol.dispose`, which also dispose in reverse order.

</details>

### Q 8 · Hard

```python
def f():
    try:
        return "try"
    finally:
        return "finally"

print(f())
```

<details>
<summary>Answer</summary>

```text title="Output"
main.py:5: SyntaxWarning: 'return' in a 'finally' block
  return "finally"
finally
```

Explanation: A `return` inside `finally` **replaces** the pending return value, so the caller gets `"finally"`. Since Python 3.14 the compiler also emits a `SyntaxWarning` for this (PEP 765), because `return`, `break` or `continue` in a `finally` block is almost always a bug. The warning is printed once when the file is compiled, before any output. Older versions print only `finally`.

</details>

### Q 9 · Hard

```python
def f():
    try:
        raise ValueError("lost")
    finally:
        return "swallowed"

print(f())
```

<details>
<summary>Answer</summary>

```text title="Output"
main.py:5: SyntaxWarning: 'return' in a 'finally' block
  return "swallowed"
swallowed
```

Explanation: When `finally` executes a `return`, any exception that was propagating is **discarded**. The `ValueError` disappears without a trace and the function returns normally. This is the main reason PEP 765 added the `SyntaxWarning` you see at the top. JavaScript behaves the same way (a `return` in `finally` swallows a thrown error) but gives no warning.

</details>

### Q 10 · Hard

```python
try:
    int("abc")
except ValueError:
    raise LookupError("not found") from None
```

<details>
<summary>Answer</summary>

```text title="Output"
Traceback (most recent call last):
  ...
LookupError: not found
```

Explanation: `from None` sets `__suppress_context__` to `True` without setting a cause, so the traceback shows **only** the new exception. The original `ValueError` is still stored in `__context__` for debugging, but it is not printed. Use this when the low-level error is an implementation detail that would only confuse the caller.

</details>

### Q 11 · Hard

```python
class Suppress:
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc, tb):
        print("exit saw", exc_type.__name__)
        return exc_type is KeyError

for key in ["a", "b"]:
    with Suppress():
        if key == "a":
            raise KeyError(key)
        raise ValueError(key)
    print("after with", key)
print("end")
```

<details>
<summary>Answer</summary>

```text title="Output"
exit saw KeyError
after with a
exit saw ValueError
Traceback (most recent call last):
  ...
ValueError: b
```

Explanation: If `__exit__` returns a **truthy** value, the exception is suppressed and execution continues after the `with` block. For `"a"` it returns `True` for the `KeyError`, so `after with a` runs. For `"b"` it returns `False` for the `ValueError`, so the exception propagates out of the loop and `end` never prints. This is exactly how `contextlib.suppress` works. Returning `None` (no `return` at all) also means "do not suppress".

</details>

### Q 12 · Hard

```python
from contextlib import contextmanager

@contextmanager
def tag(name):
    print(f"<{name}>")
    try:
        yield
    except ZeroDivisionError:
        print("handled inside")
    finally:
        print(f"</{name}>")

with tag("a"):
    with tag("b"):
        1 / 0
    print("after b")
print("done")
```

<details>
<summary>Answer</summary>

```text title="Output"
<a>
<b>
handled inside
</b>
after b
</a>
done
```

Explanation: `@contextmanager` turns a generator into a context manager. Code before `yield` is `__enter__`. When the `with` body raises, the exception is **thrown into the generator at the `yield`** using `gen.throw()`. The inner `tag("b")` catches it, so its generator finishes normally, which tells `__exit__` to suppress the exception. The outer block therefore never sees an error, and both closing tags and `after b` print in order.

</details>

### Q 13 · Hard

```python
try:
    raise ExceptionGroup("batch", [
        ValueError("v1"), TypeError("t1"), ValueError("v2"),
    ])
except* ValueError as eg:
    print("values:", [str(e) for e in eg.exceptions])
except* TypeError as eg:
    print("types:", [str(e) for e in eg.exceptions])
print("after")
```

<details>
<summary>Answer</summary>

```text title="Output"
values: ['v1', 'v2']
types: ['t1']
after
```

Explanation: `except*` (Python 3.11+) splits an `ExceptionGroup`. Unlike plain `except`, **every** matching clause runs, and each receives a sub-group containing only its matching exceptions. Both `ValueError`s go to the first clause and the `TypeError` to the second. Because nothing is left unhandled, execution continues. This is what `asyncio.TaskGroup` raises when several tasks fail. JavaScript's closest relative is `AggregateError` from `Promise.any`, but it has no matching syntax.

</details>
