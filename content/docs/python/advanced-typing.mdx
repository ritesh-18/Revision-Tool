This page covers the parts of Python's type system you need for library-quality code: generic functions and classes, variance, structural typing, typed dicts, typing decorators, and the special forms that FastAPI and Pydantic are built on. If you know TypeScript generics well, most of the ideas carry over. Where they don't, it is usually because **Python classes are nominal by default** and because **annotations exist at runtime**.

<Callout type="info">
Runtime snippets ran on **CPython 3.14.6**. Checker output is from **mypy 2.4.0** and **pyright 1.1.414**. File paths are shortened. A `reveal_type` call in a snippet that is also executed was imported from `typing`, which prints `Runtime type is '...'` to stderr.
</Callout>

## Generics

A generic function or class is parameterised by a **type variable**: a placeholder that the checker solves at each call site.

### Old style: `TypeVar` and `Generic`

Before Python 3.12 you declared type variables as module-level objects and listed them in `Generic[...]`:

```python title="generics_old.py"
from typing import TypeVar, Generic

T = TypeVar("T")

def first_old(items: list[T]) -> T:
    return items[0]

class OldBox(Generic[T]):
    def __init__(self, item: T) -> None:
        self.item = item
```

It works, but it is clumsy: the `TypeVar` lives in module scope (so its scope is unclear), the name must be repeated as a string, and variance has to be declared by hand.

### New style: PEP 695 (Python 3.12+)

PEP 695 added type-parameter lists in square brackets, right where TypeScript puts angle brackets:

```python title="generics_new.py"
def first[T](items: list[T]) -> T:
    return items[0]

class Box[T]:
    def __init__(self, item: T) -> None:
        self.item = item
    def get(self) -> T:
        return self.item

reveal_type(first([1, 2, 3]))
reveal_type(Box("hi").get())
b: Box[int] = Box("oops")
```

```text title="mypy output"
generics_new.py:12: error: Argument 1 to "Box" has incompatible type "str"; expected "int"  [arg-type]
```


What happens at runtime: the interpreter creates real `TypeVar` objects scoped to the function or class, stores them in `__type_params__`, and makes the class inherit from `Generic` for you.

```python title="generics_runtime.py"
def first[T](items: list[T]) -> T:
    return items[0]
class Box[T]:
    def __init__(self, item: T) -> None:
        self.item = item
print(first.__type_params__)
print(Box.__type_params__, Box.__mro__)
print(Box[int], Box[int]("x").item)
T = first.__type_params__[0]
print(type(T), T.__name__)
```

```text title="Output"
(T,)
(T,) (<class '__main__.Box'>, <class 'typing.Generic'>, <class 'object'>)
__main__.Box[int] x
<class 'typing.TypeVar'> T
```

Note `Box[int]("x")` runs fine and stores a string. Generic parameters are never checked at runtime.

Python 3.13 added **defaults for type parameters** (PEP 696): `class Box[T = str]: ...`, like TypeScript's `class Box<T = string>`.

<Callout title="Coming from JS">
`def first[T](items: list[T]) -> T` is `function first<T>(items: T[]): T`. Differences: there is no explicit call-site instantiation like `first<number>(...)` for functions (the checker always infers), but you *can* write `Box[int](...)` for classes. The default variance is also different: TypeScript checks generic types structurally and mostly bivariantly for methods, while Python checks each type parameter as invariant, covariant or contravariant (next section). Finally, Python has no conditional types, mapped types or `keyof`. The type system is less of a programming language and more of a fixed vocabulary.
</Callout>

### Bounds and constraints

A **bound** says "T must be a subtype of X" (TypeScript's `T extends X`). A **constraint** says "T must be exactly one of these types".

```python title="bounds.py"
from collections.abc import Hashable
from decimal import Decimal

def dedupe[H: Hashable](items: list[H]) -> set[H]:       # bound
    return set(items)

def total[N: (int, Decimal)](xs: list[N]) -> N:           # constraints
    return sum(xs[1:], xs[0])

reveal_type(dedupe(["a", "b"]))
dedupe([[1], [2]])
reveal_type(total([1, 2]))
reveal_type(total([Decimal("1.5")]))
total([1.5, 2.5])
```

```text title="mypy output"
bounds.py:10: note: Revealed type is "set[str]"
bounds.py:11: error: Value of type variable "H" of "dedupe" cannot be "list[int]"  [type-var]
bounds.py:12: note: Revealed type is "int"
bounds.py:13: note: Revealed type is "decimal.Decimal"
bounds.py:14: error: Value of type variable "N" of "total" cannot be "float"  [type-var]
```

Lists are unhashable, so `list[int]` does not satisfy the `Hashable` bound. The old-style spellings are `TypeVar("H", bound=Hashable)` and `TypeVar("N", int, Decimal)`.

The subtle difference: with a **bound**, the checker solves T to the *actual* type passed (a subclass stays a subclass). With **constraints**, T is solved to one of the *listed* types, never a subclass of them. Use constraints for things like `AnyStr` (`str` or `bytes`, never mixed). Use a bound almost everywhere else.

**Trap:** don't write a generic when a plain union will do. `def f[T: (int, str)](x: T) -> None` (constraints, but T used only once) is just `def f(x: int | str) -> None`. A type variable earns its keep when it links two positions, such as an input and the output.

## Variance

Variance answers: if `Dog` is a subtype of `Animal`, what is the relationship between `Container[Dog]` and `Container[Animal]`?

- **Covariant**: `Container[Dog]` is a subtype of `Container[Animal]`. Safe when the container only **produces** T (read-only). Examples: `Sequence`, `Iterable`, `Mapping` values, `tuple`, `frozenset`, return types of callables.
- **Contravariant**: the relationship flips: `Container[Animal]` is a subtype of `Container[Dog]`. Safe when the container only **consumes** T. Example: parameters of a `Callable`. A function that can handle any animal can be used where a dog handler is needed.
- **Invariant**: no relationship. Required when T is both read and written. Examples: `list`, `dict`, `set`, any class with a mutable attribute of type T.

Why `list` must be invariant:

```python title="variance.py"
from collections.abc import Callable, Sequence

class Animal:
    def speak(self) -> str: return "..."
class Dog(Animal):
    def fetch(self) -> None: ...

def add_cat(animals: list[Animal]) -> None:
    animals.append(Animal())

dogs: list[Dog] = [Dog()]
add_cat(dogs)                       # invariant: rejected

def chorus(animals: Sequence[Animal]) -> None:
    for a in animals: print(a.speak())

chorus(dogs)                        # covariant: fine

def train_dogs(handler: Callable[[Dog], None]) -> None:
    handler(Dog())

def pet_any(a: Animal) -> None: ...
def walk_dog_only(d: Dog) -> None: ...
def needs_animal_handler(h: Callable[[Animal], None]) -> None: ...

train_dogs(pet_any)                 # contravariant param: fine
needs_animal_handler(walk_dog_only) # rejected
```

```text title="mypy output"
variance.py:12: error: Argument 1 to "add_cat" has incompatible type "list[Dog]"; expected "list[Animal]"  [arg-type]
variance.py:12: note: "list" is invariant -- see https://mypy.readthedocs.io/en/stable/common_issues.html#variance
variance.py:12: note: Consider using "Sequence" instead, which is covariant
variance.py:27: error: Argument 1 to "needs_animal_handler" has incompatible type "Callable[[Dog], None]"; expected "Callable[[Animal], None]"  [arg-type]
```

If `add_cat(dogs)` were allowed, `dogs` would now contain a non-dog, and a later `dogs[-1].fetch()` would crash. The checker blocks that at the call.

### Variance of your own generics

With PEP 695 syntax, **variance is inferred** from how T is used. With old-style `TypeVar` you declare it yourself (`covariant=True` / `contravariant=True`, conventionally named `T_co` / `T_contra`), and the checker verifies it.

```python title="inferred_variance.py"
class Animal: ...
class Dog(Animal): ...

class Reader[T]:                 # only returns T: inferred covariant
    def __init__(self, item: T) -> None:
        self._item = item
    def read(self) -> T:
        return self._item

class Writer[T]:                 # only accepts T: inferred contravariant
    def write(self, item: T) -> None: ...

class Cell[T]:
    def __init__(self, item: T) -> None:
        self.item = item         # public mutable attribute: invariant

rd: Reader[Dog] = Reader(Dog())
ra: Reader[Animal] = rd              # ok, covariant
wd: Writer[Dog] = Writer[Animal]()   # ok, contravariant
wa: Writer[Animal] = Writer[Dog]()   # error
cd: Cell[Dog] = Cell(Dog())
ca: Cell[Animal] = cd                # error, invariant
```

```text title="pyright output"
inferred_variance.py:20:22 - error: Type "Writer[Dog]" is not assignable to declared type "Writer[Animal]"
    "Writer[Dog]" is not assignable to "Writer[Animal]"
      Type parameter "T@Writer" is contravariant, but "Dog" is not a supertype of "Animal"
        "Animal" is not assignable to "Dog" (reportAssignmentType)
inferred_variance.py:22:20 - error: Type "Cell[Dog]" is not assignable to declared type "Cell[Animal]"
    "Cell[Dog]" is not assignable to "Cell[Animal]"
      Type parameter "T@Cell" is invariant, but "Dog" is not the same as "Animal" (reportAssignmentType)
```

Note that `Reader` stores T in `self._item`. Inference treats underscore-prefixed (private) attributes as not part of the public interface, so `Reader` is still covariant. Rename it to `self.item` and it becomes invariant.

Declaring the wrong variance by hand is caught too:

```python title="bad_variance.py"
from typing import TypeVar, Generic
T_co = TypeVar("T_co", covariant=True)
class Reader(Generic[T_co]):
    def __init__(self, item: T_co) -> None:
        self._item = item
    def read(self) -> T_co: return self._item
    def put(self, item: T_co) -> None: ...
```

```text title="mypy output"
bad_variance.py:7: error: Cannot use a covariant type variable as a parameter  [misc]
```

<Callout title="Coming from JS">
TypeScript is deliberately unsound here: arrays are covariant (`Dog[]` is assignable to `Animal[]`), and method parameters are bivariant, so the `add_cat` bug compiles. `strictFunctionTypes` fixes it only for function-typed properties, not methods. TS 4.7 added explicit `in`/`out` annotations on type parameters, which map to contravariant and covariant. Python is strict by default. In practice that means writing `Sequence` and `Mapping` in parameter types far more often than you write `ReadonlyArray` in TypeScript.
</Callout>

## `Protocol`: structural typing

Python classes are **nominal**: a `Conn` is only a `Closeable` if it inherits from it. `typing.Protocol` gives you opt-in **structural** typing: any class with matching members is accepted, no inheritance needed. It is the Python form of a TypeScript `interface`.

```python title="protocols.py"
from typing import Protocol

class SupportsClose(Protocol):
    def close(self) -> None: ...

class Conn:                       # does not inherit anything
    def close(self) -> None:
        print("closed")

class Doc:
    def save(self) -> None: ...

def shutdown(r: SupportsClose) -> None:
    r.close()

shutdown(Conn())
shutdown(Doc())

# by contrast, ordinary classes are nominal:
class UserId(int): ...
class OrderId(int): ...
def get_order(oid: OrderId) -> None: ...
get_order(UserId(5))
```

```text title="pyright output"
protocols.py:17:10 - error: Argument of type "Doc" cannot be assigned to parameter "r" of type "SupportsClose" in function "shutdown"
    "Doc" is incompatible with protocol "SupportsClose"
      "close" is not present (reportArgumentType)
protocols.py:23:11 - error: Argument of type "UserId" cannot be assigned to parameter "oid" of type "OrderId" in function "get_order"
    "UserId" is not assignable to "OrderId" (reportArgumentType)
```

`UserId` and `OrderId` have identical structure but are rejected because neither inherits from the other. In TypeScript they would be interchangeable.

How it works:

- A protocol is checked **statically** by comparing members: methods (with compatible signatures), attributes, properties.
- Protocols can be generic: `class Repository[T](Protocol): def get(self, id: int) -> T | None: ...`.
- The standard library is full of them: `Iterable`, `Sized`, `Hashable`, `SupportsInt`, `ContextManager`. That is why `len` accepts anything with `__len__`.
- A class *may* inherit from a protocol explicitly. It then becomes a normal base class and the checker verifies the implementation.

### Runtime checks with `@runtime_checkable`

By default you cannot use a protocol in `isinstance`. With `@runtime_checkable` you can, but the check only tests that the **names exist**, not their signatures or types:

```python title="runtime_protocol.py"
from typing import Protocol, runtime_checkable

@runtime_checkable
class SupportsClose(Protocol):
    def close(self) -> None: ...

class Conn:
    def close(self) -> None: ...

class Liar:
    close = 42          # not callable, still passes isinstance

print(isinstance(Conn(), SupportsClose))
print(isinstance(Liar(), SupportsClose))
print(isinstance("x", SupportsClose))

class Plain(Protocol):
    def close(self) -> None: ...
try:
    isinstance(Conn(), Plain)
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
True
True
False
TypeError: Instance and class checks can only be used with @runtime_checkable protocols
```

Also, runtime protocol checks are slow compared to normal `isinstance`, since they inspect attributes each time. Don't put them in hot paths.

**When to use `Protocol` vs `ABC`:** use a Protocol when you describe what you *need* from callers you don't control (dependency injection, test fakes, third-party objects). Use an abstract base class when you own a hierarchy and want shared implementation and runtime enforcement that subclasses implement the abstract methods.

<Callout title="Coming from JS">
In TypeScript *everything* is structural, so `interface Closeable { close(): void }` is matched by any object with `close`. In Python only `Protocol` types (and `TypedDict`, `Callable`) behave that way. Regular classes, dataclasses and Pydantic models are nominal. A NestJS-style injected `interface` becomes a `Protocol`, and a class implementing it does not need `implements`.
</Callout>

## `TypedDict`

A `TypedDict` describes the shape of a plain `dict` with fixed string keys. It is the right tool for JSON-like payloads, `**kwargs`, and libraries that hand you dicts. At runtime it is just a `dict`: no class instance, no validation.

```python title="typed_dicts.py"
from typing import TypedDict, NotRequired, Required, ReadOnly

class UserIn(TypedDict):
    id: int
    email: str
    nickname: NotRequired[str]        # key may be absent

class Patch(TypedDict, total=False):  # every key optional by default...
    email: str
    id: Required[int]                 # ...except this one

class Event(TypedDict):
    id: ReadOnly[int]                 # cannot be assigned after creation
    name: str

u: UserIn = {"id": 1, "email": "a@b.c"}
bad: UserIn = {"id": "1", "email": "a@b.c", "extra": True}
p: Patch = {"email": "x"}
e: Event = {"id": 1, "name": "deploy"}
e["id"] = 2
e["name"] = "rollback"
print(u.get("nickname", "-"))
reveal_type(u["email"])
u["nickname"].upper()
```

```text title="mypy output"
typed_dicts.py:17: error: Extra key "extra" for TypedDict "UserIn"  [typeddict-unknown-key]
typed_dicts.py:17: error: Incompatible types (expression has type "str", TypedDict item "id" has type "int")  [typeddict-item]
typed_dicts.py:18: error: Missing key "id" for TypedDict "Patch"  [typeddict-item]
typed_dicts.py:20: error: ReadOnly TypedDict key "id" TypedDict is mutated  [typeddict-readonly-mutated]
typed_dicts.py:23: note: Revealed type is "str"
```

```text title="pyright output"

    "Literal['1']" is not assignable to "int" (reportAssignmentType)
typed_dicts.py:18:12 - error: Type "dict[str, str]" is not assignable to declared type "Patch"
    "id" is required in "Patch" (reportAssignmentType)
typed_dicts.py:20:1 - error: Could not assign item in TypedDict
    "id" is a read-only key in "Event" (reportTypedDictNotRequiredAccess)

```

Notice line 24: pyright flags `u["nickname"]` on a `NotRequired` key (it could raise `KeyError`). mypy does not. Use `.get()` or `"nickname" in u` to be safe with both.

Versions: `Required`/`NotRequired` arrived in 3.11 (PEP 655), `ReadOnly` in 3.13 (PEP 705). On older Pythons import them from `typing_extensions`.

At runtime, a TypedDict "call" just builds a dict, and wrong types go straight through:

```python title="typeddict_runtime.py"
from typing import TypedDict, NotRequired
class UserIn(TypedDict):
    id: int
    nickname: NotRequired[str]
u = UserIn(id="not an int")
print(u, type(u))
print(UserIn.__required_keys__, UserIn.__optional_keys__)
```

```text title="Output"
{'id': 'not an int'} <class 'dict'>
frozenset({'id'}) frozenset({'nickname'})
```

**Traps:**

- `isinstance(x, UserIn)` raises `TypeError`. You cannot check a TypedDict at runtime without a validator. Pydantic's `TypeAdapter(UserIn)` does exactly that (see the Pydantic page).
- TypedDicts are **structurally** compatible with each other, but a `TypedDict` is not assignable to `dict[str, object]`, because a dict type allows adding arbitrary keys. Use `Mapping[str, object]` if you need a general read-only view.
- "Extra keys" are rejected only in literal assignments. A TypedDict value obtained elsewhere may have more keys at runtime. PEP 728 (closed TypedDicts with `closed=True` / `extra_items=`) addresses this and is supported by recent checkers through `typing_extensions`.

<Callout title="Coming from JS">
A `TypedDict` is the closest thing to a TypeScript object type used for data: `{ id: number; email: string; nickname?: string; readonly createdAt: string }`. `NotRequired` is `?:`, `ReadOnly` is `readonly`. Pick a `TypedDict` when the data stays a dict (JSON in, JSON out). Pick a dataclass or Pydantic model when you want attribute access, methods and an actual class.
</Callout>

## `ParamSpec` and `Concatenate`: typing decorators

A decorator that wraps arbitrary functions needs to say "the wrapper takes the **same parameters** as the original". `Callable[..., R]` loses the signature, so callers get no checking. `ParamSpec` (written `**P` in PEP 695 syntax) captures the full parameter list.

```python title="paramspec.py"
import functools, time
from collections.abc import Callable

def timed[**P, R](fn: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(fn)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter() - start:.4f}s")
    return wrapper

def loose(fn: Callable[..., object]) -> Callable[..., object]:
    return fn

@timed
def greet(name: str, excited: bool = False) -> str:
    return name + ("!" if excited else "")

@loose
def greet2(name: str) -> str:
    return name

reveal_type(greet)
greet(42)
greet2(42)
```

```text title="mypy output"
paramspec.py:25: note: Revealed type is "def (name: str, excited: bool =) -> str"
paramspec.py:26: error: Argument 1 to "greet" has incompatible type "int"; expected "str"  [arg-type]
```

`greet` keeps its exact signature, so the bad call is caught. `greet2(42)` is not flagged, because `loose` erased the signature to `Callable[..., object]`. At runtime, `greet(42)` crashes inside the function with `TypeError: unsupported operand type(s) for +: 'int' and 'str'` after printing the timing line.

`P.args` and `P.kwargs` must be used together, exactly as `*args: P.args, **kwargs: P.kwargs`.

### `Concatenate`: adding or removing parameters

Decorators that inject an argument (a request, a DB session, a logger) remove a parameter from the visible signature. `Concatenate[X, P]` means "X followed by the parameters P":

```python title="concatenate.py"
from collections.abc import Callable
from typing import Concatenate

class Request:
    user = "ada"

def with_request[**P, R](fn: Callable[Concatenate[Request, P], R]) -> Callable[P, R]:
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        return fn(Request(), *args, **kwargs)
    return wrapper

@with_request
def get_item(req: Request, item_id: int) -> str:
    return f"{req.user} reads {item_id}"

reveal_type(get_item)
print(get_item(7))
get_item(Request(), 7)
```

```text title="mypy output"
concatenate.py:16: note: Revealed type is "def (item_id: int) -> str"
concatenate.py:18: error: Too many arguments for "get_item"  [call-arg]
concatenate.py:18: error: Argument 1 to "get_item" has incompatible type "Request"; expected "int"  [arg-type]
```

```text title="Output"
Runtime type is 'function'
ada reads 7
TypeError: get_item() takes 2 positional arguments but 3 were given
```

Old-style spelling: `P = ParamSpec("P")`, then `Callable[P, R]`. Async decorators work the same with `Callable[P, Awaitable[R]]`.

<Callout title="Coming from JS">
TypeScript does this with `Parameters<F>` and `ReturnType<F>`: `function timed<F extends (...a: any[]) => any>(fn: F): (...a: Parameters<F>) => ReturnType<F>`. `ParamSpec` is more precise because it also keeps keyword names, defaults and keyword-only markers, which TypeScript tuples cannot express. `Concatenate` is like typing `(req: Request, ...rest: P)` and stripping the first element.
</Callout>

## `TypeVarTuple`: variadic generics

`TypeVarTuple` (written `*Ts`) stands for a whole sequence of types. It enables typed `*args` that keep each position's type, and shape-typed arrays.

```python title="variadic.py"
def args_to_tuple[*Ts](*args: *Ts) -> tuple[*Ts]:
    return args

reveal_type(args_to_tuple(1, "a", 2.0))

class Array[*Shape]:
    def __init__(self, *dims: *Shape) -> None:
        self.dims = dims

reveal_type(Array(3, 4))
```

```text title="pyright output"
variadic.py:4:13 - information: Type of "args_to_tuple(1, "a", 2)" is "tuple[int, str, float]"
variadic.py:10:13 - information: Type of "Array(3, 4)" is "Array[int, int]"
```

(mypy reports the same shapes, with literal types: `tuple[Literal[1]?, Literal['a']?, float]`.) Day to day you will mostly meet `TypeVarTuple` in the signatures of libraries such as `asyncio.gather` overloads and NumPy-style array types, rather than writing it yourself.

## `Self`

`Self` (3.11, PEP 673) means "the type of the current instance, including subclasses". It is what fluent builders and `classmethod` constructors need.

```python title="self_type.py"
from typing import Self

class QueryBuilder:
    def __init__(self) -> None:
        self.parts: list[str] = []
    def where(self, cond: str) -> Self:
        self.parts.append(cond)
        return self

class UserQuery(QueryBuilder):
    def active(self) -> Self:
        return self.where("active")

q = UserQuery().where("age > 18").active()
reveal_type(q)
print(q.parts)
```

```text title="mypy output"
self_type.py:15: note: Revealed type is "self_type.UserQuery"
```

```text title="Output"
Runtime type is 'UserQuery'
['age > 18', 'active']
```

Had `where` been annotated `-> "QueryBuilder"`, the result of `UserQuery().where(...)` would be a `QueryBuilder` and `.active()` would be an error. `Self` is TypeScript's polymorphic `this` return type.

## `@overload`

Overloads declare several signatures for one function when the return type depends on argument values or types. Only the final, undecorated implementation exists at runtime. The `@overload` stubs are for the checker.

```python title="overloads.py"
from typing import overload, Literal

@overload
def fetch(raw: Literal[True]) -> bytes: ...
@overload
def fetch(raw: Literal[False] = ...) -> str: ...
def fetch(raw: bool = False) -> str | bytes:
    data = b"hello"
    return data if raw else data.decode()

reveal_type(fetch())
reveal_type(fetch(raw=True))

def use(flag: bool) -> None:
    reveal_type(fetch(flag))
```

```text title="mypy output"
overloads.py:11: note: Revealed type is "str"
overloads.py:12: note: Revealed type is "bytes"
overloads.py:15: error: No overload variant of "fetch" matches argument type "bool"  [call-overload]
overloads.py:15: note: Possible overload variants:
overloads.py:15: note:     def fetch(raw: Literal[True]) -> bytes
overloads.py:15: note:     def fetch(raw: Literal[False] = ...) -> str
overloads.py:15: note: Revealed type is "Any"
```

```text title="pyright output"
overloads.py:11:13 - information: Type of "fetch()" is "str"
overloads.py:12:13 - information: Type of "fetch(raw=True)" is "bytes"
overloads.py:15:17 - information: Type of "fetch(flag)" is "bytes | str"
```

A plain `bool` matches neither literal overload. pyright expands the `bool` into `True` and `False` and unions the results. mypy rejects it. The portable fix is a third, catch-all overload `def fetch(raw: bool = ...) -> str | bytes: ...`, after which both report `str | bytes`.

**Traps:** overloads are tried in order, so put specific signatures first. The implementation signature must accept every overload's arguments. Don't use overloads when a generic would do (`def first[T](xs: list[T]) -> T` needs no overloads).

## `TypeGuard` and `TypeIs`: custom narrowing

`isinstance` narrows automatically. For your own checks, a function returning `TypeIs[X]` (3.13, PEP 742) or `TypeGuard[X]` (3.10, PEP 647) tells the checker what a `True` result proves.

```python title="narrowing_functions.py"
from typing import TypeGuard, TypeIs

def is_str_list(xs: list[object]) -> TypeGuard[list[str]]:
    return all(isinstance(x, str) for x in xs)

def is_str(x: object) -> TypeIs[str]:
    return isinstance(x, str)

def guard_only(x: object) -> TypeGuard[str]:
    return isinstance(x, str)

def demo(v: int | str) -> None:
    if is_str(v):
        reveal_type(v)
    else:
        reveal_type(v)
    if guard_only(v):
        reveal_type(v)
    else:
        reveal_type(v)

def worse(x: int | str) -> TypeIs[bytes]:
    return False
```

```text title="mypy output"
narrowing_functions.py:14: note: Revealed type is "str"
narrowing_functions.py:16: note: Revealed type is "int"
narrowing_functions.py:18: note: Revealed type is "str"
narrowing_functions.py:20: note: Revealed type is "int | str"
narrowing_functions.py:22: error: Narrowed type "bytes" is not a subtype of input type "int | str"  [narrowed-type-not-subtype]
```

The differences:

| | `TypeIs[X]` | `TypeGuard[X]` |
|---|---|---|
| True branch | intersection of the input type and X (here `str`) | exactly X |
| False branch | narrowed too: X removed (here `int`) | not narrowed |
| X must be a subtype of the input | yes, checked | no |
| Typical use | "is this value of type X" checks, the normal case | changing to an unrelated type, such as `list[object]` to `list[str]` |

`list[str]` is not a subtype of `list[object]` (lists are invariant), which is why `is_str_list` must use `TypeGuard`. Prefer `TypeIs` for everything else. It behaves like `isinstance`.

**Trap:** the checker trusts your function body completely. A `TypeIs[list[str]]` that only checks `isinstance(x, list)` passes both checkers and lies.

<Callout title="Coming from JS">
`TypeIs[str]` is TypeScript's `x is string` predicate, including narrowing in the else branch. `TypeGuard` is the weaker, older form with no TypeScript equivalent: it narrows only the true branch, but it can narrow to a type that is not a subtype of the input.
</Callout>

## `NewType` for IDs

`NewType("UserId", int)` creates a distinct type for the checker that is just `int` at runtime. It is how you stop a user ID from being passed where an order ID is expected.

```python title="newtype_ids.py"
from typing import NewType

UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)

def get_user(uid: UserId) -> str:
    return f"user {uid}"

uid = UserId(42)
print(uid, type(uid), uid + 1)
print(get_user(uid))
get_user(42)
get_user(OrderId(42))
reveal_type(uid + 1)
```

```text title="Output"
42 <class 'int'> 43
user 42
Runtime type is 'int'
```

```text title="mypy output"
newtype_ids.py:12: error: Argument 1 to "get_user" has incompatible type "int"; expected "UserId"  [arg-type]
newtype_ids.py:13: error: Argument 1 to "get_user" has incompatible type "OrderId"; expected "UserId"  [arg-type]
newtype_ids.py:14: note: Revealed type is "int"
```

How it works: at runtime `UserId(42)` is an identity function that returns the same `int`, so it costs almost nothing. For the checker, `UserId` is a subclass of `int`: it can go anywhere an `int` can, but not the other way. Arithmetic returns plain `int` (`uid + 1` is not a `UserId`).

Limits: you cannot subclass a `NewType`, and `isinstance(x, UserId)` fails. For values that must be validated (for example "a positive int"), combine with Pydantic or a small class instead.

<Callout title="Coming from JS">
This replaces TypeScript's branded types, `type UserId = number & { __brand: 'UserId' }`, without the cast dance. Creating one is `UserId(42)` instead of `42 as UserId`.
</Callout>

## `Annotated`: metadata for libraries

`Annotated[T, x, y]` means "type T, plus some metadata x, y". Checkers treat it as plain `T` and ignore the metadata. Runtime libraries read the metadata. This is how FastAPI and Pydantic attach validation rules and parameter sources to ordinary types.

```python title="annotated_runtime.py"
from dataclasses import dataclass
from typing import Annotated, get_type_hints, get_args, get_origin

@dataclass(frozen=True)
class MaxLen:
    n: int

def register(name: Annotated[str, MaxLen(20)]) -> None: ...

print(get_type_hints(register))
hints = get_type_hints(register, include_extras=True)
print(hints["name"])
print(get_origin(hints["name"]) is Annotated, get_args(hints["name"]))
print(hints["name"].__metadata__)
```

```text title="Output"
{'name': <class 'str'>, 'return': <class 'NoneType'>}
typing.Annotated[str, MaxLen(n=20)]
True (<class 'str'>, MaxLen(n=20))
(MaxLen(n=20),)
```

`get_type_hints` strips the metadata unless you pass `include_extras=True`. Real-world usage looks like this (a sketch: `Session` and `get_db` stand for your own DB session type and dependency):

```python title="fastapi_annotated_sketch.py"
from typing import Annotated
from fastapi import Depends, Query
from pydantic import Field

type PositiveInt = Annotated[int, Field(gt=0)]           # reusable constrained type
type PageSize = Annotated[int, Query(ge=1, le=100)]      # FastAPI: read from query string

def list_items(size: PageSize = 20, db: Annotated[Session, Depends(get_db)] = ...): ...
```

Because the metadata is attached to the *type*, you can name it with a `type` alias and reuse it across models and endpoints. That is the modern FastAPI style. (Both a `type` statement alias and a plain `PageSize = Annotated[...]` assignment worked when tested with FastAPI 0.143. On older FastAPI releases, prefer the plain assignment.) It is also why `Annotated` matters far more than its simple definition suggests.

<Callout title="Coming from JS">
This is what NestJS and class-validator do with decorators (`@IsEmail() @MaxLength(20) email: string`) and what zod does with chained schema methods. Python attaches the same information *inside the type annotation*, so the checker sees `str` and the validator sees `str` plus the rule. No `reflect-metadata` needed.
</Callout>

## Common checker errors and how to fix them

Real messages from this file:

```python title="common_errors.py"
import yaml

def parse(port: str) -> int:
    if port.isdigit():
        return int(port)

items = []

class Base:
    def handle(self, x: int) -> str: return ""
class Child(Base):
    def handle(self, x: str) -> str: return ""

def get(d: dict[str, int], k: str) -> int:
    return d.get(k)

def greet(name: str = None) -> str:
    return name
```

```text title="mypy output"
common_errors.py:1: error: Library stubs not installed for "yaml"  [import-untyped]
common_errors.py:1: note: Hint: "python3 -m pip install types-PyYAML"
common_errors.py:3: error: Missing return statement  [return]
common_errors.py:7: error: Need type annotation for "items" (hint: "items: list[<type>] = ...")  [var-annotated]
common_errors.py:12: error: Argument 1 of "handle" is incompatible with supertype "Base"; supertype defines the argument type as "int"  [override]
common_errors.py:12: note: This violates the Liskov substitution principle
common_errors.py:15: error: Incompatible return value type (got "int | None", expected "int")  [return-value]
common_errors.py:17: error: Incompatible default for parameter "name" (default has type "None", parameter has type "str")  [assignment]
common_errors.py:17: note: PEP 484 prohibits implicit Optional. Accordingly, mypy has changed its default to no_implicit_optional=True
```

| Error | Cause | Fix |
|---|---|---|
| `import-untyped` / `import-not-found` | library has no types | install the `types-...` stub package, or `ignore_missing_imports` for that module |
| `Missing return statement` | a path falls off the end and returns `None` | add the missing return or raise, or widen the return to `int` or `None` |
| `Need type annotation` | empty container with nothing to infer from | `items: list[str] = []` |
| `incompatible with supertype` | override narrows a parameter (breaks Liskov) | accept the same or a wider type in the subclass |
| `Incompatible return value type` (got an optional int) | `dict.get`, `re.match`, `os.getenv` return optional values | `d[k]`, `d.get(k, 0)`, or narrow with `if x is None: raise` |
| `Incompatible default ... None` | implicit Optional | annotate the parameter as an optional str with a `None` default |
| `"list" is invariant` | passing `list[Sub]` where `list[Base]` expected | accept `Sequence[Base]` |
| `Returning Any` | value from `json.loads` or untyped code | validate it (Pydantic, `TypeAdapter`) or `cast` after checking |
| `has no attribute` on a union | using a member not shared by all union members | narrow with `isinstance` or a `match` statement first |

Two more tools for the edge cases:

- **`typing.cast(T, value)`** tells the checker "trust me, this is T". It does nothing at runtime. Use it after a check the checker can't follow, never as a shortcut around a real error.
- **`assert_never(x)`** in the final `else` or `case _:` makes the checker prove a union or enum is fully handled, like TypeScript's `never` exhaustiveness trick.

## When to use what

| Need | Tool |
|---|---|
| Link input and output types | type parameter (`def f[T]`) |
| "Any type with a `.close()`" | `Protocol` |
| Typed JSON-shaped dict | `TypedDict` (with `NotRequired`, `ReadOnly`) |
| Decorator that preserves signatures | `ParamSpec` (`**P`), plus `Concatenate` to inject arguments |
| Fluent methods, alternate constructors | `Self` |
| Return type depends on an argument value | `@overload` with `Literal` |
| Reusable narrowing check | `TypeIs` (or `TypeGuard` for non-subtype narrowing) |
| IDs that must not be mixed up | `NewType` |
| Attach validation or DI metadata to a type | `Annotated` |

## Interview questions

1. **What does PEP 695 change about generics?**
   **It adds inline type-parameter syntax (`def f[T]`, `class Box[T]`, `type Alias[T] = ...`), scopes type variables to their function or class, and infers variance automatically. No module-level `TypeVar` is needed.**
2. **Why is `list[Dog]` not a `list[Animal]`?**
   **`list` is mutable, so it is invariant. Allowing it would let a function insert a non-dog into a list of dogs. Read-only `Sequence` is covariant, so `Sequence[Dog]` is accepted where `Sequence[Animal]` is expected.**
3. **What is the difference between a bound and constraints on a type variable?**
   **A bound (`T: Base`) accepts any subtype and solves T to the actual type passed. Constraints (`T: (int, str)`) require T to be exactly one of the listed types.**
4. **How does `Protocol` differ from an ABC?**
   **A Protocol is structural: any class with matching members satisfies it, with no inheritance. An ABC is nominal: classes must inherit from it, and abstract methods are enforced at instantiation. `isinstance` with protocols needs `@runtime_checkable` and only checks member names.**
5. **`TypeIs` vs `TypeGuard`?**
   **`TypeIs` narrows both branches and requires the target to be a subtype of the input, like `isinstance`. `TypeGuard` narrows only the true branch but can narrow to an unrelated type.**
6. **How do you type a decorator so the wrapped function keeps its signature?**
   **Use a ParamSpec: `def deco[**P, R](fn: Callable[P, R]) -> Callable[P, R]`, with the wrapper taking `*args: P.args, **kwargs: P.kwargs`. Use `Concatenate` when the decorator adds or removes leading parameters.**
7. **What does `NewType` cost at runtime?**
   **Almost nothing. Calling it returns its argument unchanged. The distinction exists only for the checker.**
8. **Why do FastAPI and Pydantic use `Annotated`?**
   **It attaches metadata (constraints, parameter source, dependencies) to a type in a way checkers ignore but runtime code can read through `get_type_hints(..., include_extras=True)`. That keeps the visible type accurate and makes the metadata reusable through aliases.**

## Recap

- PEP 695 syntax (`def f[T]`, `class Box[T]`) replaces `TypeVar` boilerplate and infers variance. Bounds restrict T to subtypes, constraints to an exact list.
- Mutable containers are invariant, read-only ones covariant, callable parameters contravariant. Python enforces this more strictly than TypeScript.
- Python is nominal by default. `Protocol` and `TypedDict` opt into structural typing.
- `TypedDict` types dicts with `Required`, `NotRequired` and `ReadOnly`, but never validates at runtime.
- `ParamSpec`, `Concatenate`, `TypeVarTuple`, `Self` and `@overload` cover decorators, variadics, fluent APIs and value-dependent returns.
- `TypeIs` is the modern custom-narrowing tool, `NewType` gives cheap branded IDs, and `Annotated` carries the metadata that FastAPI and Pydantic run on.
