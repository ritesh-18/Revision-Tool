This is the most important page in the basics section. Nearly every confusing Python bug (a list that changes "by itself", a default argument that remembers old calls, a `+=` that behaves differently on two types) comes from one model: **variables are names that point at objects**. Get this right and the rest of the language becomes predictable.

<Callout type="info">
Snippets were run on **CPython 3.14.6**. Anything about specific `id` values, caching of small ints or interning of strings is a CPython implementation detail and is labelled as such.
</Callout>

## Everything is an object

In Python, every value is an object: numbers, strings, `None`, functions, classes, modules, even types themselves. There are no "primitive" values that live outside the object system.

```python
for obj in (42, 3.14, "hi", [1], None, len, int, type):
    print(f"{obj!r:<24} type={type(obj).__name__}")
print(isinstance(int, object), isinstance(len, object), type(type))
```

```text title="Output"
42                       type=int
3.14                     type=float
'hi'                     type=str
[1]                      type=list
None                     type=NoneType
<built-in function len>  type=builtin_function_or_method
<class 'int'>            type=type
<class 'type'>           type=type
True True <class 'type'>
```

Classes are objects whose type is `type`, and `type` is its own type. That is why you can pass a class as an argument, store functions in a dict, or add attributes to a function.

### What an object is in CPython

In CPython, every object is a C struct allocated on the heap that starts with a common header (`PyObject`):

- **`ob_refcnt`**: the reference count, how many references point at this object.
- **`ob_type`**: a pointer to the object's type (another object, e.g. the `int` type).

After the header comes type-specific data (the digits of an int, the pointer array of a list, and so on). A Python "variable" is never this struct itself; it is a **reference** (a pointer) to it.

Every object has three properties:

| Property | How to see it | Can it change? |
|---|---|---|
| **Identity** | `id(obj)` (in CPython: the memory address) | Never, for the object's lifetime |
| **Type** | `type(obj)` | Practically never |
| **Value** | the data, `==` compares it | Only if the type is **mutable** |

<Callout title="Coming from JS">
JavaScript splits values into primitives (`number`, `string`, `boolean`, `null`, `undefined`, `bigint`, `symbol`) that behave like values, and objects that behave like references. Python has **no primitives**: `42` is an object with methods (`(42).bit_length()`). In practice immutable Python objects (int, str, tuple) behave like JS primitives, because nobody can change them, while mutable ones (list, dict, set) behave like JS objects and arrays.
</Callout>

## Names are bindings, not boxes

In C, `int x = 10;` creates a box called `x` that holds `10`. In Python, `x = 10` does two separate things:

1. Evaluate the right-hand side to get an object (the int `10`).
2. **Bind** the name `x` to that object in the current namespace (a dict-like mapping from names to references).

Names have no type; objects do. A name can be rebound to an object of any type at any time.

```python
a = [1, 2, 3]
b = a
b.append(4)
print(a, b, a is b, id(a) == id(b))
```

```text title="Output"
[1, 2, 3, 4] [1, 2, 3, 4] True True
```

`b = a` did not copy the list. It made `b` a second name for the **same** object.

Now compare with an immutable value:

```python
x = 10
y = x
x = x + 1
print(x, y)
```

```text title="Output"

```

`x + 1` creates a **new** int object `11`, then `x` is rebound to it. `y` still points at `10`. Nothing was modified; a name was moved.

### Assignment never copies

This is a rule with no exceptions: `=` never copies an object. The same is true for:

- passing an argument to a function (the parameter becomes a new name for the caller's object),
- returning a value,
- putting an object into a list or dict,
- `for item in items` (each `item` is a name for an element, not a copy).

This model is often called **"call by object reference"** or "call by sharing". It is neither C-style pass-by-value (no copy is made) nor pass-by-reference (rebinding the parameter does not affect the caller's name).

```python
def rebind(lst):
    lst = [99]        # rebinds the local name only

def mutate(lst):
    lst.append(99)    # changes the shared object

data = [1]
rebind(data); print(data)
mutate(data); print(data)
```

```text title="Output"
[1]
[1, 99]
```

<Callout title="Coming from JS">
This is exactly how JavaScript passes objects: `function f(arr) { arr.push(1) }` mutates the caller's array, while `arr = []` inside the function does not. Python just applies the same rule to **every** value, including numbers and strings. Since those are immutable, the difference is invisible for them.
</Callout>

To actually copy, ask for it: `lst.copy()`, `lst[:]`, `list(lst)`, `dict(d)`, `copy.copy(x)` (shallow) or `copy.deepcopy(x)`. The copying page goes into shallow vs deep copies in detail.

### Chained assignment shares too

```python
a = b = []
a.append(1)
print(a, b)
```

```text title="Output"
[1] [1]
```

`a = b = []` creates one list and binds two names to it. The same trap appears with list multiplication:

```python
row = [0] * 3
grid = [row] * 3          # three references to ONE row
grid[0][0] = 9
print(grid)

grid = [[0] * 3 for _ in range(3)]   # three separate rows
grid[0][0] = 9
print(grid)
```

```text title="Output"
[[9, 0, 0], [9, 0, 0], [9, 0, 0]]
[[9, 0, 0], [0, 0, 0], [0, 0, 0]]
```

`[x] * 3` repeats the **reference** three times. It is fine for immutable elements like `0`, and a bug for mutable ones like lists.

## Mutability vs immutability

A **mutable** object can change its value in place while keeping its identity. An **immutable** object cannot; any "change" produces a new object.

| Immutable | Mutable |
|---|---|
| `int`, `float`, `complex`, `bool` | `list` |
| `str`, `bytes` | `bytearray` |
| `tuple`, `frozenset` | `dict`, `set` |
| `None`, `range` | most user-defined class instances |
| `frozendict` (new built-in in 3.15) | |

```python
s = "hello"
t = s.upper()
print(s, t)
try:
    s[0] = "H"
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
hello HELLO
TypeError: 'str' object does not support item assignment
```

Why immutability matters:

- **Hashing**: only objects whose value cannot change can safely be dict keys or set members, because the hash is computed from the value. That is why `tuple` can be a key and `list` cannot.
- **Safe sharing**: you can hand an immutable object to any function without fear it will be changed.
- **Optimizations**: CPython can share and reuse immutable objects (see caching below) precisely because nobody can modify them.

### Immutable containers can hold mutable things

A tuple's immutability is shallow. It fixes **which objects** the tuple refers to, not whether those objects can change:

```python
t = ([1, 2], "x")
try:
    t[0] += [3]
except TypeError as e:
    print("TypeError:", e)
print(t)
```

```text title="Output"
TypeError: 'tuple' object does not support item assignment
([1, 2, 3], 'x')
```

This famous puzzle both raises **and** modifies the list. `t[0] += [3]` runs in two steps: first `t[0].__iadd__([3])` extends the list in place (succeeds), then Python tries to store the result back with `t[0] = ...` (fails, because tuples do not support item assignment). Such a tuple is also not hashable, because one of its elements is not.

## Augmented assignment: `+=` on mutable vs immutable

`x += y` is not just shorthand for `x = x + y`. Python first tries the in-place method `x.__iadd__(y)`. If the type does not define it, Python falls back to `x = x.__add__(y)`. Either way, the result is then **bound back to the name**.

- `list` defines `__iadd__`: it extends the same list in place and returns it.
- `tuple`, `int` and `str` do not: a new object is created and the name is rebound.

```python
nums = [1, 2]
alias = nums
nums += [3]
print(nums, alias, nums is alias)

t = (1, 2)
alias_t = t
t += (3,)
print(t, alias_t, t is alias_t)
```

```text title="Output"
[1, 2, 3] [1, 2, 3] True
(1, 2, 3) (1, 2) False
```

And `nums = nums + [3]` on a list creates a new list, so an alias is **not** affected:

```python
nums = [1, 2]
alias = nums
nums = nums + [3]
print(nums, alias)
```

```text title="Output"
[1, 2, 3] [1, 2]
```

Also note that `lst += "ab"` works (it extends with any iterable, giving `[..., 'a', 'b']`) while `lst + "ab"` raises `TypeError`. `__iadd__` on lists behaves like `extend`, which accepts any iterable.

## `is` vs `==`

- `a == b` asks: **do these have equal values?** It calls `a.__eq__(b)`, which each type defines. For your own classes it defaults to identity unless you override `__eq__`.
- `a is b` asks: **are these the same object?** It compares identities (pointers). It cannot be overridden and is very fast.

```python
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b, a is b)
```

```text title="Output"
True False
```

When to use `is`:

- Comparing to singletons: `x is None`, `x is not None`. Also sentinel objects you create yourself (`_MISSING = object()`).
- Checking `True`/`False` identity is rarely needed; just use truthiness.

When **not** to use `is`: numbers and strings. Whether two equal ints or strings are the same object depends on caching details (below). Python 3.8+ emits a `SyntaxWarning` when you write `is` with a literal:

```text title="Output"
SyntaxWarning: "is" with 'int' literal. Did you mean "=="?
```

<Callout title="Coming from JS">
Python's `==` is closer to JavaScript's `===` than to `==`: there is **no type coercion**. `1 == "1"` is `False`. But Python's `==` compares **values deeply** for built-in containers: `[1, 2] == [1, 2]` is `True`, whereas in JS `[1,2] === [1,2]` is `false` because JS compares object references. Python's `is` is the identity comparison that JS `===` does for objects. One coercion that does exist: `1 == 1.0 == True` is `True`, because `bool` is a subclass of `int` and numeric types compare by value.
</Callout>

A consequence of numeric equality that surprises people:

```python
print({1: "a", True: "b", 1.0: "c"})
```

```text title="Output"
{1: 'c'}
```

`1`, `True` and `1.0` are equal and have the same hash, so they are the same dict key. The first key object is kept, and the last value wins.

### Identity implies equality... almost

For most objects, `a is b` implies `a == b`. The exception is NaN. Containers use an identity shortcut (`x is y or x == y`) when searching and comparing, which leads to:

```python
nan = float("nan")
lst = [nan]
print(nan == nan, nan in lst, lst == [nan])
```

```text title="Output"
False True True
```

## Lifetime, reference counting and `id`

CPython frees an object when its reference count drops to zero (plus a cycle collector for reference cycles; the memory management page covers this). So an `id` is only unique **while the object is alive**. Two short-lived objects can get the same id:

```python
print(id(object()) == id(object()))
```

```text title="Output"
True
```

The first `object()` was freed right after `id()` returned, and the second was allocated at the same address. Never store `id`s as long-term keys for objects you do not keep alive.

`del x` deletes the **name**, not the object. The object is freed only if that was the last reference.

## Small-int caching and string interning (implementation details)

Because immutable objects can be shared safely, CPython reuses some of them. None of this is a language guarantee.

### Small integers

CPython preallocates the ints from `-5` to `256` at startup. Any operation that produces one of these returns the cached object:

```python
a = int("256"); b = int("256")
print(a is b)
a = int("257"); b = int("257")
print(a is b, a == b)
a = int("-5"); b = int("-5")
print(a is b)
a = int("-6"); b = int("-6")
print(a is b)
```

```text title="Output"
True
False True
True
False
```

(`int("...")` is used to force the numbers to be created at run time.)

There is a second, separate effect: the compiler **deduplicates constants inside one code object**. In a script file, this prints `True`, while typing the same three lines into the REPL one at a time prints `False`, because each REPL line is compiled separately:

```python
a = 1000
b = 1000
print(a is b)
```

```text title="Output"
True
```

That inconsistency is exactly why you never use `is` for numbers.

### Immortal objects

Since 3.12 (PEP 683), objects like `None`, `True`, `False`, small ints and interned strings are **immortal**: their reference count is pinned at a huge sentinel value and never changes. This avoids constant writes to their refcount field (good for CPU caches and for the free-threaded build).

```python
import sys
print(sys.getrefcount(None), sys.getrefcount(0))
```

```text title="Output"
3221225472 3221225472
```

### String interning

**Interning** means keeping one canonical copy of a string so equal strings can be compared by pointer. CPython automatically interns:

- identifiers used in code (variable, function, attribute names), which makes attribute and dict lookups fast,
- string constants that look like identifiers (letters, digits, underscore),
- results of constant folding at compile time.

Strings built at run time are usually **not** interned, but you can force it with `sys.intern`:

```python
import sys
s1 = "hello_world"
s2 = "hello_" + "world"          # folded by the compiler into one constant
s3 = "".join(["hello_", "world"])  # built at run time
print(s1 is s2, s1 is s3, s1 == s3)
print(sys.intern(s3) is s1)
```

```text title="Output"
True False True
True
```

`sys.intern` can save memory when you hold millions of repeated strings (e.g. keys parsed from a big JSON or CSV file), but it is a niche optimization. More in the strings page.

## `None`

`None` is the single instance of `NoneType`. It means "no value" and is what a function returns when it has no `return` statement (or a bare `return`).

```python
print(type(None), None is None, None == False, bool(None))
def f(): pass
print(f())
```

```text title="Output"
<class 'NoneType'> True False False
None
```

- Always compare with `is None` / `is not None`. A class can override `__eq__` to claim it equals `None`, but nothing can fake identity.
- `None` is falsy but **not equal** to `False`, `0` or `""`.
- When `None` is a valid value and you need "argument not given", use a private sentinel: `_MISSING = object()` and `if arg is _MISSING:`.

<Callout title="Coming from JS">
Python has **one** "nothing" value. There is no `undefined`. Accessing a missing variable raises `NameError`, a missing attribute raises `AttributeError`, and a missing dict key raises `KeyError` (use `d.get(key)` to get `None` instead). That means there is no optional chaining `?.` and no nullish coalescing `??` operator; you write `x if x is not None else default` or use `getattr(obj, "attr", None)` and `d.get("k", default)`.
</Callout>

## Truthiness

Any object can be used in a boolean context (`if`, `while`, `and`, `or`, `not`). Python decides truth with this rule:

1. If the type defines `__bool__`, call it (must return `True` or `False`).
2. Otherwise, if it defines `__len__`, the object is falsy when the length is 0.
3. Otherwise, the object is truthy.

So the falsy values among built-ins are: `None`, `False`, zero of any numeric type, and **empty** containers and sequences.

```python
falsy = [None, False, 0, 0.0, 0j, "", [], (), {}, set(), range(0), b""]
print([bool(v) for v in falsy])
print(bool("0"), bool("False"), bool([0]), bool(" "), bool(float("nan")))
```

```text title="Output"
[False, False, False, False, False, False, False, False, False, False, False, False]
True True True True True
```

Your own classes participate through the same protocol:

```python
class Cart:
    def __init__(self, items): self.items = items
    def __len__(self): return len(self.items)

class Flag:
    def __bool__(self): return False

class Plain: pass

print(bool(Cart([])), bool(Cart([1])), bool(Flag()), bool(Plain()))
```

```text title="Output"
False True False True
```

<Callout title="Coming from JS">
The big difference: **empty list `[]` and empty dict `{}` are falsy in Python**, but `[]` and `{}` are truthy in JavaScript. `if (arr.length)` in JS becomes `if items:` in Python. Also, `NaN` is truthy in Python but falsy in JS, and the string `"0"` is truthy in both.
</Callout>

### Trap: truthiness when `0` or `""` is valid

```python
def set_limit(limit=None):
    if not limit:          # BUG: limit=0 is treated as "not given"
        limit = 100
    return limit
```

When `0`, `""` or an empty list is a legitimate value, test `if limit is None:` explicitly. This is the Python version of the JS `||` vs `??` problem.

## The mutable default argument trap

Default values are evaluated **once**, when the `def` statement runs, and stored on the function object. A mutable default is therefore shared across calls:

```python
def add_item(item, bucket=[]):
    bucket.append(item)
    return bucket

print(add_item(1))
print(add_item(2))
```

```text title="Output"
[1]
[1, 2]
```

The fix is the `None` sentinel idiom:

```python
def add_item(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket
```

<Callout title="Coming from JS">
JavaScript evaluates default parameters **on every call** (`function f(x = [])` gives a fresh array each time). Python evaluates them once at definition time. Linters (Ruff rule `B006`) flag mutable defaults for this reason.
</Callout>

## Interview questions

**What happens when you write `b = a` for a list?**
**No copy is made. `b` becomes a second name bound to the same list object, so mutations through either name are visible through both.**

**What is the difference between `is` and `==`?**
**`is` compares identity (same object, a pointer comparison that cannot be overridden). `==` compares value via `__eq__`. Use `is` only for singletons like `None` and sentinels.**

**Why does `a = 256; b = 256; a is b` give `True` but it can be `False` for 257?**
**CPython caches ints from -5 to 256, so they are always the same object. Larger ints are created fresh unless the compiler deduplicated identical constants in the same code object. It is an implementation detail; never rely on it.**

**Is Python pass-by-value or pass-by-reference?**
**Neither: it is call by object reference (call by sharing). The parameter is a new name for the caller's object. Mutating the object is visible to the caller; rebinding the parameter is not.**

**Why does `t = ([1],); t[0] += [2]` raise and still change the list?**
**`+=` first calls `list.__iadd__`, which extends the list in place, then tries to assign the result back into the tuple slot, which fails because tuples are immutable.**

**Which values are falsy in Python?**
**`None`, `False`, numeric zeros, and empty sequences and collections (`""`, `[]`, `()`, `{}`, `set()`, `range(0)`, `b""`), plus any object whose `__bool__` returns `False` or whose `__len__` returns 0.**

**Why is a mutable default argument a bug?**
**Defaults are evaluated once at function definition and stored on the function, so the same list or dict is reused and mutated across calls. Use `None` and create the object inside the function.**

**Why can a tuple be a dict key but a list cannot?**
**Dict keys must be hashable, and a hash must stay stable for the object's lifetime. Lists are mutable so they define no hash; tuples are immutable (and hashable as long as all their elements are).**

## Recap

- Every value is an object with an identity, a type and a value. Names are references, not boxes.
- `=` binds a name; it never copies. Function arguments, returns and container elements follow the same rule.
- Mutable objects change in place and all aliases see it; immutable objects only ever get replaced.
- `+=` uses `__iadd__` when available (in place for lists), else creates a new object.
- `==` compares values, `is` compares identity. Use `is` for `None` and sentinels only.
- Small-int caching, constant deduplication and string interning are CPython details.
- `None` is the only null. Empty containers are falsy, unlike in JS. Test `is None` when zero or empty is valid.
