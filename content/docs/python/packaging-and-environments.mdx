Python packaging has a reputation for being confusing, mostly because twenty years of tools are still lying around. The current picture is simpler than its history: **one `pyproject.toml` per project, one virtual environment per project, one lock file for apps**, and these days usually **uv** to drive all three.

Commands below were run with **CPython 3.14.6** and **uv 0.12.1** on Windows. Paths are shortened, and long installer output is trimmed.

## Why virtual environments exist

### The problem

When Python runs `import requests`, it searches `sys.path`, and the third-party part of `sys.path` is a single `site-packages` directory belonging to **the interpreter**. Without isolation, every project on the machine shares one `site-packages`, so project A needing `pydantic 1` and project B needing `pydantic 2` can't both work. On Linux the system Python is also used by the OS itself, which is why modern distros mark it "externally managed" (PEP 668) and `pip install` refuses to touch it.

### What a venv actually is

A virtual environment is a **directory** containing:

- a `pyvenv.cfg` file,
- a small `python` executable (a copy or symlink of the base interpreter),
- its own empty `site-packages`.

```text title="Output"
$ python -m venv .venv
$ ls .venv .venv/Scripts
.venv:
Include  Lib  Scripts  pyvenv.cfg

.venv/Scripts:
Activate.ps1  activate  activate.bat  activate.fish  deactivate.bat
pip.exe  pip3.14.exe  pip3.exe  python.exe  pythonw.exe

$ cat .venv/pyvenv.cfg
home = C:\Users\ritesh-18\miniconda3
include-system-site-packages = false
version = 3.14.6
executable = C:\Users\ritesh-18\miniconda3\python.exe
```

(`Scripts\` on Windows, `bin/` on Linux and macOS.)

How it works underneath: at startup, the `site` module looks for a `pyvenv.cfg` next to the executable (or one directory up). If it finds one, it sets `sys.prefix` to the venv directory and uses the venv's `site-packages` instead of the global one. The standard library still comes from the base install (`home`), so a venv is cheap: no copy of the stdlib, only packages.

```python
import sys
print(sys.prefix)
print(sys.base_prefix)
print(sys.prefix != sys.base_prefix)     # the usual "am I in a venv?" check
print([p for p in sys.path if "site-packages" in p])
```

```text title="Output"
C:\work\venvdemo\.venv
C:\Users\ritesh-18\miniconda3
True
['C:\\work\\venvdemo\\.venv\\Lib\\site-packages']
```

**Activation is optional.** `source .venv/bin/activate` only puts `.venv/bin` first on `PATH` (and sets `VIRTUAL_ENV` and the prompt). Running `.venv/bin/python app.py` directly does exactly the same thing, which is what Docker images, systemd units and `uv run` rely on.

Traps:

- **Venvs aren't relocatable.** Scripts in `bin/` hard-code the absolute interpreter path. Don't move them or copy them between machines. Rebuild them from the lock file.
- **Don't commit `.venv`.** Add it to `.gitignore` and `.dockerignore`.
- **A venv is tied to one interpreter build.** Upgrading the base Python (3.13 to 3.14) means recreating the venv, because compiled extensions are built for a specific ABI.

<Callout title="Coming from JS">
A venv is Python's `node_modules`, with two differences. First, Node resolves packages by walking up from the **importing file** to the nearest `node_modules`, so isolation per project is automatic. Python resolves from the **interpreter's** `sys.path`, so isolation needs a separate interpreter context, which is the venv. Second, `node_modules` can hold several versions of the same package nested inside each other. A Python environment holds **exactly one version of each distribution**, so the resolver has to find a single version that satisfies everyone. Version conflicts that npm hides by nesting become hard resolution errors in Python.
</Callout>

## pip, requirements files and lock files

`pip` installs distributions into the environment of the interpreter that runs it. Always call it as `python -m pip` so you know which environment that is.

```text title="Output"
$ python -m pip install "requests==2.32.*"
$ python -m pip freeze
certifi==2026.7.22
charset-normalizer==3.5.2
idna==3.20
requests==2.32.5
urllib3==2.8.0
```

The classic workflow is `pip freeze > requirements.txt`, and it has known problems:

- It mixes your **direct** dependencies with **transitive** ones, so you can no longer tell why `idna` is there.
- It records whatever is installed, including stray packages you tried once.
- It has no hashes, no per-platform information, and no record of which Python it was resolved for.

The improved classic setup (pip-tools) splits **intent** from **result**:

| File | Contains | Who edits it |
|---|---|---|
| `requirements.in` or `pyproject.toml` | direct deps with loose ranges, e.g. `fastapi>=0.115` | you |
| `requirements.txt` (compiled) or `uv.lock` | every package, exact versions, hashes | the tool |

A **lock file** is that second file in a richer format: exact versions of the whole tree, artifact hashes, and environment markers so one file works on Linux, macOS and Windows. Since PEP 751 (2025) there's also a standard `pylock.toml` format that tools can exchange.

<Callout title="Coming from JS">
`pyproject.toml` dependencies are your `package.json` `dependencies`, and `uv.lock` is `package-lock.json` or `pnpm-lock.yaml`. `pip freeze > requirements.txt` is like committing the output of `npm ls --all` as your manifest. It works, but you lose the distinction between what you asked for and what came along. `pip install -r requirements.txt` is roughly `npm install`, and `uv sync --locked` is `npm ci`.
</Callout>

## uv: the modern workflow

[uv](https://docs.astral.sh/uv/) is a single Rust binary from Astral that replaces `pip`, `pip-tools`, `virtualenv`, `pyenv`, `pipx` and most of `poetry`. It's fast because it resolves in parallel, keeps a global cache, and installs by hard-linking or copy-on-write cloning from that cache instead of unpacking wheels again for every project.

### Creating a project

```text title="Output"
$ uv init orders-api --python 3.14
Initialized project `orders-api` at `orders-api`

$ tree orders-api
.python-version
README.md
pyproject.toml
src/orders_api/__init__.py
```

Current uv versions create applications with a **src layout** and a build backend by default (`uv init --no-package` gives the older flat `main.py` project, and `uv init --lib` adds a `py.typed` marker for a library):

```toml
[project]
name = "orders-api"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.14"
dependencies = []

[project.scripts]
orders-api = "orders_api:main"

[build-system]
requires = ["uv_build>=0.12.1,<0.13.0"]
build-backend = "uv_build"
```

`.python-version` contains `3.14`. uv uses it to pick (and download if needed) the interpreter.

### Adding dependencies

```text title="Output"
$ uv add fastapi "uvicorn[standard]"
Creating virtual environment at: .venv
Resolved 21 packages in 381ms
Prepared 8 packages in 408ms
Installed 20 packages in 636ms

$ uv add --dev pytest ruff
 + pytest==9.1.1
 + ruff==0.17.0
```

One command did four things: it created `.venv`, **edited `pyproject.toml`**, **resolved and wrote `uv.lock`**, and **synced** the environment.

```toml
dependencies = [
    "fastapi>=0.143.0",
    "uvicorn[standard]>=0.54.0",
]

[dependency-groups]
dev = [
    "pytest>=9.1.1",
    "ruff>=0.17.0",
]
```

- `uvicorn[standard]` asks for an **extra**: optional dependencies the package declares (here `uvloop`, `httptools` and others).
- `[dependency-groups]` (PEP 735) holds dev-only tools. Unlike `[project.optional-dependencies]` (extras), groups are *not* published with your package.

### The lock file

```toml
version = 1
revision = 3
requires-python = ">=3.14"

[[package]]
name = "fastapi"
version = "0.143.0"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "annotated-doc" },
    { name = "opentelemetry-api" },
    { name = "pydantic" },
    { name = "starlette" },
    { name = "typing-extensions" },
    { name = "typing-inspection" },
]
sdist = { url = "https://files.pythonhosted.org/.../fastapi-0.143.0.tar.gz", hash = "sha256:1acffe48...", size = 468391 }
```

`uv.lock` is **universal**: uv resolves for every platform and Python version allowed by `requires-python` at once, recording markers where the answer differs. One lock file serves your Mac, the Linux CI runner and the Docker image. Commit it for applications.

### Running and syncing

```text title="Output"
$ uv run orders-api
Hello from orders-api!

$ uv run python -c "import sys, fastapi; print(sys.prefix.endswith('.venv'), fastapi.__version__)"
True 0.143.0

$ uv tree --depth 1
orders-api v0.1.0
├── fastapi v0.143.0
├── uvicorn[standard] v0.54.0
├── pytest v9.1.1 (group: dev)
└── ruff v0.17.0 (group: dev)

$ uv sync --locked
Resolved 28 packages in 1ms
Checked 27 packages in 2ms
```

`uv run` checks that the lock file matches `pyproject.toml`, syncs `.venv` if needed, then runs the command inside the environment. You never activate anything. The commands you'll use daily:

| Command | What it does |
|---|---|
| `uv add pkg` / `uv remove pkg` | edit deps, re-lock, sync |
| `uv lock` | re-resolve `uv.lock` without installing |
| `uv lock --upgrade-package fastapi` | bump one package within its allowed range |
| `uv sync` | make `.venv` match the lock (removes extras) |
| `uv sync --locked` | same, but **fail** if the lock is out of date (use in CI) |
| `uv sync --frozen` | use the lock as is without checking it (Docker layer trick) |
| `uv run cmd` | run inside the project env |
| `uv export` | write a `requirements.txt` from the lock for other tools |
| `uv tool install ruff` / `uvx ruff` | global CLI tools in isolated envs (like `npx`) |
| `uv pip install ...` | pip-compatible interface for existing workflows |

### Managing Python versions

uv downloads standalone CPython builds, so you don't need pyenv or the system Python:

```text title="Output"
$ uv python install 3.15
$ uv python list --only-installed
cpython-3.14.6-windows-x86_64-none     C:\Users\ritesh-18\miniconda3\python.exe
cpython-3.11.15-windows-x86_64-none    C:\Users\ritesh-18\AppData\Roaming\uv\python\...
$ uv python pin 3.13
error: The requested Python version `3.13` is incompatible with the project `requires-python` value of `>=3.14`.
```

`uv python pin` writes `.python-version` and checks it against `requires-python`. Free-threaded builds are available as `3.14t`.

<Callout title="Coming from JS">
The mapping is close: `uv init` is `npm init`, `uv add` is `pnpm add`, `uv add --dev` is `pnpm add -D`, `uv sync --locked` is `npm ci`, `uv run` is `npm run` or `npx` inside the project, `uvx tool` is `npx tool`, and `uv python install` combined with `.python-version` is `nvm`/`fnm` with `.nvmrc`. One difference: Python has no `"scripts"` section that runs shell commands. `[project.scripts]` defines **console entry points** that get installed as executables. For task running, people use `uv run pytest`, a Makefile, or tools like `poe` or `just`.
</Callout>

## `pyproject.toml` in depth

### `[project]`: PEP 621 metadata

This table is standardized, so every build backend reads the same keys:

```toml
[project]
name = "orders-api"                     # distribution name on PyPI
version = "0.1.0"                       # or: dynamic = ["version"]
description = "Order service"
readme = "README.md"
requires-python = ">=3.12"
license = "MIT"                         # SPDX expression (PEP 639)
authors = [{ name = "Ada", email = "ada@example.com" }]
dependencies = ["fastapi>=0.115", "sqlalchemy>=2.0,<3"]

[project.optional-dependencies]         # extras: pip install orders-api[postgres]
postgres = ["asyncpg>=0.29"]

[project.scripts]                       # console commands created on install
orders-api = "orders_api.cli:main"

[project.urls]
Homepage = "https://github.com/acme/orders-api"
```

The distribution name (`orders-api`) and the import name (`orders_api`) are different things. They often match, but not always: `pip install pillow` gives you `import PIL`, and `scikit-learn` gives you `import sklearn`.

### `[build-system]`: the build backend

```toml
[build-system]
requires = ["hatchling"]                # installed into an isolated build env
build-backend = "hatchling.build"       # the object pip/uv calls
```

PEP 517 split the **frontend** (pip, uv, `python -m build`), which creates an isolated environment and calls hooks, from the **backend**, which actually produces the wheel. Common backends:

| Backend | Notes |
|---|---|
| `uv_build` | uv's own, fast, pure-Python packages only, strict about layout |
| `hatchling` | popular general-purpose backend, plugins for dynamic versions |
| `setuptools` | the original, needed for many C-extension projects |
| `flit-core` | minimal, pure Python |
| `maturin` | Rust extensions (PyO3) |
| `scikit-build-core`, `meson-python` | C/C++ extensions via CMake/Meson |

Without a `[build-system]` table the project isn't installable as a package: uv treats it as a "virtual" project and installs only its dependencies. That's fine for a script collection, but it means `import orders_api` works only from the right working directory.

### `[tool.*]`

Every tool reads its own table: `[tool.ruff]`, `[tool.pytest.ini_options]`, `[tool.mypy]`, `[tool.uv]`. This replaces the old `setup.cfg`, `tox.ini` and `.flake8` sprawl.

## Wheels and sdists

`uv build` (or `python -m build`) produces two artifacts:

```text title="Output"
$ uv build
Building source distribution...
Building wheel from source distribution...
Successfully built dist\orders_api-0.1.0.tar.gz
Successfully built dist\orders_api-0.1.0-py3-none-any.whl
```

- **sdist** (`.tar.gz`): the source plus metadata. Installing it means running the build backend, which for C extensions needs a compiler.
- **wheel** (`.whl`): a zip that's already built. Installing it is just unzipping into `site-packages`. The filename tags say where it works: `py3-none-any` means pure Python, any OS. `cp314-cp314-manylinux_2_28_x86_64` means CPython 3.14 on glibc 2.28+ Linux. `cp314t` is the free-threaded ABI.

When a wheel for your platform is missing (new Python version, Alpine/musl, an exotic CPU), pip falls back to the sdist and you see compiler errors. That's the root of most "pip install failed" stories, and the reason you should be careful with Alpine images.

## The src layout

```text
orders-api/
├── pyproject.toml
├── src/
│   └── orders_api/
│       ├── __init__.py
│       └── api.py
└── tests/
    └── test_api.py
```

Versus the flat layout, where `orders_api/` sits next to `pyproject.toml`.

**Why `src/`:** when you run `pytest` or `python` from the project root, the current directory is on `sys.path`. With a flat layout `import orders_api` picks up the **source folder directly**, even if the package isn't installed or its packaging config is broken. Tests pass locally, and then the built wheel is missing a module. With `src/`, the only way to import the package is to **install** it, so tests exercise what you ship. It also stops stray top-level folders from being imported by accident.

## Editable installs

During development you want edits to take effect without reinstalling. An **editable** install (`pip install -e .`, and the default for the project itself under `uv sync`) puts a pointer in `site-packages` instead of a copy:

```text title="Output"
$ cat .venv/Lib/site-packages/orders_api.pth
C:\work\orders-api\src

$ uv run python -c "import orders_api; print(orders_api.__file__)"
.\src\orders_api\__init__.py
```

A `.pth` file is read by `site` at startup, and each line is appended to `sys.path`. Some backends use a custom import finder instead (PEP 660 leaves the mechanism to the backend), which can confuse static analysers. If your IDE can't resolve imports from an editable install, that's usually why.

Trap: entry points and metadata (`[project.scripts]`, the version in `importlib.metadata`) are written at install time. After changing them, run `uv sync` again.

## Dependency pinning: apps vs libraries

This is the rule people get wrong most often.

| | Application (API, worker, CLI you deploy) | Library (published to PyPI, used by others) |
|---|---|---|
| `pyproject.toml` deps | lower bounds, e.g. `fastapi>=0.115` | **broad** ranges, e.g. `httpx>=0.25` |
| Upper bounds | optional | avoid unless you know a release breaks you |
| Lock file | **commit it**, deploy from it | commit it for your own CI if you like, but users never see it |
| Goal | reproducible deploys | coexist with everyone else's dependencies |

Why libraries shouldn't pin exactly: a Python environment can hold only one version of each package. If your library requires `pydantic==2.7.1` and another library requires `pydantic>=2.8`, the user can't install both. Tight caps like `<3` on every dependency cause the same problem a year later. Applications are the end of the chain, so they lock *everything* exactly and upgrade on purpose (`uv lock --upgrade`, with Renovate or Dependabot opening PRs).

<Callout title="Coming from JS">
npm can install two versions of one package side by side, so a library pinning `lodash@4.17.20` is merely wasteful. In Python it's a resolution failure for your users. Treat library ranges like `peerDependencies`: as wide as you can honestly support.
</Callout>

## Publishing basics

1. Choose a free name on PyPI and fill in `[project]` metadata (license, readme, URLs, classifiers).
2. Build: `uv build`, which writes the sdist and wheel to `dist/`.
3. Test on TestPyPI: `uv publish --publish-url https://test.pypi.org/legacy/`.
4. Publish: `uv publish`. Prefer **trusted publishing** from GitHub Actions (OIDC, no long-lived API token stored in secrets) over pasting tokens.
5. Version with SemVer-ish rules. `uv version --bump minor` edits `pyproject.toml` for you.

Pure-Python packages need one `py3-none-any` wheel. Packages with C or Rust code need wheels for each platform and Python version, usually built in CI with `cibuildwheel` or `maturin`.

## Docker for Python apps

### Picking a base image

| Image | Size | Notes |
|---|---|---|
| `python:3.14` | about 1 GB | full Debian with compilers, for build stages |
| `python:3.14-slim` | about 150 MB | **default choice** for runtime |
| `python:3.14-alpine` | small | musl libc: many wheels don't exist, so builds from source are slow, and musl's allocator can be slower |
| distroless / chainguard | small | no shell, good for hardening |

### A uv-based Dockerfile

Following the patterns in the uv Docker guide: install dependencies in a cached layer first, then copy the code. Build in one stage and ship only the venv. (I haven't built this image as part of these notes. It's a template.)

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.12.1 /uv /uvx /bin/

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_NO_DEV=1 \
    UV_PYTHON_DOWNLOADS=0

WORKDIR /app

# 1) dependencies only: this layer is reused until uv.lock or pyproject.toml change
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --frozen --no-install-project --no-editable

# 2) the project itself
COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-editable

FROM python:3.14-slim
RUN useradd --create-home app
COPY --from=builder --chown=app:app /app/.venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1
USER app
EXPOSE 8000
CMD ["uvicorn", "orders_api.api:app", "--host", "0.0.0.0", "--port", "8000"]
```

Why each piece is there:

- **Pinned uv image tag** (and ideally a digest) for reproducible builds.
- **`--no-install-project` first**: dependencies change rarely and the code changes constantly, so the slow layer stays cached. It's the same reason Node Dockerfiles copy `package.json` before `src/`.
- **`--mount=type=cache`** keeps uv's download cache between builds without baking it into the image. `UV_LINK_MODE=copy` avoids hard-link warnings, since the cache mount is a different filesystem.
- **`--locked`** fails the build if `uv.lock` is stale, and **`UV_NO_DEV=1`** leaves out pytest and ruff.
- **`--no-editable`** installs the project into the venv as a real package, so the final stage needs only `.venv`, not the source tree.
- **`UV_COMPILE_BYTECODE=1`** writes `.pyc` files at build time, so the container doesn't compile on every cold start (it can't write them as a non-root user anyway).
- **`PYTHONUNBUFFERED=1`** makes logs show up immediately in `docker logs`.
- Both stages must use the **same base image**, since the venv's `python` points at `/usr/local/bin/python`.
- Add `.venv`, `__pycache__` and `.git` to `.dockerignore`.

## Interview questions

1. **What does a virtual environment change at runtime?** **`site` finds `pyvenv.cfg` next to the interpreter and sets `sys.prefix` to the venv, so the venv's `site-packages` is used instead of the global one. The stdlib still comes from the base install. Activation only edits `PATH`.**
2. **Why can't Python install two versions of the same package like npm can?** **Imports resolve by name through `sys.path` and cache in `sys.modules`, so there's one `requests` per environment. The resolver must find a single version that satisfies everyone.**
3. **`requirements.txt` vs a lock file?** **A frozen requirements file lists installed versions, with no separation of direct and transitive deps, no hashes and no cross-platform markers. A lock file such as `uv.lock` records the full resolved graph with hashes and markers for every platform, generated from the loose ranges in `pyproject.toml`.**
4. **How should pinning differ for an app and a library?** **Apps commit a lock file with exact versions for reproducible deploys. Libraries declare broad ranges so they can coexist with other packages, because exact pins cause unresolvable conflicts for users.**
5. **What's a build backend?** **The tool named in `[build-system]` (hatchling, setuptools, uv_build, maturin) that turns source into a wheel and sdist through PEP 517 hooks. pip and uv are frontends that call it in an isolated environment.**
6. **Why use the src layout?** **The package can't be imported from the working directory by accident, so tests run against the installed package and packaging mistakes surface before release.**
7. **What does `uv sync --locked` do and why use it in CI?** **It installs exactly what `uv.lock` says and fails if the lock no longer matches `pyproject.toml`, which catches forgotten lock updates. It's the counterpart of `npm ci`.**
8. **How do you keep Python Docker builds fast and small?** **Use a slim base, install dependencies in a cached layer before copying the code (`--no-install-project`), use a uv cache mount, and do a multi-stage build that copies only `.venv` (`--no-editable`), with bytecode compiled at build time.**

## Recap

- A venv is a directory with `pyvenv.cfg` and its own `site-packages`. It isolates projects because Python resolves imports per interpreter, not per file.
- `pyproject.toml` holds metadata (`[project]`), how to build (`[build-system]`) and tool config (`[tool.*]`). The lock file holds the exact resolved graph.
- uv covers it all: `uv init`, `uv add`, `uv lock`, `uv sync --locked`, `uv run`, `uv python install`, `uv build`, `uv publish`.
- Use the src layout and editable installs during development, and wheels for distribution.
- Lock apps exactly, keep library ranges broad.
- Docker: a slim image, a cached dependency layer, a multi-stage build that copies only the venv, and a pinned uv version.
