Python 3 draws a hard line between **text** (`str`) and **binary data** (`bytes`). Text is a sequence of Unicode code points; bytes are a sequence of integers from 0 to 255. You move between them only by **encoding** and **decoding** with a named encoding. Once you internalize that line, a whole class of bugs (mojibake, `UnicodeDecodeError` in production, wrong string lengths) disappears.

<Callout type="info">
Snippets were run on **CPython 3.14.6** with UTF-8 mode on (`python -X utf8`). Sizes from `sys.getsizeof` and timings are CPython specific and machine dependent.
</Callout>

## `str`: a sequence of code points

A `str` is an **immutable sequence of Unicode code points**. A code point is a number from 0 to 0x10FFFF that Unicode assigns to a character (`"é"` is U+00E9, the snake emoji is U+1F40D). Indexing, slicing and `len` all work in code points.

```python
s = "café 🐍"
print(len(s), [hex(ord(c)) for c in s])
print(s[3], s[-1], chr(0x1F40D), "\u00e9", "\N{SNAKE}")
```

```text title="Output"
6 ['0x63', '0x61', '0x66', '0xe9', '0x20', '0x1f40d']
é 🐍 🐍 é 🐍
```

- `ord(c)` gives the code point number, `chr(n)` gives the one-character string.
- Escapes: `\xNN` (2 hex digits), `\uNNNN` (4), `\UNNNNNNNN` (8), and `\N{NAME}` by Unicode name.
- There is no separate `char` type. `"abc"[0]` is a `str` of length 1.

<Callout title="Coming from JS">
JavaScript strings are sequences of **UTF-16 code units**, so `"🐍".length` is `2` and `"🐍"[0]` is half a surrogate pair. In Python, `len("🐍")` is `1` and indexing never splits a code point. (Both languages still count a user-perceived character made of several code points, like `"e"` plus a combining accent or a family emoji, as more than one; see normalization below.)
</Callout>

### How CPython stores strings (PEP 393)

CPython does not use one fixed encoding internally. Each string picks the **narrowest** fixed width that fits its largest code point:

| Largest code point | Storage per character | Name |
|---|---|---|
| up to U+007F (ASCII) | 1 byte | ASCII compact |
| up to U+00FF | 1 byte | Latin-1 |
| up to U+FFFF | 2 bytes | UCS-2 |
| above U+FFFF (emoji etc.) | 4 bytes | UCS-4 |

```python
import sys
for t in ("abc", "é", "€", "🐍"):
    print(t, sys.getsizeof(t), sys.getsizeof(t * 100))
```

```text title="Output"
abc 44 341
é 61 157
€ 60 258
🐍 64 460
```

100 ASCII characters cost about 1 byte each, 100 euro signs about 2 bytes each, 100 snakes about 4 bytes each. Because widths are fixed per string, `s[i]` is O(1), unlike indexing into UTF-8 data. The cost: a single emoji in a large ASCII document quadruples its memory. The object header is around 40 to 60 bytes.

## Encoding and decoding

**Encoding** turns `str` into `bytes`; **decoding** turns `bytes` into `str`. An encoding is the rule for mapping code points to bytes. **UTF-8** is the default almost everywhere: ASCII characters take 1 byte, most European and Middle Eastern scripts 2, most Asian scripts 3, emoji 4.

```python
b = s.encode("utf-8")
print(b, len(b), type(b))
print(b.decode("utf-8"))
print(len("é".encode("utf-8")), len("é".encode("utf-16-le")), len("🐍".encode("utf-16-le")))
```

```text title="Output"
b'caf\xc3\xa9 \xf0\x9f\x90\x8d' 10 <class 'bytes'>
café 🐍
2 2 4
```

6 code points became 10 bytes. **Length in characters and length in bytes are different numbers**; when a database column, HTTP header or API limit is defined in bytes, measure `len(s.encode())`.

### The "Unicode sandwich"

The robust pattern for any program that does I/O:

1. **Decode at the edges**: as soon as bytes come in (file, socket, HTTP body), decode them to `str`.
2. **Work with `str` inside** your program.
3. **Encode at the edges**: when writing out, encode to bytes.

Frameworks usually do steps 1 and 3 for you (FastAPI gives you `str` and `dict`, `open(path)` in text mode decodes). The bugs appear when you guess the encoding wrong.

### Errors and error handlers

Not every `str` fits every encoding, and not every byte sequence is valid UTF-8:

```python
try:
    "café".encode("ascii")
except UnicodeEncodeError as e:
    print("UnicodeEncodeError:", e)
print("café".encode("ascii", errors="replace"), "café".encode("ascii", errors="ignore"),
      "café".encode("ascii", errors="xmlcharrefreplace"), "café".encode("ascii", errors="backslashreplace"))

raw = b"caf\xe9"          # "café" encoded as Latin-1, not UTF-8
try:
    raw.decode("utf-8")
except UnicodeDecodeError as e:
    print("UnicodeDecodeError:", e)
print(raw.decode("utf-8", errors="replace"), raw.decode("latin-1"))
print(repr(raw.decode("utf-8", errors="surrogateescape")))
```

```text title="Output"
UnicodeEncodeError: 'ascii' codec can't encode character '\xe9' in position 3: ordinal not in range(128)
b'caf?' b'caf' b'caf&#233;' b'caf\\xe9'
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 3: unexpected end of data
caf� café caf\udce9
```

| `errors=` | On encode | On decode |
|---|---|---|
| `"strict"` (default) | raise | raise |
| `"replace"` | `?` | U+FFFD replacement character |
| `"ignore"` | drop silently | drop silently |
| `"backslashreplace"` | `\xe9` escape | `\xe9` escape |
| `"xmlcharrefreplace"` | `&#233;` | n/a |
| `"surrogateescape"` | restores original bytes | smuggles bad bytes as lone surrogates |

`"latin-1"` never fails to decode (every byte maps to a code point), which makes it a tempting "fix" that silently produces mojibake. Prefer `strict` and find out what the real encoding is. `surrogateescape` is what Python uses for undecodable file names on Unix so they round-trip losslessly.

### Default encodings (and the Windows trap)

- Source files are UTF-8 by default.
- `open(path)` without `encoding=` uses the **locale encoding**. On Linux and macOS that is usually UTF-8; on Windows it is often a legacy code page like `cp1252`. Code that works on a Mac can crash on a Windows server. (While writing these notes, printing an emoji to a redirected stdout on Windows failed with `UnicodeEncodeError: 'charmap' codec can't encode character` until UTF-8 mode was enabled.)
- **Python 3.15 makes UTF-8 mode the default** (PEP 686): `open()` and the standard streams use UTF-8 regardless of locale. Until all your environments run 3.15+, always pass `encoding="utf-8"` explicitly, or run with `PYTHONUTF8=1` / `-X utf8`.

## `bytes` and `bytearray`

`bytes` is an immutable sequence of ints in `range(256)`. `bytearray` is its mutable sibling. Their literals look like strings with a `b` prefix, but only ASCII characters may appear literally.

```python
data = b"GET / HTTP/1.1"
print(data[0], data[:3], list(data[:3]), b"A" + b"B", data.split())
try:
    data + "x"
except TypeError as e:
    print("TypeError:", e)
print(b"abc" == "abc")
```

```text title="Output"
71 b'GET' [71, 69, 84] b'AB' [b'GET', b'/', b'HTTP/1.1']
TypeError: can't concat str to bytes
False
```

- **Indexing gives an `int`**, slicing gives `bytes`.
- `bytes` and `str` never compare equal and never mix. That strictness is the point.
- `bytes` has most `str` methods (`split`, `strip`, `startswith`, `replace`), working on ASCII semantics.

Constructing and inspecting:

```python
print(bytes([72, 105]), bytes(3), bytes.fromhex("de ad be ef"), b"\xde\xad".hex(), b"\xde\xad".hex(":"))
buf = bytearray(b"hello")
buf[0] = ord("J"); buf.extend(b"!!")
print(buf, bytes(buf))
mv = memoryview(buf)
mv[1:3] = b"EL"
print(buf)
```

```text title="Output"
b'Hi' b'\x00\x00\x00' b'\xde\xad\xbe\xef' dead de:ad
bytearray(b'Jello!!') b'Jello!!'
bytearray(b'JELlo!!')
```

- `bytes(3)` is three zero bytes, not `b"3"`. A common mistake when converting a number.
- `bytearray` is useful as a growable buffer (e.g. assembling a network frame).
- `memoryview` gives a zero-copy view over a buffer; slicing it does not copy, so you can parse or patch large binary data without allocating.
- For structured binary data (headers, packed numbers) use the `struct` module or `int.to_bytes` and `int.from_bytes`.

### Trap: `str(b"...")`

```python
print(str(b"abc"), b"abc".decode())
```

```text title="Output"
b'abc' abc
```

`str()` on bytes gives the **repr** (`"b'abc'"` with the prefix and quotes), not the decoded text. This shows up as `b'...'` appearing inside log lines, file names or JSON. Always `.decode()`.

<Callout title="Coming from JS">
`bytes` corresponds to Node's `Buffer` / `Uint8Array`, and `.encode()` / `.decode()` correspond to `Buffer.from(str, "utf8")` and `buf.toString("utf8")` (or `TextEncoder` / `TextDecoder`). The difference is strictness: Node's `toString` silently replaces invalid sequences with U+FFFD, while Python's `decode` raises by default.
</Callout>

## Slicing

Strings, bytes, lists and tuples all support the same slicing syntax `seq[start:stop:step]`:

- `start` is inclusive, `stop` is exclusive, `step` defaults to 1.
- Negative indices count from the end (`-1` is the last element).
- Omitted bounds mean "from the beginning" or "to the end" (reversed when `step` is negative).
- **Slices never raise IndexError** for out-of-range bounds; they clamp. Single indexing does raise.

```python
s = "hello, world"
print(s[0], s[-1], s[0:5], s[7:], s[:-7], s[::2], s[::-1], s[100:], s[-100:3])
try:
    s[100]
except IndexError as e:
    print("IndexError:", e)
```

```text title="Output"
h d hello world hello hlo ol dlrow ,olleh  hel
IndexError: string index out of range
```

A slice of a `str` always **creates a new string** (it copies the characters). For huge binary data, slice a `memoryview` instead to avoid copies.

<Callout title="Coming from JS">
`s[1:4]` is `s.slice(1, 4)`. Negative indexing `s[-1]` works directly (JS needs `s.at(-1)`). `s[::-1]` reverses a string in one expression, where JS needs `[...s].reverse().join("")`.
</Callout>

## Common methods

All `str` methods return **new** strings; nothing mutates in place. Calling `s.upper()` and ignoring the result is a silent no-op bug.

```python
s = "  Hello, World  "
print(repr(s.strip()), repr(s.lstrip()), s.lower(), s.upper(), s.strip().casefold())
print("a,b,,c".split(","), "a  b\tc\n".split(), "k=v=w".split("=", 1), "k=v=w".rsplit("=", 1), "k=v".partition("="))
print("-".join(["2026", "10", "13"]), "abc".startswith(("x", "a")), "report.pdf".endswith(".pdf"))
print("hello".find("l"), "hello".find("z"), "hello".rfind("l"), "hello".count("l"), "hello".replace("l", "L", 1))
```

```text title="Output"
'Hello, World' 'Hello, World  '   hello, world     HELLO, WORLD   hello, world
['a', 'b', '', 'c'] ['a', 'b', 'c'] ['k', 'v=w'] ['k=v', 'w'] ('k', '=', 'v')
2026-10-13 True True
2 -1 3 2 heLlo
```

Notes on the ones that trip people up:

- `split()` with **no argument** splits on runs of any whitespace and drops empty strings. `split(" ")` splits on each single space and keeps empty strings.
- `partition(sep)` always returns a 3-tuple, which makes parsing `key=value` safe even when `=` is missing.
- `find` returns `-1` when missing; `index` raises `ValueError`. Prefer `in` for a yes/no check.
- `startswith` and `endswith` accept a **tuple** of options.

```python
print("v1.2.3".removeprefix("v"), "file.tar.gz".removesuffix(".gz"), "xxhixx".strip("x"), "abcba".strip("ab"))
print("42".isdigit(), "4.2".isdigit(), "²".isdigit(), "²".isdecimal(), "abc".isalpha(), "  ".isspace())
print("ß".upper(), "ß".casefold(), "Straße".lower() == "strasse", "Straße".casefold() == "strasse".casefold())
```

```text title="Output"
1.2.3 file.tar hi c
True False True False True True
SS ss False True
```

- `strip("ab")` treats its argument as a **set of characters** to remove from both ends, not as a prefix. To remove an exact prefix or suffix use `removeprefix` / `removesuffix` (3.9+). Using `lstrip("https://")` to remove a URL scheme is a classic bug.
- `isdigit()` is `True` for superscripts like `"²"` that `int()` cannot parse. To validate input, just try `int(s)` and catch `ValueError`.
- For case-insensitive comparison use `casefold()`, not `lower()`; it handles cases like German ß.

### Comparison and ordering

```python
print("a" < "b", "Z" < "a", "apple" < "apricot", "10" < "9", sorted(["b", "A", "a", "B"]), sorted(["b", "A", "a", "B"], key=str.casefold))
```

```text title="Output"
True True True True ['A', 'B', 'a', 'b'] ['A', 'a', 'b', 'B']
```

Strings compare by code point, lexicographically. Uppercase letters sort before lowercase, and `"10" < "9"`. For human-friendly ordering use a `key` function (or `locale.strxfrm`, or the third-party `natsort` for "file10 after file9").

## f-strings in depth

An f-string (`f"..."`) is a string literal with embedded expressions in braces. The compiler turns it into bytecode that evaluates each expression, formats it, and concatenates the pieces (no runtime parsing of the template), which is why f-strings are the fastest formatting option.

The full syntax of a replacement field is:

```text
{expression = !conversion :format_spec}
```

All parts after the expression are optional.

### Conversions and format specs

```python
name, n, price = "Ada", 3, 1234.5
print(f"{name!r} bought {n} items for {price:,.2f}")
print(f"{name:>8}|{name:<8}|{name:^8}|{name:*^9}")
print(f"{n:05d} {price:10.1f} {price:e} {0.25:%} {255:x} {255:#o} {1_000_000:_}")
```

```text title="Output"
'Ada' bought 3 items for 1,234.50
     Ada|Ada     |  Ada   |***Ada***
00003     1234.5 1.234500e+03 25.000000% ff 0o377 1_000_000
```

- **Conversions**: `!r` calls `repr()`, `!s` calls `str()`, `!a` calls `ascii()`. Use `!r` in log and error messages so empty strings and whitespace are visible.
- **Format spec** (the "format mini-language"): `[[fill]align][sign][#][0][width][grouping][.precision][type]`.
  - align: `<` left, `>` right, `^` center, `=` pad after the sign.
  - grouping: `,` or `_` thousands separators.
  - types: `d` int, `f` fixed, `e` exponent, `g` general, `%` percent, `x` / `o` / `b` hex, octal, binary, `s` string.
- The spec is passed to the object's `__format__` method, so each type can define its own. `datetime` uses `strftime` codes:

```python
from datetime import datetime
d = datetime(2026, 10, 13, 9, 5)
print(f"{d:%Y-%m-%d %H:%M}", f"{d=!r}")
```

```text title="Output"
2026-10-13 09:05 d=datetime.datetime(2026, 10, 13, 9, 5)
```

### Nested fields

The format spec can itself contain replacement fields, which is how you make width or precision dynamic:

```python
width, prec = 10, 3
print(f"{3.14159:{width}.{prec}f}|")
```

```text title="Output"
     3.142|
```

### The `=` debug specifier

Adding `=` after the expression (3.8+) prints the expression text, `=`, and the value. Whitespace around `=` is preserved, and it defaults to `repr` unless you add a conversion or format spec:

```python
print(f"{n=}, {price * 2 = }, {name=!s}, {price=:.0f}")
```

```text title="Output"
n=3, price * 2 = 2469.0, name=Ada, price=1234
```

This is the quickest way to debug-print variables.

### What changed in 3.12 (PEP 701)

Since 3.12, f-strings are parsed by the real Python parser instead of a special mini-parser, which removed old restrictions:

```python
items = {"a": 1}
print(f"{items['a']}", f"{'nested ' + f'{n}'}", f"{{literal braces}}")
print(f"{"double quotes reused"}")
print(f"{'\n'.join(['x', 'y'])}")
print(f"""{
    n   # a comment inside a multi-line f-string (3.12+)
    + 1
}""")
```

```text title="Output"
1 nested 3 {literal braces}
double quotes reused
x
y
4
```

- You can **reuse the same quote** type inside the expression (`f"{"x"}"`). Before 3.12 this was a syntax error.
- **Backslashes** are allowed in the expression part.
- Multi-line expressions and `#` comments are allowed inside triple-quoted f-strings.
- Double the braces (two opening or two closing braces) to get a literal brace.

### When not to use f-strings

- **Logging**: write `logger.info("user %s logged in", user_id)` rather than an f-string. The logging module only formats the message if the record is actually emitted, and log aggregators can group messages by the constant template.
- **SQL, HTML, shell commands**: never build them with f-strings from user input. Use parameterized queries (`cursor.execute("... WHERE id = %s", (user_id,))`), template engines with auto-escaping, and `subprocess.run([...])` with a list.
- **Templates defined at run time** (e.g. loaded from a config): use `str.format` or `string.Template`, since f-strings are evaluated where they are written.

### Template strings (`t"..."`, 3.14)

Python 3.14 added **t-strings** (PEP 750). They look like f-strings but evaluate to a `Template` object that keeps the static text and the interpolated values **separate**, instead of producing a `str`. A library can then process the values safely (escape HTML, parameterize SQL):

```python
from string.templatelib import Template
import html

user = "<script>"
t = t"Hello {user}!"
print(type(t).__name__, t.strings, [i.value for i in t.interpolations])
print("".join(p if isinstance(p, str) else html.escape(p.value) for p in t))
```

```text title="Output"
Template ('Hello ', '!') ['<script>']
Hello &lt;script&gt;!
```

<Callout title="Coming from JS">
f-strings are template literals: `` `Hello ${name}` `` becomes `f"Hello {name}"`. t-strings are Python's answer to **tagged templates** (`` html`...` ``): instead of a tag function receiving strings and values, the receiving function gets a `Template` object. JS template literals have no built-in equivalent of the format spec (`:,.2f`); you use `toFixed` or `Intl.NumberFormat`.
</Callout>

### Other formatting styles you will meet

```python
"%s has %d items" % ("cart", 3)        # printf-style, old but still used in logging
"{} has {} items".format("cart", 3)     # str.format, useful for runtime templates
"{name} has {n} items".format(name="cart", n=3)
```

## Joining vs `+` in loops

Strings are immutable, so `s += piece` must, in principle, allocate a new string and copy everything accumulated so far. Doing that in a loop is **O(n squared)** in the total length.

CPython has an optimization: if the string on the left has **no other references**, `+=` resizes it in place instead of copying. That makes the naive loop fast, until something else holds a reference and the optimization silently turns off:

```python
import timeit

def concat(n):
    s = ""
    for i in range(n):
        s += str(i)
    return s

def concat_alias(n):
    s = ""
    for i in range(n):
        keep = s          # a second reference disables the in-place trick
        s += str(i)
    return s

def joined(n):
    return "".join([str(i) for i in range(n)])

for n in (20_000, 80_000):
    for f in (concat, concat_alias, joined):
        t = min(timeit.repeat(lambda: f(n), number=3, repeat=3)) / 3 * 1000
        print(f"n={n:<6} {f.__name__:<13} {t:7.2f} ms")
```

```text title="Output"
n=20000  concat           2.82 ms
n=20000  concat_alias    21.32 ms
n=20000  joined           1.96 ms
n=80000  concat          12.41 ms
n=80000  concat_alias   334.52 ms
n=80000  joined           9.89 ms
```

With 4 times more data, `concat_alias` got about 16 times slower (quadratic), while the others grew linearly. The in-place trick is a CPython detail that PyPy and other implementations do not have, and it also does not apply in many real situations (attributes like `self.buf += x`, strings shared elsewhere).

**Rule**: collect pieces in a list and `"".join(parts)` once at the end. `join` computes the total length, allocates once and copies each piece once. (A list comprehension is slightly faster than a generator expression inside `join`, because `join` needs to materialize the sequence anyway to measure it.) For building large text incrementally, `io.StringIO` is another option.

## Raw strings

A raw string (`r"..."`) turns off backslash escape processing. Use it for **regular expressions** and **Windows paths**:

```python
print(r"C:\new\table", "C:\new\table")
print(len(r"\n"), len("\n"))
import re
print(re.findall(r"\d+", "a1b22c333"))
```

```text title="Output"
C:\new\table C:
ew	able
2 1
['1', '22', '333']
```

In the non-raw version, `\n` became a newline and `\t` a tab. Unknown escapes like `"\d"` currently produce a `SyntaxWarning` (it was a `DeprecationWarning` before 3.12) and will become errors in a future version, so always write regexes as raw strings.

Trap: a raw string cannot end with an odd number of backslashes (`r"C:\dir\"` is a syntax error), because the backslash still escapes the closing quote for the tokenizer. For paths, prefer `pathlib.Path` and forward slashes, which work on Windows too.

## `str.translate`

`translate` maps characters one by one through a table built with `str.maketrans`. It does all replacements in a single pass in C, which is faster and clearer than chaining many `replace` calls:

```python
table = str.maketrans({"-": "_", " ": None, "é": "e"})
print("my-file name é.txt".translate(table))
print("hello".translate(str.maketrans("el", "ip")))
```

```text title="Output"
my_filenamee.txt
hippo
```

Mapping a character to `None` deletes it. Typical uses: slugifying, stripping punctuation, normalizing quotes.

## Unicode normalization

The same visible text can be encoded as **different code point sequences**. "é" can be one code point (U+00E9, precomposed) or two ("e" plus U+0301 COMBINING ACUTE ACCENT, decomposed). They render the same, but they are different strings:

```python
import unicodedata
a = "café"
b = "cafe\u0301"
print(a, b, a == b, len(a), len(b))
print(unicodedata.normalize("NFC", b) == a, len(unicodedata.normalize("NFD", a)))
print([unicodedata.name(c) for c in b[-2:]])
```

```text title="Output"
café café False 4 5
True 5
['LATIN SMALL LETTER E', 'COMBINING ACUTE ACCENT']
```

| Form | What it does | Use for |
|---|---|---|
| **NFC** | compose where possible | storing and comparing text (most common) |
| **NFD** | decompose fully | stripping accents |
| **NFKC** | compose + replace "compatibility" characters | usernames, search, identifiers |
| **NFKD** | decompose + compatibility | search indexing |

```python
print(unicodedata.normalize("NFKC", "ﬁ ①"))

def strip_accents(t):
    return "".join(c for c in unicodedata.normalize("NFD", t) if not unicodedata.combining(c))
print(strip_accents("Crème brûlée"))
```

```text title="Output"
fi 1
Creme brulee
```

Where this matters in a backend: macOS file systems historically returned NFD file names, user input from different keyboards and OSes varies, and **unique constraints on usernames or emails** should be applied to a normalized (NFKC plus `casefold`) form, or two visually identical accounts can exist. Python itself normalizes identifiers in source code with NFKC.

<Callout title="Coming from JS">
`unicodedata.normalize("NFC", s)` is `s.normalize("NFC")` in JS. For splitting text into user-perceived characters (grapheme clusters), JS has `Intl.Segmenter`; Python's standard library has no grapheme API, so use the third-party `grapheme` or `regex` (with `\X`) packages.
</Callout>

## String interning

As covered in the object model page, CPython **interns** some strings: identifiers and identifier-like constants are stored once, so equal ones are the same object and dict lookups on attribute names can compare pointers first. Strings created at run time (read from files, built with `join`, decoded from bytes) are not interned automatically. `sys.intern(s)` returns the canonical copy, which can save memory when you hold many duplicate strings, such as repeated keys from millions of parsed records. Never rely on interning for correctness; compare strings with `==`.

## Interview questions

**What is the difference between `str` and `bytes`?**
**`str` is an immutable sequence of Unicode code points (text); `bytes` is an immutable sequence of integers 0 to 255 (binary data). You convert with `encode` and `decode` and an explicit encoding; they never mix or compare equal.**

**Why can `len(s)` differ from `len(s.encode())`?**
**`len(s)` counts code points; the encoded length counts bytes. In UTF-8 non-ASCII characters take 2 to 4 bytes.**

**How does CPython store strings in memory?**
**Per PEP 393 each string uses a fixed width of 1, 2 or 4 bytes per character, chosen by its widest code point, which keeps indexing O(1).**

**Why is `"".join(parts)` preferred over `+=` in a loop?**
**Strings are immutable, so repeated concatenation can copy the accumulated string each time (quadratic). CPython's in-place optimization only works when nothing else references the string. `join` allocates once and copies each piece once.**

**What does the `=` specifier in an f-string do?**
**`f"{expr=}"` prints the expression text, an equals sign, and the value's repr, which is handy for debugging.**

**Why do two strings that look identical compare unequal?**
**They may use different Unicode sequences (precomposed vs combining characters). Normalize both with `unicodedata.normalize("NFC", ...)` (or NFKC plus `casefold` for identifiers) before comparing.**

**What is the difference between `strip("ab")` and `removeprefix("ab")`?**
**`strip` removes any of the given characters from both ends, as a set. `removeprefix` removes that exact prefix once.**

**When should you not use f-strings?**
**In logging calls (use lazy `%s` arguments), and for SQL, HTML or shell commands built from user input (use parameterized queries, escaping templates, or t-strings with a processing library).**

## Recap

- `str` is immutable Unicode code points; indexing, slicing and `len` count code points, not bytes or UTF-16 units.
- Encode `str` to `bytes` and decode back with an explicit encoding (UTF-8). Decode at the edges and work with `str` inside.
- Always pass `encoding="utf-8"` to `open()` until 3.15's UTF-8 default reaches all your environments.
- `bytes` indexing gives ints, `str(b)` gives the repr, and `bytes` and `str` never mix.
- f-strings support conversions, format specs, nested fields and `=` debugging; since 3.12 they accept any expression. t-strings (3.14) keep values separate for safe processing.
- Build strings with `join`, use raw strings for regexes, `translate` for character mapping, `casefold` and normalization for comparisons.
