Type hints are the closest thing Python has to TypeScript, but the relationship between the annotations and the running program is very different. In TypeScript, types are erased by the compiler before anything runs. In Python there is no compiler step: the annotations stay in your source, the interpreter stores them as ordinary objects, and then **ignores them**. Checking is done by a separate tool you run yourself.

<Callout type="info">
Snippets on this page were run with **CPython 3.14.6**. Checker output comes from **mypy 2.4.0** and **pyright 1.1.414** (installed from PyPI) run against the same files. Where the two checkers disagree, both are shown, because that disagreement is something you will meet in real projects.
</Callout>

## What type hints are

A type hint is an expression placed after a colon (for variables and parameters) or after `->` (for return values). Python evaluates it (or, since 3.14, stores a way to evaluate it later) and puts the result in the object's `__annotations__`. Nothing else happens. No check, no conversion, no error.

```python title="hints_are_ignored.py"
def add(a: int, b: int) -> int:
    return a + b

print(add(2, 3))
print(add("ab", "cd"))   # wrong types, runs anyway
print(add.__annotations__)
```

```text title="Output"
5
abcd
{'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

The second call violates every annotation and still works, because `+` works on strings. The annotations are just data hanging off the function.

So who uses them?

- **Static type checkers** (mypy, pyright, and newer ones such as Astral's `ty` and Meta's Pyrefly) read your source and report errors without running it, the same job `tsc --noEmit` does.
- **Editors** use them for completion, go-to-definition and inline errors. VS Code's Pylance is pyright inside.
- **Runtime libraries** read `__annotations__` on purpose: `dataclasses`, Pydantic, FastAPI, SQLAlchemy 2.0, Typer, msgspec. For them the annotation *is* the configuration. That is why Python annotations being real objects matters, and why the next page and the Pydantic page exist.

<Callout title="Coming from JS">
In TypeScript, `tsc` refuses to emit (or at least shouts) when types are wrong, and the types are erased from the output JavaScript. In Python there is no build step that can fail. Your app runs with type errors unless you put mypy or pyright in CI and make it fail the build. Also, annotations are *not* erased: a library can read them at runtime, which TypeScript can only fake with `reflect-metadata` and `emitDecoratorMetadata` (the NestJS trick). Python gives every library that power by default.
</Callout>

## Annotating variables, functions and return types

```python title="annotations_tour.py"
# variables
port: int = 8000
host: str = "localhost"
retries: int            # declaration with no value: legal, creates no variable

# functions
def connect(host: str, port: int = 5432, *, timeout: float = 5.0) -> bool:
    return True

# *args and **kwargs: annotate the type of EACH element, not the tuple/dict
def log(*messages: str, **fields: int) -> None:
    ...

# methods: self and cls are inferred, never annotate them
class Repo:
    def get(self, key: str) -> bytes | None:
        ...
```

Things worth knowing about how checkers treat these:

- **Inference.** You rarely need to annotate locals. `port = 8000` is inferred as `int`. Annotate function signatures and let inference handle the body, exactly like TypeScript.
- **`-> None`** is the equivalent of `: void`. A function with no `return` returns `None` at runtime.
- **Unannotated functions are a big difference between checkers.** mypy, by default, does not check the body of a function that has no annotations at all, and treats its return as `Any`. pyright infers return types from the body.

```python title="inference.py"
def f(x: int):
    return x * 2
reveal_type(f)

def g(x):
    return x * 2
reveal_type(g)
reveal_type(g(1))

counts = {}
counts["a"] = 1
reveal_type(counts)
```

```text title="mypy output"
inference.py:3: note: Revealed type is "def (x: int) -> Any"
inference.py:7: note: Revealed type is "def (x: Any) -> Any"
inference.py:8: note: Revealed type is "Any"
inference.py:12: note: Revealed type is "dict[str, int]"
```

```text title="pyright output"
inference.py:3:13 - information: Type of "f" is "(x: int) -> int"
inference.py:7:13 - information: Type of "g" is "(x: Unknown) -> Unknown"
inference.py:8:13 - information: Type of "g(1)" is "Literal[2]"
inference.py:12:13 - information: Type of "counts" is "dict[Unknown, Unknown]"
```

Two surprises. mypy does **not** infer the return type of `f` (it becomes `Any`), so always write the return annotation. And the two tools infer the empty dict differently: mypy looks at the next assignment, pyright gives up with `Unknown`. Writing `counts: dict[str, int] = {}` makes both agree.

## Built-in generics

Since Python 3.9 the built-in containers can be subscripted directly. You no longer need `typing.List`, `typing.Dict` and friends (they still work but are deprecated aliases).

```python
names: list[str] = []
scores: dict[str, int] = {}
point: tuple[float, float] = (1.0, 2.0)      # fixed length, two floats
row: tuple[int, ...] = (1, 2, 3)             # any length, all ints
unique: set[int] = set()
frozen: frozenset[str] = frozenset()
```

For parameters, prefer the **abstract** types in `collections.abc`, because they accept more callers and say what you actually need:

| You need | Annotate with | Accepts |
|---|---|---|
| to loop once | `Iterable[str]` | lists, tuples, sets, generators, dict keys |
| indexing and `len` without mutation | `Sequence[str]` | lists, tuples, `str`, `range` |
| a read-only mapping | `Mapping[str, int]` | `dict`, `OrderedDict`, `MappingProxyType` |
| to mutate | `list[str]` / `dict[str, int]` | only the concrete type |

Return concrete types and accept abstract ones. The advanced typing page explains the deeper reason (variance): `list[Dog]` is *not* a `list[Animal]`, but it is a `Sequence[Animal]`.

At runtime, `list[int]` is a real object (a `types.GenericAlias`), but it carries no checking power:

```python title="generic_alias_runtime.py"
print(list[int], type(list[int]), list[int]())
try:
    isinstance([1], list[int])
except TypeError as e:
    print("TypeError:", e)
```

```text title="Output"
list[int] <class 'types.GenericAlias'> []
TypeError: isinstance() argument 2 cannot be a parameterized generic
```

<Callout title="Coming from JS">
`tuple[float, float]` is TypeScript's `[number, number]`, and `tuple[int, ...]` is `number[]` used as an immutable array. The odd one is `str`: it is a `Sequence[str]` (iterating a string gives one-character strings), so a function typed `Sequence[str]` happily accepts `"abc"` as a sequence of letters. This is a classic bug source with no TypeScript equivalent.
</Callout>

## Optional, `X | None` and Union

`int | None` means "an int or None". `Optional[int]` is the older spelling of exactly the same thing, and `Union[int, str]` is the older spelling of `int | str`. Since 3.10 the `|` operator works at runtime too, so prefer it.

```python title="unions_runtime.py"
from typing import Optional, Union
print(Optional[int] == (int | None), Union[int, str] == (int | str))
print(int | None, type(int | None))
print(isinstance(3, int | str))
```

```text title="Output"
True True
int | None <class 'typing.Union'>
True
```

(In 3.14, `typing.Union` and the `types.UnionType` created by `|` became the same class, which is why the type prints as `typing.Union`.)

The checker forces you to handle the `None` branch before using the value, just like `strictNullChecks`:

```python title="narrowing.py"
def find_user(user_id: int) -> str | None:
    return "ada" if user_id == 1 else None

name = find_user(1)
print(name.upper())
if name is not None:
    reveal_type(name)
```

```text title="mypy output"
narrowing.py:5: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
narrowing.py:7: note: Revealed type is "str"
```

```text title="pyright output"
narrowing.py:5:12 - error: "upper" is not a known attribute of "None" (reportOptionalMemberAccess)
narrowing.py:7:17 - information: Type of "name" is "str"
```

Narrowing works with `is None` / `is not None`, `isinstance`, truthiness (`if name:`), `==` against literals, `match` statements, early `return`, and `assert`.

**Traps:**

- **`Optional` does not mean "optional argument".** `def f(x: Optional[int])` still requires `x` to be passed; it can just be `None`. An argument becomes optional because it has a *default*.
- **Implicit Optional is gone.** `def greet(name: str = None)` used to be accepted by mypy. It is now an error: `Incompatible default for parameter "name" (default has type "None", parameter has type "str")`. Write `name: str | None = None`.
- **Truthiness narrowing also drops falsy values.** `if count:` removes `None` but also `0`. When `0` is valid, use `if count is not None:`.

<Callout title="Coming from JS">
Python has one "nothing" value, `None`. There is no `undefined`, so there is no `?:` optional-property vs `| undefined` distinction on function parameters. A missing *dict key* is a different story, handled by `TypedDict` with `NotRequired` on the next page.
</Callout>

## `Any` vs `object`

Both accept any value. They are opposites in what they let you do afterwards.

- **`Any`** turns checking off. Every operation on it is allowed and its result is also `Any`. It is TypeScript's `any`.
- **`object`** is the top of the class hierarchy. Every value is an `object`, but you can only do what *every* object supports until you narrow it. It is TypeScript's `unknown`.

```python title="any_vs_object.py"
from typing import Any

def f(x: Any) -> None:
    x.whatever()        # allowed: Any switches checking off

def g(x: object) -> None:
    x.whatever()        # rejected: object has no such attribute
    if isinstance(x, str):
        print(x.upper())  # fine after narrowing
```

```text title="mypy output"
any_vs_object.py:7: error: "object" has no attribute "whatever"  [attr-defined]
```

Use `object` for "I accept anything and will inspect it". Use `Any` only as an escape hatch, for example around untyped libraries. `Any` spreads: `json.loads` returns `Any`, so a function that returns `json.loads(s)` while annotated `-> dict[str, int]` passes silently unless you turn on `warn_return_any` (included in `--strict`).

## `Callable`

`Callable[[ArgTypes...], ReturnType]` describes something you can call. Import it from `collections.abc`.

```python title="callable_demo.py"
from collections.abc import Callable

def apply(fn: Callable[[int, int], int], a: int, b: int) -> int:
    return fn(a, b)

apply(lambda x, y: x + y, 1, 2)
apply(len, 1, 2)
```

```text title="pyright output"
callable_demo.py:7:7 - error: Argument of type "(obj: Sized, /) -> int" cannot be assigned to parameter "fn" of type "(int, int) -> int" in function "apply"
    Type "(obj: Sized, /) -> int" is not assignable to type "(int, int) -> int"
      Function accepts too few positional parameters; expected 2 but received 1
```

Limits of `Callable`: it can only describe positional parameters. For keyword arguments, defaults or overloads, write a `Protocol` with a `__call__` method. `Callable[..., int]` means "any parameters, returns int". To keep a wrapped function's exact signature in a decorator, use `ParamSpec` (advanced typing page).

## Type aliases and the `type` statement

A type alias gives a name to a type expression. Python 3.12 added a dedicated statement for it (PEP 695):

```python title="aliases.py"
type UserId = int
type Pair[T] = tuple[T, T]
print(UserId, type(UserId).__name__)
print(UserId.__value__)
print(Pair[str], Pair.__type_params__)

type Bad = Undefined   # lazy: no error until __value__ is touched
print("Bad defined")
try:
    Bad.__value__
except NameError as e:
    print("NameError:", e)
```

```text title="Output"
UserId TypeAliasType
<class 'int'>
Pair[str] (T,)
Bad defined
NameError: name 'Undefined' is not defined
```

How it works: `type X = ...` creates a `typing.TypeAliasType` object whose value is evaluated **lazily**, the first time someone asks for `__value__`. That makes forward references and recursive aliases simple:

```python
type JSON = dict[str, JSON] | list[JSON] | str | int | float | bool | None
```

The older forms still exist: a plain assignment `UserId = int` (an "implicit" alias that checkers guess at) and `UserId: TypeAlias = int` (explicit, deprecated in favour of the `type` statement).

**Trap:** an alias is not a new type. `type UserId = int` lets you pass any `int` where a `UserId` is expected. If you want the checker to keep `UserId` and `OrderId` apart, you need `NewType` (advanced typing page). Also, `TypeAliasType` objects cannot be used with `isinstance`; at runtime they are just named boxes.

<Callout title="Coming from JS">
`type UserId = int` looks exactly like TypeScript's `type UserId = number` and behaves the same for checking: it is purely an alias with structural equality. The generic form `type Pair[T] = tuple[T, T]` mirrors `type Pair<T> = [T, T]`. Unlike TypeScript, the alias exists at runtime as an object with a name, which Pydantic and FastAPI can read.
</Callout>

## `Literal`

`Literal[...]` restricts a value to specific constants: strings, ints, bools, enum members, bytes, or `None`.

```python title="literal_final.py"
from typing import Final, Literal

type Method = Literal["GET", "POST"]

def request(method: Method, url: str) -> None: ...

request("GET", "/a")
request("PATCH", "/a")

m = "GET"
request(m, "/b")

MAX_RETRIES: Final = 3
MAX_RETRIES = 4
```

```text title="mypy output"
literal_final.py:8: error: Argument 1 to "request" has incompatible type "Literal['PATCH']"; expected "Literal['GET', 'POST']"  [arg-type]
literal_final.py:11: error: Argument 1 to "request" has incompatible type "str"; expected "Literal['GET', 'POST']"  [arg-type]
literal_final.py:14: error: Cannot assign to final name "MAX_RETRIES"  [misc]
```

```text title="pyright output"
literal_final.py:8:9 - error: Argument of type "Literal['PATCH']" cannot be assigned to parameter "method" of type "Method" in function "request"
literal_final.py:14:1 - error: "MAX_RETRIES" is declared as Final and cannot be reassigned (reportGeneralTypeIssues)
```

Look at line 11. mypy widens `m = "GET"` to `str` and rejects it. pyright remembers the narrowed literal type of `m` and accepts it. To make both happy, annotate `m: Method = "GET"` or mark it `Final`. Checkers do disagree on inference details like this, so pick one checker for CI and stick to it.

At runtime you can get the allowed values back with `typing.get_args(Method.__value__)` (or `get_args(Method)` for an old-style alias), which is handy for building validation or CLI choices. But nothing stops a wrong string at runtime unless you check it yourself or use Pydantic.

<Callout title="Coming from JS">
`Literal["GET", "POST"]` is the union-of-string-literals pattern `'GET' | 'POST'`. Python has no `as const`: a checker will not infer a tuple of literals from `("GET", "POST")`. Annotate with `Final` (for single values) or write the `Literal` type by hand. For a closed set used everywhere, an `enum.StrEnum` is often better because it also exists at runtime.
</Callout>

## `Final`

`Final` marks a name that must not be reassigned (like `const`), and in classes an attribute that must not be overridden or reassigned. With `Final = 3` and no explicit type, the checker infers `Literal[3]`. It is **only** a checker rule: at runtime `MAX_RETRIES = 4` runs fine. And like `const`, it does not freeze the object, so `ITEMS: Final = []` can still be appended to. Use `Final[tuple[str, ...]]` or `frozenset` when you want both.

There is also the `@final` decorator for classes that must not be subclassed and methods that must not be overridden.

## Running mypy and pyright

Install either into your project's dev dependencies:

```bash
uv add --dev mypy pyright      # or: pip install mypy pyright
mypy src/
pyright src/
```

pyright is written in TypeScript and the PyPI package downloads a Node.js runtime the first time it runs (or uses the one you have). mypy is pure Python with an optional compiled core.

### Strictness levels

| | mypy | pyright |
|---|---|---|
| Default | checks annotated functions only, skips the bodies of unannotated ones | `standard` mode: checks everything, infers a lot, stays quiet about missing annotations |
| Middle | add flags one by one: `disallow_untyped_defs`, `warn_return_any`, `no_implicit_reexport` | `basic` is looser than `standard`, `off` disables most rules |
| Strict | `strict = true` turns on a bundle of about a dozen flags | `typeCheckingMode = "strict"` also reports anything `Unknown` |
| Per file | `[[tool.mypy.overrides]]` by module pattern | `# pyright: strict` or `# pyright: basic` comment at the top of a file |
| Silence one line | `# type: ignore[error-code]` | `# pyright: ignore[ruleName]` (also honours `# type: ignore`) |

The same untyped function under default and strict mypy:

```python title="gradual.py"
def untyped(x):
    return x.nonexistent + 1

def typed(x: int) -> int:
    return untyped(x)
```

```text title="mypy output (default)"
Success: no issues found in 1 source file
```

```text title="mypy output (--strict)"
gradual.py:1: error: Function is missing a type annotation  [no-untyped-def]
gradual.py:5: error: Returning Any from function declared to return "int"  [no-any-return]
gradual.py:5: error: Call to untyped function "untyped" in typed context  [no-untyped-call]
Found 3 errors in 1 file (checked 1 source file)
```

Practical advice: start new projects in strict mode. Always write the error code in ignores (`# type: ignore[arg-type]`), and turn on `warn_unused_ignores` so stale ignores get flagged.

<Callout title="Coming from JS">
`strict = true` is roughly `"strict": true` in `tsconfig.json`, and `ignore_missing_imports` is like declaring `declare module 'x'`. Third-party types come from the package itself (marked with a `py.typed` file) or from separate **stub** packages such as `types-requests` and `types-PyYAML`, the equivalent of `@types/...`. mypy even prints the install hint: `Library stubs not installed for "yaml"` followed by `Hint: "python3 -m pip install types-PyYAML"`.
</Callout>

## Gradual typing

Python's type system is **gradual**: typed and untyped code live together, and `Any` sits at the boundary. `Any` is compatible with every type in both directions, so untyped code never causes errors in typed code. It just stops checking from flowing through. This is what lets a large codebase adopt types one module at a time.

The cost is that `Any` hides bugs. A checker that reports nothing on a codebase full of `Any` proves very little. Strict mode exists to find where `Any` leaks in: unannotated functions, untyped libraries, `json.loads`, `**kwargs` without types. pyright's strict mode is especially loud about this because it tracks implicit `Any` separately as `Unknown`.

## `reveal_type`

`reveal_type(expr)` asks the checker "what type do you think this is?". It is the fastest way to debug a confusing error. Checkers understand it without an import.

At runtime, though, a bare `reveal_type` is not a builtin and crashes with `NameError`. Since Python 3.11 you can import it from `typing`. It then prints the *runtime* type to stderr and returns its argument unchanged:

```python title="reveal_runtime.py"
from typing import reveal_type
x = reveal_type([1, 2])
print(x)
```

```text title="Output"
Runtime type is 'list'
[1, 2]
```

Remove it before committing. Checkers report every `reveal_type` as a note or information message.

## Annotations at runtime

### `__annotations__` and `get_type_hints`

Functions, classes and modules store annotations in `__annotations__`. Annotated class attributes without a value are *not* created as attributes. They only appear in `__annotations__`, which is exactly what dataclasses and Pydantic read:

```python title="class_annotations.py"
class User:
    id: int
    name: str = "anon"
print(User.__annotations__)
print("id" in User.__dict__, "name" in User.__dict__)

import inspect
def f(n: int) -> int: return n
print(inspect.signature(f))
```

```text title="Output"
{'id': <class 'int'>, 'name': <class 'str'>}
False True
(n: int) -> int
```

`typing.get_type_hints(obj)` goes further: it resolves string annotations into real objects, merges annotations from base classes for classes, and by default strips `Annotated` metadata (pass `include_extras=True` to keep it). Libraries use it rather than reading `__annotations__` directly.

### Deferred evaluation in Python 3.14 (PEP 649 and PEP 749)

Historically, annotations were evaluated eagerly when the `def` or `class` statement ran. That caused two problems:

1. **Forward references failed.** You could not use a class in an annotation above its definition, so people wrote string annotations like `"Config"`.
2. **Import-time cost.** Every annotation was evaluated even if nobody ever looked at it.

The workaround was `from __future__ import annotations` (PEP 563), which turns *every* annotation into a string. That fixed forward references but broke libraries that need real objects, since they had to `eval` the strings later, sometimes in the wrong scope.

Python 3.14 implements **PEP 649**, refined by **PEP 749**: annotations are now evaluated **lazily**. The compiler wraps them in a hidden function, `__annotate__`, and only calls it when someone accesses `__annotations__`. The result is cached.

```python title="deferred.py"
import annotationlib
from typing import get_type_hints

def make(cfg: Config) -> Config:   # Config is defined later
    return cfg

print("defined fine")
try:
    print(make.__annotations__)
except NameError as e:
    print("NameError:", e)

print(annotationlib.get_annotations(make, format=annotationlib.Format.FORWARDREF))
print(annotationlib.get_annotations(make, format=annotationlib.Format.STRING))

class Config:
    debug: bool = False

print(make.__annotations__)
print(get_type_hints(make))
print(make.__annotate__)
```

```text title="Output"
defined fine
NameError: name 'Config' is not defined
{'cfg': ForwardRef('Config', owner=<function make at 0x0000024792AC3D70>), 'return': ForwardRef('Config', owner=<function make at 0x0000024792AC3D70>)}
{'cfg': 'Config', 'return': 'Config'}
{'cfg': <class '__main__.Config'>, 'return': <class '__main__.Config'>}
{'cfg': <class '__main__.Config'>, 'return': <class '__main__.Config'>}
<function make.__annotate__ at 0x000002479255FAB0>
```

What this shows:

- Defining `make` with an undefined name **no longer fails**. On 3.13 and earlier the `def` line itself raised `NameError`.
- Accessing `__annotations__` too early still raises, because that evaluates the real values.
- The new **`annotationlib`** module lets tools ask for annotations in different *formats*: `Format.VALUE` (real objects, the default, may raise), `Format.FORWARDREF` (real objects where possible, `ForwardRef` placeholders for unresolved names) and `Format.STRING` (source-like strings).
- Once `Config` exists, plain access works.

What changes for you:

- **You can drop quotes around forward references** in code that targets 3.14+ only.
- **`from __future__ import annotations` keeps working** in 3.14 with its old stringifying behaviour. PEP 749 plans to deprecate it only after Python 3.13 reaches end of life, and to remove it at least two releases after that. New code targeting 3.14 does not need it. Code supporting older versions can keep it.
- **Library authors** should use `annotationlib.get_annotations()` (or `typing.get_type_hints()`) instead of reading `obj.__dict__["__annotations__"]`. That dict entry may not exist any more, because annotations live behind `__annotate__`.
- **Import cost drops**, because annotations nobody reads are never evaluated.

For comparison, here is the PEP 563 behaviour, which you will still see in many codebases:

```python title="future_annotations.py"
from __future__ import annotations
def f(a: int, b: list[str] | None = None) -> dict[str, int]: ...
print(f.__annotations__)
from typing import get_type_hints
print(get_type_hints(f))
```

```text title="Output"
{'a': 'int', 'b': 'list[str] | None', 'return': 'dict[str, int]'}
{'a': <class 'int'>, 'b': list[str] | None, 'return': dict[str, int]}
```

  E --> F["first access to __annotations__"]
  F --> G["evaluated once and cached"]
  D --> H["get_type_hints evals strings later"]
`} />

**Traps:**

- Under the old eager model, `x: SomeExpensiveCall()` ran at import time. Under 3.14 it runs on first access, possibly in a different context. Annotations should be plain type expressions, not side-effecting code.
- Code that creates a class and immediately inspects annotations of names defined later in the module still fails. Lazy evaluation delays the error, it does not remove it.

## When to use what

- **Annotate every function signature** and public attribute. Let inference do locals.
- Prefer `X | None` over `Optional[X]`, `list[int]` over `List[int]`, `collections.abc` abstract types for parameters.
- Use `object` (not `Any`) for "anything". Use `Any` only where you must, and keep it at the edges.
- Use `Literal` or `StrEnum` for closed sets of values, `Final` for constants, the `type` statement for aliases.
- Run one checker in strict mode in CI. pyright is faster and stricter by default and gives the best editor experience through Pylance. mypy has the larger plugin ecosystem (Django, Pydantic and SQLAlchemy plugins).
- Remember that none of this validates runtime data. HTTP bodies, env vars and JSON need Pydantic or similar.

## Interview questions

1. **Do type hints affect runtime behaviour?**
   **No. The interpreter stores them in `__annotations__` and ignores them. Only tools (mypy, pyright) and libraries that read them on purpose (dataclasses, Pydantic, FastAPI) give them meaning.**
2. **What is the difference between `Any` and `object`?**
   **`Any` disables checking in both directions (like TS `any`). `object` accepts every value but allows only operations valid for all objects until you narrow it (like TS `unknown`).**
3. **Does `Optional[int]` make a parameter optional?**
   **No. It means the value may be `None`. A parameter becomes optional only by having a default. Modern spelling is `int | None`.**
4. **Why prefer `Sequence[str]` over `list[str]` for a parameter?**
   **It accepts more inputs (tuples, other sequences), documents that you won't mutate, and is covariant, so a `list[SubType]` is accepted.**
5. **What changed about annotations in Python 3.14?**
   **PEP 649 and 749: annotations are evaluated lazily through a generated `__annotate__` function and cached on first access. Forward references no longer need quotes, `annotationlib` exposes VALUE, FORWARDREF and STRING formats, and `from __future__ import annotations` remains supported but is slated for eventual deprecation.**
6. **What does `reveal_type` do?**
   **It makes the checker report the inferred type of an expression. At runtime it needs `from typing import reveal_type` (3.11+) and prints the runtime type to stderr.**
7. **What is gradual typing?**
   **Typed and untyped code coexist, with `Any` as the compatible-with-everything boundary type, so a codebase can adopt types incrementally. Strict mode helps find where `Any` leaks in.**
8. **How is `type UserId = int` different from `NewType`?**
   **The `type` statement creates a transparent alias, so any `int` is accepted. `NewType` creates a distinct type for the checker, so a plain `int` or another `NewType` is rejected.**

## Recap

- Type hints are runtime data that the interpreter ignores. Checkers, editors and libraries give them meaning.
- Annotate signatures, let inference do the rest. Always annotate return types for mypy.
- Use built-in generics, `X | None`, abstract parameter types from `collections.abc`, `Callable` for simple function types.
- `Any` turns checking off, `object` is the safe top type.
- `type` aliases (3.12+) are lazy and generic-capable. `Literal` and `Final` cover TypeScript's literal unions and `const`.
- Configure mypy or pyright in `pyproject.toml`, go strict, and run it in CI. The checkers sometimes disagree.
- Python 3.14 evaluates annotations lazily. Use `annotationlib` or `get_type_hints` to read them, and drop forward-reference quotes when you target 3.14+.
