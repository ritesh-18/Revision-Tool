Python treats functions as values, and the standard library builds a toolbox on top of that: `sorted(key=...)`, `functools.partial`, `lru_cache`, `singledispatch` and the `operator` module. This page covers how each one works, where it goes wrong (`lru_cache` on methods is a real memory leak), and when to use it versus a plain loop or comprehension.

<Callout type="info">
  Snippets run on **CPython 3.14.6**. Timings are from one Windows laptop: compare the ratios, not the absolute numbers.
</Callout>

## Lambdas

### What a lambda is

`lambda params: expression` creates a function object, exactly like `def`, with three restrictions: it has no name (its `__name__` is `<lambda>`), its body is **one expression** whose value is returned, and it can't contain statements. It supports the full parameter syntax: defaults, `*args`, keyword-only, `**kwargs`.

```python
add = lambda a, b=10, *rest, **kw: a + b + sum(rest)
print(add(1), add(1, 2, 3, 4))
print(add.__name__)
print(type(add) is type(lambda: None))

def add_def(a, b=10, *rest, **kw):
    return a + b + sum(rest)
print(add_def.__name__)

classify = lambda n: "even" if n % 2 == 0 else "odd"   # expressions only
print(classify(7))
```

```text title="Output"
11 10
<lambda>
True
add_def
odd
```

There's no "lambda type": the compiler produces the same kind of code object and the same `MAKE_FUNCTION` instruction as for `def`. A lambda is just a `def` with less syntax and no name.

### The limits

```python
for src in ("lambda x: return x", "lambda x: y = x", "lambda x: (y := x * 2)"):
    try:
        compile(src, "<demo>", "eval")
        print("ok:         ", src)
    except SyntaxError as err:
        print("SyntaxError:", src)
```

```text title="Output"
SyntaxError: lambda x: return x
SyntaxError: lambda x: y = x
ok:          lambda x: (y := x * 2)
```

- No statements: no `return`, `=`, `if` blocks, `try`, `for` loops, `with` or `raise` (a conditional **expression** `a if c else b` and `:=` are fine, being expressions).
- No type annotations on parameters.
- The anonymous name hurts debugging. A traceback shows `in <lambda>` rather than a useful name:

```python
import traceback
parse = lambda s: int(s)
try:
    parse("abc")
except ValueError:
    for line in traceback.format_exc().splitlines():
        if "line" in line and "File" in line:
            print(line.split(", ", 1)[1])
```

```text title="Output"
line 5, in <module>
line 3, in <lambda>
```

**When to use one:** short, throwaway functions passed **inline** as an argument, like `key=lambda u: u.age`. PEP 8 says not to assign a lambda to a name (`f = lambda x: ...`). Use `def`, which gives it a real name for tracebacks and lets you add a docstring and annotations.

<Callout title="Coming from JS">
  Arrow functions are the everyday way to write functions in JS: multi-line bodies with braces, `async` arrows, and lexical `this`. Python lambdas are deliberately weaker: **one expression only**, no `async lambda`, no statements. There's no `this` to worry about, since Python passes `self` explicitly. So the habit of writing `const handler = (req) => { ... }` becomes a `def` in Python, and lambdas stay small and inline.
</Callout>

## `map` and `filter` versus comprehensions

`map(fn, iterable)` and `filter(pred, iterable)` return **lazy iterators**, not lists. They compute each item on demand and can be consumed **only once**.

```python
nums = [1, 2, 3, 4, 5]
squares = map(lambda n: n * n, nums)
print(type(squares).__name__)
print(list(squares))
print(list(squares))                 # iterator already consumed

print(list(filter(lambda n: n % 2, nums)))
print(list(filter(None, [0, 1, "", "a", None, [], [0]])))   # None means "truthy"
print(list(map(str.upper, ["get", "post"])))
print(list(map(pow, [2, 3, 4], [5, 2])))                   # stops at shortest input

print([n * n for n in nums if n % 2])                       # the comprehension version
```

```text title="Output"
map
[1, 4, 9, 16, 25]
[]
[1, 3, 5]
[1, 'a', [0]]
['GET', 'POST']
[32, 9]
[1, 9, 25]
```

The empty second `list(squares)` is the trap: an exhausted iterator silently yields nothing, so a value passed through two loops looks "empty" the second time.

Which is faster? It depends on whether a Python-level function call is involved:

```python
import timeit
setup = "nums = list(range(1000))"
tests = {
    "map(str, nums)": "list(map(str, nums))",
    "[str(n) for n in nums]": "[str(n) for n in nums]",
    "map(lambda n: n * 2, nums)": "list(map(lambda n: n * 2, nums))",
    "[n * 2 for n in nums]": "[n * 2 for n in nums]",
}
for label, stmt in tests.items():
    t = min(timeit.repeat(stmt, setup, number=2000, repeat=5))
    print(f"{label:28} {t * 1000 / 2000:.3f} ms per run")
```

```text title="Output"
map(str, nums)               0.056 ms per run
[str(n) for n in nums]       0.072 ms per run
map(lambda n: n * 2, nums)   0.070 ms per run
[n * 2 for n in nums]        0.034 ms per run
```

- `map` with a **built-in** function (`str`, `int`, `str.upper`) is slightly faster, since the loop stays in C.
- `map` with a **lambda** is slower than the comprehension, because each item pays for a Python function call while the comprehension evaluates `n * 2` inline.

**Rule of thumb:** use a comprehension by default (it's more readable and handles map and filter in one expression). Use `map` when you already have a named function, especially a built-in. Use a generator expression `(f(x) for x in xs)` when you want laziness.

<Callout title="Coming from JS">
  `arr.map()` and `arr.filter()` in JS are **eager** array methods that return new arrays and chain left to right. Python's `map` and `filter` are **lazy** global functions that nest inside out and return one-shot iterators. Chained JS like `users.filter(u => u.active).map(u => u.email)` is written as `[u.email for u in users if u.active]` in Python.
</Callout>

## Sorting with `key`

`sorted(iterable, key=fn)` returns a new list. `list.sort(key=fn)` sorts in place and returns `None`. `min`, `max`, `heapq.nsmallest` and `itertools.groupby` take the same `key`.

```python
users = [
    {"name": "ana", "age": 31},
    {"name": "Bob", "age": 25},
    {"name": "cy", "age": 31},
]
print([u["name"] for u in sorted(users, key=lambda u: u["age"])])
print([u["name"] for u in sorted(users, key=lambda u: (-u["age"], u["name"].lower()))])
print(sorted(["banana", "Apple", "cherry"]))
print(sorted(["banana", "Apple", "cherry"], key=str.lower))
print(max(users, key=lambda u: u["age"])["name"])     # first max wins
```

```text title="Output"
['Bob', 'ana', 'cy']
['ana', 'cy', 'Bob']
['Apple', 'banana', 'cherry']
['Apple', 'banana', 'cherry']
ana
```

How it works:

- **The key is computed once per element**, then the sort compares keys (the old "decorate, sort, undecorate" pattern, built in). So an expensive key is fine:

```python
calls = 0
def key(s):
    global calls
    calls += 1
    return len(s)

words = ["pear", "fig", "banana", "kiwi", "apple"] * 200
sorted(words, key=key)
print(len(words), "items,", calls, "key calls")
```

```text title="Output"
1000 items, 1000 key calls
```

- **Tuples compare element by element**, so returning a tuple gives you multi-field sorting. Negate a number for descending on that field only.
- **The sort is stable** (Timsort, and since 3.11 Powersort for merging runs). Items with equal keys keep their original order, so you can sort in several passes, least significant key first:

```python
from operator import itemgetter
rows = [("ana", "eng", 31), ("bob", "ops", 25), ("cy", "eng", 25), ("dee", "ops", 31)]
by_age = sorted(rows, key=itemgetter(2))
by_team_then_age = sorted(by_age, key=itemgetter(1))   # stable: age order kept within team
print(by_team_then_age)
```

```text title="Output"
[('cy', 'eng', 25), ('ana', 'eng', 31), ('bob', 'ops', 25), ('dee', 'ops', 31)]
```

- If you have an old-style comparator (returns negative, zero or positive), wrap it with `functools.cmp_to_key`:

```python
from functools import cmp_to_key
def compare_versions(a, b):
    pa, pb = [int(x) for x in a.split(".")], [int(x) for x in b.split(".")]
    return (pa > pb) - (pa < pb)
print(sorted(["1.10.0", "1.2.0", "1.9.3"]))
print(sorted(["1.10.0", "1.2.0", "1.9.3"], key=cmp_to_key(compare_versions)))
```

```text title="Output"
['1.10.0', '1.2.0', '1.9.3']
['1.2.0', '1.9.3', '1.10.0']
```

(A key function is simpler here: `key=lambda v: tuple(map(int, v.split(".")))`.)

<Callout title="Coming from JS">
  JS `arr.sort((a, b) => a.age - b.age)` takes a **comparator** and sorts **in place**, and without one it compares as strings (`[10, 9, 1].sort()` gives `[1, 10, 9]`). Python 3 has no comparator argument at all: you pass a **key** function, and default sorting compares the real values (mixing `int` and `str` raises `TypeError` instead of guessing).
</Callout>

## `functools.partial`

`partial(fn, *args, **kwargs)` returns a callable with some arguments pre-filled. It's a C-implemented object storing `func`, `args` and `keywords`. Calling it calls `func(*args, *new_args, **{**keywords, **new_kwargs})`.

```python
from functools import partial

def power(base, exp):
    return base ** exp

square = partial(power, exp=2)
print(square(5))
print(square.func.__name__, square.args, square.keywords)
print(square(5, exp=3))           # keyword can be overridden at call time
try:
    square(5, 3)                  # 3 fills 'exp' positionally AND exp=2 is passed
except TypeError as err:
    print("TypeError:", err)

int_from_hex = partial(int, base=16)
print(int_from_hex("ff"))
```

```text title="Output"
25
power () {'exp': 2}
125
TypeError: power() got multiple values for argument 'exp'
255
```

New in 3.14: `functools.Placeholder` lets you leave a positional slot open, so you can pre-fill arguments that come **after** it:

```python
from functools import partial, Placeholder

def clamp(value, low, high):
    return max(low, min(value, high))

to_percent = partial(clamp, Placeholder, 0, 100)   # leave the 1st slot open (3.14+)
print(to_percent(150), to_percent(-5), to_percent(42))
```

```text title="Output"
100 0 42
```

Why `partial` over a lambda: it binds values **eagerly** (no late-binding bug in loops), it's introspectable (`.func`, `.args`), and it pickles if the wrapped function does, which matters when sending work to `multiprocessing` or `ProcessPoolExecutor`. Lambdas can't be pickled. Typical uses: callbacks for `loop.run_in_executor`, `sorted(key=partial(distance, origin))`, and configuring a function once at startup.

## `functools.reduce`

`reduce(fn, iterable, initial)` folds a sequence into one value: `fn(fn(fn(initial, x0), x1), x2)`.

```python
from functools import reduce
import operator

print(reduce(operator.add, [1, 2, 3, 4]))           # ((1 + 2) + 3) + 4
print(reduce(operator.mul, [1, 2, 3, 4], 10))       # initial value comes first
print(reduce(lambda acc, w: acc | {w: len(w)}, ["go", "rust"], {}))
try:
    reduce(operator.add, [])
except TypeError as err:
    print("TypeError:", err)
print(sum([1, 2, 3, 4]), max([3, 9, 2]))            # usually clearer
```

```text title="Output"
10
240
{'go': 2, 'rust': 4}
TypeError: reduce() of empty iterable with no initial value
10 9
```

`reduce` was moved out of builtins in Python 3 because Guido found most uses harder to read than a loop. Prefer `sum`, `max`, `min`, `any`, `all`, `math.prod`, `"".join` or a plain `for` loop. Always pass an initial value if the input can be empty. Since 3.14, `initial` can be passed as a keyword.

<Callout title="Coming from JS">
  `arr.reduce((acc, x) => ..., init)` is the same idea, with arguments in a different order: Python takes `reduce(fn, iterable, initial)`. JS developers reach for `reduce` much more often. In Python it's idiomatic to use a loop or a builtin instead.
</Callout>

## `lru_cache` and `cache`

### What they do

`@lru_cache(maxsize=128)` memoises a function: it stores results keyed by the arguments and returns the stored result on a repeat call. When the cache is full, the **least recently used** entry is evicted. `@cache` (3.9+) is shorthand for `lru_cache(maxsize=None)`: unbounded, no eviction, slightly faster.

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(80))
print(fib.cache_info())
print(fib(80))
print(fib.cache_info())
fib.cache_clear()
print(fib.cache_info())
print(fib.__wrapped__(10))   # the original, uncached function
```

```text title="Output"
23416728348467685
CacheInfo(hits=78, misses=81, maxsize=128, currsize=81)
23416728348467685
CacheInfo(hits=79, misses=81, maxsize=128, currsize=81)
CacheInfo(hits=0, misses=0, maxsize=128, currsize=0)
55
```

Without the cache, `fib(80)` would take on the order of 10^16 calls. With it, each `n` is computed once (81 misses).

### How it works

The C implementation keeps a **dict** from a key to a node in a **circular doubly linked list**:

- The **key** is built from the positional arguments, then a marker, then the keyword arguments as name/value pairs, in the order given. With `typed=True` the argument types are added too.
- On a **hit**, the node is moved to the front of the list (most recently used) and its result is returned. That's a dict lookup plus a few pointer swaps.
- On a **miss**, the function is called, and the result is stored at the front. If the cache is over `maxsize`, the node at the back (least recently used) is removed.

```python
from functools import lru_cache

@lru_cache(maxsize=2)
def load(key):
    print(f"  loading {key}")
    return key.upper()

load("a"); load("b"); load("a")   # 'a' becomes most recently used
load("c")                          # evicts 'b' (least recently used)
load("a"); load("b")               # 'a' is a hit, 'b' must reload
print(load.cache_info())
```

```text title="Output"
  loading a
  loading b
  loading c
  loading b
CacheInfo(hits=2, misses=4, maxsize=2, currsize=2)
```

### Traps

```python
from functools import lru_cache

@lru_cache
def area(w, h):
    return w * h

area(2, 3); area(w=2, h=3); area(h=3, w=2); area(2.0, 3)
print(area.cache_info())     # four calls, how many misses?

try:
    area([2], 3)
except TypeError as err:
    print("TypeError:", err)

@lru_cache
def get_tags(post_id):
    return ["python"]

tags = get_tags(1)
tags.append("hacked")        # mutates the cached object
print(get_tags(1))
```

```text title="Output"
CacheInfo(hits=1, misses=3, maxsize=128, currsize=3)
TypeError: unhashable type: 'list'
['python', 'hacked']
```

1. **Call style matters.** `area(2, 3)`, `area(w=2, h=3)` and `area(h=3, w=2)` are three different keys. `area(2.0, 3)` *hit* the `area(2, 3)` entry because `2 == 2.0` and they hash the same (use `typed=True` to separate them).
2. **Arguments must be hashable.** Lists, dicts and sets raise `TypeError`. Convert to tuples or `frozenset` first.
3. **Cached results are shared objects.** Return immutable values (tuples, frozen dataclasses), or callers will corrupt each other's results, as `get_tags` shows.
4. **Unbounded memory.** `@cache` and `maxsize=None` never evict. Keyed on something like user input or request IDs, it grows forever in a long-running server:

```python
from functools import cache

@cache                        # same as lru_cache(maxsize=None)
def slug(s):
    return s.lower().replace(" ", "-")

for i in range(100_000):
    slug(f"Post Title {i}")
print(slug.cache_info())
print(slug.cache_parameters())
```

```text title="Output"
CacheInfo(hits=0, misses=100000, maxsize=None, currsize=100000)
{'maxsize': None, 'typed': False}
```

That's 100,000 entries and zero hits: all cost, no benefit. Use `@cache` only for a small, bounded set of inputs (config parsing, a regex per pattern name). Otherwise set a `maxsize` and watch `cache_info()` hit rates in your metrics.

5. **No expiry.** There's no TTL. For data that changes (feature flags, prices), use a TTL cache (`cachetools.TTLCache`, or Redis across processes). The [decorators page](/docs/python/decorators) builds a small one.
6. **Per process.** With Gunicorn or Uvicorn workers, every worker has its own cache.
7. **Thread safety.** The cache's internal structure is safe to use from several threads, but two threads missing the same key at the same time will **both** call the function. Don't rely on it to run something exactly once.

### Caching methods correctly

Putting `@lru_cache` on a method is a common, quiet memory leak. `self` is part of the cache key, so the cache (which lives on the **class**, shared by all instances) holds a strong reference to every instance that ever called it:

```python
import gc, weakref
from functools import lru_cache

class PriceService:
    def __init__(self, region):
        self.region = region
    @lru_cache(maxsize=None)
    def price(self, sku):
        return f"{self.region}:{sku}"

svc = PriceService("eu")
svc.price("A1")
ref = weakref.ref(svc)
del svc
gc.collect()
print("instance still alive:", ref() is not None)
print(PriceService.price.cache_info())
PriceService.price.cache_clear()
gc.collect()
print("after cache_clear:", ref() is not None)
```

```text title="Output"
instance still alive: True
CacheInfo(hits=0, misses=1, maxsize=None, currsize=1)
after cache_clear: False
```

In a server that creates a service object per request, that's one leaked object (and everything it references) per request. It also requires instances to be hashable, and the cache is shared across instances. Ruff rule `B019` flags it.

Fixes, depending on what you need:

- **Value depends only on the instance, no arguments**: use `@cached_property` (next section).
- **Per-instance cache with arguments**: build the cache in `__init__`, so it lives and dies with the instance:

```python
import gc, weakref
from functools import lru_cache

class PriceService:
    def __init__(self, region):
        self.region = region
        # per-instance cache: dies with the instance
        self.price = lru_cache(maxsize=256)(self._price)
    def _price(self, sku):
        return f"{self.region}:{sku}"

svc = PriceService("eu")
svc.price("A1"); svc.price("A1")
print(svc.price.cache_info())
ref = weakref.ref(svc)
del svc
gc.collect()                      # the bound-method cycle needs the cyclic GC
print("instance still alive:", ref() is not None)
```

```text title="Output"
CacheInfo(hits=1, misses=1, maxsize=256, currsize=1)
instance still alive: False
```

- **Value doesn't depend on the instance**: make it a module-level function or a `@staticmethod` and cache that, keyed only by the real inputs.

## `cached_property`

`@cached_property` computes a value on first access and stores it in the **instance `__dict__`** under the same name. Because it's a non-data descriptor (it defines `__get__` but not `__set__`), the instance dict wins on later lookups, so subsequent accesses are plain attribute reads with no function call at all.

```python
from functools import cached_property

class Report:
    def __init__(self, rows):
        self.rows = rows
    @cached_property
    def total(self):
        print("  computing total")
        return sum(self.rows)

r = Report([1, 2, 3])
print(r.total)
print(r.total)
print(r.__dict__)
r.rows.append(4)
print(r.total)          # stale: it was cached
del r.total             # invalidate
print(r.total)
```

```text title="Output"
  computing total
6
6
{'rows': [1, 2, 3], 'total': 6}
6
  computing total
10
```

Traps:

- **Staleness.** It never recomputes on its own. `del obj.attr` invalidates it.
- **Needs a `__dict__`.** It fails on classes with `__slots__` (and no `__dict__` slot):

```python
from functools import cached_property

class Point:
    __slots__ = ("x",)
    def __init__(self, x):
        self.x = x
    @cached_property
    def double(self):
        return self.x * 2

try:
    Point(2).double
except TypeError as err:
    print("TypeError:", err)
```

```text title="Output"
TypeError: No '__dict__' attribute on 'Point' instance to cache 'double' property.
```

- **No locking since 3.12.** Before 3.12 it had an internal lock that serialised access across **all** instances. That lock was removed, so two threads can compute the value at the same time. Add your own lock if computing twice is unsafe.
- Since the value lives on the instance, it's freed with the instance: no leak, unlike `lru_cache` on a method.

<Callout title="Coming from JS">
  The JS equivalent is a lazy getter that redefines itself: `get total() { const v = compute(); Object.defineProperty(this, "total", { value: v }); return v; }`. Python's `cached_property` does exactly that, using the descriptor protocol (see [descriptors](/docs/python/descriptors-and-metaclasses)).
</Callout>

## `wraps`

`functools.wraps(fn)` is a decorator for **your wrapper function**. It copies `__name__`, `__qualname__`, `__doc__`, `__module__`, `__annotations__` (and others) from `fn` onto the wrapper, merges `__dict__`, and sets `wrapper.__wrapped__ = fn`. Without it, every decorated function shows up as `wrapper` in logs, tracebacks, `help()` and framework introspection. Full treatment on the [decorators page](/docs/python/decorators).

## `singledispatch`

`@singledispatch` turns a function into a **generic function** that picks an implementation based on the **type of the first argument**. It's how you extend behaviour for types you don't own, without an `isinstance` ladder.

```python
from functools import singledispatch
from datetime import date
from decimal import Decimal

@singledispatch
def to_json(obj):
    raise TypeError(f"cannot serialise {type(obj).__name__}")

@to_json.register
def _(obj: date):
    return obj.isoformat()

@to_json.register
def _(obj: Decimal):
    return str(obj)

@to_json.register(list)
@to_json.register(tuple)
def _(obj):
    return [to_json(x) for x in obj]

@to_json.register
def _(obj: int | float):           # union types work since 3.11
    return obj

print(to_json(date(2026, 10, 13)))
print(to_json([Decimal("9.99"), 3, (1.5, date(2026, 1, 1))]))
print(to_json(True))               # bool is a subclass of int -> int handler
try:
    to_json({1, 2})
except TypeError as err:
    print("TypeError:", err)
```

```text title="Output"
2026-10-13
['9.99', 3, [1.5, '2026-01-01']]
True
TypeError: cannot serialise set
```

How it works: `register` stores implementations in a `registry` dict keyed by type. On a call, it looks at `type(args[0])` and walks that type's **MRO** to find the most specific registered class (`bool` has no entry, so it falls back to `int`). The result is cached per type, and the cache is cleared when you register something new. Abstract base classes work too, so you can register for `collections.abc.Mapping`.

For methods, use `functools.singledispatchmethod`, which dispatches on the first argument **after** `self`:

```python
from functools import singledispatchmethod

class Formatter:
    @singledispatchmethod
    def fmt(self, value):
        return repr(value)
    @fmt.register
    def _(self, value: float):
        return f"{value:.2f}"
    @fmt.register
    def _(self, value: list):
        return ", ".join(self.fmt(v) for v in value)

print(Formatter().fmt([1.23456, "x", 2.0]))
```

```text title="Output"
1.23, 'x', 2.00
```

Limits: it dispatches on **one** argument only, by **type**, not by value. For dispatching on several arguments you'd need a library like `plum` or `multipledispatch`, or `match` statements.

## `total_ordering`

Define `__eq__` plus **one** of `__lt__`, `__le__`, `__gt__` or `__ge__`, and `@total_ordering` fills in the other comparisons:

```python
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, text):
        self.parts = tuple(int(p) for p in text.split("."))
    def __eq__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts == other.parts
    def __lt__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts < other.parts
    def __repr__(self):
        return "Version(" + ".".join(map(str, self.parts)) + ")"

a, b = Version("1.10.0"), Version("1.9.3")
print(a > b, a >= b, a <= b, a != b)
print(sorted([a, b, Version("1.2")]))
print(Version.__ge__.__qualname__)
```

```text title="Output"
True True False True
[Version(1.2), Version(1.9.3), Version(1.10.0)]
_ge_from_lt
```

The last line shows what happened: the decorator inserted a generated `__ge__` built from your `__lt__` (as "not less than"). The generated methods add an extra Python call per comparison, so for hot paths, or simply less code, a `@dataclass(order=True)` is often the better choice. Return `NotImplemented` (not `False`) for foreign types, so Python can try the other operand's method.

## The `operator` module

`operator` exposes Python's operators and lookups as C-implemented functions: `operator.add`, `operator.mul`, `operator.not_`, plus three factories that are perfect for `key=`:

```python
from operator import itemgetter, attrgetter, methodcaller
from types import SimpleNamespace as NS

rows = [("ana", 31, "eng"), ("bob", 25, "ops")]
print(sorted(rows, key=itemgetter(1)))
pick = itemgetter(0, 2)
print(pick(rows[0]))                         # several keys -> tuple
print(itemgetter("id")({"id": 7, "x": 1}))

users = [NS(name="ana", profile=NS(city="Pune")), NS(name="bob", profile=NS(city="Agra"))]
print([u.name for u in sorted(users, key=attrgetter("profile.city"))])
print(list(map(methodcaller("strip", "-"), ["-a-", "--b"])))
print(itemgetter(1))
```

```text title="Output"
[('bob', 25, 'ops'), ('ana', 31, 'eng')]
('ana', 'eng')
7
['bob', 'ana']
['a', 'b']
operator.itemgetter(1)
```

- `itemgetter(k)` is `lambda x: x[k]`. With several keys it returns a tuple, handy for multi-field sorts.
- `attrgetter("a.b")` is `lambda x: x.a.b` and supports dotted paths.
- `methodcaller("m", *args)` is `lambda x: x.m(*args)`.

They are faster than the equivalent lambdas, since there's no Python frame per call, and they have a readable `repr` and can be pickled:

```python
import timeit
setup = "from operator import itemgetter; rows = [(i, -i) for i in range(1000)]; ig = itemgetter(1)"
for label, stmt in {"key=lambda r: r[1]": "sorted(rows, key=lambda r: r[1])",
                    "key=itemgetter(1)": "sorted(rows, key=ig)"}.items():
    t = min(timeit.repeat(stmt, setup, number=2000, repeat=5))
    print(f"{label:20} {t * 1000 / 2000:.3f} ms per sort")
```

```text title="Output"
key=lambda r: r[1]   0.055 ms per sort
key=itemgetter(1)    0.010 ms per sort
```

(The input here is already in reverse order, so Timsort does almost no comparing and the key calls dominate. On random data the gap is smaller.)

## Interview questions

1. **What's the difference between a lambda and a `def` function?**
   **None at the object level: both are function objects. A lambda is limited to one expression, has no name (`<lambda>`), and can't hold statements or annotations.**

2. **`map` or a list comprehension?**
   **Comprehension by default for readability. `map` with a built-in function can be slightly faster, and `map` with a lambda is usually slower. Both `map` and `filter` return lazy one-shot iterators.**

3. **How does `sorted(key=...)` work, and is it stable?**
   **The key is computed once per element and the keys are compared. It's stable, so multi-pass sorts and tuple keys give multi-field ordering.**

4. **Why is `@lru_cache` on a method a problem?**
   **The cache lives on the class and keeps `self` in its keys, so it holds a strong reference to every instance (a leak), requires hashable instances, and is shared across instances. Use `cached_property` or a per-instance cache.**

5. **What's the danger of `@cache` in a web server?**
   **It never evicts, so a cache keyed on unbounded inputs grows forever. It's also per process, has no TTL, and returns shared mutable objects.**

6. **How does `cached_property` avoid calling the function again?**
   **It's a non-data descriptor that writes the result into the instance `__dict__` under the same name, and the instance dict takes priority on later lookups.**

7. **How does `singledispatch` pick an implementation?**
   **By the type of the first argument, walking its MRO to the most specific registered type. The result is cached per type.**

8. **Why prefer `partial` over a lambda in a loop or with multiprocessing?**
   **`partial` binds values eagerly (no late binding), is introspectable, and is picklable, while lambdas aren't picklable.**

## Recap

- Lambdas are single-expression anonymous functions. Use them inline as arguments, and use `def` for anything named.
- `map` and `filter` are lazy and one-shot. Comprehensions are the default choice.
- Sorting uses a key function computed once per element. It's stable, and tuples give multi-field order.
- `partial` pre-fills arguments (with `Placeholder` since 3.14). `reduce` is usually better written as a builtin or a loop.
- `lru_cache` is a dict plus an LRU linked list. Watch key style, hashability, shared results, unbounded growth, and never put it on methods.
- `cached_property` stores the result in the instance dict, has no lock since 3.12, and doesn't work with `__slots__`.
- `singledispatch` dispatches on the first argument's type, and `total_ordering` derives comparisons from `__eq__` plus one ordering method.
- `itemgetter`, `attrgetter` and `methodcaller` are faster, picklable replacements for small lambdas.
